English

Start with one DB allocation loop, distinguish room-type pools, assigned room-nights, and a flash-sale SKU, and explain all three nights or none.

Trace a hold through creation, confirmation, and release; explain why unknown commit cannot be blindly restocked and how to rebuild after Redis loses state.

先约定什么算成功，再分配处理预算Define success and budgets

先说清资源怎样标识，以及哪一步才算成功。酒店的所有入住夜放在同一笔数据库事务中；确认和释放只能处理本 hold 拥有的预占。秒杀流量超过预算时，再加 Redis 控制准入，库存仍由数据库终审。提交结果未知，就沿用同一请求身份核对；重建时，先停写、切换 epoch，再取快照。

本章设计有限库存的预占、确认和归还，默认只有一个地域，相关记录在同一数据库中，也不允许技术层自行超售。搜索、定价和支付账本暂不展开。Ch18 负责核验收款，并保留退款或人工核对的责任；发给库存服务的确认命令，必须绑定已经验证的 owner、order_id 和 hold_id。仅凭 webhook 中一个“支付成功”字段，不能授权确认库存。

Define resource keys and success first. Put all hotel nights in one DB transaction; confirm or release only the hold that owns them. Add Redis admission only when scale exceeds the budget, retaining DB adjudication. Resolve unknown commit through the same request identity. Recover by pausing writes, advancing epoch, and snapshotting.

This chapter owns finite-stock holds, confirmation, and restoration: one region, one DB, no implicit overbooking. Search, pricing, and payment ledgers stay outside. Ch18 validates funds and retains refund/review obligations. A confirmation command must bind the verified owner, order_id, and hold_id; a webhook field alone cannot authorize confirmation.

中文

酒店的平均入住速率要分步计算：5,000×200=1,000,000 间房，乘以 70% 入住率，得到每天 700,000 个已住房晚；再除以平均 3 晚，得到每天约 233,333 次入住，最后除以 86,400，约为每秒 2.70 次。这是稳态下的简化，不含取消、尝试预占和流量尖峰。库存行数则是 5,000×10×365=18,250,000。一晚的最后一间房仍可能同时迎来数百个请求，所以全站日均流量不能用来确定热点库存行的预算。

秒杀先比较流量和预算：2,000÷800=2.5，说明入口限流后，请求量仍是数据库库存事务预算的 2.5 倍。本例把创建限制在 500 次/秒，再加上确认 200 次/秒、释放 50 次/秒，合计 750 次/秒。恢复时会暂停销售，不能假定恢复作业可以免费塞进剩余的 50 次/秒。按 Little’s Law，500×0.020=10 只能帮助估计平均在途请求数；慢请求会更久地占用连接，因此连接池仍需硬上限。如果没有这些超预算的依据，数据库条件扣减配合入口限流可能已经够用，可以先不加 Redis。

English

Compute the hotel mean fully: 5,000×200=1,000,000 rooms, ×70%=700,000 occupied room-nights/day, ÷3 nights=233,333 stays/day, ÷86,400≈2.70/s. This steady-state simplification excludes cancellations, attempted holds, and peaks. Night rows are 5,000×10×365=18,250,000, not national rooms times daily requests. Hundreds of requests may still contend for the last room; a global mean does not size a hot row.

For the sale, 2,000÷800=2.5: even rate-limited ingress exceeds the inventory-TX budget. Admit only 500 creates/s; 200 confirms/s and 50 releases/s bring the total to 750/s. Sales pause during recovery, so its work is not assumed to fit freely in the remaining 50/s. 500×0.020=10 mean in-flight is the arithmetic intuition of Little’s Law; slow requests hold connections longer, so a hard pool limit still applies. Without this budget evidence, DB conditional allocation plus ingress limiting may already suffice and Redis can be omitted.

1 · 先确定资源、库存权威和请求身份1 · Resource model, authority, and request identity

库存是否可占，以主数据库（Primary）为准；读缓存（Read Cache）只提供展示提示。 下面先走通一次数据库预占，再加入重试身份，区分房型池和指定房晚。最后看一个反例：即使缓存多报了一间，数据库仍会拒绝超出容量的请求。

Primary owns stock; Read Cache supplies display hints. In frame 5 the DB rejects despite an optimistic cache. Frame 2 supplies retry identity; frame 3 separates interchangeable capacity from assigned resources.

酒店日期按当地营业日期处理，入住范围采用半开区间 [入住日,退房日)。房型池连续三夜都有余量，只能保证每夜有这种房型，未必能让客人三夜住同一间。如果承诺全程同房，就要先选出三夜都可用的物理房间，再在同一事务中占用它的三条房晚。指定房间可以单设活跃占用表 occupancy，用唯一键防止重复预订；释放时只删除本 hold 的占用，历史记录另行保存。超售必须由业务明确允许，本章始终采用 cap=total。

计数行保存 free,reserved,confirmed,cap，分别表示可用、预占、已确认和容量，全部设为 NOT NULL。CHECK 约束保证各项非负，并满足 free+reserved+confirmed=cap，但不能核验另一张表中的占用归属 [2]。创建时执行 UPDATE ... WHERE free>=q，并检查影响行数。在 PostgreSQL 18（PG18）的 Read Committed 隔离级别下，竞争更新等待结束后，会对最新行重新检查 WHERE 条件 [1]。因此，这个单行模式不必先由应用读取 version；涉及多夜时，仍要用下一节的事务保证全部成功或全部撤销。

Use local business dates [check-in,check-out). Spare capacity on three type-nights does not guarantee the same physical room throughout. A same-room promise requires choosing one compatible room and allocating all its nights in one transaction. Assigned rooms can use a separate active occupancy table with uniqueness, deleting only this hold’s occupancy on release while retaining history elsewhere. Overbooking needs explicit business policy; here cap=total.

Counted rows store NOT NULL free,reserved,confirmed,cap, with nonnegative CHECK constraints and free+reserved+confirmed=cap. CHECK cannot validate ownership in another table [2]. A guarded UPDATE ... WHERE free>=q checks affected rows; PG18 Read Committed rechecks WHERE after a competing updater completes [1]. This single-row pattern needs no initial application version read. Multi-row all-or-nothing still needs the next transaction.

请求身份绑定完整意图，重试时返回原创建回执Bind identity to complete intent and replay a fixed receipt

UNIQUE(owner, CREATE_HOLD, request_key) 用来判定是否为同一次创建操作。服务端先归一化资源和日期，再计算摘要；摘要要覆盖 scope、全部资源及数量、order_id 和 policy_version。如果接口还承诺价格，就要加入可信的 quote_id、金额和币种。本章由 Ch18 绑定价格，库存接口不重新定价。只要数量、日期、订单或政策发生变化，复用同一个键就应报冲突。token_id 是服务端在该身份作用域内计算的确定性摘要；知道摘要并不代表通过鉴权。

服务单独保存原创建回执。即使 hold 后来已变为 CONFIRMED 或 RELEASED，创建重试仍返回原来的 201、hold_id 和截止时间；要了解当前状态，另行调用 GET /holds/{id}，并核验 owner。旧回执中的 HELD 不能授权再次付款或履约。请求记录、hold、完整 hold_items、库存计数和 Outbox 都保存在同一数据库中；生产环境的复制和切主也必须保住已经确认的提交，才能延续这份身份保证。

UNIQUE(owner, CREATE_HOLD, request_key) adjudicates one operation. Normalize resources/dates first, then hash scope, every resource/quantity, order_id, and policy_version. If this API also promises price, bind a trusted quote_id, amount, and currency. Here Ch18 binds price; inventory does not reprice. Changed quantity, dates, order, or policy with the same key conflicts. token_id deterministically hashes the server-scoped identity; a hash is not authentication.

Persist the original create receipt separately. Even after CONFIRMED/RELEASED, replay its 201, hold_id, and original deadline; owner-authorized GET /holds/{id} returns current state. An old HELD receipt authorizes neither new payment nor fulfillment. Requests, holds, complete hold_items, counters, and outbox share one DB. Production replication/failover must preserve acknowledged commits to retain this guarantee.

2 · 三夜入住：全部订到，或一夜也不占2 · A multi-night stay: all nights or none

三夜必须全部扣减成功，预占才能成立。影响 0 行不是 SQL 异常，应用必须主动撤销此前的房晚扣减与本次 hold。 下面的主例订 q=1 间，独立失败例订 q=2 间；两个例子都从可用数 [2,1,2] 开始。

Commit only when every night succeeds. Zero affected rows is not a SQL error; the application must undo earlier nights. The normal q=1 and separate failed q=2 examples both start at [2,1,2].

实现时，把条件扣减、占用归属和拒绝结果一起保存Expand guarded allocation, ownership, and rejection

下面是 PG18 风格的教学伪代码。输入为认证身份、完整请求意图和可选的 Redis 准入信息，输出为固定的创建回执。所有 SQL 都使用绑定参数，事务、保存点、唯一约束和行锁均由同一数据库提供。库存明确不足时，代码回滚到 SAVEPOINT，撤销所有房晚和 hold，同时保留已经认领的请求身份；随后在同一事务中保存确定的 REJECTED 结果及回执。遇到未预期错误，则回滚整笔事务。[3]

This is PG18-style pseudocode: authenticated identity, complete intent, and optional Redis admission produce a fixed create receipt. SQL parameters are bound. The DB supplies BEGIN, SAVEPOINT, uniqueness, and row locks, rather than an abstract cross-service TX. On definite insufficiency, a savepoint preserves the claimed identity while undoing all nights/hold, then commits REJECTED and its receipt. Unexpected errors roll back the whole transaction. [3]

create(owner, key, intent, admission):                 // authenticated input
  items = normalize_unique_sorted_resources(intent)   // positive integer quantities
  digest = SHA256(canonical(owner, CREATE_HOLD, intent))
  if gated: require admission binds (owner, key, digest, scope, items[0].q)
  BEGIN ISOLATION LEVEL READ COMMITTED
  fence = SELECT * FROM fences WHERE scope=:scope FOR SHARE
  require fence.active AND (not gated OR admission.epoch == fence.epoch)
  INSERT INTO requests(owner, op, key, digest, scope, token) VALUES (...)
    ON CONFLICT(owner, op, key) DO NOTHING
  if not inserted:
    r = SELECT * FROM requests WHERE identity=:identity FOR UPDATE // new statement
    require r.digest == digest
    COMMIT; return r.original_receipt                  // current state: GET /holds/id
  SAVEPOINT allocation                               // identity remains claimed
  INSERT hold(state=HELD, expected_items=items, owner=owner, order_id=intent.order_id)
  for item in items:                                 // fixed resource/date order
    UPDATE stock SET free=free-:q, reserved=reserved+:q
      WHERE scope=:scope AND resource=:resource AND free>=:q
    if affected_rows != 1:
      ROLLBACK TO SAVEPOINT allocation                // undo ALL nights and hold
      receipt = {http:409, result:REJECTED}
      UPDATE requests SET outcome=REJECTED, original_receipt=:receipt WHERE ...
      INSERT outbox(REQUEST_TERMINAL, receipt(REJECTED, version=1, admission))
      COMMIT; return receipt
    INSERT hold_items(hold_id, resource, q) VALUES (...) // immutable ownership
  UPDATE holds SET deadline=clock_timestamp()+interval '15 minutes' WHERE ...
  receipt = {http:201, hold_id:id, result:HELD, deadline:deadline}
  UPDATE requests SET outcome=CREATED, hold_id=:id, original_receipt=:receipt WHERE ...
  INSERT outbox(HOLD_STATE, event_id=(id,1), state=HELD, version=1, current_epoch=fence.epoch)
  RELEASE SAVEPOINT allocation
  COMMIT; return receipt
// Any unexpected error: ROLLBACK the WHOLE transaction, including identity.
// COMMIT ACK lost: discard connection; query/retry SAME identity, never restock.
// Direct hotel path has no token. Only trusted API calls Lua; Redis is not public authority.

代码中的两种结果与图一致：初始为 [2,1,2]，q=1 成功后剩 [1,0,1]；q=2 在第二夜失败后，三夜仍为 [2,1,2]。缺少任一库存行，也要拒绝整个入住区间。请求身份的 CLAIMED 中间态不能单独提交。唯一键竞争失败的请求，要用一条新的 SELECT 语句读取赢家的记录，因为原 INSERT 语句的旧快照未必能看见刚刚造成唯一冲突的行。[1]

所有路径统一按 fence → 请求身份（需要时）→ hold → 有序库存行的顺序拿锁，日期也保持固定顺序；条件 UPDATE 本身就会取得行锁。支付网络调用留在事务外。只有已经确认回滚的死锁或序列化冲突，才允许最多额外重试整笔事务 2 次，因此 100 个竞争者最多产生 300 次尝试；库存不足不自动重试。跨酒店、跨数据库的全部成功或全部失败，需要另外设计协议，不能直接沿用这里的本地事务承诺。

From [2,1,2], q=1 leaves [1,0,1]; failed q=2 leaves [2,1,2]. Any missing night rejects the stay. Never separately commit CLAIMED. A loser at uniqueness reads the winner with a new SELECT statement; the INSERT’s earlier snapshot may not see the conflicting committed row. [1]

Lock dates in fixed order. Every path follows fence → request identity when needed → hold → ordered stock rows; payment network calls stay outside. Conditional UPDATE itself takes row locks. Only known-rolled-back deadlock/serialization conflicts allow two extra full-transaction retries: 100 contenders can make 300 attempts. Do not retry insufficient stock automatically. Cross-hotel/cross-DB all-or-nothing needs another protocol.

3 · 确认与到期释放：同一笔预占只能结束一次3 · Confirm and expiry compete on this hold

hold 和不可变明细记录库存归属，确认与释放只能有一个终态胜出。 以容量 10 件、预占 3 件为例，预占后的 (free,R,C) 为 (7,3,0)；如果确认，就变成 (7,0,3)；如果释放，则变成 (10,0,0)。某个 hold 已经结束后，不能因为其他用户仍有 reserved，就再次归还它的库存。

The hold and immutable items record ownership; only one terminal transition wins. Holding 3 of cap=10 gives (free,R,C)=(7,3,0); confirm gives (7,0,3), release (10,0,0). Another guest’s reserved stock cannot justify releasing a finished hold again.

下面的伪代码接收 Ch18 适配层发来的认证命令，返回库存状态。服务先根据 hold 不可变的归属确定 scope，拿锁后再核对，不能让调用者自行选择另一把 fence 来绕过保护。确认命令 CONFIRM 必须已核验资金和订单绑定，到期命令 EXPIRE 则由扫描任务发起。hold 不存在、归属不符、明细不完整或计数失配时，都要拒绝并回滚。

The pseudocode accepts an authenticated command from Ch18’s adapter and returns inventory state. Derive scope from immutable hold ownership and recheck it under lock, rather than trusting a caller-selected fence. CONFIRM requires validated funds/order binding; expiry jobs issue EXPIRE. Missing holds, wrong ownership, incomplete items, and inconsistent counters reject and roll back.

finish(hold_id, command):                              // internal authenticated command
  require command.kind in {CONFIRM, EXPIRE}
  scope = lookup_immutable_hold_scope(hold_id)          // never take scope from caller
  BEGIN
  fence = SELECT * FROM fences WHERE scope=:scope FOR SHARE
  if not fence.active: ROLLBACK; return PENDING_MAINTENANCE
  h = SELECT * FROM holds WHERE hold_id=:id FOR UPDATE
  require h exists AND h.scope == fence.scope
  require command.owner == h.owner AND command.order_id == h.order_id
  if h.state != HELD: COMMIT; return h.state            // never revive a terminal hold
  now = SELECT clock_timestamp()                      // AFTER waiting for hold lock
  if command.kind == CONFIRM AND now >= h.deadline:
    COMMIT; return EXPIRED_NOT_CONFIRMED                // Ch18 records refund/review duty
  if command.kind == EXPIRE AND now < h.deadline:
    COMMIT; return NOT_DUE
  target = CONFIRMED if command.kind == CONFIRM else RELEASED
  items = SELECT * FROM hold_items WHERE hold_id=:id ORDER BY resource
  require items == h.expected_items AND all(items.scope == h.scope AND items.q > 0)
  UPDATE holds SET state=:target, version=version+1 WHERE hold_id=:id AND state=HELD
  require affected_rows == 1
  for item in items:                                  // same transaction, fixed order
    if target == CONFIRMED:
      UPDATE stock SET reserved=reserved-:q, confirmed=confirmed+:q
        WHERE scope=:scope AND resource=:resource AND reserved>=:q
    else:
      UPDATE stock SET reserved=reserved-:q, free=free+:q
        WHERE scope=:scope AND resource=:resource AND reserved>=:q
    require affected_rows == 1                        // mismatch aborts, never partial
  INSERT outbox(HOLD_STATE, event_id=(id,h.version+1), state=target,
                version=h.version+1, current_epoch=fence.epoch, token=h.token)
  COMMIT; return target
// Unexpected error rolls back state, ALL counters, and outbox together.
// CONFIRM is supplied only after Ch18 validates funds and immutable order binding.
// Timeout/EXPIRED/RELEASED is not payment failure: Ch18 retains the funds obligation.

是否还有确认资格，以拿到 hold 行锁之后读取的数据库当前时间为准。PG 的 now()/CURRENT_TIMESTAMP 固定为事务开始时刻，等待锁后应使用 clock_timestamp() 等当前时钟 [9]。确认要求 now<deadline，释放要求 now≥deadline；条件在拿锁后判定，实际提交可能晚于截止时间。每 5 秒扫描一次只是目标，故障和积压都可能推迟释放。只要仍是 HELD，就继续计入 R，重建可用数时也必须扣除。

如果确认先成功，到期扫描就不再回补；如果释放先成功，或确认判定时已经到期，迟到收款也不能复活这份预占。库存服务返回 RELEASED 或 EXPIRED_NOT_CONFIRMED 后，Ch18 仍要根据实际扣款（capture）保留退款或人工核对责任。超时则继续保留待处理状态并查询结果。合法的售后取消需要另设业务状态和政策，不能复用到期释放函数。

Eligibility is adjudicated with current DB time after acquiring the hold lock. PG now()/CURRENT_TIMESTAMP retain transaction-start time; use current time such as clock_timestamp() after waiting [9]. Confirmation requires now<deadline and expiry now≥deadline; commit may finish after the deadline. A five-second scan is a target, not a release bound. HELD keeps occupying R until a release commits, including during rebuild.

If confirm wins, expiry restores nothing. If release wins, or confirmation is already expired, late funds cannot revive allocation. RELEASED/EXPIRED_NOT_CONFIRMED leaves Ch18 responsible for a refund or review per real capture. Timeout remains pending/queryable. Post-sale cancellation uses separate business states and policy.

4 · 秒杀准入：Redis 控制请求量，数据库终审库存4 · Sale admission: atomic Lua, DB authority

Redis 过滤过载请求，数据库判定这份库存是否归本 hold 占用。 酒店场景可以先按 hotel_id 共置数据，使用本地事务。秒杀场景中，入口每秒放行 2,000 次，而数据库库存事务的预算为每秒 800 笔，所以还要为创建请求设置更小的准入额度。

Redis filters excess work; the DB decides whether this hold owns stock. A hotel can begin with hotel-local DB transactions. The sale earns a narrower create gate because 2,000 arrivals/s exceed an 800 inventory-TX/s budget.

下面是可执行的 Redis 7+ Lua 教学示例。输入包括 epoch、服务端生成的 token_id、已认证主体 principal、完整意图摘要和数量 q，返回 ADMITTED、REPLAY 或拒绝结果。一个 gate:{scope}:7 hash 同时保存 free、cap、新 token 配额和 t:token 账本；未核销的身份不能靠 TTL 自动删除。若扩展为集群多键操作，相关键仍必须位于同一哈希槽 [7]。Lua 可以阻止命令交错 [4]，但不保证数据库提交，也不保证 Redis 重启后保住状态。

This executable Redis 7+ Lua teaching example accepts epoch, server token_id, authenticated principal, full-intent digest, and q. It returns ADMITTED/REPLAY or rejection. One gate:{scope}:7 hash holds free/cap, quota, and the t:token ledger; unresolved identities never expire by TTL. A multi-key cluster extension must retain one hash slot [7]. Lua prevents interleaving [4], not DB commit or restart durability.

-- Redis 7+; trusted server only. One hash: gate:{scope}:epoch; never TTL it.
-- ARGV: epoch, token=SHA256(owner,op,key), principal, intent_digest, quantity.
local function uint(s, lo, hi)
  local n = tonumber(s)
  if not n or n ~= math.floor(n) or n < lo or n > hi then return nil end
  return n
end
local epoch, token, principal, digest = ARGV[1], ARGV[2], ARGV[3], ARGV[4]
local q = uint(ARGV[5], 1, 10000)
if #KEYS ~= 1 or #ARGV ~= 5 or not q or not uint(epoch, 1, 1000000000)
  or not token or #token ~= 64 or token:find('[^a-f0-9]')
  or not principal or #principal < 1 or #principal > 128
  or not digest or #digest ~= 64 or digest:find('[^a-f0-9]') then
  return redis.error_reply('INVALID_INPUT')
end
local m = redis.call('HMGET', KEYS[1], 'epoch', 'ready', 'free', 'cap', 'sec', 'used')
if m[1] ~= epoch or m[2] ~= '1' then return {'CLOSED'} end
local free, cap, last, used = uint(m[3], 0, 10000), uint(m[4], 1, 10000),
  uint(m[5], 0, 10000000000), uint(m[6], 0, 500)
if not free or not cap or free > cap or not last or not used then
  return redis.error_reply('CORRUPT_GATE')
end
local old = redis.call('HGET', KEYS[1], 't:' .. token)
if old then
  local ok, r = pcall(cjson.decode, old)
  if not ok or type(r) ~= 'table' then return redis.error_reply('CORRUPT_TOKEN') end
  if r.principal ~= principal or r.digest ~= digest or r.q ~= q then
    return redis.error_reply('IDENTITY_CONFLICT')
  end
  return {'REPLAY', r.state}                           -- query DB; no new allocation
end
local sec = math.max(last, tonumber(redis.call('TIME')[1])) -- clock rollback: fail closed
if sec > last then used = 0 end
if used >= 500 then return {'RATE_LIMITED'} end
if free < q then return {'SOLD_OUT_HINT'} end
local record = cjson.encode({principal=principal, digest=digest, q=q, state='ADMITTED', v=0})
redis.call('HSET', KEYS[1], 'free', free-q, 'sec', sec, 'used', used+1, 't:'..token, record)
return {'ADMITTED', token, epoch}

脚本先读取、校验并编码结果，最后只执行一次 HSET，同时更新库存提示和 token 记录。这样安排，是因为脚本报错不会自动回滚此前写入。这个实现只控制准入，不限制每个账号的购买数量。如果题目要求限购，数据库还要提供“活动×用户”的权威约束，Redis 标记只能提前过滤。酒店的多夜请求，也不能直接套用这个单 SKU 脚本。

500 是每个 Redis 计时秒内新 token 的上限，相邻秒的边界仍允许突发，时钟回拨则不会重新打开已用过的时间桶。外层数据库调度器另外限制所有创建尝试，包括重复请求和冲突重试：合计每秒 500 次，确认每秒 200 次，释放每秒 50 次，并设置硬并发上限。这段 Lua 没有实现这套完整调度器。查询和核对还需单独分配预算，预算不足时就减少新准入。500×0.020s=10 仅代表平均在途请求数。首批请求每个 token 对应一件、且没有回补重售时，10,000÷500=20 秒也只是名义稳态等效时长；固定秒窗口可在首尾边界突发，不能据此给出这个墙钟硬下界，累计数据库工作量也可能超过库存件数。

Read, validate, and encode before a final HSET changes both hint and token. A script error does not roll back earlier writes. This example implements admission, not per-account purchase limits; those require an authoritative campaign/user DB constraint, with Redis as a filter. This single-SKU script also does not allocate a multi-night stay.

500 caps new tokens per Redis-clock second; adjacent-second boundaries can burst, while clock rollback does not reopen a bucket. An outer DB scheduler separately caps all create attempts, including duplicates/conflict retries, at 500/s, with 200 confirms/s, 50 releases/s, and a hard concurrency limit. Lua does not implement that full scheduler. Budget lookup/reconciliation separately and reduce new admission when necessary. 500×0.020s=10 is only mean in-flight. With one unit/token and no reopened stock, 10,000÷500=20 seconds is only a nominal steady-rate equivalent, not a wall-clock lower bound under fixed-window boundary bursts; cumulative DB work can exceed stock quantity.

5 · 提交结果未知：沿同一身份核对，凭终态回补5 · Unknown commit: cancel by identity, restore from outcomes

查不到记录，不能证明创建从未发生；必须先排除迟到 CREATE，才可修复 Redis 闸门。 Lua 已经扣减提示数、数据库尚无记录时，也会留下孤儿 token，单扫 hold 表找不到它。准入账本因此要保留完整身份；超过 30 秒只触发核查，绝不能自动 INCR。

A missing lookup does not prove no create. Close delayed CREATE before repairing the gate. Lua can debit before any DB row exists, leaving an orphan that a hold scan cannot find. Retain complete admission identity; thirty seconds triggers investigation, never an automatic INCR.

下面的伪代码与 CREATE 争同一个唯一请求身份。如果旧 CREATE 已插入身份但尚未提交，取消操作的 INSERT 就等待它提交或回滚；如果取消墓碑先提交，迟到 CREATE 就只能重放取消结果。只有拿到已知的提交结果后，才能据此处理终态。服务端还要认证核对程序，不能让用户凭猜到的键取消别人的预占。

This pseudocode competes with CREATE on the same unique identity. An uncommitted CREATE makes the cancel INSERT wait for commit/rollback; a tombstone that commits first makes delayed CREATE replay cancellation. Interpret a terminal outcome only after a known commit. Authenticate the reconciler; guessed keys cannot cancel another owner’s hold.

resolve_or_cancel(owner, key, exact_intent, token):   // trusted reconciler, same identity
  BEGIN ISOLATION LEVEL READ COMMITTED
  fence = SELECT * FROM fences WHERE scope=:scope FOR SHARE
  require fence.active AND token.epoch == fence.epoch
  INSERT requests(identity, digest, scope, token, outcome=CANCELLED, original_receipt=...)
    VALUES (...) ON CONFLICT(identity) DO NOTHING
  if inserted:
    INSERT outbox(REQUEST_TERMINAL, receipt(CANCELLED, version=1, token))
    COMMIT; return CANCELLED                          // durable tombstone closes late CREATE
  r = SELECT * FROM requests WHERE identity=:identity FOR UPDATE // new statement
  require r.digest == SHA256(canonical(owner, CREATE_HOLD, exact_intent))
  if r.outcome == CREATED:
    h = SELECT * FROM holds WHERE hold_id=r.hold_id
    COMMIT; return {original_receipt:r.original_receipt, current_state:h.state}
  COMMIT; return r.original_receipt                   // existing terminal event is retryable
// CREATE claims this SAME unique identity before any stock allocation.
// Its uncommitted claim makes INSERT wait; rollback lets cancel win; commit reveals hold.
// HELD: wait or call normal expiry. CONFIRMED: no restock. Unknown: keep pending.
// Return quota only by the DB terminal receipt, never by an empty SELECT or elapsed TTL.

数据库状态转换与 Redis 回补，分别保证幂等Deduplicate DB outcomes and Redis effects separately

下面的可执行 Lua 只接收来自可信数据库 Outbox的收据，字段包括 epoch、token、principal、digest、q、version 和 state。HELD 只登记状态，CONFIRMED 不增加 free，CANCELLED、REJECTED 或 RELEASED 最多回补一次。即使终态收据先到、HELD 后到，也不能把状态改回去；同版本出现不同状态，或两个终态互相冲突时，脚本报错而不覆盖。没有对应 token 的归属记录，也就没有可回补的数量。

The executable Lua accepts a receipt from a trusted DB outbox: epoch, token, principal, digest, q, version, and state. HELD records ownership; CONFIRMED never restores free; CANCELLED/REJECTED/RELEASED restore at most once. A terminal receipt arriving before HELD never regresses. Same-version/different-state or conflicting terminal receipts error rather than overwrite. No token ownership means no quota creation.

-- Trusted DB outbox only. ARGV: epoch, token, principal, digest, q, version, state.
local terminal = {CONFIRMED=true, RELEASED=true, REJECTED=true, CANCELLED=true}
local restore = {RELEASED=true, REJECTED=true, CANCELLED=true}
local function uint(s, lo, hi)
  local n = tonumber(s)
  if not n or n ~= math.floor(n) or n < lo or n > hi then return nil end
  return n
end
local e, token, p, d, state = ARGV[1], ARGV[2], ARGV[3], ARGV[4], ARGV[7]
local q, v = uint(ARGV[5],1,10000), uint(ARGV[6],1,2)
if #KEYS ~= 1 or #ARGV ~= 7 or not q or not v
  or not (terminal[state] or state == 'HELD')
  or (state == 'HELD' and v ~= 1) or (state == 'RELEASED' and v ~= 2)
  or (state == 'CONFIRMED' and v ~= 2)
  or ((state == 'REJECTED' or state == 'CANCELLED') and v ~= 1) then
  return redis.error_reply('INVALID_RECEIPT')
end
local m = redis.call('HMGET', KEYS[1], 'epoch', 'ready', 'free', 'cap', 't:'..token)
if m[1] ~= e or m[2] ~= '1' then return {'STALE_OR_CLOSED'} end
if not m[5] then return {'NO_OWNERSHIP'} end          -- never mint quota from nothing
local ok, r = pcall(cjson.decode, m[5])
local free, cap = uint(m[3],0,10000), uint(m[4],1,10000)
if not ok or type(r) ~= 'table' or not free or not cap or free > cap
  or not uint(r.v,0,2) or not (r.state == 'ADMITTED' or r.state == 'HELD' or terminal[r.state]) then
  return redis.error_reply('CORRUPT_GATE')
end
if r.principal ~= p or r.digest ~= d or r.q ~= q then return redis.error_reply('BINDING') end
if v < r.v then return {'STALE'} end
if v == r.v then
  if state ~= r.state then return redis.error_reply('CONFLICT') end
  return {'REPLAY'}
end
if terminal[r.state] then return redis.error_reply('TERMINAL_CONFLICT') end
local next_free = free + (restore[state] and q or 0)
if next_free > cap then return redis.error_reply('COUNTER_MISMATCH') end
r.state, r.v = state, v
local record = cjson.encode(r)                        -- encode BEFORE the sole write
redis.call('HSET', KEYS[1], 'free', next_free, 't:'..token, record)
return {'APPLIED', state}

Redis 的确认回复（ACK）丢失时，重发同一份收据即可。如果数据库不可用、等待锁超时或提交结果未知，就继续保留待核查状态，接受暂时少卖。TTL 删除一个键，不会替另一个计数执行 INCR；键空间通知使用的 Pub/Sub 会在断线时丢事件，过期通知也不保证准时发出 [5]。若 Redis 整层丢失，孤儿账本也会一起丢失，此时必须走下一节的恢复流程。

请求身份和取消墓碑，要保留到约定的 24 小时重试窗口结束，并且在途任务已经排空；仍有活跃占用时还要保留更久。本示例不删除身份。生产环境若要清理，必须能验证服务端签发的作用域和有效期，让过期旧键只能查询或被拒绝，不能因记录过期而重新创建。15 分钟的预占期限与 24 小时的身份重试窗口，是两项不同的约定。

Lost Redis ACK means replay the same receipt. DB outage, lock timeout, or unknown commit remains unresolved, accepting temporary undersell. Key deletion never INCRs another counter; keyspace Pub/Sub loses disconnected events and expiry notifications are not punctual [5]. Whole Redis loss also loses orphan records and requires the next recovery protocol.

Retain identity/tombstones until the 24-hour contractual retry window ends and in-flight work drains; retain live ownership longer. This example never deletes identities. Production cleanup must verify server-issued lifetime/scope so expired keys only query or reject, rather than becoming new CREATE operations. The fifteen-minute hold deadline and twenty-four-hour identity window are different contracts.

6 · Redis 丢失后：停写、切换代次，再用快照恢复6 · Pause, fence, snapshot, and recover events

恢复时先暂停创建、确认和释放，等在途事务排空后，再取完整快照。 即使开启 AOF 每秒 fsync，Redis 仍可能丢失最近的写入 [6]，所以每次创建都必须经过数据库条件终审。闸门丢失状态后可能多发 token；数据库仍会守住容量，但承受的请求和错误会增加，因此应关闭入口并恢复闸门。

Pause creates, confirms, and releases, then drain before taking a complete snapshot. AOF fsync-every-second still leaves a recent-write loss window [6], so every create retains the DB guard. Lost gate state can admit excess tokens without authorizing DB oversell, but increases pressure/errors and triggers closure and recovery.

每笔库存事务都持有同一 scope 的 fence 共享锁，直到提交。恢复操作取得排他锁后，将 active=false 与 epoch+1 一起提交；拿到这把锁说明此前进入的库存事务已经结束，之后带旧 epoch 的创建会被拒绝。暂停期间，确认和释放保留为待处理，由调用方可靠重试。快照要核对库存计数是否与完整 hold_items 一致，包含到期但未释放的 HELD，并导入活跃归属以及仍需支持重放的请求和墓碑终态。

Every inventory transaction holds a shared scope-fence lock until commit. Recovery takes the exclusive lock and commits active=false with epoch+1, draining entered transactions and rejecting later old-epoch creates. Paused confirmation/release stays pending for durable retry. Cross-check counters against complete hold_items, include expired but unreleased HELD, and import both live ownership and retained request/tombstone outcomes.

recover(scope):                                     // one gated SKU; all writers use fence
  close_ingress(scope)
  BEGIN
  f = SELECT * FROM fences WHERE scope=:scope FOR UPDATE // waits for shared writer locks
  UPDATE fences SET active=false, epoch=epoch+1, recovery_id=:fresh_id WHERE ...
  COMMIT                                             // old entered transitions have drained
  snapshot = read_while_paused(scope, f.epoch+1)
  // Cross-check each stock row against ALL HELD + CONFIRMED hold_items.
  // Expired-but-HELD remains occupied. Any mismatch: stay closed and investigate.
  // Include live ownership AND retained request/tombstone terminal identities.
  key = "gate:{scope}:" + snapshot.epoch                // never reuse an epoch key
  EVAL install.lua key snapshot                       // validate; ready=0; chunks; ready=1
  // Existing key + same snapshot is a read-only replay; never reset a live counter.
  // Same closed partial baseline: retry; corrupt/different snapshot: stay closed, NEW epoch.
  require Redis metadata == (snapshot.epoch, snapshot.snapshot, ready=1)
  BEGIN
  f = SELECT * FROM fences WHERE scope=:scope FOR UPDATE
  require not f.active AND f.epoch == snapshot.epoch AND f.recovery_id == fresh_id
  UPDATE fences SET active=true WHERE ...
  COMMIT; publish_current_epoch_and_open_ingress(snapshot.epoch)
// Old-e7 writes fail the DB fence. Effects for e7 never modify the current e8 key.
// An e7 hold still HELD is imported; its later transition emits a CURRENT-e8 receipt.
// Install/ACK unknown: retry the same immutable snapshot; never DEL/reinstall live state.
// Failure after resume: close ingress and repeat with a NEW epoch, not this baseline.

install.lua 是可执行的快照安装器。它先验证整份快照，再以 ready=0 分块写入，全部完成后才置 ready=1，因此中途失败不会开放半份数据。同一份尚未开放的快照可以重试；已开放的同一快照再次到达时只读返回，绝不重置 free。每个 epoch 使用独立键，旧安装器和旧收据都不能修改当前键。本示例最多接受 20,000 个身份、4 MB 的快照，超出后保持关闭；恢复时长和大规模暂停的代价尚未压测。

这份快照已经吸收 e7 的数据库变化，e8 闸门不能再重放 e7 的效果。原属 e7、现在仍是 HELD 的 hold 会被导入 e8，将来释放时发出当前 e8的收据。恢复控制器还必须核对 recovery_id、epoch 和安装摘要，才能重新开放数据库写入和入口，防止旧控制器误解除新一轮暂停。如果要在线重建而不停写，就另需快照位点、变化日志追平和切换屏障；本章采用暂停写入的方案。

install.lua is executable: validate the whole snapshot, write bounded chunks with ready=0, then set ready=1 only when complete. Failure never opens a half-baseline. Retry the same closed snapshot; replay of an already-open identical snapshot is read-only and never resets free. Separate epoch keys prevent old installers/receipts from changing the current key. This example rejects snapshots above 20,000 identities or 4MB and stays closed; recovery duration and large-scale pause cost are not load-tested.

The baseline already includes e7 DB changes, so e8 never reapplies e7 effects. A still-HELD e7 hold is imported and its later release emits a current-e8 receipt. Before reopening DB/ingress, the controller checks recovery_id, epoch, and installed digest, preventing a stale controller from resuming a newer pause. Online rebuilding needs a snapshot position, change-log catch-up, and cutover barrier; this chapter uses the paused version.

Outbox 保证数据库状态与事件一起提交Outbox binds DB state and event

库存状态与事件在同一事务中提交。转发程序投递后，要等接收方持久确认，才能标记 sent；ACK 丢失时就重发。消费者则把 inbox 去重记录与本地业务效果放在同一事务中 [8]。下面的投影保存完整状态，按 hold 版本拒绝旧状态覆盖新状态；增量计费或发货仍需自己的唯一任务和补偿协议，不能只靠丢弃旧版本。Redis 收据是另一个投递目的地，有独立的确认记录，不能与 Order API 共用一个 sent 标记。

两类事件的用途也要区分：HOLD_STATE 带着真实 hold_id 投递给 Order API；没有创建 hold 的拒绝或取消，则生成 REQUEST_TERMINAL，仅在请求经过闸门时投递给 Redis。数据库本地仍保留终态回执，支持按 owner 和原请求键查询。hold 事件接收器先验证类型、非空身份、版本和状态，验证失败就不写 inbox，也不返回 ACK。投影主键明确设为 NOT NULL；缺少 hold 身份的请求，不能写成 NULL 或大家共用的假 id。

Commit state and event together, and mark sent only after the receiver’s durable ACK; lost ACK redelivers. Commit consumer inbox and local effect together [8]. The projection below carries full state and rejects stale overwrites by hold version. Incremental billing/shipping still needs its own unique jobs and compensation. Redis receipts have a separate destination and ACK from Order API, rather than sharing one sent flag.

Events have explicit types: HOLD_STATE carries a real hold_id to Order API. A holdless rejection/cancellation is REQUEST_TERMINAL, delivered only to Redis for gated requests; authority retains its outcome receipt for owner-scoped lookup by the original request key. The hold consumer validates type, nonempty identity, version, and state before committing inbox or ACKing. Its projection key is explicitly NOT NULL; a missing hold never becomes a NULL or shared placeholder identity.

  require nonempty_string(event.id) AND positive_integer(event.v)
