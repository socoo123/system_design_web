量化省的是权重。KV cache 仍可能是 FP16 或 FP8。上下文一长，它才是大头。decode 每来一个新 token 都要读历史 K/V，所以必须 cache。它随层数、KV 头、头维、序列长度、精度、并发一起涨，面试先抓「长度 × 并发」这条近似线性的账。

公开锚点是 vLLM 2023 年的博客，不是某厂内部数：LLaMA-13B 单条序列的 KV 可以到约 1.7 GB；按最大长度连续预留时，碎片加上超订能浪费 60%–80% 的显存。所以卡还没吃满算力，已经 OOM，很常见。

一次聊天可能 prefill 几千 token，再 decode 几百 token，占着 GPU 好几秒。教学假设可以这么说：池子里大约 100 个并发会话，输入约 4k、输出约 300。一条会话若占大约 10 秒，新请求大约是每秒 10 个。这个 QPS 把 token 工作藏起来了。一张卡也放不下 100 条长 KV。100 是池子的并发，是假设。

权重是固定租，KV 是变动租。我不敢报精确 GB。并发上限先看 KV 能不能放下，再看算力。限流按 token/分钟，输入和输出可以拆开。

English

This back-of-the-envelope is not byte-precise. They are listening for two GPU-memory bills, and for a rate limit counted in tokens. The session count below is a teaching assumption, so you can talk. Public anchors stay labeled. Do not invent an internal number.

Quantization saves weights. The KV cache may still be FP16 or FP8. At long context, that is the bulk. Every new decode token reads historical K/V, so you cache. It grows with layers, KV heads, head dim, length, precision, and concurrency. On the interview, grab the roughly linear bill: length times concurrency.

The public anchor is the vLLM blog from 2023, not a company's internal figure: KV for one LLaMA-13B sequence can land around 1.7 GB, and reserving a contiguous max-length block can waste 60%–80% of GPU memory to fragmentation and over-reservation. The card OOMs while the cores are still idle. That is common.

One chat may prefill thousands of tokens, decode a few hundred, and hold the GPU for several seconds. A teaching assumption you can say: on the order of 100 concurrent sessions in the pool, about 4k in and 300 out. If a session holds a worker for about 10 seconds, new requests are about 10 a second. That QPS hides the token work. One card does not hold 100 long KV caches. One hundred is pool concurrency, and it is an assumption.

Weights are a fixed lease. KV is a variable lease. I won't quote an exact GB. Concurrency first asks whether KV fits, then compute. Rate-limit in tokens per minute. Input and output can be separate buckets.

Hard part：KV cacheHard part: KV cache

中文

面试官问「为什么 OOM」或「为什么一换引擎吞吐就上去」，答案几乎都在这里。自回归 decode 每次只新算 1 个 token，attention 却要用前面所有 token 的 K/V。留在显存里，decode 就从「对全序列重算」变成「读 cache，再算当前步」。上下文从 4k 到 32k，同一并发下 KV 可以差一个数量级。权重没变。

早期做法是按 max sequence length 给每条请求预留一整块连续 KV。输出长短差很大：预留了 4k，只用了 200，这是内部碎片；空闲总量够，却找不到连续大块，这是外部碎片。vLLM 的公开结论是这种浪费可以到 60%–80%。算力还闲着，batch 上不去。

PagedAttention（Kwon et al.，SOSP 2023）不是新的 Transformer。vLLM 博客把它比作操作系统的虚拟内存：KV 切成固定大小的 page，逻辑连续，物理可以散开，用 block table 映射。decode 多一步再要一页，结束立刻还回空闲池。浪费主要在最后一页没填满，博客写实际浪费可以到 4% 以下。同一前缀可以共享物理页。

前缀缓存：新请求的 token 前缀和已算过的块对得上，就跳过那段 prefill，复用 KV 页。系统提示、多轮历史、同一份文档反复问，TTFT 会受益。失效就三件：前缀字节变了（系统提示多一个空格也算）、页被挤出去、模型或 LoRA 换了。它只加速 prefill，不缩短逐步出字。整段答案的语义缓存在网关层，是后一章。

PagedAttention 是 KV 的分页分配。连续预留把显存切碎，batch 就上不去。分页之后，continuous batching 的随时进出才便宜。

English

When they ask why you OOM, or why a different engine jumps throughput, the answer is almost always here. Autoregressive decode computes one new token per step, and attention still needs K/V for every earlier token. Keep that in GPU memory and decode goes from recomputing the whole sequence to reading the cache and computing this step. Context 4k to 32k, same concurrency, KV can move by an order of magnitude. The weights did not change.

The early approach reserved one contiguous KV block per request at max sequence length. Output lengths vary wildly. Reserving 4k and using 200 is internal fragmentation. Enough free memory and no contiguous block is external fragmentation. vLLM's public write-up puts that waste at 60%–80%. Compute sits idle, and the batch cannot grow.

PagedAttention (Kwon et al., SOSP 2023) is not a new Transformer. The vLLM blog treats it like OS virtual memory: slice KV into fixed-size pages, keep the logical order contiguous, let the physical pages scatter, and map them with a block table. One more decode step asks for one more page. When the request finishes, the pages return to the free pool. Waste is mostly the last page left partly empty. The blog puts real waste under 4%. A shared prefix can share physical pages.

Prefix cache: if the new request's token prefix matches blocks you already computed, skip that prefill and reuse the KV pages. System prompts, multi-turn history, the same document asked again: TTFT benefits. Three misses: the prefix bytes changed (one extra space in the system prompt counts), the pages were evicted, or the model or LoRA changed. It only speeds prefill. It does not shorten stepwise decode. A semantic cache of the whole answer sits at the gateway. That is a later chapter.

PagedAttention is paged allocation of KV. Contiguous reservation fragments GPU memory, so the batch cannot grow. Paging is what makes continuous batching's enter-and-leave cheap.

这不是 Ch28 的配置 KV。KV cache 是 GPU 上的工作集。缓存直觉后读 Ch38 · 缓存与 CDN。语义缓存后读 Ch32 · LLM API 网关。This is not the config KV in Ch28. The KV cache is the working set on the GPU. The cache habit is Ch38 · cache and CDN. Semantic cache is Ch32 · LLM API gateway.

Hard part：continuous batchingHard part: continuous batching

中文

GPU 靠 batch 才饱。输出长度是随机变量：有人 20 个 token 结束，有人 2000。静态批凑满 N 条，一起跑到最慢的那条结束。短请求陪着长请求空转，p50 和 p99 都被尾巴拖住。

continuous batching 也叫 iteration-level scheduling。公开源头是 Orca（OSDI 2022）。vLLM 把它做成默认调度。每一个 decode 步结束，调度器重看队列：刚到 EOS 的序列立刻退出，KV 页归还；等待中的新请求可以马上占位，先 prefill，再加入 decode 批。批的成员每步都变。公开文章里的吞吐倍数是数量级，别背某一天的图表。

它和 PagedAttention 是一对。批在变、长度在变，连续大块会碎。分页让进出便宜。批更大，集群 TPS 更高，每一步更慢，单用户 TPOT 变差，TTFT 也可能因为一堆 prefill 挤在一起而变差。在 SLO 下把批开到显存和延迟还能接受的最大。这是 trade-off。

chunked prefill 把长 prompt 切段，和 decode 交错，避免一条超长 prefill 冻住同卡上所有 decode。它是 colocate 时的缓解，不是 prefill / decode 分离。

English

A GPU fills up through the batch. Output length is a random variable: someone finishes in 20 tokens, someone in 2000. A static batch waits for N requests, then runs until the slowest one finishes. Short requests idle beside long ones. The tail drags p50 and p99.

Continuous batching is also called iteration-level scheduling. The public origin is Orca (OSDI 2022). vLLM made it the default scheduler. After every decode step the scheduler looks at the queue again. A sequence that just hit EOS leaves, and its KV pages return. A waiting request can take the slot: prefill first, then join the decode batch. Membership changes every step. Throughput multiples in public write-ups are an order of magnitude. Do not memorize one day's chart.

It pairs with PagedAttention. The batch changes and the lengths change, so a contiguous block fragments. Paging makes enter and leave cheap. A bigger batch lifts cluster TPS, slows each step, worsens per-user TPOT, and can worsen TTFT when prefills pile up. Under the SLO, open the batch as far as GPU memory and latency still allow. That is the trade-off.

Chunked prefill slices a long prompt and interleaves it with decode, so one huge prefill does not freeze every decode on that card. It is relief while you colocate. It is not a prefill / decode split.

Hard part：长尾延迟Hard part: tail latency

中文

长尾是一条很长的 decode，占着这一步，别人的延迟跟着变。两个阶段的脾气也不一样。

阶段工作脾气SLO
prefill一次吃完 prompt，写出 KV偏 compute-boundTTFT
decode逐步出一个 token，反复读权重和 KV偏 memory-boundTPS / TPOT

放在同一张 GPU 上，新来的大 prefill 要么打断正在 decode 的人，要么和 decode 挤在同一步里。公开论文把这叫 prefill–decode interference。你只能优先 TTFT，或优先 TPOT，或靠多配 GPU 两个都救。

规模上来、两个 SLO 都要守的时候，再把 prefill 池和 decode 池拆开。prefill worker 算完 KV，经机房高速互连搬到 decode worker，再流式出 token。两池可以分开扩。DistServe（OSDI 2024）拆开是为了 goodput：同时满足 TTFT 和 TPOT 的有效吞吐，不是裸 TPS。2025–2026 的大规模服务栈把这种分离当成 playbook。公开讨论里也有反例：prefill 池太小、KV 搬得慢、或者负载根本不互相干扰时，colocate 更快。小集群的第一张图仍然是 colocate，加上 continuous batching，需要时再加 chunked prefill。

English

The tail is one long decode. It holds the step, and everyone else's latency moves with it. The two phases also want different hardware.

PhaseWorkTemperamentSLO
prefillEat the prompt once, write KVLeans compute-boundTTFT
decodeEmit one token at a time, reread weights and KVLeans memory-boundTPS / TPOT

On the same GPU, a new large prefill either interrupts people who are decoding, or shares the step with decode. Public papers call that prefill–decode interference. You prioritize TTFT, or you prioritize TPOT, or you spend extra GPU to hold both.

When the pool is large and both SLOs have to hold, split a prefill pool and a decode pool. The prefill worker finishes the KV, moves it over the datacenter fabric to a decode worker, then tokens stream. The pools scale apart. DistServe (OSDI 2024) splits for goodput: throughput that meets both TTFT and TPOT, not raw TPS. Large-scale stacks in 2025–2026 treat that split as a playbook. Public write-ups also have the counterexample: a small prefill pool, a slow KV move, or load that does not actually interfere, and colocate is faster. Picture one for a small cluster is still colocate, plus continuous batching, and chunked prefill when you need it.

失败路径Failure path

中文

失败单独画。成功路径上不要再塞一堆红框。GPU worker 不是无状态 web。70B 这一档的权重加载常常是分钟级，扩容来不及挡突发。突发先排队、把批缩小，保住已经在跑的会话。SLO 还是破，再加卡。

OOM 的账是权重 + 激活 + KV × 并发。没分页时，利用率很低也会爆。量化砍的是权重。队列一长，TTFT 先爆，所以要超时和 429。引擎挂了，KV 在那张卡上，这条生成没了。网关断开 SSE，客户端重试，可能换 worker，prefill 可能重算。健康检查把新流量打到还活着的 replica。前缀缓存通常也不在另一张卡上。

扩缩容我按 GPU 池来。突发先排队和降批。SLO 破了再加卡。观测换成这题的四件：TTFT、TPS、队列深度、KV 占用。

English

Draw failures on their own. Do not drop a pile of red boxes onto the happy path. A GPU worker is not a stateless web tier. Loading 70B-class weights is often minutes, so scale-out misses a spike. A spike queues and shrinks the batch, which protects sessions already running. If the SLO is still broken, add cards.

The OOM bill is weights plus activations plus KV times concurrency. Without paging you can blow up at low utilization. Quantization cuts the weights. A long queue blows TTFT first, so you need a timeout and a 429. When the engine dies, KV is on that card and this generation is gone. The gateway drops the SSE. The client retries, maybe on another worker, and prefill may run again. Health checks send new traffic to a live replica. The prefix cache is usually not on the other card either.

I scale a GPU pool. A spike queues and shrinks the batch. If the SLO breaks, then I add cards. The four numbers for this prompt are TTFT, TPS, queue depth, and KV occupancy.

The 2020 books barely have this prompt

追问Follow-ups

中文

  1. 上下文变长，显存怎么涨？ KV 近似随长度 × 并发线性涨。权重不变。先问 KV 放不放得下。
  2. 为什么会 OOM？ 不是「7B 所以一张小卡一定行」。权重 + 激活 + KV × 并发。没分页时，利用率很低也会爆。
  3. 批越大越好吗？ 集群 TPS 上去，单请求的 TTFT / TPOT 往往变差。按 SLO 盖帽。
  4. 前缀缓存何时失效？ 前缀改了，页被驱逐，模型或 LoRA 换了。只帮 prefill。
  5. 引擎挂了怎么办？ 进行中的 KV 没了，流会断。客户端重试到别的 replica，prefill 可能重算。
  6. 第一张图就要拆 prefill / decode 吗？ 小流量 colocate 就对。双 SLO 加大规模再拆，还要付 KV 搬运。限流仍然按 token。第二个模型是另一个池。

English

  1. Context gets longer. How does GPU memory grow? KV grows roughly linearly with length times concurrency. Weights stay put. First ask whether KV fits.
  2. Why OOM? A 7B model does not mean a small card is enough. Weights plus activations plus KV times concurrency. Without paging you blow up at low utilization.
  3. Is a bigger batch always better? Cluster TPS goes up. Per-request TTFT / TPOT usually gets worse. Cap it with the SLO.
  4. When does prefix cache miss? The prefix changed, pages were evicted, or the model or LoRA changed. It only helps prefill.
  5. The engine dies. Then what? In-flight KV is gone and the stream drops. The client retries on another replica. Prefill may run again.
  6. Do you split prefill / decode on picture one? Tiny traffic stays colocated. Split for a large pool that must hold both SLOs, and you pay to move KV. The rate limit stays in tokens. A second model is another pool.
