约 35 分钟 · 前置：Ch03、Ch04 · 6 组 / 31 帧演进图~35 min · after Ch03, Ch04 · 6 decks / 31 evolution frames

本章要点：先兑现资源承诺，再提高利用率Core: honor commitments before improving utilization

请求要经过两道准入检查：排队时限制等待描述的数量和各租户的份额；进入 GPU 时，为输入提示词与最大输出一次预留足够的页信用，也就是对未来显存的承诺。之后每一轮执行，还要检查计算预算。

取消要分两步完成：先停止后续调度；等所有相关 GPU 访问都已完成（退休）后，才释放请求的页引用和信用。旧生成代次（generation）和旧 worker 启动标识（worker boot）的消息，不能操作新池。

容量要分开核算：显存能容纳多少请求、在目标延迟下能服务多少请求，以及用户实际收到多少内容，需要分别计算和测量。

Two admission gates: bound waiting descriptions and tenant shares. Commit prompt-plus-output-cap page credits at GPU admission, then check compute budgets each iteration.

Two cancellation steps: stop future scheduling, then release references and credits after every relevant GPU access retires. Old generations and worker boots cannot touch a new pool.

Three capacity ledgers: memory fit, service at target latency, and client delivery require separate calculations and measurements.

设计范围：先约定服务，再写下假设Scope and replaceable assumptions

本章设计一个自托管、单地域、单模型的在线文本聊天服务。先在同一张卡上完成输入提示词（prompt）的预填充（prefill）和后续逐步解码（decode）；离线摘要使用独立队列和资源池，RAG 只在上游准备提示词。设计前先问清输入与输出的长度分布、首个 token 延迟（TTFT）与输出停顿目标、模型版本，以及是否允许用户明确发起续写。

请求沿 Client → API gateway → Scheduler → GPU worker 进入系统，即从客户端经过 API 网关和调度器，到达 GPU 工作进程；输出再逐跳返回。KV 分页负责存放注意力的键和值，连续批处理（continuous batching）负责选择每一轮参与的请求。内核优化解决的是计算问题，租户公平和资源生命周期仍需单独设计。

示例接口为 POST /v1/chat/completions，设置 stream=true。浏览器通过 fetch 发送 POST，再解析 SSE 格式的响应。原生 EventSource 不能直接发起这个 POST；事件 id 和 Last-Event-ID 也不会替服务器保存 token 日志或恢复 KV。[9]

Self-host one model for online text chat in one region, initially colocating prefill and decode. Offline summaries have another queue and pool. RAG prepares the prompt upstream. Clarify length distributions, first-token and stall targets, model identity, and explicit continuation.

The path is Client → API gateway → Scheduler → GPU worker, with every return hop. Paging manages placement; continuous batching selects each iteration’s members. Kernel optimization does not provide tenant fairness or lifecycle safety.

The illustrative API is POST /v1/chat/completions, stream=true. Browsers use fetch for POST and parse an SSE-format response. Native EventSource does not directly issue this POST; event IDs and Last-Event-ID supply neither a server token log nor KV recovery. [9]

估算容量：能预留 128 条，不代表能服务多快Estimate: 128 reservations do not establish throughput

先计算全注意力模型中每个 token 的 KV：2 × 32层 × 8 KV head × 128维 × 2 B = 128 KiB/token。每页容纳 16 token，因此一页占 2 MiB。为输入和最大输出一起预留时，ceil((2,048 + 512) ÷ 16) = 160页 = 320 MiB/请求。40 GiB 等于 40,960 MiB，最多容纳 128 条这样的满额预留；再接第 129 条，就会超出 320 MiB。这里按 KV 头的数量计算，结果不包含权重等运行时开销。

使用 Little 定律时，进入、离开和驻留时间必须采用同一边界。令 λ 表示稳定状态下进入和退出 GPU 的尝试率，取消的尝试也计入；W 表示从 GPU 准入到页引用与信用释放的平均驻留时间，不含排队。如果 λ=10/s、W=6s，平均有 60 条活动请求，需要 18.75 GiB 的保守信用。如果持续以 30/s 接纳，且 W 仍为 6s，就需要 180 条请求、56.25 GiB 的信用，超过单池容量。这个条件推导说明需要拒绝部分请求、扩容或调整预算，不能用 128÷6 反推单卡算力。

算力容量要另做负载基准测试。假设最大接纳率 C=12 req/s 时，仍有至少 99% 的请求同时满足 TTFT≤800 ms 和该请求最大的 worker ITL≤50 ms，规划只使用其中的 70%，即 8.4 req/s。峰值每秒 30 次请求，需要 ceil(30÷8.4)=4 个副本。若要损失一个副本后仍保留相同预算，就需要 5 个；剩下 4 个可提供 33.6 req/s。这里的 12 尚未实测；即使只给出“goodput=12”，也不能直接把它当作总完成率或队列服务率。

Full-attention KV is 2 × 32 layers × 8 KV heads × 128 dimensions × 2 B = 128 KiB/token. A sixteen-token block is 2 MiB. ceil((2,048 + 512) ÷ 16) = 160 blocks = 320 MiB/request. Forty GiB is 40,960 MiB and fits 128 full-cap reservations; number 129 exceeds it by 320 MiB. Count KV heads, excluding weights and other runtime overhead.

Little’s law needs one boundary. Let λ be stable admitted/departing attempts per second, including cancellation, and W mean residence from GPU admission through reference/credit release, excluding queueing. At λ=10/s and W=6s, mean active count is sixty and conservative credits are 18.75 GiB. Sustained thirty/s with W still six requires 180 requests/56.25 GiB. This conditional demand exceeds one pool and requires rejection, expansion, or a changed budget. It does not infer compute capacity from 128÷6.

Benchmark compute separately. Suppose maximum admission C=12 req/s still gives ≥99% of requests both TTFT≤800ms and maximum worker ITL within that request≤50ms. Plan at 70%, or 8.4 req/s. Peak thirty needs ceil(30÷8.4)=4 replicas; five preserve the same N−1 budget, leaving 33.6 req/s. Twelve is unmeasured. A goodput of twelve alone is not total completion rate or a queue service rate.

进一步复算：输入输出需求、权重与长上下文Demand, weights, and longer-context calculations

权重占用为 8×10⁹×2=16 GB≈14.9 GiB。按 A1，请求的输入需求平均为 20,480 token/s、峰值为 61,440 token/s。如果所有请求都获准并完成，且平均输出 256 token，输出需求平均为 2,560 token/s、峰值为 7,680 token/s。租户的输入配额若为 4,096 token/s，大约每秒容许 2 条标准提示词；输出较长时，仍要预留输出配额并限制活动请求数量。

如果把输入改为 8,192 token，输出上限仍为 512 token，每个请求就需要 8,704×128 KiB=1,088 MiB。40,960÷1,088≈37.65，因此只能预留 37 条满额请求；预填充时长和新上下文下的工作区峰值也要重新测量。只量化权重（weight-only）不会改变每个 token 的 KV 字节数，但可能腾出更多空间，扩大可用 KV 池。

Weights are 8×10⁹×2=16 GB≈14.9 GiB. Input demand averages 20,480 and peaks at 61,440 tokens/s; output averages 2,560 and peaks at 7,680 tokens/s if all requests complete with mean output 256. A 4,096 input-token/s quota permits about two standard prompts/s, while long outputs still need output reservations and active caps.

Changing input to 8,192 with output cap 512 needs 8,704×128 KiB=1,088 MiB; 40,960÷1,088≈37.65 fits thirty-seven reservations. Remeasure prefill and workspace peaks. Weight-only quantization keeps KV bytes/token unchanged but may enlarge the usable pool.

在线请求：排队时不占 KV，进入 GPU 时预留容量Online loop: queue without KV, commit at admission

网关先固定模型、聊天模板和分词器（model/template/tokenizer），再按实际 token 数校验长度。共享的尝试存储（Attempt Store）用请求主体、key 和规范化正文哈希绑定一次尝试；重复请求或更换网关时，仍读取同一记录，不重复预留输入与输出配额。如果尝试记录和配额位于不同数据库，就需要可恢复的预留与撤销协议。下面的伪代码从“请求已持久受理、配额已准备好”开始；本地队列承担等待，持久去重仍由共享记录负责。

一个 Scheduler 独占调度 worker 的本次启动实例，等待队列只保存数量有界的请求描述。调度器轮流查看各租户的队列，避免某个租户的队头请求阻塞其他租户，同时分别限制排队数量、活动序列和页信用。等待期限和排队数量需要分别检查。假设总完成率为每秒 12 条，100 条约相当于 8.33 秒的工作量，远超 600 ms；即使把数量限制为 7 条，也不能证明排队的 p99 达标。

The gateway fixes model/template/tokenizer and validates actual token lengths. A shared Attempt Store binds principal/key/canonical-body hash to one attempt; input/output quota is reserved once across retries and gateway changes. Separate stores require recoverable reserve/revoke steps. The next listing starts with a durable claim and ready quota; a local queue is not durable deduplication.

One scheduler exclusively controls a worker boot. Waiting stores bounded descriptions. Rotate tenants and separately bound queued count, active sequences, and page credits. Deadlines and counts are separate limits: at an assumed total completion rate of twelve/s, one hundred requests represent about 8.33 seconds of work, exceeding 600ms. Capping at seven still does not prove p99.

# Teaching pseudocode: one live scheduler owns this worker boot.
# A shared Attempt Store has already claimed (principal, key, body_hash).
# queued_total = sum(queue sizes); active_total = sum(per-tenant active counts).
enqueue(attempt, trusted_tenant, prompt_tokens, max_output, now):
  require fixed model/template/tokenizer; 1 <= prompt_tokens <= 2048
  require 1 <= max_output <= 512 and prompt_tokens + max_output <= 2560
  row = read_authority_attempt(attempt)       # read failure is unknown, never an empty row
  if row.state == TERMINAL: return row.saved_http_result
  if row.state != ASSIGNED or row.owner != attempt.owner: return PENDING
  if attempt is already queued or active: return saved_status(attempt)
  if queued_total == 100 or queued[trusted_tenant].size == 25:
    return reject_unstarted(attempt.owner, 429, OVERLOADED) # next listing
  # Input/output quota reservation belongs to attempt, not the HTTP connection.
  if attempt.quota != RESERVED: return PENDING # recover the same quota reservation
  r = Entry(attempt, trusted_tenant, prompt_tokens, max_output)
  r.wait_deadline = now + 600ms             # local monotonic time, not persisted
  r.request_deadline = now + validated_remaining_service_budget
  queued[trusted_tenant].append(r)
  return QUEUED                           # no KV credit and no physical KV

admit_waiters(now):                        # execute on the same event loop
  for tenant in rotating_tenant_ring:      # one head/tenant per pass
    q = queued[tenant]
    while q and now >= q.head.wait_deadline:
      expired = q.head
      decision = reject_unstarted(expired.owner, 429, WAIT_EXPIRED)
      if decision == PENDING: recover_owner(q.pop()); continue # no guessed refund
      q.pop()
    if not q: continue
    r = q.head
    need = ceil((r.prompt_tokens + r.max_output) / 16)
    if active[tenant] == 32 or tenant_page_credits[tenant] + need > 5120: continue
    if active_total == measured_safe_sequence_cap: continue
    if not calibrated_shape_allows(r): continue
    # Only this scheduler mutates local credits; worker validates boot/generation.
    if not worker_ledger.admit(r.owner, r.prompt_tokens, r.max_output): continue
    q.pop(); active[tenant] += 1; tenant_page_credits[tenant] += need
    charged[r.owner] = (tenant, need)
    ready[tenant].append(r)                # prefill runs in iteration(), below
  rotate_ring_start()                      # blocked tenant does not block others

on_release(owner):                         # same event loop; poll ledger transitions
  if worker_ledger.state(owner) != RELEASED: return
  grant = charged.get(owner)
  if not grant: return                     # already fully settled locally
  persist_terminal_and_quota_settlement(owner) # actual use; recover unknown commit by same attempt
  # Failure keeps charged as retryable work; schedule retry until durable confirmation.
  charged.remove(owner)                    # remove only after confirmed terminal/outbox
  active[grant.tenant] -= 1; tenant_page_credits[grant.tenant] -= grant.need

队列满后：先保存拒绝结果，再可靠释放配额A full queue is a durable terminal result with recoverable quota release

请求已经预留了 token 配额，因此返回 429 时还要处理这份预留。系统先在保存 Attempt 的同一个数据库事务中，写入终态、原始 429 结果和这次尝试唯一的结算事件。以后用同一个 key 重试，仍返回这个 429；即使队列已经空出位置，也不重新入队。配额服务按 attempt 原子释放未消费的预留，转发程序（relay）确认成功后才确认结算事件（ACK）。如果释放结果的回包丢失，或者释放后尚未 ACK 就崩溃，可以重复投递同一事件。依赖故障时，结算保持待处理并持续重试，因此不能承诺故障期间一定在固定秒数内退还配额。

首次向 GPU 提交工作前，必须通过条件更新确认取得 RUN_GRANTED。拒绝事务只接受仍为 ASSIGNED 的 owner，所以拒绝与启动竞争时，最多只有一方成功。已经启动或执行结果未知的请求，不能一律按“未消费”退还全部配额。

本地的 on_release 也要先确认终态与结算 outbox 已持久保存，才能删除 charged 待办并退还租户计数。如果写入失败或提交结果未知，就保留待办，按原 attempt 查询并重试。这段是教学伪代码；已有双 SQLite 适配检查事务和重复投递，但没有运行跨机器的配额服务。

Input quota is already reserved, so 429 cannot merely discard HTTP state. Commit the terminal attempt, original 429 result, and a unique attempt settlement event in one database transaction. Same-key retries keep that 429 even after capacity returns. The quota authority atomically releases unused reservations once per attempt; acknowledge the outbox only after confirmation. Lost replies and release-before-ACK crashes safely retry. Outages retain pending settlement for recovery, without a fixed refund-time promise.

Before first GPU submission, conditionally obtain RUN_GRANTED. Rejection accepts only the still-ASSIGNED owner, so it races execution with one winner. Started or unknown execution cannot receive a blanket unused refund. Local on_release confirms the durable terminal/outbox before removing charged and decrementing tenant counters. Failed or unknown commits keep charged retryable under the same attempt. This is teaching pseudocode, with an actual two-SQLite adaptation for transaction/redelivery checks, not a cross-machine quota experiment.

# Teaching pseudocode: Attempt + SettlementOutbox share one authoritative DB.
reject_unstarted(owner, status, reason):
  BEGIN; row = SELECT Attempt WHERE id=owner.attempt FOR UPDATE
  if row.state == TERMINAL: COMMIT; return row.saved_http_result
  if row.owner != owner or row.state != ASSIGNED: COMMIT; return PENDING
  UPDATE Attempt SET state=TERMINAL, saved_http_result=(status, reason)
    WHERE id=:attempt_id AND owner=:owner AND state=ASSIGNED
  require affected_rows == 1
  INSERT SettlementOutbox(attempt_id, command=RELEASE_UNSPENT)
    # UNIQUE(attempt_id); immutable command for this unstarted terminal attempt
  COMMIT                                    # unknown: query same attempt; do not re-enqueue
  return saved_http_result                  # same-key retry returns this 429

KV 分页：区分页信用、物理页和共享引用Paged KV: credits, physical pages, and shared references

图中 L0、L1、L2 分别映射到 P7、P2、P9，表示物理地址可以分散；注意力计算按页表（block table）读取 KV。演示用每页 4 个状态，因此 7→8 时填满 P2，8→9 时才增加 P9；容量估算则始终按每页 16 token 计算。PagedAttention 可以减少要求连续分配带来的碎片，但是否把同一份容量承诺给多个请求，仍要由准入策略控制。[2]

本章采用保守策略：为每个请求的输入与最大输出预留完整页信用，物理页随实际缓存状态增长而分配。因此，物理空页可能已经承诺给活动请求的未来输出，只有总承诺还有余量时，才能接纳新请求。下面可运行的 Java 17 模型在一个 worker 的 CPU 锁内，串行执行信用检查、扣除和物理页分配；跨进程的尝试身份仍由共享记录负责。

L0/L1/L2 map to P7/P2/P9: physical blocks may be scattered while attention follows the block table. Toy pages hold four states; 7→8 fills P2 and 8→9 adds P9. Capacity assumptions use sixteen-token pages. PagedAttention reduces contiguous-allocation fragmentation without solving logical overcommit. [2]

Our conservative policy reserves prompt-plus-output-cap credits while allocating physical blocks on demand. Empty physical blocks may already be promised to active requests’ future output. Admission needs uncommitted credits. This runnable Java17 model serializes credit checks/debits and allocation under one worker’s CPU lock; shared records separately govern distributed attempt identity.

public synchronized boolean admit(Owner owner, int prompt, int maxOutput) {
    long total = (long) prompt + maxOutput;
    if (prompt <= 0 || maxOutput <= 0 || total > contextLimit)
        throw new IllegalArgumentException("Token limits");
    if (!healthy || !boot.equals(owner.boot())) return false;
    int need = (int) ((total + BLOCK - 1) / BLOCK);
    Generation prior = generations.get(owner);
    if (prior != null) {
        if (prior.credits != need) throw new IllegalArgumentException("Changed request");
        return prior.state == State.RUNNING;
    }
    boolean oldOwnerLive = generations.entrySet().stream().anyMatch(e ->
            e.getKey().attempt().equals(owner.attempt()) && e.getValue().state != State.RELEASED);
    if (oldOwnerLive || need > pool.length - reserved) return false;
    generations.put(owner, new Generation(need));
    reserved += need;                    // promise full output; allocate no page yet
    return true;
}

public synchronized Handle allocate(Owner owner) {
    Generation gen = mutable(owner);
    if (gen.pages.size() >= gen.credits) throw new IllegalStateException("Credit exhausted");
    for (int i = 0; i < pool.length; i++) {
        Page page = pool[i];
        if (page.refs != 0 || page.pins != 0) continue;
        page.incarnation = Math.incrementExact(page.incarnation);
        page.cached = page.sealed = false; // evict an unused cache entry if needed
        page.refs = 1;
        Handle h = new Handle(boot, i, page.incarnation);
        gen.pages.add(h);
        return h;
    }
    throw new IllegalStateException("Pool accounting violated");
}

模型以执行归属 owner=(attempt,generation,worker boot)、输入长度和最大输出为输入，返回是否接受页信用预留，或返回一个带分配代次 incarnation 的页句柄 Handle。每个 generation 保存自己持有的页集合；每页分别记录活动引用数 refs 和在途访问数 pins。模型只共享已经计算完成、不可变的完整块，不处理未满尾页的共享或写时复制（COW）。如果真实引擎使用超订、COW，或额外占用工作区，这些开销也必须计入同一资源预算。

前缀缓存要比较 token 和计算身份，包括固定的模型/LoRA、位置语义和信任域。vLLM v0.15.1 按父哈希、块内 token 和额外身份缓存完整块，用 cache salt 隔离复用；本设计由服务器按信任域分配这个值。自动前缀缓存（APC）只减少重复的预填充计算，后缀仍要逐步生成；未命中时正常重算。模型升级要换缓存命名空间，命中缓存也不会减少输出配额。[5] [6]

完整前缀在 refs=0 后，可以继续作为可驱逐的缓存保留；只要还有 refs 或 pins，就不能复用该物理地址。本章不利用共享节省的空间增加页信用承诺，以便守住最大输出的预算。如果要超订仍在使用的页，就需要另外设计抢占与重算，并承担被抢占请求增加的延迟。

Inputs are owner=(attempt,generation,worker boot), prompt, and output cap. Outputs are admission or an incarnation-stamped block Handle. The source tracks a generation’s page set, with separate active references and in-flight pins per page. It shares only complete immutable blocks; partial-tail sharing/COW is outside this model. Real overcommit, COW, and hidden workspaces need the same explicit budget.

Reuse compares tokens and computation identity, fixing model/LoRA, positions, and trust domain. vLLM v0.15.1 caches complete blocks using parent hashes, block tokens, and extra identity. Cache salts isolate reuse; this design assigns them by server trust domain. APC saves repeated prefill, not suffix steps; misses compute normally. Model upgrades change namespaces and hits never bypass output quota. [5] [6]

A full prefix with refs=0 may remain an evictable cache entry. References or pins prevent address reuse. We do not sell sharing savings as more credits, simplifying worst-output promises. Live-page overcommit instead needs explicit preemption/recomputation and its waiting cost.

逐轮组批：调整成员，也限制这一轮的工作量Iteration batching: change members and bound work

在 t 轮中，A、B、C 参与解码；B 完成并退休引用后，t+1 可以考虑让 D 预填充，t+2 再让 D 解码。Orca 的逐轮调度（iteration-level scheduling）消除了“必须等整批请求全部结束”的屏障，但页资源、计算预算和公平分配仍可能让 D 等待多轮。CPU 负责选择成员和预填充分块，注意力内核负责执行；FlashAttention 优化的是 I/O，租户公平仍由调度器实现。[1] [4]

调度器为每个租户保留可累计的工作额度 deficit 和请求游标，按上下文、执行阶段和 token 数计算成本。余额可以跨轮累积，其上限至少要容纳最大的合法分块；每轮还要轮换起始租户，避免同一个租户总是先使用剩余预算。准入阶段继续限制各租户的活动请求数和页份额；进入单轮后，每条请求最多贡献一个预填充分块或一个解码步骤。较高权重表示较大的相对份额，并不提供硬实时保证。

Iteration t has A/B/C. B finishes and retires references; t+1 may admit D’s prefill and t+2 decodes D. Orca’s iteration scheduling removes the whole-request batch barrier, but pages, compute, and fairness may still delay D many rounds. CPU selects members/chunks and kernels execute. FlashAttention optimizes IO rather than scheduler fairness. [1] [4]

Keep tenant deficits and request cursors. Charge by context, phase, and token count; carry balances across rounds with a cap large enough for the largest legal chunk. Rotate the first tenant so the same tenant does not always consume residual budget first. Admission also caps tenant active/page shares. Each request contributes at most one chunk or decode step per iteration. Weights are relative shares, not real-time guarantees.

延迟指标：先写清从哪里测到哪里Latency metrics need explicit endpoints

客户端 TTFT 从发送请求测到收到首个内容，包含排队、网络传输和刷新缓冲（flush）。A6 中的 50+等待+150≤800，是一次请求在给定条件下的预算，各部分的 p99 不能直接相加。worker ITL 则统计相邻 token 就绪（token-ready）的时间差。客户端的一个 SSE 响应块可能合并多个 token，因此要另报响应块的到达间隔，不能把它当成 GPU 每步的执行时长。

TPOT 在同一个 worker 的时间轴上，按 (末token−首token)/(N−1) 计算。N=1 时没有这个平均值；即使有平均值，也可能掩盖某一步的长停顿。256 个输出 token 之间有 255 个后续间隔，固定每步 20 ms 的例子共需 5.1 s；再加上假设的首段 200 ms，约为 5.3 s。ITL 的 p99 为 50 ms，不代表每一步都不会超过 50 ms，也不能由此推断整次请求的总时长。

goodput 统计每秒完成且联合达标的请求数，同时还要报告统计分母和联合达标比例。TTFT 与 ITL 各自的 p99 达标，并不能证明有 99% 的请求同时满足两项要求。

Client TTFT spans request send to first content, including queueing, network, and flush. A6’s 50+wait+150≤800 is a conditional per-request budget, not summed p99s. Worker ITL is the gap between adjacent token-ready times. SSE chunks may combine tokens, so separately report client chunk-arrival gaps rather than calling them GPU step times.

TPOT is (last token−first token)/(N−1) on the same worker clock; it is undefined for N=1 and may hide a stall. 256 outputs have 255 later gaps: at fixed twenty ms, 5.1s, or approximately 5.3s with an assumed 200ms first-token path. A fifty-ms ITL p99 is no hard step or total-duration bound. Goodput counts jointly compliant completions/s; also report its denominator and joint attainment. Separate TTFT/ITL p99s do not establish 99% joint request attainment.

取消与完成：等 GPU 访问结束，再释放资源Cancel and completion: retire accesses before releasing pages

图中依次是运行（RUNNING）、等待取消完成（CANCEL_PENDING）、访问已退休（RETIRED）和资源已释放（RELEASED）。Java 模型把等待退休的状态记作 RETIRING；满足 inFlight==0 后，就进入访问已退休并立即释放的阶段，不另外保存一个瞬态字段。提交 GPU 工作前，ticket 先固定 owner 与页快照，并增加在途访问计数 pin。取消操作只标记停止；正常结束（EOS）和取消在同一把锁内竞争，以最先记录的停止原因为准。

The diagram is RUNNING → CANCEL_PENDING → RETIRED → RELEASED. Java calls the waiting state RETIRING; inFlight==0 allows RETIRED and immediate release without storing that transient phase. Before launch, a ticket snapshots owners/pages and pins them. Cancel marks stop; EOS and cancel contend for the first stop reason under the same lock.

public synchronized Ticket issue(List<Owner> batch) {
    if (!healthy || batch.isEmpty() || new HashSet<>(batch).size() != batch.size())
        throw new IllegalArgumentException("Invalid batch");
    List<Hold> holds = new ArrayList<>();
    for (Owner owner : batch) {
        Generation gen = mutable(owner);
        if (gen.pages.isEmpty()) throw new IllegalStateException("Missing KV");
        holds.add(new Hold(owner, List.copyOf(gen.pages)));
    }                                   // validate everything before mutating
    long id = Math.incrementExact(nextTicket);
    for (Hold hold : holds) {
        generations.get(hold.owner()).inFlight++;
        for (Handle h : hold.pages()) page(h).pins++;
    }
    nextTicket = id;
    launches.put(id, List.copyOf(holds));
    return new Ticket(boot, id);          // pin before submitting any GPU access
}

public synchronized boolean stop(Owner owner, Reason reason) {
    Objects.requireNonNull(reason);
    Generation gen = generations.get(owner);
    if (!healthy || gen == null || gen.state != State.RUNNING) return false;
    gen.reason = reason;                 // first stop/EOS wins
    gen.state = State.RETIRING;           // prevents all later issue calls
    releaseIfRetired(gen);
    return true;
}

真实适配器需要提供覆盖全部相关访问的完成证据，包括读写 KV、访问页表，以及相关复制操作涉及的所有 stream 依赖。CUDA event 只证明它捕获的工作与依赖已经完成；查询一个不相关的 stream，不能作为还页依据。下面的模型由测试手工调用 complete，模拟“这些完成证据已经成立”，没有实际执行 CUDA。[10]

public synchronized boolean complete(Ticket ticket, Set<Owner> eos) {
    if (!healthy || !boot.equals(ticket.boot())) return false;
    List<Hold> holds = launches.remove(ticket.id());
    if (holds == null) return false;      // duplicate/old completion
    for (Hold hold : holds) {
        for (Handle h : hold.pages()) page(h).pins--;
        Generation gen = generations.get(hold.owner());
        gen.inFlight--;
        if (eos.contains(hold.owner()) && gen.state == State.RUNNING) {
            gen.reason = Reason.EOS;
            gen.state = State.RETIRING;
        }
        releaseIfRetired(gen);
    }
    return true;
}

private void releaseIfRetired(Generation gen) {
    if (gen.state != State.RETIRING || gen.inFlight != 0) return;
    for (Handle h : gen.pages) page(h).refs--;
    gen.pages.clear();
    reserved -= gen.credits;             // return promise exactly once
    gen.state = State.RELEASED;
    // A page is reusable only at refs==0 && pins==0; cached data may remain.
}

先走一个危险反例：A 预留了 2 页信用，实际只占 1 页，内核仍在读取 P7。若收到取消后就立刻退还信用并复用资源，B 可能获准进入并覆盖 P7，A 随后读到的就可能是 B 的 KV。模型要等 ticket 对应的访问完成后才释放，并且每个 launch 只能从记录表中删除一次，避免重复完成造成重复释放。页地址复用后会换 incarnation，旧 Handle 也不能再指向 B 的新分配。如果前缀由 A、B 共享，即使 A 退出，B 的 refs 和 pins 仍会保护它。正常 EOS 也经过同样的释放检查。

对于慢读客户端，待发送数据达到 64 KiB，或者持续 2 秒没有进展时，就停止后续调度或取消该请求，其他请求继续处理。若 128 条流都达到这个缓冲上限，合计是 8 MiB；这是这组流的教学上界，不是全局常数。

页信用不足可以通过准入拒绝来控制；激活峰值导致显存不足（OOM）时，能否只回滚一条请求，要看引擎是否支持，以及 CUDA 执行上下文（context）是否仍健康。非法地址（illegal address）等致命错误要按整个 worker 死亡处理：隔离旧池，用新 boot 重建，不能在旧池中释放一个 block 后继续运行。[8]

Dangerous trace: A reserves two blocks but occupies one while its kernel still reads P7. Returning credits on cancel could admit B and overwrite P7 while A reads it. This example waits for the ticket, removes each launch once, and stamps reused handles with a new incarnation. A shared prefix remains protected by B’s refs/pins after A leaves. Normal EOS uses the same release gate.

Stop future scheduling or cancel a slow reader at 64 KiB pending sends or two seconds without progress, while others continue. At 128 capped streams this is 8 MiB for that serving set, not a global constant. Missing credits are controlled denial. Local recovery from activation OOM requires a healthy context and engine support. Fatal errors such as illegal addresses mean worker loss: quarantine the old pool and rebuild under a new boot, rather than freeing one block and continuing. [8]

流中断后：尝试去重与 token 送达是两件事Interrupted streams: attempt dedupe is not token delivery

worker 死亡可能丢失 KV、采样状态和未保存的输出。系统把匹配 owner 的尝试记为 INTERRUPTED；连接仍可用时，再逐跳返回终止事件。如果只是网关失联，worker 未必已经死亡：应先查询或取消旧 owner，或者隔离它的输出和后续执行，不能仅因没有心跳就启动第二份生成。同一个 key 不会重新生成，即使记录显示“尚无 write”也是如此。

retry(principal, key, hash):
  row = claim(principal, key, hash, authority_now())
  if conflict_or_expired(row): return row
  if row.state in [CLAIMED, ASSIGNED, RUN_GRANTED]: return PENDING_WITHOUT_SECOND_STREAM
  if row.saved_http_status == 429: return row.saved_http_result # no new queue admission
  if row.metadata.reason == DONE: return COMPLETION_METADATA
  return INTERRUPTED_REQUIRES_EXPLICIT_NEW_KEY
# Unknown dispatch/terminal commits are queried by the same key, never guessed.
# Crash after ASSIGNED before enqueue may fail closed as INTERRUPTED after fencing.
# Token logs, replay, cross-worker live migration, and quota atomicity are separate.

正常路径是：认领尝试（claim）→ 唯一绑定执行者（bind）→ 按同一个 owner 投递 → 保存匹配的终态。同一个 key 携带不同正文时返回冲突；两个 Scheduler 争抢绑定时，也只有一个能更新成功。如果绑定已成功、投递前却崩溃，可以查询旧 owner，隔离后将尝试明确终止为 INTERRUPTED；持久受理并不保证每次尝试都会执行。终态提交结果未知时，按原 key 查询；重复或旧 owner 的终态不能覆盖已有结果。

幂等记录保留 24 小时，覆盖客户端最多 15 分钟的自动重试窗口。活动记录不会被 TTL 删除；终态记录到期后，也不承诺无限期去重。

网关成功 write 了 seq=37，不代表客户端已经展示第 37 段。若要重放，必须先持久保存 attempt/seq 事件再发送，并提供客户端游标、去重和保留期；即使客户端有 ACK，也不能恢复死亡 GPU 上的 KV。本章基本方案中，同 key 只读取已存状态或元数据：OVERLOADED 重放原 429，INTERRUPTED 在示例中返回 409。用户明确重新生成或续写时，才用新 key、新页信用和新预填充，并重新校验实际 token 长度。把已收文本作为 assistant 消息重新放入提示词，可能改变模板，不能保证得到原来的 token 前缀。

Normal: claim → one binding → same-owner delivery → matching terminal. Different body conflicts; only one of two schedulers binds successfully. A crash after binding but before delivery may query the owner, then fence and fail closed as INTERRUPTED; admission does not promise execution. Unknown terminal commits are queried by the original key; duplicate/old terminals do not overwrite. Twenty-four-hour retention covers fifteen-minute client retries. Active rows are not TTL-deleted; expired terminal rows do not promise unbounded deduplication.

A successful seq=37 write does not prove client display. Replay needs attempt/seq events persisted before sending, client cursors/deduplication, and retention. Client ACK does not restore dead KV. Baseline same-key retries return saved status/metadata: OVERLOADED replays its 429, while INTERRUPTED illustratively returns 409. Explicit regeneration/continuation uses a new key, credits, and prefill with renewed token-length checks. Text reinserted as an assistant message may alter templates rather than match the old token prefix.

阶段分离：先测量同卡干扰，再计算传输代价Phase separation: measure interference and transfer cost

先通过预填充分块、逐轮预算和并发上限调整同卡方案。长预填充通常更依赖计算，解码通常更依赖带宽，但实际瓶颈会随模型、上下文、批大小和硬件变化。如果两项延迟目标仍无法同时满足，且资源规模足以支持分离，再考虑两个池。DistServe 按延迟目标和达标比例优化 goodput；论文中的吞吐倍数不能直接当作本站容量。图中的 A、B 是两种互斥方案。[3]

分离时，调度器先为 Decode 目标端预留页信用，再执行预填充和传输。目标端接收 KV 字节，以及首个采样 token，或初始 logits 与采样元数据；验证模型/LoRA、请求、epoch、长度和块清单后，才确认接受。源端只有收到匹配的接受确认，或者完成对旧 owner 的隔离与撤销后，才能退休引用。仅仅发起复制或收到元数据，都不足以释放源端资源。Decode 的输出直接返回 Scheduler，不再经过 Prefill。

提示词的 KV 为 2,048×128 KiB=256 MiB=268,435,456 B。假设有效带宽为 10 GB/s，纯传输需 26.84 ms；每秒 30 次请求需要 7.5 GiB/s≈8.05 GB/s≈64.42 Gb/s，占这份带宽的 80.53%。这些计算尚未包含排队、复制、握手、重传和两端暂存。如果目标端容量不足，只增加 Prefill worker，就只会积压更多 KV。

First tune colocation with chunks, iteration budgets, and active caps. Long prefill is often compute-heavy and decode bandwidth-heavy, but bottlenecks vary by model/context/batch/hardware. Split only when both latency goals still conflict at sufficient scale. DistServe optimizes goodput under latency and attainment goals; paper speedups are not our capacity. A/B in the diagram are mutually exclusive. [3]

Reserve destination Decode credits before prefill/transfer. The target receives KV bytes plus the first sampled token or initial logits/sampling metadata; it validates model/LoRA, request, epoch, length, and manifest before accepting. Retire source references only after matching acceptance or a fenced abort. Starting a copy or receiving metadata is insufficient. Decode returns directly to Scheduler rather than through Prefill.

Prompt KV is 2,048×128 KiB=256 MiB=268,435,456 B. At assumed effective ten GB/s, ideal transfer is 26.84ms. Thirty/s is 7.5 GiB/s≈8.05 GB/s≈64.42 Gb/s, or 80.53%, excluding queues, copies, handshakes, retries, and duplicate staging. More Prefill without target capacity merely accumulates KV.

接受确认丢失、目标池故障与扩缩容Lost acceptance ACK, pool loss, and scaling

发送方超时，可能只是目标端已接受后的 ACK 丢失。此时按 transfer id 和 epoch 查询已有结果，重复接受返回原结果，不再多占一份容量。撤销时先隔离旧 owner，再清理两端引用。源端保留的提示词 KV 不包含后续解码与采样状态，因此目标端死亡后，仍要按上一节明确中断，或由用户明确发起新的预填充，不能保证无感恢复。

扩容时要一起观察 Prefill 排队、Decode 活动页与输出间隔，以及互连带宽。缩容时先停止接纳新请求，再等待已有请求完成（drain），或明确取消旧请求。多卡张量并行（tensor parallel）还要分别计算各 rank 的权重、KV 与通信。本章没有进行真实 GPU、网络传输或设备故障实验；Java 内存状态模型不能验证生产吞吐、CUDA 正确性或分布式恢复。

Sender timeout may follow accepted transfer with a lost ACK. Query by transfer ID/epoch and make repeated acceptance return the existing result. Abort fences the owner before cleaning both references. Source prompt KV omits subsequent decode/sampling state; target loss still means explicit interruption or new prefill, not seamless recovery.

Scale against Prefill wait, Decode pages/gaps, and interconnect together. Scale-in stops admission and drains or explicitly cancels old requests. Tensor-parallel ranks need separate weight/KV/communication accounting. No real GPU, transfer, or device-failure experiment was performed. The Java memory model proves neither production throughput, CUDA correctness, nor distributed recovery.
