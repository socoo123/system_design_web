中文

从一场服务端结算走到持久分数，再走到 Redis 有序视图，分清「已经计分」和「已经可见」。能把 top100、自己的序号、上下各五人画成有请求和回程的闭环。

用有边界的复合分数解释先达者靠前，纠正命令、浮点精度和并列名次的误解；在一张热榜必须切桶时，证明 topK 合并的条件，承认个人全球名次的代价。

English

Walk a server-settled match to durable scores and then to an ordered Redis projection. Distinguish committed scoring from visible ranking, and draw request/reply loops for top100, personal position, and five neighbors on each side.

Explain first-achieved ordering with a bounded composite score; correct command, floating-point, and tie-rank misconceptions. If one hot board must be partitioned, prove the conditions for topK merging and state the cost of a personal global rank.

30 秒开场：先定计分契约，再估热榜The 30-second open: scoring contract before capacity

中文

我先确认是游戏分数榜，读同赛季全球/区服 top100、自己的名次和附近玩家。游戏服结算绝对分，已经确认的分数不允许因为 Redis 宕机消失；榜单投影可以晚两秒。默认单地域，持久分数与 outbox 同事务，Projector 按玩家版本幂等更新 ZSET。先按榜和赛季拆 key，再谈单热 key 的应用分桶。同分先比较达成秒，秒内按固定格式玩家 ID 兜底。最后讲故障重建和赛季结算，不把推荐、推送或数仓画进开场。

先问五个改变结构的问题：谁算分；是覆盖总分、累计积分还是只保最高；同分是否共享名次；分数确认后能否丢；赛季结束要不要按榜奖励。本章选择绝对总分、可纠错降分、唯一序号。若对方只做休闲展示且明确允许丢最近几秒，先 Redis 后异步持久化才可能成立；一旦奖品依赖排名，就要换成本章的持久确认。不能替产品默默接受丢分。

用户读到落后的榜和系统忘记赢局是两种错误。前者能够显示更新时间并稍后重试，后者会把数据库、缓存和赛季奖励一起带歪。响应区分 committed_version 与 projected_version：写确认带前者，读榜带后者。玩家刚打完一局可以先显示已结算总分，名次若尚未追平就标更新中，不能拿旧名次假装这笔已上榜。

规模先算日总量，再除以秒数。1000 万 × 5 = 5000 万笔结算/天，÷86,400 = 578.7 笔/秒，峰值 ×5 = 2,893.5。读为 1000 万 ×3 ÷86,400 ×5 = 1,736.1 次/秒。全球与区服两类视图把投影更新放大到约 5,787 次/秒，却仍只有约 2,894 笔权威事务。把这两个数混用会错买数据库，也会错把 aggregate 当成单 key 压力。

内存按单榜 1000 万人、每成员 160 B 的教学估算，得到 1.6 GB。全球 10M 人、区服合计 10M 人，各主加一副本共两份，是 1.6 ×2 ×2 = 6.4 GB。这个数没有算版本 Hash、持久事实、outbox、碎片、复制缓冲和重建的新 epoch，也不是 Redis 每条固定 160 B。必须对真实 ID 长度、结构编码和装载量执行 MEMORY USAGE 采样，再留故障恢复空间。[10]

English

I clarify a game score board: global and regional top100 within one season, personal position, and nearby players. Game servers settle absolute scores; acknowledged scores survive Redis loss, while projection can lag two seconds. Default to one region, score plus outbox in one transaction, and version-idempotent ZSET projection. Split board/season keys before partitioning one hot key. Ties compare achievement seconds, then fixed-format player IDs. Close on recovery and settlement rather than adding recommendations, push, or a warehouse.

Ask five structural questions: who computes scores; replacement, accumulation, or high-score only; shared tie ranks; acknowledged-score durability; and rewards at season end. This chapter chooses absolute totals, downward corrections, and ordinal positions. Redis-first asynchronous persistence can fit a casual display only when the product explicitly accepts recent loss. Rewards require the durable acknowledgement here; do not silently choose score loss.

A stale display and a forgotten match are different failures. The first can show a timestamp and retry; the second corrupts storage, caching, and rewards. Write responses carry committed_version, reads projected_version. Immediately after a match the UI can show the settled score while labeling rank as updating, instead of presenting an old rank as proof the new score was projected.

Compute daily counts before rates. 10M × 5 = 50M settlements/day, /86,400 = 578.7/s, ×5 peak = 2,893.5/s. Reads are 10M × 3 /86,400 ×5 = 1,736.1/s. Global and regional views amplify projection updates to about 5,787/s but leave about 2,894 authoritative transactions/s. Mixing these numbers mis-sizes the database and mistakes aggregate load for one hot key.

Assume 10M members and 160 B/member for one board: 1.6 GB. Global 10M members plus 10M across all regions, each with a primary and one replica, yield 1.6 ×2 ×2 = 6.4 GB. This excludes version hashes, durable facts, outbox, fragmentation, replication buffers, and a new rebuild epoch. Redis does not guarantee 160 B/entry. Sample MEMORY USAGE for actual ID lengths, encodings, and loading, then reserve recovery space. [10]

1 · 一笔结算先成为事实，再成为名次1 · A settlement becomes a fact before a position

中文

正常路径。 Client 的对局动作进入 Game server；游戏服验证结算后，把 settlement_id、player_id、board_id、绝对分、达成时间交给 Board API。API 不接受任意客户端的加分请求。游戏服计分权威按玩家分配单调 authority_seq；DB 事务拒绝旧 seq，以 settlement_id=(game,match,player,kind) 去重，再改分/版本与 outbox，处罚是显式新修订。提交满足 A7 的耐久边界之后，确认按 Score DB → Board API → Game server → Client 返回。确认不等待 Redis，可见性由投影版本另行回答。

为什么选 outbox。 单纯「写 DB，然后从内存发送 Redis 更新」有两步间的崩溃窗口：事实已经提交，消息还没发。outbox 把待投影的事实也放进同一事务，Projector 稍后轮询已提交行再应用，失败继续重试。这里 Projector 同时承担 outbox relay 与有序视图消费者，无需为了形式额外加一个 MQ；以后有多个订阅者再把 relay 与队列拆开。官方 outbox 模式强调同事务和消费者幂等，[6] 它消除的是消息遗漏窗口，不是让所有系统共享一个分布式事务。

重复与乱序。 对局去重和投影去重分两层。settlement_id 的唯一约束防止一局被重复结算；(board_id, player_id, version) 防止投影重试和旧事件覆盖新事实。Redis 同 slot 的版本 Hash 与 ZSET 在短脚本内处理：版本不大于已应用值则跳过；较新版本才设置绝对 C 并保存版本。新版本即使降分也要接受，不能用 GT 拦截。重复事件不再做 ZINCRBY，所以投影成功但消费确认丢失时，再投一次仍得到相同状态。

失败时行为。 DB 提交超时意味着结果未知，游戏服带同一个 settlement_id 重试或查询结果，不能换一个新 ID 再算一遍。Redis 超时不会撤销已提交分数；Projector 不推进消费水位，继续恢复投影。数据库自己也必须守住 A7：本地 WAL 落盘可保进程重启，要承诺主机丢失后已确认事实仍在，还要等指定同步副本持久化，并且禁止把落后副本强行提升。[9] 若权威存储失去这条保障，计分暂停，读可按独立的旧值契约降级。

代价与边界。 两张榜可由同一结算事实派生，各自带独立 projected_version；它们不会因为用了同一 settlement_id 就自动同时可见。outbox 积压监控看最老未应用时间、重试次数和连续水位，不只看消费者活着没有。2 秒是 p99 目标，断电或长时间分区时可能失守，界面必须标更新中而不是继续声称实时。权威事务的数据库行锁、索引和同步确认要按约 2,894/s 压测；图中没有任何「数据库永远够」的常数。

替代方案。 高频战斗日志可以先汇总成游戏服的绝对结果，但不能把赢局在未持久化之前压掉。「最后写赢」只在同一玩家、同一语义的绝对状态且保留较新版本时成立，不能把两个累计增量随便覆盖。如果产品真的要求即时读到新名次，写确认后可限时等待该玩家投影版本追平；到时返回 committed/pending，不把计分是否成功绑在 Redis 网络上。

English

Normal path. Client sends gameplay to Game server. After validation, the server submits settlement_id, player_id, board_id, absolute score, and achievement time to Board API. The API rejects arbitrary client score additions. The game server scoring authority assigns monotonic per-player authority_seq. A Score DB transaction rejects old sequences, deduplicates settlement_id=(game,match,player,kind), and updates score, version, and outbox. Penalties are explicit new revisions. Once A7 durability is met, acknowledgement returns Score DB → Board API → Game server → Client. It does not wait for Redis; projection versions answer visibility separately.

Why outbox. Writing the DB and then sending a Redis update from RAM has a crash gap: the fact committed, but the update was never sent. An outbox commits the pending projection fact in the same transaction; Projector polls committed rows and retries failed application. Here Projector combines relay and projection consumption, so an MQ is unnecessary until multiple subscribers justify it. The official pattern requires a shared transaction and idempotent consumers. [6] It removes missing notification, rather than sharing a distributed transaction across all systems.

Duplicates and order. Deduplicate twice. A unique settlement_id prevents duplicate settlement; (board_id, player_id, version) prevents replay or an older projection overwriting newer facts. A short Redis script handles the same-slot version hash and ZSET: ignore versions no greater than the applied value; otherwise set absolute C and version. A newer correction may reduce score and must not be blocked by GT. Replayed events never call ZINCRBY, so applying then losing the consumer acknowledgement produces the same state on replay.

Failure. A DB commit timeout is an unknown outcome: retry or query with the same settlement_id, without inventing a new ID. A Redis timeout does not undo durable scoring. Projector leaves its checkpoint unchanged and restores projection. Score DB must enforce A7: local WAL flush survives process restart; acknowledged host-loss durability also requires the designated synchronous standby to persist WAL and forbids forced promotion of a lagging standby. [9] Without that boundary, pause scoring while reads follow their separate stale-data contract.

Cost and boundaries. Two boards derive from one settlement and report independent projected_version values. Sharing settlement_id does not make both views visible together. Monitor the oldest unapplied age, retry count, and continuous frontier rather than only consumer liveness. The 2 s p99 goal may fail during power loss or a long partition; show updating rather than claim real time. Test authoritative locks, indexes, and synchronous acknowledgements at about 2,894/s. The diagram supplies no universal database throughput guarantee.

Alternatives. Game servers may aggregate battle logs into absolute results but cannot discard unpersisted wins. Last-write-wins applies only to one player’s absolute state with the newest version, not arbitrary additive events. If the product demands immediate rank visibility, wait a bounded time after commit for that player’s projection version. On expiry return committed/pending instead of tying scoring success to the Redis network.

2 · 有序结构、精度和并列：把排序规则写成数据2 · Ordering, precision, and ties: encode the actual rule

中文

正常路径。 大榜用 Sorted Set：member 是固定格式 player_id，一人一条；score 是复合 C，展示的基础分仍从权威记录或拆解后取得。Projector 用 ZADD 设置绝对值，主榜按分降序。命令写准确：top100 是 ZRANGE key 0 99 REV WITHSCORES，降序序号是 ZREVRANK key member，再加 1 展示。ZRANK 是升序，语法没有 REV；Redis 6.2 的 REV 扩展属于 ZRANGE，不属于所有 Z 命令。[2][3][4]

并列必须是产品决定。 ZSET 同 score 的默认顺序是 member 字节序，降序则反字节序，不是先插入先赢。基础分相同，先达秒更早者靠前；同秒无法判断更细先后，本章明确用逆固定格式 ID 稳定兜底。P7 与 P3 同秒同分，P7 在前。数值 ID 先补零，不能让字符串 "9" 和 "10" 的字节序冒充数值序。把 playerId#seq 当 member 也不是通用解法：前缀 playerId 已经先决定排序，后面的 seq 不会忽然变成主排序键。

精度推导。 赛季相对秒数 t ≤30×24×3600 = 2,592,000，选 T=3,000,000、B=T+1。C=S×B+(T−t)，其中 S 为 0..10⁶ 的整数。t 变小，C 变大，降序让更早者靠前；基础分高 1 带来的 B 又大于 tie 的最大差 T，不会倒置两名不同分玩家。最大 C=10⁶×3,000,001+3,000,000 = 3,000,004,000,000。Redis 文档给出的精确整数范围含 ±2⁵³，正边界 9,007,199,254,740,992；本章最大值远在它以内。[1]

更新语义。 最高分榜可用 ZADD GT，仅在新 score 更高时改既有成员，新成员仍可加入；XX 才是不新增成员的限制。CH 改的是返回值：新增或实际变更都计数，相同 score 不计。普通 ZADD 更新既有成员返回 0 并不代表失败。主线有处罚和修正，必须由 player_version 决定是否覆盖，所以不用 GT。重复的相同基础分要保留首次达成秒；否则每次重试都把 t 刷新，会悄悄让玩家后退。[1]

为什么不用一句 SQL 不行带过。 SQL 有合适的有序索引时，ORDER BY 加 LIMIT K 能高效拿头部，不是一概全表扫描。[14]真正难的是在持续改分下，任意玩家序号需要统计领先成员，索引也要处理计数与写入竞争。大 ZSET 的 ZADD、ZREVRANK 文档复杂度为 O(log N)，取 K 人是 O(log N+K)；[1][3][4][12] 这是操作复杂度，不是压测容量承诺。小榜放 SQL 完全可以，用真实延迟和更新率决定什么时候增加有序热视图。

序号与共享名次。 A6 的完整规则给每个人唯一次序，所以展示 1、2、3。若基础分为 100、100、90，competition 是 1、1、3，dense 是 1、1、2，它们都不是 ZREVRANK 的原始输出。产品要共享名次，就保留基础分统计结构来数更高人数或更高不同分值；复合 C 已经把同分拆开，不能直接拿 C 的 rank 冒充 dense。先说清奖励按唯一次序还是按并列分组，后续切桶和快照才有确定的比较器。

English

Normal path. A large board uses a Sorted Set with one fixed-format player_id member and composite C per player. Display base scores from authoritative records or decoding. Projector sets absolute values with ZADD. Top100 is ZRANGE key 0 99 REV WITHSCORES; descending ordinal position is ZREVRANK key member, plus one for display. ZRANK is ascending and has no REV. Redis 6.2 added REV to ZRANGE, not every Z command. [2][3][4]

Ties are a product choice. Equal-score ZSET members use byte order, reversed for descending reads, not insertion order. Equal base scores compare achievement seconds; within one second this chapter explicitly falls back to reverse fixed-format IDs. P7 precedes P3 at equal score and second. Zero-pad numeric IDs rather than confusing the byte order of "9" and "10" with numeric order. playerId#seq is not a generic fix: the playerId prefix already dominates comparison before seq is inspected.

Precision. Season-relative t ≤30×24×3600 = 2,592,000. Choose T=3,000,000, B=T+1, and C=S×B+(T−t), with integer S in 0..10⁶. Earlier t makes C larger for descending reads. A one-point increase adds B, exceeding the maximum tie difference T. Maximum C=10⁶×3,000,001+3,000,000 = 3,000,004,000,000. The Redis documented exact integer range includes ±2⁵³, with positive limit 9,007,199,254,740,992. Our maximum lies well inside it. [1]

Update semantics. For a high-score-only board, ZADD GT updates an existing member only when the new score is larger; it still admits new members. XX prevents additions. CH changes reporting: count additions and actual changes, not unchanged scores. A regular ZADD update returning 0 is not a failure. The mainline supports penalties and corrections, so player_version controls replacement without GT. Preserve the original achievement second when the same base score repeats, or retries silently move the player backward. [1]

Why avoid a blanket SQL rejection. An ordered SQL index can efficiently support ORDER BY with LIMIT K; it is not always a full scan. [14] The harder operation is counting everyone ahead of an arbitrary player under continuous score changes and write contention. Documented large-ZSET operations ZADD and ZREVRANK are O(log N), and fetching K members is O(log N+K). [1][3][4][12] Complexity is not measured throughput. SQL is suitable for small boards; use measured latency and updates to justify a hot ordered projection.

Positions versus shared ranks. A6 defines a total order, displayed 1,2,3. For base scores 100,100,90, competition ranks are 1,1,3 and dense ranks 1,1,2; neither is raw ZREVRANK output. Shared ranks need statistics of higher base-score players or distinct higher base scores. Composite C breaks ties, so its rank cannot pretend to be dense. State whether rewards use ordinal positions or tied groups before partitioning and snapshotting.

3 · 头部缓存与自己的附近：两种读取契约3 · Head caching and around-me: two read contracts

中文

正常路径。 Client → Board API → Redis ZSET，结果按 Redis ZSET → Board API → Client 回来。个人读取在一个有界 EVAL 内，先 ZREVRANK 得零基 r，不存在则回未上榜；存在就取 ZRANGE 的降序区间 max(0,r−5)..r+5，再带 rank+1、epoch 和已应用版本返回。区间两端包含，因此中间玩家最多得到 11 人；头部、尾部会少一些，不能为凑 11 人把边界算成负数并触发 Redis 的尾部索引语义。

故障时的用户行为。 一台 Redis 网络抖动可以在预算内重试一次；整个投影丢失时，个人读明确 503 或更新中，原绿色成功回程整条淡化。共享 head 有最后完整快照就按不超过 30 秒返回，附 as_of；没有或过期同样失败。头像服务超时不改变排名，而有序存储不可读就没有当前序号。尤其不能把 nil、timeout 和空榜混成同一种空数组，再默认每个人都是第一。

限流保护哪一边。 1,736.1 次/秒的读峰值在 Redis 故障时不能全部绕去 Score DB 做 COUNT 与排序，数据量与写入竞争没有突然消失。API 合并重复 head 请求并按榜限流，个人读的超时与并发要独立封顶；超预算直接失败。计分事务、outbox 读取和重建各留资源预算，重建不抢掉新的权威提交。读可暂不可用，是为了守住已确认事实，而不是因为排行榜可以随意忘记分数。

恢复步骤。 取得当前分数/版本的一致快照和对应 outbox 起点 W₀，在隔离的 E+1 构建全榜及版本 Hash，继续应用 W₀ 之后的事实。装载期间玩家更新仍按版本取新，旧快照不能覆盖已应用新版本。追到目标连续水位后比较人数、版本覆盖、校验和和 topK，才原子切换当前 epoch 指针。客户端一次请求固定一个 epoch，不能先在 E 定位再到 E+1 截段。旧 E 保留到在途请求完成，再按预算清理。

恢复算术。 两视图共 20M 项，若总重建与投影预算为 100,000 项/s，而基准新投影持续 5,787/s，净清空速度 94,213/s。20,000,000÷94,213≈212.3 秒是忽略读库、网络、Hash、索引和重试的理想下界，不是 p99 RTO。只用 20M÷100k=200 秒会遗漏持续新增。若新流量达到总预算，队列永远追不平，必须增加容量、放缓非关键视图或暂停该轮重建切换，不能早切一个半空榜。

6 · 赛季截止：先排空水位，后发奖励6 · Season close: drain the frontier before rewards

中文

为什么不是到点抓一次 top100。 23:59:59 提交的一笔有效结算可能还在 outbox，00:00:00 的 Redis head 不是最终事实。Projector 要把所有分区的连续 applied frontier p 推到 W。W 是向量，不是最大的自增 ID；事务 42 先提交、41 后提交时，看到 42 不能认为 41 已处理。CDC 提交位置、提交有序日志或者明确无缺口的处理集合可以表达 frontier，选择哪一种都要证明无跳洞。不能用 MAX(id) 省掉这一段证明。

冻结与快照。 所有 p 覆盖 W 才 FROZEN，旧榜停止业务变更，生成不可变 Score snapshot。快照带 season_id、snapshot_id、watermark、comparator_version 和校验结果，奖励读取它而非仍在轮询的热榜。图上的 FROZEN→FINAL 是受「快照已验证」约束的状态边，数据必须经过下面的快照路径。topK、玩家总数和版本覆盖不一致就保持未结算状态，不能绕过校验直发奖。

迟到、处罚与重算。 迟到事实在允许窗口内先接纳再进入 W；超过窗口按规则进入新赛季或拒绝，不能静默改赛季 ID。冻结后发现作弊，要由有审计记录的修正产生新 snapshot_version，明确奖励追回或差额处理，不修改已经发布的旧快照。奖励任务以 season_id、snapshot_id、player_id 去重，回调重试不能再发同一份奖。这里讲的是结算输入的稳定性，支付账本和外部付款确认在 Ch24 继续。

失败时行为。 B 分区停在 p<W，红线只回到 CLOSING，不进入 FINAL。可以继续展示带时间的旧 head，但不能把少了 B 的冠军名单叫完整结算。消费者崩溃恢复后从连续水位重放，版本门确保重投安全；权威库恢复边界不清就延迟收官。赛季结束是一项长任务，用户等待几分钟比错发冠军奖励更容易修复，等待状态也要有最老未处理事实和落后分区的监控证据。

清理与替代。 FINAL 之后先把事实、快照、比较器版本和奖励结果归档，并核验可恢复，才给旧 Redis key 过期。一次 DEL 大榜可能产生阻塞，清理应采用该部署支持的异步释放方式并测量内存峰值，不把删除当成免费动作。若产品没有奖品，仍可在明确窗口内展示近实时榜而略去奖励流程；一旦精确最终名次是合同，就必须保留冻结、水位和快照这三笔。

Mismatched topK, member count, or version coverage leaves settlement incomplete rather than bypassing validation.

Late facts, penalties, and recalculation. Accepted late facts join W within the predefined grace window. After that, route to the new season or reject according to policy without silently changing season_id. Post-freeze anti-cheat changes produce an audited new snapshot_version and explicit clawback or adjustment, never edits to the published old snapshot. Reward tasks deduplicate season_id, snapshot_id, player_id. Retried callbacks cannot duplicate rewards. Stable settlement input is here; payment ledgers and external payment confirmation continue in Ch24.

Failure. A shard B at p<W returns only to CLOSING on the red path, never FINAL. Display may retain a timestamped head, but a winner list missing B is not a complete settlement. Recovering consumers replay from the continuous frontier with version-idempotent application. An unclear authority recovery boundary postpones close. Waiting minutes is easier to fix than wrongly awarding a champion; expose oldest pending age and lagging-partition evidence while waiting.

Cleanup and alternatives. After FINAL, archive and validate recoverability of facts, snapshots, comparator versions, and reward results before expiring old Redis keys. Deleting a large key may block; use supported asynchronous freeing and measure memory peaks rather than treating deletion as free. A no-prize product may use an explicit near-real-time display window without rewards. Exact final positions require freeze, frontiers, and snapshots.

追问：把代价和故障说到具体行为Follow-ups: concrete costs and failure behavior

中文

「必须毫秒实时呢？」 先改 A4，再量同步确认和投影预算。可以在提交后等该玩家的版本追平，不把未投影说成未计分。若既要跨地域同步又要低延迟，网络距离已改变题目；不靠多画一个缓存兑现未经验证的时延。

「最高分就直接 GT 行不行？」 只保最高且不允许下降的榜可以，仍要先持久事实与对局幂等。处罚下降就换版本控制的绝对覆盖；复合 score 的达成时间也必须保留，不让相同基础分重试改变排名。

「分桶以后我排第 120 万怎么算？」 每桶按同一完整顺序计领先人数并相加，同 C 的 tie 也计入；要同一瞬间的精确值就用同快照。在线不同时间只能承诺已解释的弱一致结果，全球邻居还要跨桶候选，不是一条本地 ZREVRANK。

「为什么不每天把数据库全部灌一遍？」 能恢复不等于满足 2 秒新鲜度。基准 20M 项共享总预算的理想下界已是约 212.3 秒，数据库读放大和新写竞争还没算；正常路径增量投影，完整重建只在 epoch 损坏或升级时做。

「这题是不是可以丢分？」 由产品确认。短暂旧名次可以，已确认事实在本章不可以。即使奖励最后才算，缺失赢局也不会被一份更快的缓存找回来。排行榜与支付的耐久要求可以相近，支付额外要求资金账本和外部状态对账。

「赛季到点就 TTL？」 TTL 是释放内存，不能围住结算事实。先入口 fence、连续 W、全部投影追平、快照校验与奖励幂等，归档确认可恢复之后再清理；任何一个落后分区都让 FINAL 等待。

English

“Must it be millisecond real time?” Change A4 and measure durable acknowledgement plus projection. Waiting for the player’s projection version after commit is possible; pending projection is not failed scoring. Cross-region synchronous writes change the latency problem. A cache drawing cannot promise unmeasured latency.

“Can high scores just use GT?” A board that only increases can, with durable facts and match idempotency first. Penalties need version-controlled absolute replacement; repeated base scores preserve achievement time to avoid moving rank.

“How do I get global #1.2 million after bucketing?” Count preceding players on each bucket with the same total order, including equal-C ties, then sum. A precise single-time answer requires aligned snapshots. Live reads across times provide an explicitly weak contract; neighbors also need cross-bucket candidates.

“Why not reload the database every day?” Recoverability does not meet a 2 s freshness goal. 20M entries already have an ideal 212.3 s lower bound under the shared baseline budget, before DB read amplification and write competition. Normal operation projects increments; full epoch rebuild is for loss or migration.

“Can a leaderboard lose points?” The product decides. Briefly stale positions are allowed here; acknowledged facts are not. Final rewards cannot reconstruct lost matches from a faster cache. Payments add monetary ledgers and external reconciliation to potentially similar durability needs.

“Just set TTL at cutoff?” TTL frees memory; it does not fence facts. Admission fence, continuous W, complete projection, validated snapshot, and idempotent rewards precede cleanup after archive validation. Any lagging partition delays FINAL.
