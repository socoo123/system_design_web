概览：先写不变量，再选协调方式Overview: specify invariants before coordination

先问双跑的代价：只是多算一次，还是会破坏库存、账本或文件？锁负责协调持有者，业务资源负责拒绝不合法的写。获取成功、业务提交、释放成功是三份不同的确认。

本章以两台 Worker 竞争同一个 SKU 为例：效率去重可以接受 Redis 偶发双跑；数据正确性先看唯一约束、条件更新与短事务。跨系统的旧持有者写入，则需要可靠世代和资源端 fencing。[9]

Ask what duplicate execution costs: extra computation, or broken inventory, ledger, or file state? Locks coordinate ownership; the business resource rejects invalid writes. Acquisition, business commit, and release are separate acknowledgements.

Two workers compete for one SKU. Efficiency deduplication can accept occasional Redis overlap; correctness first uses uniqueness, guarded updates, and short transactions. Stale writers across systems need durable epochs and resource-side fencing. [9]

获取与释放：owner 只证明身份Acquire and release: owner proves identity

一条 SET NX PX 同时写 owner 和过期；释放必须把比较与删除放在一个原子操作内。收到 OK 还要检查剩余预算，超时只代表结果未知。

One SET NX PX writes the owner and expiry. Release compares and deletes atomically. Even OK needs a remaining-budget check; timeout means an unknown result.

图 1 的第 1/2 步争同一个 lock:sku:7；第 3 步 Worker 直接写 Primary，Redis 不代理 SQL。第 4 步只删自己的 owner，第 5 步 B 用新随机值重试。每次尝试使用新 owner，禁止在释放/过期后复用；下面是调用流程伪代码，runWithDeadline 只限制新派发，不实现分布式互斥。[1]

Steps 1/2 contend for lock:sku:7; step 3 writes directly to Primary, independently of Redis. Step 4 deletes only the matching owner; B retries with a fresh random value in step 5. Never reuse an owner after release/expiry. This pseudocode describes dispatch policy; runWithDeadline does not implement distributed exclusion. [1]

owner = freshRandomOwner()                  // never reuse after release/expiry
sent = monotonicNow()
reply = SET key owner NX PX 10000           // OK, busy, or unknown/error
if reply != OK:
    ownerCheckedCleanup(key, owner)         // best effort; no business work
    return NOT_ACQUIRED
remaining = 10000ms - (monotonicNow() - sent) - 200ms
if remaining <= 0:
    ownerCheckedCleanup(key, owner)
    return EXPIRED_LOCALLY
runWithDeadline(min(8000ms, remaining))      // dispatch budget, not remote rollback
finally ownerCheckedCleanup(key, owner)     // Lua below; never bare DEL

ownerCheckedCleanup 就是以下 Lua：输入一把锁和本次 owner，返回 1 表示删除，0 表示不匹配或已不存在。SETNX 后另发 EXPIRE 会留下崩溃后永不过期的键；先 GET 再 DEL 会在两步之间换任，误删 B。脚本把这一项判断放在 Redis 单实例原子执行内。[2]

ownerCheckedCleanup is the Lua below: one lock key and this owner in, 1 if deleted or 0 if absent/mismatched out. SETNX followed by EXPIRE has a crash window; GET followed by DEL can delete a successor. The script makes this check atomic on one Redis instance. [2]

-- KEYS[1]: one string lock; ARGV[1]: this attempt's random owner.
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0

获取回包丢失时不要开始业务，安全清理失败就等到期；释放超时也不能改用裸 DEL。Lua 不把 Redis 和业务库合成事务，pipeline 也不把 GET/DEL 变成原子判断。Redis 8.4 起还有 DELEX key IFEQ owner；本章用兼容旧版本的 Lua。[11]

Do not start work after a lost acquisition reply; if safe cleanup fails, await expiry. Uncertain release never justifies bare DEL. Lua is not a Redis/database transaction, and pipelining is not an atomic GET/DEL. Redis 8.4 adds DELEX key IFEQ owner; this chapter uses Lua for older versions. [11]

旧写与 fencing：资源端才是拒绝点Stale writes and fencing: rejection belongs at the resource

TTL 到期不会停止旧进程或撤回数据包。资源先持久接受 34，才会拒绝晚到的 33；发号本身不会更新外部库。

TTL does not stop an old process or recall packets. The resource rejects delayed 33 after durably accepting 34; issuing 34 alone does not update an external database.

图 2：A 持有 33 后暂停，租约过期，B 拿 34 并写入，A 的旧写随后到达。UUID 只能比较身份相等；fencing token 才表示可靠的持有顺序。资源必须把比较、业务变更和最大世代持久化放在同一原子决定中，所有写入口都执行它。[9]

以下 SQL 是 PostgreSQL 风格的教学片段：库存行事先存在，SKU 唯一，qty 非负，last_fence BIGINT NOT NULL DEFAULT 0。图上的 max_fence 对应这里的 last_fence 列。绑定正整数 amount 和正 BIGINT f；本章限定每个世代一次变更。调用方必须检查影响行数，0 行不是成功。

Deck 2: A pauses with 33, expires, B acquires 34 and writes, then A’s old write arrives. UUIDs support equality; fencing tokens order acquisitions. Every write path must atomically compare, mutate, and durably retain the maximum epoch. [9]

This PostgreSQL-style teaching statement assumes an existing unique SKU, nonnegative qty, and last_fence BIGINT NOT NULL DEFAULT 0. The diagram’s max_fence is this last_fence column. Bind positive integer amount and positive BIGINT f. We permit one mutation per epoch; check affected rows, because zero is not success.

-- Existing row: sku PRIMARY KEY, qty >= 0, last_fence BIGINT NOT NULL DEFAULT 0.
-- Positive BIGINT f is bound to a successful acquisition; one mutation per f.
UPDATE inventory
SET qty = qty - :amount, last_fence = :f
WHERE sku = :sku
  AND :amount > 0 AND :f > 0
  AND last_fence < :f
  AND qty >= :amount;

正常：last_fence=32、qty=2，f=34、amount=1 后成为 34/1；33 再来影响 0 行。同号 34 重试也被拒，但这不证明第一次成功，要按业务 operation_id 查回执。若库存不足，上面的 UPDATE 不会提升世代；而 B 尚未到达资源时，33 仍可能被接受。要求“新任开始前完成交接”时，先原子安装新世代，再用 current_fence=f 验业务写，并另做幂等/序号。[12]

Normal case: last_fence=32 and qty=2 become 34/1 for f=34 and amount=1; a later 33 affects zero rows. Retrying 34 also fails, which does not reveal the first outcome: query an operation receipt. Insufficient stock does not advance this UPDATE’s fence. Before B reaches storage, 33 may still pass. A stronger handoff installs the new epoch before work, then checks current_fence=f with separate idempotency/sequencing. [12]

发号必须与成功持有绑定Bind issuance to successful ownership

不能先拿锁再单独 INCR：A 获取后在 INCR 前暂停，过期后 B 先拿号 100；A 恢复拿到 101，旧任反而更大。单节点原子绑定能堵这个窗口，但切主丢计数仍会重用/倒退。计数不设过期并不等于持久顺序。

图中的 Coordinator 是可靠发行接口，不是 Redis INCR 改名。etcd Lock 返回持有 key，可在 etcd 事务中检查；成功持有对应 key 的创建 revision 可作候选世代，不能取无关 GET 的最新 header revision。[6][7] 还要保证独立获取不共享同一 lease/持有 key，并把世代传入外部资源。灾难恢复/重建不得回退命名空间；资源的 fence 也要和数据同耐久，不能存在易失内存里。

Do not acquire and then issue a separate INCR: A pauses before INCR, expires, B gets 100, then A resumes and gets 101. Atomic binding on one node removes that race, but failover can still lose the counter. A nonexpiring counter is not durable ordering.

Coordinator is a reliable issuance contract, not Redis INCR renamed. etcd Lock returns an ownership key usable in etcd transactions. The creation revision of the successfully held key is a candidate epoch; an unrelated GET header revision is not. [6][7] Independent acquisitions must not share the same lease/key. Carry the epoch to external storage, preserve its namespace through restore/recreation, and persist the resource fence with its data.

切主与选型：可用性不替代安全性Failover and selection: availability does not prove safety

异步切主能让两台 Worker 都记得自己拿到 OK。WAIT 改善复制安全性，不提供共识或自动回滚。

Asynchronous failover can leave two workers remembering OK. WAIT improves replication safety; it provides neither consensus nor automatic rollback.

图 3：A 的 owner 尚未复制，主节点已宕机；提升空副本后 B 的 NX 成功。两个 OK 是不同时间的历史，但客户端工作会重叠。红线是后续交互发现故障，不会撤销已经发出的业务请求。[11]

成功 SET 后，同一连接的 WAIT 返回已经确认前序写的副本数；低于目标时不开始业务，并做 owner 安全清理。WAIT 超时不撤销 SET；文档也明确已复制到多个副本的写仍可能在切主时丢失。[3] 它还增加获取耗时，必须计入剩余租期。

Deck 3: A’s owner is not replicated before the primary dies. Promotion of the empty replica lets B succeed. The two historical OK replies can cause overlapping work. The later red failure does not recall business requests already sent. [11]

After SET, WAIT on the same connection returns how many replicas acknowledged prior writes. Below the target, do not start work; clean up by owner. Timeout does not undo SET, and acknowledged replicated writes may still be lost during failover. [3] Include WAIT latency in the lease budget.

Redlock：多数成功还需有效时间Redlock: majority success still needs valid time

官方例子在 5 个独立、互不复制的 Redis 主节点用相同随机 owner 争锁，至少 3 个成功，还要扣获取耗时与时钟余量。10−0.1−0.2=9.7 s；即使 3 个成功，耗时 10.1 s 仍不能开工。失败/过期要对所有尝试节点做 owner 校验释放，包括结果未知的节点。[11]

这种多数派没有 Raft 的共同已提交日志，也不发行有序 fencing token。Kleppmann 质疑时间模型与旧写；Antirez 从相对计时、获取耗时检查等假设答辩。[9][10] 本章对正确性关键业务优先选可执行的资源不变量，不能把争议简化成“节点够多就安全”。

The official example uses five independent Redis masters with the same random owner, needs at least three successes, and deducts acquisition time plus clock margin. 10−0.1−0.2=9.7 s; three successes taking 10.1 s still cannot start work. Failed/expired attempts owner-check cleanup on every attempted node, including unknown outcomes. [11]

This majority does not share a Raft committed log or issue ordered fencing tokens. Kleppmann questions timing and stale writes; Antirez counters with relative-time assumptions and elapsed-time checks. [9][10] For correctness-sensitive work, prefer enforceable resource invariants; node count is not a proof.

何时换协调器When to change coordinators

已有 Redis、双跑可接受：用短租约降低重复率。所有状态在一个 Primary：优先短事务。跨系统领导者交接且资源支持验号：考虑共识协调。etcd 失去法定多数不能继续提交需要共识的更新；外部写仍需 fencing，内部 etcd 写可同事务检查持有 key。[6][7] 公平、可重入和持久排队都是额外契约，不能由 tryLock 推出。

Existing Redis with tolerable overlap favors short efficiency leases; co-located state favors short transactions. Cross-system leadership with resource fencing may justify consensus coordination. etcd cannot commit consensus-dependent updates without quorum. External writes still need fencing; internal writes can check ownership in the same etcd transaction. [6][7] Fairness, reentrancy, and durable queuing are separate contracts.

续租与时间：本地停止不是远端撤回Renewal and time: local stopping is not remote rollback

续租必须原子比较 owner；客户端要从请求发出前扣时间。一旦认定丢失，不允许迟到的成功响应把旧任务复活。

Renewal atomically checks the owner; the client budgets from before sending. Once ownership is considered lost, a late success must not revive that task.

图 4 的 t=10 续满 30 s，到期为 40；进程 t=11…45 暂停 34 s，超过剩余 29 s。B 在 41 获取，A 在 45 的续租必须返回 0。Redisson 默认看门狗为 30 s，查阅时源码按 timeout/3 调度；并非硬实时保证。下面 Lua 仅适用本章字符串 owner，不是 Redisson 的可重入 hash 协议。[4][5]

At t=10 renewal extends expiry to 40. A 34 s pause from 11 to 45 exceeds the 29 s remaining; B acquires at 41 and A’s renewal at 45 must return zero. Redisson documents a 30 s watchdog, with inspected source scheduling at timeout/3, not a hard real-time guarantee. This Lua uses a string owner, not Redisson’s reentrant hash protocol. [4][5]

-- Same string lock as SET NX PX; not Redisson's reentrant hash format.
-- ARGV[1]: owner; ARGV[2]: positive TTL in milliseconds, at most one day.
local ttl = tonumber(ARGV[2])
if not ttl or ttl ~= math.floor(ttl) or ttl < 1 or ttl > 86400000 then
  return redis.error_reply('invalid TTL')
end
if redis.call('GET', KEYS[1]) ~= ARGV[1] then
  return 0
end
-- Owner comparison and expiry change execute on this Redis instance atomically.
return redis.call('PEXPIRE', KEYS[1], ttl)

1 表示该 Redis 实例原子校验并续期；0 表示已失去当前 owner，错误/超时表示无法证明仍持有。这里采用失败关闭：停止派发新工作，安全清理并核对业务结果。只收到续租 OK 仍不够——回包可能晚到，本地预算也可能已过。

One means this Redis instance atomically renewed the matching owner; zero means ownership is gone. Error/timeout cannot prove ownership. This design fails closed: stop dispatch, clean up safely, and reconcile business results. Renewal OK alone is insufficient if it arrives after the local budget expires.

Java 17：一个租约的本地预算Java 17: one lease’s local dispatch budget

完整可运行类 LeaseBudget.java 用单一事件循环调用；时间均来自同一个 System.nanoTime()，10 s TTL 减 0.2 s 余量得到 9.8 s 窗口。构造器只接受明确 OK 且未过期的获取；下面是同源续租状态逻辑。限定最多一个在途续租，状态丢失不可逆，续租成功从发送时刻重算。它不连接 Redis，也不证明远端排他。

The runnable LeaseBudget.java uses a single event-loop caller and one System.nanoTime() clock. A 10 s TTL minus 0.2 s margin gives a 9.8 s window. Construction admits only explicit, timely acquisition OK. This source excerpt allows one in-flight renewal, makes loss terminal, and rebases a successful renewal on send time. It is not a Redis client or proof of remote exclusion.

    public boolean usable(long now) {
        if (now - sent < 0 || now - sent >= WINDOW) held = false;
        return held;                          // LOST is terminal for this object
    }
    public boolean beginRenewal(long now) {
        if (pending || !usable(now)) return false;
        renewalSent = now; pending = true;    // at most one renewal in flight
        return true;
    }
    public boolean finishRenewal(long now, boolean ok) {
        if (!pending) throw new IllegalStateException("no pending renewal");
        pending = false;
        // First check the OLD lease: a late OK must never resurrect it.
        if (!ok || !usable(now) || now - renewalSent < 0
                || now - renewalSent >= WINDOW) {
            held = false;
            return false;
        }
        sent = renewalSent;                   // budget from SEND, not reply
        return true;
    }
    public void abandon() { held = false; }  // cancellation/unknown renewal

获取已用 0.1 s，所以接收时剩 9.7 s；再给 8 s 工作预算，示例余量为 1.7 s。TTL/P99=10/2=5 不是最大耗时证明。客户端单调计时也修不好服务端 TTL 的墙钟跳变；200 ms 只是教学余量，不能覆盖任意时钟变化。[11]

7.9 s 发出的 SQL 可能到 12 s 才执行。Future 取消、线程中断、HTTP 断连都不证明远端回滚；租约、本地截止点、资源校验是三层不同约束。监控 busy、unknown、续租丢失、剩余时间、fence 拒绝和幂等回放，演练进程暂停、晚到请求与恢复。

Acquisition uses 0.1 s, leaving 9.7 s on receipt; an 8 s work budget leaves 1.7 s. TTL/P99=10/2=5 is not a maximum-duration proof. Client monotonic time cannot fix server TTL wall-clock shifts; 200 ms is an illustrative margin, not protection against arbitrary clock changes. [11]

SQL dispatched at 7.9 s may execute at 12 s. Future cancellation, interruption, or HTTP disconnect does not prove remote rollback. Leases, local deadlines, and resource checks constrain different layers. Monitor busy, unknown outcomes, lease loss, remainder, fence rejection, and idempotent replay; exercise pauses, late requests, and recovery.

单库替代：把不变量留在事务里Single-database alternative: enforce invariants in a transaction

如果请求记录、库存和回执在同一数据库，先考虑短事务。唯一请求号防同请求重复，库存/版本条件防不同请求冲突。

If operations, inventory, and receipts share one database, start with a short transaction. A unique operation ID prevents duplicate requests; inventory/version guards protect distinct requests.

图 5 的 op:7 占号、扣减、保存结果同事务提交。下面伪代码指定 PostgreSQL READ COMMITTED：唯一冲突等待原事务结局；DO NOTHING 后的独立 SELECT 获取新语句快照。必须核对持久回执和原载荷，不能把唯一异常直接当成功。[8][12]

Deck 5 commits the op:7 claim, debit, and receipt in one transaction. This pseudocode specifies PostgreSQL READ COMMITTED: uniqueness contention waits for the original transaction; the separate SELECT after DO NOTHING gets a new statement snapshot. Validate the durable receipt and bound payload; a uniqueness exception is not success. [8][12]

// PostgreSQL READ COMMITTED; operation_id PRIMARY KEY; all data in one DB.
// Validate amount > 0; bind op_id to canonical (sku, amount).
BEGIN
claimed = INSERT operation(op_id, sku, amount)
          VALUES (:op, :sku, :amount)
          ON CONFLICT (op_id) DO NOTHING RETURNING op_id
if claimed is empty:
    receipt = SELECT sku, amount, result FROM operation WHERE op_id = :op
    if receipt is missing: ROLLBACK; retry same op within budget
    if receipt.payload != (sku, amount): ROLLBACK; return PAYLOAD_MISMATCH
    COMMIT; return receipt.result
rows = UPDATE inventory SET qty = qty - :amount
       WHERE sku = :sku AND :amount > 0 AND qty >= :amount
result = (rows == 1 ? SUCCESS : UNAVAILABLE)
UPDATE operation SET result = :result WHERE op_id = :op
COMMIT                                      // claim + debit + receipt together
// A lost COMMIT reply is UNKNOWN: query/retry the SAME operation ID.

任意 SQL 错误都回滚事务。这里“回执不存在”只能重新尝试，不能扣库存后再补占号；回执保留覆盖约定重试/对账窗口，未完成事务不对外暴露结果。提交回包丢失时按同 op_id 查询或重试，禁止换新号再次扣减。amount 必须为正，避免负数把扣减变成加库存。

图中 op:8 是不同请求，预期 version=12 而当前为 13，因此以下更新影响 0 行。重读后是否重试由业务决定并受总预算限制；同一请求去重不能替代库存条件。

Roll back on every SQL error. A missing receipt requires retry, never debit before claiming. Retain receipts for the retry/reconciliation contract and expose only committed results. A lost commit reply is resolved with the same op_id, never a new debit ID. Require positive amount so subtraction cannot increase stock.

op:8 is distinct: expected version 12 versus current 13 makes this update affect zero rows. Reread and retry only when the business allows it within the total budget. Deduplicating one operation does not replace the stock predicate.

-- Existing row; amount is a positive integer; version is NOT NULL.
UPDATE inventory
SET qty = qty - :amount, version = version + 1
WHERE sku = :sku
  AND :amount > 0
  AND version = :expected_version
  AND qty >= :amount;

version 保护读改写依赖，qty 保护非负库存，fence 保护持有顺序，operation_id 保护同请求去重，它们可以组合但不能互换。上述事务没有外部调用；远端支付/邮件不随 SQL 回滚。跨系统副作用需要 outbox 与下游幂等，若下游均不支持，必须说明重复窗口。永久 UNIQUE 占位也不等于长任务崩溃后的可接管状态机。

Version protects read-modify-write assumptions, qty nonnegative inventory, fence ownership order, and operation_id request deduplication. They combine but are not interchangeable. The transaction has no external call: payments/mail do not roll back with SQL. Cross-system effects need an outbox and downstream idempotency, or an explicit duplicate window. A permanent unique claim is not a recoverable long-task state machine.

容量：先数命令，再找串行上限Capacity: count commands, then identify serialization

1,000 次首次争锁/s 中，800 次成功各需释放：1,000+800=1,800 命令/s。若 200 个失败者各追加 3 次尝试，且这些追加尝试均 busy，则加 600，合计 2,400；追加尝试若成功，还要另计释放。60 个持有者每 10 s 续租，平均再加 6/s，但集中续租有峰值。

20 ms 临界区的无开销上限为 1÷0.020=50 次/s。100 次/s 全想成功意味着利用率 2>1。增加 Worker 或锁节点不改变单键串行上限；缩短临界区、合并、排队，或按真正独立资源拆分。随机退避减轻冲击，不保证公平或持久任务交付。

Of 1,000 initial attempts/s, 800 successes need release: 1,000+800=1,800 commands/s. If 200 losers each make three further attempts and all remain busy, add 600 for 2,400. Additional successful retries also need releases. Sixty holders renewing every ten seconds add 6/s on average, with burstier peaks.

A 20 ms critical section has a zero-overhead ceiling of 1÷0.020=50/s. Serving all 100/s would require utilization 2>1. More workers or lock nodes do not remove per-key serialization. Shorten, batch, queue, or split genuinely independent resources. Random backoff does not guarantee fairness or durable task delivery.

面试官问“你能保证绝对互斥吗”，先把对象说清：服务端当前 key 的唯一 owner、客户端认为自己持有、资源端允许的业务变更，是三个不同观察点。我们保证资源不变量的方式是原子条件、可靠世代和幂等，而不是保证所有远端进程在同一瞬间停止。若资源根本不提供这些接口，应坦诚说明仍有哪些副作用可能重复，再讨论改产品契约。

If asked for absolute exclusion, distinguish the server’s current key owner, client ownership belief, and permitted business mutations. Atomic predicates, durable epochs, and idempotency enforce resource invariants; they do not stop every remote process at the same instant. If the resource lacks these interfaces, explain the remaining duplicate effects and change the contract.
