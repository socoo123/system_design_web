键值存储Key-value store

约 40 分钟 · 前置：Ch03、Ch05 · 6 组演进图，从复制确认到安全删除~40 min · after Ch03, Ch05 · 6 evolution decks, from replication to safe deletion

本章的三个决定Three decisions in this chapter

  • 确认什么：W 份响应怎样连接本地 WAL、可读状态和超时？
  • 读到什么：副本集合相交后，LWW 与因果版本分别保留什么？
  • 怎样恢复：漏写、旧 hint 和删除墓碑怎样安全收敛？
  • What is acknowledged: connect W replies to local WAL, visibility and timeout outcomes.
  • What is read: after set intersection, distinguish LWW selection from causal version reconciliation.
  • How to recover: reconcile missed writes, old hints and tombstones safely.

概览：固定副本、明确版本、限定成功含义Overview: fixed owners, explicit versions and bounded success

设计单地域、单 key、小 value 的 KV，默认 N=3、W=2、R=2。存可覆盖的偏好值，先接受竞争更新只选一个胜者；余额扣减与跨 key 事务不在这个合同里。第 1 组终图是全局路径：Client → Coordinator → 三个跨机架的物理 owner；第 5 组再放大副本内部。Coordinator 是一次请求的聚合角色，可以由存储节点承担。

Build a single-region, single-key, small-value KV with N=3, W=2 and R=2. Replaceable preferences may select one overwrite winner; balance deductions and cross-key transactions are outside this contract. Deck 1’s final frame is the overview: Client → Coordinator → three physical owners across racks. Deck 5 zooms into a replica. Coordinator is a per-request aggregation role and can run on a storage node.

接口为 get(key)、put(key,value,mutation_id,ts) 和带相同版本字段的 delete。同一 mutation 的内容、ID、时间戳重试时都不变；超时是结果未知。默认整值 LWW 按 (ts,id) 决胜，删除也参与比较。严格 quorum、整值 LWW 和同步 WAL 是本章教学组合，不等于 Dynamo 或 Cassandra 的完整实现；因果兄弟版本是后面的另一种接口。[1][2]

The API is get(key), put(key,value,mutation_id,ts) and delete with the same version fields. Retries preserve mutation content, ID and timestamp; timeout means unknown outcome. Whole-value LWW orders by (ts,id), including deletions. Strict quorum, whole-value LWW and synced WAL form our teaching design, not a complete Dynamo or Cassandra implementation. Causal siblings introduce an alternative interface below. [1][2]

写路径：三份发送，两份确认Write path: three sends, two acknowledgements

关键实现：只数同一 epoch 的不同副本Implementation: count distinct owners in one epoch

图第 2 帧并行发三份，第 4 帧在第二个耐久 ACK 到达时成功。伪代码输入单 key 的不可变 mutation 与总 deadline；输出已确认版本或 UNKNOWN。重复回包不能凑 W；临时 D 和本地 hint 不能算正常 owner。成功表示 mutation 已被 W 个节点按版本规则处理，不保证其 value 是全局胜者。

Frame 2 sends all three in parallel; frame 4 succeeds at the second durable ACK. The pseudocode takes one immutable mutation and an overall deadline and returns its acknowledged version or UNKNOWN. Duplicate replies cannot fill W; fallback D and a local hint are not owner ACKs. Success means W replicas processed the mutation under reconciliation; its value need not be the global winner.

# One key; fixed epoch; N=3, W=2; immutable mutation m
PUT(key, m, deadline):
    epoch, owners = placement.snapshot(key)  # distinct physical A, B, C
    send APPLY(epoch, key, m) to ALL owners in parallel
    acked = set()
    while before(deadline):
        reply = await_next_reply(deadline)
        if reply == TIMEOUT: break
        if reply.matches(epoch, key, m.id) and reply.durable:
            if reply.node in owners: acked.add(reply.node)
        if size(acked) >= 2:
            return ACKNOWLEDGED(m.version)  # not "m must be the winner"
    return UNKNOWN  # never roll back remotely applied mutations

APPLY(epoch, key, m):
    with local_key_serialization_and_membership_guard(epoch, key):
        # validate ownership/epoch; reject obsolete routing before writing
        next = winner(read_all_local_versions(key), m)  # reject conflicts first
        WAL.append(m); WAL.sync()  # I/O failure: no durable ACK
        visible[key] = next
        # recovery replays WAL through this same winner rule
        return DURABLE_ACK(node_id, epoch, key, m.id)

local_key_serialization_and_membership_guard 必须由每个副本的单 key 串行执行器/存储事务与成员 fencing 实现：从 epoch 校验到 WAL 与可读状态发布不被本地并发写或交权打断。winner 下文给出；读全本地版本包含 SST 与墓碑，不能只看 memtable。同一 guard 内先计算胜者并拒绝同版本不同内容，再写 WAL，避免把非法记录写入恢复日志。WAL sync 成功但内存发布前崩溃时，通过日志重放恢复；sync/I/O 失败不得回耐久 ACK。该锁只保护一台副本，绝不提供跨副本 CAS。[4]

The guard requires a per-key serial executor/storage transaction plus membership fencing on each replica: epoch validation, WAL work and visible-state publication must not race local writers or handoff. The winner implementation follows; local versions include SST data and tombstones, not just Memtable. Inside the same guard, compute the winner and reject equal-version conflicts before logging, so recovery never replays that invalid record. A crash after WAL sync but before publication is recovered by replay; sync/I/O failure must not produce a durable ACK. This guard protects one replica and supplies no distributed CAS. [4]

失败窗口：A 已保存，B 已保存但 ACK 丢失，协调层仍可能超时；它无法撤回远端写入。正常路径剩余 C 的投递继续由受限后台任务处理，失败留原 mutation 的 hint，冷键另靠反熵。成员 epoch 由外部受控交接协议维护；给请求加一个数字本身不能防止两个成员集合各自成功。W=1 更早确认、W=3 等全部，N 仍为 3。

Failure window: A stores the write and B stores it but loses its ACK; the coordinator can still time out and cannot undo remote mutations. Bounded background work continues delivery to C, retains original-mutation hints on failure and relies on anti-entropy for cold keys. An external controlled handoff protocol maintains epochs; adding an epoch field alone does not prevent disjoint configurations from succeeding. W=1 acknowledges sooner and W=3 waits for all; N remains 3.

容量：value 空间与复制载荷Capacity: value storage and replication payload

为什么这样选：容量落到真正的线和盘上Why: charge capacity to actual links and storage

一亿 key×1,000 B=100 GB value；乘三副本是 300 GB。教学再把 SST 空间系数设为 2，得到约 600 GB 活跃文件预算，未计 key、索引、WAL、备份和 compaction 临时重叠。若要求已规划占用最多到总容量的 80%，则 600÷0.8=750 GB，仍只是同一估算口径的总量下限。不能从“一亿”直接推出机器数，更不能用压缩后的容量再忘记乘副本。

100M keys × 1,000 B = 100 GB of values; three copies give 300 GB. A teaching SST space factor of 2 gives 600 GB of active files, excluding keys, indexes, WAL, backups and temporary compaction overlap. Keeping that planned occupancy below 80% requires 600÷0.8=750 GB, still a scoped aggregate lower bound, not a machine count.

峰值写载荷是 10,000×1 KB=10 MB/s。发送到三份副本，副本总接收约 30 MB/s，也就是 240 Mb/s；W 改成 1 或 3 都不改变这笔。若 Coordinator 自身也存一份，额外跨节点 value 复制约为两份、20 MB/s；若 Coordinator 是独立代理，则三份都穿网络。协议、索引和修复另加。网络带宽必须按实际拓扑计数。

Peak write payload is 10,000 × 1 KB = 10 MB/s. Three replica destinations receive 30 MB/s total, or 240 Mb/s, whether W=1 or W=3. If Coordinator stores one copy, extra cross-node value copies are about 20 MB/s; an independent proxy sends all three over the network. Add protocol, indexing and repair separately rather than calling every topology “30 MB/s replication bandwidth.”

读路径：集合相交，还要正确解释版本Read path: intersect sets, then interpret versions

关键实现：收齐 R，再比较；空值和失败分开Implementation: collect R, then reconcile; absence is not failure

固定全集 U={A,B,C}，完成写 W={B,C}，读 R={A,B}，至少相交 W+R−N=1 个节点。要选出 v2，还需版本顺序正确、数据未丢、没有覆盖它的更新、成员配置相同。图只读两份完整 value，实际产品也可先读摘要。

Within U={A,B,C}, completed write W={B,C} and read R={A,B} overlap in at least W+R−N=1 replica. Selecting v2 also needs correct version order, no data loss or superseding update, and the same membership. This diagram reads two full values; products may first read digests.

# Full values, including tombstones; fixed N=3, R=2
GET(key, deadline):
    epoch, owners = placement.snapshot(key)
    targets = choose_two_distinct(owners)
    send READ(epoch, key) to targets in parallel
    replies = map()  # one valid response per physical replica
    while size(replies) < 2 and before(deadline):
        reply = await_next_reply(deadline)
        if reply == TIMEOUT: break
        if reply.valid_for(epoch, key) and reply.node in targets:
            replies[reply.node] = reply.record  # absence is a valid result
    if size(replies) < 2: return UNAVAILABLE  # do not claim NOT_FOUND
    best = fold(winner, replies.values, ABSENT)
    enqueue_bounded_repairs(key, best, replies)  # original version, no wait
    if best == ABSENT: return NOT_FOUND
    if best.deleted: return NOT_FOUND(best.version)  # retain tombstone
    return VALUE(best.value, best.version)

READ 从副本一致的本地快照返回最大版本或不存在，且校验 epoch；不是随机拿一张 SSTable。后台修复复用 APPLY 并保留版本，队列满或修复失败不伪装成成功收敛，交由反熵补齐。NOT_FOUND 也可能来自获胜墓碑，必须保留其版本；没收够 R 是 UNAVAILABLE。

READ returns the reconciled maximum version or absence from a consistent local snapshot and validates the epoch; it does not pick an arbitrary SSTable. Background repair reuses APPLY with the original version. Queue overflow or repair failure does not imply convergence; anti-entropy must cover it. NOT_FOUND may result from a winning tombstone whose version is retained. Fewer than R replies means UNAVAILABLE.

关键反例：2+2>3 仍可能先读新、再读旧Counterexample: 2+2>3 can still read new, then old

起初 A/B/C 都是 v1；一次未完成的写只到 A，留下 v2。读①取 {A,B} 返回 v2；异步修复尚未执行时，读②取 {B,C} 返回 v1。两次都满足 R=2，却回退了。第 2 组选择返回后异步修复，只是教学策略；Cassandra 文档的默认 BLOCKING 读修复会等待修复达到一致性级别，用来防止这类 quorum 读回退，仍不能据此把 LWW 称为完整线性一致协议。[9]

Initially A/B/C hold v1. An incomplete write places v2 only on A. Read 1 from {A,B} returns v2; before async repair, read 2 from {B,C} returns v1. Both satisfy R=2 but regress. Deck 2’s repair after the response is our teaching policy. Cassandra’s documented default BLOCKING repair waits for the configured consistency level to prevent this kind of quorum-read regression; it still does not turn LWW into a complete linearizability protocol. [9]

容量与热点：按副本读而非只按客户端读算Capacity and hotspots: count replica reads

为什么这样选：读放大和热点要一起算Why: account for read amplification and hotspots

图采用两份完整 value 回给 Coordinator 的简化模型。读出口是 50,000×1 KB=50 MB/s，约 400 Mb/s；副本到 Coordinator 却是 50,000×2×1 KB=100 MB/s，约 800 Mb/s。不能只算客户端返回，也不能以为读写比 5:1 就只有五倍存储操作。产品可用摘要加一份完整结果降低正常带宽，摘要不一致再拉数据；图没有画摘要协议，所以这个 100 MB/s 是本图口径，不是 Cassandra 所有读请求的固定值。

The simplified diagram returns two full values. Client egress is 50,000 × 1 KB = 50 MB/s, about 400 Mb/s; replicas send 50,000 × 2 × 1 KB = 100 MB/s, about 800 Mb/s, to Coordinator. A 5:1 client read/write ratio does not mean only five times the storage work. A digest plus one full value can reduce normal bytes, fetching data on mismatch. Our 100 MB/s belongs to the drawn model, not every Cassandra read.

A8 的十台机器在均匀分布下，每台平均 100,000÷10=10,000 次副本读/秒，低于 12,000 的计划预算。若一个共享 key 吃掉 20% 客户端读，它每秒有 10,000 次；剩余 40,000×2÷10=8,000 次普通副本读分到每台。热点固定读两台，这两台各约 8,000+10,000=18,000，超过预算 50%。即使三份均摊热点的两份读取，8,000+20,000÷3≈14,667 仍超预算。多加不拥有这个 key 的机器帮不上忙。

With A8’s ten machines, uniform traffic averages 100,000÷10=10,000 replica reads/s each, below the 12,000 budget. A shared key receiving 20% of client reads gets 10,000/s. Ordinary traffic contributes 40,000×2÷10=8,000 per machine. Two fixed hot targets each get 18,000, 50% above budget. Even spreading two hot reads across three copies yields 8,000+20,000÷3≈14,667. Adding machines that do not own the key does not help.

热点缓存要声明旧值窗口；合并相同读取、限在途 RPC 与重试次数可减少放大。增加不拥有该 key 的机器不能分担它；增加读副本也要重定义放置、新鲜度和修复。

Hot-key caching needs a staleness contract. Coalescing reads and bounding in-flight RPCs/retries reduce amplification. Machines that do not own the key cannot serve it; adding read replicas changes placement, freshness and repair.

分区：严格 quorum 与 sloppy quorum 改了什么Partition: what strict and sloppy quorum change

切换策略，就要重写成功条件Changing policy changes the success condition

严格：正常 owner={A,B,C}，只剩 A 可达，1<W=2，因此不能确认成功；超时仍是结果未知。B/C 一侧若有入口和两份可达副本，可以继续。Sloppy：扩展候选里借 D 临存，假设 {A,D} 都耐久才能确认；D 保存原 mutation 和目标 owner，恢复后交还。它不保证任意故障下都可用。[1]

Strict: owners={A,B,C}; only A is reachable, so 1<W=2 and success cannot be acknowledged. Timeout still means unknown outcome. The B/C side can continue if it has an entry point and both replicas. Sloppy: fallback D stores the original mutation and intended owner; only durable {A,D} responses meet this alternative threshold. Handoff follows recovery. This does not promise availability under every failure. [1]

写 {A,D} 与读 {B,C} 交集为空。D 不属于原三副本全集，2+2>3 的证明前提已经换掉。读取需接受旧值/冲突，或等待交还修复。Cassandra 普通 QUORUM 的 hint 不能代替正常副本 ACK；有 hinted handoff 不等于采用 Dynamo sloppy quorum。超时/Gossip 只是怀疑不可达，也不能授权各节点自行改成员再重新计算多数。[3]

Write {A,D} and read {B,C} are disjoint. D is outside the original universe, so the 2+2>3 proof no longer applies. Accept stale/conflicting reads or wait for handoff and repair. Cassandra ordinary QUORUM does not count a hint as an owner ACK; hinted handoff does not imply Dynamo sloppy quorum. Timeout/gossip expresses suspicion, not authority for each node to invent a new majority. [3]

冲突：LWW 得到一个胜者，代价是丢掉其他更新Conflicts: LWW selects one winner and discards other updates

实现一：LWW 的确定性胜者Implementation 1: a deterministic LWW winner

下面是可运行 Java 17 示例的纯函数节选（片段需放入完整类中编译）；输入同一个 key 的两份不可变 mutation，输出胜者。ASCII mutation_id 全局唯一且不能改内容；同版本内容不同直接拒绝。按 (timestamp,id) 排序是本章规则，不冒充 Cassandra 的同戳决胜细节；Cassandra 按单元格处理，本例按整个 value。[2]

This is a pure-function excerpt from the runnable Java 17 example (compile it inside the complete class): two immutable mutations for one key produce one winner. ASCII mutation IDs must be globally unique and cannot change content; equal versions with unequal content are rejected. Ordering by (timestamp,id) is our rule, not Cassandra’s equal-timestamp behavior. Cassandra reconciles cells; this example reconciles a whole value. [2]

record Mutation(long timestamp, String id, String value, boolean deleted) {
    Mutation {
        if (timestamp < 0 || id == null || !id.matches("[A-Za-z0-9_-]+"))
            throw new IllegalArgumentException("invalid version");
        if (deleted != (value == null)) throw new IllegalArgumentException("value/tombstone");
    }
}
static Mutation winner(Mutation a, Mutation b) {
    if (a == null) return b;  // null means absence, not deletion
    if (b == null) return a;
    int order = Long.compare(a.timestamp(), b.timestamp());
    if (order == 0) order = a.id().compareTo(b.id()); // canonical ASCII IDs
    if (order == 0 && !a.equals(b))
        throw new IllegalArgumentException("same version, different mutation");
    return order >= 0 ? a : b;
}

正常路径 winner(v1@100,v2@200)=v2；同 mutation 重放不变，DEL@300 胜过 PUT@200。图中的 X 真实 1000、戳 1200，Y 真实 1100、戳 1100，所以后写 Y 输；W/R 不能修正排序。两个客户端读 10 后各写 11，最后仍是 11，不能把覆盖存储当原子加一。收敛不等于因果安全，也不等于保留业务意图。

Normally winner(v1@100,v2@200)=v2; repeating a mutation is idempotent and DEL@300 beats PUT@200. In the diagram X occurs at real time 1000 with timestamp 1200; later Y at 1100 has timestamp 1100 and loses. W/R cannot correct ordering. Two clients that read 10 and each write 11 leave 11, not an atomic increment to 12. Convergence is neither causal safety nor preservation of business intent.

实现二：保留兄弟版本，再带上下文写回Implementation 2: retain siblings and write with context

若不能静默丢并发版本，改为 get → siblings + context、put(value,context)。向量逐项不大且至少一项小才是祖先；[A:2] 与 [A:1,B:1] 不可比，应同时返回。应用决定合并后的 value，按分量取最大上下文，再加入新事件；这是替代 LWW 的另一份协议，不能把两者对同一记录混用。[1]

If silently losing concurrent versions is unacceptable, use get → siblings + context and put(value,context). A vector is an ancestor only when every component is ≤ and at least one is smaller. [A:2] and [A:1,B:1] are incomparable and both survive. The application chooses a merged value, joins context componentwise and adds a new event. This is an alternative to LWW, not a second rule mixed into the same record. [1]

static boolean before(Version a, Version b) {
    Set<String> actors = new HashSet<>(a.clock().keySet());
    actors.addAll(b.clock().keySet());
    boolean strict = false;
    for (String actor : actors) {
        long x = a.clock().getOrDefault(actor, 0L);
        long y = b.clock().getOrDefault(actor, 0L);
        if (x > y) return false;
        strict |= x < y;
    }
    return strict; // a is an ancestor only if <= everywhere and < somewhere
}
static List<Version> siblings(List<Version> versions) {
    return versions.stream().distinct()
        .filter(a -> versions.stream().noneMatch(b -> before(a, b))).toList();
}
// Actor is one causal writer; context includes all of its own prior events.
// Concurrent writers need distinct actors, not a shared coordinator ID.
static Version resolved(List<Version> context, String actor,
                        long reservedCounter, String applicationValue) {
    Map<String, Long> joined = new HashMap<>();
    for (Version v : context)
        v.clock().forEach((k, n) -> joined.merge(k, n, Math::max));
    if (reservedCounter <= joined.getOrDefault(actor, 0L))
        throw new IllegalArgumentException("counter must advance context");
    joined.put(actor, reservedCounter);
    return new Version(joined, applicationValue);
}

因果 writer 契约：actor 是一个独立、串行的因果写入者，后一次写的 context 必须包含该 writer 自己此前全部事件；并发 writer 必须用不同 actor，不能共用 Coordinator ID。这个限制不能仅靠“计数器唯一递增”替代。reservedCounter 必须由 actor 的持久、串行分配器按 key 保证唯一且严格递增，并大于 context 中本 actor 的分量；重启或新实例不可重用 actor+counter。相同向量只能对应同一事件/value；入口必须验证它，纯函数不负责网络信任。返回的 context 必须由客户端原样携带，不能用服务器未曾读给客户端的新版本替换。否则会把未见更新误标为祖先。

Causal writer contract: an actor identifies one independent, serialized causal writer. Each new context must include all of that writer’s prior events; concurrent writers need distinct actors, never a shared coordinator ID. Unique increasing counters alone are insufficient. A durable serialized allocator must reserve a unique, increasing counter per actor/key above the actor component in the context; restart or replacement must not reuse actor+counter. One vector identifies one event/value, enforced at admission; pure functions do not authenticate clients. A write must carry the context actually returned to the client, not newer unseen server context, or it can incorrectly classify unseen updates as ancestors.

违反契约的反例：两客户端同读 [A:1] 却共用 actor B，分别发 [A:1,B:1] 与 [A:1,B:2]，后者会错误支配前者，丢掉未见并发。测试刻意展示这个失败；换成两个独立 writer actor 才保留两份。纯函数不实现调用方历史校验，不能把它直接部署成共享协调节点发号器。正常合并两兄弟得到 [A:2,B:2]，会覆盖它们；未见的 [A:3] 仍并发保留。applicationValue 不是自动集合并集：简单并集可能把购物车删除的商品加回来。计数可选合适的 CRDT；库存非负、唯一出售等不变量仍需协调。此示例不实现副本存储、计数器分配、向量截断或因果一致的完整读写协议。

Contract-violation counterexample: two clients both read [A:1] but share actor B, producing [A:1,B:1] and [A:1,B:2]. The latter falsely dominates the former and loses unseen concurrency. A test deliberately shows this failure; distinct writer actors retain both. These pure functions do not validate caller history and cannot be deployed as a shared coordinator’s version allocator. Merging the two siblings yields [A:2,B:2] and replaces both; unseen [A:3] remains concurrent. applicationValue is not an automatic set union: union can resurrect removed cart items. Appropriate CRDTs can model counters; nonnegative stock or unique-sale invariants still need coordination. This example implements neither replica storage, counter allocation, vector truncation nor a complete causally consistent I/O protocol.

Run javac --release 17 VersionedKv.java && java VersionedKv, with no dependencies. Full source and counterexample tests; source parity checks cover all four page snippets.

节点内 LSM：前台确认，后台还带宽与空间的账Local LSM: foreground confirmation, background bandwidth and space

本地确认边界：sync + 可读，不等 flushLocal acknowledgement: sync plus visibility, before flush

APPLY 的两行落在图第 2、3 帧：WAL 同步完成，再把版本合并到可读状态，才 ACK。追加到 OS 缓存不等于掉电耐久。RocksDB 默认非同步写和显式 sync=true 不同，本章选择后者对应的耐久合同。崩溃恢复重放 WAL；冻结 memtable 后后台 flush，新 SST 安全发布且覆盖日志后才能回收相关 WAL。[4][5]

The APPLY steps correspond to frames 2 and 3: sync the WAL, reconcile into readable state, then ACK. Appending to an OS buffer is not power-loss durability. RocksDB’s default non-sync writes differ from explicit sync=true; our contract selects synced durability. Recovery replays WAL; frozen Memtables flush in the background. Safely publish SSTs covering the data before retiring the corresponding WAL. [4][5]

读路径：Bloom 只能排除某个候选文件Read path: Bloom excludes an individual candidate file

一次本地 GET 先查内存中的候选版本，再查可能含 key 的文件。对于本章按 mutation 戳比较的 value，不能因为内存里碰巧有一份就无条件提前结束：重放或时钟偏斜可能把旧戳写进新文件，墓碑也要参与比较。具体引擎可根据索引、序列与版本规则安全地缩小搜索；Cassandra 的按单元格 reconciliation 和 RocksDB 的序列号快照是不同语义。面试先说比较正确，再讨论优化到少读几个文件。

A local GET checks memory candidates and relevant files. With our mutation-timestamp semantics, a memory hit cannot unconditionally terminate: replay or clock skew may put an older timestamp in newer storage, and tombstones participate. Engines can safely prune using indexes and their own version rules. Cassandra cell reconciliation and RocksDB sequence snapshots are different semantics; establish correctness before pruning.

普通 Bloom 对一个正确构建的文件索引，只会给“肯定不在”或“可能在”；前者跳过该文件，不代表全库不存在，后者还要查索引与数据。教学按 10 个阴性文件、每个 1% 假阳性，期望额外探查 10×0.01=0.1 个文件；若还假设误报独立，至少一次误报概率是 1−0.99¹⁰≈9.56%。这是阴性点查的期望，不是所有查询的 p99。官方表给约 9.9 bit/key 对应约 1% 误报；按 10 bit 口算：100,000,000×10÷8=125,000,000 B=125 MB，三份约 375 MB，未计多版本和开销。[6]

A correctly built ordinary Bloom filter says definitely absent or possibly present in one file. Absence skips that file, not the database; a positive still needs lookup. For ten absent files at 1% false positives, expected extra probes are 10×0.01=0.1. With independent false positives, any false positive occurs with 1−0.99¹⁰≈9.56%, not a p99 bound. The official table gives about 9.9 bit/key for 1%; rounding to 10 gives 100,000,000×10÷8=125,000,000 B=125 MB per filter, or 375 MB for three copies, before versions and overhead. [6]

后台容量：写放大与积压如何反压前台Background capacity: amplification and backpressure

为什么这样选：吞吐快，不等于写放大小Why: high throughput does not mean low write amplification

顺序日志和内存批次把随机改页的工作移出前台，但 SSTable 会在 compaction 中被读取、合并和重写。A7 把累计 SST 输出字节除以逻辑 value 写入字节定义为教学写放大 10：10 MB/s×3×10=300 MB/s 全集群 SST 输出，约 2.4 Gb/s 等价字节速率。它是磁盘输出口径，不是网络复制需求；如果 WAL 也写相同载荷，再加约 30 MB/s，compaction 的输入读取另算。不要把空间系数 2 当成写放大 2。

Logging and memory batches move random-page work out of the foreground, but compaction reads, merges and rewrites SST data. A7 defines teaching SST write amplification as cumulative SST output divided by logical value bytes: 10 MB/s×3×10=300 MB/s cluster-wide, equivalent to 2.4 Gb/s of bytes, not network replication. Add about 30 MB/s if WAL writes the same payload, plus compaction reads. Space factor 2 is not write amplification 2.

长时间写入时，平均后台处理速率必须盖住输入。否则冻结 memtable 和 L0 文件越积越多，读需要查更多候选，内存与临时空间也上升，最后前台被限速或停写。给 compaction 留独立 I/O 和空间余量、控制并发与流入，比只把“峰值写入很快”写在答案里完整。写压力很小、点查延迟严的场景，可以比较 B+Tree；LSM 的选择是把成本在时间上搬到后台，不是把成本删除。

Under sustained writes, background throughput must cover input. Otherwise immutable Memtables and L0 files accumulate, reads face more candidates and memory/temporary space rise until writes throttle or stall. Reserve I/O and space and control concurrency and inflow. Low-write, tight point-latency workloads may prefer a B+Tree; LSM moves cost to the background rather than deleting it.

修复与删除：旧副本回来以后，不能让数据复活Repair and deletion: returning replicas must not resurrect data

修复复用版本比较，不能制造新业务写Repair reuses reconciliation; it does not create a new write

第 3 帧 hint 保存原 mutation 与目标 C，第 4 帧恢复后通过 APPLY 重放、收到确认再清记录。PUT@200 不能换成“重试时刻”400，否则会赢过 DEL@300 并复活；DEL@300 也不能改成更晚的删除，否则可能误删合法重建。Java 的 winner 与幂等/旧 hint 反例验证了这条规则。[3]

Frame 3’s hint retains the original mutation and target C. Frame 4 replays it through APPLY and clears the record after acknowledgement. Retimestamping PUT@200 at retry time 400 defeats DEL@300 and resurrects data; retimestamping DEL@300 can erase a valid later recreation. The Java winner and retry/old-hint scenarios check this rule. [3]

本章假设本地 hint 保留 1 h；这不是 Cassandra 的默认配置。官方 max_hint_window=3h 限定节点故障后继续生成新 hint 的窗口，不能简化成每条 hint 恰好存 3 h。hint 与读修复都是尽力而为；冷键、丢失的 hint、长故障需要完成范围反熵。Merkle tree 只定位差异，实际记录还要传输并比较。[3]

We assume local hints retained for 1 h; this is not a Cassandra default. The documented max_hint_window=3h bounds how long new hints are generated after a node fails, not an exact three-hour lifetime for every hint. Hints and read repair are best effort; cold keys, lost hints and long failures need completed range anti-entropy. Merkle trees locate differences; actual records still need transfer and reconciliation. [3]

删除不等于缺失；清墓碑需要覆盖证据Deletion is not absence; purging needs coverage evidence

A/B 的 DEL@300 胜过 C 的 v2@200。若把前两份直接抹空，winner(ABSENT,v2)=v2，修复就复活旧值；TTL 也必须有可传播的过期/删除信息。教学墓碑 7 天、离线最长 1 天、修复最长 2 天，2+1=3<7 只留下 4 天余量，并没有证明删除已经传播。[7]

DEL@300 on A/B beats C’s v2@200. Physical erasure yields winner(ABSENT,v2)=v2, resurrecting old data; TTL also needs propagatable expiry/deletion metadata. Teaching retention is seven days with one-day outage and two-day repair bounds: 2+1=3<7 leaves four days of margin, without proving deletion has propagated. [7]

  • 副本覆盖：相关范围、当前成员与交接/临时副本的修复实际成功；超过允许离线期的副本隔离重建后再接入。
  • 本地覆盖：compaction 包含墓碑及可能含更旧数据的相关文件，避免旧 SST 重新暴露值。
  • 全部旧写来源：客户端超时重试、在途/迟到 RPC、hint、旧备份和退役副本都不能把删除前的 mutation 重新注入。仅修完当前副本和旧 SST 不够。
  • Replica coverage: repair actually completed for relevant ranges, current membership, handoff and fallback copies; isolate and rebuild over-age replicas before serving.
  • Local coverage: compaction covers the tombstone and relevant files that may contain older data, so old SST data cannot reappear.
  • All stale-write sources: client retries after timeout, in-flight/delayed RPCs, hints, old backups and retired replicas must not inject pre-delete mutations. Repairing current replicas and old SSTs is insufficient.

本章代码不实现墓碑 GC，默认保留删除记录。反例：三份都已收到 DEL@300，随后全部清空墓碑；超时客户端合法重试原 PUT@200，此时 winner(ABSENT,PUT@200) 仍会复活值。若不能证明所有旧 mutation 都有受强制执行的寿命上限并已排空/拒绝，就不能完整清除删除历史。可保留持久删除水位并让所有写入口拒绝不高于水位的 mutation，但它本质上仍是压缩墓碑，需要与数据同耐久；本章未实现该协议。Cassandra 文档默认 gc_grace_seconds=864000，即 10 天；到期后仍由 compaction 检查清理条件。only_purge_repaired_tombstones 是另外的可选限制，不应误说所有配置都会自动验证整个集群修复成功。复制不能代替历史备份，备份恢复也必须遵守删除与成员边界。[7]

This chapter implements no tombstone GC and retains deletion records by default. Counterexample: all three replicas receive DEL@300 and later erase every tombstone; a timed-out client legally retries the original PUT@200, and winner(ABSENT,PUT@200) resurrects the value. Without enforced lifetime bounds and drainage/rejection for every old mutation, deletion history cannot be completely discarded. A durable deletion watermark checked at every write entry point can reject mutations at or below it, but that is still a compact tombstone and must survive with the data; this protocol is not implemented here. Cassandra documents gc_grace_seconds=864000, or ten days; compaction still determines eligibility after expiry. only_purge_repaired_tombstones is an additional optional restriction, not proof that every configuration automatically verifies whole-cluster repair. Replication does not replace historical backups, and restores must respect deletion and membership boundaries. [7]

追问：会话新鲜度、Redis Cluster 与故障域Follow-ups: session freshness, Redis Cluster and failure domains

追问怎么接：让每个答案落回一个条件Follow-ups: connect each answer to a condition

要立刻读到自己刚写的值，怎么改？How do I immediately read my own write?

先问“刚写的”指收到成功还是结果未知。固定全集、版本顺序正确且没有并发覆盖时，本章 3/2/2 可以读到已经完成的那次写；分区替代路径和错误时钟不在这个证明里。需要跨请求的读写会话契约，可以让成功响应携带版本并让读侧检查至少见到该版本，否则等待或返回失败。若要求条件更新和所有客户端的实时顺序，改用相应的协调协议，不能只调 R。

Clarify whether the write succeeded or timed out. Under fixed membership, correct ordering and no concurrent overwrite, 3/2/2 can read the completed write. Sloppy fallback and clock errors are outside that proof. A session may carry a returned version and require reads to observe it or wait/fail. Conditional updates and global real-time order require coordination, not just a larger R.

Redis Cluster 也是 KV，可以直接当这张图吗？Can Redis Cluster replace this diagram?

它有 16,384 个 hash slot，槽由 primary 负责，并异步复制到 replica；这是另一种复制与故障转移契约。官方规范写明已确认写仍有可能在复制尚未到副本、primary 故障后丢失。因此不把它笼统说成“严格 CP”或拿来证明本章的多写副本 quorum。系统都能存 key/value，不代表 Client→Coordinator→三个对等副本的路径能原封不动套上。[8]

Redis Cluster has 16,384 hash slots served by primaries with asynchronous replicas, a different contract. Its specification allows acknowledged-write loss when a primary fails before replication completes. Avoid calling it strictly CP or using it to prove peer-replica quorum behavior. A shared key/value interface does not imply the same replication diagram. [8]

复制放大、空间放大、写放大能只用一个倍数吗？Can one factor represent replication, space and write amplification?

不能。三副本把逻辑 value 数乘 3；SST 空间系数 2 描述同时保留的文件；SST 写放大 10 描述一段时间累计输出。100 GB×3×2≈600 GB 与 10 MB/s×3×10=300 MB/s 的单位不同。新增记录还要看留存与增长，不能用峰值 PUT 数直接乘一年，本章 PUT 中很多是覆盖已有 key。持续吞吐、存量与新增速度是三种预算。

No. Three replicas multiply logical copies; SST space factor 2 describes resident files; SST write amplification 10 describes accumulated output. 100 GB×3×2≈600 GB and 10 MB/s×3×10=300 MB/s have different units. New-record growth and retention are separate; peak PUTs include overwrites, so multiplying them by a year does not estimate retained keys.

确认两份，是不是再也不会丢？Do two acknowledgements guarantee no later loss?

只有在 ACK 真正耐久、故障域独立程度满足需求、剩余副本及时修复的边界内，才能说抵御指定故障。两台机架同时损坏、两份都只有未同步缓存、错误合并覆盖正确值，是不同问题。备份还要覆盖误删与长期灾难，并定期验证恢复；复制把同一个删除发到三份，不能替你保留删除前的历史。收尾时说明这些边界。

Durable ACKs, suitable failure domains and timely repair resist specified failures. Two rack losses, unsynced buffers and incorrect reconciliation are distinct risks. Backups cover accidental deletion and long-term disaster and require restore verification; three replicated deletes do not preserve prior history. State these bounds when closing.

面试复盘：沿一条请求说出边界Recap: walk one request and state its boundaries

按这条顺序口述：固定 owner 与 epoch → 并行发 N、等 W 个耐久 ACK → 读 R 份比较版本 → 严格分区失败或明确切换 sloppy → 按原版本修复 → 用覆盖证据清墓碑。遇到“强一致吗”先给未完成写的读回退反例，再给 LWW 时钟反例；遇到“不会丢吧”先定义掉电、故障域与恢复范围。

Explain fixed owners and epoch → parallel N sends and W durable ACKs → R reads and version reconciliation → strict partition failure or explicit sloppy alternative → original-version repair → tombstone purge with coverage evidence. For “strongly consistent?”, show incomplete-write read regression and then LWW clock skew. For “never loses data?”, first define power loss, failure domains and recovery scope.
