先明确交互方式，再约定接口和传输协议Ask about interactions, then select contract and transport

选协议前，我先确认三个问题：调用方能否统一升级，双方是否都要持续发送数据，断线后是继续查看原有状态，还是重新执行动作。公开接口先考虑 HTTP 资源接口，调用方受控的服务间通信可以用 gRPC；需要频繁双向交互时选 WebSocket，单向事件订阅可以用 SSE。HTTP/3 则是 HTTP 交互的传输选择。REST、gRPC、WS、SSE 和 QUIC 不是一条必须逐级升级的链。

Ask three questions: can callers upgrade together, must both sides send continuously, and does reconnect resume observation or execute an action again? Public APIs start with HTTP resource contracts; controlled services may use gRPC. Frequent duplex interaction favors WebSocket and one-way events may use SSE. HTTP/3 is a transport choice for HTTP interactions, not a REST→gRPC→WS→SSE→QUIC upgrade ladder.

Client sends GET /items/42. REST 的约束与无状态REST constraints and stateless interaction

为什么要讲资源与表示，不能只列四个动词Why a resource contract is more than four verbs

REST 是 Fielding 在 2000 年论文第 5 章提出的一组架构约束，包括客户端与服务端分离、无状态交互、缓存、统一接口、分层，以及可选的按需代码。[1] 统一接口还要求资源标识、通过表示进行操作、自描述消息和超媒体驱动状态。常见的 HTTP JSON API 借用了这些规则，但使用 JSON 不等于完整满足 REST。面试时，先说明资源如何标识、表示包含什么、状态如何表达、客户端如何导航，再谈具体动词，才能解释架构上的选择。

Fielding’s 2000 chapter 5 defines REST through client/server separation, stateless interaction, cache, uniform interface, layering and optional code-on-demand. [1] The interface includes resource identity, representations, self-description and hypermedia. HTTP JSON APIs often borrow these rules; JSON alone does not establish REST. Explain resource, representation, status and navigation before listing verbs.

无状态交互要求每个请求携带理解这次请求所需的上下文，并不要求服务没有数据库，商品库存仍然可以持久保存。把会话放进共享库，能让任意副本接收请求，却不自动满足严格的 REST 会话约束。这种设计也有代价：公开表示和认证信息需要反复携带，中间层必须按接口约定理解字段。对于内部专用批处理，直接定义一个明确的 RPC 方法，可能比通用资源表示更合适。

Stateless interaction requires sufficient context in each request, not an absence of databases. Inventory remains durable. Shared sessions can make replicas interchangeable without automatically meeting strict REST session constraints. Public representations/authentication repeat context and intermediaries must interpret the contract; an internal batch operation may benefit from a specific RPC instead.

失败行为：安全、幂等和结果查询不是一回事Failure: safety, idempotency and result lookup differ

HTTP 语义区分安全（safe）与幂等（idempotent）：GET 不应被设计成扣款，PUT、DELETE 的幂等则是说，重复相同请求产生的预期效果相同。[2] 第二次 DELETE 可以返回不同状态，幂等不要求两次响应的字节完全一致。创建或扣款的 POST 若要安全重试，业务需要把操作键、参数摘要、结果与业务动作一并原子保存；这是应用提供的保证，不是 POST 自带的属性。如果首个请求已经提交，回程却断了，客户端只能认定结果未知。此时应沿用原操作身份查询回执，盲目换一个键可能真的再执行一次。

HTTP distinguishes safety from idempotency: GET should not implement charging; PUT/DELETE idempotency concerns repeated intended effects. [2] A second DELETE may have a different response. Retriable POST mutations need an application transaction binding operation key, argument digest, result and effect. If commit succeeded but the reply was lost, query using the original identity; a new key can execute again.

共享缓存还要正确处理 Cache-Control、Vary 和认证规则。这里只示例公开响应 public, max-age=30；私有数据明确禁止共享，不能因为 URL 相同就认定资源表示也相同。ETag 是验证器，条件请求得到 304 后，应按缓存规则更新已有表示的元数据。[2][3] 304 不携带新的业务正文，也不允许缓存自行猜测、延长新鲜度。机制与权威事实的详细边界见 Ch38；这里先确保请求、验证与回程都遵守授权规则。

Shared reuse must honor Cache-Control, Vary and authentication. This exercise uses public, max-age=30; private data has an explicit nonshared policy. Equal URLs alone do not prove equal representations. ETag validates; a 304 updates stored metadata under caching rules. [2][3] It is neither a fresh business body nor permission to invent renewed freshness. Ch38 covers the deeper authority boundary.

内部 gRPC：类型约定与截止时间都要传到下游Internal gRPC: propagate schema and deadline together

一次 RPC 调用要遵守两层约定The two contracts of one RPC hop

Gateway 接收公开 JSON 请求后，通过生成的 stub 调用 App 的业务查询。App 返回 protobuf 消息与最终 RPC 状态，Gateway 再将它们映射为 HTTP 状态和公开表示。gRPC 提供一元调用（unary）、服务端流（server-stream）、客户端流（client-stream）和双向流（bidi）四种调用形式；流内消息有序，不代表业务已经落盘。[4] 本图只展开一跳调用，不需要为了展示内部系统而把每个业务字段都拆成微服务。选择 gRPC 的理由应是共享消息结构、支持跨语言客户端或内部流式调用，而不能在没有测量的情况下认定二进制一定更快。

Gateway maps JSON into a generated stub call to App, then maps the protobuf result and final RPC status back to public HTTP. Unary, server-stream, client-stream and bidi are four RPC shapes; ordered messages do not imply durable business acceptance. [4] Keep one hop rather than splitting every field into a service. Shared schema, language support and internal streaming justify the switch; “binary is always faster” does not.

原生 gRPC 的常见协议约定基于 HTTP/2，一条连接可以承载多条 RPC 流。外层 HTTP 200 不能代替最终的 grpc-status；如果代理丢掉携带最终状态的尾部字段（trailers），RPC 失败就可能被误认为一次正常的 HTTP 返回。[14]gRPC-Web 为浏览器提供了另一套约定，官方示例通过 Envoy 转接。[6] 浏览器的 fetch 没有向 JavaScript 开放任意发送原生 HTTP/2 帧、完整控制 trailers 的能力，因此不能向任意 Web 客户端无条件承诺原生 gRPC 的全部四种调用能力。

The common native gRPC contract uses HTTP/2 with multiple RPC streams on one connection. HTTP 200 is not final grpc-status; dropped trailers can hide an RPC failure. [14] gRPC-Web provides a separate browser contract and the official example uses Envoy. [6] JavaScript fetch does not expose arbitrary native HTTP/2 frames or full trailer control; do not promise every native streaming shape to every web client.

消息结构演进：能解析还不够Schema evolution: parsing is insufficient

字段号要保留，时间预算也不能重新算起Why neither field tags nor remaining time can restart

protobuf 用字段号标识线路上的字段。删除字段后，要保留其字段号和名称，不能再分配给另一种含义；新增字段时，也要检查旧消费者忽略它之后是否仍然安全。[7] 例如，新版本增加了“需要人工确认”字段，旧服务即使能解析消息，也可能忽略这个字段，仍按原逻辑直接执行。这就属于语义不兼容。滚动升级期间新旧版本会共存，因此还要验证 Gateway 的 DTO 映射，不能只凭能够反序列化就验收通过。

Protobuf tags identify wire fields. Reserve deleted numbers and names; additions also need semantic compatibility checks. [7] An old consumer may parse a new approval-required field yet ignore it and execute immediately. Rolling upgrades must support coexistence, and Gateway DTO mapping is part of contract validation. Successful deserialization is insufficient.

A2 给一次调用分配的总预算是 300 ms。发起内部请求前已经用了 40 ms，再为回程预留 20 ms，下游就只剩 300−40−20=240 ms。继续调用其他服务时，还要扣除后续实际耗时，每一跳不能重新获得 300 ms。gRPC 文档建议显式设置截止时间，并在传播时扣除已用时间；应用派生的工作也需要主动响应取消。[5] 图中红色的失败结果逐跳返回客户端。取消能停止不再需要的工作，却不能撤销已经提交的数据。

A2 starts at 300 ms; after 40 ms elapsed and a 20 ms return reserve, downstream has 300−40−20=240 ms. Further calls deduct additional elapsed work. gRPC recommends explicit deadlines and propagation of remaining time; spawned application work must cooperate with cancellation. [5] Red failure returns hop by hop. Cancellation stops unwanted work but does not undo committed data.

关键实现：尝试次数增加，时间预算不会重新开始Implementation: attempts consume the original budget

下面是可运行的 Java 17 代码摘录，仅依赖标准库，对应第 3–5 帧。输入时间来自同一进程的单调时钟，输出是下游还能使用的时长。按 A2，已经用去 40 ms 时还剩 240 ms，再过 100 ms 就只剩 140 ms；到达为回程预留的边界后，不再发起下游请求。适配器必须在临发起调用前设置这段超时时长，并与入站 gRPC 上下文的截止时间取更严格的限制。本地 nanoTime 的计时起点不能跨机器传播。[5 Deadline Propagation]

This runnable Java17 excerpt uses only the standard library, covering frames 3–5. Inputs use one process-local monotonic clock; output is a remaining duration. A2 leaves 240 ms after 40 ms, then 140 ms after another 100 ms. The reserve boundary prevents dispatch. Apply this timeout immediately before the call, capped by the incoming gRPC context deadline; never transmit a local nanoTime epoch. [5 Deadline Propagation]

record Budget(long startedNanos, long totalNanos, long returnReserveNanos) {
    Budget {
        if (totalNanos <= 0 || returnReserveNanos < 0
                || returnReserveNanos >= totalNanos) {
            throw new IllegalArgumentException("invalid budget");
        }
    }

    long downstreamNanos(long nowNanos) {
        long elapsed = nowNanos - startedNanos;
        if (elapsed < 0) {
            throw new IllegalArgumentException("non-monotonic clock");
        }

        long usable = totalNanos - returnReserveNanos;
        return elapsed >= usable ? 0 : usable - elapsed;
    }

    boolean canStart(int attemptsStarted, boolean retrySafe, long nowNanos) {
        return attemptsStarted >= 0 && attemptsStarted < 2
                && (attemptsStarted == 0 || retrySafe)
                && downstreamNanos(nowNanos) > 0;
    }
}

同一操作要沿用同一个 Budget、操作键和尝试总计数。retrySafe 只是业务已经确认可以安全重试后提供的输入，这段代码本身不提供分布式幂等保证；写入结果未知时，仍要先查询原回执。调用库的重试也计入最多两次的总量，不能让每一层各自再试两次。

Keep one Budget, operation key and total attempt counter per operation. retrySafe is an application-proven input, not distributed idempotency created by this code; query unknown writes first. Include library retries in the two-attempt total rather than granting each layer its own retries.

超时之后：何时重试，何时先查询结果Alternatives and windows: retry or query first

超时可能发生在排队时、执行前、执行中，也可能发生在提交后的回程上。如果业务写入没有原子幂等机制和回执查询，换成 gRPC 只是改变编码方式，结果未知的问题仍然存在。A3 规定同一操作总共最多尝试两次，而且共用原截止时间。第二次启动前，要检查剩余预算、失败类型是否允许重试，以及是否沿用原操作键。时间已经不足时，应直接返回失败，避免继续启动注定迟到的工作。尝试次数与成功率是两个指标；调用库与 Gateway 的重试还要统一计数，不能各自增加两次。

A timeout can occur while queued, before execution, during execution or after commit on the return path. Without atomic idempotency and result lookup, gRPC changes encoding rather than uncertainty. A3 caps total attempts at two under the original deadline. Check remaining time, retry eligibility and identity before starting the second. Too little time means fail instead of spawning doomed work. Library and Gateway retries cannot each silently multiply attempts.

内部继续使用 HTTP JSON 也合理。调用不频繁、团队间可共用的编程语言较少、现成运维工具又很重要时，统一使用资源接口的成本可能更低。gRPC 提供生成的 stub 和明确的方法定义，同时也带来消息结构发布、状态映射与代理配置成本。如果负载均衡只按连接分配，一条繁忙的 HTTP/2 连接仍会固定在同一后端；可以考虑按 RPC 选路的 L7 代理，或由受控客户端发现多个后端。扩容也不会自动分走已经开始的长流，选协议时要一起说明这条边界。

原生 EventSource 通过 GET 建立订阅，响应类型为 text/event-stream。data: 承载文本，id: 更新事件标识，空行结束一个事件，整个事件流使用 UTF-8。连接丢失后，浏览器可以自动重连，并在适用的重连请求中带回已保存的 last event ID；服务器返回 204 可以让客户端停止重连。[10] 这些规则定义了浏览器与字节流的行为；持久队列、业务确认与历史保留范围，要由应用另外设计。

Native EventSource subscribes with GET to text/event-stream. data: carries text, id: supplies identity, and a blank line ends the event; encoding is UTF-8. On reconnect a stored last event ID can be sent back, and 204 stops reconnect. [10] These are browser/framing rules, not a durable queue, business receipt or unlimited history.

本章应用用订阅范围（scope）、日志代次（epoch）和连续事件序号（seq）共同标识事件。Client 带来 E:42 时，Gateway 先验证用户是否有权访问该范围，再从 Event Log 查询 E:42 之后的事件，即 seq > 42：从 E:43 开始，包含 43，之后持续尾读。客户端负责去重，并识别序号缺口和日志代次变化。浏览器的 last event ID 只记录传输状态；处理器出错、页面崩溃或状态尚未持久保存时，都不能据它认定业务已应用。需要可靠处理时，应用还要单独保存已应用游标，并显式传回服务端，不能直接把浏览器的内部游标当作应用进度。

Our application defines scope, epoch and contiguous sequence. For E:42, Gateway verifies scope permission, reads events with seq > 42, starting at and including E:43, and tails Event Log. Client deduplicates and detects gaps/epoch changes. Browser last event ID is transport state; handler failure, page crash or unpersisted state can invalidate application progress. Reliable processing needs a separate applied cursor supplied explicitly.

关键实现：游标等于 oldest−1 时，仍能从首条保留事件开始补齐Implementation: oldest−1 can replay; pruning requires RESET

下面的 Java 17 纯判定函数对应第 5–6 帧。输入只接受应用已经处理并持久保存的游标，不能使用浏览器的传输游标。LogView 由日志权威方提供，反映同一截面的保留范围，保证 [oldest,high] 区间内的事件连续保留；authorized 是本次对订阅范围重新鉴权的结果。oldest=43 时，applied=42 可以从 43 开始补齐；applied=41 则缺少事件 42，必须 RESET。若 high=50，游标 51 超出当前范围，应明确拒绝，不能让它跳过未来事件。初次订阅要先取得快照和对应游标。

This Java17 classifier covers frames 5–6. Its input is the application's durably applied cursor, not the browser transport cursor. An authoritative, coherent LogView retains every entry in [oldest,high]; authorized is fresh scope authorization. With oldest=43, applied=42 replays from 43; 41 requires RESET because 42 is missing. Reject 51 beyond high=50 instead of skipping future events. Initial subscriptions obtain a snapshot and cursor first.

record Cursor(String scope, String epoch, long seq) {}
// LogView is a coherent view: all [oldest, high] entries are retained.
// Empty log: oldest = high + 1. Values are nonnegative, below Long.MAX_VALUE.
record LogView(String scope, String epoch, long oldest, long high) {}

enum Resume {
    REPLAY_AFTER, RESET, INVALID_CURSOR
}

static Resume resume(Cursor applied, LogView log, boolean authorized) {
    if (!authorized || !log.scope().equals(applied.scope())) {
        throw new SecurityException("scope not authorized");
    }
    if (log.high() < 0 || log.high() == Long.MAX_VALUE
            || log.oldest() < 1 || log.oldest() > log.high() + 1) {
        throw new IllegalArgumentException("invalid retained range");
    }

    if (applied.seq() < 0) {
        return Resume.INVALID_CURSOR;
    }
    if (!log.epoch().equals(applied.epoch())) {
        return Resume.RESET;
    }
    if (applied.seq() > log.high()) {
        return Resume.INVALID_CURSOR;
    }
    if (applied.seq() < log.oldest() - 1) {
        return Resume.RESET;
    }

    return Resume.REPLAY_AFTER; // Read seq > applied.seq(), then tail SAME log.
}

事件处理器失败后，怎样重建订阅：立即调用 source.close()，停止旧流自动重连，并递增应用的处理器代次（generation）。处理器串行执行，在开始本地事务前检查代次；等旧处理器提交或回滚后，再读取已提交的游标。随后用 ?after=E%3A42 创建新订阅，服务端优先校验这个应用游标，不能让自动携带的 Last-Event-ID 覆盖它。

例如，E:43 要把本地值从 100 加到 107，投影行与已应用序号必须在同一个本地数据库事务中提交。如果中途崩溃，两者一起回滚到 100/E:42；重放后再一起提交为 107/E:43。seq≤applied 的事件是重复事件，直接忽略；seq>applied+1 表示有缺口，要停止应用并恢复。这个本地事务不覆盖外部副作用。判定通过后，日志仍可能继续裁剪，因此实际读取和尾读时，要固定所需历史的保留范围，或重新检查；发现缺口就明确返回 RESET。

Recreate after handler failure: immediately call source.close() to stop old automatic reconnects and increment the application generation. Serialize handlers, check generation before their local transaction, await the previous handler's commit/rollback, then read the committed cursor. Open a new subscription with ?after=E%3A42; validate this application cursor with explicit precedence over automatic Last-Event-ID.

For E:43 adding 7 to local value 100, commit projection rows and applied seq in one local database transaction. A crash rolls both back to 100/E:42; replay then commits 107/E:43 together. Ignore seq≤applied duplicates; stop and recover on seq>applied+1. This local transaction does not cover external side effects. Retention can advance after classification, so read/tail pins needed history or rechecks and explicitly RESETs gaps.

历史裁剪后，快照状态为什么必须配上同一截面的游标Why reset needs state and cursor from the same snapshot

游标过旧或日志代次改变时，Gateway 在流内发送应用定义的 RESET。客户端丢弃这轮局部状态，通过普通 HTTP 读取 Snapshot，取得一致的业务状态及对应游标，再订阅该游标之后的日志。状态与游标必须来自同一截面：如果先读状态，再单独读最新高水位，中间的变更可能尚未进入快照，却已被游标跳过。生成快照并从其游标开始订阅期间，还要保留所需日志区间，否则客户端刚恢复就会再次 RESET。无法保住所需历史时，应明确返回失败，不能在 RESET 循环中声称恢复成功。

生成流：及时返回增量，并限制慢读与重复生成Generation streams: forward promptly, bound stalls and duplicate runs

响应头发出后，错误要怎样在流内表达Which error contract applies after headers?

TCP 数据块、HTTP 帧、一次 ReadableStream 读取和一个 SSE 事件之间，没有一一对应关系。同一个事件可能分多次读取，也可能一次读到多条事件。解析器要保留未完成的行和 UTF-8 解码状态，直到空行结束事件后，才交给应用处理，不能每读一块数据就直接 JSON.parse。代理、压缩器和写入端可以适度聚合数据来提高效率，但等待时间必须有上限，不能攒完整段生成后才交给用户。

TCP chunks, HTTP frames, stream reads and SSE events are not one-to-one. One event may span reads and one read may contain many events. Preserve partial lines and UTF-8 decoder state, dispatch only complete events, and never blindly JSON.parse each read. Bounded coalescing is valid, but proxy/compressor/writer waiting must stay bounded rather than buffering the whole generation.

Stop taking increments at the cap, propagate backpressure where supported, and abort Edge → Gateway → App at the stall deadline. Closing only the browser socket while App fills an unlimited queue turns slow networks into server memory failures.

生成 POST 断线后，不自动重新生成。如果产品支持继续查看原输出，客户端先查询原运行任务的状态，再从已保留输出的游标之后恢复；没有可恢复的历史时，就明确返回失败，或由用户发起新任务。原任务可能已经完成、已经失败，也可能还在取消，网络错误不能证明模型没有执行。取消回执也不表示业务回滚，工具副作用与计费结果要从原操作记录中查清。详细的持久屏障见 Ch32；本章的协议约定需要保留运行标识和终止状态，让后续恢复有据可查。

Disconnected POST must not automatically regenerate. If resumption is supported, query the original run and replay retained output after its cursor. Without history, fail explicitly or let the user request a new run. Network errors do not reveal whether the model completed, failed or is cancelling. Cancellation is not rollback; consult operation records for tool effects/accounting. Ch32 details durable barriers; the protocol must expose run ID and termination state.

关键实现：限制待发字节，并检测写入是否停滞Implementation: bounded payload and no-progress timing

下面的 Java 17 摘录来自由单个事件循环独占的 BoundedWriter，构造参数为 65,536 B 和 2,000,000,000 ns；队列、计数器及 closed 的完整定义见源码。offer 成功后，数组的独占所有权转交给写入器，生产者不能再修改它；缓冲溢出时直接关闭并清空队列，不能静默丢弃需要可靠传递的数据。队列为空时不计算停滞时间，首字节入队后开始计时；只有实际写入了正数字节，才重新计时，零写入和继续入队都不能延长时限。

This Java17 excerpt belongs to a BoundedWriter owned by one event loop, constructed with 65,536 B and 2,000,000,000 ns. See the source for its queue, counters and closed state. Successful offer transfers exclusive array ownership; the producer cannot mutate it afterward. Overflow closes and clears instead of silently dropping durable bytes. An empty queue has no stall timer; the first pending byte starts it. Only positive writes reset it, never zero writes or new queued bytes.

boolean offer(byte[] owned, long now) {
    if (!tick(now)) {
        return false;
    }
    if (owned.length > capacity - pending) {
        abort();
        return false;
    }
    if (owned.length == 0) {
        return true;
    }

    if (pending == 0) {
        progressedAt = now;
    }
    queue.add(ByteBuffer.wrap(owned)); // Success transfers exclusive ownership.
    pending += owned.length;

    return true;
}

boolean flush(NonBlockingSink sink, long now) throws IOException {
    if (!tick(now)) {
        return false;
    }
    if (pending == 0) {
        return true;
    }

    ByteBuffer head = queue.peek();
    int before = head.remaining();
    try {
        int n = sink.write(head); // One nonblocking write; zero is no progress.
        if (n < 0 || n > before || before - head.remaining() != n) {
            abort();
            throw new IllegalStateException("sink contract violated");
        }

        if (n > 0) {
            pending -= n;
            progressedAt = now;
            if (!head.hasRemaining()) {
                queue.remove();
            }
        }
        return true;
    } catch (IOException failure) {
        abort();
        throw failure;
    }
}

boolean tick(long now) { // Run even when the socket is not writable.
    if (!closed && pending > 0 && now - progressedAt >= stallNanos) {
        abort();
    }
    return !closed;
}

void abort() {
    closed = true;
    queue.clear();
    pending = 0;
}

适配器必须满足的约定：sink.write 必须非阻塞，按返回的字节数推进 ByteBuffer，而且背后不能藏着无界的应用或框架队列。普通 gRPC write 返回时，可能只是框架已经接收数据，并不证明数据已经发到网络上。[16] 适配器要按剩余容量从上游拉取，最多暂存一个有界数据块，例如 4 KiB，缓冲满了就停止拉取。即使没有可写回调，也要定时调用 tick。返回 false 或抛出异常后，要沿 Edge → Gateway → App 取消并清理资源。坏连接上可能连 error 也发不出去，但没有 done 仍不能视为成功。

A9 的 12.5 MiB 只计算队列中的数据载荷，暂存块、TLS、内核、模型状态和对象都要另算。连续无进展恰好达到 2 秒时就终止；如果每次只写出一点字节，仍可能避开停滞检测，因此还要另设整体运行截止时间或最低吞吐策略。三个摘录与源码逐字同步，依赖和运行方式见示例说明。本地模拟的 sink 只能验证这些策略，不等于真实代理、TLS 或弱网实验。

Adapter contract: sink.write is nonblocking, advances ByteBuffer by its return value, and hides no unbounded application/framework queue. A gRPC write return can mean framework acceptance rather than network delivery. [16] Pull upstream according to capacity with at most one bounded staging chunk, such as 4 KiB, and stop pulling when full. Call tick even without writable callbacks. False/exception propagates abort Edge → Gateway → App and cleanup. A broken channel may not carry error; missing done still cannot mean success.

A9's 12.5 MiB covers queued payload only; staging, TLS, kernel, model state and objects are extra. Exactly 2 s without progress aborts. A byte trickle can evade stall detection, requiring a separate overall deadline/minimum throughput policy. Three excerpts exactly match source; see dependencies and running instructions. A local simulated sink is not a real proxy, TLS or impaired-network experiment.

HTTP/2 与 HTTP/3：丢包后，哪些流需要等待HTTP/2 and HTTP/3: who waits after loss?

先把接收端的层次展开Expose layers inside the receiver

HTTP/2 已经能在一条 TCP 连接上复用多条流，并不是 HTTP/3 才支持并行。上排把接收端 TCP 层画成一个框，是为了展示传输层向上交付的位置，没有增加新的中间服务。A10 假设 P1 携带 A 的前部字节并丢失，随后携带 B 字节的 P2 已经到达。TCP 要按序交付同一个字节流，缺口补齐前，后到的 B 字节也不能越过缺口交给 HTTP/2。这就是 TCP 造成的跨流队头阻塞（head-of-line blocking）。

HTTP/2 already multiplexes streams on one TCP connection; parallelism did not start with HTTP/3. The upper TCP receive box exposes an endpoint layer, not a new service. Under A10, P1 containing earlier A bytes is lost and later B packet P2 arrives. TCP’s ordered byte-stream delivery prevents later B bytes passing the gap to HTTP/2: cross-stream TCP HOL blocking.

下排改用 QUIC。RFC 9000 将可靠顺序限定在每条流内部，丢失包涉及哪些流的数据，那些流就需要等待重传。[11] 如果 B 的字节和解码依赖都已经齐备，B 可以继续交付，A 则仍要等待。这就是下排正常交付线与上排淡化线的区别。QUIC 仍负责确认、重传、流量控制和加密，并非用 UDP 发出数据后就不再处理；应用获得的仍是有明确约束的可靠传输。

QUIC provides reliable order per stream. RFC 9000 ties loss blocking to streams whose data was in the lost packet. [11] Ready B data with satisfied decoding dependencies can advance while A waits. That is the live lower delivery path versus the muted upper path, not fire-and-forget UDP. QUIC still handles acknowledgement, repair, flow control and encryption.

哪些前提下会受益，还有哪些等待没有消失Benefit premises and remaining waits

A10 特意让 A、B 的数据放在不同包中。如果丢失的 P1 同时包含两者，两条流都可能需要等待补齐。丢包也会影响共享的拥塞控制，网络容量下降时，其他流未必能维持原速率。HTTP/3 的 QPACK 将头部表状态放在独立流上，但请求头解码仍可能等待必要的表项。如果应用规定 B 必须使用 A 的结果，传输层能独立交付也无法消除这种依赖。[12] 因此，可以说 HTTP/3 减少了 TCP 引入的跨流等待，不能承诺所有请求互不影响。

A10 deliberately separates packets: if P1 carried both streams, both can need repair. Loss also affects shared congestion, so other streams may slow down. HTTP/3 QPACK state uses independent streams but headers can need table entries; applications may also make B depend on A. [12] Say it reduces TCP-induced cross-stream waiting, not that all HTTP/3 requests are independent.

协议切换是否值得，要在题目的实际路径上验证。移动弱网、多资源页面或频繁切网时，这一差异可能减少用户看见的等待；同地域的一次耗时很短的一元 RPC 调用，则未必有足够收益。继续使用 HTTP/2 仍是合理选择：代理与诊断工具更熟悉，部署成本也可能更低。HTTP/3 则需要客户端、入口和网络共同支持。切换传输协议不能替代应用截止时间、缓存、准入与业务幂等，也不会自动解决源站的慢 SQL。

Validate benefits on the actual path: mobile loss, many resources or network switches may improve visible waits, while one short same-region unary RPC may not justify migration. HTTP/2 offers familiar proxies/diagnostics and lower deployment effort; HTTP/3 needs client, edge and network support. Transport does not replace deadlines, caching, admission or idempotency, nor fix slow SQL.

QUIC 的使用边界：早期数据、路径迁移与回退QUIC boundaries: early data, migration and fallback

0-RTT 是少等一轮握手，不是网络耗时为零0-RTT saves a wait, not all network time

客户端已有连接恢复信息时，可以尝试在握手完成前发送早期数据。A11 假设 RTT 为 40 ms，如果服务器接受安全的早期读取，可能少等一轮、约 40 ms 的握手时间。冷连接、早期数据被拒绝，或请求仍需等待业务排队时，都不能直接套用这个收益。少等握手不代表响应无需在网络上传播，也不保证请求一定被接受。因此，0-RTT 不等于首响应耗时为 0 ms，更不能推出所有弱网请求都会更快。

With resumption information, a client may try early data before handshake completion. A11’s 40 ms RTT can yield a roughly one-RTT handshake saving when safe early reads are accepted. Cold connections, rejected early data or business queues invalidate that shortcut. Zero handshake waits does not mean zero propagation, guaranteed acceptance or universally faster weak-network requests.

早期数据存在重放风险。HTTP 规则限制提前发送不安全或安全性未知的方法，425 Too Early 则明确表示服务端拒绝承担这种处理风险。[13] 本例对扣款等请求采取保守策略：由可信的早期数据检查点（Early Gate）在分派业务前拒绝请求，425 经 Gateway、Edge 返回客户端，握手完成后再沿用原操作键重试。握手重放保护、跨节点去重和业务幂等解决的是不同层面的问题，单个进程中的短期键集合，不能覆盖整个集群的重放窗口。

Early data has replay risk. HTTP restricts unsafe or unknown-safety early methods and 425 Too Early explicitly refuses that risk. [13] This exercise conservatively rejects mutations at trusted Early Gate before dispatch, returning 425 through Gateway/Edge, then retries with the original key after handshake. Handshake replay defenses, cluster-wide deduplication and business idempotency have distinct scopes; a short-lived local key set cannot cover the cluster window.

代理要保留早期数据的来源，迁移要验证新路径Proxies preserve provenance; migration validates paths

如果 Edge 终结 QUIC 后丢掉早期数据的来源信息，Gateway 就可能把早期扣款当作普通请求执行。A12 要求入口生成可信标志并传给检查点，同时清理客户端伪造的同名内部头；做不到时，就在 Edge 直接禁用相应早期请求。图中的 Early Gate 表示 Gateway 的逻辑检查职责，不要求单独部署一台服务。还要分清“拒绝执行”与“已经执行”：请求已经分派后才返回 425，就不能再据此证明尚未发生副作用，恢复时仍须查询原动作的回执。

If Edge drops early-data provenance after terminating QUIC, Gateway can treat an early mutation as ordinary. A12 requires trusted ingress provenance with forged internal headers removed, or rejection at Edge instead. Early Gate is a logical Gateway check, not a mandatory separate deployment. Returning 425 after dispatch loses this exercise’s evidence that no effect occurred; query the original operation instead.

从 Wi-Fi 切到蜂窝网络会改变地址。连接 ID 可以帮助端点继续识别原连接，但 RFC 9000 的路径迁移仍需验证新路径，也受端点能力与策略约束。[11] 连接 ID 不是授权令牌，不能因为新地址带着它，就认定这个地址可信。业务会话和原操作身份也要保留。切网期间仍可能丢包、排队或等待验证，因此只能说有机会保留连接，不能保证完全没有停顿，更不能把同一个标识当作允许重复执行业务的依据。

A Wi-Fi/mobile switch changes addresses; connection ID can preserve recognition of a connection, but RFC 9000 requires path validation subject to endpoint capability/policy. [11] CID is not an authorization token and an arbitrary new address is not trusted merely by presenting it. Preserve business identity and expect loss/queueing/validation delays. Migration offers continuity, not guaranteed invisible switching or permission to repeat business actions.

标准中的风险标志也必须保留：Edge 按 RFC 转发早期请求时，要携带 Early-Data: 1，已有的该头也不能删除。即使当前这一跳已经完成握手，前一跳的早期数据风险仍然存在；清理伪造的内部信任头，不等于删除这个标准头。只有确认上游理解该头并能正确拒绝时，才提前转发，否则应延后转发、拒绝请求或禁用早期数据。收到 425 后的重试不得再使用早期数据。[13 §5.1, §5.2, §6.1]

保留同一连接，不要求一直使用同一个 CID。RFC 9000 §9.5 要求端点从多个本地地址发包时，不复用连接 ID；NAT 重绑等被动地址变化另有边界。主动迁移还受握手确认状态与对端参数限制，新路径仍须验证。图中的 Path Check 表示端点内部的路径检查，不是新的业务任务。[11 §8.2, §9, §9.5]

Preserve the standard risk bit: Edge sends Early-Data: 1 when forwarding early requests under RFC rules and cannot remove an existing header. Completing this hop's handshake does not erase earlier-hop risk. Remove forged internal trust headers separately from this standard header. Early forwarding requires an origin known to understand it and reject correctly; otherwise defer, reject or disable early data. A 425 retry must not use early data. [13 §5.1, §5.2, §6.1]

Same connection does not mean a fixed CID. RFC 9000 §9.5 forbids reusing connection IDs when sending from multiple local addresses, with separate passive-change cases such as NAT rebinding. Active migration also depends on handshake confirmation and peer parameters; validate the new path. Path Check is an endpoint abstraction rather than a new business task. [11 §8.2, §9, §9.5]

UDP 不通时，如何回退、如何恢复也要提前约定Define failure behavior when UDP is unavailable

HTTP/3 连接失败可能是 UDP 不可达造成的，标准建议尝试基于 TCP 的 HTTP。[12] A12 要求先确认客户端与 Edge 支持相应的 TLS/TCP 路径，再切换传输方式，并保留资源与操作键。回退时，不能顺手把失败的生成 POST 重新执行一次。如果业务请求尚未发出，可以建立新连接后再发；如果请求可能已经到达服务端，就要按原操作身份查询结果。这是两种不同的恢复条件。回退属于可用性设计的一部分，也需要设置限额、提供诊断，并在真实的网络故障条件下验证。

HTTP/3 can fail when UDP is unreachable; the standard recommends attempting TCP-based HTTP. [12] A12 requires supported TLS/TCP fallback without changing resource/operation identity. Do not automatically repeat a generation POST. No business request sent and a possibly executed request are different recovery conditions: connect/send in the former, query the existing operation in the latter. Bound and validate fallback on real impaired networks.

复盘：沿一个故障窗口，把处理过程讲清楚Review: narrate one failure window

先说明交互方向和调用方能力，再交代如何标识动作、什么证据表示成功、何时超时、能恢复哪些历史。可以推演“m7 已提交但回执丢失”，或“E:43 已收到但本地事务回滚”，沿请求和回程走完一次。最后再说明 HTTP/3 能让哪一段连接受益。

Start with interaction direction and caller capabilities, then identify the operation, success evidence, timeout and replay range. Trace m7 committed with a lost receipt, or E:43 received with a rolled-back local transaction. Discuss H3 benefit on a specific link last.
