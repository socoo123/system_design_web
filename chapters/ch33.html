本章要点：批准具体动作，查清业务结果Core: approve one action, establish one outcome

模型提出动作，执行面检查权限。 参数结构（schema）校验只能判断“参数格式是否符合要求”，资源授权才判断“这个主体能否操作这份资源”。即使模型看得到工具目录、生成的 JSON 也合法，平台仍须检查权限。

批准要绑定完整动作快照，发出前还要复查。 快照固定租户、操作者、Agent、业务动作标识（intent）、工具与目的端版本、实际生效的参数、资源版本、策略和期限。等待人工审批时，动作保存在持久库中，不占用 RPC 槽位。

网关的事务管不到远端业务变更。 业务端必须把业务键（key）、带条件的更新和回执放在同一事务中。如果两库之间的回包丢失，网关就保留结果未知（UNKNOWN）；取消、租约到期或 TTL 到期，都不能证明业务没有发生变更。

The model proposes; the execution plane authorizes. Schema checks shape, while resource authorization checks whether this subject may act on this object. Catalog visibility and valid JSON grant no authority.

Approve the full snapshot and recheck before dispatch. Bind tenant, actor, agent, intent, tool/route revisions, effective arguments, resource version, policy and expiry. Approval waits consume no RPC slot.

A gateway transaction does not include the remote effect. The backend commits the key, conditional effect and receipt together. Lost evidence between the two databases remains UNKNOWN; cancellation, leases and TTL do not prove no effect.

范围与需求：查询和关闭内部工单Scope: internal ticket reads and closure

可信运行时（Runtime）携带经过认证的身份，把模型提出的工具名、版本和参数交给工具网关（Tool GW）。本章约定：权限范围内的读操作自动执行，写操作逐笔由人工审批。平台接入已注册的 HTTP 和 MCP 工具，提供统一的执行契约，同时为每个后端分别声明授权、幂等、结果查证和取消能力。如果只有几个内部读函数，可以先放在同一模块中；等多个 Runtime 需要共享凭据和审计能力时，再独立成网关。

设计前先问清楚：谁在调用，动作会产生什么副作用，工具由谁维护，审批依赖哪些资源条件，下游能否防重和查询结果，以及调用期限、敏感审计数据的留存要求。Ch32 负责调用模型，Ch34 负责多步循环与恢复，本章只处理其中一次工具动作。使用客户端工具时，应用负责处理 tool_use/tool_result；供应商也可以托管服务端工具，具体职责要按接入方式区分。[1]

Authenticated Runtime sends model-proposed name, revision and arguments to Tool GW. This lesson automatically executes allowed reads and requires per-action human approval for writes. MCP and registered HTTP share an execution contract while declaring backend-specific authorization, deduplication, lookup and cancellation. Embed a small module first; extract a gateway when multiple runtimes share credentials and audit.

Clarify subjects, effects, owners, approval conditions, backend evidence, deadlines and sensitive retention. Ch32 calls models and Ch34 owns multi-step recovery. Client tools use application-handled tool_use/tool_result; suppliers can also host server tools. [1]

1 · 总览：固定工具契约，结果沿原路返回1 · Overview: pin the contract, return through every hop

工具定义以 Registry 为准，执行决定保存在 Execution DB，业务变更则由业务库（Business DB）提交。 经过认证的 POST /tools/invoke 接收工具提议和稳定的 intent，租户、操作者与 Agent 身份取自可信上下文。网关依次检查工具版本、参数结构、资源权限、调用限额和审批情况，在发出前持久记录 intent 与事件。Adapter 只调用快照绑定的一个目的端，结果经 Tool API → Adapter → Tool GW → Runtime 返回。

Registry 保存输入和输出 schema、目的端版本、拥有者、副作用、权限、期限，以及重试和审批策略。模型只能拿到过滤后的名称、说明和 schema；真正执行时仍须检查当前权限，不能信任模型自行填写的 tenant、URL 或“readOnly”声明。缓存只保存派生数据，多个网关实例共享同一权威执行库。[8]

平台把结果区分为待批（PENDING）、拒绝（DENIED）、成功（SUCCEEDED）、已确认无业务效果的失败（FAILED_KNOWN）和结果未知（UNKNOWN），并返回 intent、尝试标识（attempt）、工具版本（revision）和可查询句柄。本平台的 202 只表示请求已持久接收。HTTP 或 JSON-RPC 成功不等于业务成功；MCP 的 isError 只表示工具报错，不能单凭它证明没有副作用。只有业务契约或回执能确认未产生效果时，才归为 FAILED_KNOWN；无法确认时应保留 UNKNOWN。[2]

Registry fixes contracts, Execution DB records decisions, and Business DB owns effects. Authenticated POST /tools/invoke accepts a proposal and stable intent; identity comes from trusted context. Recheck revisions, schema, resources, budgets and approval. Persist intent/events before sending to one pinned route. Results return Tool API → Adapter → Tool GW → Runtime.

Registry stores schemas, route revision, owner, effects, access, deadline, retry and approval policy; the model receives only a filtered projection. Reauthorize during execution. Model-provided tenant, URLs and safety labels confer no permission. Caches are derived; all gateways share one execution authority. [8]

Return PENDING, DENIED, SUCCEEDED, FAILED_KNOWN or UNKNOWN with intent/attempt/revision and a status handle. Our 202 means durable acceptance. HTTP/JSON-RPC success is not business success, and MCP isError reports a tool error, not proof of no effect. Only authoritative no-effect evidence establishes FAILED_KNOWN. [2]

2 · 协议：工具如何发现，会话如何关联2 · Protocol: discovery is not authorization; sessions are not intents

模型侧的工具调用与服务侧的 MCP 连接，需要分别处理。 Adapter 完成协议协商和初始化后，读取所有分页的 tools/list，再把候选工具交给 Registry 审查；通过后才发布为 r7。执行时使用 tools/call，并沿用审查通过的映射。schema、说明或目的端有变化，就要创建新版本；未审查的 r8 不能替换已经获批的 r7。不可信服务给出的 readOnlyHint/idempotentHint 只是提示，工具拥有者还需证明实际副作用、防重能力和保留期，才能把它标为 retry_safe。[2]

本例为已有服务固定使用 MCP 2025-11-25，接入 stdio 和 Streamable HTTP。后者通过 POST 发送消息，响应可以是 JSON 或 SSE；服务端可以分配 MCP-Session-Id，之后的请求必须携带该标识。连接断开不能证明请求已取消；重新连接或重建协议会话，也不能重新创建同一笔业务动作。[3]

业务会话（business session）关联对话，intent 标识一笔业务动作，JSON-RPC id 关联一份报文，传输会话（transport session）关联服务端上下文。平台要分别持久记录这些标识及其关联。HTTP Adapter 只调用注册好的路由模板，不接受模型提供的 URL；解析后的目的地址、重定向和网络出口都受策略约束。凭据还要校验适用的接收方与权限范围（audience/scope），不能原样转发不适用于目的端的 token。[6]

Model tool calling and server-side MCP are separate contracts. Adapter negotiates/initializes and consumes paginated tools/list, then submits candidates for Registry review. Use tools/call only against the reviewed mapping. Changed schema/descriptions/routes require a new revision; reject unreviewed r8. Untrusted safety annotations are hints; owners must establish actual effects, deduplication and retention. [2]

Pin MCP 2025-11-25: stdio and Streamable HTTP; the latter posts messages and accepts JSON/SSE responses. Servers may assign session IDs that subsequent requests must carry. Disconnect is not cancellation; reconnecting or recreating a session does not recreate the business action. [3]

Business sessions group conversations, intents identify actions, JSON-RPC IDs correlate messages, and transport sessions identify server context. Track each separately. HTTP routes are registered templates rather than model URLs; constrain resolved destinations/redirects/egress and validate credential audience/scope. [6]

3 · 准入：先校验参数，再检查资源权限3 · Admission: schema and resource access are separate

工单标识 ticket_id 格式合法，仍可能指向其他租户的工单。 图中的 RESOLVED → SCHEMA_OK 只检查参数结构，SCHEMA_OK → AUTHZ_OK 才检查资源属于哪个租户，以及用户、Agent 和工具策略共同允许什么操作。服务凭据有写入能力，也不能让只读用户获得写权限。Tool API 还要检查业务对象权限，因为网关提前读取一次资源，无法消除后续的并发竞争。

下面的代码对应第 3 组图的前 3 帧：先限制输入不超过 16 KiB、嵌套不超过 8 层，再解析 JSON、拒绝重复键，并显式检查必填字段、额外字段和类型。JSON Schema 的 properties 只描述字段，本身不会要求字段必填，也不会禁止额外字段。[5] 本例使用固定的平面 schema，严格区分整数 4、浮点数 4.0、布尔值 true 和字符串“4”。如果要填入默认值或规范化参数，都必须在展示审批内容之前完成。这里的编码只用于本例固定格式，并非通用 JSON 规范化标准。

A valid ticket_id can still identify another tenant’s ticket. RESOLVED → SCHEMA_OK validates shape; SCHEMA_OK → AUTHZ_OK checks ownership and user∩agent∩tool permissions. A service write credential never upgrades a read-only user. The backend reauthorizes; a gateway pre-read cannot eliminate later races.

This contract covers the first three admission frames: bound 16 KiB/eight levels, reject duplicate keys and explicitly validate required/extra fields/types. JSON Schema properties alone neither require fields nor close extras. [5] This fixed flat schema distinguishes 4, 4.0, true and “4”; apply defaults/normalization before displaying approval. Its encoding is domain-specific, not universal JSON canonicalization.

prepare(authenticatedContext, confirmedIntent, rawArguments):
  reject bytes > 16 KiB, nesting > 8, duplicate keys or non-JSON numbers
  args = parse closed schema:
    ticket_id: ASCII ticket ID; expected_version: positive integer
    reason: nonempty string <= 160 characters; no extra fields
  // No coercion: true, 4.0 and "4" are not integer version 4.
  canonicalArgs = UTF8_JSON(sorted keys, exact validated values)
  BEGIN IMMEDIATE on ExecutionDB
    key = (auth.tenant, confirmedIntent)
    old = SELECT intent WHERE (tenant, intent_id) = key
    if old exists:
      require old.actor/agent/tool/revision/args == this request
      COMMIT; return old.state  // retain original route/grant/deadlines
    tool = reviewedRegistry["ticket.close", "r7"]  // never model URL
    require tool.enabled and caller may use this exact revision
    require resource tenant == auth.tenant
    require userScope AND agentScope AND toolPolicy allow ticket.close
    proposal = (auth.tenant, auth.actor, auth.agent, confirmedIntent,
                tool.name, tool.revision, tool.routeRevision, tool.policy,
                canonicalArgs, args.ticket_id, args.expected_version)
    now = trustedClockAfterLock()
    snapshot = proposal + (newGrantId, now+5min, now+24h)
    binding = SHA256(versioned stable encoding of snapshot)
    INSERT intent(snapshot, binding, state=PENDING)
    INSERT single-use grant(newGrantId, snapshot.key, binding)
    INSERT audit(event_id, snapshot.key, "pending")
  COMMIT before returning 202 + authenticated status handle
  // Store the complete snapshot too; the digest is not the permission.
  // Approval UI shows the full effective action, not a hash alone.

输入有误就拒绝，不发出调用，也不消费批准凭据。PENDING 只能等待审批，不能直接进入执行；尚未发出的动作到期后，统一记为 DENIED(reason=expired)，与发出后结果不明的 UNKNOWN 区分。输出也必须限制在 64 KiB 内，检查声明的结构，并按访问权限脱敏。超限时可以分页、返回受保护的查询句柄，或明确标记 truncated，不能把部分结果说成已经检查了全部数据。工具输出应保留来源，并作为不可信数据处理；它不能变成系统指令，也不能授予下一次调用的权限。

Invalid input neither dispatches nor consumes a grant. PENDING has no execution edge. Undispatched expiry is DENIED(reason=expired), distinct from postdispatch UNKNOWN. Bound outputs at 64 KiB, validate declared structure and redact by access; paginate or mark truncation. Treat tool text as untrusted sourced data, never as new system instructions or authority.

4 · 审批：绑定完整动作，分别提交批准和发出决定4 · Approval: full binding, separate approval and dispatch transactions

审批者必须看得到这次动作具体会做什么。 Approval UI 从可信网关取得实际动作、生效参数和影响，审批者身份及可批准范围则来自认证会话。grant 绑定租户、操作者、Agent、intent、工具名及版本、目的端版本、规范化参数、资源 ID 及版本、策略、到期时间和单次凭据标识。界面只显示一个 hash，无法让人审阅动作；绑定内容有任何变化，都需要新快照和新批准。

第 4 组图中，第 3 帧提交批准事务，第 4 帧提交发出事务。两次点击只会消费一个 grant，APPROVED 也还没有产生业务效果。执行器取得权威执行库的锁后，再读取时间、检查当前权限和版本，并更新状态与事件；确认提交之后，才能发出网络请求。如果连提交确认都未收到，就先按原业务键读回记录，不能假定事务没有提交。下面每个 BEGIN 都只覆盖指定的单个数据库，不包含 HTTP 或 MCP 调用。

Approval covers a readable concrete snapshot. The gateway supplies effective arguments and impact; authenticated sessions supply approver identity/scope. Bind tenant, actor, agent, intent, tool name/revision, route revision, canonical arguments, resource ID/version, policy, expiry and grant identity. A hash alone is not a reviewable action; changed fields need new review.

Frame 3 commits approval, frame 4 commits dispatch intent. Duplicate clicks consume one grant; APPROVED is not executed. Under the execution database lock, sample time and recheck current permissions/revisions, then update state/events. Send only after confirming commit; ambiguous commit acknowledgements require a same-key readback. Each BEGIN covers one database, never HTTP/MCP.

approve(authenticatedApprover, intentKey, reviewedBinding):
  BEGIN IMMEDIATE on ExecutionDB
    i, g = SELECT intent and grant by intentKey
    require approver may approve i.tenant; require binding matches i and g
    if i.state != PENDING: COMMIT; return existing state
    now = trustedClockAfterLock()
    require now < i.expiresAt and current user/agent/tool permission
    UPDATE grant SET consumed=1 WHERE grant_id=g.id AND consumed=0
    require exactly one row; UPDATE intent SET state=APPROVED
    INSERT audit(event_id, intentKey, "approved", approver.id)
  COMMIT

claimForDispatch(authenticatedContext, intentKey):
  BEGIN IMMEDIATE on ExecutionDB
    i = SELECT intent by intentKey
    require exact caller identity matches i; if state != APPROVED: stop
    now = trustedClockAfterLock()
    if expired, cancelled, revoked, or current tool/route/policy != i:
      UPDATE intent SET state=DENIED, reason=actualReason
      INSERT audit(event_id, intentKey, "denied"); COMMIT; stop
    UPDATE intent SET state=DISPATCH_INTENT, epoch=epoch+1
      WHERE key=intentKey AND state=APPROVED
    require exactly one row; INSERT audit(event_id, intentKey, "dispatch")
  COMMIT  // no network request before this commit is confirmed/read back
  send persisted snapshot and SAME business key through its pinned Adapter
  // Crash here: recovery queries evidence; never assume no send.
  // Epoch fences ExecutionDB writes, not a running remote request.

如果批准时工单为 v4，执行时已变成 v5，业务端必须在修改事务中检查 version/If-Match 前置条件。返回 stale_precondition 后应重新审查动作，不能自动把参数换成 v5 重试。[7] 无条件写入的后端无法保证原快照仍成立，需要改造接口契约，或明确批准一个不依赖该快照的动作。如果还要求“权限撤销后，业务提交时一定不能写入”，就需要业务端的权限版本或屏障机制；网关检查只能保证本地准入时的权限成立。

5 分钟 grant 到期会阻止新的调用，不会回滚已发出的请求。取消请求与执行器领取动作（claim）在同一库中串行处理：取消先于 claim，就能确定没有发出；claim 之后，只能记录 cancel_requested、尽力向下游传递取消并查询结果。补偿需要作为另一笔业务动作，重新满足授权、批准和幂等要求；重新打开工单并不自动等于原事务回滚。

If approved v4 becomes v5, the backend checks version/If-Match in the modification transaction and returns stale_precondition; do not silently retry v5. [7] Unconditional backends cannot preserve snapshot assumptions. Stronger commit-time revocation likewise needs backend policy versions/barriers; gateway admission has a local authorization point.

The five-minute grant blocks new dispatch after expiry, without undoing an issued call. Cancellation serializes with claim: before claim it can prove no dispatch; afterward record cancel_requested, propagate best effort and query evidence. Compensation is another authorized/approved/idempotent action, not automatic rollback.

5 · 幂等与 UNKNOWN：业务提交后，网关还要保存结果5 · Idempotency and UNKNOWN: one action, two commits

一笔动作的 intent 由可信业务交互确定，不能由模型重新生成。 重放同一动作时保持原业务键；用户确实要执行两次相同动作，就应有两个 intent。tool_call_id 和参数 hash 都无法推断用户意图。Execution DB 中唯一的 (tenant,intent) 只能防止网关重复准入：快照不同就返回冲突，不能复用旧批准，也不能为结果未知的写操作更换 Adapter 或目的端。[8]

业务变更是否重复，由 Business DB 负责约束。它先查询同一业务键的已有回执；只有新操作才检查当前权限和资源条件，并在同一事务中提交修改与回执。已有成功回执要先于新的版本或有效期检查返回。 否则，原操作成功把 v4 改为 v5 后，它自己的重放反而会被误报为版本失败。epoch 和 CAS 只限制谁能向本网关库写入结果，远端仍要检查业务键和资源条件。

Trusted business interaction defines intent; the model does not regenerate it. Replays retain a key; two legitimate identical actions have two intents. Model call IDs and argument hashes cannot determine human intent. Unique (tenant,intent) prevents gateway admission duplicates only; changed snapshots conflict, and unknown writes never move to another Adapter/route. [8]

Business DB protects effects: read an existing keyed receipt first; only new work checks current access/resource conditions, then commits modification and receipt together. Replay a stored success before applying a new version/expiry check, or the original v4→v5 success would incorrectly fail its own replay. Epoch/CAS fences local outcome writers; backend keys/conditions protect effects.

toolApiClose(authenticatedAdapter, immutableSnapshot):
  require adapter identity and delegated caller match the snapshot
  BEGIN IMMEDIATE on BusinessDB  // NOT the ExecutionDB transaction
    receipt = SELECT receipt WHERE key=(tenant, intent_id)
    if receipt exists:
      require receipt.snapshot == immutableSnapshot
      COMMIT; return retained outcome  // no second effect, even after expiry
    require current user AND agent permission for resource tenant
    changed = UPDATE ticket SET state=CLOSED, version=version+1
      WHERE tenant=:tenant AND id=:ticket AND version=:expected
        AND state=OPEN
    outcome = SUCCEEDED if changed == 1 else FAILED_KNOWN(stale_precondition)
    INSERT receipt(key, snapshot, outcome, result)  // unique key
    // A failure inserting the receipt rolls back the ticket UPDATE too.
  COMMIT; return outcome

recordOutcome(key, epoch, authoritativeReceipt):
  BEGIN IMMEDIATE on ExecutionDB
    UPDATE intent SET state=receipt.outcome, result=receipt.result
      WHERE key=:key AND epoch=:epoch AND state IN (DISPATCH_INTENT, UNKNOWN)
    INSERT audit only if exactly one intent row changed
  COMMIT before reporting completion

recover(key):
  query original backend receipt without invoking the effect
  if matching receipt exists: recordOutcome(key, currentEpoch, receipt)
  else: retain UNKNOWN  // absence cannot exclude a delayed old request
  // Replay can execute a missing operation: allow only with live authority,
  // unexpired approval and verified backend dedupe retention; same key/route.
  // After retention compact bodies, keep key+binding+outcome tombstones.

两库之间有两个容易失去证据的时点。第一个是发出决定已提交，进程却在发送前崩溃；仅凭本库记录，无法区分“还没发”和“已发但没收到结果”。第二个是业务已提交，但回包丢失或本地结果写入失败。两种情况都要保留 UNKNOWN 和原 intent，先查询原目的端回执。查不到回执也不能证明没有副作用，因为旧请求可能仍在路上。终态只能由可靠证据修复；如果后端既不能查证结果，也不能保证原子幂等，就停止自动重发，接受部分动作无法自动完成。

沿用同一业务键重放，可能会首次执行一个原先没有送达的动作。因此仍须具备当前授权、未到期且未取消的原批准，以及已验证的下游防重保留期。本例的 5 分钟 grant 比 24 小时防重窗口更早到期，此后只允许查询。旧请求一旦发出仍可能继续，TTL 或租约到期都不能解除 UNKNOWN。响应正文到期后可以压缩，但业务键、绑定关系和已知结果或未决标记要保留为墓碑；如果删除整条唯一记录，同一业务键就可能再次执行。

第三方接口需要按各自契约适配。例如，Stripe API v1 保存首次执行结果，包括 500；至少 24 小时后允许清理，已清理的键再次使用会被当作新请求，参数变更则会报错。该文档另有 API v2 语义，不能把 v1 的约定推广到所有 Stripe API 或所有工具。[9] 如果还要在业务事务外发邮件或付款，就又增加一个事务边界，需要继续依靠下游防重、结果查证或事务发件箱（outbox）。这里的事务只保证工单行与所在业务库的回执一起提交。

Window 1: dispatch intent commits, then the process crashes before sending; locally this is indistinguishable from a sent call without evidence. Window 2: Business DB commits, but reply/local result persistence fails. Keep UNKNOWN plus intent and query the original backend. No receipt is not proof of no effect: an old request may still arrive. Without lookup/atomic deduplication, stop automatic redispatch and accept incomplete work.

Same-key replay can execute an originally undelivered action. It still needs live authority, unexpired/uncancelled approval and verified backend retention. This example’s five-minute grant closes earlier than its 24-hour dedupe window; afterward only query. Issued requests may continue. Retain key/binding/outcome or unresolved tombstones when compacting bodies; deleting the whole unique record can reauthorize an old action.

Adapt each provider separately. Stripe API v1 retains the initial executed result including 500, allows pruning after at least 24 hours, treats reused pruned keys as new requests and rejects changed parameters. The page distinguishes API v2; do not generalize v1 to all Stripe APIs/tools. [9] Email/payment outside this database adds another boundary needing downstream evidence/deduplication or outbox. This transaction proves only the ticket row and its local receipt.

6 · 期限、取消与审计：限制执行开销，保留结果证据6 · Deadlines, cancellation and audit: bound work, preserve evidence

获批后，一次执行总共使用 8 秒预算，最多尝试两次，网关和所有 SDK 共用计数；审批等待另计。 只有业务语义安全、错误可重试、剩余预算足够时，才允许再试一次。参数结构、授权、审批或前置条件检查未通过，都不能靠更换凭据或工具绕过。是否安全要看业务语义，不能只看 HTTP 方法，因为 MCP 读调用也会使用 POST。自动重试非幂等请求，需要已知的幂等保证，或能证明原请求尚未应用的证据。[7]

在 MCP 2025-11-25 中，普通请求通过 notifications/cancelled 取消，接收方可能因请求已完成或无法取消而忽略；采用任务机制的请求（task-augmented request）必须使用 tasks/cancel。[4] 取消可以释放本地等待和缓冲，却不能立即归还仍可能在运行的远端工作额度。如果 64 个槽位只统计客户端正在等待的请求，反复超时就会让实际远端并发持续增加。因此，未决远端工作仍须占用额度，直到能验证它已经终止；也可以由后端通过硬性准入上限或最大执行期限约束工作量。取消通知本身不是终止回执。

审计要记录身份、intent 和 attempt、工具与策略版本、批准者、脱敏摘要及业务回执。不要记录原始凭据、私有全文或 grant token。取值空间较小的摘要可能被猜出，单独计算 hash 既不能保密，也不能证明记录真实完整。关联标识应使用访问受控的随机 ID，并只保留必要字段。状态与 outbox 事件在同一库中提交，relay 写入 archive 并收到确认后才推进 checkpoint；崩溃可能导致重复发送，因此 archive 按 event_id 去重。[10] 积压接近容量上限时，应拒绝新的准入，同时为 UNKNOWN 查证和终态写入预留空间。

After approval, one execution has an eight-second budget (approval wait is separate) and at most two attempts shared by every SDK. Retry only with safe semantics, retryable errors and sufficient remaining time. Never bypass schema/access/approval/precondition denials with another credential/tool. MCP reads also use POST; non-idempotent retries need known idempotency or evidence that the original was not applied. [7]

Pinned MCP uses notifications/cancelled for ordinary requests; receivers may ignore completed/uncancellable work. Task-augmented requests require tasks/cancel. [4] Cancellation may release local waiting/buffers, not a remote work credit that may still be active. Counting only local waiters under 64 slots permits timeout-driven remote overload. Retain unresolved remote occupancy until verified termination, or enforce a backend cap/bounded execution contract. A cancellation notification is not a termination receipt.

Audit identities, intent/attempt, tool/policy revisions, approver, redacted summaries and receipts. Never log credentials/private text/grant tokens. Low-entropy hashes can be guessed; hashing alone provides neither confidentiality nor authenticity. Use access-controlled random correlation IDs and minimal fields. Commit state/outbox together; export to archive, await acknowledgment, then checkpoint. Replay can duplicate events, so deduplicate IDs. [10] Reserve reconciliation/outcome storage before rejecting new admission on backlog pressure.

展开容量复算与示例验证范围Expand capacity arithmetic and validation limits

A1–A3：20×3=60 次逻辑调用/秒。在稳定观察区间内，平均在途数为 60×0.3=18；若 10% 的调用各增加一次安全重试，就变为每秒 66 次物理 RPC，平均在途数为 19.8。最多两次尝试，只能保证一批 N 个逻辑动作合计不超过 2N 次调用，不能据此声称任意 1 秒都不会超过 120 次，因为不同秒的原请求和重试可能集中到一起。64 个槽位是准入上限，无法证明 p99 延迟达标；还要分别核对每个工具，以及部分实例故障后其余实例的容量。

A4–A7：3.5+0.2+3.5+0.8=8 秒；60×20%×30=360 个稳态待批动作。审批积压时应改看最老待批年龄和数量增长率。2,000×60×86,400=10,368,000,000 B=10.368 GB≈9.656 GiB，前提是峰值持续全天。热数据保留 7 天、两份拷贝需 145.152 GB；冷归档保留 30 天、两份拷贝需 622.08 GB，两者分别占空间，索引、WAL 和额外重试事件另计。64×64 KiB=4 MiB 只计算同时保留的结果载荷，连接和解析等内存还要另外估算。

示例与运行说明提供三份与页面同步的伪代码，以及用 Python 3 标准库实现的双 SQLite 数据库适配器。既有验证实际覆盖多连接并发、数据库触发器故障、两次提交之间的交付或回包丢失，以及过期、取消和墓碑记录等路径。SQLite 的 BEGIN IMMEDIATE 锁粒度比生产数据库的行锁更粗；身份、审批会话、时钟和经过认证的 Adapter 均作为可信前提注入。示例没有实现签名、MCP 客户端、真实远端工具、复制、远端取消后的终止证明，也没有进行生产压测。[11]

A1–A3: 20×3=60 logical calls/s; steady mean concurrency is 60×0.3=18. One safe retry on 10% gives 66/s and 19.8. Two attempts bound total calls for a cohort of N actions by 2N; they do not enforce a 120/s cap in every second because retries can cluster across boundaries. Validate per-tool and survivor capacity; 64 slots do not prove p99.

A4–A7: 3.5+0.2+3.5+0.8=8 seconds; 60×20%×30=360 steady pending, with age/growth used under accumulation. 2,000×60×86,400=10.368 decimal GB≈9.656 GiB for an all-day peak. Seven hot days/two copies need 145.152 GB and thirty archive days/two copies 622.08 GB separately, excluding indexes/WAL/extra retries. 64×64 KiB=4 MiB covers result payloads only.

Sources and run instructions provide three synchronized pseudocode contracts and a standard-library Python two-file SQLite adapter. Actual multi-connection/SQL-trigger fault cases exercise commit gaps, lost replies, expiry, cancellation and tombstones. SQLite locks are coarser than production row locks. Identity/session/clock/authenticated Adapter are fixture premises; no signature issuer, MCP client, live tool, replication, remote-termination proof or production load test is implemented. [11]

复盘：走完调用与返回，讲清两种风险Recap: one path, two uncertainty windows

沿 Runtime → Tool GW → Adapter → Tool API 走一次调用，再沿原路返回，并说明各处负责什么：Registry 固定工具契约，Execution DB 持久保存执行决定，Business DB 原子提交业务变更。先看审批后的资源竞争：批准时是 v4，执行前却变成 v5，需要由业务事务中的前置条件拒绝。再看业务已提交但回包丢失：网关保留 UNKNOWN，再按原业务键查询回执来修复状态。只有唯一键、审批通过记录或已发出的取消通知，都不足以证明远端只执行一次，也不足以确定没有写入。

工具说明、目录过滤、参数结构校验、授权、审批和幂等，分别解决不同的问题。低风险自动化可以采用明确的机器预授权与额度，本章则用逐笔人工审批写操作来解释边界。Ch34 的多步对话暂停与恢复要延续原 intent；Agent 重启后，也不能把结果未决的动作重新执行。

Walk Runtime → Tool GW → Adapter → Tool API and every return. Registry pins contracts, Execution DB persists decisions, Business DB commits effects. Window one: approved v4 becomes v5, rejected by the backend transaction condition. Window two: effect commits but reply is lost, repaired from the original keyed receipt. A unique key, approval or sent cancel notification alone proves neither one remote execution nor no effect.

Descriptions, catalog filtering, schema, access, approval and idempotency solve separate problems. Explicit machine grants/limits can support low-risk automation; this lesson uses per-action write approval. Ch34 resumes multi-step work with the same intent, preserving unresolved actions across restarts.
