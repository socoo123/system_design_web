先问半径和实时性Radius and freshness first

中文

邻近服务三个 hard part：二维收成格子键、半径查询要带邻格、热点格子要分片。默认是附近的商家和 POI，按距离排序。白板先画 geohash 前缀。Quadtree 是 trade-off，H3 六边形是备选。

第一问是范围。半径用 0.5、1、2、5 km 这几档，它决定 geohash 多长。实时性决定写路径：静态 POI 的改动很少；附近的人会把位置上报变成写 hotspot。距离要排。类型和营业时间后置过滤。DAU 写成教学假设，大约一千万，用来谈热格。问过 10 分钟还在问，也该停。地图瓦片和骑手匹配先收口，前者是选修，后者是 Ch27 · 配送。

我假设：附近商家 / POI，半径 0.5–5 km，按距离排序。索引用 geohash 前缀，查当前格加 8 个邻居。位置只存粗格子、短 TTL。方向不对你打断我。

English

Nearby has three hard parts: turn 2D into a cell key, query a radius with neighbor cells, and shard the hotspot cells. Default is nearby businesses and POI, ranked by distance. Draw a geohash prefix first. Quadtree is the trade-off. H3 hexagons are the backup.

The first question is scope. A radius of 0.5, 1, 2, or 5 km is what sets the geohash length. Freshness sets the write path: a static POI catalog changes rarely; nearby people turn location reports into a write hotspot. You rank by distance. Type and opening hours are a post-filter. Write DAU as a teaching assumption, about 10 million, so you can talk about hot cells. Still asking after 10 minutes is its own red flag. Close map tiles and rider matching early. Tiles are elective. Matching is Ch27 · delivery.

I'll assume nearby businesses and POI, radius 0.5–5 km, ranked by distance. The index is a geohash prefix. Query the current cell plus 8 neighbors. Store a coarse cell and a short TTL. Stop me if that direction is wrong.

English

The formulas live in Ch03 · estimates. Here you only prove one thing: the bottleneck is radius reads on hot cells, not nationwide POI writes. Everything below is a teaching assumption.

About 10 million DAU, about 5 nearby searches a person a day, about 20 million POI. 1e7 × 5 / 86400 is about 600 QPS. A 5× peak is still thousands. 高层，一条读路径High-level, one read path

中文

从左到右只画一条读路径。Client 带 lat、lng、radius。Nearby API 编出当前格，算出邻居，向 geo index 取候选 ID，再按 poi_id 到 POI store 补全，最后用真实距离排 top-K。列表只回名称、距离、坐标。Geo index 是 geohash 前缀 → ID 列表。

隐私一句就停：位置截断到格子，短 TTL，不留轨迹。瓦片、路网、配送调度、多 Region 都先不画。画完问一句：方向可以的话，下一笔是格子键怎么选。

English

Left to right, one read path. The client sends lat, lng, and radius. Nearby API encodes the current cell, computes the neighbors, loads candidate IDs from the geo index, hydrates them from the POI store by poi_id, then ranks top-K by true distance. The list is name, distance, and coordinates. The geo index is geohash prefix to ID list.

Privacy, then stop: truncate location to the cell, short TTL, no trace. Leave tiles, road networks, delivery dispatch, and multi-region off this picture. Ask before you continue: if the direction is fine, the next stroke is which cell key you pick.

Hard part：geohash 还是 quadtreeHard part: geohash or quadtree

中文

B-tree 吃的是一维有序键。给 lat 一棵、给 lng 一棵，两个范围相交仍然很大，附近没有变成 seek。2026 白板第一句：平面切成格子，格子 ID 当键。

Geohash 把经纬度的比特交错，编成 base32。多一位，格子更小。公共前缀越长，越可能靠近。白板映射够用：大约 0.5 km 用长度 6，1–2 km 用 5，5–20 km 用 4。能做前缀扫描的库都能存，WHERE geohash LIKE 'wx4g%' 就是这个意思。Redis GEO 把 geohash 当成 sorted-set 的 score，命令是 GEOADD 和 GEOSEARCH。

Quadtree 在密的地方继续切、疏的地方留粗，适合单机内存。邻居要往树上走。静态 POI 一上来自研四叉树，是 over-engineering。trade-off：geohash 哪里都能存前缀，高纬会拉长，角上的邻居更远；quadtree 密度自适应，却不好当成前缀分片键。

H3 是六边形备选。6 个边邻居到中心等距，半径用 k-ring 往外扩。讲不清 resolution，就不要把它换成唯一答案。PostGIS 的 GiST 点到即可。S2 和均匀网格等追问再提。邻格怎么漏，放在失败路径里画。

English

A B-tree wants a one-dimensional ordered key. One index on lat and one on lng still leaves a huge intersection, so nearby never becomes a seek. The 2026 first sentence: tile the plane, and use the cell ID as the key.

Geohash interleaves lat and lng bits into base32. One more character, a smaller cell. A longer shared prefix usually means close. Enough for the board: about 0.5 km is length 6, 1–2 km is 5, 5–20 km is 4. Any store that can prefix-scan works. WHERE geohash LIKE 'wx4g%' is that idea. Redis GEO stores the geohash as a sorted-set score. The commands are GEOADD and GEOSEARCH.

A quadtree keeps splitting where it is dense and stays coarse where it is sparse. That fits one process in memory. Neighbors mean walking up the tree. Leading with a quadtree you wrote yourself, for static POI, is over-engineering. trade-off: geohash stores anywhere as a prefix; cells stretch at high latitude, and corner neighbors sit farther out. A quadtree adapts to density, and it is a poor prefix shard key.

H3 is the hexagon backup. Six edge neighbors are equidistant from the center, and you grow the radius with a k-ring. If you cannot say the resolution, do not make H3 the only answer. PostGIS and GiST, mention and stop. S2 and a uniform grid wait for a follow-up. How a missing neighbor leaks results is the failure path, drawn on its own.

键落在哪种存储上，回 Ch37 · 存储选型 看一眼即可。Which store holds the key is a glance at Ch37 · storage.

位置多久写一次How often location is written

中文

静态目录：商家改一条，写详情，再更新这一行的 geohash，或者 GEOADD。隔夜重建 index 也可以，第二天可见就接受。请求线程里不要扫全表算距离。

附近的人用同一套格子键。每个 GPS 点都写，写路径变成 hotspot，而且你在存一条轨迹。写得太稀，人还在上一格里。中间那档是格子变了再写。缓存 key 用格子 ID。原始经纬度一抖就会打出无数缓存项。短 TTL。讲到这里就停，不要改成轨迹系统，也不要改成 Ch27 · 配送 的匹配。

English

Static catalog: a merchant edits one row, you write the details, then update that geohash row, or GEOADD. A nightly rebuild is fine when next-day visibility is acceptable. Do not scan the table and compute distance on the request thread.

Nearby people use the same cell keys. A write on every GPS sample turns the write path into a hotspot, and you have stored a trace. Write too rarely and the person is still in the previous cell. The middle setting is: write when the cell changes. Cache on the cell ID. Raw lat/lng jitter explodes the key space. Short TTL. Stop there. This does not become a trace store, and it does not become matching in Ch27 · delivery.

写频率讲完就收口。供需匹配留给 Ch27 · 配送。Stop once the write cadence is clear. Supply and demand matching waits for Ch27 · delivery.

热点区域Hotspot cells

中文

POI 和流量都偏在地理上。市中心一格又挤又热，郊区几乎空。全国一个 Redis GEO key，写和 GEOSEARCH 堆在同一个 ZSET 上。按 poi_id 哈希，一次附近查询变成对所有分片的 fan-out。

分片键用格子前缀。一次查询打当前格和少数邻居，多数落在一到两个 shard。长度 3 会装下半个省。和半径同级的 5 到 6 用来路由。再长，一次查询 fan-out 几十片。市中心在长度 6 仍满，就该区域改用长度 7，或者只给这个前缀加读副本。前缀挂到一致性哈希的环上，用虚拟节点，避免对 N 取模。

数据量小的时候，单机加副本仍然成立，把这个假设说出来。原书「geo 索引很小所以绝不切分」不要当 2026 的第一张图。缓存只点到：热前缀的 ID 列表可以短 TTL。就近部署一句够，不要展开多 Region。

English

POI and traffic both skew by place. Downtown is one packed, hot cell. A suburb is almost empty. One nationwide Redis GEO key piles writes and GEOSEARCH onto one ZSET. Hashing by poi_id turns one nearby query into a fan-out across every shard.

The shard key is the cell prefix. One query hits the current cell and a few neighbors, and most of those land on one or two shards. Length 3 holds half a province. Route at length 5 or 6, the same scale as the radius. Much longer, and one query fans out across dozens of shards. If downtown is still hot at length 6, store that area at length 7, or add a read replica only on that prefix. Hang prefixes on a consistent-hash ring, with virtual nodes, so you are not doing modulo N.

A small dataset on one box plus replicas still holds. Say that assumption if they push. The book's "the geo index is small, so never split it" is not the 2026 first picture. Cache, one line: a hot prefix's ID list can take a short TTL. "Deploy nearby" is enough. Do not open a multi-region lecture.

前缀挂到环上的方式在 Ch05 · 一致性哈希。How a prefix sits on the ring is Ch05 · consistent hashing.

失败路径Failure path

中文

这条单独走，不要塞进成功路径的最后一笔。格子是粗筛。圆压在边上，只查当前格，对面的点前缀不同，结果就漏了。这是功能 bug。公共前缀长，往往近；近，不一定前缀长。跨格边、赤道、本初子午线，都要自己算出 8 个邻居，O(1)，和当前格一起查。

格子比圆大，会召回圈外的点。再用球面距离排序，截断 top-K。不要默写公式，也不要假装格里的点都在半径内。半径里不够：geohash 丢掉最后一位再查一圈，H3 加大 k。先约定只返回半径内。为了不漏去扫全表，半径查询就变成扫描。

一行 GEOSEARCH BYRADIUS 做原型很好。一个 key 不能分片。API 对 geo:{prefix} 做 fan-out，合并后再排。邻居可能跨 shard，仍然是一到两个，不是把所有片问一遍。

English

Walk this on its own. Do not hide it as the last stroke of the happy path. A cell is a coarse filter. The circle sits on an edge. Query only the current cell and the point on the other side has a different prefix, so you miss it. That is a functional bug. A long shared prefix usually means close. Close does not mean a long shared prefix. Across a cell edge, the equator, or the prime meridian, compute the 8 neighbor geohashes, O(1), and query them with the current cell.

A cell bigger than the circle recalls points outside it. Then sort by spherical distance and cut to top-K. Do not recite the formula. Do not pretend every point in the cell is inside the radius. Not enough inside the radius: drop the last geohash character and query again, or bump the H3 k. Agree first that you only return points inside the radius. Scanning the table so you never miss turns the radius query into a scan.

One GEOSEARCH BYRADIUS line is a good prototype. One key cannot shard. The API fans out to geo:{prefix}, merges, then ranks. Neighbors may cross a shard. That is still one or two shards, not a question to every shard.

收尾就用漏边、单 key、热格这三句。存储和环分别在 Ch37 · 存储选型Ch05 · 一致性哈希。Close on three lines: the missed edge, the single key, the hot cell. Storage and the ring are Ch37 · storageCh05 · consistent hashing.

The book led with a quadtree and "never shard"

Edges, neighbor cells, and reads over writes still hold. What aged is treating a quadtree memory estimate as a must-dig, leaving the geo index as read replicas only, and never mentioning Redis GEO or H3. In 2026 you draw a geohash prefix first, then shard the hot prefix. H3 waits until they ask for hexagons. Quadtree is the density trade-off, one sentence. Privacy is a coarse cell and a short retention. Label the magnitudes as assumptions. Map rendering and delivery matching stay off this board.
