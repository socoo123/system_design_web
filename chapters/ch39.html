30 秒开场：先定粒度，再定状态Opening: selection grain, then state

中文

我先问均衡的是连接、单次 RPC 还是一整条流。普通 HTTP API 用能读懂请求的 L7；只需转发 TCP/UDP 流或保持 TLS 过身时可选 L4。应用可替换，会话从共享权威读取；真正的内存对局和长流承认连接归属，故障要重连。短请求先轮询，耗时差异大再看 active RPC 与准入额度。计划下线先停新调度，再排空已有工作；突然故障先摘池，已有工作可能失败。高吞吐软件 L4 可评估 Maglev：本机连接表优先，miss 才查固定表；它减少重置，不能把 TCP 状态搬到另一台 App。

这章接在 Ch02 的 LB 与会话外置之后，数字沿用 Ch03 的估算方式，补齐设计题经常省略的机制。七组图依次讲 L4、L7、会话、容量、生命周期、查表、分布式入口故障。每组最后一帧是一张能解释正常路径、代价和失败的完整图。

澄清时要问：客户端可不可信、能否知道多个后端，连接有多长、每条上有多少 RPC，TLS 私钥在哪，允许失去登录还是必须立即撤销，故障按进程还是整台机器计。默认单地域，用两台示意 App 表达路径，真实十二台在容量表里算；游戏迁移协议、DNS 全流程和网格控制面不扩展到本章。

English

Clarify whether selection is per connection, RPC or entire stream. HTTP APIs use request-aware L7; TCP/UDP forwarding or TLS passthrough can use L4. Apps are replaceable and read shared session authority; memory-owned games and streams retain ownership and reconnect on failure. Start short requests with round robin; varied work motivates active-RPC accounting and admission. Planned removal stops new selection then drains; sudden failure excludes the host and may fail active work. Evaluate Maglev for high-throughput software L4: local bindings first, fixed-table lookup on miss; reduced resets do not transfer TCP state.

This extends Ch02’s LB/session evolution using Ch03’s calculation method. Seven decks cover L4, L7, sessions, capacity, lifecycle, lookup and distributed-ingress failures. Each final frame supports normal paths, costs and failure behavior.

Ask about trusted clients and discovery, connection lengths/RPC counts, TLS key placement, login-loss versus immediate revocation, and process versus machine failures. Assume one region. Two Apps illustrate paths; twelve actual instances are sized separately. Game migration, full DNS and mesh control planes stay beyond scope.

连接级 L4：一条大连接可以压满一台L4: one busy connection can fill one backend

正常路径：流键选择一次，后续包保持归属Normal path: select a flow owner and retain it

中文

图上的 Client 把包发给 VIP，L4 LB 按源 IP、源端口、目的 IP、目的端口、协议这五元组匹配一个流，再送 App 1。TLS 和 HTTP/2 在 App 1 处理，本组回程 App 1→L4 LB→Client。包转发型实现可以改地址或封装，并不必终止 TCP；另一类传输代理会终止 TCP 再连后端，但仍可原样搬运加密字节。判断 L4/L7 要看有没有解析请求，不能只问 TCP 在哪终止。

UDP 没有 TCP 那种建立连接的握手；均衡器通常以五元组和空闲超时维护流亲和。QUIC 还可能随迁移改变五元组，是否用 connection ID 取决于具体实现，不能把这里的 TCP 例子扩成所有协议保证。L4 数据面可选择快速转发，健康、路由更新和连接表的成本仍要算。

English

Client sends VIP packets. L4 matches source/destination IPs, source/destination ports and protocol, then selects App 1. App 1 processes TLS/HTTP/2; this deck returns App 1→L4 LB→Client. Packet forwarding can rewrite or encapsulate without terminating TCP. A transport proxy may terminate TCP yet copy encrypted bytes unchanged. Request parsing, not TCP termination alone, distinguishes the selection layer.

UDP lacks TCP connection establishment; flow affinity commonly uses tuples and idle expiration. QUIC migration may change tuples, and connection-ID awareness is implementation-specific. The TCP example is not a universal protocol guarantee. Fast forwarding still pays for health, route updates and flow tracking.

为什么加第二台，仍未必均衡工作Why a second backend may not balance work

中文

HTTP/2 在同一连接上多路复用 stream。[2] A4 的 1,200 RPC/s 全属 c1，即使 App 2 很空，L4 也把它们留在 App 1。1,200÷1,000=120%，已经越过假设舒适线；两台合计的 2,000/s 是总容量，不能拿来证明 c1 能处理。源端口不同的 c2 可被选到 App 2，连接数足够多且工作相近时才可能摊开。

要保端到端 TLS、无需读 path 时可以接受这种粒度，用多连接分散只是替代策略，不能保证一个热点 stream 被拆开。故障摘池主要影响新流，已建立 TCP 换到无状态的另一个 App 也会失去传输状态；应用可替换不表示 socket 可迁移。把“没有业务会话”解释成“连接不存在状态”，会同时错判扩容和容灾。

English

HTTP/2 multiplexes streams on one connection.[2] All A4’s 1,200 RPC/s belong to c1 and remain on App 1 even with an idle App 2: 1,200/1,000=120% of the assumed comfortable line. The aggregate 2,000/s cannot prove c1 capacity. A different-port c2 may use App 2; many similarly loaded flows can spread work.

Passthrough with no path routing may accept this grain. Multiple connections are an alternative, not a guarantee of splitting one busy stream. Ejection primarily affects new flows. Moving an established TCP flow to another business-stateless App still loses transport state. Replaceable Apps do not imply migratable sockets.

正常路径与 TLS 边界Normal path and TLS boundaries

中文

客户端一条 HTTP/2 连接承载 stream 1 和 3。L7 终止客户端 TLS、解析请求并按 path、租户或负载选后端；再通过自己管理的 upstream 连接发送 RPC。stream 1 给 App 1，stream 3 可给 App 2。App 的 headers、正文或 token 先回 L7，再被映射到正确下游流，不能画成 App 直接回客户端。图中两段都加密，后端证书验证和身份边界单独管理。

这是两套连接，不要求一条下游连接对应一条新 upstream，也不要求两边 stream ID 相同。连接池可以复用，每个 RPC 的所属实例在开始时固定；流内每个数据块、WebSocket 消息或 token 不会轮询换后端。后端断开时，已经公开的输出也无法靠代理抹掉，恢复需业务协议支持。

English

One downstream HTTP/2 connection carries streams 1 and 3. L7 terminates client TLS, parses requests and chooses by path, tenant or load, forwarding over managed upstream connections. Stream 1 uses App 1; stream 3 may use App 2. Headers/body/tokens return to L7 and map onto the correct downstream stream. Both segments are encrypted here, with separate upstream identity/certificate validation.

These are separate connection sets: no one-to-one upstream-connection or matching-stream-ID requirement. Pools can reuse connections; each RPC pins an instance when it begins. Chunks, WebSocket messages and tokens do not rotate backends. Proxying cannot retract already exposed output after failure; recovery requires application support.

替代：客户端本身也能按 RPC 均衡Alternative: the client can balance RPCs

中文

“gRPC 必须 L7”要改成条件句：要把一条下游连接里的新 RPC 拆到多个后端，代理必须理解 HTTP/2；但可信客户端可以发现多个后端，建立多个 subchannel，再为每次 RPC 选择一个。[3] 这时没有集中 L7 数据面，客户端要承担发现、健康、策略和各语言 SDK 一致性；不可信公网客户端仍常通过代理。L4 前有足够连接也能分散流量，只是它不感知 RPC 工作量。

A6 算代理负载：6,000×2,000=12 MB/s 请求，6,000×20,000=120 MB/s 响应=960 Mb/s。响应进入代理又从代理发出，I/O 工作量是 240 MB/s；分方向合并，请求加响应使代理接收约 132 MB/s、发送约 132 MB/s，各约 1.056 Gb/s，包头、TLS 和重传另计。这不是一条链路必须达到 2.112 Gb/s 的说法；要看前后网卡和全双工布局。DSR 只适合明确的 L4 拓扑，不能用它删掉 L7 的响应处理。

English

Replace “gRPC requires L7” with a condition: a proxy splitting new RPCs within one downstream connection must understand HTTP/2. A trusted client can instead discover backends, open multiple subchannels and choose per RPC.[3] This removes a central L7 data plane but distributes discovery, health and SDK policy responsibilities. Untrusted public clients commonly use proxies. L4 with many flows can spread traffic without understanding RPC work.

A6 gives 6,000×2,000=12 MB/s requests and 6,000×20,000=120 MB/s=960 Mb/s responses. Receiving and transmitting response bytes is 240 MB/s of I/O work. Combining directions, the proxy receives and sends about 132 MB/s each, or 1.056 Gb/s per direction, before headers/TLS/retransmission. This is not a required 2.112 Gb/s single-link rate; evaluate interfaces and full duplex. L4 DSR cannot eliminate L7 response processing.

无状态应用：会话权威外置，失败契约保留Stateless Apps: shared session authority with failure contracts

从粘滞迁到任意实例From affinity to any instance

中文

最初 sid=s9 只在 App 1 内存，LB 通过 Cookie 亲和把它送回那里。App 1 OOM，用户即使带着同一个 Cookie，也找不回丢失的表。先把有效会话迁入 Session Store，记录 sid、user_id、expires_at、撤销版本；App 1 改读权威并核验，再逐步让 App 2 接流量。迁移时双读不能“哪份说有效就算有效”，旧本地表可能已经过期或被撤销；切换过程中必须明确唯一权威。

共享后两台走相同查询，权威回复再经 App→L7 LB→Client 返回。无状态的定义是实例重启不丢业务权威，仍允许在途请求、连接池和可重建缓存占内存。购物车、库存与幂等结果也不能因入口换机就消失。一个长连接网关可以拥有 socket 与临时 presence，持久聊天记录另放，重连后恢复；对局需要真实的迁移/重放协议，单加 sticky 不是备份。

English

Initially sid=s9 exists only in App 1 RAM and cookie affinity finds that process again. After OOM, the cookie cannot restore lost records. Migrate valid sessions into Session Store with sid, user_id, expires_at and revocation version, switch App 1 to authority reads, then let App 2 receive traffic. Dual reading must not accept whichever copy says valid: a local copy may be expired/revoked. Retain a single authority during migration.

Both Apps read the same authority; replies traverse App→L7 LB→Client. Stateless means restarting an instance loses no business authority; in-flight requests, pools and reconstructible caches can still occupy RAM. Carts, inventory and idempotency results also outlive ingress changes. Connection gateways may own sockets/temporary presence, with durable messages elsewhere. Games need real migration/replay; sticky routing is no backup.

代价、撤销与存储故障Costs, revocation and storage failure

中文

每个受保护 API 查一次会话，A1 就是约 6,000 次会话读/秒，不能看 A7 只有 256 MB 就宣布一台够。A7 两份裸记录 2×1,000,000×256=512,000,000 B=512 MB；索引、对象开销、TTL、复制缓冲和余量另计。共享会话增加一次依赖和 RTT，源 IP 亲和则可能把同一个 NAT 出口的很多人压到一台；可信用户键亲和能少改路由，却仍不能保护内存状态。

安全契约比选 Redis 这个名字更重要。A8 不接受旧授权，所以本例查当前权威、校验过期，不做正向本地授权缓存；存储超时返回不可用，记录不存在或过期才返回未登录。续期、权限修改和撤销用版本条件原子执行，不能无条件 SET 把旧授权续回来。Redis 默认异步复制，WAIT 也不自动提供强一致；提升时可能丢已确认撤销。[5] 要求撤销不丢，就选择满足耐久与一致性契约的权威，或故障期间暂停受保护操作。

已经通过鉴权的请求和随后发生的撤销仍可能竞争。要求“撤销提交后不能发生敏感写”，执行者必须在业务写的安全边界重查 epoch，并让撤销/写按可证明的顺序竞争；单靠入口查一次不能保证。JWT 可本地验签，但签名不等于加密，立即撤销仍要共享状态或短寿命策略。会话标识使用合适的 Cookie 属性，登录/权限变化时轮换标识，登出在服务端失效。[6] 无状态把依赖摆明，没有免掉这些安全成本。

English

One lookup per protected API means about 6,000 session reads/s under A1; A7’s small record volume proves no single-node throughput. Two raw copies are 2×1,000,000×256=512,000,000 B=512 MB. Indexes, object overhead, TTL, replication buffers and headroom are extra. Shared authority adds RTT/dependency. Source-IP affinity can concentrate NAT users; trusted-user affinity reduces remapping but does not protect RAM state.

A8 rejects stale authorization: query current authority, validate expiry and avoid local positive-auth caching. Timeout is unavailable; missing/expired records mean unauthenticated. Renewal and revocation require atomic version conditions. Redis replication is asynchronous by default; WAIT does not automatically provide strong consistency, so promotion can lose acknowledged revocation.[5] Choose authority meeting the durability/consistency contract or pause protected operations.

Entry authorization can race a later revocation. To prohibit sensitive writes after revocation commits, recheck epochs at the write’s security boundary and define provable ordering with revocation; one ingress check is insufficient. Locally verified JWTs do not supply immediate revocation or encryption by signing. Cookie attributes, identifier rotation on privilege change and server-side logout invalidation matter.[6] Statelessness exposes these dependencies without removing their costs.

轮询的前提与容量除法Round robin assumptions and capacity arithmetic

中文

同构实例、相近工作量的短请求，轮询很容易解释和运维；机器大小不同可给权重，但权重应来自同一负载与 SLO 下的容量测试。least-connection 看的是连接，不是请求：HTTP/2 一条可压很多 RPC，另一条可能空闲。least-request 或两候选择少看 active 请求更贴近占用，仍不知道下一笔是轻查还是重算。Envoy 等权 least-request 默认抽两个候选，不要求每次扫描所有实例。[4] 这是运行时选择，与固定哈希表不同。

A2 规划值是 1,000×0.6=600/s；10 台×600=6,000/s 只恰好覆盖。A3 部署 12 个独立机器实例，单机不可用剩 11×600=6,600/s，峰值用规划容量的 6,000÷6,600≈90.9%。一次发布停一台又坏一台，剩 10×600=6,000/s，无规划余量；不是还余 40%。60% 是相对原舒适线，不是新的剩余比例。若 12 个实例放三台机器各四个，坏一台剩 8×600=4,800/s，缺 1,200/s，必须增容量或拒绝约 20% 原始到达。

English

Round robin works well for similar short requests on homogeneous hosts. Weight heterogeneous hosts using capacity under the same workload/SLO. Least-connections counts connections, not RPCs: one HTTP/2 connection can be busy while another is idle. Active-request policies or power-of-two choices better reflect occupancy but do not predict the next request’s cost. Envoy’s equal-weight least-request defaults to two candidates rather than scanning every host.[4] Runtime selection differs from a fixed hash table.

A2 plans 1,000×0.6=600/s; ten instances only cover 6,000/s. Twelve independent machine instances leave eleven at 6,600/s after one loss: peak uses 6,000/6,600≈90.9% of planned capacity. One rollout exclusion plus a failure leaves ten at 6,000/s with no planned headroom, not another 40%. If twelve instances share three machines with four each, one loss leaves eight at 4,800/s, short by 1,200/s, requiring more capacity or rejecting about 20% of original arrivals.

指标只能帮选择，准入才会保护资源Metrics guide selection; admission protects resources

中文

A5 在教学稳态满足 Little 定律，平均 active=6,000/s×0.050 s=300。它不能推出 p99<200 ms，也不能直接把并发上限定为 300；方差、排队、下游与故障分布都需要测试。比较 8 和 2 个在途可选后者，但两个 LB 同时看到 2，都送新请求，会在指标传播前把同一台塞满。图里的 Admission 表示所选 App 的原子额度检查与有限队列，不是每笔都调用一个额外中心服务；permit 可由后端本地实施或由各入口分配保守份额。

队列到顶立即返回过载，等待会消耗同一个 deadline，不能无限排。重试也算工作：如果有 10% 原始请求各多一次 attempt，执行流量是 6,000×1.1=6,600/s，正好吃完单机故障后的规划值；这仍假设重试成本相同且失败不相关。真实整池抖动会相关放大，要有全局重试预算、退避和一次总上限。换成 Maglev 不会生成缺少的 600/s 容量，哈希热点也不会被 round robin 自动治好。

English

A5’s teaching steady state gives Little’s-law mean active work 6,000/s×0.050 s=300. It proves neither p99<200 ms nor an appropriate concurrency ceiling of 300; test variance, queues, dependencies and failures. Selecting two active requests rather than eight helps, but multiple LBs can concurrently observe two and overfill the same host. Admission denotes atomic per-App capacity and bounded queuing, not an extra central RPC service. Enforce locally or allocate conservative ingress shares.

Reject full queues; waiting consumes the same deadline. If 10% of original requests each add one equal-cost attempt, execution rate is 6,000×1.1=6,600/s, exhausting single-loss planned capacity. Correlated failures can amplify more; cap total retries, back off and honor remaining deadlines. Maglev does not create missing capacity, nor does round robin resolve a mandatory affinity hotspot.

探测与下线：突然失败不走优雅退出Health and drain: crashes differ from planned exits

探测有窗口，摘池有传播Probes and ejection have bounded windows

中文

主动探测负责证明某个 endpoint 当前可接工作；被动统计真实调用的超时、连接错误或异常响应，发现只影响业务的故障。TCP 可连只证明 listener 活着，readiness 还要核对服务身份、必要依赖与代表性业务检查；昂贵的全依赖串探又可能造成共同故障，检查要分层和限频。返回 200 不是永久健康承诺，业务请求仍可能刚好遇到崩溃。[7]

A9 设探测间隔 2 s、连续两次失败、每次 timeout 0.3 s。故障发生在上次成功之后最坏时点，探测开始约在 t=2、t=4，第二次到 4.3 s 判失败，选择最多再传播 0.2 s，预算 4.5 s。它假设固定起始节拍、没有调度抖动，并且传播上界真成立；不同调度方式要重算。十二台均匀时坏实例约分到 6,000÷12=500/s，窗口最多约 500×4.5=2,250 个初始 attempt 暴露于风险，不等于全部用户失败，重试成功要按最终结果计。

English

Active probes establish present endpoint readiness; passive timeouts/connection errors/responses reveal business-path failures. TCP listener reachability does not prove service identity, dependencies or representative operations. Expensive correlated full-dependency checks need layering and rate limits. A successful probe is no permanent promise; the next call can hit a crash.[7]

A9 uses 2-second probe intervals, two failures and 0.3-second timeout. A worst-phase failure starts probes near t=2 and t=4; the second expires at 4.3 seconds, followed by at most 0.2-second selection propagation: 4.5 seconds. This assumes fixed probe start cadence, no scheduling jitter and a real propagation bound. With twelve evenly loaded hosts, the failed one receives about 6,000/12=500/s: up to 2,250 initial attempts are exposed, not necessarily failed user requests after retries.

下线屏障、在途和长流Removal barrier, in-flight work and long streams

中文

计划发布走 READY→DRAINING：先撤掉新调度、观察所有相关入口已接收的版本，旧进程保留到在途归零。若只设置一个 discovery 标志就立刻杀进程，入口旧快照还会送新请求；所以本地 admission 也拒绝新工作。更一般的传播没有硬上界，就用确认屏障与截止时间，不能把 sleep 五秒当成已切流的证据。不是每个现成代理都自动实现这套屏障，部署协调器必须验证所用能力。

L7 可停止给旧实例分配新 RPC，HTTP/2 GOAWAY 用 last-stream-id 表明可能已处理的范围；范围内的旧流可以完成，客户端为新请求建立新连接。[2] L4 只停新连接仍不够：已有连接能继续创建 stream，应用或协议端点须主动停止新流。Envoy 文档区分 listener drain、上游连接池和不同协议行为；直接 shutdown 默认也不等于先排空，不能泛化成所有 TCP 协议都能优雅下线。[8]

English

Planned rollout enters DRAINING: remove new selection, observe relevant ingress revisions, then retain the process until active work reaches zero. Discovery flags followed by immediate kill leave stale selectors sending work; local admission must reject late new calls. Without bounded propagation use an acknowledgment barrier and deadline, not a fixed sleep as proof. A deployment coordinator must validate actual proxy capabilities.

L7 can stop new RPC placement. HTTP/2 GOAWAY’s last-stream-id identifies potentially processed streams; old streams can complete and new requests use another connection.[2] L4 refusing new connections does not prevent new streams on an existing one; the protocol endpoint must cooperate. Envoy distinguishes listener draining, upstream pools and protocol behavior; default direct shutdown is not automatically a prior drain.[8]

未知结果不能靠换机器解决A new machine does not resolve an unknown outcome

中文

A10 到 30 s 还活着的长流必须明确取消、关闭或由业务支持续接。取消释放资源的确认另算；应用已提交的订单不会因 socket 断开撤销。突然 UNHEALTHY 的机器可能根本无法排空，故障分支直接停止新选择，已有请求可能失败。恢复先进 WARMING，验证版本、依赖与预热后再回 READY，避免抖动反复进出。

请求重试还要问“后端可能已执行吗”。RFC 9110 对非幂等方法的自动重试有条件限制。[9] 下单即使是无状态 API，也要在业务库里把幂等键、参数摘要、写入和结果原子提交；缺 201 后另一实例按原键查结果，同键换参数拒绝。代理不能因为没有看到响应就断言没有提交。一个 GET 重试通常容易，一条已输出 token 的流或一次付款要额外恢复契约。

English

At A10’s 30-second deadline, explicitly cancel/close long streams or use supported business resumption. Resource-release confirmation is separate; socket loss does not undo committed orders. A suddenly UNHEALTHY host may be unable to drain: stop new selection and allow active calls to fail. Recovery enters WARMING before version/dependency/warmup evidence proves READY.

Retry asks whether execution may already have occurred. RFC 9110 restricts automatic retry of non-idempotent methods.[9] Stateless order APIs still atomically persist an idempotency key, parameter digest, business writes and result. After a missing 201, another instance queries the same key; changed parameters are rejected. A proxy cannot infer no commit from no response. GETs, exposed token streams and payments have different recovery contracts.

Maglev：先连接跟踪，再查一张固定表Maglev: tracking first, table lookup on miss

选择机制与内存账Selection mechanism and memory arithmetic

中文

第六组画决策，不画端到端响应。包先匹配 VIP，再查本机 ConnTrack：命中且原后端仍能服务，就复用；miss 或无效绑定才取 table[hash(flow) mod M]，保存选择，再封装投递。表生成在控制面，包路径只索引一项；有限连接表会过期或被压力冲掉，所以它不能无限保留所有历史 TCP。[1]

M=65,537 是论文默认表大小，现有 Envoy Maglev 配置文档也列相同默认值。[11] A11 另外假设每槽 4 B，65,537×4=262,148 B，除 1,024≈256 KiB；构建时两份是 524,296 B≈512 KiB。它只算单个选择表，VIP 数量、连接跟踪、对象索引与配置存储另计。一千张表约 262.148 MB/份，不能把单表 256 KiB 当整个 LB 的内存用量。

English

Deck six shows selection, not end-to-end responses. Match VIP, then local ConnTrack: reuse a healthy serving binding; otherwise read table[hash(flow) mod M], record it and encapsulate. Build tables off the packet path; lookup indexes one entry. Finite connection tracking expires or evicts entries and cannot preserve unlimited TCP history.[1]

M=65,537 is the paper’s default and also the current Envoy Maglev API default.[11] A11 separately assumes 4 B/slot: 65,537×4=262,148 B≈256 KiB; two copies during rebuilding are 524,296 B≈512 KiB. VIP counts, ConnTrack, indexes/configuration are extra. A thousand such tables are about 262.148 MB/copy, not 256 KiB for the entire LB.

替代与目标：哈希不是负载测量Alternatives and objectives: hashing does not measure load

中文

理解填表只需一句：每个后端从稳定身份生成槽位偏好，按确定顺序轮流填空槽；输入相同才会重建相同表。图上五个玩具槽不冒充真实算法手算。槽位份额接近均匀，仍可能有一个流承载大量字节；更大表可以改善部分重映射表现，也多耗内存与构建时间。表更新整体换入，正在构建的半张表不能被请求看见。

环、rendezvous 与 Maglev 都可以用于后端选择；环也常服务缓存分区，不能说“环只能给 KV”。Karger 等人的 1997 年工作面向 Web 缓存与集合变化时少改映射。[10] 选哪一种要看查找成本、均匀度、任意成员变动和亲和目标。LB 的 HTTP Cookie 哈希键、数据分片键、L4 五元组是三种输入语义，同用一个算法也不会变成同一种工作。

摘掉 N 台里的 1 台，旧属它的约 1/N 槽必须换主人，是直观下限，不是 Maglev 全部改槽比例的保证。重建还可能调整幸存后端间的归属；稳定表也不按 CPU 动态挪一个已建连接。[11] 要治热点，先识别流的大小、请求代价与剩余额度；“查表 O(1)”证明的是选择开销，不是 App p99 或系统吞吐。

English

A deterministic population order gives each stable backend identity a slot preference and fills unoccupied slots in turns. The five toy slots are illustrative. Even ownership does not equal bytes/work: one flow can dominate. Larger tables trade remapping behavior for memory/build time. Publish complete tables atomically, never half-built state.

Ring, rendezvous and Maglev can all select backends; rings also commonly partition caches, so they are not KV-only. Karger et al.’s 1997 work concerns Web caching and minimally changing mappings under membership changes.[10] Choose lookup cost, balance, arbitrary membership and affinity objectives. HTTP cookie keys, data partition keys and L4 tuples give distinct semantics even with the same algorithm.

Removing one of N backends forces reassignment of its roughly 1/N old slots, an intuition for necessary movement, not a guarantee of total Maglev remapping. Surviving owners may also exchange slots.[11] A stable table does not reactively move established flows by CPU. O(1) proves selection cost, not App p99 or system capacity.

多台 LB：同表是条件，DSR 是拓扑Multiple LBs: conditional table agreement and explicit DSR

正常包路径与直接回程Normal packets and direct return

中文

Router 通过 ECMP 把 VIP 包给 LB 1，LB 1 选 App 1 并以 GRE 封装；App 1 才是拥有 TCP 状态的端点。第七组使用 Maglev 论文的 DSR 路径：响应以 VIP 为源，App 1→Router→Client，不穿软件 LB。[1] 回程仍经过路由器，没有把它画成神奇的端到端直线。配置必须允许这种源地址与返回路由，不是给任意反向代理加一条绿线就能实现。

这与第二组 L7 是不同的连接拓扑。DSR 能避开 A6 里的大响应数据面，但 L7 要解密、映射 stream、执行响应策略就必须接回响应。架构图每少一跳，都要有协议与地址机制依据。Anycast 让同一地址在多个地点宣告，路由选的是拓扑路径，不保证物理距离最近；DNS 入口切换也受缓存限制。二者都不搬迁已经存在的 TCP 会话。

English

Router ECMP selects LB 1 for a VIP packet; LB 1 encapsulates to App 1, the TCP owner. Deck seven uses the paper’s DSR: source VIP, App 1→Router→Client, bypassing software LB.[1] Router remains on the return. Source-address and route configuration must support this topology; adding a green shortcut to any proxy does not implement it.

This differs from deck two’s L7 topology. DSR avoids large response payload at the L4 data plane, whereas L7 must receive replies to decrypt/map streams/enforce response policy. Any removed hop requires protocol/address evidence. Anycast chooses a topology path, not guaranteed closest physical distance; DNS changes face caching. Neither relocates established TCP sessions.

故障窗口：新数据面没有旧连接表Failure: a new data plane lacks the old binding

中文

LB 1 消失，Router 把 c1 交给 LB 2；LB 2 的本地连接表没有它，只能重新选择。要继续选到 App 1，须有相同有序后端身份、健康集合、权重、M、哈希种子和算法版本。只说“后端集合相同”漏掉了确定性条件。控制面先生成完整 r7 快照再原子使用，监控实例 revision 分歧；配置或健康传播窗口内，新连接也可能得到不同归属。

r7 完全相同且 App 1 健康，miss 后同表可以帮助连接继续；若 LB 2 已切 r8，表把 c1 改到 App 2，它没有 c1 的 TCP 状态，会 reset 或丢包。若 App 1 自己坏了，保住映射也无用。论文用一致性哈希降低重新选择的风险，并用本机连接跟踪保护大部分已有流，不承诺所有改表、丢 LB 和后端故障都零重置。[1][11]

English

When LB 1 disappears, Router sends c1 to LB 2, which lacks its local binding and must choose anew. Choosing App 1 again requires identical ordered identities, health set, weights, M, hash seeds and algorithm version. “Same backend set” omits determinism conditions. Build and atomically use full r7 snapshots, monitor revision divergence, and retain config/health propagation windows.

Matching r7 with healthy App 1 can preserve the owner. If LB 2’s r8 maps c1 to App 2, that endpoint lacks TCP state and resets/drops packets. App 1 failure defeats matching placement too. Hashing reduces reselection risk and local tracking protects many existing flows; all membership/LB/backend failures are not zero-reset guarantees.[1][11]

代价与边界：应用无状态不等于入口无状态Costs and boundaries: stateless Apps do not erase ingress state

中文

尽量不共享连接表减少同步成本，代价是依赖确定性与少改映射。若业务硬要故障后不断流，就必须证明连接状态接力、协议重建或应用续传，不能从 Maglev 名字推出。长流通常选择客户端重连、明确游标与业务 checkpoint，重新鉴权再继续；有副作用的请求还按原幂等键找结果。

完整口述要保留四条事实：ECMP 选 LB，后端算法选 App，健康/容量决定能不能接，传输与业务状态决定故障后能否继续。单台连通、表均匀和十二台容量是三种证据，互不替代。回到设计题只画必需的层：普通 HTTP API 用请求级入口加可替换应用；要过身才按流；要特定亲和再选哈希；入口本身按故障域扩容并测试，不因为 App 变多就自动获得高可用。

English

Avoiding shared connection tables reduces synchronization cost but relies on deterministic low-remapping selection. Hard no-interruption requirements need proven transport-state handoff, protocol reconstruction or application resumption. Long streams often reconnect with cursors/checkpoints and renewed authorization; side effects recover by the original idempotency key.

Keep four facts: ECMP chooses LB, backend selection chooses App, health/capacity determine admission, and transport/business state determine continuation. Reachability, slot balance and twelve-instance capacity are distinct evidence. In design problems use only necessary layers: request-aware ingress/replaceable HTTP Apps, flow selection for passthrough, hashing for required affinity. Expand and test ingress fault domains independently of App count.
