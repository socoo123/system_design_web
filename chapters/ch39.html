负载均衡与无状态Load balancing & statelessness

本章核心：选谁、能否接、何时停Core: select, admit, then stop

L4 按流保端点，L7 可按新请求选后端；健康只给候选，真正额度由 App 原子准入。应用可替换的前提是会话、业务效果与幂等结果在持久权威里。

  1. 先定选择粒度：连接、新 RPC，还是已开始的长流？
  2. 再定负载口径：观测中的 attempt、实际执行数与容量预算不能混用。
  3. 最后定退出：本地拒新、传播移除、排空；超时或断线仍可能留下未知写结果。

L4 retains flow owners; L7 can choose per new request. Health supplies candidates; App admission enforces actual capacity. Replaceable Apps require durable authority for sessions, business effects and idempotency results.

  1. Choose the selection grain: connection, new RPC or active stream.
  2. Define load: observed attempts, actual execution and capacity budgets differ.
  3. Define exit: close admission, propagate removal, then drain. A timeout or disconnect can still leave a write outcome unknown.

边界：单地域、可替换 API 实例Scope: one region, replaceable API instances

贯穿场景是 Client→L7 LB→App→Session Store，两台 App 示意路径，真实容量假设为 12 台独立机器。先问客户端能否发现多个后端、连接有多长、TLS 在哪结束、故障按进程还是机器算，以及撤销是否允许旧授权。内存对局迁移、DNS 与网格控制面留给专章；本章不声明生产压测。

The running path is Client→L7 LB→App→Session Store. Two Apps illustrate it; capacity assumes twelve independent machines. Clarify client discovery, connection duration, TLS termination, process versus machine failures and acceptable stale authorization. Game migration, DNS and mesh control planes belong elsewhere; this chapter makes no production benchmark claim.

L4：一条大连接仍只落一台L4: a busy connection still has one owner

图1中 c1 固定 App 1，新增 c2 才产生另一次选择。HTTP/2 能在 c1 复用多个 stream，L4 并不因此看懂单次 RPC。[2]

Deck 1 pins c1 to App 1; c2 creates another selection. HTTP/2 multiplexes streams inside c1, without making L4 understand individual RPCs. [2]

包转发例按五元组识别流，TLS 在 App 终止，回程 App→L4 LB→Client。包转发可改地址或封装而不终止 TCP；传输代理也可终止 TCP 后原样转发加密字节。判断粒度要看是否解析应用请求。UDP 的流亲和需空闲超时；QUIC 若变五元组，是否识别 connection ID 是实现能力，不能从本图推断。

A4 的 c1 带 1,200 RPC/s，单 App 能力假设 1,000/s，负载为 120%；两台合计 2,000/s 无法拆掉这条热点。更多连接可能分散新工作，扩容不会搬迁已有 TCP 状态。无状态指业务权威不在进程，不代表 socket 没有状态。

This packet-forwarding example identifies a flow by its 5-tuple, terminates TLS at the App and returns App→L4 LB→Client. Address rewriting or encapsulation need not terminate TCP. A transport proxy may terminate TCP while copying encrypted bytes; request parsing determines selection grain. UDP needs an idle-expiry policy; QUIC connection-ID awareness is implementation-specific.

A4 sends 1,200 RPC/s through c1 against assumed 1,000/s per App: 120%. An aggregate 2,000/s does not split that hotspot. More connections may distribute new work; scaling does not move existing TCP state. Business-stateless Apps still own sockets.

L7：拆新 RPC，已有流保留归属L7: select new RPCs, retain active streams

图2是两套连接：下游 TLS 在 L7 终止，L7 解 HTTP/2 后为每个新 RPC 选择 upstream；后端 TLS 的证书与身份另管。

Deck 2 has two connection sets: downstream TLS terminates at L7, which parses HTTP/2 and selects upstreams for new RPCs. Upstream TLS has separate identity/certificate checks.

stream 1 给 App 1，stream 3 可给 App 2；回复都回 L7，再映射到原下游流。连接池不要求上下游一对一，也不要求 stream ID 相同。一次 RPC、WebSocket 或生成流已开始后，不会逐消息/token 换机；已公开输出无法收回，故障要按应用游标、checkpoint 或重连协议恢复。

gRPC 还可由可信客户端发现后端、建立多个 subchannel，按 RPC 选择；代价是各 SDK 都承担发现、健康和策略。[3] “代理拆单连接里的 RPC 要 L7”成立，“gRPC 一律必须集中 L7”不成立。

Stream 1 uses App 1; stream 3 may use App 2. Both replies return to L7 and map onto the original downstream streams. Pools need neither one-to-one connections nor matching stream IDs. An active RPC, WebSocket or generation stream does not change backends per message/token; exposed output cannot be retracted. Recovery needs application cursors, checkpoints or reconnect protocols.

Trusted gRPC clients can discover backends, open multiple subchannels and select per RPC, distributing discovery, health and policy duties across SDKs. [3] Splitting one connection at a proxy requires L7; gRPC does not universally require a central L7 proxy.

展开 A6：响应为什么也占代理带宽A6: why responses also consume proxy bandwidth

6,000×2,000=12 MB/s 请求，6,000×20,000=120 MB/s=960 Mb/s 响应。代理接收响应后再发给客户端，仅响应就有 240 MB/s I/O 工作；合并请求后，接收和发送各约 132 MB/s=1.056 Gb/s，TLS、包头与重传另计。按网卡、前后链路与全双工分别预算，不能简单宣称一条链路需要 2.112 Gb/s。后文 L4 DSR 的回程特例不能套给这张 L7 图。

Requests: 6,000×2,000=12 MB/s. Responses: 6,000×20,000=120 MB/s=960 Mb/s. Receiving then forwarding responses produces 240 MB/s of I/O work; including requests gives about 132 MB/s=1.056 Gb/s received and sent per direction. Add TLS, headers and retransmission. Budget individual interfaces and full-duplex links; this is not a 2.112 Gb/s single-link requirement. The later L4 DSR topology does not apply to L7.

无状态：外置权威，保留持久与撤销契约Statelessness: external authority still has contracts

亲和是路由偏好，不是备份。图3先把会话放到唯一共享权威，再让 App 2 承接；App 1 重启才能不丢业务事实。

Affinity is a routing preference, not a backup. Deck 3 establishes one shared session authority before App 2 receives work, so an App 1 restart loses no business facts.

sid=s9 的本地表 OOM 后，Cookie 找不回它。迁移要先持久化有效 sid、主体、过期时间与撤销 epoch，再切权威读取；双读不能“任一旧副本说有效就放行”。无状态仍允许连接池、在途请求和可重建缓存留内存；购物车、订单、聊天消息与幂等结果要外置持久权威，连接网关的临时 presence 也要承认重连边界。

A8 查当前会话且不作正向本地授权缓存：不存在/过期是未登录，查超时是不可用，不能放行。续期与撤销按版本原子竞争，不能无条件 SET 续回旧权限。Redis 默认异步复制，WAIT 也不把它变为强一致，切主仍可能丢已确认撤销；选满足耐久契约的权威，或故障时暂停受保护操作。[5]

A Cookie cannot recover a sid=s9 record lost to OOM. Persist valid IDs, principals, expiry and revocation epochs before switching authority reads; dual reading must not accept any stale copy that says valid. Pools, in-flight work and reconstructible caches can stay local. Carts, orders, messages and idempotency results need durable authority; temporary connection presence has reconnect boundaries.

A8 reads current sessions without a positive local-auth cache. Missing/expired means unauthenticated; timeout means unavailable. Renewal and revocation compete atomically by version. Redis defaults to asynchronous replication; WAIT does not make it strongly consistent, so promotion may lose an acknowledged revocation. Use authority meeting the required durability contract, or pause protected work during failure. [5]

展开：敏感写安全边界与会话成本Sensitive-write security boundary and session cost

入口鉴权仍可与之后撤销竞争。若承诺“撤销提交后零敏感写”，要把撤销 epoch 与业务写放进同一可串行化边界，或证明等价协议；单独查共享会话不够。JWT 签名不等于加密，也不自动实现即时撤销。Cookie 属性、登录/权限变化时轮换标识及服务端登出失效按 OWASP 执行。[6]

每受保护 API 一查时，A1 是约 6,000 次会话读/s。A7 单份 1,000,000×256=256 MB，两份 512 MB 只是裸记录，索引、TTL、复制缓冲和余量另算；小体积不证明单机吞吐。按源 IP 亲和还可能把同 NAT 的大量用户压到同一台。

Ingress authorization can race later revocation. A promise of no sensitive write after revocation commits needs revocation epochs and business writes in one serializable boundary, or a proven equivalent protocol. A shared-session lookup alone is insufficient. JWT signing is neither encryption nor immediate revocation. Apply OWASP Cookie controls, rotation after login/privilege changes and server-side logout invalidation. [6]

One lookup per protected API gives about 6,000 session reads/s. A7 is 1,000,000×256=256 MB per raw copy, 512 MB for two, before indexes, TTL, replication buffers and headroom. Small volume proves no throughput. Source-IP affinity can concentrate many NAT users on one App.

路由与准入：先过滤，再比较负载Routing and admission: filter before comparing load

轮询、权重与 P2C 只在可用目标中选择；没有目标就拒绝。图4从等权短请求演进到两候选，再落到各 App 的原子门。灰色 RR 是上一种选择路径，不是绕过准入的通道。

Round robin, weights and P2C select among available targets; no target means rejection. Deck 4 evolves from equal short requests to two choices and the local App gate. The gray RR lane is the earlier policy, not an admission bypass.

候选先满足当前成员快照中的 READY、健康/未摘除与相应 incarnation。普通同构短请求可轮询；异构权重要来自同工作量与 SLO 下的容量。least-connection 数连接，HTTP/2 一条可能承载许多 RPC；等容量 P2C 随机取两个不同候选，选观测 active 更少者。Envoy 等权默认两候选，非等权有另一条动态加权分支；下面不复刻完整产品算法。[4]

Filter the current membership snapshot by READY, healthy/not-ejected status and serving incarnation. Round robin suits comparable short requests; weights require capacity for the same workload/SLO. Least-connections counts connections, which HTTP/2 multiplexing can make misleading. Equal-capacity P2C samples two distinct candidates and chooses fewer observed active requests. Envoy defaults to two for equal weights and uses a different dynamic weighting branch otherwise; this example is narrower. [4]

static Endpoint choose(List<Endpoint> snapshot, RandomGenerator random) {
    var available = snapshot.stream()
        .filter(e -> e.phase() == Phase.READY && e.healthy()).toList();
    int n = available.size();
    if (n == 0) return null; // explicit no-host rejection, no unhealthy fallback
    int i = random.nextInt(n);
    if (n == 1) return available.get(i);
    int j = random.nextInt(n - 1);
    if (j >= i) j++; // sample two distinct candidates
    var a = available.get(i);
    var b = available.get(j);
    return a.observedActive() <= b.observedActive() ? a : b;
}

observedActive 是这个入口所见未结束的 upstream attempt，可能滞后；入口超时后服务端也可能仍在执行。本章显式无可用目标就返回 503，不是 Envoy 的默认 panic 回退政策。[13] READY 也不等于有剩余额度，多个 LB 同看 active=2 仍会同时拥向一台。

真正保证在途不超过 limit 的是所选 App 本地门。以下 Java 17 摘录对应图4 App admission：所有入口在 handler 开始前调用，锁内同时检查代次、READY、进程本地 deadline 和额度，再登记 permit；本例队列长度为 0。只在真实 handler/stream 结束时 finish；调用方超时或发 cancel 不提前释放。完整可运行代码与并发验证在 examples/ch39。

observedActive counts this ingress’s observed unfinished upstream attempts and may lag; server work can outlive a caller timeout. This chapter explicitly returns 503 with no available target, unlike Envoy’s default panic policy. [13] READY does not mean spare capacity: multiple LBs can all observe two and select the same App.

The selected App’s local gate actually bounds active work. This Java 17 excerpt implements deck 4’s App admission. Every ingress path enters it before starting a handler; one lock checks incarnation, READY, process-local deadline and capacity before recording a permit. The queue is zero. finish runs only on actual handler/stream completion, never merely on caller timeout or requested cancellation. Runnable source and concurrency checks are in examples/ch39.

Permit tryAdmit(long expectedIncarnation, long deadline) {
    lock.lock();
    try {
        long now = clock.getAsLong(); // sample after acquiring the lock
        if (expectedIncarnation != incarnation || phase != Phase.READY ||
            now - deadline >= 0 || active.size() >= limit) return null;
        long id = Math.incrementExact(sequence);
        sequence = id; active.add(id);
        return new Permit(this, incarnation, id);
    } finally { lock.unlock(); }
}
boolean finish(Permit permit) { // actual handler completion, not caller timeout
    lock.lock();
    try {
        return permit != null && permit.owner == this &&
            permit.incarnation == incarnation && active.remove(permit.sequence);
    } finally { lock.unlock(); }
}

finish 绑定 Gate 和代次，并用集合删除保证只释放一次。本地锁只保护这一台 App；观测计数不是全局额度协议。deadline 用锁后采样的 monotonic 时钟，跨机器传剩余预算后再转换，不能直接比较两台的 nanoTime。

finish binds Gate/incarnation and removes each permit once. A local lock protects this App only; observed counts are not a distributed reservation protocol. Sample the monotonic clock after acquiring the lock. Convert remaining budgets into each process’s clock domain rather than comparing raw nanoTime values across hosts.

展开 A1–A5：正常、故障、重试与均值A1–A5: normal load, failures, retries and means

单 App 规划 1,000×60%=600/s；正常至少 6,000÷600=10 台，恰好覆盖。12 台各在独立机器，一台故障剩 11×600=6,600/s，峰值使用规划值的约 90.9%；发布停一台再坏一台只剩 10×600=6,000/s，无规划余量。若三机各四个实例，坏一机剩 8×600=4,800/s，缺 1,200/s，须增容或拒绝 20% 原始到达。

10% 原始请求各多一次等成本 attempt，执行率 6,000×1.1=6,600/s，吃完单故障预算；相关失败还会放大，需总重试预算、退避和 deadline。稳态 Little 定律给平均在途 6,000×0.050=300，不能用它设 limit=300 或证明 p99<200 ms。limit、等待队列与多维资源上限要按实测请求分布决定；本例不排队，饱和即拒绝。

Plan 1,000×60%=600/s per App. Normal load needs 6,000/600=10 instances with no planned headroom. Twelve independent machines leave 11×600=6,600/s after a loss, about 90.9% utilized. One rollout exclusion plus a failure leaves 10×600=6,000/s. Four instances on each of three machines leave 8×600=4,800/s after one machine loss: a 1,200/s deficit, or 20% of original arrivals.

If 10% add one equal-cost attempt, execution is 6,000×1.1=6,600/s, exhausting the single-loss budget. Correlated failures need total retry budgets, backoff and deadlines. Little’s-law mean is 6,000×0.050=300 active; it establishes neither limit=300 nor p99<200 ms. Size admission, queues and other resource bounds for the measured request distribution; this example rejects at saturation without queuing.

健康与排空：关本地门，再等旧工作Health and drain: close locally, retain old work

健康检查有滞后，readiness 不是资源锁。计划下线在本地与准入原子竞争：先 DRAINING 拒新，再发布移除；已有工作保留。突然失败则停止新选择，不能承诺完成在途。

Health checks lag; readiness is not a resource lock. Planned drain competes atomically with local admission: enter DRAINING first, then publish removal and retain active work. Sudden failure stops new selection without promising completion.

主动探测检查身份与代表性业务，被动信号观察真实超时/错误；TCP 可连只证明 listener 活着。[7] 共享依赖全失败时，盲目让所有实例同时退出会失去可恢复入口；检查分层、限频，区分共同依赖故障与单实例故障。短暂过载优先由额度拒绝和背压处理，别把每次 503 都当进程死掉再重启。

以下摘录闭合图5的计划分支。beginDrain 先核验命令的 incarnation 再关本地门，协调器随后发布带 revision 的移除。acknowledgeRemoval 只接受可信协调器对相关入口的确切代次/版本确认；普通 readiness=false 或 Kubernetes EndpointSlice 异步更新不等于这个屏障。[12] 若产品没有确认能力，按截止执行显式强停并承认晚路由风险，不能用 sleep 当证据。

Active probes check identity/representative operations; passive signals observe real errors/timeouts. TCP reachability proves only a listener. [7] Blindly ejecting every instance for one shared dependency failure can remove recovery paths. Layer and rate-limit checks; distinguish shared and per-instance failures. Handle transient overload with admission/backpressure rather than treating every 503 as a dead process.

This excerpt closes deck 5’s planned branch. beginDrain checks the command’s incarnation and closes locally before the coordinator publishes removal at a revision. acknowledgeRemoval accepts only trusted evidence for the exact incarnation/revision at relevant ingress instances; readiness=false or asynchronous Kubernetes EndpointSlice updates are not that barrier. [12] Without confirmation support, take an explicit bounded forced path and admit stale-routing risk; sleep is not evidence.

long beginDrain(long expectedIncarnation, long revision, long budgetNanos) {
    lock.lock();
    try {
        if (expectedIncarnation != incarnation) throw new IllegalStateException("stale incarnation");
        if (phase == Phase.DRAINING && revision == drainRevision) return drainUntil;
        if (phase != Phase.READY || revision < 1 || budgetNanos < 0 ||
            budgetNanos >= (1L << 62)) throw new IllegalStateException();
        long now = clock.getAsLong();
        phase = Phase.DRAINING; // close locally before publishing removal
        drainRevision = revision;
        drainUntil = now + budgetNanos;
        return drainUntil;
    } finally { lock.unlock(); }
}
boolean acknowledgeRemoval(long expectedIncarnation, long revision) {
    lock.lock();
    try {
        if (expectedIncarnation != incarnation || phase != Phase.DRAINING ||
            revision != drainRevision) return false;
        removalAck = true; return true;
    } finally { lock.unlock(); }
}
DrainDecision pollDrain() {
    lock.lock();
    try {
        if (phase != Phase.DRAINING) throw new IllegalStateException();
        long now = clock.getAsLong();
        if (removalAck && active.isEmpty()) return DrainDecision.CLEAN_EXIT;
        return now - drainUntil >= 0 ? DrainDecision.FORCE_REQUIRED : DrainDecision.WAIT;
    } finally { lock.unlock(); }
}

重复 drain 保留原截止，不能续长；CLEAN_EXIT 要求移除确认且真实 active=0，FORCE_REQUIRED 只请求取消/关闭或强杀，不清计数，也不证明 OS 已退出。STOPPED 由外部 supervisor 确认。进程一代只允许 WARMING→READY 一次；DRAINING/UNHEALTHY 不被迟到探测复活，恢复在新进程 incarnation 完成预热，旧路由/回调不能改新门；不能在同进程另建 Gate 抹掉仍执行的旧工作。

L7 停止给旧实例分配新 RPC；L4 只停新连接仍挡不住旧 HTTP/2 连接新建 stream，需协议端点协作。GOAWAY 的 last-stream-id 标出可能已处理范围，更大 stream ID 可按协议重试；范围内不能据“没回复”断言没处理。[2] Envoy 的 drain 行为依赖协议和网络过滤器，普通 shutdown 默认不等于先 graceful drain。[8]

Duplicate drain retains the original cutoff. CLEAN_EXIT requires confirmed removal and actual zero active work; FORCE_REQUIRED asks for cancellation/close/kill without clearing counts or proving OS exit. A supervisor observes STOPPED. An incarnation enters READY only once from WARMING; late probes cannot revive DRAINING/UNHEALTHY. Recovery warms a fresh process incarnation, isolating old routes/completions; replacing a Gate object must never hide old work still running in that process.

L7 stops assigning new RPCs; L4 refusing new connections still permits new streams on existing HTTP/2 unless protocol endpoints cooperate. GOAWAY’s last-stream-id marks potentially processed streams; larger IDs may retry under the protocol, while a missing reply at or below the bound does not establish nonexecution. [2] Envoy draining depends on protocol/filter support; default shutdown does not imply a prior graceful drain. [8]

展开 A9：4.5 秒探测窗口A9: the 4.5-second detection window

固定开始节拍每 2 s、连续 2 次失败、timeout=0.3 s，故障刚好发生在上次成功后：下一次约 t=2，第二次约 t=4，到 4.3 判失败，再加传播≤0.2，预算 4.5 s。只有无调度抖动且传播真有上界才成立，不套用给任意产品。十二台均匀时每台约 6,000÷12=500/s，按均匀稳态估计约 500×4.5=2,250 个初始 attempt 暴露（不是随机路由的严格上界）；最终用户失败要再看有界重试，不把所有暴露都算失败。

With fixed probe starts every 2 s, two failures and 0.3 s timeouts, a failure immediately after success is probed near t=2 and t=4. The second expires at 4.3 s; propagation≤0.2 gives 4.5 s. This requires no scheduling jitter and a real propagation bound. At 6,000/12=500/s per evenly loaded App, about 500×4.5=2,250 initial attempts are exposed, not necessarily failed user requests after bounded retries.

断线后的写：先保留 UNKNOWNWrites after disconnect: retain UNKNOWN

订单在 DB 提交，App 尚未回 201 就断线：换一个无状态实例也不能判断“没执行”。业务幂等键必须绑定租户、主体、操作、资源与规范参数，和业务写/结果在同一库事务提交，保留至少覆盖重试与查账期。之后按原键查询或在有效防重契约内同键重放；同键改参数拒绝。外部付款效果不能被本库事务包住，按 Ch24 查权威回执。

A10 至多重试一次仍受原 deadline/预算约束，且必须先有安全重试语义。RFC 9110 要求代理不得自动重试非幂等请求，不能仅凭 POST 没回包就换机重发。[9] 长流已输出的 token 或已提交的写不会因关 socket 回滚；调用方超时也不能替服务端释放准入额度。

An order commits in the DB, then the connection fails before 201. Another stateless App still cannot infer nonexecution. Bind idempotency to tenant, principal, operation, resource and canonical arguments; commit effect/result together in one database and retain them through the recovery window. Query the original key, or replay that key only under a valid dedupe contract; changed binding conflicts. External payment effects remain outside that transaction and require authoritative receipts as in Ch24.

A10’s one retry remains subject to the original deadline/budget and safe retry semantics. RFC 9110 prohibits proxies from automatically retrying non-idempotent requests; a missing POST response is insufficient. [9] Closing a socket does not retract exposed tokens or committed writes. Caller timeout cannot release the server’s active-work permit.

Maglev：本机绑定优先，miss 才查表Maglev: local bindings first, table on miss

图6只画后端选择，不画 HTTP 回程。应用无状态与 LB 连接状态是两份契约；完整 L4/DSR 包路径在下一组。

Deck 6 depicts backend selection, not HTTP responses. Stateless Apps and LB connection tracking are separate contracts; deck 7 shows the full L4/DSR packet path.

VIP 包先查本机 ConnTrack，命中且原后端仍可服务就复用；miss/无效才索引 table[hash(flow) mod M] 并记录归属。表外构建后整体原子换入，包路径只查一项。论文的连接表有限、仅过期才逐出；满后不能记录的新流会依赖重新选择，不是承诺压力逐出所有活跃表项。[1]

每个稳定后端身份生成槽偏好，按确定顺序轮流填空槽；同输入才同表。五个玩具槽不冒充完整填表算法。移除一台，其旧约 1/N 槽必须换主，但幸存后端之间也可能改槽；Envoy 明确 minimal disruption 不是绝对保证。[11] 槽数均匀不等于字节/CPU均匀，O(1) 查表不证明 App p99。

环、rendezvous 和 Maglev 都能选后端；Karger 原文就面向 Web 缓存，不能把环说成 KV 专用。[10] 选择依据是查找成本、成员变化、均衡和亲和目标；数据分区键、Cookie、L4 五元组是不同语义的输入。

A VIP packet first consults local ConnTrack. Reuse a binding while its backend can serve; on miss/invalidity index table[hash(flow) mod M] and record the owner. Build complete tables off-path and swap atomically. The paper’s finite tracking table evicts only expired entries; when full, unrecorded flows depend on reselection, not a promise of pressure-evicting active bindings. [1]

Stable identities generate slot preferences and deterministic filling; identical inputs yield identical tables. Five toy slots do not implement the full population algorithm. Removing one backend forces its roughly 1/N old slots to move, but surviving owners can exchange slots too. Envoy explicitly treats minimal disruption as nonabsolute. [11] Even slot counts do not imply balanced bytes/CPU; O(1) lookup proves no App p99.

Rings, rendezvous and Maglev all select backends. Karger’s original work targets Web caching, so rings are not KV-only. [10] Decide by lookup cost, membership changes, balance and affinity. Partition keys, Cookies and L4 tuples have distinct meanings.

展开 A11：单表内存不是整个 LB 内存A11: one table is not total LB memory

论文及 Envoy 默认 M=65,537。[1][11] A11 自设每槽 4 B，单份 65,537×4=262,148 B≈256.004 KiB；双缓冲 524,296 B≈512.008 KiB。1,000 张表是 262.148 MB/份。VIP、连接跟踪、索引与配置都要另算，表更大也增加构建成本。

The paper and Envoy default to M=65,537. [1][11] A11 separately assumes 4 B/slot: 262,148 B≈256.004 KiB per table; double buffering is 524,296 B≈512.008 KiB. A thousand tables take 262.148 MB/copy, before VIP, tracking, index and configuration costs. Larger tables also cost more to build.

多台 LB：同表帮助重选，不迁移 TCPMultiple LBs: same-table reselection does not migrate TCP

ECMP 先选 LB，LB 再选 App；TCP 状态仍在 App。图7明确采用论文的 GRE+DSR：回复 App→Router→Client，不经过软件 LB。[1]

ECMP selects an LB; that LB selects an App, which owns TCP state. Deck 7 explicitly uses the paper’s GRE+DSR: App→Router→Client replies bypass the software LB. [1]

DSR 需要 VIP 源地址、封装和回程路由支持；不能给任意 L7 反向代理加一条绿线就删掉响应处理。LB 1 消失后，LB 2 本地没有 c1 绑定，若 r7 的有序身份、健康集、权重、M、hash 种子及算法版本全同，才可重选仍健康的 App 1。控制面整体发布快照并监控 revision 分歧，不能只写“后端集合相同”。

若 LB 2 的 r8 把 c1 改到 App 2，它没有 TCP 状态，会 RESET 或丢包；若原 App 自己坏了，同表也无用。Maglev 减少重新选择风险，没有保证入口、后端与改表同时失败也零重置。[1][11] 长连接要证明状态接力或应用重连/续传；Anycast 与 DNS 路由同样不搬旧 TCP。

DSR needs VIP source-address, encapsulation and return-routing support; it cannot erase L7 response processing by adding a shortcut arrow. After LB 1 loss, LB 2 lacks c1’s binding. Matching r7 requires ordered identities, health set, weights, M, hash seeds and algorithm version to reselect healthy App 1. Publish complete snapshots and monitor revision divergence; the same backend set alone is insufficient.

If r8 maps c1 to App 2, the missing TCP state causes RESET/drop. Failure of App 1 defeats matching tables too. Maglev reduces reselection risk without guaranteeing zero resets across every ingress/backend/table failure. [1][11] Long connections need proven state handoff or application reconnect/resumption; Anycast and DNS do not relocate old TCP either.
