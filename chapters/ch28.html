English

  • Walk both the write path and the read / watch path on one picture: console, Config Service, a versioned Config Store, a notify channel, and a local snapshot inside each process.
  • Say whether readers must already observe N+1 when the publish API returns, and which freshness assumption covers the mixed-version window.

中文

配置中心解决的是：运行中的进程如何拿到一份新的、可回滚的键值，而不把每次业务请求打到配置库上。我先假设这是应用配置：超时、限流阈值、feature flag、文案和少量运维开关。写路径是 Admin Console 到 Config Service，再追加一条带版本的 Release 到 Config Store。读路径是进程启动时拉一份快照，之后用 long-poll 或一条长连接 watch；通知只带 namespace 和版本，正文再 GET。发布接口在存储提交后返回，不要求每一台实例已经换成 N+1。灰度是同一把 key 上故意存在的第二份版本。注册发现只回答「谁活着」，这里只回答「这个 key 现在是什么值」。

Git 仓库、部署清单、服务网格和完整的服务治理都不进第一张图。配置中心挂了之后，已经在跑的进程默认继续用上一份校验通过的快照；只有标成安全熔断的 key，才在快照过期后拒绝那条危险动作。这些是写在白板上的假设，面试官可以改规模或改新鲜度。

English

A configuration center answers how a running process obtains a new, rollback-able value without sending every business request to the config database. Assume application config: timeouts, rate-limit thresholds, feature flags, copy, and a few operational switches. The write path goes from the Admin Console through Config Service and appends a versioned Release to the Config Store. The read path pulls a snapshot at startup, then watches with long-poll or one long-lived connection. Notify carries the namespace and the version; the body is a separate GET. The publish API returns after the store commits. It does not wait until every instance has moved to N+1. A gray release is a second version of the same key, published on purpose. Discovery answers who is alive. This system answers what the key is.

A Git repository, a deploy manifest, a service mesh, and a full governance platform stay off the first diagram. So do URL shorteners, object storage, and recommendations. When the center is down, an already-running process keeps the last snapshot that passed its checksum. Only a key marked as a security kill-switch refuses the dangerous action once that snapshot is too old. These are whiteboard assumptions so the design can continue. The interviewer can change the scale, the freshness target, or demand a stronger rule for one key.

中文

数量级是为了删掉错误的第一张图。假设舰队有 10,000 个进程，每个进程关心 10 个 namespace。如果每个 namespace 每 5 秒做一次短轮询，请求率是 10,000 × 10 / 5 = 20,000 次 GET/秒。发布本身每秒往往不到一次，所以这 2 万次里绝大多数是「没变」。短轮询把控制面做成了一条假的高 QPS 读路径。Chubby 的论文用 DNS 的 TTL 做过同一类账：3,000 个客户端、60 秒 TTL、彼此都要解析名字时，查找会到每秒 15 万次；他们改用会话上的显式失效，就是为了让「没变」不再产生按 key 计费的轮询。[3]

把 10 个 namespace 复用到每进程一条 long-poll 上，空闲挂起 60 秒再续约。稳态续约是 10,000 / 60 ≈ 167 QPS，外加真正变更时被叫醒的那一小批。167 和 20,000 差两个数量级，这就是 long-poll 相对短轮询的理由。push 的连接数仍然约是 1 万。它省掉的是大部分续约，并把「变更已发生」压到一次推送往返。在这个假设规模上两者都放得下。默认先讲 long-poll，是因为它仍是普通 HTTP。杀伤性开关若把新鲜度收到 1 秒以内，再把这一类订阅改成 push。

本地快照要单独算，因为它决定 Config Store 在不在用户路径上。假设每个进程每秒调用 1,000 次 getConfig，舰队是 10,000 × 1,000 = 10,000,000 次/秒。这些调用若穿过网络去读配置库，控制面会变成业务读的同步依赖。快照把这 1,000 万次留在进程内。Config Store 稳态只看见发布（峰值假设 50 QPS）、watch 续约（约 167 QPS）和对账。对账若每 5 分钟每进程一次，是 10,000 / 300 ≈ 33 QPS。

磁盘不是瓶颈，但要算一次。假设不同的 key 约 2,000 个，值平均 4 KB，每个 key 保留 30 条历史 Release。原始体积约 2,000 × 4 KB × 30 = 240 MB。三副本和索引之后，按 1 GB 这一档规划就够。Chubby 的抽样里 90% 的文件不超过 1 KB，后来还加了 256 KB 上限，因为有人把它当成通用存储。[3] 配置中心同样拒绝大对象。

English

The order of magnitude exists to delete the wrong first diagram. Assume 10,000 processes, each interested in 10 namespaces. A short poll of every namespace every 5 seconds is 10,000 × 10 / 5 = 20,000 GETs per second. Publishes are often below one per second, so almost all of those 20,000 are “unchanged.” Short-polling turns the control plane into a fake high-QPS read path. The Chubby paper runs the same kind of account for DNS TTLs: 3,000 clients, a 60-second TTL, and a quadratic name-resolution pattern produced on the order of 150,000 lookups per second. They moved to explicit invalidation on a session so that “unchanged” stopped generating a poll per name. [3]

Multiplex those 10 namespaces onto one long-poll per process and renew after a 60-second idle hold. Steady renewals are 10,000 / 60 ≈ 167 QPS, plus the small set that wakes when something actually changes. What you hold is about 10,000 connections, not 20,000 empty GETs. Two orders of magnitude is the reason to prefer long-poll over short-poll. A push connection still costs about 10,000 sockets. What it removes is most of those 167 renewals, and it shrinks “a change happened” from “unblock the held request, then GET” to one push round trip. At this assumed scale both fit. Lead with long-poll because it stays ordinary HTTP and does not ask the load balancer to speak a new streaming protocol. If a kill-switch freshness assumption tightens to under a second, move that subscription to server push. The SLO triggers the switch.

The local snapshot needs its own line because it decides whether the Config Store sits on the user path. Assume each process calls getConfig 1,000 times a second on the business path: timeouts, limits, flags. The fleet is 10,000 × 1,000 = 10,000,000 calls a second. If those calls cross the network into the config database, the control plane becomes a synchronous dependency of product traffic, and a low publish rate does not save you. The snapshot keeps those 10 million calls in-process. In steady state the Config Store sees three small streams: publishes (an assumed peak of 50 QPS), watch renewals (about 167 QPS), and an optional reconcile. A version check every five minutes per process is 10,000 / 300 ≈ 33 QPS. “Read the config database on every request” amplifies a low-hundreds control plane into the tens of millions under this assumption.

Disk is not the bottleneck, but say the sum once so you do not invent a storage crisis. Assume about 2,000 distinct keys, because many processes subscribe to the same namespaces, an average value of 4 KB, and 30 historical Releases kept per key. Raw size is about 2,000 × 4 KB × 30 = 240 MB. Three replicas, indexes, and audit rows still plan in the 1 GB range. Chubby’s production sample was the same shape: 90% of files were at most 1 KB, and files over 10 KB were 0.2%. They later capped files at 256 KB because a client had started using the lock service as general storage. [3] A config center refuses large objects the same way. A picture, an experiment blob, or a rule document can live here. User uploads and model files do not.

高层架构：写进去，再被 watch 出来High-level architecture: a write, then a watch

顺着终图走一遍

操作者在 Admin Console 里提交草稿。Config Service 核对身份、namespace 写权限、值的大小、checksum 和 expected_version。通过之后向 Config Store 追加 Release，版本变成 N+1。存储若用 Raft 一类的复制日志，记录在多数副本收下之后才算提交。领导者可以对发布者返回成功，同时把同一条日志补给慢副本。[2] 绿色回箭头上的 201 停在这一步。它证明版本已经在权威日志里，不证明每台 App 的内存已经换成新值。

提交之后，Config Service 往 Notify Bus 放一条瘦事件：namespace、key、新版本号、checksum。总线失败时，发布仍然保持已提交。订阅者会在 long-poll 超时后续约，或在对账里用版本号发现差距。ZooKeeper 的 watch 也是这个形状：通知只说明变了，不附带新内容；客户端必须再读一次，并在同一次读上重新登记，因为 watch 是一次性的，触发或会话结束就会注销。[1] 我们的 GET 就是那一次再读。checksum 通过之后才替换快照。此后 getConfig 只读这份快照。

三台 App 用来表明扇出发生在 watch，不发生在用户请求。Config Service 可以加机器来挂住约 1 万条连接，但任何一台都不许把版本日志只放在自己的堆里。两台同时接到发布时，冲突由 Config Store 的条件写裁决：expected_version 已经不是 N 的那次得到 409。内存里的 Map 做不到这一点，进程一重启，发布就消失。

Walk the final frame

The operator submits a draft in the Admin Console. Config Service checks identity, write permission on the namespace, value size, the declared checksum, and the client’s expected_version. It then appends a Release to the Config Store and the version becomes N+1. If that store is a Raft-style replicated log, the record is committed once a majority has it. The leader may return success to the publisher and keep shipping the same entry to a slow follower. [2] The green 201 stops there. It proves the version is in the authority log. It does not prove that App A, B, and C have swapped their memory.

After the commit, Config Service puts a thin event on the Notify Bus: namespace, key, new version, checksum. If the bus fails, the publish stays committed. Subscribers notice on the next long-poll renewal or on the reconcile pass, using the version number. A ZooKeeper watch has the same shape: the notification says that something changed and does not include the new bytes. The client must read again and re-arm the watch on that read, because a watch is a one-time trigger, dropped when it fires or when the session closes. [1] Our GET is that second read. The process checks the checksum and replaces the in-process snapshot. Later getConfig calls read only that snapshot.

The three apps are there to show that fan-out happens on the watch, not on the user request. Config Service can add machines to hold the roughly 10,000 connections, and none of those machines may keep the version log only on its heap. When two Config Service nodes accept a publish together, the Config Store’s conditional write decides the winner. The call whose expected_version is no longer N receives 409, and the console reloads before it submits again. An in-memory map cannot do that. A restart would erase the publish.

为什么是这五个角色

Admin Console 拥有草稿、审批和谁点了发布，不拥有运行中进程的连接表。Config Service 拥有校验、条件写和 watch 的挂起，不拥有版本的存活。Config Store 拥有 Release 序列，是唯一的 source of truth。Notify Bus 把叫醒移出发布延迟，不拥有正文，所以重放一条通知是安全的。本地快照拥有这台进程当前相信的值，以及 version、checksum、策略和拉取时间。

这个拆分来自前面的算术。发布峰值按假设只有几十 QPS，一张带单调版本的表或一条复制日志就够，不必为写分片。连接数约 1 万，所以要能挂起请求的服务，而不是让数据库替每个订阅者保持一条查询。getConfig 约 1,000 万次/秒，所以快照必须在进程内。ZooKeeper 把配置当成基本的协调问题，并且不让慢客户端挡住写：watch 在本地副本上触发，写仍走可线性化的广播。[1] 要讲清的是这几条性质：持久的版本顺序、一次性通知、读者用本地副本继续干活。

Why these five roles

The Admin Console owns drafts, approval, and the record of who pressed publish. It does not own the connection table of running processes. Config Service owns validation, the conditional write, and parking or releasing watches. It does not own the survival of a version: any of its machines can be replaced. The Config Store owns the Release sequence and is the only source of truth. The Notify Bus owns the decision to take the wake-up out of the publish latency. It does not own the body, so replaying a notice is safe and subscribers dedupe on the version. The local snapshot owns the value this process currently believes, plus that value’s version, checksum, policy, and fetch time. Business code owns how to use the value. It does not own how to discover that the value changed.

The split comes from the arithmetic. An assumed publish peak of a few tens of QPS means a table with a monotonic version, or one replicated log, is enough. You do not shard for writes. About 10,000 connections mean a service that can park requests, not a database query held open per subscriber. About 10 million getConfig calls a second mean the snapshot stays in-process. Invalidation targets one namespace inside one process, not a row in the product database. The ZooKeeper paper names configuration as a basic coordination problem and deliberately leaves locks out of the server, so a slow client cannot stall an update. Watches are served from a local replica. Writes still go through a linearizable broadcast. Reads are not placed in that same total order. [1] A config center needs those properties: a durable version order, a one-shot or session-scoped change notice, and readers that keep working from a local copy. A coordination service can store a few tiny critical keys, or you can build the Config Store yourself. Name the property you need.

另一条能走通的路

若新鲜度假设收紧到「每个订阅者确认之后发布才返回」，架构就变成 Chubby 的缓存协议：主副本记下谁可能缓存了这份数据，写入被挡住，直到每个客户端确认失效，或它的租约到期。他们要的是「要么看到一致状态，要么看到错误」。代价是慢客户端把修改拖到租约结束。默认租约延长是 12 秒，过载时主副本会把租约抬高。[3] 普通 flag 的发布不采用这个等待。安全熔断把「不能再用旧值」放在读侧：一台已经死掉的进程不会拖住紧急开关的提交。

小规模时 Console、Config Service 和 Store 可以是同一进程里的三个模块。接口仍是 get、watch、publish，仍有 expected_version。连接数或审计跨过单机之后，再把 Store 换成复制日志。单区域的提交定义还没讲清之前，不上多区域。

A design that also works

If the freshness assumption tightens to “return from publish only after every subscriber acks,” the architecture becomes Chubby’s cache protocol. The master remembers who might have cached the file, and the write blocks until every such client acks the invalidation or its cache lease expires. Chubby chose that because a client should see either a consistent state or an error, and because they expected programmers to misuse anything weaker. [3] The same section states the cost: a slow or unreachable client delays the modification until lease expiry. Their default lease extension is 12 seconds, and an overloaded master raises it toward 60 seconds to cut KeepAlives. For timeouts and experiment flags, that wait ties a human publish to the slowest machine, so this design does not take it. For a security kill-switch, “do not keep using the old value” lives in the reader’s local policy, not in the success condition of the publish RPC. A dead process then cannot stall the commit of an emergency switch.

At small scale the console, Config Service, and store can be three modules in one process, with an embedded library in front. Keep the same interface shape: get, watch, publish, and expected_version. When connections or audit outgrow one machine, move the store to a replicated log and hang watches on a separate Config Service. Multi-region on day one immediately asks which region’s N+1 counts, and what the current pointer does during a partition. Do not pay that until a single region’s commit rule is explicit.

这一层最容易说漏的边界

201 返回之后、GET 完成之前，舰队里同时有 N 和 N+1。这是 API 的定义。若改成「返回等于全球已经生效」，回箭头必须收齐失效确认，并给失联客户端租约超时，可用性就绑在最慢客户端上。ZooKeeper 拒绝挡住写的失效，因为慢客户端会延迟更新。[1] 异步通知不能口头说成同步切流。

The boundary that gets dropped

Between the 201 and the subscriber’s GET, the fleet necessarily holds N and N+1 at once. That is the definition of this API, not a replication bug. If the interviewer changes the assumption to “publish returns only when the change is globally visible,” move the end of the return arrow: it must collect every invalidation ack and give an unreachable client a lease timeout. Availability then becomes a function of the slowest client or of the lease length. ZooKeeper rejected blocking invalidation because Chubby delays an update on a slow client. Watches take that problem off the write path. [1] The two papers describe two contracts. A config center picks one and writes it into the SLO. An async notify on the diagram cannot be narrated as a synchronous cutover.

API 与最小数据模型API and the minimum data model

中文

三个调用把终图上的箭头固定下来。get 读取一份 namespace 在某个版本下的正文。watch 只回答「你知道的版本还是不是当前版本」。publish 追加一条新 Release。三者不要并成一个「推送整份配置」的套接字消息，否则灰度时不同实例本该看到不同 Release，重试时又分不清失败发生在校验、提交还是通知。

English

Three calls pin the arrows on the final frame. get reads the body of a namespace at a version. watch answers only whether the version the caller knows is still current. publish appends a Release. Do not collapse them into one socket message that pushes the whole document. A gray release needs different instances to observe different Releases, and a retry needs to know whether the failure was validation, commit, or notify.

字段各自挡住一种事故

expected_version 是乐观并发，不是可选的提示。两个人同时编辑同一把 key，后保存的那次若仍携带旧版本，Config Store 拒绝写入并返回 409。Chubby 的 SetContents 允许客户端带上 content generation number，只有号码仍是当前值才写入，用来模拟 compare-and-swap；文件内容整份原子替换。[3] 配置发布同样整份替换一个 key 的值，不做字段级合并。控制台收到 409 之后重新 GET，把差异显示给人，而不是静默覆盖。

checksum 同时出现在发布请求、存储记录和 GET 响应里。它发现的是「通知说版本 42，拉下来的正文却对不上 42」以及磁盘快照在进程崩溃时写了一半。校验失败的正文不能替换上一份好快照。ZooKeeper 的 watch 本来就不携带新值，客户端必须再读；我们把 checksum 放进这次读的契约里，避免把半份 JSON 装进超时或限流路径。[1]

policy 跟 key 走，不跟进程走。同一台 App 里，超时用 serve_last，关闭危险调试入口的开关用 fail_closed。把策略放在 Release 上，是为了让拉取快照的人不必猜测。下面的客户端图会把两种策略画在一起。

Idempotency-Key 表示一次发布意图。控制台超时后不知道 201 是否已经生成。用同一把键重试必须返回第一次的 version，不能再追加一条内容相同的 N+2。这和 expected_version 是两回事：前者挡住「同一次点击写两次」，后者挡住「两个编辑者互相覆盖」。幂等记录的保留时间要长于控制台的最大重试窗口。

rollout 决定这次 Release 对谁可见。mode 为 full 时，当前指针把 steady 指到新版本。mode 为 canary 时，steady 仍指着旧版本，另一条指针按 tag 或百分比指向新版本。灰度因此是存储里的第二份已发布版本，不是两个副本偶然不一致。watch 事件里要带上规则的版本，否则实例只知道「有个新版本」，却不知道自己是否在金丝雀集合里。

Each field blocks one accident

expected_version is optimistic concurrency, not a hint. When two people edit the same key, the later save still carrying the old version is rejected with 409. Chubby’s SetContents accepts a content generation number and writes only when that number is still current, which is a compare-and-swap. File contents are replaced atomically, as a whole. [3] A config publish replaces one key’s value the same way. There is no field-level merge. On 409 the console GETs again and shows the diff to a person.

checksum appears on the publish request, the stored record, and the GET response. It catches “the notice said version 42, but the body is not 42” and a snapshot file torn by a crash. A body that fails the check must not replace the last good snapshot. A ZooKeeper watch does not carry the new value; the client has to read. [1] Putting the checksum on that read keeps a half-written JSON document out of the timeout and rate-limit path.

policy travels with the key, not with the process. Inside one app, a timeout can be serve_last while the switch that closes a dangerous debug entry is fail_closed. Storing the policy on the Release means the process that fetches the snapshot does not guess. The client deck draws both policies together.

Idempotency-Key names one publish intent. After a timeout the console does not know whether the 201 was produced. A retry with the same key must return the first version and must not append a second identical N+2. That is a different job from expected_version: one stops a double submit of the same click, the other stops two editors from overwriting each other. Keep the idempotency record longer than the console’s maximum retry window.

rollout decides who can see this Release. In full mode the current pointer moves steady to the new version. In canary mode steady still names the old version, and a second pointer names the new version by tag or percent. A gray release is therefore a second published version in the store, not two replicas that drifted. The watch event has to carry the rule version. Otherwise an instance learns that some new version exists and still does not know whether it is in the canary set.

版本、generation、namespace 各管一件事

version 是这一把 key 的发布序号，只增不减。回滚不会把序号拨回去。已经看过 N 的客户端若看见「当前仍是 N」，版本比较会得到 304，坏的 N+1 就撤不回来。generation 是整个 namespace 的计数，一条 watch 就能比较「这包变了没有」。namespace 是故障和权限的边界，结账和搜索建议分开之后，一次错误发布不会顺带改掉另一个团队的超时。值是小 JSON。单值超过 256 KB 这一档就返回 413，调用者改去对象存储，配置里只留指针和 checksum。

Current 里的 steady 和 canary 两枚指针，让「现在生效的是哪一条 Release」成为数据，而不是把旧行删掉。历史因此能回答谁在什么时候把 N 改成了 N+1。发布者身份来自控制台的认证主体。Raft 的日志在多数派提交之后，领导者仍会把条目补给慢副本。get 若打到尚未追上的副本，可能短暂返回 N，而领导者已经对发布者返回了 N+1。[2] 权威读要打到已经追上 commit index 的副本。调用者手里的版本若比这次读更新，服务端应当拒绝，而不是用旧副本的 N 覆盖客户端快照。

Version, generation, and namespace each do one job

version is the publish sequence of one key. It only increases. Rollback does not rewind it. The failure deck explains why: a client that has already observed N, and is then told that current is still N, gets a 304 from the version compare, so a bad N+1 cannot be undone. generation can be a single counter for the whole namespace, so one watch compares “did this bundle change” without listing every key in the parked request. namespace is the fault and permission boundary. When checkout and search suggestions live in different namespaces, one bad publish does not also change the other team’s timeout. key is unique inside the namespace. The value is text or small JSON. Cap it from the size assumption, for example in the 256 KB range per value. Above that, return 413 and let the caller use object storage, leaving only a pointer and a checksum in config.

The two pointers in Current make “which Release is active” data, instead of deleting the old row. Historical Releases stay, so audit can say who changed the value from N to N+1 and when. Publisher identity comes from the console’s authenticated principal, not from a string the client typed. After a Raft majority commit, the leader still replicates the entry to a lagging follower. A get that hits a follower which has not caught up can briefly return N after the leader has already returned N+1 to the publisher. [2] An authoritative get therefore hits the leader, or a replica that has caught the commit index. If the caller’s known version is newer than what that read returned, the server rejects the read instead of writing the old replica’s N back over the client snapshot.

发布时序：先提交，再通知，中间有一段窗口Publish sequence: commit, then notify, with a window in between

按一次真实发布走

控制台把 namespace、key、value、expected_version、checksum、policy 和 rollout 一次提交。Config Service 先做便宜检查：主体是否能写这个 namespace，值是否超过 256 KB 这一档的上限，checksum 是否等于正文的摘要，rollout 的百分比是否落在 0 到 100。任何一项失败都返回 4xx，Config Store 里的当前指针不动，Notify Bus 上没有事件。通过之后才发条件写：仅当存储中的 steady 或被编辑的那条草稿版本仍等于 expected_version，才插入 version = N+1 的 Release。Raft 的常见路径是，条目被多数副本收下之后，领导者才对客户端返回结果；慢副本不参与这次成功的判定。[2] 因此 201 的含义是「配置日志的多数派已经有 N+1」。

返回 201 的同一时刻，图上的 App 仍标着 snapshot N。窗口是刻意留下的。下一步才把瘦事件放进 Notify Bus，订阅者被解开 long-poll 或收到 push，再 GET 正文，校验 checksum，替换快照，然后执行回调。回调刷新超时、限流或 flag。回调失败只影响这一台进程，不应该把已经提交的 Release 回滚掉。发布者若要「至少一台金丝雀已经拉到」，那是额外的确认查询，不是 201 的定义。

Walk one real publish

The console submits namespace, key, value, expected_version, checksum, policy, and rollout together. Config Service runs the cheap checks first: whether this principal may write the namespace, whether the value exceeds the cap in the 256 KB range, whether the checksum matches the body, and whether a percent sits between 0 and 100. Any failure returns 4xx. The current pointer in the Config Store does not move, and the Notify Bus gets no event. Only then does the conditional write run: insert Release N+1 only while the stored version still equals expected_version. On the common Raft path, the leader returns to the client after a majority has the entry. A slow follower does not decide success. [2] A 201 means a majority of the config log has N+1.

At the moment of that 201, the apps on the diagram are still labeled snapshot N. The window is left there on purpose. Notify is the next step: a thin event enters the Notify Bus, the subscriber’s long-poll unblocks or a push arrives, the process GETs the body, checks the checksum, replaces the snapshot, and only then runs the business callback. The callback refreshes a timeout, a limit, or a flag. A callback failure affects application logic on that one process. It must not roll back a committed Release. If the publisher wants “at least one canary has fetched,” that is a separate confirmation read, not the definition of 201.

为什么不把舰队确认放进发布 RPC

新鲜度假设是：已连接订阅者里 99% 在 10 秒内读到新版本。10 秒是为了继续设计而写的目标，不是某份公开仪表盘上的数字。因此发布 RPC 不能等待全部实例。1 万个进程里总会有正在重启或网络分区的。Chubby 把写入挡住，直到失效被确认或租约到期，失联客户端会把修改拖到租约结束。[3] 我们的 201 站在 ZooKeeper 一侧：写路径不等待慢读者。某个客户端收不到 watch，也不会挡住更新进入日志。[1]

10 秒假设改变的是通知怎么做，不是存储在哪里提交。变更发生时 long-poll 会被立刻解开，快乐路径通常远小于挂起上限。60 秒是空闲上限，也是服务端漏解开时客户端最晚发现的时间。收到 1 秒的假设，仍不让 201 等待 1 万次确认，而是改用更短的 push 和本地失败关闭。放到一两分钟，周期拉取就够。

Why fleet acknowledgement stays out of the publish RPC

The freshness assumption is that 99% of connected subscribers read the new version within 10 seconds. Ten seconds is a target chosen so the design can continue. It is not copied from a public dashboard. Once it is written down, the publish RPC cannot wait for every instance. Among 10,000 processes some are restarting, some are partitioned, and some are parked on a Config Service node that has not yet seen the bus message. Chubby blocks a write until every client that might have cached the file acks the invalidation or its lease expires. The paper also says an unreachable client delays the modification until lease expiry, and overload stretches the lease up from the 12-second default. [3] Our 201 takes the ZooKeeper side: the write path does not wait for slow readers. A ZooKeeper watch fires from the local replica, and a slow client that misses the notice does not stop the update from entering the log. [1]

The 10-second assumption changes how notify is built, not where the store commits. A long-poll unblocks as soon as the change exists, so the happy-path delay is “release the parked request plus one GET,” usually far below the hold cap. A 60-second hold is the idle cap, and it is also the latest moment a client notices that the server failed to unblock it. Tightening the assumption to one second still does not require the 201 to collect 10,000 acks. It requires a shorter push path, a denser reconcile, and local fail-closed behavior for security keys. Relaxing it to a minute or two means periodic fetch is enough, and the Notify Bus can wait. The number chooses the component.

替代、并发和一种不完整的说法

同步扇出是另一条能走通的路：发布线程逐台调用实例的管理端口，全部返回后再给 201。几十台、同一个机房时，它更简单，测试也能断言「返回了就生效了」。在 1 万实例的假设下它站不住。尾延迟会把一次点击拖进超时，没有 Idempotency-Key 的重试还会再写一条版本。所以它是小规模的合理第一版，不是这张图的默认。

并发窗口有三个。第一，两人带着同一个 expected_version 提交，只有一次条件写成功，另一次 409。第二，提交已经完成，201 在网络上丢失，同一把 Idempotency-Key 的重试必须取回已有 version，不能再插入。第三，201 已经到达，通知还没到，读者仍在 N。重试只补第二扇。漏通知靠 watch 续约和对账。Notify Bus 通常是另一套日志，不能和 Config Store 假装成同一次提交。版本以存储为准，通知可以重放，订阅者用版本号决定要不要拉。把 1 万个客户端拉进同一个事务，会把发布的可用性交给客户端。

An alternative, the races, and one incomplete line

Another workable design is synchronous fan-out: the publish thread calls every instance’s admin port and returns 201 only after all of them respond. With a few dozen instances in one building, that is simpler, and an integration test can assert that a returned publish is already visible. It does not survive this assumption. The tail latency and failures of 10,000 internal RPCs push one human click into a timeout, and a retry without an Idempotency-Key appends another version. Synchronous fan-out is a reasonable first version at small scale. It is not the default on this final diagram.

Three races need separate sentences. First, two writers submit the same expected_version. Only one conditional write succeeds; the other receives 409. Second, the conditional write has committed and the 201 is lost on the network. A retry with the same Idempotency-Key must fetch the existing version and must not insert again. Third, the 201 has arrived and the notify has not, so readers remain on N. A republish does not close the third window. Retries belong to the second. A missed notify is closed by watch renewal and reconcile. “Put the commit and the notify in one transaction” sounds complete. The Notify Bus is usually a second log. A crash between two stores leaves a committed version and an unsent event. The repair is: the store wins, the notice may be replayed, and the subscriber decides whether to fetch by version. A transaction that covers only the Release row and the Current pointer inside the Config Store is appropriate. Pulling 10,000 clients into that transaction hands publish availability to the clients.

客户端快照：中心挂了，按 key 决定继续还是拒绝Client snapshot: when the center is down, the key decides

中心不可达时实际发生什么

进程已经在跑，watch 失败。对 serve_last 的 key，getConfig 继续返回 checksum 已经核对过的内存快照。超时、限流和普通 feature flag 走这条，不会因为配置中心抖动把请求打成 500。磁盘快照不在热路径上。它在下一次启动、且中心仍不可用时，用来代替空白内存。磁盘也没有时，serve_last 用编译进二进制的默认值，并把指标标成 degraded。

policy = fail_closed 走另一条。典型是安全熔断：关闭危险调试入口，或在不确定时不要继续放行。快照年龄超过假设的 30 秒，或者根本没有快照，getConfig 对这个 key 返回「拒绝该动作」。30 秒和 10 秒新鲜度一样是假设，写出来是为了能测：把时钟拨过 30 秒，动作应被拒绝。它不是把整个进程退出。支付主路径若被标成 fail_closed，中心一抖动就会拒绝全部交易。这个标记只给「继续用旧值比停下来更危险」的 key。

What actually happens when the center is unreachable

The process is already running and the watch socket or long-poll has failed. For policy = serve_last, getConfig keeps returning the in-memory snapshot whose checksum was checked when it was stored. Request timeouts, rate-limit thresholds, and ordinary feature flags take this path. The process does not turn every request into a 500 because the config center blipped. The disk snapshot is not on the hot path in this phase. It is used on the next start, if Config Service is still unavailable, so memory does not come up empty. A cold start with neither network nor disk uses the default compiled into the binary for serve_last keys and marks a degraded metric, because that default may be older than the last real publish.

policy = fail_closed takes the other path. The usual case is a security kill-switch: close a dangerous debug entry, refuse a privilege bypass, or stop allowing something when the process is unsure. If the snapshot is older than the assumed 30 seconds, or there is no snapshot, getConfig returns “refuse this action” for that key and the caller skips the dangerous branch. Thirty seconds is an assumption, like the 10-second freshness target. It is written down so the policy is testable: a test can move the clock past 30 seconds and assert the action was refused. It does not exit the process. If the payment path were mis-labeled fail_closed, a blip in the center would refuse every transaction. The mark belongs only on keys where keeping the old value is more dangerous than stopping.

为什么不照搬 Chubby 的清缓存

Chubby 在本地租约到期、会话是否有效都不确定时，会清空并停用缓存，宽限期内挡住 API，避免读到可能错过失效的数据。契约是看到一致视图，或看到错误。[3] 这对手动锁和主身份是对的。超时不是锁。所有 key 都在断会话时失败，会让业务可用性不超过配置中心。ZooKeeper 允许从本地副本读，watch 由客户端自己维持，更新不被缓存持有者挡住。[1] serve_last 继续用本地副本，fail_closed 在不确定时停。Fowler 把熔断和发布开关分成不同类别，方向要按 key 定。[4]

磁盘快照是第三份状态，校验规则和内存相同。写入采用「写临时文件，checksum 通过后改名」，避免崩溃留下半份 JSON。启动时若磁盘 checksum 失败，这份文件作废，退回编译默认值或拒绝 fail_closed 的动作，不能把损坏的文件当上一份好快照。好快照的定义是 checksum 通过，不是「文件存在」。

Why this does not copy Chubby’s cache flush

When a Chubby client’s local lease expires and it cannot tell whether the session is still valid, it empties and disables its cache. During the grace period, API calls block so the application does not read data that might have missed an invalidation. The paper’s contract is that the client sees either a consistent view or an error. [3] That is the right contract for a lock and for “am I still the primary,” because a stale “I am primary” splits the writers. A timeout in config is not a lock. Failing every key when the session drops makes business availability a subset of config-center availability. ZooKeeper serves reads from a local replica and linearizes writes. Clients keep their own cache with watches, and the server does not block every cache holder on an update. [1] Our serve_last path is closer to “keep serving the local copy.” fail_closed is closer to Chubby’s “if unsure, do not continue.” Both are required because Fowler separates operational switches from release switches. A kill-switch must change quickly, and the direction taken when unsure needs its own design. An ordinary release flag can keep the old behavior a little longer. [4]

The disk snapshot is a third copy, with the same checksum rule as memory. Write a temporary file and rename it only after the checksum matches, so a crash does not leave a partial JSON document. If the disk checksum fails at startup, discard the file and fall back to the compiled default, or refuse the fail_closed action. Do not treat a corrupt file as the last good snapshot. Good means the checksum matched, not merely that a file exists.

听起来稳妥、其实会放大故障的做法

「配置中心挂了就直接查库」会把本地读打回 Config Store。中心挂了往往是因为连接已经过载，1,000 万次 getConfig 会把还活着的副本打满。降级是继续读快照，并停掉重连风暴。另一种说法是所有 key 都失败关闭。旧的限流阈值通常比重启全部实例更安全；旧的「允许调试端口」则不安全。策略写在 key 上。

A line that sounds safe and enlarges the outage

“If the config center is down, read the database” puts the local reads we already counted back onto the Config Store. The center is often down because connections or nodes are already overloaded. Ten million getConfig calls hitting the database at that moment fill whatever replica is still alive. The degradation is to keep reading the snapshot and to stop a retry storm of new watches. The failure deck draws the reconnect. Another line is “fail closed on every key, because that is safest.” Safety depends on the direction of the old value. An old rate-limit threshold is usually safer than restarting every instance. An old “debug port allowed” is not. The policy belongs on the key, not on the whole product.

一致性与灰度：第二份版本是故意的Consistency and gray release: the second version is deliberate

一次灰度实际怎么选版本

操作者发布时 rollout.mode = canary，tag = canary，percent = 5。Config Store 插入 Release N+1，Current.steady_version 仍是 N，Current.canary_version 变成 N+1，canary_rule 记下 tag 和百分比。Config Service 在 GET 和 watch 响应里看调用者的 instance id 与 tag。命中 tag，或 hash(instanceId) 对 100 取模后小于 5 的实例，拿到 N+1 的 value 和 checksum。其余实例拿到 N。两条响应都带上自己的 version，所以实例的快照会写成它真正收到的那一版，而不是一律写成「最新」。通知只叫醒规则判定为发生变化的那一组；稳态组的 known_version 仍是 N，比较结果是 304。

全量是另一次发布：steady 指针移到 N+1，清掉 canary 指针。回退灰度是拿掉 canary 指针，让那 5% 重新读 N。两种操作都追加审计。Fowler 把金丝雀描述成先对一小群打开新路径，看指标后再全开，并把取模分桶和指定内部用户区分开。[4] 这里的分桶键是 instance id 或 tag。用户维度的实验在应用里求值，配置中心不必按用户存值。

How one gray release actually picks a version

The operator publishes with rollout.mode = canary, tag = canary, percent = 5. The Config Store inserts Release N+1. Current.steady_version stays N. Current.canary_version becomes N+1, and canary_rule records the tag and the percent. On GET and on the watch response, Config Service looks at the caller’s instance id and tag. An instance that matches the tag, or whose hash(instanceId) modulo 100 is under 5, receives the value and checksum of N+1. Everyone else receives N. Both responses carry their own version, so the snapshot stores the version that instance actually received, not a blanket “latest.” Notify wakes only the group whose rule result changed. The steady group’s known_version is still N, and the compare is a 304.

A full rollout is another publish: move the steady pointer to N+1 and clear the canary pointer. Aborting the gray release removes the canary pointer so that 5% reads N again. Both operations append audit, because “who moved the percent from 5 to 100” is the same kind of question as “who changed the value.” Fowler describes a canary as turning a new path on for a small cohort, watching business metrics, then deciding whether to go fully on. He also separates a modulo cohort from a named set of internal users. [4] The bucket key here is instance id or tag, not user id. A user-level experiment can evaluate the same rule inside the app. That is flag evaluation. The config center does not have to store a value per user.

为什么灰度必须是第二份版本

若金丝雀是「先把值改成 N+1，再希望只有一部分实例已经 watch 到」，两组差异来自通知延迟，不能按 tag 复现。把差异写成 Current 里的两条指针之后，同一台实例每次 GET 都落到同一条 Release，直到规则改变。副本滞后是另一种情况：本该返回 N+1 的读打到了还停在 N 的跟随者，修复是读 commit index，或只从已经追上的副本读当前指针。灰度是规则要求这一台返回 N、那一台返回 N+1。看这个值是否出现在 Current 的某条指针上，就能把发布计划和漏 watch 分开。

namespace 把这个计划限制在一个团队的 key 集合里。generation 让一条 watch 能发现「规则或任一 key 变了」，而不必为百分比规则单独发明第三种通道。version 仍是 key 级别的单调序号，用来做 304 和 checksum 绑定。三个字段不要并成一个「时间戳当版本」。时钟回拨会让 304 把新正文当成没变。

Why a gray release has to be a second version

If a canary means “write N+1 and hope only some instances have watched it,” the split comes from notify delay. It is not controllable and it cannot be reproduced with a tag. Once the split is two pointers in Current, the same instance lands on the same Release on every GET until the rule changes. That is different from a lagging replica. Replica lag is a read that should return N+1 but hits a follower still on N. The fix is to read the commit index, or to read the current pointer only from the leader. A gray release is the rule requiring this instance to return N and that instance to return N+1. Both look like “two values in the fleet” on a dashboard. The question that separates them is whether the value is named by a pointer in Current. If it is, it is the rollout. If it is not, and it differs from the rest of its group, it is a missed watch or a split, and it belongs on the failure deck.

namespace confines the plan to one team’s keys. generation lets one watch notice that the rule or any key changed, without a third channel invented only for percents. version stays a per-key monotonic sequence, used for 304 and bound to the checksum. Do not collapse the three fields into “a timestamp is the version.” A clock step backward makes a 304 treat a new body as unchanged.

不该拿来灰度的变更

同一套代码读不同阈值，是这张图的前提。若 N 和 N+1 是两种互不兼容的序列化，金丝雀组会写出另一组读不懂的数据。那种变更跟着二进制发布走。Fowler 也把发布开关看成过渡，寿命以天或周计；长期留下的是权限类开关和少数运维熔断。[4] 配置中心里长期存在的应是超时、限流和真正的熔断。做完的实验 flag 要删，否则 namespace 会堆满已经没有第二份版本意义的 key。

网关按权重把流量打到两套二进制，切的是代码版本，执行点在网关。这里切的是 KV，执行点在 Config Service 按实例身份选择 Release。两套机制可以同时存在。小规模且只有一个实例组时，可以先不做 canary 指针，每次发布都是 full。

Changes that do not belong in a gray release

The diagram assumes one codebase reading different thresholds. If N and N+1 mean two incompatible serializations, the canary group writes data the other group cannot read. That change follows the binary release, not a config pointer. Fowler also treats release toggles as transitional, with a life measured in days or weeks, not as permanent branches in the core path. What lives for a long time is a permission toggle or a small set of operational kill-switches. [4] What should live for a long time in this config center are timeouts, rate limits, and real kill-switches. Someone deletes a flag after the experiment. Otherwise the namespace fills with keys that no longer have a reason to exist as a second version.

A gateway sending traffic to two binaries by weight is a different problem: it splits code versions, and the decision sits at the gateway. Here the split is a KV, and Config Service picks the Release from the instance identity. Both mechanisms can exist. One “90 / 10” picture does not finish this prompt. At small scale, with one instance group, skip the canary pointer and make every publish full. Add the second pointer when the first bad config needs “only one group eats it.” A percent without an error-rate comparison between the groups only shrinks the blast radius. It does not create a decision.

故障：漏通知、重连风暴、坏配置与回滚Failures: missed notify, reconnect storm, bad config, rollback

漏掉的 watch 为什么会发生

ZooKeeper 把 watch 定义成一次性触发，和会话绑在一起：触发之后或会话关闭就注销。通知只说明变了，不附带新内容。同一份数据若在客户端处理通知之前变了两次，它只会收到一次事件。会话事件也会送到回调，用来说明通知可能被推迟。[1] 配置客户端若更新了内存，却忘记在随后的 GET 上重新登记 watch，下一次发布就不会再叫醒它。它会停在旧快照上，直到重启或对账。对账假设每 5 分钟比较一次 generation，这就是漏 watch 的最坏发现时间，要和新鲜度假设一起说。

和灰度的差别要能指着图说出来。灰度里两条指针都在 Config Store 中，版本是规则的输出。漏 watch 里 Current 只有一个指针，某一台的快照却落后于同组邻居。修复是让这台重新 GET 并重新登记。只靠 push、没有对账，等于假设通知永不丢失。

Why a watch goes stale

ZooKeeper defines a watch as a one-time trigger tied to a session. It is unregistered once it fires or the session closes. If the client sets the watch on getData, the server promises to notify when the information it returned changes. If that data changes twice before the client handles the event, the client gets one “changed,” and the event does not include the new bytes. Session events are delivered to the watch callback so the client knows notifications may be delayed. [1] A config client that applies “changed” to memory and forgets to re-arm the watch on the following GET will not be woken for the next publish. It stays on the old snapshot until restart or the periodic reconcile. Reconcile GETs the generation every five minutes and fetches the body on mismatch. Five minutes is an assumption. It is the worst-case detection time for a missed watch, and it should be stated next to the freshness SLO.

You should be able to point at the diagram and separate this from a gray release. In a gray release both the steady pointer and the canary pointer live in the Config Store, and the two versions are outputs of the rule. In a missed watch, Current has one pointer and one instance’s snapshot lags its neighbors in the same group. The repair is not another percent. That instance GETs again and re-arms. Periodic reconcile automates the repair. Push without reconcile assumes a notice is never lost. The paper already says sessions drop and notices can be late.

重连风暴的算术

假设 10,000 个进程在同一次网络闪断后同时重连，每个立刻 GET 自己的 namespace 包，Config Service 在 1 秒内收到约 10,000 个请求。每个包按 10 个 key、每个 4 KB 估算，合计约 400 MB 正文。把重连延迟均匀打散到 30 秒，速率变成 10,000 / 30 ≈ 333 QPS，和 long-poll 续约的 167 同一数量级。客户端先睡眠 0 到 30 秒的随机数，再做全抖动退避；服务端对同一个 namespace 单飞，让同一秒的重复 GET 共用一次存储读。没有这个除法，图上的红色箭头只是在说「可能会挤」。

Chubby 过载时的典型故障，是来不及处理约占 93% RPC 的 KeepAlive，会话随之被丢掉。他们加长租约，而不是让每个缓存条目各自轮询。[3] 风暴期间先保住还挂着的连接和存储。正在跑的 serve_last 进程继续用内存快照。

The reconnect arithmetic

Assume 10,000 processes notice a dropped watch after the same network blip. If each immediately GETs its namespace bundle, Config Service receives about 10,000 requests in one second. At 10 keys of 4 KB, that is about 40 KB each, about 400 MB of bodies leaving the store or the service cache in that second, before TCP handshakes. Spreading reconnect delay uniformly over 30 seconds makes 10,000 / 30 ≈ 333 QPS, the same order as the 167 long-poll renewals, which a single-region service can take. The client sleeps a random 0 to 30 seconds after disconnect, then uses full-jitter exponential backoff. The server single-flights concurrent origin reads for one namespace, so duplicate GETs in the same second share one store read. The jitter window is an assumption. It turns a 10,000 QPS spike into a few hundred. Without that division, the red arrows only say “it might get crowded.”

The failure Chubby records for an overloaded cell is falling behind on KeepAlives, which were about 93% of RPCs, and then dropping sessions. They lengthened leases to cut handshakes, rather than polling each cached entry. [3] Our watch renewal is the same class of cost. During a storm, protect the connections you still hold and the store. Do not refresh every process’s disk snapshot immediately. A running serve_last process keeps its memory snapshot and stays off those extra reads beyond the 333 QPS.

回滚为什么是新版本

坏的 N+1 已经在多数派日志里。Raft 的领导者完整性是：已经提交的条目会出现在之后更高任期的领导者日志中，已经应用到状态机的下标不会被另一条命令替换。[2] 配置日志同样不把 N+1 抹掉。回滚插入 N+2，value 和 checksum 复制自 N，Current 改指向 N+2。watch 比较版本号，所以 N+2 会触发 GET。若只把指针改回 N，本地版本已经是 N 的实例会得到 304，不再去拉。审计行记下操作者、request_id，以及正文等于 Release N。没有这行，回滚发生了，却答不出是谁发布的。

「不提供回滚，坏了再改回去」若是覆盖同一行并保持版本号不变，客户端的 304 会把修复吞掉。再发布才是回滚。按钮应选中历史 Release N，生成 N+2。DELETE 当前行会让 get 短暂 404，fail_closed 的进程会把缺失当成拒绝。

Why rollback is a new version

The bad N+1 is already on a majority of the log. Raft’s leader-completeness property says a committed entry is present in the logs of leaders of later terms, and an index applied to the state machine is not replaced by a different command. [2] The config log likewise does not erase N+1 from history. Rollback inserts N+2, copies N’s value and checksum, and points Current at N+2. Watches compare version numbers. N+2 equals neither the N nor the N+1 the client remembers, so a GET fires. If the pointer is quietly moved back to N, instances whose local version is already N receive 304 and do not fetch. Instances stuck on the bad N+1 can return, and instances on an older snapshot do not refresh the checksum. The audit row records the operator, the request_id, the move from N+1 to N+2, and “bytes equal Release N.” Without that row the rollback happened and nobody can say who published it.

“No rollback; we will just change it back” sounds like a feature you can skip. If changing it back overwrites the row and keeps the version number, the client’s 304 swallows the repair. If changing it back means publishing again, that is a rollback, only without a button. The button selects historical Release N and produces N+2. It does not DELETE the current row. DELETE makes get return 404 for a while. serve_last processes cope. fail_closed processes treat the brief absence as a refusal, which is a wider outage than the operator had in mind.

通道选择：用同一组假设比较短轮询、long-poll 和本地快照Channel choice: one set of assumptions for short-poll, long-poll, and the snapshot

三个数怎么推出默认通道

同一组假设放在一起，默认通道就定了：短轮询是 20,000 QPS 空转，long-poll 是约 1 万条连接加 167 QPS 续约，快照吃掉 1,000 万次本地读。存储侧按假设只剩两百出头的发布、续约和对账。启动时 GET 一次，之后每进程一条 long-poll。只有新鲜度短于「解开挂起再 GET」时，才给熔断 key 单独开 push。

167 这个数还决定服务端怎么挂起请求。若每个挂起的 HTTP 请求占一条操作系统线程，1 万条线程会先于 CPU 打满。long-poll 要放在异步运行时上，用少量线程等待上万个套接字。Chubby 把 KeepAlive 挂在主副本上，直到租约快到期或有失效要捎带，抽样里这类握手约占 93% 的 RPC。[3] 在 1 万连接这个假设下，long-poll 和 push 的贵都在连接表，不在发布写入。

How three numbers pick the default channel

Hold one set of assumptions together: 10,000 processes, 10 namespaces each, a 5-second short-poll period, a 60-second idle long-poll hold, 1,000 getConfig calls per process per second, and a reconcile every five minutes. Short-poll is 20,000 idle QPS. Long-poll is about 10,000 connections plus 167 renewal QPS. The local snapshot keeps 10,000,000 business reads in-process. The store then sees a publish peak of 50, renewals of 167, and reconcile of 33, a little over two hundred. The default channel is therefore: GET once at startup or reconnect to fill the snapshot, one long-poll per process after that, and business reads only from the snapshot. Push is not cheaper in sockets. It earns its place when the freshness assumption is shorter than what “unblock a hold, then GET” can reliably hit, for example a sub-second wake for a security kill-switch. That class of key can use push while ordinary timeouts stay on long-poll.

The number 167 also decides how the server parks requests. If each parked HTTP request owns an operating-system thread, 10,000 threads exhaust memory and scheduling before CPU. Long-poll belongs on an asynchronous runtime, with a few threads waiting on tens of thousands of sockets. Chubby hanging a KeepAlive at the master until the lease is nearly due, or until an invalidation can be piggybacked, is the same “park instead of poll” shape. In their sample, KeepAlives were about 93% of RPCs. [3] Do not retell that structure as “a long-lived stream is always more advanced than long-poll.” At an assumed 10,000 connections, both are expensive in the connection table, not in publish writes.

Git 仓库为什么接不住这个扇出

Git 能保存文本、review 和作者，适合做 Admin Console 后面的草稿。它接不住运行时扇出：没有 per-process 的 watch，没有按实例身份选择的第二条指针，1 万个进程也不会按 30 秒抖动去拉取。仓库仍可以是人类编辑的源头。进程看见的版本日志是 Config Store。

「每个请求读配置库」被同一组数否定。哪怕命中率做到 99%，剩下的 1% 仍是约 10 万 QPS，比留给存储的几百 QPS 高出两个数量级，命中率一掉就回到千万。快照是把控制面从用户路径上移走。每把 key 都等失效确认，会把 Chubby 为了锁付出的写延迟加到每一次改超时上。[3] 回滚若不让版本号前进，304 会把修复吞掉。

Why a Git repository does not absorb this fan-out

Git stores text, review, and authorship. That is a draft system and it can sit behind the Admin Console. It does not absorb runtime fan-out. There is no per-process watch, no second pointer that combines expected_version with instance identity, and a fetch does not retry across 10,000 processes with 30-second jitter. Using the repository as the config center replaces the 20,000 QPS short-poll with “everyone pulls,” leaves it unknown whether a version reached a given machine, and makes rollback a new commit without a local snapshot protocol after the checksum. The repository can still be where humans edit. The Config Store is the version log processes see.

“Read the config database on every business request” fails the same numbers. Even a 99% cache hit rate leaves 100,000 QPS on the store, more than two orders above the few hundred we budgeted, and a hit-rate drop returns the full ten million. The snapshot is not a cache tuning. It moves the control plane off the user path. Requiring every key to wait for invalidation acks adds the write delay Chubby paid for locks onto every timeout edit. [3] A few fail_closed keys approach “stop when unsure” with a local age check. The other keys accept mixed versions inside the 10-second assumption. Without a rollback button, a bad N+1 can only be overwritten by hand, and if the version does not advance, the overwrite is invisible to watches.

追问Follow-ups

1 · 为什么不让每个请求都强一致？

强一致在这里的可操作定义，是 Chubby 那种「写入等到失效被确认或租约到期」。它保护的是锁和主身份，代价是慢客户端拖住发布。[3] 超时和 flag 的假设允许 10 秒内新旧并存，所以发布在多数派提交后返回。[2] 若面试官把某一把 key 的假设改成亚秒且不允许旧值，只把这一把改成 fail_closed 加更密的 push，不要把整个 namespace 的写路径改成等待 1 万个确认。

1 · Why not strong consistency on every read?

The operational meaning of strong consistency here is Chubby’s rule: a write waits until invalidations are acked or leases expire. That protects locks and primary identity, and a slow client stalls the publish. [3] Timeouts and flags are allowed to mix old and new for the assumed 10 seconds, so publish returns after the majority commit. [2] If the interviewer tightens one key to sub-second and forbids the old value, change that key to fail_closed plus a denser push. Do not change the whole namespace so that every write waits for 10,000 acks.

2 · 和注册发现是一个系统吗？

经常被一起问，数据不是一种。发现回答某服务名下面现在有哪些健康地址，心跳很密，短暂的脏列表往往可接受。配置回答某 key 的值和版本，发布很稀，历史和回滚是产品的一部分。同一套进程可以顺便做这两件事，白板上仍是两张表、两种 watch。把实例列表塞进配置 key，会让心跳刷新变成配置发布。

2 · Is this the same system as discovery?

They are often asked together, and the data is not the same. Discovery answers which healthy addresses currently sit under a service name. Heartbeats are dense, and a briefly dirty list is often acceptable. Config answers a key’s value and version. Publishes are rare, and history plus rollback are part of the product. One set of processes can do both jobs. The whiteboard still has two tables and two watches. Stuffing the instance list into a config key turns a heartbeat refresh into a config publish.

3 · 多区域怎么接？

先问要的是读就近，还是每个区域都能发布。只读就近时，一个区域写 Config Store，其它区域异步复制 Release 日志，本地快照照旧。新鲜度假设要加上复制延迟。每个区域都能发布时，必须规定哪一边的 Current 指针获胜，否则分区会造出两个 N+1。Raft 成员变更本身是另一套重叠多数派，不要把「应用配置的灰度」说成「共识组的成员变更」。[2]

3 · How does this go multi-region?

Ask whether the goal is local reads or publish in every region. For local reads, one region writes the Config Store, other regions replicate the Release log asynchronously, and local snapshots stay. Add replication delay to the freshness assumption. If every region can publish, you must say which side’s Current pointer wins, or a partition creates two N+1s. Raft membership change is its own overlapping-majority protocol. Do not describe an application-config canary as a consensus membership change. [2]

English

A publish returns a new version on a store majority, not a fleet that has already switched. An already-running process, when the center is unreachable, follows the key’s policy and either keeps the snapshot or refuses the action. A gray release is a second pointer on Current. An instance that disagrees with its group and matches no pointer is a missed watch. Rollback appends N+2, and the audit says who published it.

Last twenty seconds: 10,000 processes, short-poll is 20,000 idle QPS, long-poll is about 167 renewals, and 10 million getConfig calls stay in the local snapshot. The 201 does not wait for every reader. An expired kill-switch refuses. A canary is deliberate N and N+1. A bad value is repaired by a new version whose bytes equal N.
