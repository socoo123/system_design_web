一条控制面One control plane

中文

从左到右只画一条线。发现、mesh、Git 先不出现。面试官点头之后再拆 watch、版本、gray release。

键空间够用就停：namespace / app / cluster / key。值是文本或 JSON。每次发布一条 Release，带单调 version，或内容 MD5。Gray release 的规则挂在同一条 key 上。

读：启动 GET 进内存，并落一份本地快照。getConfig 读进程内缓存。变更靠 watch，再到 callback，业务刷新超时、开关、限流阈值。

写：鉴权，带上当前 version 做乐观并发，落 DB，更新缓存，再通知。方向 OK 的话，下一笔是 push/pull。

English

Left to right, one line. Discovery, mesh, and Git stay off this picture. After they buy in, split watch, versions, and gray release.

Stop the keyspace when it is enough: namespace / app / cluster / key. The value is text or JSON. Each publish is a Release with a monotonic version, or a content MD5. Gray-release rules hang on that same key.

Read: GET the set into memory at startup, and write a local snapshot. getConfig reads the in-process cache. Changes arrive on the watch, then a callback refreshes timeouts, switches, and rate-limit thresholds.

Write: auth, optimistic concurrency with the current version, persist to the DB, update the cache, then notify. If the direction is OK, the next stroke is push/pull.

Hard part · push/pullHard part · push/pull

中文

2026 的默认答案是：启动拉，变更通知，再拉内容。通道可以是 HTTP long-poll，也可以是 gRPC 或 WebSocket 长连接。都叫 watch，差别在协议。

Long-poll：Client 带上当前 version 打通知接口。服务端把请求 hold 几十秒。没变就 304。变了就返回哪个 key、哪个版本。Client 再 GET。延迟上界大约一个 hold 窗口，LB 仍然当普通 HTTP。

长连接 push：双向流挂着，服务端推变更事件，常见仍只带 key。正文另拉。延迟更低。服务器要管空闲超时、断线重连、重新订阅。

短轮询Long-poll长连接 push
空转每隔几秒 GET，QPS 是假的挂起，空转流量几乎没有一条连接，事件驱动
延迟最长一个周期最长一个 hold变更就可以推
服务端状态无挂起的请求连接表，断线要重订
面试当唯一方案是 red flag2026 可以当默认2026 也可以当默认

通知接口只回答「变了没有」。拉正文是另一条幂等 GET。通道薄，好重试，也方便 gray release：不同实例本来就该拿到不同的值。WebSocket 是同类通道，面试官问「必须上 WS 吗」，答案是两条都能 watch。

启动拉一次，然后 watch。Long-poll 或 gRPC 都行。通知只带 key，再拉内容。短轮询留到被追问。

trade-off：long-poll 好实现，延迟有上界。长连接更及时，连接运维更重。把全文塞进通知，看起来少一次往返，重试和 gray release 都会变难。

English

The 2026 default is pull at startup, notify on change, then pull the content. The channel is HTTP long-poll, or a gRPC or WebSocket connection that stays open. Both are watch. The difference is the protocol.

Long-poll: the client calls the notify API with its current version. The server holds the request for tens of seconds. No change, 304. A change returns which key and which version. The client then GETs. Latency is bounded by about one hold window, and the load balancer still sees ordinary HTTP.

Long-lived push: a bidi stream stays up. The server pushes a change event, usually still just the key. The body is a later pull. Latency is lower. The server owns idle timeout, reconnect, and re-subscribe.

Short-pollLong-pollLong-lived push
IdleGET every few seconds. The QPS is fakeHeld. Almost no idle trafficOne connection, event-driven
LatencyUp to one periodUp to one holdPush when it changes
Server stateNoneHeld requestsA connection table. Reconnect re-subscribes
InterviewA red flag as the only designA fine 2026 defaultAlso a fine 2026 default

The notify API only answers “did it change?” Pulling the body is a separate idempotent GET. A thin channel retries cleanly, and gray release stays possible, because different instances are supposed to receive different values. WebSocket is the same class of channel. If they ask “must it be WebSocket?”, both channels are watch.

Pull once at startup, then watch. Long-poll or gRPC both work. Notify carries only the key, then pull the content. Short-poll waits until they ask.

trade-off: long-poll is simple, and latency has a ceiling. A long-lived connection is quicker, and connection ops are heavier. Putting the body in the notify looks like one fewer round trip. Retry and gray release both get harder.

English

Config gray release is the same code, with different instances reading different values. A gateway canary sends requests to different code versions. Same idea, small then large, and you can roll back. The object is different, so the board gets two pictures.

Stop the rules when they are enough: by IP or instance id, by tag (zone, cluster, canary group), by percent with hash(instance id) mod 100. A hit reads the gray Release. A miss reads production. That change wakes only the matching subscribers. Watch error rate and the business metric, then merge to full, or stop the gray.

A user-level flag still lives in config. The decision can run in the app on userId. That is client-side evaluation. Shipping two values by instance is a separate picture.

Say the dangerous case out loud. Gray-releasing a switch for an incompatible protocol splits the fleet: half serialize A, half B. That follows a deploy. Timeouts, rate-limit thresholds, and flags you can turn back are what you gray first.

The registry is often asked in the same breath. Config is KV, with history and CAS. Discovery is the instance list and heartbeats, and it fears being down more than being briefly dirty. 版本与回滚Versions and rollback

中文

面试官问「改了谁能看见」，答案是一条 per-key 的版本时钟，加上每个 Client 自己追。中间必然新旧并存。

每次成功发布生成一条 Release。Client 记住上次的 version。GET 带上本地号，一样就 304。灰度是同一条 key 上的另一条 Release。key 名保持不动，规则才挂得住。

两人同时改同一份草稿：后写带着旧 version 或旧 MD5，冲突拒绝。静默的 last-write-wins 会丢一次发布。回滚是把上一条 Release 再发布一次。历史和当前行都留着，控制台从历史里再选一次。

阶段看见什么
DB 提交权威版本在了。只内存，重启就丢
服务端缓存Config API 能读到新值。多节点可能短暂落后
Notify订阅者被叫醒。只带变了的 key，可以分批
Client callback这一台用上新值。舰队里一段时间两版都在

发布落库并 bump 版本，CAS 防覆盖。通知之后每个 Client 自己拉。窗口是秒到几十秒。回滚走历史 Release。

trade-off：版本加历史，换来可审计、可回滚，多占存储，发布多一步。让所有实例事务提交之后才返回，会把发布的可用性和延迟一起拖垮。跨实例 2PC 就是这种拖垮。一条 key 上的版本时钟已经够用。

English

When they ask who sees the change, the answer is a per-key version clock, and each client catching up on its own. Old and new sit together in the middle.

Each successful publish creates a Release. The client remembers the last version. GET carries that number. The same number is a 304. Gray release is another Release on the same key. Keep the key name, so the rule still attaches.

Two people edit one draft. The later write still carries the old version or the old MD5, and the server rejects the conflict. Silent last-write-wins drops a publish. Rollback publishes the previous Release again. History stays, and so does the current row. The console picks the older Release and publishes it once more.

StageWhat you see
DB commitThe authoritative version is in. Memory only loses it on restart
Server cacheConfig API can read the new value. Nodes may lag briefly
NotifySubscribers wake. Only the changed key, and you can batch
Client callbackThat instance is on the new value. The fleet holds both for a while

Publish lands in the DB and bumps the version. CAS blocks the overwrite. After notify, each client pulls on its own. The window is seconds to tens of seconds. Rollback is a historical Release.

trade-off: version plus history buys an audit trail and rollback, costs storage, and adds a step to publish. Returning only after every instance has committed a transaction drags publish availability and latency down together. Cross-instance 2PC is that drag. A per-key version clock is enough.

Hard part · 丢更新和本地缓存Hard part · dropped updates and local cache

中文

再短的 push 也会丢。本地缓存让 getConfig 快，也让这一台在追平之前继续用旧值。这是这题的一致性 trade-off。修法是每台自己追平，加上分钟级对账。

你承诺的是：每个实例最终看见同一条已发布版本。窗口是秒到几十秒，取决于 watch 通道和 fan-out。所以才要 gray release，先让一部分实例看见 v2。

兜底是分钟级对账：拉 MD5 或版本，没变就 304。callback 到了之后，业务刷新自己的阈值。重活留在监听线程外面。类结构、序列化协议这种不能热更的项，承认那是发版。

Notify 可能丢。getConfig 读本地缓存，所以会旧。分钟级对一下版本。舰队里 v1 和 v2 并存是正常的。同一毫秒全球生效，我不承诺。

English

Even a short push can drop. A local cache makes getConfig fast, and it also keeps that instance on the old value until it catches up. That is the consistency trade-off. The fix is each instance catching up on its own, plus a minute-level reconcile.

What you promise: every instance eventually sees the same published version. The window is seconds to tens of seconds, depending on the watch channel and the fan-out. That is why you gray-release, and let a subset see v2 first.

The safety net is a minute-level reconcile: pull the MD5 or the version, and 304 when it matches. After the callback, the app refreshes its own thresholds. Heavy work stays off the listener thread. A class-shape change or a serialization change cannot hot-reload. Say so: that is a deploy.

Notify can drop. getConfig reads the local cache, so it can be stale. Reconcile the version about once a minute. v1 and v2 together in the fleet is normal. I will not promise a global cutover in the same millisecond.

失败路径Failure path

中文

失败路径单独画。配置中心宕了，进程仍然要起来。本地磁盘快照是上一次成功拉到的值。多数产品开关 fail-open，用旧阈值继续服务。鉴权和安全开关 fail-close，快照缺失或过期就拒绝。

另一条失败是发布请求自己：在请求线程里同步叫醒上万 watch，发布接口会被惊群拖死。叫醒分批，和业务读路径解开。

callback 只把新文本交出去。外部依赖和重算大表若放进监听线程，一次热更新会把实例打满。不能热更的变更走发版。Gray release 只装能退回的阈值和 flag。

English

Draw the failure path on its own. If the config center is down, the process still has to boot. The local disk snapshot is the last value that pulled successfully. Most product switches fail-open and keep serving on the old threshold. Auth and security switches fail-close: a missing or expired snapshot refuses.

The other failure is the publish request itself. Synchronously waking about 10k watches on that thread lets a thundering herd take the publish API down. Wake in batches, off the business read path.

The callback only hands over the new text. An external call or a big recompute on the listener thread lets one hot reload saturate the instance. A change that cannot hot-reload ships as a deploy. Gray release carries thresholds and flags you can turn back.

English

  1. Can Git be the config center? It can store. It has no watch, and it cannot gray-release by instance. Runtime switches go through the config center.
  2. Why not short-poll? Idle QPS, and latency equals the period. Long-poll or a long-lived connection.
  3. Why does notify omit the body? Split the APIs. Retry stays easy, and so does gray release. The client then GETs.
  4. Does every machine see it at once? Each instance catches up alone. Old and new coexist in the middle.
  5. The center is down? Boot from the local snapshot. Product flags fail-open. Security items fail-close.
  6. They want more boxes on the final picture? Mesh, GitOps, and a feature matrix are a different prompt. The three hard parts, said to the bottom, score higher than twenty boxes.
