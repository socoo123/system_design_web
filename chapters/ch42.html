本章核心：承诺、负载与退出各有一道门Core: separate promises, load and shutdown

  • 先完成效果，再确认来源。同库去重、业务变更和结果一起提交；丢回执仍用原事件身份恢复。
  • 按真实能力接受新工作。积压用净余量排空；退避不创造容量，超时不归还仍在占用的资源。

  • Complete the effect before acknowledging its source. Commit deduplication, business changes and the outcome together; recover lost replies with the original identity.
  • Admit work against real capacity. Drain backlog with spare capacity; backoff creates no capacity, and timeout frees no resource still occupied.
  • Preserve the contract during shutdown. Close local admission before draining work; replacement does not undo an old process’s effects.

1 · 消费：同库事务挡住重复效果1 · Consumption: one DB transaction prevents repeated effects

图1的正确次序是：fetch → Effect DB提交 → Group Cursor提交。先确认位点再写业务，崩溃会漏效果；先写业务再确认位点，崩溃会重放。后者靠接收端幂等恢复，不代表消息只投递一次。[2]

下面是SQL与应用分支伪代码，对应图1第2–5帧。输入由可信消费者验证身份与权限，scope包含租户和业务职责；digest由规范化的操作、账户和金额计算。inbox与ledger都使用PRIMARY KEY(scope,event_id)，身份列还必须显式NOT NULL且非空，避免SQLite复合主键的NULL例外。[18]

Deck 1 orders fetch → Effect DB commit → Group Cursor commit. Acknowledging the position first can lose an effect on crash. Applying first can replay after crash, which receiver idempotency must handle. This is not once-only delivery. [2]

Track a prefix of fetched records, not consecutive integers. This Java 17 excerpt runs on the poll thread with one paused batch per partition. For fetched [81,83,90] and batch next=95, completing 90 permits no commit; completing 81 permits 83; all done permits 95. Numeric holes are not unfinished records. The real Kafka adapter also preserves leader epochs and commits explicit partition positions; an empty poll does not erase pending work.

static final class BatchProgress {
    final long generation, batchNext;
    final long[] fetched;
    final boolean[] done;
    int prefix;
    boolean owned = true;
    BatchProgress(long generation, long[] fetched, long batchNext) {
        if (fetched.length == 0) throw new IllegalArgumentException("empty");
        this.generation = generation;
        this.fetched = fetched.clone();
        this.batchNext = batchNext;
        this.done = new boolean[fetched.length];
        for (int i = 1; i < fetched.length; i++)
            if (fetched[i] <= fetched[i - 1]) throw new IllegalArgumentException("order");
        if (batchNext <= fetched[fetched.length - 1]) throw new IllegalArgumentException("next");
    }
    void complete(long ticketGeneration, int index) {
        if (!owned || ticketGeneration != generation) return;
        done[index] = true;
        while (prefix < done.length && done[prefix]) prefix++;
    }
    OptionalLong safeNext() {
        if (!owned || prefix == 0) return OptionalLong.empty();
        return OptionalLong.of(prefix == fetched.length ? batchNext : fetched[prefix]);
    }
    void revoke() { owned = false; }
}

2 · EOS与Outbox：指出事务到哪里为止2 · EOS and Outbox: state the transaction boundary

Kafka的consume–process–produce可以把Kafka输出与输入位点放入同一事务，读者用read_committed；外部效果库与HTTP不自动进入该事务。幂等producer也不识别两个独立业务调用是不是同一笔扣款。[1]

图2源库中，Order、Outbox和已接受结果同事务，Relay才有持久意图可恢复。Relay收到符合合同的broker ACK后标sent或推进CDC；回执丢失仍发原e7。接收端的inbox属于另一份本地事务，不能把两套物理库圈成同一原子边界。[3]

外部付款或短信要持久dispatch intent、稳定业务键，以及远端原子记录键与效果、可查询结果的合同。拿不到回执就保留UNKNOWN并核账，不能先记done，也不能换键补发。不同动作还要核实体版本：取消与发货即使各自幂等，乱序仍可非法。详见Ch24 · 支付。

Kafka consume–process–produce can transact Kafka outputs with input positions, with read_committed readers. External DB/HTTP effects do not join automatically. Producer idempotence does not identify two independent business invocations as the same charge. [1]

Deck 2 commits Order, Outbox and acceptance together so Relay has a durable intent. Mark sent or advance CDC only after the broker’s contracted ACK; a lost receipt still resends e7. Receiver inbox belongs to another local transaction. The two physical databases are separate atomic boundaries. [3]

Remote payments or messages need durable dispatch intent, a stable business key, and a receiver that atomically records the key/effect and supports outcome lookup. A missing receipt remains UNKNOWN for reconciliation, rather than pre-recording done or choosing a new key. Entity versions still guard order: idempotent cancellation and shipment can be illegal when reordered. See Ch24 · payments.

3 · 积压：用净处理余量计算恢复3 · Backlog: recover using spare service capacity

图3假设六个均衡分区、每owner单顺序worker、每owner含效果提交可完成200/s；三个owner共600/s，六个共1,200/s。更多组员不增加本模型的owner数。内部并行是另一份设计，须重新核下游预算、实体顺序与提交前缀。[2]

故障积压=(1,200−600)×(9×60)=324,000条。恢复到μ=1,200/s但新流量仍λ=1,200/s，净余量为0；把新准入降到600/s，T=324,000÷(1,200−600)=540s。270s漏算了持续到来的工作。

提交lag是位置差，不总等于消息数；事务/压缩日志可能有空洞，拉取lag小也不代表效果完成。还要看各分区最老未完成年龄、outbox年龄、完成率与保留窗口。A5裸载荷为1,200×86,400×1,000×7×3=2.17728TB，另算元数据、压缩与DLQ。

Admission在新承诺前返回429/503并限额；已接受订单的outbox不能为清lag删除。pull只控消费者取件，不会自动限制producer。恢复给live和replay分预算，队列、worker与连接池都要有界。[4]

Deck 3 assumes six balanced partitions, one sequential worker per owner, and 200 completed effects/s per owner: three give 600/s, six give 1,200/s. More group members add no owners in this model. Internal concurrency requires a separate downstream, ordering and prefix design. [2]

Incident backlog=(1,200−600)×(9×60)=324,000 records. Restoring μ=1,200/s with λ=1,200/s leaves zero spare rate. Reduce admission to 600/s and T=324,000÷(1,200−600)=540s. The 270s answer omits ongoing arrivals.

Committed lag is a position difference, not always a record count. Transactional/compacted logs can have holes; low fetch lag does not prove effects completed. Monitor per-partition oldest age, outbox age, completion rate and retention. A5 raw payload is 1,200×86,400×1,000×7×3=2.17728TB, with metadata, compression and DLQ separate.

Admission rejects with 429/503 before making new promises. Accepted orders keep their outbox obligations. Pull controls consumer fetch, not producer arrival. Allocate live/replay budgets during recovery and bound queues, workers and connections. [4]

4 · DLQ与退避：转移责任，别抹掉业务身份4 · DLQ and backoff: transfer responsibility without changing identity

schema错误、无效身份与非法版本直接隔离；网络抖动或429只有在可安全重复、预算允许时补调用。异步任务若承诺跨重启最多两次，需要持久attempt计数或领取记录；内存计数会被崩溃重置。

图4写入原始数据、e7、来源分区/offset、schema、错误与尝试证据，等DLQ持久ACK后才推进源位点。ACK丢失就保留源位点并用原身份补写。DLQ故障时暂停并告警；入DLQ表示进入修复流程，不能把订单改成履约成功。

严格实体顺序需持久停车。不能让失败v8后面的v9继续。若要提交源前缀，先持久登记实体阻塞与恢复顺序，并要求重启/新owner加载阻塞；只有内存pause不够。另一种简单方案是不提交该失败位置，停整个分区。Replay Gate修复并核当前业务状态后限速重放，保留e7与effect_scope，新envelope只作审计。

Invalid schema/identity/version goes to quarantine. Retry transient networking or 429 only when repetition is safe and budgets allow. A cross-restart two-attempt limit for asynchronous work needs durable attempt/claim records; memory counters reset after crashes.

Deck 4 persists original data, e7, source partition/offset, schema, error and attempt evidence, then waits for durable DLQ ACK before advancing the source. Lost ACK retains the source position and repeats the original identity. Pause and alert if DLQ fails. Quarantine begins repair; it does not make fulfillment successful.

Strict entity order needs durable parking. Do not run v9 after failed v8. To advance the source prefix, first persist entity blocking/recovery order and require restarted/new owners to load it. An in-memory pause is insufficient. Alternatively keep the failing source position uncommitted and park the whole partition. Replay Gate repairs, validates current state and replays at a bounded rate, preserving e7/effect_scope; fresh envelopes serve audit only.

下面是同步依赖调用的退避伪代码，使用A7的同一800ms deadline；异步修复任务应另有业务期限，不沿用已结束的HTTP等待。正常路径是首次临时失败、本地I/O已结束、delay=60ms、剩余400ms：60+250+50≤400，拿到额外流量token才补一次。永久错、退避前只剩300ms且无法容纳退避、旧I/O仍活或额度耗尽都停止。定时唤醒与临发前都重算剩余；固定250ms尝试加50ms返回预留不足300ms就停止。预算由该层的准入控制器统一核发，若分实例分配，则各份总和不能超过层级上限。[20]

This is synchronous dependency-retry pseudocode under A7’s original 800ms deadline. Asynchronous repair needs its own business expiry, rather than inheriting an expired HTTP wait. Normal trace: transient failure, old local I/O ended, 60ms delay, 400ms remaining; 60+250+50≤400 permits one retry if an extra-traffic token is granted. Permanent errors, only 300ms left before a nonzero delay, live old I/O or exhausted budget stop it. Recompute time after the timer wakes and immediately before dispatch; stop below the fixed 250ms attempt plus 50ms return reserve. The tier’s admission controller issues that budget; per-instance allocations must sum within the tier limit. [20]

// Same business key; at most 2 TOTAL attempts including the first.
if permanent_error or unsafe_to_repeat: STOP_OR_RECONCILE
if attempts_started >= 2: STOP
if previous_local_io_has_not_terminated: WAIT_WITHIN_DEADLINE_OR_STOP
delay = uniform_random(0, 100 ms)         // A6/A7 bounded jitter
if now + delay + 250 ms + 50 ms > original_deadline: STOP

at scheduled time:

    if remaining < 250 ms + 50 ms: STOP
    recheck business validity

Deck 5’s Pool A/B are logical App bulkheads with independent permits/execution resources. A7 totals 50+300+100+250+50=750ms≤800ms, including connection, TLS, queueing and response time. Three layers with three total attempts each amplify by up to 3³=27. One retrying layer plus ≤10% extras turns 100/s originals into at most 110/s. Jitter spreads timing only. [4][20]

A8 uses means: 100/s×0.08s=8; at 2s it needs 200 concurrent calls. Cap 20 has a theoretical mean ceiling of 20÷2=10/s; reject or defer the rest. Little’s model does not prove p99. Semaphores alone do not isolate a shared A-saturated executor/connection pool from B. [5]

This excerpt from a runnable Java 17 example bounds local I/O for one dependency in one process. Each bulkhead has its own executor with zero queue. actualIo is a synchronous adapter that returns only after local blocking I/O ended, with no hidden background work. A future timeout completes waiting; the worker’s finally returns the permit. [6][17]

CompletionStage<String> call(Callable<String> actualIo, long deadlineNanos) {
    if (deadlineNanos - System.nanoTime() <= 0)
        return CompletableFuture.failedFuture(new TimeoutException());
    if (!permits.tryAcquire())
        return CompletableFuture.failedFuture(new RejectedExecutionException("full"));
    var reply = new CompletableFuture<String>();
    try {
        workers.execute(() -> {
            try {
                if (reply.isDone() || deadlineNanos - System.nanoTime() <= 0) {
                    reply.completeExceptionally(new TimeoutException());
                    return; // scheduled too late: do not start new I/O
                }
                // This synchronous adapter returns only after LOCAL I/O ends.
                reply.complete(actualIo.call());
            } catch (Exception failure) {
                reply.completeExceptionally(failure);
            } finally {
                permits.release(); // worker exit, never caller timeout
            }
        });
    } catch (RejectedExecutionException rejected) {
        permits.release(); // no worker started
        reply.completeExceptionally(rejected);
    }
    long left = Math.max(0, deadlineNanos - System.nanoTime());
    return reply.orTimeout(left, TimeUnit.NANOSECONDS).minimalCompletionStage();
}

正常完成与I/O异常都释放一次；提交executor被拒绝时没有worker，调用线程归还。worker开始前重查同一deadline，调度已迟到就不再发新I/O；这不是硬实时屏障，检查后仍可能被抢占，传输客户端也必须用剩余预算。

调用方已超时而worker仍阻塞时，许可继续占用，后续请求被拒绝；如果I/O永不结束，这个舱会保持耗尽，需要单独的硬停止/进程恢复策略。本地socket结束仍不证明远端业务停止。远端必须有自己的准入、deadline与业务幂等，取消不是rollback；未知写按原键查结果。

Success and I/O failure each release once. Executor rejection starts no worker, so the caller returns that permit. The worker rechecks the same deadline before dispatch and skips expired work. This is not a hard real-time barrier: preemption can follow the check, and the transport client must also enforce remaining budgets.

If the caller times out while the worker is blocked, its permit remains held and later calls are rejected. Never-ending I/O can exhaust this bulkhead and needs a separate hard-stop/process-recovery policy. Local socket termination does not prove remote business work stopped. The receiver still needs admission, deadlines and idempotency. Cancellation is not rollback; query unknown writes with the original key.

6 · 熔断：根据样本拒绝，用探针恢复6 · Circuit breaking: reject on samples and recover through probes

箭头表示状态迁移：CLOSED记录完成样本；达到最少样本且失败/慢调用率触阈值才OPEN；等候后HALF_OPEN放少量真实探针。A10窗口100、最少20、失败阈值50%：1/2虽为50%但不开；10/20才触发。统计窗口不是并发上限，仍需隔离舱。[7]

参数错、权限拒绝、本地舱满不能不加区分都算远端失败；明确失败、业务结果与忽略样本。半开三个是每个本地breaker的参数，八App最多8×3=24个本轮探针，不是全站三个；慢探针也须受deadline与舱限制。恢复后低速放量，重新量完成率，别一次灌回全部replay。

OPEN省掉调用，App仍须经Gateway给用户结果。头像可省略；核心写要明确失败或UNKNOWN，fallback访问别的远端也须保护。Resilience4j是实现选项；Hystrix官方状态是maintenance mode、无积极开发与新版本，不能直接改述为“不能用”。[8]

Arrows are state transitions. CLOSED records completed samples; enough samples plus the configured failure/slow-call threshold open it. HALF_OPEN later admits real probes. A10 has window 100, minimum 20 and 50% failures: 1/2 is 50% but insufficient; 10/20 qualifies. A statistical window does not bound concurrency; keep the bulkhead. [7]

Do not count invalid input, authorization refusal and local saturation indiscriminately as remote failures. Define failures, business results and ignored samples. Three half-open calls is per local breaker: eight Apps may admit 8×3=24 in this probe round, not three globally. Probe work still needs deadlines and bulkheads. Ramp recovery and remeasure completions before replay.

OPEN saves a call, but App still responds through Gateway. Omit an optional avatar; core writes require explicit failure or UNKNOWN. A remote fallback needs its own protection. Resilience4j is an implementation option; Hystrix officially states maintenance mode without active development/new releases, rather than being unusable. [8]

7 · 容器与排空：期望态不等于可用容量7 · Containers and drain: desired state is not usable capacity

普通Linux容器是共享宿主内核的隔离进程：namespaces限制可见视图，cgroups限制资源；VM有客户机内核。Pod可含一个或多个紧密协作容器，共享网络与声明的卷，PID空间不默认全共享；不可信执行仍须按威胁模型选沙箱/VM。[9][10][11]

图7的API Store概括API Server与持久API状态。Controller经API补对象；Scheduler给未绑定Pod选节点并写binding；kubelet观察本节点spec，经CRI运行时启动容器，再回报状态。这是重复对齐回路，不是Scheduler直接启动。containerd和CRI-O都可对接；1.24移除dockershim并未废掉兼容Docker镜像。[12][14][15]

只数Ready预算：3×250=750/s覆盖600/s；少一份只有500/s，需拒绝100/s。若要求一独立节点失效后仍守同预算，至少ceil(600÷250)+1=4份，且真有独立节点与余量。Running或desired=3不是第三份容量。startup、readiness、liveness分别管启动、普通端点准入和重启，不让远端DB故障触发全App的liveness重启。[13]

排空先关本地门，不等待路由传播。下面是应用集成伪代码，不是Kubernetes控制器实现。preStop可主动调用同一个幂等drain入口，TERM也走它；Pod宽限包含preStop，应用只使用预先分配的剩余排空预算并保留close/exit时间。端点更新与本地退出并行，不提供“所有入口已撤路由”的屏障；迟到流量由本地门拒绝。[19]

Ordinary Linux containers are isolated processes sharing the host kernel: namespaces constrain views, cgroups constrain resources, while VMs have guest kernels. A Pod holds one or more cooperating containers with shared networking/declared volumes; PID sharing is not universal by default. Untrusted execution still needs threat-model-based sandbox/VM choices. [9][10][11]

Deck 7’s API Store abstracts the API Server and durable API state. Controller creates objects through the API; Scheduler selects nodes/binds pending Pods; kubelet observes local specs, executes through CRI and reports status. This repeats rather than making Scheduler launch containers. Both containerd and CRI-O are options; 1.24 removed dockershim without invalidating compatible Docker images. [12][14][15]

Count Ready budgets: 3×250=750/s covers 600/s; one lost leaves 500/s and a 100/s deficit. Surviving one independent-node failure under the same budget requires at least ceil(600÷250)+1=4 replicas and actual independent node capacity. Running or desired=3 is not another usable replica. Startup, readiness and liveness govern initialization, normal endpoint admission and restart; a remote DB incident should not restart the entire App tier through liveness. [13]

Close locally before waiting for routing propagation. This is application-integration pseudocode, not a Kubernetes controller. preStop may invoke the same idempotent drain entry as TERM. Pod grace includes preStop, so use a preallocated remaining drain budget with time reserved for close/exit. Endpoint updates and local shutdown proceed concurrently; they supply no all-ingress removal barrier. The local gate rejects late traffic. [19]

on preStop drain request or TERM:
    under the same local lock as HTTP admission:
        if already draining: return existing drain task
        close admission; fix monotonic drain cutoff once
    report not-ready
    stop dispatching new queue work
    pause every assigned partition           // poll thread only
    disable new retries; keep existing durable obligations
    while before local drain cutoff:
        poll paused consumer; process completion notifications
        commit only safe fetched-record prefixes still owned
        if actual local I/O == 0 and no dispatched work remains: break
    final bounded commit of safe positions if still assigned
    close consumer within remaining budget
    exit; unfinished effects/unknown commits replay with original keys
// Queue ownership loss invalidates the old completion generation.
// Endpoint propagation and TERM run in parallel: late routes are refused.
// preStop consumes the Pod grace period; reserve time for close/exit.
// SIGKILL may cut any step; neither exit nor cancellation proves rollback.

正常路径：关门、暂停新派发，e7效果持久完成，poll线程提交安全前缀并退出。反例：截止时e7仍无回执或commit结果未知，就不把它标done，接手者用原键重放；SIGKILL可能切断任一步。节点失联时旧进程甚至仍运行，补一个Pod不替代业务唯一约束或fencing。队列消费者的归属由group协调，readiness本身不让它停止取件。

Normal path: close admission, pause new dispatch, durably finish e7, then commit its safe prefix on the poll thread and exit. Counterexample: e7 has no receipt or its commit is unknown at cutoff; do not mark it done, and let the next owner replay the original key. SIGKILL can cut any step. An unreachable node may still execute, so replacement does not replace uniqueness/fencing. Consumer ownership belongs to group coordination; readiness alone does not stop fetch.

面试复盘：用一个反例检查每道门Interview review: test every gate with a counterexample

  • 业务已提交、offset未提交：原e7重放，效果不能再加一次。
  • 90先完成、81未完成：只能等已拉取前缀，不取最大offset。
  • DLQ持久但回执丢失：保留源位点并重复隔离；严格顺序必须恢复持久阻塞。
  • Future已超时、socket仍活：许可继续占用；socket结束也不证明远端撤销。
  • 新Pod尚未Ready、旧Pod被TERM：容量按幸存Ready算，退出先关本地门。

  • Effect committed, offset uncommitted: replay e7 without another delta.
