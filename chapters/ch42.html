30 秒开场：先把承诺、容量和恢复分开A 30-second opening: promises, capacity and recovery

中文

我默认用 at-least-once，加接收端原子幂等。消息拉到不代表业务完成，业务提交也不代表位点已经确认。积压按 λ−μ 增长，恢复按 μ−λ 排空；毒消息先持久隔离再推进。同步调用继承 deadline，每个依赖限真实在途数，熔断靠证据半开。Kubernetes 维持期望态，调度只选节点，就绪证明才让副本接流量。

本章把 Ch20 · MQ 的投递合同、Ch41 · 事务 的持久意图接到运行时。沿用订单事件 e7：订单被接受后，账本消费者最终应用这份事件；可选头像依赖则允许省略。账本和头像有不同失败合同，不能因为同样经过队列或 HTTP 就统称“降级成功”。

学习顺序是七张终图：消费重放、Outbox 两端、积压与准入、DLQ 责任转移、deadline 和隔离舱、熔断三态、Pod 对齐回路。先口述正常路径，再找崩溃发生在两份回执之间的窗口。容器不会修复双写，队列不会创造处理容量，熔断也不会撤销已执行的扣款；每个组件都要有明确承担的责任。

本章数字均为 assumption，不是某个产品的线上指标。协议语义钉住 Kafka 4.1 普通 consumer group；share group 等另一种消费合同不套本章“一分区一个 owner”的估算。[1][2] 机制可以复用于通知、订单、支付和任务调度，分区复制细节仍留给 Ch20。

English

I default to at-least-once with atomic receiver idempotency. Fetch is not effect completion, and effect commit is not cursor acknowledgment. Backlog grows at λ−μ and drains at μ−λ; persist quarantine before advancing. Propagate deadlines, cap real active work per dependency, and half-open on evidence. Kubernetes maintains desired state; scheduling selects a node, while readiness admits traffic.

Connect Ch20 · MQ delivery to the durable intent in Ch41 · transactions. Event e7 represents an accepted order eventually applied by a ledger consumer. An optional avatar dependency may be omitted. Ledger and avatar failure contracts differ even when both use queues or HTTP.

Follow seven final diagrams: replay, both ends of Outbox, backlog and admission, DLQ responsibility transfer, deadlines and bulkheads, breaker states, and Pod reconciliation. Walk the normal path before locating a crash between receipts. Containers do not repair dual writes, queues do not create service capacity, and breakers do not undo a charge.

Every sizing number is an assumption, not production data. Consumer semantics are pinned to Kafka 4.1 classic groups; share groups have another contract and do not inherit this chapter’s one-owner-per-partition estimate.[1][2] Apply the mechanisms to notifications, orders, payments and scheduling; replication internals stay in Ch20.

一、消费语义：业务先提交，位点随后推进1. Delivery: durable effect before cursor advancement

中文

正常路径先走完整：Consumer 向 Event Log fetch，Event Log 返回 offset 81 的事件 e7；Consumer 在 Effect DB 的本地事务中插入 inbox 身份、更新账本并存结果，Effect DB 返回持久提交证据；最后 Consumer 提交 Group Cursor 的 next=82，等待确认。Group Cursor 是 broker 中这个消费组的持久位点，单独展开画出以区分它与业务库。拉取位置前进，只说明记录到了内存。[2]

先提交 82 再写业务，是 at-most-once 的典型丢失窗口：进程死后恢复从 82 开始，81 的效果没有出现。先业务后位点，是 at-least-once 的典型重复窗口：效果库已经提交，进程来不及提交位点就死，接手者从 81 再处理。它保证的范围以 A2 为前提；日志被保留策略删除、持久副本全部丢失、永久无人恢复，都不能再声称“不丢”。需要长期追索的承诺应有额外业务凭据与修复路径。

“按事件 id 做 upsert”只是一种写法，必须说明效果。把累计金额执行 balance=balance+100，即使把消息行 upsert 成同一行，余额仍可能加两次。正确边界是同一事务中先以 UNIQUE(effect_scope,event_id) 抢到处理资格，再写账本增量和持久结果；任一步失败全部回滚。两个并发消费者竞争同键，由数据库唯一约束定胜负，不能先 SELECT 没见到，再各自加一笔。

效果作用域也不能省。订单 e7 会让账本入账、通知用户，这两个合法动作不能被一张只按 event_id 去重的全局表互相挡掉。作用域应能区分消费者业务职责；同一作用域同键还必须核参数摘要和资源身份。重复时读已有结果，相同键携带不同金额则拒绝并告警。权限检查也照常做，幂等结果不能把先前用户的回执交给另一个调用者。

图上还藏着一个批处理陷阱：81、82、83 并发处理，83 完成而 81 没完成，不能提交 next=84。那会把空洞里的工作永久跳过。每分区维护连续已完成前缀，只有前缀能前进；失败分区可以 pause，其他分区继续 poll，避免整个组因长处理失去活性。[2] 普通 group 的 ownership 不等于旧进程物理停止，业务端唯一约束和必要的版本检查仍要拒绝旧动作。

幂等需要和重放期限一起设计。只把 inbox 放缓存一天，却允许 DLQ 三十天后重放，旧 e7 会再次获得资格。A2 要求覆盖全部获准重放期，超出时走人工核账和业务唯一凭据，不能简单清 TTL 后当新事件。exactly-once effect 在这个效果库事务内可以讲清；把这句话扩成“消息在任何地方只投一次”，就丢掉了边界。

English

Walk the normal path: Consumer fetches e7 at offset 81 from Event Log. In one Effect DB transaction it inserts inbox identity, updates the ledger and stores an outcome. Effect DB supplies durable completion evidence. Consumer then commits next=82 to Group Cursor and awaits acknowledgment. Group Cursor expands broker-managed group position separately from business state; fetch position only shows what reached memory.[2]

Commit 82 before the effect and a crash can lose 81: restart begins at 82. Commit the effect first and a crash before cursor commit can replay it: the next owner begins at 81. At-least-once relies on A2. Expired retention, loss of every durable replica or permanent failure to resume invalidate an unconditional no-loss claim. Long-lived obligations need additional business evidence and repair.

An event-id upsert must identify the effect it protects. Upserting a message row while executing balance=balance+100 can add twice. In one transaction claim UNIQUE(effect_scope,event_id), write the ledger delta and persist the outcome, rolling everything back on failure. Concurrent receivers race on the DB constraint, not a SELECT-then-update gap.

The effect scope matters. Ledger application and customer notification for e7 are different valid actions; one global event-id-only inbox can suppress one of them. Include the business responsibility and verify payload digest and resource identity. Return the stored matching result; reject conflicting amounts. Authorization still applies so another caller cannot inherit a prior user’s receipt.

Concurrent completion of 83 while 81 is unfinished does not permit committing next=84. Advance only the contiguous completed prefix per partition. Pause a failed partition while polling others to retain group progress.[2] Group ownership does not physically stop an old process; uniqueness and appropriate version checks still guard business effects.

Deduplication lifetime must cover replay. An inbox cached for one day cannot protect a replay thirty days later. A2 covers the full authorized horizon; older work requires reconciliation against enduring business uniqueness. Exactly-once effects can be described within this DB transaction boundary, not as messages being delivered once everywhere.

二、EOS 与 Outbox：两种不同的事务边界2. EOS and Outbox: distinct transaction boundaries

中文

Kafka 的 consume–process–produce 闭环可以把输出记录与输入消费位点放入同一个 Kafka 事务，读者用 read_committed 只看已提交输出。[1] 进程在事务提交之前死，两者都不生效；在提交之后丢回执，事务协议恢复它的已决结果。幂等 producer 解决协议范围内的重发去重，不会因为两个独立业务调用恰好参数一样，就自动知道它们是同一笔扣款。

这个闭环也有代价：协调事务、提交确认、隔离读取都会增加管理与延迟，未决事务可能阻挡后续可见输出。是否值得买它，要看读者必须看到怎样的跨记录原子结果。金额账本不能靠“Kafka 开了 EOS”替代效果库的约束；Kafka 文档也把外部系统结果与消费位点的协调作为额外问题。[1] 本章选择把接收库 inbox 与业务变更同事务，承认跨系统投递会重复。

另一头是产生事件。App 接受订单时，把 Order、Outbox 和同请求键的已接受结果写进 Order DB 同一事务；图里上方只画这份源库承诺。若先提交订单，再从进程内存 send，宕机窗口会留下有订单、无事件。Outbox 消掉这个窗口：只要提交成立，Relay 就有持久记录能扫描或由 CDC 送出。[3] 源库和 Effect DB 是两套物理事务域，不把两个圆柱圈成一份原子事务。

Relay 发 e7 给 Event Log，必须等待满足持久合同的 publish ACK，才把 outbox 标为已发或推进 CDC 位点。事件已经到 broker、ACK 丢失时，Relay 仍重发 e7，所以 Consumer 端的原子去重不可少。数据库确认只是“订单和发件意图已在”，不是“客户收到短信”；Broker 确认只是“我负责保存”，也不是“账本已入账”。用户若查询状态，应能分别看到接受、待履约、已完成或失败。

若 Consumer 调的是外部支付或短信 HTTP，本地 inbox 不能和远端效果一起提交。先写 done 再调，崩溃会漏发；先调再写 done，回执丢失会重复。需要持久 dispatch intent、稳定业务键，以及远端将该键和效果原子记录、可查询结果的能力。得不到这种能力，就承认 UNKNOWN，做核账或人工处理；不能以“本地有锁”推出远端只执行一次。相关两库推导可回 Ch24 · 支付。

顺序还要另说。订单取消与发货事件重排，两个都“幂等”仍可能产生非法状态。按实体版本作条件迁移，必要时同键分区顺序处理；重复事件读取原结果，过时事件拒绝或补偿。Outbox 把事件意图可靠带出源库，EOS 把 Kafka 内的输出与位点绑定，业务版本保护的是合法迁移。三者能组合，但不是同一种保证。

English

Kafka consume–process–produce can commit output records and input positions in one Kafka transaction; read_committed readers observe committed output.[1] A crash before commit applies neither, while a lost post-commit receipt is resolved by the transaction protocol. Producer idempotency deduplicates protocol retries, not independent business calls with coincidentally equal payloads.

This boundary costs coordination, commit acknowledgment and isolation; undecided transactions can delay later visible output. Buy it for a required atomic observation contract. Kafka EOS does not replace ledger constraints. Its documentation treats coordination with external output systems as an additional problem.[1] Here inbox and business mutation commit locally while cross-system delivery may repeat.

At the source, App commits Order, Outbox and the accepted result for the same request key together in Order DB. Sending from memory after order commit leaves an order-without-event crash gap. Outbox preserves a durable record for Relay scanning or CDC.[3] Order DB and Effect DB are separate physical transaction domains, not one atomic transaction.

Relay sends e7 to Event Log and marks progress only after a publish ACK satisfying durability. Lost ACK causes another e7, requiring Consumer deduplication. DB acknowledgment means accepted order and intent, not delivered SMS; broker acknowledgment means saved work, not an applied ledger effect. Status should distinguish acceptance, pending fulfillment, completion and failure.

An external payment or SMS HTTP effect cannot join the local inbox transaction. Marking done first risks omission; calling first risks duplication after a lost receipt. Persist dispatch intent and a stable key, and require remote atomic key/effect recording plus outcome lookup. Without them, preserve UNKNOWN and reconcile instead of claiming a local lock guarantees one remote effect. See Ch24 · payments.

Ordering is separate. Idempotent cancellation and shipment can still form an illegal state transition if reordered. Apply entity-version conditions and, when needed, sequential same-key handling. Repeats read stored outcomes; stale actions are rejected or compensated. Outbox preserves source intent, EOS binds Kafka output and positions, and business versions guard valid transitions.

三、积压：用净处理余量算恢复3. Backlog: recover with spare service capacity

中文

先定尺子。提交 lag 可用日志末端位置减 committed position，表示已留在日志里却尚未确认完成的距离；已拉取 lag 小不代表效果已完成。事务日志、压缩日志里的 offset 可能有空洞，位置差也不总等于业务消息条数。[2] 图中 A3 为简化，按连续、等大小的事件算记录数量。生产端已确认却仍滞留 outbox 的工作，还没进入 broker lag，必须另看源端年龄与未发送数量。

正常链路是 Producer 经过 Admission 准入，Admission 追加 Event Log 等持久 ACK，再回 Producer。Consumer 控速 fetch，完成效果后 commit。这里的 Consumer 是整组的聚合框，不是“一台同时拥有六份独立能力”的实测。A3 假设六个分区均匀、每分区保序、每 owner 单工作线程且下游有预算，每个 owner 完成 200/s；三个 owner 总量 600/s，六个 owner 1,200/s。更多普通 group 成员只等待分区归属。[2]

这个上限也有条件：一个 owner 可以把独立工作交给线程并发，但要维护上一组的连续提交前缀，并保护实体顺序。此时吞吐取决于内部并发与下游，不再用“分区数乘顺序处理速率”直接套。share group 或传统 work queue 可以用另一种分发合同。面试官一问并行，先说选了什么模型，再说瓶颈。加分区也会改 key 路由，不可把正在飞行的旧 key 顺序当成自动延续。

A4 故障时每秒少完成 1,200−600=600 条，九分钟是 9×60=540 s，积压 L=600×540=324,000 条。恢复六个 owner 到 μ=1,200/s，但如果新流量仍 λ=1,200/s，μ−λ=0，积压永远不下降。将新准入收成 600/s 后，净排空 1,200−600=600/s，T=324,000÷600=540 s。除以全部处理能力得到 270 s，错在把仍持续到来的新工作忽略。

日志空间也要算。A5 极端按全天峰值：1,200×86,400=103,680,000 条/天，乘 1,000 B 是 103.68 GB/天；七天为 725.76 GB，三份为 2,177.28 GB=2.17728 TB。这个只是原始记录载荷模型，元数据、事务标记、压缩收益和 DLQ 不在里面。容量够七天，也不保证第八天还能重放。告警同时看每分区最老未完成年龄、提交速度、outbox 年龄和磁盘剩余。

背压要发生在新的承诺之前。Admission 对尚未接受的请求返回 429 或 503，调用方按合同退避；对已提交订单则暂停接新的类似工作、限速修复持久意图，不能删除它的 outbox 假装队列恢复。pull 是消费者对 broker 的控速，不是生产者自动限速。把积压藏进无界堆队列，只把用户等待变成一次 OOM。恢复期间还要给 live 和 replay 分预算，防止历史流量挤掉新请求或把下游再打倒。[4]

English

Committed lag is the distance from log end to committed position; a small fetched lag does not prove effects completed. Offsets can have gaps in transactional or compacted logs, so distance is not always a business-record count.[2] A3 simplifies to continuous equal-sized records. Accepted work still in Outbox is absent from broker lag and needs its own age and count metrics.

Producer is accepted through Admission, which appends to Event Log and waits for durable ACK before replying. Consumer pulls at its pace and commits after effects. Its box aggregates the group. With six balanced partitions, one sequential worker per owner and downstream capacity, A3 gives 200/s per owner: three give 600/s, six 1,200/s. Additional classic-group members await assignment.[2]

An owner may process independent work concurrently if it preserves contiguous commits and entity order. Throughput then depends on internal concurrency and downstream capacity, not this sequential partition formula. Share groups and work queues have different contracts. State the chosen model first. Adding partitions also changes key routing and does not automatically preserve order across in-flight old assignments.

A4 loses 1,200−600=600 completions/s for 9×60=540 s, creating 324,000 backlog. Restoring μ=1,200/s while λ remains 1,200/s leaves zero drain. Reducing admission to 600/s creates 600/s spare capacity, so T=324,000÷600=540 s. Dividing by all 1,200/s to get 270 s incorrectly omits ongoing new arrivals.

A5 models all-day peak: 1,200×86,400=103,680,000 records/day. At 1,000 B each this is 103.68 GB/day, 725.76 GB for seven days, and 2,177.28 GB=2.17728 TB for three copies. Metadata, transaction markers, compression and DLQ are separate. Seven-day storage does not promise day-eight replay. Alert on partition age, commit speed, outbox age and free disk.

Backpressure acts before new promises. Admission returns 429 or 503 for unaccepted requests; callers back off under contract. Already committed orders retain their outbox obligations while new admission is reduced and repairs are paced. Consumer pull does not automatically throttle producers. An unbounded heap queue merely turns waiting into OOM. Allocate separate live and replay budgets during recovery.[4]

四、DLQ：确认责任转移，保留原业务身份4. DLQ: acknowledge responsibility transfer and preserve identity

中文

第一步不是“一律重试两次”，而是分类。非法 schema、签名错误、不可满足的业务版本，不会随着退避变正确；隔离并报警。临时网络不可达、下游 429 或短暂 5xx，只有在业务合法、可幂等恢复而且预算允许时才补调用。两次总 attempt 包含首次，不是先做一次再重试两次。等待重试的分区可暂停取新件，但控制循环仍须保持活性，不能靠睡一整分钟把组心跳和 poll 都卡住。

Consumer 从 Event Log 拉 e7，正常成功用第一组的效果库合同。失败进入隔离时，将原始记录、事件身份、来源分区与 offset、schema 版本、错误分类和尝试证据写入 DLQ Log，并等待持久 ACK。之后才能提交源 Group Cursor 的 next=82。DLQ 只说明主流程停止自动尝试、工作进入人工或受控修复；它不是业务完成。订单状态应能表明隔离失败，不能只在技术监控里留下一个计数。

DLQ ACK 丢失时，这份记录可能已经持久保存。Consumer 不确定，就保留源位点，恢复后用原身份再投一次。DLQ 存储可以按来源身份去重，也可以保存重复 envelope 便于审计；后续业务效果仍以 e7 去重。源端先 commit 再发 DLQ，会在进程死时既不再消费、也没有隔离副本，这条路径必须被否决。若 DLQ 本身不可用，选择暂停分区或对应实体并告警；不能为了清 lag 直接跳过。

还有业务顺序代价。库存事件 v8 无法解释，却把 v9 发货继续执行，会比积压更严重。要求严格实体顺序时，停住这个实体的后续事件，或把它们一起转入有明确恢复协议的停车区；允许独立实体继续。按分区暂停最简单，却会牵连同分区其他实体。按实体停车更细，代价是保存阻塞状态、恢复序列和连续提交关系。选择哪种取决于你愿意承担的实现复杂度，不能暗示进 DLQ 后所有后续事件都自动合法。

Replay Gate 是有负责人和审计的恢复工具。先修 schema 或业务数据，核当前订单状态、权限、效果是否已经发生，再限速重放，得到 Event Log 持久 ACK 才标记已重放；业务完成另等效果回执。保留原 event_id 和 effect_scope；新 envelope_id 只标识这次搬运。若要发起新的补偿，那是显式新业务动作，要另有合法状态迁移和补偿身份。直接“改一个 id 再试”，会把历史副作用重新执行。重放速率也算进上一组的 μ−λ 余量。

让 DLQ 可运营，至少要回答四件事：最老一件是谁负责、是否超过业务死线、能否解释失败分类、重放后怎样确认完成。保留三十天不是自动授权三十天后的旧命令仍然有效；A2 的去重期和当前业务版本验证一起守边界。对于不能再执行的旧付款通知，可以核账并标记人工结案。隔离是把无法自动完成的责任留下来，而不是给毒消息换一个叫 trash 的目录。

English

Classify before retrying. Invalid schema, signatures or impossible business versions do not heal with backoff. Isolate and alert. Temporary connectivity, 429 or brief 5xx may merit a retry only when business legality, idempotency and budget permit. Two total attempts include the first. Pause fetching where needed while keeping the consumer control loop alive.

Consumer fetches e7 and normally applies the first deck’s effect contract. Quarantine persists original data, identity, source partition and offset, schema version, error class and attempt evidence in DLQ Log, waits for durable ACK, then commits next=82. DLQ means controlled repair replaces automatic attempts, not business completion. Order status must expose isolation failure.

A lost DLQ ACK may follow successful persistence. Retain the source cursor and republish the original identity. DLQ may deduplicate source identity or retain duplicate envelopes for audit; effects still deduplicate e7. Committing source first risks a crash with neither processing nor quarantine. If DLQ is unavailable, park the partition or entity and alert instead of skipping to clear lag.

Strict ordering changes the decision. Uninterpretable inventory v8 followed by shipment v9 can be worse than backlog. Park the entity’s subsequent events or move them into a controlled recovery sequence, letting independent entities proceed. Partition parking is simpler but affects neighbors; entity parking requires durable blocked state and ordered recovery. Neither choice makes every later event automatically legal.

Replay Gate has an owner and audit. Repair schema or data, verify current state, permissions and prior effects, then replay at a bounded rate. Mark replayed only after durable Event Log ACK; business completion still needs an effect receipt. Retain event_id and effect_scope; a new envelope_id identifies transport only. A genuine compensation is an explicit new business action with its own valid transition and identity. Changing ids to retry repeats effects. Replay consumes the previous deck’s spare service budget.

Operational DLQ questions include ownership of the oldest case, business deadline, intelligible failure class and confirmation after replay. Thirty-day retention does not authorize a thirty-day-old command. Deduplication and current version validation jointly protect A2. An obsolete payment notice may require reconciliation and manual closure. Isolation preserves responsibility instead of hiding it in trash.

五、deadline 与隔离舱：超时不等于实际工作消失5. Deadlines and bulkheads: timeout does not erase active work

中文

把图里的请求逐跳走一次：Client 到 Gateway，Gateway 到 App；App 通过 Pool A 调 Dep A，通过 Pool B 调 Dep B。B 的结果由 Dep B 回 Pool B、App；A 的失败由 Dep A 回 Pool A、App，再经 Gateway 回 Client。图里 App 上的隔离舱展开为两个逻辑许可池，不要求生产环境多部署两台机器。A 是可选头像字段，B 是核心业务，只有前者允许失败后省略字段。

先钉总 deadline，再为尝试分配预算。A7 从 800 ms 减前段 50、首次尝试最多 300、jitter 最多 100、补调用最多 250、返回 50，合计 750 ms，还余 50 ms。下游要用实际剩余时间，connect、TLS、排队和读响应不能藏在“300 ms 之外”。连接阶段耗了 100 ms，响应阶段就只剩这次尝试的 200 ms。客户端超时负责切断等待，不能只把外层 Future 包起来就以为阻塞 socket 必然停了。[6]

Pool A cap=20、Pool B cap=10，是并发上限，不是每秒请求数。信号量可以限制执行中的调用，固定线程池则要连排队长度一起封顶。[5] 舱满时快速拒绝或在很短的剩余预算内等待。两个依赖若最终共用一个已经被 A 占满的阻塞线程池，表面画了两个 semaphore 仍没有隔离。连接池、执行线程和队列的占用也要按依赖分开预算；异步执行也要数真实在途工作。

容量算术用均值。A8 正常平均在途 N=λ×W=100/s×0.08 s=8；变慢到 2 s 则 N=200，超过 20。20 个许可只是硬封顶，要达到 100/s 还需实际服务时间足够短；在 2 s 下，理论均值上限只有 20÷2=10/s，额外请求必须拒绝或延后。这个均值模型不证明 p99 达标，真实分布、连接建立与取消时间要压测。不要把 20 的 permit 数说成测得能处理 20 QPS。

最容易漏掉的是幽灵调用。调用方 Future 在 300 ms 超时后立即释放 permit，而远端或底层 I/O 继续两秒，新的二十个又进来，就不再是“最多二十个真实调用”。取消请求可以发给远端，但要有本地 I/O 终止证据才归还许可；库包装器的顺序和取消能力必须核验。对于不能立即中止的工作，可以给它单独的退休状态与硬资源上限。应用线程返回不等于远端 rollback，未知的扣款回执仍须以原业务键查询。

重试是新增流量。反例 A9 三层各最多三次总 attempt，最底层最坏是 3×3×3=27 次，原始 100/s 会打成 2,700/s；全部补调都成立且首次就失败时才取这个最坏数。方案只让选定一层补调用，并把全局额外重试限制到原始流量的 10%，于是 100+10=110/s。两次总 attempt 是单请求边界，10% 是整层边界，二者都要守。[4] jitter 防齐步，不会凭空削掉总工作量。

English

Walk each hop: Client→Gateway→App. App calls Dep A through Pool A and Dep B through Pool B. B replies via Pool B to App; A failure returns through Pool A, App and Gateway to Client. Pools expand logical permits inside App, not necessarily two additional deployed machines. A is an optional avatar field; B is core work.

Allocate attempts within one deadline. A7 totals 50 ms front, 300 first attempt, at most 100 jitter, 250 retry and 50 return: 750 ms, leaving 50 of 800 ms. Use actual remaining time. Connect, TLS, queueing and response reads fit inside the attempt budget; a 100 ms connection leaves 200 of its 300 ms. Timing out an outer Future alone does not ensure blocked socket work has stopped.[6]

Pool A cap=20 and B cap=10 limit concurrency, not requests per second. Semaphores constrain active execution; fixed thread pools also need bounded queues.[5] Reject saturation or wait briefly within remaining time. Two semaphores above one A-saturated blocking executor do not isolate B. Budget connections, threads, queues and asynchronous active work appropriately.

A8 uses means: N=λ×W=100/s×0.08 s=8 normally, but 200 at two seconds, exceeding cap 20. The cap is not throughput evidence. At two seconds, 20÷2=10/s is the theoretical mean ceiling; excess must be rejected or deferred. This mean model does not prove p99, which needs service distribution, connection and cancellation testing.

Ghost work appears if a caller releases its permit after a 300 ms Future timeout while real work continues for two seconds. New admissions exceed twenty real calls. Send cancellation, but return the permit only on evidence of local I/O termination; verify wrapper order and cancellation behavior. Noninterruptible work needs a bounded retirement state. A returned thread is not remote rollback; query unknown charges with the original key.

Retries add traffic. A9’s counterexample has three layers with three total attempts each, making 3×3×3=27 lowest-layer calls and up to 2,700/s from 100/s originals when all branches retry. Retry in one selected layer and cap global extras at 10% of originals: 100+10=110/s. Two total attempts bounds one request; 10% bounds the tier.[4] Jitter spreads timing without eliminating work.

六、熔断：基于样本拒绝，凭探针恢复6. Circuit breaking: reject on evidence, recover through probes

中文

这一组箭头是状态迁移，不是把 timeout、bulkhead、circuit 三个库排成网络链。CLOSED 允许调用并记录完成结果；满足最少样本且失败率或慢调用率达到策略阈值，转 OPEN 拒绝后续普通调用；等待后进 HALF_OPEN，用少量实际调用探测。Resilience4j 文档明确指出，滑动窗口统计与并发执行限制不同，后者需要 bulkhead。[7] 所以必须先知道单次等待何时结束，再讨论连续异常后要不要继续打。

A10 用最近一百次完成调用的窗口、最少二十个样本、50% 失败阈值。如果只完成两次、一成功一失败，虽然算术上 1÷2=50%，样本门槛还不满足，不开断路；二十次中十次失败，10÷20=50%，才符合图里的开启条件。它们是本章选择的教学参数，不是照搬库默认值。高低流量接口的最少样本与窗口尺度不同，要在误伤和反应速度之间做取舍。

失败分类关系到健康证据。用户传错参数、权限拒绝，本地 A 舱满，与 Dep A 实际超时是不同责任；全部记成远端失败，会在正常依赖前误开断路。所有异常都忽略又会永远关着。定义哪些异常算失败、哪些算业务完成、哪些不进入分母；慢调用阈值也要按这份依赖合同设置。多个主机各有本地 breaker 时，统计不是全站共享的真相，观测页面必须能看到分实例差异。

OPEN 时省掉的是调用，不是用户响应。可选头像按 A12 省略字段；核心支付返回明确失败或 UNKNOWN，并保留可查询的业务状态。fallback 本身若要访问另一套远端服务，它也需要 deadline 和隔离，不能把第二套依赖写成永不失败。旧值的产品期限与鉴权同样需要约束。入口用户响应是 App 经 Gateway 返回，不能把 breaker 画成直接越过 App 给用户造一个成功。

HALF_OPEN 也要算全站预算。单实例放三个探针，八个实例就是 8×3=24，不是只探三次。探针批次失败率低于阈值才回 Closed，仍达到阈值则回 Open；本章假设等五秒后允许探测。[7] 刚恢复的下游未必立刻扛得住积压，所以先低速放量、观察真实完成率，再调整新准入与 replay。把 breaker 关上后马上所有队列 drain，会把下一轮故障主动制造出来。

实现名只作为路标。新 Java 项目可以采用 Resilience4j 或同等机制，仍须核客户端超时与装饰顺序；不把注解当成传输取消证明。Hystrix 官方说的是 maintenance mode、已无积极开发及新版本发布，[8] 用“已停止积极开发”比把它笼统写成不可用更准确。既有系统可以理解它的线程隔离设计，新方案先把机制与边界讲清。完整的服务拆分和发现继续留给 Ch44。

English

These arrows are state transitions, not three libraries arranged as network hops. CLOSED permits calls and records outcomes. Sufficient samples and the configured failure or slow-call threshold open the breaker. OPEN denies ordinary calls; HALF_OPEN later admits a few real probes. Resilience4j distinguishes window statistics from concurrency limits, which need a bulkhead.[7] Determine bounded single-call waiting before deciding when repeated failures should stop calls.

A10 uses a window of one hundred completed calls, minimum twenty and a 50% failure threshold. One failed of two is 1÷2=50% but lacks the minimum. Ten failures among twenty give 10÷20=50% and qualify. These are teaching parameters, not library defaults. Window size and minimum samples balance reaction speed against false positives for the interface’s traffic.

Classify evidence: invalid input, authorization refusal, local pool saturation and real Dep A timeout have different causes. Counting all as remote failures can open against a healthy dependency; ignoring every exception prevents opening. Specify failures, business outcomes and ignored observations. Local breakers on multiple hosts are not one shared global health state, so expose per-instance variation.

OPEN saves calls, not user responses. Omit the optional avatar under A12. Core payment returns explicit failure or UNKNOWN with queryable state. A fallback that calls another remote service needs its own deadline and isolation. Staleness and authorization remain constrained. App responds through Gateway; a breaker must not bypass App to manufacture success.

Budget probes across instances: three per instance on eight instances gives 8×3=24. A probe batch below the threshold closes; one reaching it reopens. A10 assumes a five-second open wait.[7] A recovered dependency may not immediately absorb backlog. Ramp gradually, observe completions, and budget admission and replay rather than draining everything on close.

Implementation names are signposts. Resilience4j or equivalent still needs client timeouts and verified decorator order; an annotation is not cancellation evidence. Hystrix officially states maintenance mode with no active development or new releases,[8] more precise than calling it unusable. Existing systems can retain its isolation design; new designs explain the mechanism. Service splitting and discovery remain in Ch44.

七、容器与 Pod：期望态是控制回路，就绪才算容量7. Containers and Pods: reconciliation and ready capacity

中文

容器先当作受隔离的进程来理解。Linux namespaces 控制进程看见的 PID、网络、挂载等视图；cgroups 控制资源分配与限制，例如 CPU 和内存。[9][10] 普通容器共享宿主内核，没有给每个容器启动一份完整客户机内核。VM 有自己的客户机内核，提供另一层隔离边界。可信普通服务可以用容器提高密度，不可信多租户执行仍需根据威胁模型选沙箱或 VM，不能把“有 namespace”说成任意代码都安全。

Pod 是 Kubernetes 创建、调度和管理的基本单元，可包含一个或多个紧密协作的容器，共享网络命名空间并使用声明的共享卷。[11] app 与 sidecar 能通过 localhost 协作，但不会因此每个 Pod 都固定有两个容器；也不是所有 PID 空间都默认共享。镜像描述程序和文件系统，Pod 描述要怎样一起运行，节点是实际提供内核和算力的机器。把容器当一台带独立内核的 VM，会误读资源与故障边界。

图里的 API Store 合并表示 API Server 入口与其持久的 API 状态，所有参与者通过 API 读写，绝不是 kubelet 直接访问底层 etcd。Controller 观察 desired=3 与已有 Pod，创建缺失的 Pod 对象；Scheduler 观察未绑定对象，选节点并通过 API 写 binding；节点 kubelet 观察分给自己的 spec，再经 CRI 调 containerd 启停容器。[12][15] 对齐会重复发生，运行状态由运行时返回 kubelet，再经 API 回报，不能画成 Scheduler→Pod→containerd 一次性接力。

声明三个副本，只是期望，不是三份已可用的能力。A11 里每个 Ready 副本预算 250 req/s，三份共 3×250=750/s，覆盖 600/s；只剩两份 Ready 是 500/s，缺 600−500=100/s。Pending 或刚 Running 的新 Pod 不可拿来补这条算式。若要求独立节点失一份后仍覆盖峰值，则至少需要 ceil(600÷250)+1=4 份预置容量，并真有足够节点承接；多写一份 spec 不会凭空加机器。

探针承担不同责任。startup 给慢启动一次完成机会；readiness 失败让普通 Service 端点停止接新流量；liveness 失败按策略重启容器。[13] 不能让 liveness 直接检测整个远端 DB 可用性，否则 DB 故障会导致全体应用重启。发布先验证新副本 Ready，再把旧副本退出新流量并给已接工作 drain 时间；传播有延迟，客户端仍需 timeout 和幂等。特殊 publishNotReadyAddresses 等合同要另说，本图只用普通就绪端点。

节点失联时旧节点也许还在执行。控制面创建替代 Pod，不等于把旧库写、旧 HTTP 调用或旧队列处理物理取消。业务写仍需稳定身份、唯一约束或 fencing，队列位点仍按连续完成提交，优雅退出先停止取件再处理已在途工作。无状态副本可替换的意思是进程不保存唯一业务真相，不是“杀进程会把外面的一切撤销”。这也把本章第一组的崩溃恢复接回最后一组。

运行时名称说准即可：Kubernetes 1.24 移除了内置 dockershim，kubelet 使用 CRI 对接兼容运行时，例如 containerd 或 CRI-O；Docker 构建的兼容镜像仍能使用。[14] 不把 containerd 写成唯一选择，也不把 Docker 镜像与 Docker Engine 混为一件事。Borg 论文提供声明任务与集群管理的经典背景，[16] 今天的 Pod 与探针细节以 Kubernetes 原文为准。对账、关单、misfire 的业务调度仍去 Ch25。

English

Treat containers as isolated processes. Linux namespaces control views of PID, networking and mounts; cgroups control resource allocation and limits such as CPU and memory.[9][10] Ordinary containers share the host kernel instead of booting a full guest kernel each. VMs have guest kernels and another isolation boundary. Container density suits trusted services; untrusted tenancy may need sandboxing or VMs under the threat model.

A Pod is Kubernetes’ basic created, scheduled and managed unit, containing one or more cooperating containers with shared network namespace and declared volumes.[11] App and sidecar can communicate on localhost, but not every Pod needs two containers and PID namespaces are not all shared by default. Images describe programs/filesystems, Pods their joint running contract, and nodes the actual kernel and compute.

API Store combines the API Server endpoint and durable API state; participants use the API, not direct kubelet access to etcd. Controller creates missing Pod objects for desired=3. Scheduler selects nodes for unbound objects and writes API bindings. Node kubelet observes assigned specs and calls containerd through CRI.[12][15] The loop repeats, with status returning through runtime, kubelet and API instead of a one-off Scheduler→Pod→containerd relay.

Three desired replicas are not three usable replicas. A11 budgets 250 req/s per Ready replica: 3×250=750/s covers 600/s, while two leave 500/s and a 100/s deficit. Pending or newly Running Pods do not fill it. Surviving one independent-node loss at peak requires at least ceil(600÷250)+1=4 pre-provisioned replicas and actual node capacity; another spec does not create a machine.

Startup, readiness and liveness have different jobs. Startup permits slow initialization; failed readiness stops normal Service admission; failed liveness can restart a container.[13] Testing remote DB health as liveness can restart the entire App tier during a DB incident. Wait for new Ready replicas before removing old ones from new traffic and draining accepted work. Propagation is delayed; callers still need timeouts and idempotency. Special publishNotReadyAddresses contracts are outside the normal endpoint model here.

An unreachable old node may still execute. A replacement Pod does not physically cancel prior DB writes, HTTP calls or queue processing. Business effects still need stable identities, uniqueness or fencing. Commit contiguous completed work and stop fetching before graceful drain. Replaceable stateless replicas mean the process does not hold unique business truth, not that process death undoes external effects. This closes the loop to the first deck’s recovery contract.

Kubernetes 1.24 removed built-in dockershim. kubelet uses CRI-compatible runtimes such as containerd or CRI-O; compatible Docker-built images remain usable.[14] containerd is not the sole choice, and an image is distinct from Docker Engine. Borg supplies the classic cluster-management background,[16] while Kubernetes documentation governs current Pod and probe details. Business reconciliation, order closing and misfire scheduling remain in Ch25.

追问怎么接How to answer follow-up questions

中文

能做到恰好一次吗？ 先问作用域。Kafka 内的输出与消费位点可以用事务和 read_committed；同效果库用 inbox 与业务变更原子提交；外部 HTTP 要远端幂等结果合同。能证明的是指定边界内的效果一次，不把它说成全链投递一次。

为什么不能一直扩消费者？ A3 选普通 group、六分区和顺序处理；owner 六个已占满。内部并发可以另设计，但要连续提交和守实体顺序。先看下游预算和每分区年龄，不能用总 lag 平均数掩盖一个热分区。

熔断、限流和隔离舱哪个先加？ 先有 deadline 才有可解释的单次失败。限流约束到达速率，隔离舱约束真实在途数量，熔断根据最近完成样本拒绝不健康依赖。装饰顺序还决定哪些拒绝进入统计，不能用一行注解替代这个约束图。

节点挂了，自愈不是已经解决吗？ 自愈修复进程与期望副本数；旧节点未必停了，权威数据与远端副作用还需要第一组的去重和旧版本拒绝。新 Pod 未 Ready 前容量仍按幸存实例算。

English

Can it be exactly once? Ask the boundary. Kafka output/positions can use transactions and read_committed; one effect DB can commit inbox and mutation atomically; external HTTP requires a remote idempotency/outcome contract. Prove effects once in a specified scope, not once-only delivery everywhere.

Why not scale consumers indefinitely? A3 chooses classic groups, six partitions and sequential handling, already filled by six owners. Internal concurrency needs contiguous commits and entity order. Inspect downstream budget and per-partition age; total lag averages can hide one hot partition.

Which comes first: breaker, limiter or bulkhead? Start with a deadline. A limiter constrains arrival rate, a bulkhead constrains real active work, and a breaker rejects unhealthy dependencies based on completed samples. Decorator order determines which rejections enter statistics; annotations do not replace the contract.

Does node self-healing solve it? It repairs processes and desired counts. Old nodes may still run, so authoritative data and remote effects retain deduplication and version checks. Capacity counts survivors until a replacement is Ready.
