先定交付语义Delivery semantics first

中文

设计 Kafka 风格日志，不是 Rabbit 五种 exchange，也不是弹性全书。三个 hard part：partition 与顺序、consumer group 再均衡、ISR / exactly-once / KRaft。顺序只在 partition 内。exactly-once 贵，白板默认 at-least-once 加 idempotency。协调面 2026 默认 KRaft。

上一章 Ch19 · 邻近服务 讲附近怎么查。这题换成事件怎么可靠传。第一问必须是范围：消费即删，还是留着可重放。接着只问保序到哪、留存多久、几个独立 consumer group、日消息的数量级。问过 10 分钟还在问，本身就是 red flag。五种 exchange、Flink 窗口、熔断重试，承认差别然后收口。积压在 Ch42 · 消息与弹性。和数据库同一事务走 Outbox，在 Ch41 · 复制与事务。

三种语义的 trade-off 要在画架构之前说完。at-most-once：先提交 offset 再处理，进程崩溃就丢。at-least-once：处理完再提交，崩溃会重放，消费者必须按业务键做 idempotency。exactly-once：幂等 producer 加事务，延迟和运维都贵，而且只在 Kafka 闭环里成立。写出外部库，事务覆盖不到。

我假设：分区日志，可重放，不是 Rabbit 手册。顺序按 message key 保 partition 内 FIFO。留存约 7 天。默认 at-least-once，消费者按业务键幂等。RF=3，acks=all，ISR。协调面 KRaft。方向不对你打断我。

English

Design a Kafka-style log, not Rabbit's five exchanges, and not a resilience encyclopedia. Three hard parts: partitions and ordering, consumer group rebalance, ISR / exactly-once / KRaft. Order is partition-local only. exactly-once is expensive. The whiteboard default is at-least-once plus idempotency. The 2026 control plane is KRaft.

The previous case, Ch19 · nearby, was how you query what is close. This prompt is how events travel reliably. The first question has to be scope: consume-and-delete, or a log you can replay. Then only ask how far order goes, how long you retain, how many independent consumer groups, and the daily order of magnitude. Still asking after 10 minutes is its own red flag. Five exchanges, Flink windows, circuit-breaker retries: name the difference and close it. Backlog is Ch42 · messaging and resilience. The same transaction as the database is Outbox, in Ch41 · replication and transactions.

Say the trade-off before you draw the architecture. at-most-once commits the offset, then processes: a crash drops the record. at-least-once processes, then commits: a crash replays, so the consumer needs idempotency on a business key. exactly-once is an idempotent producer plus transactions. It costs latency and ops, and it only holds inside the Kafka loop. An external database is outside that transaction.

I'll assume a partitioned log you can replay, not a Rabbit handbook. Order is FIFO inside a partition by message key. Retention is about 7 days. Default at-least-once, consumers idempotent on a business key. RF=3, acks=all, ISR. Control plane is KRaft. Stop me if that direction is wrong.

从左到右只画一条数据面：producer、broker 上的 append-only log、consumer。这张图不扇出 Schema Registry、Connect、Flink、五种 exchange，也不画多 Region。KRaft 管 topic、partition leader 和 ISR，不搬业务字节，所以先不画在数据面上。

English

Left to right, one data plane: producer, an append-only log on the broker, consumer. Do not fan out Schema Registry, Connect, Flink, five exchanges, or multi-region on this diagram. KRaft owns topics, partition leaders, and the ISR. It does not carry business bytes, so leave it off the data plane for now.

Write path: the client picks a partition by key, batches, and hits that partition's leader. The leader appends the WAL. After followers catch up and sit in the ISR, the high watermark moves, and acks=all is the only success. An event that must share a transaction with the database: write the Outbox, then produce. Do not make "write the row, then a naked send on the request thread" the only plan. CDC from the binlog into a topic is one sentence, not this chapter.

Read path: the consumer joins a consumer group, is assigned partitions, and pulls from the committed offset with a long poll. Process, then commit the offset. Consume does not delete the log. Retention drops old segments. Another group can replay from the start. Throughput is sequential write, batch, and pagecache, not "messages must live in memory." Why the log sits on disk is a glance at Ch37 · storage. Latency wants small batches. Log aggregation wants large ones. Do not teach zero-copy at this layer.

The producer hits the broker's partitioned log. The consumer pulls by group. Consistency with the database is Outbox. The control plane is KRaft. The data plane does not draw ZooKeeper. If this direction is fine, next is partition and order, then the replica, then offset, replay, and idempotency.

Hard part：partition 与顺序Hard part: partition and order

中文

第一个 hard part。并行单位是 partition，不是 topic，也不是整条总线一条 FIFO。2026 白板第一句：顺序只在 partition 内；同一个 key 哈希进同一个 partition。没有全局顺序。

topic 是逻辑流。每个 partition 是一条只追加的文件，切成 segment。位置是单调的 offset。没有 key 时，客户端把一批粘在某个 partition 上换吞吐，不保跨消息顺序。有 key：hash(key) % N，Kafka 默认 murmur2，同 key 同 partition，这个 key 的事件 FIFO。分片键用 user_id 或 order_id。随机 UUID 还承诺「这个用户的事件有序」，这句话不成立。

不要轻易改 N。N 一变，几乎所有 key 的路由都变，原来同区的顺序被拆开。Kafka 允许加 partition，不允许减。创建时预分够，多于近期 consumer 数。扩吞吐先加 consumer，不动 N。热 key，大用户或热 SKU，加多少 partition 也挤在一区。这是模型的 trade-off，不是再哈希一次就能消掉。全局 FIFO 等于单 partition，吞吐等于一台 leader，只有审计总账才考虑。组内两个 consumer 读同一个 partition，顺序必乱，所以一区同时只派给组里一个成员。这句话接到后面的 offset。

顺序跟着 key 进 partition。全局顺序就是单 partition，别随口答应。分区数预留够，别为了扩容改 N，把亲和打乱。

English

First hard part. The unit of parallelism is the partition, not the topic, and not one FIFO for the whole bus. The 2026 first sentence: order is partition-local only. The same key hashes to the same partition. There is no global order.

A topic is a logical stream. Each partition is one append-only file, cut into segments. The position is a monotonic offset. With no key, the client sticky-batches onto one partition for throughput, and order across messages is gone. With a key: hash(key) % N, murmur2 by default in Kafka. Same key, same partition, that key's events are FIFO. The key is a user_id or an order_id. A random UUID plus a promise that "this user's events are ordered" does not hold.

Do not change N lightly. When N changes, almost every key moves, and events that used to share a partition split. Kafka lets you add partitions, not shrink them. Pre-create enough, more than the near-term consumer count. Scale throughput by adding consumers first. Leave N alone. A hot key, a whale user or a hot SKU, still sits in one partition no matter how many you add. That is the model's trade-off. Another hash round does not erase it. Global FIFO is one partition, throughput equals one leader, and you only consider it for an audit ledger. Two consumers in a group reading one partition destroy order, so a partition is assigned to one member at a time. That sentence feeds the offset section.

Order follows the key into a partition. Global order is one partition. Do not promise it casually. Pre-partition enough. Do not change N to scale and smash affinity.

热 key 和改 N 是这题的 trade-off。复制的通用说法在 Ch41 · 复制与事务，下一套只开口 ISR。The hot key and changing N are the trade-off. General replication is Ch41 · replication and transactions. The next deck only opens the ISR.

Hard part：replica 与 ISRHard part: replica and ISR

中文

第二个 hard part 先讲副本，exactly-once 的贵留在下一套。每 partition 的 RF 常见是 3。producer 只写 leader，follower 来 fetch。ISR 是在 replica.lag.time.max.ms 里跟上的副本。acks=all 从 Kafka 3.0 起是默认，要等当前 ISR 都追加。consumer 只读到 high watermark，避免读到可能被截掉的脏尾。

min.insync.replicas=2：ISR 缩到 1 时，acks=all 拒写。用可用性换不丢。把它设成等于 RF，一台 follower 抖动，写入就停。leader 挂了只从 ISR 里选。unclean leader election 可能丢掉已经 ack 的数据，白板默认关掉。ELR 只说一句：ISR 里再筛一批可以安全当 leader 的副本，然后停。

acks=all 等 ISR。新 leader 只从 ISR 选。读停在 high watermark。为了绝对不丢把 min.insync 设成 RF，一台抖动就写不进去。

English

Second hard part starts at the replica. Why exactly-once is expensive waits for the next deck. RF per partition is commonly 3. The producer writes the leader only. Followers fetch. The ISR is the replicas that have caught up within replica.lag.time.max.ms. acks=all is the default since Kafka 3.0, and it waits for the current ISR to append. Consumers read only up to the high watermark, so they never see a dirty tail that might get truncated.

min.insync.replicas=2: when the ISR shrinks to 1, acks=all refuses the write. You trade availability for durability. Set it equal to RF and one jittery follower stops writes. If the leader dies, elect only from the ISR. Unclean leader election can lose data that was already acked, so the whiteboard default is off. ELR is one sentence: a safer-to-elect subset of the ISR, then stop.

acks=all waits for the ISR. A new leader comes only from the ISR. Reads stop at the high watermark. Setting min.insync equal to RF so you "never lose a byte" means one jittery follower refuses writes.

leader 挂了选谁，放在失败路径那一套。这里先把「怎样才算写成功」说清。Who becomes leader after a death is the failure deck. Here you only say when a write counts.

Hard part：offset、重放、幂等Hard part: offset, replay, idempotency

中文

第三个 hard part。consumer group 同时是点对点和发布订阅。同一组抢 partition，一条记录在组内只处理一次。不同组各有自己的 offset，同一条日志被独立重放。组内并行上限就是 partition 数。consumer 比 partition 多，多出来的空闲。

默认 pull。消费者自己控速，空日志用长轮询，不要空转打满 broker。offset 在处理后提交，就是 at-least-once，崩溃会重放。先提交再处理，就是 at-most-once。自动提交适合演示，处理失败时容易丢或重。面试说选手动提交。

幂等落在业务键上，用来接住 at-least-once 的重复。幂等 producer 用 PID 加分区序号，3.0 起默认打开，而且要求 acks=all。它只保证同一次会话、同一个 partition 不会因为重试双写。跨 partition、consume-process-produce、把 offset 和输出绑在一起，才要 transactional id 和 read_committed。这套端到端 exactly-once 只在 Kafka 里面。写出外部库，仍是业务 idempotency 或 Ch41 · 复制与事务 的 Outbox。

成员加入、离开、心跳超时，group coordinator 按 group id 重分配 partition。经典协议是 stop-the-world，全组暂停 fetch。2026 可以开口 cooperative，只挪受影响的 partition。Kafka 4.0 的新协议要客户端 opt-in，别说老客户端已经全部默认增量。Share group 是队列式抢单条，不是这张白板的默认。积压看 lag。同步 RPC 加无限重试会打出 retry 风暴，熔断和死信去 Ch42 · 消息与弹性，点到即停。

一组里一个 partition 一个 consumer，顺序才在。多组各自记 offset，才能重放。exactly-once 贵。实践默认 at-least-once 加消费侧 idempotency。

English

Third hard part. A consumer group is both point-to-point and pub-sub. Members of one group compete for partitions, so a record is processed once inside the group. Different groups each keep an offset, so the same log is replayed independently. In-group parallelism caps at the partition count. Consumers beyond that sit idle.

The default is pull. The consumer controls the rate. An empty log uses a long poll so you do not spin the broker. Commit the offset after processing and you have at-least-once: a crash replays. Commit first and you have at-most-once. Auto-commit is fine for a demo and easy to drop or duplicate when processing fails. Say you prefer a manual commit.

Idempotency sits on a business key, so the at-least-once duplicate is safe. An idempotent producer, PID plus a per-partition sequence, is on by default since 3.0 and it requires acks=all. It only stops a retry from double-writing in the same session and the same partition. Cross-partition work, consume-process-produce, tying the offset to the output: that needs a transactional id and read_committed. End-to-end exactly-once stays inside Kafka. An external database still needs business idempotency, or the Outbox in Ch41 · replication and transactions.

A member joins, leaves, or misses heartbeats, and the group coordinator, a broker found by group id, reassigns partitions. The classic protocol is stop-the-world: the whole group pauses fetch. The 2026 opening is cooperative: only the affected partitions move. Kafka 4.0's newer protocol is a client opt-in. Do not pretend every old client already defaults to incremental. A share group steals single records like a queue. It is not this board's default. Backlog is lag. Sync RPC plus unbounded retries is a retry storm. Circuit breakers and a dead-letter queue are Ch42 · messaging and resilience. Mention them and stop.

One consumer per partition in the group is what keeps order. Multiple groups each store an offset, which is how you replay. exactly-once is expensive. The practice default is at-least-once plus idempotency on the consumer.

积压和 retry 风暴去 Ch42 · 消息与弹性。本场停在 offset 和 idempotency。Backlog and retry storms go to Ch42 · messaging and resilience. This loop stops at offset and idempotency.

失败路径Failure path

中文

失败不要画回成功路径上。四件事先分开说：leader 挂了、unclean 选举、再均衡把整组停住、协调面还画着 ZooKeeper。

leader 挂了，只从 ISR 里选，已经越过 high watermark 的记录还在。打开 unclean，可能把没跟上的副本抬成 leader，已经 ack 的数据会没。ISR 缩到 min.insync 以下时拒写，这是上一套的 trade-off，失败时把它说成「现在写不进去」，不要改成静默丢。

再均衡的经典协议会 stop-the-world。大组、滚动发布，fetch 暂停，lag 涨。2026 开口只挪受影响的 partition，而且客户端要 opt-in。消费者里同步调用加无限重试，会在恢复之后打出风暴，熔断和死信留在 Ch42 · 消息与弹性。

协调面：控制器用 Raft 写集群元数据，broker 拉增量。生产常见 3 或 5 个专职 controller，不要和重磁盘的 broker 混部当第一答案。Kafka 4.0 起不再提供 ZooKeeper 模式。3.x 还在 ZK 上，必须先迁 KRaft 再上 4.x。原书全程 ZK，放在折叠里。

leader 挂了只从 ISR 选，unclean 默认关。再均衡经典会停消费。控制面是 KRaft，不画 ZooKeeper。

English

Do not draw failures back onto the happy path. Four cases, separate: the leader dies, unclean election, rebalance pausing the whole group, and a control plane that still shows ZooKeeper.

When the leader dies, elect only from the ISR. Records past the high watermark stay. Turn unclean election on and a replica that had not caught up can become leader. Data that was already acked can disappear. When the ISR falls below min.insync, the write is refused. That trade-off was the previous deck. On the failure path, say "writes stop now." Do not turn it into a silent drop.

Classic rebalance is stop-the-world. A large group or a rolling deploy pauses fetch and lag grows. The 2026 opening moves only the affected partitions, and the client has to opt in. A sync call plus unbounded retries inside the consumer becomes a storm after recovery. Circuit breakers and a dead-letter queue stay in Ch42 · messaging and resilience.

Control plane: the controller quorum writes cluster metadata with Raft, and brokers pull the delta. Production commonly runs 3 or 5 dedicated controllers. Do not colocate them with heavy-disk brokers as the first answer. Kafka 4.0 no longer ships ZooKeeper mode. A 3.x cluster still on ZK has to move to KRaft before 4.x. The book's all-ZK path goes in the fold.

If the leader dies, elect only from the ISR. Unclean stays off. Classic rebalance stops consume. The control plane is KRaft. Do not draw ZooKeeper.

弹性全书在 Ch42 · 消息与弹性。和库一起提交仍是 Ch41 · 复制与事务 的 Outbox。The resilience encyclopedia is Ch42 · messaging and resilience. Committing with the database is still the Outbox in Ch41 · replication and transactions.
