设计搜索系统Design a search system

约 40 分钟 · 前置：Ch02、Ch03、Ch08 · 用 6 组图串起查询、更新与故障处理~40 min · after Ch02, Ch03, Ch08 · 6 decks: a query, updates and failures

本章要点：先说清一页结果提供什么保证Core: define what a page promises

  • 读：搜索 API 先检查旁路缓存；未命中时，协调器（Coordinator）从每个逻辑分片选一份副本，取得各片排名前 k 的候选（top-k），全局合并后再获取入选文档（fetch）。
  • 写：业务库提交变更后，变更数据捕获（CDC）异步更新索引；单调递增的版本与持久保存的逻辑墓碑阻止旧更新覆盖新状态，refresh 决定这些变更何时对搜索可见。
  • 连续读：时间点快照（PIT）固定本次翻页的索引视图，游标绑定查询、排序和扫描进度；缺少必要分片时整页失败，权威过滤后的短页仍要能继续向后扫描。
  • Read: API checks a look-aside cache; one copy per logical shard returns local top-k for global merge and fetch.
  • Write: CDC follows the authoritative commit; monotonic versions and retained logical tombstones reject stale updates, while refresh controls search visibility.
  • Continue: PIT pins the view; the cursor binds query, order and scan progress. Missing shards fail; filtered short pages must still advance.

I will design lexical search over an existing public knowledge base in one region: 100M documents and a planned 10K peak searches/s. Start with API → Coordinator → document shards, then add look-aside caching. The write side derives its index from the business log. I will focus on versioned deletion, shard merging and PIT pagination. Autocomplete has its own prefix top-k endpoint and keyboard traffic budget.

Clarify corpus/languages, phrases and filters, relevance, freshness, page jumps and suggestions. Semantic retrieval needs a separate vector-index budget. If prices, deletion or private access must reflect authority, validate before returning cached and PIT hits too; fail when validation is unavailable. Responses already in flight after that check cannot be recalled.

先算三个数：多少请求回源，每片承受多少，故障后还剩多少容量Three numbers first: origin traffic, per-shard load and failure headroom

本例先作以下假设：1,000 万 DAU × 每人每天 8 次搜索读取 ÷ 86,400 ≈ 925.9 QPS；峰值按平均值的 10 倍计算，约为 9,259 QPS，容量向上取到 10,000/s。只缓存首屏，假设它能让全部搜索读取中的 60% 命中缓存，就剩下 4,000/s 需要回源查询索引。每次普通查询都搜索四个文档分片，因此整层每秒处理 16,000 个分片任务，每片仍是每秒 4,000 个。

每片保存三份数据，包含主分片；假设每份的可用查询预算为每秒 2,000 次。正常时各份分担 4,000÷3≈1,333 次/秒；一份故障后，剩余两份各处理 2,000 次/秒，恰好满足预算。如果缓存命中率降至 40%，不限流时每片就会收到 6,000 次/秒；再坏一份，剩余各份要处理 3,000 次/秒，已经超过预算。因此先把回源量限制在每秒 4,000 次，再考虑增加副本或降低查询成本。增加文档分片，并不会自动把每片收到的请求率减半。

正文容量为 1 亿 × 2,000 B=200 GB；倒排索引暂按正文的 1 倍估算，也是 200 GB。分成四片后，每片约 50 GB；各保存三份，共需 600 GB 倒排索引空间。这里都用十进制单位，尚未计入正文副本、段合并临时空间、日志和备份。四片和单份每秒 2,000 次的预算，都要用有代表性的语料与负载验证；50 GB 也不是通用的最优分片大小。

Teaching assumptions: 10M DAU × 8 search reads/day / 86,400 ≈ 925.9 QPS; a 10× peak is ≈9,259, rounded up to 10,000/s. Shared first-page cache is assumed to contribute 60% hits across all reads, leaving 4,000/s at origin. Four document shards mean 16,000 aggregate shard tasks/s, still 4,000/s per shard.

Each shard has three copies including primary, each assumed to serve a usable 2,000/s: normally 4,000/3≈1,333, and after one copy loss each survivor handles 2,000. At 40% cache hits, each shard gets 6,000/s and survivors get 3,000 after a loss, exceeding the budget. Cap origin at 4K, then add copies or reduce query cost; more document shards do not automatically halve per-shard request rate.

100M × 2,000 B=200 GB text. An assumed 1× index adds 200 GB, 50 GB per shard or 600 GB with three copies. Units are decimal; stored-body copies, temporary merge space, logs and backups are extra. Four shards and 2K/s require representative load measurements; 50 GB is not a universal optimum.

一次搜索怎样完成：把缓存放在旁路One search loop: keep cache look-aside

缓存减少索引查询，响应数据仍要发送Caching saves index work, not response bytes

搜索 API 先校验查询文本的长度和允许使用的字段，再按产品语义规范化，随后查缓存。未命中时，API 调用 Coordinator；各片返回候选，协调器全局合并后，只获取最终入选文档的标题和摘要，组成一页结果，经 API 返回客户端。缓存本身不查询索引。完整的缓存键包含查询文本（query）、语言、过滤、排序、分页参数，以及分析器与索引世代；私有数据场景还要绑定租户和权限范围。规范化必须保留原意，例如不能随意删掉 C++ 中的加号。

每页 20 KB 时，API 整层要发送 10K×20 KB=200 MB/s；其中缓存约提供 120 MB/s，Coordinator 约提供 80 MB/s，内部候选传输另计。60% 的整体命中率仍是待测目标，后续 PIT 页不进入共享首屏缓存。如果缓存出错率为 0.1%，约每秒 10 次额外请求可能在预算内绕过缓存；整层宕机时，却是每秒 1 万次全部要求回源，达到 4,000 次预算的 2.5 倍。即使合并了相同热门查询的并发未命中请求，仍要执行全局回源准入，并限制队列长度；超额的约 6,000 次/秒返回 429 或 503。

回填沿用查询开始时确定的截止时间。每次查询开始时捕获配置 g，固定使用 g 指定的具体索引、分析规则和缓存键。发布新配置只切换一份配置指针，旧请求仍写入旧键，因此不要求索引别名与独立缓存参加跨系统事务。只有整页成功才回填，并设置 not_after=query_started_at+30s；迟到回填不得重算期限，读取方也要检查这个时间。跨节点使用墙钟时，需要约定时钟误差并保守扣除；偏差未知时，就不能声称严格满足 33 秒上界。缓存故障时，默认拒绝超额流量，也不能假定不可用的缓存还能提供旧页。

API validates query length and fields, normalizes by product semantics, then checks cache. On a miss it calls Coordinator; shards return candidates, global merge chooses winners, and fetch retrieves their titles and snippets. The complete page returns through API. Cache does not query the index. Keys bind query, language, filters, sort, page parameters and analyzer/index generation, plus tenant and authorization scope for private data. Do not casually remove the plus signs in C++.

At 20 KB/page the API returns 10K×20 KB=200 MB/s; cache supplies about 120 MB/s and Coordinator about 80 MB/s, excluding internal candidates. The 60% hit goal needs measurement; PIT continuation pages bypass shared first-page cache. A 0.1% cache error rate is about 10/s, but full cache loss sends all 10K/s to origin, 2.5× its 4K budget. Coalesce hot-key misses, then enforce global admission and a bounded queue, rejecting roughly 6K/s overflow with 429/503.

Fills inherit absolute age. Capture configuration g when the query starts and use its concrete index, analysis and cache key. Publication swaps one configuration pointer; old requests still write old keys, without claiming a transaction across aliases and a separate cache. Fill only successful pages with not_after=query_started_at+30s; delayed writes never reset expiry, and readers also check it. Cross-node wall clocks need a known error allowance; unknown skew invalidates a strict 33-second bound. Cache failure sheds overflow rather than assuming an unavailable cache can supply stale pages.

倒排与 BM25：候选怎样产生，分数怎样解释Postings and BM25: where candidates and scores come from

先看候选怎样产生。倒排索引根据词项（term）找到有序文档列表（posting），正排查询则根据文档 ID（doc_id）找到正文。对于 docker=[2,5,9]、guide=[5,9,12]，AND 得到 [5,9]，OR 得到 [2,5,9,12]。双指针每一步至少前进一个位置，因此最多扫描 x+y 个位置；多词求交时先处理短列表。短语查询还需要词项位置，不能因为 new 与 york 都出现，就认定它们相邻。[1] 主搜索的索引分析规则和查询分析规则应兼容；前缀 edge n-gram 是查询侧可以使用不同规则的例外。[2]

再看候选怎样排序。BM25 综合考虑词项稀有度、词频饱和与长度归一化。本章固定使用 Lucene 9.12.1，其默认参数为 k1=1.2、b=0.75。[3] 当文档长度等于平均长度时，教科书公式中的 TF 因子为 tf×2.2/(tf+1.2)：tf=1 时是 1，tf=3 时是 6.6/4.2≈1.57。这个演算用来说明词频增益会趋于饱和，并不等于 Lucene 的原始分数。字段权重、同义词和拼写处理都要用带相关性标签的样本评估；点击数据有位置偏差，不能直接当作无偏的相关性判断。

最后区分分片统计与全局统计。普通查询模式 query_then_fetch 使用各分片本地的词项统计；dfs_query_then_fetch 则多执行一轮，先取得全局统计。[6] 下一节的 top-k 证明，是在已经约定的同一总序下选出前 k 条。本地统计产生的分数可以按数值合并，但所得排名不等于对整个语料统一计算 BM25 的排名。如果不同分片的租户或语言分布差异很大，就要评估是否需要全局统计；局部分数更高，并不能天然说明它在全局更相关。

Retrieve: an inverted index maps terms to sorted postings; forward lookup maps doc IDs to bodies. docker=[2,5,9] and guide=[5,9,12] give AND=[5,9] and OR=[2,5,9,12]. Each two-pointer step advances at least one position, bounding scans by x+y; intersect shorter lists first. Phrases require positions: merely containing both new and york does not prove adjacency. [1] Main index/search analysis must be compatible; prefix edge n-grams are an exception that may use different query analysis. [2]

Rank: BM25 combines term rarity, saturating frequency and length normalization. Lucene 9.12.1 defaults are k1=1.2 and b=0.75. [3] At average document length, the textbook TF factor is tf×2.2/(tf+1.2): 1 at tf=1 and 6.6/4.2≈1.57 at tf=3. This illustrates relative saturation, not a raw Lucene score. Evaluate field weights, synonyms and spelling with labeled relevance samples; clicks have position bias.

Shard statistics: query_then_fetch uses local term statistics, whereas dfs_query_then_fetch adds a round for global statistics. [6] The next proof selects top-k under one declared total order. Locally derived scores can still be numerically merged, but that is not the ranking of a single corpus-wide BM25 model. Evaluate global statistics when shard populations differ strongly by tenant or language; a higher local score does not inherently mean greater global relevance.

文档分片：怎样合并结果，缺少一片怎么办Document shards: prove the merge, then define missing-shard behavior

系统按文档 ID 分片（hash(doc_id)），让一篇文档及其词项落在同一片。普通查询没有指定 doc_id，因此要搜索所有可能命中的分片。每个逻辑分片只选一份副本执行，同片的三份数据不算三个独立语料库。图中画两片，容量仍按四片计算；查询阶段返回候选，取回阶段只获取最终入选文档。[6]

为什么各片只返回 top-20 就够？假设全局前二十中有一条不在所属分片的前二十，那么同片至少已有二十条排在它前面，它就不可能进入全局前二十，形成矛盾。这个结论要求各片使用同一视图、过滤条件和总序，且文档不在片间重复。先取 top-20 再做权威过滤，则不保证最后仍能返回二十条。四片每轮最多返回 80 个候选元组，按每个 32 B 计算，是 2,560 B≈2.56 KB，正文另行取回。下面是 Java 17 教学节选，只负责结果合并；RPC、BM25、PIT 和分布式一致性由其他部分提供。可查阅完整可运行源码及编译/运行命令。

hash(doc_id) places a document and its terms on one shard. Without a doc ID, queries search every potentially matching shard. Select one serving copy per logical shard; three replicas are not three corpora. The diagram draws two shards, but capacity uses four. Query returns candidates; fetch retrieves winners. [6]

Why is local top-20 enough? If a global top-20 hit were outside its local top-20, at least twenty same-shard hits would precede it, a contradiction. This assumes the same view, filters and total order with disjoint document ownership; top-20 before an authority filter need not fill twenty results afterward. One four-shard round returns at most 80 tuples, 32 B each=2,560 B≈2.56 KB, excluding bodies. The Java 17 teaching excerpt below performs pure merging; it implements neither RPC, BM25, PIT nor distributed consistency. See the complete runnable source and compile/run commands.

  public record Hit(String id, double score, long tie) {}
  public record Reply(String shard, boolean ok, List<Hit> hits) {}
  public record Merged(List<Hit> hits, Set<String> missing) {
    public boolean complete() { return missing.isEmpty(); }
  }
  private static final Comparator<Hit> ORDER = Comparator
      .comparingDouble(Hit::score).reversed().thenComparingLong(Hit::tie);

  // Adapter supplies exact local top-k under the same view, filter and order.
  public static Merged merge(Set<String> expected, List<Reply> replies,
                             int k, boolean allowPartial) {
    if (k < 1 || expected.isEmpty()) throw new IllegalArgumentException("bounds");
    var seen = new HashSet<String>(); var ids = new HashSet<String>();
    var ties = new HashSet<Long>(); var good = new HashSet<String>();
    var candidates = new ArrayList<Hit>();
    for (Reply r : replies) {
      if (!expected.contains(r.shard()) || !seen.add(r.shard()))
        throw new IllegalArgumentException("unexpected/duplicate logical shard");
      if (!r.ok()) continue;                // timed-out hits cannot count
      if (r.hits().size() > k) throw new IllegalArgumentException("local limit");
      for (int i = 0; i < r.hits().size(); i++) {
        Hit h = r.hits().get(i);
        if (!Double.isFinite(h.score()) || !ids.add(h.id()) || !ties.add(h.tie()))
          throw new IllegalArgumentException("invalid/duplicate candidate");
        if (i > 0 && ORDER.compare(r.hits().get(i - 1), h) > 0)
          throw new IllegalArgumentException("unsorted local result");
        candidates.add(h);
      }
      good.add(r.shard());
    }
    var missing = new HashSet<>(expected); missing.removeAll(good);
    if (!allowPartial && !missing.isEmpty())
      throw new IllegalStateException("incomplete: " + missing);
    candidates.sort(ORDER);
    return new Merged(List.copyOf(candidates.subList(0, Math.min(k, candidates.size()))),
                      Set.copyOf(missing));
  }

示例用 Reply.ok 表示该逻辑分片按时返回了完整的查询候选；合并后，只要任一必需文档取回失败，外层仍要丢弃整页结果和游标。适配器负责提供按同一总序排列的局部 top-k；PIT 会话中的同分排序键 tie 对应唯一的 _shard_doc。完整模式拒绝缺片；演示参数 allowPartial=true 只允许返回标明缺片列表 missing 的近似首屏，不能将它写入完整结果缓存，也不能签发续页游标。生产实现可以用 k 路堆合并；这里最多只有 80 个候选，直接排序更容易看清保证。

一次请求共用 200 ms 总期限，覆盖排队、查询、正文取回、校验和次数受限的副本重试。A 故障时只重试 A，B 无需重做；如果查询计算本身过于昂贵，换副本可能只是额外增加一份负载。假设每片按时响应的概率均为 99%，且相互独立，四片全到齐的概率为 0.99⁴≈96.06%；这个例子只用于说明尾延迟会被放大。缺片、超时或正文取回错误，默认都让整页返回 503；真正的零命中必须由全部必要分片确认。因此要检查 timed_out 和失败分片，不能只看 HTTP 200。[6]

Reply.ok covers timely, complete query candidates for that logical shard. Any required fetch failure after merging still discards the whole page/cursor in the outer response path. Adapters supply local top-k under the common order; a PIT session uses unique _shard_doc ties. Complete mode rejects missing shards. Demonstration option allowPartial=true returns an explicitly marked approximate first page with missing IDs, never a complete-cache entry or continuation cursor. A production k-way heap is possible; sorting at most 80 tuples keeps the guarantee visible here.

One 200 ms deadline covers queues, query, fetch, checks and a bounded replica retry. Retry A only while B continues; intrinsically expensive computation may just run twice. Assuming independent 99% timely responses per shard gives 0.99⁴≈96.06% for all four, illustrating tail amplification only. Missing shards, timeouts or fetch errors default to whole-page 503, not zero hits; a complete zero-hit result needs every required shard. Check timed_out and failed shards rather than HTTP 200 alone. [6]

更新链：在同一次索引操作中比较版本并替换文档Ingestion: version comparison and replacement share one index operation

业务库在同一事务中提交文档或删除状态、单调递增的版本，以及可重放事件，CDC 随后消费已提交日志；业务接口的 201 只确认这次业务提交。事件携带不复用的文档 ID（doc_id）、业务版本（version）、操作类型和完整文档快照。同一 (doc_id,version) 必须对应唯一的规范化摘要；消费端不能把乱序增量补丁直接应用到索引。版本由源库行版本或 CAS 可靠递增，不使用墙钟时间戳代替。

删除也通过带版本的 INDEX 写入。请求固定指向一个具体索引世代，以 version_type=external 在同一次索引操作中比较版本并完整替换该 ID；只有更大版本才能写入。[7] 删除 v13 时写入 {deleted:true, source_digest:…}，不保留旧正文；所有查询都强制加入 deleted=false。这条逻辑记录会保留删除版本，而物理 DELETE 的版本元数据会被 index.gc_deletes 清理，无法阻止任意迟到的重放。[9] 保留逻辑删除状态，也不代表旧段或快照中的正文已经立即从物理介质擦除。

The business database co-commits document/deletion state, a monotonic version and a replayable event. CDC consumes committed records; 201 acknowledges only the business commit. Events carry a non-reused doc ID, version, operation and full document snapshot. Each (doc_id,version) has one canonical digest; unordered delta patches are unsafe. Source-row versions/CAS provide increments, not wall-clock timestamps.

Index a versioned deletion record too. Target a concrete generation and use version_type=external for the atomic version comparison plus full replacement of that ID; only a greater version wins. [7] Deletion v13 stores {deleted:true, source_digest:…} without old content; every query forces deleted=false. This retained logical document keeps its version, whereas physical DELETE metadata is cleaned according to index.gc_deletes and cannot block arbitrarily late replay. [9] This does not immediately erase historical bytes in old segments or snapshots.

# Pseudocode: full immutable source events; concrete index generation g.
apply(event, g):
  require event.version > 0 and canonical_digest(event) == event.digest
  body = {source_digest: event.digest, deleted: event.op == DELETE}
  if not body.deleted: body.fields = analyze(event.full_document, g.analyzer)
  # DELETE is also an INDEX of this same ID, with no old content retained.
  result = ES.index(g.index, event.doc_id, body,
                    version=event.version, version_type="external")
  if result.transport_unknown or result.retryable_error:
    return RETRY_SAME_EVENT                 # applied state may already exist
  if result.status == 409:
    current = ES.get(g.index, event.doc_id, realtime=true)
    if current.unavailable: return RETRY_SAME_EVENT
    if not current.found or current.version < event.version:
      return STOP_PARTITION_AND_ALERT       # violated retained-state contract
    if current.version == event.version and current.source_digest != event.digest:
      return STOP_PARTITION_AND_ALERT       # one version, two different events
    return ACKABLE                         # identical replay or superseded
  if not result.success:
    return STOP_PARTITION_AND_ALERT         # mapping/auth errors are not ACKs
  return ACKABLE

consume_source_partition(events, g):
  for event in events:                      # per-partition sequential example
    while true:
      decision = apply(event, g)
      if decision == ACKABLE: break
      if decision == STOP_PARTITION_AND_ALERT: halt_without_committing()
      bounded_backoff()                     # retry the same event, not the next
    commit_source_offset(event.offset)      # after confirmed durable apply only
  # Lost checkpoint => safe replay. Never skip a failed offset.
  # Do not physically delete tombstones; rebuild g with retained versions too.

这里的原子保证由 ES 对单个 ID 的 external 版本写入提供，不能靠 worker 本地锁，也不能先读版本再无条件写入。遇到 409 后，worker 用 realtime GET 读取当前记录：版本更大，说明本事件已被更新版本覆盖；版本相等且摘要一致，才确认是同一事件的重放；版本相等但载荷不同，则停止源分区并告警。读不到应保留的记录、读到更小版本，也说明前提被破坏，需要停分区；读取结果不明确时则重试，不跳过事件。[7][10] 网络超时只表示写入结果未知，因此仍重试同一事件。永久映射错误或鉴权错误不能当作成功确认。示例按源分区顺序提交消费检查点（checkpoint）；并发处理时，也只能推进到已经确认成功的连续前缀。

CDC 传递、索引应用和 refresh 的正常目标各为 1 秒，索引约 3 秒可见；再加首屏最多 30 秒的绝对年龄，就得到约 33 秒的健康新鲜度预算。积压或时钟偏差未知时，这个上界不成立。refresh 打开新的搜索读取视图，与业务提交、索引写入确认是不同步骤；逐条强制刷新也不能解决消费积压。[5] 应监控最老事件年龄、可搜索水位、重试和死信。每秒 200 次变更积压十分钟，会产生 120,000 个事件；恢复后每秒处理 600 个，扣除每秒 200 个新事件，净追赶速率为 400 个/秒，理想情况下需要 300 秒追平。

如果删除或撤权必须以权威状态为准，缓存命中和旧 PIT 的结果也要在返回前读取权威状态；无法完成校验时拒绝请求。这个约定只反映校验时已经提交的禁止状态，不能撤回在途响应。版本墓碑防止索引被旧事件恢复，权威校验防止旧视图展示已禁止内容，两者各有作用。如果要求删除提交后，连已经获准但尚未发出的响应也停止，还需要额外协调许可与发送，并明确已经在途的响应边界。

The atomic boundary is ES external-version indexing for one ID, not a local worker lock or a read followed by an unconditional write. After 409, realtime GET distinguishes a higher superseding version from equal-version replay; equal version with a different digest stops the source partition and alerts. An inconclusive read retries without skipping. [7][10] A network timeout means unknown outcome: retry the same event. Permanent mapping/auth failures are not ACKs. This sequential source-partition example commits each checkpoint after confirmed apply; parallel processing may commit only the contiguous successful prefix.

Healthy targets of one second each for CDC, apply and refresh yield about three seconds, plus thirty seconds of absolute first-page age for a healthy budget of roughly 33 seconds. It is no guarantee during backlog or unknown clock skew. Refresh opens the search reader; it differs from business commit and index-write acknowledgement. Refreshing every write does not cure backlog. [5] Monitor oldest-event age, searchable watermarks, retries and dead letters. At 200 changes/s a ten-minute pause builds 120,000 events; recovery at 600/s minus 200/s arrivals drains at 400/s, ideally taking 300 seconds.

Deletion/access checks cover cached and old-PIT hits and fail closed when unavailable. The promise reflects prohibited state committed before the check; it cannot recall an in-flight response. Version tombstones prevent index resurrection, while authority checks prevent stale-view display. A stronger rule stopping already-admitted but unsent responses after deletion needs additional coordination and an explicit in-flight boundary.

重建索引时怎样保留删除版本，何时才可能回收墓碑Rebuild and tombstone reclamation boundaries

重建时先记录一致快照对应的日志水位，将仍存活的文档和保留的删除版本一起载入新世代，再重放该水位之后的变更。追平日志并校验后，才发布新的配置指针。旧世代的在途请求和 PIT 仍按各自期限结束；新请求使用新的具体索引和缓存命名空间。只扫描存活记录会丢失墓碑；扫描后不追日志，则会遗漏扫描期间发生的删除。

本例不物理回收墓碑，也不复用文档 ID。如果要回收，必须证明所有日志重放、最老快照、重试和离线任务都已越过删除版本；或者让另一份持久版本账本在索引写入的原子路径上拒绝旧版本。仅规定“保留几分钟”，不能完成这个证明。整个索引丢失时，需要从源快照和日志重建；本例没有实验验证副本切主与全盘故障的行为。

Record a consistent snapshot watermark, load live documents and retained deletion versions into the new generation, replay later events, catch up and validate, then publish the configuration pointer. In-flight old-generation requests/PITs keep their own lifetimes; new requests use a new concrete index and cache namespace. Scanning only live rows loses tombstones; scanning without log replay loses concurrent deletions.

This example never physically reclaims tombstones or reuses IDs. Reclamation requires proof that all log replays, oldest snapshots, retries and offline work have crossed the deletion version, or another durable version ledger enforcing rejection in the atomic index path. A short arbitrary retention period proves none of this. Total index loss requires reconstruction from source snapshots/logs; replica failover and disk-loss behavior were not experimentally verified.

PIT 分页：游标记录最后扫描的位置PIT pagination: the cursor records the last scanned position

当 from=10,000,size=20 时，四片最多保留 4×10,020=40,080 个候选；按每个 32 B 计算，是 1,282,560 B≈1.28 MB。一轮游标查询最多保留 80 个候选，约 2.56 KB，两者相差 501 倍；这不是倒排列表扫描量的对比。该请求超过 Elastic 默认的 10,000 结果窗口，应拒绝它，或改用 PIT+search_after；扩大窗口并不能消除查询成本。[4]

PIT 固定搜索读取视图，排序规则 _score desc,_shard_doc asc 则在该 PIT 内提供确定的总序。翻页期间保持查询、过滤和排序不变，每次沿用最新 PIT ID 以及锚点的全部 sort 值。[4][11] 游标由服务端认证保护，还要绑定访问主体、租户、权限范围版本、页大小和期限；查询或权限上下文改变时，必须重新开始。打开 PIT 和每轮搜索都拒绝缺片，即使 HTTP 状态是 200，也要检查超时与失败分片。PIT 丢失或过期时，本章产品接口返回 410，不能偷偷切到新视图。

With from=10,000,size=20, four shards retain up to 4×10,020=40,080 candidates. At 32 B each that is 1,282,560 B≈1.28 MB. Versus one cursor round of 80/2.56 KB, retained candidates grow 501×; this is not a posting-scan estimate. The request exceeds Elastic’s default 10,000 result window, so reject or switch to PIT+search_after. Raising the window does not remove the cost. [4]

PIT pins the reader; _score desc,_shard_doc asc supplies a total order inside it. Keep query/filters/sort fixed and carry the latest PIT ID plus all sort values. [4][11] A server-authenticated token also binds subject, tenant, authorization-scope version, page size and expiry; changed query/access context restarts the session. Reject missing shards both when opening PIT and on each search, checking timeout/failure even on HTTP 200. A missing/expired PIT maps to this product’s 410 restart contract, never a silent new view.

# Pseudocode: one 200 ms request deadline; no shared cache for PIT sessions.
page(request, auth):
  deadline = monotonic_now() + 200ms
  require 1 <= request.limit <= 20           # malformed => 400
  ctx = canonical(request.query, request.filters + deleted_false, FIXED_SORT,
                  request.limit, auth.tenant, auth.subject, auth.scope_version)
  if request.cursor:
    c = authenticated_open(request.cursor)   # forged => 400; expired => 410
    require c.context_hash == hash(ctx)      # changed context => 400 restart
    pit, after = c.latest_pit_id, c.last_scanned_sort
  else:
    pit = open_complete_pit(ctx, keep_alive=60s, deadline=deadline)
    after = NONE                            # open must reject missing shards
  out, scanned, exhausted = [], 0, false
  while len(out) < request.limit and scanned < 100 and not exhausted:
    n = min(request.limit - len(out), 100 - scanned)
    pit_expiry = now() + 60s                 # conservative renewal start
    r = search(pit, ctx, after, size=n, keep_alive=60s, deadline=deadline,
               allow_partial_search_results=false)
    if r.pit_missing: fail(410, "restart")  # never silently open a new PIT
    if r.failed or r.timed_out or not r.all_required_shards:
      fail(503, "incomplete")                # discard buffered hits and cursor
    pit = r.latest_pit_id
    for hit in r.hits:                       # ordered, fetched from the PIT
      after = hit.all_sort_values           # advance even when access is denied
      scanned += 1
      decision = authority_check(hit.doc_id, auth, deadline)
      if decision.unavailable: fail(503, "authority unavailable")
      if decision.allowed_and_live: out.append(hit)
    exhausted = len(r.hits) < n
  if deadline_expired(deadline): fail(503, "deadline")
  cursor = NONE if exhausted else authenticated_seal(
      hash(ctx), pit, after, expires_at=pit_expiry)
  if exhausted: close_pit_best_effort(pit)
  return {hits: out, cursor: cursor, complete: true,
          truncated: scanned == 100 and len(out) < request.limit and not exhausted}

候选全部被过滤，扫描进度仍要向前。如果前二十个旧候选已经全部删除，用“最后返回的文档”作锚点就会停在原地。因此每扫描一个候选，先更新扫描位置 after，再做权威校验；需要补取时，仍受原来的 200 ms 期限和每页最多扫描 100 个候选的限制，后者是教学设定。如果只是扫描数量预算耗尽，可以返回短页甚至空页，同时带上 truncated=true 和已经前移的游标。这里的 complete=true 只表示必要分片齐全；truncated 表示扫描预算用尽，不代表已经穷尽所有合规命中，也不属于缺片导致的 partial。只有实际扫描到快照末尾，才不再返回游标；最后一页刚好填满时，下一次请求返回空的末页也合法。

图中的 80 个候选是一轮查询的上界，补取会增加轮次和总工作量；search_after 并不保证只扫描二十个倒排项。权威校验（authority_check）读取当前删除和权限状态，校验超时就丢弃已经缓冲的结果，不返回成功游标；正文取回意外失败，也让整页失败。这段伪代码依赖适配器提供 PIT、预算、完整性检查与权威读取，并不是可以直接运行的搜索服务。

60 秒是本章选择的空闲续期时间；令牌期限从最后一轮查询开始时保守计算，服务端如果提前丢失 PIT，仍可能更早要求重新搜索。应限制并发 PIT 数量和总寿命，读完主动关闭。保留旧段、跟踪删除状态都会占用磁盘、文件句柄和堆内存；固定排序视图不会冻结用户权限。[11]

Even a fully filtered page must advance. If the first twenty old hits are now deleted, using the last returned document leaves the cursor stuck. Advance after on every examined candidate before authority checks; refill within the original 200 ms deadline and at most 100 scanned hits/page, a teaching cap. Budget exhaustion may return a short or empty page with truncated=true and an advanced cursor. Here complete=true means shard completeness, while truncated means scan-budget exhaustion, without claiming all eligible hits were exhausted. It is not a missing-shard partial result. Only snapshot exhaustion removes the cursor; a full last page may legitimately be followed by an empty terminal request.

The diagram’s 80-candidate bound is per query round; refills add rounds and work, and search_after does not guarantee twenty posting scans. authority_check reads authoritative deletion/access state. Its timeout discards buffered hits and withholds a successful cursor; unexpected fetch failures fail the whole page too. Adapters implement PIT, budgets, completeness and authority reads. This pseudocode is not a directly runnable search service.

Sixty seconds is our idle-renewal policy. Compute token expiry conservatively from the final search round’s start; actual PIT loss may require earlier restart. Bound concurrency/total lifetime and close finished PITs. Old segments and deletion tracking consume disk, handles and heap. Stable order never freezes permissions. [11]

自动补全：单独规划容量，客户端丢弃过时响应Autocomplete: separate capacity and reject stale client replies

自动补全返回建议查询词，主搜索返回文档页。本例设置 250 ms 输入防抖、前缀长度 2–32 个字符，并保守按每次搜索读取产生四个补全请求规划，因此峰值为 10K×4=40K/s。四次来自用户行为假设，并不是 250 ms 的倒数。Suggest API 与 Search API 可以先部署在同一进程，但需要独立的线程池、限流额度和缓存预算。客户端每次输入变化，都递增输入序号 seq 并清空旧建议。取消旧请求只能减少工作，丢弃 seq 与当前输入序号不一致的响应，才能防止旧结果覆盖新结果。补全失败时，用户仍可按回车执行搜索。

Trie 先沿前缀走过 m 个字符，再复制 k 个建议 ID，复杂度为 O(m+k)，字符串字节的复制另计。200 万节点×5×8 B=80 MB 也只计算 ID 数组。图中的 root→d→do 表示依次走过字符 d 和 o，并非用一条边读取两个字符 do。Lucene 9.12.1 的 FSTCompletion 可以作为压缩替代，但它用离散权重桶排序，并不保证精确按热度排列。[8]

用户提交完整查询后，系统异步写日志。Builder 按主体和时间窗口限制贡献量，聚合、过滤后加载 g18，再原子切换内存指针；构建期间继续用 g17 处理读取，构建失败则保留旧版。图中把提交日志的入口汇总在 Suggest API，实际输入是用户提交搜索的事件，不是每次输入前缀的按键。如果某条建议被禁止，应在线屏蔽旧世代和缓存中的对应内容，不能等到下次重建才生效。

Autocomplete returns suggested queries; main search returns document pages. With 250 ms debounce, 2–32 characters and a conservative four prefix requests per search read, planned peak is 10K×4=40K/s. Four is a behavior assumption, not the reciprocal of 250 ms. Suggest and Search may start in one process but need separate thread, rate and cache budgets. Every input change increments seq and clears old suggestions. Cancellation saves work; discarding responses whose seq is no longer current prevents stale overwrites. Suggestion failure still permits Enter to search.

A Trie walks m prefix characters and copies k IDs in O(m+k), plus string bytes. 2M nodes×5×8 B=80 MB counts only ID arrays. root→d→do labels show traversal through d and o, not a two-character edge. Lucene 9.12.1 FSTCompletion is a compact alternative with discretized weight buckets rather than exact popularity order. [8]

Log completed query submissions asynchronously. Builder limits contributions per subject/window, aggregates and filters, then loads g18 and swaps the in-memory pointer while g17 continues serving; failed builds retain the old generation. The diagram summarizes the submission-log ingress at Suggest API; its actual input is a submitted-search event, not every prefix keystroke. Online suppression must cover prohibited suggestions in old generations/caches until rebuild.

复盘：三个最值得演练的反例Review: three counterexamples worth rehearsing

  • 先删除 v13，再收到更新 v12：同 ID 的逻辑墓碑保留 v13，因此旧写入返回 409；相同版本如果摘要不同，也不能当作同一事件的重放。
  • A 缺席，B 有结果：默认让整页失败；如果产品允许近似首屏，必须在 missing 中列出缺片，不能写入完整结果缓存，也不能签发续页游标。
  • 二十个候选全部被删除：扫描游标仍要向前推进；在预算内补取后，即使返回空页，也可能需要保留续页游标，不能误报已经扫到快照末尾。

再试着口述一次搜索的请求与响应过程，说明版本写入与 refresh 的区别，以及缓存宕机时为何仍限制每秒 4,000 次回源。可用 Ch03 · 估算 检查单位，再通过 Ch38 · 缓存 理解派生结果的年龄限制与权威校验。

  • delete v13 → upsert v12: the same-ID logical tombstone retains v13 and rejects the stale write with 409; an equal version with a different digest is not replay.
  • A absent, B has hits: default to a whole-page failure. An optional approximate first page names missing shards and yields neither a complete-cache entry nor a continuation cursor.
  • All twenty hits now deleted: scan progress still advances; bounded refill may yield a continuable empty page, not false snapshot exhaustion.
