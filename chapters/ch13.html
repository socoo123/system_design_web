30 秒开场：先确认搜什么The 30-second open: define the corpus

中文

我设计站内知识库搜索，文档已经在业务库，不从爬虫起步。假设千万日活、每天八次搜索、十倍峰值，约九千次每秒，容量向上按一万算。查询先看旁路缓存，miss 由 API 调 Coordinator；各文档分片用倒排召回和 BM25 排序，再合并、取正文。更新从业务库日志异步进索引，普通搜索允许短暂陈旧。深翻用 PIT 加 search_after，补全另走 debounce 加前缀 top-k。我会先走一条读，再解释新鲜度和故障时返回什么。

先问六件事：站内还是全网、文档数和语言、短语与过滤、相关性、新鲜度、跳页和补全。本章选已有公开知识库、单地域与词法相关性；购物价格和私有文档权限要在返回前查权威状态，新约束必须改变图。

先用几分钟澄清估算并走读路径，再深挖倒排、分片、新鲜度和分页。主线用 BM25 与字段权重；语义召回需要另算向量索引、候选合并与评估。

「完整结果」要求所有必要分片参与，缺片不等于零命中。普通搜索允许旧，严格删除和撤权需要权威过滤；这决定故障时返回旧页、明确 partial，还是错误。

English

I’ll design search over an existing site knowledge base, not begin with a crawler. Assume 10M DAU, eight searches a day and a 10× peak: roughly 9K/s, rounded up to 10K for capacity. API checks a look-aside cache, then calls Coordinator on a miss. Document shards retrieve postings, rank with BM25, merge and fetch bodies. Business logs asynchronously update the index; ordinary search may be briefly stale. Deep pages use PIT plus search_after, and autocomplete uses debounce plus prefix top-k. I’ll walk one read before freshness and failure behavior.

Ask about site/web scope, size and languages, phrases/filters, relevance, freshness and pages/suggestions. This design uses an existing public knowledge base in one region with lexical relevance. Commerce prices and private-document permissions require authoritative validation before return; new constraints must change the design.

Spend a few minutes clarifying, estimating and walking reads, then go deep on postings, partitions, freshness and pagination. This round uses BM25 and field weights; semantic retrieval needs a separate budget for a vector index, candidate merging and evaluation.

Complete results require every necessary partition; an absent partition is not zero hits. Ordinary search may be stale, while strict deletion/revocation requires authority checks. These contracts determine stale pages, explicit partial responses or errors.

中文

搜索日请求是 10,000,000 × 8 = 80,000,000，平均 80,000,000 ÷ 86,400 ≈ 925.9 QPS，峰值乘十约 9,259，规划向上用 10,000。补全用规划峰值乘四是 40,000 QPS；按未取整值约 37,037。四是 debounce 后的行为假设，要用输入日志测量，不能仅凭 250 ms 倒数就断言每个用户每秒固定四个请求。

正文 100,000,000 × 2,000 B = 200 GB。倒排暂按 1 倍也是 200 GB，四片各 50 GB，三份副本共 600 GB 倒排。这个数不含正文存储、段合并临时空间、日志、快照和备份，也不声称倒排总是正文的固定倍数。词表、位置、字段、压缩与语言会改比例，先取代表性文档建索引再测。四片是待验证的部署假设，50 GB 是除法结果，不是通用最佳分片大小。

首屏共享缓存对整体查询贡献 60% 命中，把 10,000 收到 4,000 次回源。普通查询要搜四片，所以是 4,000 × 4 = 16,000 次分片查询/秒；每片仍是 4,000。三份平摊约 1,333，坏一份后二份各 2,000。副本增加容量，分片缩小每片文档与索引，作用不同。若命中只有 40%，每片回源 6,000，三份平时各 2,000，故障时各 3,000，就失去故障余量；要补副本、降低入场预算或改查询成本。

English

Daily search requests are 10,000,000 × 8 = 80,000,000; average is 80,000,000 / 86,400 ≈ 925.9 QPS, and the 10× peak is about 9,259. Plan conservatively at 10,000. Multiplying the planned peak by four gives 40,000 suggestion QPS; the unrounded estimate is about 37,037. Four is behavior after debounce that must be measured, not a constant obtained by inverting 250 ms.

Text is 100,000,000 × 2,000 B = 200 GB. Assuming a 1× index gives another 200 GB, or 50 GB per partition and 600 GB with three copies. This excludes stored bodies, temporary merge space, logs, snapshots and backups. Vocabulary, positions, fields, compression and language change the ratio; build a representative sample and measure it. Four partitions is a deployment assumption to validate; 50 GB is the division result, not a universal ideal shard size.

Caching shared first pages with a 60% overall query hit goal reduces 10,000 to 4,000 origin searches/s. Searching four partitions produces 4,000 × 4 = 16,000 shard queries/s in aggregate, still 4,000 per partition. Three copies share about 1,333 each; after one loss, two handle 2,000 each. Replicas add serving capacity while partitions reduce the document set per shard. At 40% hits, origin is 6,000, three copies each see 2,000 normally and 3,000 after a loss, so failure headroom disappears. Add copies, reduce admission or lower query cost.

一条搜索闭环：缓存放旁路One search loop: keep cache look-aside

正常路径与缓存键Normal path and cache keys

中文

用户提交 q=docker、language=en、过滤条件与页大小。Search API 先限制长度、规范化空白并校验合法字段，再用完整语义组成缓存键。命中拿到整页；miss 由 API 自己调 Coordinator。Coordinator 对需要的文档分片发查询，各片返回局部候选，合并后只向赢家所在的片取标题、摘要等正文，再把整页沿 API 返回。缓存不会向索引查 miss，这是图里最容易画反的一处。

查询键至少包含规范化 query、语言、过滤、排序、页参数、分析器/索引世代。相同文字不同排序不是同一结果；带权限时，还必须绑定租户和权限范围。只用 query 字符串做键，会串结果或泄露数据。规范化也不能随手删标点：产品搜 C++，删加号可能变成另一类词。先定义分析规则，再让缓存键与查询执行按同一语义解释。

English

Client submits q=docker, language=en, filters and page size. Search API validates length and fields and normalizes whitespace before building a semantic cache key. Hits return the page; on a miss API itself calls Coordinator. Coordinator queries document partitions, merges local candidates and fetches titles and snippets only from winning shards, then returns the page through API. Cache never queries the index for a miss.

Keys include normalized query, language, filters, sort, page parameters and analyzer/index generation. With permissions they also bind tenant and authorization scope. A query string alone can mix results or leak data. Normalization must preserve meaning: deleting punctuation from C++ may change the term. Define analysis rules first, then align cache keys with query execution.

容量、选择与替代Capacity, choices and alternatives

中文

缓存选择首屏，是因为查询热度通常偏斜，而且后续页与个人快照不易共享；60% 是目标，要靠负载测出来。按 20 KB/页，10,000 × 20 KB = 200 MB/s，是 API 整层返回体量。命中约 6,000 × 20 KB = 120 MB/s，Coordinator 回页约 4,000 × 20 KB = 80 MB/s，候选与内部复制另计。缓存并没有让 API 少返回字节，它主要减少重复的索引查询。

替代方案是完全不缓存：图可以拿掉 Query cache，代价是每片接 10,000/s，三份各约 3,333，超过 A3 的 2,000。若搜索特别冷、重复度低，这个替代反而更合理，但要增加读副本或降低峰值目标。不要为了命中率，把有时效要求的过滤条件删掉，也不要把未到 refresh 的新数据靠一个短 TTL 宣称立即可搜。

English

Cache first pages because query popularity can be skewed and later pages tied to private snapshots are harder to share. The 60% target needs load validation. At 20 KB/page, 10,000 × 20 KB = 200 MB/s of aggregate API output. Hits account for about 6,000 × 20 KB = 120 MB/s and Coordinator returns about 4,000 × 20 KB = 80 MB/s; candidates and replication are separate. Cache reduces repeated index work, not the bytes API must send.

Without cache each partition receives 10,000/s, or roughly 3,333 per copy with three copies, above the assumed 2,000. For cold queries with little repetition that alternative can be appropriate, but it needs more serving copies or a lower traffic target. Never remove meaningful filters to improve hits, or claim short TTL makes unrefreshed data immediately searchable.

缓存失败如何止损Contain cache failures

中文

零星缓存错误与整层宕机要分别算。缓存错误率若假设 0.1%，10,000 × 0.001 = 10 次/秒，可以在预算内绕到 Coordinator；整层宕机是 10,000 次/秒全部绕路，相比 4,000 上限多出 6,000。API 先按热点键合并相同 miss，再用全局入场与有界排队守住回源上限；合并只能减少同一个键，不能让一万个不同查询也只执行一次。

本章默认缓存层失效时超额回 429/503，而不是悄悄返回无限旧页。若产品同意旧页，还需要一份可用的独立旧值来源，并注明它的世代和年龄；坏掉的缓存自身不能发旧值。图里红线从缓存回 API，在 API 停住；被拒绝的请求由 API 回客户端。发布缓存空集群前先预热或分批切流，避免把一次部署变成整层故障。

English

Separate isolated errors from full cache loss. At an assumed 0.1% cache error rate, 10,000 × 0.001 = 10/s can bypass within budget. Full loss sends 10,000/s toward a 4,000/s cap, leaving 6,000 excess. Collapse same-key misses and use admission control plus bounded queues. Coalescing one key cannot collapse ten thousand distinct queries into one execution.

On full cache loss this design returns 429/503 for overflow. Serving old pages would require an independent accessible stale source with explicit generation and age; a dead cache cannot supply it. The cache-error arrow stops at API, which returns rejection to Client. Warm a new cache or switch traffic gradually so a deployment does not create a full-layer outage.

倒排与 BM25：先召回，再解释为什么排在前面Postings and BM25: retrieve, then explain rank

posting 与分析规则Postings and analysis rules

中文

正排从 doc_id 找标题与正文；倒排从 term 找 posting list。例子 docker 对应 [2,5,9]，guide 对应 [5,9,12]，AND 用双指针求交得到 [5,9]，OR 求并得到 [2,5,9,12]。列表按 doc_id 有序，一次比较后总有指针前进，最坏 O(x+y)；多个词先处理短列表，让中间候选不超过它。[1] 常见错误是把倒排说成「把每篇正文放进 HashMap」，没有解释为何查询不用扫一亿篇。

分析器做分词、大小写与字段规范化；主搜索默认索引和查询使用同一套兼容规则。例如 Docker 与 docker 得到同一 term，中文切词也不能写一套、查另一套。这里不把「必须相同」讲成不可违反的规律：前缀索引可在写时生成 edge n-gram，查询只保留完整前缀，否则输入 appli 被拆成 a、ap 后会错配 apple。Elastic 原文明确给出这种例外。[2]

English

Forward lookup maps doc_id to title and body; inverted lookup maps a term to postings. docker has [2,5,9], guide has [5,9,12]; AND intersects to [5,9], OR unions to [2,5,9,12]. Sorted doc IDs allow two pointers, advancing at least one per comparison for O(x+y) worst case. With multiple terms start with shorter lists to bound intermediate candidates. [1] A map containing whole documents alone does not explain how search avoids a 100M-document scan.

Analyzer handles tokenization, case and field normalization. Main search uses compatible rules at index and query time, so Docker and docker meet the same term and language segmentation agrees. Identical analyzers are not a universal rule: prefix indexing can emit edge n-grams while search keeps the full prefix. Otherwise appli might become a and ap and incorrectly match apple. Elastic documents this exception. [2]

位置、饱和与长度Positions, saturation and length

中文

posting 至少有 doc_id 与 tf，短语还要 position。查询 new york 时，文档里两词各出现一次但隔开十个位置，不等于短语命中。保存位置要更多空间，省掉位置则事后取正文验证，多一次读和更多候选。对只需要 OR 关键词的产品可以省，知识库要支持短语就保留。skip 与压缩减少长列表成本，仍不能把任意热词扫描说成一次常数时间读取。

BM25 看三个因素：稀有词更能区分文档，词频增长有饱和，文档长度要归一。Lucene 9.12.1 的默认 k1=1.2、b=0.75，版本要写准。[3] 为看清饱和，按 A11 令文档长度等于平均长度，常见公式的 TF 因子变成 tf×(k1+1)/(tf+k1)。tf=1 时 2.2/2.2=1；tf=3 时 6.6/4.2≈1.57。把词写三次只多约 57%，不是加三倍分。完整得分还含 IDF、字段权重与其他细节；Lucene 可省同一查询的常数因子，图上的数不是它的原始分数。

English

Postings need doc_id and TF, plus positions for phrases. new and york ten positions apart are not a phrase match. Storing positions costs space; omitting them moves verification to later body reads and adds I/O and candidates. OR-only products can omit them; this knowledge base supports phrases. Skips and compression help long lists without turning every hot-term scan into constant-time lookup.

BM25 combines rarity, saturating TF and length normalization. Lucene 9.12.1 defaults are k1=1.2 and b=0.75. [3] Under A11, document length equals average, so the textbook TF factor is tf×(k1+1)/(tf+k1). TF 1 gives 2.2/2.2=1; TF 3 gives 6.6/4.2≈1.57, about 57% more, not 3×. Full scoring also includes IDF, field weights and implementation details. Lucene may omit a query-wide constant factor, so the displayed values are not raw Lucene scores.

相关性与分片统计边界Relevance and shard-statistics boundaries

中文

标题可比正文加更高字段权重，但权重靠相关性评估决定，不能说「标题两倍」对所有产品成立。少见 query、短文与长文、拼写差异要进入离线样本，线上看无结果率、用户是否改词、首屏结果是否满足需求。点击只是有位置偏差的信号，不能直接当真相关标签。词法搜索能解释排名原因，代价是对同义词、含义相近但无共同词的文本不够好，这才是以后加同义词或语义召回的动机。

候选局部打分后交 top-k，Coordinator 合并；这要求各片按照同一个明确的排序比较。不同片的 term 频率可能不同，默认 shard-local 统计会使分数有偏差。Elastic Search API 区分 query_then_fetch 的本地统计与 dfs_query_then_fetch 的全局统计。[6] 文档随机均匀分布时先压测默认路径；若不同片按语言或租户切得很偏，就评估全局统计多一轮通信的成本，不能宣称所有 BM25 分数天然可比。

English

Title can receive higher weight than body, but evaluation chooses that weight. Test rare queries, short and long documents and spelling variants offline; inspect no-results rate, reformulations and first-page usefulness online. Clicks have position bias and are not direct relevance labels. Lexical ranking is explainable but misses related meanings without shared terms, motivating later synonyms or semantic retrieval.

Local top-k results must use a comparable, explicit order for global merge. Shard term frequencies may differ; default local statistics can bias scores. Elastic distinguishes local-statistic query_then_fetch from global-statistic dfs_query_then_fetch. [6] Benchmark the default for uniform random document distribution; language- or tenant-skewed partitions may justify another statistics round trip. BM25 scores are not automatically comparable under arbitrary sharding.

文档分片：扇出的是查询，副本不重复计数Document partitions: fan out queries, select one copy

分片路由与候选合并Partition routing and candidate merge

中文

默认按 hash(doc_id) 分文档，每片都有这批文档的所有 term。查询 docker guide 没有给 doc_id，不能知道答案在哪片，所以 Coordinator 向四片散发。按 term 分片则只打相关 term 的片，但 AND 要跨片合并 posting，热词也集中在某一片。这里读极重且要词组与字段过滤，选择文档分片，支付 scatter-gather 的成本；不能说「按用户哈希」就让公共搜索只查用户的一片。

每片提交局部 top-20，四片最多 80 个候选。按 A7 的 32 B 元组，4 × 20 × 32 = 2,560 B，约 2.56 KB，是每次 query 阶段候选回包，不含协议与正文。全局前二十若有一个文档不在它所在片的局部前二十，则同片已有至少二十个排在它前面，它也不可能进全局前二十；这个推理要求排序一致、候选无跨片重复及约束相同。合并后再 fetch 胜出文档，图中的一对车道概括 query 和 fetch 两轮。

English

Shard by hash(doc_id), with all terms for each assigned document held locally. docker guide gives no document ID, so Coordinator fans out to four partitions. Term sharding contacts only relevant term partitions but requires cross-partition postings merges for AND and can concentrate hot terms. This read-heavy product needs phrases and filters, so document sharding pays scatter-gather. Hashing users does not make public corpus search a single-user-shard read.

Each partition returns local top-20, at most 80 candidates across four. At A7’s 32 B tuple, 4 × 20 × 32 = 2,560 B, about 2.56 KB before protocol and bodies. A global top-20 document must be in its partition’s local top-20: otherwise that partition alone has at least twenty earlier documents. The argument requires consistent ordering, no cross-partition duplicates and the same constraints. Merge first, then fetch winners; the diagram’s paired lanes summarize both rounds.

副本容量与尾延迟Replica capacity and tail latency

中文

主分片和读副本含同一逻辑片的文档，不是三倍 corpus。Search shard routing 原文描述选择一个分片副本，副本选择还能参考响应速度与队列。[6] 本章按每片三份、每份可用 2,000/s 算正常和单份故障；可用预算应在目标延迟、实际 query mix、更新流量与段合并同时存在时测，不是拿一次纯命中微基准证明能扛热词、短语和任意深分页。

p99 被最慢必要分片拖住。若粗假设每片在期限内响应的概率都是 99%，且相互独立，四片全到齐是 0.994≈96.06%；这只是说明扇出放大慢尾，不是生产可用性预测，共享网络与段合并可能相关。对每次逻辑搜索设置一个 200 ms 总期限，把排队、query、fetch 与一次有界换副本都放进去；后端 deadline 要随剩余时间传播，不能每跳再赠送 200 ms。

English

Primary and replicas contain the same logical partition, not three times the corpus. Search shard routing describes selecting one shard copy, with adaptive choice using response time and queue information. [6] Three copies at 2,000 usable queries/s each cover normal load and one loss. Benchmark that usable rate with the real query mix, update load and merges under the latency goal, not an all-cache-hit microbenchmark.

The slowest required partition drives the tail. If each independently responds in time with probability 99%, four all arrive with 0.994≈96.06%. This illustrates tail amplification, not production availability; shared networks and merges can correlate delays. Use one 200 ms end-to-end deadline for queueing, query, fetch and a bounded replica retry. Propagate the remaining time instead of giving every hop another 200 ms.

重试与缺片的行为Retries and missing partitions

中文

图里的 A 超时后先把故障还给 Coordinator，Coordinator 在剩余预算内选 Replica A；B 的工作不用重做。若是节点故障，副本有帮助；若是同一热词扫描太贵，换副本只会把同一份昂贵工作再做一遍。限制重试次数与并发，超时取消未完成任务；不要一页失败就向每份副本同时广播，故障时三倍请求最容易把剩下的副本拖死。

本章要求完整页，因此一个逻辑片无可用副本就明确失败，部分页不进入完整结果缓存。若产品接受 partial，响应必须显式标出缺片与结果不完整，不能告诉用户「只有这些命中」。Elastic 的 allow_partial_search_results 正是这种政策开关。[6] fetch 若发现文档已删除，按权威状态过滤并继续取合规候选，宁可页不足二十也不能显示受禁内容。

English

A timeout returns to Coordinator, which selects Replica A within the remaining budget; B does not need re-execution. A replica helps a node failure, but repeating an expensive hot-term scan just repeats expensive work. Bound retries and concurrency and cancel unfinished tasks. Broadcasting a failed query to all copies can triple load and take down the survivors.

This chapter requires a complete page: an unavailable logical partition makes the page fail and partial results do not enter the complete-result cache. If the product allows partial responses, declare missing partitions and incompleteness. Elastic’s allow_partial_search_results encodes that policy. [6] If fetch discovers a deleted document, apply authoritative filtering and continue through eligible candidates; fewer than twenty results are preferable to prohibited content.

更新链：提交、重放与 refresh 是三件事Updates: commit, replay and refresh are separate

权威写入与乱序重放Authority and out-of-order replay

中文

业务库是 authority，倒排是可重建的派生视图。事务先提交，再由 CDC 消费已提交日志，批量做分析器处理并应用到索引。客户端收到业务写成功只说明业务事实已落库，不等于索引已经可搜。若应用写完主库又直接调用索引，中途进程死掉会留下「主库新、索引永远旧」；CDC 或事务 outbox 能从已提交记录继续，不把内存里的第二次写当可靠事件。

每个事件带 doc_id、单调业务版本与 upsert/delete；同一文档按序处理，跨文档可以并行。索引端仍做版本比较，以抵抗重投与慢批次。假设 v12 更新比 v13 删除晚到，必须保留 v13 的删除墓碑来拒绝 v12。若删除后立刻连版本一起清空，晚到更新看见「不存在」就会把文档重新建回来。墓碑保留时间至少覆盖源日志可重放窗口、重建快照年龄与最长重试，不是随手设一个短 TTL。

English

Business DB is authority and the inverted index is rebuildable. Commit first, consume committed logs through CDC, analyze batches and apply them to the index. Business-write success does not imply searchable visibility. Calling index directly after a DB write can lose the second write if the process dies; CDC or transactional outbox resumes from durable committed records.

Events carry doc_id, monotonic business version and upsert/delete. Preserve order per document and parallelize across documents, with sink-side version checks for replay and slow batches. A late update v12 after delete v13 must be rejected using a retained v13 tombstone. Clearing the version on deletion lets v12 recreate the document. Retention must cover log replay, snapshot age and longest retry, not an arbitrary short TTL.

版本接口与查询可见性Versions and visibility

中文

Elastic Index API 的 external 版本只接受比当前严格大的版本，乱序到达最终保留最新；相同版本会冲突。[7] 本章消费逻辑对相同版本的重放校验为已应用，不能把所有冲突都忽略，也不能直接使用 external_gte 覆盖同版本不同内容。业务 version 要在源端可靠生成，服务器时间戳会有同毫秒冲突与时钟倒退。若系统自身删除元数据只有限保留，本章的长期墓碑必须另存或以带 deleted 标志的版本化记录保存。

索引返回写入确认之后，查询还读取旧 reader view；refresh 才把新段打开给搜索。Elastic 的近实时搜索原文说明 refresh 与提交不同，其传统默认每秒刷新还附带最近三十秒有搜索的条件。[5] 本章把 refresh 的一秒当 A6 预算，不能照搬成所有部署和所有索引的保证。为了低吞吐后台强制每个写都刷新，会增加小段与合并压力；批量写、周期刷新更适合这条异步路径。

English

Elastic external versions accept only a strictly greater version; exact versions conflict, and out-of-order operations preserve the newest. [7] A consumer can validate same-version replay as already applied; it must not ignore all conflicts or use external_gte to overwrite equal-version different content. Generate versions reliably at the source rather than trusting wall-clock timestamps. If engine deletion metadata is only temporarily retained, keep long-lived tombstones separately or as versioned deleted records.

An index write acknowledgement can precede visibility; refresh opens new segments to readers. Elastic separates refresh from commit and describes the traditional one-second default with a recent-search condition of thirty seconds. [5] A6 uses one second as our target, not a universal deployment guarantee. Refreshing on every write creates small segments and merge pressure; batching and periodic refresh better fit this async path.

陈旧窗口、严格删除与重建Staleness, strict deletion and rebuild

中文

正常目标是 CDC 一秒、应用一秒、refresh 一秒，相加约三秒；最后一次旧首屏若在可见性前写入缓存，再留三十秒，陈旧窗口约三十三秒。这按每段目标满足、没有积压、TTL 不滑动续期来算。消费者落后二十分钟时，短 TTL 只是在旧索引上重复查，不会修复新鲜度。监控要记业务版本到可搜版本的水位差、最老待处理事件年龄、失败重试与死信，并把 query p99 和数据年龄分开。

删除、撤权要有不同契约。普通改标题允许短暂旧；需要立即不可见的内容，在返回前用权威删除/授权状态过滤，覆盖缓存命中与旧 PIT。缓存删键也要可靠投递，单次 delete 丢失用 TTL 兜底，但 TTL 不是严格删除保证。过滤不可用时按敏感内容契约拒绝；不能拿「缓存可用」替代「用户仍有权看」。文档写成功后，详情可读权威库，搜索页标明索引处理中，不要强迫它承诺同一毫秒。

重建索引要先记日志水位，从一致快照灌新世代，再重放水位后的变更，追平后原子切换查询别名与缓存世代。只全量扫描业务库、不处理扫描期间发生的删除，会让新索引重新带入旧文档。变更 200/s 若暂停消费十分钟，积压 200 × 600 = 120,000 条；恢复 worker 若实测 600/s，扣掉持续到来的 200/s，净追赶 400/s，至少 120,000 ÷ 400 = 300 秒。六百是条件假设，重试和合并会拉长时间。

English

Normal targets add one second CDC, one apply and one refresh: roughly three seconds. An old first page cached just before visibility can remain thirty more seconds, about thirty-three total. This assumes targets hold, no backlog and a non-sliding TTL. A consumer twenty minutes behind remains stale despite short cache TTL. Monitor searchable-version watermarks, oldest pending event age, retries and dead letters separately from query p99.

Strict deletion or revocation differs from an ordinary title update. Authoritative deletion/permission filtering before return must cover cache hits and old PIT views. Reliably deliver invalidations; TTL limits a lost invalidation but is not a strict deletion guarantee. Reject sensitive reads if the authority check is unavailable. Details can read authority after write while search reports indexing in progress, without claiming same-millisecond visibility.

For rebuilding, record a log watermark, load a consistent snapshot into a new generation, replay later changes, catch up and atomically switch query alias and cache generation. A full scan alone can resurrect documents deleted during the scan. At 200 changes/s, a ten-minute pause yields 200 × 600 = 120,000 pending events. If a recovered worker is measured at 600/s, subtract ongoing 200/s for a net 400/s; catch-up needs at least 120,000 / 400 = 300 seconds. The conditional 600/s is not guaranteed; retries and merges extend recovery.

分页：游标必须绑定同一份结果视图Pagination: bind the cursor to one result view

浅页选择与深页成本Shallow pages and deep-page cost

中文

搜索常见第二、第三页跳转，浅 offset 是合理产品选择。代价是每片为 from + size 保留候选，Coordinator 才能跳过前面的全局结果。from=10,000、size=20、四片，最多 40,080 个候选；32 B/个约 1.28 MB。对比首屏的 80 个候选、2.56 KB，是 501 倍候选容量。真实堆对象、排序状态和网络协议更多，posting 扫描也可能远超候选数；这一步证明的是深 offset 放大排序与回包，不能用它预测完整延迟。

Elastic 原文给出默认 from + size 不超过 10,000 的保护窗口，并建议深翻改 search_after。[4] 图里 from=10,000、size=20 超过这个默认限制，是需要拒绝或改接口的例子，不是可以直接发送的默认合法请求。把 max_result_window 改得巨大只是解除护栏，不会降低保留候选与排序成本。需要任意跳到深页的产品，要承认成本，或者预计算有限结果集并给出明确有效期。

English

Shallow offset supports page jumps. Each shard retains from + size candidates so Coordinator can skip globally earlier results. At from=10,000, size=20 and four shards, up to 40,080 candidates at 32 B each cost about 1.28 MB. Compared with 80 candidates and 2.56 KB on page one, that is 501× retained-candidate capacity. Real objects, sorting and protocols cost more; postings scanned can far exceed this count, so it is not a complete latency estimate.

Elastic defaults to a 10,000-hit from + size window and recommends search_after for deeper pagination. [4] The diagram’s from=10,000 plus size=20 exceeds the default and is a rejection/redesign example, not a legal default request. Increasing max_result_window removes protection without reducing work. Arbitrary deep jumps require acknowledging the cost or precomputing a bounded result set with a stated lifetime.

固定视图与游标契约Fixed views and the cursor contract

中文

search_after 带上一页最后一条的全部排序值，继续取后面的结果。稳定次序不够，还要稳定视图：refresh、新文档、删除及 IDF 改变会移动边界；一个文档可能跨过旧分数锚点，造成重复或遗漏。PIT 固定这次搜索的 reader view，本章按 score 降序、_shard_doc 升序；_shard_doc 在该 PIT 内打破同分，不是永久业务 doc_id。换 PIT，旧值就不能假装仍有效。

游标是服务器验证的 opaque token，绑定 query/过滤/排序摘要、最新 PIT ID、最后命中的全部 sort 数组、页大小和过期时间。下一页保持 query 与 sort 不变，并采用返回的最新 PIT ID，Elastic 文档对此有明确要求。[4] 用户改 query 或权限范围时重新开始，不能沿用旧 cursor。PIT 绑定排序会话，不能直接塞进共享 query cache；普通首屏缓存与快照会话的结果语义不同。

English

search_after uses all last-hit sort values. Stable ordering also needs a stable view: refresh, insertion, deletion and changing IDF can move boundaries and produce repeats or omissions. PIT pins the reader view. Here sorting is score descending and _shard_doc ascending, a PIT-local tiebreaker rather than permanent business doc_id. An old value cannot be reused with a different PIT.

The server validates an opaque cursor bound to query/filter/sort hash, latest PIT ID, all last-hit sort values, page size and expiry. Keep query and sort fixed and use the latest returned PIT ID, as documented by Elastic. [4] A changed query or permission scope restarts the session. PIT pages are session-specific and do not belong in the shared first-page cache.

查询成本与快照失效Query cost and snapshot expiry

中文

四片每片只需保留这一页的 top-20，合计约八十个候选，省掉巨大 offset 窗口；search_after 不保证只扫描二十个 posting，也不保证查询恒定时间。昂贵的词组、排序和聚合仍需执行。若只是导出全部文档且不需要相关性排序，可以用适合遍历的排序与快照方式；实时搜索分页不要为了支持滚动就背一套长寿命 scroll 服务。

PIT 保留旧段与搜索上下文，要限制寿命和并发。本章空闲六十秒到期，读完主动关闭；续期只给下一页足够时间，不给用户永久快照。到期 API 返回本章自定的 410 与重启提示，不偷偷打开新视图接旧锚点。旧 PIT 可能仍包含已删除文档，严格删除仍走上一节权威过滤；稳定快照保证排序连续，不能保证安全状态冻结不变。

English

Four partitions retain at most about eighty candidates for this page, avoiding the huge offset window. search_after does not mean only twenty postings are scanned or constant-time query work. Expensive phrase queries, sorts and aggregations still execute. Full export without relevance can use a traversal-appropriate sort and snapshot; interactive search does not need an unlimited scroll service just to support scrolling.

PIT retains old segments and context, so bound lifetime and concurrency. This design expires after sixty idle seconds and closes finished views. API maps expiry to its own 410/restart contract instead of silently creating a fresh view for an old anchor. Strict deletion still applies authoritative filtering to old PIT hits; stable pagination does not freeze authorization or safety state.

自动补全：键盘路径单独算账Autocomplete: give keyboard reads their own budget

独立预算与客户端序号Separate budget and client sequencing

中文

补全输入是前缀，输出五个建议 query；主搜索输入是完整查询，输出文档和摘要。即使两者从同一批用户行为得到热度，也不把补全路由到主倒排做四片全搜索。Suggest API 与 Search API 可先同进程部署，但有独立线程池、限流与缓存空间，避免热词输入把正常结果页饿死。峰值补全四万次每秒，是搜索一万的四倍，省掉这条预算是最常见的漏算。

客户端等二百五十毫秒没有新输入，至少两个字符才发请求；超过三十二字符按本章产品规则停止补全，回车仍可提交合法完整搜索。四次前缀请求是保守假设，翻页实际不触发补全，不是 debounce 固有结果。客户端取消旧请求以省工作，每次前缀变化递增 seq；响应的 seq 与当前输入不同就丢弃。即使旧请求已在服务端执行、取消没来得及生效，序号检查也能防止旧建议覆盖新建议。

English

Autocomplete takes prefixes and returns five suggested queries; main search returns documents and snippets. Do not route keyboard reads through four-partition document search. Both APIs can initially share deployment, but isolate worker pools, rate limits and cache memory. The 40K/s suggestion peak is four times the 10K search peak and needs its own budget.

Wait 250 ms without typing and require two characters. Above thirty-two characters this product stops suggestions while still allowing valid submitted search. Four requests per search read is conservative; page turns do not trigger suggestions. Cancel old requests to save work, increment seq on each prefix change and discard replies whose seq is not current. Validation still prevents stale overwrite when cancellation arrives too late.

前缀结构与真实内存Prefix structure and actual memory

中文

Trie 用字符边表示前缀，root→d→o 找到 do。到达节点后读取预存 top-5，节省遍历整棵子树；走到前缀却仍花 O(m)，复制 k 个建议 ID 花 O(k)，合计 O(m+k)，返回字符串另算字节成本。图里 do 是前缀节点标签，root→d→do 表示已经走过 d、o，不是把 do 当两个字符的单一边。汉字、大小写和 Unicode 规范化须与热度构建兼容。

200 万前缀节点乘五个 ID、每 ID 八字节，数组就是 80,000,000 B = 80 MB；节点结构、边、热度、完整建议字符串与分配器开销都没算。若百万个节点各塞长字符串，估出来的内存会差一大截。可以让节点存 ID，字符串放共享表；top-k 写时要更新祖先，所以本章倾向批处理发布新世代。Lucene FSTCompletion 提供压缩前缀查找，权重近似排序而不是本章 Trie 的精确 top-k，换实现还要验证排序需求。[8]

English

Trie edges encode characters. Walking root then d then o reaches prefix do. Cached top-5 avoids subtree enumeration, but prefix walking costs O(m) and copying k IDs costs O(k), for O(m+k), plus string bytes. The diagram labels cumulative prefix do; it does not imply a two-character single edge. Normalize Unicode and case consistently with popularity construction.

Two million nodes times five IDs times eight bytes is 80,000,000 B, or 80 MB for arrays alone. Topology, edges, weights, strings and allocator overhead are extra. Store IDs with shared strings rather than copying long strings into each node. Updating top-k affects ancestors, favoring batch generations. Lucene FSTCompletion offers compressed prefix lookup with approximate weight ordering rather than this Trie’s exact top-k; validate that ranking trade-off. [8]

异步构建与失败时行为Async builds and failure behavior

中文

只采集提交的完整 query，异步记 Query logs；若每个按键的前缀都记一次，do 会比 docker 获得更多伪热度。Builder 去重、聚合与过滤，把有效建议生成到 g18，服务读继续用 g17，完整加载后原子切换。构建中途失败就保留旧世代，日志积压告警，但不让按键等待构建完成。新发布若数据格式不兼容，可回到旧世代；世代号让缓存不会混用两版建议。

质量与滥用也要说出失败行为：少数恶意提交可以刷热度，因此按主体/时间窗口去重和限制贡献，再过滤敏感与禁止建议；计数只能是排序信号。删除一条建议需要线上屏蔽名单覆盖旧世代与缓存，等下次重建太慢。补全故障时输入框仍能打字、回车搜索，建议区为空或提示暂不可用，不把补全失败传播成主搜索不可用。完整输入变化时还应清理旧列表，避免用户看到与当前前缀不一致的建议。

English

Collect submitted full queries asynchronously into Query logs, not every typed prefix, which would give do artificial popularity over docker. Builder deduplicates, aggregates and filters into g18 while serving remains on g17. Switch atomically after a complete load. Build failure preserves the old generation; backlog ages popularity without delaying keystrokes. Generation keys avoid mixing cached suggestions across versions and support rollback.

Limit popularity contributions per actor and time window, then filter prohibited suggestions; counts are only ranking signals. An online blocklist covers old generations and caches when a suggestion must disappear immediately. If suggestions fail, typing and submitted search remain available with an empty/unavailable suggestion list. Clear obsolete lists on input changes so displayed suggestions match the current prefix.

追问怎么接Follow-ups

缓存命中变成 40%，先坏在哪里？Where does a 40% hit rate break the plan?

中文

每片回源 10,000 × 0.6 = 6,000/s，三份各 2,000；坏一份就各 3,000，超过 A3。先保护 4K 入场，再增副本或降查询成本，不能把四片改八片当成每片 QPS 自动减半。

English

Each partition gets 10,000 × 0.6 = 6,000/s: 2,000 per copy normally and 3,000 after a loss, above A3. Protect 4K admission, then add copies or lower cost; doubling partitions does not halve per-partition query rate.

写入成功后为何搜不到？Why is an acknowledged write not searchable?

中文

业务提交、CDC、应用、refresh 与缓存可见性不同。正常预算三秒，首屏可能再旧三十秒；积压会更长。返回写入内容供详情展示，搜索暴露索引进度。

English

Commit, CDC, apply, refresh and cache visibility differ. Normal index budget is three seconds, with up to thirty more for first-page cache and more under backlog. Return written content for details and expose indexing progress.

PIT 已固定，还要过滤删除吗？Does a fixed PIT still need deletion filtering?

中文

要。PIT 故意保留旧视图，删除后旧文档可能还在其中；普通缓存页也一样。严格删除/撤权走权威校验，校验失效就按敏感数据契约拒绝。稳定翻页不是冻结用户权限。

English

Yes. PIT retains an old view that may include later-deleted documents, as can cached pages. Strict deletion/revocation requires authority checks and rejection when that check is unavailable. Stable pages do not freeze permissions.

更换分词器如何避免混用？How do analyzer changes avoid mixed token rules?

中文

新分析器生成新索引世代；一致快照加日志追平，校验召回与排序后原子切别名和缓存世代。只改 query analyzer，旧 posting 不会自动转换，可能导致明明有文档却搜不到。

English

Build a new generation, load a consistent snapshot, replay logs, validate retrieval/ranking, then switch alias and cache generation atomically. Changing query analysis alone does not rewrite old postings.

为什么补全不直接查主索引？Why not use the main index for every prefix?

中文

补全峰值四万，是主搜索四倍；独立前缀 top-k 避免每个按键重复四片查询。主索引实现前缀字段也可行，但仍要独立预算、兼容分析器与故障隔离，不能当免费接口。

English

Its 40K peak is four times main search. Prefix top-k avoids four-shard queries per keystroke. Prefix fields on a main-index implementation can work, but still require independent budgets, compatible analysis and failure isolation.

换副本也超时，如何保住系统？What if the replica retry also times out?

中文

在原总期限结束时取消剩余任务，返回明确失败，不重置两百毫秒。限制热词、复杂过滤和深页入场；按错误类型做有界重试。若只是查询计算太贵，副本不能消掉计算本身。

English

Cancel remaining work at the original deadline and fail explicitly; do not reset 200 ms. Bound expensive queries, filters and deep pages, and retry by error type. Replicas do not remove intrinsically expensive computation.
