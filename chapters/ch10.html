为什么先算扇出

A1 的一千万日活、每人十条，先得到 100,000,000 条用户通知每天。A2 假设每人平均有 1.4 个有效推送端点，而且本章逐端点调用供应商，于是 100,000,000 × 1.4 = 140,000,000 次调用。平均 140,000,000 ÷ 86,400 = 1,620.37/s，峰值乘 5 得 8,101.85/s，口播约 8,102。原先的 1,157 和 5,787 只算到了用户意图，不能称为设备吞吐。活动创建可以一次覆盖千万人，API 压力必须再按生产者的单发与群发比例计算；二十万次事务通知每天只是约 2.31 次意图/秒，仍不是全天供应商容量。

A4 的活动只提交一行和受众快照引用，逐步展开后才有 10,000,000 × 1.4 = 14,000,000 次调用。十分钟完成要求 14,000,000 ÷ 600 ≈ 23,333/s；独占 2,000/s 时需要 7,000 秒，约 1.94 小时。这是无重试、无静默、无其他流量的理想下界，2,000 也是规划假设而非厂商公开限额。若共享出口已有日常平均 1,620.37/s，只剩 379.63/s，活动下界就成为 14,000,000 ÷ 379.63 ≈ 36,878 秒，约 10.24 小时。活动要更快，应提高真实配额或分开配额池，单纯增加 worker 无法缩短这个下界。

还要证明正常流量能排完。A3 假设 8,101.85/s 的峰值持续 600 秒，2,000/s 出口的新增积压是 (8,101.85 − 2,000) × 600 ≈ 3,661,111 条。之后流量回到平均，空余约 379.63/s，清理这份积压约需 9,644 秒，即 2.68 小时；若峰值长期不降，队列只会增长，必须提高能力或入口拒绝。A5 的消费预算 500/s 使 2,000 ÷ 500 = 4 个消费分区，留一倍余量先用 8 个；它不证明 broker 接得住 8,102/s，发布吞吐和积压字节另测。按 hash(user_id) 分区打散受众，租户公平由调度配额实现。

A6 按每个端点的短状态行 0.5 KB = 500 B 估算：140,000,000 × 500 = 70 GB/天，×30 = 2.1 TB 原始，×3 = 6.3 TB 三份。通知意图、正文、索引、Attempt 和备份都未计入，不能把 6.3 TB 宣称为总存储。营销正文只留模板版本和参数引用，端点状态保留到重放窗口结束；未知和失败保留详细尝试，长期审计归档。这样才能解释主库的保留边界。活动快照和分页游标也有耐久成本，不能用一行 Campaign 就声称千万收件人完全不占存储。

Why fan-out comes first

A1 gives 100,000,000 user notifications per day. A2 assumes 1.4 active push endpoints per user and one provider call per endpoint, so 100,000,000 × 1.4 = 140,000,000 calls. Average traffic is 140,000,000 / 86,400 = 1,620.37/s; a 5× peak is 8,101.85/s, about 8,102. The earlier 1,157 and 5,787 described user intents, not device throughput. One campaign creation can cover millions of users, so API load also needs the producer mix of single sends and campaigns. The separate example of 200,000 transactional intents per day is 2.31 intents/s, not total provider capacity.

Under A4, one campaign stores a row and an audience-snapshot reference, then expands into 10,000,000 × 1.4 = 14,000,000 calls. Finishing in ten minutes requires 14,000,000 / 600 ≈ 23,333/s. Exclusive use of 2,000/s takes 7,000 seconds, about 1.94 hours. This is a lower bound with no retries, quiet hours, or competing traffic; 2,000 is a planning assumption, not a published provider limit. If daily average traffic already consumes 1,620.37/s of the same outlet, only 379.63/s remains: 14,000,000 / 379.63 ≈ 36,878 seconds, or 10.24 hours. Faster completion requires more real quota or a separate quota pool; more workers cannot remove this bound.

Prove that ordinary traffic can drain too. A3 sustains 8,101.85/s for 600 seconds, so a 2,000/s outlet accumulates (8,101.85 − 2,000) × 600 ≈ 3,661,111 items. At the subsequent average, 379.63/s remains and recovery takes about 9,644 seconds, or 2.68 hours. A permanent peak grows the queue indefinitely and requires capacity or admission control. A5 budgets 500/s per consumer partition: 2,000 / 500 = 4, or 8 with 2× headroom. That does not prove the broker can ingest 8,102/s; measure publication throughput and backlog bytes separately. Hash user_id to spread recipients and enforce tenant fairness through scheduling quotas.

A6 estimates a compact endpoint-state row at 0.5 KB = 500 B: 140,000,000 × 500 = 70 GB/day, ×30 = 2.1 TB raw, ×3 = 6.3 TB copied. Notification intents, bodies, indexes, Attempt, and backups are excluded, so 6.3 TB is not total storage. Marketing retains a template version and parameter references; endpoint state survives the replay window, detailed unknown or failed attempts survive investigation, and long-term audit is archived. This sets primary-store retention. Audience snapshots and page cursors also cost durable bytes; a single Campaign row does not make ten million recipients free.

接受延迟为什么不能包含供应商

《The Tail at Scale》的例子把单机超过 1 秒的概率设为 1%，等 100 台中最慢的一台时，约 63% 请求超过 1 秒。[7] 用独立性近似重算是 1 − 0.99100 ≈ 63.4%，不是三个供应商一定有这个比例；它说明同步扇出会放大尾部。通知接受路径因此只等本地事务，供应商进入独立投递时钟。验证码与营销也分消费资源，避免批量工作把用户正在等的工作压在同一条先进先出里。独立队列只解决排队隔离，供应商总配额还要预留，否则高优先级仍发不出去。

A7 是工作目标，请面试官修改，不是供应商合同。5 分钟验证码到期后不发送，GET 状态允许客户端恢复重取按钮。供应商健康时的 30 秒指标用于定位内部排队，还要同时监控全时段过期率，不能把故障时的失败从结果里删掉。

Why accept latency cannot include the providers

The example in “The Tail at Scale” assumes a 1% chance that one server exceeds one second; waiting for the slowest of 100 makes about 63% of requests exceed one second. [7] An independence approximation gives 1 − 0.99100 ≈ 63.4%, not a claim about three providers. Synchronous fan-out amplifies tails, so acceptance waits only for a local transaction and providers use a separate delivery clock. OTP and marketing also have separate consumer resources so batch work cannot block work a user is waiting for. Separate queues isolate waiting, while reserved provider quota makes that priority executable.

A7 contains working targets to revise, not provider contracts. Do not send a code after its five-minute expiry; a status query lets the UI offer a new code. The healthy-provider 30-second metric isolates internal queueing, while an all-period expiry metric still counts outage failures.

正常路径

生产者带模板、收件人和幂等键进 Notif API。校验身份与权限，提交 Notification 和 Outbox，数据库确认逐跳回到 API，再回生产者 202 和 notification_id。Outbox relay 读取未发布行，按通道和优先级送入 Push Q、Email Q、SMS Q；worker 先查端点投递状态，再执行发送前的门和外部调用。供应商回复只回 worker。整体图省略的 Delivery、Attempt 写入在第三组展开，过滤步骤在第四组展开，组件名称和调用方向一直相同。

Walkthrough

Producer brings a template, recipient, and idempotency key to Notif API. After identity and authorization checks, Notification and Outbox commit in Notif Store. The durable reply returns through the API to Producer as 202 plus notification_id. Outbox relay reads unpublished work and routes by channel and priority into Push Q, Email Q, or SMS Q. Workers inspect endpoint delivery state before pre-send gates and provider calls. Provider replies end at workers. 为什么这样选

Notif Store 拥有「我们已经接受这条意图」这件耐久事实，队列保存待执行工作，供应商保存它是否接受外部请求。三者状态不互相冒充。队列的消息在送出但尚未终态时丢失，不能仅看已发布 outbox 就假定会恢复；保留 Delivery 的 next_attempt_at，由补偿扫描器重建未终态工作，扫描和消费者都用相同投递键。小规模时 API、relay、worker 可以同进程部署，仍先提交再发送。把工作挪到线程池只能释放请求线程，不能代替耐久工作记录。

推送、邮件和短信的等待时间、费用和错误类不同，所以按通道隔离消费池，再在通道内隔离事务和营销。A5 假设邮件出口 200/s，300 万封 ÷200 = 15,000 秒，约 4.17 小时；它比推送独占配额的 1.94 小时更长，活动完成要分通道统计。OTP Q 不是整个平台唯一的一条队列，而是每个通道的优先级子队列。A10 在共享推送配额中预留 200/s，剩余通常为 1,800/s，空闲时可借给营销；因此 1.94 小时只适用于全部 2,000/s 真正可用的情形。

Why this shape

Notif Store owns the durable fact that an intent was accepted; the queue holds execution work and the provider knows whether it accepted an external request. These facts are different. If already-published work disappears before a terminal outcome, a published outbox alone does not repair it. Retain Delivery.next_attempt_at and let a repair scan reconstruct unfinished work with the same delivery keys as consumers. API, relay, and workers may share a process at small scale but still commit before sending. A thread pool frees a request thread; it does not replace durable work records.

Push, email, and SMS have different latency, cost, and failure modes, so isolate channel consumer pools and then transactional versus marketing work within each. A5 assumes 200 emails/s: 3M / 200 = 15,000 seconds, or 4.17 hours, longer than the exclusive push bound of 1.94 hours. Track campaign completion per channel. OTP Q denotes a priority subqueue within a channel, not one platform-wide queue. A10 reserves 200/s of the shared push quota, normally leaving 1,800/s; marketing can borrow idle capacity. The 1.94-hour bound applies only when all 2,000/s is actually available.

替代方案

每天几千条时，数据库工作表加定时轮询可以暂代独立 broker。worker 领取一个端点，写租约与 next_attempt_at，再执行外部调用；扫表和租约恢复承担消息恢复，不能用提交后的一次内存调用当队列。代价是扫表延迟、索引和锁竞争；千万级活动出现时，展开、待发送和补偿扫描争用同一库，再引入 broker。保留原投递键和状态表，可逐步迁移，不需要改调用方的 202 语义。

Alternative

At a few thousand daily sends, a DB work table and polling can replace a separate broker. Workers claim one endpoint, persist a lease and next_attempt_at, and make the external call; polling and lease recovery restore work. A one-off in-memory call after commit is insufficient. The costs are polling delay, indexes, and locking. A campaign eventually makes expansion, delivery, and repair compete on the DB, motivating a broker. Retaining delivery keys and state permits gradual migration without changing the caller’s 202 semantics.

故障窗口

202 已经返回、relay 还没把消息放进队列的这段时间，用户什么也收不到，调用方却已经认为「系统收下了」。这不是丢意图：行在库里，状态仍是 accepted。用户能感知到的是验证码来晚了。若这段空白长过验证码的 not_after，晚到的短信本身也没用，所以过期检查在 worker，不在已经返回的 202 上。供应商整家不可用时，另一条通道的队列继续被消费；图上没有一条跨通道的同步边。

Failure window

Between the 202 and the relay’s publish, the user receives nothing while the caller already believes the system accepted the intent. The intent is not gone: the row is committed and still accepted. What the user notices is a late code. If that gap outlives not_after, a late SMS is useless too, so the expiry check sits in the worker, not inside the 202 that already left. When one provider is down, the other channels’ queues keep moving. The diagram has no synchronous edge across channels.

API、幂等与每个端点的投递状态API, idempotency, and endpoint delivery state

中文

租户身份来自调用方认证，不来自请求体里可以随便填的 tenant_id。幂等键的作用域是这个租户加 Idempotency-Key。同一把键、同一份请求摘要，无论第一次还是超时后的重试，都返回同一个 notification_id 和同一份 202 表示。同一把键配上不同的正文摘要，返回 409，避免把「重试」和「换了一个收件人」混成一次成功。键的保留时间要长过调用方的最大重试窗口，这里按 24 小时假设。

状态码告诉调用方能不能原样重试。正文不合法是 400，未认证是 401，这个租户不能用该通道是 403，键冲突是 409，租户或用户配额不够是 429 并带 Retry-After，存储暂时不可用是 503。429 和 503 用同一把键重试。不要用 HTTP 200 加一段「failed」字符串表示所有结果，调用方的重试库认不出来。

English

Tenant identity comes from caller authentication, not from a tenant_id the body can set to anything. The idempotency scope is that tenant plus Idempotency-Key. The same key and the same request digest return the same notification_id and the same 202 representation on the first call and on a timeout retry. The same key with a different body digest returns 409, so a retry is not silently merged with “this is actually a different recipient.” Keep the key longer than the caller’s maximum retry window; the assumption here is 24 hours.

Status codes tell the caller whether to retry the same bytes. A malformed body is 400, missing authentication is 401, a channel the tenant may not use is 403, a key reused with a different body is 409, a tenant or user quota miss is 429 with Retry-After, and a store that is briefly unavailable is 503. Retry 429 and 503 with the same key. An HTTP 200 wrapped around a string that says failed is invisible to a normal retry library.

幂等键不是模板，也不是手机号

幂等键代表一次意图：重复点击复用键就返回原 id，新一次验证码必须换键。手机号或模板名不能充当键，否则会合并下一次合法发送。活动创建有活动键，分页展开再按活动加收件人去重，不让创建请求携带千万个键。

The key is not the template or the phone number

An idempotency key identifies one intent: repeated clicks reuse its id, while a new OTP requires a new key. A phone or template is not a key because that would merge later legitimate sends. Campaign creation has its own key; expansion deduplicates campaign plus recipient without millions of keys in the create request.

快照里放什么

Notification 按请求保存 channels 数组，Delivery 按通道和端点拆行，不能用一个 channel 列和一个 sent 位覆盖多设备。端点首次展开时冻结 endpoint_id 集合，同一 delivery_id 重试不会顺便加入刚登记的新设备。邮件和短信地址保留接受时快照，密码重置不会跟随中途改邮箱；推送则在每次调用前读取该端点最新 token/version。失效响应只停用被调用的那一版，避免旧请求的迟到 410 删掉刚轮换的新 token。租户、列表、通道共同作用于 Preference，退订这一列表不影响另一租户或验证码。

Delivery 是端点状态：queued → leased → provider_accepted，或变成 retry_wait、suppressed、expired、failed；unknown 由下一次重试决策处理。Attempt 记录每次调用的 accepted、rejected、timeout_unknown、rate_limited，保留 provider_message_id。已知成功的端点在重投时只 ack，未成功的其他端点继续，Notification 的汇总可能是 partially_accepted。补偿和 relay 更新状态要带条件，不允许 queued 覆盖已经成功的端点。Attempt 不等于已读记录；业务验证验证码才是业务成功，不能由通知状态机推断。

What the snapshot holds

Notification stores a channels array; Delivery has one row per channel and endpoint. One channel column or sent bit cannot describe several devices. Initial expansion freezes endpoint_ids, so retrying a delivery_id does not add newly registered devices. Email and SMS retain accepted address snapshots so a reset does not follow an intervening email change. Push reads the latest token/version for the chosen endpoint before each call. An invalid-token response disables only the version used by that attempt, preventing an old 410 from deleting a freshly rotated token. Preference is scoped by tenant, list, and channel; opting out of one list affects neither another tenant nor OTP.

Delivery describes an endpoint: queued → leased → provider_accepted, or retry_wait, suppressed, expired, or failed; unknown outcomes require a later retry decision. Attempt logs accepted, rejected, timeout_unknown, or rate_limited for each external call with provider_message_id. Replaying a known successful endpoint only acknowledges it, while remaining endpoints continue, making a notification partially_accepted. Relay and repair updates are conditional so queued cannot overwrite success. Attempt is not a read receipt. A business verification of an OTP proves its use; notification state cannot infer that fact.

写路径：提交在库里，发布在事务外面Write path: the commit is in the database, the publish is outside it

正常路径

校验后按租户和幂等键查 Notification。同摘要命中返回原 id；未命中在一个事务内插入通知、收件人快照和 Outbox，唯一索引冲突就回读赢家。提交成功才回 202。relay 用短事务和 SKIP LOCKED 领取未发布行，写有期限的发布租约后释放数据库锁，再调用 broker；拿到耐久发布确认后才标 published_at。发布租约到期恢复。别在等待 broker 的整个网络周期持有行锁；也别先标已发布再 publish，否则进程中断会丢工作。租约避免常规并发重复，崩溃后的重复发布仍可发生。

Walkthrough

After validation, look up Notification by tenant and key. Matching hashes return the original id; a miss inserts Notification, recipient snapshot, and Outbox in one transaction, and a unique-index loser rereads the winner. Return 202 only after commit. A short relay transaction uses SKIP LOCKED to claim unpublished rows with an expiring publication lease, then releases the DB locks before the broker call. Mark published_at only after durable broker acknowledgment; lease expiry recovers a crash. Do not hold row locks across a broker network round trip or mark publication before publishing. The lease avoids ordinary concurrent publishers but does not eliminate crash-related repeats.

为什么是 outbox，而不是跨库的一句承诺

通知行和队列消息住在两个系统里，没有一个参与者能同时提交两边。把「写库」和「入队」放进口头上的同一步，崩溃点仍然在两次网络往返之间。outbox 把可恢复的事实收进数据库事务：只要提交成功，就一定有一行等着被发布。relay 是补偿进程，允许重复发布。Kafka 的设计说明写得很直接：对 Kafka 以外的目的地，恰好一次通常需要对方系统配合，否则默认是至少一次。[6] 我们不把 FCM 拉进这个数据库事务。

Why an outbox

The notification row and the queue message live in two systems. No single participant commits both. Calling “write the database” and “enqueue” one step still leaves a crash between two network round trips. The outbox pulls the recoverable fact into the database transaction: if the commit succeeded, some row is waiting to be published. The relay is the repair process, and it is allowed to publish more than once. Kafka’s design document says exactly-once toward destinations outside Kafka generally requires those systems to cooperate; otherwise delivery is at-least-once by default. [6] FCM is not enrolled in this database transaction.

故障窗口

提交前失败，用同一把键重试；提交后响应丢失，回读原 id，不创建第二套意图。broker 已收、published_at 尚未记下时，relay 会重发；worker 按 delivery_id 查询已知终态。端点已成功就跳过，外部已成功但本地未知仍可能重复。过期验证码不补发，调用方通过查询状态允许用户重取。

Failure window

Retry a pre-commit failure with the same key; a lost post-commit reply rereads the original intent. If the broker accepted before published_at was recorded, relay publication repeats. Workers inspect delivery_id: known success skips sending, while unrecorded external success may duplicate. Do not resend expired OTP; status queries let the caller offer a new code.

常见错误：先发再落库，或用 SETNX 替代同库唯一索引。前者缺恢复记录，后者把键和通知的成功条件拆成两处。Common mistake: sending before persistence, or replacing DB uniqueness with SETNX. The former loses recovery evidence; the latter splits the success of key and intent across stores.

投递：租约、尝试记录，以及超时和明确拒绝Delivery: the lease, the attempt, and timeout versus an explicit reject

正常路径

Push worker 领取一个 delivery_id，租约按 A8 为 30 秒；先读 Delivery，已知成功就确认而不再发送。否则核对 not_before、not_after、偏好和配额，用 FCM HTTP v1 的短时 OAuth Bearer 调用 messages:send，5 秒超时是本章预算。[1] 成功后在一个本地事务中写 Attempt 和端点 provider_accepted，再 ack。HTTP、查询和写结果的总耗时都要在租约内，长任务续租；租约失效的 worker 停止开始新调用，仍不能撤销在途请求。这里使用带可见性租约的工作队列；若实现选 Kafka，30 秒不是 Kafka 的默认租约，恢复点是分区消费者与提交偏移。[6]

Walkthrough

Push worker claims a delivery_id with the A8 30-second lease and checks Delivery; known success is acknowledged without another send. Otherwise check timing, preference, and quota before FCM HTTP v1 messages:send with a short-lived OAuth Bearer token and this chapter’s 5-second timeout. [1] On success, commit Attempt and endpoint provider_accepted in one local transaction before acknowledging. The total HTTP, lookup, and persistence time must fit the lease; renew long tasks and stop starting calls after losing it, though in-flight requests cannot be recalled. This is a visibility-lease work queue. A Kafka implementation recovers through consumer partitions and committed offsets, not a default 30-second visibility lease. [6]

超时和明确拒绝

5 秒没响应记 timeout_unknown，不判定已送达，也不删除 token。先提交 Attempt、Delivery.next_attempt_at 和重试 Outbox，才确认原消息；持久化失败则让原租约恢复。供应商明确失效是另一类：FCM UNREGISTERED 为 404，停止使用该 token；APNs 410 表示对应 topic 的 token 不活跃，不能无限重推。[2][3] APNs 文档建议 5xx 在 15 分钟后重试，已超过假设 5 分钟验证码寿命，此码应过期，不能套用普通短信的秒级退避。鉴权或模板错误先修配置，未知超时不自动切通道，以免把一次可能已成功的请求变成跨通道重复。

Timeout versus an explicit reject

No reply within 5 seconds records timeout_unknown without declaring delivery or deleting a token. Commit Attempt, Delivery.next_attempt_at, and a retry Outbox before acknowledging the original; failed persistence leaves lease recovery intact. Explicit invalidation is different: FCM UNREGISTERED is 404 and ends use of that token; APNs 410 means inactive for the topic. [2][3] APNs recommends waiting 15 minutes after 5xx, already beyond the assumed 5-minute OTP lifetime, so expire that code rather than borrowing ordinary SMS backoff. Fix authentication or template configuration before retrying. An unknown timeout does not automatically switch channel and turn a possibly successful request into cross-channel duplication.

至少一次的重复从哪来

重复有两个窗口。第一种是 accepted 已写库、ack 丢失，重投查 Delivery 就能跳过；第二种是供应商已接受、本地尚未记录，结果未知，只能在产品允许时重试，仍可能重复。[6] 应用自行处理的推送可以在展示前按 notification_id 去重，但 FCM notification 消息在后台由 SDK 自动展示，应用并不总有机会先拦截。[9] 因而不能承诺通知栏一定只出现一次，邮件和短信也没有统一客户端去重机制。业务验证码验证保持幂等、界面允许重取，比宣称传输端到端恰好一次更可信。

Where the at-least-once duplicate comes from

There are two duplicate windows. If accepted is durable but the queue acknowledgment is lost, replay checks Delivery and skips sending. If the provider accepted before any local record, the outcome is unknown and an allowed retry may repeat it. [6] App-managed push can deduplicate notification_id before display, but a background FCM notification message is displayed automatically by the SDK, so the app cannot always intercept first. [9] Neither the notification tray nor email and SMS have a universal dedupe guarantee. Keep business OTP verification idempotent and allow requesting a new code; transport cannot promise end-to-end exactly-once.

常见错误：把 accepted 当用户已读。供应商结果、展示和业务验证码验证是三个不同终点。[1][3][4]Common mistake: calling accepted “read.” Provider acceptance, display, and business OTP verification are separate endpoints. [1][3][4]

扇出：过滤和限流画在供应商调用之前Fan-out: the filter and the rate limit sit before the provider call

正常路径

活动提交后，Expander 按 A5 的 1,000 人一页读稳定受众快照。每页用 (campaign_id, user_id) 唯一键建意图，在同一事务中更新游标并生成展开 outbox；发布和标记之间的重复仍由端点键吸收。Push worker 只处理一个端点，先查营销同意和用户 IANA 时区；静默时段把任务写成 not_before。醒来重新检查偏好、过期和频控，不从旧快照复用同意。图中的 Preference gate 和 Rate gate 是 worker 内部步骤，供应商回复直接回 worker；它们不是两个要跳过回程的 RPC 服务。OTP 跳过营销规则，仍过安全限制和真实供应商配额。

Walkthrough

After campaign commit, Expander reads the stable audience snapshot in A5 pages of 1,000 users. A (campaign_id, user_id) uniqueness constraint creates intents while a local transaction updates the cursor and writes expansion outbox work; endpoint keys absorb publication repeats. Push worker handles one endpoint and checks marketing consent and the user’s IANA time zone; quiet hours create a durable not_before. The pictured Preference gate and Rate gate are local worker steps, so provider replies go to that worker; they are not RPC services omitted from the response chain. OTP bypasses marketing rules but retains abuse limits and real provider quota.

为什么缓存只放在这里

Preference 是权威，缓存键包括 tenant、user、channel 和 list。千万不同用户的第一轮查询并不自动有高命中率；缓存主要复用跨设备和同窗口重试的读，冷活动仍要分页回主库并限速，不能画上缓存就假设主库零压力。A9 的 60 秒从权威读取开始计时，抖动只缩短；回填沿用原到期时间，不能重新给满 60 秒。退订提交并记录失效 outbox，删除和重试只能缩短旧值窗口；已启动的旧读仍可能迟到回填。可用版本栅栏拒绝旧版本，要求更严时在发送前读主库；在途供应商请求仍不可撤回，也不能保证只多发一条。

Why a cache exists only here

Preference is authoritative and cache keys include tenant, user, channel, and list. A first pass over ten million distinct users is not automatically a cache hit; the cache mainly reuses cross-device and retry reads. A cold campaign still pages primary reads under a cap. A9 starts the 60-second ceiling at authoritative-read initiation and jitter only shortens it; late fills retain the original expiry. Unsubscribe commits invalidation outbox work; deletion and retries shorten staleness, but an older in-flight read can refill later. A version fence may reject old fills, or stricter products read the primary before sending. In-flight provider calls remain irreversible, and staleness cannot be bounded to one extra message.

两层限流，两种用户可见结果

入口限流在 202 之前拒绝过量活动或恶意验证码请求，返回 429 与 Retry-After。排水限流在 202 之后管理已经接受的工作，耗尽配额就持久化 next_attempt_at，而不是向已结束的 HTTP 返回 429。worker 先为用户频次预占一个 delivery_id 名额，再扣租户和供应商配额；重复消费复用该预占，避免一条消息多扣次数。明确失败可以释放用户名额，未知结果保守保留到窗口结束。OTP 预留独立 worker 和供应商配额，营销只能借用空闲份额；跨租户公平不能靠同一个 tenant_id 全压进一个分区。

Two rate limits, two visible outcomes

Admission limits reject excess campaigns or OTP abuse before 202 with 429 and Retry-After. Drain limits manage already-accepted work after 202, persisting next_attempt_at when quota is exhausted instead of replying to a finished HTTP request. Reserve a user-frequency slot under delivery_id before spending tenant and provider quota; replays reuse it instead of charging the same message twice. Definite failures may release the user slot, while unknown sends conservatively retain it through the window. Reserve both OTP workers and provider quota and let marketing borrow idle capacity. Tenant fairness does not come from pinning all of tenant_id to one partition.

常见错误：先发后过滤，或用机房时区代用户时区。两者都在真正打扰之后才发现决策错了。Common mistake: filtering after sending, or using the datacenter zone for a user. Both discover the wrong decision after the interruption.

故障：一条通道倒下时，其他通道还在走Failure: when one channel falls over, the others keep moving

四种用户能感知的失败Four failures a person can actually notice

1 · 供应商不可用

普通 SMS 按 A10 初次后最多重试 3 次，等待采用带抖动的指数退避且不早于供应商 Retry-After，不能在 worker 里 sleep 占着租约。SMS worker 持久化计划，Retry scheduler 到点交还同通道，次数用尽进入 SMS DLQ 并告警。验证码每次先检查 5 分钟 not_after，过期直接终态。明确不可用时可以由 worker 选备用聚合商；结果未知时切备用可能重复收费和展示，必须由产品接受这个代价。同一业务码只在明确允许的通道里发送，不因故障自行追加短信。

1 · Provider unavailable

Normal SMS has at most three retries under A10, with jittered exponential delays no earlier than provider Retry-After. Do not sleep inside a worker while holding its lease. SMS worker persists the plan; Retry scheduler returns due work to the same channel and exhausted work enters SMS DLQ with an alert. OTP checks its five-minute not_after before every call and expires directly. A worker may select a backup for definite unavailability; failing over an unknown outcome can duplicate cost and display and needs a product policy accepting that trade. Send the same business code only over explicitly allowed channels; failure does not add SMS automatically.

2 · 热门租户或热门 token

热门活动耗尽营销份额时，该租户排得更久，OTP 使用预留消费池和配额。APNs 的 429 针对同一 token，退避该端点而非全租户。[3] 入口 429 则是接受前拒绝，调用方立即知道没有新意图；这与 202 之后的内部排水延迟不同。

2 · Hot tenant or hot token

A hot campaign waits longer once its marketing share is exhausted; OTP uses reserved consumers and quota. APNs 429 targets the same token, so back off that endpoint rather than the tenant. [3] Admission 429 rejects before acceptance, whereas internal drain delay follows a completed 202.

3 · 重复展示

用户看见两条推送，可能是外部已接受、本地记录前退出，恢复无法证明第一次成功。端点 Delivery 能消除已知成功后的重投，消不掉这个未知窗口；应用控制展示时可以去重，自动展示时不能一概承诺。[6][9] 邮件和短信更直接地暴露重复。监控分别记录 unknown 比例和同 delivery_id 的尝试次数，不把多设备的合法发送算作重复。若重复不可接受，未知结果要先查询供应商可用的请求状态或转人工核查，代价是延迟或漏发，而不是换一个新的 notification_id 掩盖问题。

3 · Duplicate display

Two visible pushes may follow external acceptance and a crash before local persistence, leaving recovery unable to prove success. Delivery suppresses known-success replays, not this unknown window. App-controlled display can dedupe while automatic display cannot promise it. [6][9] Email and SMS expose repeats more directly. Measure unknown outcomes and repeated attempts per delivery_id, distinguishing legitimate different endpoints. If duplicates are unacceptable, first query provider status when available or investigate an unknown outcome; the cost is delay or omission, not a fresh notification_id hiding the problem.

4 · 已经 202，人还没收到

202 表示请求已接受，界面应显示正在处理而非已经送达。relay 或供应商延迟超过 not_after，任务进入 expired，允许重取。供应商健康但队列过老要告警；营销静默按用户时区计算，到点仍重新检查，不能把旧偏好快照一路带到调用。

4 · 202 already returned, nothing in the hand yet

202 means accepted, so show processing rather than delivered. If relay or provider delay outlives not_after, expire the task and allow a new request. Alert when queues age despite healthy providers. Marketing quiet hours use the user’s zone and due work rechecks preference rather than retaining old consent.

常见错误：把通道隔离和配额隔离混为一谈。独立消费池避免头阻塞，共享供应商配额仍需调度预留。[7]Common mistake: confusing consumer isolation with quota isolation. Independent pools prevent head-of-line blocking; shared provider quota still needs reservations. [7]

退订和伪造：信任边界上只有一扇窄门Unsubscribe and spoofing: one narrow door on the trust boundary

正常路径

营销邮件带 HTTPS 的 List-Unsubscribe 和 List-Unsubscribe-Post: List-Unsubscribe=One-Click；有效 DKIM 必须覆盖两头，这是邮箱决定是否提供一键退订时验证的条件。[5][8] 入口处理的是另一次 HTTPS POST，校验绑定 tenant、user、channel、list 的随机能力，不依赖 cookie、HTTP 登录或邮件 From。提交 opt-out、版本递增和失效 outbox 后回 202，再删除缓存；删除失败仍可恢复。不要重定向这个 POST，也不要让邮件预取的一次 GET 改偏好。令牌有效期要覆盖营销邮件合理寿命，不用验证码的短寿命照搬到退订链接。

Walkthrough

Marketing mail carries an HTTPS List-Unsubscribe URI and List-Unsubscribe-Post: List-Unsubscribe=One-Click; valid DKIM covers both headers, which the mailbox verifies when offering one-click unsubscribe. [5][8] The endpoint handles a separate HTTPS POST and checks a random capability bound to tenant, user, channel, and list, independent of cookies, HTTP login, and mail From. Commit opt-out, the new version, and invalidation outbox before 202, then delete the cache with durable recovery if needed. Do not redirect this POST or let a prefetched GET mutate preferences. Capability validity must cover the useful lifetime of marketing mail rather than copying the short OTP lifetime.

为什么是能力令牌，而不是登录页

一键退订由邮箱服务器代用户请求，要求浏览器登录会挡住它。能力令牌允许持有者仅退订指定列表，不能充当账户删除或密码重置凭证。用户同意、静默和设备可用性也分开：营销 opt-out 不阻止业务验证码；但操作系统关闭推送权限不一定立刻让 token 失效，供应商接受仍可能没有可见通知。只有明确 UNREGISTERED 或 410 才按被调用的 token 版本停用。[2][3] 不能从“用户没看到”推断卸载或自动转发短信。

Why a capability, not a login page

One-click unsubscribe is the mailbox server acting for a user; requiring browser login blocks it. Its capability can only unsubscribe the specified list, not delete an account or reset a password. Keep marketing consent, quiet hours, and endpoint validity distinct. Opt-out does not stop business OTP; disabling OS push permission does not necessarily invalidate a token immediately, so accepted sends may remain invisible. Disable only the attempted token version after explicit UNREGISTERED or 410. [2][3] Missing display does not prove uninstall and does not authorize automatic SMS fallback.

伪造和内部路径

伪造邮件与伪造 POST 是两种入口。前者若缺有效 DKIM 覆盖，邮箱按 RFC 8058 不应提供一键退订；后者若没有正确能力令牌，公开入口返回 4xx，不写 Preference。[5] 真令牌被转发或泄露，持有者仍能退订指定列表，所以权限要窄且操作幂等。缓存失效成功也不承诺撤销已经在途的营销；若要求严格从提交之后停止新发送，把营销发送门与偏好版本核验协调，说明仍存在提交前已启动的请求。图中的淡红线是 opt-out 后发送的被否决路径。

Spoofing and the internal path

Forged mail and forged POST are different entry points. Without valid DKIM coverage, the mailbox should not offer one-click unsubscribe under RFC 8058; without the right capability, the public endpoint returns 4xx without modifying Preference. [5] A forwarded or leaked real capability can still unsubscribe its narrow list, so keep its scope small and the operation idempotent. Successful cache invalidation cannot recall marketing already in flight. A stricter stop-after-commit policy coordinates the send gate with preference-version validation and still accounts for requests started before commit. The muted red send path is the rejected action after opt-out.

追问：从新约束往下改Follow-ups: change the design from a new constraint

1 · 「Kafka 事务不是已经恰好一次了吗？」

Kafka 事务能协调 Kafka 主题之间的读写及消费偏移；外部目的地需要配合。[6] relay 从数据库读 outbox，即使开了幂等生产者，也只减少同一生产者会话内的网络重试重复，不能消除 relay 崩溃后重新读取同一行的第二次发布。真正防已知重复仍依赖稳定 delivery_id 和端点终态；FCM、APNs、SMTP 不参与本地提交，外部未知结果也不会因 broker 换产品而消失。

1 · “Don’t Kafka transactions already give exactly-once?”

Kafka transactions coordinate Kafka topic writes with consumer offsets; external destinations need cooperation. [6] A DB outbox relay with an idempotent producer reduces network-retry duplicates within its producer session, not republication when a crashed relay rereads a row. Known repeats still need stable delivery_id and terminal endpoint state. FCM, APNs, and SMTP do not join the local commit, and changing brokers does not remove unknown external outcomes.

2 · 「用户已读怎么做？」

这版不做已读权威。推送的 200 和邮件的 250 都停在供应商接受。若产品要「用户打开了邮件」，那是另一条不可靠的像素或链接回调，容易被预取、被隐私功能挡住，不能写进投递 SLO。支付或验证码若必须确认「人用过这码」，确认点在业务系统的校验接口，不在通知状态机的下一格。

2 · “How do we know the user read it?”

This version has no read authority. Push 200 and mail 250 stop at provider acceptance. If the product wants “the user opened the mail,” that is a separate, unreliable pixel or link callback, easily defeated by prefetch and privacy features, and it does not belong in the delivery SLO. If a payment or a code must confirm that a person used it, the confirmation is the business system’s verify call, not the next state in the notification machine.

3 · 「多 Region 呢？」

先问多地域为了接受延迟还是地域故障恢复。单主仍满足 200 ms 时不必改写入权威；满足不了，再讨论按租户归属地域及跨地域恢复。多写者需要幂等冲突、通知重放归属和偏好版本复制；A 区已退订、B 区仍用旧值是新的窗口。多地域不会提高供应商配额，也不能消除 1.94 小时排水下界，先定位约束再加地域。

3 · “What about multiple regions?”

Ask whether regions address acceptance latency or regional-failure recovery. Keep one write authority if it still meets 200 ms; otherwise discuss tenant home regions and cross-region recovery. Multiple writers introduce idempotency conflicts, notification replay ownership, and preference-version replication, including opt-out in A with stale consent in B. Regions do not increase provider quota or remove the 1.94-hour drain bound. Identify the constraint before adding them.

4 · 「模板在哪渲染？」

模板在过滤和配额之后、供应商调用之前按 locale 和固定 template_version 渲染。版本固定才让重试内容一致。验证码不能只存在接受请求的内存里，否则返回 202 后进程重启，worker 无法重建消息；用短期加密载荷或加密引用随意图耐久保存，保留到 not_after，再清理，不写普通日志。业务系统保存验证所需的摘要，通知系统只拿到发送所需的受限内容。接受前不渲染千万份营销正文，重试时也不重新生成业务验证码。

4 · “Where is the template rendered?”

Render after policy and quota checks and before the provider call, using locale and fixed template_version so retries preserve content. OTP cannot live only in accept-request memory: after 202 and a restart, workers must reconstruct it. Persist short-lived encrypted content or an encrypted reference with the intent until not_after, then clean it up and omit it from ordinary logs. The business service owns the verification digest; notification workers receive only restricted send content. Do not render millions of marketing bodies before acceptance or mint a new business code on notification retry.

中文

收尾沿图讲三笔：通知和 outbox 同事务提交后回 202；端点 Delivery 和耐久重试减少丢失与已知重复，但保留外部未知窗口；偏好、频控和供应商配额在发送前检查，OTP 只绕过营销规则。活动独占配额下约 1.94 小时，共享日常平均流量时约 10.24 小时，两个都不是 API 延迟。供应商接受始终不等于用户看见。

English

Close on three paths: commit intent and outbox before 202; use endpoint Delivery and durable retries to reduce loss and known duplicates while retaining unknown external outcomes; check preferences, frequency, and provider quota before sending, with OTP bypassing only marketing policy. Campaign bounds are 1.94 h with exclusive quota and 10.24 h with daily average contention, neither an API latency. Provider acceptance never proves display.
