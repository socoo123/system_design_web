1 · 分层：沿访问路径算保留成本1 · Tier by access and size retention

中文

正常点查沿 Client→Query→Hot KV→Query→Client 往返。查询协调器（Query）先完成鉴权，再用包含租户和事件标识的键读取。Hot KV 是服务点查的索引视图，丢失后应从持久事件重建。报表则沿 Query→Scan Worker→Object Files 读取数据，由扫描工作进程（Scan Worker）把局部结果返回 Query，再交给客户端。这两条路径服务不同目标；分析查询不应遍历在线 KV，把事件逐条取出再做 SUM。

热、温、冷描述访问频率和时效要求，列存描述文件布局，对象存储描述保存字节的介质，三者可以组合。近期 Parquet 文件放在对象存储上，配合活跃的扫描工作进程和缓存，就可以组成温层；冷数据仍可保留同一格式，只减少常驻算力或调整访问约定。湖仓论文讨论的是低成本存储上开放文件与管理能力的结合 [8]，并不要求数据从温层转冷时，必须跨三种产品搬运一份全量。

先按原始容量等价比较成本：全部放热存储为 365×100=36,500 单位/月；若一天的热视图等价于 1 TB，其余 364 TB 放对象存储，则为 1×100+364×10=3,740 单位/月，约减少 89.8%。这是 A4 的简化推导，不是实际报价；30 天温层窗口也不意味着必须再复制 30 TB。热视图索引、重建时的临时副本、存储请求、跨区流量和 Worker 计算费都应另列。压缩会改变物理容量，因此逻辑 TB 不能直接当作计费 TB。

把旧数据移到冷层后，不能立即删除热层数据。先完成持久输出，核对事件范围和数量，再发布可查询的位置，最后等旧读者结束才回收。按事件时间划分边界时还要处理迟到：今天收到的事件可能属于昨天。跨热视图和历史表联合查询，需要固定各分区输入位点组成的向量和查询边界，或按 event_id/version 去重。仅按墙上时钟切成两段再 UNION，可能漏算或重复计算。本章把两类接口分开，不承诺未经协调的跨库原子快照。

故障时仍要遵守访问约定。热视图可以重建，但不能让全部毫秒级点查都退回全湖扫描；应限制回源量，或明确返回不可用。冷对象若需恢复，就提交有稳定标识的查询任务，返回 RESTORE_PENDING，按租户限制并发，并允许查询和取消任务。对象服务也有低延迟访问形式 [10]，因此不能仅凭存储介质断言“对象永远慢”或“冷层都是秒级”。调整冷热分配时，要同时看访问频率、恢复成本和延迟目标；旧热门数据可以重新缓存，其事件时间和数据年龄不会因此改变。

English

Point reads follow Client→Query→Hot KV and return through Query; authorize tenant/event keys first. Hot KV is rebuildable from durable events. Reports use Query→Worker→Files with partial results returning hop by hop. Bulk analytics should not enumerate the online KV.

Temperature, file layout and byte-storage medium are different axes. Recent Parquet objects with active workers/cache are warm; cold data can keep that format with less resident compute or a different access contract. Lakehouse discusses managed open files over low-cost storage [8], not mandatory full copies across three products.

At illustrative raw-equivalent A4 rates, all-hot is 365×100=36,500 units/month; one hot TB plus 364 object TB is 100+3,640=3,740, about 89.8% lower. This excludes indexes, temporary copies, requests, networking and compute. The warm window is not another mandatory 30 TB copy; compression changes billed bytes.

Tier handoff needs durable output, range/count validation, location publication and old-reader completion before cleanup. Late arrivals can belong to yesterday. A combined hot/history query needs fixed input progress and a query boundary or event/version deduplication; a wall-clock UNION can miss or duplicate events. The diagram separates interfaces and promises no uncoordinated cross-store atomic snapshot.

Protect contracts on failure: rebuilding Hot KV does not justify sending all point traffic into lake scans. Bound fallback or fail explicitly. Restore-dependent queries become identified, cancellable RESTORE_PENDING jobs with tenant limits. Object services include low-latency modes [10], so medium alone does not determine latency. Old popular data can be cached without changing its event time.

2 · 列存：先排除文件和列，再算 CPU 开销2 · Columnar scans: files, columns and CPU

中文

Query 解析 SUM(price) 和时间、国家过滤条件，规划器根据固定快照选出候选文件；Worker 再读取所需页范围、解码、精确过滤并完成局部聚合。Parquet 在行组（row group）中按列组织列块（column chunk），通过文件元数据定位所需内容 [3]。图中的 decode 和 local sum 都是同一个 Worker 内的执行算子。Query 汇总局部结果后才返回 Client，文件服务不能把尚未聚合的金额列直接交给客户端。

A3 的报表有全表读取权限，不按 tenant_id 过滤行。如果租户报表必须读取 tenant_id，而可靠元数据又无法证明候选数据都属于该租户，就需要读取 4 列：1 TB×4/20÷4=50 GB。8 台 Worker 独占资源时，扫描下界为 25 s；两条查询均分时为 50 s。不能因为已经鉴权，就漏算过滤所用的字段。处理删除所需的字段和 delete 文件也要另算；37.5 GB 只覆盖三列数据页，并非查询的全部 I/O。

按 A3，先用一天的时间范围把 30 TB 原始候选缩小到 1 TB，再读取 20 个等宽字段中的 3 个，得到 150 GB 未压缩列数据；按 A4 压缩 4:1 后为 37.5 GB。30,000 GB÷37.5 GB=800，比较基线是扫描全时段、全部字段的原始数据，而非已经压缩的行存。时间剪枝贡献 30 倍，减少列数贡献约 6.67 倍，压缩贡献 4 倍，三者相乘才得到 800 倍。

少读列减少的是完整事件内容 payload 的搬运，并没有消除所有 CPU 开销。过滤所需的 country 和 event_time 仍要读取；若没有可用统计来排除数据页，即使最终能过滤掉很多行，也仍需读页并解码。相似列值有利于字典、RLE 等编码，高基数字符串或加密 payload 则未必容易压缩。只读取少数列，也可能产生更多随机范围请求。向量化一次处理一批值，延迟物化则在确有需要时才拼成完整行；这些能力共同降低执行成本，不能把列式引擎理解为“每列拆一张行表” [2]。

Dremel 的 T1 实验包含 850 亿条记录、87 TB 未压缩数据。单列实验读取约 0.5 TB 压缩数据，按记录布局的 MR 则读取约 87 TB。两者的压缩和执行模型都不同，因此 174 倍只表示该实验的读取字节比，不能用作本章的延迟承诺。[1 §7 / Figure 10]

A5 假设 8 台 Worker 合计有效吞吐为 8×250 MB/s=2 GB/s，因此 37.5 GB÷2 GB/s=18.75 s。这只是独占带宽、且没有其他瓶颈时的数据扫描下界。两条查询均分资源后，每条只有 1 GB/s，下界变为 37.5 s，已经超过 A2 的 30 s 目标。此时应控制并发、在实测基础上增加资源，或缩小查询范围。COUNT DISTINCT 和高基数 GROUP BY 还会扩大聚合状态与 shuffle 开销；读取很多列或拼接完整记录时，列存的收益也会减小。

English

Query plans a snapshot-bound SUM with time/country filters. Workers get page ranges, decode, filter and partially aggregate. Parquet column chunks sit inside row groups, and metadata locates needed content [3]. Decode/sum are local operators, not remote services. Query merges partials before replying.

A3 is an authorized whole-table report with no tenant_id row filter. A tenant report that must read tenant_id needs 4 fields unless trusted metadata proves tenant scope: 1 TB×4/20÷4=50 GB, with 25 s exclusive or 50 s shared scan lower bounds. Include delete fields/files separately; 37.5 GB covers only the three data fields, not all query I/O.

Dictionary/RLE benefit suitable values, not arbitrary high-cardinality or encrypted payloads. Vectorized operations and late materialization complement column layouts; vertically splitting row tables is not a complete engine [2].

关键实现：内存放不下时，分块落盘并限制归并路数Implementation: spill bounded chunks and merge with bounded fan-in

第 2 组图中的 local sum 遇到高基数 GROUP BY 时，不能让 HashMap 无限制增长。下面是仅使用标准库的可运行 Java17 摘录。输入行已经鉴权、固定 snapshot、精确过滤，并应用了应生效的删除；分组键长度有上限，金额非空且以整数分表示。算法先对最多 B=maxRows 行排序，把同键金额相加，写成有序临时文件（run）；随后每次最多合并 F=fanIn 份文件，直到得到一份完整候选结果。国家列通常只有少数取值，这个算法也能处理取值更多、但键长度仍有上限的分组。

The local sum in deck 2 must not grow a hash map without bound for high-cardinality GROUP BY. This runnable Java17 excerpt uses only the standard library. Input rows are already authorized, snapshot-bound, exactly filtered and delete-aware; values are non-null integer cents with bounded keys. Sort and reduce at most B=maxRows rows per run, then merge at most F=fanIn runs per wave until one complete candidate remains. Country normally has few groups; the same algorithm supports higher-cardinality bounded keys.

static Path aggregate(Iterator<Row> input, int maxRows, int fanIn, Path job)
        throws IOException {
    if (maxRows < 1 || fanIn < 2) {
        throw new IllegalArgumentException("budget");
    }

    Files.createDirectory(job); // unique attempt; never overwrite another job
    Path stage = Files.createDirectory(job.resolve("stage-0"));
    long count = 0;
    while (input.hasNext()) {
        List<Row> block = new ArrayList<>();
        while (block.size() < maxRows && input.hasNext()) {
            block.add(input.next());
        }
        block.sort(Comparator.comparing(Row::key));
        writeChunk(block, stage.resolve("run-" + count++));
    }
    if (count == 0) {
        return Files.createFile(stage.resolve("run-0"));
    }

    for (int pass = 1; count > 1; pass++) {
        Path next = Files.createDirectory(job.resolve("stage-" + pass));
        long outputs = 0;
        for (long first = 0; first < count;) {
            List<Path> group = new ArrayList<>();
            for (int n = 0; n < fanIn && first < count; n++, first++) {
                group.add(stage.resolve("run-" + first)); // expected identities
            }
            merge(group, next.resolve("run-" + outputs++)); // a missing run fails
        }
        removeStage(stage); // only after the entire next wave is complete
        stage = next;
        count = outputs;
    }

    Path candidate = stage.resolve("run-0");
    try (InputStream verify = Files.newInputStream(candidate)) {
        verify.read();
    }
    return candidate; // readable now; publication/retention is the caller's job
}

static void merge(List<Path> runs, Path output) throws IOException {

            Comparator.comparing((Head h) -> h.row().key())
                    .thenComparingInt(Head::reader));

    try (RunReaders readers = new RunReaders(runs);
         BufferedWriter out = Files.newBufferedWriter(output,
                 StandardOpenOption.CREATE_NEW, StandardOpenOption.WRITE)) {
        for (int i = 0; i < runs.size(); i++) {
            Row row = readRow(readers.get(i));
            if (row != null) {
                queue.add(new Head(i, row));
            }
        }

        String key = null;
        long sum = 0;
        while (!queue.isEmpty()) {
            Head head = queue.remove();
            Row row = head.row();
            if (key != null && !key.equals(row.key())) {
                writeRow(out, new Row(key, sum));
                sum = 0;
            }
            key = row.key();
            sum = Math.addExact(sum, row.cents());

            Row next = readRow(readers.get(head.reader()));
            if (next != null) {
                queue.add(new Head(head.reader(), next));
            }
        }
        if (key != null) {
            writeRow(out, new Row(key, sum));
        }
    }
}

A7 每天生成 100×1,440=144,000 个小文件，30 天累计 4,320,000 个。一天即使只有几百 GB，文件打开、任务规划和元数据处理也可能先成为瓶颈。表格式的 manifest 减少了规划时 LIST 整个桶的需要，但候选文件跟踪、范围请求、文件尾部元数据（footer）读取和任务调度仍有成本，不能把小文件的所有代价都归为 LIST。延长写入批次、按分区汇聚写入方或在上游缓冲，都能从生成端减少碎片，代价是数据更晚可见。

合并时，先在 s41 中固定 128 个 4 MB 输入，读取应生效的版本和删除，再写出约 512 MB 的候选文件。Catalog 原子发布 s42，从表集合中移除这批输入，同时加入输出。Iceberg 的维护文档说明，小文件合并可以减少元数据和文件打开成本 [7]。这种 rewrite 保持逻辑行集合不变，不能先追加一份重复数据，再慢慢删除旧文件。它与 LSM 层间合并都有重写数据的思路，但对象、索引和发布协议不同，LSM 的细节见 Ch37。

按 A8 的串行模型，打开原来 128 个文件需 128×10 ms=1.28 s，合成一个后约为 10 ms。实际请求可以并行，大文件也可能拆成多个扫描任务，因此不能保证延迟降低 128 倍。文件数据量仍约 512 MB；最低重写流量是读 512 MB 加写 512 MB，共 1.024 GB。保留旧快照时，这批新旧对象的峰值占用也至少约 1.024 GB，元数据、失败输出和额外副本另算。目标文件过大还会减少任务并行度，需要结合分区大小和查询范围调整，512 MB 并非固定的最优值。

并发 DELETE 若恰好作用于这批输入，合并进程（Compactor）不能只检查 current 指针是否变化。它要验证输入集合、相关删除和序列规则是否仍兼容，必要时重新读取删除或重新选择输入，并在发布时保留表格式规定的删除适用规则。另一个 Compactor 已经替换的输入，也不能用旧内容重新加回表中。CAS 保证原子发布；语义验证才决定这个候选是否仍可发布。恢复时遗漏验证，可能把已删除的数据重新写回来。

GC 既要确认当前表不再引用对象，也要确认其他合法操作不再需要它。旧快照、分支或受保护读者仍有引用，就必须保留旧文件。尚未提交的输出也可能仍在写入、提交结果未知或等待重试，不能立即回收。维护文档提醒，未引用对象（orphan）的保留窗口过短，可能删除仍在进行中的文件 [7]。因此不能套用一个统一 TTL：先检查可达集合和提交标识，再满足写入方安全窗口。对象生命周期策略也要与表保留规则协调，否则桶的自动过期可能绕过 Catalog，破坏仍可读取的快照。

English

A7 creates 144,000 files/day and 4.32 million in 30 days. Manifests reduce bucket-list planning, but candidate metadata, range/footer requests and task scheduling still cost work. Larger batches or partition-aware writer aggregation reduce fragmentation at the cost of freshness.

Read 128×4 MB inputs in s41 with applicable versions/deletes, write roughly 512 MB output, then atomically remove inputs/add output in s42. Iceberg maintenance links compaction to lower metadata and file-open costs [7]. This preserves logical rows rather than append duplicates and later delete them; Ch37 covers LSM-specific mechanisms.

The serial teaching open cost falls from 1.28 s to about 10 ms. Real opens and scan splits are parallel, so latency need not fall 128×. About 512 MB stays logically present; rewrite traffic is at least 1.024 GB and overlapping old/new objects occupy at least 1.024 GB for this set. Tune target size against parallelism and query scope.

Concurrent DELETE/rewrite requires validating input identity and deletion/sequence compatibility, then rereading or replanning when necessary. Another compactor may already have replaced inputs. CAS provides atomic publication; semantic validation decides whether the candidate remains safe. Retrying stale content can resurrect rows.

GC distinguishes absence from current metadata from safety for every legal operation. Retain snapshot/branch/reader references and protect writing, UNKNOWN and retry candidates. Maintenance warns that short orphan retention can delete in-progress files [7]. Check reachability, commit identity and writer lifetime; coordinate object lifecycle with table retention.

7 · 批流与回放：隔离重算结果，再切换读取入口7 · Batch/stream replay and verified cutover

中文

Lambda 让批计算结果和实时增量共同服务，需要维护两套逻辑，并约定如何合并。Kappa 则用同一类流处理模型，依靠可回放输入重算。Kreps 2014 年的原文讨论了双栈复杂度，并描述让新版本处理器重放历史、追平后切换输出的方法 [9]。这只是选型起点；能否正确复算，还取决于输入留存、外部依赖版本、状态初始化、迟到处理规则和下游幂等。需要大量有界 shuffle 的任务，也未必适合放进持续流算子。

图中 Processor v1 持续提交 View v1，对应的下游提交确认后才推进消费位点。源记录用 (stream, partition, offset) 稳定标识；同一业务事件若出现在不同位点，还需用 event_id/version 去重。每次重跑都变化的随机 batch ID，无法识别同一批输入。Processor v2 从 S 回放到独立的 View v2，不能把历史计数再加到在线累计结果中。若下游（sink）已提交、位点检查点（checkpoint）尚未写入就崩溃，恢复后会重读这一批，需要稳定 batch/event_id，并在下游原子处理去重与业务结果。只说流引擎提供“exactly once”，还不足以证明外部表、邮件或计费只产生一次效果，必须说明 sink 的提交协议。

Lambda 也必须写清合并边界：批结果覆盖哪些输入位点，流结果从哪里接续，迟到和更正由哪一侧处理。事件时间早于今天，不代表它已进入昨夜批结果；直接相加“批算昨天、流算今天”，可能漏掉迟到数据，也可能重复计算正在刷新的那一段。应按各分区输入位点定义覆盖范围，再更正历史窗口，或按稳定事件版本重算。事件时间水位（watermark）反映处理策略，并不证明每个分区都已持久完成到相应输入位点（durable offset）。

回放耗时要按净吞吐计算。A11 的积压为 1 TB，回放有效吞吐为 100 MB/s，同时新增 20 MB/s，净吞吐为 80 MB/s，因此 1,000,000 MB÷80=12,500 s≈3.47 h。若只除以 100，会得到 2.78 h，漏算实际追赶期间新增的 250 GB。回放只有 20 MB/s 时，积压不会减少；低于 20 MB/s 时，积压反而增长。输入保留期必须覆盖从 S 到追平完成的范围，并预留部署和故障恢复时间，不能让源日志在回放途中删掉 S 之后尚未读取的片段。

本章统一用 next-offset 表示位点：S[p] 是分区 p 的起始位置，H[p] 是接下来尚未处理的位置，回放范围为 [S[p],H[p])。H 只能越过已经连续、持久完成的前缀，不能直接取所有 Worker 已完成 offset 的最大值。切换前，v2 必须证明该范围内的状态和输出都已持久保存，并核对行数、关键聚合、删除和迟到更正，之后才按条件发布读取入口。若要求切换无缺口，可以短暂停消费，或建立可恢复的切换屏障，确保 v2 从各分区 H 接续新增输入，v1 不再产生权威的新输出。旧视图仍要保留给在途读者和经过验证的回退；新视图接收更多写入后，回退旧版也要补齐这些变化。修正回放逻辑时，还必须遵守历史删除和权限撤销，不能从原始日志把它们重新恢复出来。

English

Lambda merges batch and live increments with two logic stacks; Kappa reuses stream processing over replayable input. Kreps describes replaying with a new processor and switching output after catch-up [9]. Correctness still requires retention, versioned dependencies, state initialization, late-event policy and idempotent output.

Processor v1 commits View v1 before checkpointing; v2 replays from S into isolated View v2. Stable source identity is (stream,partition,offset); business duplicates at different offsets need event_id/version deduplication too. A new random batch ID per retry is insufficient. A crash after sink commit but before checkpoint repeats input, requiring stable identities and atomic deduplicated effects. Engine-level exactly-once language does not establish external sink, email or billing semantics.

Lambda needs explicit batch coverage, streaming start and correction ownership. Yesterday’s event time does not prove inclusion in yesterday’s batch. Define coverage with partition-specific input progress and correct/recompute late versions; an event-time watermark is not a durable consumed offset.

Drain 1 TB at net 100−20=80 MB/s: 12,500 s≈3.47 h. Dividing by 100 gives 2.78 h and omits 250 GB arriving during true catch-up. At or below 20 MB/s there is no convergence. Retention must cover S through completion plus deployment/recovery margin.

Use next-offset conventions: S[p] starts partition p, H[p] is its next unprocessed position, and replay covers [S[p],H[p]). Advance only a contiguous durable prefix, never the maximum completed worker offset. Prove durable state/output coverage for this range, validate counts/aggregates/deletes/corrections, then conditionally publish the read entry. A recoverable barrier or brief pause can coordinate continuation after H. Retain old views for readers and validated rollback, which must include newer changes. Replay must respect historical deletions and revoked access.

中文

这些机制也能用于前面的设计题。搜索 Ch13 用倒排服务支持在线检索，把查询日志放入温层列存，并保留可回放的构建输入。对象存储 Ch22 保存字节，表格式管理一致的文件集合，两者需要协调删除和保留规则。排行榜 Ch23 分开维护实时有序视图和历史赛季表，结束的赛季也可能因审计再次变热。消息队列 Ch20 的日志负责输送和回放输入，但保留期有上限；落地后的表提供另一种读取接口，不能把 Kafka 当作容量无限的数仓。

问到“高基数 ID 能不能做分区”时，应看查询方式和文件规模。固定数量的 bucket(id) 可以限制桶数，点查仍需要合适的索引和文件统计。问到“文件是否越大越好”时，要一起分析打开成本、任务并行度、重写峰值、查询时间范围和延迟目标。批计算也不天然正确：重复输入、逻辑错误、删除处理和快照选择都会影响结果，仍需遵循明确一致的业务定义并校验。

讲述时可以沿“访问要求 → 文件与列剪枝 → 有界分治 → 原子发布 → 受保护的回收 → 隔离回放”展开，并在相应步骤指出失败条件：漏算过滤字段、run 缺失、UNKNOWN 时盲目重试、GC 抢在读取保护登记前删除文件，或位点跨过未完成记录。数字用于检验设计选择，不能代替实现必须提供的保证。下一章 Ch44 将把这些数据约定放回服务治理中讨论。

English

Ch13 keeps online inverted indexes separate from analytic query logs; Ch22 stores bytes while table formats manage coherent sets and coordinated retention; Ch23 separates live boards and historical seasons. Ch20 logs transport/replay data with bounded retention rather than act as an infinite warehouse.

High cardinality is not a blanket partitioning ban; bounded buckets can fit a workload. Bigger files trade fewer opens against parallelism and rewrite peaks. Batch processing is not inherently correct: duplicate input, bugs, deletions and snapshot selection still need business definitions and validation.

Explain access contracts → file/field pruning → bounded division → atomic publication → protected GC → isolated replay. Name one failure at each step: omitted predicate fields, missing runs, unsafe UNKNOWN retry, pin/GC races or checkpoint holes. Numbers test decisions; they do not replace contracts. Ch44 connects these data contracts to service governance.
