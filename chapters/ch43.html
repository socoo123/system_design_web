30 秒开场：先说访问合同，再谈规模Opening: access contracts before scale

中文

先问点查还是聚合、允许延迟与新鲜度。热视图承担点查，列式文件承担分析；先剪文件和列，再把超过内存的计算拆成有界任务。正确性抓三件事：固定快照、条件发布、可恢复的输入身份。合并要保留旧读者，回放写隔离视图再切流。

本章沿用 Ch02 的逐笔演进和 Ch03 的算术。教学对象是一张行为事件表：有 event_id、tenant_id、event_time、country、price 与 payload。在线接口按 ID 查事件，报表按租户和时间求和，审计回放历史。它们可以共享持久输入，但不该共享同一个查询延迟承诺。宽列与分析列存的区别仍回 Ch37，对象 GET/PUT 的底层机制回 Ch22。

规模要先落成四个量：每天新增字节、保留天数、一次查询要碰多少文件和列、峰值查询并发。数据总量很大不意味着每个请求都扫全量。设计时先固定一次查询范围，再算候选字节与执行槽位；否则“再加一台大数据机器”无法说明瓶颈是网络、CPU、文件打开还是结果 shuffle。后文吞吐、压缩率和延迟目标都是教学假设，需单独实测。

English

Fix point-read versus aggregate access, latency and freshness. Use serving views and columnar files, prune files/fields, then divide oversized computation into bounded tasks. Correctness rests on a pinned snapshot, conditional publication and recoverable input identity. Protect old readers and replay into an isolated view before switching.

The teaching workload is an event table with event_id, tenant_id, event_time, country, price and payload. ID reads, tenant/time reports and historical audits may share durable input but have different latency contracts. Ch37 covers wide-column versus analytical columnar storage; Ch22 covers object GET/PUT.

Fix daily bytes, retention, files/fields per query and peak concurrency. Large total data does not mean every query scans everything. Size one query range before execution slots and identify bandwidth, CPU, file-open or shuffle limits. All workload numbers are teaching assumptions requiring separate measurement.

1 · 分层：沿访问路径算保留成本1 · Tier by access and size retention

中文

正常点读走 Client→Query→Hot KV→Query→Client，键必须包含租户与事件身份，鉴权在查数前完成。Hot KV 是面向点查的索引视图，重建依据是持久事件，而不是这份热视图本身。报表走 Query→Scan Worker→Object Files，再逐跳返回局部结果。两条路径解决不同访问目标；分析扫描不应该穿过在线 KV，再把每条事件吐出来做 SUM。

温、冷描述访问频率与时效，列存描述文件布局，对象描述保存字节的介质。这三个轴可以组合：近期 Parquet 放在对象上，配活跃扫描 Worker 和缓存就能是温层。冷数据也可以保留同一格式，只减少常驻算力或换访问合同。湖仓论文讨论低成本存储上开放文件与管理能力的结合 [8]，不是要求每次温变冷都跨三种产品搬一份全量。

成本先只比较原始容量等价：全热 365×100=36,500 单位/月；若一日热等价 1 TB，其余 364 TB 放对象，1×100+364×10=3,740，约少 89.8%。这只是 A4 的简化成本推导，不是实际报价，也没让温窗口再加一份 30 TB。热视图的索引、临时重建副本、存储请求、跨区流量和 Worker 计算费都应另列；压缩会改变物理 TB，不能悄悄把逻辑 TB 当账单 TB。

“旧数据搬到冷层后删热数据”必须有交接证明。先完成持久输出、核对事件范围与数量，再发布可查询位置，最后等旧读者结束才回收。按事件时间划边界会遇到迟到：今天到达的事件可能属于昨天。若跨热视图与历史表联合查询，就要固定输入位点向量和查询边界，或按 event_id/version 消重；拿墙钟切成两半直接 UNION，会漏数或重数。本章图把两类接口分开，不承诺未经协调的跨库原子快照。

故障时先保合同。热视图坏了可以重建，但不能让全部毫秒点查退到扫全湖；限量回源或明确不可用。冷对象若需要恢复，提交带身份的查询任务，返回 RESTORE_PENDING，按租户限并发并给出可取消状态。对象服务也存在低延迟访问形式 [10]，所以“对象永远慢”“冷层都秒级”都过于绝对。冷热重分配看频率、恢复成本和延迟目标；旧爆款可以重新缓存，存储年龄不会被改写。

English

Point reads follow Client→Query→Hot KV and return through Query; authorize tenant/event keys first. Hot KV is rebuildable from durable events. Reports use Query→Worker→Files with partial results returning hop by hop. Bulk analytics should not enumerate the online KV.

Temperature, file layout and byte-storage medium are different axes. Recent Parquet objects with active workers/cache are warm; cold data can keep that format with less resident compute or a different access contract. Lakehouse discusses managed open files over low-cost storage [8], not mandatory full copies across three products.

At illustrative raw-equivalent A4 rates, all-hot is 365×100=36,500 units/month; one hot TB plus 364 object TB is 100+3,640=3,740, about 89.8% lower. This excludes indexes, temporary copies, requests, networking and compute. The warm window is not another mandatory 30 TB copy; compression changes billed bytes.

Tier handoff needs durable output, range/count validation, location publication and old-reader completion before cleanup. Late arrivals can belong to yesterday. A combined hot/history query needs fixed input progress and a query boundary or event/version deduplication; a wall-clock UNION can miss or duplicate events. The diagram separates interfaces and promises no uncoordinated cross-store atomic snapshot.

Protect contracts on failure: rebuilding Hot KV does not justify sending all point traffic into lake scans. Bound fallback or fail explicitly. Restore-dependent queries become identified, cancellable RESTORE_PENDING jobs with tenant limits. Object services include low-latency modes [10], so medium alone does not determine latency. Old popular data can be cached without changing its event time.

2 · 列存：先剪文件，再剪列，再算 CPU2 · Columnar scans: files, columns and CPU

中文

Query 解析 SUM(price) 与时间、国家过滤；规划器产出固定快照下的候选文件，Worker 读取页范围、解码、精确过滤并局部聚合。Parquet 的 row group 内按列组织 column chunk，文件元数据帮助定位需要的内容 [3]。图里 decode 和 local sum 在同一 Worker 内，是执行算子，不是两个远程服务。Query 收集局部结果后才返回 Client，不能让文件服务直接回客户端一个尚未聚合的价格列。

本组 A3 是获授权的全表报表，不带 tenant_id 行过滤。若租户报表必须读 tenant_id，且没有可靠元数据证明候选都属于该租户，就需要 4 列：1 TB×4/20÷4=50 GB；8 Worker 独占下界为 25 s、两并发 50 s。鉴权不能成为漏算谓词字段的理由。删除所需字段与 delete 文件也另计；37.5 GB 仅是三列数据页预算，非全部查询 I/O。

A3 先从 30 TB 原始候选按一天时间范围剪成 1 TB，再读取 20 个等宽字段中的 3 个，得到 150 GB 未压缩列数据；A4 所选列 4:1 后是 37.5 GB。30,000 GB÷37.5 GB=800 是对“全期、全列、原始数据扫描”的字节比，不是与已经压缩的行存基线比较。时间剪枝给 30 倍，剪列给约 6.67 倍，压缩给 4 倍；三项相乘才有 800，列存本身不能独占这个数字。

这一步删掉的是全行 payload 的搬运，不是所有 CPU。过滤字段 country 和 event_time 都要读取；谓词只排除行却没有可用统计时，页仍得读并解码。列值相似有利于字典、RLE 等编码，但高基数字符串或加密 payload 未必压得好；列投影更少也可能多出随机范围请求。向量化按一批值处理，延迟物化在确有需要时才拼行，能减轻执行成本；这些是列式引擎的配套能力，不能把“每列拆一张行表”当作全部实现 [2]。

Dremel 的 T1 实验有 850 亿记录、87 TB 未压缩数据；选一列的实验读约 0.5 TB 压缩数据，而记录布局 MR 读约 87 TB。压缩与执行模型都不同，因此 174 倍只是该实验的读取字节比，不能移植为本章延迟承诺。[1 §7 / Figure 10]

A5 的 8 台 Worker 合计有效 8×250 MB/s=2 GB/s。37.5 GB÷2 GB/s=18.75 s，只是独占带宽且没有其他瓶颈时的数据扫描下界。两条查询均分时各 1 GB/s，下界变 37.5 s，已经超过 A2 的 30 s 目标。设计后果是控制并发、增加实测后的预算或缩小范围；不能先报 30 s 再用这个算术替它背书。COUNT DISTINCT、高基数 GROUP BY 还会放大聚合状态与 shuffle，筛选很多列或拼完整记录时，列存收益也会减小。

English

Query plans a snapshot-bound SUM with time/country filters. Workers get page ranges, decode, filter and partially aggregate. Parquet column chunks sit inside row groups, and metadata locates needed content [3]. Decode/sum are local operators, not remote services. Query merges partials before replying.

A3 is an authorized whole-table report with no tenant_id row filter. A tenant report that must read tenant_id needs 4 fields unless trusted metadata proves tenant scope: 1 TB×4/20÷4=50 GB, with 25 s exclusive or 50 s shared scan lower bounds. Include delete fields/files separately; 37.5 GB covers only the three data fields, not all query I/O.

A3 reduces 30 TB raw to 1 TB by date, then 3/20 fields to 150 GB; A4 compression gives 37.5 GB. 30,000/37.5=800 compares all-period/all-field raw bytes, not a compressed row-store baseline. Time contributes 30×, projection about 6.67× and compression 4×.

Projection removes payload transfer, not all CPU. Read both predicate fields; unavailable pruning statistics still require page reads and decoding. Dictionary/RLE benefit suitable values, not arbitrary high-cardinality or encrypted payloads. Vectorized operations and late materialization complement column layouts; vertically splitting row tables is not a complete engine [2].

Dremel’s T1 experiment contains 85B records and 87 TB uncompressed. Its one-column scan reads about 0.5 TB compressed versus 87 TB for record-oriented MR. Compression and execution differ; 174× describes that experiment’s byte ratio, not this chapter’s latency. [1 §7 / Figure 10]

Eight A5 workers offer an assumed 2 GB/s effective data rate. 37.5/2=18.75 s is a scan lower bound; two equally sharing queries each need at least 37.5 s, beyond A2’s 30 s target. Bound concurrency, measure additional capacity or narrow scope. Distinct/group-by state, shuffle and wide record assembly add costs.

关键实现：内存放不下，就分块落盘、有限路数归并Implementation: spill bounded chunks and merge with bounded fan-in

第 2 组的 local sum 遇到高基数 GROUP BY 时，不能无限扩张 HashMap。以下是可运行 Java17 摘录，仅标准库：输入是已鉴权、固定 snapshot、精确过滤且应用删除后的行；按有界分组键求非空整数分金额之和。先把最多 B=maxRows 行排序并同键求和，落为有序 run；每轮最多合并 F=fanIn 份，直到一份完整候选。国家列通常只有少数值，这段还适用于更高基数的有界分组键。

The local sum in deck 2 must not grow a hash map without bound for high-cardinality GROUP BY. This runnable Java17 excerpt uses only the standard library. Input rows are already authorized, snapshot-bound, exactly filtered and delete-aware; values are non-null integer cents with bounded keys. Sort and reduce at most B=maxRows rows per run, then merge at most F=fanIn runs per wave until one complete candidate remains. Country normally has few groups; the same algorithm supports higher-cardinality bounded keys.

static Path aggregate(Iterator<Row> input, int maxRows, int fanIn, Path job)
        throws IOException {
    if (maxRows < 1 || fanIn < 2) throw new IllegalArgumentException("budget");
    Files.createDirectory(job); // unique attempt; never overwrite another job
    Path stage = Files.createDirectory(job.resolve("stage-0"));
    long count = 0;
    while (input.hasNext()) {
        List<Row> block = new ArrayList<>();
        while (block.size() < maxRows && input.hasNext()) block.add(input.next());
        block.sort(Comparator.comparing(Row::key));
        writeChunk(block, stage.resolve("run-" + count++));
    }
    if (count == 0) return Files.createFile(stage.resolve("run-0"));
    for (int pass = 1; count > 1; pass++) {
        Path next = Files.createDirectory(job.resolve("stage-" + pass));
        long outputs = 0;
        for (long first = 0; first < count;) {
            List<Path> group = new ArrayList<>();
            for (int n = 0; n < fanIn && first < count; n++, first++) {
                group.add(stage.resolve("run-" + first)); // expected identities
            }
            merge(group, next.resolve("run-" + outputs++)); // a missing run fails
        }
        removeStage(stage); // only after the entire next wave is complete
        stage = next;
        count = outputs;
    }
    Path candidate = stage.resolve("run-0");
    try (InputStream verify = Files.newInputStream(candidate)) { verify.read(); }
    return candidate; // readable now; publication/retention is the caller's job
}

count 记录本轮完整输入集合，归并按 run-i 的期望身份逐一打开；不靠“目录里还剩哪些文件”猜完整性。少一份输入就失败。最终候选在返回前也实际打开读取，覆盖只有一个 run、无需归并的分支。这个瞬时检查不能阻止交接后的删除，发布层仍须保护对象身份、保留期和 GC fence。B 限制块内存，F 限制文件句柄、缓冲和堆中候选；目录路径只保留当前一组，避免另一份全量列表。下一轮全部完成后才清理上一轮；异常不会返回可发布结果。

The recorded count defines the complete input set; open expected run-i identities rather than infer completeness from a directory listing. Missing input fails. Open/read the final candidate before return, including a single run with no merge wave. This momentary check cannot prevent deletion after handoff; publication still owns identity, retention and GC fencing. B bounds chunk storage, while F bounds handles, buffers and heap heads; retain paths only for the current group. Delete a wave only after its successor completes. Any exception returns no publishable result.

static void merge(List<Path> runs, Path output) throws IOException {
    PriorityQueue<Head> queue = new PriorityQueue<>(
            Comparator.comparing((Head h) -> h.row().key())
                    .thenComparingInt(Head::reader));
    try (RunReaders readers = new RunReaders(runs);
         BufferedWriter out = Files.newBufferedWriter(output,
                 StandardOpenOption.CREATE_NEW, StandardOpenOption.WRITE)) {
        for (int i = 0; i < runs.size(); i++) {
            Row row = readRow(readers.get(i));
            if (row != null) queue.add(new Head(i, row));
        }
        String key = null;
        long sum = 0;
        while (!queue.isEmpty()) {
            Head head = queue.remove();
            Row row = head.row();
            if (key != null && !key.equals(row.key())) {
                writeRow(out, new Row(key, sum));
                sum = 0;
            }
            key = row.key();
            sum = Math.addExact(sum, row.cents());
            Row next = readRow(readers.get(head.reader()));
            if (next != null) queue.add(new Head(head.reader(), next));
        }
        if (key != null) writeRow(out, new Row(key, sum));
    }
}

每个 run 在优先队列中最多保留一个头；取最小 key、累加、补进该来源下一条。同 key 即使跨越所有 run 也会收敛到一个输出。完整源码包含 writeChunk 的同键归并、资源关闭与驱动：ExternalAggregate.java。设初始 run 数 R=ceil(N/B)，约需 ceil(logFR) 轮；不计压缩和局部缩减时每轮近似读写全部输入一次。scratch 空间、查询 deadline、取消与磁盘满也要预算。

第 4 组的 b17 如何真正可恢复？这里给自定义 Catalog 的教学伪代码，不是 Iceberg API。catalog(table_id PRIMARY KEY, current) 与 accepted(table_id, batch_id, digest, snapshot) 在同一个支持事务的权威数据库中，后者以 (table_id,batch_id) 唯一且各字段非空。Catalog 服务鉴权、串行化条件更新并原子提交两张表；读取恢复身份走权威一致读。digest 绑定表、操作、输入分区范围与处理版本，重试不得改它；candidate 可以在安全 rebase 后重建。

How is b17 recoverable? This is teaching pseudocode for a custom Catalog, not an Iceberg API. Store catalog(table_id PRIMARY KEY, current) and accepted(table_id,batch_id,digest,snapshot) in one authoritative transactional database, with a non-null unique (table_id,batch_id). The authorized Catalog serializes conditional updates and atomically commits both tables; recovery uses authoritative reads. Bind digest to table, operation, input ranges and transform version. Retain it across retries; a safe rebase may rebuild candidate metadata.

publish(table, batch, digest, expected, candidate):
  # All candidate objects are durable; batch identifies one logical operation.
  BEGIN TRANSACTION
    known = SELECT digest, snapshot FROM accepted
            WHERE table_id = table AND batch_id = batch
    if known exists:
      require known.digest == digest
      COMMIT; return known.snapshot
    changed = UPDATE catalog SET current = candidate
              WHERE table_id = table AND current = expected
    if changed != 1:
      ROLLBACK; return CONFLICT
    INSERT accepted(table_id, batch_id, digest, snapshot)
           VALUES(table, batch, digest, candidate)
    # UNIQUE(table_id, batch_id); any insert failure rolls back UPDATE too.
  COMMIT
  return candidate

on timeout or CONFLICT:
  known = strongly_read_accepted(table, batch)
  if known exists:
    require known.digest == digest
    return known.snapshot
  # Absence does not rule out an in-flight transaction.
  retry SAME batch + digest within budget, or return UNKNOWN
  # Rebase only after refreshing and validating operation-specific assumptions.
  # Never delete output while publication can still complete.

正常 meta40→meta41 时，b17 的结果随指针一起提交；ACK 丢失后即使 current 已到 meta42，也能从 accepted 找回 meta41。相同 b17 换摘要必须拒绝；身份冲突或事务中断须回滚指针更新，再重查身份。死锁/序列化失败在预算内重试整个事务。accepted 保留覆盖重试与恢复期；超出保留期的旧请求要明确拒绝，不能当新 batch 接受。

单次查询“没有 b17”不是终态失败证据：旧事务可能仍在执行。可用相同身份继续幂等重试，或保持 UNKNOWN；要回收候选，先由服务端终结/隔离该 attempt，保证它以后也不能发布，再核引用和安全窗口。每次重建候选仍须验证追加/DELETE/rewrite 的各自前提，不能让通用事务包替过期合并结果背书。[5 Retry validation]

For meta40→meta41, b17’s result commits with the pointer. A lost ACK is resolved through accepted even after current reaches meta42. Reject a changed digest for b17. An identity conflict or aborted transaction rolls back the pointer, then resolves the identity; retry the whole transaction for bounded deadlock/serialization failures. Retain accepted through the retry/recovery horizon and explicitly reject identities older than that horizon.

An absent lookup does not prove failure while an old transaction can still execute. Retry with the same identity or remain UNKNOWN. Before collecting output, the service must terminate/fence that attempt against future publication and check reachability and safety windows. Rebuilt candidates still need append/DELETE/rewrite-specific validation; the transaction does not validate a stale compaction automatically. [5 Retry validation]

7 · 批流与回放：先隔离结果，再切读取入口7 · Batch/stream replay and verified cutover

中文

Lambda 用批计算与实时增量共同服务，代价是两套逻辑和合并合同；Kappa 让同一类流处理依靠可回放输入重算。Kreps 2014 的原文强调双栈复杂度，并描述新版本处理器重放历史、赶上后切换输出 [9]。这两句是选型入口，不是正确性证明。能否复算还取决于输入留存、外部依赖版本、状态初始化、迟到政策和下游幂等；有界大 shuffle 的任务也未必适合硬塞进一个持续流算子。

图里的 Processor v1 持续提交 View v1，消费位点在对应下游提交确认后推进。源记录的稳定身份是 (stream, partition, offset)，跨位点重复的业务事件还需 event_id/version 去重；不能只用每次重跑都变化的随机 batch ID。Processor v2 从 S 回放到独立 View v2，不能把历史计数再追加到在线累加器。若提交 sink 成功、checkpoint 未写就崩溃，重放会重复该批；稳定 batch/event_id 与原子下游结果处理负责消重。只说流引擎“exactly once”而不解释 sink 的提交协议，不足以保证外部表、邮件或计费也只发生一次。

Lambda 也要写明确合并边界：批结果覆盖哪些输入位点，流结果从哪里开始，迟到与更正归谁处理。事件时间小于昨天，不代表该事件已进入昨夜批结果；用“批算昨天、流算今天”直接相加会漏掉迟到数据，也可能重复刷新中的那一段。用分区输入位点向量定义覆盖，更正历史窗口或按稳定事件版本重算；时间 watermark 是处理策略的证据，不能冒充每个分区完整消费的 durable offset。

回放容量按净速度。A11 有 1 TB 积压，回放有效 100 MB/s，持续新增 20 MB/s，净 80 MB/s；1,000,000 MB÷80=12,500 s≈3.47 h。只除以 100 会报 2.78 h，漏掉回放期间新增的 250 GB。若回放仅 20 MB/s，backlog 不下降；低于 20 就越追越远。留存必须盖住选定 S 到追平完成的输入范围，还要包含部署与故障恢复余量；不能在处理器运行时让源日志把 S 后尚未读取的片段删掉。

本章统一 next-offset 语义：S[p] 是分区 p 的起始位置，H[p] 是尚未处理的下一位置；回放覆盖 [S[p],H[p])。H 只前进到连续完成的前缀，不能取所有 worker 已完成 offset 的最大值。切流让 v2 证明状态与输出均持久覆盖该范围，并核对行数、关键聚合、删除与迟到修正；再条件发布读取入口。若要求无缺口切换，可短暂停消费或写一个可恢复的切换屏障，保证 v2 接续 H 后新增，v1 不再承担权威新输出。旧视图保留给正在跑的读者与可验证回退；新视图接了更多写以后，退回旧版也要追这些变化。回放逻辑修好不代表历史删除或权限撤销可以被原始日志重新复活。

English

Lambda merges batch and live increments with two logic stacks; Kappa reuses stream processing over replayable input. Kreps describes replaying with a new processor and switching output after catch-up [9]. Correctness still requires retention, versioned dependencies, state initialization, late-event policy and idempotent output.

Processor v1 commits View v1 before checkpointing; v2 replays from S into isolated View v2. Stable source identity is (stream,partition,offset); business duplicates at different offsets need event_id/version deduplication too. A new random batch ID per retry is insufficient. A crash after sink commit but before checkpoint repeats input, requiring stable identities and atomic deduplicated effects. Engine-level exactly-once language does not establish external sink, email or billing semantics.

Lambda needs explicit batch coverage, streaming start and correction ownership. Yesterday’s event time does not prove inclusion in yesterday’s batch. Define coverage with partition-specific input progress and correct/recompute late versions; an event-time watermark is not a durable consumed offset.

Drain 1 TB at net 100−20=80 MB/s: 12,500 s≈3.47 h. Dividing by 100 gives 2.78 h and omits 250 GB arriving during true catch-up. At or below 20 MB/s there is no convergence. Retention must cover S through completion plus deployment/recovery margin.

Use next-offset conventions: S[p] starts partition p, H[p] is its next unprocessed position, and replay covers [S[p],H[p]). Advance only a contiguous durable prefix, never the maximum completed worker offset. Prove durable state/output coverage for this range, validate counts/aggregates/deletes/corrections, then conditionally publish the read entry. A recoverable barrier or brief pause can coordinate continuation after H. Retain old views for readers and validated rollback, which must include newer changes. Replay must respect historical deletions and revoked access.

追问与收尾：把机制放回设计题Follow-ups and where this fits

中文

搜索 Ch13：倒排服务在线检索，query log 进温列存，构建输入可以回放；对象存储 Ch22：保存字节，表格式负责一致集合，两者的删除保留要协调；排行榜 Ch23：实时有序视图与历史赛季表分开，已结束赛季也可能因审计再次变热。消息队列 Ch20：日志是输送与回放输入，保留有上限，落地表是另一种读取接口，不能把 Kafka 当无限数仓。

面试官问“高基数 ID 绝对不能分区吗”，答查询与文件规模决定，而不是一律禁止。固定数量 bucket(id) 可以限制桶数，但点查仍要匹配索引与文件统计。问“文件越大越好吗”，答打开成本与并行度相互制约，还要考虑重写峰值、时间范围与延迟目标。问“批层一定准吗”，答它也会受重复输入、逻辑 bug、删除和快照选择影响；准不准取决于同一份明确的业务定义与校验。

最后沿“访问合同 → 文件/列剪枝 → 有界分治 → 原子发布 → 受保护回收 → 隔离回放”口述。每一步说出一个失败条件：谓词漏列、run 缺失、UNKNOWN 乱重试、GC 抢过 pin、位点跨洞。数字只用于检验选择，不能替代实现合同。下一章 Ch44 把这些数据合同放回服务治理。

English

Ch13 keeps online inverted indexes separate from analytic query logs; Ch22 stores bytes while table formats manage coherent sets and coordinated retention; Ch23 separates live boards and historical seasons. Ch20 logs transport/replay data with bounded retention rather than act as an infinite warehouse.

High cardinality is not a blanket partitioning ban; bounded buckets can fit a workload. Bigger files trade fewer opens against parallelism and rewrite peaks. Batch processing is not inherently correct: duplicate input, bugs, deletions and snapshot selection still need business definitions and validation.

Explain access contracts → file/field pruning → bounded division → atomic publication → protected GC → isolated replay. Name one failure at each step: omitted predicate fields, missing runs, unsafe UNKNOWN retry, pin/GC races or checkpoint holes. Numbers test decisions; they do not replace contracts. Ch44 connects these data contracts to service governance.
