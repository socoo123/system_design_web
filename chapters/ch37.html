存储选型Storage choices

这一章结束你能做什么What you can do after this chapter

中文

  • 用四问开口：读写比、查询形状、要不要事务、一条数据有多大。然后才说库的类型。
  • 按这个顺序把关系库、KV、wide-column、对象存储、搜索加到白板上。

English

  • Open with four questions: read/write ratio, query shape, whether you need a transaction, and how big one value is. Then name a kind of store.
  • Add relational, KV, wide-column, object storage, and search to the board in that order.
  • Say the B+Tree versus LSM trade-off, and keep wide-column, analytic column-store, object, and vector apart.

20 秒：先问访问模式20 seconds: ask the access pattern

中文

这是词典，不是又一道 4 步设计题。Ch36 决定你偏 AP 还是偏 CP；这一章决定模型和引擎怎么接上去。短链、订单、视频、网盘、搜索卡在「用什么库」时跳过来，引用一句就回到题目。

四问，然后停。读写谁多。查询是 point lookup、join，还是 scan。这条路径要不要一次 commit。一条 value 有多大、key 有多少。要事务、join、约束，关系库是默认，这不是 SQL 过时不过时的问题。只有 get/put 而且 value 小，用 KV。写很重的稀疏宽行用 wide-column，引擎多半是 LSM。大块字节用对象存储，元数据仍常在关系库。关键词用倒排。读延迟紧的 OLTP 用 B+Tree，写吞吐用 LSM，compaction 是税。

念完让面试官选：挖选型、挖引擎，还是挖「别混」。一上来报云产品名，是 red flag。

English

This is a dictionary, not another 4-step design. Ch36 decides AP versus CP. This chapter decides how the model and the engine plug into that grid. When a short URL, an order, a video, a drive, or search gets stuck on "which store", you jump here, cite one line, and go back to the problem.

Four questions, then stop. Which of read or write dominates. Is the query a point lookup, a join, or a scan. Does this path need one commit. How big is one value, and how many keys are there. If you need a transaction, a join, and constraints, relational is the default. That is not a question about whether SQL is old. Point get/put of a small value is a KV. A write-heavy sparse row is wide-column, usually on an LSM. Large blobs go to object storage, and the metadata usually stays relational. Keywords use an inverted index. Tight OLTP reads use a B+Tree. Write throughput uses an LSM, and compaction is the tax.

Then let them choose: the choice, the engine, or "don't mix those up". Leading with a cloud product name is a red flag.

第一笔候选：关系库First candidate: relational

中文

订单、库存、支付账本、网盘目录，要的是原子提交、跨表一致、唯一和外键。第一句仍是关系库。面试官若问「SQL 是不是太老了」，你回到访问模式：要事务、join、约束，它就是默认。

隔离级别不要开课。你真会碰到的引擎是 MVCC。PostgreSQL 的默认隔离级别是 Read Committed，InnoDB 的默认是 Repeatable Read，两条默认都读不到未提交的写。钱的路径如果要 Serializable，代价是吞吐和回滚，不要给全站当默认。五种级别的对照表在复制与事务那一章。分片、跨库事务、Saga、Outbox 也在那边。

还有一句就够：想要 SQL、又要水平扩展时，SQL 加分布式共识这条线存在。不要开成产品巡礼。

English

Orders, inventory, a payment ledger, a drive directory: you need an atomic commit, consistency across tables, and unique or foreign keys. The first sentence is still a relational store. If they ask whether SQL is too old, go back to the access pattern. Transactions, joins, and constraints make it the default.

Do not teach the isolation ladder. The engines you will actually meet are MVCC. PostgreSQL's default isolation is Read Committed. InnoDB's default is Repeatable Read. Neither default returns an uncommitted write. Serializable on a money path costs throughput and aborts. Do not make it the default for the whole product. The comparison table, plus sharding, cross-store transactions, Saga, and Outbox, belong to the replication and transactions chapter.

One more sentence is enough. If you still want SQL and you need to scale out, the line "SQL plus distributed consensus" exists. Do not turn that into a product tour.

订单在 Ch18 · 电商订单，支付在 Ch24 · 支付。隔离级别和 Saga 在 Ch41 · 复制、分片、事务。Orders are Ch18 · e-commerce orders. Payments are Ch24 · payments. Isolation levels and Saga are Ch41 · replication, sharding, transactions.

加上 KVAdd a KV

中文

查询收成 get(key) / put(key, value)，而且 value 小，就选 KV。会话、购物车、短链的 code 到 url，都是高 QPS 的点查。没有 join。跨 key 的事务也不在这里当权威。

它还经常站在关系库前面，做 cache-aside。那是热路径少打一次权威，不是第二本账本。穿透、击穿、雪崩在缓存那一章展开。quorum、LWW、节点内部的 LSM 写路径已经在键值存储那一章，这里只回答何时选它。

有主从、按 slot 切分的内存集群，和论文里那种分区时仍要 put 的 AP KV，不是同一个框。不要因为名字里都有 key 就画在一起。

English

When the query collapses to get(key) / put(key, value) and the value is small, pick a KV. Sessions, carts, and a short URL's code-to-url map are high-QPS point lookups. There is no join. A cross-key transaction is not the source of truth here.

A KV also often sits in front of a relational store as cache-aside. That is "don't hit the authority on every hot read", not a second ledger. Penetration, breakdown, and avalanche belong to the cache chapter. Quorum, LWW, and the LSM write path inside a node are already in the key-value chapter. Here you only answer when to pick it.

An in-memory cluster with a primary and hash slots is a different box from the paper's AP KV, the one that still accepts a put during a partition. Sharing the word "key" does not make them the same drawing.

机制在 Ch06 · 键值存储。短链样板是 Ch09 · 短链。cache-aside 在 Ch38 · 缓存与 CDN。Mechanics are Ch06 · key-value store. The short-URL sample is Ch09 · URL shortener. Cache-aside is Ch38 · cache and CDN.

加上 wide-columnAdd wide-column

中文

写远重于读，一行又宽又稀疏，查询是按分区键找到这一行、再按聚簇键扫行里的列。这是 wide-column。写是追加，引擎几乎总是 LSM。行内原子常见。跨行 ACID 不是它的卖点。

时间线、按用户堆出来的事件，可以落在这里，也可以落在 KV，看你要不要「一行里按时间排开很多列」。账户、权限、钱仍然留在关系库。按数据拆，不要全站一个引擎。

下一组 trade-off 会把分析列存拆开。这里先钉住：wide-column 的「列」是稀疏行上的动态列，不是把同一字段竖着排好去扫表。

English

Writes dominate, the row is wide and sparse, and the query finds that row by a partition key, then walks columns inside it by a clustering key. That is wide-column. Writes append. The engine is almost always an LSM. Atomicity inside the row is common. Cross-row ACID is not the selling point.

A timeline, or a pile of events per user, can live here or in a KV, depending on whether you need many time-ordered columns inside one row. Accounts, permissions, and money stay relational. Split by data. Do not run the product on one engine.

The trade-off group splits off the analytic column-store. Nail this first: a wide-column "column" is a dynamic column on a sparse row. It is not the same field stacked vertically so you can scan a table.

节点里的 LSM 写路径在 Ch06 · 键值存储。时间线会在 Feed、聊天那类题里碰到，权威账户仍回关系库。The LSM write path inside a node is Ch06 · key-value store. Timelines show up in feed and chat problems. The account of record still goes back to relational.

加上对象存储Add object storage

中文

视频原片和分片、网盘的块、备份、静态资源：不可变字节，写一次，之后按 id 读整段或一段 Range。这是对象存储。目录、ACL、时长、版本号是小记录，仍进元数据库，多半是关系库。

顺序要说清。先把字节落地，再 commit 元数据。库里不能指向一个还不存在的对象。API 只交换 object id，不把大文件从自己的进程里转发过去。

介质只点一句，不当脊梁。库盘常见是块设备。多机共享一个目录，才是文件。对象是 HTTP 语义的 blob，不是一块 POSIX 盘。上传、分片和一致性的展开在对象存储那一章。

English

Video source and chunks, drive blocks, backups, static assets: immutable bytes, written once, then read whole or by range from an id. That is object storage. Directory, ACL, duration, and version are small records. They stay in a metadata store, usually relational.

Say the order. Land the bytes, then commit the metadata. The store must not point at an object that does not exist yet. The API exchanges an object id. It does not proxy the large file through its own process.

The medium gets one sentence, and it is not the spine of the chapter. A database disk is usually a block device. A directory shared across machines is a file system. Object storage is an HTTP blob, not a POSIX disk. Upload, multipart, and consistency are unpacked in the object-storage chapter.

视频在 Ch14 · 视频，网盘在 Ch15 · 网盘。上传和一致性在 Ch22 · 对象存储。Video is Ch14 · video. A drive is Ch15 · cloud drive. Upload and consistency are Ch22 · object storage.

加上搜索Add search

中文

查询是词，不是主键。倒排把 term 指到文档列表，正文或对象另存。精确 id、普通的 SQL 条件，仍然走 KV 或关系库。倒排不是通用库，也不是账本。

同一套四问把剩下的模型收掉，不必再报品牌。JSON 的形状还在变，可以用文档模型，约束挪到应用层；schemaless 不是许可证，脏数据会进来，后来加上的校验才是实话。关注关系一两跳，join 或闭包表就够；反复多跳、路径本身是查询，才用图。指标是 append 加降采样加过期，不要拿时序库存订单。排行榜的热列表是有序的 top-k 读路径，权威分数仍可以在库里，这不是再买一个图数据库。

查询变成「和这条 embedding 最像的 k 条」，才上向量。行已经在关系库里、还要和行 join，先用库内向量索引。ANN 自己就是产品，过滤和副本成了 bottleneck，引擎那一章再展开。没问有多少条，就不要上专用集群。关键词搜索不要换成向量装门面。

English

The query is a term, not a primary key. An inverted index points the term at a posting list. The body lives in another store, or in an object. An exact id, or an ordinary SQL predicate, still goes to a KV or a relational store. The index is not a general-purpose database, and it is not the ledger.

The same four questions close the remaining models. You do not need another brand. JSON whose shape is still moving can be a document, with constraints moved into the app. Schemaless is not a license: dirty data gets in, and the honest story is the validation you add later. One or two hops of a follow graph are a join, or a closure table. A graph store is for repeated multi-hop, when the path itself is the query. Metrics are append, downsample, and expiry. Do not store orders in a time-series store. A leaderboard's hot list is an ordered top-k read path. The authoritative score can still live in a database. That is not a reason to add a graph store.

You add a vector index when the query is "the k nearest embeddings". If the rows already live in the relational store and you need to join them, start with an in-database vector index. When ANN is the product, and filters and replicas are the bottleneck, the engine chapter takes over. Do not stand up a dedicated cluster before you know how many vectors you have. Do not dress keyword search up as vectors.

站内搜索在 Ch13 · 搜索。向量引擎在 Ch31 · 向量检索，RAG 在 Ch30 · RAG。热列表在 Ch23 · 排行榜。On-site search is Ch13 · search. The vector engine is Ch31 · vector search. RAG is Ch30 · RAG. A hot list is Ch23 · leaderboard.

Trade-off：引擎，以及别混Trade-off: the engine, and don't mix them

中文

第二个 hard part 是引擎，不是再背一条 WAL 到 memtable 到 SSTable 的链。那条热路径键值存储那一章画过。这里要能推导 trade-off。

B+Tree 把数据放在页里，查找从根走到叶，高度通常很小，点查和沿叶节点的范围都稳。更新是原地改页，加 WAL 对付崩溃。代价是随机写页：改很小一块，也可能把整页刷下去。关系库的 OLTP 索引走这个家族。

LSM 的热路径不改旧页。写按顺序进 WAL，再进内存里的 memtable，满了 flush 成不可变的 SSTable。后台 compaction 合并文件、丢掉旧版本。盘上是顺序追加，所以写吞吐高。wide-column 和不少 AP KV 的节点内部就是它。

写放大是：用户写了一小段，盘上实际写了多少。B+Tree 已经有一截，因为页比行大，但它不会把同一条 key 在后台合并中重写多遍。LSM 会。同一条 key 从 memtable flush 出去，再被 compaction 往下推，层越多，重写越多。这就是 compaction 税：用额外的写，换更少的文件、更干净的读。所以「LSM 写得快」说的是热路径吞吐，不是写放大低。两句并成一句，是 red flag。compaction 之前，旧版本还占着盘，那是空间上的放大。

读放大是：一次 point get 碰了多少页或文件。B+Tree 大约是树的高度，可预期。LSM 要看 memtable，再加上若干部 SSTable，文件越多越疼。Bloom filter 一句：过滤器说不在，这个 SSTable 可以跳过，没有假阴性；说可能在，才打开文件，允许假阳性。compaction 用写放大换读放大。合并完，要查的层变少。

读极多、写很少、延迟又紧，不要因为「大家都用 LSM」就把 LSM 当主 OLTP。那是配错。写极多、扛得住 compaction 的毛刺，用 LSM。混合负载在白板上点到「用写放大换读放大」就停，不要开成调参课。短链读多写少，权威映射可以是 KV，但引擎要回头问读写比：读的延迟极严时，B+Tree 家族是说得通的答案。

第三个 hard part 是用词。wide-column 存稀疏行，查询是分区键点查或短范围，写引擎是 LSM。分析列存把一列连续放好，利于压缩，查询是扫列做聚合。对象是不可变字节加 object id，查询是 GET 整段或 Range。向量是 embedding，查询是 ANN 的 top-k。把 wide-column 和数仓列存都叫 columnar，是这章最大的用词 red flag。对象没有「列」。向量索引也不是 B+Tree 点查。

English

The second hard part is the engine. You are not reciting WAL, then memtable, then SSTable again. The key-value chapter already drew that hot path. Here you derive the trade-off.

A B+Tree keeps data in pages. Lookup walks from the root to a leaf. The height is usually small, so point lookups and ranges along the linked leaves are both stable. An update rewrites the page in place, and a WAL covers a crash. The cost is random page IO: a tiny change can still flush a whole page. OLTP indexes in a relational store are this family.

An LSM does not mutate old pages on the hot path. The write goes sequentially into the WAL, then into an in-memory memtable. When that fills, it flushes to an immutable SSTable. Background compaction merges files and drops old versions. Disk IO is sequential append, so write throughput is high. Wide-column stores, and the inside of many AP KV nodes, are this.

Write amplification: the user writes a small change, and you ask how much actually hits disk. A B+Tree already has some, because a page is much larger than a row. It does not rewrite the same key over and over in the background. An LSM does. The key flushes out of the memtable, then compaction pushes it down. More levels, more rewrites. That is the compaction tax: extra writes in exchange for fewer files and cleaner reads. So "an LSM writes fast" means hot-path throughput. It does not mean write amplification is low. Collapsing those two sentences is a red flag. Before compaction, old versions still occupy disk. That is space amplification.

Read amplification: how many pages or files one point get touches. A B+Tree is about the height of the tree, which you can predict. An LSM checks the memtable plus several SSTables. More files, more pain. Bloom filter, one line: if it says "not in", skip that SSTable. There is no false negative. If it says "maybe", open the file. False positives are allowed. Compaction trades write amplification for read amplification. After the merge, fewer layers to check.

If reads dominate, writes are rare, and the latency target is tight, do not pick an LSM as the primary OLTP store just because it is popular. That is a mismatch. If writes dominate and you can live with compaction spikes, pick an LSM. On a mixed load, point at "trade write amplification for read amplification" and stop. Do not start a tuning lecture. A short URL is read-heavy. The authoritative map can still be a KV, but ask the read/write ratio before you freeze the engine. If read latency is extremely tight, a B+Tree family is a fair answer.

The third hard part is vocabulary. Wide-column stores a sparse row. The query is a point lookup or a short range on the partition key, and the write engine is an LSM. An analytic column-store lays one column out contiguously so it compresses, and the query scans columns to aggregate. Object storage is immutable bytes plus an object id. The query is a GET of the whole object or a range. A vector index stores embeddings. The query is ANN top-k. Calling wide-column and a warehouse column-store both "columnar" is this chapter's biggest vocabulary red flag. An object has no column. A vector index is not a B+Tree point lookup.

三篇必读，两篇选读Three papers to name, two optional

中文

能点名，不要背页码，也不要编论文里的内部数字。教学顺序是 AP KV，再到写引擎，再到 wide-column 系统。这不是发表年表：LSM 那篇早于 Bigtable，Bigtable 早于 Dynamo。

文献面试用哪一句
DeCandia 等，SOSP 2007，Dynamo必读AP KV：分区时仍要 put。可以点 hinted handoff。生产冲突默认 LWW。不要把论文全家桶讲成实现说明书。

English

You should be able to name them. Do not memorize page numbers, and do not invent internal figures from the papers. The teaching order is AP KV, then the write engine, then the wide-column system. That is not publication order. The LSM paper is earlier than Bigtable, and Bigtable is earlier than Dynamo.

中文

  1. 为什么还用关系库？因为要事务、join、约束。账本不要用 AP KV 当权威。
  2. 访问模式怎么问？读写比、point / join / scan、要不要一次 commit、value 多大。答完再报模型。
  3. 文档库是不是没有 schema？约束在应用层。形状还在变才适合文档。脏数据是风险，不是卖点。
  4. wide-column 和分析列存？稀疏宽行加 LSM 灌入，对上扫列做聚合。不要都叫 columnar。
  5. 关注关系要不要图数据库？一两跳用 join。多跳路径才是理由。时序库是 append 加降采样，不要存订单。
  6. 视频为什么不放 KV？value 太大。对象加元数据小库。API 不中转文件。
  7. B+Tree 和 LSM 谁更快？看读写。读稳走 B+Tree，写吞吐走 LSM。写得快不等于写放大小。compaction 用重写换更少的 SSTable。
  8. Bloom、Dynamo、隔离级别？Bloom 说不在就跳过 SSTable。Dynamo 可以点 hinted handoff，生产冲突默认 LWW。隔离默认是 MVCC 那条线，细表不在这章。
2026 和旧笔记差在哪

旧笔记把存储写成云盘和托管数据库的目录，又把 wide-column 和数仓都叫成列式。上场只带四问、模型和引擎。块设备、共享文件、对象，只在讲 blob 时点一句，不当目录。隔离级别不背五种；PostgreSQL 默认 Read Committed，InnoDB 默认 Repeatable Read，都是 MVCC，都读不到脏数据。向量时钟留在 Dynamo 论文里，生产冲突默认 LWW。一种引擎打全站，是 over-engineering。

English

  1. Why a relational store at all? You need a transaction, a join, and constraints. Do not make an AP KV the ledger of record.
  2. How do you ask the access pattern? Read/write ratio, point versus join versus scan, whether you need one commit, and how big the value is. Name the model after that.
  3. Does a document store have no schema? Constraints live in the app. Pick it when the shape is still moving. Dirty data is a risk, not a feature.
  4. Wide-column versus an analytic column-store? Sparse wide rows plus LSM ingest, versus scanning columns to aggregate. Do not call both columnar.
  5. Does a follow graph need a graph store? One or two hops: a join. Multi-hop paths are the reason. A time-series store is append plus downsample. Do not store orders there.
  6. Why not put video in a KV? The value is too big. Object storage plus a small metadata store. The API does not proxy the file.
  7. Which is faster, B+Tree or LSM? It depends on read versus write. Stable reads: B+Tree. Write throughput: LSM. Fast writes are not low write amplification. Compaction rewrites keys to end up with fewer SSTables.
  8. Bloom, Dynamo, isolation? A Bloom filter that says "not in" skips that SSTable. You can name hinted handoff on Dynamo. The production conflict default is LWW. Isolation stays on the MVCC line. The detail table is not this chapter.
What changed since the old notes

Old notes turned storage into a catalog of cloud disks and managed databases, and they called both wide-column and a warehouse "columnar". You walk in with the four questions, the model, and the engine. Block devices, shared files, and objects get one sentence when you are talking about blobs. They are not the outline. You do not recite five isolation levels. PostgreSQL defaults to Read Committed, InnoDB defaults to Repeatable Read, both are MVCC, and neither returns dirty data. Vector clocks stay in the Dynamo paper. The production conflict default is LWW. One engine for the whole product is over-engineering.
