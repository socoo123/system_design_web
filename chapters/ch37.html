存储选型Storage choices

约 45–50 分钟 · 前置：键值存储、CAP / PACELC · 7 组 / 38 帧自动播放演进图~45–50 minutes · after the KV chapter and CAP / PACELC · 7 decks / 38 autoplay evolution frames

本章核心：先写查询，再选存储Core: write the queries before choosing a store

  • 访问键与查询形状：点查、短范围、全文候选、大对象和全列扫描，需要不同的数据局部性。
  • 一次提交的不变量：订单、库存和幂等结果怎样同成败，不能靠两次 put 或先查后写代替。
  • 成功到底承诺什么：本地 WAL、远端持久、回放可见和灾难 RPO 分开；最后才比较引擎放大与运维成本。
  • Access key and query shape: point lookup, short range, term candidates, blobs and column scans need different locality.
  • One-commit invariants: make order, stock and idempotency succeed together; two puts or a precheck cannot substitute.
  • What success promises: separate local WAL, remote durability, replay visibility and disaster RPO before comparing engine amplification and operations.

先定负载与访问路径Fix the workload and access paths

主场景是结账。平均 40 笔/s，8 倍峰值 320 笔/s；每笔 1,500 B 订单快照，两个 40 B 索引。按 order_id 确认、按 user_id 列表，并按 sku 条件扣库存。选择事务型行存，是因为这些状态要同提交；320 不是单库够用的证明。

先以一个主库、两份异步副本为待验证方案：一年快照和所列索引约 1.993 TB/份，三活副本加一紧凑备份约 7.97 TB；活副本旧版本按 1.5 倍计则约 10.96 TB。其他表、日志、空闲空间和备份历史另计。确认读回当前主库并开启新读视图；允许旧一秒的列表才考虑副本。

The running workload is checkout. Assume 40 transactions/s on average, an 8× peak of 320/s, a 1,500 B snapshot and two 40 B index entries. Confirm by order_id, list by user_id, and decrement stock conditionally by sku. A transactional row store joins these changes in one commit; 320 alone proves no capacity limit.

Evaluate one primary and two async replicas. Annual snapshots plus the specified indexes total about 1.993 TB/copy: three live copies and one compact backup need 7.97 TB, or 10.96 TB with a 1.5× live-version factor. Other tables, logs, free space and backup history are extra. Confirmation uses the current primary and a fresh read view; stale-allowed lists may use replicas.

行存：把不变量放进一次提交Row store: put invariants in one commit

图1：一个主库事务拥有订单、库存与结果。唯一键为可信 caller 的 (caller,key)，绑定完整规范请求；示例把重复 sku 合并、正数量有界验证并排序，delivery_ref 也参与绑定。同键同参读已存结果，同键换参冲突；外部支付不在这个事务内。

Deck 1: one primary transaction owns order, stock and result. A trusted caller scopes the unique (caller,key). Bind the whole canonical request, including delivery_ref; merge repeated skus, validate positive bounded quantities and sort. Same-key retries reuse the result; changed parameters conflict. External payment is outside this transaction.

关键实现：条件扣减与持久幂等Implementation: conditional decrement and durable idempotency

下面是伪代码；可执行适配用 Python 标准库和 SQLite 3.38+，并实际运行同一条库存 SQL。BEGIN IMMEDIATE先获取该数据库的唯一写事务；这解释了为何幂等 SELECT 后不会有另一写者插队，不把“先查没有”当通用防重。其他引擎须处理唯一键冲突、行锁、死锁/序列化失败并有界重试整个事务。[11][12]

This is pseudocode; the executable adapter uses Python’s standard library and SQLite 3.38+ with the same stock SQL. BEGIN IMMEDIATE acquires the database’s single writer before reading idempotency, rather than relying on a generic not-found precheck. Other engines need unique-conflict handling, row locks and bounded whole-transaction retries for deadlock/serialization errors.[11][12]

checkout(trustedCaller, key, request):
  binding, sortedLines = validateAndCanonicalize(request)
  # Positive bounded quantities; merge duplicate SKUs; bind delivery_ref too.
  BEGIN IMMEDIATE  # SQLite adapter: acquire the database writer before SELECT.
  try:
    prior = SELECT binding, outcome, order_id FROM idempotency
            WHERE caller = :trustedCaller AND key = :key
    if prior exists:
      if prior.binding != binding: ROLLBACK; return KEY_CONFLICT
      COMMIT; return prior.outcome, prior.order_id
    INSERT idempotency(trustedCaller, key, binding, PENDING, NULL)
    SAVEPOINT effect
    orderId = newId()
    INSERT orders(orderId, trustedCaller, request.delivery_ref)
    outcome = CREATED
    for (sku, qty) in sortedLines:
      changed = execute("UPDATE inventory SET on_hand = on_hand - :qty "
                        "WHERE sku = :sku AND on_hand >= :qty", sku, qty)
      if changed != 1:
        ROLLBACK TO effect  # Undo every earlier SKU and the order.
        outcome = OUT_OF_STOCK; orderId = NULL; break
      INSERT order_line(orderId, sku, qty)
    RELEASE effect
    UPDATE idempotency SET outcome = :outcome, order_id = :orderId
      WHERE caller = :trustedCaller AND key = :key
    COMMIT  # Return only after the configured local durability barrier.
    return outcome, orderId
  on database or connection error:
    ROLLBACK if transaction is still active
    return UNKNOWN_OR_RETRY_SAME_KEY  # Never claim a new successful order.

UPDATE ... on_hand>=qty 的受影响行数必须恰为 1。第二个 sku 不足时回到 savepoint，撤销前面的库存和订单，再提交稳定的 OUT_OF_STOCK 回执；补货后同键仍返回原拒绝，新业务意图才用新键。成功结果与库存同提交，不提交 PENDING；示例不清理幂等记录，真实保留期须覆盖重试/恢复窗口。

Require exactly one affected row from UPDATE ... on_hand>=qty. If the second sku fails, the savepoint undoes earlier decrements and the order, then the transaction stores a stable OUT_OF_STOCK receipt. Restocking does not change that key’s result; new intent uses a new key. Successful results and stock commit together; PENDING is never committed. The demo never expires dedupe records; real retention must cover retry/recovery windows.

本地持久、复制和灾难 RPOLocal durability, replication and disaster RPO

WAL 先满足所需持久屏障，数据页可稍后回刷；成功不要求逐笔刷完所有数据页。[7] 图中只等本地持久，复制异步：主盘永久损坏可同时丢订单与幂等表，重试不能补回未复制的事务，必须对账。提交前确知未提交则回滚；跨提交点断连则查同键，不能武断宣布失败。

The required durable WAL barrier precedes persistent data-page flush; commit need not flush every data page.[7] This diagram waits only for local durability and replicates asynchronously. Permanent primary-disk loss can lose both orders and dedupe records; retries cannot reconstruct an unreplicated transaction. Reconcile business effects. A known pre-commit abort rolls back; a disconnect across commit is unknown until same-key recovery.

若承诺已确认写幸存单机故障，要等位于相应故障域的同步持久副本，并隔离旧主、只提升满足屏障的副本；这仍不涵盖所有地域同时丢失。[8] 收到、写入 OS、持久落盘和回放可见不同；PostgreSQL18 的 remote_apply等待同步副本回放，但旧快照仍需结束。列表一秒是目标，异步复制不自动兑现；没有可信回放/变更水位就不能证明最大陈旧，超限应回主或明确失败。

To survive a host loss without losing acknowledged writes, wait for durable synchronous copies in the required failure domains, fence the old primary and promote only an eligible replica. This does not cover loss of every region.[8] Received, OS-written, durable and replay-visible are distinct. PostgreSQL18 remote_apply waits for synchronous replay, but readers must still leave old snapshots. A one-second list target is not automatic with async replication: without trusted replay/change watermarks, maximum staleness is unproved; route over-budget reads to the primary or fail explicitly.

单键 KV：写全成员集合与 ACK 含义Single-key KV: name membership and ACK meaning

图2限定为 Dynamo 风格单键协议。健康时 N=3、R=W=2：写确认 W={N1,N2}，后读 R={N2,N3} 在 N2 相交，但仍需版本排序/合并。反例换一轮写：N2 对写方失联、N3 投递延迟，候补 N4 代收，W={N1,N4} 已成功；N2 恢复但提示/N3 写尚未到时，R={N2,N3} 两份都可旧。2+2>3 没有约束扩大后的成员集合。[2]

Deck 2 is a Dynamo-style one-key protocol. With N=3 and R=W=2, healthy W={N1,N2} intersects later R={N2,N3}, but still needs version ordering/reconciliation. In a new write, N2 is unreachable, N3 delivery lags, and fallback N4 accepts W={N1,N4}. After N2 recovers but before handoff or N3 delivery, R={N2,N3} can return two old values. The inequality 2+2>3 does not constrain the expanded membership.[2]

图上 ACK 为“已持久”是额外教学约定。Dynamo 论文 §6.1 还讨论缓冲写、以耐久换延迟，不能由 W=2 推出两份已落盘。[2] hint 是修复，不是强读证明；严格 quorum 拒绝候补换成员会减少可写窗口，相交也不自动带来线性一致或跨键事务。

Durable ACKs are an additional assumption in the diagram. Dynamo §6.1 also describes write buffering that trades durability for latency: W=2 alone does not prove two durable copies.[2] Hints repair placement; they do not prove strong reads. Refusing fallback membership reduces write availability, while intersection still does not create linearizability or a cross-key transaction.

候选负载是可合并偏好或定义过增删合并规则的购物车。A9 的 1 KB 会话、6,400 QPS 只匹配键形状；撤销、一次性令牌和权限收紧不能随便读旧。LWW 覆盖会丢并发增量，不能安全扣库存；事务型 KV 是否满足结账，应另查提交和读契约，不能套这张图。

Candidates include mergeable preferences or carts with defined add/delete reconciliation. A9’s 1 KB sessions at 6,400 QPS match a key shape without proving revocation, one-time-token or authorization safety. LWW can lose increments and cannot safely decrement stock. A transactional KV needs its own commit/read contract rather than inheriting this diagram.

宽表：按行键聚集短范围Wide rows: cluster a short range by row key

图3的局部性在行键。Bigtable2006 论文用 (row,column,timestamp)→bytes，tablet 管连续行范围，提供单行原子读写/读改写，不提供通用跨行事务。[1] 本例行键是 conversation_id+日桶，msg 限定符为 (sent_at,message_id)；50 条消息是 50 个单元格，同一单元格版本留给编辑。多页、多桶不自动组成一份快照，游标应固定查询边界及最后时间/id。

Deck 3 localizes by row key. Bigtable’s 2006 paper models (row,column,timestamp)→bytes, assigns contiguous row ranges to tablets, and provides single-row atomic reads/writes/read-modify-writes without general cross-row transactions.[1] Here conversation_id plus a day bucket names the row; msg qualifiers use (sent_at,message_id). Fifty messages are fifty cells, while versions represent edits. Multiple pages/buckets need an explicit query boundary and time/id cursor rather than an assumed global snapshot.

A8：2,000×400 B=0.8 MB/s；最近 50 条正文为 20 KB。规模小时，行存复合索引 (conversation_id,sent_at,message_id) 同样匹配“会话等值 + 时间范围/排序”；先测计划和工作集，再决定是否宽表。[14] 时间桶限制历史体积，不能分散同一当前热桶；加盐分散写后，读要 fan-out 并按时间/id 归并。全局时间前缀还会集中最新写。

A8 gives 2,000×400 B=0.8 MB/s; fifty bodies total 20 KB. At smaller scale, a relational composite index (conversation_id,sent_at,message_id) fits conversation equality followed by time range/order. Inspect the plan and working set before choosing wide rows.[14] Time buckets bound history rather than spreading current hot writes. Salting adds fan-out and time/id merge; a global-time prefix concentrates fresh writes.

节点内仍需合并内存与文件版本；过期数据停止可见和旧文件物理回收分开。宽表的列是行内限定符；分析列存把许多行上的同字段聚在一起。两者都能“扫描”，但短会话范围与全年金额 SUM 的读取代价不同。

A node still reconciles memory/file versions; expiry visibility and physical file reclamation are separate. A wide-row column is a qualifier within a row, while an analytical stripe groups one field across rows. Both can scan, but a short conversation range and an annual amount SUM have different access costs.

对象：直传字节，条件发布元数据Objects: direct bytes, conditional metadata publication

图4把大字节直传和发布决定分开。先持久创建 PENDING 会话，绑定 caller/key、完整内容、blob_id、大小、校验和与期限，再签发准确键的 create-only 上传权限。S3 的 If-None-Match: *检查当前键版本是否存在；它不是对象天生不可变的证明。禁止绕过条件写、限制删除/重用键或绑定 version_id，才守住本例不可变身份。[10]

Deck 4 separates direct bytes from publication. Persist a PENDING session binding caller/key, full content, blob_id, size, checksum and expiry, then issue create-only upload authority for that exact key. S3 If-None-Match: * checks the current key version; it does not make every object inherently immutable. Enforce conditions and restrict deletion/key reuse, or bind a version_id, to preserve the immutable identity assumed here.[10]

PUT 超时是结果未知，先查上传结果并核验；存在不等于内容正确。可信验证器按该会话的完整 object_key（含存储命名空间）做 HEAD，proof 绑定 caller/upload_id/object_key/version/size/checksum。适配先拒绝错 caller/id，SQL 再核会话已存 key；同内容 B 的 HEAD 不能用于发布 A。客户端不能构造 proof，ETag 也不能一概当内容摘要。真实核验是外部契约，本地适配不实现 S3。[10]

A PUT timeout is unknown: query and verify, not merely check existence. A trusted verifier HEADs the session’s full object_key, including its storage namespace, and binds proof to caller/upload_id/object_key/version/size/checksum. The adapter rejects wrong caller/id and SQL checks the stored key; B’s identical content cannot supply A’s publication proof. Clients cannot mint proof, and ETags are not universal content digests. Live verification remains external; the adapter does not implement S3.[10]

关键实现：只有状态转换胜者有权发布或清扫Implementation: only the transition winner may publish or clean

-- publish: proof binds caller/upload_id/full object key and the exact version.
UPDATE upload
SET state = 'COMMITTED', object_version = :version
WHERE caller = :caller AND upload_id = :id AND state = 'PENDING'
  AND expires_at > unixepoch()
  AND object_key = :object_key
  AND expected_size = :size AND checksum = :checksum
RETURNING upload_id, state, object_version;

-- cleanup: a returned row plus confirmed COMMIT grants deletion ownership.
UPDATE upload SET state = 'ABORTED'
WHERE caller = :caller AND upload_id = :id AND state = 'PENDING'
  AND expires_at <= unixepoch()
RETURNING upload_id, state, object_version;

SQLite 3.38+ 的 unixepoch()在拿到写事务后随语句采样，不复用锁前时间。先取完 RETURNING 行，再确认 COMMIT；0 行不代表获权。[12] 发布重试只在会话、完整对象键、准确版本/大小/校验和与已提交记录全相同时返回原 COMMITTED；清扫重试不给新的删除权。

SQLite 3.38+ samples unixepoch() in the statement after acquiring the writer transaction rather than reusing pre-lock time. Consume RETURNING rows and confirm COMMIT before acting; zero rows grant no ownership.[12] Publication retries reuse COMMITTED only when session, full object key and exact version/size/checksum match. Cleanup retries grant no new deletion ownership.

清扫若先把 PENDING 改成 ABORTED，迟到 finalize 失败；发布先赢则清扫不能删 COMMITTED。已签发请求仍可能在过期后落盘，清扫还需在权限失效、在途请求有界排空后复查准确版本的迟到孤儿。元数据必须 COMMITTED 才签发读权限；对象库与元数据库仍有两个提交。小而频繁变化、要同库存提交的订单行不会因字节量小就适合对象。

If cleanup wins PENDING→ABORTED, late finalize fails; if publication wins, cleanup cannot delete COMMITTED. Previously issued uploads may finish after expiry, requiring exact-version orphan rechecks after authority expiry and a bounded in-flight drain. Issue read authority only for COMMITTED metadata. Body and metadata still have two commits; small mutable order rows needing stock atomicity do not fit this path merely because bandwidth is low.

倒排：先保留源，再派生搜索Inverted index: retain the source before deriving search

图5的倒排是派生视图，源库是权威。正文、所有者、源版本和 outbox 同库事务，saved 不代表已可搜索。Relay 至少一次投递固定版本快照或删除标记；Indexer 按 doc_id/source_version 幂等，只在索引确认后推进交付，旧版本不能盖回新值/墓碑。中途宕机重投；单调源版本、删除保留与重建截止点要一起定义，详见 Ch13。

Deck 5 treats the inverted index as a derived view and the source as authority. Commit body, owner, source version and outbox together; saved does not imply searchable. Relay delivers versioned snapshots/deletions at least once. Indexer applies doc_id/source_version idempotently and advances only after index acknowledgment; old versions cannot overwrite new data/tombstones. Recovery replays; version order, deletion retention and rebuild cutoffs belong together. See Ch13.

A10：80×20 B=1,600 B≈1.6 KB posting/文档，词典、位置、删除和副本另计。A4 的五秒是新鲜度目标，积压时看最老待办年龄。查询先拿候选 id/version，再回源校验当前 ACL、删除、版本和词匹配；可过滤陈旧命中，不能找回尚未入索引的新文档。源库/倒排缺失就有界失败，不能把不完整说成完整。

A10 assumes 80×20 B=1,600 B≈1.6 KB of postings/document, excluding dictionary, positions, deletions and replicas. A4’s five seconds is a freshness target; monitor oldest pending age. Retrieve candidate ids/versions, then validate current source ACL, deletion, version and term match. This removes stale hits without discovering unindexed new documents. Bound failures or incomplete results when source/index data is unavailable.

若保存与可搜索必须同成败，可评估同事务引擎的全文索引。同步调用外部搜索仍是两次写，不会回滚已提交源数据。本章由源可重建，索引不能冒充唯一账本；若另选搜索引擎作权威，必须重新证明其耐久、更新、权限、备份/重建契约，而不是由“能存正文”推断。

If saving and searchability must succeed together, evaluate full-text indexing in the same transaction engine. A synchronous external search call is still a second write and cannot undo the source commit. Here the source supports rebuilding, so the derived index cannot become the sole ledger. Choosing a search engine as authority requires a separate durability/update/authorization/backup/rebuild contract rather than inferring authority from stored display fields.

引擎：热路径之后，还要支付后台成本Engines: budget background cost after the hot path

图6上下是同一 API 的两种候选，不是串联两套库。B+Tree 按页组织有序键，点查沿树、范围读沿叶序；上层缓存使树高不等于物理 I/O，非聚簇索引还可能回表。修改缓冲页会生成 WAL，回刷持久页前必须先持久相应日志。[7] 多索引、页分裂、整页日志与同页合写决定实际放大，A6 的 16.384 倍只是模型。

Deck 6 shows two alternatives behind one API, not two stores in series. B+Tree orders keys in pages, descends for point access and follows leaf order for ranges. Cached upper pages make height differ from physical I/O; a non-clustered index may need a row fetch. Buffer changes generate WAL, whose relevant records must be durable before persistent-page flush.[7] Indexes, splits, full-page logs and coalescing determine actual amplification; A6’s 16.384× is only a model.

本例 LSM 选择“WAL 持久 → 引擎装入 memtable → 回成功”，SSTable flush/合并在后台；仅有 WAL 文件不代表已经完成内存应用，也不能过早回收恢复所需日志。[5][13] LSM 结构不强制每笔同步落盘，RocksDB 默认非同步写可幸存进程退出却可能在机器故障丢最近写，需按需求设置 WriteOptions.sync=true等持久策略。[13]

The LSM path here chooses durable WAL → engine installs Memtable → success; SSTable flush and compaction run in the background. WAL existence alone is not completed memory application, and required recovery logs must be retained.[5][13] The structure does not force synchronous writes. RocksDB’s default non-sync writes can survive process failure yet lose recent writes on machine failure; configure a durability policy such as WriteOptions.sync=true when required.[13]

先定义放大口径，再算持续预算Define amplification before budgeting sustained load

本章 WA=引擎写到存储设备字节/用户字节，含 WAL、flush、合并；NAND 内部放大另算。A12：10 MB/s 输入、100 MB/s 盘写预算，WA=6 得 60 MB/s，WA=12 得 120 MB/s，后者已超预算。还需预算合并读 I/O、临时空间和尾延迟；不能把 WAL 顺序写很快当成持续吞吐证明。不同产品指标可能排除 WAL，比较前对齐分子。

Here WA is engine bytes written to storage per user byte, including WAL, flush and compaction; internal NAND amplification is separate. A12’s 10 MB/s input and 100 MB/s write budget yield 60 MB/s at WA=6 but 120 MB/s at WA=12, already over budget. Compaction reads, temporary space and tail latency also matter. Sequential WAL speed is not sustained-throughput proof; align numerators when product metrics exclude WAL.

更多未合并文件/版本会增加读工作与空间压力，输入/输出共存还需临时空间。RocksDB 的 immutable memtable、L0 文件和待合并字节积压能触发减速/停写。[9] 限入流、保留后台资源并测恢复速度；加应用实例不修复合并瓶颈。读需合并版本/墓碑；旧值或能恢复旧值的副本尚在时，墓碑不能只凭年龄删除。

More uncompacted files/versions increase lookup work and space pressure, while simultaneous inputs/outputs need temporary space. RocksDB can slow or stop writes for immutable-memtable, L0-file or pending-compaction backlogs.[9] Bound ingestion, reserve background resources and measure recovery; application replicas do not fix this bottleneck. Reads reconcile versions/tombstones; age alone cannot justify deleting a tombstone while older values or restoring replicas remain.

正确且未损坏的 Bloom 对已插入键没有假阴性：no 可跳过该点查文件，maybe 仍要查索引/数据，缓存可能免去物理 I/O；它不返回值，也不能把整段范围判空。[1] B+Tree 与 LSM 都能做点查/范围；事务/复制另看协议。选型压测保留真实键偏斜、索引、压缩和后台任务；论文的负载特化思想不是“每个表都配新系统”。[6]

An intact, correctly built Bloom filter has no false negatives for inserted keys: no skips a point-lookup file; maybe still needs index/data probes, possibly served from cache. It returns no value and cannot declare an entire range empty.[1] Both B+Tree and LSM support point/range access; transactions and replication are separate protocols. Benchmark real skew, indexes, compression and background work. Workload specialization does not demand a new system for every table.[6]

列条带：少数字段，完整快照聚合Column stripes: a few fields, one complete snapshot

图7把一次分析固定在同一不可变快照和 manifest。只扫 amount 时，一年 1,261,440,000×8 B=10.09152 GB；加 1 B status 共 11.35296 GB，整行则 1.89216 TB。1,500÷8=187.5 是裸字节比，不是延迟倍数。Dremel2010 的列条带与执行树用于只读嵌套分析；这不等于所有列式产品都不支持更新/事务。[4]

Deck 7 pins analysis to one immutable snapshot and manifest. Annual amount bytes are 1,261,440,000×8 B=10.09152 GB; adding one-byte status gives 11.35296 GB versus 1.89216 TB of full rows. The 187.5=1,500÷8 ratio concerns raw bytes, not latency. Dremel2010 uses column stripes and an execution tree for read-only nested-data analysis; this does not imply every columnar product lacks updates or transactions.[4]

关键实现：完整片段才能得到准确 SUMImplementation: exact SUM requires complete fragments

下面摘自可运行 Java17 示例。可信 manifest 已证明片段完整、不重叠，并固定 query/snapshot/manifestVersion 与内容 hash；可信叶子按该查询的过滤/算子和准确文件算部分和。协调代码只检查身份、重复冲突和完整性，不能从一个 hash 自行证明叶子算对。空 manifest 表示已验证的空数据集，非请求漏传。

This excerpt compiles in the runnable Java17 example. A trusted manifest proves complete, disjoint fragments and pins query/snapshot/manifestVersion/content hashes. Trusted leaves apply the declared query filter/operator to the exact files. This coordinator checks identity, duplicate conflicts and completeness; a hash alone cannot prove a leaf computed correctly. An empty manifest means a verified empty dataset, not omitted request data.

public record Part(String query, String snapshot, String manifestVersion, String fragment,
                   String contentHash, BigInteger sum) {
    public Part {
        Objects.requireNonNull(query); Objects.requireNonNull(snapshot);
        Objects.requireNonNull(manifestVersion);
        Objects.requireNonNull(fragment); Objects.requireNonNull(contentHash);
        Objects.requireNonNull(sum);
    }
}
public static BigInteger exactSum(String query, String snapshot, String manifestVersion,
        Map<String, String> manifest, List<Part> replies) {
    // The trusted manifest is complete and its fragments do not overlap.
    Objects.requireNonNull(query); Objects.requireNonNull(snapshot);
    Objects.requireNonNull(manifestVersion);
    manifest = Map.copyOf(manifest);
    Map<String, Part> accepted = new HashMap<>();
    for (Part part : replies) {
        if (!query.equals(part.query()) || !snapshot.equals(part.snapshot())
                || !manifestVersion.equals(part.manifestVersion())
                || !part.contentHash().equals(manifest.get(part.fragment()))) {
            throw new IllegalArgumentException("wrong query/snapshot/fragment/hash");
        }
        Part previous = accepted.putIfAbsent(part.fragment(), part);
        if (previous != null && !previous.equals(part)) {
            throw new IllegalArgumentException("conflicting duplicate");
        }
    }
    if (!accepted.keySet().equals(manifest.keySet())) {
        throw new IllegalStateException("INCOMPLETE: retry missing fragments only");
    }
    BigInteger total = BigInteger.ZERO;
    for (Part part : accepted.values()) total = total.add(part.sum());
    return total;
}

正常 A=100 分、B=200 分得到 300；重投相同 A 仍为 300，错快照、错 manifest 版本、陌生片段或冲突部分和拒绝；缺 B 是 INCOMPLETE，绝不把 100 当准确总计。用 BigInteger 累加避免 long 溢出；仍需上游定义金额单位、符号与范围。真实服务应有截止时间、有界重试缺片、版本化完整 manifest 和验证过的叶子回执。

With A=100 cents and B=200 cents, the sum is 300; replaying identical A still gives 300. Reject wrong snapshots/manifest revisions, unknown fragments and conflicting partial sums. Missing B is INCOMPLETE, never an exact 100. BigInteger avoids long overflow, while upstream still defines units/sign/range. A real service also needs deadlines, bounded missing-fragment retries, immutable complete manifests and verified leaf receipts.

小数据先用行存 SUM；历史扫描与结账抢 I/O 时再导出列文件，记录截止位置和完整 manifest。导出延迟可被报表接受，不能借给确认页。选型来自读取字段/范围与更新要求，不能只按“宽表也有列”或“列存一定只读”分类。

For small data, start with a row-store SUM. Export column files with a cutoff and complete manifest when history scans contend with checkout I/O. Reports may tolerate export lag; confirmation cannot. Fields/ranges and update requirements drive the choice, rather than equating wide-row columns with stripes or assuming all column stores are read-only.

面试复盘与验证边界Interview recap and validation boundaries

口述顺序：访问键/查询 → 原子不变量 → 成功与故障承诺 → 引擎/复制与代价。结账先守住订单、库存、幂等同提交；聊天按会话时间聚集；对象按准确版本发布；搜索从可恢复源派生；分析缺片不回准确总计。规模不足以单独决定产品。

Interview order: access/query → atomic invariant → success/failure promise → engine/replication and cost. Checkout joins order/stock/idempotency. Chat clusters conversation/time; objects publish exact versions; search derives from a recoverable source; missing analytical fragments never produce an exact sum. Scale alone does not choose a product.
