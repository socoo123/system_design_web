先定一条负载，再开口引擎Fix one workload before naming an engine

中文

我先不报产品名。结账要在一次提交里写入订单、明细，并按 sku 扣库存；确认页要读到自己的写；列表按 user_id 查。平均 40 笔成功事务每秒，8 倍峰值 320。逻辑行 1.5 KB。这条路径的权威是主行存，二级索引跟同一次提交走。副本可以接允许旧一点的列表读，窗口是复制延迟。对象存储、把倒排当唯一副本、用 KV 的二级索引假装 join，都接不住这组约束。

后面六组图各自回答一种访问形状：点写加事务、单键 quorum、行键加列范围、不可变大对象、异步倒排、以及三条明确走错的路径。分析列扫描单独成组，因为它和宽表扫描不是同一条磁盘路径。块设备、共享文件、向量近邻的内部结构、隔离级别百科都不在这章展开。云厂商的服务名单也不背。

English

I do not open with a product name. Checkout must insert the order and its lines and decrement stock by sku in one commit. The confirmation page must read its own write. The list is by user_id. The assumption is 40 successful transactions per second, 320 at an 8× peak, and a 1.5 KB logical row. Authority sits in a primary row store; the secondary index commits with that transaction. A replica may serve list reads that tolerate staleness, and the window is replication lag. An object store, an inverted index as the only copy, and a KV secondary index pretending to be a join all miss this constraint set.

The next six decks are six access shapes: a transactional point write, a single-key quorum, a row key plus a column range, an immutable blob, an async inverted index, and three paths that are explicitly wrong. A columnar analytic scan is its own deck, because it is not the wide-row scan. Block devices, shared files, vector-index internals, and an isolation encyclopedia stay out. So does a cloud product catalog.

把假设算成设计

40 笔每秒乘 86,400 秒，是每天 3,456,000 笔订单。再乘 365，是每年 1,261,440,000 笔。每笔 1,500 字节，原始行是 1,892,160,000,000 字节，也就是 1.89 TB/年（按 1012 字节的 TB，不是 TiB）。两个二级索引各按 40 字节估算，一年一份拷贝约 0.10 TB。行加索引一份是 1.99 TB，三副本约 6.0 TB/年。再留一份备份约 2.0 TB，6.0+2.0=8.0 TB。若活副本再按假设的 1.5 倍计入 MVCC 旧版本，6.0×1.5+2≈11 TB。规划取 8–11 TB/年，这仍是假设。

峰值 320 笔事务每秒乘 1.5 KB，逻辑写入只有约 480 KB/s。若每次提交把主行和两个二级索引各弄脏一个 8 KB 页，上界是 320 × 3 × 8 KB = 7.68 MB/s。相对 0.48 MB/s 的逻辑负载，这个上界约 16 倍，而且同一页往往能装下多行，真实脏页会更低。数量级仍然远没到“必须上对象存储”或“必须先做分布式写扩展”。它真正推动的决定是：一次提交要覆盖订单、明细和库存；确认读要读自己的写；列表读可以接受一段复制延迟。

读侧用同一组假设。20 次读乘 40，平均 800 QPS；8 倍峰值 6,400 QPS。确认页那一次必须看见刚提交的订单，所以它回到主库，或者等一个已经应用到本次日志的副本。其余列表读若允许旧一秒（这也是假设的 SLO，不是测量），就可以打异步副本，把主库留给事务和行锁。6,400 次点读还不够单独证明要在前面再加一层缓存；缓存是读 QPS 或热键再抬一个数量级时的下一章。

热点要单独标成假设。若某个 sku 占结账的 30%，峰值约 96 次更新打到同一库存行，行锁在这一行上排队。那是争用。先确认偏斜是否存在，再谈拆分或单行排队。把 1.5 KB 的可变行搬进对象存储解不开这把锁。

示例 SLO 同样是假设，面试时要请对方改：结账提交可用性 99.9%、服务端 p99 小于 300 ms；购买者的确认读满足 read-your-writes；列表读的复制延迟告警线例如 1 秒；搜索可见延迟例如 5 秒。它们决定副本能不能接读、倒排能不能异步，不决定海报上的 CAP 字母。

Turn the assumptions into a design

Forty checkouts a second times 86,400 seconds is 3,456,000 orders a day. Times 365 is 1,261,440,000 orders a year. At 1,500 bytes each, the raw rows are 1,892,160,000,000 bytes, or 1.89 TB/year using TB as 1012 bytes, not TiB. Two secondary indexes at an assumed 40 bytes each add about 0.10 TB for one copy. Rows plus indexes are 1.99 TB a copy, and three replicas are about 6.0 TB/year. One backup adds about 2.0 TB, so 6.0+2.0=8.0 TB. If live replicas also carry an assumed 1.5× of old MVCC versions, 6.0×1.5+2≈11 TB. The planning band is 8–11 TB/year, still an assumption.

A peak of 320 transactions a second times 1.5 KB is only about 480 KB/s of logical writes. If every commit dirties one 8 KB page for the primary row and one page for each of two secondary indexes, the upper bound is 320 × 3 × 8 KB = 7.68 MB/s. Against 0.48 MB/s of logical payload that bound is about 16×, and a real page usually holds more than one row, so the dirty-page rate is lower. The magnitude does not force object storage or a distributed write scale-out. It forces a commit that covers the order, the lines, and the stock decrement, a confirmation read that sees that commit, and list reads that may sit behind replication lag.

Reads use the same assumptions. Twenty reads times 40 is 800 QPS average, and an 8× peak is 6,400 QPS. The confirmation read has to observe the order just committed, so it goes to the primary, or to a replica that has applied this log record. Other list reads may use an async replica when a one-second lag is acceptable — that one second is an assumed SLO, not a measurement — and the primary keeps the transactions and the row locks. 6,400 point reads do not by themselves require a cache in front. A cache is the next chapter, when read QPS or a hot key jumps another order of magnitude.

Label the hot key as an assumption. If one sku is 30% of checkouts, the peak is about 96 updates on one stock row, and row locks queue there. That is contention. Confirm the skew before splitting or serializing the row. Moving a 1.5 KB mutable row into an object store does not open that lock.

The sample SLOs are assumptions, and you should invite the interviewer to change them: checkout availability 99.9% with server-side p99 under 300 ms; the buyer's confirmation read is read-your-writes; list reads alert at, for example, one second of replication lag; search becomes visible within, for example, five seconds. Those numbers decide whether a replica may serve reads and whether the inverted index may be async. They do not pick a CAP letter off a poster.

行存：一次提交，再谈副本延迟Row store: one commit, then replication lag

沿这条路径走一遍

客户端带 Idempotency-Key 调用 POST /v1/orders，正文是 user_id 和若干 {sku, qty}。订单服务先按调用方加上这个键查找。命中就返回已经生成的 order_id，库存不会再扣一次。未命中才在主行存开始事务：插入 Order，插入 OrderLine，再执行 UPDATE inventory SET on_hand = on_hand - qty WHERE sku = ? AND on_hand >= qty。受影响行数是 0 就整笔回滚，接口返回冲突或校验失败，而不是留下已扣库存却没有订单的状态。user_id 二级索引由引擎在同一次提交里维护。提交成功后响应 201 和 order_id。购买者马上刷新的确认读回到主库，按 order_id 取刚写的行。

最小记录是 Order(order_id, user_id, status, version, created_at)、OrderLine(order_id, line_no, sku, qty)、Inventory(sku, on_hand)，以及 Idempotency(caller, key, order_id)。列表查询走 (user_id, created_at)。这个索引和行在同一条提交日志里，副本追日志时两者一起落后，不会出现“行已经在副本上、索引还指着旧订单”这种拆开的窗口。那是后面 KV 二级索引才会有的裂缝。

Walk the path in order

The client calls POST /v1/orders with an Idempotency-Key, a user_id, and lines of {sku, qty}. The order app looks up caller plus key first. A hit returns the existing order_id and does not decrement stock again. A miss starts a transaction on the primary: insert Order, insert OrderLine, then UPDATE inventory SET on_hand = on_hand - qty WHERE sku = ? AND on_hand >= qty. Zero rows updated aborts the whole transaction. The API returns a conflict or a validation error, not a stock debit without an order. The engine maintains the user_id secondary index inside that commit. Success is a 201 and an order_id. The buyer's immediate confirmation read goes back to the primary and loads that row by order_id.

The minimal records are Order(order_id, user_id, status, version, created_at), OrderLine(order_id, line_no, sku, qty), Inventory(sku, on_hand), and Idempotency(caller, key, order_id). The list uses (user_id, created_at). That index and the row share one commit log, so a replica that is behind is behind on both. You do not get a replica where the row is present and the index still points at an older order. That split is the KV secondary-index crack, later.

为什么是行存，而峰值只有 320

320 次小事务和 7.68 MB/s 的脏页上界，说明第一版用一个主库加一个异步副本就覆盖得住写吞吐。选择行存的原因是提交边界：库存条件和订单插入必须同时成功或同时失败。二级索引放大是这笔选择的代价，要在口播里算出来。两个索引意味着一次逻辑插入至少碰到主结构加两份索引；若每个结构弄脏一整页，上界约 16 倍于 480 KB/s 的逻辑字节。忽略这个倍数，就会把“行只有 1.5 KB”误当成“磁盘只写了 1.5 KB”。

这条路径上的页式引擎是原地改页加 WAL。库存的随机更新会弄脏页，但读自己的写很短，树高可预期。O'Neil 等人 1996 年的 LSM-tree 针对另一端：历史表插入极高时，用 B-tree 实时维护索引可能把事务 I/O 大约加倍，于是把变更攒在内存组件里，再像归并一样刷到磁盘组件；立刻返回的点查有时更贵。[5] 结账不是那条历史表。热路径吞吐高，不等于写放大低。宽表的追加才更接近这篇论文，也更接近 Bigtable 的 memtable 加不可变 SSTable。[1]

Why a row store, at a peak of only 320

320 small transactions and a 7.68 MB/s dirty-page upper bound say a first version is one primary plus one async replica. The row store wins because of the commit boundary: the stock predicate and the order insert succeed or fail together. Secondary-index amplification is the cost, and it belongs in the spoken math. Two indexes mean one logical insert touches the primary structure plus two index structures. If each dirties a full page, the upper bound is about 16× the 480 KB/s of logical bytes. Skip that factor and “the row is 1.5 KB” gets heard as “disk wrote 1.5 KB”.

The page engine on this path updates the page in place and appends a WAL record. A random stock update dirties a page, but read-your-writes stays short and the tree height is predictable. The 1996 LSM-tree targets the other end: on a history table with a very high insert rate, a live B-tree index can about double transaction I/O, so changes batch in a memory component and merge into disk components. Point lookups that must return immediately can cost more.[5] Checkout is not that history table. High hot-path throughput is not low write amplification. Wide-row appends are closer to that paper, and to Bigtable's memtable plus immutable SSTables.[1]

替代、延迟窗口、常见错法

替代是同步副本：提交要等副本确认，列表读可以更接近主库，代价是提交延迟和副本故障会拖住结账。当前假设把列表 SLO 放在大约 1 秒，所以日志异步船出去更合适。另一个替代是把库存和订单拆成两个库，用补偿把扣减“补回去”。那会制造新的窗口：订单已提交、补偿还没跑、库存已经少了。在 320 QPS 的单主库还能放下这两类行时，不付这个窗口。

故障按时间排。事务在返回前崩溃，调用方重试同一个幂等键，库存只扣一次。提交已经成功但响应丢失，同样靠幂等键返回原 order_id，而不是再插入一笔。副本落后时，客服列表会暂时看不见新订单；购买者自己的确认读若被误送到副本，就会看到“支付成功但订单不存在”。所以 read-your-writes 要写进路由，不能靠默认。主库不可用时，结账失败；副本可以继续提供明确标成旧数据的列表，不能接受新的扣库存。

常见错法是“NoSQL 更快，所以订单用 KV”。320 QPS 若真的疼，疼在热点 sku 的行锁，不在 480 KB/s。单键 put 表达不了“库存够才插入订单”。异步副本是复制延迟的选择。跨机房外部一致的等待放到故障那一节，用 TrueTime 来说。[3]

Alternative, lag window, and the usual miss

The alternative is a synchronous replica: the commit waits for the replica, list reads stay closer to the primary, and commit latency plus a replica outage stall checkout. The assumed list SLO is about one second, so async log shipping fits. Another alternative splits stock and orders across two stores and compensates. That opens a window where the order is committed, the compensation has not run, and stock is already down. While one primary still holds both kinds of row at 320 QPS, do not pay that window.

Order the failures by time. If the transaction crashes before the response, a retry with the same idempotency key decrements stock once. If the commit succeeded and the response was lost, the same key returns the original order_id instead of inserting another order. While the replica is behind, a support list can miss the new order. If the buyer's confirmation read is routed there by mistake, they see a successful payment and no order. Read-your-writes has to be a routing rule. When the primary is down, checkout fails. The replica may keep serving a list that is explicitly stale. It must not accept a new stock decrement.

“NoSQL is faster, so put orders in a KV” misses the constraint. If 320 QPS hurts, it hurts as row-lock contention on a hot sku, not as 480 KB/s. A single-key put cannot say “insert the order only if stock is sufficient.” An async replica is a replication-lag choice. The cross-site external-consistency wait belongs with the failure section, and it is the TrueTime wait.[3]

单键 KV：分区、quorum、以及 sloppy 改了什么Single-key KV: partition, quorum, and what sloppy changes

论文里和这张图对得上的部分

Dynamo 要在故障下仍然接受单键 put。摘要写明：为此它在某些故障里牺牲一致性，并依赖对象版本和由应用协助的冲突处理。[2] 图上的协调者是优先列表里的一台副本，通常是一致性哈希环上的后继，再把值放到后续副本，这里 N=3。健康时 put 在 W 个确认后返回，get 等 R 个回复。(3, 2, 2) 满足 R 加 W 大于 N，但相交只在参与者仍是同一组优先副本时成立。并发 put 仍可能产生要调用方合并的多个版本。图上没有向量时钟，这张图不是时钟算法。

sloppy quorum 改的是成员。优先副本不可达时，写改到下一台健康节点，它不在原来的前 N 个环位置上。hinted handoff 让临时节点记下原目标，恢复后再送回。送达前，只读 N1、N2、N3 可能碰不到握有新值的 N4，因此 R 加 W 大于 N 盖不住这张故障图。put 已返回，也不等于值在规范副本上。临时节点若在送出前损坏，写入可能丢掉。这换来故障期间仍可写；库存扣减接不住。

What in the paper matches this drawing

Dynamo keeps accepting single-key puts through failure. The abstract says that availability sacrifices consistency under certain failures, using object versioning and application-assisted conflict resolution.[2] The coordinator is a preference-list replica, typically the successor on the consistent-hash ring, and it stores the value on the following replicas. N here is 3. While healthy, the put returns after W acknowledgements and the get waits for R. (3, 2, 2) has R plus W greater than N, and the intersection holds only while everyone stays in that same preferred set. Concurrent puts can still return versions the caller must reconcile. The diagram draws no vector clocks, so it is not the clock algorithm.

Sloppy quorum changes membership. When a preferred replica is unreachable, the write moves to the next healthy preference-list node, outside the original first N ring positions. Hinted handoff means that node records the intended target and forwards the write after recovery. Until then, a read of only N1, N2, and N3 can miss N4, so R plus W greater than N does not cover this frame. A returned put is not “the value is on the canonical replicas.” If the hint holder dies before delivery, the write can be lost. The mechanism buys writes during failure. A stock decrement cannot use that window.

什么负载才该走这条路径

访问键是单个小值，例如会话 id 或购物车 id，读写都是 get/put，没有第二行要一起提交。把前面的结账数字换一种问法才比较得清：若 6,400 QPS 全是按 session_id 取 1 KB 会话，没有 sku 条件更新，分区 KV 的单键 quorum 就对上了。会话丢一个并发写进来的字段，产品可以接受；库存少扣一次，不可以。最后写赢是论文之外另加的策略，用来把多个版本折成一个。它会丢掉并发的增量。on_hand 这种计数不能用它。论文留给应用的是看见多个版本之后的合并，不是默认覆盖。[2]

替代是单主的行存或单主 KV：一个主键点查、写入量在百级 QPS 时，主副本比可调 quorum 更容易讲清 read-your-writes。等键空间和可用性交集真的超出一台主库，再引入 N 副本和 R/W。另一条替代是把 W 和 R 都设成 N，故障时直接拒绝写入。那更接近“宁可不可用也不改道”，就不再是 Dynamo 这篇论文在买的性质。结账若仍然要跨 order 与 inventory 两行，任何单键 quorum 都不是替代品，包括把 R 和 W 调大。

常见错法有三句。第一句把 R 加 W 大于 N 说成线性一致。健康路径上它只保证 quorum 相交；版本分叉仍然存在。第二句把 sloppy 写过的值说成已经落在规范副本上。图上的红区就是反例。第三句把会话 KV 和订单行存画成同一个权威。会话可以放在分区 KV 前面做加速，订单和库存的提交仍在主行存。名字里都有 key，不表示故障时的行为相同。

Which workload belongs on this path

The access key is one small value, a session id or a cart id, and every operation is a get or a put. No second row joins the commit. Recast the checkout numbers to see the contrast: if all 6,400 QPS are fetches of a 1 KB session by session_id, with no sku predicate, a partitioned KV quorum matches. Losing one concurrently written session field can be acceptable. Losing one stock decrement is not. Last-write-wins is an extra policy on top of the paper, used to collapse versions. It drops concurrent increments. A counter such as on_hand cannot use it. What the paper leaves to the application is reconciliation after multiple versions are visible, not a default overwrite.[2]

The alternative is a single-primary row store or a single-primary KV. At a few hundred writes a second of primary-key lookups, a primary and a replica explain read-your-writes more directly than a tunable quorum. Add N replicas and R/W when the key space and the availability target actually outgrow one primary. Another alternative sets both W and R to N and refuses the write during failure. That prefers unavailability over rerouting, which is not the property this Dynamo paper is buying. If checkout still touches two rows, order and inventory, no single-key quorum is a substitute, including a larger R and W.

Three misses show up constantly. The first calls R plus W greater than N linearizability. On the healthy path it is a quorum intersection; siblings still happen. The second treats a sloppy write as already stored on the canonical replicas. The red region on the last frame is the counterexample. The third draws the session KV and the order row store as one authority. A session may sit in a partitioned KV as an accelerator. The order and the stock decrement still commit in the primary row store. Sharing the word key does not make their failure behavior the same.

宽表：行键加上列范围，不是二级索引 joinWide row: a row key plus a column range, not a secondary-index join

为什么聊天和指标都要这个形状

Bigtable 的数据模型是一张稀疏、分布式、持久的多维有序映射，下标是行键、列键和时间戳，值是一段字节。行键按字典序排，一段行范围叫做 tablet，是分布和负载均衡的单位。短的行范围通常只和少数机器通信。同一个行键下的读写是原子的，不管这次碰到多少列。它不提供完整的关系模型。[1] 聊天记录把 conversation_id 放进行键，把每条消息放进列族 msg 的一个限定符里，限定符按时间排序。一次“最近 50 条”是这一行里的一段限定符扫描。指标把 series_id 放进行键，把时间桶放进限定符或行键后缀，读的仍是一小段连续键。

论文里的 Analytics 原始点击表用同一条局部性：行名是站点加上会话创建时间，同一站点的会话挨在一起并按时间有序。[1] 这是行键为连续扫描而设计。列族宜少，论文的意图是最多几百个且很少改；限定符可以很多，所以消息 id 做限定符。同一单元格的多个版本按时间戳从新到旧排。五十条消息是五十个列。版本表示“这一列被更新”，不表示“又来了一条消息”。

Why chat and metrics want this shape

Bigtable's model is a sparse, distributed, persistent multidimensional sorted map. The index is a row key, a column key, and a timestamp; the value is an uninterpreted string of bytes. Row keys are lexicographic. A tablet is one row range and the unit of distribution. Reads of short row ranges typically touch a small number of machines. Every read or write under a single row key is atomic, however many columns it touches. The system does not provide a full relational model.[1] Chat puts conversation_id in the row key and each message in a qualifier of family msg, with qualifiers ordered by time. “Last 50” is a qualifier scan inside that row. Metrics put series_id in the row key and the time bucket in a qualifier or a row-key suffix. The read is still a short contiguous key range.

The paper's Analytics raw click table uses the same locality: the row name is the site plus the session's creation time, so one site's sessions sit together and stay chronological.[1] The row key is designed for a contiguous scan. Families stay few — the paper's intent is at most the hundreds, rarely changed — while qualifiers are plentiful, so a message id is a qualifier. Versions of one cell are newest timestamp first. Fifty messages are fifty columns. A version means “this column was updated,” not “a new message arrived.”

规模、替代和行太宽

沿用前面的数量级方法，单独给聊天一个假设，避免和结账的 40 QPS 混成同一笔账。假设峰值 2,000 条消息每秒，每条 400 字节，访问键是 conversation_id 加时间。逻辑写入约 0.8 MB/s。若每条消息都先写一个二级索引项再随机读正文，2,000 次索引查找加 2,000 次回表会把本来一次顺序扫描能完成的“最近 50 条”拆开。宽表让这 50 条落在一个行键的连续列上，一次扫描返回。单行原子足够覆盖“追加一条消息”。它覆盖不了“扣库存并且插入订单”，因为那是两行以上。

较小规模时，行存里的复合主键 (conversation_id, sent_at) 就是同一种访问形状，一个主库往往够用。宽表是这个形状在行范围上的扩展，不是一种更高级的 join。行不能无限长。设计规则是按时间把行键分桶，例如 conv#42#2026-09，让“最近 50 条”多半落在最新的桶里，更早的历史是下一个桶的短范围。论文强调的高效情况正是短范围。[1] 行键本身在论文里上限约 64 KB，常见是 10 到 100 字节；不要把整段消息正文编码进行键。

节点内部是内存表加不可变有序文件，后台再合并。Bigtable 写明：读要查看组成 tablet 的各个 SSTable；Bloom filter 询问某个 SSTable 是否可能包含指定的行/列，于是多数不存在的行或列不必碰盘。[1] “可能有”仍要打开文件，因为会误报；“没有”才跳过。这是读放大。合并则是 LSM 的税：热路径追加快，同一键会在后台被重写。[5] 对全表某一个金额列求和，不是这种短范围扫描。

Scale, the alternative, and a row that grows without bound

Reuse the estimating method, but keep chat on its own assumption so it does not share the checkout's 40 QPS ledger. Assume a peak of 2,000 messages a second, 400 bytes each, keyed by conversation_id plus time. Logical ingest is about 0.8 MB/s. If every message first writes a secondary-index entry and then randomly fetches the body, 2,000 index lookups plus 2,000 body fetches split a “last 50” that one sequential scan could have returned. The wide row keeps those 50 cells on contiguous columns of one row key. Single-row atomicity covers “append one message.” It does not cover “decrement stock and insert an order,” because that is more than one row.

At smaller scale a row store with composite primary key (conversation_id, sent_at) is the same access shape, and one primary is often enough. A wide map is that shape scaled across row ranges, not a smarter join. A row must not grow without a bound. The design rule is to bucket the row key by time, for example conv#42#2026-09, so the latest 50 messages usually hit the newest bucket and older history is the next short range. The case the paper calls efficient is the short range.[1] The paper's row-key limit is about 64 KB, and 10 to 100 bytes is the common size. Do not encode the message body into the row key.

Inside the node, an in-memory table plus immutable sorted files is merged in the background. Bigtable says a read consults the SSTables that make up the tablet, and a Bloom filter asks whether an SSTable might contain a given row/column pair, so most lookups of absent rows or columns skip disk.[1] “Might” still opens the file, because it can be a false positive. “No” is what skips it. That is read amplification. The merge is the LSM tax: the hot path appends quickly, and the same key is rewritten later.[5] A full-table sum of one amount column is not this short-range scan.

对象：不可变的体，元数据另存，响应是 idObject: immutable body, metadata elsewhere, the reply is an id

正常路径和两个崩溃窗口

上传服务先在元数据行存里插入一行 pending：调用方、预期校验和、新的 blob_id。然后把字节 PUT 到对象存储，键就是这个 id，体一旦写完就不再原地修改；要换内容就写新 id。PUT 成功后，元数据行更新为 committed，响应里只带 blob_id。之后的下载按 id 直接取对象，应用不再中转整份大文件。元数据行上有主人和校验和，权限和“这个 id 是否正式可见”由行存的一次更新决定。

窗口要按顺序说。若字节已经写入、标记 committed 的更新没完成，重试会看到 pending 行并继续标记，不会再占一个新 id。若进程在 PUT 之前崩溃，留下的 pending 行没有体，读者不会拿到成功的 id；清扫任务按超时删掉这行。若先 PUT 再插入元数据，崩溃会发生“有体无主”的孤儿对象，清扫要靠上传会话而不是靠目录遍历去猜。把顺序说成“同时写入两个存储”是错的，因为它们没有同一个提交。

The normal path and two crash windows

The upload app inserts a pending metadata row first: caller, expected checksum, and a new blob_id. It then PUTs the bytes to the object store under that id. Once written, the body is not edited in place; a new body is a new id. After the PUT succeeds, the metadata row becomes committed and the response carries only the blob_id. Later downloads fetch the object by id. The app does not proxy the whole large file. Owner and checksum live on the metadata row, so visibility of the id is one row-store update.

Say the windows in order. If the bytes are stored and the committed mark is not, a retry sees the pending row and finishes the mark instead of allocating another id. If the process dies before the PUT, the pending row has no body and readers never receive a successful id; a sweeper deletes that row after a timeout. If you PUT first and insert metadata second, a crash leaves an orphan body with no owner, and garbage collection needs the upload session rather than a guess from a directory listing. “Write both stores at the same time” is the wrong sentence, because they do not share a commit.

为什么小行结账不该在这里

结账峰值 320 次、每次 1.5 KB，逻辑带宽约 480 KB/s。字节速率从来不是瓶颈。对象路径的费用在每次请求的往返、元数据操作，以及“改状态就要新 PUT 一份”的版本膨胀。订单状态从已留货变成已支付，是同一行的原地更新，还要和库存条件放在一个事务里。对象体没有这个事务，元数据行若只保存 id，也表达不了 sku 库存。所以终图上那条红线不是审美，是在说：不可变大对象走 id，可变小行留在行存。

视频、备份包和原图走这条路径：写一次，按 id 读，目录和权限留在元数据行。几十 KB 且总是和元数据一起读时，放进行存大字段可以少一次往返。到了兆字节或要续传，大字段会把页和复制的放大带进备份。没有元数据行就没有原子的可见或隐藏。把每次状态变更存成新对象再扫前缀，是把点更新做成了列举。

Why the small checkout row does not belong

Checkout peaks at 320 transactions of 1.5 KB, about 480 KB/s logical. The byte rate is not the bottleneck. The object path pays a round trip and a metadata operation per request, and a status change becomes a fresh PUT. Moving an order from reserved to paid is an in-place update of one row, in one transaction with the stock predicate. The blob body has no such transaction. A metadata row that only stores an id cannot express sku stock either. The red line on the final frame says: immutable large objects travel as ids; small mutable rows stay in the row store.

Video, backup bundles, and original uploads fit: write once, read by id, keep catalog and permissions on the metadata row. Tens of kilobytes always read with their metadata can live in a large field and save a hop. At megabytes, or when uploads resume, that field drags page and replication amplification into backups. Without a metadata row there is no atomic visible or hidden state. Storing every status change as a new object and scanning a prefix turns a point update into a listing.

倒排：先写权威库，查询再回源补全Inverted index: source store first, then hydrate

写、延迟、再查询

Writer 先把正文、所有者和版本提交进源行存，响应 doc_id，这次提交不写倒排。出站事件要和提交绑在同一条 outbox 里再转发，避免库里有文档、队列里却没有事件。消费者按 id 取已提交正文，切词，追加 posting。假设 1.5 KB 文本切出 80 个词，每条 posting 20 字节，帖子就是 1,600 字节，已和源行同级，词典和副本还没算。所以建索引放在提交之外。“已保存”到“搜得到”的间隔就是 lag。5 秒是假设的新鲜度，不是测量值。

查询从词到 posting，得到 doc_id，再读源库的当前字段才返回。源库若说已删除或版本已变，就丢掉命中，不用倒排里残留的旧标题。高亮用的字段拷贝仍是派生的，重建必须从源库重放。队列堆积时保存继续成功，用积压时长告警新鲜度。源库不可用则保存失败；已有的倒排不能升格成唯一账本。

Write, lag, then query

The writer commits body, owner, and version in the source row store and returns doc_id. That commit does not write the inverted index. The outbox row shares the commit and is forwarded later, so the store cannot hold a document whose event never existed. The consumer loads the committed body, tokenizes, and appends postings. Assume 1.5 KB yields 80 tokens at 20 bytes each: 1,600 bytes of postings, already the size of the source row, before the dictionary and replicas. Indexing stays off the commit. The gap from “saved” to “findable” is the lag. Five seconds is an assumed freshness, not a measurement.

A query walks terms to postings, gets doc ids, and replies only after reading current fields from the source. If the source says deleted or the version moved, drop the hit instead of serving a stale title from the index. A highlight copy is still derived, and a rebuild replays the source. When the queue backs up, save still succeeds and backlog age is the freshness alert. When the source is down, save fails. An existing index must not be promoted to the only ledger.

替代和把索引当账本

若搜索必须和保存同成败，可以把倒排更新放进同一个事务或同一条同步调用。提交延迟会加上切词和 posting 写入，320 次结账里只要有一次搜索索引抖动，下单就抖动。当前把搜索可见放在 5 秒，所以异步是匹配 SLO 的选择，不是习惯。另一个替代是只在内存里建索引、重启再从源库全量重建。那适合小语料和可以接受冷启动的场景；订单这种要跨重启仍能按词找回的数据，倒排应该落盘，但落盘的仍是派生副本。

常见错法是“搜索库就是数据库”。用户更新了收货地址，若只改倒排、源库没有这次更新，重建索引或另一台消费者会把旧地址写回去。删除也一样：倒排删了、源库还在，下一次修复任务会把文档加回来。索引放大被忽略时，人们会把 1,600 字节的 posting 算成“和行一样便宜”，从而把建索引留在用户请求的提交里。结账主路径的两个二级索引已经是同库里的放大；倒排是另一套放大，而且词的数量随正文变，不随列数固定。

Alternatives, and treating the index as the ledger

If search must succeed or fail with the save, fold the inverted-index update into the same transaction or the same synchronous call. Commit latency then includes tokenization and posting writes, and one search-index hiccup stalls checkout at 320 QPS. The visibility assumption here is five seconds, so async matches the SLO. It is not a habit. Another alternative builds the index only in memory and rebuilds from the source on restart. That fits a small corpus that can tolerate a cold start. Orders that must remain findable across restarts should persist the index, and the persisted index is still a derived copy.

“The search store is the database” fails the update. If a shipping address changes only in the index, a rebuild or another consumer writes the old address back from the source. Deletes fail the same way: remove the posting and leave the source, and the next repair puts the document back. Ignoring amplification treats 1,600 bytes of postings as “as cheap as the row” and leaves indexing inside the user-facing commit. Checkout already pays two secondary indexes inside one store. The inverted index is a second amplification, and the token count follows the text, not a fixed column list.

三条走错的路径Three paths that use the wrong engine

每条错路径怎么迁回来

KV 二级索引当 join 用时，user_id 到 order_id 的映射和订单体是两次 quorum 写。崩溃窗口里客户端重试可能再扣一次库存，列表也可能指向不存在的 order_id。迁回的做法是以行存事务为新权威：停写双键，按 order_id 扫出仍能读到的值，在行存里重新插入订单和库存的对账结果，对不上的键进人工或补偿队列。读路径先切到行存，旧的 KV 索引只读一段时间用于比对，而不是继续当列表的来源。

倒排若是唯一副本，就没有可重放的正文。补救是把已存字段导出成源库行，并承认没有 posting 的文档已经丢了。之后更新先写源库，索引用队列重建。对象里的小行按 id 读出写入行存，然后停止把状态变更做成新 PUT。本来就该不可变的大附件留在对象存储，元数据改指向 blob_id。三条迁移都是先定一个提交边界，再停掉旧路径的写。

How each wrong path migrates back

When a KV secondary index stands in for a join, the user_id to order_id map and the order body are two quorum writes. In the crash window a retry can decrement stock again, and the list can point at an order_id that is not there. The move back makes the row-store transaction the new authority: stop the double put, scan whatever order_id values are still readable, reinsert reconciled orders and stock, and send keys that do not match to a repair queue. Reads switch to the row store first. The old KV index stays readable for a comparison pass. It does not stay the list.

If the inverted index is the only copy, there is no body to replay. Export the stored fields into source rows, and admit that documents with no posting are gone. Later updates hit the source first and the index rebuilds from the queue. Small object rows are read by id into the row store, and status changes stop becoming new PUTs. Attachments that were already immutable blobs stay put; metadata now points at blob_id. Each migration fixes one commit boundary, then stops writes on the old path.

和“一种库打全部访问”对着说

Stonebraker 与 Çetintemel 在 2005 年写过：一种传统的数据库引擎布局已经不再适合每一种负载，数仓和其他当时的新负载需要不同的组织方式。[6] 面试里这句话的可用形式是：访问路径决定引擎。它不是“关系库过时了”。结账这条 320 QPS、要跨行提交的负载仍然用行存；聊天的行键范围用有序宽表；大文件用对象体加元数据行；词检索用派生倒排。把这四条压进一个引擎，省下的是一张架构图，付掉的是某一条路径上的提交、扫描或重建。

CAP 海报是另一条走错的路：看见 AP 就把库存放进故障时会改道的 quorum。分区取舍在前一章。复制延迟、sloppy 窗口和搜索延迟是三条时间缝。若目标改成外部一致——T1 提交后才开始的 T2，提交时间戳必须更大——Spanner 用 TrueTime 把时钟不确定度暴露成区间。协调者选出时间戳后，要等到它确定已经过去，提交才可见；区间越宽，等待越长。论文里的部署一般小于 10 ms，多数时候大约 4 ms。[3] 买到的是外部一致。Bigtable 没有跨行事务，一行原子结不了账。[1][3]

Against one store for every access pattern

In 2005 Stonebraker and Çetintemel argued that one traditional database engine layout had stopped being a fit for every workload, and that warehouses and other then-new workloads needed different organizations.[6] The interview form of that sentence is: the access path picks the engine. It is not “relational stores are obsolete.” Checkout at 320 QPS with a cross-row commit stays on a row store. A chat row-key range uses an ordered wide map. Large files use a blob body plus a metadata row. Term lookup uses a derived inverted index. Collapsing the four into one engine saves a box on the diagram and spends the commit, the scan, or the rebuild on one of those paths.

A CAP poster is another wrong turn: an AP label puts stock into a quorum that reroutes during failure. The partition trade-off is the previous chapter. Replication lag, the sloppy window, and search lag are three separate gaps. If the goal becomes external consistency — T2 starts only after T1 commits, so T2's commit timestamp is greater — Spanner exposes clock uncertainty through TrueTime as an interval. After choosing a commit timestamp, the coordinator waits until that timestamp is definitely past before the commit is visible. A wider interval lengthens the wait. The paper's deployment is generally under 10 ms, and about 4 ms most of the time.[3] The wait buys external consistency. Bigtable has no cross-row transactions, so single-row atomicity does not check out an order.[1][3]

列条带：很多行里只读少数几列Column stripes: a few fields across many rows

用同一笔订单量估算扫描量

一年 1,261,440,000 笔订单，每笔 1,500 字节，按行读完约 1.89 TB。amount 若单独占 8 字节，这一列是 1,261,440,000 × 8 = 10,091,520,000 字节，约 10.1 GB，大约是整行的 1/187。再加上 1 字节的 status，约 11.4 GB。同一列排在一起还更好压缩，这里没把压缩比算进去。Dremel 就是这种只读嵌套数据上的交互分析：多级执行树加列式布局，可以只取一个嵌套字段的连续值。重复级和定义级用来在不读全字段时还原结构。[4] 论文里的万亿行、数秒级聚合是他们的规模，不是这 12.6 亿行的 SLO。这句 SUM 已经不是结账那次 1.5 KB 的点写。

宽表扫描回答的是“这个行键附近的列”。列条带回答的是“所有行上的这一列”。把 Bigtable 叫成数仓，是把 tablet 上的行范围说成了列条带。Bigtable 可以高效读短的行范围；对全部订单求一个字段的和，短范围这个前提不成立。[1][4] Dremel 是只读分析，可以就地读已有的文件或表，它不替代结账的提交。写仍进行存；分析可以读行存导出的列文件，也可以读复制出来的快照。导出有延迟，报表允许这个延迟，确认页不允许。

Estimate the scan with the same order volume

A year is 1,261,440,000 orders. At 1,500 bytes each, full rows are about 1.89 TB. An 8-byte amount column is 1,261,440,000 × 8 = 10,091,520,000 bytes, about 10.1 GB, roughly 1/187 of the full row. Adding a 1-byte status makes about 11.4 GB. Values of one field also compress more cheaply; that ratio is not in the arithmetic. Dremel is interactive analysis of read-only nested data: a multi-level tree plus a columnar layout, so a query reads contiguous values of one nested field. Repetition and definition levels rebuild structure without every field.[4] Trillion-row aggregations in seconds are the paper's scale, not an SLO for these 1.26 billion rows. This SUM is not the checkout's 1.5 KB point write.

A wide-row scan answers “columns near this row key.” A column stripe answers “this field on all rows.” Calling Bigtable a warehouse treats a tablet's row range as a column stripe. Bigtable reads short row ranges efficiently. A sum of one field over every order does not have that short-range premise.[1][4] Dremel is read-only analysis. It can read data in place from existing files or tables. It does not replace the checkout commit. Writes still enter the row store. Analysis reads an exported columnar file or a snapshot. Export lag is acceptable for a report and unacceptable for the confirmation page.

替代和常见混名

数据量还在单机能扫完的时候，行存上的这句 SUM 可以是第一版，尤其是一年只有测试用的几百万行时。1.89 TB 的整行扫描已经值得把分析读和结账写分开。分开的代价是导出作业、列文件的小文件合并，以及报表与在线表之间的延迟。若查询总是带月份，再按月切文件，一次 SUM 只打开当年的那些条带。这是文件级剪枝，叠在列级剪枝上面，不是又一种数据库产品。

把“列”当成一个词会选错。宽表的列是一行里的限定符，局部性在行键。分析列存的列是很多行上同一字段的连续存放，局部性在字段。对象没有列，向量近邻也不是列扫描。为了这句 SUM 把结账改成列存，会让列条带的重写落在每一次下单上。页式行存承担结账的原地更新，LSM 的内存组件加磁盘合并承担高插入追加，列条带承担只读聚合。[5][4]

Alternative, and the word that gets mixed

While one machine can still scan the data, the SUM on the row store can be version one, especially if a year is only a few million test rows. A 1.89 TB full-row scan is already a reason to separate analytic reads from checkout writes. The cost is the export job, merging small columnar files, and lag between the report and the online table. If the query always names a month, partition the files by month and the SUM opens only that year's stripes. That is file pruning stacked on column pruning, not another database product.

Using “column” for both layouts picks the wrong engine. A wide-row column is a qualifier inside one row; locality is the row key. An analytic column is one field laid out across many rows; locality is the field. An object has no column, and a vector probe is not a column scan. Moving checkout onto a columnar engine so this SUM is local would put stripe rewrites on every order. A page-oriented row store takes in-place checkout updates, an LSM's memory component and disk merges take high-rate appends, and column stripes take read-only aggregation.[5][4]

追问与错误答案Follow-ups and wrong answers

主库什么时候不够

320 次跨行事务还放得下时，不要为了分片而切开 order_id。先看热点 sku 的行锁，再看复制延迟有没有破 SLO。真要拆，一笔结账的订单和明细必须落在同一分片；按 sku 分库存时，热门 sku 仍是一行。跨分片会把本地事务换成两阶段提交。只有写速率或数据量超过单主目标才付这笔代价。跨地域外部一致还要加上时钟不确定度上的等待。[3]

When one primary is not enough

While 320 cross-row transactions still fit, do not split order_id just to have shards. Check the hot sku's row lock, then whether replication lag breaks the SLO. If you split, one checkout's order and lines stay on one shard. Stock partitioned by sku still leaves a popular sku as one row. A cross-shard commit replaces the local transaction with two-phase commit. Pay that only when write rate or volume exceeds the single-primary target. Cross-region external consistency adds the clock-uncertainty wait.[3]

聊天为什么有时仍是行存

峰值每秒两千条、按会话加时间读取时，复合主键的行存和宽表是同一种键。选宽表的理由是行范围已经跨过多台机器，而且你需要单行里大量稀疏列的原子追加。若全部历史放得进一个主库，行存更省一套运维。不要因为消息“看起来像 NoSQL”就离开行存。也不要把这个范围扫描升级成每条消息一个对象：五十条历史会变成五十次 GET。

Why chat sometimes stays on a row store

At two thousand messages a second, read by conversation plus time, a composite primary key in a row store and a wide map are the same key. The wide map wins when the row range already spans many machines and you need an atomic append of many sparse columns in one row. If the history fits one primary, the row store saves a second operational surface. Do not leave the row store because messages “look like NoSQL.” Do not upgrade the range scan into one object per message either: fifty history items become fifty GETs.

倒排里能不能存正文

可以存一份用于展示的字段，但写路径仍先提交源库，查询仍要能用源库的版本否决过期命中。只把正文放在倒排里，重建、部分更新和删除都会失去权威。索引放大按词数算：80 个词乘 20 字节已经约 1.6 KB，和 1.5 KB 的源行同级。这个倍数是异步的理由之一。

May the inverted index store the body

It may store a field copy for display. The write path still commits the source first, and the query must still be able to reject a stale hit using the source version. A body that lives only in the index loses its authority on rebuild, partial update, and delete. Amplification follows the token count: 80 tokens times 20 bytes is already about 1.6 KB, the same magnitude as the 1.5 KB source row. That factor is one reason the index is async.

Three sentences to close

Checkout is one commit on a primary row store, the secondary index is in that commit, the confirmation read returns to the primary, and list reads may sit on a replica inside the replication-lag window. A single-key session is the quorum case, and you have to say that sloppy quorum and hinted handoff break the intersection until the hint is delivered. Chat and metrics are a row key plus a column or time range. A sum of one field over many rows is a column stripe. A large object returns an id. A small row that changes often does not go into the object store. The inverted index is derived, and queries hydrate from the source. One store, one CAP letter, or “NoSQL is faster” has not answered the access key.
