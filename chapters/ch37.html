先定一条负载，再开口引擎Fix one workload before naming an engine

中文

我先不报产品名。结账要在一次提交里写入订单、明细，并按 sku 扣库存；确认页要读到自己的写；列表按 user_id 查。平均 40 笔成功事务每秒，8 倍峰值 320。逻辑行 1.5 KB。这条路径的权威是主行存，二级索引跟同一次提交走。副本可以接允许旧一点的列表读，窗口是复制延迟。对象存储、把倒排当唯一副本、用 KV 的二级索引假装 join，都接不住这组约束。

七组图依次回答：结账事务、单键 quorum、宽表范围、对象直传、派生倒排、B+Tree / LSM 引擎、分析列扫描。每组从访问键画起，终图交代回程和失败行为。块设备、共享文件和向量近邻的内部结构不展开，云服务名单也不背。

English

I do not open with a product name. Checkout must insert the order and its lines and decrement stock by sku in one commit. The confirmation page must read its own write. The list is by user_id. The assumption is 40 successful transactions per second, 320 at an 8× peak, and a 1.5 KB logical row. Authority sits in a primary row store; the secondary index commits with that transaction. A replica may serve list reads that tolerate staleness, and the window is replication lag. An object store, an inverted index as the only copy, and a KV secondary index pretending to be a join all miss this constraint set.

The seven decks cover checkout transactions, one-key quorum, wide-row ranges, direct object upload, a derived inverted index, B+Tree/LSM engines, and analytic column scans. Each starts with the access key and ends with replies and failure behavior. Block/file internals, ANN internals and cloud product lists stay outside the scope.

把假设算成设计

A1 的 40×86,400=3,456,000 笔/天，再×365=1,261,440,000 笔/年。只算 A2 的订单快照行，×1,500 B=1,892,160,000,000 B，约 1.892 TB；两个 40 B 索引项再加 0.101 TB，一份约 1.993 TB。A5 的三份活副本加一份紧凑备份是 1.993×4≈7.97 TB；若活副本按 1.5 倍计旧版本，则 1.993×3×1.5+1.993≈10.96 TB。这是订单快照与所列索引的 8–11 TB 规划区间，明细、库存、幂等表、WAL 留存、空闲空间和备份历史另计。TB 用十进制，不和 TiB 混算。

峰值 320×1,500 B=480,000 B/s，约 0.48 MB/s，是新增快照的逻辑负载。A6 简化为一次快照插入弄脏主结构和两个索引各一页，8 KiB=8,192 B，则页写模型是 320×3×8,192=7,864,320 B/s，约 7.86 MB/s；相除为 16.384 倍。它不是完整事务的盘写上界：还漏 WAL、库存、明细、页分裂和整页日志；多次更新合并到同页又会降低回刷量。这个数量级支持先评估单主，不能代替压测，也不能推出“单库肯定够”。

读侧 A3 是 20×40=800 QPS 平均，×8=6,400 QPS 峰值。确认页回当前主库并开一个足够新的读视图；带提交位置等副本应用也是替代，但超时后要回主库或明确失败。允许旧一秒的列表才分给异步副本。主库加两份副本与容量账一致，实际读分配要按索引命中、工作集、查询代价和故障幸存预算压测。没有单台可用 QPS，就不能用 6,400 证明需要缓存或证明不需要缓存。

热点按 A7 单列：某 sku 占 30%，则 320×0.30=96 次更新/秒。若持锁时间平均 10 ms，串行占用约 96×0.010=0.96，已经几乎没有排队余量。10 ms 也是假设；先测锁等待和事务长度，再谈预占队列或拆库存份额。加读副本和把行搬到对象存储都不会分散这把写锁。

A4 的 99.9%、服务端 p99<300 ms、列表一秒和搜索五秒都是工作目标。演示图采用本地 WAL 持久确认、异步复制，特意保留灾难性主库损坏的 RPO 窗口；不是财务订单的默认保证。若已确认订单必须幸存单机故障，就买同步副本的持久确认和安全提升，不能用“列表允许旧”替代这条耐久性要求。[8]

Turn the assumptions into a design

A1 gives 40×86,400=3,456,000 orders/day and ×365=1,261,440,000/year. Count only the A2 order snapshot: ×1,500 B=1,892,160,000,000 B, about 1.892 TB. Two 40 B index entries add 0.101 TB, giving 1.993 TB/copy. A5 has three live copies and one compact backup: 1.993×4≈7.97 TB. With 1.5× old versions on live copies, 1.993×3×1.5+1.993≈10.96 TB. This 8–11 TB band covers only snapshots and the specified indexes; lines, stock, idempotency, retained WAL, free space and backup history are extra. TB is decimal, distinct from TiB.

The peak is 320×1,500 B=480,000 B/s, or 0.48 MB/s of new snapshot payload. A6 assumes one snapshot insert dirties one primary-structure page and two index pages. With 8 KiB=8,192 B, the model gives 320×3×8,192=7,864,320 B/s, about 7.86 MB/s, or 16.384× the payload. This is not a whole-transaction disk-write upper bound: WAL, stock, lines, page splits and full-page logging are omitted; coalesced page updates can reduce flush bytes. The scale supports evaluating a primary first, but cannot replace a benchmark or prove capacity.

A3 gives 20×40=800 average read QPS and ×8=6,400 peak. Confirmation reads use the current Primary with a sufficiently new read view. A commit-position barrier on a replica is an alternative, with timeout fallback or explicit failure. Only stale-allowed lists go to async replicas. One primary plus two replicas matches the capacity estimate; query cost, working set, index hits and failure-survivor load need benchmarking. Without usable per-node QPS, 6,400 proves neither that a cache is required nor that it is unnecessary.

A7 isolates skew: one sku at 30% receives 320×0.30=96 updates/s. An assumed mean lock hold of 10 ms gives serial occupancy 96×0.010=0.96, leaving little queueing headroom. Measure lock wait and transaction length before reservation queues or split stock allocations. Read replicas and object storage do not distribute this write lock.

A4 sets working goals: 99.9%, server p99<300 ms, one-second lists and five-second search freshness. The demonstration acknowledges local durable WAL with async replication and deliberately retains a catastrophic-primary-loss RPO window; this is not a default financial-order guarantee. If acknowledged orders must survive a host loss, require durable synchronous replicas and safe promotion. Stale-allowed lists cannot substitute for durability.[8]

行存：一次提交，再谈副本延迟Row store: one commit, then replication lag

沿这条路径走一遍

客户端带 Idempotency-Key 调用 POST /v1/orders，订单服务在主库事务里对 (caller,key) 建唯一约束，同时存参数摘要和结果 order_id。并发相同键只有一个事务能提交；另一方读已提交结果，同键不同参数则拒绝。再插入 Order、OrderLine，并执行库存条件更新：UPDATE inventory SET on_hand=on_hand-qty WHERE sku=? AND on_hand>=qty。任何 sku 影响行数为零就整笔回滚，多 sku 用固定顺序拿锁并对死锁做有界重试。唯一幂等结果与扣库存同事务，不能靠事务前一次“查不到”防重。

最小记录是 Order(order_id,user_id,status,version,created_at)、OrderLine(order_id,line_no,sku,qty)、Inventory(sku,on_hand) 和 Idempotency(caller,key,digest,order_id)。列表索引是 (user_id,created_at,order_id)，由引擎和行一起提交；在同一读视图里不会像应用双写那样只有索引没有对应行。确认读按 order_id 查当前主库。旧快照事务即使在主库上，也可能看不到新提交；read-your-writes 要同时检查路由和快照。

Walk the path in order

The client calls POST /v1/orders with an Idempotency-Key. In the primary transaction, a unique (caller,key) constraint stores a parameter digest and resulting order_id. Only one concurrent same-key transaction commits; another reads the committed result, while changed parameters are rejected. Insert Order and OrderLine and conditionally decrement inventory: UPDATE inventory SET on_hand=on_hand-qty WHERE sku=? AND on_hand>=qty. Any zero-row update rolls back the whole order. Lock multiple skus in a fixed order and retry deadlocks within a bound. The unique result and decrement share the transaction; a pre-transaction not-found check cannot prevent duplicates.

The minimal records are Order(order_id,user_id,status,version,created_at), OrderLine(order_id,line_no,sku,qty), Inventory(sku,on_hand), and Idempotency(caller,key,digest,order_id). A list index on (user_id,created_at,order_id) commits with the row and is coherent in one read view, unlike application dual writes. Confirmation reads order_id on the current primary. Even a primary read can miss a new commit in an old snapshot; read-your-writes needs both routing and snapshot rules.

为什么是行存，而峰值只有 320

行存的决定来自订单、库存和幂等结果要同时成功，不来自“320 次很小”。先以一个主库加两份异步副本作为待验证候选，测真实事务 p99、锁等待、WAL 刷盘和故障后的读容量。二级索引是付出的维护税，7.86 MB/s 只描述 A6 的三页模型。若索引不参与查询，删掉它比换存储引擎更直接；若工作集放不下，容量和尾延迟会先迫使分区，而不仅是每秒字节数。

模型、布局和引擎是三条轴：关系模型不等于 B+Tree，KV 也不等于 AP 或 LSM。这里选择行式事务库，再用页式索引组织点查；后面把 B+Tree 的改页与 WAL、LSM 的追加与合并分别画出来。O’Neil 等人 1996 年用内存组件加磁盘归并改善高插入索引，但点查成本可能更高。[5] 选择的是访问约束，不是产品名字暗含的速度。

Why a row store, at a peak of only 320

Choose a row store because order, stock and idempotency must succeed together, not because “320 is small.” Evaluate one primary plus two async replicas with real transaction p99, lock wait, WAL flush and survivor read capacity. Secondary indexes impose maintenance cost; 7.86 MB/s describes only A6’s three-page model. Remove unused indexes before changing engines. An oversized working set can force partitioning through capacity and tail latency, not just bytes per second.

Model, layout and engine are separate axes: relational does not imply B+Tree, and KV does not imply AP or LSM. Here a row-oriented transactional store uses page indexes for point access. A later deck separates B+Tree page updates/WAL from LSM append/merge. O’Neil et al. use memory components and disk merges for high insertion rates, with potentially more expensive point finds.[5] Choose access constraints, not speed inferred from a product name.

替代、延迟窗口、常见错法

同步复制还要区分收到了、持久了、应用了。等副本 WAL 落盘能改善已确认写的故障耐久性，不保证该副本马上可读；PostgreSQL 18 的 remote_apply 才等到同步副本回放可见。[8] 当前图按异步教学场景展示列表滞后；若业务要求 RPO=0，要改提交确认和提升规则，副本不可达时可能阻塞或拒绝写。把库存和订单拆成两个库则引入跨库原子提交或补偿，不能只为了“分工漂亮”付这笔代价。

提交前崩溃，事务恢复为提交或回滚；提交成功而 201 丢失，重试同一幂等键找原结果。副本滞后时，列表可能缺新订单，确认读不能误送过去。主库不可用时暂停扣库存；故障提升还要隔离旧主、选到满足耐久屏障的副本。若原图的异步未送达日志随主盘永久丢失，幂等表也可能一起丢，重试无法凭空恢复结果，要进入业务对账。缓存和幂等键都补不回没有持久副本的事务。

“NoSQL 更快”没回答事务边界；“320 QPS 就够”也没回答锁和尾延迟。条件写、事务、复制协议都要逐项问能力，不能从 SQL / NoSQL 标签推断。跨地域外部一致还需事务排序与时钟等待；Spanner 的 TrueTime 是实现之一，不是选型海报上的另一种字母。[3]

Alternative, lag window, and the usual miss

Synchronous replication distinguishes received, durable and applied. Waiting for replica WAL durability improves acknowledged-write survival but does not prove immediate read visibility. PostgreSQL 18 remote_apply waits for replay visibility on synchronous standbys.[8] This async teaching scenario demonstrates list lag. RPO=0 changes commit and promotion rules, potentially blocking or rejecting writes when replicas are unavailable. Separating stock and orders introduces cross-store atomic commit or compensation; architectural tidiness alone is not a reason to pay that cost.

Before-response crashes recover as committed or rolled back. If commit succeeded but 201 was lost, retry the same idempotency key to find the original result. Lagging lists can omit fresh orders; confirmation must avoid that route. Pause stock writes when Primary is unavailable. Promotion must fence the former primary and select a sufficiently durable replica. In this async model, permanent primary-disk loss can also lose unshipped idempotency records, requiring business reconciliation. Caches and idempotency keys cannot reconstruct an unreplicated transaction.

“NoSQL is faster” ignores the transaction boundary; “320 QPS is enough” ignores lock contention and tail latency. Ask separately about conditional writes, transactions and replication instead of inferring them from SQL/NoSQL labels. Cross-region external consistency adds transaction ordering and clock waits; Spanner’s TrueTime is one implementation, not another product-selection letter.[3]

单键 KV：分区、quorum、以及 sloppy 改了什么Single-key KV: partition, quorum, and what sloppy changes

论文里和这张图对得上的部分

Dynamo 为单键高可用接受故障期间的写入，并用版本与应用协助处理冲突。[2] 图中把协调角色单独抽出，实际可由优先列表里的副本承担；它分别向 N1、N2、N3 发 RPC，不让 N1 转发给 N2 再到 N3。A9 的 (N,R,W)=(3,2,2)，健康写确认集合 {N1,N2}，随后读 {N2,N3} 在 N2 相交。还需要版本比较、冲突处理等协议才能定义读结果；只写 R+W>N 不能证明线性一致。

故障反例必须把集合写全。新一轮写中 N2 对写方不可达，N3 的投递仍滞后；N1 和候补 N4 已持久确认，因此 W={N1,N4}。N2 恢复后、hint 和 N3 写都还没到，另一轮 R={N2,N3} 可以读到两个旧值。两集合交点为空，虽然 2+2>3。N4 保留原目标 N2，恢复后 handoff；hint 是修复机制，不是强读证明。不能只画“写到了 N4”就断言任意 R=2 都读旧，读到 N1 的集合就不是这个反例。

What in the paper matches this drawing

Dynamo accepts single-key writes through failures and relies on versions and application-assisted conflict reconciliation.[2] The diagram separates the coordinator role; in practice a preferred replica may serve it. It sends independently to N1, N2 and N3, never through a replica relay. With A9 (N,R,W)=(3,2,2), healthy write acknowledgments {N1,N2} intersect a later read {N2,N3} at N2. Version comparison and reconciliation still define the result; R+W>N alone does not prove linearizability.

Specify the whole counterexample. In a new write, N2 is unreachable to the writer and N3 delivery is delayed. N1 and fallback N4 durably acknowledge W={N1,N4}. After N2 recovers but before handoff or delayed N3 delivery, R={N2,N3} can return two old values. The sets are disjoint despite 2+2>3. N4 retains N2 as the intended target and eventually hands off. Hints repair placement; they are not strong-read proofs. Merely drawing a write to N4 does not prove every R=2 read stale: a set containing N1 differs from this witness.

什么负载才该走这条路径

适合的访问形状是购物车或可合并偏好的单键 get/put，且业务接受并发版本与合并。A9 若把 6,400 QPS 看成 1 KB 会话点读，只说明键形状匹配，不证明会话安全：撤销、一次性令牌和权限收紧不能随便读旧。LWW 会丢并发增量；购物车也要定义删除和添加如何合并，不能把“可用”直接翻译成覆盖旧值。库存减少、支付确认不能借用这套故障默认值。

较小键空间可以先用单主行存或事务型 KV，把条件更新与读自己的写讲清。固定成员严格 quorum 拒绝向候补改道，会减少可写窗口；把 R 和 W 都设成 N 也会在缺一成员时不可用，但并不自动解决并发排序。跨 order 与 inventory 的不变量仍要多键事务、业务预分配或补偿设计，调大 R/W 不能补出不存在的提交边界。

三句容易错：相交等于线性一致、sloppy 成功等于规范副本已更新、所有 KV 都不支持事务。它们分别混了集合条件、物理成员和产品能力。图只分析 Dynamo 风格单键协议；如果选的是支持事务的 KV，就要另画事务提交和冲突规则，不能沿用这张图却宣布库存已经安全。

Which workload belongs on this path

A suitable shape is single-key get/put for a cart or mergeable preferences when the business accepts concurrent versions and reconciliation. Treating 6,400 QPS as 1 KB session reads in A9 matches the key shape but does not prove session safety: revocation, one-time tokens and tightened permissions cannot casually read stale data. LWW loses concurrent increments; carts need explicit add/delete merge rules. Stock decrements and payment confirmations cannot inherit this failure policy.

For a smaller key space, start with a primary row store or transactional KV and explain conditional updates and read-your-writes. Fixed-member strict quorum avoids fallback membership at a cost to write availability. R=W=N also becomes unavailable when a member is missing, without automatically solving concurrent ordering. An invariant across order and inventory still needs multi-key transactions, business allocation or compensation; larger R/W cannot invent a missing commit boundary.

Three mistakes conflate distinct issues: intersection means linearizability; sloppy success means preferred replicas are updated; all KV stores lack transactions. These confuse set conditions, physical membership and product capability. This diagram analyzes a Dynamo-style one-key protocol. A transactional KV needs its own commit/conflict diagram before claiming safe stock updates.

宽表：行键加上列范围，不是二级索引 joinWide row: a row key plus a column range, not a secondary-index join

为什么聊天和指标都要这个形状

Bigtable 的论文模型是稀疏、多维有序映射：(row,column,timestamp)→bytes，连续行范围组成 tablet；同一行的读写原子，但没有通用跨行事务。[1] 图里的聊天行键为 conversation_id 加日桶，限定符用发送时间加 message_id，防同毫秒碰撞。五十条消息是五十个不同单元格，时间戳版本留给一条消息被编辑；不是把五十条消息塞进一个单元格的五十个版本。指标也可按 series_id 加时间范围组织，但不因此就有专用时序引擎的保留和降采样策略。

论文的点击记录把站点与会话创建时间放进行名，利用同站点会话相邻的局部性。[1] 这说明先设计键，再买分布式模型。列族定义宜少而稳定，限定符随消息增长；长期历史要分桶。单行原子只保证本行内的一次操作，不保证把多次翻页或多个桶看成一份全局快照。读历史的分页游标应固定查询边界并包含最后一条的时间与 id。

Why chat and metrics want this shape

Bigtable's model is a sparse, distributed, persistent multidimensional sorted map. The index is a row key, a column key, and a timestamp; the value is an uninterpreted string of bytes. Row keys are lexicographic. A tablet is one row range and the unit of distribution. Reads of short row ranges typically touch a small number of machines. Every read or write under a single row key is atomic, however many columns it touches. The system does not provide a full relational model.[1] Chat puts conversation_id in the row key and each message in a qualifier of family msg, with qualifiers ordered by time. “Last 50” is a qualifier scan inside that row. Metrics put series_id in the row key and the time bucket in a qualifier or a row-key suffix. The read is still a short contiguous key range.

Bigtable’s paper model is a sparse multidimensional sorted map: (row,column,timestamp)→bytes. Contiguous row ranges form tablets. Reads/writes within one row are atomic, without general cross-row transactions.[1] The chat row key uses conversation_id plus a day bucket; qualifiers combine send time and message_id to prevent same-millisecond collisions. Fifty messages occupy fifty distinct cells; timestamp versions represent edits to one message. Metrics can use series_id plus time ranges, without thereby gaining a dedicated TSDB’s retention/downsampling policies.

The paper places website and session creation time in click-record row names to cluster related sessions.[1] Design the key before buying the distributed model. Column families should be few and stable; qualifiers grow with messages and long histories need buckets. Single-row atomicity does not make multiple pages or buckets one global snapshot. A history cursor should fix the query boundary and include the last item’s time and id.

聊天单独用 A8：2,000 条/s×400 B=0.8 MB/s。一次最新五十条是 20 KB 正文，加协议和索引另算；不是先查五十个 id 再做五十次远端 GET。规模小时，行存复合索引 (conversation_id,sent_at,message_id) 也能完成这条范围路径。要不要宽表由数据分布、工作集、写入和运维要求决定，不由“聊天像 NoSQL”决定。

日桶限制一行的历史体积，不分散最新桶的热点；同一个超大群仍可能集中在一个 tablet。可加分片盐分散写，代价是查最新五十条时并行读多个盐桶并按时间归并。只用全局时间作行键又会把所有新写推到最末端范围。保留期限和物理清理也要分开：过期单元格不能再返回，不代表旧 SSTable 已立即回收。

Tablet 内部仍要查 memtable 和多个 SSTable，并按版本合并；Bloom 的否定可跳过不含目标行/列的文件，肯定只说明“可能有”。[1] 这是点查优化，不能把范围内每个键都用一次 Bloom 变成“整段范围不存在”的证明。后台合并付额外读写并处理墓碑；这一层机制留到引擎图。宽表的局部性在行键，跨全部订单扫金额则要另一种布局。

Chat has its own A8: 2,000 messages/s×400 B=0.8 MB/s. Fifty recent messages carry 20 KB before protocol/index overhead, rather than fifty remote body GETs after id lookups. At smaller scale a relational composite index (conversation_id,sent_at,message_id) supports the same range path. Distribution, working set, ingestion and operations decide on a wide-row model, not the label “chat looks like NoSQL.”

Day buckets bound historical row size but do not spread the latest bucket’s hot writes; one huge group may still concentrate on one tablet. Salted buckets distribute writes at the cost of parallel reads and time merge for the latest fifty items. A global-time-only key concentrates all fresh writes in the newest range. Retention visibility differs from physical cleanup: expired cells must stop returning before obsolete SSTables are necessarily reclaimed.

Inside a tablet, reads reconcile memtable and SSTables by version. A negative Bloom result can skip a file lacking the target row/column; a positive means only “possibly present.”[1] This point-lookup optimization is not a proof that a whole range is absent. Compaction adds reads/writes and handles tombstones, covered in the engine deck. Wide-row locality is by row key; scanning amount across all orders needs another layout.

Inside the node, an in-memory table plus immutable sorted files is merged in the background. Bigtable says a read consults the SSTables that make up the tablet, and a Bloom filter asks whether an SSTable might contain a given row/column pair, so most lookups of absent rows or columns skip disk.[1] “Might” still opens the file, because it can be a false positive. “No” is what skips it. That is read amplification. The merge is the LSM tax: the hot path appends quickly, and the same key is rewritten later.[5] A full-table sum of one amount column is not this short-range scan.

对象：不可变的体，元数据另存，响应是 idObject: immutable body, metadata elsewhere, the reply is an id

正常路径和两个崩溃窗口

上传控制先在 Metadata 持久建 PENDING 会话：(caller,key,digest,blob_id,size,checksum,expires_at)。唯一键让重试拿同一会话，同键内容变化拒绝。App 只发绑定这个对象键的短期上传权限，客户端直传 create-only 对象；例如 S3 的 If-None-Match 可以防同键覆盖。[10] finalize 由 App 查准确对象版本、大小和校验和后，CAS 把该会话改为 COMMITTED，再返回 201 和 blob_id。元数据为 COMMITTED 才能签发读权限；对象的原生可变能力没有被当成跨库事务。

PUT 超时不能当失败重占 id：先 HEAD 或查询上传结果，校验匹配才继续提交；不能只看到对象“存在”就信任内容。体已落盘、元数据未提交时仍是 PENDING，恢复可重复核验。清扫先 CAS PENDING→ABORTED，再清理未发布体；finalize 若先赢，清扫无权删 COMMITTED。反之清扫先赢，迟到 finalize 必须拒绝。过期签名可能仍有在途 PUT，所以还要在权限过期并留出有界在途窗口后复查、清理迟到孤儿；两个存储不存在同一个原子提交。

The normal path and two crash windows

Upload control persists a PENDING Metadata session: (caller,key,digest,blob_id,size,checksum,expires_at). A unique key returns the same session on retry; changed content is rejected. Upload App issues short-lived authority bound to that object key, and the client directly performs a create-only upload; S3 If-None-Match can prevent same-key overwrites.[10] On finalize, App verifies the exact object version, size and checksum, then CAS-publishes COMMITTED and returns 201 with blob_id. Read authority requires COMMITTED metadata. Object-store mutation capabilities are not treated as a cross-store transaction.

A PUT timeout does not justify allocating another id: query the upload outcome or HEAD and verify matching content before publication. Existence alone is insufficient. A stored body with uncommitted metadata remains PENDING and can be reverified. Cleanup must CAS PENDING→ABORTED before deleting unpublished bytes. If finalize wins, cleanup cannot delete COMMITTED; if cleanup wins, late finalize is rejected. In-flight uploads may outlive signed authority, requiring later rechecks and orphan cleanup after authority expiry and a bounded in-flight window. The two stores do not share an atomic commit.

为什么小行结账不该在这里

结账的 0.48 MB/s 只是逻辑快照字节。订单状态和库存条件要求一次提交，普通对象 API 不提供这组多行事务。把它改成“每次状态变化生成一个新对象”仍要元数据库决定当前版本，还增加小请求、旧版本和两库恢复成本。对象适合视频、备份和大附件；如果选用支持条件修改的对象 API，也要逐项核查语义，不能把“对象一定不可变”当产品事实。不可变 id 是本章主动采用的约束。

视频、备份包和原图走这条路径：写一次，按 id 读，目录和权限留在元数据行。几十 KB 且总是和元数据一起读时，放进行存大字段可以少一次往返。到了兆字节或要续传，大字段会把页和复制的放大带进备份。没有元数据行就没有原子的可见或隐藏。把每次状态变更存成新对象再扫前缀，是把点更新做成了列举。

Why the small checkout row does not belong

Checkout’s 0.48 MB/s counts only logical snapshot bytes. Order state and stock conditions require a shared commit that ordinary object APIs do not supply. Creating a new object for each state change still needs metadata to choose the current version, adding small requests, old versions and cross-store recovery. Objects suit video, backups and large attachments. Conditional object updates require explicit capability checks; “objects are inherently immutable” is not a product fact. Immutable ids are this chapter’s chosen constraint.

Video, backup bundles, and original uploads fit: write once, read by id, keep catalog and permissions on the metadata row. Tens of kilobytes always read with their metadata can live in a large field and save a hop. At megabytes, or when uploads resume, that field drags page and replication amplification into backups. Without a metadata row there is no atomic visible or hidden state. Storing every status change as a new object and scanning a prefix turns a point update into a listing.

倒排：先写权威库，查询再回源补全Inverted index: source store first, then hydrate

写、延迟、再查询

Writer 同事务提交正文、所有者、版本和 outbox，再返回 saved id。事件携带同事务版本快照或删除标记，Relay 至少一次交给 Indexer；按 doc_id 与源版本幂等应用，删除事件也要带版本并保留恢复所需的墓碑。只有倒排更新已确认，交付游标才前进。A10 假设每文档八十个 posting、每个二十字节，80×20=1,600 B，约 1.6 KB，词典、位置和副本另计。五秒表示工作新鲜度，不是“保存成功”保证。

查询从词拿候选 id 和版本，再在源库读当前正文、ACL、版本和删除状态。过期版本需重验匹配或丢弃，权限收紧先按源拒绝；这能去掉陈旧命中，不能找回尚未建索引的新文档。过滤后不足就说明有界结果，不无限补查。Relay 积压时保存仍可成功，告警看最老待办年龄；索引或源库不可用则查询有界失败。重建从源快照加包含删除的增量回放，并在完整后切换，不能把旧事件倒序写回。

Write, lag, then query

Writer commits body, owner, version and outbox together, then returns saved id. Events carry the same-transaction version snapshot or deletion marker, and Relay delivers them at least once to Indexer, which applies doc_id/source-version updates idempotently. Deletions carry versions and retain recovery tombstones. Delivery advances only after index updates are acknowledged. A10 assumes eighty postings per document at twenty bytes each: 80×20=1,600 B, about 1.6 KB, excluding dictionary, positions and replicas. Five seconds is a freshness goal, not a consequence of saved success.

Search retrieves candidate ids and versions, then reads current body, ACL, version and deletion state from Source store. Revalidate term matches or discard changed versions; current permissions reject revoked access. This removes stale hits but cannot discover fresh unindexed documents. Return bounded insufficient results rather than endlessly refilling. Saved writes may continue during relay backlog; alert on oldest pending age. Index or source failure makes search fail within a bound. Rebuild from a source snapshot plus ordered increments including deletions before switching a complete index.

替代和把索引当账本

要让搜索与保存同成败，最简单的替代是同一事务引擎里的全文索引，代价是切词与索引维护进入提交。对外部搜索服务再同步调用一次仍是两次写：源库提交后索引超时，无法靠同步二字回滚。可以另定义“已保存但待发布”的业务状态或分布式协议，不能伪装成同事务。当前允许五秒新鲜度，用 outbox 异步派生更清楚。[6]

常见错法是“搜索库就是数据库”。用户更新了收货地址，若只改倒排、源库没有这次更新，重建索引或另一台消费者会把旧地址写回去。删除也一样：倒排删了、源库还在，下一次修复任务会把文档加回来。索引放大被忽略时，人们会把 1,600 字节的 posting 算成“和行一样便宜”，从而把建索引留在用户请求的提交里。结账主路径的两个二级索引已经是同库里的放大；倒排是另一套放大，而且词的数量随正文变，不随列数固定。

Alternatives, and treating the index as the ledger

If search and save must succeed together, a full-text index within one transactional engine is the simplest alternative, at the cost of tokenization/index maintenance in commit. A synchronous call to an external search service is still two writes: an index timeout cannot roll back an already committed source. Define a saved-but-pending-publication business state or a distributed protocol rather than claiming one transaction. With five-second freshness, an outbox-derived index is clearer.[6]

“The search store is the database” fails the update. If a shipping address changes only in the index, a rebuild or another consumer writes the old address back from the source. Deletes fail the same way: remove the posting and leave the source, and the next repair puts the document back. Ignoring amplification treats 1,600 bytes of postings as “as cheap as the row” and leaves indexing inside the user-facing commit. Checkout already pays two secondary indexes inside one store. The inverted index is a second amplification, and the token count follows the text, not a fixed column list.

引擎：热路径快，税落在哪Engine: a fast hot path still pays a cost

这一组比较同一 API 的两种引擎选择，上下两条不是同时部署。B+Tree 让键在页里有序，点查沿树下降，范围读利用叶序；上层页可在内存，非聚簇索引还可能回表。写先改缓冲页并生成 WAL，必须先让日志满足耐久屏障，之后才能回刷对应数据页。PostgreSQL 的 WAL 说明明确把日志持久与逐笔刷数据页分开。[7]

LSM 先追加所需的持久 WAL，再由引擎把版本装入 memtable；成功写不等 SSTable flush。满表冻结，后台刷成不可变文件，再合并多文件。[5] 读要从内存和文件中找版本与墓碑，不能看到一个老值就返回。结构选择不决定分布式复制和事务能力，这些协议还要另画。

This deck compares two engines behind one API; the upper and lower alternatives are not deployed together. B+Tree keeps ordered keys in pages. Point reads descend the tree; range reads use leaf order. Upper pages may be cached, and a non-clustered index can require a row lookup. Writes dirty buffers and generate WAL. The required durable log barrier precedes persistent page flush. PostgreSQL explicitly separates WAL durability from per-transaction data-page flush.[7]

LSM appends the required durable WAL, then Engine installs the version in Memtable. Successful writes need not wait for SSTable flush. Frozen memory tables flush immutable files and background merges reconcile them.[5] Reads consider versions and tombstones across memory/files instead of returning an arbitrary old value. The structure alone does not determine distributed replication or transaction support.

把放大写进预算Put amplification in the budget

写放大先定义分子：本例用引擎写到存储设备的字节除以用户字节，含 WAL、flush 和合并，设备内部 NAND 放大另算。RocksDB 的具体统计口径可能不同，要看指标定义。A12 假设输入 10 MB/s、盘写预算 100 MB/s：若该口径 WA=6，则 10×6=60 MB/s；若 WA=12，则 120 MB/s 已超预算。额外读 I/O 和尾延迟还没入账。不能只看 WAL 顺序追加很快，就宣布持续写入也能跟上。

合并积压会留下更多文件和版本，提高点查工作与临时空间；磁盘快满时后台合并需要的输入、输出共存也可能无处放。RocksDB 公开文档说明 memtable、L0 文件或待合并字节积压可减速或停写。[9] 限入流、保留合并资源并监控恢复速度，比继续加应用实例有效。墓碑在旧值和可能恢复旧值的副本仍存在时，不能仅凭时间到就清掉。

Define the numerator of write amplification. Here it is engine bytes written to storage divided by user bytes, including WAL, flush and compaction; device-internal NAND amplification is separate. RocksDB statistics may use another scope, so read their definition. A12 assumes 10 MB/s input and a 100 MB/s disk-write budget. WA=6 gives 10×6=60 MB/s; WA=12 gives 120 MB/s, exceeding the budget before read I/O and tail latency. Fast sequential WAL append does not prove sustained ingestion.

A compaction backlog leaves more files/versions, increasing lookup work and temporary space. Nearly full disks may have nowhere to keep compaction input and output simultaneously. RocksDB documents slowdown/stop triggers from memtables, L0 files and pending compaction bytes.[9] Bound ingestion and reserve compaction resources rather than adding application instances. Tombstones cannot be dropped merely by age while older values or replicas capable of restoring them remain.

Bloom、替代与改选Bloom, alternatives and changing the choice

正确构建且未损坏的 Bloom 对已加入键没有假阴性；“没有”可跳过这个文件，“可能有”还要查索引和数据。[1] 它不返回值，也不把整段范围查询变成一次过滤。读放大应分文件探测、页读和实际物理 I/O，缓存命中会改变三者关系。页式更新也有 WAL、整页与索引维护的税；LSM 也能做范围和事务，不能把“读优/写优”当绝对分类。

选型收口为约束、决策、代价、失败：短点查与混合更新可先测页式事务引擎；持续追加可测 LSM，并把合并预算和停写行为写进目标。读极多未必非 B+Tree，写极多也未必非 LSM，测试必须保留实际键偏斜、索引、压缩和后台任务。Stonebraker 与 Çetintemel 的结论是不同负载需要不同组织，不是关系库过时，也不是每个表都买一套新系统。[6]

A correctly built, uncorrupted Bloom filter has no false negatives for inserted keys. “No” skips that file; “maybe” still requires index/data lookup.[1] It neither returns values nor filters an entire range in one step. Separate file probes, page reads and physical I/O; caches change their relationship. Page engines pay WAL/page/index costs too, while LSM can support ranges and transactions. Read/write optimized are tendencies, not absolute categories.

Close with constraints, decision, cost and failure: benchmark a page-oriented transactional engine for short point reads and mixed updates; benchmark LSM for sustained appends with compaction resources and stall behavior in the goals. Preserve key skew, indexes, compression and background work in tests. Stonebraker and Çetintemel argue for workload-specific organization, not obsolete relational databases or a new system per table.[6]

列条带：很多行里只读少数几列Column stripes: a few fields across many rows

用同一笔订单量估算扫描量

A11 沿用一年 1,261,440,000 行：整行×1,500 B≈1.892 TB，金额×8 B=10,091,520,000 B≈10.09 GB，再读一字节 status 就是约 11.35 GB。金额的裸扫描字节降低 1,500÷8=187.5 倍；压缩、编码、页头、选择性与 CPU 另计，不承诺同倍提速。Dremel 2010 用列条带、重复级和定义级表示嵌套数据，再由执行树聚合，是只读分析。[4] 本章未实测秒级延迟，也不把论文吞吐移植成我们的 SLO。

宽表扫描回答的是“这个行键附近的列”。列条带回答的是“所有行上的这一列”。把 Bigtable 叫成数仓，是把 tablet 上的行范围说成了列条带。Bigtable 可以高效读短的行范围；对全部订单求一个字段的和，短范围这个前提不成立。[1][4] Dremel 是只读分析，可以就地读已有的文件或表，它不替代结账的提交。写仍进行存；分析可以读行存导出的列文件，也可以读复制出来的快照。导出有延迟，报表允许这个延迟，确认页不允许。

Estimate the scan with the same order volume

A11 reuses 1,261,440,000 rows/year: full rows×1,500 B≈1.892 TB; amount×8 B=10,091,520,000 B≈10.09 GB; an extra one-byte status brings this to about 11.35 GB. The raw-byte ratio is 1,500÷8=187.5. Compression, encoding, headers, selectivity and CPU are extra; latency does not improve by that guaranteed factor. Dremel 2010 combines column stripes, repetition/definition levels and an aggregation tree for read-only nested-data analysis.[4] No seconds-level latency was benchmarked here or imported from the paper.

A wide-row scan answers “columns near this row key.” A column stripe answers “this field on all rows.” Calling Bigtable a warehouse treats a tablet's row range as a column stripe. Bigtable reads short row ranges efficiently. A sum of one field over every order does not have that short-range premise.[1][4] Dremel is read-only analysis. It can read data in place from existing files or tables. It does not replace the checkout commit. Writes still enter the row store. Analysis reads an exported columnar file or a snapshot. Export lag is acceptable for a report and unacceptable for the confirmation page.

替代和常见混名

小数据可先让行存执行 SUM，不急着另建数仓。大历史与结账抢 I/O 时，导出列文件并固定 snapshot_id、截止位置和完整文件清单。叶子各扫不重叠片段，值回叶子，部分和回 Root，再回分析者。重试同一片段只记一份贡献；缺一片不能把部分和说成准确总和。代价是导出延迟、文件合并和快照管理；按月份裁剪只减少该次打开的片段，不让列存获得结账事务。

把“列”当成一个词会选错。宽表的列是一行里的限定符，局部性在行键。分析列存的列是很多行上同一字段的连续存放，局部性在字段。对象没有列，向量近邻也不是列扫描。为了这句 SUM 把结账改成列存，会让列条带的重写落在每一次下单上。页式行存承担结账的原地更新，LSM 的内存组件加磁盘合并承担高插入追加，列条带承担只读聚合。[5][4]

Alternative, and the word that gets mixed

For small data, a row-store SUM may be enough. When history scans contend with checkout I/O, export column files with a fixed snapshot_id, cutoff and complete file manifest. Leaves scan disjoint fragments; values return to leaves, partial sums to Root, and the total to Analyst. Retrying a fragment must not double-count its contribution, and a missing fragment cannot yield an exact sum. Costs include export lag, file merging and snapshot management. Monthly pruning reduces opened fragments without adding checkout transactions to the column store.

Using “column” for both layouts picks the wrong engine. A wide-row column is a qualifier inside one row; locality is the row key. An analytic column is one field laid out across many rows; locality is the field. An object has no column, and a vector probe is not a column scan. Moving checkout onto a columnar engine so this SUM is local would put stripe rewrites on every order. A page-oriented row store takes in-place checkout updates, an LSM's memory component and disk merges take high-rate appends, and column stripes take read-only aggregation.[5][4]

追问与错误答案Follow-ups and wrong answers

主库什么时候不够

先测真实事务和工作集，确认哪条约束先破；没有测量就不从 320 推出单主上限。分片时订单和明细可同片，但库存若按 sku 另分，就可能跨片。需要的原子不变量可由支持的分布式事务承担，也可重定业务为预留与补偿；不是一分片就自动买两阶段提交。迁移先定单一写权威、快照加增量、校验和切流屏障，不能让读先去尚未追平的新库。外部一致若是硬约束，再讨论 Spanner 的事务排序和 TrueTime 提交等待。[3]

When one primary is not enough

Benchmark transactions and the working set to find the first violated constraint; 320 alone does not prove a primary limit. Order and lines can share a shard, while sku-sharded stock may cross it. A supported distributed transaction can protect the invariant, or the business can use reservations/compensation; sharding does not automatically mandate two-phase commit. Migration needs one write authority, snapshot plus increments, validation and a cutover barrier before reads reach the new store. If external consistency is required, discuss Spanner’s ordering and TrueTime commit wait.[3]

聊天为什么有时仍是行存

按会话和时间读取时，行存复合键与宽表都匹配局部性；两千条/s 本身不足以二选一。需要很多稀疏限定符、跨机器行范围和单行操作时再评估宽表。一个热会话仍要控制桶大小与写热点；单行原子不等于跨桶快照。时序查询另问保留、压缩和降采样，文档查询另问嵌套聚合与字段索引，多跳路径才评估图，ANN 才评估向量，不能按 JSON 的外观选模型。

Why chat sometimes stays on a row store

Conversation/time reads fit both a relational composite key and wide-row locality; 2,000 messages/s alone does not decide between them. Evaluate wide rows for sparse qualifiers, distributed row ranges and single-row operations. Hot conversations still need bounded buckets and write-skew controls; single-row atomicity is not a cross-bucket snapshot. Ask separately about TSDB retention/compression/downsampling, document aggregates/indexes, graph multi-hop paths and vector ANN instead of choosing by JSON appearance.

倒排里能不能存正文

可以存一份用于展示的字段，但写路径仍先提交源库，查询仍要能用源库的版本否决过期命中。只把正文放在倒排里，重建、部分更新和删除都会失去权威。索引放大按词数算：80 个词乘 20 字节已经约 1.6 KB，和 1.5 KB 的源行同级。这个倍数是异步的理由之一。

May the inverted index store the body

It may store a field copy for display. The write path still commits the source first, and the query must still be able to reject a stale hit using the source version. A body that lives only in the index loses its authority on rebuild, partial update, and delete. Amplification follows the token count: 80 tokens times 20 bytes is already about 1.6 KB, the same magnitude as the 1.5 KB source row. That factor is one reason the index is async.

收尾三句

口述先报访问键、提交边界和故障结果，再报模型。结账的订单、库存和幂等结果同事务，确认读回当前主库；单键可合并数据才考虑 Dynamo 风格 quorum，并写出故障成员集合。聊天按会话加时间聚集，分析按字段扫列，大对象直传而由元数据发布，搜索从持久源派生。引擎再选：页式点查与 WAL，或追加、合并和 Bloom；每一种都要把放大、可恢复来源和失败行为讲清。

Three sentences to close

State access keys, commit boundaries and failure outcomes before naming a model. Order, stock and idempotency commit together; confirmation reads the current primary. Consider Dynamo-style quorum for mergeable one-key data and name failure membership sets. Chat clusters by conversation/time, analytics scans fields, blobs upload directly with metadata publication, and search derives from durable source. Then choose page access/WAL or append/merge/Bloom and explain amplification, recovery authority and failure behavior.
