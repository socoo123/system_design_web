向量检索服务Vector search service

约 40 分钟 · 前置：Ch03、Ch30 · 6 组 / 33 帧渐进白板图~40 min · after Ch03, Ch30 · 6 decks / 33 progressive frames

本章要点：近邻可以近似，范围和读状态必须准确Core: approximate neighbors, precise scope and read state

本章为 Ch30 的 RAG 后端设计向量检索服务。先根据向量占用的字节数和过滤条件选择索引，再说明写入什么时候能被搜索、所有分片怎样一起发布，以及分片缺失时该返回什么。

设计中要确定三件事：用不可变的向量规格（schema）固定模型、维度和距离度量；在同一快照内检查候选的权限与版本；为每次查询固定完整索引包（bundle）和每片的读取位点（cut）。查询失败时必须明确报错，不能伪装成没有匹配结果。

Provide vector retrieval to Ch30 RAG. Choose an index from bytes and predicate shape, then implement visibility, all-shard publication and missing-shard responses.

Three decisions: bind model/dimensions/metric in a schema; validate candidate scope and version within one snapshot; pin a complete bundle and fixed per-shard cuts, with explicit failure states.

先约定接口，以及一次查询能读到什么Define the API and read contract

POST /v1/vectors/search 接收已经计算好的查询向量、模型及其规格（model/schema）、期望结果数 k、元数据过滤条件，以及可选的写入令牌（token）。查询服务（Query svc）根据调用方身份确定租户和集合（tenant/collection），用户提供的条件只能进一步缩小范围。响应返回结果的 id/version/distance、所用索引包、每片读取位点、分片覆盖情况（coverage）和完整标记 complete。complete 只表示所有必需分片都成功响应，不表示近似近邻搜索（ANN）找到了精确的 top-k。

向量规格由服务端登记，登记后不可变，其中包含向量嵌入模型（embedding）的具体版本、维度、距离度量（metric）和归一化规则。完整索引包还绑定索引、量化码本（codebook）、路由代次，以及各分片的读根（root，即该片完整读状态的引用）。两种模型即使输出维度相同，也不能混用向量。

L2 距离越小越近，内积则越大越近。为了统一排序，本章输出的 distance 都是“小为近”：分别使用平方 L2、1−cosine 或负内积。Faiss 的 L2 输出平方距离；计算余弦相似度（cosine）时，可以先把查询向量和存储向量都归一化，再计算内积 [2]。

本服务接收现成向量；计算 embedding、融合 BM25 结果和做语义重排，仍由 Ch30 负责。这里用原向量重新评分（rescore），只是按同一种距离度量重算。索引中的权限投影可能落后于保存正式文档的权威库，因此 Ch30 在读取证据和最终发出回答时，仍要复查权限。

POST /v1/vectors/search takes an already-computed query vector, model/schema, k, metadata predicate and optional write token. Identity fixes tenant/collection; user predicates only narrow scope. Return ID/version/distance, bundle, per-shard cuts, coverage and complete. Here complete means every required shard succeeded, not exact ANN top-k.

An immutable server registry binds the exact embedding model revision, dimensions, metric and normalization. A bundle additionally binds index/codebook, routing generation and all shard roots. Equal dimensions do not make models compatible. Canonical distance ranks low first: squared L2, 1−cosine or negative inner product. Faiss reports squared L2 and supports cosine through normalized inner product [2].

Embedding, lexical fusion and semantic reranking remain in Ch30. Raw-vector rescoring recomputes the same metric. Index-projected permissions may lag the authoritative document store, so Ch30 still rechecks evidence access and response release.

规模假设：307.2 GB 原向量会怎样影响选型Scale assumptions: what 307.2 GB changes

1 亿条向量，每条 768 维，每维用 4 B 的 float32 保存，原向量共占 1 亿 × 768 × 4 B = 307.2 GB。均匀分成四片后，每片 76.8 GB；每片保留两份副本，原向量合计 614.4 GB。本例假设峰值为每秒 200 次查询，k=10，完整查询的 p95 延迟目标不超过 50 ms。这些目标、索引参数和吞吐预算都用于教学，本章没有运行真实向量库压测。

100M × 768 × 4 B = 307.2 GB raw vectors; four shards need 76.8 GB each, with 614.4 GB for two copies. Peak 200 queries/s, k=10 and complete-query p95≤50 ms are teaching targets. Index parameters and throughput budgets are assumptions; no vector-database benchmark was run.

一次查询：先固定读状态，再搜索和返回Query loop: validate state before returning

查询服务先固定本次使用的索引包，再核对查询向量的模型和规格是否与它完全匹配，同时检查维度、数值是否有限、k 和并发预算。检查通过后，服务向全部必需分片发出请求。如果查询别名（alias）已经切换到另一种模型，旧 embedding 必须被拒绝，或由上游重新计算，不能只替换模型标签。

索引副本搜索本次固定的增量状态（growing）和冻结段（sealed），先剔除旧版本、墓碑和不合格候选，再对有数量上限的短名单按同一种距离度量重算，最后交回查询服务归并。读取原向量时，键必须包含集合、向量规格、租户、ID 和版本（collection/schema/tenant/id/version）；只用裸 id，可能读到别的范围或错误版本。

50 ms 的延迟目标包含排队、内部网络、搜索和归并，不包含上游计算 embedding 的时间。每次独立扫描全库要读取 307.2 GB，峰值每秒 200 次就是 61.44 TB/s 的逻辑读取量。因此，本题不能直接把全库扫描当作默认方案；小允许集的精确扫描，或经过硬件验证的批量精确检索，仍是可选路线。

Query svc first pins this request’s bundle, then validates query model/schema against it, dimensions, finite values, k and concurrency before calling all required shards. After an alias model switch, reject old embeddings or have upstream recompute them; do not relabel them. Replicas search pinned growing/sealed state, exclude stale/deleted/ineligible candidates before local top-k, and rescore a bounded shortlist under the same metric. Raw-vector keys include collection/schema/tenant/ID/version.

The fifty-millisecond target includes queuing, internal networking, search and merging, excluding upstream embedding. Independent full scans imply 307.2 GB/query or 61.44 TB/s at 200/s. This rejects an unvalidated default corpus scan, while small exact subsets or validated batched exact search remain alternatives.

展开内存与副本预算Memory and replication budget

307.2 GB≈286.1 GiB，均匀分成四片后，每片约 71.53 GiB。每台机器的热数据预算为 128 GiB×70%=89.6 GiB，扣除原向量后，只剩约 18.07 GiB 用来保存图、ID、标量索引和版本状态。两份副本的原向量合计约 572.2 GiB，构建峰值、日志、备份和运行状态还要另外估算。把冷原向量放在 SSD 上可以节省 RAM，但必须另测随机 I/O 的尾延迟。

307.2 GB≈286.1 GiB, or about 71.53 GiB/shard. A 70% hot-state budget on 128 GiB leaves 89.6−71.53≈18.07 GiB for graph, IDs, scalar indexes and versions. Two raw copies total about 572.2 GiB. Add build peaks, logs, backups and runtime; SSD raw storage trades RAM for measured random-I/O latency.

HNSW：先在上层导航，再扩大底层候选HNSW: navigate above, broaden below

HNSW 的上层是随机形成的稀疏图。搜索沿更近的节点导航，再逐层下降；图中的 F 在两层都是同一个 ID，箭头表示副本内部的邻接关系读取和距离计算，并非 RPC。到底层后，候选队列会扩大探索范围，但仍可能漏掉真正的近邻 [3]。

A4 中，M=16 影响邻接规模，ef_construction=128 影响建图时的探索，ef_search=64 控制查询的候选宽度。这些参数与返回数量 k=10 要分开看：ef_search 既不是最多访问 64 个点的上限，也不保证召回率。图已在内存而原向量仍需读取冷存储、过滤很严格、删除很多等场景，都要分别测量完整查询的尾延迟。

索引是否支持更新和删除，取决于具体实现。Faiss 的 HNSW 文档明确不支持移除向量 [1]。服务可以先通过版本和墓碑阻止旧点进入结果，再异步重建索引。旧点即使仍能提供内部导航所需的邻接关系，也不代表它有资格被返回。

HNSW navigates sparse random upper layers and descends; F is one ID at two levels. Arrows are local adjacency/distance accesses, not RPCs. Bottom-layer exploration broadens candidates but can still miss true neighbors [3].

M=16 budgets adjacency, ef_construction=128 controls build exploration and ef_search=64 controls query width. These differ from k=10; width is neither a sixty-four-visit cap nor a recall guarantee. Measure cold-vector, restrictive-filter and deletion-heavy tails separately.

Update/delete support is implementation-specific. Faiss HNSW does not support removing vectors [1]. Service-level versions/tombstones may hide old points until rebuilding; internal navigation does not make a point eligible for results.

怎样粗估邻接槽位的占用A simplified adjacency-slot budget

假设每个底层节点最多保存 2M 个邻接 ID，每个 ID 占 4 B，那么每点需要 2×16×4=128 B，1 亿点合计 12.8 GB，每片 3.2 GB。这只计算邻接槽位；完整 HNSW 的高层、容器、内存对齐、版本和引擎对象还要另算。如果 ID 改用 8 B，仅这一项占用就会翻倍。

Assuming 2M four-byte base-layer IDs gives 128 B/point, 12.8 GB/100M and 3.2 GB/shard. Add upper layers, containers, alignment, versions and engine objects; eight-byte IDs double this term.

IVF-PQ：少探查列表，也少读每个候选的字节IVF-PQ: fewer lists and smaller candidates

IVF 根据训练得到的粗质心，把向量分入倒排列表，查询时只探查其中 nprobe 个。IVF-Flat 在这些列表内比较原向量，IVF-PQ 则比较压缩后的短码。PQ 将向量分成多个子空间，并训练量化码本；残差 IVF-PQ（residual IVF-PQ）编码的是向量相对粗质心的残差，查询时通过查表计算距离 [1][4]。因此，IVF 减少要检查的候选数，PQ 减少每个候选占用的字节；不搭配 IVF 的 Flat PQ 仍需扫描全部短码。

按 A5，768/96=8，即每段 8 维。每段用 8 bit 编码，整条短码共 96 B；加上 8 B 的 ID，1 亿条合计 10.4 GB。3,072/96=32 倍只比较一条原向量和一条短码，不能解释为整个服务的存储缩小了 32 倍。若要用原向量重算距离，原向量仍须保留。

重算只能修正短名单内部的排序，无法补回未探查的列表或图中漏掉的点。训练数据的分布发生漂移后，列表可能更不均匀，量化误差也可能变化。使用新码本时，必须重新编码并发布完整索引包，不能直接改变旧码的解释方式。

IVF assigns vectors to trained coarse lists and probes nprobe lists. IVF-Flat compares raw vectors; IVF-PQ scores subspace codes. Residual IVF-PQ encodes residuals to coarse centroids and uses lookup-table distances [1][4]. IVF reduces candidate count; PQ reduces candidate bytes. Flat PQ still scans all codes.

768/96 gives eight dimensions/subspace. Eight-bit codes total 96 B/vector; with eight-byte IDs, 100M use 10.4 GB. The 3,072/96=32 ratio compares raw vectors with codes, not whole-service storage. Retain raw vectors if rescoring requires them.

Rescoring corrects shortlist order, not unprobed lists or missed graph points. Distribution drift affects list skew and quantization error. A new codebook requires recoding and complete-bundle publication rather than reinterpreting old codes.

展开短码扫描与原向量重算的带宽Scan and rescore bandwidth

在列表均匀的假设下，每片每个列表约有 25M/4,096≈6,103.5 条记录。探查 16 个列表，要扫描约 97,656.25 条；每条短码加 ID 占 104 B，因此约读 10.15625 MB/片。四片合计 40.625 MB/查询，峰值每秒 200 次查询，对应 8.125 GB/s 的逻辑短码读取量。

重算时，每片最多读取 100×3,072=307,200 B 原向量，四片合计 1.2288 MB/查询，峰值为 245.76 MB/s。这些只是逻辑读取量估算，尚未计入列表不均、质心距离计算、缓存复用、CPU 和随机 I/O，不能直接据此推导 p95 延迟。

With uniform lists: 25M/4,096≈6,103.5/list; sixteen probes scan about 97,656.25 records, or 10.15625 MB/shard at 104 B each. Four shards imply 40.625 MB/query and 8.125 GB/s at 200/s. Rescoring up to 100 raw vectors/shard costs 307,200 B/shard, 1.2288 MB/query and 245.76 MB/s. These logical estimates exclude skew, centroid scoring, cache reuse, CPU and random I/O; they do not establish p95.

过滤：能参与导航，不等于能进入结果Filtering: eligibility differs from navigation

ANN 可能漏掉近邻，但权限、版本和向量规格不能近似判断。符合条件的允许集较小时，可以精确扫描；集合较大时，可以使用支持过滤的 ANN，或在预算内继续补充候选。无论选择哪条路线，候选进入片内 top-k 前，都必须按同一快照复查完整过滤条件和有效版本。

ANN can miss neighbors; permissions, versions and schema remain exact. Use exact small-set scans or filter-aware ANN/bounded refill, with complete predicates and live-version checks before local top-k in the same snapshot.

public static Result select(Schema schema, String queryModel, String tenant,
    String category, List<Double> query, Map<Key, Point> pinnedLive,
    List<Candidate> stream, int k, int inspectLimit) {
  if (!schema.model().equals(queryModel) || k < 1 || k > 100 ||
      inspectLimit < k || inspectLimit > 100) throw new IllegalArgumentException("request");
  double[] q = checked(schema, query);
  Map<Key, Point> live = Map.copyOf(pinnedLive); // one immutable read cut
  Set<Key> allowed = new HashSet<>();
  for (Point p : live.values())
    if (!p.deleted() && p.key().tenant().equals(tenant) &&
        p.schemaId().equals(schema.id()) && p.category().equals(category))
      allowed.add(p.key());
  Map<Key, Hit> hits = new HashMap<>();
  int inspected = 0;
  for (Candidate c : stream) {
    if (inspected == inspectLimit) break;
    inspected++; // denied, stale and duplicate candidates also cost budget
    if (!schema.id().equals(c.schemaId())) throw new IllegalStateException("mixed schema");
    Point p = live.get(c.key());
    if (p == null || !allowed.contains(c.key()) || p.version() != c.version()) continue;
    if (hits.containsKey(c.key())) continue;
    double d = distance(schema, q, checked(schema, p.vector()));
    hits.put(c.key(), new Hit(c.key(), p.version(), d));
  }
  List<Hit> ranked = hits.values().stream()
      .sorted(Comparator.comparingDouble(Hit::distance)
          .thenComparing(h -> h.key().id())).limit(k).toList();
  String status = ranked.size() == allowed.size() ? "ALLOWED_SET_EXHAUSTED"
      : ranked.size() == k ? "K_REACHED" : "APPROX_SHORTFALL";
  return new Result(ranked, status, inspected);
}

上面的 Java 17 标准库示例可以运行，摘自 VectorCandidates.java。它接收受信副本在固定读取位点上的不可变状态 pinnedLive：Key 包含租户和 ID，Point 保存版本、向量规格、元数据和原向量。查询使用的 queryModel 必须匹配服务端规格。checked 拒绝维度不匹配和非有限数值；计算 cosine 时，还会拒绝零向量，并对双方统一归一化。distance 把三种度量都转换成“小为近”的距离，算术溢出也会被拒绝。

引擎只提供候选的 ID 和版本，其附带数据或分数不能作为权威。代码先检查过滤条件与版本，再读取原向量重算距离。重复、已删除和被拒绝的候选都消耗检查预算，最多重算 100 个。为了便于演示，代码扫描整个 Map 来统计允许点数；亿级生产系统需要同一快照下的标量索引或位图（bitset），不能照搬这种做法。这个示例不执行 HNSW、IVF 或 ACORN，因此不能证明召回水平。

K_REACHED 表示找到了 k 条结果，仍可能漏掉真正的近邻；只有已返回全部允许点时，才能报告 ALLOWED_SET_EXHAUSTED；其余情况为 APPROX_SHORTFALL。全局状态还要综合各片的搜索状态。允许集本来只有三条、预算不足只找到三条，以及某个分片没有回复，是三种不同的结果。

为什么 k/s 只能算期望值Why k/s is only an expectation

def apply_next(self, space, shard, fail_before_commit=False):
    with self.tx():  # actual SQLite BEGIN IMMEDIATE / COMMIT
        p = self.db.execute("SELECT * FROM progress WHERE space=? AND shard=?", (space,shard)).fetchone()
        lsn = p["applied"] + 1
        e = self.db.execute("SELECT body FROM event WHERE space=? AND shard=? AND lsn=?", (space,shard,lsn)).fetchone()
        if e is None:
            return False  # never jump across a hole
        body = json.loads(e["body"])
        old = self.db.execute("SELECT version,body FROM mvcc WHERE space=? AND shard=? AND tenant=? AND id=? ORDER BY version DESC LIMIT 1",
                              (space,shard,body["tenant"],body["id"])).fetchone()
        same = self.db.execute("SELECT body FROM seen_version WHERE space=? AND shard=? AND tenant=? AND id=? AND version=?",
                               (space,shard,body["tenant"],body["id"],body["version"])).fetchone()
        if same is not None and same["body"] != e["body"]:
            raise Rejected("same version, different payload; stop the prefix")
        self.db.execute("INSERT OR IGNORE INTO seen_version VALUES (?,?,?,?,?,?)",
                        (space,shard,body["tenant"],body["id"],body["version"],e["body"]))
        if old is None or body["version"] > old["version"]:
            self.db.execute("INSERT INTO mvcc VALUES (?,?,?,?,?,?,?)",
                            (space,shard,lsn,body["tenant"],body["id"],body["version"],e["body"]))
        # A stale event is a deterministic no-op, including an old upsert after delete.
        self.db.execute("UPDATE progress SET applied=? WHERE space=? AND shard=?", (lsn,space,shard))
        if fail_before_commit:
            raise Rejected("injected rollback")
    return True  # this transaction committed vector + metadata + version + watermark

完整索引包：一起发布所有分片，查询始终读固定位点Complete bundles: publish all shards and read fixed cuts

def publish(self, alias, expected_seq, bundle, barrier):
    with self.tx():  # all roots and the alias CAS share one authority transaction
        b = self.db.execute("SELECT * FROM bundle WHERE id=?", (bundle,)).fetchone()
        if b is None:
            raise Rejected("unknown bundle")
        required = set(self.schema(b["space"])["shards"])
        roots = self.db.execute("SELECT * FROM root WHERE bundle=?", (bundle,)).fetchall()
        if set(barrier) != required or {r["shard"] for r in roots} != required:
            raise Rejected("missing shard or barrier")
        for r in roots:
            epoch, minimum = barrier[r["shard"]]
            if r["epoch"] != epoch or r["cut"] < minimum or digest(json.loads(r["document"])) != r["hash"]:
                raise Rejected("stale or corrupt root")
        self.db.execute("INSERT OR IGNORE INTO alias VALUES (?,0,NULL)", (alias,))
        changed = self.db.execute("UPDATE alias SET seq=seq+1,bundle=? WHERE name=? AND seq=?",
                                  (bundle,alias,expected_seq)).rowcount
        if changed != 1:
            raise Rejected("publication CAS lost")
        self.db.execute("UPDATE bundle SET published=1 WHERE id=?", (bundle,))
    return expected_seq + 1

上面的 Python/SQLite 摘录可以运行：它在同一个权威数据库事务中核对全部读根、可信屏障（barrier）要求的每片最低位点，并通过别名序号 seq 的 CAS 提交发布。竞争发布只有一个胜者。序号单调递增，即使别名切换后又切回来，旧发布者也不能凭原来的序号提交。

到了截止时间仍有分片缺失，默认返回 UNAVAILABLE、complete=false，且不输出普通结果。只有上游明确允许，才返回 PARTIAL，并列出已覆盖和缺失的分片（covered/missing）。只有全部必需分片都成功的空结果，才能解释为本次搜索没有返回匹配；即便如此，ANN 空集仍不能证明精确搜索下没有近邻。

每片先去重、过滤，再按同一种距离排序，取片内 top-k；协调者最多合并 4×10=40 项。若各片返回精确 top-k，并用稳定 ID 处理同距情况，这些候选足以覆盖全局 top-k；使用 ANN 时，各片仍可能漏点。别名或查询保护记录仍在引用旧索引包时，不得回收它。示例没有自动超时回收机制，进程崩溃可能泄漏保护记录；生产中若使用租约，必须先确保过期工作进程停止访问旧资源，不能只删记录就回收文件。

为各片固定一组读取位点，不等于得到跨片同一时刻或原子事务快照。本设计不提供跨片原子写入。默认查询可以使用已发布的旧索引包；写入令牌则绑定向量空间、规格、分片和 epoch/LSN。模型切换后，即使数值碰巧相同，也不能把旧空间的令牌用于新空间。如果索引包未覆盖令牌要求，就要等待或建立覆盖它的完整索引包，否则返回失败，不能悄悄退回旧数据。

迁移和回退怎样保持读要求，故障时容量够不够Migration, rollback and failure capacity

只重建索引时，可以保留原来的 embedding 规格。每片先按快照构建新码本或索引，再回放包含删除在内的日志，追到选定屏障；全部读根加载并固定后，才通过 CAS 发布完整索引包。更换 embedding 模型则要另建向量空间，并由上游提供新模型生成的向量。源变更游标必须同时驱动旧、新模型并协调屏障，不能给旧向量换个模型标签就使用。扩容改变路由时，也要先复制快照、追增量、验证完整的新分片集合，再一次发布；旧令牌需要做路由转换，否则应明确拒绝。

若要回退，旧编码器和旧向量空间必须持续摄取变更，再生成满足当前新鲜度要求的读根和索引包。只保留旧文件，无法安全承接新的读取；已开始的旧请求则继续使用自己的查询保护记录。如果新一代尚未完整就绪，就继续使用旧版本或返回失败，不能混用两种模型搜索。示例只验证切换已经提供好向量的空间，不执行 embedding、物理搬片或真实增量迁移。

容量也要按完整查询计算。全局每秒 200 次查询，会让每片都收到 200 次，合计每秒 800 次分片搜索。两份副本各有每秒 120 次的预算，稳态均分后各接 100 次，利用率为 83.3%；失去一份后，只剩 120 次/秒。若要维持每秒 200 次查询，须实测幸存副本有更高容量，或增加冗余并配合限流。即使四片各自都有 95% 的请求赶上延迟阈值，在独立假设下，四片同时赶上的概率也只有 0.95⁴≈81.45%。完整查询的 p95 仍必须实测。

验收时分别检查召回率、可见性和隔离Evaluate recall, visibility and isolation separately

评估时要分别看严格过滤及其与向量分布的相关性、小租户和热点、删除和 growing 增量，以及冷热数据页。调参集与独立回归集分开使用，同时测量完整查询的 p95、超时率和资源占用。

检查可见性时，要推演这些反例：WAL 确认丢失后重试、应用中途失败、删除后又收到旧 upsert、同版本对应不同正文、构建发布输掉 CAS、发布时缺片、旧查询遇到新发布、令牌超出索引包覆盖范围，以及同片回复迟到或重复。检查隔离时，可以放入一个距离更近的其他租户的点，要求它的 ID、附带数据和分数都不得输出。仅仅凑满十条结果，无法证明这些保证。

本章已有的实际运行验证覆盖 Java 17 候选与距离模型，以及 SQLite 事务和双连接竞争。源码、运行命令、同源检查和限制见 examples/ch31；没有执行真实 ANN、复制集群、embedding、迁移或生产压测。面试时可以沿这条线展开：先按字节开销选择结构，再讲过滤和版本、持久接收和连续可见、全分片索引包的固定读取，最后说明缺片与回退的边界。

Freeze queries, schema, identity, predicate and data snapshot. Compute exact ground truth within the same allowed set: K=min(k,allowed count), Recall=|returned∩truth|/K. Treat K=0 as empty-set correctness. Nine of ten is 0.9; mean≥0.95 does not establish every query≥0.95. Slice predicate correlation/selectivity, tenant hotspots, deletes/growing and hot/cold pages. Separate tuning and held-out sets and measure complete-query p95/timeouts/resources.

Visibility counterexamples include lost acknowledgements, failed apply, old upserts after deletes, conflicting same revisions, losing build CAS, missing publication shards, old queries across new publication, uncovered tokens and late/duplicate attempts. Inject a closer foreign-tenant point and require zero ID/payload/score output. Returning ten proves none of these guarantees.

Actual execution covers Java17 candidate/distance models and SQLite transactions/two-connection races. See examples/ch31 for sources, commands, synchronization and limitations. No real ANN, replicated cluster, embedding, migration or production benchmark ran. Explain bytes → candidate scope/version → durability/contiguous visibility → all-shard fixed bundles → failure/rollback boundaries.
