三个决定：存好字节，再发布版本Three decisions: store bytes, then publish a version

  • 分开两条路径：字节直传，目录、权限与版本走元数据事务。
  • 分开两种成功：块已核验并被保护，才允许条件提交；PUT ACK 还不是文件已保存。
  • 分开两种进度：服务端提交由幂等回执确认；设备同步按持久变更游标补齐，GC 不得删掉其依赖。
  • Separate paths: direct bytes, transactional directory, permission and version metadata.
  • Separate successes: verify and pin every block before conditional publication; a PUT ACK is not a saved file.
  • Separate progress: idempotent receipts confirm server commits; durable change cursors repair device sync while GC protects their dependencies.

30 秒开场：纯文件，不做字符级协作The 30-second open: files without character-level collaboration

稳定 file_id 对应版本历史，每版是有序块列表。客户端切块、查可复用引用、上传缺块；服务端核验并 pin，再按父版本条件提交。两个离线编辑不能默默覆盖，失败者可另存冲突副本。通知只叫醒设备，正确性靠变更日志和补拉；删除先去引用，再回收无保护块。

先确认单文件上限、最长离线期、冲突策略、历史保留、租户与分享权限。本章选文件上传/下载、多端同步与 30 天历史；不实现实时协作、端到端加密或跨地域双活。

A stable file_id owns version history, with an ordered block manifest per version. Clients chunk, locate authorized reuse and upload missing blocks. The server verifies and pins before conditionally committing the parent. Offline edits cannot silently overwrite: the loser can save a conflict copy. Notifications wake devices; change history and catch-up establish correctness. Remove references before reclaiming unprotected bytes.

Clarify file limits, offline duration, conflict policy, history, tenancy and sharing. This chapter covers upload/download, device sync and 30-day history, without implementing live collaboration, end-to-end encryption or regional active-active.

“已保存”：版本事务确认后，权威读取可见该版或后续提交版；按版本读取仍取同一不可变 manifest。其他设备最终补齐。对象 PUT、块核验/pin、版本提交、另一端本地应用是四个状态，界面分别展示。

Saved: after commit acknowledgement, authority reads observe that version or a later commit; version-specific reads retain the same immutable manifest. Other devices catch up eventually. Object PUT, verification/pin, version commit and remote local application are four distinct UI states.

一天文件保存数是 10,000,000 × 2 = 20,000,000，平均 20,000,000 ÷ 86,400 ≈ 231.5 次/秒，峰值约 1,157.4 次/秒。这只是文件级操作。一天入站 10,000,000 × 100 MB = 1 PB，平均 11.57 GB/s，乘 8 是 92.59 Gb/s，再乘峰值 5，约 462.96 Gb/s。字节走直传的原因就在这笔带宽，不是元数据 API 已经有几十万 QPS。

10,000,000 × 2 = 20,000,000 file saves/day; ÷86,400 ≈231.5/s average, ≈1,157.4/s at peak. Those are file operations. Daily inbound is 10,000,000 ×100 MB =1 PB, averaging 11.57 GB/s or 92.59 Gb/s, with a 5× peak of ≈462.96 Gb/s. This bandwidth forces direct upload; it does not mean the metadata API has hundreds of thousands of QPS.

块请求必须另算。100 MB/人除以 4,194,304 B 得到约 23.84 个满块；每个文件向上取整。若每人两份都恰好是 50 MB，每文件 ceil(50,000,000 ÷ 4,194,304) = 12 块，一天 2,000 万 × 12 = 2.4 亿 PUT，平均约 2,778/s，峰值约 13,889/s。只知道总字节数时，每文件尾块最多再多一块：1 PB ÷ 4 MiB + 2,000 万 < 2.585 亿块/天，峰值约 14,955/s，先预算约 1.5 万。真实分布决定更精确的数。

Size block operations separately. 100 MB/user ÷4,194,304 B ≈23.84 full-block equivalents, but round up per file. If both files are exactly 50 MB, each needs ceil(50,000,000/4,194,304)=12 blocks: 240M PUTs/day, ≈2,778/s average, ≈13,889/s peak. With total bytes alone, each file adds less than one rounding block: 1 PB/4 MiB +20M <258.5M blocks/day, ≈14,955/s peak. Budget around 15K initially; the size distribution gives a closer estimate.

配额天花板是 50,000,000 × 10 GB = 500 PB，不能说成已经落盘的占用。按每日 1 PB 输入，连续 30 天全部是新内容且完全不共享，字节增量上界是 30 PB；教学模型乘三份是 90 PB，未含此前仍存的文件、manifest、日志和备份。若只保证版本保留 30 天，也不能把所有当前文件 30 天后删掉，所以这不是全站存储总量。去重率未知，容量先用 0% 节省；上线后再从唯一块增量测节省比例。

The quota ceiling is 50,000,000 ×10 GB =500 PB, not occupied storage. With 1 PB/day of entirely new unshared input, 30 days adds at most 30 PB of logical bytes; three teaching-model copies are 90 PB, excluding older live files, manifests, logs and backups. Thirty-day version retention does not delete every current file after thirty days, so this is not total site storage. Plan with 0% dedup savings until unique-block growth is measured.

下载按每次保存只同步到另一个设备估为同量级，不把上传和下载相加后说成一条方向的网卡速率。公开分享、重复下载和本地缓存命中需要分别加减。5 秒同步目标只覆盖在线设备与小增量：4 MiB × 8 ÷ 20 Mb/s ≈ 1.68 秒是纯传输下限，还要留出通知、鉴权和落盘时间；1 GiB 在同一链路上约 429 秒，不能承诺也在 5 秒内完成。

With one other syncing device per save, downloads have a similar magnitude; do not combine both directions into one-direction NIC capacity. Public sharing, retries and local cache hits need separate accounting. A five-second sync target applies to online devices and small deltas: 4 MiB ×8/20 Mb/s ≈1.68 s of transfer alone, plus notification, authorization and persistence. A 1 GiB transfer takes ≈429 s on that link and cannot share the five-second target.

15.1 · 分层：字节直传，版本由元数据发布15.1 · Layers: direct bytes, metadata publication

控制面拥有一个原子边界One atomic boundary belongs to the control plane

初始化冻结 (tenant,owner,file,base,ordered[digest,length],size)，返回持久会话 u42；不能在同一会话下换清单。Metadata、Block svc 和 GC 是不同进程，相关元数据却必须在同一权威事务数据库：guard、ACL、File、Session/SessionBlock、BlockGeneration、Version/VersionBlock、Receipt、Change、Outbox。图是逻辑服务分层，不能理解成跨库 FOR UPDATE。

教学实现以 PostgreSQL 18 的 READ COMMITTED 表达：预建每租户一行 guard，所有会改变 ACL、目录、会话/pin、版本引用、配额或 GC 状态的操作，都先 SELECT … FOR UPDATE，锁持到事务结束。[11] 它使同租户操作串行，便于看清边界；热租户会成为瓶颈，拆细锁/分片后必须重新证明这些约束。

Initialization freezes (tenant,owner,file,base,ordered[digest,length],size) and returns durable session u42. Its manifest cannot change. Metadata, Block svc and GC are processes, but their relevant rows share one authoritative transactional database: guard, ACL, File, Session/SessionBlock, BlockGeneration, Version/VersionBlock, Receipt, Change and Outbox. Logical service separation does not imply cross-database FOR UPDATE.

The teaching implementation uses PostgreSQL 18 READ COMMITTED: pre-create one tenant guard row. Every mutation of ACL, directory, sessions/pins, references, quota or GC first locks it with SELECT … FOR UPDATE through transaction end. [11] This serializes a tenant for clarity and creates a hot-tenant bottleneck. Finer locking or sharding must re-establish the invariants.

锁 guard 不等于自动过滤租户。所有辅助函数和逻辑行键都绑定认证的 auth.tenant；File、Session、Version、VersionBlock、Receipt、Change、pins 的读写均使用完整租户复合键，SQL 的 UPDATE/DELETE/扫描显式带 tenant_id 条件。GC 只处理内部可信任务，按 (job.tenant,generation) 读取持久 Job/BlockGeneration，再使用该行的物理对象 key；不能接受裸 ID 或客户端任意租户参数。

Locking a guard does not filter tenant rows. Every helper and logical row key binds authenticated auth.tenant. File, Session, Version, VersionBlock, Receipt, Change and pin access uses complete tenant composite keys; SQL UPDATE/DELETE/scans carry explicit tenant_id predicates. Trusted internal GC jobs load durable Job/BlockGeneration rows by (job.tenant,generation), then use that row’s physical object key, never bare IDs or client-selected tenant scope.

-- Teaching shape: PostgreSQL 18; all rows belong to one metadata authority.
-- Every metadata writer first locks its pre-created tenant_guard row.
CREATE TABLE tenant_guard (
  tenant_id TEXT PRIMARY KEY, change_head BIGINT NOT NULL CHECK (change_head >= 0),
  used_bytes BIGINT NOT NULL CHECK (used_bytes >= 0), quota_bytes BIGINT NOT NULL
);
-- The complete schema also contains File, ACL, Session and immutable Manifest.
CREATE TABLE block_generation (
  tenant_id TEXT NOT NULL, generation TEXT NOT NULL, digest TEXT NOT NULL,
  byte_length BIGINT NOT NULL CHECK (byte_length > 0),
  object_key TEXT NOT NULL UNIQUE, state TEXT NOT NULL,
  PRIMARY KEY (tenant_id, generation)
);
CREATE UNIQUE INDEX one_ready_generation
  ON block_generation (tenant_id, digest, byte_length) WHERE state = 'READY';
CREATE TABLE commit_receipt (
  tenant_id TEXT NOT NULL, owner_id TEXT NOT NULL, request_key TEXT NOT NULL,
  intent_digest TEXT NOT NULL, file_id TEXT NOT NULL, version BIGINT NOT NULL,
  change_seq BIGINT NOT NULL,
  PRIMARY KEY (tenant_id, owner_id, request_key)
);
-- SessionBlock PK=(tenant,session,ordinal), recording generation and proof.
-- Version PK=(tenant,file,version); VersionBlock PK=(tenant,file,version,ordinal).
-- Change and Outbox each have PK=(tenant,change_seq).
-- File has UNIQUE(tenant,parent,name); Session has at most one result.
-- No sequence allocates change_seq; the locked ordinary guard row does.

以上是约束形状，不是完整 DDL。初始化还限制单文件至 1,024 块（4 GiB）、核对总长度、非末块 4 MiB、末块长度和空文件规则；File 的名称唯一与权限校验同事务。这里配额按所有仍保留版本的逻辑长度之和计费，包含历史/回收站，字节去重不减账；清除保留版本时才在同事务移除引用并减账。

字节先进 Object store，版本后进 Primary。前者成功后元数据失败只是暂存；反序会发布缺块版本。数据库确认须符合选定持久化/切主策略，不能把单机事务写成跨地域零丢失。对象存储也须提供确认后可读、不可变最终对象与所承诺的耐久性，不能对有效对象另配无协调的生命周期删除。

This is a constraint shape, not complete DDL. Initialization also bounds a file to 1,024 blocks (4 GiB), validates total length, full nonfinal 4 MiB blocks, tail size and empty-file rules. File name uniqueness and permissions share the transaction. Quota charges the sum of retained versions’ logical lengths, including history/trash, regardless of dedup. Removing a retained version atomically removes references and its charge.

Store bytes before metadata publication. Metadata failure then leaves staging; the reverse order exposes missing bytes. Database acknowledgement depends on the chosen durability/promotion policy, not a claim of zero-loss regional failover. Object storage must provide acknowledged readable immutable final objects and its promised durability, with no unrelated lifecycle rule deleting valid content.

为什么不让 API 中转全部字节Why avoid proxying all bytes through the API

本例入站峰值约 463 Gb/s。代理可以统一校验、加密和入口，但整层吞吐随字节增长；直传把带宽留在存储接入层，API 负责授权、核验和发布。Primary 不可用时继续本地保存，已签上传可继续但不能显示“已保存”；核验服务不可用就等待，不能相信客户端进度条。缺一个对象，下载整版失败，不能少块也算成功。

Peak inbound is about 463 Gb/s. A proxy centralizes validation, encryption and ingress, but its capacity follows bytes. Direct upload leaves throughput at storage ingress while APIs authorize, verify and publish. During a Primary outage, clients save locally; issued uploads may continue without showing Saved. Unavailable verification waits instead of trusting client progress. A missing object fails the version download rather than producing a shorter successful file.

15.2 · 分块与 COW：复用的条件要说清15.2 · Chunking and COW: state the reuse conditions

逻辑内容键与物理对象代际分开Separate content identity from physical generations

逻辑键是 (tenant,SHA256,length)，物理地址另带不可复用 generation。图中的 hA/hB 是逻辑内容引用，经目录映射到已核验物理对象；manifest 保留顺序与长度，VersionBlock 冻结具体 generation。父版本只记录编辑来源，读 v8 无须重放 v7。空文件是空列表、长度 0；清单摘要含序号、长度与总长，换序不能蒙混。

Venti 原论文说明按内容摘要命名、不可变块和共享，不把其历史哈希选型照搬。[1] Dropbox 的公开 content_hash 用 4,194,304 B 分块，逐块 SHA-256 后拼二进制摘要再 SHA-256；它是整文件校验 API，不保证内部去重布局。[2] 本章的独立块摘要与最终聚合摘要不是同一个 key。

The logical key is (tenant,SHA256,length); physical addresses add a never-reused generation. hA/hB in the diagram name logical content mapped to verified objects. Manifests retain order and length; VersionBlock freezes generations. Parent versions record ancestry, without patch replay. Empty files use an empty list and zero length. The manifest digest includes ordinals, lengths and total size, preventing reordered intent.

Venti describes digest naming, immutable blocks and sharing; its historical hash choice is not adopted. [1] Dropbox content_hash uses 4,194,304-byte blocks, SHA-256 per block, then SHA-256 over concatenated binary digests. It verifies whole files without promising an internal dedup layout. [2] This design’s block keys differ from that aggregate digest.

去重先证明可采用，再省上传Authorize adoption before skipping upload

同租户也不能凭 hash 偷挂别人的私有块。跳过上传必须证明该调用者当前能读某份已提交版本里的对应引用；否则仍上传实际字节到自己的 staging，由服务端核验。查缺不向未获授权者暴露“别人已有这个 hash”。权限撤销与 pin/commit 同 guard 协调，复用证明在提交时重查；内容 hash 从不等于下载凭证。

本章采用碰撞难以构造的 SHA-256 假设，仍逐块核长度与摘要；碰撞/损坏告警隔离对象，不能覆盖既有字节。默认租户内去重，跨租户去重会增加内容存在性和密钥边界问题，留作单独设计。

A same-tenant hash does not authorize adopting another private block. Skipping upload requires a currently readable committed version containing that reference. Otherwise upload actual bytes to private staging for service verification. Missing-block lookup must not disclose an unauthorized content-existence hit. Revocation, pinning and commit share the guard; commit rechecks reuse permissions. Digests never serve as download credentials.

This assumes SHA-256 collisions are infeasible to construct, while validating both digest and length. Suspected collision/corruption quarantines content instead of overwriting bytes. Default dedup stays within a tenant; cross-tenant existence and key boundaries require separate design.

COW 的节省取决于边界与修改范围COW savings depend on boundaries and locality

三块各 4 MiB，v7=[hA,hB,hC]，只把中间块等长改为 hD：两版逻辑共 24 MiB，唯一块 16 MiB，省 33.3%。1 GiB 有 256 个 4 MiB 块，仅 32 B 摘要就要 8 KiB；换 64 KiB 块变 16,384 块、512 KiB 摘要，请求数为 64 倍。小块减修改放大，大块减请求和索引。

文件头插字节会移动定长边界；压缩或加密也可能传播改动。CDC 用内容定边界，通常能在插入后重新同步，restic 文档解释了此机制。[3] 它仍需扫描和 hash CPU，并非任何修改都只传一块。

With three 4 MiB blocks, v7=[hA,hB,hC] and a same-length middle edit to hD total 24 MiB logically but 16 MiB uniquely, saving 33.3%. A 1 GiB file has 256 blocks; 32-byte digests alone need 8 KiB. At 64 KiB there are 16,384 blocks and 512 KiB of digests, with 64 times the requests. Small blocks reduce edit amplification; large blocks reduce operations and indexing.

Prefix insertion shifts fixed boundaries, while compression/encryption may spread edits. CDC selects content boundaries and can usually resynchronize after insertion, as restic explains. [3] It still costs scanning and hashing and does not guarantee one block per edit.

15.3 · 断点续传：超时后向服务器对账15.3 · Resume: reconcile after a timeout

从 PUT 收据到可信 pin，中间还有核验Verification separates a PUT receipt from a trusted pin

u42 是持久的应用块会话，不是 S3 multipart upload。每块状态为 missing/pending/verified-and-pinned；状态查询认证会话 owner，并重查权限。ACK 丢失后向服务端对账；对象存在但缺可信记录就重新核验，不用本地位图或对象名直接置 durable。授权过期可在活会话内刷新，会话过期则新建并重新鉴权，旧会话不能复活。

预签名 URL 不自带不可变性。S3 普通预签 PUT 可在到期前多次使用，同 key 已存在时可替换。[12] 所以客户端只写版本化 staging；授权先登记绑定 session/ordinal/摘要/长度的新 attempt 和租约。服务端按精确 staging version ID读字节，验摘要/长度，再写只有服务端可写的新最终 generation。最终 key 创建一次且不复用，核验后仍持有旧 URL 也改不了它。

u42 is a durable application block session, distinct from S3 multipart. Blocks are missing, pending or verified-and-pinned. Status authenticates the owner and checks permissions. After a lost ACK, reconcile with authority; an object without a trusted record needs verification, not trust in a bitmap or object name. Refresh grants inside a live session; expiry requires a new authorized session rather than revival.

Presigned URLs do not imply immutability. Ordinary S3 presigned PUTs can be reused until expiry and replace the same key. [12] Clients therefore write versioned staging only. Grant issuance first registers a fresh attempt and lease bound to session, ordinal, digest and length. The service reads an exact staging version ID, verifies it and writes a fresh final generation using service-only credentials. Creating final keys once without reuse prevents old upload URLs from modifying them.

verify_and_pin(auth, session_id, ordinal, proof):
  // Session, attempt, source and generation reads all bind auth.tenant.
  // Init froze ordered (digest,length), file, base, size and owner.
  expected, attempt = authority.read_bound_attempt(auth, session_id, ordinal)
  if proof.kind == UPLOAD:
    // Grant issuance registered attempt + fresh generation + expiry first.
    bytes = Object.GET(attempt.staging_key, version_id=proof.version_id)
    require length(bytes) == expected.length and SHA256(bytes) == expected.digest
    // Only the service writes final keys; a physical key is never reused.
    final = Object.PUT_IF_ABSENT(attempt.final_key, bytes, checksum=expected.digest)
    require confirmed_exact_final(final, expected) else RETRY_UNKNOWN_OR_FAIL
    // This gate inspects a pre-existing key too; unknown never reaches READY.
  begin Metadata transaction:
    SELECT tenant_guard WHERE tenant_id=auth.tenant FOR UPDATE
    s = require_owned_OPEN_session(auth, session_id, db_now())
    require current_write_acl(auth, s.file_id)
    require s.manifest[ordinal] == expected
    if proof.kind == REUSE:
      source = require_currently_readable_version(auth, proof.file, proof.version)
      g = source.block_at(proof.ordinal)
      require g.digest_length == expected and g.state == READY
    else:
      require proof.kind == UPLOAD and attempt.still_live_and_UPLOADING(db_now())
      g = find_READY_generation(auth.tenant, expected)
      if g is absent: g = promote_verified_attempt_to_READY(attempt)
      else: mark_unused_attempt_ORPHAN(attempt)
    UPSERT SessionBlock(auth.tenant, s.id, ordinal, g.generation, proof)
    // A pin is active only while its owned session is OPEN and unexpired.
    COMMIT
  return VERIFIED_AND_PINNED(g.generation)
  // Any failed requirement aborts: no pin and no file publication.

对应第 3–4 帧：外部 GET/PUT 在事务外；已注册 attempt 在有效期内保护正在写的 generation。随后 guard 锁内重查当前权限、会话、attempt 和 READY 状态，写 SessionBlock 才算 pin；每个 ordinal 的摘要/长度不可换。辅助 promote 只改变同库目录状态，不做网络 I/O。PUT 结果未知就读同一不可变 key 的长度和显式 checksum；ETag 不能充当 SHA-256。失败或过期留下候选待 GC，不发布文件。迟到写入旧 DELETING generation 也不得把它重新变 READY，后台继续清孤儿。

复用路径从当前可读 VersionBlock 取得 generation，再与冻结清单核对；不接受裸 hash 证明。重复上传可命中同一 READY generation；多余的已核验候选标 ORPHAN。这里为清楚而读回校验、再写最终对象，会增加存储内部读写；有可信 checksum 与条件写的存储可优化，但必须保住精确对象与不可变性边界。

Frames 3–4: external GET/PUT run outside the transaction. The pre-registered live attempt protects its in-progress generation. Under the guard, recheck current permissions, session, attempt and READY state before recording the SessionBlock pin. Ordinal digest/length cannot change. Promotion changes only catalog rows, without network I/O. An unknown PUT inspects the same immutable key’s length and explicit checksum; ETag is not SHA-256. Failures/expiry leave GC candidates, without publication. Late writes to a DELETING generation cannot make it READY again; orphan cleanup retries.

Reuse takes the generation from a currently readable VersionBlock and matches the frozen manifest, never a bare digest. Duplicate uploads can adopt one READY generation while extra verified candidates become ORPHAN. Read-back verification followed by final-object writing adds internal storage I/O; trusted checksums and conditional writes may optimize it while preserving exact-object and immutability boundaries.

续传的节省与协议边界Resume savings and protocol boundaries

1 GiB 的 256 块中确认 192 块，剩 64×4 MiB=256 MiB。20 Mb/s 理想下限为 107.37 s，整份是 429.50 s，少传 75%；限制并发、退避加抖动，别让多个在途块争满弱网。第 5 帧只展示补 PUT，全部补完仍须核验/pin 再提交。

tus 1.0.0 核心用 HEAD 读 Upload-Offset、PATCH 顺序续传，错偏移 409。[4] multipart 则上传编号 part 后 complete 组装一个对象，ETag 不保证 MD5，遗留 part 要 complete/abort 或生命周期清理。[5] S3 非末尾 part 至少 5 MiB，不能直接套本章 4 MiB 逻辑块；这里是普通独立对象 PUT。[6]

After verifying 192 of 256 blocks in 1 GiB, 64×4 MiB=256 MiB remains. At 20 Mb/s, ideal transfer is 107.37 s versus 429.50 s for the whole file, saving 75%. Bound concurrency and use backoff with jitter. Frame 5 shows replacement PUTs; all still need verification/pins and commit.

tus 1.0.0 core reads Upload-Offset with HEAD and resumes sequential PATCH, returning 409 for an offset mismatch. [4] Multipart uploads numbered parts then completes one object; ETag need not be MD5 and leftover parts require completion/abort or lifecycle cleanup. [5] S3 requires at least 5 MiB for nonfinal parts, unlike these independent ordinary 4 MiB object PUTs. [6]

A11 gives 1 PB/day×1% abandoned=10 TB/day, or about 20 TB over 48 h before redundancy. A 24 h session expiry closes admission/pins; GC determines deletion. Those timings are assumptions, not a safety proof.

15.4 · 发布与冲突：比较父版本，保留失败编辑15.4 · Publication and conflicts: compare the parent

一次完成事务：先认旧结果，再比较父版本One completion transaction: replay before comparing the parent

对应第 2–3 帧：下列伪代码展示更新已有目标 file_id的完成事务。guard 排空同租户其他元数据写入，唯一回执键是 (tenant,owner,key)；意图含不可变会话 ID 和 manifest 摘要。会话已冻结 file/base/长度/有序清单，换序、换父版或换文件须新会话。同键不同意图拒绝，同会话即使用另一个键也只有一次结果。

Frames 2–3: this pseudocode updates an existing target file_id. The guard excludes other tenant metadata writers. Receipt uniqueness is (tenant,owner,key); intent includes the immutable session ID and manifest digest, which bind file, base, size and ordered blocks. Changed order, base or file requires a new session. Reject changed intent under one key; one session has one result even with another key.

complete(auth, session_id, request_key, manifest_digest):
  // All helpers and logical row keys are scoped to authenticated auth.tenant.
  intent = SHA256(canonical(auth.tenant, auth.user, session_id, manifest_digest))
  begin Metadata transaction:
    SELECT tenant_guard WHERE tenant_id=auth.tenant FOR UPDATE
    prior = Receipt[auth.tenant, auth.user, request_key]
    if prior exists:
      require prior.intent_digest == intent else KEY_REUSED
      return COMMIT_AND_REPLY(prior.minimal_status) // no manifest or URLs
    s = require_owned_session(auth, session_id)
    require s.manifest_digest == manifest_digest else INTENT_CHANGED
    if s.result exists:
      INSERT Receipt(auth.tenant, auth.user, request_key, intent, s.result)
      return COMMIT_AND_REPLY(s.minimal_status)
    require s.state == OPEN and s.expires_at > db_now() else EXPIRED
    require current_write_acl(auth, s.file_id) and not File[auth.tenant,s.file_id].deleted
    require all_REUSE_proofs_still_readable(auth, s)
    require every ordinal has a pin to a READY matching generation else INCOMPLETE
    require File[auth.tenant,s.file_id].head == s.base_version else PRECONDITION_FAILED_412
    require used_bytes + s.size <= quota_bytes else QUOTA_EXCEEDED
    v = checked_add(s.base_version, 1)
    INSERT Version(auth.tenant, s.file_id, v, s.immutable_manifest)
    INSERT VersionBlock(auth.tenant, s.file_id, v)
      SELECT ordered generations FROM SessionBlock[auth.tenant,s.id]
    UPDATE File SET head=v
      WHERE tenant_id=auth.tenant AND id=s.file_id AND head=s.base_version
    require affected_rows == 1
    UPDATE tenant_guard SET used_bytes=used_bytes+s.size,
                            change_head=checked_add(change_head,1)
      WHERE tenant_id=auth.tenant
    seq = TenantGuard[auth.tenant].change_head
    INSERT Change(auth.tenant, seq, s.file_id, v); INSERT Outbox(auth.tenant, seq, hint_only)
    INSERT Receipt(auth.tenant, auth.user, request_key, intent, s.file_id, v, seq)
    UPDATE Session SET state=COMMITTED, result=(v,seq)
      WHERE tenant_id=auth.tenant AND id=s.id
    DELETE SessionBlock WHERE tenant_id=auth.tenant AND session=s.id
    COMMIT
  return SAVED(v, seq)
  // All failures roll back; unknown COMMIT outcome retries the same key.

没有跨存储事务：所有外部字节早已存好，完成事务只检查同库 READY/pin/ACL，挂版本引用、改 head、计配额、写 change/outbox/回执、关闭会话一起提交。所有 REUSE 证明在锁内重查读权，防 pin 后源权限被撤销。任意检查失败整笔回滚，候选和会话仍待处理。全量保留版本的逻辑长度计配额，所以这里加 s.size；清历史时才减账。

同键并发只有一个新提交。成功后 ACK 丢失，重试先返回原最小回执，不能因为 head 已是 8 再报 412；客户端必须先查询未知结果，再决定冲突另存。最小回执只返回调用者自己提交的 version/seq/status，不含 manifest 或 URL，即使后来撤权或会话到期仍可查；任何内容读取、新提交都检查当前 ACL。回执与会话终态本例不 GC，不能仅用“客户端只重试 24 h”删除服务端去重证据。

No cross-storage transaction: bytes already exist. Completion checks same-database READY/pin/ACL state, creates version references, advances head, charges quota, writes Change/Outbox/Receipt and closes the session atomically. Recheck read rights for every REUSE proof under the lock. Any failed check rolls everything back, preserving candidates for retry. Retained logical versions charge their full size, so add s.size; pruning later releases that charge.

Concurrent retries make one new commit. A lost success ACK replays its receipt before checking parent=7 against head=8; query unknown status before creating a conflict copy. Minimal replay returns only the caller’s own version/seq/status, without manifests or URLs, even after revocation/session expiry. Content reads and new commits check current ACL. This example retains receipts and terminal session state; a client’s 24 h retry policy cannot justify deleting dedup evidence.

两个 parent=7：失败编辑另存，不猜二进制合并Two parent=7 writers: preserve the losing edit

A 先提交 v8，B 的原子父版比较失败。以强 If-Match 表达时，本章选择 412；RFC 9110 要求条件不符时不执行该修改，也允许识别已成功请求后回成功。[7] 业务 JSON 版本协议可另定义 409，别混层。hash 命名字节的 content-addressable storage，与比较 head 的 compare-and-swap 都叫 CAS，却解决不同问题。

第 4–5 帧另建 f99，head 从 1 开始；新建操作用独立、持久幂等键，并在 guard 事务内申请名称、重查目标目录权限/配额、转入同一 owner 的仍有效已核验 pins，写日志和回执。重复请求必须回同一个 f99，不能每次超时多一份。此创建/移动接口未在上段展开。删文件的 tombstone、重命名、移动和 ACL 变更同样在 guard 下条件更新；离线旧会话不得无条件复活删除文件。未上传字节仍靠客户端本地持久保存。

A commits v8 first; B’s atomic parent condition fails. This chapter chooses 412 for strong If-Match. RFC 9110 forbids applying a false condition and permits success for a recognized already-applied request. [7] A JSON version protocol may define 409 separately. Content-addressable storage names bytes; compare-and-swap advances head, despite sharing the abbreviation CAS.

Frames 4–5 create f99 at head=1. Creation uses a separate durable key and one guard transaction for name allocation, current destination-directory permission/quota, transfer of the same owner’s still-live verified pins, log and receipt. Retries return the same f99. That create/move API is not expanded above. Tombstones, renames, moves and ACL changes likewise use guarded conditional updates. Offline sessions must not resurrect deleted files unconditionally; unuploaded bytes still require local persistence.

15.5 · 多端同步：通知可丢，变更日志不能丢15.5 · Sync: lossy hints, durable change history

变更编号必须反映提交顺序Change positions must follow commit order

第 1 帧 event 102 已和 v8 提交。每个改变目录/版本/可见性的事务持 guard，更新普通 change_head 行再插 Change/Outbox，回滚时编号也回滚。后一个事务只能在前一个结束后分号，所以不会出现“103 已可见，102 晚提交却被游标跳过”。不能换成事务外 nextval：数据库 sequence 原子分号不等于提交顺序，abort 也不收回号。[11]

Relay 只释放已提交 outbox，获得通知系统持久接受后再标已发；发送后标记前崩溃会重复。通知系统到设备允许丢失/重复，设备周期拉日志兜底。outbox 消除数据库与直接推送的双写窗口，不使网络恰好一次。[8]

Frame 1’s event 102 committed with v8. Each directory/version/visibility mutation holds the guard and updates the ordinary change_head row before Change/Outbox insertion; abort rolls the counter back too. A following transaction allocates only after its predecessor ends, preventing visible 103 from causing a later-committing 102 to be skipped. External nextval is unsuitable: atomic sequence allocation is not commit order, and abort does not reclaim values. [11]

Relay releases committed outbox rows and marks sent after durable notification-system acceptance. Crash after publish but before marking can duplicate. Device hints may be lost/repeated; periodic log pull repairs them. Outbox closes the database/direct-push dual-write gap without providing exactly-once transport. [8]

changes(auth, cursor, bound_or_empty, acl_epoch):
  // Guard values, membership, epoch and floor are for auth.tenant only.
  begin short Metadata transaction:
    SELECT tenant_guard WHERE tenant_id=auth.tenant FOR UPDATE
    require current_membership(auth)
    require acl_epoch == current_acl_epoch(auth) else RESET_REQUIRED
    require retention_floor <= cursor <= tenant_guard.change_head else RESET_REQUIRED
    H = tenant_guard.change_head if bound_or_empty is NONE else bound_or_empty
    require cursor <= H <= tenant_guard.change_head
    rows = SELECT Change WHERE tenant_id=auth.tenant AND cursor < seq AND seq <= H
      ORDER BY seq LIMIT 100
    // Walk raw rows, then authorize; do not paginate the filtered result.
    visible = currently_authorized_events_or_removal_markers(auth, rows)
    next = rows.last.seq if rows else H
    COMMIT
  return (visible, next, H, acl_epoch)
  // Token binds tenant,user,H,epoch; client cannot supply another scope.
  // Persist received work + next together locally. applied_cursor advances
  // only after the full returned prefix has been applied or safely omitted.

对应第 4 帧：第一次取已提交水位 H，之后分页固定 H，按原日志每页 100 条后再过滤授权，next 是最后扫描位置；空可见页不等于已经到尾。token 由服务端绑定用户、租户、H 与 ACL epoch，不能由客户端改 scope。ACL 变化递增租户可见性 epoch，旧页明确 RESET_REQUIRED；新授权也不能藏在已扫描的旧位置。这个简化会让无关设备也重建，可用更细权限日志优化。

本例数字 cursor 是教学协议。Google Drive 提供保存 page token 后检索 changes 的公开机制，不说明 opaque token 内部就是整数。[9] 其 changes 通知也无文件内容，仍需读取变更。[10] 超过保留 floor 时，保留本地未提交编辑，获取同一快照边界的目录与结束 H再补之后的日志；快照的多页清单须冻结并受读取 pin 保护，不能扫描活目录后直接跳到当前游标。

Frame 4: first obtain committed H, then page within that bound. Scan 100 raw log rows before authorization filtering; next is the last scanned position, so an empty visible page does not imply completion. Server-bound tokens include user, tenant, H and ACL epoch. ACL changes increment tenant visibility epoch, forcing old pages to RESET_REQUIRED; new grants cannot hide behind a previously scanned position. This simple policy also resets unaffected devices; finer permission logs can optimize it.

The integer cursor is a teaching protocol. Google Drive exposes stored page tokens for retrieving changes, without documenting integer token internals. [9] Its changes notifications omit file contents and require later reads. [10] Below the retention floor, preserve unsent edits and obtain a directory snapshot and H from the same snapshot boundary, then replay later history. Freeze and read-pin paged snapshots instead of scanning a changing directory then jumping to the current cursor.

本地替换和游标之间用可恢复顺序闭合Close the local replace/cursor gap with recoverable ordering

第 5 帧只取缺的 hD，按 manifest 顺序重组、核长度/摘要；先写临时文件并持久化，同文件系统 rename 替换、持久化目录，再写本地状态和连续 applied_cursor。文件系统 rename 与本地数据库不是一个事务：先把事件/next/目标版本记入持久待办，替换后标完成。替换后掉电而游标未写，只会重做；掉电恢复扫描待办与目标版本，不能只看内存。具体 fsync/rename 保证取决于 OS/文件系统，本例未实现设备存储层。

同一 file_id 串行应用并防旧版回滚；本地有未提交编辑时先保留候选，不让远端替换覆盖它。并发下载只在所有较早事件完成或经授权安全省略后推进连续水位。新签 manifest/URL 重查 ACL，签名 URL 为短期 bearer capability，应用层撤权停止续签但不收回已保存字节；已签地址的剩余访问窗口见存储策略。[12] 立即阻止后续读取需在线授权与在途请求屏障，不是只改 ACL 一行。

Frame 5 fetches only hD, reconstructs manifest order and verifies lengths/digests. Persist a temporary file, rename on the same filesystem, persist its directory, then update local state and the contiguous applied_cursor. Filesystem rename and the local database are not one transaction: persist event/next/target work first and complete it after replacement. Crash after replacement but before the cursor causes replay. Recovery inspects durable work and target versions rather than memory. Actual fsync/rename guarantees depend on OS/filesystem; the device storage layer is not implemented here.

Serialize application per file_id and reject rollback to an older version. Preserve unsent local edits before remote replacement. Parallel downloads advance only a fully completed or safely omitted authorized prefix. Manifest/URL grants recheck ACL. Signed URLs are short-lived bearer capabilities: application revocation stops new grants but cannot retract saved bytes, and issued grants have a storage-policy access window. [12] Immediate denial needs online authorization and an in-flight request barrier, beyond an ACL row update.

15.6 · 回收：共享字节不能跟着单个文件直接删15.6 · Reclamation: shared bytes outlive individual files

mark 找候选，DELETING 才关闭采用竞态Mark finds candidates; DELETING closes the adoption race

删除先在 guard 事务里写 tombstone 和日志。只要当前版、30 天保留历史、回收站、冲突副本仍有效，它们的 VersionBlock 就是根；活跃会话/读取 pin 也保护 generation。先 mark 可以慢慢扫，但最终删除前必须在 guard 内重新查完整权威引用，不能相信旧扫描或对象年龄。

48 h grace 只给失败恢复时间，不提供互斥。第 3 帧的 fence 具体是把候选 generation 持久置 DELETING，同时落 DeleteJob；所有采用/完成都要求 READY。若 pin 先赢，GC 看到保护拒删；若 GC 先赢，新 pin 拒用旧 generation。锁不跨外部 DELETE，其他 generation 仍能发布。

Deletion first commits a guarded tombstone and change. VersionBlock roots cover current versions, retained history, trash and conflict copies; live sessions/read pins also protect generations. Slow marking can find candidates, but final deletion must recheck complete authoritative references under the guard, never trust an old scan or object age.

Grace of 48 h gives recovery time, not exclusion. Frame 3’s fence durably changes the candidate generation to DELETING and writes DeleteJob; every adoption/completion requires READY. If pinning wins, GC sees protection and refuses. If GC wins, new pins reject the old generation. No lock spans the external DELETE; other generations can publish.

fence_candidate(tenant, generation):
  // Trusted GC worker scope; every helper binds this tenant, never bare IDs.
  begin Metadata transaction:
    SELECT tenant_guard WHERE tenant_id=tenant FOR UPDATE
    g = BlockGeneration[tenant, generation]
    require g.state in {READY, ORPHAN, UPLOADING}
    require g.age >= grace and not live_upload_attempt(g, db_now())
    require no_retained_VersionBlock(g) and no_active_session_or_read_pin(g)
    UPDATE BlockGeneration SET state=DELETING
      WHERE tenant_id=tenant AND generation=g.generation
    INSERT DeleteJob(tenant, g.generation, g.exact_object_key) ON CONFLICT DO NOTHING
    COMMIT

sweep(job):
  job = require_durable_job(job.tenant, job.generation)
  // Outside the DB transaction; retries always target this physical key.
  result = Object.DELETE(job.exact_object_key, version_id=job.version_if_enabled)

      WHERE tenant_id=job.tenant AND generation=job.generation
    UPDATE DeleteJob SET complete=true
      WHERE tenant_id=job.tenant AND generation=job.generation
    COMMIT

  // Identical content can enter a fresh generation and be adopted normally.

对应第 4 帧：DeleteJob 唯一键为 (tenant,generation)，固定精确物理 key，超时只重试旧目标。新上传同摘要用新 generation；旧 DELETE 即使晚到也删不到新对象。DELETING/DELETED 永不回 READY，不因 TTL 清除终态后复用物理 key；对象若开启版本化，删除还须指定精确 version ID，普通 DELETE 可能只加 delete marker。[13]

grant 先登记 UPLOADING attempt，其租约与会话 expiry 参与同一 guard 检查；过期迟到 PUT 不能重新发布死 generation，孤儿扫描继续删除。读取 pin 也必须覆盖已发 URL 和有界在途读取，下载会话排空后才释放；不能把 URL 到期直接当成全部在途 GET 结束。S3 可允许到期前开始的下载继续。[12] 本例只给 GC 的元数据判定契约，未实现下载租约排空。

Frame 4: DeleteJob is unique by (tenant,generation) and targets one exact physical key. Unknown deletion retries that target. Reuploading identical content uses a fresh generation, so a delayed old DELETE cannot remove the new object. DELETING/DELETED never return to READY; terminal expiry never permits physical-key reuse. In versioned storage, delete exact version IDs: an ordinary DELETE may add only a delete marker. [13]

Grants first register UPLOADING attempts whose leases/session expiry share guarded checks. Late PUTs cannot republish dead generations; orphan cleanup retries. Read pins must cover issued URLs and bounded in-flight reads, releasing only after download-session drain. URL expiry alone does not finish every active GET: S3 can continue a download started before expiry. [12] This example specifies the GC metadata contract without implementing download-lease draining.

Failed GC costs space; incorrect GC loses content. Without complete roots, the guard or exact-generation evidence, retain the candidate. COW does not force one-version storage cost: ten full-block rewrites still need 10×12=120 MiB. Set retention age/count and logical quotas together.

追问与翻车点：把限制说成可验证的行为Follow-ups and failure-prone answers

展开跨地域、热门分享和缩短历史的追问Expand regional, hot-sharing and retention follow-ups

“为什么不一开始做跨地域双活？”先问单地域故障时的恢复目标；元数据强一致 head 若跨洋同步，会增加写延迟，异步复制则故障切换可能丢最近提交。字节多地域复制不自动解决目录竞争，两个地域都接同一 file_id 写入需要额外仲裁或冲突语义。把恢复目标和允许丢多少时间内的提交写清，再讨论扩展；本章逻辑 Primary 没有承诺跨地域零丢失。

For multi-region active-active, establish recovery targets first. Synchronous metadata heads add intercontinental latency; asynchronous replication can lose recent commits on failover. Replicating bytes does not resolve directory races; concurrent regional writers need arbitration or conflict semantics. State the tolerated loss window before extending the design. This chapter’s logical Primary does not promise zero-loss regional failover.

“分享热门文件怎么办？”下载仍走授权的对象路径，可以按不可变块或文件导出物加缓存，但私有内容要把权限和短期地址的生命周期算进去。用户私有同步通常不是公开视频播放模型，不能无条件把所有对象放进共享 CDN。对象存储热点、单租户查缺风暴、巨型目录和同一文件的竞争分别扩展；别让 231 次文件保存这个平均数掩盖某一热文件的局部瓶颈。

For popular shared files, downloads stay on authorized object paths; cache immutable blocks or exports with permission and grant lifetime semantics. Private sync is not automatically public video distribution. Scale storage hot spots, tenant lookup storms, huge directories and contention on one file separately. The average of 231 file saves/s can hide a local hot-file bottleneck.

“空间紧了能不能马上缩历史？”先把保留策略改成一次元数据事务并产生可补拉变更，再让 GC 按新根集合回收；不能直接按对象年龄删。用户正在查看旧版时可以持有短期读取租约，租约保护边界要和下载授权一致。版本、配额、回收站、冲突副本各自对用户可见，后台省空间不应让已经显示可恢复的旧版突然成为损坏文件。

When shortening history, first transactionally change retention metadata and expose relevant changes, then reclaim from the new roots; do not delete by object age. A historical reader may hold a short read lease aligned with download authorization. History, quota, trash and conflict copies are user-visible contracts; background space savings must not silently corrupt versions advertised as recoverable.

收尾：沿四个确认点复述Close: explain four confirmation points

用约 231.5 次文件保存/s、约 1.5 万峰值块 PUT/s、约 463 Gb/s 区分请求和字节。随后依次说：可信对象 → 受保护 pin → 条件版本提交 → 设备连续应用。hA/hC 共享不授予读权，父版本 CAS 不替代完整性，通知不替代日志，宽限期不替代 generation 栅栏。重点练 ACK 丢失、两个 parent=7、撤权与迟到 DELETE 四条反例。

Distinguish about 231.5 file saves/s, 15K peak block PUTs/s and 463 Gb/s. Then explain trusted objects → protected pins → conditional version commit → contiguous device application. Shared bytes grant no read rights, parent CAS does not verify integrity, hints do not replace history, and grace does not replace generation fencing. Rehearse lost ACKs, two parent=7 writers, revocation and delayed DELETEs.
