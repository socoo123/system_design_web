粗略估算Back-of-the-envelope estimates

约 25 分钟 · 前置：Ch01、Ch02 · 从假设推到峰值和容量，再检查故障时是否够用~25 min · after Ch01, Ch02 · assumptions → peak → budget → failure check

本章要点：用估算为设计决定提供依据Core: an estimate must change a decision

  • 先说清计算口径。从活跃用户数算出每天的请求数，再推导峰值速率。存储要看每天新增多少数据，吞吐能力则要按峰值规划。
  • 再分配容量预算。分别写清单机的基准能力、计划使用的比例，以及发生故障后仍要达到的目标。读写若共用资源，要先把两者的工作量加起来，再向上取整。
  • 最后用反例检查。少一台实例、缓存完全不可用，或对象变大时，原来的方案还能承受吗？找出最先超出预算的环节。
  • Normalize inputs. Users become requests, then peak rates; daily totals size storage, peaks size throughput.
  • Set budgets. Separate baseline capacity, utilization target, and failure target; include writes before rounding up.
  • Try a counterexample. Lose an instance, lose the cache, or increase object sizes: which budget breaks first?

1 · 先约定单位和计算假设1 · Fix units and teaching assumptions

本章用一个信息流接口（Feed API）串起估算过程。业务量、峰值系数、单机能力和缓存命中率都是为练习设定的假设。我们先用数量级判断架构方向，再用精确算式确定台数，尤其要留意接近容量上限的情况。图中按一天 100,000 秒做白板口算；确定最终配置时，统一按一天 86,400 秒复算。

One Feed API carries the examples. All workload, peak, capacity, and hit-rate figures are teaching assumptions, not production data. Use magnitude to choose architecture and exact arithmetic near thresholds. The retained animations use 100,000 seconds/day for mental math; final sizing uses 86,400.

2 · 从峰值算台数：分别检查正常运行和少一台的情况2 · Peak to instances: separate normal and N−1

先看图中只计算读取的白板估算。图里的 10 台实例在少一台后，负载会达到剩余基准能力的约 67%。这相当于故障时放宽使用比例，已经超出了原来的 60% 预算。后面会按精确日秒数，把共用资源池的读写一起算进去：一天取 100,000 秒会把 QPS 低估 13.6%，写流量占比小也不能直接略去。

The animation is a read-only mental estimate. Ten boxes and 67% illustrate relaxed failure utilization, not a promise to preserve 60%. Using 100,000 seconds understates QPS by 13.6%; even small writes count in a shared budget.

现在按精确日秒数计算完整需求。读峰值为 200,000,000/86,400×3 ≈ 6,944.44 次/秒，写峰值为 10,000,000/86,400×3 ≈ 347.22 次/秒。假设读写成本都为 1，合计峰值工作量 P ≈ 7,291.67 个工作单位/秒。每台基准能力为 C = 1,000，计划使用比例为 u = 0.6，因此每台预算 C×u = 600 个工作单位/秒。

正常运行需要 N = ceil(P/600) = 13 台，这里的 ceil 表示向上取整。如果要求少一台后仍使用同样的预算，就必须满足 (N−1)×600 ≥ P，因此需要部署 N = 14 台。下面把几种计算口径放在一起，方便比较。

Exact path: read peak=200M/86,400×3≈6,944.44/s; write peak≈347.22/s. Equal-cost total P≈7,291.67 work units/s. Per-instance budget C×u=1,000×0.6=600. Normal N=ceil(P/600)=13. To preserve the budget after losing one instance, (N−1)×600≥P, so deploy N=14.

用 13 台检查一次故障。正常运行时，总预算为 13×600 = 7,800，能够覆盖峰值；少一台后只剩 12×600 = 7,200，比 7,291.67 少了约 91.67。剩余实例的基准能力虽然还有 12,000，但这不能说明 60% 的规划目标仍然达成。部署 14 台后，少一台还剩 7,800 的预算，才足以覆盖峰值。

如果允许同时有 f 台实例不可用，可以按 N = ceil(P/(C×u))+f 计算。“再加一台”只覆盖单实例故障；整可用区失效、负载集中到热点，以及发布和故障同时发生，都需要另行建模。

Counterexample: thirteen boxes budget 7,800 normally, but only 7,200 after one loss, short by 91.67. Spare baseline capacity of 12,000 does not satisfy the 60% target. Fourteen leave 7,800 after one loss. For f unavailable instances, N=ceil(P/(C×u))+f; one spare does not cover a whole zone, skew, or concurrent rollout and failure.

单机基准 C = 1,000，实际应在指定硬件、请求组合和延迟目标下测量得到；本章先用假设继续推导。60% 表示计划使用基准能力的比例，也不能直接当作 CPU 利用率。如果一次写入的成本相当于 5 次读取，就要按 QPSread+5×QPSwrite 汇总工作量，再分别检查 CPU、网络、内存和下游依赖。Google SRE 的 Handling Overload 解释了为什么只看 QPS 无法反映不同请求的成本。

C=1,000 should be measured for a specific request mix, hardware, and latency target; here it is assumed. The 60% is a planning fraction, not automatically CPU utilization. If a write costs five reads, use QPSread+5×QPSwrite, then check CPU, network, memory, and dependencies separately. Google SRE’s Handling Overload explains the limitations of uniform QPS.

3 · 用代码实现精确取整和故障余量计算3 · Runnable implementation: exact ceilings and budgets

下面是一个使用 Java 17 标准库的可运行示例，展示了计算部署台数的核心方法。输入中，每天的工作量 dailyWork 已按读写成本统一为工作单位；整数峰值系数 peakFactor 用来把平均需求放大到峰值；单机基准 unitQps 也必须使用相同的工作量单位。计划使用比例 utilizationPercent 取 1–100 的整数百分比，failures 表示同时不可用的实例数。方法最后返回需要部署的台数。

中间计算使用 BigInteger，避免乘法溢出和浮点数造成的向上取整误差。输入不合法时抛出 IllegalArgumentException；计算结果超出 int 范围时抛出 ArithmeticException。

This is the core of a Java 17 standard-library example. dailyWork is cost-normalized daily work, peakFactor an integer multiplier, unitQps the matching per-instance baseline, utilizationPercent a planning percentage from 1–100, and failures the simultaneously unavailable instance count. It returns deployed instances. BigInteger avoids intermediate overflow and floating-point ceilings; invalid inputs throw IllegalArgumentException, and counts outside int throw ArithmeticException.

// dailyWork is cost-normalized work units, not arbitrary mixed QPS.
static int instances(long dailyWork, int peakFactor, long unitQps,
                     int utilizationPercent, int failures) {
    if (dailyWork < 0 || peakFactor < 1 || unitQps <= 0
            || utilizationPercent < 1 || utilizationPercent > 100
            || failures < 0) {
        throw new IllegalArgumentException("invalid capacity assumption");
    }
    if (dailyWork == 0) return 0; // no minimum warm pool in this model
    BigInteger numerator = BigInteger.valueOf(dailyWork)
            .multiply(BigInteger.valueOf(peakFactor))
            .multiply(BigInteger.valueOf(100));
    BigInteger denominator = BigInteger.valueOf(86_400)
            .multiply(BigInteger.valueOf(unitQps))
            .multiply(BigInteger.valueOf(utilizationPercent));
    BigInteger[] qr = numerator.divideAndRemainder(denominator);
    BigInteger survivors = qr[0].add(qr[1].signum() == 0
            ? BigInteger.ZERO : BigInteger.ONE); // exact ceiling
    return survivors.add(BigInteger.valueOf(failures)).intValueExact();
}

本例每天共有 2.1 亿个等成本工作单位，调用 instances(210_000_000,3,1000,60,0) 返回 13；把 failures 设为 1，则返回 14。计算沿用了第一组动画的“每日请求数 → 峰值 → 单机预算”过程，同时改用精确日秒数，并把写入成本计入总量。

零负载时返回 0，模型没有设置最小热备实例池。方法也不直接接受小数成本或小数峰值系数；需要先用共同的整数单位归一化，并验证这样得到的成本模型。这段代码验证的是算术，实际吞吐、少一台后的流量切换速度，以及服务目标能否达成，仍需另外验证。

instances(210_000_000,3,1000,60,0) returns 13; failures=1 returns 14. It follows deck one’s daily-demand→peak→budget steps, with exact day length and write cost. Zero demand returns zero, excluding a minimum warm pool. Fractional costs/multipliers are not directly supported; normalize into common integer units and validate that model. This verifies arithmetic, not throughput, failover speed, or SLOs.

完整示例见 CapacityEstimate.java，其中包含正常输入、取整阈值、非法输入和故障容量不足的检查。先运行 javac --release 17 -d /tmp/ch03-java examples/ch03/CapacityEstimate.java 编译，再运行 java -cp /tmp/ch03-java CapacityEstimate。

Complete normal, threshold, invalid-input, and failure-capacity checks: CapacityEstimate.java. Run javac --release 17 -d /tmp/ch03-java examples/ch03/CapacityEstimate.java, then java -cp /tmp/ch03-java CapacityEstimate.

4 · 估算带宽：先看字节实际经过哪条链路4 · Bandwidth: charge bytes to the actual path

计算带宽时，先得到每秒字节数（B/s），再乘 8 换成每秒比特数（bit/s）。图中继续使用白板读峰值 6,000 次/秒；换成精确速率时，这些带宽结果都要乘 100,000/86,400 ≈ 1.1574。还要分清两条路径：JSON 经过应用服务，图片则由 CDN 返回客户端。分别计算整层的出口总量和每台实例的出口，才能判断压力落在哪里。

Write B/s first, then multiply by eight for bit/s. The diagram keeps 6,000 reads/s; exact rates multiply by 100,000/86,400≈1.1574. Separate JSON from media and aggregate from per-instance traffic; CDN bytes do not traverse App.

这些结果只计算响应体净荷，还没有加入 HTTP/TLS 开销、重试、复制、写请求，以及负载分配不均带来的影响。960 Mb/s 已经接近 1 Gb/s 链路的标称速率，不能因此认为余量足够；按精确读负载计算，净荷本身就约为 1.111 Gb/s。

还要分清带宽与延迟。在 1 Gb/s 链路上发送 20 KB 数据，理想情况下需要 20,000×8/10⁹ = 0.16 ms。这只是把这些字节发送出去的时间，不是网络往返时间（RTT），也不是整次请求的延迟。

Boundary: these are response-body payloads, excluding HTTP/TLS, retries, replication, writes, and skew. 960 Mb/s near a nominal 1 Gb/s link is not comfortable headroom; exact read payload alone is about 1.111 Gb/s. Serializing 20 KB on 1 Gb/s ideally takes 20,000×8/10⁹=0.16 ms, not an RTT or a full-request latency.

使用命中率前，要先问它统计的是请求数还是字节数。如果命中的 90% 请求都在读取小对象，而未命中的 10% 在读取大对象，字节命中率可能远低于 90%。本图明确假设字节命中率为 90%，因此回源带宽 = 媒体出口带宽×(1−字节命中率)。缓存完全冷启动时，几乎所有媒体流量都可能回源；需要通过限流，或验证预热后的容量，确认回源能否承受。

Ask what the hit-rate denominator counts. Hitting 90% of small requests while missing large objects can yield far below 90% byte hits. This diagram assumes a 90% byte hit rate: origin bandwidth=media egress×(1−byte hit rate). A cold cache can push nearly all media traffic to origin; validate capacity with admission control or warming.

5 · 估算存储：从每天新增的数据算到实际空间5 · Storage: daily growth, retention, then physical overhead

元数据的主算式是：10,000,000 新增行/天×1,000 B×365×3 = 10.95 TB。这只覆盖三份行数据。如果再假设索引、存储格式等使空间放大为 1.5 倍，并要求磁盘计划填充率不超过 70%，就需要配置合计 10.95×1.5/0.7 ≈ 23.46 TB 的空间。1.5 倍和 70% 也都是本例的教学参数。

备份、预写日志（WAL）、重建过程的临时空间，以及故障后数据能否放到剩余节点，都要另外计算。整个集群还有空闲空间，并不意味着每个分片都能用到这些空间。

Main calculation: 10M new rows/day×1,000 B×365×3=10.95 TB for three row copies. If indexes/format add a hypothetical 1.5× factor and planned disk fill is 70%, aggregate provisioned space is 10.95×1.5/0.7≈23.46 TB. Both factors are assumptions. Backups, WAL, rebuild workspace, and failure-time placement are separate; global free space is not necessarily usable by every shard.

保留 365 天也不意味着数据会无限增长。如果每天写入量恒定、到期数据及时删除，满一年后逻辑数据量会趋于稳定；如果写入量逐日增长，就要把留存窗口内每天新增的字节相加。三份副本这里只表示存储字节数，不能保证无损切换主库，因为图中的异步副本可能落后。主库确认写入、同步提交与恢复保证的区别见 Ch41。

A 365-day retention window is not unbounded growth: constant writes with timely expiration stabilize after a year. With growth, sum daily bytes inside the retention window. Three copies specify bytes, not lossless failover; the illustrated asynchronous replicas may lag. See Ch41 for acknowledgement, synchronous commit, and recovery guarantees.

6 · 估算延迟：沿关键路径计算，再验证实际分布6 · Latency: add the critical path, not an assumed SLO

下面用 Dean 在 2009 年演讲中列出的历史数量级作比较：一次内存访问约 100 ns，同机房 RTT 约 0.5 ms，机械盘寻道约 10 ms，加州到荷兰再返回（CA→NL→CA）的 RTT 约 150 ms。这些数字帮助我们判断哪些环节可能更耗时，不能用来预测现代 SSD、网络或本系统的 p99。来源为 LADIS 2009 原始幻灯片中的“Numbers Everyone Should Know”；其中不包含下面使用的 20 ms 接入 RTT，这个数值是本章另设的假设。

The animation uses historical scales from Dean’s 2009 talk: 100 ns memory access, 0.5 ms datacenter RTT, 10 ms mechanical seek, and 150 ms CA→NL→CA RTT. These distinguish magnitudes, not modern SSD/network performance or our p99. Source: original LADIS 2009 slides, “Numbers Everyone Should Know”. The 20 ms access RTT is our assumption.

沿串行路径，可以把相同口径的时间预算相加；并行执行时，则要看请求必须等待的最慢分支，再加上合并结果的成本。但各服务的 p99 不能直接相加，作为端到端 p99；95% 的缓存命中率，也推不出整体 p99 就是命中延迟。排队、延迟波动和尾部表现，要用端到端的延迟分布验证。

磁盘数量也要检查预算。如果每次未命中都需要寻道，每秒 300 次回源、单盘上限每秒 100 次，并且只计划使用 60%，就至少需要 ceil(300/(100×0.6)) = 5 块盘。这仍没有计入写入和故障余量，还不能直接用作采购数量。

Add like-for-like budgets along serial paths; parallel branches contribute the slowest awaited branch plus merge cost. Adding service p99s does not give an end-to-end p99, and 95% cache hits do not make p99 a hit latency. Validate queueing, variance, and tails end to end. If every miss seeks, 300/s at 60% of 100/s per disk requires at least ceil(300/60)=5 disks, still excluding writes and failure reserves.

7 · 估算可用性：同时检查错误预算和故障回源量7 · Availability: count failures and fallback demand

先说清服务指标（SLI）怎样统计、统计多久，以及什么算成功。本例的目标是：一天内符合统计条件的 Feed 读请求，成功比例至少达到 99.9%。服务等级目标（SLO）规定要达到什么水平，服务等级协议（SLA）还包括未达标时约定的后果。按时间统计的可用率与按请求统计的成功率是两种指标，尤其在流量不均时，不能直接互换。相关定义见 Google SRE：Service Level Objectives。

Define the SLI, window, and success condition first. Here the target is ≥99.9% successful eligible Feed reads per day. An SLO is a target; an SLA includes contractual consequences. Time availability and request success are distinct, especially with uneven traffic. See Google SRE: Service Level Objectives.

回源容量要按总量计算。95% 的命中率留下每秒约 300 次普通未命中，缓存调用错误又可能增加约 6 次。如果两者有重合，不能重复计算；假设调用错误与未命中独立，总量为 6,000×[0.001+0.999×0.05] = 305.7 次/秒。图中的约 306 次/秒是保守口算，不能只拿新增的 6 次去比较每秒 100 次的能力。

整层故障时，每秒 100 次的回源上限必须由所有 App 实例共享。分配这项预算时，还要先扣除仍在进行的写入和其他负载；如果每个实例都各自放行 100 次/秒，总量就会放大为 N 倍。

Budget total origin demand. A 95% hit rate leaves 300/s of normal misses and cache errors may add about 6/s. Avoid double-counting overlaps; with independent errors the total is 6000×[0.001+0.999×0.05]=305.7/s. About 306/s is a conservative shortcut, not a comparison of six with 100. The outage cap of 100/s must be shared across the App tier and account for writes/other work; 100 per instance multiplies it by N.

进一步检查整个缓存层不可用的情况：假设没有可用且仍有效的旧数据，每秒获准回源的 100 次请求全部成功，白板读峰值仍有每秒 5,900 次失败。若当天的 20 万次错误预算尚未使用，就会在 200,000/5,900 ≈ 33.90 秒内耗尽；改用精确读峰值，则是 200,000/(6,944.44−100) ≈ 29.22 秒。

允许使用最多 30 秒前的旧数据，只是本例的产品假设，还要求这份数据已经存在，而且使用时仍满足有效期要求。限流、合并请求和使用旧数据各自能减少一部分压力，不能仅凭这些机制就保证缓存宕机期间仍能达到 SLO。

With no cache or eligible stale value, assuming 100/s origin reads succeed, the shortcut leaves 5,900 failures/s and spends the daily budget in 200,000/5,900≈33.90 seconds. Exact reads give 200,000/(6,944.44−100)≈29.22 seconds. A 30-second stale allowance is a product assumption and requires an available, still-eligible copy; caps, coalescing, and stale data do not guarantee the SLO during cache outage.

如果一次请求必须依次访问三个依赖，而且各自的成功率都是 99.95%，只有统计口径一致、失败相互独立时，才可以相乘，得到 0.9995³ ≈ 99.850075%。如果三者的失败互不重叠，应把错误率相加，得到整体成功率 99.85%；“互不重叠”与“独立”是不同条件。依赖若共享故障域，独立假设就可能不成立，因此增加副本或地域也不能自动多出几个 9。依赖独立性的讨论见 Implementing SLOs。

For three required serial dependencies each at 99.95%, multiplication gives 0.9995³≈99.850075% only with matching request scope and independent failures. Mutually exclusive failures instead sum to 99.85%; they are not independent. Shared failure domains break independence, so replicas or regions do not automatically add nines. See Implementing SLOs.

如果另外按 365 天的时间可用率定义指标，99.99% 允许的不可用时间为 0.0001×365×24×60 = 52.56 分钟/年；99.9% 则允许 8.76 小时/年。这些是时间指标下的预算，不能当作前面请求失败所对应的实际停机记录。来源见 SRE Availability Table。

Under a separate 365-day time-availability definition, 99.99% allows 0.0001×365×24×60=52.56 minutes/year; 99.9% allows 8.76 hours/year. These are time budgets, not measured downtime inferred from the request failures above. See the SRE Availability Table.

8 · 换成短链服务，再走一遍估算过程8 · Transfer to short links and rehearse

把同样的方法用于 Ch09 的短链服务：假设每天创建 100 万条短链、发生 1 亿次跳转，峰值是平均值的 10 倍。跳转读峰值为 100,000,000/86,400×10 ≈ 11,574.07 次/秒，向上取到 11,600 次/秒继续规划。每台按每秒 600 个工作单位分配预算，正常运行需要 20 台；要求少一台后仍不超过同样的预算，则要部署 21 台。

如果创建和跳转共用资源池、成本也相同，还要加入创建峰值约 115.74 次/秒。重新计算后仍为正常 20 台、容忍一台不可用时 21 台。但这个结果来自复算，不能因为写入占比小就一律忽略。

Following Ch09: 1M creates/day, 100M redirects/day, 10× peak. Redirect peak=100M/86,400×10≈11,574.07/s, conservatively 11,600. A 600/s budget gives 20 instances normally, 21 for N−1. Equal-cost shared writes add about 115.74/s and still give 20/21, but recompute rather than assuming a small fraction never matters.

假设跳转响应为 500 B，按每秒 11,600 次计算，出口为 5.8 MB/s = 46.4 Mb/s；浏览器随后访问的目标网页并不经过短链服务。存储则按每天新增的映射记录计算：每条 500 B，每天 100 万条，保留 365 天，共 182.5 GB；三份共 547.5 GB，索引、备份和日志另算。这样，台数、带宽和存储三个结果就分别对应到跳转实例、出口链路和映射数据。

At 11,600/s, 500 B responses give 5.8 MB/s=46.4 Mb/s; destination pages do not traverse the short-link service. 500 B×1M/day×365=182.5 GB, or 547.5 GB for three copies, before indexes, backups, and logs. The three numbers size redirect instances, egress, and mapping storage.

面试时可以这样串起来讲：“我先列出假设和单位。每天的请求数除以 86,400，再乘峰值系数，并按请求成本汇总工作量。用它除以单机预算，向上取整得到正常台数，然后检查少一台是否还够用。带宽按字节实际经过的路径计算，存储按每天新增量、留存时间和物理开销计算。最后推演缓存完全不可用时的回源量与错误预算，并说明哪些假设还需要压测验证。”

Interview recap: “I state assumptions and units, divide daily requests by 86,400, apply peak and cost weights, then round up against the instance budget and check one failure. I charge bandwidth to actual byte paths and size storage from retained daily growth plus overhead. Finally, a full-cache-outage scenario tests origin and error budgets and identifies what needs measurement.”
