分布式唯一 IDDistributed unique IDs

本章要点：证明 ID 唯一，解释时间窗与号段Core: unique tuples, authorized time windows, durable segments

  • 说明时间戳、生成器标识和序列组成的 (timestamp, worker, sequence) 为什么不会重复，并区分位布局的容量与实测吞吐。
  • 沿着具体分支，说明时钟回拨、序列耗尽、进程重启，以及旧进程迟到返回时怎么办。
  • 用已提交的号段摆脱对墙钟的依赖，再用剩余库存除以故障后的请求速率，估算还能发号多久。
  • Prove uniqueness of (timestamp, worker, sequence) and separate layout space from measured throughput.
  • Implement rollback, exhaustion, restart, and delayed old-owner boundaries.
  • Replace wall-clock dependence with committed ranges; size outage tolerance using inventory / failover traffic.

先约定要求：生成 ID 与提交订单是两步Set the contract: minting is not business commit

本例为订单生成内部主键，要求 ID 唯一、能用 64 位正整数表示，并随时间大致递增；允许编号不连续，也就是留下空洞。教学假设是峰值每秒生成 1 万个 ID，部署两个实例。默认采用进程内的 Snowflake：每个 ID 都在本地计算，控制流程先分配互不重叠的发号空间，业务数据库则负责提交订单。

开场先问清楚，“有序”具体指什么。两台机器的时钟有偏差时，较晚到达的请求可能拿到更小的 ID。即使中心依次发出 1、2，也可能是订单 2 先提交，订单 1 最终失败。如果要求全局严格按顺序分配，或只给已提交订单分配连续编号，就需要在相应的分配或提交环节统一串行处理。另外，知道 ID 不代表拥有访问权限，外部请求仍须鉴权。

Assume internal order keys: unique positive 64-bit values, rough ordering, gaps allowed, a teaching peak of 10,000 IDs/s and two instances. Default to local Snowflake: each ID is computed locally, the control path grants disjoint spaces, and the business database commits orders.

Define ordering first. Clock skew can give a later request a smaller ID. Even central allocation of 1 then 2 cannot prevent order 2 committing before order 1 fails. Strict allocation order or gapless commit numbering requires serialization at the relevant boundary. IDs are not permissions; external identifiers still need authorization.

请求主流程：本地取号，确认订单提交后再返回Global path: mint locally, respond after order commit

第一组图的最后一帧就是整体方案：客户端（Client）经 App 调用进程内的生成器（Generator），随后由 App 向订单主库（Primary）提交订单，最后返回 201。注册中心（Registry）不参与每次发号，订单库仍在业务请求路径上。如果进程在取号之后、执行 INSERT 之前崩溃，只会留下空洞，这个号码不能回收重用。

唯一性要按字段分别证明。不同毫秒由时间戳 timestamp 区分，同一毫秒内的不同生成器由 worker 字段区分，同一生成器在同一毫秒内的调用则由受保护的序列区分。每个授权窗只能由一份状态机使用，不同进程代次使用互不相交的时间窗。本地也不能只锁住序列 sequence：比较上次发号时间 last、重置或递增序列，以及更新 last，必须在同一个串行过程里完成。

业务幂等还需要单独保证。订单行要同时保存 ID、调用者、幂等键和请求摘要。数据库通过 UNIQUE(caller, key)，让同一调用者使用同一幂等键发起的竞争请求最多提交一行。遇到重复键时，查回原 ID，并检查请求摘要是否一致；如果同一个键被用于不同内容，就返回冲突。订单已经提交、但回执丢失时，重试应返回原订单，不能因为又拿到了一个唯一 ID 就再次执行 INSERT。若幂等记录与订单分表保存，两者必须在同一事务中提交。

API 应把大整数 ID 编成十进制字符串。JSON 跨实现能精确互通的整数范围只有 ±(2^53−1)，JavaScript 的 Number 可能丢失 ID 的低位。[6]

The final frame is the overview: Client→App→in-process Generator, then App→Primary commits the order before 201. Registry is off the per-ID hot path; the order database remains on the business path. A crash between minting and INSERT leaves a gap; never reclaim the ID.

Prove uniqueness field by field: timestamp separates time slices, worker separates issuers within a slice, and the protected sequence separates calls within one worker/slice. One grant has one state machine; process generations use disjoint windows. Locking sequence alone is insufficient: last comparison, reset/increment, and last update must serialize together.

Business idempotency is separate: store ID, caller, idempotency key, and request digest on the order row. UNIQUE(caller, key) permits only one competing insert to commit. On a duplicate, fetch the existing ID and check the digest; reject key reuse with different content. After a lost commit reply, return the original order instead of inserting another freshly minted ID. Separate idempotency and order tables must commit in one transaction.

Transmit large IDs as decimal strings. JSON interoperable exact integers are limited to ±(2^53−1); JavaScript Number may lose low bits. [6]

位预算：能编码多少，不代表每秒能执行多少Bit budget: encodable space is not execution throughput

拼接公式为 ID = (t << 22) | (worker << 12) | seq，其中 t=now−epoch。历史 Snowflake 把 10 位身份字段拆成 5 位机房标识和 5 位 worker 标识；本章将它们合并，编码预算不变。[1] 输入必须满足 0≤t<2^41、0≤worker<1024、0≤seq<4096，不能用掩码把越界问题隐藏起来。符号位为 0 只能保证非负，三个字段全为 0 时，ID 仍然是 0。因此，本章可运行示例不使用 t=0 的整个时间片，而是从 t≥1 开始发号，以满足 ID 必须为正数的要求。

Pack ID = (t << 22) | (worker << 12) | seq, where t=now−epoch. Historical Snowflake splits the ten identity bits into five datacenter and five worker bits; combining them preserves the budget. [1] Require 0≤t<2^41, 0≤worker<1024, and 0≤seq<4096; never hide invalid input with masks. A zero sign guarantees nonnegative values, not positivity: the all-zero tuple is zero. The runnable example reserves the entire t=0 slice and starts at t≥1.

One survivor must meet latency goals across CPU, lock waits, GC and the order database. Never wrap t=2^41 to zero; the largest legal tuple is Long.MAX_VALUE.

生成器生命周期：先持久预留时间窗，再本地发号Worker lifecycle: durably reserve time before minting

只说“租约 30 秒，重启后读取 H”，协议还不完整：租约到期时，暂停的旧进程可能尚未停止；如果只偶尔保存 last，也会遗漏上次保存之后已经发出的时间戳。本章采用不可回收的时间窗，授出后不再重新分配。Registry 为每个 worker 保存一行 (generation, high_exclusive)。新进程领取 [L,H)，其中 L 不小于历史 H；只有 H 可靠提交后，进程才能使用这个窗口。H 是排他上界，即窗口不包含 H，并不表示最后一个已发号的毫秒。

下面的伪代码通过权威数据库同一行上的事务锁，保证领取和续窗的原子性。并发操作由 FOR UPDATE 串行处理；generation 一旦变更，旧进程就不能再续窗。已确认的记录必须在所有允许的故障切换后仍然保留，因此不能把丢失高水位的异步副本提升为主库。

实例崩溃后，要领取新窗并弃用旧窗。如果授权响应的结果不确定，也要弃用这次结果，重新领取，不能按旧 request_id 找回授权后重置序列。每份已提交的授权结果，只允许一个活进程接受一次；复制虚拟机内存或生成器对象都会破坏这个前提。

“Thirty-second lease, read H on restart” is not a protocol: expiry cannot stop a paused process, and occasional last snapshots miss issued timestamps. This design uses non-reclaimable time windows. Registry stores one (generation, high_exclusive) row per worker. A new process receives [L,H), with L≥historical H, and consumes only after H durably commits. H is an exclusive upper bound, not the last issued millisecond.

The pseudocode serializes claims/extensions using a transaction row lock at the authoritative database. Generation changes reject old extensions. Every permitted failover must preserve confirmed records; a stale asynchronous replica is unsafe. On restart, reserve a fresh window and discard the old grant. Burn ambiguous responses too; never replay an old request ID into reset sequence state. Each committed result is accepted once by one live process; VM-memory or generator cloning is forbidden.

# Registry transaction; timestamps are relative to one immutable epoch.
# windows(worker PRIMARY KEY, generation, high_exclusive)
# Preseed one row per worker 0..1023, generation=0, high_exclusive=1.
# Checked integer arithmetic: reject overflow, never wrap a generation.
# A fresh boot uses a NEW generation; it NEVER resumes a prior grant.
BEGIN
row = SELECT generation, high_exclusive FROM windows
      WHERE worker = :worker FOR UPDATE
lo = max(1, :observed_now, row.high_exclusive)
hi = lo + 30_000
REQUIRE hi <= 2^41
UPDATE windows SET generation = row.generation + 1,
                   high_exclusive = hi WHERE worker = :worker
COMMIT  # must survive every permitted failover
# Return only after confirmation; ambiguous commit => burn and reserve again.
return Grant(worker, row.generation + 1, lo, hi)

# One live generator may extend without losing last/sequence.
BEGIN
row = SELECT generation, high_exclusive FROM windows
      WHERE worker = :worker FOR UPDATE
REQUIRE row.generation == :my_generation
REQUIRE row.high_exclusive == :my_hi
new_hi = row.high_exclusive + 30_000
REQUIRE new_hi <= 2^41
UPDATE windows SET high_exclusive = new_hi WHERE worker = :worker
COMMIT
# Install hi under the SAME local lock; preserve last and sequence.
# Ambiguous extension: halt; a fresh boot obtains a fresh window.

先走正常流程，再看反例。旧窗 [1000,1030) 已经发到 (1000,7,42)，替代进程领取 [1030,1060)。如果新进程的时钟仍为 1000，它就还不能启动发号；等到 1030，才可以从 seq=0 开始。旧进程暂停后可能迟到返回 (1000,7,43)，这个 ID 数值更小，却不会与新窗重合。相反，如果恢复旧窗并把 seq 清零，就会再次发出 (1000,7,0)。代码测试专门复现了这个错误，也说明本地锁不能代替生成器身份管理。

窗宽 30,000 限定的是可使用的时间戳范围。时钟向前跳可能提前用尽窗口，停钟或回拨可能触发本地错误，进程暂停也会延后响应。因此，不能承诺断网后一定还能再发号 30 秒。重启可能要等到旧 H，频繁重启还会弃用更多未来窗口。只有同一份活状态机可以续窗，并且必须保留 last/seq；旧代次被拒绝续窗后，就不再获得新的发号空间。时间窗隔离的是 ID 的数值范围，不能保证下游拒绝旧持有者产生的业务副作用；后者需要下游隔离机制（fencing），见 Ch08。

这套时间窗协议是本章的教学设计，并非 Twitter 的内置协议。历史实现只校验传入的 worker/datacenter；Leaf 则使用持久顺序节点分配身份。[1][2] 即使采用独占部署、身份永不复用的简化方案，也仍要处理重启后时间片被重新使用，以及进程状态丢失的问题。

Normal path and counterexample: the old [1000,1030) window issues through (1000,7,42); a replacement gets [1030,1060). It cannot start at clock 1000, but may emit sequence 0 at 1030. The old process may later return (1000,7,43): smaller, yet disjoint. Replaying the old window with a reset sequence duplicates (1000,7,0). The test reproduces that error rather than treating a local lock as identity management.

A 30,000-wide window bounds timestamps only. Clock jumps consume it early, a frozen/backward clock can fail locally, and pauses delay replies. It does not promise thirty extra seconds after disconnection. Restart may wait for old H; repeated restarts burn more future windows. Extension is only for the same live state machine with last/sequence retained; a rejected stale generation gets no new space. Windows isolate ID values, not stale business side effects; downstream fencing is covered in Ch08.

This is a teaching design, not a built-in Twitter protocol. Historical code validates supplied worker/datacenter numbers; Leaf describes persistent sequential-node identity allocation. [1][2] Even a simpler exclusive-deployment/no-reuse policy must handle timestamp reuse after lost process state.

本地发号：回拨时保留序列，耗尽后等待新毫秒Implementation: preserve sequence on rollback, wait after exhaustion

下面是 可运行 Java 17 示例 的核心方法，不依赖外部库。构造器要求传入已确认提交、且只绑定单一实例的 Window，并校验 worker 与 1≤L<H≤2^41。这个例子不实现 Registry，只使用一个固定时间窗；续窗协议仅在前面的伪代码中说明。

Clock.millis() 返回相对于统一 epoch 的毫秒时间，nanos() 用于进程内的单调计时，pause() 只让出执行机会，之后仍须重新读时钟。测试会注入可控时钟；部署时应分别接入墙钟与 System.nanoTime，不能用墙钟计算等待预算。

This is the core method from the dependency-free runnable Java17 example. Construction requires a committed, single-instance Window and validates worker plus 1≤L<H≤2^41; it does not implement Registry and consumes one fixed window; extension is only specified in the earlier pseudocode. Clock.millis() is relative to the shared epoch, nanos() measures monotonic local elapsed time, and pause() merely yields before re-reading. Tests inject a controlled clock. Deployment adapters use wall time and System.nanoTime separately; wall time must not measure the wait budget.

synchronized long nextId() {
    if (halted) throw new IllegalStateException("HALTED: obtain a fresh window");
    long started = clock.nanos();
    boolean waited = false;
    for (;;) {
        long now = clock.millis();
        if (now < grant.lo() || now >= grant.hi())
            throw stop("outside committed timestamp window");
        if (last - now > 5) throw stop("rollback exceeds 5 ms");
        if (waited && clock.nanos() - started >= 5_000_000L)
            throw stop("wait budget exhausted");
        int candidate = now == last ? sequence + 1 : 0;
        if (now >= last && candidate < 4096) {
            last = now;
            sequence = candidate;
            return (now << 22) | ((long) grant.worker() << 12) | sequence;
        }
        // Small rollback or same-millisecond exhaustion: re-read, never wrap.
        waited = true;
        clock.pause();
    }
}

代码对应图中的三条处理路径。now>last 时把序列归零，now=last 时继续递增，now<last 时保留全部状态并等待。例如 last=1000、seq=42、now=998，等时钟恢复到 1000 后，必须接着发出序列 43；序列发到 4095 后，只有时间戳严格增大，才能重新从 0 开始。检测到 5 ms 等待预算已用满、回拨幅度过大或时间越出授权窗时，这个对象都会进入 HALTED 状态。恢复时要重新取得授权，不能清空旧对象的 last 后重试。

5 ms 是取得本地锁之后的检测预算，不能限制线程调度暂停、锁外排队或整个请求的延迟。调用也可能在通过校验后暂停，恢复时才返回旧 ID；即使回执晚于 H，也不会与新窗重复。synchronized 只保护当前对象的内部状态，把同一个 Window 交给第二个对象仍可能生成重复 ID，示例专门测试了这一反例。完整示例还验证了 8 个线程并发执行 4,000 次调用、4,096 个槽位耗尽、时间字段最大值，以及重启后使用新窗。

历史 Snowflake 遇到回拨会直接拒绝；同一毫秒内序列回绕时，则等待时间戳严格增大。本章在此之外采用了“小幅回拨等待、大幅回拨拒绝、超时后停用”的策略。[1] 如果改用逻辑时间，把时间固定在 last，那么 seq=42 之后也只剩 4095−42=4053 个槽位，按每秒 5,000 次发号计算，只能维持 0.8106 秒。借用未来时间戳仍须遵守持久时间窗的边界，不能靠一个反复复用的“回拨位”无限发号。

The three diagram exits: reset for now>last, increment at equality, and preserve state while waiting for now<last. With last=1000, seq=42, now=998, recovery to 1000 must emit 43. After 4095, sequence 0 is legal only at a strictly newer millisecond. Five ms of accumulated waiting, large rollback or leaving the grant halts this object. Recovery requires a fresh grant, not clearing last in the old object.

The 5 ms check starts after acquiring the local lock; it does not bound scheduler pauses, lock queues or end-to-end latency. A call paused after validation may return its old ID after H without duplicating the new window. synchronized protects one object only. Sharing its Window with another object can collide, explicitly demonstrated by the test. Tests also cover 8 threads/4000 calls, 4096-slot exhaustion, timestamp limits and new-window restart.

Historical Snowflake refuses rollback immediately and waits for a strictly newer millisecond on sequence wrap; this chapter adds small-wait/large-refuse and timeout halting. [1] Pinning logical time at last leaves only 4095−42=4053 slots, or 0.8106 s at 5000/s. Borrowing future timestamps must stay within durable grants; a “rollback bit” cannot be recycled indefinitely.

号段：提交后才能发号，库存决定故障时能撑多久Segments: reserve durably, then consume; inventory bounds outages

如果希望发号不依赖墙钟，可以改用数据库号段。账本中的 high 表示第一个尚未预留的 ID；把它从 1000 推进到 2000，就授予 [1000,2000)。下面的 PostgreSQL 17 教学事务通过同一行上的 UPDATE 排他地串行更新，再用 RETURNING 取得更新后的边界，因此相同 name 的并发事务不会领到同一段。[8] 不同 name 各自计数，只能保证各自域内唯一；要跨域唯一，就须共用一份账本，或把域标识编码进 ID。

For clock-independent IDs, reserve database ranges. high is the first unreserved ID; advancing 1000→2000 grants [1000,2000). This PostgreSQL17 teaching transaction serializes UPDATE on one row and uses RETURNING for post-update bounds, so competing transactions for one name do not receive the same range. [8] Names have separate counters; cross-name uniqueness needs one shared ledger or an encoded domain.

-- PostgreSQL 17 teaching transaction; :name and :step are driver parameters.
-- ledger(name TEXT PRIMARY KEY, high BIGINT NOT NULL CHECK (high >= 1))
-- high is the first ID not yet reserved; seed orders with high = 1000.
BEGIN;
UPDATE ledger
SET high = high + :step
WHERE name = :name AND :step > 0
  AND high <= 9223372036854775807 - :step
RETURNING high - :step AS lo, high AS hi;
-- Require exactly one returned row; retain [lo, hi) privately until COMMIT.
COMMIT;
-- Only after confirmed commit: install the range in one live allocator.
-- Timeout / lost commit reply: discard this result and reserve another range.
-- Never decrement high; after restart discard ALL old in-memory grants.

RETURNING 返回结果，不表示事务已经提交。只有确认 COMMIT 后，才能向调用方发号。超时只能说明结果未知：要丢弃这次预留结果，重新领取一个确认提交的新段，即使留下空洞也不能把 high 退回。重启后丢弃全部旧库存，不能从以前领过的号段起点重新发号。每个确认段只交给一份活分配器，本地索引递增与缓冲区切换必须在同一个临界区完成。主库 Primary 切换时，也必须保留已经确认的高水位；否则旧实例还在发号，新主库就可能把重叠区间再次授出。

图中的 Current range 和 Next range 标出的是最初授予的完整范围，并不表示剩余数量。App 1 领到 [1000,2000) 后，另一个实例可能已经领走 [2000,3000)，因此它的下一段是 [3000,4000)。估算预取库存时，只能计入已经确认的号段。第 3 帧表示后续补领失败，前面已确认的段仍可使用；到第 5 帧库存耗尽，才拒绝发号。Leaf 对双缓冲和动态调整 step 的讨论支持这一设计方向，但不意味着数据库故障时可以无限发号。[2][3]

RETURNING is not commit confirmation. Emit nothing before confirmed COMMIT. A timeout is ambiguous: discard that reservation result and obtain another confirmed range, allowing gaps; never reduce high. Restart discards old inventory instead of replaying an earlier grant from its beginning. One live allocator consumes each grant, with local increments and buffer switching in one critical section. Primary failover must preserve confirmed high-water marks or reissue ranges that old instances still consume.

Current/Next labels are originally granted ranges, not remaining counts. Another instance may reserve [2000,3000), so App1 follows [1000,2000) with [3000,4000). Count confirmed inventory only. The third frame depicts a later refill failure while previously committed ranges remain consumable; frame five rejects after exhaustion. Leaf discusses two buffers and adaptive step sizing, not unlimited availability during database failure. [2][3]

以上时间都是按均匀流量估算的理想窗口，瞬时突发会更快用完库存。加大每段的号码数 step，可以减少领段往返，却会增加崩溃时浪费的号码和空洞。App 2 先发 2000、App 1 后发 1001，两个 ID 仍然唯一。这说明号段只保证单个分配器内部递增，不能据此推导全局实时顺序或业务提交顺序。

These ideal windows assume uniform traffic; bursts exhaust inventory sooner. Larger steps reduce reservation round trips but increase crash waste and gaps. App2 issuing 2000 before App1 issues 1001 remains unique: local range order is neither global real-time order nor business commit order.

方案取舍：ID 长度、索引局部性与使用约束Tradeoffs: width, locality and consumer constraints

如果 64 位不是硬性要求，可以再比较 UUID。RFC 9562 定义的 UUID 长度为 128 位，其中 v4 有 122 个随机位，v7 则用高 48 位的 Unix 毫秒时间提供时间前缀。随机方案的唯一性是概率保证，依赖可靠的随机源；时间前缀也不能建立跨进程的严格顺序。[4] 对于规模较小、能接受每次发号都访问数据库的业务，直接使用自增也合理。Flickr Ticket 的原方案采用两台服务器，分别生成奇数和偶数，步长为 2，并非只有一台服务器。[7]

设计短码前，要先算清能表示的数值范围。62^6=56,800,235,584，而覆盖整个正数 long 域需要 11 个 base62 字符。以相对时间经过 10 年为例，按每年 365.25 天计算，t=315,576,000,000ms；仅 t×2^22≈1.324×10^18，就已大于 62^10≈8.393×10^17。早期 ID 可能更短，但直接截取后六位，不同 ID 就可能映射到同一个短码。紧凑短码的号段容量见 Ch09。

Consider UUID when 64 bits are optional. RFC9562 defines 128-bit UUIDs, 122 random bits for v4 and a high 48-bit Unix-millisecond prefix for v7. Probabilistic uniqueness needs a good random source; time prefixes do not create strict cross-process order. [4] Database auto-increment is reasonable for small workloads accepting a round trip per ID. Flickr Ticket used two odd/even servers with stride two, not a single server. [7]

Size the short-code domain. 62^6=56,800,235,584; covering every positive long needs 11 base62 characters. Ten elapsed years at 365.25 days/year give t=315,576,000,000 ms, and t×2^22≈1.324×10^18 already exceeds 62^10≈8.393×10^17. Early IDs may be shorter, but truncating to six characters destroys injectivity. See Ch09 for compact range sizing.

主键变宽后，多占多少空间Storage cost of wider keys

InnoDB 的二级索引会携带主键。[5] 本例假设有 1 亿行数据、3 个二级索引。16 字节的二进制 UUID 比 8 字节整数多 8 字节，因此主数据中的原始主键载荷增加 800 MB，3 个二级索引再增加 2.4 GB，合计 3.2 GB。这只是键载荷的差额，不是完整索引大小，尚未计入页头、填充、其他列和副本；这里比较的也是二进制 UUID，没有把 36 字符字符串当作 16 字节。插入性能仍须用真实数据测量。

InnoDB secondary indexes carry the primary key. [5] For a teaching 100M rows and three secondary indexes, a 16-byte binary UUID adds 8 bytes over an integer: 800 MB of raw primary-key payload plus 2.4 GB in secondary indexes, or 3.2 GB total. This excludes headers, fill, other columns and replicas; it does not equate a 36-character string with 16 bytes. Measure insertion performance on real data.

一分钟复盘：在前述约束下，Snowflake 可以保证唯一，并提供大致的时间顺序。本地状态机处理回拨与序列耗尽，持久保存且互不相交的时间窗避免重启后重用发号空间。如果改用号段，就用持久账本和有限库存替代对墙钟的依赖。业务幂等、提交顺序、下游隔离和 ID 唯一性，都要分别证明。

One-minute recap: Snowflake provides uniqueness and rough time ordering. Local state handles rollback/exhaustion; durable disjoint windows handle restart reuse. Segments replace the clock with a durable ledger and finite inventory. Prove business idempotency, commit order, downstream fencing and ID uniqueness separately.
