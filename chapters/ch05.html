中文

  • 用完整余数周期证明取模的重映射比例，分别算清扩容、缩容的期望迁移量。
  • 在展开的环上手算归属、环回和区间切分，解释为什么查找不沿服务器逐跳发送。

English

  • Prove modulo remapping over a full residue cycle and distinguish expected addition and removal movement.
  • Resolve ownership, wraparound and interval splits on an unfolded ring without implying network traversal.
  • Separate virtual nodes, hot keys, replication and epoch handoff, and explain what remains after computing a new owner.

开场：先说放置合同，再选分区函数Open with the placement contract

我先按缓存或 KV 的分区来答：节点有稳定名字，会任意加减，希望只改变必要的 key 归属。取模把机器数放进公式，十台加到十一台会重映射约 90.91%。环把固定 token 排序，用 key 的 hash 找顺时针下一点；旧点不动时，新增机器只拿走自己的区间。均匀随机、等容量假设下，百万 key 扩容期望迁约九万零九百零九个。虚拟节点改善区间分布并分散接管，实际迁移还要版本、复制与交接协议。

先问三个会改变设计的问题：数据是可丢缓存还是权威记录；节点是任意命名机器还是只能追加的逻辑桶；负载按 key 数、字节还是请求成本衡量。缓存换归属后可以从权威库重建，但会增加回源；权威记录必须在新位置准备好再切流量。节点只能追加时可以讨论 Jump Hash，任意下线时环更容易解释。几条澄清足够推进，不必把所有哈希变体摆上白板。

本章把 owner 定义为第一责任机器，不代表只有一份数据。复制数、读写 quorum、冲突合并留给后续 KV 章节；本章只指出它们与放置函数的接口。名称中的“一致性”指成员变化时映射扰动较小，不是读写的强一致性。Karger 等人的 1997 年论文讨论这种平滑变化，以及客户端视图不同的情况；它没有把所有成员视图自动变成同一个版本。[1]

图上的环展开成从左到右的有序点，末端环回。箭头在前四组图中表达索引顺序或归属变化，最后一组才表达通信时序。Router 是执行放置规则的路由层，可以实现在客户端库、代理或存储协调节点中；算法本身不要求另建独立服务。相同 epoch 下，用同一套规则可在本地算出目标，避免每个请求询问配置中心。

I will use cache or KV partitioning: machines have stable names, arbitrary additions and removals are allowed, and only necessary ownership should change. Modulo remaps about 90.91% when ten machines become eleven. A ring sorts fixed tokens and resolves the first clockwise token from a key’s hash. With old tokens unchanged, a newcomer takes only its intervals. Under uniform, equal-capacity assumptions, one million keys move about 90,909 in expectation. Virtual nodes improve interval distribution and spread takeover; actual migration still needs versions, copying and handoff.

Clarify disposable cache versus authoritative records, arbitrary named machines versus append-only logical buckets, and whether load means key count, bytes or request cost. Cache entries can be rebuilt but origin traffic rises. Authoritative records must be ready before routing changes. Append-only buckets make Jump Hash relevant; arbitrary removal is easier to explain with a ring. These questions are enough to proceed without presenting every variant.

Owner means first-responsible machine, not the only copy. Replication, quorums and conflict resolution belong to the KV chapter; here we identify their placement interfaces. “Consistent” refers to limited mapping disruption under membership changes, not strongly consistent reads and writes. Karger et al.’s 1997 paper discusses smoothness and differing client views, not automatic agreement on one membership version. [1]

The ring is unfolded into a sorted line with wraparound. Arrows in the first four decks mean index order or ownership transitions; the final deck shows communication. Router is a routing role implemented in a client library, proxy or storage coordinator, not necessarily a separate service. Given one epoch and one rule set, it resolves placement locally without querying a configuration center for every request.

第一笔：取模为什么会让幸存机器之间也搬家Modulo also remaps between surviving machines

固定旧编号，才能比较同一台机器Keep old IDs stable when comparing owners

先用 N=3，桶号 0、1、2 分别对应 S0、S1、S2；扩容只在尾部加 S3，旧编号不变。hash=0 始终归 S0；hash=3 从 S0 到 S3；hash=4 却从 S1 到 S0。第三条是关键：扩容需要新人接一份负载，取模却让旧机器之间也搬数据。若把服务器列表重新排序，同一个桶号还可能换物理机，那是额外扰动，不能混进余数证明里。

3 与 4 的最小公倍数为 12，所以枚举 hash 0–11 就能看完整周期。要让 h%3=h%4=r，r 只能是 0、1、2，且 h−r 同时是 3 和 4 的倍数。在这个周期只有 h=0、1、2 成立，其余 9 个重映射，迁移比例 9/12=75%。旧稿的 8 个 key 缩容例子只有局部样本，能展示问题，却不能证明一般迁移比例。

同理，n 与 n+1 互质，周期为 n(n+1)；相等余数只有 n 个，所以保留比例 n/[n(n+1)]=1/(n+1)，移动比例 n/(n+1)。A1 的 10→11 因此移动 10/11≈90.91%，百万 key 约 909,091 个换机器。前提是 hash 在这个周期近似均匀，且原桶编号不变；小样本和偏斜 key 集未必得到这个百分比。

取模 O(1)、内存小，固定 worker 池完全可以用它。会动态变化的缓存集群更在乎暖数据和归属稳定性，才需要另选放置函数。取模变更也不会在逻辑上保证每个请求都 miss：旧值可能有重复副本，新位置也可能预热。它增加的是大范围失配风险；到底有多少回源，要把新位置的命中状态和请求分布带进容量计算。

With N=3, buckets 0/1/2 refer to S0/S1/S2. Append S3 while keeping old IDs stable. Hash 0 stays on S0, hash 3 moves from S0 to S3, but hash 4 moves from S1 to S0. Expansion needs some newcomer load; modulo also causes old-to-old movement. Reordering the server list adds a different disturbance that should not be mixed into the residue proof.

The least common multiple of 3 and 4 is 12. For h%3=h%4=r, r must be 0, 1 or 2, and h−r must be divisible by both. Only h=0/1/2 satisfy this in 0–11. Nine of twelve move: 75%. The old eight-key removal example is a partial sample, useful for illustration but not a general remapping proof.

Since n and n+1 are coprime, the cycle is n(n+1), with n equal residues. The retained fraction is 1/(n+1) and movement n/(n+1). Thus 10→11 moves 10/11≈90.91%, about 909,091 of one million keys. This assumes hashes uniform across the residue cycle and stable old bucket IDs; small or skewed populations may differ.

Modulo gives O(1) lookup with little memory and is reasonable for a fixed worker pool. Changing cache membership prioritizes warm entries and stable placement. Modulo does not logically force every request to miss: duplicates or warming may exist. It creates broad placement mismatch risk; actual origin traffic depends on destination hit state and request distribution.

第二笔：环是本地有序索引，顺时针不是 RPC 接力A ring is a local sorted index

先命中 token，再得到物理 ownerResolve a token, then its physical owner

A2 把 hash 空间缩成 0–99，放三个 token：10→S0，40→S1，75→S2。Router 持有这份排序后的表，先把 key 按固定规则序列化、计算 hash，再找第一个不小于它的 token。hash=25 得到 40→S1；hash=40 也得到 S1；hash=90 的二分结果越界，就取首项 10→S0。环回没有跨机器通信，最终只向选中的 owner 发请求。

采用左开右闭区间，S1 接 (10,40]，S2 接 (40,75]，S0 接 (75,99]∪[0,10]。在整数教学空间，分别有 30、35、35 个 hash 位置。空成员表必须返回明确的不可路由错误，不能取首项；重复 token 必须按统一规则处理。端点采用 ≥ 是本章约定，若系统选另一种约定也可以，但所有路由者和数据分区工具必须一致。

所谓“不依赖 N”，准确说是不把节点数当作取模除数。映射仍依赖当前 token 集合、owner 映射和版本。一个 Router 看到 ep7，另一个看到 ep8，hash=18 就会去不同机器；节点名字、字节序或种子不同，也会得到不同结果。“各自算得一样”只在输入协议与成员视图一致时成立，故障检测和成员发布要另设计。

节点身份要稳定。若每次重启都用临时 IP 生成新 token，一次普通滚动发布就可能表现为全批节点删除后重新加入。用稳定的节点标识和显式 token 清单，把网络地址更新与责任区间变化分开；token 对应的 owner 可以换地址，hash 位置不必跟着跳。客户端库升级也要保留同一套序列化测试向量，不能把语言的默认字符串 hash 当成跨进程协议。

A2 uses hashes 0–99 and tokens 10→S0, 40→S1, 75→S2. Router stores this sorted table, serializes the key consistently, hashes it, and finds the first token at or above the result. Hash 25 resolves to S1, as does hash 40. Hash 90 exceeds the maximum and wraps to S0. Lookup performs no network traversal; the real request goes directly to its owner.

With left-open, right-closed intervals, S1 owns (10,40], S2 (40,75], and S0 (75,99]∪[0,10], holding 30/35/35 integer positions. An empty membership must fail explicitly. Duplicate tokens need a shared rule. Using ≥ is this chapter’s convention; other endpoint conventions work if all routers and partitioning tools agree.

“Independent of N” means machine count is not a modulo divisor. Placement still depends on the token set, owner map and epoch. Routers at ep7 and ep8 send hash 18 to different machines; different serialization, byte order or seeds also disagree. Determinism requires matching inputs and membership. Failure detection and version publication are separate mechanisms.

Use stable node identities. Hashing a temporary IP on every restart makes rolling deployment resemble mass deletion and insertion. Separate endpoint updates from ownership changes through stable IDs and explicit token lists. Preserve serialization test vectors across client-library upgrades; a language’s default string hash is not a cross-process protocol.

查找预算买的是每个 Router 的索引Lookup memory is per Router

A4 的 100×160=16,000 点，用排序数组二分最多约 14 次比较，因为 2¹⁴=16,384。每项暂按 16 B，原始条目为 16,000×16=256,000 B，约 256 KB，另加数组、字符串和对象开销。每个 Router 都需要这份索引，而不是整个集群只存一份。更新时构建完整的新数组再原子换引用，可让一条请求始终按同一 epoch 查找；这只解决本地半更新，没解决跨 Router 交接。

排序数组读多改少时简单，代价是成员变更需要构建和分发新快照。平衡树也可以做 O(log T) 查找；逐点扫描是 O(T)，只有很小的教学环才适合直接扫。哈希与序列化的成本也算在请求路径里，尤其大 key；“二分只十几次”不是整个路由动作的延迟承诺。

A4 gives 100×160=16,000 tokens. Binary search needs at most about 14 comparisons since 2¹⁴=16,384. At a provisional 16 B each, raw entries use 256,000 B, about 256 KB, plus container, string and object overhead. Each Router needs a copy. Build a full replacement array and swap its reference atomically so one request uses one epoch. This prevents a locally half-updated index, not cross-Router handoff races.

A sorted array suits frequent reads and rare membership changes, at the cost of snapshot rebuilding and distribution. A balanced tree also supports O(log T); scanning is O(T) and appropriate only for small examples. Hashing and serialization remain on the request path, particularly for large keys. Fourteen comparisons are not a routing latency guarantee.

第三笔：加点切一段，删点交下一家Addition splits a range; removal hands it forward

手算固定坐标，再算随机模型的期望Separate fixed coordinates from expectation

ep7 的 S1 原先接 (10,40]。在 25 加 S3 后，顺时针第一点变成 25 的那部分，也就是 (10,25]，改由 S3 接；(25,40] 仍归 S1。S0、S2 的区间没有改变，hash=25 恰好归新人。新增只在有新 token 插入的区间改变归属，没必要把旧节点之间的 key 重新洗牌，这就是图上的单调性。

这组坐标实际移动 15 个 hash 位置，占 15%；四台份额为 S0 35%、S1 15%、S2 35%、S3 15%。它不是均匀环。再从 ep8 删除 S1，(25,40] 交给下一点 S2@75，S2 负责 (25,75]，得到 50%；S0 35%、S3 15% 保留。删除前后的数组要一起展示，不能用“总是迁 1/n”盖掉这次明确的 15%。

A1 才能用对称性算期望：n 台等容量、每台相同数量的独立均匀 token，旧 token 不动，新增同样一台后，每台期望份额是 1/(n+1)。新人所占 key 全来自原 owner，因此期望迁 K/(n+1)。删一台时移走的是它原有的份额，期望 K/n。百万 key 从十台加到十一台是 1,000,000/11≈90,909；从十台删一台是 100,000，两个分母不同。

这些是 key 数期望，不是字节、QPS 或迁移时长保证。若某个区间集中了一批大对象，15% 的 key 可能远超 15% 的数据；若热门对象落在小段上，移动很少 key 也会改变很多请求。容量规划应同时记录区间的 key 数、总字节和请求成本。新机按权重加入时，期望份额变成新权重/总权重，还要检查权重更新有没有移动旧 token。

S1 initially owns (10,40] at ep7. Adding S3 at 25 captures (10,25]; (25,40] stays on S1. S0/S2 are unchanged, and hash 25 goes to S3. With old tokens fixed, ownership changes only in intervals captured by new tokens, avoiding old-to-old reshuffling.

This chosen ring moves 15 positions, 15%, and gives S0/S1/S2/S3 shares of 35%/15%/35%/15%. Removing S1 from ep8 passes (25,40] to S2, expanding S2 to (25,75] or 50%; S0 and S3 retain 35% and 15%. Show the versions rather than replacing this concrete 15% with “always 1/n.”

A1 supports an expectation by symmetry: equal-capacity machines with equal counts of independent uniform tokens, keeping old tokens fixed. A newcomer’s expected share is 1/(n+1), all taken from existing owners, so movement is K/(n+1). Removal moves the deleted machine’s old expected K/n share. One million keys on ten machines therefore move about 90,909 on addition and 100,000 on removal.

These expectations count keys, not bytes, QPS or duration. Large objects or hot requests can concentrate in a small interval. Measure interval key count, bytes and request cost separately. Weighted addition uses new weight/total weight in expectation, while checking whether weight changes also move old tokens.

迁移时间决定扩容要提前多久Movement time determines expansion lead time

A5 每 key 1 KB，用十进制单位，新增一台期望复制 90,909×1,000 B≈90.91 MB。有效复制速度 10 MB/s，理想时间 90.91/10≈9.09 s。取模约移动 909.09 MB，同速约 90.91 s，量级差十倍。这里只复制一份逻辑数据，没算副本、索引构建、校验与并发更新；9.09 秒是简化模型，不是切换截止时间。

复制不能吃掉用户请求的所有磁盘与网络余量。给迁移单独限速，按下游 p99 和积压调整；源机本来就过载时，扩容复制可能先让它更慢。若变更产生增量的速度接近追平速度，快照传完也收不了尾。先估可用复制能力，再决定批次、提前量和写暂停窗口；“机器已启动”只说明准备工作开始。

At A5’s 1 KB/key in decimal units, addition copies about 90,909×1,000 B=90.91 MB. Effective 10 MB/s copying gives an ideal 9.09 s. Modulo moves about 909.09 MB, or 90.91 s at the same speed, ten times as much. This models one logical copy and excludes replicas, index building, validation and concurrent changes; it is not a cutover deadline.

Migration competes with user traffic for disk and network. Throttle it separately and adjust using downstream p99 and backlog. Copying from an already overloaded source may initially worsen latency. If incoming deltas approach catch-up throughput, snapshot completion does not finish the job. Estimate available copying capacity before choosing batches, lead time and the write pause.

第四笔：虚拟节点把一大段变成多小段Virtual nodes divide ownership into smaller ranges

虚拟的是位置，不是机器和副本A vnode is a position, not another machine or replica

一个物理节点只有一个随机点时，责任区间取决于它与前驱的间距。三点教学环已经有 30%、35%、35%，更差的随机布局也可能让一台独占大半。虚拟节点给同一物理 owner 多个分散位置，查找仍命中顺时针 token，然后通过 owner 映射回 S0 等物理机。增加的是路由表中的责任入口，进程、连接池和数据副本不按 token 数翻倍。

A3 用两点演示：S0@10、60，S1@30、95，S2@45、80。S0 接跨零的 15% 加 (45,60] 的 15%，共 30%；S1 接 20%+15%=35%；S2 接 15%+20%=35%。删物理 S1 必须删除它的所有 token，(10,30] 转给 S2，(80,95] 转给 S0，接管后分别为 55% 与 45%。只删一个点会留下指向故障机器的另一部分路由。

vnode 的收益来自多个小区间累加：随机差异有机会互相抵消，删一台也能交给多个邻居。Dynamo 论文 §4.2 说明多 token 对分布、增减与异构容量的作用。[2] 但两点只是教学图，不是推荐参数；实际布局可能让多个点的下一 owner 都相同。按机架或地域选择副本时还要避开共享故障域，不能因为 token 名字不同就当成独立机器。

加权可给强机更多 token，例如容量权重 2:1:1、每个权重单位 100 点，期望份额为 200/400=50%、25%、25%。这是随机模型下的期望，不保证每组散点恰好如此。更改权重或重建实现若同时改变旧点数量，会带来额外迁移。libketama 源码按容量比例与节点数计算点数，取整也参与结果；不能不查配置就把所有加权变更当成“只拿新机那份”。[4]

With one random token per machine, ownership depends on the predecessor gap. Even three points can be very uneven. Vnodes give one physical owner multiple dispersed positions. Lookup still resolves a clockwise token, then its physical owner. More entries do not multiply processes, connection pools or replicas.

A3 places S0 at 10/60, S1 at 30/95 and S2 at 45/80. S0 gets 15% across zero plus 15%, totaling 30%; S1 gets 20%+15%=35%; S2 gets 15%+20%=35%. Removing physical S1 removes both tokens. Its (10,30] goes to S2 and (80,95] to S0, yielding 55% and 45%. Deleting only one token leaves routes to the failed machine.

Summing smaller random ranges lets deviations partly cancel and spreads takeover. Dynamo §4.2 describes multiple-token placement and capacity weighting. [2] Two tokens are illustrative, not a sizing recommendation; several successor tokens may have the same physical owner. Replica selection must also consider rack or regional failure domains.

For capacity weights 2:1:1 and 100 tokens per weight unit, expected shares are 200/400=50%, 25%, 25%, not exact outcomes. Weight changes or implementations that rebuild old token counts cause extra movement. Libketama’s source derives token counts from capacity proportions and node count, including rounding. Audit the configuration before assuming weighted changes move only the newcomer’s share. [4]

点数、误差与哈希位宽都要有出处Source token counts, deviation and hash width

Richard Jones 的 2007 年 Ketama 原文给出每服务器约 100–200 个点，并明确说 continuum 是 32 位空间。[3] 源码用 MD5 摘要拆出 32 位点，同容量时 40 份摘要×每份 4 点=160 点。[4] MD5 的摘要长度是 128 位，不等于这个实现的环宽；Dynamo 则在论文里明确采用 128 位 key 标识。[2] 本章用 160 做索引预算有依据，但不把它升级成所有系统的默认配置。

Jump Hash 论文图 2 比较经典随机环的空间份额，100 点时 σ/μ=0.0996996，约 9.97%；1,000 点时为 0.0315723，约 3.16%。[5] 这是哈希空间份额的相对标准差，不是最大偏差，也不是请求 p99 或某集群的 SLA。点数增加十倍，索引和变更工作也增加；热门 key 和大对象分布仍需另测，不能拿这组误差当实际负载保证。

32 位空间也不能一律说碰撞可忽略。token 冲突会让一个位置对应多个 owner，必须拒绝并重新分配，或规定所有客户端一致的排序与去重办法。key 的 hash 碰撞通常只是两个 key 去同一机器，存储仍用完整 key 区分，并不必然覆盖值。不同位置的 vnode 更不代表多副本；挑复制目标时要数不同物理 owner，连续三个 token 可能只来自两台机器，Dynamo §4.3 专门提醒这一点。[2]

Richard Jones’s 2007 Ketama article gives roughly 100–200 points per server and a 32-bit continuum. [3] The source extracts 32-bit points from MD5; equal-capacity servers use 40 digests×4 points=160 tokens. [4] A 128-bit MD5 digest does not imply a 128-bit ring. Dynamo explicitly uses 128-bit key identifiers. [2] This supports our 160-token index budget, not a universal default.

Jump Hash’s Figure 2 reports classical random-ring space-share σ/μ of 0.0996996, about 9.97%, at 100 points, and 0.0315723, about 3.16%, at 1,000. [5] These are relative standard deviations, not maximum imbalance, request p99 or production SLAs. Ten times more tokens increases indexing and update work; hot keys and object sizes still require measurement.

Do not universally dismiss 32-bit collisions. Conflicting tokens need reassignment or a deterministic shared ordering/deduplication rule. Colliding key hashes ordinarily colocate distinct full keys rather than overwrite values. Vnodes are not replicas: replication must count distinct physical owners. Three successor tokens might belong to two machines, as Dynamo §4.3 notes. [2]

第五笔：先准备数据，再交出写权限Prepare data before handing over write authority

环的数学性质，不会自动完成迁移协议Ring properties do not perform migration

hash=18 在 ep7 去 S1，ep8 去 S3。若先广播 ep8 再复制，第一笔 GET 可能直接读空，新 PUT 还可能和旧 Router 发给 S1 的写分叉。图里的 S3 先作为候选机出现，S1 仍是权威 owner；从 S1 复制 (10,25] 快照并记录迁移期间的增量，校验范围与内容。条带上的新归属只是规划结果，不能当作数据就绪证明。

A9 选择容易解释的交接：在最后阶段暂停或缓冲该段写，等待旧在途写完成，使 S1 对旧 epoch 的新提交实行隔离，再送最终增量。S3 校验并确认就绪，Router 才激活 ep8。这里的隔离也叫 fencing，意思是旧 owner 不再有权提交这段新写；不是只给配置加一个递增数字。旧写没有被服务端挡住，客户端带版本号也防不了分叉。

Router 在图中代表协调后的路由层，不暗示只部署一台。多 Router 不会同时收到消息，切换期间要能识别旧 epoch：旧 owner 拒绝或重定向旧路由，Router 刷新后限次重试，避免旧版仍写 S1、新版开始写 S3。读是否暂时继续给旧值，应由读合同决定；若要求交接后看到新写，就不能让旧 Router 默默长期读保留快照。

这版短写窗口的代价要说出来：受迁移区间影响的写要等待、进入有上限的缓冲，或收到明确的可重试错误。缓冲满不能无限排队，重复写需要操作标识与去重。替代方案是持续转发、双版本路由或复制协议内的领导权切换，它们能缩小窗口，却引入故障时的补偿与幂等；“直接双写”两次独立成功失败不相等，不能替代交接协议。

故障分阶段处理。快照尚未完成时 S3 坏了，ep7 继续服务，重试复制即可；S1 突然坏了则需要已有副本或备份恢复，环本身不会造出丢失的值。交接隔离后协调层失联，优先暂停受影响写，确认权威 epoch 再恢复。ep8 已经接受新写时回滚，必须把新增量迁回并重新交权，否则退回旧环会把已确认更新藏起来。

旧副本要延迟清理：确认新版本稳定，旧请求和增量处理结束，校验通过，再按保留策略回收旧区间。保留旧数据可以帮助故障恢复，但保留不代表旧写权限仍开放。环位置、物理数据、路由版本、写权限是四种状态；只检查“新配置已发出”，会遗漏后三者的不同完成时间。

Hash 18 goes to S1 at ep7 and S3 at ep8. Publishing ep8 before copying can yield empty reads and split writes between old and new Routers. S3 first appears as a candidate while S1 remains authoritative. Copy the snapshot of (10,25], capture concurrent deltas and validate the range. Planned ownership is not readiness evidence.

A9 uses a simple handoff: pause or buffer writes for the final stage, drain old in-flight writes, fence further old-epoch commits at S1, then send the final delta. S3 validates readiness before Router activates ep8. Fencing removes old write authority; a larger configuration number alone does not prevent stale clients from committing on S1.

Router represents a coordinated layer, not a single deployed instance. Multiple Routers receive updates at different times. Old owners must reject or redirect stale epochs, and Routers refresh with bounded retries. Reads from retained old copies require an explicit staleness contract; read-after-write expectations cannot tolerate indefinitely serving an old snapshot.

The write window costs waiting, bounded buffering or explicit retryable errors. A full buffer cannot grow forever; repeated writes need operation IDs and deduplication. Forwarding, dual-version routing or a replication protocol’s leadership transfer can reduce the window but add failure recovery and idempotency. Independent dual writes do not form a safe handoff protocol.

Failures are phase-dependent. A candidate failure before readiness leaves ep7 serving. Sudden loss of S1 needs existing replicas or backup; hashing cannot recreate records. Coordination loss after fencing pauses affected writes until authority is known. Rolling back after ep8 accepts writes requires moving those deltas back and transferring authority again.

Reclaim old data only after the new epoch is stable, old requests and deltas are drained, and validation passes. Retaining recovery data does not retain write permission. Ring positions, physical data, routing epochs and write authority have different completion times; “configuration sent” verifies only one.

真实系统会把迁移状态做成显式协议Real systems expose migration states

Redis Cluster 用 16,384 个固定 hash slot，再把 slot 分配给节点，节点数变化时 hash 到 slot 的公式不变；它不是本章的随机 token 环。规范列出 MIGRATING、IMPORTING 状态以及 ASK、MOVED 重定向，说明数据搬运和路由更新之间需要过渡协议。[7] 这里只借它验证“不能只有新映射”的事实，图上的暂停写模型并非照抄 Redis 的迁移过程。

Apache Cassandra 文档也将 token、物理 endpoint 与 host ID 分开，描述 vnode 和成员信息传播。[6] 若设计 KV，应继续补复制、故障检测和修复；缓存则能舍弃值，但仍要保护回源容量。计划下线可以先迁数据再摘成员，故障摘除却可能没有源机可搬，两者共用新的归属函数，不能共用“源机复制完即可”的恢复保证。

Redis Cluster hashes into 16,384 fixed slots, then assigns slots to machines. Node count changes do not alter key-to-slot hashing; this is not a random-token ring. Its MIGRATING/IMPORTING states and ASK/MOVED redirects demonstrate the need for a transition protocol between moving data and updating routes. [7] Our write-pause model illustrates the requirement, not Redis’s exact migration procedure.

Cassandra distinguishes tokens, physical endpoints and host IDs and describes vnodes and membership propagation. [6] A KV design still needs replication, failure detection and repair. Cache values may be discarded, but origin capacity must be protected. Planned removal can copy before detaching; crash recovery may have no source available. Both compute new placement without sharing the same recovery guarantee.

少迁 key 之后，仍要算热点和回源Limited movement still needs hotspot and origin budgets

A6 总读 10,000/s，十台负载真正均匀时平均 1,000/s，低于每台计划 1,500/s。掉一台且接管分散时，剩余平均 10,000/9≈1,111/s，仍有余量。但“平均没超”不等于每台安全；若单 token 布局把失效节点的整份流量压给一个原本 1,000/s 的邻居，它会到 2,000/s，超过上限。vnode 改善接管分布，容量告警仍要看最忙节点。

A7 把 40% 请求放在共享热点 post:9，热点本身 10,000×0.4=4,000/s，其余 6,000/s 均匀分摊，热点 owner 约 4,000+6,000/10=4,600/s。增加这个 owner 的 token 不会把同一个 key 分出去，甚至可能给它更多普通区间。加机器也不保证热点恰好移动，更不保证搬走后能承受 4,000/s；它只是换了一个拥堵地点。

热点读可以用请求合并、应用内短缓存、专用副本或复制热点值，代价是失效与陈旧窗口。热点写要先问是否可拆：计数能按子 key 分片再聚合，要求单 key 原子顺序的余额不能随意加盐。拆 key 改了数据模型和读放大；多个读副本改了读路由与复制协议。要把选择接回语义，不能只说“加随机后缀”就宣布问题解决。

A8 的缓存扩容有另一笔负载：新机接 1/11 的读且起初全 miss，约 10,000/11=909.09/s；其余 10/11 保持 95% 命中，回源约 10,000×10/11×0.05=454.55/s。合计 1,363.64/s，约 1,364，比原来的 500/s 高约 2.73 倍，也超库预算 800/s。虽然只换 9.09% 的归属，暖数据缺失已足够把回源打穿。

若先把新机预热到命中率 h，回源是 454.55+909.09×(1−h)。要不超过 800，需 h≥1−(800−454.55)/909.09≈62%。这只是在均匀读假设下的静态下限，不包含重试或既有故障余量。可分批切区间、限制冷读回源、只允许一个加载者，再按产品合同给旧值或拒绝；预热要验证有代表性的键分布，不能只报“复制完了多少 key”。

A6’s 10,000 reads/s across ten uniformly loaded machines averages 1,000/s, below a planned 1,500/s cap. After one failure with dispersed takeover, the average is 10,000/9≈1,111/s. This does not bound the busiest machine. A single-token ring could move a full 1,000/s onto an already 1,000/s neighbor, giving 2,000/s. Vnodes improve takeover distribution; monitor the maximum load.

A7 concentrates 40% on shared key post:9: 4,000/s plus about 6,000/10=600/s background gives its owner 4,600/s. More vnodes on that owner do not split the key. Adding machines neither guarantees that the hot key moves nor makes 4,000/s affordable at its destination.

Hot reads can use coalescing, short local caching, dedicated replicas or replicated hot values, with invalidation and staleness costs. Hot writes require semantic analysis: sharded counters can aggregate subkeys, but an atomically ordered balance cannot be arbitrarily salted. Splitting keys changes the data model and read amplification; read replicas change routing and replication.

In A8, a cold newcomer handles 1/11 of reads, all misses: 909.09/s. The remaining 10/11 retains 95% hits, producing 454.55 origin reads/s. Total origin load is 1,363.64/s, about 1,364, or 2.73× the previous 500/s and above the 800/s budget. Moving only 9.09% of ownership can still overload origin.

If the newcomer is warmed to hit rate h, origin load is 454.55+909.09×(1−h). Staying within 800 requires h≥62%. This static threshold assumes uniform reads and excludes retries and failure headroom. Switch ranges in batches, cap cold origin reads and use one loader per key, then serve stale data or reject according to the product contract. Warming must cover representative requests, not merely a count of copied keys.

变体只回答约束，不抢走主线Variants answer a constraint, not replace the main story

环加 vnode 是本章选择，因为命名节点可任意增减、需要可解释区间和权重。Jump Hash 的输入是 key 与桶数，输出 0…N−1；论文给出极小的额外内存与期望 O(log N) 时间，限制是连续桶编号。[5] 追加尾桶很合适，任意删除中间逻辑桶需要额外映射层。物理机器坏了也可以由副本接管同一逻辑桶，所以不能把它硬说成“存储节点不能故障”。

Maglev 面向软件网络负载均衡，用预计算表提供快速后端选择；2016 论文 §5.3 的默认表大小是 65,537。[8] 查表快不等于成员变化免费，构表、分发和连接跟踪仍有工作；它的扰动性质也不能直接套成本章固定 token 环的严格区间证明。网络 LB 的细节留到 Ch39，本章只说清为什么“每包查表”与“数据区间迁移”关注不同约束。

固定 slot 表则把 key→slot 与 slot→machine 拆开，迁移一批 slot 时，不必重算所有 key 的 slot。粒度有限、slot 可能有热点，表也需要版本和迁移协议。哪种放置函数都不能独自完成可用性、读写一致性或热点保护；面试时先给满足当前约束的一个方案，再用一两句说明替代条件，比背变体名字更容易核验。

This chapter chooses ring+vnodes for named, arbitrarily removable machines, explicit ranges and weighting. Jump Hash maps key and bucket count to 0…N−1 with minimal extra memory and expected O(log N) time, but requires sequential bucket IDs. [5] Appending buckets fits; removing an arbitrary logical middle bucket needs indirection. Physical failure can still be handled by replicas taking over the same logical bucket.

Maglev targets software network load balancing with a precomputed backend lookup table; its 2016 paper §5.3 uses 65,537 as the default table size. [8] Fast lookup still requires rebuilding, distribution and connection tracking. Its disruption properties should not be replaced with this ring’s exact interval argument. Ch39 covers packet-level balancing; here distinguish it from data-range migration.

Fixed slots separate key→slot from slot→machine. Moving slots preserves key-to-slot hashing, but granularity, hotspots, versions and migration remain. No placement function alone supplies availability, read/write consistency or hotspot protection. Select one design for the current constraints and state the conditions for alternatives.

追问与验算：证明改动真的局部Follow-ups: verify that changes are local

“一致性怎么测？”先验证端点和环回：在 A2 中查 10、11、25、40、41、75、76、99，旧环应依次去 S0、S1、S1、S1、S2、S2、S0、S0。再加入 S3@25，枚举全部 100 个位置，只有 11–25 改归属，其余完全相同。这个测试检验单调性；看平均节点 key 数相近，只能检验分布，发现不了无谓迁移。

“机器重启会怎样？”稳定身份和 token 清单不变时，地址更新不应改变 owner；若用新身份加入，就需要按删除与新增评估扰动。“客户端版本不同呢？”对相同字节 key 和同一清单，跨语言测试向量必须得到相同 hash、token、owner；旧 epoch 请求在交接后必须被服务端拒绝或重定向。仅比较配置文件大小没有意义。

“加一台为什么不能立即救过载？”它需要初始化、复制或预热，再追平与切流量；迁移还占用过载源机的资源。“有 vnode 还需要留余量吗？”需要，节点故障后总容量少了一台，热点和不均匀不会随着平均除法消失。扩容实验至少记录实际移动 key、移动字节、最忙 owner、缓存命中与回源 p99；只有新机变绿，不足以验收。

“How do you test consistency?” Check A2 endpoints and wraparound: hashes 10/11/25/40/41/75/76/99 resolve to S0/S1/S1/S1/S2/S2/S0/S0. Add S3@25 and enumerate all 100 positions: only 11–25 change. This verifies monotonicity; similar average key counts test distribution but cannot detect needless reassignment.

“What about restarts?” Stable identities and tokens keep ownership while endpoints change; new identities require deletion/addition analysis. Cross-language vectors must agree on hash, token and owner for the same bytes and membership. After handoff, servers must reject or redirect stale epochs rather than merely compare configuration sizes.

“Why not add a machine immediately?” Initialization, copying or warming, catch-up and activation take time and consume source resources. Vnodes do not replace headroom: failure removes capacity and averages conceal hotspots. Measure changed keys, bytes, maximum owner load, hit rate and origin p99; a healthy newcomer alone is insufficient.

收尾：归属、容量、交接各说一句Close on placement, capacity and handoff

旧桶编号固定时，取模十到十一台重映射约 90.91%；环保留旧 token，等容量随机模型只需迁新人期望的 9.09%。查找是在本地有序表中找 successor，不沿机器接力。vnode 将责任分成多段，可改善分布和接管，但一个热 key 仍落同一 owner。扩容先复制或预热、追平与隔离旧写，再激活新 epoch；缓存冷启动在本例会把回源从 500/s 拉到约 1,364/s，所以迁得少仍要容量封顶。

合上页面，先手算 hash=90 的环回，再说新增 S3@25 时只变哪一段，最后解释新机就绪之前为何仍走 S1。能讲出这三条路径，就能接下一章的复制与 quorum。Ch02 给过按用户分片的直觉，Ch03 教你把 key 数、字节和 QPS 分开；本章提供放置函数，复制和分区故障不应被一句“已有一致性哈希”带过。

With stable old IDs, modulo 10→11 remaps about 90.91%. Keeping old ring tokens fixed moves only the newcomer’s expected 9.09% under an equal-capacity random model. Lookup finds a successor locally, not through server forwarding. Vnodes spread responsibility and takeover without splitting one hot key. Expansion copies or warms, catches up, fences old writes, then activates the next epoch. In this example a cold cache raises origin from 500/s to about 1,364/s, so limited movement still needs a capacity cap.

Close the page and resolve hash 90, identify the range captured by S3@25, then explain why reads remain on S1 until readiness. These paths connect placement to the next chapter’s replication and quorums. Ch02 introduces user sharding and Ch03 separates counts, bytes and QPS. A placement function does not settle replication or partition failures.
