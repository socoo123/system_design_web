English

  • Prove modulo remapping over a full residue cycle and distinguish expected addition and removal movement.
  • Resolve ownership, wraparound and interval splits on an unfolded ring without implying network traversal.
  • Separate virtual nodes, hot keys, replication and epoch handoff, and explain what remains after computing a new owner.

开场：先明确数据怎样分配，再选择分区函数Open with the placement contract

一致性哈希用来决定：节点加入或离开后，每个键应由哪台机器负责。它把节点位置（token）和键的哈希值放在同一个环上，再沿顺时针找到第一个节点位置。新增机器时，旧位置保持不变，只有新机器接管区间内的键会改变归属。数据复制、强一致读写和安全迁移仍需另外设计。[1]

选方案前，先确认三件事：存的是缓存还是权威数据，节点可以任意命名还是必须使用连续逻辑桶，负载按键数、字节数还是 QPS 衡量。本章选择“环＋虚拟节点（vnode）”，允许使用稳定名称的机器任意增减，依次讲清节点定位、成员变化和读写权限交接。下文的 owner 指首先负责某个键的机器，不表示数据只有这一份。

前四组图的箭头表示本地索引顺序或键的归属变化，第五组才表示通信。图中的 Router 是负责路由的一方，可以位于客户端库、代理或协调节点中。它根据当前成员配置版本（epoch）在本地查找，然后直接联系负责该键的机器，无须沿环逐台发送 RPC。

Consistent hashing handles placement as membership changes: preserve old tokens, select the first clockwise token, and move only ranges captured by the newcomer. It does not itself provide replication, strongly consistent I/O, or safe migration. [1]

Clarify cache versus authoritative data, arbitrary machine identities versus sequential logical buckets, and key counts versus bytes/QPS. We choose a ring with vnodes for named machines, then explain lookup, membership changes, and authority transfer. Owner means the first-responsible machine, not the only data copy.

Arrows in the first four decks show local index order or placement changes; only the last deck shows communication. Router is a role in a client library, proxy, or coordinator. Given one epoch, it searches locally and contacts the owner directly without RPC traversal of the ring.

先看取模：扩容为什么也会改变旧节点之间的归属Modulo also remaps between surviving machines

保留旧节点编号，才能比较扩容前后的归属Keep old IDs stable when comparing owners

保留旧编号 S0、S1、S2，扩容时只追加 S3。此时，hash=0 的键留在 S0，hash=3 的键从 S0 到 S3，hash=4 的键则从 S1 到 S0。最后一种情况说明，即使旧机器都保留，取模仍会改变它们之间的归属。如果同时重排服务器列表，还会产生另一层变化；这里暂不把它算进去。

3 和 4 的完整余数周期是 12。在 0–11 中，只有 0、1、2 满足 h%3=h%4，所以共有 9/12=75% 的位置需要重新分配。一般地，n 与 n+1 互质，在长度为 n(n+1) 的周期里，只有 n 个位置的余数相同，因而归属变化比例为 n/(n+1)。假设哈希值在周期内均匀分布，从 10 台扩到 11 台时，100 万个键预计约有 909,091 个改变归属，占 90.91%。

取模的查找复杂度为 O(1)，索引也很小，适合成员固定的场景。缓存节点经常增减时，则要重视已有缓存数据能否继续使用，以及键的归属是否稳定。不过，归属变化也不意味着每次请求都会缓存未命中：数据副本、预热程度和请求分布共同决定实际回源量，后面会单独计算。

Keep S0/S1/S2 stable and append S3. Hash 0 stays, hash 3 moves S0→S3, and hash 4 moves S1→S0: modulo also disturbs ownership between survivors. Reordering the server list causes additional disturbance outside this proof.

The complete residue cycle for 3 and 4 is 12. Only 0/1/2 satisfy h%3=h%4, so 9/12=75% remap. In general n and n+1 are coprime; n of n(n+1) residues match, giving movement n/(n+1). Thus 10→11 moves about 909,091 of one million keys, 90.91%, assuming uniform hashes across the cycle.

Modulo offers O(1) lookup and a small index for fixed membership. Dynamic caches value stable ownership and warm data. Remapping is not an automatic miss for every request: copies, warming, and request distribution determine the origin load calculated later.

节点定位：在本地有序表中查找环上的下一点A ring is a local sorted index

先找到节点位置，再找到负责的物理机器Resolve a token, then its physical owner

A2 中，排好序的节点位置是 10→S0、40→S1、75→S2。查找时，先找出第一个满足 token≥hash 的位置，再读取它对应的物理机器。因此，25 和 40 都归 S1，90 超过最后一个位置后则环回 S0。各段区间左开右闭：S0 负责 (75,99]∪[0,10]，S1 负责 (10,40]，S2 负责 (40,75]。

下面是可运行示例中的 Java 17 片段。构造环时，先排序，再复制成不可变表；空环和重复节点位置都会被拒绝，已有归属不会被覆盖。环上只有一个节点时，它负责整个空间。代码把 long 当作无符号 64 位数比较，避免把最高位为 1 的哈希值排到前面。图中的 0–99 仅用于手算，实际哈希值不会被取模到这 100 个位置中。

A2 sorts 10→S0, 40→S1, 75→S2. Find the first token≥hash: 25 and 40 go to S1, while 90 wraps to S0. Intervals are left-open/right-closed: S0 owns (75,99]∪[0,10], S1 (10,40], and S2 (40,75].

This Java 17 excerpt belongs to the runnable example. Construction sorts and copies an immutable table; empty rings and duplicate tokens are rejected instead of overwriting owners. One token covers the entire ring. Compare long values as unsigned 64-bit positions so high-bit hashes do not sort first. The diagram’s 0–99 is for hand calculation; production hashes are not reduced modulo 100.

public record Token(long position, String owner) {
    public Token {
        if (owner == null || owner.isBlank())
            throw new IllegalArgumentException("empty owner");
    }
}
public record Ring(long epoch, List<Token> tokens) {
    public Ring {
        if (epoch < 0 || tokens.isEmpty())
            throw new IllegalArgumentException("invalid epoch / empty ring");
        var sorted = new ArrayList<>(tokens);
        sorted.sort((a, b) -> Long.compareUnsigned(a.position(), b.position()));
        for (int i = 1; i < sorted.size(); i++)
            if (sorted.get(i - 1).position() == sorted.get(i).position())
                throw new IllegalArgumentException("token collision");
        tokens = List.copyOf(sorted);
    }
    public String owner(long hash) {
        int lo = 0, hi = tokens.size();
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (Long.compareUnsigned(tokens.get(mid).position(), hash) < 0)
                lo = mid + 1;
            else hi = mid;
        }
        return tokens.get(lo == tokens.size() ? 0 : lo).owner();
    }
}

完整源码 ConsistentRing.java 约定了键的编码和哈希规则：把字符串原样编码为 UTF-8，不做隐含的 Unicode 归一化，再取 SHA-256 摘要的前 8 个字节，按大端顺序解释。例如，abc → ba7816bf8f01cfea。这套协议用于教学，与 Ketama 不兼容。节点位置由权威清单明确给出；如果新位置发生碰撞，控制层负责重新分配并统一发布，Router 不能各自随机重试。两个键的哈希值相同，只会让它们落在同一台机器上，存储仍按完整键区分。

节点的稳定 ID 要与网络地址（endpoint）分开。机器重启后即使换了 IP，也不应重新生成节点位置。成员版本、哈希协议和序列化规则都属于同一份清单。如果不同 Router 看到的成员版本不同，它们就可能算出不同的负责节点；环上的查找算法无法替它们达成共识。

The full ConsistentRing.java defines UTF-8 without normalization, then the first eight SHA-256 bytes in big-endian order: abc → ba7816bf8f01cfea. This is a teaching protocol, not Ketama compatibility. Tokens come from an authoritative manifest. The control plane reallocates a colliding new token and publishes one result; Routers must not retry randomly on their own. Colliding key hashes merely colocate full keys, which storage still distinguishes.

Separate stable node identity from endpoint addresses. An IP change must not regenerate tokens. Membership epoch, hashing protocol, and serialization belong to the manifest. Different epochs may select different owners; the ring does not establish consensus between Routers.

索引内存要按每个 Router 分别计算Lookup memory is per Router

A4 中，100 台机器每台有 160 个点，共有 100×160=16,000 个点。因为 2¹⁴=16,384，在有序数组中二分查找最多约需 14 次比较。每项暂按 16 B 计算，原始条目占 16,000×16=256,000 B，约 256 KB，此外还有数组、字符串和对象开销。每个 Router 都要保存这份索引。更新时，先构建完整的新数组，再原子替换引用，让一次请求始终使用同一个成员版本；这样可以避免本地读到半更新的表，多个 Router 之间的交接仍需协调。

成员变化少、查找多时，有序数组比较简单，代价是每次成员变化都要重新构建和分发快照。平衡树也支持 O(log T) 查找；逐点扫描则是 O(T)，只适合很小的教学环。序列化和计算哈希也占用请求时间，大键尤其如此。因此，二分只需十几次比较，并不能直接推出整个路由过程的延迟。

A4 gives 100×160=16,000 tokens. Binary search needs at most about 14 comparisons since 2¹⁴=16,384. At a provisional 16 B each, raw entries use 256,000 B, about 256 KB, plus container, string and object overhead. Each Router needs a copy. Build a full replacement array and swap its reference atomically so one request uses one epoch. This prevents a locally half-updated index, not cross-Router handoff races.

A sorted array suits frequent reads and rare membership changes, at the cost of snapshot rebuilding and distribution. A balanced tree also supports O(log T); scanning is O(T) and appropriate only for small examples. Hashing and serialization remain on the request path, particularly for large keys. Fourteen comparisons are not a routing latency guarantee.

成员变化：新增节点切走一段，删除节点交给后继Addition splits a range; removal hands it forward

固定坐标逐段算，随机模型再求期望Separate fixed coordinates from expectation

在 ep7 中，S1 负责 (10,40]。25 处加入 S3 后，(10,25] 内各键顺时针遇到的第一点变成 S3，因此改归 S3；(25,40] 仍归 S1。S0、S2 的区间保持不变，恰好位于 25 的键也归 S3。保留旧点时，归属只会在新点接管的区间内改变，旧节点之间无需重新交换键，这就是图中体现的单调性。

这次共有 15 个哈希位置改变归属，占 15%，四台份额依次为 S0 35%、S1 15%、S2 35%、S3 15%。再从 ep8 删除 S1，它的 (25,40] 交给后继 S2@75。此时 S2 负责 (25,75]，份额增至 50%，S0 和 S3 仍为 35% 和 15%。对比删除前后的表，可以直接算出本次有 15% 的位置改变归属，无须套用随机模型的 1/n。

A1 的随机模型则可以用对称性求期望。假设 n 台机器容量相同，各有同样数量、独立均匀分布的节点位置。保持旧点不动，再加入同样一台机器后，每台的期望份额都是 1/(n+1)。新机器负责的键全部来自旧节点，因此预计迁移 K/(n+1) 个键。删除一台时，改变归属的是它原有的份额，期望为 K/n。100 万个键从 10 台扩到 11 台，预计迁移 1,000,000/11≈90,909 个；从 10 台减为 9 台，则预计迁移 100,000 个。新增和删除使用的分母不同。

这些期望只统计键数，不能保证迁移的字节数、QPS 或耗时。如果某段集中了一批大对象，15% 的键可能占远超 15% 的数据；如果热门对象集中在小区间里，少量键改变归属也会带走大量请求。因此，容量规划要分别记录区间内的键数、总字节数和请求成本。只有独立均匀的节点位置数量精确按权重分配时，新机器的期望份额才等于“新权重÷总权重”；发生取整或调整旧点后，要按实际节点位置数量重新计算。

S1 initially owns (10,40] at ep7. Adding S3 at 25 captures (10,25]; (25,40] stays on S1. S0/S2 are unchanged, and hash 25 goes to S3. With old tokens fixed, ownership changes only in intervals captured by new tokens, avoiding old-to-old reshuffling.

This chosen ring moves 15 positions, 15%, and gives S0/S1/S2/S3 shares of 35%/15%/35%/15%. Removing S1 from ep8 passes (25,40] to S2, expanding S2 to (25,75] or 50%; S0 and S3 retain 35% and 15%. Show the versions rather than replacing this concrete 15% with “always 1/n.”

A1 supports an expectation by symmetry: equal-capacity machines with equal counts of independent uniform tokens, keeping old tokens fixed. A newcomer’s expected share is 1/(n+1), all taken from existing owners, so movement is K/(n+1). Removal moves the deleted machine’s old expected K/n share. One million keys on ten machines therefore move about 90,909 on addition and 100,000 on removal.

These expectations count keys, not bytes, QPS or duration. Large objects or hot requests can concentrate in a small interval. Measure interval key count, bytes and request cost separately. New weight/total weight is the expected share only when independent uniform token counts are exactly proportional to weights. Recompute from actual token counts after rounding or changes to old positions.

成员快照：让一次请求始终使用同一个版本Membership snapshots: one version per request

新增 S3 时，先构建完整的 ep8 表，并保留 S0、S1、S2 的旧节点位置；删除物理节点时，则移除它的全部节点位置。候选表可以先用来规划迁移范围，只有下文的交接提交后，才能安装为实际处理请求的快照。安装时使用经过验证的权威清单，并把成员版本与内容摘要绑定。本地的比较并交换（CAS）只控制本机更新，不能替代控制层对清单内容的一致决策。

Build the complete ep8 table while preserving old S0/S1/S2 positions. Removing a physical owner filters all its tokens. Candidate tables can plan changed ranges, but become serving snapshots only after the handoff commits. Installation consumes a validated authoritative manifest binding epoch to content digest; local CAS cannot replace control-plane agreement.

public record Route(long epoch, String owner) {}
public static final class Router {
    private final AtomicReference<Ring> current;
    public Router(Ring initial) {
        current = new AtomicReference<>(Objects.requireNonNull(initial));
    }
    public Route route(long hash) {
        Ring snapshot = current.get();
        return new Route(snapshot.epoch(), snapshot.owner(hash));
    }
    // Only consume a validated, committed control-plane manifest.
    public boolean install(long expectedEpoch, Ring next) {
        Ring old = current.get();
        if (old.epoch() != expectedEpoch || next.epoch() <= old.epoch())
            return false; // stale update, replay or same-epoch fork
        return current.compareAndSet(old, next);
    }
}

路由方法 route 从同一份快照中返回成员版本和负责节点，请求再携带这个版本交给存储层校验。安装方法 install 只接受更高版本，同时要求调用者预期的旧版本仍是当前版本。因此，两个线程都基于 ep7 发布时，最多只有一个成功；失败的一方应重新读取权威清单，不能盲目重试旧提案。Router 可以跳过未见过的中间版本，但必须先验证最新的已提交清单。重复投递同一版本也会返回 false，调用者可以核对内容摘要，确认它是否已经安装；同一版本号下的不同内容不能相互覆盖。

运行示例时，先执行 javac --release 17 -d /tmp/ch05-java examples/ch05/*.java，再执行 java -cp /tmp/ch05-java ConsistentRingTest。测试覆盖归属枚举、空环、位置碰撞、高位哈希值、环回、不可变性和并发发布。这些检查验证的是本地算法，分布式迁移是否安全仍要另行验证。

route returns epoch and owner from one snapshot; send the epoch to storage for validation. install accepts only a higher version while the caller’s expected old epoch is still current. Two publishers based on ep7 have at most one winner; a loser reloads authoritative state instead of blindly resubmitting its proposal. Skipping unseen epochs is allowed only after validating the latest committed manifest. Replays also return false; the caller may compare digests to recognize an already-installed version, never overwrite different content at the same epoch.

Run javac --release 17 -d /tmp/ch05-java examples/ch05/*.java, then java -cp /tmp/ch05-java ConsistentRingTest. Checks enumerate ownership, empty/colliding rings, high bits, wraparound, immutability, and racing publishers. They verify local algorithms, not distributed migration safety.

迁移时间决定扩容要提前多久Movement time determines expansion lead time

A5 假设每个键占 1 KB，并使用十进制单位。从 10 台扩到 11 台时，预计复制 90,909×1,000 B≈90.91 MB。有效复制速度若为 10 MB/s，理想耗时就是 90.91/10≈9.09 秒。取模方案约需移动 909.09 MB，同样速度下约耗时 90.91 秒，是前者的 10 倍。这里只计算一份逻辑数据，尚未计入副本、索引构建、校验和并发更新，因此 9.09 秒不能直接作为完成切换的时间承诺。

迁移和用户请求会争用磁盘、网络资源，需要为迁移单独限速，并根据下游 p99 延迟和积压调整速度。源机器已经过载时，扩容中的复制反而可能先让它更慢。如果新增变更产生的速度接近增量追平速度，即使快照传完，也可能迟迟无法完成交接。因此要先估算可用复制能力，再决定迁移批次、扩容提前量和读写暂停窗口。机器启动成功，只代表准备工作已经开始。

At A5’s 1 KB/key in decimal units, addition copies about 90,909×1,000 B=90.91 MB. Effective 10 MB/s copying gives an ideal 9.09 s. Modulo moves about 909.09 MB, or 90.91 s at the same speed, ten times as much. This models one logical copy and excludes replicas, index building, validation and concurrent changes; it is not a cutover deadline.

Migration competes with user traffic for disk and network. Throttle it separately and adjust using downstream p99 and backlog. Copying from an already overloaded source may initially worsen latency. If incoming deltas approach catch-up throughput, snapshot completion does not finish the job. Estimate available copying capacity before choosing batches, lead time and the I/O pause.

虚拟节点：让一台机器负责多个分散区间Virtual nodes divide ownership into smaller ranges

虚拟节点表示位置，数据副本另行安排A vnode is a position, not another machine or replica

每台物理机只有一个随机位置时，它负责多大区间，取决于这个位置与前驱之间的距离。三点教学环的份额是 30%、35%、35%，更差的随机布局甚至可能让一台机器占去大半。虚拟节点让同一台机器拥有多个分散的位置：查找时仍先选中顺时针第一个点，再通过归属映射找到 S0 等物理机器。增加的是路由表中的位置，进程、连接池和数据副本不随点数翻倍。

A3 给每台机器两个点：S0 在 10、60，S1 在 30、95，S2 在 45、80。S0 负责跨越零点的 15%，再加上 (45,60] 的 15%，共 30%；S1 为 20%+15%=35%；S2 为 15%+20%=35%。删除 S1 时，要移除它的全部节点位置。(10,30] 交给 S2，(80,95] 交给 S0，最终 S2 占 55%，S0 占 45%。如果只删一个点，部分请求仍会被送往故障机器。

虚拟节点的收益来自多个小区间的累加：不同区间的随机偏差有机会相互抵消，一台下线时，也有机会由多个邻居分别接管。Dynamo 论文 §4.2 说明了多节点位置对负载分布、成员增减和异构容量的作用。[2] 不过，每台两点只是教学设置，实际布局中，多个位置的后继仍可能属于同一台机器。选择副本时，还要考虑机架、地域等共同故障域；位置名称不同，并不代表物理机器独立。

机器容量不同时，可以给容量更大的机器更多节点位置。例如，容量权重为 2:1:1，每个权重单位分配 100 个点，期望份额就是 200/400=50%、25%、25%。这是随机模型中的期望，具体布局未必恰好符合。如果更改权重，或重建环时同时改变旧节点的点数，还会引起额外迁移。libketama 源码按容量比例和节点数计算点数，取整也会影响结果，因此要核对配置，才能判断某次加权调整会移动哪些区间。[4]

With one random token per machine, ownership depends on the predecessor gap. Even three points can be very uneven. Vnodes give one physical owner multiple dispersed positions. Lookup still resolves a clockwise token, then its physical owner. More entries do not multiply processes, connection pools or replicas.

A3 places S0 at 10/60, S1 at 30/95 and S2 at 45/80. S0 gets 15% across zero plus 15%, totaling 30%; S1 gets 20%+15%=35%; S2 gets 15%+20%=35%. Removing physical S1 removes both tokens. Its (10,30] goes to S2 and (80,95] to S0, yielding 55% and 45%. Deleting only one token leaves routes to the failed machine.

Summing smaller random ranges lets deviations partly cancel and spreads takeover. Dynamo §4.2 describes multiple-token placement and capacity weighting. [2] Two tokens are illustrative, not a sizing recommendation; several successor tokens may have the same physical owner. Replica selection must also consider rack or regional failure domains.

For capacity weights 2:1:1 and 100 tokens per weight unit, expected shares are 200/400=50%, 25%, 25%, not exact outcomes. Weight changes or implementations that rebuild old token counts cause extra movement. Libketama’s source derives token counts from capacity proportions and node count, including rounding. Audit the configuration before assuming weighted changes move only the newcomer’s share. [4]

环上点数、分布误差和哈希位宽要分别理解Source token counts, deviation and hash width

Richard Jones 的 2007 年 Ketama 原文给出每台服务器约 100–200 个点，并明确说明环空间（continuum）为 32 位。[3] 源码从 MD5 摘要中提取 32 位点；同权重的理想情况下，40 份摘要每份提取 4 点，共 40×4=160 点。实际数量还受浮点运算和向下取整（floor）影响，未必对任意节点数都恰好为 160。[4] MD5 摘要有 128 位，也不能据此认定这个环有 128 位；Dynamo 论文则明确使用 128 位键标识。[2] 因此，本章可以用 160 点估算索引内存，但它不是所有系统通用的默认值。

Jump Hash 论文图 2 比较了经典随机环的空间份额分布：100 点时，σ/μ=0.0996996，约为 9.97%；1,000 点时，σ/μ=0.0315723，约为 3.16%。[5] 这里衡量的是哈希空间份额的相对标准差，不能当作最大偏差、请求 p99 或集群 SLA。点数增加 10 倍，索引和更新工作也会增加；热门键和大对象的分布仍需单独测量，实际请求负载不能由这组误差直接保证。

32 位空间中的碰撞也需要处理。如果两个节点位置相同，一个位置就会对应多个负责节点；可以拒绝清单后重新分配，也可以制定所有客户端一致的排序、去重规则。两个键的哈希值碰撞，通常只意味着它们落到同一台机器，存储按完整键区分时不会因此覆盖数据。选副本还要统计不同的物理机器：连续三个节点位置可能只属于两台机器，Dynamo §4.3 专门提醒了这一点。[2]

Richard Jones’s 2007 Ketama article gives roughly 100–200 points per server and a 32-bit continuum. [3] The source extracts 32-bit points from MD5; ideal equal weights give 40 digests×4 points=160 tokens; floating-point arithmetic and floor rounding can change the actual count, so 160 is not exact for every cluster size. [4] A 128-bit MD5 digest does not imply a 128-bit ring. Dynamo explicitly uses 128-bit key identifiers. [2] This supports our 160-token index budget, not a universal default.

Jump Hash’s Figure 2 reports classical random-ring space-share σ/μ of 0.0996996, about 9.97%, at 100 points, and 0.0315723, about 3.16%, at 1,000. [5] These are relative standard deviations, not maximum imbalance, request p99 or production SLAs. Ten times more tokens increases indexing and update work; hot keys and object sizes still require measurement.

Do not universally dismiss 32-bit collisions. Conflicting tokens need reassignment or a deterministic shared ordering/deduplication rule. Colliding key hashes ordinarily colocate distinct full keys rather than overwrite values. Vnodes are not replicas: replication must count distinct physical owners. Three successor tokens might belong to two machines, as Dynamo §4.3 notes. [2]

安全交接：先准备数据，再转移读写权限Prepare data before handing over write authority

交接的约定：先停旧读写，再启用新节点Handoff contract: fence old I/O before enabling the new owner

以 hash=18 从 S1 迁到 S3 为例。如果先广播 ep8，新请求可能到尚无数据的 S3 读取，使用不同版本的 Router 也可能分别向两台机器写入。这里采用的教学方案是短暂停止该区间的读写，状态不明确时保持不可用：准备期间仍由 S1 服务；冻结后，S1 拒绝新读写，并等待已受理的操作完成；S3 追到最终日志位置、校验通过后，才获得服务权限。如果缓存业务允许旧值，可以另行放宽读取条件，但必须明确允许陈旧到什么程度。

下面的伪代码用线性一致 CAS 持久保存交接计划（plan），把计划 ID、区间、旧新成员版本和负责机器绑定起来，同一区间一次只允许一个提案。每条命令都要校验这份固定计划；命令重试时，先读取持久状态，再从原阶段恢复。阶段只能向前推进，重复冻结应返回同一个最终日志屏障（barrier），新节点激活后也要拒绝迟到的快照覆盖。

存储侧的 freeze 与每次读写，共用同一份持久区间保护记录（range guard），并按同一顺序串行执行。这份保护记录必须由存储侧落实；Router 中的内存锁不能替代它。机器重启后要恢复 FROZEN 状态；有副本时，保护状态还必须进入同一复制日志，避免切主后重新放行旧请求。

Hash 18 moves S1→S3. Publishing ep8 first can produce empty reads and split writes between old and new Routers. This teaching design uses a brief range I/O pause and unavailability on ambiguity: S1 serves during preparation, then rejects new reads/writes and drains admitted work. S3 becomes active only after replaying the final log position and validating the range. A cache may relax reads only under a separate staleness contract.

The control record durably binds plan ID, range, old/new epoch, and owners using linearizable CAS, with one proposal per range. Every command validates this fixed plan; retries recover its durable state. Phases advance monotonically: repeated freeze returns the same barrier, and activation rejects late snapshot overwrites. At storage, freeze and every read/write share one durable range guard and serialization order, not a Router memory lock. Restart restores FROZEN; replicated deployments must put the guard into the same replicated log so failover cannot revive old authority.

# Teaching pseudocode; one range, durable state, unavailable on ambiguity.
# Control record serializes plans for this range via linearizable CAS.
handoff(plan, oldEpoch, newEpoch, oldOwner, newOwner):
    require newEpoch > oldEpoch
    require control.CAS(ACTIVE(oldEpoch), COPYING(plan))
    newOwner.stage(plan, snapshotAndLogFrom(oldOwner))
    # FROZEN is persisted in the SAME serialization order as old reads/writes.
    barrier = oldOwner.freeze(plan, oldEpoch)
    # freeze rejects later old I/O and waits for earlier admitted work to finish.
    newOwner.replayThrough(plan, barrier)  # updates, deletes, retry receipts
    require newOwner.verifyRangeAndBarrier(plan, barrier)
    require control.CAS(COPYING(plan), COMMITTED(newEpoch, plan, barrier))
    newOwner.activateOnlyIfCommitted(plan, newEpoch, barrier)
    publishCommittedManifest(newEpoch)   # lagging Routers get RETRY_EPOCH
    # Timeout: read durable plan state; never blindly unfreeze oldOwner.

# Both serving and freeze lock the same durable range guard.
serve(range, request):
    transaction on the owning shard:
        guard = lockRangeGuard(range)
        if guard.state != ACTIVE or request.epoch != guard.epoch:
            return RETRY_EPOCH  # applies to reads as well as writes
        if request.isRead: return readFullKey(request.key)
        receipt = lookupReceipt(request.operationId)
        if receipt exists:
            require receipt.payloadHash == request.payloadHash
            return receipt.result
        result = applyMutation(request.key, request.value)
        saveReceipt(request.operationId, request.payloadHash, result)
        commit mutation and receipt before returning result

快照与日志必须对应同一个一致起点，再追到冻结操作返回的最终日志屏障。迁移内容要包括更新、删除墓碑和幂等回执，回执的保留时间也要覆盖约定的重试期限。校验方法 verifyRangeAndBarrier 检查区间清单、内容以及日志位置是否连续。只有复制调用返回成功，还不足以证明数据就绪。控制记录提交后、新节点激活前，请求可能短暂被拒绝；恢复时只能执行与已提交计划匹配的命令，不能因超时就擅自退回旧环。

每次写入，都要把区间保护记录的校验、数据修改和操作回执放在同一分片事务或同一次串行日志应用中提交，图中的最终增量也必须包含这次提交。读取同样受这份保护记录约束。因此，ep8 的新写成功后，旧 Router 若仍访问 S1，会收到 RETRY_EPOCH，而不会读到旧快照。Router 随后刷新版本并限次重试，写请求保持同一个 operationId 和负载摘要。错误和超时都不能解释为“这个键不存在”。

Snapshot and log need one consistent starting position and replay through the freeze barrier. Transfer updates, deletion tombstones, and idempotency receipts; receipt retention covers the contractual retry period. verifyRangeAndBarrier checks the range manifest, content validation, and continuous log position, not merely a successful copy call. Requests may briefly fail between control commit and destination activation. Only matching-plan commands recover committed state; a timeout never authorizes reverting the ring.

The write guard check, mutation, and operation receipt commit within one shard transaction or serialized log application; the final delta includes that commit. Reads use the same guard, so an old Router visiting S1 after an ep8 write gets RETRY_EPOCH rather than a stale snapshot. Refresh with bounded retries, preserving operation ID and payload digest for writes. An error or timeout is not “key absent.”

请求轨迹或失败时机Trace / failure window系统必须怎样处理Required behavior

如果候选机器在冻结前失败，可以重试准备过程，旧节点继续服务；冻结后失败则要按原计划恢复，暂停时间可能延长。如果旧节点突然丢失且没有副本，环算法无法恢复数据。ep8 已经接收新写后，若要退回 S1，必须再做一次数据迁回和权限交接；旧文件仍在，不代表 S1 仍有写权限。只有新版本稳定、相关请求处理完毕且校验通过后，才能回收旧数据。

A candidate failure before freezing permits retried preparation while the old owner serves. After freezing, recover the same plan and accept a longer pause. Losing the old owner without a replica loses recoverability. Returning to S1 after ep8 accepts writes requires another migration and authority transfer. Retaining old files does not retain authority; reclaim them only after stable activation, draining, and validation.

实际系统怎样处理迁移：Redis slots 与 CassandraProduct boundaries: Redis slots / Cassandra

迁移过程需要明确的状态和协议Real systems expose migration states

Redis Cluster 先把键映射到 16,384 个固定哈希槽（hash slot），再把槽分配给节点。节点数变化时，键到槽的哈希公式保持不变。它采用的是固定槽位方案，与本章的随机放点的环不同。规范中的 MIGRATING、IMPORTING 状态和 ASK、MOVED 重定向，展示了数据搬运与路由更新之间怎样通过过渡协议衔接。[7] 本章借此说明，算出新映射后还需要迁移协议；前面的暂停读写模型并不是 Redis 的具体迁移过程。

Apache Cassandra 文档也区分环上位置（token）、节点网络地址（endpoint）和稳定身份（host ID），并介绍虚拟节点及成员信息传播。[6] 设计键值存储时，还需要补齐复制、故障检测和修复；缓存虽然可以丢弃后重新加载，仍要限制回源量。计划下线时可以先迁数据再删除成员，突发故障时却可能已无源机器可供复制。两种情况都能算出新的归属，但数据恢复的前提不同，不能共用“等源机器复制完”的保证。

Redis Cluster hashes into 16,384 fixed slots, then assigns slots to machines. Node count changes do not alter key-to-slot hashing; this is not a random-token ring. Its MIGRATING/IMPORTING states and ASK/MOVED redirects demonstrate the need for a transition protocol between moving data and updating routes. [7] Our I/O-pause model illustrates the requirement, not Redis’s exact migration procedure.

Cassandra distinguishes tokens, physical endpoints and host IDs and describes vnodes and membership propagation. [6] A KV design still needs replication, failure detection and repair. Cache values may be discarded, but origin capacity must be protected. Planned removal can copy before detaching; crash recovery may have no source available. Both compute new placement without sharing the same recovery guarantee.

算完迁移量，还要检查热点和回源容量Limited movement still needs hotspot and origin budgets

A6 的总读取量为每秒 10,000 次。如果十台机器负载均匀，平均每台 1,000 次，低于每秒 1,500 次的计划上限。一台故障且接管分散时，剩余机器平均为 10,000/9≈1,111 次/秒。但平均值无法证明每台都安全：如果每台只有一个节点位置，故障机器的 1,000 次/秒可能全部交给一个原本已有 1,000 次/秒的邻居，使它达到 2,000 次/秒，超过计划上限。虚拟节点可以改善接管分布，告警仍要关注最忙的那台机器。

A7 把 40% 的请求集中到共享热点键 post:9。这个键每秒有 10,000×0.4=4,000 次请求，其余 6,000 次均匀分布后，负责热点的机器合计约需处理 4,000+6,000/10=4,600 次/秒。给这台机器增加节点位置，无法拆开同一个键，反而可能让它再接到更多普通区间。新增机器也不保证热点键恰好迁走；即使迁走，目标机器仍需承受热点本身的每秒 4,000 次请求。

热门键主要被读取时，可以考虑请求合并、应用内短时缓存、专用副本或复制热点值，同时处理失效和陈旧数据。热门键主要被写入时，则先看业务是否允许拆分：计数可以拆成多个子键后聚合，要求单键原子顺序的余额却不能随意加随机后缀。拆键会改变数据模型，并增加读取工作；增加读副本则要调整读路由和复制协议。选择哪种做法，要从业务语义出发。

A8 还要计算缓存扩容期间的回源负载。新机器接到 1/11 的读取，起初没有缓存，这部分每秒约有 10,000/11=909.09 次请求全部回源。其余 10/11 仍保持 95% 命中率，每秒回源约 10,000×10/11×0.05=454.55 次。合计为 1,363.64 次/秒，约 1,364 次，是扩容前每秒 500 次的约 2.73 倍，也超过了数据库每秒 800 次的预算。虽然只有 9.09% 的归属变化，新机器缺少缓存仍足以让数据库过载。

如果先把新机器预热到命中率 h，总回源量就是 454.55+909.09×(1−h)。要控制在每秒 800 次以内，需要 h≥1−(800−454.55)/909.09≈62%。这个静态下限基于均匀读取假设，没有计入重试或其他故障余量。实际可以分批切换区间、限制冷数据回源，并让同一个键只由一个加载者回源；无法立即加载时，再按业务约定提供旧值或拒绝请求。验证预热效果要使用有代表性的请求分布，仅统计复制了多少个键还不够。

A6’s 10,000 reads/s across ten uniformly loaded machines averages 1,000/s, below a planned 1,500/s cap. After one failure with dispersed takeover, the average is 10,000/9≈1,111/s. This does not bound the busiest machine. A single-token ring could move a full 1,000/s onto an already 1,000/s neighbor, giving 2,000/s. Vnodes improve takeover distribution; monitor the maximum load.

A7 concentrates 40% on shared key post:9: 4,000/s plus about 6,000/10=600/s background gives its owner 4,600/s. More vnodes on that owner do not split the key. Adding machines neither guarantees that the hot key moves nor makes 4,000/s affordable at its destination.

Hot reads can use coalescing, short local caching, dedicated replicas or replicated hot values, with invalidation and staleness costs. Hot writes require semantic analysis: sharded counters can aggregate subkeys, but an atomically ordered balance cannot be arbitrarily salted. Splitting keys changes the data model and read amplification; read replicas change routing and replication.

In A8, a cold newcomer handles 1/11 of reads, all misses: 909.09/s. The remaining 10/11 retains 95% hits, producing 454.55 origin reads/s. Total origin load is 1,363.64/s, about 1,364, or 2.73× the previous 500/s and above the 800/s budget. Moving only 9.09% of ownership can still overload origin.

If the newcomer is warmed to hit rate h, origin load is 454.55+909.09×(1−h). Staying within 800 requires h≥62%. This static threshold assumes uniform reads and excludes retries and failure headroom. Switch ranges in batches, cap cold origin reads and use one loader per key, then serve stale data or reject according to the product contract. Warming must cover representative requests, not merely a count of copied keys.

方案变体：根据约束选择放置方式Variants answer a constraint, not replace the main story

连续逻辑桶、网络负载均衡和固定槽位，各有什么约束By constraint: Jump for sequential buckets, Maglev for network LB, slots for fixed granularity

本章选择环加虚拟节点，是因为节点有稳定名称、可以任意增减，同时需要明确区间和容量权重。Jump Hash 的输入是键和桶数，输出为 0…N−1；论文给出了很小的额外内存开销和期望 O(log N) 时间，前提是逻辑桶编号连续。[5] 因此，它适合在末尾追加桶；要任意删除中间的逻辑桶，则需要额外的映射层。物理机器故障后，仍可以由副本接管原逻辑桶，所以连续编号的约束并不意味着物理节点不能故障。

Maglev 面向软件网络负载均衡，使用预先计算的表快速选择后端。2016 年论文 §5.3 给出的默认表大小为 65,537。[8] 查表很快，成员变化时仍要构建、分发表，并处理连接跟踪；其归属变化性质也需要单独分析，不能直接套用本章保留固定节点位置的环的区间证明。网络负载均衡的细节见 Ch39。这里先区分两类需求：一类要为每个网络包快速选择后端，另一类要规划数据区间怎样迁移。

固定槽位表把“键→槽位”和“槽位→机器”分开。迁移一批槽位时，键所属的槽位无须重算，但槽位数量限制了分配粒度，槽位也可能过热，表本身仍需版本和迁移协议。无论选择哪种放置函数，可用性、读写一致性和热点保护都要另行设计。面试时先给出满足当前约束的方案，再说明什么条件下会换用其他方案，才能让选择有据可查。

This chapter chooses ring+vnodes for named, arbitrarily removable machines, explicit ranges and weighting. Jump Hash maps key and bucket count to 0…N−1 with minimal extra memory and expected O(log N) time, but requires sequential bucket IDs. [5] Appending buckets fits; removing an arbitrary logical middle bucket needs indirection. Physical failure can still be handled by replicas taking over the same logical bucket.

Maglev targets software network load balancing with a precomputed backend lookup table; its 2016 paper §5.3 uses 65,537 as the default table size. [8] Fast lookup still requires rebuilding, distribution and connection tracking. Its disruption properties should not be replaced with this ring’s exact interval argument. Ch39 covers packet-level balancing; here distinguish it from data-range migration.

Fixed slots separate key→slot from slot→machine. Moving slots preserves key-to-slot hashing, but granularity, hotspots, versions and migration remain. No placement function alone supplies availability, read/write consistency or hotspot protection. Select one design for the current constraints and state the conditions for alternatives.

面试追问：怎样验证归属变化确实有限Follow-ups: verify that changes are local

“怎样测试成员变化的影响？”先检查边界和环回：在 A2 的旧环中，哈希值 10、11、25、40、41、75、76、99 应依次归 S0、S1、S1、S1、S2、S2、S0、S0。再加入 S3@25，枚举全部 100 个位置，确认只有 11–25 改变归属。这能检验单调性；仅看各机器的键数是否接近，只能检查分布，发现不了多余的迁移。

“机器重启会怎样？”稳定身份和节点位置清单不变时，更新网络地址不应改变归属。如果以新身份加入，就要按一次删除和新增评估迁移量。“客户端版本不同呢？”跨语言测试应确认：相同的键字节和同一份清单，得到相同的哈希值、节点位置和负责机器。交接后，服务端必须拒绝或重定向旧版本请求，仅比较配置文件大小无法证明这些行为正确。

“为什么加一台机器不能立即缓解过载？”新机器还要初始化、复制或预热、追平更新，再切换流量，迁移本身也会占用源机器的资源。“用了虚拟节点，还要预留容量吗？”需要。故障后总容量少了一台，平均值也无法消除热点和分布不均。扩容实验至少应记录实际改变归属的键数、迁移字节数、最忙机器的负载、缓存命中率和回源 p99；只看到新机器健康，尚不足以验收。

“How do you test consistency?” Check A2 endpoints and wraparound: hashes 10/11/25/40/41/75/76/99 resolve to S0/S1/S1/S1/S2/S2/S0/S0. Add S3@25 and enumerate all 100 positions: only 11–25 change. This verifies monotonicity; similar average key counts test distribution but cannot detect needless reassignment.

“What about restarts?” Stable identities and tokens keep ownership while endpoints change; new identities require deletion/addition analysis. Cross-language vectors must agree on hash, token and owner for the same bytes and membership. After handoff, servers must reject or redirect stale epochs rather than merely compare configuration sizes.

“Why not add a machine immediately?” Initialization, copying or warming, catch-up and activation take time and consume source resources. Vnodes do not replace headroom: failure removes capacity and averages conceal hotspots. Measure changed keys, bytes, maximum owner load, hit rate and origin p99; a healthy newcomer alone is insufficient.

复盘：分别讲清归属、容量和交接Close on placement, capacity and handoff

保留旧桶编号时，从 10 台扩到 11 台，取模预计会改变约 90.91% 的键归属。一致性哈希保留旧节点位置，在等容量随机模型中，只需迁移新机器预计接管的 9.09%。定位时，Router 在本地有序表中找到第一个不小于哈希值的点，再直接联系负责机器。虚拟节点能把一台机器的责任分散到多个区间，改善分布和故障接管，但同一个热门键仍由同一台机器负责。扩容还要先复制或预热，冻结旧读写并追平更新，再激活新成员版本。本例中，冷缓存会把回源量从每秒 500 次拉高到约 1,364 次，因此迁移少，也仍要限制回源。

合上页面后，可以先手算 hash=90 怎样环回，再指出新增 S3@25 时哪一段改变归属，最后解释为什么新机器就绪前，hash=18 仍由 S1 服务。讲清这三条过程，就能继续学习下一章的复制与 quorum 读写机制。Ch02 介绍了按用户分片的直觉，Ch03 区分键数、字节数和 QPS；本章解决数据放在哪里，复制和网络分区中的故障行为则要继续设计。

With stable old IDs, modulo 10→11 remaps about 90.91%. Keeping old ring tokens fixed moves only the newcomer’s expected 9.09% under an equal-capacity random model. Lookup finds a successor locally, not through server forwarding. Vnodes spread responsibility and takeover without splitting one hot key. Expansion copies or warms, freezes old I/O, catches up, then activates the next epoch. In this example a cold cache raises origin from 500/s to about 1,364/s, so limited movement still needs a capacity cap.

Close the page and resolve hash 90, identify the range captured by S3@25, then explain why reads remain on S1 until readiness. These paths connect placement to the next chapter’s replication and quorums. Ch02 introduces user sharding and Ch03 separates counts, bytes and QPS. A placement function does not settle replication or partition failures.
