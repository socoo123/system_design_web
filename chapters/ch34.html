中文

我设计一个处理客服诊断和退款的 Agent Runtime。开放诊断用有界循环，模型提出下一工具；退款用固定 workflow，模型只在节点里抽字段，资格、批准和打款的边由代码决定。用户提交得到持久 run_id，worker 领取 owner 代次，每次模型调用前占预算，工具调用前固定业务 intent，结果确认后才写 observation。写需要人工批准时把 run 持久挂起并释放活跃槽；恢复先查未清动作，副作用需要撤销时按业务依赖补偿，不能重跑整段对话。

先问六件事：路径是否已知、哪些工具会写、批准针对什么动作、run 是否跨进程或隔夜恢复、下游是否支持防重与回执查询、用户取消后必须停止什么。默认单角色足够；有真正的指令或权限分叉再 handoff。设单地域、有持久关系库、工具串行，客户端连接与执行解耦；多地域双写会增加 owner 与恢复问题，等这张图闭合之后再讨论。

Ch32 提供模型网关，Ch33 提供受审工具、审批和远端执行契约；本章负责跨这些调用保存“走到了哪里”。Ch25 的调度机制可复用，但 cron 不能替代模型步数、批准等待和副作用账本。选择依据是路径控制与恢复重放边界。[1]

English

Design a customer-support diagnostic/refund runtime. Open diagnostics use a bounded model-selected tool loop; refunds use code-defined eligibility/approval/payment edges with models inside nodes. Persist run_id, claim an owner generation, reserve model budgets, pin business intents before tools, and commit confirmed observations. Park approval waits outside active slots. Recovery first reconciles pending actions; business-dependent compensation never reruns the whole conversation.

Clarify known paths, writes, action-bound review, cross-process/overnight recovery, backend deduplication/receipt support and cancellation semantics. Begin with one role; hand off only for meaningful instructions/authority differences. Assume one region, durable relational storage, serialized tools and detached client connections. Discuss cross-region ownership only after closing this design.

Ch32 supplies LLM GW; Ch33 owns reviewed tools, approvals and execution contracts. This chapter persists orchestration progress. Ch25 scheduling mechanisms are reusable, but cron does not supply model budgets, approval waiting or an effect ledger. Framework names illustrate mechanisms; the deciding question is who controls progression and what replays [1].

中文

这些数字都是白板 assumption，不是某家公司吞吐或 SDK 默认。平均在途只能用同一边界、稳定区间的到达率乘平均驻留时间；本章把 run 的活跃时间、审批等待与物理 RPC 分开。所有全局预算都持久保留，暂停和换角色不清零前向预算。

English

These are whiteboard assumptions, not production throughput or SDK defaults. Mean concurrency needs a consistent boundary and stable interval. Separate run active time, approval wait and physical RPCs; persistent global budgets survive pauses and role changes.

持久接单：请求结束，run 才开始 Durable admission: the request ends before the run does

正常路径：接单与完成的承诺 Normal path: admission and completion are different promises

中文

客户端用业务 request_key 提交 POST /runs。Run API 从可信身份取 tenant、actor，把唯一映射 (tenant, request_key) → run_id、初始状态与 READY 事件写在同一事务里；同键参数摘要不同就冲突，不能悄悄复用另一任务。提交确认后返回 202 和状态地址，客户端断线也能查同一 run。只有接收进程内存里有任务、再异步写库，进程死一次就会出现已接单但永远没有结果的任务。[6][8]

Runtime 收到提醒后条件领取 READY 行，读当前 checkpoint 与版本。先拿租约再调 LLM GW，返回 tool_call 时做结构、工具数及预算验证，把具体动作写成持久 intent 后交 Tool GW。observation 经 Runtime 写回 Run Store，再开始下一拍模型。用户的 GET /runs/{id} 经 Run API 读权威状态返回，模型结果不直接绕到客户端。每个外部调用都有本地前置记录，正常结果也有确定提交点。

English

POST /runs uses a business request_key. Run API derives tenant/actor and atomically writes the unique key-to-run mapping, parameter digest, initial state and READY event. Conflicting same-key input is rejected. A confirmed commit returns 202/status location; reconnects recover the same run. Memory-first admission followed by asynchronous persistence can lose accepted work [6][8].

Runtime conditionally claims READY and loads checkpoint/version before LLM GW. Validate proposals, tool count/state/budgets and persist the exact intent before Tool GW. Commit observations before the next model step. GET /runs/{id} reads authority through Run API; model results do not bypass it. Every external call has a durable precondition and result commit.

选择与代价：一个权威库先换来清楚的恢复边界 Choice and cost: one authority gives a clear recovery boundary

中文

约束是跨进程与隔夜恢复，所以不能把 messages 与当前 step 只留在 worker。关系库先承载 run 状态、step/action 记录、消息索引与 outbox，原始大文本可以存成不可变对象并用校验和引用；对象确认可读后再提交引用，失败留下的孤儿对象后续清理。不要每步重写整份历史：增量消息带唯一 event_id，checkpoint 固定所覆盖的末序号，读者用快照加连续增量重建，缺序号就停止恢复。

代价是每步多一次持久化、需要留存与迁移。只有短只读任务、明确允许丢进度时，内存循环才是较轻的方案；持久 workflow 引擎也可以提供调度与 checkpoint，但接入后仍要理解它的重放边界。LangGraph 文档将线程 checkpoint 与跨线程 store 分开，并明确内存 saver 重启会丢失。[3] memory 不能自动提供恢复承诺。

English

Cross-process recovery and overnight approval require durable messages/progress. Start with one relational authority for runs, steps/actions, message indexes and outbox. Large immutable objects are referenced only after readable acknowledgment/checksum; clean orphaned objects later. Append unique event IDs instead of rewriting history, and rebuild from a snapshot plus contiguous deltas; gaps block recovery.

Costs include persistence latency, retention and migrations. Memory loops fit explicitly disposable short read tasks; a workflow engine may supply checkpoint/scheduling while its replay boundary still matters. LangGraph distinguishes thread checkpoints from cross-thread stores and warns that in-memory savers lose state on restart [3]; generic memory is not the recovery guarantee.

失败窗口：提醒可以丢，持久接单不能丢 Failure window: hints may be lost, accepted work must remain

中文

Run API 的 wake 只是降低排队延迟，扫描器仍按 A12 每 5 秒扫描可运行行。若事务已提交而提醒没发出，扫到 READY 就能启动；若提醒重复，条件领取只让一个 owner 成功。READY 扫描要分页、限速，监控最老可运行年龄，不能故障恢复后一口气拉满模型网关。图里未单独画扫描器，因为它只补同一 Runtime 的候选入口，权威仍是 Run Store。

Run Store 写不可用时，新接单不能先回 202，已运行 worker 也不能继续发新的副作用；保留已发动作的可查询身份，等待恢复后核账。异步读副本可用于明确标陈旧的进度展示，但不能决定领取、批准恢复或 DONE。租约到期不是证明旧进程已停止，所以所有提交都要带 owner epoch 和预期 version，下一组恢复图会把这个窗口画实。

English

Wakeups only reduce queue latency; A12 scans runnable rows every five seconds. Missing/duplicate hints are repaired by scanning/conditional claim. Page and rate-limit scans and alert on oldest runnable age rather than saturate LLM GW after recovery. The scanner supplies the same Runtime candidate path; Run Store remains authority.

If authoritative writes fail, do not acknowledge new acceptance or dispatch new effects. Preserve queryable identities for already-sent actions and reconcile after recovery. Explicitly stale progress may use read replicas; ownership, approval resume and DONE may not. Expiry does not prove old processes stopped, so commits require epoch/expected version.

有界循环：模型提议，Runtime 决定继续或停 Bounded loop: models propose, Runtime decides continuation

正常路径：先占预算，再调用，再提交 Normal path: reserve, call, commit

中文

step 是一次逻辑模型调用，先原子增加 step_count 并记录输入 revision，再发请求。相同 step 的供应商重试是物理 attempt，要另计费用与次数；模型输出未持久化前进程死了，可以为同一逻辑 step 再请求一次，但必须把额外费用记到账，并且只有第一个合法 CAS 输出能固定下一动作。工具尚未发出前允许模型输出变化，已经持久的业务 intent 则不能跟着新的模型答案变化。

一拍模型可能给多个工具，也可能给终答。本章按稳定 action_id 串行执行，每个 invoke 另占工具计数；后端回执查询属于恢复工作，不让它占一个新的业务副作用身份，仍消耗操作与墙钟预算。已知结果组成完整 observation bundle，消息里保留 call/result 对应关系，提交成功后才回到预算门。终答通过输出 schema 与流程完成条件后保存，未到退款终态的“已处理好”必须拒绝，不把没 tool_call 当作业务已成功。

English

Define a step as one logical model call. Persist step_count/input revision before dispatch. Supplier retries are physical attempts with separate cost/count. A crash before output persistence may reissue the same logical step, accounting for costs; only the first valid CAS output pins progression. Undispatched model proposals may differ, but persisted business intent must remain stable.

Serialize multiple tool proposals by stable action_id with separate invocation budgets. Recovery queries consume operation/time budgets without inventing a new effect identity. Persist complete matched call/result observations before continuation. Validate schema and workflow completion before persisting final output; tool-free prose does not prove a refund completed.

为什么四种预算一起用 Why four budgets are needed

中文

12 次模型 step 只能限制模型轮次，不能限制单拍十个写工具；8 次 invoke 又挡不住一个请求卡住两分钟。因此同时设逻辑步数、工具动作数、活跃时间和 token/费用预算，每次发出前复查。输入 12,000 token 是投影上限，不是每次调用都会用满；实际预算预留已知输入加允许的最大输出，响应后按可信 usage 结算，usage 缺失保留未清费用，不凭“超时”退款。Ch32 已有物理重试与配额账，本章不在外层再套无界重试。

ReAct 论文把推理与行动交织，通过环境观察更新后续行动；这不要求保存模型私有思考过程。[2] 本章只存允许保留的消息、工具调用、结果与可审计决策摘要。停止条件由代码执行：达到终态、预算用尽、用户取消或检测无进展。AI SDK 文档给出 stopWhen 与 prepareStep 等控制点，[5] 这里只引用有界控制的机制，教学 12 不冒充其通用默认或业务 SLA。

English

Twelve model steps do not bound ten tool writes in one output; eight tools do not bound a two-minute hang. Enforce steps, tools, active time and token/cost budgets before each dispatch. The 12,000-input-token cap is a maximum, not average consumption. Reserve input plus allowed output and settle trusted usage; missing usage keeps costs unresolved. Ch32 owns physical retries/quota accounting; do not add unbounded outer retries.

ReAct interleaves reasoning/actions with observations [2] without requiring private model reasoning retention. Store permitted messages, calls, results and decision summaries. Code enforces completion, budget, cancellation and no-progress rules. AI SDK stopWhen/prepareStep illustrate control mechanisms [5]; twelve is our assumption, not an SDK default or SLA.

边界：重复不一定卡死，停止也不一定没有副作用 Boundary: repetition may progress, stopping may leave effects

中文

stuck 指纹规范化工具名、参数和相关业务 revision（排除 step_count 等记账变化），结合观察进展连续检测三次。查长任务状态三次可能恰好从排队走到完成，不能只 hash(tool,args) 就认定卡死；反过来模型每次换一句话、同一业务状态完全没动，也不能逃过检查。它是减少浪费的启发式，硬上限仍由预算保证。停止时保存原因、剩余预算和待核动作，向用户给可恢复的状态地址。

取消与工具 dispatch 也有竞态。取消事务先赢，后续条件 dispatch 必须失败；dispatch 先被持久确认，则取消是尽力终止，远端可能已经写完。Runtime 进入 CANCEL_REQUESTED 后先核账，再由业务策略决定补偿或人工。不能因为客户端关了页面就把后台 run 删除，更不能把 UNKNOWN observation 传成“未执行”，诱导下一角色再次写。

English

Canonicalize tool/arguments and relevant business revision excluding bookkeeping such as step_count and inspect three repetitions without progress. Polling a job may legitimately advance queued to done; text variations may hide an unchanged business state. This is a waste-control heuristic; budgets enforce hard limits. Persist stop reason, remaining budgets and pending obligations with a recoverable status URL.

Cancellation races dispatch. A winning cancel blocks subsequent conditional dispatch; a previously committed dispatch may already have effects despite best-effort cancellation. CANCEL_REQUESTED first reconciles, then compensates/escalates by policy. Closing a client page must not delete the run or turn UNKNOWN into unexecuted.

已知流程：模型在节点里工作，代码固定业务边 Known workflows: models inside nodes, code owns business edges

从资格到通知，谁允许下一条边 From eligibility to notification: who authorizes each edge

中文

退款先核原订单、已退款金额与资格，再审批具体 intent，执行退款，确认业务回执后通知。模型可以抽订单号、分类申诉或草拟回复，但资格规则是确定代码，不能由它生成新的 workflow 边。transition 同时验证当前节点、workflow_revision、输入证据和 owner，提交后才启动下一节点。节点内探索用有界 loop，共享总预算，结果仍由外层验证。

图中 Eligibility 向 Model task 取字段并接回结果，接下来横向箭头都是持久控制状态转换，不是 HTTP 回程。批准边只表示拿到授权，不表示已经退款；Refund UNKNOWN 时留在回执核查，Notify 只有确认退款成功才启动。通知成功的回执使流程到 DONE，已知通知失败则进 REPAIR，仅补通知。用户要的退款已经成立，邮件故障不是撤销退款的业务理由。

English

Refund eligibility checks the order, prior refunded amount and policy before exact-intent approval, refund and receipt-gated notification. Models may extract IDs/classify/draft, but code defines legal edges. Transitions check current node, workflow revision, evidence and owner before committing the next node. Node-local exploration shares global budgets and its output is validated by the outer workflow.

Eligibility’s model call has a return; horizontal arrows are persisted control transitions. Approval authorizes but does not complete a refund. UNKNOWN stays in refund reconciliation. Confirmed refund permits Notify; notification receipt yields DONE, known notification failure yields notification-only REPAIR. A failed email is no business reason to undo a valid refund.

选择、替代与流程升级 Choice, alternatives and workflow upgrades

中文

约束是退款必须通过固定审查，所以选择 workflow，代价是需要维护状态与版本，新增政策不能只改 prompt。开放客服诊断则事先不知道先查账单还是网络，强行写死路径容易脆，应让模型选候选、Runtime 验执行门。两者不按“有没有 LLM”区分，而按谁决定路径。[1] 单次字段抽取可以就是一次调用，不必把每个请求都包装成复杂图引擎。

升级流程时，新 run 固定新 revision，老 run 保留原规则或经过显式迁移。等待批准的动作参数与政策绑定在旧 revision，不能部署后自动按新代码越过检查。需要迁移就暂停、验证历史证据是否仍满足新要求、重建待批意图，再提交迁移记录。测试先覆盖合法与拒绝边，再注入每个外部调用前后崩溃、批准/取消竞争和重复回执，检查不变量，而不是仅看模型能否说出一句顺口回复。

English

Mandatory review favors workflows at the cost of maintaining states/revisions; prompt edits cannot silently change policy. Open diagnostics have unknown tool order and favor model proposals with runtime admission rather than brittle exhaustive graphs. The distinction is who selects the path [1], not whether an LLM exists. Simple extraction may remain one call.

Pin revisions for new runs and retain old rules or migrate explicitly. Pending approvals bind old arguments/policy and cannot skip checks after deployment. Migration pauses, revalidates evidence, rebuilds pending intent and commits migration records. Test legal/rejected edges plus crashes, cancel/approve races and duplicate receipts against invariants.

崩溃恢复：checkpoint 不替远端保证恰好一次 Crash recovery: checkpoints do not guarantee one remote effect

持久状态必须包含下一动作，而不只是聊天记录 Durable state must include the next action, not just chat

一分钟收尾：走正常链，再指定一个崩溃点 One-minute wrap-up: normal path plus one crash point

中文

从 Client 到 Run API 持久接单，worker 领取 owner，预算门放行模型，工具 intent 先落库，回执回来提交 observation，下一拍再检查预算。开放问题走 loop，退款固定 workflow；handoff 改角色但不改 run 与总预算。审批先持久暂停后释放槽，用权威决定与状态 CAS 唤醒；未知副作用先核账，需要撤销的按业务依赖补偿，未清义务持久交人工。

追问扣款后崩溃，指恢复图的 Business DB 与 Run Store：B 拿 epoch 8、读 pending k9、查回执、提交一次 observation；A 的 epoch 7 不能推进，本地 fence 也不能撤销已发网络请求。最后报 100 逻辑模型/s、60 工具/s、约 221 正常活跃、1,800 平均待批，并说明额外模型重试给 110/s 与约 241 活跃。用这一个窗口解释预算、权限与状态。

English

Walk Client → Run API durable admission → owner claim → model budget → persisted tool intent → receipt → observation commit → next budget check. Open paths loop; refunds follow fixed workflow. Handoff preserves run/budgets. Persist approval parking, resume from authoritative decisions/CAS, reconcile unknown effects, compensate by dependencies and durably escalate obligations.

For a crash after charge, point to Business DB versus Run Store: B claims epoch 8, reads pending k9, queries receipt and commits one observation; epoch 7 cannot advance, and local fences cannot undo sent packets. Quote 100 logical model/s, 60 tools/s, about 221 normal active and 1,800 parked; added attempts give 110/s and about 241 active. Tie one concrete window to budgets, authority and state.
