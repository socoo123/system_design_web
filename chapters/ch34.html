设计 Agent 编排与运行时Agent orchestration and runtime

约 40 分钟 · 前置：Ch25、Ch32、Ch33 · 7 组 / 37 帧渐进白板图~40 min · after Ch25, Ch32, Ch33 · 7 decks / 37 progressive frames

本章核心：从已提交的状态继续运行Core: advance only from committed state

运行时（Runtime）负责持久保存并推进一次运行（run），模型只提出候选结果。这里有三个关键决定：先保存任务再确认接单，固定外部输入和动作身份，每次推进前检查持有者与版本。 这样，即使工作进程（worker）重启、任务等待人工批准，或工具调用超时，运行时也能找到应该继续的位置。

  • 先读 Ch32 的模型预算，以及 Ch33 的工具、批准和副作用契约。
  • 本章以客服诊断和退款为例：诊断路径未定时，用有界循环逐步探索；退款必须经过哪些业务步骤，则由工作流固定。
  • 取消后停止新工作；已经发出的动作先核对执行结果，确认产生了业务效果后，再按业务规则补偿。

Runtime persists and advances a run; the model proposes candidates. Three decisions: persist acceptance, pin external inputs/action identities, and check ownership/version at every transition. Recovery can then find the correct continuation after crashes, approval waits or tool timeouts.

  • Ch32 owns model admission; Ch33 owns tools, approval and effect contracts.
  • Support diagnosis uses a bounded loop; refund policy uses fixed workflow edges.
  • Cancellation stops new work. Reconcile sent actions before compensating confirmed effects.

范围与规模：单地域内串行推进Scope and load: one region, serial progression

用户提交任务时携带业务请求键 request_key，取得对应持久运行记录的 run_id 后轮询状态。执行能持续多久，由运行记录决定，不依赖客户端连接是否还在。本例假设只有一个权威关系数据库，每次运行只有一个有效持有者（owner），工具也串行执行。设计前要先问清：路径是否固定，哪些工具会写入业务数据，批准覆盖哪个动作，是否需要隔夜恢复，下游能否查询回执，以及取消后必须停止到哪一步。

工作流与 Agent 的区别在于由谁选择下一步路径；如果只是抽取一次字段，一次模型调用可能就够了，无需引入图引擎。[1] 本章假设每秒到达 20 次运行，每次平均调用模型 5 次、工具 3 次，因此逻辑模型调用为每秒 100 次，工具调用为每秒 60 次。这些都是教学假设。由后文的耗时还能算出，平均约有 221 次运行处于活跃状态、1,800 次等待批准，两类运行分池管理。

A user submits a request_key and polls a durable run_id; connection lifetime is independent of execution. Assume one authoritative relational database, one valid owner per run and serial tools. Clarify path control, writing tools, approval scope, overnight recovery, receipt lookup and the required cancellation boundary.

Workflows and agents differ in who selects the path; extraction may need only one call. [1] Teaching assumptions of 20 runs/s, five model calls and three tools/run give 100 logical model/s and 60 tool/s. About 221 active and 1,800 parked runs belong in separate pools.

持久接单与领取：返回 202 承诺了什么Durable admission and claim: what 202 promises

图 1 中，运行状态以 Run Store 为准。 运行接口 Run API 在同一个事务中写入请求键到运行 ID 的映射 (tenant,request_key)→run_id、可信的操作者身份（actor）、请求摘要、READY 状态和待发送事件（outbox）。同一请求键若换了主体或内容，就应报告冲突。只有确认提交后才返回 202；回包丢失时，客户端查询原运行即可。唤醒消息只是提醒：后台每 5 秒分页扫描 READY 记录，补回遗漏的提醒；条件领取则保证重复提醒不会产生多个有效持有者。[6][8]

下面这条 SQL 会在可执行的 SQLite 适配程序中原样运行。程序先取得写事务锁，再由数据库采样当前时间。工作进程必须既取得返回行，又确认 COMMIT，才有权开始工作；返回 0 行表示没有取得持有权。[12] 旧持有者租约到期后，接管者仍沿用原有动作和预算。运行已过期或已取消时，只能核对既有动作的结果，不能发起新业务。

Run Store is the authority in deck 1. One transaction writes tenant/request-key mapping, trusted actor, request digest, READY and outbox; changed identity/content conflicts. A confirmed commit precedes 202; lost replies read the original run. Wakeups are hints; five-second paged scans repair loss and conditional claims absorb duplicates. [6][8]

The executable SQLite adapter runs this SQL verbatim after acquiring its writer transaction; time comes from the database. Only a returned row plus confirmed COMMIT permits work. Zero rows means no ownership. [12] Takeover preserves actions/budgets; expired or cancelled runs may reconcile but cannot start new business.

-- SQLite 3.38+ adapter: acquire BEGIN IMMEDIATE before this statement.
-- READY starts forward work; expired active owners may only reconcile first.
WITH clock(now) AS (SELECT unixepoch('now'))
UPDATE runs
SET owner = :worker,
    epoch = epoch + 1,
    version = version + 1,
    lease_until = (SELECT now FROM clock) + 15,
    status = CASE WHEN status = 'READY' THEN 'RUNNING' ELSE status END
WHERE run_id = :run_id
    AND version = :version
    AND (
        (status = 'READY' AND cancelled = 0
            AND deadline > (SELECT now FROM clock))
        OR (status IN ('RUNNING', 'CANCEL_REQUESTED', 'COMPENSATING')
            AND lease_until <= (SELECT now FROM clock))
    )
RETURNING *;
-- Zero rows: lost the race / not runnable. Do not invoke anything.
-- COMMIT acknowledgment must be known before dispatch; otherwise read back.

这条 SQL 的原子边界是同一个数据库内的条件更新。先 SELECT、再无条件 UPDATE，并不等于比较并交换（CAS）；即使用生产数据库的行锁，也必须检查实际影响的行数。[7] 此后每次提交结果，都要重新检查租约代次 epoch、状态版本 version、角色版本 role_revision、租约有效期和运行状态。Run Store 无法写入时，停止发起新调用。有复制延迟的副本只能展示已标明陈旧的进度，不能据此批准动作、领取任务或判定运行已完成（DONE）。

This is a single-database conditional update. A SELECT followed by an unconditional UPDATE is not CAS; inspect affected rows with production row locks too. [7] Outcome commits recheck epoch, version, role revision, lease and status. Stop new calls if authority cannot be written. A stale replica may display labelled progress, never decide claim, approval or DONE.

有界步骤：固定输入，提交输出后才继续Bounded steps: pin input, commit output, then continue

一个模型步骤（step）是一次逻辑调用，一次尝试（attempt）才是物理请求。 调用前的事务先占用一个步骤名额，并固定模型、工具和工作流的版本，以及按权限投影的消息、检索结果、已记录的时间和随机值。恢复时仍读取这些输入。如果输出已经提交，就直接复用，不能为了“回放”再问一次模型；如果输出尚未保存，可以重新请求，结果也可能不同，但要另记费用，并且只允许一个通过 CAS 检查的提交结果固定后续动作。

下面的代码对应图 2 的预算门和 Commit 提交点。运行时要先验证输出结构（schema）、工作流允许的转换，以及 tool_call 数量。稳定的业务意图（business intent）来自可信业务交互，不能用模型生成的 call_id 或参数哈希重新定义。模型请求发生在两个本库事务之间；用一个 transaction 包住网络调用，也无法让网络和数据库提交变成原子操作。

A model step is logical; an attempt is physical. Admission reserves one step and pins model/tool/workflow revisions, authorized messages, retrieved evidence and recorded time/random values. Recovery reads the same input. Reuse committed output; missing output may be regenerated and differ, but charge the attempt and let only a valid CAS winner pin actions.

This contract covers deck 2’s budget gate and Commit. Validate output schema, legal workflow edges and call count. Trusted business interaction defines intent; model call IDs or argument hashes do not. External requests sit between two local transactions; no transaction makes the network atomic.

advance(run, owner, epoch, roleRevision, expectedVersion):
    BEGIN RunStore transaction;
        lock run
        require current owner/epoch/roleRevision, version=expectedVersion, live lease
        require RUNNING, not cancelled, before deadline
        if unresolved action exists:
            COMMIT;
            return RECONCILE_OR_WAIT

        step = current logical step
        if step exists:
            require matching revisions, or perform explicit migration
        if step exists and step.output is stored:
            COMMIT;
            return stored output + actions
        if step does not exist:
            require step_count < 12;
            increment step_count
            INSERT step with workflow/model/tool revisions, messages,
                retrieved evidence, recorded time/random values, input hash

        require physical attempt and token reservation within remaining caps
        INSERT attempt;
        reserve input + max_output tokens;
        bump run version
        attemptVersion = updated run.version;
        retain exact owner/epoch/role token
    COMMIT;
    on uncertain acknowledgment, read step/attempt before sending

    output, usage = LLM_GW.call(step.immutableInput, attempt.id)  // outside TX
    record trusted usage by attempt.id;
    missing usage keeps its reservation
    proposals = validate(output, pinned schema and allowed workflow edge)

    BEGIN RunStore transaction;
        lock run and step
        require current owner/epoch/roleRevision, version=attemptVersion, live lease
        require RUNNING, not cancelled, before deadline
        if step exists and step.output is stored:
            COMMIT;
            return stored output + actions

        UPDATE step SET output = proposals WHERE output IS NULL
        INSERT exact actions with stable business intent, binding and PREPARED
        INSERT checkpoint + next-state event;
        bump run version
    COMMIT;
    only the committed winner may advance

    // Tool dispatch separately checks state, budget, approval and Ch33 contract.
    // Renewal/version changes require revalidation; never reuse the old entry version.
    // No saved output: a new attempt may differ/cost more; never replace an intent.

因为一次模型响应可能提出多个工具调用，12 次模型调用之外，还要分别限制 8 个前向动作、120 秒活跃时间和 60,000 token，并管理费用预算。每个物理尝试都要持久预留“已知输入加最大输出”的 token，再按可信用量（usage）结算；如果用量缺失，就保留这份占用。暂停和角色交接都不清零预算。供应商重试由 Ch32 负责，运行时不再在外面套一层无界重试。ReAct 的行动与观察交织，以及 AI SDK 的 stopWhen/prepareStep，只用于说明机制，不能替代持久状态和硬预算，也不要求保存模型的私有思考。[2][5]

同一工具、规范化参数和业务版本连续重复 3 次且没有进展，只是判断运行卡住的启发式规则；业务版本在推进的轮询应允许继续。STOPPED 仍保留停止原因和未清义务。复用已保存输出是本设计的契约，不能泛化为所有框架的行为：LangGraph 从旧检查点显式回放（replay）时，会重新执行之后的 LLM/API/interrupt 调用；sync、async、exit 的持久化时机也不同。因此，同样叫作 checkpoint，不代表都提供本章的保证。[11]

Twelve model steps cannot cap a multi-tool response; separately bound eight forward actions, 120 active seconds and 60,000 tokens/cost. Persist reservations per physical attempt and settle trusted usage; missing usage retains the hold. Pause/handoff never resets budgets. Ch32 owns supplier retries. ReAct and AI SDK stopWhen/prepareStep illustrate control, not durability or hard admission, and do not require private reasoning storage. [2][5]

Three repeated tool/argument/business-revision fingerprints without progress are only a stuck heuristic; versioned polling may progress. STOPPED retains reasons/obligations. Stored-output reuse is this design’s contract: explicit LangGraph replay from an older checkpoint re-executes later LLM/API/interrupt calls, and sync/async/exit persist at different times. [11]

路径已知时：由代码固定工作流的业务转换Known workflows: code owns business edges

退款必须依次经过资格检查、具体动作审批、确认退款回执和发送通知，模型不能跳过其中的业务步骤。 模型只在资格节点 Eligibility 中抽取字段，代码则验证证据、当前节点、工作流版本 workflow_revision 和运行持有者，再持久提交状态转换。退款结果为 UNKNOWN 时继续核查，不能发送“退款成功”；退款已成功而邮件失败时，只进入通知修复状态 REPAIR，不机械撤销退款。

新运行固定使用新流程版本，旧运行继续保留原版本，或经过显式迁移。迁移时先暂停，检查历史证据和已有批准是否仍适用，再提交新状态。仅修改提示词，不能绕过资格检查或审批。路径未定的诊断适合有界循环，必须经过固定审查的路径适合工作流；后者的代价是需要维护流程版本及其合法转换。[1]

Eligibility → exact-action approval → refund receipt → notification are code-owned edges. The model extracts fields within Eligibility. Code validates evidence, node, workflow revision and owner before persisting a transition. UNKNOWN refund stays in reconciliation; failed email after successful refund repairs notification only.

New runs pin new revisions; old runs retain their revision or migrate explicitly after parking and validating prior evidence/approval. Prompt edits cannot bypass policy. Open diagnosis suits a bounded loop; mandatory review suits workflow at the cost of revision/edge maintenance. [1]

故障恢复：本地检查点与远端业务效果分别确认Recovery: checkpoint and remote effects are separate records

图 4 的关键窗口是：Business DB 已提交 k9，Run Store 中的动作却仍待确认。 接管者先读取原动作的业务键、完整绑定信息（binding）和参数，再向 Ch33 查询权威回执；确认成功后，才补写一次工具观察结果。查不到回执，也可能是旧请求仍在传输，不能据此认定动作没有执行。只有防重契约仍有效时，才允许按同一业务键有界重放；否则保留 UNKNOWN，并转入 NEEDS_REVIEW。不能改业务键、换目的端 route，或让模型重新生成动作。

运行记录 Run 保存运行状态、节点和角色版本、持有者、租约代次、租约期限、状态版本，以及全局预算。步骤记录 Step 保存固定输入与输出；动作记录 Action 保存业务意图、工具与目的端、参数、资源和策略版本、动作状态及回执。动作结果、消息索引、检查点末序号和后续事件在同库事务中提交，唯一的工具观察结果记录防止本地重复推进。

大文本可保存为不可变对象引用，但提交引用前必须确认对象可读。恢复时用快照加连续增量重建状态，发现序号缺口就停止。线程检查点与跨线程存储 store 承担不同职责，不能混为一谈。[3]

Deck 4’s critical gap: Business DB committed k9 while Run Store remains pending. A new owner reads the original key, full binding and arguments, then queries Ch33 receipts. Confirm success before inserting one observation. Absence may mean an old request is still in flight. Bounded same-key replay requires a still-valid dedupe contract; otherwise retain UNKNOWN/NEEDS_REVIEW, never change key/route or regenerate the action.

Run holds state, node/role revisions, ownership and budgets; Step pins input/output; Action holds intent, tool/route/arguments/resource/policy revisions, status and receipt. Commit outcome, message index, checkpoint sequence and next event in one database transaction. Unique observations prevent duplicate progression. Large content uses acknowledged immutable objects; snapshot-plus-deltas recovery stops at gaps. Thread checkpoints and cross-thread stores have different roles. [3]

recover(run, action, newOwnerEpoch):
    // Claim first; retain original action key, binding, budgets and revisions.
    receipt = Ch33.query(action.key, action.exactBinding)  // outside RunStore TX

    if receipt is absent or inconclusive:
        if not cancelled and contract permits bounded same-key replay now:
            BEGIN RunStore transaction;
                lock run and action
                require recovery owner/epoch/version, live lease, not cancelled, before deadline
                INSERT bounded replay attempt referencing original key and binding
            COMMIT;
            confirm acknowledgment before sending

            retry original action through Ch33;
            never change key/route/arguments
        else:
            persist UNKNOWN + NEEDS_REVIEW + escalation outbox;
            return
    else:
        BEGIN RunStore transaction;
            lock run and action
            require current recovery owner/epoch/version and live lease
            INSERT observation UNIQUE(run_id, action_id), or read matching prior one
            UPDATE action with authenticated known outcome and receipt
            if success:
                INSERT confirmed effect ledger entry
            if cancelled:
                preserve cancel flag;
                never schedule a new model step
            INSERT checkpoint + next legal recovery event;
            bump run version
        COMMIT

    if cancelled and confirmed effects require undo:
        choose next action from persisted business dependencies
        persist stable compensation key linked to original effect
        dispatch through Ch33 with its own approval and bounded recovery budget
        // UNKNOWN compensation blocks dependents; query the same compensation key.

    if undo cannot safely finish:
        persist NEEDS_REVIEW + stable case_key + outbox
        relay to case system;
        checkpoint relay cursor only after durable case receipt

    // COMPENSATED is a recovered business failure, never successful DONE.

B 取得 epoch 8 后，图中 epoch 7 的 A 就不能继续推进本库状态。B 仍沿用 k9，也不重置步数。本库的隔离检查挡不住已经发出的远端请求。 远端必须原子检查原业务键、完整绑定信息和业务条件，并在同一事务中保存业务效果与回执；如果采用租约代次隔离（epoch fence），也必须由受保护的资源验证。[10] 尚未发出的意图可以因到期而被拒绝；结果为 UNKNOWN 的动作即使到期，仍须保留身份和核查义务，不能因 TTL 到期删除记录，再据此发起新写入。

Epoch 7 cannot advance local state after epoch 8; B keeps k9 and budgets. Local fencing cannot stop an already-sent packet. The backend must atomically check key/binding and business conditions and store effect plus receipt; any epoch fence must be enforced by the protected resource. [10] Expired undispatched intents may be denied. Expired UNKNOWN retains identity and reconciliation obligations; TTL deletion never authorizes a new write.

角色交接：角色变了，运行与未清义务仍保留Handoff: change role, retain run and obligations

角色交接时，先提交控制权转换，再启动 B。 在当前持有者的事务中，运行时检查角色转换是否合法，解决或显式继承未清动作，并在同一事务中更新 current_agent、role_revision 和下一节点。运行 ID、总预算与副作用账本继续保留。旧角色 A 的迟到输出会因 epoch 或 role_revision 不匹配而被拒绝。批准记录可留作审计，但绑定 A 的批准凭据不会自动授权 B；写动作更换 Agent 后，必须经过 Ch33 重新校验或重新审批。

B 接收的历史先按权限过滤，再生成摘要；tool_call/result 消息成对保留。摘要要带覆盖序号和来源，但不能作为权限凭据或成功回执。如果将专门处理某类问题的 Agent 作为工具，它只返回有界的只读结果，仍由当前负责人答复用户；稳定的子任务 ID、截止时间和费用都归属父运行。只有指令或权限确实需要分叉时，才引入多个角色，避免增加无意义的调用。

Commit control transfer before starting B. Under the owner transaction, validate the role edge, resolve or explicitly inherit pending actions, and update current_agent, role revision and next node together. Retain run ID, budgets and effect ledger; reject late A outputs by epoch/role revision. Keep approval records for audit, but an A-bound grant does not authorize B; Ch33 must revalidate or obtain new approval.

Filter history by authorization before summarizing; keep tool call/result pairs. A summary has covered sequence/source references, never authority or receipt status. A specialist-as-tool returns bounded read-only results while the current role answers; subtask identity/deadline/cost remain with the parent run. Add roles only for real instruction or permission differences.

暂停与批准：决定可以早到，同次暂停只恢复一次Pause and approval: decisions may arrive early, resume wins once

PENDING 不代表成功，批准也不代表动作已经执行。 暂停时，运行时在同一事务中保存 pause_id、approval_id、精确动作绑定信息和检查点，把状态改为 WAIT_APPROVAL，并释放持有权。确认提交后，才归还活跃槽位。批准可能早于暂停发生，因此暂停提交后应立即重读 Ch33 的决定，后台还要扫描等待记录。webhook 只是加快恢复，不能作为唯一唤醒证据。重复通知由唯一 decision_id 和针对同一状态、版本的 CAS 消化。

审批必须绑定租户 tenant、操作者 actor、Agent、业务意图 intent、工具及版本、目的端 route、规范化参数、资源 ID 及版本、策略和期限；审批界面要把动作展示成可读内容。金额、资源或主体变化时，必须产生新版本。Resume API 读取权威决定，不接受客户端自报 approved=true。运行回到 READY 后，工作进程仍要重新领取，Ch33 的执行门也要复查当前权限、资源和批准凭据。本章示例适配器假设在批准时签发有效期为 5 分钟的凭据。如果直接接入 Ch33 的示例实现，则须沿用它已持久保存的到期时间 expires，不因批准、恢复或排队重新计时；执行前已过期，就重新审查。

PENDING is not success; approval is not execution. Commit pause/approval IDs, exact binding, checkpoint, WAIT_APPROVAL and released ownership before returning the active slot. Approval can beat parking: reread Ch33 after parking and scan waiting rows. Webhooks accelerate recovery. Unique decision IDs and state/version CAS absorb duplicate notifications.

Bind tenant, actor, agent, intent, tool/revision, route, canonical arguments, resource ID/version, policy and expiry; show readable actions. Changes require a new revision. Resume API reads authoritative decisions rather than caller-supplied approved=true. READY still requires claim and Ch33’s execution-time recheck. Five-minute grants begin at approval; expiry while queued requires review.

park(run, action, ownerEpoch, expectedVersion):
    BEGIN RunStore transaction;
        lock run
        require current ownerEpoch/version, RUNNING and live lease
        require exact action still PREPARED;
        create stable pause_id

        INSERT pause(pause_id, approval_id, action.binding)
        UPDATE run SET status=WAIT_APPROVAL, owner=NULL, lease_until=0,
            epoch=epoch+1, version=version+1
        INSERT checkpoint + waiting event
    COMMIT;
    only then release the active slot

    reread Ch33 decision now;
    periodically scan waiting rows as a backstop

resume(run, pause_id, expectedVersion, notification):
    decision = Ch33.readAuthoritativeDecision(notification.approval_id)

    BEGIN RunStore transaction;
        lock run and pause
        if decision_id was accepted for this run/pause/binding:
            COMMIT;
            return saved result

        require WAIT_APPROVAL, matching pause, version=expectedVersion, not cancelled
        require run deadline is in the future
        require decision is APPROVED and grant is still valid
        require exact tenant/actor/Agent/intent/tool/route/args/resource/policy binding

        INSERT accepted_decision with UNIQUE(tenant, decision_id)
        UPDATE run SET status=READY, version=version+1
            WHERE status=WAIT_APPROVAL AND pause_id=:pause AND version=:expectedVersion
        require affected_rows = 1;
        INSERT READY outbox event
    COMMIT;
    a later worker must claim, then Ch33 rechecks at dispatch

    // Any failure rolls back this one database transaction.
    // DENIED/expired means replan or review, never silently APPROVED.

取消和恢复竞争同一状态及版本。取消先成功时，迟到批准只留作审计；恢复先成功但尚未派发动作时，取消仍可在下一道执行门拦住它。动作已持久记录为派发后，取消只能尽力终止，不能据此宣称远端没有产生效果。LangGraph 恢复 interrupt 所在节点时，会从节点开头重新执行，interrupt 之前的代码可能再次运行。因此，持久暂停并不保证进程栈停在原来那一行。[4]

每秒 6 次暂停，平均等待 300 秒，就得到 6×300=1,800 次平均待批运行。它们消耗持久记录和查询能力，不占用 320 个活跃槽位。如果审批处理能力跟不上，这个稳态平均值就不再成立；此时应限制每个租户的待批数量，并观察最老待批任务的年龄，以及到达率减去处理率后的积压增长速度。

Cancel/resume contend on the same state/version. A winning cancel makes late approval audit-only; cancellation after resume but before dispatch can still win the next gate. After durable dispatch, termination is best effort and remote effects remain possible. LangGraph resumes interrupt nodes from the beginning, so earlier code may rerun; a pause is not a suspended process stack. [4]

Six pauses/s × 300 seconds gives 1,800 mean parked runs using storage/query capacity rather than 320 active slots. If review falls behind, bound tenant backlog and monitor oldest age and arrival-minus-completion rate.

取消与补偿：先查发生了什么，再决定怎么修Cancel and compensate: establish effects before repairing

取消禁止新的前向动作，迟到的成功结果仍须入账。 动作在发出前已被明确拒绝时，可以结束这条未执行的路径；已经发出而结果未知的动作，则先查询原回执。不能猜测“可能扣款了”就退款，也不能猜测“可能没扣”就再扣一次。确认产生的效果写入副作用账本，保存原交易、补偿工具、当前执行条件、业务依赖和进度。图 7 要求先退款 c2、再释放预占 c1；前面退款成功后邮件失败的例子，则只修复通知。顺序取决于业务依赖，不是通用的逆序栈。[9]

补偿是一个新的业务动作。它使用与前向动作不同的稳定业务键，关联原效果，并遵守同样的 Ch33 权限、审批和回执契约。每个补偿动作最多允许 2 次经过分类、确认安全的尝试；c2 结果未知时会阻塞 c1，此时只能查询原补偿键。前向预算耗尽或运行到期，都不能删除未清义务，而应转交独立恢复任务。若有 8 项已确认效果，每项最多 2 次尝试，则补偿总调用最多 16 次；这是本例的总量界限，不是每秒调用速率上限。

撤销要根据当前状态和可退额度执行条件动作，不能拿旧快照覆盖他人的修改。补偿本身也可能失败；无法安全重放或无法确认结果时，要持久保存 NEEDS_REVIEW、稳定工单键 case_key 和 outbox。人工工单系统按原 case_key 防重，转发程序取得持久回执后，才推进游标；交接期间，未清义务仍然保留。全部补偿完成后记为 COMPENSATED，但用户原来的目标仍未成功，不能记为 DONE。

Cancellation blocks new forward work; record late success. Undispatched denial may finish, but sent uncertain actions first query original receipts. Never refund speculation or charge again on guessed failure. Confirmed effects enter a ledger with original transaction, undo tool, conditions, dependencies and progress. Deck 7 requires refund c2 before release c1; failed email repairs notification. Order is business-specific. [9]

Compensation is a new business action with a distinct stable key linked to the original effect, subject to Ch33 authorization/approval/receipts. Each has at most two classified safe attempts; UNKNOWN c2 blocks c1. Exhausted forward budgets or expiry transfer obligations to durable recovery. Eight effects times two attempts bounds sixteen total calls, not calls/second.

Use current state/refundable balance; never overwrite concurrent changes from an old snapshot. Unsafe replay or unknown results retain NEEDS_REVIEW, stable case key and outbox. Deduplicated case receipt precedes relay cursor acknowledgment. Fully undone work is COMPENSATED, not successful DONE.

展开流量、并发和增量存储的计算Traffic, concurrency and incremental-storage calculations

中文

按 A1，逻辑模型调用为 20×5=100 次/秒，即每分钟 6,000 次；工具调用平均为 20×3=60 次/秒。A6 假设 10% 的模型步骤各多一次物理尝试，因此物理模型调用为 100×1.1=110 次/秒，token 流量为 110×60×4,000=26,400,000 token/min，即 26.4M TPM；不加重试时是 24M TPM。这里的 4,000 是每次物理请求的平均输入加输出，与单次输入上限 12,000、每次运行总上限 60,000 是三个不同口径。实际验收要按供应商的计费和限额规则核对，不能直接复用 Ch32 单轮聊天的流量预算。

按 A3，不含重试和审批的正常路径耗时为 5×2 + 3×0.3 + 8×0.02 = 11.06 秒，平均活跃运行数为 20×11.06=221.2，可近似说成 221。如果那 10% 的额外物理模型调用也平均耗时 2 秒，每次运行就多出 0.5×2=1 秒，活跃均值变成 20×12.06=241.2。320 个槽位是保护上限，不能用平均值证明 p99 达标；还要在给定配额下压测排队、尾延迟和租户公平性。

如果每次运行都用满 12 次模型和 8 次工具，仍按 A3 的阶段均值计算，不含重试和审批，20 次结果检查点计入后的耗时为 12×2+8×0.3+20×0.02=26.8 秒，需要的平均在途运行数为 20×26.8=536，已经超过 320 个槽位。因此，观察到步骤数增多时就要收紧准入，不能用平均五次模型调用的容量，承诺支撑每次都走满上限的负载。

A3 的阶段均值已经包含调用前的持久准入，这里只另外加上结果检查点的耗时。结果状态增量为 20×8=160 次写/秒，每秒写入 160×2,000=320,000 B=0.32 MB。按该峰值持续全天计算，得到 0.32×86,400=27,648 MB=27.648 GB/天；保留七天、保存两份，则为 27.648×7×2=387.072 GB。完整消息、接单记录、调用前的预算和意图写入、持有者续租、审批与补偿，以及索引和 WAL 都要另计。如果每一步都把完整历史写回，消息越长，每次写入就越大，2 KB 的增量假设也会失效；这正是采用增量记录和对象引用的原因。另有 1,800 次待批运行保存在暂停池中，不能把它们和活跃运行数相加，就当成所需的 CPU 实例数。
