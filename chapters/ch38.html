缓存与 CDNCache and CDN

这一章结束你能做什么What you can do after this chapter

中文

  • 沿着 Client → Edge → Shield → App → Cache tier → Store 走完一次命中回包和一次 miss 回填，并说出每一跳谁拥有状态。
  • 用 RFC 9111 的存储条件解释 max-age、s-maxage、no-store、private 各自改的是这条路径的哪一段，而不是背「GET 一定缓存」或「302 一定不缓存」。
  • 把穿透、击穿、雪崩、热 key、缓存层宕机画成五条不同的失败路径：短 negative cache、singleflight / lease、TTL jitter、副本或本地缓存、带预算的旁路。

English

  • Walk one hit reply and one miss fill along Client → Edge → Shield → App → Cache tier → Store, and say who owns state at each hop.
  • Use the RFC 9111 storage rules to say what max-age, s-maxage, no-store, and private change on that path. Do not recite “GET is always cached” or “302 is never cached.”
  • Draw penetration, stampede, avalanche, a hot key, and cache-tier loss as five different failures: a short negative cache, singleflight or a lease, TTL jitter, a replica or local cache, and a budgeted bypass.

先把对象、权威和数量级钉死Pin the object, the authority, and the order of magnitude

中文

公开目录卡，不是账本。读路径是 Client 到 CDN Edge：新鲜就从边缘把响应回给用户。未命中才进 Origin Shield，再进 App，再进 Cache tier，最后才读 source of truth，然后按原路回填。这份响应能不能留在共享缓存里，看 Cache-Control 和状态码的缓存规则，不看方法名字的口头禅。改价先在 Store 提交，再 purge 或换版本 URL；TTL 只兜住没送到的失效。不存在的 key 用几秒的 negative cache。一个热 key 过期，用 singleflight 或 lease 让一个 leader 回源。一批 key 一起过期，用 TTL jitter 把 miss 摊开。缓存层挂了，旁路必须带速率预算，不能把峰值读全打到数据库。

整章只用这一个例子：GET /catalog/sku-1842，一张公开的目录卡，字段是价格、图片 URL、version、status。图片字节是另一个 URL，GET /media/sku-1842.<version>.jpg，版本进路径，所以换图不必全球 purge。购物车、余额、库存扣减不走这条共享边缘。语义缓存和向量近邻不在这里，一句回到 Ch32 · LLM 网关。视频怎么切片也不在这里。下面的 QPS、命中率、TTL 和字节数都是为了把设计算下去的假设，开口时要说「这是我定的数量级，请纠正」，不要说成某家公司的生产数字。

English

A public catalog card, not a ledger. The read path is Client to CDN Edge: if the response is fresh, the edge sends it back. A miss goes to an Origin Shield, then the App, then the Cache tier, and only then the source of truth, and the fill walks back the same way. Whether that response may sit in a shared cache comes from Cache-Control and the status-code rules, not from a slogan about the method. A price change commits in the Store first, then a purge or a versioned URL; TTL only covers an invalidation that never arrived. A key that does not exist gets a few seconds of negative cache. One hot key expiring gets singleflight or a lease so one leader fills. Many keys expiring together get TTL jitter. If the cache tier is down, the bypass has a rate budget. It does not dump the peak onto the database.

One example for the whole chapter: GET /catalog/sku-1842, a public catalog card with price, image URL, version, and status. The image bytes are a second URL, GET /media/sku-1842.<version>.jpg. The version is in the path, so a new picture does not need a worldwide purge. A cart, a balance, and an inventory decrement do not ride this shared edge. Semantic cache and nearest-neighbor embeddings are out of scope; one line points at Ch32 · LLM gateway. Video packaging is out of scope too. Every QPS, hit rate, TTL, and byte count below is an assumption chosen so the design can be calculated. Say “this is the order of magnitude I am using, correct me.” Do not present it as a company’s production figure.

读路径：边缘命中，以及 miss 怎样回填Read path: an edge hit, and how a miss fills back

一次命中、一次未命中，按真实顺序走Walk one hit and one miss in execution order

正常路径

客户端请求 GET /catalog/sku-1842。Edge 的 cache key 至少是方法加目标 URI；如果响应带了 Vary，被点名的请求头也进 key。RFC 9111 把这一点写进缓存模型：key 用来挑选已存响应，最低限度包含取出该响应时的方法和目标 URI，并用 Vary 区分内容协商的多份表示。[1] 目录卡若仍新鲜，Edge 把 200 和正文回给客户端。这一跳的状态在 Edge 里，Shield、App、Cache tier、Store 都不参加。回包箭头停在 Client，而不是停在 Edge 的框上。

未命中或已过期时，Edge 把请求送进源站一侧的 Shield。Shield 也是缓存，不是又一个应用。它的工作是把多个 POP 上同一对象的并发 miss 收成一次回源。假设有 40 个 POP，对象刚过期，没有父缓存就是 40 次打到 App；有 Shield，同一对象收成 1 次。40 和 1 都是这个例子的假设，用来说明父缓存改变的是回源次数，不是品牌。

App 不保存目录卡。它先用内部 key catalog:sku-1842 查 Cache tier。命中就把价格、图片 URL、version、status 交回去，再按产品语义生成 HTTP 响应，让 Shield 和 Edge 按响应头决定留不留。Cache tier 也 miss，App 才 SELECT Store。Store 返回行之后，App 把这份值写回 Cache tier，带上带抖动的 TTL，再把 HTTP 响应沿 Shield、Edge 送回客户端。回填是同一次请求的返回路径，不是后台另起的一套流水线。Nishtala 等人把这种用法叫做 demand-filled look-aside：缓存不知道数据库的存在，Web 服务器 miss 之后自己读库并填进去；缓存不是权威，允许被淘汰。[3]

Happy path

The client sends GET /catalog/sku-1842. The edge cache key is at least the method plus the target URI. If the response carries Vary, the named request headers join the key. RFC 9111 puts that in the cache model: the key selects a stored response and includes, at minimum, the method and target URI used to retrieve it, with Vary distinguishing negotiated representations. [1] If the catalog card is still fresh, the edge returns 200 and the body to the client. State for that hop lives at the edge. Shield, App, Cache tier, and Store do not participate. The reply arrow ends at the client, not on the edge box.

On a miss or expiry the edge forwards into the shield on the origin side of the POP boundary. The shield is a cache, not another application. Its job is to collapse concurrent misses for one object from many POPs into one origin fetch. Assume 40 POPs and an object that just expired. Without a parent cache that is 40 hits on the app. With a shield it is one. Both 40 and 1 are assumptions of this example. They show that a parent cache changes origin fan-out, not a brand name.

The app does not own the catalog card. It looks up the internal key catalog:sku-1842 in the cache tier. A hit returns price, image URL, version, and status, and the app builds the HTTP response so the shield and the edge can decide whether to store it. Only a cache-tier miss SELECTs the store. After the row comes back, the app writes the value into the cache tier with a jittered TTL, then sends the HTTP response back through the shield and the edge. The fill is the return path of this request, not a second pipeline started in the background. Nishtala et al. call this a demand-filled look-aside: the cache does not know the database exists; the web server reads the database on a miss and fills; the cache is not authority and may evict. [3]

命中率怎样改写源站 QPSHow hit rate rewrites origin QPS

为什么这样选

峰值按假设是 40,000 QPS，合计命中率按假设是 95%。未命中比例 1 − 0.95 = 0.05，源侧 40000 × 0.05 = 2,000，落在 Store 预算 3,000 里面。90% 时是 40000 × 0.10 = 4,000，已经超预算。缓存层消失时命中率按 0，源侧回到 40,000，不能裸放。缓存把数据库容量从峰值改成未命中切片。

95% 不是本章测出来的，也不是 Zipf 定律吐出的常数。Breslau 等人检查过多份 Web 代理 trace：分布并不严格服从 Zipf，而是 Zipf-like，指数随 trace 变化。他们再用独立请求、引用概率为 Zipf-like 的模型，复现了这些 trace 里命中率的渐近行为。这里只用这个模型解释「少数热对象可以吃掉大部分读」。它不是本目录的测量，本章不报告 α。[4]

本地 LRU 用同一套算法。假设目录卡的值是 2 KB，按 2,000 字节计，图片字节不进这个堆。最热 80,000 张卡是另一个假设。80000 × 2000 = 160,000,000 字节，即 160 MB 的值。哈希和对象头再按 1.5 倍估算，约 240 MB/进程。30 个进程是 30 × 240 = 7,200 MB，约 7.2 GB，而且是同一热头的副本。本地缓存只放极热、可以短暂陈旧的字段。

Why this shape

Peak is an assumed 40,000 QPS and the combined hit rate is an assumed 95%. The miss ratio is 1 − 0.95 = 0.05, so origin QPS is 40000 × 0.05 = 2,000, inside the store’s 3,000 budget. At 90% it is 40000 × 0.10 = 4,000, already over budget. If the cache tier disappears, hit rate is 0 and origin is 40,000, which a bypass must not release raw. A cache sizes the database for the miss slice, not the peak.

Ninety-five percent is not a measurement in this chapter, and it is not a constant from Zipf’s law. Breslau et al. checked several web-proxy traces. The distribution is Zipf-like, not Zipf’s law exactly, and the exponent varies by trace. An independent-request model with a Zipf-like reference probability reproduced the asymptotic hit ratios in those traces. This chapter uses that model only to explain why a small hot set can absorb most reads. It is not a measurement of this catalog, and it does not report an α. [4]

Local LRU uses the same arithmetic. Assume a catalog value is 2 KB, counted as 2,000 bytes, with image bytes kept out of this heap. The hottest 80,000 cards are a second assumption. 80000 × 2000 = 160,000,000 bytes, 160 MB of values. At an assumed 1.5× for the hash table and object headers, about 240 MB per process. Thirty processes are 30 × 240 = 7,200 MB, about 7.2 GB, copies of the same hot head. Local cache holds only an extremely hot, briefly stale field set.

不上 CDN，或不上 ShieldSkipping the CDN, or skipping the shield

替代方案

对象不能放进共享缓存时，正确的替代是只留本地 LRU 和 Cache tier，不画 Edge。用户到机房的 RTT 还在，40,000 QPS 里能被吃掉的只是应用缓存命中的那部分，边缘节省的带宽没有了。目录卡若带用户价、优惠券或登录态，就属于这一支，后面用 private 把它从共享缓存里赶出去。流量还在一个区域、POP 还没成为延迟或回源问题的时候，先不上 CDN 是合理的第一版，不是简陋。

另一支替代是有 Edge、没有 Shield。POP 少、对象冷，每个边缘自己回源。POP 一多，过期对齐的那一秒，回源次数是「刚过期的对象数 × 同时 miss 的 POP 数」。Shield 和 singleflight 是同一件事的两层。Read-through 让缓存库自己回源，App 只发 get；权威仍是 Store。面试默认说 lookaside，Facebook 的 memcache 就是应用在 miss 之后填。[3]

Alternatives

When the object must not enter a shared cache, the right alternative is local LRU plus the cache tier, and no edge on the board. The RTT from the user to the data center remains. Of the 40,000 QPS, only the application-cache hits disappear, and the bandwidth the edge would have saved is gone. A catalog card that includes a user-specific price, a coupon, or a login state belongs on this branch. private pushes it out of the shared cache below. While traffic is still one region and POPs are not yet a latency or origin problem, skipping the CDN is a reasonable first version.

The other alternative is an edge without a shield. Few POPs and a cold object can each fetch origin. Once POP count is large, origin fetches in the aligned second become “objects that just expired × POPs missing together.” The shield and singleflight are the same idea at two layers. Read-through lets the cache library fetch origin while the app only gets; authority is still the store. The interview default is lookaside: Facebook’s memcache is filled by the application after a miss. [3]

回填和超时不能写成 404A fill race is not a 404, and a timeout is not a 404

故障窗口

命中回包和 miss 回填会在更新附近重叠。Edge 上还是旧价，同时另一个请求已经 miss 到 Store，读到新价，正往 Cache tier 和 Edge 填。谁后写，谁留下。看路径不能只看「有缓存所以是新的」。写路径必须先让 Store 成为新版本，再让旧副本失效，而不是靠一次 SET 和另一次 SET 比赛。这个窗口在失效那一节展开。

另一条边界是：Cache tier 超时、Store 超时，和「没有这张卡」不是同一个返回值。前两者是这一层不可用，响应应该是 503 或让调用方重试，绝不能写成 404 再放进 negative cache。否则一次数据库抖动会变成全网「没有 sku-1842」，而且短 TTL 之内新请求都会相信这个假缺席。key 不存在才允许负缓存，而且 TTL 是秒级。常见错误是把「加 CDN」说成可以拆掉 Cache tier。边缘保存的是 HTTP 响应，Cache tier 保存的是 App 能按 key 删除的字段。图片字节走 Edge，价格和 version 仍要有一份应用删得掉的副本。

Failure window

A hit reply and a miss fill overlap near an update. The edge still has the old price while another request has missed through to the store, read the new price, and is filling the cache tier and the edge. Whichever write lands last remains. “There is a cache, so it is new” does not follow from the drawing. The write path has to make the store the new version first and then invalidate old copies, not race one SET against another. That window is the invalidation section.

The other boundary: a cache-tier timeout and a store timeout are not the same result as “this card does not exist.” The first two mean the layer is unavailable. The response is a 503 or a retry, never a 404 written into the negative cache. Otherwise one database blip becomes “sku-1842 does not exist” for the whole negative TTL, and every new request believes the false absence. Only a key that is absent may be negative-cached, and the TTL is seconds. A common mistake is treating “add a CDN” as permission to delete the cache tier. The edge stores an HTTP response. The cache tier stores fields the app can delete by key. Image bytes ride the edge. Price and version still need a copy the application can delete.

同一条路径上，Cache-Control 改的是哪一跳On the same path, what Cache-Control changes

把三条指令放到同一次 GET 上Put the three directives on the same GET

正常路径

目录卡的响应是 200，加上 Cache-Control: public, max-age=30, s-maxage=30。Edge 是共享缓存。新鲜期按 RFC 9111 第 4.2.1 节的第一条匹配：共享缓存看到 s-maxage 就用 30 秒，不再去看 max-age。[1] 年龄小于 30 秒时，下一次相同的 GET 由 Edge 回包，Shield 和 Store 这次空闲。年龄一过 30 秒，这份响应变 stale。s-maxage 还带上了 proxy-revalidate 的语义：共享缓存在重新验证成功之前，不得用这份 stale 响应去应答下一次请求。[1]

若产品要求每一次读都回到源，响应改成 Cache-Control: no-store。Edge 把请求继续送到 Shield 和 App，App 读 Cache tier 或 Store，响应沿原路回到客户端，但是 Edge 不得把这份响应存进非易失存储，也要尽快从易失存储里清掉，并且不得用它应答别的请求。[1] 回箭头还在，存储消失。这和「不返回响应」不是一回事。

购物车是另一条请求，GET /cart，响应 Cache-Control: private。未限定的 private 告诉共享缓存不得保存。[1] 浏览器里的私有缓存可以存。红色虚线画的是「不得写入 POP」，不是「请求失败」。若连浏览器也不能留，再加 no-store。带 Authorization 的请求还有一条独立限制：除非响应里有明确允许共享缓存的指令，共享缓存不得用已存响应去应答后续请求。[1] 所以个性化不能靠「CDN 很聪明，会看 Cookie」。

Happy path

The catalog response is 200 with Cache-Control: public, max-age=30, s-maxage=30. The edge is a shared cache. Freshness uses the first match in RFC 9111 section 4.2.1: a shared cache that sees s-maxage uses 30 seconds and does not consult max-age. [1] While age is under 30 seconds, the next identical GET is answered by the edge. Shield and Store sit idle. Past 30 seconds the response is stale. s-maxage also carries proxy-revalidate: a shared cache must not reuse that stale response until origin revalidation succeeds. [1]

If every read must reach origin, the response becomes Cache-Control: no-store. The edge forwards to the shield and the app, the app reads the cache tier or the store, and the response walks back to the client. The edge must not intentionally store it in non-volatile storage, must try to drop it from volatile storage promptly, and must not use it for another request. [1] The reply arrow remains. Storage does not. That is not the same as refusing to answer.

The cart is a different request, GET /cart, with Cache-Control: private. Unqualified private tells a shared cache not to store it. [1] A private browser cache may. The red dashed line is “do not write this into the POP,” not “the request failed.” Add no-store when the browser must not keep it either. A request that carries Authorization has a separate rule: a shared cache must not reuse a stored response for a later request unless the response carries a directive that explicitly allows shared caching. [1] Personalization is not “the CDN is smart and will notice the cookie.”

为什么不能靠状态码或方法名Why the status code or the method name is not the policy

为什么这样选

RFC 9111 第 3 节的存储条件里，和本章直接有关的是这几条同时成立：方法被缓存理解；状态码是最终的；响应里没有 no-store；若缓存是共享的，则没有拦住它的 private，并且带 Authorization 时要有明确允许共享的指令；响应里至少还要有一样「可以存」的标记，例如 public、max-age、Expires、共享缓存的 s-maxage，或者一个被定义成可启发式缓存的状态码。[1] GET 的响应在语义上是可缓存的，缓存可以用它应答后续的 GET 和 HEAD，除非 Cache-Control 另有指示。[2] 「可缓存」是允许，不是「每一次 GET 都会被留下」。PUT 和 DELETE 的响应则被定义成不可缓存；若一次成功的 PUT 或 DELETE 穿过某个缓存，那个缓存要作废它已为该 URI 保存的响应。[2] 穿过的是这一跳上的缓存，不是地球上每一个 POP。

302 同样不是「永不存储」的状态码。RFC 9110 把可启发式缓存的状态码列成包括 200、301、308、404、410 等，301 的正文写明 301 可启发式缓存；302 Found 的正文没有这句，列表里也没有 302。[2] 同一份规范又写明：任何带最终状态码的响应，只要有显式新鲜期，就可以被缓存；可启发式缓存只是允许在没有显式新鲜期时被缓存。[2] 所以一张带 max-age 的 302 可以进缓存，一张只有状态码、没有新鲜期、也没有 public 的 302 不能靠启发式进去。要每次都回到源，就写 no-store。短链那章对跳转用 no-store，是因为每次点击都要回源，不是 302 的属性。

省略 Cache-Control 也不会得到「不要缓存」。200 是可启发式缓存的，缓存可以在没有显式过期时自己估一个新鲜期；规范不规定算法，只限制最坏情况，并鼓励在有 Last-Modified 时不要超过自那以来间隔的某个比例，常见取值是 10%。[1][2] 目录价格若靠启发式，新鲜期由缓存实现决定，60 秒的可见性 SLO 就没有着落。显式 max-age=30 是把这个数从实现手里拿回来。

Why these directives

The storage conditions in RFC 9111 section 3 that matter here must hold together: the method is understood; the status is final; the response has no no-store; if the cache is shared, private does not forbid it, and an Authorization request needs a directive that explicitly allows shared caching; and the response has at least one positive signal such as public, max-age, Expires, s-maxage on a shared cache, or a status code defined as heuristically cacheable. [1] A GET response is cacheable in the semantic sense: a cache may use it for a later GET or HEAD unless Cache-Control says otherwise. [2] “Cacheable” is permission, not “every GET is stored.” PUT and DELETE responses are defined as not cacheable. A successful PUT or DELETE that passes through a cache invalidates stored responses that cache holds for that URI. [2] “Through that cache” means the caches on the path of that request, not every POP on earth.

A 302 is not a status that means “never store.” RFC 9110’s heuristically cacheable list includes 200, 301, 308, 404, and 410, among others. The 301 text says a 301 is heuristically cacheable. The 302 Found text does not, and 302 is not in that list. [2] The same specification says any response with a final status code can be cached if it has explicit freshness; heuristic cacheability is what allows storage without explicit freshness. [2] A 302 that carries max-age may be stored. A 302 that is only a status code, with no freshness and no public, does not get in on a heuristic. If every request must reach origin, send no-store. The short-link chapter uses no-store on a redirect because every click must reach origin. That is not a property of 302.

Omitting Cache-Control is not “do not cache.” A 200 is heuristically cacheable, so a cache may invent a freshness lifetime when no explicit expiration is present. The specification does not fix the algorithm. It bounds the worst case and encourages caches that see Last-Modified to use no more than some fraction of the age of that timestamp, with 10% a typical setting. [1][2] If catalog price depends on a heuristic, the lifetime belongs to the cache implementation and the 60-second visibility SLO has nothing to hold. Explicit max-age=30 takes that number back.

Vary、跟踪参数，以及故意的短暂陈旧Vary, tracking parameters, and intentional brief staleness

替代与边界

语言不同的目录卡用 Vary: Accept-Language，Edge 按语言分存。RFC 9111 允许把 Vary 点名的请求头并进 key。[1] 目标 URI 已经在 key 里，?utm_source=... 会把同一张卡切碎，源站 QPS 从 2,000 往上爬。进缓存前剥掉这些参数。把 Cookie 塞进 Vary 会在共享节点上按会话各存一份，伤命中率，也把别人的正文放在共享缓存里。用户态走 private。

stale-while-revalidate 不是 max-age 的替代。RFC 5861：响应变 stale 之后，缓存可以在给定秒数内先回旧响应，同时后台重新验证。例子 max-age=600, stale-while-revalidate=30 是新鲜 600 秒，再陈旧最多 30 秒；窗口结束还没验证成功，就不再当新鲜用。[5] stale-if-error 只覆盖 500、502、503、504，在额外上限内用旧响应换可用性。[5] 不认识该扩展的缓存必须忽略它，退回普通过期。[1] 窗口要落进 60 秒 SLO，不能永远脏。没有 stale-if-error 时，源站宕机不会自动续命。

三句不要带上场。「GET 一定缓存」和「302 一定不缓存」都越过了上面的存储条件。「CDN 缓存登录后的 JSON」越过了 private。目录卡用 public 加短 s-maxage；用户态用 private 或 no-store，并且不要和目录卡共用 cache key。

Alternatives and boundaries

A catalog card that varies by language sends Vary: Accept-Language so the edge stores one response per language. RFC 9111 lets a cache add the named request headers to the key. [1] The target URI is already in the key, so ?utm_source=... slices one card apart and origin QPS climbs from 2,000. Strip those parameters before the cache. Putting Cookie into Vary stores one body per session on a shared node, wrecks the hit rate, and parks someone else’s response there. User state uses private.

stale-while-revalidate is not a replacement for max-age. RFC 5861: after a response is stale, a cache may serve it for the given number of seconds while revalidating in the background. The example max-age=600, stale-while-revalidate=30 is fresh for 600 seconds, then stale for at most 30; if the window ends without a successful revalidation, it is not served as fresh. [5] stale-if-error covers only 500, 502, 503, and 504, and may serve stale inside an extra bound. [5] A cache that does not recognize the extension must ignore it and fall back to ordinary expiry. [1] The window has to fit the 60-second SLO. It is not permission to stay dirty forever. Without stale-if-error, an origin outage does not extend the object by itself.

Three sentences to drop: “GET is always cached” and “a 302 is never cached,” both of which skip the storage rules above, and “the CDN caches logged-in JSON,” which skips private. The catalog card uses public plus a short s-maxage. User state uses private or no-store, and it does not share the catalog cache key.

失效：先提交权威，再 purge 或换 URLInvalidation: commit authority, then purge or change the URL

一次改价实际做了什么What one price change actually does

正常路径

运营把 sku-1842 的价格从 20 改成 18。App 在 Store 里更新行，version 从 1 变成 2，事务提交成功。这一刻起 Store 是 v2，但 POP A、POP B 和 Cache tier 里还可能是 v1。提交成功之后，App 做两件本地能立刻做的事：删除 Cache tier 的 catalog:sku-1842，以及把一条 purge 放进队列。队列是异步的，画出虚线，是因为失效要送到许多 POP，不能塞进用户请求的同步尾延迟里。POP A 先处理到这条 purge，丢掉 v1，下一次 GET 会 miss 并填到 v2。POP B 的 purge 还在队列里或第一次发送失败，于是继续用新鲜期内的 v1 回包。客户端在 POP B 看到的旧价，就是这个窗口。

图片不走同一条 purge。新图写入 /media/sku-1842.9c2.jpg，目录卡的 image_url 指过去。客户端请求的是新 URL，Edge 对这个 key 是 miss，回源填充。旧 URL 不再被新页面引用，留在边缘直到它自己的 max-age，不会被当成新图发出去。稳定 URL 的目录卡做不到这一点：价格的路径还是 /catalog/sku-1842，必须 purge 或等到新鲜期结束。

Cache tier 上这一笔是删除，不是 SET 新价。Nishtala 等人先执行 SQL，再 delete，因为 delete 幂等，缓存不是权威。[3] 提交之后才广播删除；跨区域时删除和数据库复制走同一条通道，避免失效比新行先到、又把旧行填回去。[3] 目录卡只用这个顺序，不搬他们的路由拓扑。

Happy path

An operator changes sku-1842 from 20 to 18. The app updates the row, version moves from 1 to 2, and the transaction commits. From that instant the store is v2, while POP A, POP B, and the cache tier may still hold v1. After the commit the app does two things it can do locally at once: delete catalog:sku-1842 in the cache tier, and enqueue a purge. The queue is async, drawn dashed, because the invalidation has to reach many POPs and must not be appended to the user’s synchronous tail latency. POP A processes the purge, drops v1, and the next GET misses and fills v2. POP B’s purge is still queued or the first send failed, so it keeps replying with v1 for the rest of the freshness lifetime. The old price a client sees in POP B is that window.

The image does not take the same purge. The new bytes are written at /media/sku-1842.9c2.jpg, and the card’s image_url points there. The client requests the new URL. The edge misses that key and fills from origin. The old URL is no longer referenced by the new page. It may remain at the edge until its own max-age, and it will not be served as the new picture. The stable catalog URL cannot do this. The price still lives at /catalog/sku-1842, so it needs a purge or the end of the freshness lifetime.

On the cache tier this step is a delete, not a SET of the new price. Nishtala et al. run SQL and then delete, because a delete is idempotent and the cache is not authority. [3] The delete is broadcast after commit. Across regions it shares the replication channel, so the invalidation does not arrive before the new row and get followed by a fill of the old one. [3] The catalog card uses that order. It does not import their routing topology.

60 秒 SLO 怎样推出 30 秒新鲜期How a 60-second SLO produces a 30-second lifetime

为什么这样选

可见性 SLO 按假设是 60 秒内全球看到新价。purge 是缩短窗口的机制，TTL 是 purge 失败时的上限。若共享新鲜期是一天，purge 丢一次，旧价可以留一天，SLO 已经破了。把 s-maxage 定成 30 秒，是让「purge 完全没到」的最坏情况仍落在 60 秒里，还留一点给时钟和队列。purge 正常到达时，窗口是队列延迟，通常远小于 30 秒。所以 TTL 不是你向面试官描述的失效手段，它是你承认管道会丢消息之后留下的保险。

Facebook 的抽样说明窗口不是装饰。源和目标都在主区域时，1 秒内大约四个 9 的样本已生效，一小时后大约五个 9；都在主区域之外时，1 秒内大约三个 9，10 分钟大约四个 9。几秒后仍没失效，最常见是第一次发送失败，重试会补上。[3] 这是他们的采样，不是本章的数字，也不是「全球一秒完成」。管道在飞的时候，边缘仍回旧对象。

本地 LRU 的 TTL 必须短于 Cache tier。这里取 5 秒，共享层大约 30 秒再加抖动。否则共享层已经 DELETE，某台 App 仍从本地把 v1 交出去，或用一次迟到的 SET 把 v1 写回去。Nishtala 等人用 lease 挡住这种 stale set：set 必须带上 miss 时的 token，中间的 delete 会作废 token。token 的发放间隔和 herd 的数字放在击穿那一节，那里才是它们改变回源次数的地方。[3]

Why 30 seconds

The visibility SLO is an assumed 60 seconds to see the new price worldwide. Purge is the mechanism that shortens the window. TTL is the ceiling when purge fails. A one-day shared lifetime means one lost purge can leave the old price up for a day, and the SLO is already broken. Setting s-maxage to 30 seconds makes the worst case, “the purge never arrived,” still land inside 60 seconds, with a little room for clocks and the queue. When the purge arrives normally, the window is queue delay, usually far under 30 seconds. TTL is not the invalidation mechanism you describe. It is the insurance you keep because the pipe drops messages.

Facebook’s sample shows the window is not decorative. When source and destination are both in the master region, about four nines of the sample have taken effect within one second, and about five nines after an hour. Outside the master region, about three nines within one second and about four nines within ten minutes. A miss after a few seconds is usually a failed first send; retries clear it. [3] That is their sample, not this catalog, and not “worldwide in one second.” While the pipe is in flight, edges still reply with the old object.

Local LRU TTL must be shorter than the cache tier: 5 seconds locally, about 30 seconds plus jitter in the shared tier. Otherwise one app still returns v1 from its LRU after the shared delete, or a late SET writes v1 back. Nishtala et al. stop that stale set with a lease: the set must present the miss token, and a delete in between voids it. The token interval and the herd numbers belong in the stampede section, where they change origin reads. [3]

Write-through、Write-back，以及「双删」Write-through, write-back, and the double-delete habit

替代方案与常见错误

Write-through 是可行替代：写 Store 和写 Cache tier 都完成才给客户端成功。下一次读更常命中新价，代价是写延迟变成两跳，而且两边仍可能只有一边成功。它不是分布式事务。写完几乎不再读的字段会把缓存占满，那些 key 应该绕过缓存。CDN 边缘做不到对每一个 POP 同步 write-through，所以 through 只描述应用和 Cache tier，不描述全球 Edge。

Write-back 先写缓存，再异步刷 Store。合并写、扛计数吞吐时它成立，进程在刷盘前死掉就会丢更新。价格、库存和订单不是这种数据。播放次数这类可以丢几秒的计数才可以讨论 back，并且要说出恢复点目标。默认仍是 lookaside：缓存挂了，读变慢，但 Store 还在就能读到正确行；back 在缓存挂掉时可能把还没刷出的写一起葬送。

「Cache-Aside 写库然后删 key」停在这里，就没有 stampede 计划。删除本身是对的，因为它幂等。[3] 热 key 被删的一瞬，所有 App 同时 miss。Aside 还要说出 singleflight、lease 或源并发预算。「延迟双删就能线性一致」只缩短漏网 SET 的窗口，POP B 仍可能回 v1。「purge 全球瞬间完成」被图上 POP B 的旧对象回包直接反掉。[3]

Alternatives and the usual wrong answers

Write-through is a real alternative: succeed to the client only after both the store write and the cache-tier write finish. The next read is more likely to see the new price. The cost is write latency of two hops, and one side can still succeed alone. It is not a distributed transaction. Fields that are written and almost never read should bypass the cache or they occupy it. A CDN edge cannot synchronously write through to every POP, so through describes the app and the cache tier, not the global edge.

Write-back writes the cache first and flushes the store asynchronously. It is how you coalesce writes and take counter throughput. If the process dies before the flush, the update is gone. Price, stock, and orders are not that data. A play count that can lose a few seconds can discuss write-back, and it has to name a recovery-point objective. The default stays lookaside: if the cache dies, reads get slower, but a live store still returns the right row. Write-back can bury the writes that had not flushed.

Stopping at “cache-aside writes the database and deletes the key” leaves no stampede plan. The delete itself is right because it is idempotent. [3] The instant a hot key is deleted, every app misses together. Aside still has to name singleflight, a lease, or an origin concurrency budget. “Delayed double-delete is linearizability” only shortens a stray SET. POP B can still reply v1. “Purge is instantaneous worldwide” is answered by POP B’s old-object reply on the drawing. [3]

穿透：key 根本不存在Penetration: the key does not exist

负缓存怎样把 2,000 QPS 收成大约 20How a negative cache turns 2,000 QPS into about 20

正常路径

客户端请求一个 Store 里没有的 sku。App 查 Cache tier，没有条目，于是读 Store。Store 明确回答没有这行，不是超时。App 返回 404，并把 catalog:sku-missing → absent 写进 Cache tier，TTL 5 秒。5 秒之内同样的 key 命中这条负记录，App 直接 404，不再读库。5 秒之后条目消失，下一次又会打到 Store。若这 5 秒里真的创建了这个 sku，创建提交成功后必须删掉这条负记录，否则新建商品会在剩余 TTL 里继续 404。这和「不存在就永远记住」相反。

数量级仍是假设。有缺陷的客户端对 100 个不存在的 sku 以合计 2,000 QPS 重试。没有负缓存时，这 2,000 都到达 Store，已经接近 3,000 的保护预算。有 5 秒负缓存时，每个 sku 大约每 5 秒穿透一次，100 个 sku 是每 5 秒 100 次，约 20 QPS。预算还在。这个乘法只在「重复的是同一批 key」时成立。

Happy path

The client asks for a sku the store does not have. The app checks the cache tier, finds no entry, and reads the store. The store explicitly says there is no row. It does not time out. The app returns 404 and writes catalog:sku-missing → absent into the cache tier with a 5-second TTL. Inside those five seconds the same key hits the negative record and the app returns 404 without reading the database. After five seconds the entry is gone and the next request reaches the store again. If the sku is actually created during those five seconds, the successful create must delete the negative record, or the new product keeps 404ing for the rest of the TTL. That is the opposite of remembering absence forever.

The order of magnitude is still an assumption. A buggy client retries 100 missing skus at 2,000 QPS combined. Without a negative cache all 2,000 reach the store, close to the 3,000 protection budget. With a 5-second negative cache each sku penetrates about once per five seconds. One hundred skus are 100 reads per five seconds, about 20 QPS. The budget holds. The multiplication is true only when the repeats are the same keys.

为什么要缓存 404，以及为什么不能永久缓存Why a 404 is cached, and why not forever

为什么这样选

不缓存 404 时，存在的卡被 Edge 挡住，不存在的 id 每次都打到 Store。RFC 9111 允许保存负结果，例如 404。[1] RFC 9110 把 404 列为可启发式缓存：没有显式新鲜期时，缓存可以自己估过期时间。[2] 「错误响应天然不进 CDN」不成立。不写显式 max-age，启发式寿命由实现决定，可能远长于 5 秒。目录卡的 404 要写短的显式新鲜期。

永久负缓存是反方向的错误。sku 一旦被创建，还记着 absent 的层会继续 404，直到有人记得 purge。5 秒加上「创建成功就删除负 key」，把忘了 purge 的后果限制在几秒。410 表示缺席被看成持久的，它同样可启发式缓存。[2] 只有这个 id 真的不再发行时才用 410，并且仍给显式寿命。

Why cache the 404

If you do not cache a 404, cards that exist are absorbed by the edge and missing ids hit the store every time. RFC 9111 says a cache may store negative results, including a 404. [1] RFC 9110 lists 404 as heuristically cacheable, so with no explicit freshness a cache may assign its own expiration. [2] “Errors never enter a CDN” is not the rule. Without an explicit max-age the heuristic lifetime belongs to the implementation and can be much longer than five seconds. A catalog 404 needs a short explicit freshness.

A permanent negative cache is the mistake in the other direction. Once the sku is created, every layer that still remembers absent keeps returning 404 until someone purges it. Five seconds plus “delete the negative key on successful create” caps a forgotten purge at a few seconds. A 410 means the absence is treated as lasting, and it is also heuristically cacheable. [2] Use 410 only when that id will not be issued again, and still send an explicit lifetime.

每次都是新 id 时，负缓存无效A negative cache does nothing when every id is new

故障边界与替代

若攻击者每秒发 2,000 个从未重复的随机 sku，每条负缓存只命中零次，Store 仍是 2,000 QPS。这时要的是边缘上的速率限制，或者一份「现存 sku」的成员关系结构：判定不在，就可以 404 而不读库；判定可能在，再读库。成员关系会有假阳性，假阳性只是多读一次库，不会把存在的商品说成没有。反过来，新建的 sku 若还没写进这个结构，会被误判成不存在。所以插入必须更新结构，不能把一份凌晨建的过滤器用一整天。负缓存解决重复缺席，成员关系结构解决高基数的一次性缺席，限流解决两者都挡不住的剩余流量。三句话不要合成「加一把锁」。

Store 超时绝不能写负缓存。那会把「数据库暂时不可用」变成「商品不存在」，而且 5 秒内所有副本都相信它。负缓存的值也要和「已下架」分开。下架是一条真实状态，可以有自己的 TTL 和 purge；缺席是没有行。合成一个 null，恢复时就分不清该信缓存还是该重读权威。

Failure boundary and the alternative

If an attacker sends 2,000 random skus per second and never repeats one, each negative entry hits zero times and the store still sees 2,000 QPS. What you want then is a rate limit at the edge, or a membership structure of skus that exist: “definitely absent” can 404 without the database; “maybe present” reads the database. A membership structure has false positives. A false positive is one extra database read. It does not report an existing product as missing. The inverse bug is a newly inserted sku that is not in the structure yet, which is reported absent. Inserts must update the structure. A filter built at dawn cannot be trusted all day. Negative cache handles repeated absence. Membership handles high-cardinality one-shot absence. A rate limit handles whatever is left. Those are not one sentence, “add a lock.”

A store timeout must never be written as a negative entry. That turns “the database is briefly unavailable” into “the product does not exist,” and every replica believes it for five seconds. The negative value also stays distinct from “delisted.” Delisted is a real status with its own TTL and purge. Absence means there is no row. One shared null makes recovery unable to tell whether to trust the cache or reread authority.

击穿：一个热 key 过期Stampede: one hot key expires

一个 leader 怎样把一波回源收成一次读How one leader turns a wave of fills into one read

正常路径

sku-1842 在 Cache tier 里的 TTL 走到 0，同时有许多请求在飞。进程内 singleflight 用这个 key 挂上一个 in-flight 的 promise：第一个请求成为 leader，去 Cache tier 或 Store 读；同一进程里后来的请求挂在这个 promise 上，不再发起自己的读。leader 拿到行，写回缓存，promise 完成，等待者拿同一份结果回给各自的客户端。跨进程时，每个进程仍会选出自己的 leader，所以 Store 可能看到「进程数」次读，而不是「请求数」次。要再收一层，就用缓存服务器发的 lease，或者给 Store 一个并发预算。

Nishtala 等人的 lease 同时处理两件事。stale set：set 必须带上 miss 时拿到的 64 位 token，期间的 delete 会作废 token，慢请求不能把旧值写回。thundering herd：每台 memcached 限制 token 发放速率，他们的默认是每个 key 每 10 秒最多一个 token；窗口内的其他请求被告知稍等，leader 通常几毫秒内就 set 完成，等待者重试时值已经在缓存里。他们对一批容易 herd 的 key 做了一周观察：没有 lease 时，cache miss 对应的数据库峰值是 17,000 次/秒；有 lease 时峰值是 1,300 次/秒。[3] 17,000 和 1,300 是他们的测量，用来说明 lease 改变的是峰值而不是平均口号。本章的 40,000 QPS 目录不借用这个比例。

Happy path

The TTL of sku-1842 in the cache tier hits zero while many requests are in flight. In-process singleflight hangs an in-flight promise on that key. The first request becomes the leader and reads the cache tier or the store. Later requests in the same process attach to the promise and do not start their own read. The leader gets the row, writes the cache, completes the promise, and the waiters return that same result to their clients. Across processes, each process still elects its own leader, so the store may see one read per process rather than one read per request. The next collapse is a lease issued by the cache server, or a concurrency budget on the store.

The lease in Nishtala et al. handles two problems at once. Stale sets: a set must present the 64-bit token from the miss, a delete in between voids the token, and a slow request cannot write the old value back. Thundering herds: each memcached server limits how fast it issues tokens. Their default is at most one token per key every 10 seconds. Other requests inside the window are told to wait. The leader usually finishes the set in a few milliseconds, and the waiters’ retry finds the value. For a week they watched keys that were prone to herds. Without leases, cache misses corresponded to a peak database rate of 17,000 queries per second. With leases the peak was 1,300 per second. [3] Those two peaks are their measurement. They show that a lease changes the peak, not a slogan about averages. This chapter’s 40,000 QPS catalog does not borrow the ratio.

为什么不是一把打在所有读上的锁Why this is not a lock on every read

为什么这样选，以及替代

命中路径不能去抢锁。40,000 QPS 里 95% 是命中，大约 38,000 次只读缓存。若每次命中都要分布式锁，锁服务会变成新的热 key。singleflight 和 lease 只在 miss 上出现。命中仍是一次 get。这是从流量形状推出来的，不是从「业界都加锁」推出来的。

可以接受陈旧时，用逻辑过期：key 不设 TTL，值里带 expireAt，过期后仍回旧值，只放行一个请求去刷新。Nishtala 等人在 delete 之后把旧值留一小会儿，能接受陈旧的应用不必干等数据库。[3] 目录价格可以借这几秒把刷新移出关键延迟。库存扣减不能用，旧库存是错账。提前刷新是另一替代，只刷检测出来的热 key。

常见错误是用负缓存或永久 TTL 来治击穿。负缓存记得的是缺席，热 key 并不缺席。永久 TTL 让改价只能靠 purge，purge 一丢，旧价没有 backstop。击穿的答案是「一个 leader 填，等待者共享」，再加上下一节的 jitter，避免许多热 key 在同一秒一起过期。

Why not a lock on every read

The hit path must not take a lock. Of 40,000 QPS, 95% are hits, about 38,000 cache reads. A distributed lock on every hit makes the lock service the new hot key. Singleflight and the lease appear only on a miss. A hit is still one get. That follows from the traffic shape, not from “the industry adds a lock.”

When staleness is acceptable, use logical expiry: the key has no TTL, the value carries expireAt, the old value is still returned, and only one request refreshes. Nishtala et al. keep a deleted value aside briefly so an application that can use stale data does not wait on the database. [3] Catalog price can spend those seconds to move the refresh off the critical path. An inventory decrement cannot. Old stock is the wrong ledger. Refresh-ahead is the other alternative, and it refreshes only keys detected as hot.

A common mistake is to treat a stampede with a negative cache or with a permanent TTL. A negative cache remembers absence. The hot key is not absent. A permanent TTL means a price change depends entirely on purge, and a lost purge has no backstop. The stampede answer is “one leader fills, waiters share,” plus the jitter in the next section so many hot keys do not expire in the same second.

雪崩：许多 key 在同一秒过期Avalanche: many keys expire in the same second

1,000 个 key 对齐时，峰值怎么变What happens to the peak when 1,000 keys line up

正常路径与计算

预热或一次发布把 1,000 个热门目录卡在同一秒写进 Cache tier，基准 TTL 30 秒，没有抖动。到第 30 秒它们一起 miss。若每个 key 已经有 singleflight，每个 key 只产生 1 次回源，这一秒仍是 1,000 次 Store 读。Store 预算是 3,000 QPS，1,000 还放得下，但只是这个假设的批次。若没有 singleflight，再假设每个 key 在到期那一秒有 20 个并发请求，就是 1000 × 20 = 20,000 次读，远超 3,000。所以 jitter 和 singleflight 解决的不是同一个乘数：前者打散 key 的个数，后者打散同一个 key 的并发。

加上大约 ±10% 的均匀抖动，30 秒变成大约 27 到 33 秒，窗口 6 秒。1,000 个 key 的到期摊在这 6 秒上，单飞之后大约 1000 / 6 ≈ 167 次填充每秒。没有单飞、每个 key 20 个并发时，大约 20000 / 6 ≈ 3,300 次每秒，仍贴着预算甚至略超，所以抖动不能代替单飞。两个数都假设到期后请求立刻到来、并且在窗口内均匀。真实到达会更抖，面试时把假设说出来，再问对方热 key 的并发大概是多少。

The path and the arithmetic

A warm-up or a deploy writes 1,000 hot catalog cards into the cache tier in the same second, base TTL 30 seconds, no jitter. At second 30 they miss together. If each key already has singleflight, each key causes one origin read, and that second is still 1,000 store reads. The store budget is 3,000 QPS, so 1,000 fits, but only for this assumed batch. Without singleflight, and with an assumed 20 in-flight requests per key in the expiry second, that is 1000 × 20 = 20,000 reads, far over 3,000. Jitter and singleflight are different multipliers. Jitter spreads the number of keys. Singleflight spreads the concurrency of one key.

A uniform jitter of about ±10 percent turns 30 seconds into about 27 to 33 seconds, a 6-second window. One thousand keys spread across those 6 seconds are about 1000 / 6 ≈ 167 fills per second after singleflight. Without singleflight, at 20 concurrent requests per key, about 20000 / 6 ≈ 3,300 per second, still against or slightly over the budget. Jitter does not replace singleflight. Both numbers assume a request arrives as soon as a key expires and that arrivals are uniform inside the window. Real arrivals are lumpier. Say the assumption, then ask how much concurrency the hot keys actually have.

抖动治不了缓存集群消失Jitter does not survive a missing cache tier

边界、替代、常见错误

雪崩这个词有时也被用来指缓存集群整层宕掉。那不是 TTL 对齐。所有 key 同时消失，抖动没有到期点可以错开。下一节的旁路和限流才是那条路径。把两件事都叫「改一下 TTL」会在集群宕机时毫无动作。

替代是分批预热：不要在同一秒写入全部热 key，写入时刻本身就错开，即使 TTL 相同，到期也会错开。代价是预热窗口里命中率较低，源站要能吃下那几分钟。另一替代是过期前刷新热 key，让它们在不同的后台周期里续期。冷 key 继续靠 TTL 自然过期，避免后台把整个 key 空间再扫一遍。

「所有 key 永不过期」会在改价之后失去 TTL 保险，只能靠会丢的 purge。「有 singleflight 就不需要 jitter」把每个 key 收成 1，1,000 个 key 仍是 1,000。一把分布式锁能挡住一个热 key，挡不住这一秒到期的 1,000 个不同 key。

Boundary, alternative, common mistake

Avalanche is sometimes also used for the whole cache tier being down. That is not aligned TTLs. Every key disappears at once, and jitter has no deadlines to stagger. The bypass and the rate limit in the next section are that path. Calling both problems “change the TTL” leaves you with nothing to do when the cluster is gone.

The alternative is to warm in batches. Do not write every hot key in the same second. The write times themselves stagger, so equal TTLs still expire apart. The cost is a lower hit rate during the warm-up window, and origin has to absorb those minutes. The other alternative is to refresh hot keys before they expire, on different background periods. Cold keys keep expiring by TTL so the background job does not rescan the whole key space.

“Never expire any key” removes the TTL backstop after a price change and leaves only a purge that can be lost. “Singleflight means jitter is unnecessary” collapses each key to one fill; one thousand keys are still one thousand. A distributed lock can hold one hot key. It cannot hold one thousand different keys due in the same second.

热 key，以及缓存层挂了以后The hot key, and what happens when the cache tier is down

8,000 QPS 的一个 key 先被谁吃掉Who absorbs one key at 8,000 QPS

正常路径

假设 sku-1842 占了峰值里的 8,000 QPS，大约是 40,000 的 20%。这些请求是命中，Store 几乎看不到它们。压力在持有这个 key 的那台缓存分片的 CPU 和网卡上。Nishtala 等人在讨论故障时写过，单个 key 可以占一台服务器请求的 20%；若故障时把 key 重哈希到幸存节点，接手的那台可能被这个热 key 打满。他们因此不用「剩下的节点分摊失败节点的 key」，而把失败的 get 转到一小池空闲机器。[3] 热 key 的复制要在故障之前做完，是计划中的额外副本，不是宕机瞬间的重哈希。

本地 LRU 先改变到达共享层的次数。30 个进程若把 8,000 QPS 均分，每进程大约 8000 / 30 ≈ 267 QPS。本地 TTL 5 秒，每个进程大约每 5 秒才向共享层要一次这个 key，30 个进程是 30 / 5 = 6 次共享读每秒，而不是 8,000。这是假设流量在进程间均匀、并且本地条目没被挤掉。复制到 4 个分片时，若客户端稳定地挑副本，每个分片大约 2,000 QPS。删除必须送到 4 个副本。少送一个，那个副本会在自己的 TTL 结束前一直回旧价。随机给每次请求加一个后缀，让 key 永远对不上，命中率会塌，那不叫复制。

Happy path

Assume sku-1842 is 8,000 of the peak QPS, about 20% of 40,000. Those requests are hits. The store barely sees them. The pressure is the CPU and the NIC of the cache shard that owns the key. Nishtala et al., writing about failures, note that a single key can account for 20% of a server’s requests. Rehashing a failed server’s keys onto the survivors can overload whoever inherits that hot key. They therefore do not spread a dead server’s keys across the rest. They send the failed get to a small pool of idle machines. [3] Replication of a hot key is done before the failure. It is a planned extra copy, not a rehash at the moment of the outage.

Local LRU changes how often the shared tier is touched. If 30 processes split 8,000 QPS evenly, each sees about 8000 / 30 ≈ 267 QPS. With a 5-second local TTL, each process asks the shared tier for this key about once every five seconds. Thirty processes are 30 / 5 = 6 shared reads per second, not 8,000. That assumes traffic is even across processes and the local entry is not evicted. Copied onto four shards, and if clients pick a replica stably, each shard sees about 2,000 QPS. The delete must reach all four. Miss one and that replica keeps returning the old price until its own TTL. Adding a random suffix on every request so the key never matches is not replication. The hit rate collapses.

为什么旁路必须有 3,000 这个数Why the bypass has to carry the number 3,000

为什么这样选

缓存层消失时，命中率按 0 计，到达 App 的仍是 40,000 QPS。Store 预算是 3,000。差额 40000 − 3000 = 37,000 必须在进 Store 之前被处理掉。限流器放行 3,000，其余要么 429，要么在本地 LRU 的 5 秒里继续用旧值。5 秒之后本地也空了，就只剩被放行的 3,000 能刷新。目录价格多陈旧 5 秒，通常还在 60 秒 SLO 里。库存扣减不能吃这 5 秒的旧值，应该失败关闭，而不是把旧库存当成功。两种数据不要共用「缓存挂了就读库」。

Nishtala 等人把「从 memcache 拿不到数据会把过大的负载打到后端，并可能级联」写成故障节的第一句。他们的 Gutter 大约是集群里 1% 的 memcached 机器。get 没有响应时，客户端改问 Gutter；Gutter 也 miss，才查数据库并把结果写入 Gutter。Gutter 里的条目很快过期，这样就不需要给 Gutter 做失效。完全故障时，Gutter 的命中率通常在 4 分钟内超过 35%，并常常接近 50%。他们还报告这套机制把客户端可见故障率降了 99%，并把每天 10% 到 25% 的失败变成了命中。[3] 这些百分比是他们的运行结果。没有这 1% 的备用池时，限流器就是同一句话的最小形式：失败的读不能每一条都变成数据库读。

Why the budget is on the arrow

When the cache tier disappears, hit rate is 0 and the app still sees 40,000 QPS. The store budget is 3,000. The difference, 40000 − 3000 = 37,000, has to be handled before the store. The limiter admits 3,000. The rest are a 429, or they keep using the local LRU value for its 5 seconds. After that the local copy is empty too, and only the admitted 3,000 refresh. Five extra seconds of catalog price usually still fits inside the 60-second SLO. An inventory decrement must not spend those five seconds of old stock. It fails closed. The two kinds of data do not share “the cache is down, so read the database.”

Nishtala et al. open their failure section by saying that the inability to fetch from memcache dumps excessive load on backend services and can cascade. Their Gutter is about 1% of the memcached machines in a cluster. When a get gets no response, the client asks Gutter. If Gutter also misses, the client reads the database and inserts into Gutter. Gutter entries expire quickly so Gutter does not need invalidations. When a server fails entirely, Gutter hit rates generally exceed 35% within four minutes and often approach 50%. They report that the mechanism reduces the rate of client-visible failures by 99% and converts 10% to 25% of failures into hits each day. [3] Those percentages are their operational results. Without that 1% spare pool, the limiter is the smallest form of the same sentence: a failed read must not become a database read one for one.

恢复时不要瞬间把缓存打满Do not refill the cache in one instant

恢复与常见错误

缓存恢复之后，若 40,000 QPS 同时 miss 去填，Store 会在恢复的第一秒看到雪崩。让请求继续走限流器，命中自然长回来；或者像他们的冷集群预热那样，向一个仍然热的集群要数据，而不是向数据库要。[3] 预热也有竞态：冷集群从热集群读到的值，可能在失效到达之前被写死。他们给冷集群的删除加了两秒的 hold-off，让这段时间里的 add 失败，客户端再去数据库拿新值。两秒是他们的参数。目录卡用得上的是「恢复期间填进去的值必须能被随后的删除打掉」，不是照抄两秒。

「Redis 挂了就无限制读库」丢掉 3,000 的预算。「热 key 加随机后缀」让 key 对不上，命中率塌掉。Nishtala 等人把短暂旧值的概率当成可调参数，用来换后端不被打穿。[3] 目录价格接受大约 30 秒；账本不接受。

Recovery and the usual mistakes

After the cache returns, if 40,000 QPS all miss and fill at once, the store sees an avalanche in the first second of recovery. Keep requests on the limiter and let the hit rate grow back, or do what their cold-cluster warm-up does: read from a cluster that is still warm instead of from the database. [3] Warm-up has a race. A value read from the warm cluster can be written into the cold cluster before the invalidation arrives. They put a two-second hold-off on deletes to the cold cluster so an add in that interval fails and the client fetches the new value from the database. Two seconds is their parameter. What the catalog card uses is “a value filled during recovery must still be killable by a later delete,” not a copied two-second constant.

“If Redis is down, read the database without a limit” drops the 3,000 budget. “Add a random suffix to the hot key” makes the key miss, and the hit rate collapses. Nishtala et al. treat the probability of a briefly stale read as a knob, traded so the backend is not punched through. [3] Catalog price accepts about 30 seconds. A ledger does not.

收口只重复三笔数：40,000 乘 0.05 是 2,000；旁路最多 3,000；本地 5 秒、共享大约 30 秒。改价先提交再 purge，TTL 是保险。负缓存、singleflight、jitter、限流旁路各管一种失败，不能合成一把锁。

Twenty-second close

The close repeats three numbers: 40,000 times 0.05 is 2,000; the bypass admits at most 3,000; local TTL is 5 seconds and the shared tier is about 30. Commit, then purge; TTL is insurance. Negative cache, singleflight, jitter, and a budgeted bypass each own one failure. They are not one lock.

A cache may evict and may be briefly stale, so it stands beside authority and does not replace the store. [3] Another regional cache is another invalidation pipe, still sized by the 60-second SLO. Load balancing is the next chapter.
