缓存与 CDNCache and CDN

约 35–45 分钟 · 前置：Ch02、Ch03、Ch37 · 7 组 / 38 帧演进图~35–45 min · after Ch02, Ch03 and Ch37 · 7 decks / 38 evolving frames

本章要点：读懂路径、限制旧值寿命、控制回源压力Three decisions to retain

  • 先讲清一次读取：请求沿 Client → Edge → Shield → App 前进。旁路缓存（look-aside）未命中时，由 App 查询 Store，再把结果写回缓存。
  • 再限制旧数据的寿命：数据从权威查询开始就有固定的硬截止时间（hard deadline）。复制数据、软刷新失败或重新包装 HTTP 响应，都不能延长这个期限。
  • 最后控制回源压力：请求合并（singleflight）减少同一个 key 的重复查询，随机抖动（jitter）错开不同 key 的刷新时间；缓存失效时，独立的回源预算继续保护数据库。
  • Draw real origin paths: Client → Edge → Shield → App; App owns a look-aside miss, reads Store and fills the side cache.
  • Bound stale evidence: hard expiry starts before the authoritative query; copies, failed refresh and HTTP repackaging cannot renew it.
  • Limit amplification: singleflight collapses one key, jitter spreads different keys, and independent origin admission survives cache loss.

范围：公开目录允许短暂滞后，结算以权威数据为准Scope: public display may lag; checkout remains authoritative

本章用 GET /catalog/sku-1842 串起整个设计。它返回公开价格、商品状态、版本和图片 URL。图片使用带内容哈希的路径，文件由对象存储经 CDN 返回；结算、余额和扣库存则由权威事务处理。公开展示可以短暂使用旧数据，但缓存中的价格不能作为成交承诺。

教学目标：更新提交后发起的新查询，最迟在 60 秒内不再成功返回旧值；没有发起请求的网页不会自动重绘。断网或依赖失联时，系统可以返回失败，不能无限使用旧数据返回 200。下文的 A1–A12 都是本例设定的假设。

The object is GET /catalog/sku-1842: public price, status, revision and image URL. Content-hash image bytes travel from object storage through CDN; checkout, balances and stock decrements use authoritative transactions. A bounded-old display price cannot authorize a sale.

Teaching target: new queries after an update commits stop returning old successful values within 60 seconds. Idle pages do not repaint automatically. Disconnection or dependency loss may fail rather than return stale 200 forever. All A-numbers below are assumptions.

读路径：分别计算 App 的到达量与 Store 的读取量Read path: size App and Store separately

一次公开目录读取先到边缘缓存 Edge；新鲜命中就直接返回，未命中才进入父缓存 Shield。Shield 也未命中时，请求才到应用服务 App。App 再查本地缓存 L1 和图中的远程缓存 Cache tier，后者只返回命中或未命中。未命中后，App 自己查询 Store，接收记录，再向缓存发起带原子资格校验的回填（guarded fill）。HTTP 响应仍经 Shield、Edge 返回客户端。这种按需填充的旁路缓存没有数据库连接。[4]

如果回填 SET 失败，刚读到的权威记录仍可在年龄和权限都合格时返回。Store 查询超时则没有证明商品不存在，因此不能把结果缓存为 null，也不能返回 404。

A fresh Edge hit replies immediately. Edge misses reach Shield, then App on Shield miss. App checks L1 / Cache tier, which only returns hit or miss. App owns the miss, SELECTs Store, receives the row and guarded-fills. HTTP replies still traverse Shield and Edge. This demand-filled look-aside cache has no database connection. [4]

A failed SET need not discard a freshly read row that still meets age and permission constraints. A Store timeout proves no absence and cannot become cached null or 404.

逐层推导：把条件未命中率相乘Derivation: multiply conditional miss rates

按 A2 计算：40,000×20%=8,000 次/秒到达 Shield；再乘 50%，剩下 4,000 次/秒到达 App；App 内部缓存又有 50% 未命中，才得到每秒 2,000 次 Store 读取。总未命中率为 0.2×0.5×0.5=5%，因此总命中率为 95%。App 实际收到每秒 4,000 次请求，不能按 2,000 次来配置容量。

如果总命中率降到 90%，Store 就要承受每秒 4,000 次读取，超过每秒 3,000 次的预算。若只靠缓存命中来满足这份预算，命中率至少要达到 1−3,000/40,000=92.5%。验证、预热和每一次真正发出的重试也消耗同一份额度。

A2: 40,000×20%=8,000/s reach Shield; another 50% leaves 4,000/s at App; another 50% cache miss leaves 2,000/s at Store. Miss fractions multiply to 5%, giving 95% hits. Do not size App at 2,000/s.

At 90% hits, Store receives 4,000/s, above its 3,000/s read budget. Hits alone must reach 1−3,000/40,000=92.5%. Validation, warm-up and every actual retry share that budget.

什么时候值得保留 Shield、L1 和缓存准入算法When Shield, L1 and admission are worthwhile

Shield 要减少重复回源，除了汇聚路由，还必须把同一个可共享表示、同一个在途窗口中的请求合并起来。A11 中“40 个 POP 合成 1 次回源”是理想情况；窗口错开、存在多个 Shield，或响应为 private、请求直接透传（pass）时，回源都可能多于 1 次。[8] 如果 POP 少，或很少有冷对象请求需要汇聚，可以省去 Shield。

A8 的 L1 热集占用为 80,000×2,000×1.5=240 MB/进程，30 份共 7.2 GB，均按十进制单位计算。这只能估算内存，不能证明命中率。扫描读取可能把常用数据挤出 LRU；TinyLFU 按频率决定哪些对象进入缓存，W-TinyLFU 再结合窗口作取舍，代价是额外元数据，但它们也不能保证本例达到 95% 命中率。[9]

Shield routing alone is insufficient: collapse must cover the same shareable representation in the same in-flight window. A11’s 40 POPs→1 fetch is ideal; separate windows, multiple Shields and private/pass responses produce more. [8] Few POPs or cold objects may not justify Shield.

A8’s L1 hot set costs 80,000×2,000×1.5=240 MB/process, or 7.2 GB across 30 copies, in decimal units. Memory does not prove hits. Scans can pollute LRU; TinyLFU admission and W-TinyLFU windows trade metadata for admission decisions, without guaranteeing this catalog’s 95%. [9]

HTTP：先选对表示，再判断能否复用HTTP: select a representation before reuse

是否保存、能否复用、是否读取权威数据，是三个不同的决定。未限定字段的 private 禁止共享缓存保存；no-store 禁止保存本次请求或响应；no-cache 允许保存，但复用前必须验证成功。它们都不会自动绕过 App 的 L1 或 Redis。[1 §5.2.2]

本章采用更严格的策略：在查询共享缓存之前，就让带 Authorization、Cookie 的请求和个性化接口直接透传到 App，App 仍需鉴权。RFC 允许在 public / s-maxage / must-revalidate 等明确指令下共享某些带 Authorization 的响应，Cookie 也不是 RFC 统一规定的禁存开关。Vary 只用于区分表示，不能代替授权。[1 §3.5, §4.1]

缓存 key 要覆盖方法、URI、语言、编码等真正影响表示的输入。只有源站也不根据某个参数改变正文、权限、签名和跳转时，才能在规范化中去掉它。ETag 还要覆盖内容、渲染器版本和表示；转码或压缩后，不能继续沿用已经不适用的强 ETag。[2 §8.8.3]

Storage, reuse and authoritative reads are separate decisions. Unqualified private forbids shared storage; no-store forbids storing this request/response; no-cache permits storage but requires successful validation before reuse. None automatically bypasses App L1/Redis. [1 §5.2.2]

This chapter passes Authorization, Cookie and personalized routes before shared lookup; App still authenticates. RFC rules permit some authenticated responses with explicit public / s-maxage / must-revalidate directives, and Cookie is not a universal storage prohibition. Our policy is deliberately stricter. Vary selects representation rather than authorizing access. [1 §3.5, §4.1]

Keys cover method, URI and actual language/coding inputs. Normalize a parameter only when origin also ignores it for body, authorization, signatures and redirects. ETags cover content, renderer version and representation; transformations cannot reuse an invalid strong validator. [2 §8.8.3]

关键实现：到达 App 的 304 验证也要读取权威数据Implementation: a 304 also needs current evidence

下面的策略伪代码对应第 3–6 帧。普通请求命中时，可以使用尚未超过硬期限的内部副本；条件验证一旦到达 App，或请求明确要求权威验证，App 就要查询主库的新快照。请求 Cache-Control、Date/Age、条件头语法和实际发送由 HTTP 栈处理，因此这段代码不是完整的 HTTP 缓存实现。GET 的 If-None-Match 使用弱比较，并支持列表和 *。[2 §13.1.2]

This policy pseudocode covers frames 3–6. Ordinary hits may use internal copies within hard age; conditionals reaching App and explicit authoritative-validation requests read a new primary snapshot. The HTTP stack handles request Cache-Control, Date/Age, conditional syntax and transport. This is not a complete HTTP cache. GET If-None-Match requires weak comparison, lists and *. [2 §13.1.2]

# Policy pseudocode, not an HTTP parser or a CDN implementation.
# The Edge applies this pass policy BEFORE any shared-cache lookup.
if request.Authorization or request.Cookie or route.isPersonalized:
    return passToAuthorizedApp(cacheControl="private, no-store")

# Origin App: canonical key includes URI + language + content coding.
key = selectedPublicRepresentation(request)
if request.IfNoneMatch or request.requiresAuthoritativeValidation:
    observed = clock.now()             # before a NEW primary snapshot
    row = originBudget.readPrimary(key) # timeout/rejection -> 503 no-store
    evidence = primaryEvidence(row, observed)
else:
    evidence = appCache.getOrReadPrimary(key)

# Evidence retains the ORIGINAL hard deadline across every cache copy.
now = clock.now()                       # ONE eligibility/budget sample
if not evidence.canSend(now):
    return error(503, cacheControl="no-store")

n = evidence.sharedSeconds(now) # deduct clock + final-send margin
headers = {
    CacheControl: "public, max-age=0, s-maxage=" + n + ", must-revalidate",
    Vary: "Accept-Language, Accept-Encoding",
    ETag: weakTag(evidence, key)
}

# RFC parser handles lists, weak comparison and '*' for this GET.
if evidence.exists and ifNoneMatchMatches(request, headers.ETag):
    return response(304, headers, noBody)
return response(evidence.exists ? 200 : 404, headers, evidence.body)
# Date/Age accumulation belongs to the HTTP stack; never reset Age at Shield.
# From the now check THROUGH final send: <=1s total; otherwise abandon.

目录基线是 public, max-age=0, s-maxage=n, must-revalidate。浏览器每次复用前都要验证，但共享缓存可以在 n 秒新鲜期内回答浏览器的条件请求，所以每次验证未必都到主库；只有真正到达 App 的验证才取得新证明。304 节省了响应正文，不一定省下 Store 查询；如果总拿缓存中的旧 v1 与 v1 比较，就会反复延长旧证明。n 要受内部数据的剩余期限限制，并扣除时钟与最终发送余量，第 3 组给出计算代码。

404 也要显式设置短期限，503/429 默认使用 no-store。CDN 清除（purge）不会删除浏览器已存的内容，也收不回已经发出的响应；[11] 浏览器的 max-age=0 和共享缓存的年龄上限分别约束各自的复用行为。

The baseline public, max-age=0, s-maxage=n, must-revalidate makes browsers validate; a shared cache may answer their conditionals within n seconds, so not every browser validation reaches primary. Only validation reaching App obtains new evidence. A 304 saves the body, not necessarily a Store read; comparing cached v1 to itself could renew stale evidence forever. Cap n by internal age, clock and final-send margins; the next group implements it.

404 has explicit short life; 503/429 default to no-store. CDN purge cannot remove browser copies or already sent responses. [11] Browser max-age=0 and the shared age cap serve distinct boundaries.

状态码与另一套允许旧数据的策略Status codes and a separate stale-tolerant profile

302 不属于可启发式缓存的响应，但显式设置新鲜期后可以允许缓存；404 则可以被启发式缓存，因此确认不存在的响应应显式设置短期限。跳转直接命中缓存时，也会跳过源站的点击日志。[2 §15.4.3, §15.5.5]

其他允许旧数据的对象，可以另选 max-age=10, stale-while-revalidate=5, stale-if-error=15。SWR 允许复用到数据年龄 15 秒，出错时的旧值退路允许到 25 秒；两个窗口都从响应变旧时起算，不能相加成 30 秒。[3] 这是一套单独的策略。若要与目录基线中严格的 s-maxage / must-revalidate 结合，必须先核对供应商的指令优先级和扩展支持。

302 is not heuristically cacheable but explicit freshness can permit storage; 404 is heuristically cacheable, so absence needs an explicit short life. Cached redirects also skip origin click logs. [2 §15.4.3, §15.5.5]

Other stale-tolerant objects may use max-age=10, stale-while-revalidate=5, stale-if-error=15: SWR extends to age 15, error fallback to 25. Both start at staleness and do not sum to 30. [3] This is a separate profile; do not casually stack it on the strict catalog s-maxage / must-revalidate policy without checking provider precedence/support.

更新：持久保存失效任务，并保留固定硬期限Updates: durable invalidation plus fixed hard expiry

改价时，App 在同一个 Store 事务中提交 row.version=2 和 Outbox(event_id,sku,version,targets)。收到确认，只表示权威记录和失效待办已经持久保存。Relay 按目标分别重试：先提高应用缓存的版本下界、撤销填充令牌并删值，再清除 CDN 缓存，减少边缘刚清空又读回旧数据的机会。

回执表示什么，要以供应商契约为准。“已接受”不等于所有 POP 都已应用；Relay 要能查询同一请求，或安全地重复 purge，不能把“已经发出”当成完成。处理重复或乱序事件时，版本下界始终取最大值。漏送、L1 未收到通知，以及在途的旧响应，仍由硬期限限制寿命；本例没有承诺写入后全球读取立即线性一致。

A price update commits row.version=2 with Outbox(event_id,sku,version,targets) in one Store transaction. Acknowledgement means durable authority and work only. Relay retries per target: raise application-cache floor, revoke fill tokens and evict, then purge CDN to reduce old-origin refill.

Receipt meaning depends on the provider contract. Accepted is not applied everywhere. Query the same request or safely repeat purge; sending is insufficient completion. Version maxima absorb duplicate/reordered events. Lost delivery, unnotified L1 and in-flight old replies still need hard age. There is no globally linearizable read-after-write promise.

关键实现：复制数据时保留原 hardExpiresImplementation: copies preserve hardExpires

下面的 Java17 可运行片段在权威查询开始前记录 observedAt，并要求查询使用主库的新快照。存在的记录有 20 秒硬期限，确认不存在的记录有 5 秒。L1 副本最长保留 5 秒，同时沿用原来的 hardExpires。构造新 HTTP 响应时，共享新鲜期 n 不超过 10 秒；先从剩余时间扣除 2 秒跨节点时钟差和 1 秒最终发送预算，再向下取整。n=0 表示没有共享新鲜期；这次直接响应能否发送，仍要通过 canSend 检查。

This runnable Java17 excerpt captures observedAt before a new primary query: twenty seconds for positive evidence, five for absence. L1 lasts at most five seconds and keeps the original hardExpires. A new HTTP response caps n at ten, subtracts two seconds of cross-node clock difference and one final-send second, then floors. n=0 grants no shared freshness; a direct response still requires canSend.

record Evidence(long version, long observedAtMs, long hardExpiresMs) {
    Evidence {
        if (version < 0 || hardExpiresMs <= observedAtMs) {
            throw new IllegalArgumentException("invalid evidence");
        }
    }

    static Evidence primary(long version, long readStartMs, boolean absent) {
        long life = absent ? 5_000 : 20_000;
        return new Evidence(version, readStartMs, readStartMs + life);
    }

    long l1Expires(long nowMs) {
        return Math.min(nowMs + 5_000, hardExpiresMs - SKEW_MS);
    }

    boolean canSend(long nowMs) {
        return nowMs + SKEW_MS + SEND_MS < hardExpiresMs;
    }

    long sharedSeconds(long nowMs) {
        long remaining = hardExpiresMs - nowMs - SKEW_MS - SEND_MS;
        return Math.max(0, Math.min(10, remaining / 1_000));
    }
}

例如，原截止时间为 120 秒，当前为 114 秒，n=floor(120−114−2−1)=3 秒，不能重新给出 10 秒。剩余时间恰好只有 3 秒时，canSend 就会拒绝；从资格检查到最终发送必须控制在声明的 1 秒内，做不到就要放弃响应。软刷新失败时，必须保留同一组 observedAt/hardExpires，不能把 now 当成新的读取证明。无法通过时钟健康检查时，就停止使用这条允许有限旧值的路径。

Shield 转发同一个 HTTP 响应时，要保留 Date，并按 RFC 累计 Age；App 把内部对象包装成新响应时，则按剩余寿命计算新鲜期。[1 §4.2.3] 即使内容没有变化，只要重新查询主库并验证成功，也能建立新证明；单纯复制旧数据做不到这一点。

With original expiry at 120s and now 114s, n=floor(120−114−2−1)=3s, rather than a new ten seconds. canSend refuses only three seconds remaining; more than one second from eligibility check through final send abandons that response. A failed soft refresh keeps the same observedAt/hardExpires, never substituting now as fresh evidence. Unhealthy clocks close this bounded-stale path.

Shield preserves Date and accumulates Age for the same HTTP response; App repackaging internal objects uses the remaining-life cap. [1 §4.2.3] A fresh primary verification can renew evidence even if bytes did not change, unlike an old copy validating itself.

怎样满足 60 秒目标，内容哈希图片又保证什么The 60-second target and immutable-image boundary

如果每层都重新计算 TTL，L2 的 33 秒、L1 的 5 秒和 Edge 的 30 秒会叠成 33+5+30=68 秒，迟到回填还可能继续延长。所有副本共用一个硬截止时间后，就不会再逐层累加。本例仍取保守范围 20+2+1+1=24 秒<60 秒，其中另计了跨节点时钟差、读取/填充和最终发送余量。代码还会扣除余量，所以 24 秒不是紧确上界。这依赖新快照、健康时钟、受限的发送时间和正确累计的 HTTP Age；任何一项不成立，都不能沿用这个保证。

图片文件要先写完并验证，目录 v2 才能引用新的哈希 URL，旧路径不能覆盖。immutable 只承诺表示在新鲜期内不变，不承诺永久保留或立即撤销。[7] 旧目录仍可能引用旧图片；敏感内容下架还需要单独的访问控制和清理策略。

Restarting each tier’s TTL gives 33s L2 + 5s L1 + 30s Edge = 68s, before late fills. A shared deadline avoids adding layers. Keep a conservative 20+2+1+1=24s<60s envelope for clock difference, read/fill and final send; code subtracts margins, so 24s is not tight. Fresh snapshots, healthy clocks, bounded sends and correct HTTP Age are prerequisites.

Publish and verify image bytes before card v2 references a new hash URL; never overwrite the old path. Immutable promises unchanged representation during freshness, not permanent retention or instant revocation. [7] Old cards can reference old images; sensitive removal needs separate access and cleanup policies.

并发：合并重复查询，在回填时校验资格Concurrency: collapse work and guard fills

这里需要两个不同的保证：请求合并减少重复工作，回填守卫则拒绝已经失去资格的写入。图中，读取方取得 e7 并读到 v1；写入方提交 v2 后发起失效，缓存在一个原子操作中提高版本下界、撤销 e7 并删值。旧读取方恢复后再做 SET(v1,e7)，就会被拒绝；取得新令牌 e8 的读取方必须重新查询主库。

只有过期锁还不够：旧持有者暂停到锁过期后，仍可能恢复执行。Redis 用唯一的持有者标识，并在删除前比较，可以避免删掉接任者的锁，却不会自动阻止普通 SET 写入。[6] Facebook 的 lease 机制把未命中令牌与删除时的撤销联动起来；本例借用这一机制，不沿用其生产测量结果。[4 §3.2.1]

Two guarantees: singleflight reduces work; guarded fill rejects writers whose eligibility was revoked. Reader e7 obtains v1; writer commits v2, then cache atomically raises floor, revokes e7 and evicts. Resumed SET(v1,e7) is refused. A new e8 must query primary again.

An expiring lock is insufficient: a paused old owner can resume. Redis unique ownership and compare-before-delete avoid deleting a successor’s lock but do not fence ordinary SET. [6] Facebook leases connect miss tokens to deletion revocation; we borrow the mechanism rather than extrapolate its measurements. [4 §3.2.1]

关键实现 A：等待者超时，不会取消共享任务Implementation A: waiters cannot cancel shared work

这段 Java17 代码为每个等待者返回独立的 future。等待者可以让自己的 future 超时或取消，负责查询的共享任务（loader）要到实际返回后才从 Group 移除。命中缓存的请求应在加入 Group 前直接处理；合并 key 要包含租户、语言和表示等作用域。一个 Group 只覆盖当前进程，因此 30 个进程仍可能各有一个发起查询的 leader。[5]

This Java17 excerpt returns a private future. A waiter may time out or cancel it; the shared loader stays registered until it actually returns. Check cache hits before joining; keys include tenant, language and representation scope. One Group covers one process, so thirty processes may still lead independently. [5]

private final ConcurrentHashMap<String, CompletableFuture<T>> calls =
        new ConcurrentHashMap<>();
private final Executor executor;

public SingleFlight(Executor executor) {
    this.executor = executor;
}

public CompletableFuture<T> join(String key, Supplier<T> fetch) {
    var leader = new CompletableFuture<T>();
    var existing = calls.putIfAbsent(key, leader);
    var shared = existing == null ? leader : existing;

    if (existing == null) {
        try {
            executor.execute(() -> {
                try {
                    leader.complete(fetch.get());
                } catch (Throwable error) {
                    leader.completeExceptionally(error);
                } finally {
                    calls.remove(key, leader);
                }
            });
        } catch (RuntimeException rejected) {
            leader.completeExceptionally(rejected);
            calls.remove(key, leader);
        }
    }

    return shared.thenApply(value -> value); // private waiter future
}

loader 必须给实际查询设置期限，或能确认取消已经完成。逻辑超时只表示调用方不再等待，不能证明 SQL 已停止，也不能提前归还 Store 的真实并发名额。依赖仍在执行、结果未知时，要保留在途状态并继续探测；每个等待者最终发送前，还要重新检查数据年龄。

The loader needs a bounded physical query or confirmed cancellation. A logical timeout ends waiting without proving SQL stopped or releasing real Store concurrency permits. Retain and probe unknown in-flight work; each waiter rechecks age before sending.

关键实现 B：在缓存写入口完成原子检查Implementation B: atomicity belongs at cache writes

下面是缓存服务事务伪代码。同源的 cache.py 在同一个 SQLite 文件上用 BEGIN IMMEDIATE 实现它，并由多个独立进程竞争执行。这个示例只验证缓存写入的原子边界，不代表 Redis 集群。领取填充资格（claim）时要重新检查缓存值，拿到写锁后再取当前时间。版本下界、令牌、运行代次和缓存值都由同一个权威端管理，业务 Store 事务另有自己的边界。[10]

This cache-service transaction pseudocode is implemented by cache.py using BEGIN IMMEDIATE on one SQLite file, exercised by independent processes. It tests that write boundary, not a Redis cluster. Recheck values during claim and sample time after acquiring the lock. Floors, tokens, epoch and cache values share one authority; business Store transactions are separate. [10]

# Cache-service transaction pseudocode; one authority owns metadata per key.
# Atomic = BEGIN IMMEDIATE / COMMIT in this example's shared SQLite file.
claim(key):
    atomic:
        now = clock.now()                     # sample AFTER write lock
        state = metadata.getOrCreate(key)      # floor persists; value is evictable
        if value[key] exists and value[key].hardExpires > now + 2000ms:
            return HIT(value[key])
        if state.leaseUntil > now:
            return WAIT

        state.ticket = randomUniqueToken()
        state.leaseUntil = now + 1000ms
        return (runtime.epoch, state.ticket)

invalidate(key, revision):
    atomic:
        state = metadata.getOrCreate(key)
        state.floor = max(state.floor, revision)
        state.ticket = null;
        state.leaseUntil = 0
        delete value[key]

guardedFill(key, token, evidence):
    atomic:
        now = clock.now()
        state = metadata.get(key)
        require metadata exists and token == (runtime.epoch, state.ticket)
        require now < state.leaseUntil and evidence.version >= state.floor
        require evidence.hardExpires - evidence.observedAt == (evidence.absent ? 5000ms : 20000ms)
        require evidence.observedAt <= now + 2000ms
        require now + 2000ms < evidence.hardExpires

        value[key] = evidence                  # keep ORIGINAL hard deadline
        state.ticket = null;
        state.leaseUntil = 0
# Restart rotates epoch; missing metadata rejects old tokens, never grants them.

先确认令牌相等，再执行普通 SET，仍然有竞态，因此检查与写入必须在同一个事务中完成。记录填充资格的元数据不能随缓存值一起被悄悄淘汰：元数据缺失时拒绝旧令牌，重启时更换运行代次。一次成功 fill 会消耗令牌，重复、过期或已撤销的请求都被拒绝。重复的低版本失效事件可能再删一次值，但不能降低版本下界。

信任与恢复也有前提：App 取得新令牌后，必须开始新的主库查询，并提供真实版本、原 observedAt 和固定期限；缓存无法识别 App 伪造的版本或时间。证明对象不存在，也要有权威的删除标记或修订号（tombstone/revision），不能在已有更高版本下界时猜 version=0。如果重启丢失了版本下界，就须恢复权威元数据，或更换运行代次并全部重新查询。TTL 只是失效通知遗漏后的后备保护，不能提供即时的全球新鲜度。

Checking a token followed by ordinary SET still races; validation and write must share one transaction. Eligibility metadata cannot silently disappear with value eviction; missing metadata rejects old tokens and restart rotates epoch. Fill consumes a token once, rejecting duplicates, expiry and revocation. A duplicated low-revision invalidation may evict again but cannot lower the floor.

Trust and recovery: after a new token, App begins a new primary query and supplies authentic revision, original observedAt and fixed lifetime. Cache cannot detect fabricated versions/timestamps. Absence needs authoritative tombstone/revision rather than guessed zero after a higher floor. Lost floors require restored authority metadata or a new epoch plus new queries; TTL remains a backstop, not immediate global freshness.

为什么 Write-through / Write-back 不能自动解决竞争Why Through / Back do not automatically fix races

如果 Write-through 只是先同步写库，再写缓存，旧读取方仍可能回填覆盖新值，两边也可能只有一边成功；因此还需要按版本原子替换，并修复失败。Write-back 则先确认、后刷盘，故障时可能丢失尚未刷出的更新。它可以用于讨论允许丢失的粗略计数，不应默认作为价格或账本的权威方案。强读仍须遵守权威读取契约。

DB-then-cache write-through can still suffer stale reader overwrite and partial failure; it needs versioned replacement and repair. Write-back acknowledges before flushing and can lose unflushed work; discuss it for lossy counters rather than default price/ledger authority. Strong reads use the authoritative contract.

不存在与未知：确认缺失才返回 404，超时返回失败Absence: 404 is evidence; timeout is unknown

只有 Store 的新快照确认对象不存在，App 才保存类型明确的 absent，并把它与商品下架状态分开。负记录的硬期限为 5 秒，CDN 的 404 响应也只能使用剩余期限。创建商品时，同样要提交 outbox、删除负记录并撤销旧查询的填充令牌；否则，“旧查询确认不存在 → 创建并 DEL → 旧查询迟到 SET absent”就可能让 404 再次出现。超时、连接失败或回源额度不足都返回 503，不能编造不存在的结论。

A9 中，100 个 key 被重复访问，合计每秒 2,000 次。只有忽略查询耗时、缓存淘汰和全部安全余量，TTL 理想模型才得到 100/5=20 次读取/秒。实际 claim 要求 hard>now+2s 才算命中，因此 5 秒硬期限只提供不足 3 秒的 L2 复用时间。在瞬时填充、持续重复访问的假设下，权威读取量约为 100/(5−2)=33.3 次/秒。首波仍可能同时发起 100 次读取，所以它既不是任意一秒的上限，也不是端到端上限。

App 的 canSend 还要预留从检查到发送的 1 秒，因此同一份不存在证明，只有在年龄不足 2 秒时才能成功返回 404。当前 HTTP 伪代码对年龄不合格的数据返回 503，不会自动重读；若要持续成功响应，就要另外设计刷新或验证策略，并计入 Store 预算。共享 HTTP 命中和到达源站的条件验证也会改变读取频率，不能把 33.3 次/秒当成端到端容量结论。每次更换新 id 时，仍然没有复用收益。

处理请求时，先检查格式、租户权限和入口配额。Bloom 过滤器的“无假阴性”只针对已经同步的成员集合；新建记录还没进入旧过滤器时，直接拒绝会误伤，因此需要在创建时登记，或加一层保存近期新增成员的 overlay。无法确认同步状态时，就在预算内查询权威数据；假阳性只会增加读取，不能授予对象访问权限。本组图省略了整段 HTTP 层，图中已经画出的内部调用者仍要逐跳经过。

Cache typed absent only after a new Store snapshot proves absence, distinct from withdrawn status. Its hard life is five seconds; CDN 404 uses only remaining life. Creation also commits outbox, evicts negatives and revokes absence tokens, preventing old absence → create/DEL → late SET absent. Timeout, connection loss and admission denial return 503 rather than invented absence.

A9 repeats 100 keys at 2,000/s. Only a TTL idealization ignoring query time, eviction and all safety margins gives 100/5=20 checks/s. Actual claim hits only while hard>now+2s, leaving under three seconds of L2 reuse from a five-second hard lifetime. With instantaneous fills and continued reuse, the rate is about 100/(5−2)=33.3 authoritative reads/s. The first wave may still contain 100; this is neither a per-second nor an end-to-end bound.

App canSend subtracts one more second from check through send, so the same absence evidence can return a successful 404 only below age two seconds. The HTTP pseudocode returns 503 for unsafe age rather than automatically rereading. Continuous successful responses need an explicit refresh/validation policy charged to Store. Shared HTTP hits and origin conditionals also change rates: 33.3/s is not end-to-end capacity. Unique IDs still gain no reuse.

Check format, tenant permission and ingress quota. Bloom no-false-negative claims cover only synchronized membership; new rows missing from old filters require creation registration or a recent-add overlay. Unknown synchronization falls back to budgeted authority. False positives add reads, not authorization. This diagram wholly omits HTTP layers while preserving every drawn caller.

软刷新：随机抖动只能错开刷新，不能延长硬期限Soft refresh: jitter cannot extend hard expiry

A10 中，1,000 个 key 同时需要刷新，每个有 20 个请求。不合并会产生 20,000 次读取，合并后仍有 1,000 次。给 16 秒的软期限加入 ±10% 随机抖动后，刷新点分布在 14.4–17.6 秒，硬期限仍是原查询起点 +20 秒。

假设均匀采样，且到期立即有请求，3.2 秒窗口内平均有 1,000/3.2=312.5≈313 次合并填充/秒；不合并则为 6,250 次/秒。随机采样仍可能聚集，平均值不能证明峰值不超过 3,000，所以每次回源仍须经过准入检查。

软过期后，只要还在硬期限内，就可以先返回现有数据，让一个 leader 刷新。刷新失败不能重设原期限；达到硬期限后，必须取得新证明或返回失败。分批预热也共用回源预算。整层宕机时没有 TTL 可供分散，随机抖动不能代替回源保护；随机制造新 key 也不能代替热点副本。

A10 refreshes 1,000 keys with twenty callers each: 20,000 reads without collapse, still 1,000 with it. Jittering a sixteen-second soft life by ±10% gives 14.4–17.6 seconds; hard age remains original query start +20 seconds.

Uniform sampling and immediate arrivals yield 1,000/3.2=312.5≈313 collapsed fills/s across 3.2 seconds, or 6,250/s without collapse. Random samples can cluster; an average does not cap peaks at 3,000. Every origin attempt still needs admission.

After soft expiry, serve existing data within hard age while one leader refreshes. Failed refresh preserves the original deadline; hard expiry requires new evidence or failure. Staggered warm-up shares the budget. Total loss has no TTL schedule to spread, and manufacturing random keys is not hotspot replication.

整层故障：在 Store 前保留独立的回源预算Total loss: independent admission protects Store

先确认哪一层出了故障。在 A2 下，如果只丢失 L2，L1 也未命中，到达 App 的仍是每秒 4,000 次请求；预算只有 3,000 次，因此至少每秒拒绝 1,000 次。只有 HTTP 层也全部冷或直接透传，且没有请求合并时，才是 40,000−3,000=37,000 次/秒。两种情况不能都只说成“缓存挂了”。

App 对失联缓存有限等待后打开熔断。图中的 Origin budget 是包在 Store 访问前的逻辑层：获准才发起查询，结果再经这层、App、Shield、Edge 返回。每秒 3,000 次是所有进程共用的总额，验证、刷新、预热和重试都消耗它，同时最多允许 100 次真实查询在途。预算协调不能依赖故障中的缓存；与协调方失联时，只能用完已分配的有界本地额度，随后关闭回源旁路。

逻辑超时不会释放仍在执行的 SQL 名额，只有实际完成或确认取消后才能归还。容量不足返回 503，明确的入口配额限制可以返回 429，错误响应默认 no-store。L1 仍受原硬期限限制，不能无限用旧数据降级。恢复时先探测，再按同一预算逐步回填，并用新运行代次拒绝旧令牌；不能同时清空所有 L1、purge Edge 并全量预热。

观测时，分别统计每层在其到达请求中的命中率和真实查询尝试，检查内容年龄、令牌拒绝量、在途数与准入量、最老 outbox 待办，以及 Store 尾延迟。缓存在线，并不证明回源量已经安全。每秒 3,000 次和 100 并发都只是未经过压测的教学预算。

Identify the failed tier. With A2, losing L2 plus L1 misses still sends 4,000/s to App, shedding at least 1,000 above the 3,000 budget. Only all-cold/passed HTTP layers without collapse produce 40,000−3,000=37,000 shed/s.

After bounded cache timeouts, App opens its circuit. Origin budget wraps Store: admitted calls return via the wrapper, App, Shield and Edge. The 3,000/s cap is global, not per process; validation, refresh, warm-up and retries share it, alongside 100 actual in-flight calls. Admission cannot depend on the failed cache; coordinator loss may consume only bounded preallocated permits, then fails closed.

A logical timeout does not release a slot while SQL still executes; wait for completion or confirmed cancellation. Capacity failure uses 503; explicit ingress quota may use 429, with no-store errors. L1 obeys original hard age. Recover with small probes, paced budgeted fill and a new epoch; do not simultaneously clear every L1, purge Edge and prewarm everything.

Observe per-tier conditional hits and actual attempts, content age, token rejection, concurrency/admission, oldest outbox and Store tail latency. An online cache does not prove safe origin load. The 3,000/s and 100 limits are unbenchmarked teaching budgets.

热点练习：L1 与显式副本各有哪些成本Hotspot exercise: L1 versus explicit copies

A8 单独假设一个热键每秒有 8,000 次请求到达 App，替换了 A2 中 App 总共每秒 4,000 次的设定。30 个进程均分后，每个约 267 次/秒。如果 L1 能稳定保留 5 秒，L2 剩余寿命也足够，L2 每秒约收到 30/5=6 次 get，冷启动、失效和硬期限边界会增加访问。若关闭 L1，改成显式复制四份值，均匀读取时每份约 2,000 次/秒，但四份都要维护版本下界、令牌撤销和失效。单纯增加分片（shard），不会把同一个 key 的请求分散开。

A8 separately sends App one hot key at 8,000/s, replacing A2’s 4,000/s total. Thirty processes average 267/s each; stable five-second L1 copies with sufficient L2 life yield about 30/5=6 L2 gets/s, plus cold starts, invalidation and hard-expiry boundaries. Without L1, four explicit value replicas average 2,000/s each and all need floors, revocation and invalidation. More shards do not distribute one key.

面试追问：把答案落到具体请求路径上Follow-ups and failure modes: answers must name a path

“写完马上刷新，怎样保证看到新价格？”写响应可以直接带回 v2；下一次强读携带 min_version=2，绕过共享缓存，再由 App 查询权威数据，或验证读取值确实满足版本下界。公开目录读取仍只承诺有限陈旧。不能把 Write-through 的两步双写称作事务，就声称所有浏览器会同时看到新值；单个用户的写后读保证，与全球副本收敛是不同要求。

“什么时候加一层或减一层缓存？”要一起考虑允许陈旧多久、对象能否复用、网络距离和回源预算。个性化请求先绕过共享 Edge；如果只在单区域服务、热键也少，可以先保留一个远程 Cache tier。每增加一层，都多一次复用机会，也多一份年龄和失效责任。能算清它减少了多少请求，并说明故障时由谁拒绝过载，才有依据保留这一层。

“How do I see the new price immediately after writing?” Return v2 in the write response; a strong read carries min_version=2, bypasses shared cache and asks App to read authority or verify a value meeting that floor. Public reads still promise bounded staleness. Renaming two write-through writes a transaction cannot synchronize all browsers; per-user read-after-write differs from global convergence.

“When should I add or remove a cache tier?” Staleness tolerance, reuse, network distance and origin budget decide together. Personalized traffic bypasses shared Edge; a single region with few hotspots may start with just remote Cache tier. Each layer adds reuse opportunities and age/invalidation responsibilities. Keep it only if you can quantify saved requests and name who rejects overload on failure.
