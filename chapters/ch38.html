先钉死对象、权威和可陈旧范围Pin down the object, authority and allowed staleness

这章沿一张公开目录卡走到底：GET /catalog/sku-1842 返回价格、状态、version 和图片 URL。图片字节使用内容哈希路径 /media/sku-1842.9c2.jpg，由对象存储经 CDN 返回；目录卡不把图片字节装进 App 回包。购物车、余额、扣库存的权威读写另走业务接口。公开展示价可以短暂旧，结算价仍由事务中的权威规则重新确定。

我会先画新鲜命中，再逐笔补 miss、失效和故障。默认 Cache-Aside：App 查可丢的副本，miss 自己查 Store，再 guarded fill。改价把行和失效 outbox 一起提交，Relay 持久重试；purge 加快收敛，hard age 封住漏送和旧回填。三种流量问题分别说：重复缺席用短负缓存，同 key 并发用合并，不同 key 的到期用 jitter；没有缓存服务时必须靠独立预算保护 Store。

下面所有 A 编号都是教学 assumption，不是厂商生产数据。60 秒目标指更新提交后发起的新查询，不能理解成所有打开的网页自动重绘。没有下一次请求就没有主动推送；断网的客户端也不在这份可见性承诺里。目标涵盖成功读的旧值年龄，依赖不可用时可以返回失败，不能用无限陈旧的 200 假装达标。

Follow one public catalog card: GET /catalog/sku-1842 returns price, status, version and an image URL. Image bytes use a content-hash path such as /media/sku-1842.9c2.jpg and travel from object storage through CDN; App does not embed them in the card reply. Cart, balance and inventory authority use business APIs. Display price may briefly lag; checkout recalculates authoritative price inside its transaction.

Start with a fresh hit, then add misses, invalidation and failures. Cache-Aside is the default: App queries an evictable copy, reads Store itself on miss and performs guarded fill. Price updates commit the row with an invalidation outbox; Relay retries durably. Purge accelerates convergence while hard age bounds missed delivery and stale fill. Repeated absence needs negative cache, concurrent callers for one key need collapse, and expiry across many keys needs jitter. Without a cache service, independent admission protects Store.

Every A-number below is a teaching assumption, not production data. The 60-second target covers new queries after an update commits, not automatic repainting of all open pages. No new request means no push, and disconnected clients are outside this visibility target. Successful reads must obey the age bound; dependency failure may return an error rather than an indefinitely stale 200.

读路径：谁管 miss，谁承受流量Read path: who owns misses and who receives load

正常路径：缓存不认识数据库Normal path: the cache does not know the database

Client 先问 Edge，选中一个仍新鲜的 HTTP 响应就直接回。Edge miss 才问 Shield；Shield miss 才叫 App。App 可以先看短 L1，再用 catalog:sku-1842 查 Cache tier。命中后 App 组 HTTP 响应，沿 Shield、Edge 回给客户端。未命中则 Cache tier 只回 miss，App 才 SELECT Store，收到行后申请 guarded SET。图中回填与回包分两条线，Cache tier 没有数据库连接。Nishtala 等人把这种模式称为 demand-filled look-aside。[4]

一次缓存 SET 失败不必把新读到的权威行一起丢掉。它只说明下次还可能 miss；当前行在年龄与权限约束内就能返回。反过来，Store 超时没有行，不能用 null 伪造一个 404。缓存也不承诺库存可扣，公开卡只是展示副本。按数据语义拆开后，读取可用性与交易正确性才有各自的失败行为。

Client first asks Edge; a selected fresh HTTP response replies immediately. Edge misses ask Shield; Shield misses call App. App may check short L1, then Cache tier using catalog:sku-1842. A hit lets App form an HTTP response and reply via Shield and Edge. On miss, Cache tier only returns miss; App SELECTs Store, receives rows and attempts guarded SET. Fill and reply have separate paths; Cache tier has no database connection. Nishtala et al. call this demand-filled look-aside.[4]

A failed SET need not discard a newly read authoritative row. It only means the next request may miss again; the current row can return within its age and permission constraints. A Store timeout provides no row and cannot become a null-backed 404. Cache does not certify inventory availability: the public card is a display copy. Data-specific semantics give read availability and transaction correctness separate failure behavior.

为什么这样选：合计命中率不能替每层算账Why: overall hits do not size every tier

A2 的百分比都按本层实际到达计：Edge 出站 40,000×(1−0.8)=8,000/s；Shield 出站 8,000×(1−0.5)=4,000/s；App 内部缓存的未命中再乘 0.5，Store 是 2,000/s。三个未命中比例相乘为 0.2×0.5×0.5=0.05，所以总命中 95%。不能把三个命中百分比直接相加，也不能说“源站只有 2,000 QPS”而让 App 按这个数买容量。

总命中率跌到 90%，40,000×0.10=4,000 已超过 3,000；最低需要 1−3,000/40,000=92.5% 才能仅靠命中守住读预算。真实预算还包含 304 验证、预热、重试，不能把余下 1,000 当成永远空闲。速率统计必须数每一次实际 Store attempt，而不是只数最后给用户成功的请求。

A2 uses conditional percentages: Edge forwards 40,000×(1−0.8)=8,000/s; Shield forwards 8,000×(1−0.5)=4,000/s; App-cache misses multiply by another 0.5, leaving 2,000/s for Store. Miss fractions multiply to 0.2×0.5×0.5=0.05, or 95% overall hits. Do not add hit percentages or size App from the 2,000 Store reads/s.

At 90% overall hits, 40,000×0.10=4,000 exceeds 3,000. Hits alone need at least 1−3,000/40,000=92.5% to fit the read budget. Actual demand includes 304 verification, warm-up and retries, so the spare 1,000 is not permanently free. Count every real Store attempt, not just successful user requests.

替代与代价：Shield、本地层都要有理由Alternatives and costs: justify Shield and L1

Shield 汇聚流量之后还要按 key 合并在途请求，才可能得到 A11 的 40→1。只是路由到同一个 POP，不自动等于一个回源；private 响应不能给其他等待者共享，多个 Shield 故障切换也会多出 leader。Fastly 原文明确区分这两件事，并说明不可缓存响应会使排队者分别回源。[8] POP 少或流量冷时先省 Shield，代价是冷对象在多个边缘各自填。

本地热集按 A8：80,000×2,000=160,000,000 B，再乘 1.5 是 240 MB/进程，30 份约 7.2 GB。这是堆预算估计，未证明命中率，扫描流量还可能把热集挤掉。LRU 简单但逐个新 id 的扫描会污染缓存；TinyLFU 讨论准入频率，W-TinyLFU 用窗口处理新访问再决定是否挤走主区条目。[9] 加频率准入的代价是额外元数据，不能靠算法名称保证这张目录的 95%。

Shield must also collapse in-flight requests by key to obtain A11’s ideal 40→1. Routing through one POP alone is insufficient; private responses cannot be shared with waiters and failover across Shields can create additional leaders. Fastly distinguishes these mechanisms and explains that uncacheable replies send waiting callers to origin individually.[8] With few POPs or cold objects, omit Shield and accept separate fills.

A8 gives 80,000×2,000=160,000,000 B, times 1.5 = 240 MB/process; 30 copies use about 7.2 GB. This is a heap estimate, not a hit-rate proof, and scans can evict the hot set. LRU is simple but unique-ID scans pollute it. TinyLFU studies frequency-based admission; W-TinyLFU uses a window for new accesses before deciding whether to replace main-cache entries.[9] Frequency metadata costs memory; an algorithm name does not prove 95% hits here.

HTTP：存储、复用、验证各是一道门HTTP: storage, reuse and validation are separate gates

HTTP cache key 至少包含方法和目标 URI，Vary 再区分被点名的请求头；例如语言、编码或特定的公开租户表示。[1] “utm 一律删掉”也不是正确性规则：只有参数确实不影响正文、鉴权、签名和跳转时，Edge 与 App 才能使用同一规范化 URI。用户态接口在查共享对象前就走 pass，不能等源响应 private 才发现已经把别人的缓存命中返回了。

不背“GET 一定缓存”。no-store 禁止保存本次请求/响应供其他请求复用；未限定 private 禁止共享缓存存储，但私有缓存可以留；no-cache 可以保存，却在复用前要验证。[1] no-store 只管 HTTP 缓存，不会自动关闭 App 的 L1、Redis 或已有旧响应；需要每读都新时，业务接口还要明确绕过内部缓存查权威。Authorization 有独立共享限制，Cookie 的存在本身也不是 RFC 统一的禁止存储开关，产品必须主动定义用户态边界。

目录卡基线使用 public, max-age=0, s-maxage=n, must-revalidate，n≤10 且受内部剩余 hard age 限制。浏览器需要验证，共享缓存使用 s-maxage，过期不返回旧成功。方法和状态码只是另一部分条件：302 不可启发式缓存，但显式新鲜期可允许它存储；404 可以启发式缓存，所以缺席必须给显式短期限。[2] 跳转缓存会减少源端点击记录，应从统计要求决定是否 pass。

ETag 标识这份表示，包含内容版本和语言等维度。Edge 发送 If-None-Match，Shield 继续传给 App；App 为这条验证路径读 primary 新快照，绕开旧 L1/L2。匹配才回 304，并更新缓存元数据；不匹配回 200 与新正文。304 少的是正文传输，不是免费免掉验证。若 App 拿旧缓存的 v1 比较 v1 后回 304，会把旧值不断证明成“新鲜”，所以它同样要消费 Store 预算。

可以陈旧的其他对象另选 SWR 配置。例如 max-age=10, stale-while-revalidate=5, stale-if-error=15，新鲜 10 秒，SWR 最多到年龄 15 秒，错误退路最多到 25 秒；两个窗口都从变 stale 开始，不相加成 30 秒。[3] 这是不同于本章目录基线的策略，不在 s-maxage / must-revalidate 的严格禁止旧值约束上随手叠扩展。要使用供应商的 stale 行为，先确认优先级与实现；未知扩展可能被忽略。

An HTTP cache key includes at least method and target URI, with Vary distinguishing selected request headers such as language, encoding or a public tenant representation.[1] Stripping all utm parameters is not inherently correct: Edge and App may share a normalized URI only when removed inputs do not affect body, authorization, signatures or redirects. Personalized endpoints take pass before shared lookup; discovering private at origin is too late after a wrong shared hit.

Do not assume every GET is cached. No-store forbids storing this request/response for reuse; unqualified private forbids shared storage but permits private storage; no-cache permits storage but requires validation before reuse.[1] No-store controls HTTP cache, not App L1, Redis or previously stored replies. A truly fresh-read endpoint must separately bypass internal caches. Authorization has independent shared-cache restrictions; Cookie alone is not a universal RFC storage prohibition, so the product must define personalization boundaries.

The card baseline is public, max-age=0, s-maxage=n, must-revalidate, where n≤10 and is capped by remaining internal hard age. Browsers validate; shared caches use s-maxage and do not return stale success after expiry. Method and status form another condition: 302 is not heuristically cacheable but explicit freshness can permit storage; 404 is heuristically cacheable, so absence needs an explicit short lifetime.[2] Cached redirects reduce origin click logging; analytics requirements decide whether to pass.

ETag identifies a representation including content revision and language dimensions. Edge sends If-None-Match through Shield to App; this validation path reads a fresh primary snapshot, bypassing old L1/L2. A match returns 304 and updates metadata; a mismatch returns 200 with the new body. A 304 saves body transfer, not validation work. Comparing a cached v1 with v1 and returning 304 would repeatedly recertify stale content, so validation also spends Store budget.

Other stale-tolerant objects can choose an SWR profile. For max-age=10, stale-while-revalidate=5, stale-if-error=15, freshness lasts 10 seconds, SWR up to age 15, and error fallback up to age 25. Both windows start at staleness; they do not add to 30 seconds.[3] This is a different policy from the card baseline, not an extension casually layered over strict s-maxage / must-revalidate restrictions. Verify provider precedence and behavior before using stale support; unknown extensions can be ignored.

更新失效：持久送达不等于全球瞬时Invalidation: durable delivery is not instant global completion

改价从 20 到 18，Store 在一个事务里写 row.version=2 与 Outbox(event_id, sku, version, targets)。确认表示权威行和待办都已持久，不表示所有副本已新。Relay 轮询或从可靠变更流读取待办，逐目标执行内部失效与 CDN purge，确认回执后推进目标状态。失败重试；不知道供应商是否接单，就凭同一请求身份查询或重复幂等 purge，而不是直接把 outbox 标完。

内部失效先抬高 floor、撤销旧 fill token 再 evict，随后送 CDN purge。重复或乱序事件用 version 最大值收敛，同 event_id 的回执可重复入账。缓存多副本时，不能只清其中一个；L1 没有广播也只能活到自己的短期限和全局 hard age。CDN 回“已接受”只是控制面接单，POP A 处理后 POP B 仍可能回 v1。这里承诺有界旧值，不声称写确认后读都线性一致。

TTL 的上界不能只盯 Edge。若 L2 33 秒、L1 5 秒、Edge 再发 30 秒，各次拷贝都从零计时，旧内容可能被续到 33+5+30=68 秒，迟到回填还会更长。新方案记录 observed_at，从一次新 primary 查询开始前取时刻，hard_expires=observed_at+20s。L1 拷贝同一截止时间，最长 5 秒且不越界；HTTP 的 n 取 max(0,min(10,floor(hard_expires-now-2)))。余量不足就重读或失败。

Shield 向 Edge 转发同一 HTTP 响应时保留 Date 并累计 Age；内部缓存被 App 包成新响应时才使用剩余寿命限额，不能借新 Date 忘掉内容已经旧了多久。[1] 时钟每节点误差≤1 秒，跨节点保守留 2 秒；读取/填充与最后发送各≤1 秒。保守预算 20+2+1+1=24 秒，小于 60，且不把 L1 和 CDN 再加一轮。这个推导依赖 A12：不能读无限旧副本、不能让迟到响应长期排队、不能自动给超龄值回 304。

图片已写入并验证完成后，目录 v2 指向新内容哈希 URL，旧 URL 从不原地覆盖。immutable 表示新鲜期内资源不变，不表示永久保留，也不把可变目录卡变成不可变。[7] 换 URL 只解决字节身份，旧目录仍可能引用旧图直到自身收敛。源文件下架或法律删除需要独立访问与清理政策，不能因为旧 URL 长缓存就宣称撤销立即生效。

Changing price from 20 to 18 commits row.version=2 with Outbox(event_id, sku, version, targets) in one Store transaction. Acknowledgement certifies durable authority and work, not fresh replicas everywhere. Relay polls or reads a reliable change stream, processes internal invalidation and CDN purge per target, then advances status after receipt confirmation. Retry failures; query an unknown provider outcome with the same request identity or repeat idempotent purge instead of completing the outbox prematurely.

Internal invalidation raises the floor, revokes old fill tokens and evicts before CDN purge. Version maxima absorb duplicate or reordered events, and event_id receipts tolerate repetition. Invalidate every application-cache replica; L1 without broadcast still obeys its short lifetime and global hard age. CDN acceptance acknowledges control-plane receipt while POP B may still return v1 after POP A applies it. This promises bounded staleness, not linearizable reads after write acknowledgement.

An Edge TTL alone cannot prove the bound. If L2 lasts 33 seconds, L1 restarts five and Edge restarts 30, stale content can survive 33+5+30=68 seconds, even longer with late fill. The new record carries observed_at captured before a fresh primary query and hard_expires=observed_at+20s. L1 copies the same deadline and lasts at most five seconds. HTTP n is max(0,min(10,floor(hard_expires-now-2))). Insufficient life requires reread or failure.

Forwarding the same HTTP response from Shield to Edge preserves Date and accumulates Age; wrapping an internal cache record into a new HTTP response requires the remaining-life cap rather than forgetting content age with a new Date.[1] With each clock within one second, allow two across nodes; read/fill and final send each take at most one. A conservative 20+2+1+1=24-second budget fits 60 without another L1 or CDN extension. A12 is essential: no arbitrarily old replicas, long-delayed replies or 304 renewal of expired evidence.

After image bytes are durably published and verified, card v2 points to a new content-hash URL; never overwrite the old path. Immutable means unchanged during freshness, not eternal retention or an immutable mutable card.[7] New URLs solve byte identity; an old card can still reference an old image until it converges. Removal needs separate access and cleanup policies; a long-cached old URL does not provide immediate revocation.

击穿与旧值回填：合并和 fencing 分开说Stampede and stale fills: separate collapse from fencing

singleflight 按 key 维护一个在途调用：leader 执行，进程内等待者共享结果，命中路径不必抢这把锁。[5] 它只在一个进程内收成一次；30 个 App 仍可能有 30 个 leader。Shield 收 HTTP 请求，应用层收对象读取，key 都必须覆盖真实表示。等待者有自己的截止时间，超时离队不代表取消别人的共享工作；leader 总截止时间到则终止并返回失败，不能让一群请求无限悬挂。

跨进程可以用按 key 的填充 lease。Facebook 的论文同时处理 herd 与 stale set：miss 给 64 位 token，删除会使 token 作废；其默认发 token 限速是每 key 每 10 秒最多一次，报告的一周热点观察中数据库峰值从 17K/s 降到 1.3K/s。[4] 这些是该系统的参数与测量，不是本章 TTL 和压测结果。我们只借“必须验证填充资格”的机制，不把论文比例乘在 40,000 上。

按图走竞态：reader 拿 e7 并读 v1；writer 提交 v2，然后快路径尝试失效，持久 Relay 仍负责补送；Cache tier 原子把 floor 抬到 2、撤销 e7、删值。reader 恢复后 SET(v1,e7) 被拒。新的 e8 要重新查 Store。guarded SET 必须在缓存端原子检查 token、epoch、有效期限、version≥floor，再写值；先 GET 锁再普通 SET，中间仍能被失效穿过。

普通 Redis 短锁只减少重复工作，不自动防 stale SET。SET NX 带过期与唯一 owner，解锁要比较 owner 后删除，不能删掉后来接任者的锁；官方文档明确展示这种所有权校验。[6] 旧持有者暂停到锁过期，恢复后仍可能运行，所以真正承接副作用的缓存写入口必须拒绝旧 token。缓存重启换 epoch，验证元数据不能比允许延迟的填充更早无痕淘汰；若丢失资格就拒绝 SET，再申请新 token。

拒绝旧 SET 不会撤回已经发给用户的 v1，也不会让尚未收到失效的 Edge 立即变新；这部分仍由 hard age 和 HTTP 验证收口。Write-through 若只是同步写库再写缓存，旧 reader 照样能覆盖，半边失败也仍在。强读可绕缓存直查权威；Through 要加版本原子替换和失败修复才有相应保证。Write-back 先承认后刷盘，故障可丢未刷更新，只给允许丢失的粗计数讨论，不当价格和账本默认。

Singleflight tracks one in-flight call per key: a leader executes and in-process waiters share the result; cache hits do not need the lock.[5] It only guarantees one within a process, so 30 Apps may still produce 30 leaders. Shield collapses HTTP requests and App collapses object reads; both keys must cover the actual representation. Waiters have deadlines; leaving a shared call need not cancel others. The leader’s overall deadline terminates stuck work rather than hanging every waiter indefinitely.

A per-key fill lease can collapse across processes. Facebook’s paper handles herd and stale set together: a miss gets a 64-bit token that deletion revokes. Their default limits token issuance to one per key per ten seconds; a week-long observation reports database peaks falling from 17K/s to 1.3K/s.[4] Those are that system’s parameters and measurements, not our TTL or benchmark. Borrow fill validation, not a multiplier applied to our 40,000/s.

Walk the race: reader gets e7 and reads v1; writer commits v2 and attempts fast-path invalidation while durable Relay remains responsible for repair. Cache tier atomically raises floor to 2, revokes e7 and evicts. A resumed SET(v1,e7) is rejected. A new e8 must reread Store. Guarded SET atomically checks token, epoch, validity and version≥floor before writing; GETting a lock and later doing ordinary SET still races with invalidation.

An ordinary Redis short lock reduces duplicate work but does not itself stop stale SET. Use SET NX with expiry and a unique owner; release compares owner before deletion so it cannot delete a successor’s lock, as the official documentation demonstrates.[6] A paused old holder can resume after expiry, so the cache write boundary must reject old tokens. Restart changes epoch; validation metadata cannot silently disappear while delayed fills remain eligible. Lost eligibility rejects SET and requires a new token.

Rejecting stale SET cannot retract v1 already sent or instantly freshen an uninformed Edge; hard age and HTTP validation still bound that case. Write-through as synchronous DB-then-cache writes can still be overwritten by old readers and can partially fail. Strong reads bypass cache; Through needs versioned atomic replacement and repair for corresponding guarantees. Write-back acknowledges before persistence and can lose unflushed updates; consider it for lossy coarse counters, not default price or ledger authority.

穿透：重复缺席与随机 id 是两种负载Missing keys: repeated absence differs from random IDs

App miss 后向 Store 查询，明确不存在才写 absent，类型与真实下架状态分开。负记录 hard age 为 5 秒，CDN 的 404 若允许缓存也截到这份剩余寿命，复制不能把 5 秒再加 5 秒。响应沿 App → Shield → Edge 或图里省略 HTTP 层的 App → Client 返回。图中省略的是整个调用层，不是把已画出的回程跳过去；这一组专讲内部缺席证明。

A9 是重复查询同一批 100 个 key，合计 2,000/s。没有负缓存每次都回源；忽略查询耗时、条目淘汰并合并同 key 并发时，每 key 每 5 秒检查一次，100/5=20 次权威查询/s。第一轮仍可能同时有 100 次，且新建后删除会额外触发读取；20 是稳态期望，不是任何一秒的峰值上界。预算不能因此被删掉。

新建商品同样提交 row 和失效 outbox，既删除旧负记录也撤销旧缺席填充令牌。否则“旧查询得出没有行 → 新建提交并 DEL → 旧查询又 SET absent”会让新商品继续 404。不能永久缓存不存在，也不能把 Store 超时、连接失败或 permit 被拒绝写成 absent。404 的意义是缺席已被证明，503 是现在证明不了；客户端与中间缓存的动作不同。

攻击者每秒换 2,000 个全新 id，负缓存零次复用，Store 仍接 2,000/s。可以在 key 格式、租户权限和入口速率处拒绝；Bloom 类成员过滤器只对它已经同步覆盖的集合没有假阴性。新行尚未加入旧过滤器时，“不在”仍会误拒，所以创建先登记或准备新增 overlay；同步状态未知就回源受预算保护，不能把过期过滤器当权威。假阳性只增加读取，没有资格返回真实对象。

App queries Store after miss and stores typed absent only for confirmed missing rows, distinct from a real withdrawn status. A negative record has five seconds of hard life; a cacheable CDN 404 is capped to its remaining life, not another five seconds. Responses return via App → Shield → Edge, or directly App → Client in this diagram with HTTP layers wholly omitted. The group isolates internal absence proof rather than skipping drawn callers.

A9 repeats the same 100 keys at 2,000/s. Without negative cache each query reaches origin. Ignoring query time and eviction, and collapsing same-key concurrency, one check per key every five seconds gives 100/5=20 authoritative checks/s. The first wave can still contain 100 checks and creation invalidation adds more. Twenty is a steady-state expectation, not a per-second bound, so keep admission.

Creation also commits the row with invalidation outbox, evicting negatives and revoking old absence-fill tokens. Otherwise an old missing-row query can SET absent after creation and DEL, keeping a new item invisible. Never cache absence forever or manufacture it from Store timeout, connection failure or permit rejection. A 404 certifies absence; a 503 means it cannot currently be proved. Clients and intermediaries handle them differently.

With 2,000 brand-new IDs each second, negatives have no reuse and Store still sees 2,000/s. Reject malformed keys, unauthorized tenants and excess ingress. Bloom-style filters avoid false negatives only for the set they actually cover. A newly created row missing from an old filter can still be denied, so register creation or maintain a recent-add overlay. Unknown synchronization falls back under budget rather than treating a stale filter as authority. False positives only add reads; they do not authorize objects.

雪崩：分散软刷新，守住硬年龄Expiry waves: spread soft refresh while keeping hard age

预热把 1,000 张卡同一秒写入，同软期限会使它们一起刷新。没有按 key 合并，每张 20 个并发就是 1,000×20=20,000 次读；有合并也还有 1,000 个不同 key，不能靠一把锁变成一行。A10 的例子把软刷新期限定为 16 秒，加减 10% 得到 14.4–17.6 秒，hard age 仍固定 20 秒，抖动不能往外延长产品的新鲜度。

均匀取样且请求到点即来，刷新窗口 17.6−14.4=3.2 秒，合并后约 1,000/3.2=312.5/s，口述 313。无合并约 20,000/3.2=6,250/s，超过 3,000。所以合并减少每个 key 的人数，jitter 分散 key 的时刻，两者改变不同乘数。现实取样仍会聚集，发布也会造成短时集中读取；“平均 313”不能证明尾部不超过数据库预算。

软期限到后可在 hard age 内返回已有值，并由一个 leader 后台刷新；到 hard age 后必须取得新证明或失败。后台任务和等待者都受总 permit 与截止时间限制，leader 不成功不能给旧值续期。分批预热是替代：把写入时刻错开，也降低到期对齐，代价是前几分钟命中较低。只刷新真实热键，避免定时扫完整个冷 key 空间把缓存变成主动制造读量的服务。

缓存集群整体消失没有 TTL 时间表可分散，jitter 对它无能为力。给所有 key 永不过期则把失效管道的每一次漏送变成永久旧值，同样不成立。扩分片也不自动解决热 key：一个键仍由一个分片服务。真正的热点可以放短 L1 或复制同一 value 到明确的多个读副本，删除、floor 与 token 撤销要覆盖全部副本，不能每次随机造一个新 key。

Prewarming 1,000 cards in one second with a common soft lifetime synchronizes refresh. Without key collapse, 20 callers each produce 1,000×20=20,000 reads; collapse still leaves 1,000 distinct keys. A10 jitters a 16-second soft lifetime by ±10% to 14.4–17.6 seconds while hard age remains 20. Jitter must not extend the product’s freshness limit.

Under uniform sampling and immediate requests, the window is 17.6−14.4=3.2 seconds. Collapse gives about 1,000/3.2=312.5/s, spoken as 313. Without collapse, 20,000/3.2=6,250/s exceeds 3,000. Collapse reduces callers per key while jitter spreads key timings. Random samples can still cluster and releases can concentrate reads; an average of 313 cannot prove the tail stays within the database budget.

After soft expiry, return existing data within hard age while one leader refreshes. At hard age, obtain new proof or fail. Background work and waiters obey total permits and deadlines; an unsuccessful leader cannot renew stale data. Staggered warm-up is an alternative that spreads write times and expiry, at the cost of lower initial hits. Refresh actual hot keys instead of scanning the entire cold keyspace and manufacturing origin load.

Total cache loss has no TTL schedule for jitter to spread. Making all keys immortal turns every lost invalidation into permanent staleness. More shards do not automatically solve a hot key either: one key still belongs to one shard. Use short L1 or explicit value replicas for genuine hotspots; evictions, floors and token revocation cover every replica. Randomly manufacturing a new key per request is not replication.

热键与整层宕机：把多余请求停在库前Hot keys and total loss: stop excess requests before Store

热点练习换成 A8 的另一个流量形状：App 收到同一个 key 的 8,000/s，不再沿用 A2 的总 App 4,000/s。30 进程均分约 8,000/30=267/s；本地副本稳定存活 5 秒、流量均匀且 L2 剩余寿命足够时，L2 约 30/5=6 次 get/s。冷启动、失效和 hard age 边界会再增加读取。关闭 L1 而显式复制到 4 个读副本，均匀选副本约 2,000/s/副本，代价是四处都要维护失效。

只丢 Cache tier、Edge 与 Shield 仍保持 A2 命中，App 到达 4,000/s；假设 L1 也 miss，3,000/s 能放行，至少 1,000/s 要结束在库前。若 HTTP 层也冷、失效或 pass，且请求不合并，最坏重新到 40,000/s，差额 37,000/s。两个事故不能混在同一个“缓存挂了”的数字里。只有各层真实计数才能告诉你现在是哪条路径，自动重试还会把 Store attempt 放大。

Origin budget 在图中是逻辑读取包装层：App 请求它，获批后它调用 Store，结果先回包装层再回 App，不是绕过 App 回用户。全局速率总额 3,000/s，加 100 在途上限保护连接和队列；App 各自发 3,000 会把总额乘上实例数。预算实现必须独立于故障缓存，失联时可用已分配的有界本地配额，配额耗尽就关闭旁路。读预算只是在选定负载与尾延迟下的设计假设，仍要真实压测。

在途名额按真实 Store 调用计，客户端超时不代表数据库里的查询已经结束。只有收到执行结束或取消确认才归还名额；结局未知继续占位并探测，重试要再消费一次速率配额。否则上一批 SQL 还在跑，下一批已经拿到被提前归还的名额，100 的并发上限只是客户端的错觉。

拒绝按原因回：容量不可用用 503 和退避；明确入口配额限流可用 429。错误响应基线 no-store，不把瞬间拒绝扩散成缓存的缺席。短 L1 只能在同一 hard age 内续服务，不能借“降级”把 60 秒变成无限长；无法验证的新价不凭旧值承诺成功。缓存超时在 App 被熔断吸收，放行的绿回程与拒绝的红回程都经 Shield、Edge 回到原调用者。

恢复先探测小流量，再按同一个 permit 逐步 guarded fill，缓存实例使用新 epoch，迟到旧请求不准写。不要同时把所有 App 的 L1 清空、所有 Edge purge 和全部 key 预热。观察每层条件命中率、填充拒绝、permit 消耗、旧值年龄与最老 outbox，而不只看 Redis 是否在线。指标若显示队列或 Store 尾延迟升高，就减慢预热；新鲜度预算不够时宁愿返回可解释失败，也不续旧证明。

The separate A8 exercise sends App 8,000/s for one key, replacing A2’s 4,000/s total App arrivals. Thirty processes receive about 8,000/30=267/s each. With stable five-second local retention, uniform traffic and sufficient remaining L2 life, L2 sees about 30/5=6 gets/s. Cold starts, invalidations and hard-age boundaries add reads. With L1 disabled and four explicit read replicas, uniform selection gives about 2,000/s per replica, at the cost of four-way invalidation.

If only Cache tier fails while Edge and Shield retain A2 hits, App receives 4,000/s. With L1 misses too, admit 3,000/s and stop at least 1,000/s before Store. If HTTP layers are also cold, invalidated or passed and requests do not collapse, the worst case reaches 40,000/s, leaving 37,000/s to shed. These incidents require distinct numbers. Actual tier counters identify the path, and retries can amplify Store attempts.

Origin budget is a logical read wrapper: App calls it, an admitted call reaches Store, and the result returns through the wrapper and App. The 3,000/s global rate plus 100 in-flight cap protect connections and queues. Per-App 3,000 limits would multiply by instance count. Admission must survive cache failure; an unavailable coordinator can leave bounded preallocated local permits, then fail closed when exhausted. This budget is an assumption under a selected workload and latency target, still requiring load tests.

In-flight permits track actual Store calls: client timeout does not prove the database query ended. Release only after completion or confirmed cancellation; an unknown outcome retains its slot and is probed. A retry spends another rate permit. Otherwise old SQL continues while new work uses prematurely returned permits, making the 100-call cap merely a client-side illusion.

Return failures by cause: capacity unavailability uses 503 and backoff, while explicit ingress quota throttling may use 429. Error replies default to no-store so transient rejection cannot become cached absence. Short L1 remains within the same hard age; degradation cannot stretch 60 seconds indefinitely or certify a new price from expired data. App’s circuit absorbs cache timeout, and both admitted green replies and rejected red replies travel through Shield and Edge to the caller.

Recover with small probes and paced guarded fill under the same permits. A new cache epoch rejects late old requests. Do not simultaneously clear all App L1, purge every Edge and prewarm every key. Observe conditional hit rates, fill rejections, permit use, content age and oldest outbox work, beyond whether Redis is online. Slow warm-up when queues or Store tail latency rise; insufficient freshness budget returns an explicit failure rather than renewing old evidence.

追问与翻车点：答案要能落到一条线Follow-ups and failure modes: answers must name a path

“写完马上刷新，怎样保证看到新价？”写响应直接带回 v2；下一次强读携带 min_version=2，绕共享缓存，并由 App 查权威或验证满足下界的值。公开目录读仍只承诺有界旧值。不能把 write-through 两步双写改名成事务，就宣称所有浏览器同时新；个人读后写与全球副本收敛是不同要求。

“减层或加层的标准是什么？”允许陈旧、对象复用、网络距离和回源预算共同决定。用户态先不放共享 Edge；只在单区域且热键很少时可以先留一个远程 Cache tier。多一层只是多一处复用机会，也多一份年龄与失效责任。图上能说出减少了多少请求，以及故障时由谁拒绝，才有理由把这一层留下。

“How do I see the new price immediately after writing?” Return v2 in the write response; a strong read carries min_version=2, bypasses shared cache and asks App to read authority or verify a value meeting that floor. Public reads still promise bounded staleness. Renaming two write-through writes a transaction cannot synchronize all browsers; per-user read-after-write differs from global convergence.

“When should I add or remove a cache tier?” Staleness tolerance, reuse, network distance and origin budget decide together. Personalized traffic bypasses shared Edge; a single region with few hotspots may start with just remote Cache tier. Each layer adds reuse opportunities and age/invalidation responsibilities. Keep it only if you can quantify saved requests and name who rejects overload on failure.
