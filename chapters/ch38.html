This is a dictionary, not another 4-step design. Where the source of truth lives was the previous chapter. This one answers a narrower question: don't punch that authority on every hot read. The redirect in Ch09 · URL shortener and the timeline in Ch11 · news feed both use that one line. Cite it inside the design problem, then go back to the problem.

Reads or writes? Read-heavy, write-light defaults to Cache-Aside: the app checks the cache, and on a miss it reads the DB and fills. The DB is the source of truth. 一层层加上去Add one layer at a time

中文

白板上先只有 App 和 DB。然后按这个顺序加：进程内，远程 Redis，最后才是 CDN。层数不是分数。五层一起画出来、却说不清谁是权威，是 over-engineering。

进程内是微秒级，没有网络。它只服务本进程。一发布，每台都是冷的。失效也难：每台各持一份，要么逐台删，要么等一个很短的 TTL。它适合挡 hot key 的第一拳，只放极热、可以 stale 的只读。本地 TTL 必须短，否则每台各执一份旧值。

Redis 是跨实例的那一份热集。一处 DEL，大家一起 miss。代价是同一次网络 RTT，容量可以分片。常见组合是 L1 本地加 L2 Redis，不是套娃。少一次 RTT，换来的是失效变难。这就是 trade-off。

要数据结构、TTL、持久化、集群，开口用 Redis，或协议兼容的远程缓存。只要纯 KV 的 lookaside，Memcached 仍是 Facebook 那篇论文里的砖。一句选型就够，不要开骂战，也不要把许可证当系统设计答案。淘汰：远程缓存 LRU 够开口。进程内常见 W-TinyLFU，准入看频率，用来抗扫描污染。Belady 最优不是实现。

CDN 最后加，因为它缓存的是 HTTP 响应，不是又一个 Redis。公开的字节走边缘。对象和渲染过的 JSON 仍走应用缓存。

English

The board starts as App and DB. Then you add, in this order: in-process, remote Redis, and only then a CDN. Layer count is not the score. Five layers drawn at once, with nobody able to say who is authoritative, is over-engineering.

In-process is microseconds, no network. It serves this process only. The moment you ship, every box is cold. Invalidation is hard: each box holds its own copy, so you delete on every box or you wait out a very short TTL. It is the first punch against a hot key. Keep it for extra-hot, stale-OK, read-only data. The local TTL has to be short, or every box keeps its own old value.

Redis is the hot set shared across instances. One DEL, and everyone misses. You pay a network RTT, and you can shard the capacity. The usual pair is L1 local plus L2 Redis, not a nesting doll. One less RTT, and invalidation gets harder. That is the trade-off.

If they want data structures, TTL, persistence, and a cluster, say Redis, or a protocol-compatible remote cache. If you only need a pure KV lookaside, Memcached is still the brick in the Facebook paper. One selection line is enough. Don't start a flame war, and don't treat a license as the system-design answer. Eviction: LRU is enough to open on a remote cache. In-process, W-TinyLFU is the common admission policy: frequency, so a scan doesn't flush the hot set. Belady-optimal is not an implementation.

CDN is the last box, because it caches HTTP responses, not another Redis. Public bytes go to the edge. Objects and rendered JSON stay in the app cache.

扩展链上先缓存、再 CDN，不要第一步就画全球边缘。那句话在 Ch02 · 从零到百万。On the growth path, cache first, then CDN. Don't draw a global edge on step one. That line is Ch02 · zero to a million.

CDN 在读路径上干什么What the CDN does on the read path

中文

CDN 把可缓存的 HTTP 响应放到离用户近的 edge，降低 RTT，挡住源站。这一章是 HTTP 边缘缓存。转码、切片、对象存储里面怎么存字节，不在这里设计。浏览器拿到的 URL 往往先打到 edge。

Client 问最近的 Edge。hit 就返回。miss 不要让每个 PoP 各自打 Origin。中间加 origin shield，把全球 miss 折叠成少数次回源。这和击穿的 single-flight 是同一件事，发生在 HTTP 边缘。

cache key 决定什么算同一份对象：路径、选定的 query、选定的 header（Vary）。语言、编码、登录态该进 key 却漏了，会串用户。广告 click id 塞进 key，命中率会碎掉。utm_ 不要进 key。个性化 API 默认 private，不进共享缓存。

stale-while-revalidate 在 RFC 5861。max-age 管新鲜；过期后一段窗口可以先吐旧的，后台再回源。兄弟指令 stale-if-error：源 5xx 或超时，继续用旧的换可用。两者都是故意的 stale，要对齐业务能接受的窗口。面试默认 pull：第一次 miss 回源，再填边缘。预推是视频题，留在视频那一章。

短链的 302 不要在 CDN 里长期缓存。效果接近 301，点击不再回到你，Analytics 没了。图、JS、可公开的 GET 才上边缘。有 CDN 所以不需要 Redis，这句话不成立。

应用缓存CDN edge
缓存什么对象、计数、渲染过的 JSONHTTP 响应、静态字节、公开 GET
谁失效应用 DEL / TTLTTL、purge、改 cache key 版本
个性化per-user key 可以带 cookie 的私人页不要共享

English

A CDN puts a cacheable HTTP response on an edge close to the user, cuts RTT, and shields origin. This chapter is HTTP edge cache. Transcoding, chunking, and how object storage keeps the bytes are not designed here. The URL the browser gets often hits the edge first.

The client asks the nearest edge. A hit returns. On a miss, don't let every PoP punch origin on its own. Put an origin shield in the middle and collapse worldwide misses into a few origin fetches. Same idea as single-flight for a stampede, happening at the HTTP edge.

The cache key decides what counts as the same object: path, selected query, selected headers (Vary). Leave out language, encoding, or login state, and you leak across users. Stuff an ad click id into the key, and the hit rate turns to dust. Keep utm_ out of the key. A personalized API defaults to private: no shared cache.

stale-while-revalidate is RFC 5861. max-age owns freshness. After expiry, for a window, you can serve the old response while you revalidate in the background. The sibling, stale-if-error, keeps serving stale when origin returns 5xx or times out. Both are intentional stale. They have to fit the window the product can accept. The interview default is pull: the first miss fetches origin, then fills the edge. Push is a video problem. Leave it in the video chapter.

Don't long-cache a short-URL 302 on the CDN. That behaves like a 301: later clicks never come back, and analytics disappears. Images, JS, and public GETs go to the edge. "We have a CDN, so we don't need Redis" does not hold.

失效和一致性的 trade-offInvalidation and the consistency trade-off

中文

2026 上场，会背六种策略不如会选默认。读多写少的 API，开口就是 Cache-Aside，也叫 lazy load、lookaside。缓存是加速器。它挂了，读穿到 DB，变慢，仍然正确。这是降级。正确性不押在缓存上。只缓存真正被请求过的 key，冷数据不占内存。

写路径删，不改。并发下常见的 bug 是：读到旧值，写库已经完成，慢请求再把旧值 SET 回去。删了 key，下一拍 miss，用 DB 的新行回填。漏删用 TTL 封顶。你不保证线性一致。短链和 Feed 这够用。钱和库存不放进缓存当账本。

Read-Through 和 Aside 差在谁去填：缓存库自己回源，还是应用自己打 DB。面试仍说 Aside，因为常见的 Redis / Memcached 用法就是应用管。Write-Around 点一句：写一次几乎不读的数据别污染热集。Refresh-ahead 是冷启动，不是第三种写入策略。

Write-Through：缓存和 DB 同步都写完才返回。下一读是新的。写变成两跳，写更慢。写了却从不读的 key 会污染缓存。双写仍可能一半成功，不要说成分布式事务。

Write-Back：先写缓存，异步刷 DB。同一个计数可以合并成一次刷盘，吞吐好。进程挂了、节点没把未 flush 的写留下，数就丢了。播放次数、点赞粗计数、监控指标可以。余额、订单、库存是 red flag。

这题读多写少，我用 Cache-Aside，加 TTL，写后删 key。要写完立刻读到新、而且写不多，再考虑 Through。Back 只给可丢的计数。三种不是满分套餐。

English

In a 2026 interview, picking a default beats reciting six policies. A read-heavy, write-light API opens on Cache-Aside, also called lazy load or lookaside. The cache is an accelerator. If it dies, reads fall through to the DB. Slower, still correct. That is degradation. Correctness is not riding on the cache. You only cache keys that were actually requested. Cold data does not sit in memory.

On the write path, delete. Don't update. The common bug under concurrency: a read already holds the old value, the DB write has committed, and a slow request SETs the old value back. Delete the key. The next beat misses and fills from the new row. TTL caps a delete you missed. You do not promise linearizability. That is enough for a short URL and a feed. Money and inventory do not live in the cache as a ledger.

Read-Through versus Aside is who fills: the cache library goes to origin, or the app hits the DB. In the interview you still say Aside, because the usual Redis or Memcached setup is the app owning it. Write-Around gets one line: data you write once and almost never read should not pollute the hot set. Refresh-ahead is a cold start, not a third write policy.

Write-Through: you return only after the cache and the DB are both written. The next read is fresh. The write is two hops, so it is slower. Keys that are written and never read pollute the cache. A dual-write can still succeed on one side only. Don't sell that as a distributed transaction.

Write-Back: write the cache first, flush the DB async. The same counter can coalesce into one flush, and throughput feels good. If the process dies and the node never kept the unflushed write, the count is gone. Play counts, coarse like counts, and metrics can live here. Balances, orders, and stock are a red flag.

穿透：key 根本不存在Penetration: the key never existed

中文

三种失败先拆开。穿透是查一个缓存和 DB 都没有的 key：随机 id、已经删掉的资源、拼错的短码。缓存永远 miss，每次都打到 DB，无效查询把库打满。

默认是 negative cache：空值也缓存，TTL 比正常条目短，避免「不存在」永久占着内存。流量再大，加 bloom。bloom 说不在，就一定不在，直接挡掉。说可能在，才查库，假阳性才会回源。bloom 要随写入更新，否则刚插入的合法 key 会被误杀。这是 trade-off，不是魔法。锁不是穿透的答案。永不过期也不是。

English

Split the three failures before you answer. Penetration is a lookup of a key that is in neither the cache nor the DB: a random id, a deleted resource, a mistyped short code. The cache always misses, every request hits the DB, and useless queries flood it.

The default is a negative cache: cache the empty value too, with a TTL shorter than a real entry, so "does not exist" does not occupy memory forever. If the traffic is large, add a bloom filter. "Not in" means definitely not in, and you block it. "Maybe" is when you query the DB. Only a false positive hits origin. The bloom filter has to be updated on writes, or a key you just inserted gets rejected. That is the trade-off. It is not magic. A lock is not the answer to penetration. Never-expire is not either.

拼错的短码就是这个形状，业务仍在 Ch09 · 短链。这里只回收这一句。A mistyped short code is this shape. The product still lives in Ch09 · URL shortener. Here you only recycle the one line.

击穿：一个热点过期Stampede: one hot key expires

中文

击穿和穿透相反。key 存在，而且极热。TTL 一到，N 个请求同时 miss，同时打 DB，再同时 SET。英文里的 stampede、thundering herd，多半说的就是这个。

默认 single-flight。同一进程里合并成一个回源。跨进程用短锁：SET 带 NX 和过期写在同一条命令里，不要拆成 SETNX 再 EXPIRE。没抢到锁的等一小会儿再 GET。业务允许 stale，就可以先读旧值。

逻辑过期是升级版：key 本身不过期，value 里带 expireAt，一个线程异步刷新。和 Facebook 论文里的 serve stale 是一个意思。Nishtala 等人 NSDI 2013，Scaling Memcache at Facebook：memcache 是 demand-filled lookaside，它不知道 DB 的存在，应用 miss 之后自己填；写库之后 delete。leased get 在 miss 时发一个 lease token，set 要带上。中途如果已经 delete，token 作废，慢请求就不能把旧行写回。同一个 key 的 token 限速发放，其余客户端稍后重试。白板说到 single-flight，可以点这一句。

English

A stampede is the opposite of penetration. The key exists, and it is extremely hot. The moment the TTL hits, N requests miss together, hit the DB together, and SET together. In English, stampede and thundering herd mostly mean this.

The default is single-flight. Inside one process, coalesce to a single origin fetch. Across processes, a short lock: SET with NX and expiry in the same command. Don't split it into SETNX and then EXPIRE. Whoever didn't get the lock waits briefly and GETs again. If the product allows stale, they can read the old value.

Logical expiry is the upgrade: the key itself has no TTL, the value carries expireAt, and one thread refreshes async. Same idea as serve stale in the Facebook paper. Nishtala et al., NSDI 2013, Scaling Memcache at Facebook: memcache is a demand-filled lookaside. It does not know the DB exists. The app fills after a miss, and deletes after it writes the DB. A leased get issues a lease token on miss, and set has to carry it. If a delete happened in between, the token is void, so a slow request cannot write the old row back. Tokens for the same key are rate-limited. Other clients retry later. When the board says single-flight, you can name that line.

爆款短码在 Ch09 · 短链。Feed 大 V 的时间线在 Ch11 · 新闻 Feed。题不要在这里重做。A viral short code is Ch09 · URL shortener. A celebrity timeline is Ch11 · news feed. Don't redo those problems here.

雪崩：一批一起过期Avalanche: a batch expires together

中文

雪崩是另一张图。一批 key 用了同一个 TTL，整点一起死；或者缓存集群在 failover 期间整层消失。回源从 1 变成 N，或者缓存层直接没了。它不是「那一个热点过期」。

同时过期的默认是 TTL jitter：TTL = base + random(0, 0.1×base) 这种形状就够，不要背函数。缓存层本身要有副本。集群真的没了，jitter 帮不上：读会穿到 DB，DB 吃不住就要限流和降级。只说「Redis 高可用」、却解释不了同时过期，是 red flag。

English

Avalanche is a different picture. A batch of keys was written with the same TTL and they all die on the hour, or the cache cluster disappears during failover. Origin fan-out goes from 1 to N, or the cache layer is simply gone. It is not "that one hot key expired".

The default for expire-together is TTL jitter: a shape like TTL = base + random(0, 0.1×base) is enough. Don't memorize a function. The cache layer itself needs replicas. If the cluster is actually gone, jitter does nothing: reads fall through, and if the DB cannot take them you rate-limit and degrade. "Redis HA" with no account of expire-together is a red flag.

限流在 Ch04 · 限流器。降级和弹性在 Ch42 · 消息、弹性、容器心智。Rate limit is Ch04 · rate limiter. Degrade and resilience are Ch42 · messaging, resilience, containers.

热点：一个分片被打满Hot key: one shard is saturated

中文

热点是第三张图，不要和击穿、雪崩画在一起。key 一直很热，即使没过期，单分片的 CPU 或网卡也是 bottleneck。single-flight 解决的是过期那一瞬间的回源。它不解决「这个分片一直被打满」。

默认两拳。第一拳是进程内 L1，把极热的只读挡在本机。第二拳是 replica：把同一个 key 复制到多个缓存节点，读打散。短链爆款、Feed 大 V 的 outbox 都是这个形状。全局把所有 key 设成永不过期，是热点的特例被误用成策略。那不是答案。

穿透是不存在的 key，空值短 TTL，流量大再加 bloom。击穿是热点过期，single-flight 只让一个回源。雪崩是同时过期或缓存挂了，TTL jitter 打散过期，挂了要限流。特别热再 replica，再加本地 L1。

English

A hot key is a third picture. Don't draw it on the stampede slide or the avalanche slide. The key stays hot even when it has not expired, and one shard's CPU or NIC is the bottleneck. single-flight covers the instant of expiry. It does not cover "this shard is saturated the whole time".

Two punches. First, in-process L1, so the extra-hot read-only value stops on the box. Second, a replica: copy the same key onto several cache nodes and spread the reads. A viral short code and a celebrity outbox are this shape. Never-expire on every key is a hotspot special case mistaken for a global policy. That is not the answer.

Penetration is a key that never existed: empty value, short TTL, and a bloom filter if the traffic is large. Breakdown is a hot key expiring: single-flight lets only one go back to origin. Avalanche is expire-together or the cache dying: TTL jitter spreads expiry, and if it's down you rate-limit. Extra hot: replica, plus a local L1.

同一句热点：Ch09 · 短链 的爆款码，Ch11 · 新闻 Feed 的大 V。媒体 URL 走 CDN，这题不设计 PoP。The same hot-key line: a viral code in Ch09 · URL shortener, a celebrity in Ch11 · news feed. Media URLs go to the CDN. You don't design PoPs on that problem.

追问Follow-ups

中文

  1. 默认哪种策略？Cache-Aside。DB 是 source of truth。写后 DEL，TTL 封顶。
  2. 为什么删而不是更新？慢读会把旧值 SET 回去。下一拍 miss 回填。
  3. Through 和 Back？Through 同步双写，写更慢，下一读是新的。Back 可能丢数，只给可丢的计数。
  4. 穿透和击穿？穿透：key 从不存在，空值或 bloom。击穿：一个热点过期，single-flight。
  5. 雪崩只改 TTL 够吗？jitter 管同时过期。集群没了要限流和降级。
  6. CDN 能换掉 Redis 吗？不能。边缘是 HTTP。Redis 是应用对象。
  7. cache key 错了会怎样？串用户，或者命中率碎掉。私人响应不要共享。302 不要长期放 CDN。
  8. Memcache 那篇怎么点？demand-filled lookaside；leased get 防 herd 和 stale set。
2026 和旧笔记差在哪

旧笔记把缓存写成六种策略的目录，外加淘汰算法全书和云产品对照。上场只带 Aside 默认、三种失败各一句、CDN 三个点。Through 和 Back 是 trade-off。Read-Through、Write-Around、预热各点一句。穿透、击穿、雪崩要会开口，不要合成一把锁。远程缓存一句选型就够，不要骂战，也不要把许可证当答案。机制是 HTTP edge 加远程 KV，不要报产品名，边缘函数也不是 hard part。语义缓存一句回到 Ch32。延迟双删不是银弹：Aside 是写库然后 DEL，再加 TTL；lease 和 single-flight 防 stale set 与 stampede。LRU 够开口，进程内 W-TinyLFU 选读。

English

  1. Default policy? Cache-Aside. The DB is the source of truth. DEL after the write, TTL caps the window.
  2. Why delete instead of updating? A slow read SETs the old value back. The next beat misses and fills.
  3. Through and Back? Through dual-writes in sync, the write is slower, the next read is fresh. Back can lose data, and only for counters you can lose.
  4. Penetration versus stampede? Penetration: the key never existed, empty value or bloom. Stampede: one hot key expires, single-flight.
  5. Is a TTL change enough for avalanche? Jitter covers expire-together. A dead cluster needs rate limit and degrade.
  6. Can a CDN replace Redis? No. The edge is HTTP. Redis is application objects.
  7. Wrong cache key? You leak across users, or the hit rate turns to dust. Don't share a private response. Don't long-cache a 302.
  8. The Memcache paper in one line? demand-filled lookaside; leased get stops the herd and a stale set.
What changed since the old notes

Old notes turned cache into a catalog of six policies, plus an eviction encyclopedia and a cloud-product comparison. You walk in with Aside as the default, one line for each of the three failures, and three CDN points. Through and Back are trade-offs. Read-Through, Write-Around, and warmup each get one line. Penetration, stampede, and avalanche have to be opened separately, not as one lock. One line picks the remote cache. No flame war, and a license is not the answer. The mechanisms are HTTP edge plus a remote KV. Don't recite a product name. Edge functions are not the hard part. Semantic cache is one line back to Ch32. Delayed double-delete is not the silver bullet: Aside is write the DB, then DEL, plus TTL; a lease and single-flight stop stale set and stampede. LRU is enough to open. In-process W-TinyLFU is optional.
