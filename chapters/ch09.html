为什么先算这些数

先算写：1,000,000 ÷ 86,400 = 11.57/s，×10 ≈ 116/s。对 A6 的 500 笔创建事务/秒预算，116 ÷ 500 = 23.2%，所以这组假设暂不逼分片；预算包含 Link、幂等记录的事务成本，要用真实 URL 长度和索引压测。写侧先解决唯一、并发重试、alias 原子抢占。不能仅凭“百级 QPS”断言任何数据库都足够。

读量是 1,000,000 × 100 = 100,000,000/天，÷86,400 ≈ 1,157/s，×10 ≈ 11.6K/s。按 A5 的 1,000 × 60% = 600 可用 QPS/台，11,600 ÷ 600 = 19.33，向上取整为 20 台 Redirect；掉一台还剩 19,000 的舒适容量，11,600 ÷ 19,000 ≈ 61.1%。这是工作预算，不是压测结论。峰值落到无状态层，LB 才有扩容理由；热点另由本地缓存与回源合并保护。

存储按每天新增积分：1,000,000 × 365 × 500 B = 182.5 GB/年逻辑行；一份主库加两份副本，×3 = 547.5 GB。A4 的 500 B 不含索引、备份与访问日志；按 0.6–1 TB/年预留也只是待测的规划区间，不能再把索引重复算进原始行。长 URL、幂等记录保留、outbox 积压与磁盘余量会改这个区间，短码不复用也会持续消耗命名空间。

最后别把目标网页流量算到短链系统。短链服务只返回一个很小的 302 响应和 Location header。真正的 HTML、图片和视频由目标站点承担。按 A5，11,600 × 500 B = 5.8 MB/s = 46.4 Mb/s，是 20 台合计出口，每台约 0.29 MB/s = 2.32 Mb/s；协议和连接开销还未计入。若把目标页的 1 MB 算进来，就错成 92.8 Gb/s。

Why these numbers come first

Writes are 1,000,000 / 86,400 = 11.57/s, or about 116/s at 10× peak. Against A6’s 500 create transactions/s, utilization is 116 / 500 = 23.2%, so these assumptions do not force sharding. That budget includes the Link and idempotency transaction; validate it with real URL lengths and indexes. First settle uniqueness, concurrent retries, and atomic alias claims. Hundreds of QPS alone is no universal database guarantee.

Reads are 1,000,000 × 100 = 100M/day, about 1,157/s on average and 11.6K/s at peak. A5 gives 1,000 × 60% = 600 usable QPS/instance; ceil(11,600 / 600) = 20 Redirect instances. Losing one leaves 19,000 comfortable capacity and 11,600 / 19,000 ≈ 61.1% utilization. This is a budget, not measured throughput. It motivates a stateless tier and LB; local cache and coalescing handle skew separately.

Storage integrates daily creation: 1M × 365 × 500 B = 182.5 GB logical rows/year, or 547.5 GB for a primary and two replicas. A4 excludes indexes, backups, and access logs. Planning 0.6–1 TB/year is only a range to validate, not another measurement or a reason to count indexes twice. Long URLs, retained idempotency rows, outbox backlog, and headroom can change it; nonreuse continues consuming the namespace.

Do not charge the destination page to this service. The shortener returns a small 302 response and a Location header; the destination serves its own HTML, images, and video. A5 gives 11,600 × 500 B = 5.8 MB/s = 46.4 Mb/s across 20 instances, or about 0.29 MB/s = 2.32 Mb/s each, excluding protocol and connection overhead. Charging a 1 MB destination page would wrongly inflate it to 92.8 Gb/s.

怎么读这张终图

Edge + LB 负责 TLS、域名路由、基础限流和把两类请求送到正确服务。它不拥有短链映射。把状态放在 Edge 里会让发布、扩缩容和多节点一致性变得困难；这里只让它做便宜、可复制的工作。

Shorten 是写侧。它做 URL 语法与 scheme 校验、tenant quota、幂等处理、自定义 alias 抢占，以及普通短码生成。它可以容忍几百毫秒延迟，却必须把“到底创建了哪一个 code”回答得确定。Redirect 是读侧，只做 code 校验、缓存 / 存储查询、状态判断和返回 302。两者逻辑拆开，是为了让延迟目标、扩缩容比例和故障影响互不绑架；小规模时它们仍可以部署在同一个代码库或进程里。

Mapping Store 保存 code → Link record，是唯一权威来源。Redis 和 Local LRU 都是派生状态；丢失时可以有限回源，已过新鲜度上限则失败关闭。缓存丢失不保证只是变慢，它也可能使容量不足，必须减少可用性来保护权威库。面试中说“Redis 挂了还有数据库”不够，还要补一句：回源必须限流并合并同 key 请求，否则缓存故障会瞬间把数据库拖死。

ID Allocator 只服务普通创建，不参与跳转。这个依赖方向很重要：即使发号器故障，已有链接仍应正常跳转。Click Stream 同样不在同步回程上；它把点击统计、去重、聚合与主路径隔开。架构图上用虚线不是装饰，而是在声明“这条支路失败时 302 仍成功”。

How to read the final diagram

Edge + LB terminates TLS, routes domains, applies basic rate limits, and sends each request type to the right service. It owns no link mapping. Putting mappings at the edge would complicate rollout, scaling, and consistency; keep this layer cheap and reproducible.

Shorten is the write side: syntax and scheme validation, tenant quotas, idempotency, custom-alias reservation, and ordinary code generation. It may tolerate hundreds of milliseconds but must answer deterministically which code was created. Redirect is the read side: validate the code, query cache or storage, evaluate status, and return the redirect. The logical split isolates latency goals, scaling ratios, and failures; at small scale both may still ship in one codebase or process.

Mapping Store owns code → Link record. Redis and Local LRU are derived state; loss permits bounded fallback and elapsed deadlines fail closed. Losing them can reduce availability through capacity limits, not merely increase latency. “Fall back to the database” is incomplete unless requests are rate-limited and same-key misses are coalesced.

ID Allocator serves normal creates only and never appears on redirect. That dependency direction preserves existing links during allocator failure. Click Stream is also outside the response path; its dashed line is a failure contract stating that a broken analytics branch does not break the 302.

为什么现在不画 CDN 和 multi-regionWhy CDN and multi-region are absent—for now

CDN 可以缓存 302，但这样点击可能不再经过 Redirect，统计、撤销和 retarget 的语义都会变化。只有当面试官把全球延迟或源站容量提为目标时，才把“边缘短 TTL + edge log / event”作为下一层 trade-off。multi-region 也一样：它会立即引入 code 唯一性、跨区复制、撤销传播和冲突解决问题。先证明单 Region 方案达不到目标，再付这笔复杂度。

A CDN can cache a 302, but clicks may then bypass Redirect, changing analytics, revocation, and retarget semantics. Add short edge TTL plus edge logs/events only when global latency or origin capacity becomes a requirement. Multi-region likewise introduces code uniqueness, replication, revocation propagation, and conflict resolution. Pay that complexity only after showing the single-region design misses a stated goal.

四个容易漏掉的语义

第一，Idempotency-Key 代表一次创建意图，不代表 target URL。客户端发出请求后超时，它不知道服务端是否已经成功写入；重试必须得到第一次的 code。若把 target URL 当幂等键，同一用户为两个 campaign 创建不同统计链接的需求就被错误合并。本题键空间包含 owner，A11 保留 24 小时，客户端必须在这个窗口内重试。同 key 携带不同参数返回 409；request_hash 比较的是规范化后的整份创建参数，不只 URL。过了窗口，接口不再承诺恢复第一次结果。[6]

第二，自定义 alias 的唯一性要靠存储条件写。“先 SELECT 看是否存在，再 INSERT”在并发下会让两个请求都看到空位。正确做法是唯一索引、INSERT ... ON CONFLICT 或 KV 的 compare-and-set / put-if-absent；谁写成功谁拥有 alias，失败者收到 409。保留 /v1、管理路由等名字；自动码与 alias 共用 code 唯一索引，alias 占用的六位空间也要扣掉。[9]

第三，状态码要让调用者知道能否重试。格式不合法是 400，未认证是 401，自定义码冲突是 409，quota / rate limit 是 429，临时存储故障是 503。对 429 / 503 返回 Retry-After，再配合相同 Idempotency-Key 重试；不要把所有失败都包成 200 加业务字符串。

第四，Link record 需要状态和版本。status 区分 active、revoked、blocked；expires_at 表示时间到期；version 帮助缓存失效和并发 retarget。删除通常做 tombstone 或状态转换而不是立刻复用 code，否则旧缓存、搜索引擎和历史消息可能把旧短链导向完全无关的新用户目标。

Four semantics people often miss

First, Idempotency-Key identifies one create intent, not a target URL. After a timeout the client cannot know whether the server committed, so a retry must recover the first code. Using the target as the key incorrectly merges two campaigns that intentionally share a landing page. Scope it by owner; A11 retains results for 24 hours and requires retries within that window. A changed request hash under the same key returns 409. Hash the complete normalized create parameters, not only the URL. After retention ends, recovering the first result is no longer promised. [6]

Second, custom-alias uniqueness belongs in a conditional storage operation. A SELECT followed by INSERT races because two writers can both observe absence. Use a unique index, INSERT ... ON CONFLICT, compare-and-set, or put-if-absent. The winner owns the alias; the loser receives 409. Reserve /v1 and management names. Generated codes and aliases share the code constraint; six-character aliases consume that namespace too. [9]

Third, status codes tell clients whether to retry. Malformed input is 400, missing authentication 401, alias collision 409, rate or quota pressure 429, and transient storage failure 503. Pair 429/503 with Retry-After and reuse the Idempotency-Key; do not flatten every failure into HTTP 200 plus a string.

Fourth, a Link record needs status and version. status distinguishes active, revoked, and blocked; expires_at handles time expiry; version supports cache invalidation and concurrent retargeting. Deletion normally becomes a tombstone or state change rather than immediate code reuse, because stale caches and old messages could otherwise redirect an old code to an unrelated new owner.

写路径：唯一性落在条件写，不落在运气Write path: uniqueness comes from conditional writes, not luck

正常创建与并发重试怎么收口Close normal creation and concurrent retries

POST 经 Edge + LB 到 Shorten，认证 owner、检查 quota、解析 target_url，只允许 http/https。URL 规范化保守处理 host 大小写和默认端口，不随意重排 query；普通码区分大小写，alias 另用允许的字符集和长度。先查 (owner, key)：找到相同 request_hash 就返回保存的结果，不分新号。

查不到时，普通码取本地号段的下一个整数并做 base62 + padding；alias 直接作为候选。Shorten 开同库事务，插入 Link 与 Idempotency，分别由 UNIQUE(code) 和 UNIQUE(owner, key) 守住。两者一起提交才返回 201。若同 key 并发，一个胜者提交，另一笔因唯一冲突回滚全部 mapping，重新读取胜者并比较摘要；这一步才保证并发重试只创建一条。[6][9]

同 URL 的两个 campaign 可以用不同 key 创建不同 code。若竞争的是同一个 alias、但 key 不同，失败者得到 409，不能冒充幂等命中。普通生成码若被 alias 抢占，丢掉该 ID、有限次数换下一个再试；连续异常则告警或 503。不能无限重试，也不能回收用过的号段。

先领到 ID 再回滚会有洞，属于可接受的分配成本。数据库已提交、连接却断开时，相同 key 的重试读回原 code；若 commit 结果未知，也按这个协议确认。第一版不把幂等记录放到另一份 KV。若确实拆库，必须另加稳定 request_id 和可恢复状态机；outbox 本身不能替两份数据库提供原子创建。

POST crosses Edge + LB to Shorten, which authenticates the owner, checks quota, parses target_url, and allows only http/https. Normalize host case and default ports conservatively; arbitrary query reordering can alter semantics. Generated codes are case-sensitive; aliases use their agreed grammar. Look up (owner, key) first and recover matching request_hash without allocating.

On a miss, a generated code takes a local-range ID and applies base62 plus padding; an alias is already a candidate. In one database transaction, insert Link and Idempotency under UNIQUE(code) and UNIQUE(owner, key). Return 201 only after both commit. Concurrent same-key requests have one winner; the loser rolls back its whole mapping, reads the winner, and compares hashes. That constraint settles the race. [6][9]

Two campaigns targeting the same URL can use different keys and receive different codes. Competing for an alias with different keys gives the loser 409, not a fake idempotency hit. If an alias occupies a generated candidate, discard the ID and retry a bounded number of new candidates; sustained conflicts alert or yield 503. Never retry indefinitely or recycle a range.

Allocating an ID before rollback leaves a harmless gap. If commit succeeds but the connection drops, the same key recovers the first code; uncertain commits use that protocol too. Keep idempotency in the same database initially. Splitting stores needs a stable request_id and recoverable state machine; an outbox alone cannot make cross-database creation atomic.

读路径：302、缓存与统计各走自己的线Read path: separate the 302, caching, and analytics lines

一次 redirect 到底做了什么What one redirect actually does

从 GET 到 Location

Edge 先拒绝明显非法的 code 形状，例如长度超限或含不在 alphabet 中的字符，避免垃圾请求进入应用层。Redirect 随后按 Local LRU → Redis → Mapping Store 查找。Local LRU 延迟最低，却是每个实例各自的一份；Redis 让实例共享热集；Mapping Store 才能回答权威状态。每一级 miss 都要区分“没有这个 key”和“这一层暂时不可用”，前者可以进入 negative cache，后者不能误判为 404。

读到记录后仍不能立刻 302。服务要检查 status、expires_at，必要时验证版本。active 才返回目标；unknown 用 404，明确 expired / revoked 可用 410 或安全说明页。把三者全部缓存成同一个 null 会让临时存储故障、真实不存在和已封禁无法区分，也会让恢复行为不可控。

成功响应包含 Location，以及与产品语义一致的 Cache-Control。为避免浏览器或代理绕过可变映射查询，本方案给 302、404、410 都加 Cache-Control: no-store；后二者也有启发式缓存资格。[1][2] 这只约束遵循标准的 HTTP 缓存，内部 Redis / Local 仍靠 valid_until 与失效事件；统计仍可能因生产者崩溃而漏记。如果允许统计近似、撤销有几十秒传播窗口，可以在浏览器或 CDN 给很短 TTL，降低源站延迟；但这是一笔明确交换，不是“302 自然不会缓存”。

From GET to Location

The edge rejects malformed code shapes—excessive length or characters outside the alphabet—before they consume application work. Redirect then checks Local LRU, Redis, and finally Mapping Store. Local cache is fastest but per-instance; Redis shares the hot set; Mapping Store alone answers authoritative state. At every layer distinguish “key absent” from “layer unavailable.” The first may be negative-cached; the second must not become a false 404.

A found record is not immediately redirectable. Check status, expires_at, and when needed its version. Only active records return the target. Unknown may be 404; explicit expiry or revocation may be 410 or a safety page. Caching all three as the same null erases the difference between absence, a temporary store failure, and a blocked link.

A successful response carries Location and cache controls matching product semantics. This design sends Cache-Control: no-store on 302, 404, and 410 to avoid HTTP caches bypassing mutable mapping lookup; the latter two are also heuristically cacheable. [1][2] This controls compliant HTTP caches. Redis/Local still require deadlines and invalidation, and producer crashes can still lose analytics events. If approximate analytics and a tens-of-seconds propagation window are acceptable, a short browser or CDN TTL can lower origin latency. That is an explicit exchange, not a property automatically granted by 302.

301、302、307 怎么选Choosing among 301, 302, and 307

301 表达永久搬迁，RFC 允许启发式缓存；浏览器、代理或搜索引擎可能长期记住目标，所以不适合默认的可撤销短链。302 表达临时目标，是传统短链最常见答案；对本题的 GET 请求，历史上的 method rewrite 差异通常不构成问题。307 也是临时重定向，但明确保持原 method 和 body；如果系统允许非 GET 短链或要严格保留方法，可选 307。真正决定统计是否回源的仍是缓存策略与统计位置，而不是背诵一个状态码。

301 declares a permanent move and is heuristically cacheable; browsers, intermediaries, and search engines may retain the target, making it a poor default for revocable links. 302 is temporary and remains the conventional shortener answer; historical method rewriting is normally irrelevant because this path starts with GET. 307 is also temporary but explicitly preserves method and body, useful if non-GET short links are supported. Whether analytics reaches origin still depends on cache policy and event placement—not a memorized status code.

统计允许什么损失，要在发布前说清State the analytics loss contract before publishing

一个 click event 至少带 event_id、code、occurred_at、粗粒度 client / referrer 信息和隐私策略允许的维度。生产者重试可能制造重复事件，因此消费者要按 event_id 去重或接受 at-least-once 后用幂等聚合。事件时间与处理时间要分开，否则 MQ 延迟会把昨天的点击算到今天。正常流向是 Redirect → Click Stream → Analytics → Click Store。事件在有界队列中交给异步生产者，不能要求线程等 MQ 确认；但响应与入队也不是原子操作。若进程在这两步间崩溃可能丢事件，重复投递则靠消费者去重。Analytics 晚到或短时不可用不改变映射状态。

如果业务声称“绝不丢一个点击”，就必须讨论本地持久化、同步日志或 edge event 的成本；它会增加跳转延迟与故障耦合。更常见的选择是 redirect SLO 优先，统计允许极小、可观测的损失，并通过 producer failure metric、queue lag 和对账任务量化，而不是嘴上说“异步所以可靠”。

A click event should include an event_id, code, occurred-at time, coarse client/referrer context, and only privacy-approved dimensions. Producer retries create duplicates, so consumers deduplicate by event ID or use idempotent aggregation under at-least-once delivery. Separate event time from processing time so queue lag does not move yesterday’s clicks into today. The normal flow is Redirect → Click Stream → Analytics → Click Store. Hand events to a bounded asynchronous producer without waiting for MQ acknowledgement. Response and enqueue are not atomic: a crash between them can lose an event, while replay can duplicate one. Analytics delay or outage does not change mapping state.

If the product claims zero click loss, discuss the latency and coupling cost of local durability, synchronous logs, or edge events. A more common choice prioritizes redirect SLO and accepts a tiny, measurable loss budget, observed through producer failures, queue lag, and reconciliation—not the slogan “it is async, therefore reliable.”

6 位 base62 的空间是 568 亿。号段让多个实例拿到不重叠的小 ID，再做 base62。它紧凑且无碰撞，但顺序可枚举。需要不可预测时，可选择足够熵的随机 token 或对连续 ID 做可逆置换；代价是碰撞处理或密钥管理。

hash 截断为什么不是免费方案

把 hash(target_url) 截成 6 个 base62 字符，确实可以让同一个输入稳定得到同一个候选码，但候选空间仍只有 N = 62^6。在候选近似独立、均匀的假设下，P(至少一次碰撞) ≈ 1 − exp(−n(n−1)/(2N))。令它等于 1/2，得到 n ≈ sqrt(2N ln 2) ≈ 280,610，约 28 万个独立候选；这是本章推导，不是外部测量。它不表示第 28 万条一定冲突，而是表示“到这个规模至少发生一次碰撞”的概率已经不可忽略。

因此 hash 方案仍要做条件插入：只有 owner、campaign、过期与去重契约都允许时，同 URL 才能复用；若对应不同 URL，就加盐、扩大长度或重试另一个候选。此时它并不真正无状态，还引入 normalization 语义和热点长 URL 的并发竞争。若需求只是幂等，用 Idempotency-Key 更精确；若需求是不可预测，用足够熵的随机 token 更直接。

顺序 ID 可枚举也不意味着“换 Snowflake 就安全”。Snowflake 高位包含时间，仍泄露结构，而且编码太长。保留顺序 ID 的一一对应关系时，可以用空间内的带密钥可逆置换；换成随机候选则靠唯一约束与碰撞重试。它改变外观，不增加 56.8B 的总熵，也不能把短码变成授权凭证。

Why a truncated hash is not free

Truncating hash(target_url) to six base62 characters gives the same input a stable candidate, but the space remains N = 62^6. Assuming approximately independent, uniform candidates, P(any collision) ≈ 1 − exp(−n(n−1)/(2N)). Setting this to 1/2 gives n ≈ sqrt(2N ln 2) ≈ 280,610, about 280 thousand candidates. This is a derivation here, not an external measurement. It does not mean the 280-thousandth row must collide; it means collision handling is already a real requirement.

The hash path still needs a conditional insert. Reuse for the same URL only when owner, campaign, expiry, and deduplication semantics all permit it; if it maps elsewhere, salt, lengthen, or generate another candidate. The design is therefore not stateless, and it adds URL-normalization semantics plus concurrent contention for popular targets. Use Idempotency-Key when the requirement is retry safety; use sufficiently random tokens when the requirement is unpredictability.

Enumerability of sequential IDs does not make Snowflake a security fix. Snowflake still exposes structure through time bits and is too large. A keyed permutation hides order while preserving a one-to-one mapping; random candidates instead require uniqueness constraints and collision retries. Neither approach increases the 56.8-billion space or turns a locator into authorization.

面试判断：在给定的百级 peak create QPS 下，先答 DB 自增也不丢分；当面试官追问多实例、数据库压力或短时不可用，再演进到 segment。复杂方案必须由需求推出。Interview judgment: at roughly one hundred peak creates per second, DB auto-increment is a defensible first answer. Evolve to segments when multi-instance allocation, database pressure, or brief allocator outages enter the requirements.

缓存新鲜度：热点之外，撤销上限怎么守Cache freshness: enforce revocation as well as hotspot protection

缓存对象和截止时刻是一份契约Cache objects and deadlines form one contract

key 是 domain + code，单域名时 domain 隐含；value 是 target_url、status、expires_at、version、checked_at、valid_until。Redirect 必须把 unknown、expired/revoked、blocked 与依赖错误分开：只有权威库确认不存在才记负缓存。版本号单独存在缓存里并不能告诉你“它是否最新”，仍需来源和年龄上限。

A10 把撤销约束在单地域权威提交后的 10 秒内，指不再发出旧目标的新跳转响应。一次权威读开始时记 checked_at，valid_until = checked_at + 8 秒，并与 expires_at 取较早者。预留 1 秒时钟不确定性与 1 秒请求在途预算；无法满足时钟或请求期限就失败关闭。Redis → Local 复制时继承原截止时刻，正向 jitter 也不能越过它。t=0 查出的 v7，t=7 搬到 Local，仍在 t=8 到期；两级各重新给 10 秒会变成接近 20 秒。

miss 读同一地域的权威主库；如果改读异步副本，必须另加可验证的复制新鲜度，否则“刚读到 v7”仍可能是很久以前的状态。慢读的年龄从读开始算，不从返回或 SET 算；超过截止就丢结果或重新读。网络分区时默认不延长 stale，撤销新鲜度优先于命中率。这个契约不撤回用户已获得的目标 URL，也不替目标资源取消访问权限。

unknown 负缓存按 A11 只留 1 秒，并在创建成功后尽力失效；这仍不能保证所有公众立即看见新 alias。要求 owner 严格写后读时，201 返回 code + version，后续 API GET 带最小版本，绕过负缓存和低版本记录读主库。若产品要求每个无版本的公众 GET 也立即可见，就取消负缓存或增加创建确认屏障，不能只说“删一下就行”。

Key by domain plus code, with domain implicit for one domain. Values include target_url, status, expires_at, version, checked_at, and valid_until. Distinguish absent, expired/revoked, blocked, and dependency failure. Negative-cache only authoritative absence. A version stored in a cache does not itself prove it is current; source and age matter.

A10 bounds new redirect responses to an old target within ten seconds of a one-region authoritative commit. Mark checked_at at authoritative read start; valid_until is checked_at + 8 seconds, capped by expires_at. Reserve one second each for clock uncertainty and in-flight work; fail closed if clock or request deadlines cannot be trusted. Redis-to-Local copies inherit this deadline, and positive jitter cannot extend it. A t=0 v7 copied at t=7 still expires at t=8; restarting ten seconds at each tier can approach twenty.

Misses read the same-region authoritative primary. Async replicas require separately verifiable freshness; a newly received v7 may otherwise be arbitrarily old. Age a slow read from its start, not its return or cache SET; discard elapsed results or reread. Partitions do not extend stale serving by default. This contract cannot retract a destination URL already disclosed or revoke access at the destination.

A11 negative-caches absence for one second and best-effort evicts on create, but that does not guarantee immediate public alias visibility. For strict owner read-after-write, 201 returns code and version; the following API GET supplies the minimum version, bypasses absent or older cache entries, and reads primary. If every unversioned public GET must be immediately visible, remove negative caching or add a creation barrier; a best-effort delete is insufficient.

删键之后，旧读为什么还能写回来Why an old read can refill after deletion

t=0 的读拿到 v7，t=1 管理请求提交 blocked v8 并写 outbox，t=2 失效已删除缓存，t=3 慢读又 SET v7。仅删键会被旧读重新填满。Invalidator 要分别通知 Redis 和所有 Local，保留每码最高 version floor；SET 时原子比较，v7 低于已见的 v8 就拒绝。进程内也要把失效与 in-flight 回填放进同一版本比较，不能无条件覆盖。[7]

outbox 让状态修改和待发事件同库提交，relay 持续投递，消费者按 code + version 幂等。只收到 v8 时不能被乱序 v7 降级；floor 保留期覆盖最大缓存年龄和回填请求期限。事件漏达、消费者离线或 floor 丢失时，继承的 valid_until 仍是最后上限，不能把版本机制当无限期正确性的证明。这里借鉴 Memcache 的 stale-set 防护，Redis 默认命令不会自动提供同样的租约协议。[7]

A read starts at t=0 with v7; an owner commits blocked v8 and outbox at t=1; invalidation deletes at t=2; the slow read SETs v7 at t=3. Delete alone permits stale refill. Invalidator independently notifies Redis and all Local caches, retaining a highest-version floor per code. Cache SET atomically compares versions and rejects v7 after v8. In-process invalidation and in-flight refill also need that comparison rather than unconditional overwrite. [7]

An outbox commits the state change and delivery intent together; a relay retries and consumers are idempotent by code/version. An out-of-order v7 cannot lower an observed v8 floor. Retain floors beyond the maximum cache age and in-flight deadline. If delivery, a consumer, or the floor is lost, inherited valid_until remains the final bound. This borrows the stale-set protection idea from Memcache; default Redis commands do not automatically implement that lease protocol. [7]

命中率怎样改变后端压力How hit rate changes origin pressure

在 11.6K peak redirect QPS 假设下，Redis + Local 合计 95% 命中，Mapping Store 只承担约 580 read QPS；90% 命中则是约 1,160 QPS。这个简单乘法比一句“缓存能抗高并发”更有用，因为它让你能反推数据库余量和降级风险。Local 也冷且 key 分散时，整层 Redis 故障会让回源需求跳回 11.6K；Local 热集仍命中则负载更小。90% 命中留下 1,160/s，已超过 A6 的 800/s 上限，需要提高命中、调预算或拒绝，不能把这两个命中率当等价方案。

Local LRU 不应追求缓存所有 code。假设一个完整缓存对象连运行时开销约 1 KB，10 万个最热 code 约占 100 MB/实例，20 台是 20 × 100 MB = 2 GB 整层内存；是否覆盖头部需要测量，不能由 LRU 名字保证。实际大小要用线上对象测量，淘汰可从 LRU / TinyLFU 一类策略中选；面试重点不是背算法，而是说明本地缓存提高速度、同时带来每实例副本和失效传播成本。

At the assumed 11.6K peak redirect QPS, a combined 95% local-plus-Redis hit rate leaves about 580 read QPS for Mapping Store; 90% leaves about 1,160. This multiplication is more useful than saying “cache handles scale” because it sizes origin headroom and degradation risk. With cold Local caches and distinct keys, total Redis failure can push origin demand to 11.6K; a warm local set reduces it. A 90% hit rate leaves 1,160/s, above A6’s 800/s cap, requiring better hits, a new budget, or rejection. These hit rates are not interchangeable designs.

Local LRU should not hold every code. If a full runtime cache object costs roughly 1 KB, the hottest 100 thousand codes cost about 100 MB per instance or 20 × 100 MB = 2 GB across the tier. Whether that covers the hot head is a measurement, not a property guaranteed by the LRU name. Measure actual object size and choose an eviction policy such as LRU or TinyLFU as needed. The interview point is that local cache buys latency at the cost of per-instance duplication and harder invalidation.

cache stampede 的三个层次Three layers of stampede control

  1. 同进程合并：按 code 建一个 in-flight promise，一个 leader 回源、waiter 共享结果；作用域是一台实例。20 台可有 20 个 leader，不能说全局只读一次；waiter 也有超时和队列上限。In-process coalescing: one in-flight promise per code per instance; one leader loads and waiters share. Twenty instances can have twenty leaders, so this is not one global read. Bound waiter count and waiting time too.
  2. 跨进程保护：Redis 仍可能收到多个实例的 leader；让 Mapping Store 有并发限额，必要时用短租约锁，但不要把全局锁放进每个正常 hit。Cross-process protection: Redis may still see one leader from every instance; cap origin concurrency and use a short lease only when justified, never a global lock on normal hits.
  3. 时间打散：在不超过 valid_until 的范围内做向下 TTL jitter 与 refresh-ahead。stale-while-revalidate 若越过默认 8 秒年龄上限，就违反撤销预算；只有另选更宽产品窗口才能启用。Time spreading: Use downward TTL jitter and refresh-ahead inside valid_until. Stale-while-revalidate beyond the default eight-second age limit violates revocation budgeting and needs an explicitly wider product window.

故障量级和错误预算必须一起算Calculate failure scale and error budget together

零星故障按 A12 的 0.1%：最坏在正常 580/s 之外多 11,600 × 0.001 = 11.6/s，合计 591.6 < 800，可以有限回源。整层 Redis 故障则按 Local 冷、key 不同的最坏情况，需求是 11,600/s；只准 800，其余 10,800/s 给 503。800 必须由整层共享预算或按实例分配额度执行，20 台各放 800 会变成 16,000/s，把保护完全取消。

A9 的 99.99% 按有效 active 跳转请求成功率计。本算例假设每天 1 亿次都纳入分母，允许失败 100,000,000 × 0.0001 = 10,000/天。峰值每秒失败 10,800，一天预算只够 10,000 ÷ 10,800 ≈ 0.93 秒；这只是按日摊出的课堂比较，不把一秒故障直接等同于任意月度 SLO 违约。它说明仅靠 fallback 达不到目标，需要缓存自身的副本、故障域隔离和恢复演练。时间比例四个 9 则是 0.0001 × 365 × 24 × 60 = 52.56 分钟/年，不能拿两种分母混算。

Mapping Store 不可用时停止创建与状态修改，fresh active cache 只能用到原截止；不能延长 TTL 来假装仍满足撤销要求。完全未知的 code 返回 503，明确 revoked / expired 返回 410，blocked 给不含 Location 的说明响应。缓存恢复后逐渐回填，先保 quota 与版本判定，再放大回源；全量 warm-up 会再次挤满预算。普通号段耗尽只影响生成码，alias 与 redirect 不依赖 allocator，但仍依赖健康的 Mapping Store。

For A12’s sparse 0.1% errors, add a worst-case 11,600 × 0.001 = 11.6/s to normal 580/s, giving 591.6 < 800. Total Redis outage with cold Local and distinct keys instead demands 11,600/s. Admit 800, return 503 for 10,800/s. Enforce that budget across the tier or allocate shares; twenty instances each admitting 800 produce 16,000/s and erase protection.

A9 measures successful eligible active redirects. Assuming all 100M daily requests enter the denominator, 99.99% allows 100M × 0.0001 = 10,000 failures/day. At 10,800 failures/s, that daily allowance lasts about 0.93 seconds. This is a classroom daily-rate comparison, not a claim that one second necessarily violates any monthly SLO. It motivates cache replicas, isolated failure domains, and recovery drills beyond fallback. Time-based four nines gives 0.0001 × 365 × 24 × 60 = 52.56 minutes/year; do not mix the denominators.

Mapping Store outage stops creation and state updates. Fresh active caches last only to their original deadline; extending TTL would violate revocation. Unknown due to dependency failure is 503, explicit expiry/revocation is 410, and blocked responses omit Location. Restore caches gradually under quotas and version checks rather than an origin-saturating full warm-up. Exhausted ranges affect generated codes; aliases and redirects bypass allocation but still need healthy Mapping Store.

安全与滥用：短码不是秘密Security and abuse: a short code is not a secret

威胁模型：系统会被怎样使用Threat model: how the system will be used

枚举：顺序码可猜相邻值，六位随机码仍是有限空间；[5] 的云文件和地图扫描证明短码不能当秘密。私密资源由目标服务做登录 / ACL；即使撤销短码，已知 target_url 也不能被收回。

钓鱼与封禁：短链隐藏域名。创建侧认证、quota、scheme allowlist 是便宜的同步检查；昂贵检测异步，高风险先 pending。目标内容或 DNS 后来会变，举报和复审必须能提交 blocked 版本，再经 outbox 传播；误杀有审计与 appeal。

扫描成本：随机 GET 新 code 每次都可 miss，1 秒负缓存不能挡住不同键。入口限流与整层 800/s 回源上限保住库；对超额请求明确 429/503，依赖错误绝不缓存成“不存在”。

预览 SSRF：Redirect 不取目标页面。若另加自动抓取器，隔离其网络；DNS 解析和每次跟随跳转都检查实际连接 IP，拒绝内网 / metadata 地址，绑定校验地址防重绑定，并限制端口、字节、跳转次数、超时。

Enumeration: sequential neighbors are guessable and six-character random tokens remain finite. Cloud-file/map scanning in [5] shows a locator is not a secret. Destinations enforce authentication/ACLs; revoking the short code cannot retract an already disclosed target_url.

Phishing and blocks: short links hide domains. Authentication, quotas, and scheme allowlists are cheap inline checks; expensive scans are async and high-risk links begin pending. Content or DNS can change later, so reports/review must commit blocked versions and relay them through outbox. False positives need audit and appeal.

Scan cost: each random new code can miss; one-second negative caching does not stop distinct keys. Boundary limits and the aggregate 800/s cap protect authority. Excess requests get explicit 429/503; dependency failures never become cached absence.

Preview SSRF: Redirect does not fetch destination pages. An optional fetcher needs network isolation, actual connection-IP checks after DNS resolution and every redirect, private/metadata address denial, binding of checked addresses against rebinding, and bounds on ports, bytes, redirects, and timeouts.

安全策略与产品体验的冲突Where safety and product experience conflict

更严格的检测会增加创建延迟和误杀，预览页会增加一次点击，封禁可能伤及已经传播的正常 campaign。正确答案不是“全部同步检查”，而是分层：便宜规则同步拒绝，昂贵扫描异步完成；高风险链接先进入 preview / pending 状态；封禁带 reason、审计和 appeal；安全状态通过高优先级 invalidation 快速进入读侧。

Stricter detection raises create latency and false positives; preview adds a click; blocking can damage a legitimate campaign already in circulation. Do not run every expensive check synchronously. Reject cheap rules inline, complete expensive scans asynchronously, place high-risk links into preview or pending state, attach reason/audit/appeal to blocks, and propagate safety state through a high-priority invalidation path.
