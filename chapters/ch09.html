English

Two endpoints: POST /v1/links creates a code and GET /{code} redirects. Reads dominate writes. I will draw create and redirect first, then go deep on code allocation, hot-key caching, and failure behavior. 为什么先算这些数

先看写入规模：每天创建 100 万条，平均为 1,000,000 ÷ 86,400 = 11.57 次/秒；假设峰值是平均值的 10 倍，则约为 116 次/秒。A6 给创建事务分配每秒 500 次的预算，峰值占 116 ÷ 500 = 23.2%，因此按这组假设，暂不需要为写入吞吐分片。这个预算包含链接记录（Link）和幂等记录的事务成本，还要用真实 URL 长度和索引压测。写入设计应先解决短码唯一、并发重试和别名的原子抢占，不能仅凭“每秒几百次请求”就认定任何数据库都能满足要求。

正常流量需要多少实例，损失一台后还够不够，要分开计算。每天 1 亿次跳转，平均约为 1,157 次/秒，峰值取 11,600 次/秒。每台按 1,000 × 60% = 600 QPS 分配预算，正常至少需要 ceil(11,600 / 600) = 20 台。但损失一台后，19 × 600 = 11,400，低于峰值。若要在 N−1 情况下继续维持相同的 60% 预算，应部署 21 台，剩下 20 台可承受 20 × 600 = 12,000 QPS。后文按 21 台计算；这些仍是有待压测的教学预算。

再按每天新增的记录累计存储量：1,000,000 × 365 × 500 B = 182.5 GB/年，这是逻辑记录的大小。一份主库加两份副本，共需 182.5 × 3 = 547.5 GB。A4 中每行 500 B 不含索引、备份和访问日志；预留 0.6–1 TB/年也只是待验证的规划区间，不能把索引再算进原始行大小。较长的 URL、保留的幂等记录、待发事件（outbox）积压和磁盘余量都会影响实际需求；短码不复用，也会持续消耗可用码空间。

出口流量只计算 302 响应及其 Location：11,600 × 500 B = 5.8 MB/s = 46.4 Mb/s。均分到 21 台，约为每台 0.276 MB/s，协议和连接开销另计。目标网页由目标站点传输，不经过短链服务。这里每次响应 500 B，与前面的每行记录 500 B，是两个独立假设。

Why these numbers come first

Writes are 1,000,000 / 86,400 = 11.57/s, or about 116/s at 10× peak. Against A6’s 500 create transactions/s, utilization is 116 / 500 = 23.2%, so these assumptions do not force sharding. That budget includes the Link and idempotency transaction; validate it with real URL lengths and indexes. First settle uniqueness, concurrent retries, and atomic alias claims. Hundreds of QPS alone is no universal database guarantee.

Separate normal capacity from failure headroom.100M redirects/day is about 1,157/s, rounded to 11,600/s at peak. Each instance budgets 1,000 × 60% = 600 QPS, so normal demand needs ceil(11,600 / 600) = 20. Losing one of twenty leaves 19 × 600 = 11,400, below peak. Deploy 21 for N−1 at the same 60% budget: twenty survivors provide 12,000 QPS. Subsequent examples use 21 instances; these are assumptions awaiting load tests.

Storage integrates daily creation: 1M × 365 × 500 B = 182.5 GB logical rows/year, or 547.5 GB for a primary and two replicas. A4 excludes indexes, backups, and access logs. Planning 0.6–1 TB/year is only a range to validate, not another measurement or a reason to count indexes twice. Long URLs, retained idempotency rows, outbox backlog, and headroom can change it; nonreuse continues consuming the namespace.

Egress counts only the 302 and Location: 11,600 × 500 B = 5.8 MB/s = 46.4 Mb/s, about 0.276 MB/s per instance across 21, plus protocol and connection overhead. The destination serves its own page. The 500 B row and 500 B response are independent assumptions.

整体架构：沿创建与跳转两条路径看职责High-level architecture: place both main paths first

从终图可以沿着两条主流程读下来。入口 Edge + LB 负责终结 TLS、路由和限流。创建服务 Shorten 校验请求并提交映射，生成普通码时按需向 ID Allocator 领取号段。跳转服务 Redirect 先查缓存，未命中时再查 Mapping Store。两者可以先放在同一个代码库中，再根据延迟目标和容量需求独立扩缩。

正式状态保存在 Mapping Store，包括链接记录、幂等回执和待发送事件。Redis 与本机缓存 Local 中的数据丢失后可以重建，但必须限制回源量，也不能延长过期快照的寿命。统计沿 Click Stream → Analytics → Click Store 异步处理，故障不会阻塞 302；发号器同样不参与已有链接的跳转。

Read the final frame as two main paths.Edge + LB terminates TLS, routes, and limits requests. Shorten validates and commits mappings, refilling normal-code ranges from ID Allocator only when needed. Redirect checks caches and loads Mapping Store on a miss. Both services can begin in one codebase, then scale independently for their latency and capacity targets.

Separate authority from derived state.Mapping Store owns Links, retry receipts, and outbox rows. Redis/Local may be lost, but origin fallback is capped and outdated snapshots cannot be renewed. Click Stream → Analytics → Click Store is an async branch, so analytics failure does not block 302. ID allocation is also absent from existing-link redirects.

什么时候再加入 CDN 和多地域部署Why CDN and multi-region are absent—for now

CDN 可以缓存 302，但缓存命中后，点击可能不再经过 Redirect，统计、撤销和目标地址修改的行为都会随之变化。只有全球访问延迟或源站容量成为明确目标时，再讨论边缘短 TTL，以及如何从边缘日志或事件中补充统计。多地域部署也会带来短码唯一性、跨区复制、撤销传播和冲突处理的成本。先说明单地域方案哪里达不到目标，再引入这些机制。

A CDN can cache a 302, but clicks may then bypass Redirect, changing analytics, revocation, and retarget semantics. Add short edge TTL plus edge logs/events only when global latency or origin capacity becomes a requirement. Multi-region likewise introduces code uniqueness, replication, revocation propagation, and conflict resolution. Pay that complexity only after showing the single-region design misses a stated goal.

API、幂等与最小数据模型API, idempotency, and the minimum data model

中文

POST /v1/links 接收目标地址 target_url、可选的自定义别名 custom_alias 和到期时间 expires_at，请求头携带幂等键 Idempotency-Key。别名已被占用时返回 409。GET /{code} 成功时返回 302 Location；确认短码不存在时返回 404，已到期或已撤销时返回 410，或展示产品约定的安全说明页。

同一个落地页可能由不同用户创建、用于不同活动，或设有不同到期时间，因此不应默认在全局按 target_url → code 去重。幂等范围由创建者身份（owner）和幂等键（key）共同确定。

English

POST /v1/links accepts target_url, optional custom_alias and expires_at, plus an Idempotency-Key header. A taken alias returns 409. GET /{code} returns 302 Location; unknown is 404, while expired or revoked becomes 410 or a product safety page.

Do not globally deduplicate target_url → code. The same landing page can belong to different owners, campaigns, or expiries. Scope idempotency by owner and key.

本例选择 PostgreSQL 18 作为单一权威数据库。下面的教学建表语句将唯一性落实为约束：短码 code 使用区分大小写的主键，幂等记录使用 owner/key 复合主键。保存的幂等响应快照保持不变，之后修改目标地址也不会重写它。这段示例没有展开完整的参数化服务、鉴权和迁移工具。

The example uses one authoritative PostgreSQL 18 database. This teaching DDL makes uniqueness concrete: case-sensitive code and composite owner/key keys. The stored idempotent response is immutable even after retargeting. A complete parameterized service, authentication, and migrations are outside the snippet.

-- PostgreSQL 18 teaching schema; one authoritative database.
CREATE TABLE Link (
  code text COLLATE "C" PRIMARY KEY,
  owner_id bigint NOT NULL,
  target_url text NOT NULL,
  status text NOT NULL CHECK (status IN ('active','revoked','blocked','pending')),
  expires_at timestamptz,
  created_at timestamptz NOT NULL DEFAULT now(),
  version bigint NOT NULL CHECK (version > 0)
);
CREATE TABLE Idempotency (
  owner_id bigint NOT NULL,
  key text COLLATE "C" NOT NULL,
  request_hash bytea NOT NULL,
  code text NOT NULL REFERENCES Link(code),
  response_status integer NOT NULL,
  response_body jsonb NOT NULL,
  retain_until timestamptz NOT NULL,
  PRIMARY KEY (owner_id, key)
);
CREATE TABLE Outbox (
  event_id uuid PRIMARY KEY,
  code text NOT NULL REFERENCES Link(code),
  version bigint NOT NULL,
  kind text NOT NULL,
  delivered_at timestamptz,
  UNIQUE(code, version)
);

本例也约定了输入限制。目标地址 target_url 按 UTF-8 编码后不得超过 2,048 B，只允许 http/https 协议，并拒绝 URL 中的用户信息部分（userinfo）、控制字符及 CR/LF；服务不会抓取目标页面。自动生成的短码固定为 6 位，字符集为 [0-9a-zA-Z]；自定义别名为 4–32 位，字符集为 [0-9a-zA-Z_-]，同样区分大小写，并保留 v1 等路由名称。校验 code 时，两种格式都要允许。

新建链接的到期时间必须在未来。不过，若同一请求已有幂等回执，应先回放回执，不能因为重试时链接已经到期就改回 400。幂等键 Idempotency-Key 长 1–128 个 ASCII 字符，创建者身份来自认证上下文；请求摘要 request_hash 覆盖规范化后的 URL、别名和到期时间。

Input limits are teaching choices: target_url is at most 2,048 UTF-8 bytes, only HTTP(S), no userinfo, controls, or CR/LF; the service does not fetch it. Generated codes are six [0-9a-zA-Z] characters; aliases are 4–32 case-sensitive [0-9a-zA-Z_-] characters with routes such as v1 reserved. Code validation admits either shape. Expiry must be future for a new create; replay an existing receipt before that time-sensitive validation, even if its link has since expired. Idempotency-Key is 1–128 ASCII characters and owner comes from authentication; the hash covers canonical URL, alias, and expiry.

四个容易漏掉的语义

第一，Idempotency-Key 标识一次创建意图。客户端超时后，无法知道服务端是否已经写入，因而重试需要找回第一次生成的短码。目标 URL 不适合作为幂等键：同一用户可能为两个活动创建不同的统计链接，虽然它们指向同一个页面。本题按创建者和幂等键确定范围，A11 约定回执保留 24 小时，客户端应在这个窗口内重试。同一键携带不同参数时返回 409；request_hash 比较规范化后的整份创建参数，包括别名和到期时间。超过保留窗口后，接口不再承诺恢复第一次结果。[6]

第二，别名由谁占用，要通过存储的条件写入决定。若先 SELECT 检查是否存在，再 INSERT，两个并发请求可能都看到空位。可以用唯一索引、INSERT ... ON CONFLICT，或 KV 的比较并交换（compare-and-set）、仅不存在时写入（put-if-absent）来约束竞争。写入成功者取得别名，冲突者返回 409。/v1 和管理路由等名称需要保留；自动码与别名共用 code 唯一索引，六位别名也会占用六位码空间。[9]

第三，状态码要能指导客户端处理失败。格式非法返回 400，未认证返回 401，别名冲突返回 409，超过配额或限流返回 429，临时存储故障返回 503。429 和 503 搭配 Retry-After 提示等待时间，重试仍使用相同的 Idempotency-Key。若把这些情况都包装成 200 加业务字符串，客户端就难以正确判断是否重试。

第四，链接记录需要保存状态和版本。status 区分启用、撤销和封禁等状态，expires_at 记录到期时间，version 支持缓存失效和目标地址的并发修改。删除时通常保留删除标记（tombstone），或改变状态，不立即复用短码。否则，旧缓存、搜索引擎和历史消息中的短链，可能把用户导向另一位创建者的新目标。

Four semantics people often miss

First, Idempotency-Key identifies one create intent, not a target URL. After a timeout the client cannot know whether the server committed, so a retry must recover the first code. Using the target as the key incorrectly merges two campaigns that intentionally share a landing page. Scope it by owner; A11 retains results for 24 hours and requires retries within that window. A changed request hash under the same key returns 409. Hash the complete normalized create parameters, not only the URL. After retention ends, recovering the first result is no longer promised. [6]

Second, custom-alias uniqueness belongs in a conditional storage operation. A SELECT followed by INSERT races because two writers can both observe absence. Use a unique index, INSERT ... ON CONFLICT, compare-and-set, or put-if-absent. The winner owns the alias; the loser receives 409. Reserve /v1 and management names. Generated codes and aliases share the code constraint; six-character aliases consume that namespace too. [9]

Third, status codes tell clients whether to retry. Malformed input is 400, missing authentication 401, alias collision 409, rate or quota pressure 429, and transient storage failure 503. Pair 429/503 with Retry-After and reuse the Idempotency-Key; do not flatten every failure into HTTP 200 plus a string.

Fourth, a Link record needs status and version. status distinguishes active, revoked, and blocked; expires_at handles time expiry; version supports cache invalidation and concurrent retargeting. Deletion normally becomes a tombstone or state change rather than immediate code reuse, because stale caches and old messages could otherwise redirect an old code to an unrelated new owner.

创建实现：发生冲突后，先查是否已有同一请求的结果Create: recover the same intent before classifying a conflict

下面的伪代码对应写入图的第 2–5 帧。先查幂等记录只是快路径，最终写入由 Link、Idempotency 的主键约束和同库事务共同保证。无论候选码来自号段中的下一个 ID，还是均匀随机生成的 base62，都通过同一套条件插入。每次尝试最多消耗一个候选码，允许序列中出现空洞。

链接的初始状态 initialStatus 由服务端可信的风险准入检查决定：通过时为 active，高风险时为 pending；拒绝创建返回 403，准入依赖不可用返回 503。客户端不能自行指定这个字段，待审状态和幂等回执仍在同一事务中提交。外围错误处理把连接、读取、BEGIN 和发号失败转为 503，并要求客户端用相同幂等键重试。查询成功却没有记录，与查询本身失败，要分别处理。

This implements write frames 2–5. Lookup is a fast path; the Link and Idempotency primary keys plus one database transaction enforce the commit. A range ID or a uniform random base62 candidate uses the same conditional insert. Each attempt can consume one candidate; gaps are allowed. initialStatus comes from trusted server risk admission: approved requests are active, high-risk ones pending, denial returns 403, and unavailable admission returns 503. Clients cannot choose it; pending and the retry receipt commit together. An outer error handler maps connection, read, BEGIN, and allocation failures to 503 with same-key retry; an empty result is distinct from a failed query.

ROLLBACK, then read the winner with a new primary statement: replay 201 for the same hash, or 409 for changed parameters. Only without a winner is an alias conflict a plain 409. 从 GET 到 Location

入口 Edge 先检查短码格式，拒绝长度超限或包含非法字符的请求，避免它们消耗应用资源。Redirect 随后依次查询本机缓存 Local LRU、共享缓存 Redis 和映射库 Mapping Store。本机缓存最快，但各实例各有一份；Redis 让实例共享常访问的数据；最终状态以 Mapping Store 为准。每一级查询都要区分“没有这个键”和“这一层暂时不可用”。只有主库查询成功且确认不存在，才能建立负缓存；本机或 Redis 未命中本身并不证明链接不存在，依赖错误也不能转成 404。

找到记录后，服务还要检查 status、expires_at，必要时核对版本，只有启用状态的记录才可返回目标地址。确认不存在用 404，明确到期或撤销可用 410 或安全说明页。如果把不存在、临时存储故障和已封禁都缓存成同一个 null，服务就无法按各自的原因正确恢复。

成功响应包含 Location，缓存策略则由产品需求决定。本方案要求浏览器和代理持续查询可变的映射，因此所有跳转与错误响应，包括 302、404 和 410，都带 Cache-Control: no-store；404 和 410 本身也允许启发式缓存。[1][2] 这个指令约束遵循标准的 HTTP 缓存，不能清除此前已缓存的永久跳转，也不能撤回历史记录、已打开的页面或已经披露的目标 URL。内部 Redis 和本机缓存仍靠 valid_until 与失效事件保证新鲜度，点击统计也仍可能因生产者崩溃而漏记。

如果产品接受近似统计，以及几十秒的撤销传播窗口，可以给浏览器或 CDN 设置很短的 TTL，减少源站访问和延迟。这样做需要明确接受相应代价，不能只凭“返回 302”就假定响应不会被缓存。

From GET to Location

The edge rejects malformed code shapes—excessive length or characters outside the alphabet—before they consume application work. Redirect then checks Local LRU, Redis, and finally Mapping Store. Local cache is fastest but per-instance; Redis shares the hot set; Mapping Store alone answers authoritative state. At every layer distinguish “key absent” from “layer unavailable.” Only a successful primary read that finds no row may create a negative cache entry. Local/Redis misses do not prove absence; dependency errors must not become false 404s.

A found record is not immediately redirectable. Check status, expires_at, and when needed its version. Only active records return the target. Unknown may be 404; explicit expiry or revocation may be 410 or a safety page. Caching all three as the same null erases the difference between absence, a temporary store failure, and a blocked link.

A successful response carries Location and cache controls matching product semantics. This design sends Cache-Control: no-store on 302, 404, and 410 to avoid HTTP caches bypassing mutable mapping lookup; the latter two are also heuristically cacheable. [1][2] This controls compliant HTTP caches. Redis/Local still require deadlines and invalidation, and producer crashes can still lose analytics events. If approximate analytics and a tens-of-seconds propagation window are acceptable, a short browser or CDN TTL can lower origin latency. That is an explicit exchange, not a property automatically granted by 302.

下面的伪代码对应读取图的第 2–5 帧。缓存未命中或不可用时，都可以尝试下一级；只有主库 SELECT 成功返回空行，才建立负缓存。最低版本要求 minimumVersion 默认为 0；创建者查询时可携带创建回执，要求至少读到 version=1，从而绕过 version=0 的负缓存。进程内请求合并（singleflight）和等待队列上限由外层实现，每秒 800 次的回源预算由所有实例合计共享。

This pseudocode follows read frames 2–5. Cache misses and errors may try the next source; only a successful empty primary SELECT creates a negative entry. minimumVersion defaults to zero; an owner read with a create receipt can require version≥1, bypassing version-zero negatives. An outer layer supplies process-local coalescing and bounded waiters; 800/s is the aggregate origin budget.

redirect(code, minimumVersion = 0):
  if not validCodeShape(code): return 404 with no-store
  if not clockWithinBudget(): return 503 with no-store
  snapshot = firstUsable(Local[code], Redis[code], minimumVersion)
  // Usable: now < valid_until AND version >= minimumVersion.
  if snapshot is absent:
    if not acquireAggregateOriginBudget(): return 503 with no-store
    checked_at = wallClockNow()         // before a NEW primary SELECT
    row = PRIMARY SELECT * FROM Link WHERE code = :code
    if read failed: return 503 with no-store  // never negative-cache errors
    snapshot = {row, checked_at,
                valid_until: checked_at + (row absent ? 1s : 8s)}
    if row exists and row.version < minimumVersion: return 503 with no-store
    if wallClockNow() >= snapshot.valid_until: return 503 with no-store
    bestEffortVersionCheckedFill(Redis, Local, snapshot)
    // Both tiers retain this SAME deadline; cache failure is not a 404.
  if not clockWithinBudget(): return 503 with no-store
  if wallClockNow() >= snapshot.valid_until: return 503 with no-store
  if snapshot.row absent: return 404 with no-store
  if snapshot.row.status in {'revoked','blocked'}: return 410 with no-store
  if snapshot.row.status == 'pending': return 200 review-page with no-store
  if snapshot.row.status != 'active': return 503 with no-store  // no Location
  if snapshot.row.expires_at != null and nowUpperBound() + 1s >= snapshot.row.expires_at:
    return 410 with no-store
  tryEnqueueBoundedClickEvent()          // allowed to drop; never waits for MQ
  emit 302 {Location:snapshot.row.target_url, Cache-Control:'no-store'}
  // Final check → emission <= 1s; recheck if delayed. No expired stale fallback.

firstUsable 将负缓存的版本视为 0。普通记录的有效期从权威读取开始时算起，为 8 秒；负缓存为 1 秒。复制到另一层缓存时，两者的截止时刻都不重新计算。

链接到期与快照变旧需要分开判断：快照仍新鲜，但 active 链接已经到达 expires_at，返回 410；pending 返回不带 Location 的 200 待审说明页；revoked 和 blocked 返回 410。若快照已经陈旧，数据库又不可达，则返回 503，因为服务无法确认链接的到期时间是否后来被延长。expires_at 可以修改，所以本例用当前时间的安全上界，再加 1 秒响应发出预算判断到期。这可能略早拒绝，却能避免检查后因排队而发出已过期的跳转。

firstUsable treats a negative entry as version zero. Positive snapshots retain read-start +8 seconds and negatives +1 second; copying never renews either. Expiry and snapshot age are separate: a fresh expired active record returns 410; pending returns a 200 review page without Location, and revoked/blocked return 410, while an outdated snapshot with an unavailable database yields 503 because expiry might have been extended. For mutable expires_at, the safe clock upper bound plus a one-second emission budget may reject slightly early, avoiding an expired redirect after queueing.

301、302、307 怎么选Choosing among 301, 302, and 307

301 表示永久搬迁，RFC 允许启发式缓存。浏览器、代理或搜索引擎可能长期记住目标，因此它不适合作为可撤销短链的默认选择。302 表示临时目标，是短链服务的常见选择；本题入口是 GET，历史上对请求方法改写的差异通常不构成问题。307 同样表示临时重定向，并明确保留原请求方法和请求体。如果需要支持非 GET 短链，或严格保留方法，可以选择 307。点击统计是否经过源站，最终仍取决于缓存策略和统计放在哪里。

301 declares a permanent move and is heuristically cacheable; browsers, intermediaries, and search engines may retain the target, making it a poor default for revocable links. 302 is temporary and remains the conventional shortener answer; historical method rewriting is normally irrelevant because this path starts with GET. 307 is also temporary but explicitly preserves method and body, useful if non-GET short links are supported. Whether analytics reaches origin still depends on cache policy and event placement—not a memorized status code.

异步统计：先说明允许丢多少，再设计投递State the analytics loss contract before publishing

每个点击事件至少包含事件标识 event_id、短码 code、发生时间 occurred_at、粗粒度的客户端与来源页面信息，以及隐私策略允许收集的维度。生产者重试可能重复发送，因此消费者要按 event_id 去重，或在至少一次投递下进行幂等聚合。统计还要区分事件发生时间和处理时间，避免消息延迟把昨天的点击算到今天。

正常流向为 Redirect → Click Stream → Analytics → Click Store。跳转线程只把事件交给有界队列中的异步生产者，不等待 MQ 确认。响应和入队无法原子完成，进程在两步之间崩溃时可能丢事件；重复投递则由消费者去重。统计程序处理变慢或短时不可用，不改变链接映射状态。

如果业务要求“一个点击都不能丢”，就要讨论本机持久化、同步日志或边缘事件的成本，它们会增加跳转延迟和故障耦合。更常见的选择是优先满足跳转 SLO，允许极小且可观测的统计损失，再通过生产者失败指标、队列积压延迟和对账任务量化损失。异步处理本身不提供可靠投递保证。

A click event should include an event_id, code, occurred-at time, coarse client/referrer context, and only privacy-approved dimensions. Producer retries create duplicates, so consumers deduplicate by event ID or use idempotent aggregation under at-least-once delivery. Separate event time from processing time so queue lag does not move yesterday’s clicks into today. The normal flow is Redirect → Click Stream → Analytics → Click Store. Hand events to a bounded asynchronous producer without waiting for MQ acknowledgement. Response and enqueue are not atomic: a crash between them can lose an event, while replay can duplicate one. Analytics delay or outage does not change mapping state.

If the product claims zero click loss, discuss the latency and coupling cost of local durability, synchronous logs, or edge events. A more common choice prioritizes redirect SLO and accepts a tiny, measurable loss budget, observed through producer failures, queue lag, and reconciliation—not the slogan “it is async, therefore reliable.”

截断哈希后，仍要处理什么

将 hash(target_url) 截成 6 个 base62 字符，可以让相同输入稳定得到相同候选码，但空间仍只有 N = 62^6。假设候选近似独立、均匀，出现过至少一次碰撞的概率为 P(至少一次碰撞) ≈ 1 − exp(−n(n−1)/(2N))。令概率等于 1/2，可得 n ≈ sqrt(2N ln 2) ≈ 280,610，即约 28 万个独立候选。这是本章推导，并非外部测量，也不表示第 28 万条一定碰撞；它说明，在这个规模下，已经需要认真处理碰撞。

因此，哈希方案仍需条件插入。只有创建者、活动、到期时间和去重契约都允许时，相同 URL 才能复用短码；若候选码已经指向另一个 URL，则需要加盐、增加长度或换一个候选重试。系统仍需保存状态，还多了 URL 规范化规则，以及热门目标地址上的并发竞争。如果要求只是安全重试，Idempotency-Key 更精确；如果要求不可预测，熵足够的随机标识更直接。

顺序 ID 可以枚举，也不能据此认定换成 Snowflake 就安全。Snowflake 的高位包含时间，仍会泄露结构，编码还更长。若希望保留 ID 的一一对应关系，可以在原空间内做带密钥的可逆置换；若采用随机候选，则依靠唯一约束和碰撞重试。两种方式都不会增加约 568 亿种取值所含的总熵，也不能让短码承担授权。

Why a truncated hash is not free

Truncating hash(target_url) to six base62 characters gives the same input a stable candidate, but the space remains N = 62^6. Assuming approximately independent, uniform candidates, P(any collision) ≈ 1 − exp(−n(n−1)/(2N)). Setting this to 1/2 gives n ≈ sqrt(2N ln 2) ≈ 280,610, about 280 thousand candidates. This is a derivation here, not an external measurement. It does not mean the 280-thousandth row must collide; it means collision handling is already a real requirement.

The hash path still needs a conditional insert. Reuse for the same URL only when owner, campaign, expiry, and deduplication semantics all permit it; if it maps elsewhere, salt, lengthen, or generate another candidate. The design is therefore not stateless, and it adds URL-normalization semantics plus concurrent contention for popular targets. Use Idempotency-Key when the requirement is retry safety; use sufficiently random tokens when the requirement is unpredictability.

Enumerability of sequential IDs does not make Snowflake a security fix. Snowflake still exposes structure through time bits and is too large. A keyed permutation hides order while preserving a one-to-one mapping; random candidates instead require uniqueness constraints and collision retries. Neither approach increases the 56.8-billion space or turns a locator into authorization.

缓存条目要同时保存内容和原截止时刻Cache objects and deadlines form one contract

缓存键由域名和短码组成，即 domain + code；只有一个域名时，可以隐含域名部分。缓存值包含目标地址 target_url、状态 status、到期时间 expires_at、版本 version、读取开始时刻 checked_at 和截止时刻 valid_until。Redirect 要区分不存在、到期或撤销、封禁，以及依赖错误；只有权威库确认不存在，才能建立负缓存。仅在缓存中保存版本号，无法证明这个版本仍是最新，还要知道它来自哪里、已经有多旧。

A10 约定：在单个地域内，撤销必须在权威库提交后的 10 秒内生效；超过这个窗口，新发出的跳转响应就不能再包含旧目标。每次开始权威读取时记下 checked_at，并设置 valid_until = checked_at + 8 秒。expires_at 仍用于单独判断链接是否到期，不能将业务到期当作缓存未命中。

余下的预算中，1 秒用于读取方与使用方合计的时钟不确定性，并非每台机器各有 1 秒；另 1 秒用于最终检查到响应发出。如果无法满足时钟误差或请求期限要求，就拒绝使用这份数据。从 Redis 复制到本机时沿用原截止时刻，即使给 TTL 加随机抖动，也不能把期限向后延。t=0 读出的 v7，t=7 复制到本机，仍在 t=8 失效；若两级各自重新给 10 秒，旧值就可能存活接近 20 秒。

缓存未命中时，读取同一地域的权威主库。如果改读异步副本，就必须另外验证复制新鲜度，否则刚返回的 v7 也可能是很久以前的状态。慢查询的年龄从读取开始算，不能从结果返回或 SET 时算起；超过截止时刻，就丢弃结果或重新读取。网络分区期间默认不延长旧数据的使用时间，优先遵守撤销新鲜度要求。这个约定无法撤回用户已知的目标 URL，也不能替目标服务取消访问权限。

按 A11，确认不存在的负缓存只保留 1 秒，创建成功后也会尽力使其失效，但这仍不保证所有公众立即看见新别名。创建者若要求严格写后读，可以在 201 中取得短码和版本，再在后续 API GET 中携带最低版本要求，绕过负缓存和低版本记录读取主库。若每个不带版本的公众 GET 都必须立即可见，就要取消负缓存，或增加创建确认屏障，不能只依赖尽力删除缓存。

Key by domain plus code, with domain implicit for one domain. Values include target_url, status, expires_at, version, checked_at, and valid_until. Distinguish absent, expired/revoked, blocked, and dependency failure. Negative-cache only authoritative absence. A version stored in a cache does not itself prove it is current; source and age matter.

A10 bounds new redirect responses to an old target within ten seconds of a one-region authoritative commit. Mark checked_at at authoritative read start; valid_until is checked_at + 8 seconds; expires_at is a separate rejection check, not a cache miss. Reserve one second of combined producer/consumer clock uncertainty (not one second per machine) and one second from final check to response emission; fail closed if clock or request deadlines cannot be trusted. Redis-to-Local copies inherit this deadline, and positive jitter cannot extend it. A t=0 v7 copied at t=7 still expires at t=8; restarting ten seconds at each tier can approach twenty.

Misses read the same-region authoritative primary. Async replicas require separately verifiable freshness; a newly received v7 may otherwise be arbitrarily old. Age a slow read from its start, not its return or cache SET; discard elapsed results or reread. Partitions do not extend stale serving by default. This contract cannot retract a destination URL already disclosed or revoke access at the destination.

A11 negative-caches absence for one second and best-effort evicts on create, but that does not guarantee immediate public alias visibility. 撤销实现：状态更新和待发事件在同一事务中提交Revocation commit: version check and outbox succeed together

管理接口 PATCH /v1/links/{code} 要求认证后的创建者身份，并通过 If-Match 携带预期版本。下面使用绑定参数的 SQL 对应撤销图第 1 帧：状态更新和事件插入在同一事务中完成，事件写入失败，整个事务都失败。若更新了 0 行，就不能报告成功；对已经授权的资源，版本不匹配返回 412，资源不存在可返回 404。并发请求使用同一个预期版本时，只允许一个更新成功。

PATCH /v1/links/{code} requires the authenticated owner and an If-Match version. This bound-parameter SQL implements revocation frame 1: state and event share one transaction; event insertion failure aborts both. Zero updated rows is a rejection, not success: for an authorized resource, a failed If-Match returns 412; a missing resource may return 404. Only one concurrent writer can win a given expected version.

-- Bound parameters, authenticated owner; execute in one transaction.
BEGIN;
WITH changed AS (
  UPDATE Link SET status = 'revoked', version = version + 1
  WHERE code = :code AND owner_id = :owner AND version = :expected_version
  RETURNING code, version
)
INSERT INTO Outbox(event_id, code, version, kind)
  SELECT :event_id, code, version, 'invalidate' FROM changed
RETURNING code, version;
-- Zero rows: no change; report 404/412 after authorization-safe lookup.
COMMIT;
-- Confirmed commit: acknowledge. Unknown outcome: GET owner state on primary.
-- Relay publishes committed rows, then marks delivered_at; replay is possible.

为什么删掉缓存后，旧查询还能把数据填回来Why an old read can refill after deletion

考虑一次迟到的查询：t=0 读取 v7，t=1 管理请求将链接封禁为 v8 并提交 outbox，t=2 失效处理删除缓存，t=3 慢查询却又 SET 回 v7。只删键，旧数据仍可能回来。因此 Invalidator 要分别通知 Redis 和所有本机缓存，为每个短码保留已见的最高版本下限。

Redis 回填须在同一个 Lua/EVAL 脚本内读取版本下限和当前 value.version，并与传入版本比较。只有传入版本不低于这两者、且 valid_until 尚未到达，才执行 SET；剩余 TTL 由原截止时刻减去当前时间得到，相关键放在同一哈希槽（hash slot）。已见 v8 就拒绝 v7，不能拆成客户端先 GET、再 SET。失效脚本先以 max 提高版本下限，再删除较低版本的缓存值；重复或乱序事件都不能降低下限。本机失效与回填也在同一临界区中比较并修改。如果只比较版本下限、不检查现有缓存值，仍可能把 v9 覆盖成 v8。[7][10]

outbox 保证状态修改和待发送事件同库提交，Relay 持续投递，消费者按短码和版本幂等处理。版本下限的保留期要覆盖最大缓存年龄和回填请求期限，收到 v8 后也不能被乱序的 v7 降级。如果事件漏达、消费者离线或版本下限丢失，继承的 valid_until 仍是最后一道时间上限，版本机制本身不允许无限期使用旧数据。这里借鉴了 Memcache 防止旧值回填的思路，Redis 默认命令并不会自动提供同样的租约协议。[7]

A read starts at t=0 with v7; an owner commits blocked v8 and outbox at t=1; invalidation deletes at t=2; the slow read SETs v7 at t=3. Delete alone permits stale refill. Invalidator independently notifies Redis and all Local caches, retaining a highest-version floor per code. A single Redis Lua/EVAL script reads the version floor and current value.version, compares both with the candidate, and SETs only a nondecreasing version whose valid_until is still in the future; remaining TTL is the original deadline minus current time. Related keys share a hash slot. A client-side GET followed by SET is not atomic. Thus v7 is rejected after v8. The invalidation script first raises the floor with max, then removes a lower-version value. Duplicates cannot lower the floor. Local invalidation and refill perform the same comparison in one critical section. Comparing only the floor, without the current value, could still downgrade v9 to v8. [7][10]

An outbox commits the state change and delivery intent together; a relay retries and consumers are idempotent by code/version. An out-of-order v7 cannot lower an observed v8 floor. Retain floors beyond the maximum cache age and in-flight deadline. If delivery, a consumer, or the floor is lost, inherited valid_until remains the final bound. This borrows the stale-set protection idea from Memcache; default Redis commands do not automatically implement that lease protocol. [7]

命中率怎样改变后端压力How hit rate changes origin pressure

按峰值每秒跳转 11,600 次估算，本机缓存与 Redis 合计命中 95%，Mapping Store 每秒约需读取 580 次；命中率降为 90%，就需约 1,160 次，已经超过 A6 的每秒 800 次上限。因此需要提高命中率、重新评估读取预算，或拒绝超额请求，不能把两种命中率当作等价方案。若 Redis 整层故障，本机缓存也未预热，而且请求访问不同的键，回源需求会回到每秒 11,600 次；本机已有常访问数据时，压力才会小一些。

本机 LRU 无需装下所有短码。假设一个完整缓存对象连同运行时开销约为 1 KB，最常访问的 10 万个短码约占每台 100 MB，21 台合计 21 × 100 MB = 2.1 GB。它能覆盖多少访问，要看实际分布，不能仅凭 LRU 这一名称保证。实际对象大小仍需测量，再按需求选择 LRU、TinyLFU 等淘汰策略。本机缓存用每实例重复保存和失效传播的成本，换取更低的读取延迟。

At the assumed 11.6K peak redirect QPS, a combined 95% local-plus-Redis hit rate leaves about 580 read QPS for Mapping Store; 90% leaves about 1,160. This multiplication is more useful than saying “cache handles scale” because it sizes origin headroom and degradation risk. With cold Local caches and distinct keys, total Redis failure can push origin demand to 11.6K; a warm local set reduces it. A 90% hit rate leaves 1,160/s, above A6’s 800/s cap, requiring better hits, a new budget, or rejection. These hit rates are not interchangeable designs.

Local LRU should not hold every code. If a full runtime cache object costs roughly 1 KB, the hottest 100 thousand codes cost about 100 MB per instance or 21 × 100 MB = 2.1 GB across the tier. Whether that covers the hot head is a measurement, not a property guaranteed by the LRU name. Measure actual object size and choose an eviction policy such as LRU or TinyLFU as needed. The interview point is that local cache buys latency at the cost of per-instance duplication and harder invalidation.

避免缓存集中失效：请求、实例和时间分别处理Three layers of stampede control

  1. 合并同进程请求：对每个短码建立一个进行中的共享结果（in-flight promise），由一个 leader 回源，其余请求等待并复用结果。它只在单个实例内生效，21 台仍可能有 21 个 leader。等待请求的数量和等待时间也要设上限。In-process coalescing: one in-flight promise per code per instance; one leader loads and waiters share. Twenty-one instances can have twenty-one leaders, so this is not one global read. Bound waiter count and waiting time too.
  2. 限制跨进程回源：每台实例都可能有自己的 leader，Redis 仍会收到多个实例的请求，所以 Mapping Store 还需设置并发上限。必要时可以使用短租约锁，但正常缓存命中无需逐次获取全局锁。Cross-process protection: Redis may still see one leader from every instance; cap origin concurrency and use a short lease only when justified, never a global lock on normal hits.
  3. 打散刷新时刻：在 valid_until 之前，随机缩短 TTL，或提前刷新（refresh-ahead）。如果采用先返回旧值、再后台刷新（stale-while-revalidate），仍不能越过默认的 8 秒年龄上限；若要超出，必须重新约定更宽的产品窗口。Time spreading: Use downward TTL jitter and refresh-ahead inside valid_until. Stale-while-revalidate beyond the default eight-second age limit violates revocation budgeting and needs an explicitly wider product window.

故障会多快消耗错误预算Calculate failure scale and error budget together

先算 A12 的零星故障：0.1% 错误最坏会在正常每秒 580 次回源之外，增加 11,600 × 0.001 = 11.6 次，合计 591.6 < 800，仍可有限回源。整层 Redis 故障则按本机缓存冷、请求访问不同键的最坏情况计算：每秒需要回源 11,600 次，只准入 800 次，其余 10,800 次返回 503。这个额度必须由所有实例共享，或分配到各实例执行；若 21 台各放行 800 次，合计就是 16,800 次/秒，保护作用便消失了。

A9 的 99.99% 按符合条件的 active 跳转请求成功率计算。此处假设每天 1 亿次请求都纳入分母，则每天允许失败 100,000,000 × 0.0001 = 10,000 次。峰值每秒失败 10,800 次，10,000 ÷ 10,800 ≈ 0.93 秒就会用完这份日预算。这是按日摊出的课堂比较，不能直接断言一秒故障就违反任意月度 SLO；它说明仅靠回源降级不足以达到目标，还需要缓存副本、故障域隔离和恢复演练。如果按时间比例计算四个 9，则为 0.0001 × 365 × 24 × 60 = 52.56 分钟/年，两种分母不能混用。

Mapping Store 不可用时，创建和状态修改都要停止。新鲜的 active 缓存只可使用到原截止时刻，不能靠延长 TTL 假装满足撤销要求。因依赖故障而无法确认的短码返回 503；新鲜快照明确显示已撤销、到期或封禁时，才返回不带 Location 的 410。恢复缓存时，先保证回源额度和版本判断，再逐步增加流量，全量预热可能再次耗尽预算。

普通号段耗尽只影响自动生成的短码。别名创建和跳转都不访问发号器，但别名创建、跳转缓存未命中时的读取，仍依赖健康的 Mapping Store；新鲜缓存命中则可独立完成跳转。

For A12’s sparse 0.1% errors, add a worst-case 11,600 × 0.001 = 11.6/s to normal 580/s, giving 591.6 < 800. Total Redis outage with cold Local and distinct keys instead demands 11,600/s. Admit 800, return 503 for 10,800/s. Enforce that budget across the tier or allocate shares; twenty-one instances each admitting 800 produce 16,800/s and erase protection.

A9 measures successful eligible active redirects. Assuming all 100M daily requests enter the denominator, 99.99% allows 100M × 0.0001 = 10,000 failures/day. At 10,800 failures/s, that daily allowance lasts about 0.93 seconds. This is a classroom daily-rate comparison, not a claim that one second necessarily violates any monthly SLO. It motivates cache replicas, isolated failure domains, and recovery drills beyond fallback. Time-based four nines gives 0.0001 × 365 × 24 × 60 = 52.56 minutes/year; do not mix the denominators.

安全与滥用：短码不是秘密Security and abuse: a short code is not a secret

威胁模型：系统会被怎样使用Threat model: how the system will be used

枚举：顺序码容易猜到相邻值，六位随机码也只有有限空间。[5] 对云文件和地图的扫描表明，短码不适合作为秘密。私密资源由目标服务负责登录和 ACL 校验；即使撤销短码，也无法收回用户已经知道的 target_url。

钓鱼与封禁：短链隐藏了目标域名。创建时可以同步完成认证、配额和协议白名单等低成本检查，昂贵检测则异步处理，高风险链接先标记为 pending。目标内容和 DNS 日后都可能改变，因此举报和复审仍需能提交 blocked 版本，再通过 outbox 传播。误封还要有审计记录和申诉渠道。

扫描成本：随机 GET 每次换一个短码，都可能触发缓存未命中，1 秒负缓存无法拦住这些不同的键。入口限流和所有实例合计每秒 800 次的回源上限负责保护数据库；超额请求明确返回 429 或 503，依赖错误绝不能缓存为“不存在”。

预览功能的 SSRF：Redirect 不抓取目标页面。如果另加自动抓取器，需要隔离网络，并在 DNS 解析后及每次跟随跳转时检查实际连接 IP，拒绝内网和云元数据地址。校验后还要绑定连接地址，防止 DNS 重绑定，同时限制端口、传输字节、跳转次数和超时时间。

Enumeration: sequential neighbors are guessable and six-character random tokens remain finite. Cloud-file/map scanning in [5] shows a locator is not a secret. Destinations enforce authentication/ACLs; revoking the short code cannot retract an already disclosed target_url.

Phishing and blocks: short links hide domains. Authentication, quotas, and scheme allowlists are cheap inline checks; expensive scans are async and high-risk links begin pending. Content or DNS can change later, so reports/review must commit blocked versions and relay them through outbox. False positives need audit and appeal.

Scan cost: each random new code can miss; one-second negative caching does not stop distinct keys. Boundary limits and the aggregate 800/s cap protect authority. Excess requests get explicit 429/503; dependency failures never become cached absence.

Preview SSRF: Redirect does not fetch destination pages. An optional fetcher needs network isolation, actual connection-IP checks after DNS resolution and every redirect, private/metadata address denial, binding of checked addresses against rebinding, and bounds on ports, bytes, redirects, and timeouts.

安全策略与产品体验的冲突Where safety and product experience conflict

检测更严格，会增加创建延迟和误封；预览页会多一次点击，封禁也可能影响已经传播的正常活动链接。因此可以分层处理：低成本规则同步拒绝，昂贵扫描异步完成，高风险链接先进入预览或 pending 待审状态。封禁附带原因和审计记录，并提供申诉渠道；安全状态经高优先级失效事件尽快传入读取侧。

Stricter detection raises create latency and false positives; preview adds a click; blocking can damage a legitimate campaign already in circulation. Do not run every expensive check synchronously. Reject cheap rules inline, complete expensive scans asynchronously, place high-risk links into preview or pending state, attach reason/audit/appeal to blocks, and propagate safety state through a high-priority invalidation path.

为什么先用关系库，何时换 KV？Why start with SQL; when would KV help?先看预算是否匹配：每秒 116 笔创建事务占 500 预算的 23.2%；95% 缓存命中后，每秒读取约 580 次，低于 800。压测混合负载，核对存储和事务需求后，再决定是否改用 KV。按键点查也仍需保证幂等记录与业务写入的原子性。It fits the assumed budgets: 116 create TX/s is 23.2% of 500, and 95% hits leave 580 reads/s below 800. Validate mixed load, storage, and transactions before changing to KV; point lookups do not remove retry atomicity.
过期数据怎么清？How is expired data removed?每次读取都检查 expires_at，不等待后台清理来保证到期失效。后台分批清理目标 URL 数据或归入冷存储，短码保留紧凑的删除标记，别名默认不复用。否则删掉唯一记录后，历史短链可能指向新的创建者。长期保留删除标记所需的空间要单独估算。Reads enforce expires_at before cleanup. Reclaim URL payloads or cold records in batches but retain compact code tombstones and do not reuse aliases. Removing the unique row permits an old URL to point to a new owner; budget long-lived tombstones separately.
单个热门短码让 Redis 压力过大怎么办？One code overheats Redis?先在各实例缓存常访问的数据，再用进程内请求合并，以及不超过 valid_until 的提前刷新。复制热点条目时仍需同步版本并预热，随机加后缀不会自动解决失效传播。若采用边缘缓存，还要重新约定统计方式与撤销窗口。Use per-instance Local hot sets, coalescing, and refresh-ahead inside valid_until. Replicated hot entries need versioning and prewarming; random suffixes do not solve invalidation. Edge caching needs new analytics/freshness semantics.
全球部署怎么演进？How does this go global?先采用单写区和就近的区域读取流程改善延迟。异步复制的延迟必须计入撤销窗口，各区不能给旧值重新计算新鲜度。需要多区写入时，再分配互不重叠的号段；别名和幂等记录仍需由权威区域或跨区条件写入解决竞争，并明确网络分区时拒绝哪些操作。One write region and nearby read paths first address latency. Include replication lag in revocation; regional rereads cannot relabel stale snapshots as fresh. Multi-region writes need disjoint ranges and authoritative or cross-region conditional writes for aliases/idempotency, with explicit partition refusals.
点击统计必须恰好处理一次吗？Exactly-once analytics?先确认统计用途。趋势看板可接受有界损失，已持久化的事件可以重放并按 event_id 去重，但响应与发布之间仍可能丢事件。若计数准确性要求更高，就需要持久日志和对账，增加相应成本；仅更换消息队列的说法无法提供这个保证。Start with the use case. Trend dashboards can accept bounded loss; durable events replay with event-ID dedupe, but a response/publish gap still loses events. Stronger counts require durable logging and reconciliation, not merely renaming the queue.
流量再增加 10 倍，哪里先超预算？Traffic grows 10×?峰值读取变为每秒 116,000 次，每台仍按 600 QPS 预算，正常需 194 台，N−1 需 195 台。即使命中 95%，每秒仍要回源 5,800 次，是 800 预算的 7.25 倍；创建事务每秒 1,160 次，也超过 500。先重新测量容量和命中率；若分片，还需解决跨片幂等的原子性。Peak reads become 116,000/s, requiring ceil(116,000/600) = 194 normally, or 195 for N−1 at the same budget. At 95% hits, 5,800 origin reads/s is 7.25× 800; 1,160 create TX/s also exceeds 500. Remeasure capacity/hits; sharding adds cross-partition retry atomicity, not just more store drawings.

紧凑码与分配成本Compact codes and allocation cost每秒创建 116 次，暂不因吞吐分片。号段减少协调，但会留下空洞，也容易枚举；最大已分配 ID 必须持久化。116 writes/s does not yet force sharding; ranges reduce coordination but allow gaps and enumeration, and require durable high-water.

跳转延迟与统计完整Redirect latency and analytics completeness302 不等待 MQ。no-store 让遵循标准的 HTTP 缓存不保存并复用本次响应，统计事件仍可能丢失。302 does not wait for MQ; no-store prevents reuse by compliant HTTP caches, but does not guarantee lossless analytics.

最后可以这样总结：创建时，用同库事务和唯一约束处理并发重试；跳转时，由 Redirect 依次查两级旁路缓存，未命中再查权威库，响应经入口逐跳返回。撤销时，用 outbox 传播事件、版本下限拒绝旧回填，并让两级缓存沿用原 valid_until。故障时，所有实例合计每秒最多回源 800 次；统计则放入有界的异步流程。Final twenty seconds: one transaction and unique constraints settle concurrent creates. Redirect queries two look-aside tiers and authority on miss, returning through the gateway. Revocation uses outbox, version floors, and inherited valid_until. Total failures cap origin at 800/s; analytics is bounded and async.
