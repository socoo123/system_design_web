设计 API 网关 Design an API gateway

约 40 分钟 · 前置：Ch03、Ch04 · 用 6 组演进图讲清请求与故障 ~40 min · after Ch03, Ch04 · 6 request and failure evolution decks

本章要点：把身份、准入和重试看清楚Three decisions to retain

  • 身份和策略保持一致：网关为每次请求固定一份配置快照，只从受控验证结果取得身份，并在每一跳认证对端。
  • 判定未知，也要限制流量：限流超时不代表额度耗尽；只有策略明确允许的安全只读请求，才能使用固定实例池的紧急预算。
  • 所有尝试共用一个截止时间：重试还要满足请求可重放、累计信用足够、流槽可用和探针规则，才能限制下游负载。
  • One identity and policy context: pin a snapshot per request; derive identity only from controlled verification and authenticate each hop.
  • Bound uncertainty: admission timeout is not quota exhaustion; only approved safe reads get a fixed-pool emergency budget.
  • One deadline, several retry gates: fixed expiry, replayability, cumulative retry credits, active-stream caps and probes bound load.

30 秒开场：先说清网关负责什么The opening: define the ingress boundary

本例设计单地域的业务 API，峰值为每秒 1 万次请求。请求沿 Client → L4 LB → Gateway → Orders 处理，响应沿原路逐跳返回。网关负责验证凭证、检查路由级权限、执行配额判定和代理请求；Orders 负责判断订单归属，并持久化提交交易。四台可替换的网关缓存已验证的配置和密钥，控制面负责发布策略。只有端侧确实需要聚合数据时，再加入面向端的聚合层（BFF）。

先问三个会改变设计的问题：凭证由谁签发，哪些接口依赖精确配额，客户端是否需要不同的页面数据。登录、短信和支付不能沿用公开列表的降级策略。网关也不能替代业务事务，加入网关本身并不要求把服务拆得更细。

One-region business APIs at 10,000 peak requests/s. Client → L4 LB → Gateway → Orders, with hop-by-hop responses. Gateway owns credentials, route permission, quota and forwarding; Orders owns object authorization and durable transactions. Four interchangeable gateways cache validated policy and keys; the control plane publishes changes. Add a BFF when client aggregation earns it.

Clarify issuer, routes requiring precise quota, and differences in page data. Login, SMS and payments cannot inherit public-list fallback policy. A gateway neither replaces business transactions nor requires fine-grained service decomposition.

先估算容量，再展开设计假设Capacity first, detailed assumptions second

先按教学假设估算实例数。每台网关的可用能力为 4,000 QPS，已经计入策略开销和预留余量。按 ⌈10,000÷4,000⌉+1 计算，需要4 台。失去一台后，还剩每秒 12,000 次的可用预算，峰值占其 83.3%；失去两台则只剩 8,000 QPS，因此可用区或地域故障要另行估算。

再按十进制单位估算网络流量：请求体平均 2 KB，响应体平均 4 KB。网关池两侧都要收发请求和响应，所以每个方向的消息体流量合计为 10,000×(2+4) KB=60 MB/s=480 Mb/s。四台均分时，每台每方向为 120 Mb/s；只剩三台时为 160 Mb/s。若使用缓存中的密钥验签，每次耗费 0.2 ms CPU，全池共需 2 核的验签算力。协议、TLS、插件、连接和重试的实际开销仍需测量。

Teaching assumptions: 4,000 usable QPS/instance already includes policy cost and reserve. ceil(10,000/4,000)+1=four; one loss leaves 12,000, with peak using 83.3% of that usable budget. Two losses leave 8,000, so zone/region loss needs separate sizing.

With decimal 2 KB request and 4 KB response bodies, both sides of the pool total 10,000×(2+4) KB=60 MB/s=480 Mb/s per direction. Each of four handles 120 Mb/s per direction, or 160 Mb/s with three. Cached-key validation at 0.2 ms CPU adds two aggregate cores. Measure protocol, TLS, plugins, connections and retries.

整体请求路径：网关只读取本地快照The complete path: local snapshots in the data plane

图 D1 中的 Gateway 代表四个实例。这里的“无状态”是说，另一台实例可以依据同一份外部权威记录继续服务；连接、缓存和在途请求仍是本地状态。控制面发布路由、配额和密钥来源，数据面负责转发业务请求，两者的故障域分开。

本地启用新配置时，原子替换的是一份不可变对象的引用。网关先检查未匹配时默认拒绝、路由是否有歧义、目标集群、配额和安全有效期，再切换引用。每个请求只读取一次引用，后续路由匹配、鉴权、额度判定和重试都沿用同一对象。旧对象要保留到在途请求结束。这个原子切换只发生在单个进程内，不是跨实例事务；新实例如果没有可用配置或密钥，就保持未就绪。

控制面暂时失联时，可以使用最后一份有效快照，但安全撤销也会因此延迟传播。安全策略一旦到期，就要拒绝请求，不能无限沿用。发布时先灰度，检查各实例实际应用的状态，再逐步推广。Envoy 1.36 xDS 的 ACK 表示单个资源有效且有应用意图，并不证明已经成功应用；NACK 也不等于所有资源都未采用。[7]

部署时先停止接收新流量，再排空在途的 HTTP/2 流。进程还活着，不能证明它已经具备处理业务请求的条件。

Gateway in D1 represents four instances. Stateless means another can serve from the same external authority; connections, caches and in-flight work remain local. The control plane publishes routes, quota and key sources; the data plane forwards business traffic, with separate failure domains.

Local activation publishes one immutable reference: validate default deny, route ambiguity, clusters, quota and security expiry, then atomically replace the reference. Each request reads it once and uses that object for matching, authentication, admission and retries. Retain old objects for in-flight work. This local atomicity is not a cross-instance transaction; new instances without usable policy/keys stay unready.

Last-good snapshots survive a control-plane outage at the cost of delayed revocation. Expired security policy rejects instead of remaining valid forever. Canary policy, inspect actually applied versions, then expand. In Envoy 1.36 xDS, ACK means isolated resource validity and intent, not successful application; NACK need not mean total rejection. [7] Drain traffic and existing HTTP/2 streams; process liveness is not readiness.

认证上下文：先清理外部身份头，再验证和传递身份Authentication context: strip, validate, then propagate

先确定路由 route_id 和适用的 audience，再验证凭证。令牌中的 issuer 只能用于选择预先允许的验证配置，未经验证的声明不能授予权限。密钥只从固定、可信的 JWKS 来源获取，不能跟随令牌中的任意 jku/x5u 地址。[1] 验证内容包括算法、签名、issuer、audience、exp/nbf 和用途；采用 RFC 9068 时，typ 接受 at+jwt 或 application/at+jwt。ID token 不能因为同样采用 JWT 格式，就替代 API access token。[2]

验证得到用户身份 subject 后，还要依据该签发者获准的租户映射确定 tenant；重复或有歧义的凭证直接拒绝。无效凭证返回 401，并附 Bearer challenge；身份已验证但缺少所需 scope 时返回 403；验证依赖不可用时返回 503。Bearer 凭证通过 TLS 传输，日志中不记录原始凭证。[3]

Determine route_id and audience, then validate credentials. An issuer can only select preallowed verification policy; unverified claims grant no authority. Use fixed trusted JWKS locations, never arbitrary token jku/x5u URLs. [1] Validate algorithm, signature, issuer, audience, exp/nbf and purpose. Under RFC 9068 accept typ at+jwt or application/at+jwt. A JWT ID token is not an interchangeable API access token. [2]

Derive subject from validation and tenant from the issuer's allowed tenant mapping. Reject duplicate/ambiguous credentials. Invalid credentials return 401 with a Bearer challenge; insufficient scope returns 403; unavailable validation dependencies return 503. Protect bearer tokens with TLS and exclude raw credentials from logs. [3]

实现 1：为一次请求固定快照，建立受控身份上下文Implementation 1: a pinned snapshot and controlled identity

# Pseudocode: one HTTP request; adapters below are part of the contract.
handle(raw, transport):
  deadline = local_deadline_at_receipt(300_ms)
  snap = snapshots.get()                 # one immutable local reference
  if snap is absent or snap.security_expired(): return 503
  req = parse_once_and_canonicalize(raw, snap.normalization)
  route = snap.match(req.host, req.method, req.path)
  if route is absent: return 404
  client_ip = transport.original_peer_from_trusted_LB_listener()
  # Ignore public Forwarded/X-Forwarded-*; trust no arbitrary chain prefix.
  headers = req.headers.remove_reserved_identity_forwarding_and_canary()
  token = req.require_single_bearer_token()
  try:
    auth = verify_access(token, snap.allowed_issuers, route.audience)
    # Trusted JWKS only; alg/typ/signature/iss/aud/exp/nbf + tenant mapping.
  catch InvalidCredential: return 401_with_bearer_challenge
  catch ValidationDependencyUnavailable: return 503
  if not auth.scopes.contains_all(route.scopes): return 403
  target = route.choose(auth.tenant, auth.subject, snap.rollout_salt)
  ctx = InternalContext(auth.tenant, auth.subject, route.id, snap.version)
  # Local object, never reconstructed from an inbound identity header.
  admission = admit_once(ctx, route, deadline.remaining())
  if admission.denied: return admission.http_error
  if deadline.expired(): return 504          # ALLOW cannot extend time
  # Pin snap, route, target version and ctx for the whole request/retry.
  return proxy(req, target, headers, ctx, deadline)
  # Only Gateway-authenticated mTLS reaches the internal listener.
  # BFF preserves ctx over another authenticated hop; Orders checks ownership.

这段伪代码用来说明入口契约，尚未实现 HTTP 解析、JWT 密码学和网络适配器。解析器必须用同一套规则处理 host、method 和 path，并拒绝有歧义的编码或非法分隔符，避免认证和代理转发因二次解码而指向不同资源。外部请求中的内部身份头、Forwarded/X-Forwarded-* 和 canary 头都要清理，InternalContext 只能由验证器产生。即使已经认证服务对端，也要限制它可以代表哪些用户，BFF 不能任意提升权限。

代理链信息本身不能证明身份。RFC 7239 §8.1 指出，客户端也能修改 Forwarded。[10] 本例只信任受保护的 LB listener 提供的原始来源元数据，例如仅允许已登记 LB 使用的 PROXY 协议通道；公网传来的同名头全部忽略。如果 LB 没有保留可信的原始地址，就无法可靠取得客户端 IP，不能把 LB 地址当成用户身份来分配公平配额。Gateway→BFF→Orders 的每一跳都要认证对端、限制入口，Orders 还要检查对象归属。端到端验证令牌或签署上下文，是另一种可选的信任设计。

遇到未知 kid 时，网关合并刷新请求，并将每实例刷新频率限制为每秒最多一次，四台合计最多 4 次/秒。用于记录查无此密钥的负缓存也要限制容量和 TTL，不能让攻击者用任意 kid 把缓存填满。已知密钥只能在获准的有效期内使用。轮换时先发布新公钥，再签发新令牌；旧密钥要保留到旧令牌寿命与允许的时钟误差都已覆盖。依赖不可用时不能跳过验签。5 分钟令牌寿命、0.2 ms 验签耗时和刷新率都是教学假设，尚未测量真实身份提供方（IdP）。

This is pseudocode: HTTP parsing, JWT cryptography and network adapters are not implemented. One parser policy normalizes host/method/path and rejects ambiguous encoding/separators, preventing authentication and forwarding from decoding different resources. Clear reserved identity, Forwarded/X-Forwarded-* and canary headers at the external boundary. Only the verifier creates InternalContext. Authenticated intermediaries must also be restricted in whose authority they may assert.

A forwarding chain is not a credential. RFC 7239 §8.1 notes that clients can modify Forwarded. [10] This design trusts original-peer metadata only from a protected LB listener, such as a PROXY-protocol channel restricted to registered LBs; ignore public forwarding headers. Without trusted original-peer metadata, client IP is unavailable: LB IP is not a fair user identity. Authenticate and restrict every Gateway→BFF→Orders hop, then enforce object ownership in Orders. End-to-end token validation or signed context is an alternative trust design.

Coalesce unknown-kid refreshes and cap at one/s/instance, four/s across the pool. Bound negative-cache size and TTL against arbitrary attacker keys. Cached keys have a usability expiry. Publish new public keys before issuance and retain old ones through token life plus allowed skew; dependency failure never skips verification. Five-minute tokens, 0.2 ms and refresh rates are unmeasured teaching assumptions.

限流三种结果：允许、拒绝和未知Three admission outcomes: ALLOW, DENY, UNKNOWN

限流键采用已验证 (tenant,subject,method+route_id) 的无歧义元组编码，不能直接拼接字符串，也不能让任意 URL 参数无限创建新桶。A7 的桶容量为 40、每秒补充 20 份令牌，因此可以先突发 40 次，随后持续速率趋近每秒 20 次；四台各自发放完整额度，就会放大成每秒 80 次、突发 160 次。共享 Redis 用单键短脚本，原子完成补充、判断、扣除和设置闲置 TTL。脚本执行期间会阻塞其他工作，集群中的多键操作还要求键共址。[4] 具体 Lua 与时间、TTL 条件见 Ch04。

正常每秒判定 1 万次、每次耗时 2 ms，约有 20 次判定同时在途。100 万个活跃桶×100 B=100 MB，保存两份为 200 MB；这只是键和值的容量下限，分配器、复制、索引和恢复开销另计。用户公平配额不能替代服务总容量保护：10 万人各自每秒发出 20 次请求，合计仍达 200 万 QPS，因此还要限制总速率、活动请求和限流客户端的在途数量。

Use unambiguous tuple encoding of validated (tenant,subject,method+route_id), not raw string concatenation or arbitrary URL parameters. Capacity 40 with 20/s refill admits a burst of 40 then approaches 20/s. Four full local quotas would grant 80/s and burst 160. One short Redis script atomically refills, checks, debits and updates idle TTL; scripts block other work, and multi-key cluster operations need colocation. [4] See Ch04 for Lua and clock/TTL conditions.

10,000 decisions/s at 2 ms imply about 20 in flight. One million buckets×100 B gives 100 MB/copy or 200 MB for two, only a key/value floor excluding allocation, replication, indexes and recovery. User fairness does not protect total capacity: 100,000 users at 20/s still produce two million QPS. Cap aggregate rate, active work and quota-client concurrency too.

实现 2：限流判定未知时，按明确策略选择降级Implementation 2: explicit fallback on an unknown decision

# Pseudocode: one decision/request; UNKNOWN is not quota exhaustion.
admit_once(ctx, route, remaining):
  if remaining <= 0: return ERROR(504)
  key = encode_tuple(ctx.tenant, ctx.subject, route.method_and_id)
  verdict = quota.take_once(key, timeout=min(5_ms, remaining))
  # Server adapter: short atomic refill/check/debit + idle TTL (see Ch04).
  # timeout/transport error -> UNKNOWN; server may already have debited.
  # No automatic retry/refund; a late result cannot forward this request.
  if verdict.kind == ALLOW: return ALLOW
  if verdict.kind == DENY: return ERROR(429, retry_after=verdict.wait_hint)
  if not route.explicit_public_safe_read: return ERROR(503)
  if not deployment.fixed_pool_policy_valid(): return ERROR(503)
  # Four non-overlapping owners; new/restarted owner starts EMPTY.
  # At construction: tokens=0, last=monotonic_now(); cap=100, rate=100/s.
  # Existing buckets never reset when Redis fails/recovers.
  if emergency_bucket.try_take(monotonic_now()): return ALLOW_DEGRADED
  return ERROR(503)                     # dependency/fallback capacity failure

# emergency_bucket.try_take, under one process-local mutex:
#   elapsed = max(0, now - last); last = max(last, now)
#   tokens = min(100, tokens + elapsed * 100_per_second)
#   if tokens < 1: return false
#   tokens -= 1; return true
# This is an aggregate emergency cap, not a distributed user quota or ledger.

只有明确拒绝（DENY）才返回 429。本章附上的 Retry-After 是等待提示，不会为下次请求预留令牌；RFC 6585 §4 允许使用此头，但不指定计数算法。[5] 超时得到 UNKNOWN 时，Redis 可能已经扣额，只是回包丢失，因此不自动重扣，也不退款，迟到结果也不能改变本次请求已选的路径或触发转发。支付、短信和登录返回 503；只有策略明确允许的公开安全读取，才尝试使用紧急总桶，紧急额度耗尽时仍返回 503。

每秒 400 次的持续速率依赖部署约束。四个不重叠的所有者各持一个容量 100、每秒补充 100 份令牌的本地桶。新建或重启的桶从空桶开始，Redis 失败或恢复都不能将它重置。部署控制器要等旧所有者停止发放额度，才能移交份额；降级期间不扩池，也不能让滚动部署中的新旧所有者重叠发放。无法确认所有权时，禁用降级。在任意 Δ 秒内，全池合计最多放行 400Δ+400 次，但失去精确的用户公平性。反复重启赠送满桶，或同时保留八个所有者，都会破坏这个上界。预分配租约或全部拒绝，是另外两种选择。

紧急桶只在进程内保护流量，不是分布式账本。Redis 异步复制切换也可能丢失已扣额度，要求严格扣费或不能超卖的库存操作不能依赖它保证正确性。[11] 全球配额需要权威协调，或保守分配地域份额；本章只讨论单地域的流量保护。

Only DENY returns 429. Our Retry-After is a hint, not a reserved token; RFC 6585 §4 permits it without mandating a counting algorithm. [5] UNKNOWN may mean debit succeeded but the reply was lost. Do not automatically retry or refund, and never let a late result trigger another forward. Payments, SMS and login return 503. Only explicitly approved public safe reads try the emergency aggregate bucket; exhaustion still returns 503.

400/s depends on deployment ownership. Four nonoverlapping owners each get capacity 100 and refill 100/s. New/restarted buckets start empty and never reset on Redis failure/recovery. The deployment controller transfers a share only after its old owner stops admission; no scale-out or overlapping rollout during fallback. Uncertain ownership disables fallback. Any Δ-second interval admits at most 400Δ+400, without precise user fairness. Repeated full-bucket restarts or eight simultaneous owners break the bound. Preallocated leases or total rejection are alternatives.

This local emergency cap is not a distributed ledger. Async Redis failover can lose debits; strict billing/inventory cannot rely on it. [11] Global quota requires authority or conservative regional shares. This chapter covers regional load protection.

BFF：在限制聚合规模的前提下减少端侧往返BFF: bounded aggregation for fewer round trips

只有移动页面确实需要统一返回 Orders、Profile 和 Comments 的数据时，才加入 Mobile BFF。Gateway 保留共享认证和入口配额；BFF 接收可信上下文，让各分支在同一个剩余期限内并行读取，再沿原路径返回页面 JSON。按 A10，同一次预算示例串行需要 80+40+120+20=260 ms，并行需要 max(80,40,120)+20=140 ms。这里没有给出各分支尾延迟的联合分布，不能取各服务 p99 的最大值，当作页面 p99。

本例明确把 Comments 设为可选分支，失败就在 BFF 结束，并标记为 unavailable；Orders 则是必需分支，不能用空数组把失败伪装成“没有订单”。聚合还要限制分支数量、响应大小、分支并发和缓存。也可以由客户端多次调用，或建立专门的读模型，分别付出网络往返成本，或数据同步与陈旧的代价。退款、库存和跨服务补偿需要持久的业务编排，不能悄悄放进页面聚合。

Add Mobile BFF only when a page needs one data shape across Orders, Profile and Comments. Gateway retains shared authentication and quota. BFF accepts trusted context, fans out under one remaining deadline, and returns page JSON along the original path. A10's single-run example is 260 ms serial versus 140 ms parallel. Maximum service p99 is not page p99 without the joint tail distribution.

Comments is optional: mark it unavailable at BFF. Orders is required: an error cannot masquerade as an empty order list. Cap fan-out, branch concurrency, response size and caches. Direct client calls or a dedicated read model trade network round trips against synchronization/staleness. Inventory, refunds and compensation require durable business orchestration, outside page aggregation.

版本路由：每次请求固定快照，回滚改变后续路由Version routing: pin a snapshot; rollback affects future work

路由使用同一套规范化 host、method 和 path，并规定明确优先级：具体规则先于默认规则，未匹配的入口请求默认拒绝或返回 404。[9] 网关用可信身份中的 tenant、subject 和本轮发布的 salt 做稳定分组，把 10% 用户导向 v2。只有每人请求速率相等，才能估算为 10,000×10%=1,000 QPS；热点用户会改变实际流量比例。客户端自填的 x-canary 不授予内部版本权限。

每次请求固定路由 route、策略版本 policy_version、用户分组 cohort 和目标版本，重试也只能选择该版本内的兼容实例。v43 回滚改变后续路由，把新请求导向 v1，但部分网关可能仍持 v42。观测时要检查各实例实际应用的版本和各版本错误率，避免全站平均值稀释问题。跨版本数据兼容由服务负责，网关调整权重不能撤销已经提交的写。若 v2 创建订单超时，不能自动换 v1 重放，而应沿用原业务键查询结果或对账。

Match one normalized host/method/path with explicit precedence, specific rules before defaults, and deny/404 unmatched ingress. [9] Hash verified tenant, subject and rollout salt for a stable 10% user cohort on v2. Only equal per-user rates imply about 1,000 of 10,000 QPS; hotspots skew traffic. A public x-canary header grants no internal-version access.

Pin route, policy_version, cohort and backend version per request; retries may select only compatible instances of that version. Rollback v43 changes future routing to v1 while some gateways may retain v42. Observe actually applied versions and version-specific errors. Services own data compatibility; routing weights cannot undo committed writes. Never replay an uncertain v2 order creation onto v1 automatically: query/reconcile using the original business key.

固定请求期限，用重试信用和熔断探针约束负载Fixed deadlines, retry credits and breaker probes

实现 3：截止时间不重算，重放请求须满足条件Implementation 3: fixed expiry and conditional replay

网关收包时，用本地单调时钟建立截止时间 end=received+300。策略处理结束后，再固定 upstreamEnd=min(now+240,end−40)。连接、排队、读取响应、重试和退避都消耗同一个窗口，不能每一层重新给足 300 ms。下面的 Java 17 代码是完整源码的教学节选，不是 HTTP 客户端。可查阅完整源码和运行/适配器契约。

单调时钟的绝对截止值只能在同一时钟域内比较，不能把一台机器的 nanoTime 传到另一台机器比较。[12] 跨机可以传递受保护的剩余时长，由下游在接收时建立本地截止时间，并扣除已知的传输和排队上界。如果 UTC 时钟误差界受到持续监测，也可以传递经过认证的 UTC 截止时间，并保守扣减误差。没有这些边界时，只能承诺网关在总截止时间停止等待，下游可能更晚结束；取消不能撤销已经提交的事务。

At receipt establish end=received+300 using a local monotonic clock. After policy, pin upstreamEnd=min(now+240,end−40). Connections, queueing, response reads, retries and backoff share that window. This Java 17 teaching excerpt is from the complete runnable core; it is not an HTTP client. See execution and adapter contracts.

Compare absolute monotonic stop values only within one clock domain; never compare nanoTime across hosts. [12] Send protected remaining duration; the receiver creates a local deadline and subtracts a known transmission/queueing bound. With monitored UTC error bounds, an authenticated UTC expiry can also be reduced conservatively for skew. Without such bounds only Gateway's own stop-waiting deadline is guaranteed; downstream may finish later. Cancellation cannot undo a committed transaction.

record Deadline(long endMs, long upstreamEndMs) {
    static Deadline afterPolicy(long receivedMs, long nowMs) {
        long end = receivedMs + 300;
        return new Deadline(end, Math.min(nowMs + 240, end - 40));
    }
    long nextAttemptMs(long nowMs, long perTryMs) {
        return Math.max(0, Math.min(perTryMs, upstreamEndMs - nowMs));
    }
}
enum Failure { RESET, CONNECT, TIMEOUT, HTTP_STATUS, CLIENT_CANCEL }
record Replay(String method, boolean bufferedBody, boolean responseStarted,
              int attempts, Failure failure) {}
static boolean mayRetry(Replay r, Deadline d, long nowMs, long delayMs) {
    // This gateway chooses the conservative GET/HEAD subset.
    boolean methodOk = r.method.equals("GET") || r.method.equals("HEAD");
    boolean transientFailure = r.failure == Failure.RESET
            || r.failure == Failure.CONNECT || r.failure == Failure.TIMEOUT;
    return methodOk && r.bufferedBody && !r.responseStarted
            && r.attempts == 1 && transientFailure && delayMs >= 0
            && d.nextAttemptMs(nowMs + delayMs, 80) >= 20;
}

代理不得自动重试非幂等请求。RFC 9110 §9.2.2 使用的要求是 MUST NOT。[6] 本网关更保守，只允许 GET/HEAD；即使 PUT/DELETE 在 HTTP 语义上幂等，也不会自动获得重试资格。POST 带有 Idempotency-Key，也不改变本章的代理策略。应用客户端如果按业务契约恢复 POST，服务必须持久保存幂等键与参数、执行中状态、结果和去重保留期的绑定关系；这属于业务恢复。

允许额外尝试还要同时满足：首次失败属于配置允许的暂时传输故障或超时，尚未向客户端发送任何响应，完整请求体已在有界内存或磁盘中保存、可以重放，且原本地传输流已经终止。每个请求最多增加一次尝试，本例不会因 429/503 或其中的 Retry-After 自动重试。示例为首次 80 ms、含抖动的退避最多 20 ms、第二次 80 ms，再加策略处理 20 ms，共 200 ms。退避结束后仍要重算预算，至少剩余 20 ms 才能尝试，单次取 min(80,remaining)。如果已经开始发送响应，就只能终止流，不能伪装成一份新的 504。

A proxy MUST NOT automatically retry non-idempotent requests under RFC 9110 §9.2.2. [6] This gateway is stricter: only GET/HEAD qualify. HTTP-idempotent PUT/DELETE are not automatically eligible, and Idempotency-Key does not change our POST policy. Application clients may recover a POST only under a business contract that durably binds key, parameters, in-progress state, outcome and retention; that is business recovery.

Require a configured transient transport failure/timeout, no response sent to the client, a fully replayable bounded memory/disk body, and a terminated prior local stream. Allow only one extra attempt. This example does not automatically retry HTTP 429/503 or act on Retry-After. Two 80 ms attempts, at most 20 ms jittered backoff and 20 ms policy total 200 ms. Recheck after waking; require at least 20 ms, and allocate min(80,remaining). Once a response has started, terminate the stream instead of fabricating a fresh 504.

实现 4：先取得重试信用，再占用真实资源Implementation 4: retry credit and actual resource occupancy

static final class RetryBudget {
    private int remainder, credits;       // EMPTY on process start
    synchronized void originalAdmitted() { // exactly once, never for a retry
        if (++remainder == 20) {
            credits = Math.min(125, credits + 1);
            remainder = 0;
        }
    }
    synchronized boolean takeRetry() {
        if (credits == 0) return false;
        credits--;
        return true;                       // never refund consumed credit
    }
}
static final class ActiveStreams {
    private final Semaphore slots = new Semaphore(800);
    StreamPermit start() {              // no hidden queue
        return slots.tryAcquire() ? new StreamPermit(slots) : null;
    }
}
static final class StreamPermit {
    final Semaphore slots;
    final AtomicBoolean released = new AtomicBoolean();
    StreamPermit(Semaphore slots) { this.slots = slots; }
    void transportTerminated() {
        if (released.compareAndSet(false, true)) slots.release();
    }                                    // timer expiry alone is not terminal
}

每个实例每准入 20 个原始请求，就获得一份额外尝试的信用。信用初始为空，最多积存 125 份，用掉后不退还，重试本身也不赚取信用。因此，从每个进程启动算起，Rᵢ≤⌊Oᵢ/20⌋；合并所有进程与代次，仍有 R≤O/20，重启只会丢失额度。固定四台最多积存 500 份突发信用。每秒准入 1 万个原始请求时，稳态约每秒赚取 500 份信用，总尝试约 10,500 次/秒；这不是任意一秒的硬上限，因为还能花掉之前的积存。若需要硬速率上限，要另设总尝试桶。

本章假设每台最多有 800 条本地活动上游流，这不是从 CPU 自动推导出的产品默认值。慢路径有 10,000/s×0.24s=2,400 条在途，四台均分约每台 600 条，三台则约每台 800 条；按完整 300 ms 请求计算，约有 3,000 个在途请求。HTTP/2 流与 TCP 连接数量不同。拿不到流槽许可（permit）时，立即返回 503，不暗中排队。只有本地流实际终止或关闭后，才能释放许可；逻辑超时先返回客户端，并不表示槽位已空。终止回调还要保证幂等，避免重复释放。远端业务仍可能继续执行，因此服务端也必须限制并发。

重试按这个顺序集成：确认旧本地流终止 → 有界退避 → 重算期限并检查客户端取消 → 消耗重试信用 → 尝试占用流槽 → 通过熔断准入 → 发送前立即再次检查期限。后两道门拒绝时，释放尚未使用的流槽，但不退还信用。探针不重试；已经获准、却在发送前放弃的探针，按失败完成。每个原始请求只计一次 O。三层各尝试两次，会放大成 2³=8 次，因此 Gateway、BFF 和客户端要约定由哪一层负责重试。

Each instance earns one credit per 20 admitted originals, starts empty, stores at most 125, never refunds a consumed credit, and earns none from retries. Since each process start, Rᵢ≤floor(Oᵢ/20); summing all processes/epochs preserves R≤O/20. Restart only loses credit. Four fixed instances store at most 500 burst credits. At 10,000 original QPS, steady-state earning is about 500/s and attempts about 10,500/s; this is not an arbitrary one-second ceiling. Add a total-attempt rate bucket if required.

800 local active upstream streams/instance is our assumption, not a product default. 10,000/s×0.24s=2,400 slow-path work, about 600 each with four or 800 with three; full 300 ms requests imply about 3,000. HTTP/2 streams are not TCP connections. Reject immediately with 503 when no permit is available. Release only when the local stream actually terminates/closes, not merely when a timer returns an error to the client; duplicate terminal callbacks cannot release twice. Remote business execution may persist, requiring server-side limits too.

Integrate in order: terminate the prior stream → bounded backoff → recheck expiry/cancellation → consume retry credit → acquire stream slot → breaker admission → recheck expiry immediately before dispatch. Later rejection releases an unused slot without refunding credit. Probes never retry; an abandoned admitted probe completes as failure. Count each original once. Three layers each trying twice can yield 2³=8 attempts: agree on one retry owner.

实现 5：每实例一条探针，迟到结果不能改变新状态Implementation 5: one local probe; fence late completions

    final LongSupplier clock;
    Breaker() { this(elapsedClock()); }
    Breaker(LongSupplier monotonicMs) { this.clock = monotonicMs; }

    synchronized Ticket enter() {
        long nowMs = clock.getAsLong();  // observe time AFTER acquiring monitor
        if (state == State.OPEN) {
            if (nowMs < retryAt) return null;
            state = State.HALF_OPEN; epoch++;
        }
        if (state == State.HALF_OPEN) {
            if (probeActive) return null;
            probeActive = true;
            return new Ticket(epoch, true);
        }
        return new Ticket(epoch, false);
    }
    synchronized void complete(Ticket t, boolean ok) {
        long nowMs = clock.getAsLong();  // terminal observation, not event time
        if (t.done) return;
        t.done = true;
        if (t.epoch != epoch) return;       // ignore a stale completion
        if (t.probe) {
            probeActive = false; epoch++; samples.clear();
            state = ok ? State.CLOSED : State.OPEN;
            if (!ok) retryAt = nowMs + 5000;
        } else if (state == State.CLOSED) {
            samples.addLast(new Sample(nowMs, ok));
            while (!samples.isEmpty() && nowMs - samples.peekFirst().observedMs >= 10000)
                samples.removeFirst();
            long failed = samples.stream().filter(s -> !s.success).count();
            if (samples.size() >= 100 && failed * 2 >= samples.size()) {
                state = State.OPEN; retryAt = nowMs + 5000; epoch++;
                samples.clear();
            }
        }
    }

这里实现的是可选的健康策略。在本地最近 10 秒内，于锁内观察到的终止样本至少有 100 个，且失败率≥50%，才进入 Open。等待 5 秒后进入 Half-open，每实例只允许一条探针，四台最多四条。限流或并发准入拒绝不计为健康失败；传输故障和超时须明确分类，业务 4xx 不计。探针成功立即回到 Closed，恢复后的流量由速率和并发门限制；探针失败则重新等待 5 秒。

代次 epoch 会在开路、探针完成等状态转换时递增，使旧代的完成结果不能把新状态改回去；重复回调也会被忽略。代码通过 LongSupplier 注入时钟，enter 和 complete 都先取得同一把监视器锁（monitor），再采样时间，不接收锁外采集的时间参数。10 秒窗口和 5 秒冷却共用这个单调时钟域。迟到回调按被观察到的时刻进入窗口，因此调度延迟会推迟故障信息的反映，不能把这个时间解释成原始网络完成时间。逐样本队列用于说明精确过期，生产实现应改用有界统计，并保持同一定义。

本地 synchronized 只保护同一进程的状态，不能保证全局只有一条探针。探针同样占用流槽，也服从固定期限；只有本地流结束后才能结算，尚未确认关闭时，就继续占用流槽和探针名额。图 D6 的健康三态不是所有代理默认采用的 circuit breaking。Envoy 1.36 还分别限制连接数、待处理请求、并发请求和并发重试；资源达到上限就可以拒绝，不需要等到错误率达到 50%。[8]

This is an optional health policy: terminal callbacks observed under the local monitor within ten seconds, at least 100 samples and ≥50% failures open it. After five seconds admit one local probe, at most four across four instances. Admission/concurrency rejection is not a health failure; classify transport/timeouts explicitly and exclude business 4xx. Success closes immediately, with rate/concurrency gates bounding recovery load; failure waits another five seconds. Epoch changes fence stale completions, and duplicate callbacks are ignored. Inject a monotonic LongSupplier and sample only after enter/complete acquire the same monitor; neither accepts an externally sampled timestamp. The ten-second window and five-second cooldown use that clock domain. Delayed callbacks count when observed, so scheduling delay can postpone health information; these are not original network completion timestamps. The per-sample queue explains expiry; production needs bounded statistics preserving this definition.

Local synchronized protects one process and does not provide one global probe. A probe occupies capacity and a fixed deadline; unresolved local transport termination retains its slot/probe. D6's health states are not a universal proxy default: Envoy 1.36 separately limits connections, pending requests, active requests and active retries. Resource saturation rejects without waiting for 50% observed errors. [8]

可以沿一次请求复述主线：读取本地快照并固定策略 → 受控验证生成身份 → 三值限流决定是否准入 → 固定目标版本和截止时间后代理请求 → Orders 检查对象权限并提交业务状态。回滚只改变后续路由，取消只传递停止的意图。POST 的结果未知时，沿用原业务键查询，不能盲目换版本重发。

观测时使用取值范围有界的 route_id、policy/upstream_version，以及是否转发（forwarded）、尝试次数（attempts）、剩余时间和额度判定延迟。不要把 user_id 或完整 URL 放进指标，制造无限增长的基数。按每条日志 300 B×每秒 1 万次请求计算，日志为 3 MB/s，一小时 10.8 GB，不能当成全天峰值流量。

日志使用有界异步缓冲；溢出时按审计策略丢弃或拒绝请求，不能让每条请求都同步等待慢磁盘。现有示例验证了本地策略和契约模型，尚不能证明真实分布式系统的可靠性。

Retell the path: pin local policy → controlled verification creates identity → three-outcome admission → proxy under a fixed target/deadline → Orders enforces ownership and commits business state. Rollback changes future routing; cancellation conveys intent; resolve uncertain POST outcomes using the original business key.

Observe bounded route_id, policy/upstream_version, forwarded status, attempts, remaining budget and admission latency. Avoid user_id/full-URL metric cardinality. 300 B×10,000/s=3 MB/s or 10.8 GB/hour, not an all-day volume. Use bounded asynchronous logs and an explicit overflow policy. Executed examples validate local policy and contract models, not real distributed reliability.
