需求与边界：先约定操作，再确定统计分母Contract: operations and denominators first

发生分区时，同一系统可以拒绝无法安全完成的账本强读，继续接纳购物车加入操作并暂存不同版本，也可以在允许的时限内展示旧 Feed 数据。每项选择都要结合哪份数据、哪种操作、什么故障来说明，产品名称无法代替这些约定。下面各组图是独立场景，A 编号列出的都是教学假设；本章没有进行数据库压测或真实故障注入。

One system may refuse an unsafe ledger read, admit divergent cart additions, and show bounded-stale Feed data. Decide per data × operation × failure, rather than by product name. Decks are separate scenarios; A-numbers are teaching assumptions, without benchmarks or real fault injection.

CAP：写入完成后，后发的读取为什么不能返回旧值CAP: a stale read after a completed write

网络分区两侧的副本如果都继续返回本地结果，就可能违反操作的实时先后；选择等待或拒绝，则会牺牲 CAP 所要求的可用性。先看第 3 帧：写入已经返回 OK。第 4 帧的读取在这之后才发起，却拿到旧值。第 5 帧再展示拒绝读取的另一种选择。

Two live replicas serving local results across a partition can violate real-time order; waiting or refusing sacrifices CAP A. Frame 3 acknowledges the write, frame 4 invokes the later read, and frame 5 shows the alternative.

C 约束读写历史，A 要求操作最终完成C is history safety; A is operation liveness

共享寄存器初值为 x=0。A 完成 x=1 的写入并返回后，B 才发起读取，期间没有其他写入。线性一致要求每次操作都像是在调用与返回之间的某个瞬间完成，而且要遵守已经发生的先后顺序，所以这次读取不能返回 x=0。分区中的 B 无法区分两种情况：远端根本没写，或远端已经写完、复制消息却丢失了。副本最终追平，也不能修复这段已经发生的历史。原始 CAP 证明采用的就是原子一致性，也称线性一致性（atomic / linearizable consistency）。[1]

这里使用异步网络模型：非失败进程仍会得到公平执行，但消息可以任意多次丢失，持续分区也在允许范围内。两个保证必须在所有允许的执行中同时成立，因此只要找到一个无法两全的执行，就能反驳该主张。排除 P 只是缩小了模型的范围，不能解决设计仍然需要面对的跨副本分区。

The shared register starts at x=0. A completes x=1 before B invokes its read, without an intervening write. Linearizability places each operation between invocation and response, respecting real-time precedence: x=0 is illegal. B cannot distinguish no remote write from a completed one with lost messages. Convergence cannot repair this history. The original CAP proof uses atomic / linearizable consistency. [1]

The asynchronous model gives non-failed processes fair execution while allowing arbitrary message loss, including a lasting split. Both guarantees must hold in every allowed execution; one conflicting execution defeats the claim. Excluding P narrows the model without repairing partitions the design still has to handle.

CAP 的“最终完成”，不同于产品的一秒期限Eventual completion has no one-second bound

CAP 的可用性要求非失败节点接到的操作最终完成，没有规定固定的延迟上限。快速返回 503 并没有完成寄存器读写；十分钟后才正确返回，虽然完成了操作，也可能违反产品的一秒 SLO。有限超时同样不能证明对端已死。因此，工程设计要按操作说明哪些请求会被拒绝、之后怎样恢复，不能把选择 CP 理解为分区时整站停机。[1] [2]

线性一致性也不同于 ACID 中的 C，不会自动提供跨键事务。两次扣款即使都先读到最新余额，再分别执行，也仍可能违反余额不能透支的约束；扣款的原子条件和幂等身份见 Ch18 / Ch24。

CAP A requires eventual completion at each non-failed node without a fixed latency limit. Fast 503 does not complete a register operation; a correct ten-minute reply may fail a one-second SLO. A finite timeout cannot prove remote death. Specify per-operation refusal and recovery rather than assuming every CP split stops the whole site. [1] [2]

Linearizability differs from ACID C and does not supply multi-key transactions. Two fresh balance reads followed by separate debits can still violate an invariant; Ch18 / Ch24 cover atomic debit and idempotent identity.

保住一致性：分别确认写入已提交、强读可安全返回Preserve consistency: prove commit and strong reads

A、B 组成多数派后可以继续提交；隔离的 C 则拒绝新写，以及无法通过屏障验证的强读。第 2–3 帧展开一条当前任期日志的处理过程：A 持久化，B 持久化后返回 ACK，协议确认提交并应用，最后结果沿 A → API → Client 返回。

A/B can commit as a majority; isolated C refuses new writes and unproven strong reads. Frames 2–3 expand one current-term entry: A persists, B durably acknowledges, the protocol commits/applies, then replies A → API → Client.

关键实现：区分成功、结果未知和服务不可用Implementation: separate success, unknown, and unavailable

下面的操作契约伪代码对应第 3–5 帧，也为下一组购物车示例作准备。外部组件 Consensus 负责完整共识协议，包括任期、选举限制、日志匹配和当前任期的提交规则，不能用两个 ACK 或本地锁代替。处理同一业务操作时，proposeAndApplyOnce 在同一复制状态机内校验 id/payload，并把业务效果与持久回执一起提交。如果真实账本位于另一数据库，就需要在那个数据库中建立相应的原子约束；这个接口不能跨越事务域提供原子性。[5]

This operation-contract pseudocode covers frames 3–5 and previews the cart. Consensus implements full terms, elections, log matching, and current-term commit rules rather than two ACKs or a local lock. proposeAndApplyOnce checks id/payload and commits effect/receipt in one replicated state machine. A separate business database needs its own atomic effect/receipt constraint; this interface does not span transaction domains. [5]

# Teaching contract; Consensus is a real external protocol, not a local lock.
strongWrite(id, payload, deadline):
    # applyOnce checks id+payload and stores receipt+effect in one state machine.
    result = Consensus.proposeAndApplyOnce(id, payload, deadline)
    if result == COMMITTED:
        return OK(result.receipt)
    if result == ID_REUSED_WITH_OTHER_PAYLOAD:
        return CONFLICT
    # A timeout/no quorum does not prove that an earlier attempt did not commit.
    return UNKNOWN(id)  # retry/query with the same id and payload

strongRead(key, deadline):
    # Barrier validates current leadership and obtains a safe commit index.
    index = Consensus.readBarrier(deadline)
    if index is unavailable or not waitApplied(index, deadline):
        return UNAVAILABLE
    return StateMachine.readAtLeast(key, index)

addOnlyCart(id, item):
    # One local durable transaction: unique id+payload, add, and retry receipt.
    # A failed/unknown local commit returns UNKNOWN, never a fabricated OK.
    return LocalStore.commitOnce(id, ADD(item))

healCart(left, right):
    merged = left.items UNION right.items  # add-only contract; no removes
    persistAndRetryBoth(merged)  # delivery may retry; union is idempotent

故障时怎样返回：没有多数派或发生超时，都可能掩盖已经提交的结果。因此，写入返回 UNKNOWN，并保留原来的 id/payload 供查询或重试。强读如果拿不到当前领导权和安全提交位点的证明，就返回 UNAVAILABLE；拿到证明后，还要在期限内等本地应用到该位点，才能返回结果，不能只读取本地看似最新的一行。恢复后挡住旧任期，也不意味着已经完成支付回执和外部效果的核对。

etcd 3.6 的 KV 操作通常默认提供线性一致性；显式选择 serializable 读，则可能读到相对于 quorum 滞后的数据。Watch 有单独的语义，不能据此把所有 API 都称为强读。本章没有运行 etcd 集群。[6]

Failure boundary: no quorum or timeout can hide commit, so writes return UNKNOWN and retain the original id/payload for recovery. Strong reads without leadership/commit proof return UNAVAILABLE and await local application through that index. Reading the newest local row is insufficient. Term rejection does not reconcile external effects or lost payment replies.

etcd 3.6 KV operations normally default to linearizability; explicit serializable reads accept data stale relative to quorum. Watch has separate semantics, without a blanket strong-read guarantee for every API. No etcd cluster was run here. [6]

继续提供服务：允许版本分叉，就要定义怎样合并Preserve service: define how divergence merges

分区两侧都接纳只加入商品的购物车操作，恢复后用并集合并，再把结果写回双方。这里的成功表示本地已经持久保存这次加入，不保证所有端点立即看到同一份列表。

Both sides admit add-only cart additions, then union and persist the merge to both copies on healing. Success means local durability without immediate agreement at every endpoint.

第 3–4 帧走完了收集版本、合并和写回双方的过程。本地接纳由 LocalStore.commitOnce 在一个事务中绑定操作身份与加入效果；磁盘持久化失败时，结果仍可能是 UNKNOWN。集合并集 union 只适用于本例的纯加入操作：若用于删除场景，它可能让已删除商品重新出现，减少数量的意图也需要其他规则表达。追平还依赖通信恢复、重试和合并规则，没有自动五秒完成的保证。Dynamo 介绍了版本管理和应用协助合并，也说明宽松法定人数（sloppy quorum）使用的临时节点可能不在原偏好集合内。[4]

Frames 3–4 close collection, merge, and persistence. LocalStore.commitOnce binds operation identity and addition in one local transaction; failed persistence can remain UNKNOWN. Union fits additions but can resurrect removes; decrements need further rules. Convergence requires restored communication, retries, and merge rules, without a five-second bound. Dynamo describes versioning, application-assisted reconciliation, and sloppy-quorum temporary nodes outside the preferred set. [4]

集合有交点，为什么读取仍可能先新后旧Overlap is insufficient: a newer read followed by an older read

固定 N=3、W=2、R=2 时，读写副本集合的交点至少为 2+2−3=1。下面的可运行 Python 反例让一次写入只到达 A、尚未凑齐 W，就允许读取它的版本，而且读取返回前不把新版本写回其他副本。R1 读取 A/B，得到 x=1；等 R1 返回后，R2 才读取 B/C，却得到 x=0。如果把那次未完成的写排在 R1 前面，R2 就读错了；排在 R1 后面，R1 又无法解释。集合始终有交点，这段历史仍不满足线性一致性。

Fixed N=3, W=2, R=2 ensures overlap ≥2+2−3=1. This runnable Python counterexample exposes a version before W completes and returns reads without writeback. R1 reads A/B and gets x=1; after R1 returns, R2 reads B/C and gets x=0. Placing the pending write before R1 makes R2 wrong, and placing it after R1 makes R1 wrong. Overlap persists but the history is illegal.

def quorum_without_writeback():
    # N=3, W=2, R=2; one immutable version order, no failures of local memory.
    replicas = {"A": (0, "x=0"), "B": (0, "x=0"), "C": (0, "x=0")}
    replicas["A"] = (1, "x=1")  # W has only one ACK: the write is pending
    r1_members = {"A", "B"}
    r2_members = {"B", "C"}
    assert len(r1_members & r2_members) == 1
    r1 = max(replicas[n] for n in r1_members)
    # R1 responds x=1; it does NOT write that version back before returning.
    r2 = max(replicas[n] for n in r2_members)  # R2 starts after R1 responds
    assert (r1[1], r2[1]) == ("x=1", "x=0")
    # Place pending write before R1 and R2 is wrong; after R1 and R1 is wrong.
    # There is no second write that could restore x=0.
    return {"R1": r1[1], "R2_after_R1": r2[1], "linearizable": False}

示例的边界：这只是按固定顺序重放本地内存中的操作历史，没有实现分布式协议，也不是不可能性证明。完整协议可以结合版本规则、读屏障或返回前写回，建立更强的保证；这个反例只说明一个交集公式还不够。2+1 分区中，单节点一侧仍凑不齐 W=2 / R=2，多数派能服务并不等于每个活节点都满足 CAP 的可用性要求。这也对应 Ch06 对固定 quorum 与宽松 quorum 的区分。

Boundary: this deterministic local history is neither a distributed implementation nor an impossibility proof. A complete protocol can add version rules, barriers, or writeback before returning to establish stronger guarantees; overlap alone is insufficient. A 2+1 singleton cannot meet W=2 / R=2. Majority service does not establish CAP A at every live node, consistent with Ch06’s fixed/sloppy quorum boundaries.

PACELC：正常复制时，确认条件怎样影响延迟PACELC: replication barriers affect everyday latency

发生分区（P）时，需要讨论可用性与一致性的取舍；没有分区（Else）时，复制系统仍要在延迟与一致性之间选择。PACELC 是分析设计的框架，不能当作产品永久不变的标签。Abadi 在 2012 年的论文中明确了 Else 所讨论的复制背景。下面只比较写入成功前需要等到的持久化条件，远端 ACK 本身不能证明线性一致性。[3]

P asks about availability/consistency; Else asks about latency/consistency in replicated systems. This framework is not a permanent product label. Abadi’s 2012 paper gives the replication context for Else. These durability barriers alone do not establish linearizability. [3]

分别验证持久化、读取保证和容灾损失Validate durability, reading, and failure loss separately

提前确认只等待 A 持久化，此时 B 可能还没有这次写入。如果 A 在 B 追平前永久丢失，切流后就可能丢失已经确认的日志尾部。等待 B 持久化能增强数据保存的保证，但不能证明 B 已应用日志，也不能保证任意副本或旧领导者上的读取都是最新的。第 4 帧通过已提交版本 commit v，让本会话等待追平或改换读取节点，从而读到自己写入的数据；要正确处理其他用户后续的写入，仍需要完整的排序和强读协议。

A4 的并行模型是 2+max(1,RTT+1) ms。RTT 为 4/80 ms 时，分别得到 7/83 ms：相对于 20 ms 目标，前者剩余 13 ms，后者超出 63 ms。写入归属和副本位置会改变必须等待的路径，增加应用实例却不能消除远端等待。故障时也不能悄悄把“同步保存后成功”改成“异步复制也算成功”；无法满足原保证时，应拒绝操作，或事先另行约定较弱的承诺。

Early ACK waits for A while B may lack the write. Permanent A loss before catch-up can lose acknowledged tail data. B persistence improves durability but does not prove application, arbitrary-replica freshness, or leadership. Frame 4’s commit v gives this session read-your-writes by waiting/routing; other users’ subsequent writes still require full ordering and strong-read rules.

A4’s parallel model 2+max(1,RTT+1) ms gives 7/83 ms at RTT 4/80. Against 20 ms, that leaves 13 ms or exceeds by 63 ms. Authority/replica placement changes the critical path; more Apps cannot remove remote waiting. A failure cannot silently turn synchronous success into asynchronous success: refuse or define a weaker contract beforehand.

复算延迟：为什么不能直接相加两个 p99Arithmetic and the p99 counterexample

提前确认的延迟是 2+1=3 ms；如果本地与远端串行执行，则为 2+1+RTT+1=8/84 ms。这些计算都假设没有排队、只复制一轮，而且各项耗时固定。示例文件 tradeoffs.py 还构造了 100 个按请求对齐的样本：两个顺序依赖各有 99 次耗时 1 ms、一次耗时 100 ms，但慢样本落在不同请求上。按最近秩法（nearest-rank），两个依赖各自的 p99 都是 1 ms；整条路径却有 98 次耗时 2 ms、两次耗时 101 ms，所以路径 p99 是 101 ms，而非 1+1=2 ms。真实尾延迟需要按整条请求路径的分布测量。

Early ACK is 2+1=3 ms; serial work gives 2+1+RTT+1=8/84 ms. Both assume one fixed-time round without queues. tradeoffs.py aligns 100 requests: each sequential dependency has 99 samples at 1 ms and one at 100 ms, with different slow requests. Nearest-rank gives each p99=1 ms; the path has 98 samples at 2 ms and two at 101 ms, so p99=101 ms rather than 1+1=2 ms. Measure the path distribution.

SLI：先定义一次用户旅程怎样才算达标SLI: define a good journey first

用户在一秒内得到正确、持久的结账终态决策，这次旅程才算达标；同一 checkout_id 的重试共享原来的期限。合法拒付可以满足“得到有效决策”的可用性要求，但不代表付款转化成功。UNKNOWN、503 和 202 pending 本身都不是终态，不过仍可能在原期限内通过恢复或重试得到终态。如果在这个期限内已经向用户交付了错误或未持久保存的终态，之后重试正确也仍算未达标。

A good journey receives a correct, durable terminal decision within one second; retries share the original checkout_id deadline. A valid decline can satisfy decision availability without payment conversion. UNKNOWN, 503, and pending 202 may recover within the original deadline. An exposed incorrect or non-durable terminal response in that window remains bad even after a correct retry.

SLI 定义怎样测量，SLO 规定目标，SLA 则是包含约定后果的对外协议；三者采用的窗口和排除项可以不同。[7] 是否纳入统计，必须在知道成败之前确定；支持范围内因过载而被拒绝的旅程也要计入。提交后丢回包，可能同时留下正确的账本和一次未达标的用户旅程。Feed 允许最多 30 秒的旧展示，还需要独立的权限与数据年龄约定，不能据此放松授权或扣款规则。

SLI defines measurement, SLO its target, and SLA an external agreement with consequences; windows/exclusions can differ. [7] Fix eligibility before outcome, including supported overload refusals. Lost post-commit replies can leave correct ledger state but a bad journey. Feed staleness ≤30 seconds needs a separate permission/age contract, without relaxing authorization/debit rules.

关键实现：保留原始时间、合并重试、等观测期限完整结束Implementation: original time, deduplication, complete cohorts

Python 接收可信入口记录的 Attempt。记录包含旅程原始开始时间 started_ms、固定的 eligible 标志、结果在用户测量边界实际交付的时间 observed_ms、终态，以及经过独立核实的 correct/durable 标志，不能仅凭 HTTP 200 推断正确和持久。业务入口还要拒绝“同一身份却换了参数”的请求。

函数按结账身份合并记录后，取 cutoff=now−1000 ms，只统计原始起点位于 (cutoff−W,cutoff] 的旅程。这批旅程（cohort）都已经获得完整的一秒观测期限，所以报表落后一秒。重试如果更改起点或是否纳入统计，就是数据质量错误。在原始一秒期限内，任何已经交付却错误或不持久的 APPROVED/DECLINED 终态，都会否决这次旅程达标，不能靠后续正确重试抵消；更晚出现的业务错误仍要由独立的正确性审计发现。

Trusted ingress Attempt records retain original started_ms, fixed eligibility, actual delivery time observed_ms at the measured user boundary, outcome, and independently verified correct/durable flags; HTTP 200 supplies neither. Business ingress rejects identity reuse with different parameters. Group by id and count original starts in (cutoff−W,cutoff], where cutoff=now−1000 ms, giving complete cohorts with one-second reporting lag. Changed start/eligibility is a data-quality error. Any exposed incorrect or non-durable APPROVED/DECLINED within the original one-second window vetoes good; later business errors still require separate correctness auditing.

def counts(attempts, now_ms, window_ms):
    if window_ms <= 0:
        raise ValueError("window must be positive")

    cutoff = now_ms - DEADLINE_MS  # complete cohorts; one-deadline lag
    groups = {}
    for a in attempts:
        groups.setdefault(a.checkout_id, []).append(a)

    eligible = bad = 0
    for rows in groups.values():
        first = rows[0]
        identity = (first.started_ms, first.eligible)
        if any((r.started_ms, r.eligible) != identity for r in rows):
            raise ValueError("retry changed original start or eligibility")
        if not first.eligible or not cutoff - window_ms < first.started_ms <= cutoff:
            continue

        eligible += 1
        # observed_ms means a result actually delivered at the measured boundary.
        terminal = [
            r
            for r in rows
            if r.outcome in {"APPROVED", "DECLINED"}
            and r.observed_ms is not None
            and first.started_ms <= r.observed_ms <= first.started_ms + DEADLINE_MS
        ]
        exposed_bad = any(not (r.correct and r.durable) for r in terminal)
        good = any(r.correct and r.durable for r in terminal) and not exposed_bad
        bad += int(not good)

    return eligible, bad

缺少结果时怎样计数：即使没有回复，入口记录也必须保留，到期后把旅程计为未达标。丢失入口记录或客户端测量，不能被当作成功，也不能让分母只剩下收到结果的旅程。发布门另外接收 telemetry_complete 判断测量是否完整；零事件表示无数据。本例假设使用同一测量时钟、观测可信，没有实现跨机时钟同步、采样、覆盖率检查或监控存储。如果采用 202 异步旅程，就需要分别定义持久接纳和最终完成期限的 SLI。

Failure boundary: retain ingress records without replies and count bad at deadline. Missing ingress/client telemetry cannot become successful samples or a denominator containing only replies. The gate separately requires telemetry_complete; zero events means no data. This model assumes one observation clock and trusted data without solving distributed clocks, sampling, coverage, or storage. Async 202 needs separate durable-admission and completion-deadline SLIs.

错误预算：滚动窗口变化时，余额也要重算Error budget: balance moves with the event window

先明确哪些旅程纳入统计，记其总数为 E、未达标数为 B，再根据目标 S 计算允许量和余额。图中的 1,000 万事件快照与每秒 1,000 次的稳态流量，是两个独立场景，不能共用分母。

Fix denominator E, bad count B, and target S before allowance/balance. The ten-million snapshot and steady thousand-per-second example are separate scenarios.

区分实际达成率、预算比例和整数事件余额Separate achievement, budget fraction, and whole-event balance

实际达成率为 SLI=(E−B)/E，按比例计算的允许量为 E(1−S)；因为事件不能拆分，最多允许 floor(E(1−S)) 次未达标。A9 中，E=10,000,000、S=0.999、B=6,000，因此允许 10,000 次未达标，剩余 4,000 次，即原预算的 40%；实际达成率则是 99.94%。下节的发布门使用整数运算，避免浮点数在边界处造成误判。

滚动窗口会同时移出旧的达标和未达标事件。事故离开窗口可能改善余额，只有达标流量离开窗口时，也可能因总数减少而降低允许量。A6 把“正确、持久且一秒内”合在一起判断一次旅程是否达标；如果另设可用性、延迟和新鲜度 SLO，就应各算各的预算，不能相加不同单位或不同分母的预算，也不能重复累加互有重叠的未达标事件。Google SRE 建议采用容易解释的 good/total 事件比率。[8]

SLI=(E−B)/E; proportional allowance is E(1−S), at most floor(E(1−S)) whole bad events. A9 has E=10,000,000, S=0.999, B=6,000: allowance 10,000, remaining 4,000 or40%; achieved SLI is separately 99.94%. The next gate uses exact integers at boundaries.

Both old good/bad leave windows: expiring incidents can improve balance, while good traffic expiring can reduce allowance. A6 combines correct, durable, and on-time into one good predicate. Separate availability/latency/freshness SLOs need separate budgets, without adding different units/denominators or double-counting overlapping bad. Google SRE recommends interpretable good/total ratios. [8]

复算时间、流量峰值和依赖可用性Time, peaks, and dependency calculations

按时间计量时，30 天共有 43,200 分钟；99.9% / 99.99% / 99.999% 分别允许 43.2 分钟、4.32 分钟、25.92 秒未达标。如果分母改为 1,000 万事件，则分别允许 10,000 / 1,000 / 100 次未达标。时间与请求之间的换算需要流量均匀等前提，这些分钟数不能当作任意时段都可使用的停服额度。

A10 假设流量始终为每秒 1,000 次：30 天总数 E=2,592,000,000，允许未达标 2,592,000 次。20 分钟内有 10% 失败，会产生 120,000 次未达标，消耗预算的 4.63%；如果这 20 分钟全部失败，则消耗 46.30%。再假设全部失败的事故期间，流量升至原来的十倍，窗口总数 E 也会增至 2,602,800,000，允许量变为 2,602,800；12,000,000 次未达标会消耗 461.04%。峰值既改变失败数，也改变分母，必须一起重算。

A11 假设两个依赖故障独立，而且都必须成功，则整体可用性为 0.999²=99.8001%，未达标率为 0.1999%，是 99.9% 目标所允许比例的 1.999 倍。如果改为故障独立、且能够及时安全切流的冗余，则为 1−0.001²=99.9999%。共享可用区（AZ）、电源、配置或入口，以及切流失败，都可能破坏这些假设；计算结果不能直接作为生产承诺。

A 30-day time SLI has 43,200 minutes; 99.9% / 99.99% / 99.999% allow 43.2 minutes,4.32 minutes,25.92 seconds. Ten million events instead allow 10,000 / 1,000 / 100 bad. Time/event conversion needs uniform traffic and other conditions, not arbitrary outage permission.

A10 holds 1,000/s throughout: E=2,592,000,000, allowance 2,592,000. Twenty minutes at10% bad yields 120,000 or4.63%; full failure spends 46.30%. A tenfold incident-only peak in the full-failure branch changes E to2,602,800,000 and allowance to2,602,800: 12,000,000 bad spends 461.04%. Recompute the denominator.

A11 independent mandatory dependencies yield 0.999²=99.8001%, with bad rate 1.999 times the 99.9% allowance. Independent timely safe redundancy gives 1−0.001²=99.9999%. Shared AZ, power, config, ingress, or failed switching can invalidate these assumptions, without a production promise.

发布门：同时检查当前消耗速率和实际余额Release gate: compute burn and actual balance

即使月窗口还有余额，当前消耗速率过高也应暂停放量；回退不会退还已经消耗的预算。每档告警都要求长、短两个窗口同时超限（AND），两档之间满足任意一档即可（OR）。先暂停扩量，再判断能否安全回退，修复后重新评估。

Positive monthly balance can still be held by high burn; rollback refunds no bad. AND within each long/short pair, OR across pairs. Hold expansion, check safe rollback, then review repairs.

消耗速率的计算式是 burn=(B/E)/(1−S)。目标为 99.9%、当前未达标率为 1% 时，消耗速率为 10 倍。在流量稳定且预算完整的前提下，30/10=3 天；只剩 40% 时，预计约 1.2 天耗尽。流量与滚动窗口会改变预测，因此还要检查实际余额。原文给出的告警起点是：1h 与 5m 都 >14.4，或 6h 与 30m 都 >6，对应的未达标率阈值为 1.44% / 0.6%。稳定速率下，14.4×1/720=2%、6×6/720=5%，这里消耗的都是完整预算的相应比例。[9]

burn=(B/E)/(1−S). At99.9%, 1% bad gives 10×: a full budget lasts 30/10=3 days at stable rate, or1.2 days with 40% remaining. Traffic/windows change forecasts; also read actual balance. Source starting rules use 1h AND 5m both > 14.4, OR 6h AND 30m both > 6, equivalent to bad-rate thresholds 1.44% /0.6%. At stable rate,14.4×1/720=2% and 6×6/720=5% of the full budget. [9]

关键实现：统一计数口径，明确处理无数据Implementation: consistent counts and explicit no-data

下面的可运行 Python 接收上一函数算出的月窗口和四个较短窗口计数，每组都是 (eligible,bad)。其中 BAD_PPM=1000、SCALE=1,000,000 表示 SLO 为 99.9%；允许的未达标事件数向下取整，消耗速率则使用有理数精确计算。这段函数只控制功能发布的放量；安全修复和紧急可靠性修复要走另一个经过审查的政策通道，不能把功能发布改称修复来绕过限制。

Runnable Python consumes monthly and four shorter (eligible,bad) windows from counts. BAD_PPM=1000, SCALE=1,000,000 encode 99.9%; whole-event allowance rounds down and burn uses rational arithmetic. This gates feature expansion only; reviewed safety/urgent repairs use a separate policy path, without relabeling a feature as repair.

def budget(eligible, bad):
    if not (0 <= bad <= eligible):
        raise ValueError("invalid counts")
    if eligible == 0:
        return None  # no data, never 100% success

    allowed = eligible * BAD_PPM // SCALE  # maximum whole bad events
    return {
        "remaining": allowed - bad,
        "allowed": allowed,
        "burn": Fraction(bad * SCALE, eligible * BAD_PPM)
    }


def feature_gate(month, windows, telemetry_complete, canary_healthy, reviewed):
    # All inputs use the same SLI, cohort cutoff, and service scope.
    monthly = budget(*month)
    rates = {
        name: budget(*windows[name])
        for name in ("1h", "5m", "6h", "30m")
    }

    if not telemetry_complete or monthly is None or any(v is None for v in rates.values()):
        return "HOLD_NO_DATA"
    if monthly["remaining"] <= 0:
        return "FREEZE_FEATURES"

    burn = {name: value["burn"] for name, value in rates.items()}
    page = (
        (burn["1h"] > Fraction(72, 5) and burn["5m"] > Fraction(72, 5))
        or (burn["6h"] > 6 and burn["30m"] > 6)
    )
    if page:
        return "HOLD_BURN"

    if not (canary_healthy and reviewed):
        return "HOLD_REVIEW"
    return "ALLOW_NEXT_CANARY_STEP"  # reviewed repair uses a separate policy path

代入一组输入：月窗口为 (10,000,000,6,000)，预算剩余 4,000。1h/5m 两窗各为 (100,000,1,441)，消耗速率均为 14.41 倍，因此输出 HOLD_BURN，暂停放量。如果只有长窗消耗高、短窗未达标率已经归零，这一档就不会触发；恰好 14.4 倍也不满足严格 > 条件。任一窗口零事件或测量不完整时，返回 HOLD_NO_DATA；月窗口未达标数达到 10,000 时，返回 FREEZE_FEATURES。

政策与实现边界：本例选择在整数事件余额 ≤0 时冻结功能发布。引用的公开政策使用四周窗口并列有例外，本章采用 30 天。低流量下，一个失败也可能产生很高的消耗速率，因此需要按业务调整窗口和样本政策；在样本量方面，这个最小模型只检查分母是否为零。函数不执行部署，也不验证数据模式（schema）或外部扣款能否撤销。如果不能安全退回 v7，应关闭相关功能或前向修复。恢复发布前，还要复评修复证据、灰度健康度和余额，不能按日期自动放行。[10]

Inputs: month (10,000,000,6,000) retains 4,000; 1h/5m each at (100,000,1,441) gives 14.41× and HOLD_BURN. A hot long/recovered short window does not trigger that pair; exactly 14.4 does not exceed the strict threshold. Zero traffic/incomplete telemetry gives HOLD_NO_DATA; month bad 10,000 gives FREEZE_FEATURES.

Policy/boundary: freeze features at whole-event balance ≤ 0. The public example uses four weeks and exceptions; this chapter chooses 30 days. One failure can dominate low traffic, requiring tailored window/sample policies; this minimal model checks zero denominators only. It neither deploys nor validates reversibility of schemas/charges. Disable or forward-fix when v7 is unsafe. Review repair evidence, canary health, and balance before reopening, without calendar resets. [10]

  4. [4] Giuseppe DeCandia et al., Amazon, Dynamo: Amazon’s Highly Available Key-value Store, 2007. 介绍版本冲突、应用协助合并和 sloppy quorum；本章仅对只加入商品的例子使用并集。 Version conflicts, application reconciliation and sloppy quorum; union is our add-only example.
