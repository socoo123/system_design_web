本章要点：服务责任、调用预算与业务结果Core: ownership, call budgets, and business outcomes

  • 先明确服务的责任。只有发布节奏或资源池确实需要独立时，才拆成服务；必须在同一事务中满足的规则，仍留在同一个边界内。
  • 调用共用一份预算。服务发现只提供候选地址；调用方负责截止时间、有限重试、熔断和在途请求上限。
  • 超时不改写业务事实。持久受理、付款、履约是不同结果；提交结果未知时，用稳定的幂等键 K 查清结果。

本章以订单系统为例：订单服务（Order）负责订单意图与状态，搜索服务（Search）负责派生索引，消费端（Effect Worker）只修改自己的积分库。A2 允许先持久保存已受理的订单（ACCEPTED），再推进履约。第五组图另用只读库存查询讲调用预算；库存预占与支付状态机见 Ch18 / Ch24。

  • Find the owner. Extract for concrete release or resource-pool needs; keep transactional invariants together.
  • Spend one call budget. Discovery gives candidates. The caller owns deadline, bounded retry, breaker and in-flight limits.
  • Timeout does not rewrite facts. Durable acceptance, payment and fulfillment differ. Recover unknown commits through stable K.

Order owns intent/state, Search a derived index, and Effect Worker local points. A2 permits durable ACCEPTED before fulfillment. Deck five is a separate read-only stock API. See Ch18 / Ch24 for reservations and payment state machines.

一 · 先明确模块责任，再拆成独立部署1 · Module ownership before deployment extraction

先验证模块接口，再拆成独立部署。图一的 Order 仍可以位于单体内：只有它能写订单表，订单、幂等结果和 outbox 由同一个本地事务提交。A1 中独立的发布节奏、搜索索引重建所需的扫描资源池，说明了拆分的收益；代价则是事件滞后、索引重建和跨服务排查问题。划分服务时，应让一个业务能力从接口到数据都由同一方负责，而不是把 Controller / Service / DAO 三层拆给三支团队。微服务的独立部署特征与业务能力边界见原文 [1]。

正常的订单请求沿 Client → Order → Order DB 提交，再逐跳返回；搜索请求沿 Reader → Search → Search DB 查询派生索引。Search 不在受理的同步链路上，因此索引重建失败不妨碍接单，搜不到订单也不能证明订单不存在。如果每次修改都牵动两个模块，事务也总要同时锁住两边的数据，就应重新考虑边界。模块化单体同样可以通过增加实例扩容。

即使共用一个物理集群，也能通过独立 schema、写入凭据和迁移责任区分逻辑上的数据归属，只是 CPU、磁盘和故障域仍然共享。反过来，即使用了两个物理库，跨库直写和同步发版也会让服务继续耦合。应通过独立构建与回滚、接口约定的维护以及实际故障表现来验证边界，不能只数进程。

Test module APIs before extracting deployment. Order may still be inside a monolith: it exclusively writes orders and owns the local order/result/outbox transaction. A1 release cadence and search rebuild pools motivate extraction, with event lag, rebuild and diagnosis costs. Give one capability an owner from API to data rather than deploying Controller/Service/DAO as three teams. The original description covers independent deployment and business capability seams. [1]

Client → Order → Order DB commits and returns hop by hop. Reader → Search → Search DB queries derived data. Search is absent from acceptance, so rebuild failure does not block intake, and a missing index does not prove a missing order. Reconsider seams that constantly require coupled changes or transactions. A modular monolith can also scale horizontally.

Separate schemas, write credentials and migrations can establish logical ownership on shared hardware, while CPU/disk/failures remain shared. Separate stores can still be coupled by direct writes and lockstep releases. Verify independent builds/rollback, contracts and actual failure behavior instead of counting processes.

二 · 同步确认什么，就只承诺什么结果2 · Synchronize only the promised result

A2 约定，成功响应表示订单已持久保存，状态为 ACCEPTED。POST 已创建订单资源，并返回 order_id 与 operation_id，因此可以返回 201；如果只是接收异步任务、尚未创建订单，202 和相应的状态查询资源更合适。HTTP 状态的含义依据 RFC 9110，后续是否拒绝、是否已付款则由业务约定决定 [14]。前端收到受理响应后，不能显示“付款成功”。

Gateway 核验入口身份并控制准入，Order 检查租户与对象权限，再决定业务变更；内部调用也必须检查对象权限 [11]。图二的同步链路是 Client → Gateway → Order → Order DB，持久提交的确认沿原路逐跳返回。第六组代码会展开订单、K、结果与 outbox 的事务。确认（ACK）丢失时，应通过同一个 K 恢复结果，不能重新创建一个意图。

业务允许稍后完成的积分、索引和通知，可以移出同步链路。如果必须当场确认库存或支付，就要把必要依赖加回关键路径；只读查询得到“还有货”，并不表示已经预占库存。如果登录验证码是当前约定中必须立即取得的结果，也不能只因为它通过邮件发送，就一律延后处理。必须与订单同时保存的审计意图，可以先放进同一个事务持久化。

A11 中五个分支各自实际耗时 80 ms，串行共 400 ms，真正并行时的理想关键路径约为 80 ms 加额外开销；把分支 P99 相加或取最大值，都不能证明整体 P99。A3 在稳定窗口内，按每秒 200 次受理、平均每次 0.1 s 计算，平均有 200/s×0.1s=20 个受理请求尚未完成。这只覆盖受理阶段，也不是并发硬上限。排队、相关故障和尾延迟仍需沿完整链路测量。

A2 success means durable ACCEPTED. POST creates an order resource with order_id/operation_id, so 201 is appropriate. Task acceptance before order creation would use 202 and a status resource. RFC 9110 defines the HTTP meanings; later rejection/payment states follow the business contract. [14] The UI must not show paid after acceptance.

Gateway verifies ingress identity/admission; Order authorizes tenant/object access and owns mutation. Internal callers also require object checks. [11] Deck two commits Client → Gateway → Order → Order DB and returns hop by hop. Deck six implements the order/K/result/outbox transaction; lost ACK requires recovery through K.

Defer points, indexes and notifications when the contract permits. Immediate stock/payment confirmation needs the required dependency on the synchronous path; a stock read is not a reservation. A login code may be required now despite being email. Audit intent required at commit can be stored in the order transaction.

A11 five actual 80 ms branches take 400 ms serially or ideally ~80 ms plus overhead in parallel. Neither summing nor maximizing branch P99s proves whole-request P99. A3 gives mean in-flight acceptance 200/s×0.1s=20 in a stable window, not a hard concurrency cap. Measure queueing, correlated failures and full-path tails.

三 · 异步处理：分别确认消息发布与消费结果3 · Asynchrony needs publication and consumption guarantees

先保存意图，再分别确认发布与消费。Order 在事务中一起提交订单与待发消息记录（outbox）；Relay 扫描待办，把 e17 发布到 Events，收到 Broker ACK 后才标记为已发布。如果先提交订单，再依赖内存发布消息，进程在两步之间崩溃就会丢事件；如果反过来先发布，消费者又可能处理一笔尚不存在的订单。本地事务解决了这个双写窗口，但没有把数据库与 Broker 变成同一个事务 [2]。ACK 丢失仍可能导致重复投递，重发时事件 ID 保持不变。

图三的消费者只修改自己的积分。下面的伪代码将唯一的 (tenant,consumer,event_id) 消费记录（inbox）与积分更新放在同一数据库事务中，组成身份的列都显式声明 NOT NULL，并要求非空。如果同一个事件 ID 对应了不同内容，就隔离冲突，不能直接发送 ACK。实际 schema 与绑定参数的适配器见 schema.sql / check_transactions.py。这里验证的是 SQLite 的本地事务，不能据此认为已验证 PostgreSQL 的并发行为。

Persist intent, then acknowledge publication and consumption separately. Order commits order/outbox. Relay scans pending e17, publishes to Events, and marks published only after broker ACK. Commit-then-memory-publish can lose events; publish-before-commit can expose nonexistent orders. A local transaction closes that dual-write window without making DB and broker atomic. [2] Lost ACK can repeat publication with the same event ID.

Deck three changes only local points. This pseudocode commits unique (tenant,consumer,event_id) inbox and points together, with explicit NOT NULL/nonempty identity columns. Changed payload for one ID is quarantined without silent ACK. See schema.sql / check_transactions.py for schema/bound SQL. SQLite local transaction checks do not prove PostgreSQL concurrency behavior.

consume(tenant, consumer, event_id, account_id, delta):
  require nonempty canonical identity;
  authorize tenant/account/event source
  digest = SHA256(canonical(account_id, delta))

  BEGIN
  won = SQL INSERT INTO inbox(tenant, consumer, event_id, digest, result)
        VALUES (:tenant, :consumer, :event_id, :digest, :delta)
        ON CONFLICT (tenant, consumer, event_id) DO NOTHING RETURNING result
  if won is empty:
    old = SQL SELECT digest, result FROM inbox
              WHERE tenant=:tenant AND consumer=:consumer AND event_id=:event_id
    if old is empty:
      ROLLBACK;
      RETRY_LATER_SAME_EVENT
    if old.digest != digest:
      ROLLBACK;
      QUARANTINE_CONFLICT_WITHOUT_ACK
    ROLLBACK
    ACK;
    return old.result

  affected = SQL UPDATE accounts SET points=points+:delta
                 WHERE tenant=:tenant AND account_id=:account_id
  if affected != 1:
    ROLLBACK;
    RETRY_OR_QUARANTINE_WITHOUT_ACK

  COMMIT
  ACK;
  return delta
# On DB/commit error: discard connection; do not ACK, replay same event_id.
# Inbox is retained; its insert and local effect share this one DB transaction.
# External email/payment is not inside this transaction.

如果在提交前崩溃，inbox 与积分变更都回滚；如果在提交后、ACK 前崩溃，重投的消息会命中 inbox，积分不会再次增加。示例永久保留 inbox，若要清理，必须另行约定最晚可能重放到什么时候。外部邮件不在这个事务中：先发邮件再记结果可能重复发送，先记结果再发邮件可能漏发。它需要外部系统支持稳定键以及原子执行或结果查询，或者明确接受重复并通过对账处理。

A4 的原始事件流为 200×1 KB=200 KB/s，按十进制计算，副本另算。停止消费 180 s 后，积压 36,000 条，即 36 MB。恢复后每秒消费 300 条，同时仍有 200 条进入，所以每秒只净减少 100 条，需要 360 s 追平；如果消费能力只有每秒 200 条，就永远追不平。在持久存储快被积压占满之前，应收紧新意图的准入。

A pre-commit crash rolls both changes back; a post-commit/pre-ACK crash replays into the inbox without more points. This example retains inbox records; cleanup requires a maximum replay contract. Email lies outside this transaction: send-before-record can duplicate, record-before-send can lose delivery. It needs external stable identity with atomic execution/query, or accepted duplicates and reconciliation.

A4 raw events are 200×1 KB=200 KB/s, decimal and before replicas. A 180s outage accumulates 36,000 events=36 MB. Recovery consumes 300/s while 200/s still arrives: 100/s net, 360s to catch up. At 200/s it never catches up. Tighten intake before durable obligations exhaust storage.

四 · 服务发现提供候选，调用方判断能否调用4 · Discovery supplies candidates, not guaranteed health

上方控制面提供候选，下方数据面直接调用。实例加载依赖后报告 READY，注册中心（Registry）记录成员、地址、健康状态与版本。调用方（Caller）获取快照，从兼容候选中选出 A，再直接发起 RPC；响应沿 A → Caller → Client 返回，Registry 不转发 RPC 数据。Consul 的发现文档与 Health API 说明了这一区分；如果只要所有健康检查都通过的实例，必须显式请求 passing=true，默认值是 false [3][4]。

A5 每 2 s 检查一次，连续失败 3 次后摘除，再给传播留 1 s，粗略预算为 3×2+1=7s；检查耗时与调度抖动还要另加。A 可能在两次检查之间失效，因此本地超时和摘除可以比等待目录更新更快，但不能因为某个调用方的网络故障，就永久删除全局成员。注册中心失联后，合格快照只能在接收后的 5 s 内沿用；快照过期且没有获准使用的健康连接池时，就拒绝派发新调用。重启后从磁盘加载快照，不能重置它的接收时间；长连接同样需要寿命、探测和撤销策略。

如果已有的 DNS、虚拟地址或服务端负载均衡能满足要求，就直接复用。无头服务（headless）记录、TTL 和连接复用都会影响失效实例被摘除的速度，不能只看是否使用 DNS。服务发现负责成员与健康信息，Ch28 的配置管理负责超时、灰度和开关；同一个产品可以承载两者，但要分别约定行为。找到 B 只解决了去哪里调用，剩余时间、操作能否重复以及熔断器是否放行，仍决定能否发起请求。

The control plane supplies candidates; the data plane calls directly. An instance reports READY after loading dependencies. Registry records membership/address/health/version. Caller selects compatible A and calls it directly; replies return A → Caller → Client. Registry does not proxy RPC bytes. Consul documents this discovery role; the Health API requires explicit passing=true for all-passing nodes (default false). [3][4]

A5 checks every 2s, requires three failures, and budgets 1s propagation: roughly 7s plus check duration/jitter. A can die between checks. Local timeout/ejection responds sooner, but caller network failure should not permanently remove global membership. Registry outage permits qualified snapshots only within five seconds; expired snapshots without an approved healthy pool reject new dispatch. Disk reload must not refresh receive time, and persistent connections need age/probe/revocation rules.

Reuse DNS, virtual addresses or server-side balancing when adequate. Headless records, TTL and connection reuse affect ejection, not the name DNS alone. Discovery owns membership/health; Ch28 configuration owns timeout/canary/flags. One product may host both with different contracts. Finding B supplies an address, not permission to ignore deadline, repeatability or breaker admission.

五 · 超时、取消和重试共用一份预算5 · Deadline, cancellation and retry share one budget

所有等待都消耗同一份时间预算。第五组图另用只读库存 API，整体截止时间仍为 800 ms。gRPC 默认不设置 deadline；传播截止时间时会扣除已经消耗的时间，服务端应用还负责停止派生工作 [5][6]。线程调度、服务发现等待、DNS、连接、远端排队与处理都要计入预算。各进程用本地单调时钟计算剩余时间，跨进程传递剩余时长，不能直接比较两台机器的单调时间戳。

A6 各阶段的计划上限为 80+220+40+220+140=700ms，距 800 ms 留下 100 ms，这不是各段 P99 之和，也不是硬实时保证。排队和线程晚醒可能消耗余量，因此每次都要重算。下面的伪代码把一次尝试至少需要的可用时间设为教学值 100 ms，上限为 220 ms，并预留 140 ms 完成处理和响应回程。如果总共只剩 250 ms，再退避 40 ms、扣除预留的 140 ms，调用就只剩 70 ms，应当停止。线程唤醒后，以及 worker 实际发出 I/O 前，都要对照同一个绝对截止时间 attempt_end 检查，不能给每个阶段重新分配 220 ms。

Charge every wait to one budget. Deck five is a separate read-only stock API with an 800ms deadline. gRPC sets no deadline by default, deducts elapsed time during propagation, and leaves spawned-work cancellation to the server application. [5][6] Include scheduling, discovery, DNS, connect, remote queue and processing. Use local monotonic time and propagate remaining duration, never compare machines’ monotonic timestamps.

A6 planned stage caps total 700ms, leaving 100ms under 800. This is neither summed P99s nor a hard real-time guarantee. Queueing/late wakeups can spend the slack. This pseudocode uses a teaching 100ms useful minimum, a 220ms attempt cap and 140ms finish/return reserve. With 250ms remaining and 40ms backoff, only 70ms remains: stop. Recheck on wakeup and in the actual I/O worker against the same absolute attempt_end; never reset each phase to 220ms.

readStock(request, D):                         # D: local monotonic deadline
  for attempt in [1, 2]:                      # Order is the only retry owner
    if attempt == 2:
      if not previous.transient or not previous.local_io_terminal:
        STOP
      sleep_cancellable(random(0, 40ms), D - 140ms)
    if cancelled or D - now() < 100ms + 140ms:
      STOP

    slot = inventory_slots.tryAcquire()       # local bounded I/O; no wait queue
    if slot is empty:
      STOP
    ticket = inventory_breaker.tryAcquire()   # OPEN rejects; HALF_OPEN: one probe
    if ticket is empty:
      release(slot);
      STOP

    attempt_end = min(now() + 220ms, D - 140ms)
    submit worker (
      on rejection:
        finish(ticket, IGNORED);
        release(slot);
        STOP
    ):
      outcome = NOT_DISPATCHED
      try:                                   # covers ALL owned-resource paths
        if not cancelled and attempt_end - now() >= 100ms:
          grant = GRANTED
          if attempt == 2:
            quota_end = min(now() + 10ms, attempt_end - 100ms)
            grant = shared_retry_budget.spend_once(quota_end, cancellation)
            # One bounded call, no SDK retry. Result: GRANTED, DENIED, or UNKNOWN.
          if grant == GRANTED and not cancelled and attempt_end - now() >= 100ms:
            # Discovery, DNS, connect, remote queue and execution share this
            # SAME attempt_end. Disable every SDK/proxy automatic retry.
            outcome = inventory_read_once(request, attempt_end)
            finish(ticket, classify_dependency(outcome))
      catch unexpected_local_error:
        outcome = LOCAL_FAILURE              # quota/parse/SDK errors included
      finally:
        try:
          finish(ticket, IGNORED)            # once-only ticket ignores fallback
        finally:
          release(slot)                     # after quota/local I/O really exits
      report outcome with local_io_terminal=true

    previous = await worker result only until attempt_end
    if caller wait timed out:
      request cancellation;
      STOP
    if previous.success:
      return previous                        # then <=140ms finishing allowance
  return failure_or_explicit_stale_read       # never invent stock/paid success
# spend_once admits <=20 extras per fixed second across ALL callers in A7.
# Its quota I/O must honor quota_end/cancellation; unknown may waste a token.
# Keep a slot for live local I/O; timeout/cancel does not prove remote rollback.
# A timed-out write resolves UNKNOWN using durable K, not this read-only loop.

这些调用还依赖适配器兑现具体约定：inventory_read_once 只发起一次调用，并关闭自动重试；预期网络错误归为依赖失败 FAILURE，额度查询、解析或 SDK 的意外本地异常则记为 IGNORED。worker 对检查、获取额度与 I/O 的处理都放在同一个外层 try/catch/finally 中，finally 兜底调用 finish 完成收尾，并归还已结束的本地 I/O 所占槽位，不能漏掉半开探针的收尾。等待异步结果的 Future 超时，不能证明底层传输已退出。代码此时保守停止重试，等本地 I/O 真正结束后才归还槽位；远端仍可能继续执行，因此还需要自己的准入与幂等机制。

spend_once 最多等待 10 ms，也不能晚于 attempt_end−100ms，并且必须响应取消。如果结果未知或额度被拒绝，就不向 Inventory 发请求，也不重试这次额度扣减；已经扣掉的令牌可以浪费。获取额度后，还要再次检查发出调用前的剩余时间。额度必须由所有调用实例共用的权威原子限额实现：本例按权威自身的时间划分固定的一秒窗口，满足 used<20 才原子递增。额度服务失败或不可达时就不重试，不能给每个进程都分配每秒 20 次。A7 在同一窗口内有 200 个原始请求，加上最多 20 次重试，共计最多 220 次准入。固定窗口交界可能短时集中调用，严格滑动窗口约定另见 Ch04；这里统计的是准入次数，不保证实际网络发送严格匀速。拿到令牌后如果在发出调用前已过期，可以浪费令牌，不能超额发送。

五层调用如果每层总共最多尝试三次，最深层最坏可能收到 3⁵=243 次调用；本例则只由 Order 负责重试，每个请求总共最多尝试两次。次数、时间和额外流量都要有上限，鉴权失败、参数错误和业务冲突不重试。AWS 同样建议只选一层负责重试，限制次数，并使用退避与随机抖动 [12]。退避本身不会增加服务容量。

The adapter contract matters: inventory_read_once performs one call with automatic retries disabled. Network errors become dependency FAILURE; unexpected quota/parse/SDK errors are IGNORED. One outer try/catch/finally covers checks, quota and I/O, with a once-only finish fallback and terminal slot release. Future timeout does not prove transport termination: the loop conservatively stops, holding its slot until local I/O ends. Remote work may continue and needs its own admission/idempotency.

spend_once waits at most 10ms and never past attempt_end−100ms, honors cancellation, and treats unknown/denied as no Inventory dispatch. Do not retry an unknown quota debit; a token may be wasted. Recheck time afterward. It needs one atomic authority across all caller instances: in this example a conditional used<20 increment in authority-time fixed one-second windows. Failure/unavailability denies retry; it is not 20/s per process. A7 admits 200 originals plus at most 20 extras per window. Window boundaries may cluster calls; strict rolling limits belong in Ch04. This counts admission, not perfectly paced physical sends. An expired dispatch may waste a token safely.

Five layers with three total attempts each can yield 3⁵=243 deepest calls. Here Order alone owns two total attempts. Bound count, time and aggregate extras; authorization/input/conflict errors are terminal. AWS likewise recommends one retry layer, caps and backoff/jitter. [12] Backoff does not create capacity.

调用方熔断：OPEN 拒绝调用，HALF_OPEN 只放一个探针Caller breaker: OPEN rejects, HALF_OPEN probes once

在 Order → Inventory 这条依赖上设置一个进程内熔断器。连续观测到三次依赖失败后，熔断器进入断开状态（OPEN）一秒，拒绝新调用；冷却结束后进入半开状态（HALF_OPEN），只放行一个探针。探针成功就关闭熔断（CLOSED），失败或未派发则重新冷却。三次失败、一秒冷却都是本章教学值。这个熔断器不控制所有实例的总流量，也不能撤销在途请求。模式说明见 [13]，下面的状态片段取自同源的 Java 17 可运行示例。

Put a process-local breaker on Order → Inventory. Three observed dependency failures open it for one second. After cooldown, HALF_OPEN admits one probe: success closes, failure or abandoned dispatch cools again. Three/one-second are teaching values. This neither caps all caller instances nor revokes in-flight calls. The pattern is documented in [13]; this state machine is extracted from the runnable Java17 example.

  enum State {
      CLOSED, OPEN, HALF_OPEN
  }

  enum Verdict {
      SUCCESS, FAILURE, IGNORED
  }

  static final class Breaker {
      final LongSupplier clock; // monotonic; read inside the lock
      State state = State.CLOSED;
      long epoch, openedAt;
      int failures;

      Breaker(LongSupplier clock) {
          this.clock = clock;
      }

      final class Ticket {
          final Breaker owner = Breaker.this;
          final long generation = epoch;
          boolean done;
      }

      synchronized Ticket tryAcquire() {
          long now = clock.getAsLong();
          if (state == State.HALF_OPEN) {
              return null;
          }
          if (state == State.OPEN) {
              if (now - openedAt < 1_000_000_000L) {
                  return null;
              }
              state = State.HALF_OPEN; // exactly one local probe
          }

          return new Ticket();
      }

      synchronized void finish(Ticket t, Verdict v) {
          if (t == null || t.owner != this || t.done) {
              return;
          }

          t.done = true;
          if (t.generation != epoch) {
              return; // ignore old in-flight completion
          }

          if (state == State.HALF_OPEN) {
              state = v == Verdict.SUCCESS ? State.CLOSED : State.OPEN;
              failures = 0;
              epoch++;
              openedAt = clock.getAsLong();
          } else if (state == State.CLOSED) {
              if (v == Verdict.SUCCESS) {
                  failures = 0;
              }
              if (v == Verdict.FAILURE && ++failures == 3) {
                  state = State.OPEN;
                  epoch++;
                  openedAt = clock.getAsLong();
              }
          }
      }
  }

所有状态转换与时钟观察都放在同一把锁内，I/O 则在锁外执行。Ticket 带有代次，并且只能完成一次，因此旧调用迟到的失败结果，不能在新探针成功后再次打开熔断器。FAILURE 只计入能够归因于依赖的失败；本地准入被拒、鉴权失败和业务冲突记为 IGNORED，不表示依赖坏了。处于 CLOSED 时，成功调用会把连续失败数清零。如果半开探针一直不结束，熔断器就会持续拒绝其他新调用，所以适配器必须有本地终止与收尾路径。每个实例都有自己的探针，重启也会重置状态；全局流量仍要靠额外调用额度与下游准入控制。

客户端超时或取消只是停止等待，写入可能已经提交，仍需按 UNKNOWN 查清结果。取消持久保存的订单需要单独的业务命令；A2 已受理的后台履约，不会因为 HTTP 连接断开就被删除。不能把这个只读重试循环直接用于扣款。

State transitions and clock observations share one lock; I/O stays outside it. Each generation-tagged ticket completes once, so an old failure cannot reopen after a newer successful probe. Count attributable dependency failures only; local denial, authorization and business conflicts are IGNORED. Success in CLOSED resets the consecutive count. A probe that never terminates keeps admission closed, so adapters need local termination/cleanup. Every caller instance has its own probe, and restart resets state; aggregate budgets and downstream admission remain necessary.

Client timeout/cancel stops waiting but cannot prove a write did not commit: it remains UNKNOWN. Cancel a durable order through a separate business command. A2 background fulfillment survives HTTP disconnect. Never reuse this read retry loop for charging.

六 · 幂等记录要跨实例共享，未知结果不能靠过期放行6 · Durable cross-instance idempotency and UNKNOWN

K 对应业务意图，不能随实例变化。tenant / operation / K 三项都要非空且经过规范化，客户端重试时保持 K 和请求内容不变。Order 检查当前授权与规范化后的摘要：同键同摘要就回放结果，同键但内容不同就返回冲突。并发竞争由数据库的组合唯一约束裁决，不能先查“没有”，再不加约束地插入。PostgreSQL 18 的唯一与 NOT NULL 约束见 [8]。下面的伪代码对应图六；完整 schema 使用可延迟检查的外键，让永久 K 映射指向同一事务中创建的订单。

K belongs to intent, not an instance. Scope nonempty canonical tenant/operation/K; keep K and request content stable. Order checks current authorization and canonical digest. Same key/digest replays, changed content conflicts. Database composite uniqueness arbitrates concurrency; unchecked read-then-insert cannot. PostgreSQL18 documents uniqueness and NOT NULL. [8] This implements deck six; the full schema uses a deferred foreign key from permanent K mapping to the order created in the same transaction.

accept(authorized_tenant, operation, K, canonical_payload, deadline):
  require nonempty canonical identity;
  authorize create for this tenant
  digest = SHA256(canonical_payload);
  new_id = random_UUID()

  # DB connection/lock/statement waits consume deadline; READ COMMITTED.
  BEGIN
  won = SQL INSERT INTO intents(tenant, operation, k, digest, order_id)
        VALUES (:tenant, :operation, :K, :digest, :new_id)
        ON CONFLICT (tenant, operation, k) DO NOTHING RETURNING order_id
  if won is empty:
    old = SQL SELECT digest, order_id, result FROM intents
              WHERE tenant=:tenant AND operation=:operation AND k=:K
    if old is empty:
      ROLLBACK;
      return UNKNOWN(K)
    if old.digest != digest:
      ROLLBACK;
      return CONFLICT
    authorize current access to old.order_id
    ROLLBACK
    return old.result or QUERY_CURRENT_STATE(old.order_id)

  SQL INSERT INTO orders(tenant, order_id, state)
      VALUES (:tenant, :new_id, 'ACCEPTED')
  SQL INSERT INTO outbox(event_id, tenant, order_id)
      VALUES (:new_id, :tenant, :new_id)
  result = immutable {order_id: new_id, state: ACCEPTED}
  SQL UPDATE intents SET result=:result
      WHERE tenant=:tenant AND operation=:operation AND k=:K

  COMMIT
  return 201(result, operation_id=new_id)
# Any DB/commit error: discard connection; return UNKNOWN(K), never new K.
# If rollback is confirmed, same K may compete again. An empty SELECT alone
# cannot prove absence while an earlier transaction remains unresolved.

在 READ COMMITTED 下，冲突的插入可能等待首个事务结束，随后 SELECT 用新的语句快照读取已提交结果 [8]；获取连接、等锁和执行语句都必须限时。如果首个事务尚未提交、结果仍不确定，查不到记录也不能证明它没有执行，应返回 UNKNOWN/IN_PROGRESS；只有确认回滚后，才可以用同一个 K 重新竞争。提交后 ACK 丢失时，B 可以查询同一数据库中的映射恢复结果。可运行演示验证的是 SQLite 的写事务串行化，没有声称已在 PostgreSQL 18 上运行。

订单、结果和 outbox 要么一起提交，要么一起回滚，示例只证明本地订单的提交承诺。Redis 过期锁、本地 Set，或者换实例后生成新键，都不足以提供这个保证。支付还需要独立的稳定 payment_operation_id，并由支付权威原子防重、支持结果查询。查询旧订单时也必须检查当前对象权限，K 不是访问凭证。

A8 按全天持续峰值计算七天、每条 1 KB 结果的存储上界：200×86,400=1,728 万条/天，即每天 17.28 GB，七天共 120.96 GB 逻辑记录；索引、副本和 outbox 另算。之后可以删除体积较大的结果，但永久保留紧凑的 K→order 映射及原摘要，旧 K 改为查询当前状态；长期映射的容量仍需另算。UNKNOWN 不能到期后就放行重做。Stripe API v1 支持保存首次执行响应并比较参数，但裁剪记录后可以重新执行，API v2 的语义也不同；这些都不等于本章的“七天结果加永久映射”政策 [7]。

Under READ COMMITTED, conflicting insert can wait for the first transaction; the following SELECT uses a fresh statement snapshot. [8] Bound connection/lock/statement waits. An empty query while prior work is unresolved does not prove absence: return UNKNOWN/IN_PROGRESS. Confirmed rollback permits the same K to compete. After commit/ACK loss, B recovers from the shared mapping. The executable adapter checks SQLite serialized writes, not PostgreSQL18 execution.

Order, result and outbox commit together, proving one local order only. Expiring Redis locks, local sets and new keys after instance changes do not suffice. Payment requires its own stable payment_operation_id and authoritative atomic dedupe/query. Replay still needs current object authorization; K is not a credential.

A8 at sustained peak gives 200×86,400=17.28M/day, 17.28 GB/day and 120.96 GB for seven days of 1 KB logical records. Indexes/replicas/outbox are separate. Trim large results afterward but permanently retain compact K→order/digest and query current state; size that mapping separately. Never expire UNKNOWN into permission to repeat. Stripe API v1 stores first execution responses and compares parameters, but permits re-execution after pruning, while API v2 differs. Neither defines this chapter’s seven-day/permanent-mapping policy. [7]

七 · 独立发布需要兼容窗口，追踪要能区分每次尝试7 · Compatibility, rollout and observable attempts

先扩展（expand），再灰度，最后收缩（contract）。图七中的 v1/v2 是同一个 Order 的两个版本，共用 K 的权威记录，并由同一个逻辑服务负责数据。先增加兼容字段与事件约定，再把新意图路由到 v2。A10 每秒有 1,000 个新意图，其中 10%=100/s 进入新版本；重试仍按已有 K 固定路由，或通过兼容的共享权威恢复，不能把同一写请求镜像给两版执行。这每秒 1,000 次属于独立的发布示例，不能与 A3 每秒 200 次订单受理混算。渐进替换的思路见 Strangler Fig [10]；真正迁移数据库时，还需要复制、追平屏障与写入所有权切换。

A9 三个实例各规划处理 600/s，总容量为 1,800/s；排空一个后还剩 1,200≥1,000 次/秒。如果只有两个实例，排空一个就只剩 600 次/秒。这些算式不能证明系统扛得住同机故障或整库故障。实例进入 READY 后才接流量；排空时先关闭本地准入，再通知路由停止新流量，然后有界等待旧请求结束。路由传播期间，本地仍要拒绝新请求。灰度异常时停止分配新流量，回退兼容代码；已提交订单继续通过 operation_id 查询。只有旧实例、旧读者、回滚窗口和保留的旧事件都能安全处理后，才删除旧字段，代码回退不会倒转业务状态。

追踪时传播 W3C traceparent 中的 trace-id/parent-id [9]，为每一跳和每次尝试分别建立 span，业务 K 则保持不变。记录路由版本、实例与版本、剩余时间、重试原因、熔断拒绝、operation_id 和积压年龄，才能分清请求慢在排队还是下游。trace_id 既不是幂等键，也不能证明访问权限；外部传入的追踪上下文还须经过信任边界处理。

Expand, canary, then contract. Deck seven is v1/v2 of one Order sharing K authority and data ownership. Add compatible fields/events before routing new intents to v2. A10 sends 10% of 1,000 new intents/s=100/s. Recover retries by existing K through pinned routing or compatible shared authority, never mirror one effectful request to both versions. This independent rollout scenario does not reuse A3’s 200/s load. Strangler Fig motivates gradual replacement. [10] Store migration additionally needs replication, catch-up barriers and write ownership transfer.

A9 three planned 600/s instances give 1,800/s; draining one leaves 1,200≥1,000. Starting with two leaves only 600. This does not prove colocated-host/store resilience. Admit after READY; drain closes local admission, tells routing to stop intake, then bounds old work. Locally reject during propagation. On canary failure stop new assignments and roll back compatible code; durable orders remain queryable. Remove fields only after old instances/readers, rollback windows and retained events are safe. Code rollback does not reverse business state.

Propagate W3C traceparent trace-id/parent-id. [9] Give hops and attempts separate spans while K remains stable. Record route revision, endpoint/version, remaining time, retry reason, breaker rejection, operation_id and backlog age to locate queueing versus downstream delay. A trace ID is neither dedupe identity nor authorization; handle incoming context at the trust boundary.
