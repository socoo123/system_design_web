中文

我先问订单与搜索是不是必须分别发布、是否需要独立资源池，以及订单成功究竟指受理还是付款。没明确痛点，就在单体里维护模块接口和表所有权。需要拆时，只抽一个能力边界。在线请求用短同步链把受理意图持久化，通知和派生视图经 Outbox 离开请求。调用方用发现快照挑实例，沿同一死线扣时间，重试只在一个层级、有总次数和额外流量预算；写入拿同一个业务键查询未知结果。发布先扩契约，再灰度、排空和回退兼容代码。

教学对象是订单系统。Order 是订单意图与状态的权威，Search 管派生索引，Effect Worker 示例只改自己的积分库。图里的库存查询是只读调用，用来算死线；跨服务库存预占、支付结算的状态机回 Ch18 与 Ch24。异步受理不放宽余额一致性。

微服务的价值是让一部分变更可以独立发布，而边界失误会让网络调用、契约和排障成本一起增加。[1] 数值均为 assumption；替换参数并重算，才能证明组件有必要。

English

Ask whether Order and Search need separate releases and resource pools, and whether success means accepted or paid. Without a concrete need, enforce module APIs and table ownership in one deployment. Extract one capability when justified. Durably accept on a short synchronous path; use outbox for deferred effects. Select endpoints from discovery snapshots, propagate remaining budget, centralize retries and recover unknown writes with one business key. Expand contracts before canary, drain and compatible code rollback.

The teaching system makes Order authoritative for intent/state, Search responsible for derived indexes, and Effect Worker responsible for local points. The inventory call in the deadline diagram is read-only. Cross-service reservations and payment state machines belong in Ch18 and Ch24. Asynchronous acceptance does not relax balance invariants.

Services can let selected changes deploy independently, while poor boundaries add remote-call, contract and operational costs. [1] All capacity, retention and detection intervals are labeled assumptions so their consequences can be recomputed.

一 · 先守住模块边界，再拆部署1 · Module ownership before deployment extraction

中文

正常路径从 Client → Order → Order DB 开始，提交再经 Order 回客户端。第一次画图时 Order 可以仍是单体中的模块，虚线框标的是将来可提取的边界。模块内部先通过接口访问数据，禁止旁边模块私自写订单表；否则把函数换成 RPC 后，同一张表仍然把所有服务焊在一起。Search 可以通过订单事件维护自己的读视图，业务查询只到它自己的索引。第三组补事件投递。

为什么选择这个边界？A1 的发布节奏不同，搜索的重建和扫描也需要独立资源池，所以拆 Search 能减少发布互相等待，并让扫描不占订单工作线程。代价是事件延迟、索引重建和跨服务定位故障。若需求总在两个模块一起改、事务总要同时锁两边数据，说明这个切法可能不合适；先在同体内把接口整理清楚，或者把必须同事务的规则留在同一个所有者里，比硬拆后再做跨库原子事务更容易解释。

替代方案是继续模块化单体。无状态单体也能加多个实例和负载均衡，服务拆分不是水平扩展的唯一办法。判断时看三件可检验的事：某个能力是否能独立构建和回滚，团队是否能独立维护它的合同，失败是否真的能被边界吸收。一个独立进程若仍同步等待另一个服务，后者故障一样可以让当前请求失败。资源隔离减少共享线程造成的拖累，业务成功是否依赖下游，则需要单独改合同。

数据所有权也不能只凭“两个库”三个字判断。同一物理集群中，各服务有独立 schema、写凭据和迁移责任，可以形成逻辑所有权；但 CPU、磁盘与整集群故障仍共享。反过来，两个物理数据库若靠跨库直写、共同 schema 和锁步发版，也仍然耦合。图上 Search DB 是派生视图，Order DB 是订单权威，不能把搜索索引缺失当成订单未创建。分布式大单体要看变更与运行时是否锁死。

故障窗口要写成具体行为：搜索重建超时，搜索接口可以暂时失败或使用明确陈旧的索引，订单受理继续；订单权威库不可用，则不能凭内存接受新的订单承诺。独立发布也不表示接口永不协调。下一版新增字段可以让旧调用方忽略，删字段、改语义或收紧枚举却可能破坏旧消费者。第七组会把兼容窗口画进发布路径，先回答“旧版还看得懂吗”，再说它能单独上线。

English

Client → Order → Order DB commits and returns through Order. Initially Order may be a monolith module; the dashed seam is an extraction boundary. Enforce interfaces and exclusive table writes before replacing calls with RPC. Search can maintain its derived read model from events; deck three expands durable publication.

A1 release cadence and search rebuild work justify a separate pool and deployment. Costs include event lag, rebuilds and cross-service diagnosis. If changes and invariants constantly span both modules, reconsider the seam: keep transactional rules together or improve the module interface before extraction.

A modular monolith can also scale behind a balancer. Test whether a capability can build/rollback independently, a team can own its contract, and failures are absorbed. Separate processes still fail requests when synchronous dependencies fail. Pool isolation and business dependency are distinct decisions.

Separate schemas, credentials and migration ownership can provide logical ownership on one physical cluster, but hardware and cluster failures remain shared. Separate physical stores can still be coupled by direct writes and lockstep schemas. Search is derived; missing search data does not mean no order. Diagnose coupled change and runtime behavior.

On a search rebuild timeout, search may fail or serve explicitly stale indexes while order intake continues. If Order authority is unavailable, memory cannot accept durable commitments. Independent deployment still requires contract evolution; additive fields differ from deleted fields or changed semantics. Deck seven makes old-version compatibility explicit.

二 · 同步到能兑现的结果，受理不等于履约2 · Synchronize only the promised result

中文

先把成功定义写出来。A2 的 POST /orders 创建一个持久订单资源，状态为 ACCEPTED，返回 order_id 与 operation_id；它没有承诺已经锁库存或已经收钱，所以用 201 可以成立。若端点只是接一个异步任务、还没有创建订单，返回 202 并提供状态资源更合适。状态机后续可以进入处理中、付款成功或拒绝，查询必须告诉用户真实状态。前端页面不能在收到“受理”后显示“付款成功”，这是协议错误，排队不能修复。

正常同步链只走 Client → Gateway → Order → Order DB。Gateway 做接入身份验证与流量准入，Order 检查用户是否能创建或读取这个租户的订单，并决定数据变化。Order DB 将订单、幂等结果与 outbox 原子提交，确认先回 Order，再经 Gateway 回 Client。业务权限不能只放在门口：内部任务和服务间调用可能绕开外部入口，带着一个合法身份也不代表能读任意 order_id。OWASP 明确要求访问对象的函数检查对象权限。[11]

为什么不把所有服务串上？A11 假设五个必要分支每个实际耗时 80 ms，串行等待就是 5×80=400 ms；真正同时发出并等待全部，理想关键路径约 max(80,…,80)=80 ms，加上编排和回程。不能说“并行五个分支的 P99 是五个超时相加”，也不能把各分支的 P99 直接相加或取最大就宣称得到整体 P99。分支尾部、共享故障与排队会改变分布，需要测完整请求；只要任一必要分支失败就整单失败，仍然会放大用户可见失败。

替代是把通知、积分和索引等允许晚到的工作移到事件链，而不是把每个依赖都删掉。如果产品必须当场确认库存或支付，就把必要依赖画在同步关键路径上，并留死线、幂等和未知结果查询。读库存“还有货”不是持久预占，不能依据一次只读结果承诺不会超卖。短链来自 A2；改变合同就重定组件与预算。

平均并发也要对应合同。A3 峰值 200 个意图/秒、平均受理在途 0.1 秒，在该稳定负载窗口里平均在途约 200×0.1=20。它只覆盖短受理，不包括之后等付款的所有订单，也不是可以买 20 个线程的证明。排队、慢事务与重试增加占用，准入需要压测。订单库提交 ACK 丢失时，同步调用返回未知状态；第三组的事件仍可能已经持久，第六组用 K 查结果恢复，不能再次受理另一个新键。

English

A2 POST creates a durable ACCEPTED order and returns order_id/operation_id, so 201 is meaningful without stock or payment success. An endpoint accepting only an asynchronous task would use 202 with a status resource. Subsequent processing may pay or reject; the UI must show the actual state, not equate acceptance with payment.

The synchronous path is Client → Gateway → Order → Order DB and back. Gateway verifies ingress identity and admission; Order authorizes tenant/object operations and decides mutations. Order DB atomically commits order, idempotent result and outbox. Internal callers also need object checks; valid identity does not authorize arbitrary order_id access. [11]

With A11 five actual 80 ms branches, serial waiting is 400 ms; true parallel all-of waiting has an ideal 80 ms critical path plus overhead. Neither summing nor taking the maximum of individual P99s proves aggregate P99. Correlated failures, tails and queueing require whole-request measurement, while required branches remain availability dependencies.

Defer work whose contract permits delay, such as notifications, points and indexing. Immediate stock/payment confirmation requires those dependencies with deadlines and recovery. A stock read is not a reservation. The short path follows A2; a different promise changes components and budgets.

At a stable A3 window, 200 intents/s × 0.1 s mean active acceptance gives about 20 in flight. This excludes long-lived payment states and is not a 20-thread cap. Queueing, slow transactions and retries need measurement. Lost commit ACK can coexist with durable outbox; recover K rather than accepting a new key.

三 · 异步不是丢给队列，而是两次本地承诺3 · Asynchrony needs publication and consumption guarantees

中文

正常路径是 Order 在 Order DB 提交订单与 outbox，Relay 扫描未发布记录，发 e17 到 Events，等待 Broker ACK，才标已发布。用户确认等订单事务，不等 Worker。队列暂不可用时，订单已经 ACCEPTED，outbox 有可恢复的待办；如果 outbox 容量或持久存储预算逼近上限，就收紧接单准入。允许异步不代表允许无限积压，这些订单占着未来履约责任，界面展示处理中。

为什么要把 outbox 和订单放一起？先提交订单、再由进程内存 publish，两步之间崩溃会留下永远没有事件的订单；先 publish 再提交，又可能让消费者处理根本不存在的订单。同一个本地事务把业务行和待投递意图绑在一起，Relay 崩溃后可继续扫描。AWS 的 Outbox 原文明确说明双写窗口以及重复消息需要幂等处理。[2] 它不是数据库与 Broker 的原子事务；发布 ACK 丢失，重复仍然存在。

消费者的承诺是另一段。Events 投递 e17，Effect Worker 在 Effect DB 的同一事务里插入唯一 inbox(event_id) 并做积分变更，commit 后才 ACK。崩溃若发生在 commit 前，事务回滚，重投可以执行；发生在 commit 后、ACK 前，重投命中 inbox，只返回已完成，不加第二次积分。本章 inbox 不删除；清理要另定最晚重放合同。内存 set 重启会丢去重证据。Broker 的确认表示消息被接受，消费者 ACK 表示这一份消费完成，不能混成一条“恰好一次”的线。

图上示例是本地积分库，不能直接推广成外部邮件。若 Worker 先发邮件再写 inbox，邮件成功但 inbox 未写时重试会重复发；先写 inbox 再发，崩溃会永远漏发。外部系统需要接收稳定业务键、原子执行并可查回执，或者业务接受重复并配补偿、对账和人工处理。消费者数据库里的 outbox 能保住下一次发送意图，但仍不能独自证明外部效果只发生一次。外部效果的责任要写进合同。

A4 每个新意图 1 条 1 KB 事件，200×1 KB=200 KB/s，是事件原始字节率，Broker 副本与索引另计。消费者全停 180 秒，积压 200×180=36,000 条，即 36 MB。恢复时一边还有 200 条/秒进入，一边能处理 300 条/秒，净下降 100 条/秒，36,000÷100=360 秒。若直接除以 300 得到 120 秒，漏了新流量；如果恢复能力只有 200，积压不会下降。这笔算术要求消费者留恢复余量，或控制新受理，增加 Broker 机器本身不会让业务消费变快。

English

Order commits order/outbox; Relay scans pending entries, publishes e17, waits for broker ACK, then marks publication. User acceptance waits only for the Order transaction. Broker outage accumulates durable obligations. Bound outbox capacity and intake, and show processing rather than accepting unlimited backlog.

Commit-then-memory-publish loses events on a crash; publish-before-commit exposes nonexistent orders. A local order/outbox transaction preserves intent for a recoverable relay. AWS describes the dual-write problem and duplicate-message handling. [2] It does not make the database and broker one atomic transaction; lost ACK still repeats events.

The consumer atomically inserts unique inbox(event_id) and changes local points, then ACKs. A pre-commit crash rolls back and permits replay; a post-commit/pre-ACK crash replays into the durable inbox without another effect. The teaching inbox is retained; cleanup needs a maximum replay contract. Memory dedupe does not survive restart. Broker acceptance and consumer completion are separate acknowledgements, not end-to-end exactly-once.

The local points proof does not extend to email. Send-before-inbox can duplicate; inbox-before-send can lose mail. External effects need a stable key with backend atomic execution/queryable receipts, or accepted duplicates with reconciliation/compensation. A local outbox preserves intent but alone cannot prove one external effect.

A4 yields 200 KB/s raw events. A 180 s outage accumulates 36,000 events or 36 MB. With 300/s consumption and 200/s continuing intake, net drain is 100/s and catch-up takes 360 s, not 120 s. At 200/s consumption backlog stays flat. Reserve recovery capacity or control intake; adding broker capacity does not necessarily speed effects.

四 · 发现给候选地址，调用方仍要判断能不能用4 · Discovery supplies candidates, not guaranteed health

中文

正常路径分两层。上方是控制面：实例加载完成后报告 READY，Registry 存名字、地址、健康信息与版本，Caller 获取快照。下方是数据面：Caller 从候选集中挑兼容的 Order A，直接发 RPC，A → Caller → Client 返回。Registry 不代理请求字节，也不应该成为每次调用的强制同步跳。Consul 文档支持登记与健康目录，Health API 的 passing 过滤需明确请求，不能把一个可能包含失败节点的原始查询当健康列表。[3][4]

A5 每 2 秒一次检查、连续 3 次失败才摘除，粗略检测预算是 3×2=6 秒，再留 1 秒传播就是约 7 秒；检查自身耗时和调度抖动还要加，不能承诺第 7 秒全世界一定切完。A 在两次检查之间崩溃，本地快照看起来仍健康。Caller 的请求超时把红线收在自己这一层，并在自己的池里短暂摘除失效地址；这比等所有节点拿到新目录更快，但局部错误也可能来自调用方网络，不能据此永久删全局实例。

注册表失联不等于所有业务实例都死了。A5 本地快照年龄最多沿用 5 秒，期间只调用符合兼容、身份和本地健康条件的实例；过期又没有政策允许的健康连接，就拒绝新 dispatch，不能无限使用旧 IP。长连接池如果允许继续用，要给同样明确的寿命、探测和撤销策略。快照年龄从可信接收时间计算，进程重启读磁盘不能把旧名单重新记成“刚收到”。年龄上限是教学策略。

替代可以是 DNS 或服务端负载均衡，不必为了名字到实例再造一套注册系统。普通稳定入口可以解析到虚拟地址，由后面的均衡器挑后端；某些 headless 记录直接列实例，TTL 与连接复用又决定更新速度。DNS 不天然只适合慢变化，也不天然保证秒级摘除。选择看平台已有的数据面、缓存语义和故障策略。Client-side discovery 的例图说明责任，不代表所有系统都必须让应用维护一份裸实例列表。

发现与配置的区别也落在责任。Registry 的数据是实例成员、地址与健康；超时阈值、灰度比例、开关属于 Ch28 的版本化配置。两种功能可以共用一个产品或底层 KV，但必须分别有成员寿命、健康检查与配置发布合同，不能用静态配置字符串冒充实时健康目录。发现选到 B 之后，剩余死线与幂等决定是否重试；权限失败、参数错误或整体过载不是“换个 IP 就再打一次”的理由。

English

The control plane registers READY instances and returns address/health/version snapshots. The data plane calls selected compatible endpoints directly and returns A → Caller → Client. Registry is not an RPC proxy. Consul documents service registration and health catalog; its Health API requires explicit passing filtering for an all-passing list. [3][4]

A5 gives a rough 3×2=6 s detection plus 1 s propagation budget, with check duration and jitter additional. Failure between checks leaves a healthy-looking snapshot. Caller absorbs timeouts and locally ejects addresses, but a local network problem should not permanently delete global instances.

Registry outage does not prove endpoint death. A5 permits snapshots for at most five seconds with compatibility, identity and local checks; without an approved healthy pool after expiry, reject new dispatch. Long-lived pools need explicit age/probe/revocation policy. Disk reload must not refresh a snapshot timestamp. This age cap is a teaching policy.

DNS or server-side balancing may already solve discovery. A stable name can resolve to a virtual address; headless records may list endpoints, with TTL and connection reuse affecting refresh. DNS is neither inherently slow-only nor a guaranteed instant ejection mechanism. Choose based on the platform, cache contract and failure behavior; client-side snapshots are one option.

Discovery owns membership, addresses and health; Ch28 configuration owns versioned thresholds, canary fractions and flags. A product or KV can implement both, but their health/lifetime and publication contracts differ. Selecting B does not authorize retry: remaining deadline and idempotency still govern, and permission/parameter/overload failures are not solved by another IP.

五 · 超时、取消和重试，必须共用一份预算5 · Deadline, cancellation and retry share one budget

中文

第五组是独立的只读库存查询接口，沿用 800 ms 总死线，不属于 A2 的受理步骤。每跳传播剩余时间。gRPC 文档说明默认可能没有死线，服务端需要停止自己派生出的工作；传播时可扣除已经过去的时间，避免让下游重新起一轮完整等待。[5][6] 实现还要核对具体语言与代理配置。教学策略在 Order 分配一次读库存调用的额度，连接建立、服务发现等待、线程排队和 RPC 处理都要扣。只设置 socket 读超时，可能把 DNS、连接和排队漏在死线之外。

A6 的时长条表示一次路径上的预算帽：本地 80 ms，第一次 220，退避最多 40，第二次 220，完成与回程 140，共 700 ms，800−700=100 ms 余量。这不是把五个组件的 P99 相加；预算内各阶段仍会失败。若第一次因连接拖到入口只剩 250 ms，先保留 140 ms 回程，再看 40 ms 退避，最多只剩 70 ms 给新 attempt。若 70 ms 不够完成有用调用，直接停止，次数未耗尽也可以停止。

为什么只能有一个重试 owner？假设五层串行调用，每层都允许最多 3 次总 attempt，底层最坏是 35=243 次，不是 5×3=15。这个独立坏例子的 3 与本章默认的两次总 attempt 不混用。网关、SDK、代理和业务代码若各自偷偷重试，就会让一个故障变成资源洪水。AWS 的可靠性文档要求限次数、退避与 jitter，并指出多层重试会复合放大。[12] 次数边界控制一条请求，额外流量预算控制整个服务，两个缺一不可。

A7 原始 200 次/秒，允许额外最多 10%，多出来 200×0.1=20 次/秒，所以总 attempt 预算是 220 次/秒。若全体都补一次，会变成 400 次/秒，虽每条都没超过两次，却超过全局预算；重试令牌耗尽就失败或按合同降级。退避随机化避免同一瞬间齐步重打，不增加吞吐。鉴权拒绝、业务冲突和不变的坏参数不会因退避修好；对方明确过载时，优先减少需求。熔断与舱壁的状态机回 Ch42，本章只钉住责任与额度。

超时、取消与业务撤销要分开。客户端到点不等，服务端仍可能已经提交；取消信号也可能晚到，所以写请求的结果是 UNKNOWN，必须查询同一 K。只读库存可以按预算重试，预占库存或扣款需要持久身份与下游保证。应用要停止排队和新增调用、释放连接与工作槽，但不能撤销已经发到外部系统的效果。接受事务完成后由后台继续履约，是 A2 合同允许的持久任务，不应被一个 HTTP 断开误删；要取消订单，应发有独立业务语义的取消命令。

English

Deck five is a separate read-only stock API with the same 800 ms deadline, not A2 acceptance. Propagate remaining time. gRPC notes that deadlines are not set by default, spawned server work must stop, and propagation deducts elapsed time; language and proxy behavior still need verification. [5][6] The teaching budget includes connection, discovery waiting, queueing and processing, not merely socket-read time.

A6 caps total 80+220+40+220+140=700 ms, leaving 100 ms under 800. These are caps, not summed component P99s. If 250 ms remains, reserving 140 for finishing and 40 for backoff leaves only 70 ms. If that is not useful, stop before spending a nominal second attempt.

In a separate worst-case example, five nested layers with three total attempts each produce 3^5=243 deepest calls, not 15. Do not confuse that example with the teaching two-attempt policy. Gateway, SDK, proxy and application retries must have one owner. AWS recommends caps/backoff/jitter and warns about compounded retries. [12] Per-operation count and service-wide extra-traffic limits solve different problems.

A7 adds at most 20 retries/s to 200 originals/s for 220 attempts/s. Retrying every request once gives 400/s and violates the global limit even though each respects two attempts. Spend retry tokens or fail/degrade. Jitter spreads traffic without creating capacity; authorization, conflicts and bad inputs remain terminal, while overload calls for reducing demand. Ch42 covers breaker/bulkhead state machines.

A client timeout or cancellation can arrive after commit, so writes remain UNKNOWN until K is resolved. Read-only stock can retry; reservation/payment needs durable identity and backend guarantees. Stop queued/new work and release resources, but do not assume external effects are undone. A2 durable fulfillment continues after HTTP disconnect; cancel an order through a separate business command.

六 · 幂等的权威要跨实例，未知结果不能过期放行6 · Durable cross-instance idempotency and UNKNOWN

中文

正常写请求有一份稳定业务意图。客户端生成 K=k17，作用域由非空 tenant、operation_type 和 K 组成，服务端要求这三列 NOT NULL，校验授权并规范化 payload 摘要。Order A 在 Order DB 中插唯一键，创建订单、写结果与 outbox，全部放在同一个事务。已存在同键且同摘要，就读取可信结果；同键不同摘要则冲突。PostgreSQL 的多列唯一约束能让并发实例竞争同一组合键，[8] 但“先查不存在再插”而无唯一约束会让两个实例同时放行。

窗口分三段讲。首事务没提交，异常回滚，可以用同 K 重新竞争；首事务已经提交且回程成功，再来返回原订单；首事务已经提交但确认丢失，A 与客户端只知道 UNKNOWN，换到 B 查共享记录才恢复。若首事务还在执行，唯一键可能等待，应用需要有界等待并返回 IN_PROGRESS，查询未解析状态不能误报“绝对不存在”。图上红线 Order DB → Order A → Gateway → Client 是第三种，绿色是另一条正常执行，不能解释成同一请求同时成功和失败。

把幂等放在 A 的本地内存、换实例后新建记录，都不能挡第二单。分开的 Redis 锁与订单库也不是自动原子：锁拿到后崩溃、锁 TTL 到期、旧执行还在跑，新执行就可能一起提交。图里用订单库的唯一记录与本地效果同事务，证明的是一份本地订单承诺。若长任务需要租约，旧 owner 的写入还得带代次并由权威拒绝；给锁延长 TTL 不是替代。幂等不是“不返回错误”，而是重复传输没有重复业务变化。

A8 保留合法重试窗口 7 天，K 与结果按 1 KB；把峰值 200 次/秒铺满整天只是采购上界，不是实际日流量。200×86,400=17,280,000 条/天，×1 KB=17.28 GB/天，×7=120.96 GB 逻辑记录。索引、副本和 outbox 另计。七天后可清理大结果，但本章永久保留紧凑 K→order 映射与原摘要，旧 K 只查订单状态，不当新意图。长期映射容量另计，120.96 GB 不是全库总量。未决 UNKNOWN 要保留与修复，不能因为七天到了就重新执行。

Stripe 文档可用来核对幂等请求的参数一致与保存结果语义，[7] 本章的七天和订单事务是自己的设计，不冒充 Stripe 参数。向支付服务再发请求时，需要向它传一个稳定的 payment_operation_id，并让支付权威原子防重、支持结果查询；订单库的 K 只能阻止重复建单，不能独自阻止外部第二次扣款。查询已存结果也需要当前对象权限，不能因为知道一个键就读取别人的订单或继续执行已被撤销的授权。

English

Scope K=k17 by tenant and operation type, require all three columns NOT NULL, authorize the request and normalize its payload digest. Order A atomically inserts the unique key, order, result and outbox. Same key/digest replays; changed intent conflicts. PostgreSQL composite uniqueness can arbitrate concurrent instances. [8] A check-before-insert without a unique constraint allows both to execute.

Before commit, rollback permits the same K to compete again. After confirmed commit, replay the original order. After commit with lost ACK, A/client know only UNKNOWN; B resolves shared authority. In-flight uniqueness may block, requiring bounded wait/IN_PROGRESS rather than an absence claim. Red and green paths show alternative executions, not simultaneous outcomes.

Instance memory and a separate expiring Redis lock do not prove one order. Old work can continue after lock expiry. The diagram proves one local order by committing unique identity and effect together. Long-task leases also need authoritative generation rejection; longer TTL is insufficient. Idempotency means repeated transport does not repeat the business change.

A8 seven days and 1 KB per K/result, with 200/s sustained all day as a bound, yield 17.28M/day, 17.28 GB/day and 120.96 GB logical records. Indexes, replicas and outbox are separate. After seven days the teaching policy removes large results but permanently retains compact K→order mappings and their original digest. Old K queries state rather than creating another intent. That long-lived mapping is sized separately; 120.96 GB is not the whole database. Do not free unresolved UNKNOWN for re-execution after seven days.

Stripe supports parameter matching and stored-result semantics, not this chapter’s seven-day Order policy. [7] External payment needs a stable payment_operation_id with payment-side atomic dedupe and result query; Order K alone cannot prevent a second external charge. Replaying stored results still requires current object authorization and does not revive revoked execution rights.

七 · 独立发布要有兼容窗口，追踪要看得见重试7 · Compatibility, rollout and observable attempts

中文

正常迁移先选一块能力，逐步把新流量切过去；Fowler 的 Strangler Fig 说明这种渐进替代思路。[10] 第七组聚焦同一个 Order 服务的 v1/v2 发布，两者共用同一份 K 权威和逻辑数据所有者，并没有创建两个可独立写订单的业务系统。抽出新服务若还要迁库，则需要额外的数据复制、追平屏障与写入所有权切换，不能从“Gateway 改路由”推导成数据已经安全迁完。图的证明范围是兼容代码发布，不代替迁库协议。

先 expand：新增可选字段，让旧代码和新代码都能读现有数据，事件版本也维持旧消费者可读。再切新意图，A10 的 10%×1,000=100 次/秒走 v2。既有 K 要能在其原路由或共享兼容权威中恢复，不能因为重试落在 v1/v2 而按新规则重复受理。只读查询可以做隔离影子比对；下单、扣款、发券不可以同时发两版来测正确率，即使两版都说自己支持幂等，也要证明键作用域和权威相同。

独立上线也要有容量。A9 是另一个读服务的发布场景，不和 200 次/秒订单混算：三台每台规划 600 次/秒，合计 1,800；排空一台剩 1,200，仍覆盖 1,000。若只买两台，排空后 600 不够，发布会自己造成过载。这个预算不证明整机损失或数据库故障可扛住；两台实例若同机，故障域还没拆开。READY 要在依赖、schema 与资源加载完成后报告，摘除后停止新请求，旧请求在有界窗口里排空，不让旧进程无限拖住发布。

失败时先停止给 v2 分新意图，再按兼容合同回退代码，已经提交的订单仍在权威库里，靠 operation_id 继续查询和处理。最后 contract 才删旧字段，要等旧实例、旧读者、回滚窗口和队列里旧事件都安全。新 schema 若让旧代码无法读，回退部署并不会恢复可用；业务状态改变后，回滚也不是把已支付订单删掉。迁移的退出条件要可观察：受理成功率、尾延迟、重复业务效果、未决结果与积压年龄都稳定，才扩大流量。

追踪只加够用的一层。W3C traceparent 带 trace-id 与 parent-id，使跨进程的父子关系可传播。[9] 一次用户请求有同一 trace，各 hop 建 span，同一 hop 的第二次 attempt 要用另一个 span 和 attempt_id，业务 K 保持不变。记录 route_revision、实例与版本、剩余死线、重试原因、operation_id，才能分清“总耗时 700 ms”是下游慢、排队还是退避。trace_id 不是幂等键，也不是权限证明；用户可提供的头要受信任边界处理。

English

Gradual replacement follows Strangler Fig. [10] Deck seven focuses on v1/v2 of one Order service sharing K authority and data ownership, not two independent business writers. A store migration additionally needs replication, catch-up barriers and write-owner transfer. Gateway routing alone proves none of that; the diagram covers compatible code release.

Expand optional fields and compatible event contracts before A10 canary sends 100 of 1,000 new requests/s to v2. Existing K must recover through pinned routing or compatible shared authority. Read-only shadow checks can be isolated; effectful dual-version mirroring needs proof of common scope and authority and is not the teaching rollout.

A9 is a separate read-service scenario: three planned 600/s instances provide 1,800/s; draining one leaves 1,200/s for 1,000/s demand. Two instances leave only 600/s. This does not prove host/store resilience; colocated instances share failures. Report READY after dependencies/schema/resources load, stop new intake on drain, and bound old in-flight work.

On failure stop assigning new intents to v2, then roll back compatible code. Durable orders remain queryable by operation_id. Contract old fields only after old instances/readers, rollback windows and retained events are safe. Deployment rollback cannot undo paid states or restore compatibility automatically. Expand only after intake, latency, duplicates, unknowns and backlog age remain healthy.

W3C traceparent carries trace-id and parent-id. [9] Use one trace with hop spans and separate spans/attempt_id for retries while K stays fixed. Record route revision, endpoint/version, remaining deadline, retry reason and operation_id to distinguish queueing, backoff and downstream time. Trace IDs are neither dedupe identities nor authorization; handle incoming context at the trust boundary.

追问：把答案指回路径Follow-ups: point back to a path

中文

为什么不按 Controller、Service、DAO 拆三层？因为业务改动仍穿过三队，数据与事务责任没有独立。按业务能力让一个所有者贯穿接口到数据，再看是否需要独立部署。DDD 的限界上下文和聚合规则留到 Ch45；一个限界上下文也不必机械映射一个进程。

为什么发现挂了还能活，Order DB 挂了却不能照样受理？实例地址是可短期缓存的候选信息，A5 给了年龄与本地探测边界；订单承诺的权威不能用地址缓存替代。业务数据与控制面状态有不同恢复合同。

邮件一定要异步吗？选择取决于用户合同。登录验证码可能是这次请求的必要结果，而下单通知可以晚到；两者都需要稳定消息身份与发送结果处理。不能按“邮件”这个名词一刀切，也不能把所有审计记录都延后：必须伴随业务提交的审计意图可与订单同事务，外部索引再异步。

重试能提高可用性吗？短暂丢包、兼容实例故障且余量还够时可能提高；全体下游过载时，它增加竞争。先看原始请求成功率、额外 attempt 比例和未知效果数量。只看重试之后 HTTP 的绿色比例，可能把重复扣款和更长等待藏起来。

English

Why not deploy Controller/Service/DAO separately? A business change still spans three teams without independent transaction responsibility. Let one owner span interface to data; deployment follows need. Ch45 covers bounded contexts/aggregates, which need not map mechanically to processes.

Why can discovery outage permit calls but Order DB outage prevent intake? Candidate endpoints can be briefly cached under A5 age/local checks. Cached addresses cannot replace durable Order authority. Control-plane information and business commitments have different recovery contracts.

Must email always be asynchronous? A login code may be required now; an order notification may be deferred. Both need stable identity and outcome handling. Likewise, audit intent required at commit can be stored atomically, while external indexing is deferred. Classify the contract, not the noun.

Can retries improve availability? Sometimes for transient loss or failed compatible endpoints with spare capacity; overload retries add contention. Measure original success, extra attempts and unresolved effects. Final HTTP success alone can hide duplicated effects and longer waits.
