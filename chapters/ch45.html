这一章结束你能做什么 What you can do after this chapter

本章把领域驱动设计（DDD）落到三个问题上：上下文说明业务词的含义，以及谁负责保存和确认事实；聚合保护每次提交时都必须成立的业务规则；集成契约约定跨边界使用的身份，以及失败后由谁恢复。我们沿着订单 o42 的明细修改、结账、收款和关单过程，看看这些决定怎样落实到聚合根的方法、版本条件和持久化事件中。

Make three decisions: contexts own meaning and facts, aggregates protect commit-time invariants, and integration contracts define identity and recovery across boundaries. Follow o42 through editing, checkout, capture and expiry into methods, version predicates and durable events.

30 秒开场：先问谁来确认“已支付” 30-second opening: where does this statement hold?

同样说“已支付”，支付模块（Pay）确认的是已完成收款这一资金事实，订单模块（Order）决定的则是能否接纳这笔钱、继续履约。聚合根的方法先产生符合规则的候选状态，再由数据库按条件提交；收款事实通过待发送事件（Outbox）、适配层和消费记录（inbox）交给订单。如果到期关单先提交，订单就保持 closed，并把退款义务存入数据库。退款调用超时时，结果记为 UNKNOWN，后续仍按原身份查询和恢复。

Where does paid hold? Pay proves capture; Order decides whether to accept that money for fulfillment. A root method produces a valid candidate, then a database predicate commits it. Outbox, adapter and inbox carry the fact across contexts. Expiry keeps the order closed and creates durable refund work; timeout leaves UNKNOWN under the original identity.

教学假设：用数字检查设计边界 Assumptions: numbers drive boundaries

本例以 USD 的整数分计价，修改明细后，订单总额从 8000 分变为 10999 分，版本从 v7 升到 v8；结账再冻结金额，进入 pending_pay v9。订单与库存（Stock）暂时共用数据库，支付模块独立提交。每个 payment_id 只对应一次全额收款；如果允许部分或多次捕获，就必须另设 capture_id 和金额处理规则。下面的吞吐、延迟和留存数字均为教学假设。

Main example: USD minor units, total 8000→10999; edit v7→v8 and freeze checkout as pending_pay v9. Order/Stock initially share a database; Pay commits separately. Each payment_id represents one full capture; partial or multiple captures need capture_id and an amount policy. Throughput, latency and retention values are teaching assumptions.

1 · 限界上下文：同一个词在两个模型中的含义 1 · Bounded contexts: owners of different facts

Order 的 paid 表示订单已接纳这笔收款、可以进入履约；Pay 的 captured 表示完成收款，reconciled 则表示后续核账结果。划分限界上下文时，要一起看词义、生命周期和决定权，再由业务专家确认。订单关闭后，支付审计证据仍须保留。[1][4]

Order paid means accepted for fulfillment; Pay captured is a money fact, and reconciled is a later comparison. Language, lifecycle and decision ownership suggest contexts for experts to confirm. Closing an order must preserve payment audit evidence. [1][4]

D1 中，每个存储都由所属模块写入，跨边界只传 ID、金额和币种。入口仍要校验租户与操作权限：order_id 只用于关联对象，不能授予写权限。托管 URL 只是支付入口；创建支付超时时，要查询原尝试的结果，不能以删除订单来撤销已经发出的外部动作。

In D1 each module writes its own Store; IDs, amount and currency cross the boundary. Authenticate tenant and operation authority: order_id correlates an object but grants no access. A hosted URL starts payment; setup timeout requires querying the original attempt. Deleting an order cannot undo remote work.

上下文可以先做成同一部署内的模块。只读组合和受控 JOIN 不授予跨模块写权限；如果按每个类拆服务，反而可能让必须同时成立的规则分散到网络两端。A5 的 20+40+120=180 ms 是按给定条件分配的阶段预算，给 300 ms 目标留下 120 ms 余量，不能据此保证请求 p99。若创建支付的尾延迟不可控，可以先返回已持久化的订单和可查询的 setup 状态，同时调整对用户的接口约定。

Contexts can begin as modules in one deployment. Read composition and controlled joins grant no cross-module write authority; per-class services can split an invariant across the network. A5 gives conditional stage budgets of 20+40+120=180 ms, leaving 120 ms, not a summed p99 guarantee. Unbounded Pay setup latency may require a durable order and queryable setup state with a revised user contract.

2 · 聚合：把必须同时成立的规则放进一次提交 2 · Aggregates: enforce invariants at commit

D2 中，订单聚合根 Order Root 与明细 Lines 共同保证：总额等于各行快照单价×数量之和，而且只有 draft 状态允许编辑。这类每次提交时都必须成立的业务规则，就是聚合的不变量。一个聚合可以存入多张表，但所有写入方都要执行完整规则。Vernon 的示例用持久化版本拒绝旧对象覆盖，并通过身份引用外部聚合。[1][2][3]

D2 puts Order Root and Lines behind two rules: total equals the sum of snapshot price×quantity, and only draft is editable. Several tables may represent the aggregate, but every writer must enforce its rules. Vernon uses persisted versions to reject stale objects and identities for external aggregates. [1][2][3]

聚合根方法：先构造符合规则的候选状态Root method: build a valid candidate before commit

下面摘录自一个只依赖标准库、可运行的 Java 17 示例。Money 不可变，金额与币种绑定，并使用 Math.addExact/multiplyExact 检查算术溢出。聚合根复制明细集合，构造器再复核总额与 SKU 唯一性。将 sku1 的数量改为 3，得到版本 v8、总额 10999 分；数量≤0、SKU 未知、订单已冻结或运算溢出时都会拒绝，原对象保持不变。

This excerpt comes from a runnable Java17 example using only the standard library. Immutable Money binds currency and uses Math.addExact/multiplyExact; the root copies its lines, and construction checks total and unique SKUs. sku1/3 yields v8 and 10999. Nonpositive quantity, unknown SKU, frozen state or overflow rejects without changing the original.

Order editQuantity(String sku, int quantity) {
    if (state != State.DRAFT) {
        throw new IllegalStateException("FROZEN");
    }
    if (quantity <= 0) {
        throw new IllegalArgumentException("QUANTITY");
    }

    List<Line> changed = new ArrayList<>(lines);
    int index = -1;
    for (int i = 0; i < lines.size(); i++) {
        if (lines.get(i).sku.equals(sku)) {
            index = i;
        }
    }
    if (index < 0) {
        throw new IllegalArgumentException("SKU");
    }

    Line old = lines.get(index);
    changed.set(index, new Line(old.sku, quantity, old.unitPrice));
    Money nextTotal = sum(changed, total.currency); // exact integer arithmetic

    return new Order(tenant, id, Math.incrementExact(version), State.DRAFT,
            changed, nextTotal, null, null); // candidate, not a committed result
}

只有数据库提交成功，才能把候选状态作为成功结果返回。A、B 同时读到 v7 后，只有一个数据库 WHERE version=7 条件更新能成功；影响 0 行时要报告冲突，不能提前把候选写入缓存。版本防止旧写覆盖，k42/hash/result 则用于找回“已经提交、响应却丢失”的原命令结果。即使订单后来已到 v9，重试 k42 仍返回原来的 v8 回执。[8]

A candidate is not a successful receipt. If A and B read v7, only one database WHERE version=7 can win. Zero rows means conflict; do not publish a candidate into cache. Version prevents stale writes; k42/hash/result recovers a committed command after a lost response. Even when a later edit reached v9, replaying k42 returns the original v8 receipt. [8]

# Pseudocode: authenticated tenant/order, one authoritative local database.
edit(auth, order_id, key, expected_version, sku, quantity):
  authorize(auth, order_id)                       # also on a replay
  hash = canonical_hash("edit-v1", auth.tenant, order_id,
                        expected_version, sku, quantity)

  BEGIN
  inserted = INSERT command_result(tenant, order_id, key, hash, result=NULL)
             ON CONFLICT (tenant, order_id, key) DO NOTHING
  if not inserted:
    saved = SELECT command_result WHERE (tenant, order_id, key) = scope
    ROLLBACK
    require saved.hash == hash                    # otherwise KEY_REUSE
    return saved.result                          # immutable original receipt

  before = SELECT root + lines WHERE tenant = auth.tenant AND id = order_id
  require before.version == expected_version     # otherwise ROLLBACK / CONFLICT
  next = before.editQuantity(sku, quantity)        # failure => ROLLBACK

  changed = UPDATE orders SET total=next.total, version=next.version
            WHERE tenant=:tenant AND id=:order_id
              AND version=:expected_version AND state='draft'
  require changed == 1                           # otherwise ROLLBACK / CONFLICT

  UPDATE order_lines SET quantity=:quantity
    WHERE tenant=:tenant AND order_id=:order_id AND sku=:sku
  UPDATE command_result SET result=:receipt_for_next
    WHERE tenant=:tenant AND order_id=:order_id AND key=:key

  COMMIT                                         # never commit result=NULL
  return receipt_for_next
# SQL/domain failure before commit => ROLLBACK; bounded whole-TX retry only
# for known aborted serialization/deadlock failures, using the same key/hash.
# Lost COMMIT acknowledgement => UNKNOWN; query this key, never reapply blindly.

这里的 BEGIN/COMMIT 是一个权威数据库中的本地事务，覆盖聚合根、明细和命令回执；请求唯一键为 (tenant,order_id,key)。参数摘要 hash 使用带类型、字段顺序固定的规范编码，包含命令类型、预期版本和全部业务参数。NULL 只是事务内的结果占位，绝不单独提交。同键并发请求由数据库唯一约束协调，等待或冲突后读取已提交结果。业务校验失败时整笔回滚；无法确认是否提交成功时，按原键查询。[8]

BEGIN/COMMIT is one authoritative database transaction over root, lines and command receipt. The unique key is (tenant,order_id,key). Hash a typed canonical encoding containing command type, expected version and all business parameters. NULL is an uncommitted placeholder, never a separate committed state. Concurrent same-key commands rely on the database constraint and read the committed result after conflict. Domain failure rolls back; uncertain commit requires an original-key lookup. [8]

默认应以一个聚合说明一笔事务。D3 为同库的 Order/Stock 使用同一事务，是本例有意放宽原则的工程选择，需要承担争用与部署耦合。如果每条命令都要修改多个聚合，就应先重新检查边界，不能把这种选择说成 DDD 的通用保证。仓储（Repository）也不能提供绕过聚合根、任意修改明细的接口。

Explain a transaction through one aggregate by default. D3 deliberately relaxes this principle for a local Order/Stock transaction and accepts contention and deployment coupling; this is an engineering choice, not a universal DDD guarantee. Revisit boundaries when every command touches several aggregates. Repositories must not expose arbitrary line writes that bypass the root.

3 · 库存：同库可以一起提交，热点仍需另算 3 · Inventory: locality and contention are separate

D3 把 v8 冻结为 pending_pay v9，并以结账请求 k9 建立唯一预占。A6 假设 Order/Stock 位于同一物理数据库，因此聚合根状态、available≥q 的条件扣减、预占记录和请求结果可以一起提交。任一 SKU 库存不足、版本冲突或事务中断，都会使整笔事务回滚；绿色回程表示已提交的结果。事务内不调用 PSP，多行加锁使用固定顺序；只有已知中止的事务，才可按原身份有界重试。[7][8]

D3 freezes v8 as pending_pay v9 and reserves under k9. Under A6 one physical database commits root state, available≥q decrement, reservation and request receipt together. Any shortage, version conflict or interruption rolls back the whole operation; green replies mean committed results. Keep PSP calls outside the transaction, use a stable row lock order, and retry known aborted transactions within a bound under the same identity. [7][8]

热点取决于数据本身。每笔排他占用 10 ms，得到乐观上限 1/0.010=100/s；每秒 300 笔则需要 3 秒占用/秒，排队无法稳定。增加应用实例不能让它们同时排他占有同一行。可以缩短事务、限制接入量，或预先划分库存份额；划分后，各份额之和仍不能超过真实库存。

The data still defines the hotspot: 10 ms exclusive occupancy gives an optimistic ceiling of 1/0.010=100/s; 300/s demands three occupancy seconds per second, so the queue cannot stabilize. More App instances cannot concurrently own that row. Shorten transactions, limit admission or preallocate stock shares while preserving total stock.

一旦拆成两个数据库，上述原子提交保证就不再成立。远程预占需要持久化身份、可查询结果和取消栅栏，单靠 TTL 挡不住迟到申请。关单释放也要按 reservation_id 保证幂等：同库时可以一起提交，跨库时先保存释放义务，再恢复执行；旧 release 不能释放新预占。完整路径见 Ch18/Ch21/Ch41。

Two databases lose that atomic contract. Remote reservation needs durable identity, queryable outcomes and a cancellation fence; TTL alone cannot stop a late request. Release is idempotent by reservation_id: commit locally when possible or persist remote release work before execution. An old release cannot free a newer reservation. See Ch18/Ch21/Ch41 for the full workflow.

4 · 领域事件：让两次本地提交之间的投递可恢复 4 · Domain events: close the delivery loop

D4 先由 Pay 校验 PSP 原始报文和支付尝试，再把收款身份、配平分录及 Outbox e17 放进同一数据库事务，提交后才确认回调。领域事件表示模型已承认的事实，对外集成事件则有单独维护的契约。本例保存当前状态和 Outbox；事件溯源（Event Sourcing）以权威事件历史重建状态，采用的是另一种存储方式。[1][11]

D4 has Pay verify the raw PSP message and payment attempt, then commit capture identity, balanced journals and outbox e17 before acknowledging the callback. A domain event is a fact acknowledged by the model; an integration event is a separately maintained contract. Current state plus outbox differs from Event Sourcing that reconstructs state from authoritative event history. [1][11]

如果先改数据库、再直接 publish，进程可能在两步之间崩溃，导致消息丢失；如果先 publish，又可能广播尚未提交的事实。Outbox 把发布义务一并纳入本地提交，Relay 扫描已保存的待发记录，收到符合约定的消息代理 ACK 后再标记。发送成功但 ACK 丢失，或收到 ACK 后、标记前崩溃，都可能重发 e17，所以消费端仍需幂等。[5]

Publishing after a database commit can lose the message in between; publishing first can announce an uncommitted fact. Outbox places the obligation in the local commit. A durable Relay scans and marks after the contracted broker acknowledgement. Lost ACK or a crash before marking can resend e17, so consumers still need idempotency. [5]

Order Adapter 把 inbox、状态决定和处理结果放进一次本地事务，提交后才 ACK，D6 会展开各个分支。若先单独提交 inbox，崩溃后的去重会抑制尚未发生的业务修改；若先 ACK，则失去消息重投的恢复入口。PSP ACK、消息代理 ACK 和消费 ACK 各自只确认自己这一步，不能据此判断订单已完成履约。[6]

Order Adapter commits inbox, state decision and result in one local transaction before ACK; D6 gives the branches. Committing inbox first can suppress an unapplied change after a crash; acknowledging first removes redelivery. PSP, broker and consumer acknowledgements each prove one step, never completed fulfillment. [6]

5 · 集成契约：把收款事实转成订单能处理的命令 5 · Contracts: translate facts instead of objects

D5 通过双方约定的发布语言（Published Language）传递事实，由适配层翻译成订单命令，避免复制 Pay 的内部对象。e17 携带来源、契约 v1、租户、p9/o42、尝试 a9、10999/USD 和支付版本 3。可信边界先验证来源，以及 Pay 持久化保存的业务绑定；聚合根再检查本地尝试、金额、币种与状态。消息载荷自称 tenant_id，并不能获得操作权限。[1]

D5 uses Published Language for facts and an adapter for translation into Order commands, without copying Pay objects. e17 carries source, contract v1, tenant, p9/o42, attempt a9, 10999/USD and Pay version 3. A trusted boundary verifies source and Pay’s durable binding; the root checks local attempt, amount, currency and state. A payload tenant_id grants no authority. [1]

这里有三种不同用途的身份：(source,event_id) 识别事件，防止同一消息重复处理；(tenant,payment_id) 在本例识别一次全额收款；Order.version 用于防止旧状态覆盖。同一次收款即使由 e17/e18 两个事件描述，也应返回同一业务结论；同一身份换了金额，则必须隔离。支付版本 3 与订单 v9 不可比较，时间戳也不能给所有事件确定先后顺序。Stripe 文档说明，事件可能重复，不同事件对象也可能描述同一业务对象，且投递不保证遵循生成顺序。[10]

Three identities serve different purposes: (source,event_id) identifies the delivery fact; (tenant,payment_id) identifies one full capture in this example; Order.version prevents stale state writes. e17/e18 for that capture return the same business outcome; changed amounts under one identity are quarantined. Pay version 3 cannot be compared with Order v9, and timestamps provide no total order. Stripe documents duplicates, separate event objects for the same business object, and no generated-order delivery guarantee. [10]

契约版本未知、金额错误或关联错误的消息，要进入持久化隔离区（Quarantine），保存原消息、原因和处理身份，确认隔离区已接管后才 ACK。若只是依赖暂时不可用，则保留重试入口。隔离区需要告警、负责人和受控重放流程；新增可忽略字段与改变金额含义，也要分别评估兼容性。PaymentCaptured 表示事实，RefundRequested 只是交给 Pay 校验和执行的意图，不能提前称为 Refunded。

Unknown schema or invalid amount/binding goes to durable Quarantine with original input, reason and identity, then ACK. A temporarily unavailable dependency retains a retry path. Quarantine needs an owner, alerts and controlled replay. Adding ignorable fields differs from changing amount semantics. PaymentCaptured is a fact; RefundRequested is an intention for Pay to validate, never a premature Refunded fact.

6 · 关单竞态：收到钱，还要判断能否履约 6 · Expiry race: acceptance differs from capture

D6 是状态图。有效收款处理与到期任务同时对 pending_pay v9 做条件更新，最多只有一个能提交成功。收款先提交，得到 paid v10；到期先提交，得到 closed v10，之后的迟到收款不能重新打开订单。图中的两条箭头表示互斥结果。

D6 is a state diagram. Valid capture and expiry race on pending_pay v9; at most one transition commits. Capture first gives paid v10; expiry first gives closed v10, and late capture cannot revive it. The arrows are alternative results, not unconditional writes.

聚合根返回决定与事件，网络调用留在根外Return decisions and events without network I/O in the root

下面的 Java 17 摘录接收已经过来源认证和业务绑定校验的 Capture。pending_pay 状态接纳收款；已 paid 且重复收到 p9 时，返回原结论；closed 收到 p9，或已 paid 后又收到 p10 时，产生退款候选，保留原订单。Money、不可变 Order、Decision 和事件类型均定义在完整源码中。此时所有结果都只是候选，数据库事务失败后，必须丢弃全部候选事件。

This Java17 excerpt takes an authenticated, binding-validated Capture. pending_pay accepts; paid/p9 returns the prior decision; closed/p9 or paid/p10 produces a refund candidate while preserving the order. The full source defines Money, immutable Order, Decision and events. These are candidates: discard every event when persistence fails.

Decision capture(Capture fact) {
    // Adapter already authenticated source and verified Pay's attempt binding.
    if (!tenant.equals(fact.tenant)
            || !id.equals(fact.orderId)
            || !Objects.equals(attempt, fact.attempt)
            || !total.equals(fact.amount)) {
        throw new IllegalArgumentException("CAPTURE_CONTRACT");
    }
    if (state == State.DRAFT) {
        throw new IllegalStateException("NOT_CHECKED_OUT");
    }
    if (state == State.PAID && acceptedPayment.equals(fact.paymentId)) {
        return new Decision(this, Outcome.ALREADY_ACCEPTED, List.of());
    }
    if (state == State.CLOSED || state == State.PAID) {
        var event = new RefundRequired(tenant, id, fact.paymentId, fact.amount,
                state == State.CLOSED ? "LATE_CAPTURE" : "EXTRA_CAPTURE");
        return new Decision(this, Outcome.REFUND_REQUIRED, List.of(event));
    }

    Order paid = new Order(tenant, id, Math.incrementExact(version), State.PAID,
            lines, total, attempt, fact.paymentId);
    return new Decision(paid, Outcome.ACCEPTED,
            List.of(new OrderPaid(tenant, id, fact.paymentId, paid.version)));
}

聚合根不判断 e17 是否重投，也不保证退款只发布一次。下面的数据库事务分别处理投递身份和业务身份，再将新决定产生的领域事件翻译成 Outbox 记录。拒收 p9 后的退款工作以 (tenant,payment_id) 保证唯一，首次分配退款身份 r17；后续 e18 复用原结论，不能再创建 r18。[6]

The root neither knows whether e17 was redelivered nor guarantees a single refund publication. The durable transaction below separates delivery and business identity and translates newly decided domain events into outbox rows. Refund work is unique on (tenant,payment_id), assigning r17 once. Later e18 returns the original decision without creating r18. [6]

# Pseudocode: Order Adapter, after source authentication and binding validation.
# One full capture per payment_id. All SQL below uses one Order DB TX.
consume(message):
  fact = strict_translate_v1(message)             # invalid => durable quarantine, then ACK

  BEGIN
  inserted = INSERT inbox(consumer, source, event_id, payload_hash, outcome=NULL)
             ON CONFLICT (consumer, source, event_id) DO NOTHING
  if not inserted:
    saved = SELECT inbox WHERE (consumer, source, event_id) = delivery_identity
    require saved.payload_hash == message.hash  # changed payload => ROLLBACK, quarantine
    ROLLBACK;
    ACK;
    return saved.outcome                         # prior committed decision

  fresh = INSERT capture_result(tenant, payment_id, fact_hash, outcome=NULL)
          ON CONFLICT (tenant, payment_id) DO NOTHING
  if not fresh:
    saved = SELECT capture_result WHERE (tenant, payment_id) = fact_identity
    require saved.fact_hash == fact.hash         # mismatch => ROLLBACK, quarantine
    outcome = saved.outcome                      # a different event can repeat this fact
  else:
    before = SELECT root + lines WHERE tenant=:tenant AND id=:order_id
    decision = before.capture(fact)              # immutable candidate + domain events

    if decision.next != before:
      changed = UPDATE orders SET state='paid', accepted_payment=:payment_id,
                                  version=:next_version
                WHERE tenant=:tenant AND id=:order_id
                  AND state='pending_pay' AND version=:before_version
      require changed == 1                      # 0 => ROLLBACK, bounded reload/retry

    for event in decision.events:
      if event is RefundRequired:
        work = INSERT refund_work(tenant, payment_id, refund_id, amount, state='pending')
          # UNIQUE(tenant,payment_id); stable refund_id r17 bound to these parameters
        public = RefundRequested(work.refund_id, event.payment_id, event.amount)
      else:
        public = translate_OrderPaid(event)
      INSERT outbox(event_id, public, state='pending')

    outcome = decision.outcome
    UPDATE capture_result SET outcome=:outcome WHERE identity=:fact_identity

  UPDATE inbox SET outcome=:outcome WHERE identity=:delivery_identity

  COMMIT;
  ACK                                            # no network calls inside this TX
# Any failure before commit rolls back inbox, state, result, refund work and outbox.
# Unknown commit => do not ACK; redelivery re-enters the same durable identities.

inbox 的主键为 (consumer,source,event_id)，capture_result 的主键为 (tenant,payment_id)，两者都保存摘要和不可变的处理结论。业务事实摘要 fact_hash 不包含投递 event_id，因此可以识别由不同事件描述的同一次收款。关联信息必须从可信的持久化映射中成功读出，不能把“查不到关联”与“读取失败”混为一谈。

更新聚合根时，如果 CAS 影响 0 行，就整笔回滚并重载；有界重试耗尽后仍不能 ACK。在本例的接纳与到期模型中，closed/paid 都是终态。退款分支即使不修改订单，也要把退款工作、处理结果和 Outbox 一起提交。

Inbox uses (consumer,source,event_id); capture_result uses (tenant,payment_id). Both retain hashes and immutable outcomes, with delivery event_id excluded from fact_hash. Binding reads must succeed against a trusted durable mapping; distinguish a missing binding from a failed read. CAS=0 rolls back everything before bounded reload, with no ACK on exhaustion. closed/paid are terminal for this acceptance/expiry model; refund branches without an order change still commit work, results and outbox together.

可以用这个反例检查恢复能力：先提交 inbox，再通过内存发起退款，进程一旦崩溃，就可能留下“消息已处理、却无人退款”的结果。本例把 inbox、拒收结论、r17 和 RefundRequested Outbox 放在同一事务中，提交后才确认消费。Order 保证关闭的订单不再进入履约，Pay 另行保证退款不超额，两边各有自己的规则与提交边界。一个补偿函数无法自动回滚两个系统。

The key counterexample commits inbox, then sends an in-memory refund: a crash leaves processed input and no refund owner. This model commits inbox, rejection, r17 and RefundRequested outbox together before acknowledging. Order prevents resurrection; Pay separately prevents excess refunds. One compensation function cannot automatically roll back both.

7 · 退款与恢复：结果未知时，继续保存并跟进 7 · Refund and recovery: own unknown outcomes

D7 中，Pay Adapter 先把 inbox、唯一的 r17 和退款执行意图提交到 Pay Store，再向 Bus 确认，扫描器负责接续尚未结束的工作。调用 PSP 时使用同一个 r17；确认成功后，提交结果和退款分录，再按前述发布路径，经 Pay Relay→Bus→Order Adapter 传递事实。消费 ACK 表示接管工作，不能据此提前显示 refunded。

In D7 Pay Adapter commits inbox, unique r17 and execution intent before acknowledging Bus; a scanner resumes the work. Call PSP under r17, then commit a definite result and refund journals before publishing through Pay Relay→Bus→Order Adapter. Consumer ACK proves custody of work, never a completed refund.

超时只能记为 UNKNOWN，因为 PSP 可能已经退款成功。此时要保留原金额、币种、身份及退款额度占用，查询原动作，或依据已核实的渠道约定安全重试；没有稳定查询能力时，转由人工核账。执行租约只能阻止旧执行者覆盖本地状态，无法拦回已经发给 PSP 的请求。

Stripe API v1 会保存开始执行后的首次结果，拒绝同键换参，并允许在至少 24 小时后清理记录；记录被清理后，再用原键可能创建新请求。这个规则不能直接用于 API v2 或其他渠道，也不能成为让 UNKNOWN 自动过期的理由。[9]

Timeout means UNKNOWN: PSP may have succeeded. Preserve original identity, parameters and reserved refund capacity; query or safely retry under a verified contract, otherwise reconcile manually. A worker lease only prevents stale local overwrites, not an already issued PSP request. Stripe API v1 retains the first result after execution begins, rejects changed parameters, and permits pruning after at least 24 hours; reuse after pruning can create a new request. Do not generalize this to API v2 or other providers, or expire UNKNOWN automatically. [9]

A10 的净排空能力为 600−300=300/s，因此积压 3.6 万条需要 120 s；若消费能力降为每秒 250 条，积压反而每秒增加 50 条。A11 保留七天、存三份的消息载荷为 300×86400×2000×7×3=1.08864 TB，资金凭证和索引另计。

幂等记录的留存要覆盖约定的重试与回放范围；未结束的退款工作则要一直保留，直到结果确定，或可靠地交由人工接管。监控时分别观察各阶段的数量和最老任务年龄。120 秒是吞吐条件下的追赶估算，不能当作每笔资金的 SLA。

A10 drains at 600−300=300/s, so 36000 entries require 120 s; at 250/s capacity backlog grows by 50/s. A11’s seven-day three-copy payload is 300×86400×2000×7×3=1.08864 TB, excluding journals and indexes. Idempotency records cover the retry/replay contract; unfinished refunds persist until a definite result or reliable manual custody. Monitor counts and oldest age per stage: the 120-second estimate is no per-payment SLA.

追问：什么变化会要求重新划分边界 Follow-ups: when should boundaries change?

中文

要求下单原子提交，并不意味着要把全站库存放进 Order。先说明可以采用同库短事务；如果所有命令都要一起修改同一组数据，再请业务专家检查是否存在共同的不变量、边界是否合理。

获取支付 URL 可以短时间同步调用，提交后的收款事实可以异步传递。每一步投递、接纳和恢复都需要明确负责人，内部规则仍可以放在本地事务中保证。

如果业务要求把历史作为事实来源，再讨论 Event Sourcing 的状态重建、兼容和回放成本。[11] 本例使用状态表与 Outbox 即可；是否采用 CQRS，也应由实际的读写需求差异决定。

English

Atomic checkout does not require global stock inside Order. State the local transaction choice; pervasive joint changes warrant expert review of real invariants.

Fetch a URL synchronously, propagate capture asynchronously. Own each delivery, acceptance and recovery; internal rules may remain local.

Consider event sourcing for authoritative history and its reconstruction, compatibility and replay costs. [11] Tables/outbox suffice here; CQRS needs read/write differences.
