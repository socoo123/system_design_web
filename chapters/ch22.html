本章主线：名字、版本、字节各由谁负责The thread: authority over names, versions, and bytes

先讲闭合的上传 → 发布 → 固定版本读取 → 逻辑删除 → 物理回收；22.6 再把上传拆成并发 parts。中间四组保留演示分别回答小对象打包、三副本、纠删码和名字分片怎样改变成本。

Walk through upload → publication → pinned-version read → logical deletion → physical cleanup, then split uploads into concurrent parts in 22.6. The other four preserved decks explain packing, replication, erasure coding, and name sharding.

范围是单地域、允许覆盖和保留版本的对象 API。Metadata 决定 tenant/bucket/key 的权限、current、上传状态与原结果；Data 保存不可变字节、校验和冗余。Metadata 成功必须同时有完整 Data 回执和已提交的名字；上传超时只表示结果未知。

The scope is a one-region object API with overwrites and retained versions. Metadata owns scope authorization, current, upload state, and saved results; Data owns immutable bytes, checksums, and redundancy. Success needs both a complete Data receipt and committed naming metadata. Upload timeout is an unknown outcome.

先确认三项契约Three contracts to settle

读什么：无版本 GET 解析 current 并固定一个版本，显式版本读仍须鉴权。成功什么：本设计单键线性化；多片 LIST 无共同快照，弱于公开 S3。删什么：delete marker 只改变名字，保留版本、读租约和未决上传分别保护字节。[1][9]

Read: resolve current once or authorize an explicit version. Success: single-key linearization, with a weaker LIST contract than public S3. Delete: a marker changes naming; retained versions, read leases, and unresolved uploads independently protect bytes. [1][9]

Metadata is one billion ×1,000 B=1012 B=1 TB, averaging 1,000/64=15.625 GB across 64 shards, or 3 TB with three copies. The raw notes’ 68 million ×1 KB is only 68 GB, not 0.5–1 TB. Sharding is also about write load, recovery, and management budgets, not a claim that a database cannot hold tens of GB.

PUT payloads are 1,000×2 MB=2 GB/s=16 Gb/s; GET egress is 10,000×1 MB=10 GB/s=80 Gb/s. This design streams through API, so it carries bytes. One NIC receives Client PUT16+Data GET80=96 Gb/s and sends Client GET80+Data PUT16=96 Gb/s. At 5 Gb/s per direction, ceil(96/5)+1=21 boxes; 20 survivors provide 100≥96 Gb/s. Protocol, TLS, and CPU require measurement; the NIC quotient is not a final instance count.

22.1 · 先落字节，原子发布，再按版本读22.1 · Durable bytes, atomic publication, pinned reads

三个身份，不能互相代替Three identities with different jobs

name=(tenant,bucket_id,key 的原始字节) 是可变入口；只规范化 bucket 身份，不擅自 trim、改大小写或归一化 key。(name,principal,operation_id) 认领一次请求；初始化在同片唯一约束下保存意图、upload_id 与 version_id，重试返回同一份身份。(version_id,layout_generation,part_attempt_id) 指定物理内容和布局；内容不变，压缩或重编码可以切到新布局。A4 的 1 KB 只预算 current 行，版本记录和可分级存储的块摘要/manifest 另计。

name=(tenant,bucket_id,exact key bytes) is mutable. Normalize bucket identity without trimming, case-folding, or normalizing key bytes. A unique (name,principal,operation_id) claims the request and durably stores its intent, upload id, and version id. (version_id,layout_generation,part_attempt_id) identifies immutable content and its physical layout; compaction may change layout without changing the logical version. A4 budgets only the 1 KB current row; version records and hierarchical block manifests/digests are additional metadata.

为把身份问题讲清，本示例初始化时已知长度和整对象 SHA-256，意图还绑定冗余策略及 expected_generation。换内容、目标、长度或前提不能复用同请求；接收未知长度流的协议需要另外冻结配额与最终校验契约。两个不同请求写同 key 分配不同版本；带相同 expected_generation 的竞争者只能一人发布，无条件写则按 Metadata 串行提交决定 current，不能按客户端时钟或 init 时刻排序。

This example knows length and whole-object SHA-256 at initialization and binds redundancy and expected_generation in the intent. A changed payload, target, length, or precondition needs a new request identity. Unknown-length streaming needs a separate quota/final-validation contract. Different requests allocate different versions. One matching-generation contender publishes; unconditional writes follow serialized Metadata publication rather than client clocks or initiation time.

发布代码：一个名字分片里的真实原子边界Publication: the actual atomic boundary on one name shard

以下为 PG18 风格伪代码，输入认证 principal、初始化返回的 upload_id、冻结清单摘要和可信 Data 回执。Data 的 receipt 验证发生在事务外；它由受信服务签发，绑定精确字节身份、长度/摘要和放置代次，不能相信客户端报告“已上传”。版本行、current、upload 与固定结果共置一片；数据库事务不包住远端磁盘。[10]

This PG18-style pseudocode accepts an authenticated principal, initialized upload id, frozen manifest hash, and trusted Data receipt. Data verification is outside the transaction. Its issuer binds exact bytes, size/digest, and placement generation; a client declaration is insufficient. Version, current, upload, and saved result share a shard. The DB transaction does not include remote disks. [10]

publish(actor, upload_id, fence, manifest_hash, durable_receipt):
  saved = Metadata.authorized_result(actor, upload_id, manifest_hash)
  if saved is terminal: return saved.result        // includes REJECTED; even after payload GC
  proof = Data.verify_receipt(durable_receipt)      // trusted issuer, exact immutable blobs
  // Data error: query that same authorized result again; unresolved stays UNKNOWN.
  BEGIN                                           // one Metadata name shard; no Data RPC inside
  name = SELECT namespace FOR UPDATE              // tenant + bucket + exact key bytes
  u = SELECT upload FOR UPDATE                    // fixed lock order: name -> upload
  authorize(actor, name, "PUT"); require u.owner == actor
  require u.manifest_hash == manifest_hash         // exact frozen part identities + order
  if u.saved_result is terminal:                    // result survives cleanup state transitions
    COMMIT; return u.saved_result                  // original version, never current again
  require u.state == FINALIZING and u.fence == fence
  require proof.binds(name, u.version, upload_id, fence, manifest_hash)
  require proof.size == u.expected_size and proof.sha256 == u.expected_digest
  require proof.meets(u.frozen_policy)             // 3 replicas OR all 6 EC fragments
  if u.expected_generation != ANY and name.generation != u.expected_generation:
    UPDATE upload SET state=REJECTED, fence=fence+1, saved_result=CONFLICT
    COMMIT; return CONFLICT                        // durable terminal decision, same retry
  INSERT version(name, u.version, u.frozen_manifest, state=PUBLISHED)
  UPDATE namespace SET current=u.version, generation=generation+1
  UPDATE upload SET state=COMPLETED, saved_result=(CREATED, u.version)
  COMMIT                                           // version + current + result are all-or-none
  return saved_result                              // COMMIT timeout => UNKNOWN, query same upload

authorized_result 是 Metadata 对同上传的权威只读查询：重新验证 tenant/bucket/key 权限、owner 和冻结清单摘要后，读取不可变原结果。它不查询 current，也不重新要求旧 payload 存在。合法回收旧版本之后，完成请求仍重放原 version；持久 CONFLICT 同样重放。主事务重新鉴权并检查结果/state/fence，关闭查询与提交之间的竞争。保存请求身份/结果至少覆盖承诺的重试窗口，过期身份必须拒绝而不能当新请求执行。

authorized_result is an authoritative Metadata lookup for this upload: reauthorize the full scope, owner, and frozen manifest hash, then read the immutable original result. It neither resolves current nor requires the old payload to survive. After lawful old-version GC, completion still replays the original version; a durable CONFLICT also replays. The transaction rechecks authorization, result, state, and fence. Retain identities/results throughout the promised retry window; reject expired identities rather than treating them as new operations.

两个崩溃窗口：Data 已耐久、Metadata 未提交，只留下不可见候选；Metadata 已提交、响应丢失，对象已经可见。两者都查询同 upload/operation，未知保持 pending，不换新身份盲传，不用一次空查询授权删除。单键强读依赖共识 Metadata 的权威已提交读与 leader fencing；权威不可达就失败。公开 S3 的原子单键/写后读契约只是接口参考，不证明本示例实现。[1]

Two crash windows: durable Data without Metadata commit leaves an invisible candidate; commit with a lost reply leaves a visible object. Resolve the same upload/operation; uncertainty remains pending. Do not blindly create another identity or authorize cleanup from an empty lookup. Strong point reads need authority reads of committed consensus Metadata and fenced leaders, failing on unavailable authority. Public S3 is an API reference, not proof of this implementation. [1]

读取：先授权并固定 manifest，再验证每块Read: authorize and pin the manifest, then verify every block

GET 的顺序是 Metadata → Data。Metadata 在同一代次的事务中解析 current/显式版本、检查权限和可读态、登记带 principal 的 read lease，再返回固定 manifest；GC 的 RECLAIMING 与此过程串行。Data 内部能力必须绑定完整 scope、版本/布局/块、允许范围、GET 操作、受众和期限，校验可信签名与封代次；知道 version_id 或拿到其他租户的 receipt 都不授权读取。

GET runs Metadata → Data. One authority transaction resolves current/explicit version, authorizes readability, and registers a principal-bound read lease, serialized against RECLAIMING. Return a pinned manifest. Internal Data grants bind full scope, version/layout/block, allowed range, GET, audience, and expiry, with trusted signatures and fencing. A guessed version id or another tenant’s receipt grants no access.

下面是 Java 17 可运行示例中的块校验方法。Expected 来自已授权的可信 manifest；Identity 含 tenant、bucket、key、version、layout 和 block。每块在交给客户端之前核对身份、长度和 SHA-256；坏副本只触发另一个同版本副本的尝试。不是把副本随字节附的自报 checksum 当权威。完整类与运行方式。

This is a block-verification method from the runnable Java 17 example. Expected comes from the authorized trusted manifest; Identity includes tenant, bucket, key, version, layout, and block. Verify identity, length, and SHA-256 before releasing a block. A bad replica triggers another replica of the same version, rather than trusting the checksum supplied alongside its bytes. Full class and run instructions.

public static byte[] readBlock(Expected expected, List<Replica> replicas) throws IOException {
    // expected comes from the trusted, pinned manifest, not from the selected replica.
    for (Replica replica : replicas) {
        final Record candidate;
        try { candidate = replica.fetch(expected.id()); }
        catch (IOException unavailable) { continue; }
        if (candidate == null || !expected.id().equals(candidate.id()) || candidate.bytes() == null) continue;
        byte[] bytes = candidate.bytes().clone();  // never expose unverified mutable input
        if (bytes.length != expected.size()) continue;
        if (!MessageDigest.isEqual(sha256(bytes), expected.sha256())) continue;
        return bytes;                            // only now may this block reach the client
    }
    throw new IOException("No verified replica for the pinned block");
}

public static byte[] sha256(byte[] bytes) {
    try { return MessageDigest.getInstance("SHA-256").digest(bytes); }
    catch (NoSuchAlgorithmException impossible) { throw new AssertionError(impossible); }
}

大对象按有界块验证并流式发送，所有块绑定同一 manifest，不能中途重查 current 拼接新版。仅在结束时算整体 hash 无法撤回先前已发字节；因此要逐块可信摘要，接收端仍核对最终长度/整对象摘要并把中断视为不完整传输。CRC32C 可以另作快速偶发损坏检测，既不是身份认证，也不等于整对象 SHA-256；multipart ETag 也不应当作通用 MD5。[6]

Stream bounded blocks from one pinned manifest; never re-resolve current and splice a newer version. An end-only hash cannot retract bytes already sent. Use trusted block digests and have the recipient verify final length/object digest, treating interruption as an incomplete transfer. CRC32C may provide fast accidental-corruption detection, not authentication or whole-object SHA-256; a multipart ETag is not universal MD5. [6]

删除与 GC：先关入口，等持有者排空，再删精确字节Deletion and GC: close admission, drain holders, delete exact bytes

开启版本保留时，DELETE 发布 delete marker；新的无版本 GET 不存在，仍保留的显式版本按权限可读。它不是销毁旧 payload 的授权。版本保留结束且不再是 current 后，权威先撤销可读引用、变 RECLAIMING 并封代次，拒绝新解析和续租，之前获得的读租约可以完成。A11 的 60 秒是最长单次租期，长读须续租；续租失败就停止。[9]

With version retention, DELETE publishes a marker: new unversioned GET sees absence, while authorized retained version reads remain possible. It does not authorize payload destruction. Once retention clears and the version is no longer current, authority withdraws readable references, enters RECLAIMING, and fences new resolutions/renewals; preexisting leases may finish. A11’s 60 seconds is a maximum per lease; long reads renew or stop on failure. [9]

claim_gc(candidate):                               // absence/elapsed TTL alone never authorizes delete

未发布候选的十分钟隔离期只减少无效清扫，真正的授权是同权威状态、无保留引用、过期租约与新 fence。Data 必须持久关闭旧代次的新写并排空已接收的 writer，之后重复扫尾；旧请求仍可能晚落字节，但已不能注册或发布。若 Data 不确认已排空，就留字节重试。FINALIZING 不可被普通过期扫描接管；专用恢复者只续跑固定清单，需要终止则先在权威显式封代次，不能靠 TTL 猜。

A ten-minute unpublished-candidate quarantine reduces wasted cleanup; authorization comes from one authority state, no retained references, expired leases, and a new fence. Data durably closes old-generation writes and drains admitted writers before repeated sweeps. Late bytes cannot register or publish. If drain is unknown, keep bytes and retry. Ordinary expiry scans cannot take FINALIZING; dedicated recovery resumes its fixed manifest or explicitly fences it before termination.

能力与租约是有限授权：本章允许先前已获租约的读继续至期限。若业务要求 ACL 撤销立即阻断正在读的内容，Data 还需在线撤销检查/权限代次屏障，缓存 ACL 或短有效期本身不能做到。签名直传可把字节从 Client 直接送到 Data，但仍受限于目标、方法、期限和限额，Metadata 最后检查 durable receipt 才发布；这个上传路径是本设计选择，不声称公开 S3 使用相同内部协议。[11]

Grants and leases are bounded authorization: preexisting reads may continue until expiry. Immediate revocation of ongoing reads requires an online revocation/permission-generation barrier at Data; cached ACLs or short expiry alone cannot deliver it. Direct signed upload can send bytes Client→Data, bounded by target, method, expiry, and quotas; Metadata still verifies durability before publication. This is our design, not a claim about S3 internals. [11]

22.2 · 小对象打包：省元数据，不承诺零寻道 22.2 · Packing: less metadata, not zero seeks

正常路径：追加记录，封存文件，索引定位 Walkthrough: append records, seal packs, locate offsets

A7 的一百万个十 KB 对象只有十 GB 字节，却是一百万条目录项和 inode 的管理任务。Data 把多个对象追加进目标一 GB 的 pack，单个记录带 object_id、version、长度、checksum 和边界标记；大约十个 pack 就放下这一批逻辑数据。节点的本地索引保存 id→pack/offset/size，索引可持久化，但追加日志才是恢复记录内容与边界的依据，写确认必须涵盖必要的日志落盘。

A7’s million 10 KB objects hold 10 GB but create a million directory/inode management tasks. Data appends records with object id, version, length, checksum, and framing into roughly ten 1 GB packs. A local id→pack/offset/size index locates records. It can be persisted, but the append log supports reconstruction and must be durable before confirmation.

文件到阈值便 seal，只读文件便于校验、编码与压缩。每磁盘组或写入分区保留独立可写 pack，避免全局只有一个追加锁；同 pack 的并发写由单个拥有者排序，换代后旧拥有者被 fencing。末尾半条记录靠长度、校验和提交边界识别，恢复时截断未确认尾部。不是把内存索引更新了就成功，进程崩溃之后还必须找得回所有已确认记录。

Seal at the threshold for read-only checksumming, coding, and compaction. Keep independent writable packs per disk group or write partition rather than one global append lock. One owner orders a pack’s appends and is fenced after replacement. Framing and checksums identify torn tails; recovery discards unconfirmed tails. An in-memory index update alone cannot justify success.

为什么：Haystack 借机制，历史数字留在原论文 Why: borrow Haystack’s mechanism, not its historical scale

Haystack 论文说明，把多张照片放进大文件并缩小每条定位元数据，使文件系统查找信息能留在内存，磁盘操作主要用于读实际内容 [2]。本章借的是合并与偏移索引，不照搬论文里的文件大小、吞吐或照片规模。一次孤立的随机对象读仍可能要一次磁盘 I/O；索引失效还可能额外读盘。合并消掉的是许多文件管理操作，不是把随机读取变成内存命中。

Haystack describes large files and compact lookup metadata held in memory, reserving disk work for payload reads [2]. This chapter borrows packing and offset lookup, not its historical file sizes or scale. An isolated random read may still need a disk I/O, and an unavailable index can add more. Packing reduces file-management work rather than guaranteeing a memory hit.

因此不把“一对象一文件”说成所有场景都错。对象数量少、文件系统元数据已缓存、存储是合适的 SSD 时，它可以是简单起点。A1 的规模与 A2 的大量小对象才逼出 pack。pack 的代价是垃圾回收、坏记录隔离和空间回收延迟；若数据只追加且很少删，这笔代价便宜，频繁修改与删除则要重新评估压缩写放大，不能只看省了多少 inode。

One file per object can be a simple start for a small count, cached metadata, and suitable SSDs. A1’s scale and A2’s many small objects motivate packs. They add garbage collection, record isolation, and delayed space reclamation. Append-heavy workloads make that cheap; frequent modification or deletion requires measuring compaction amplification.

故障窗口：复制、切指针、退休不能揉成同事务 Failure windows: copy, pointer switch, and retirement are separate

压缩先从 Pack A 的 generation 7 选存活记录，写 Pack B 并等校验及冗余策略满足；随后用 Metadata 的 CAS 切到 generation 8；最后才退休 Pack A。复制中崩溃，旧 manifest 仍可读；切完后退休失败，暂时浪费容量；切之前就删旧文件则会丢读。元数据事务与远端文件 unlink 属于不同系统，不能说“同一个事务修改映射并删旧文件”就跳过这个窗口。

Compaction copies generation 7’s live records from Pack A into durable verified Pack B, CAS-switches Metadata to generation 8, then retires Pack A. Copy crashes leave the old manifest readable; retirement failures waste capacity temporarily; early unlink loses reads. A metadata transaction and remote unlink are different systems, so one transaction cannot erase this window.

压缩期间发生 DELETE，必须重新校验存活代次，不能把快照中的已删记录重新发布。旧压缩器的 CAS 如果失败，它只能丢弃候选或重读，不可覆盖新 manifest。已发布旧版本仍有引用时，该记录不会因 current 切走就成为垃圾；显式 version GET 也会取 read lease。Pack 的退休要以所有记录引用和所有读代次都结束为条件，不能只检查“没有 current 指向这个 pack”。

A DELETE during compaction requires rechecking live generations rather than resurrecting a copied record. A failed CAS must abandon or reread the candidate. Retained old versions remain referenced after current moves, and explicit version GETs acquire leases too. Retiring a pack requires no remaining record references or readers, not merely no current pointer.

替代与计算：垃圾比例决定压缩何时值得做 Alternative and arithmetic: dead bytes set the compaction decision

若一个一 GB pack 仅有百分之十已删，压缩要读一 GB、写约九百 MB 才释放一百 MB，回收每一字节大约付出十九字节 I/O。若已删八成，读一 GB、写二百 MB 能释放八百 MB，约付出 1.5 字节 I/O。这里假设顺序扫描全文件且不计冗余，实际副本或编码会继续放大写量。优先压缩垃圾多的封存文件，并保留足够临时空间，才能避免在磁盘快满时才发现没地方放新 pack。

With 10% dead bytes, compacting a 1 GB pack reads 1 GB and writes 900 MB to reclaim 100 MB, about 19 bytes of I/O per reclaimed byte. At 80% dead, it reads 1 GB and writes 200 MB to reclaim 800 MB, about 1.5. This assumes a full sequential scan before redundancy overhead. Prioritize dead-heavy sealed packs and reserve temporary capacity.

22.3 · 三副本：空间账与确认条件一起说 22.3 · Three replicas: bytes and the acknowledgement gate

正常路径：Data 直接扇出，每份单独确认 Walkthrough: direct fan-out and separate acknowledgements

三副本组把 Data 内部展开。API 把对象流给 Data，Data 直接向 Replica A、B、C 写同一版本，各自校验并完成持久写，再把 ack 回给 Data。主线要求三份到齐才给 durable receipt；API 仍要走第一个 deck 的 Metadata 发布才对 Client 成功。图上不是 A→B→C 的接力，也没有 Replica 绕过 Data 与 API 把结果直接送给客户端。

Data fans the same version directly to Replica A, B, and C. Each verifies, persists, and independently acknowledges to Data. The baseline receipt requires all three. API still publishes through deck 1’s Metadata before Client success. There is no A→B→C relay and no replica bypassing Data and API.

A3 的热层二十 PB 需要 20×3=60 PB 副本字节；另外的八十 PB 不套这个系数。热层包括多种对象大小，选择依据是访问频率、尾延迟和修复速度。小对象先批量封存再编码，能避免每次十 KB 写都启动多块编码；但不能因为编码慢就让全部百 PB 永远复制三份，100×3=300 PB 与混合方案的 180 PB 相差 120 PB。

A3’s 20 PB hot tier needs 20×3=60 PB of payload copies. Its sizes vary; frequency, tail latency, and repair speed determine placement. Small writes can be batched before coding instead of encoding every 10 KB record. Keeping all 100 PB at three copies costs 300 PB rather than the mixed 180 PB, a 120 PB difference.

为什么：放置和读校验是冗余的一部分 Why: placement and verified reads are part of redundancy

三份落在三个 AZ，再在各自 AZ 里分开机架、主机和磁盘，防止一个交换机、供电或控制器拖垮多个拷贝。部署平台报告“节点健康”不代表字节未损坏，GET 与后台 scrub 都要重新算 checksum。一个副本读出不匹配，Data 记录坏版本与代次，改读其他已验证拷贝，回程仍是 Replica→Data→API→Client；不能把损坏内容带着 200 直接交给用户。

Place copies across three AZs and distinct racks, hosts, and disks. Node health does not prove byte integrity: GET and scrub recompute checksums. On a mismatch, Data marks the damaged generation and reads another verified copy, preserving Replica→Data→API→Client. Never return corrupted bytes as a successful read.

CRC32C 适合检测意外传输与盘上错误，但不是防恶意篡改的身份认证；有这个威胁时，需要可信元数据里的强摘要与认证、加密协议。客户端传来的 checksum 也必须与权限及请求身份绑定。S3 支持多种 checksum，并明确 multipart 的 ETag 不等于整对象 MD5 [6]；本章选择自己的 CRC32C 记录校验，不把一个历史 ETag 规则当作所有对象的完整性证明。

CRC32C detects accidental corruption, not malicious authentication. Adversarial integrity needs trusted digests plus authenticated encryption/protocols. Bind a client checksum to authorization and operation identity. S3 documents multiple algorithms and non-MD5 multipart ETags [6]; this design’s CRC32C record check does not turn an ETag into universal integrity proof.

故障与替代：三份不足时能不能继续接写 Failure and alternatives: writes with a missing copy

一份无确认，Data 本地超时，不发明来自故障盘的 timeout 回复。此时默认拒绝新 PUT，保留已完成的两份并查询操作状态，后续可补第三份再发布；已经发布的对象仍可读存活副本。这个选择使单 AZ 故障时读可继续，写可用性下降。若要降为两份就确认，必须把降级策略写进耐久契约，设缺副本数量与时间预算，不能一边喊三份保证，一边后台再慢慢补第三份。

A missing ack triggers a local Data timeout, not a fabricated disk reply. Baseline PUTs fail, preserve completed copies, and may add the third before publication. Published objects remain readable from survivors. AZ loss preserves reads but reduces writes. A two-copy degraded acknowledgement needs an explicit durability policy and deficit/time budget rather than claiming three-copy protection.

普通副本修复需要从一个健康副本读一份再写一份。若缺一 TB，约读一 TB、写一 TB；只按 A8 的五百 MB/s 读取预算算，理想至少 1,000,000/500=2,000 秒，约三十三分钟二十秒。实际还要加目标写带宽、校验、排队和竞争流量，不能把这一下限写成修复 SLO。修复期间一旦又损坏，要看剩余拷贝与失败域，不能假设第二次故障与第一次独立。

Replica repair reads one healthy copy and writes one replacement. For 1 TB missing, that is about 1 TB read plus 1 TB written. A8’s 500 MB/s aggregate read budget gives an ideal 1,000,000/500=2,000 seconds, or 33m20s. Target writes, checksums, queues, and competition increase this lower bound; it is not a repair SLO.

22.4 · 4+2 纠删码：省盘，修复吃网络 22.4 · 4+2 erasure coding: less disk, more repair traffic

左侧收紧后的 Data 框与竖线属于同一服务；竖线只是六组块收发端口，未新增中间组件。故障帧由 Data 本地验证 B0，读 B1–B4 解码，B5 的未用通路淡化；“读四写一”是该次修复，不是健康写的路径数。

The compact Data box and port spine are one service, with no added intermediary. In the fault frame Data locally rejects B0, decodes B1–B4, and leaves unused B5 muted. “Read four, write one” describes this repair, not healthy-write fanout.

正常路径：六个块，四份信息量 Walkthrough: six fragments holding four fragments of information

教学 Reed–Solomon 码把一个 stripe 的 payload 分成 k=4 个等长 data 块，再算 m=2 个 parity 块，共六块；健康全量读取四个 data 块就能拼回。理想 MDS 码在六块里任选四块足以解码，但块必须属于同一 stripe 与 generation，并且校验可信。parity 不是完整对象副本，也不是简单 XOR 两次就证明任意两块可丢；具体码的矩阵与实现要符合这项属性。

Teaching Reed–Solomon splits a stripe into k=4 equal data fragments plus m=2 parity fragments. Healthy full reads fetch the four data fragments. An ideal MDS code decodes from any four of six, provided they share stripe/generation and trusted checksums. Parity is not a full copy; the actual code must implement the claimed property.

容量倍率 (k+m)/k=6/4=1.5；八十 PB×1.5=120 PB。热层六十 PB加容量层一百二十 PB，总计 180 PB payload 物理字节，是逻辑百 PB 的 1.8 倍。这里尚未算版本保留、未完成 part、临时压缩双份、容量碎片与空闲修复盘，因此是规划下限。若新 PUT 字节也按20%副本/80%编码，才有2×1.8=3.6 GB/s；若先全写三份则2×3=6 GB/s，转码另计。

The multiplier is (k+m)/k=6/4=1.5: 80 PB becomes 120 PB. Adding the 60 PB hot tier gives 180 PB of payload bytes, 1.8× logical capacity. Versions, incomplete parts, compaction overlap, fragmentation, and repair reserve are excluded. Only if new PUT bytes also split 20% replicated/80% coded does 2×1.8=3.6 GB/s apply. All-replicated hot ingestion instead uses 2×3=6 GB/s, plus later recoding.

为什么：失败域要按每个 stripe 验算 Why: evaluate placement per stripe

图上 A、B、C 三个 AZ 各放两块，不同块放不同机架。失去一个 AZ，丢两块，剩四块，满足解码门槛；失去两个 AZ，丢四块，只剩两块，无法恢复。说“有两块冗余所以能丢任意两个 AZ”是把块和区域混为一谈。即使每个 stripe 分开机架，全地域级的软件缺陷、凭证误删或控制面错误仍可能相关，冗余方案不能消除所有共同失败。

The picture places two fragments per AZ on separate racks. One AZ loss removes two and leaves four, enough to decode. Two AZ losses remove four and leave two, insufficient. Two parity fragments do not imply tolerance of two AZs. Region-wide software defects, accidental deletion, or control-plane mistakes remain correlated risks.

正常 PUT 等六块 durable 再发布，牺牲部分故障时写可用性，换来发布时完整的冗余。丢两块之后虽然还能读取，但任意额外坏块就会越过四块门槛，应暂停把新写发布到不足放置域的 stripe，优先修复存量。健康 Range GET 可以只访问覆盖范围的 data 块；需要解码时可能触及四块，读放大与尾延迟要按请求范围计算，不能把所有读统一写成六倍。

Wait for all six durable fragments before publication, trading degraded write availability for complete initial redundancy. After two losses, reads remain possible but another bad fragment crosses the four-fragment threshold, so repair takes priority and insufficient-placement stripes stop publishing. Healthy range reads can touch only relevant data fragments; degraded decoding can touch four, so amplification depends on the requested range.

故障与推导：修一 TB 为什么要读四 TB Failure arithmetic: why 1 TB repaired can read 4 TB

按普通 RS 单缺块修复的教学假设，要收齐 k 个存活块才能算出缺块；缺块总量一 TB，每个输入同等大小，总读取约四 TB，再写一 TB。五百 MB/s 是集群汇聚的修复读取预算，不是四个源各自五百：4,000,000 MB÷500 MB/s=8,000 秒，约两小时十三分二十秒。相比副本单缺块读取的两千秒，瓶颈读取多四倍；有专门修复码时需换算法与测量，不能继续用这组算式。

Under conventional single-fragment RS repair, k surviving fragments reconstruct the missing one: 1 TB missing means about 4 TB read and 1 TB written. The 500 MB/s budget is aggregate, not per source: 4,000,000/500=8,000 seconds, or 2h13m20s, versus 2,000 seconds for replica repair. Specialized repair codes require different calculations and measurements.

丢一个 AZ 的两块时，可以一次读剩下四块同时重建这两块，比两个独立修复任务各读一遍省流量。若同一批 stripe 的总缺块是一 TB，两个缺块各半 TB，四个存活块合计约两 TB，重建写一 TB；这与“缺一个块总量一 TB”的四 TB 读取不是同一个问题。修复调度按 stripe 合并，限制源盘读、跨 AZ 流量与目标写，给前台 GET 留预算，不能无限修复把健康对象也拖到超时。

For two lost fragments in one AZ, one read of the four survivors can rebuild both. If those stripes have 1 TB total missing, each lost fragment contributes 0.5 TB; four survivors total about 2 TB read and 1 TB written. This differs from 1 TB of single-fragment loss. Coalesce repairs per stripe and limit source reads, cross-AZ traffic, and target writes to preserve foreground GET capacity.

替代与公开契约：耐久数字不从故障率乘出来 Alternatives and public contracts: do not multiply durability nines

f4 论文把温 BLOB 与热 BLOB 分开，用编码降低温层的有效冗余成本 [3]。本章借分层思路，4+2 是教学参数，不是声称 f4 或 S3 内部就用此码。可以先副本接热写，封存后后台转码，但切 manifest 前仍要拿到全部新块的 durable receipt；转码完成前保留副本，切换后等读租约耗尽才回收，和第二组 pack 代次协议一致。

f4 separates warm from hot BLOBs and lowers warm storage redundancy cost with coding [3]. We borrow tiering; 4+2 is not an assertion about f4 or S3 internals. A replica-first path may recode sealed data, requiring all new receipts before switching the manifest and retaining old copies until readers drain, as in deck 2.

AWS 文档把 Standard 类的 99.999999999% 年耐久写成 designed to provide，并说明跨 AZ 冗余 [7]；它的 SLA 按月度可用率与服务抵扣展开 [8]。所以十一 nines 是公开耐久设计目标，不是本章算出的保证，也不是那个可用性 SLA。盘故障会相关，重建有窗口，软件会批量删错，不能把独立磁盘年故障率立方就贴上六个或十一个九。主线报告丢块检测、修复时间与不可恢复对象事件。

AWS documents 99.999999999% yearly durability as a design target and describes multi-AZ protection [7]; its SLA uses monthly availability and service credits [8]. Eleven nines is therefore a published durability target, not this design’s calculation or the availability SLA. Correlated failures, repair windows, and software mistakes invalidate naïve independent-disk products. Observe corruption, repair time, and unrecoverable-object events.

22.5 · hash 点查与 prefix LIST 的冲突 22.5 · Hash lookups versus prefix LIST

正常路径：名字定位一片，列表扇出多片 Walkthrough: one shard for a name, many for a prefix

用规范化后的 bucket_id 与未经改写的 object key 原始字节做 hash，再按分片目录路由。GET 不用先全局查询 UUID 才能找到名字；Metadata 行含 current、保留版本与权限信息，Data manifest 再标记字节放置。只按 bucket 分片会把一个大公开桶压在同一片；按完整名字 hash，热桶多 key 可以分散，但单个爆款 key 仍在一片，哈希不会自动打散一个 key 的请求。

Hash the normalized bucket id plus exact, unmodified object-key bytes and route through the shard map. GET need not globally find a UUID before locating the name. Bucket-only sharding concentrates a large bucket; full-name hashing spreads its many keys, but a single hot key still has one authority shard. Hashing does not split one key’s requests.

前缀相同的名字已经打散，LIST 必须对每片做前缀条件与排序，再让 API 归并。A12 每片取一百候选，六十四片最多 6,400 行，最后只返回一百。分页 token 包含各片游标、路由 epoch 与请求参数摘要，防止后续换前缀或旧路由复用；token 要签名并设置有效期。每片索引必须支持自己的前缀范围，不能为了列一页就在所有片把每条 key 全表扫描。

Prefix names are scattered. LIST filters and sorts within each shard, then API merges. At 100 candidates per 64 shards, up to 6,400 rows produce 100 returned. Signed expiring tokens bind shard cursors, route epoch, and query parameters. Each shard needs a prefix-capable index; a one-page LIST must not full-scan all keys.

为什么：强点读不自动升级成全局快照 Why: strong point reads do not create a global snapshot

本设计单键 GET 强一致，但 LIST 明确只保证每片取数时读到该片已提交状态，没有同一跨片快照，也不保证翻页期间不漏掉新插入到已走过游标前的 key。某片故障则整页失败，而不是悄悄返回“完整”列表的子集。公开 S3 提供强写后读与 LIST 契约 [1]；这是产品参考，主线尚未实现等价的列表屏障，必须把差异直接说出来。

Single-key GET is strong; LIST reads committed state per shard without one cross-shard snapshot or stable view across pages. An insertion behind an already-passed cursor may be absent from later pages. Fail the page if a shard fails rather than silently claim completeness. Public S3’s strong LIST contract [1] is a comparison; this baseline does not implement an equivalent barrier.

如果面试要求强 LIST，就把名字索引改成按 bucket/prefix 范围切分，由负载与范围拆分处理热前缀；单键点查可能需要路由目录，但列表只扫相关范围。另一条路是维护全局索引并协调提交与可见位点，读等待索引达到 publication 水位。异步投影没有这条屏障，会在 PUT 成功后暂时漏 key；同步更新跨片又引入分布式事务。先选契约，再承担索引结构和可用性成本。

For strong LIST, range-partition names by bucket/prefix and split hot ranges, accepting routing complexity for point reads. Alternatively coordinate a global index’s commits and visibility positions, making reads wait for publication watermarks. An async index without a barrier can omit a successful PUT; synchronous cross-shard updates need distributed transactions. Choose the contract before choosing the index.

故障与替代：迁移代次、热点与版本增长 Failure and alternatives: migration epochs, heat, and version growth

分片迁移先复制快照再追增量，权威目录只在目标达到切换水位后换 epoch。旧 epoch 请求由旧片拒绝或转发到新片，写 leader 要 fencing，避免两个片同时更新 current。LIST token 固定旧 epoch 的过渡读，或直接返回要求重开列表的错误；不能把上一页一半游标按旧分片解释、下一页按新分片解释。这里的迁移协议是维护路由正确性，不能补出一个原本没承诺的全局快照。

Migration copies a snapshot, replays deltas, and changes the authority epoch only after a target watermark. Old shards reject or forward stale epochs, while write leaders are fenced. LIST tokens either retain the old transition view or require a restart; never reinterpret half a cursor set under a new map. Correct migration does not add an unpromised global snapshot.

对热 key，缓存不可变 version 的 payload 容易，但 current 名字与 ACL 仍须验证。缓存权限撤销旧值会泄露内容，未授权者即使猜到 object_id 也不能直接读 Data。可以给 API 到 Data 的内部读取能力绑定版本、权限代次与短有效期，公开对象另走明确策略。访问日志要避开泄露签名能力；扩机器解决带宽，限流保护元数据，二者不能互相替代。

Caching immutable version payloads is easier than caching current or ACLs. Stale authorization can leak data; guessed object ids must not bypass API authorization at Data. Internal read capabilities can bind version, permission generation, and short expiry, with explicit public-object policy. Avoid logging secret capabilities. More boxes handle bytes; rate limits protect metadata, and neither substitutes for the other.

一 TB 元数据只覆盖 A4 的 current 行。假设每个 key 平均还保留三条同大小旧版本行，行数变四十亿，逻辑元数据约四 TB，三副本约十二 TB；payload 的保留也可能远大于百 PB。删除 marker 仍是一条元数据，不等于释放旧版本。必须按保留策略测版本数量与旧字节比例，再对容量、索引和回收吞吐重新算，不能把 version 功能加上后继续用原采购量。

A4’s 1 TB covers current rows only. Three similarly sized retained old rows per key raise the count to four billion, about 4 TB logical metadata or 12 TB replicated. Retained payloads can exceed 100 PB too. A delete marker is another row, not old-version reclamation. Recompute capacity, indexes, and cleanup from retention measurements.

22.6 · Multipart：冻结一份清单，完成与取消争同一状态22.6 · Multipart: one frozen manifest, one state for completion and abort

每个 part_number 只表示位置，不足以标识字节。本设计的每次尝试分配新 blob_id，Metadata 条件更新 part_generation；同编号重传先核对旧代次，旧/新 receipt 不能混用。Complete 提交按编号排序的精确 part 身份清单，原子冻结为 FINALIZING 后，新的注册、普通 abort 与普通 GC 都不能改选。单 PUT 是只有一个 part 的相同协议。

A part number identifies position, not bytes. Every attempt allocates a fresh blob id; Metadata conditionally advances part_generation. Retrying a number checks its previous generation. Complete supplies an ordered list of exact part identities and atomically freezes FINALIZING, blocking reselection by registration, ordinary abort, and ordinary GC. Single PUT uses the same protocol with one part.

freeze(actor, upload_id, fence, ordered_parts):
  BEGIN; lock namespace, then upload              // same shard and lock order as publish
  authorize(actor, namespace, "PUT"); require upload.owner == actor
  digest = hash_canonical(ordered_parts)            // number + part generation + blob + size + hash
  if upload.state in {FINALIZING, COMPLETED}:
    require digest == upload.manifest_hash
    COMMIT; return upload.frozen_manifest           // retry keeps the original selected parts
  require upload.state == OPEN and upload.fence == fence
  require authority_now() < upload.lease_until
  require parts_are_unique_and_ordered(ordered_parts)
  require ordered_parts == registered_parts        // same versions, no missing or extra parts
  require sum(parts.size) == upload.expected_size
  UPDATE upload SET state=FINALIZING, manifest_hash=digest, frozen_manifest=ordered_parts
  COMMIT                                           // blocks part registration, abort, and ordinary GC
  // Outside TX: Data verifies checksums/redundancy for this immutable frozen manifest.
  // Call publish(); crashed FINALIZING is recovered using the same manifest, never reselected.

abort(actor, upload_id):
  BEGIN; lock namespace, then upload
  authorize(actor, namespace, "PUT"); require upload.owner == actor
  if upload.state == FINALIZING: ROLLBACK; return CONFLICT
  if upload.state in {COMPLETED, ABORTED, REJECTED}: COMMIT; return saved_state
  require upload.state == OPEN
  UPDATE upload SET state=ABORTED, fence=fence+1
  COMMIT                                           // durable sweep scanner will rediscover this row
  return ABORTED                                   // not a claim that physical bytes are already gone

代码中的唯一/排序和 registered_parts 比较由 Metadata 执行：清单含编号、part_generation、blob_id、长度及摘要，必须等于冻结前已登记集合。本教学契约要求所有已登记编号都在清单中，强于“任选一部分”的协议；Data 检查有序字节的总长与全对象 SHA-256，并确认三副本或六块完整后调用 22.1 发布。同 SHA-256 摘要不等于重用同一操作身份；不同上传也不默认跨用户去重。

Metadata validates ordering/uniqueness and compares numbers, part generations, blob ids, lengths, and digests against the registered set. This teaching contract selects every registered number, stricter than a protocol permitting a subset. Data checks ordered total length and whole-object SHA-256, confirms all three replicas or six fragments, then invokes 22.1 publication. Equal content does not equate request identities or imply cross-user deduplication.

恢复不重选：FINALIZING 的协调者崩溃，恢复者复用同一冻结清单；清单变化就是冲突。FINALIZING 本身不是成功，只有版本、current 与 COMPLETED 原结果同事务才成功；expected_generation 失配则同事务保存 REJECTED/CONFLICT，后续重试不能等前提改变后再成功。完成原结果在旧版本被合法回收后仍可查询，不代表该旧版永远可读。

Recovery never reselects: resume the exact frozen manifest after a coordinator crash; a changed manifest conflicts. FINALIZING is not success. Version, current, and saved COMPLETED result commit together; a generation mismatch durably records REJECTED/CONFLICT rather than later succeeding after a precondition change. The original result remains queryable after lawful old-version reclamation, without promising perpetual readability.

Abort 赢 OPEN 后先封上传代次，返回 ABORTED 只是元数据决定。Data 旧的在途写仍可能完成，先关闭入口并排空，再重复清扫。已完成上传中，未被冻结清单引用的旧尝试也要按不可变 blob_id 单独扫；不能按 part_number 删到新版。共享 pack 只有所有记录的保留引用和读租约都清除才可整体删除，压缩协议见 22.2。

An abort winning OPEN fences the upload; ABORTED is a metadata decision. Old in-flight Data writes may still land: close admission, drain, and sweep repeatedly. Completed uploads also need cleanup of unselected attempts by immutable blob id, not by a reused part-number path. A shared pack is deleted only after all records’ retained references and read leases clear; see 22.2 compaction.

公开 S3 契约与本设计假设分开Separate public S3 behavior from this design

S3 允许独立/乱序上传 parts，同编号新上传会替换该编号；complete 按所列编号递增拼装。本设计的 part_generation、FINALIZING、永久原回执和 GC 状态机都是教学方案，不是 S3 内部描述。S3 multipart 自身不因本章的 60 秒租约自动过期；未完成上传须完成、终止或由生命周期清理。[5]

S3 permits independent/out-of-order part uploads and replaces a previous part at the same number; completion concatenates listed parts in increasing order. Our part generations, FINALIZING, saved-result policy, and GC states are teaching choices, not S3 internals. Public S3 multipart does not automatically expire at our 60-second lease: explicitly finish, stop, or configure lifecycle cleanup. [5]

S3 的 AbortMultipartUpload 明确提示：在途 part 仍可能成功，可能需要重复 abort 并用 ListParts 核对为空。CompleteMultipartUpload 的初始 HTTP 200 也可能包含最终错误，直接调用者须解析最终响应，SDK 按其错误语义处理。两者都不能用“看到了 200/发过一次取消”代替最终结果。[4][12]

S3 warns that in-flight parts may succeed after abort, requiring repeated aborts and ListParts verification. CompleteMultipartUpload may carry an error after an initial HTTP 200; direct callers must parse the final response, while SDKs apply their error handling. Neither an initial status nor one cancellation request establishes the final outcome. [4][12]

A9：5 GiB÷64 MiB=80 parts，四路理想 20 轮；补一 part 是 1/80=1.25%，不是重新传五 GiB。实际时长仍由带宽和重试决定。一万次中断各留 64 MiB，就是 625 GiB 未发布字节，冗余另乘。按租户限制活跃上传数、未完成字节、续租和 FINALIZING 年龄；同时观测未知结果、坏块/修复年龄与 GC 积压。

A9: 5 GiB/64 MiB gives 80 parts and ideally 20 four-way rounds. Retrying one part sends 1.25%, with real duration bounded by bandwidth/retries. Ten thousand interrupted uploads leaving 64 MiB each consume 625 GiB before redundancy. Limit active uploads, incomplete bytes, renewals, and FINALIZING age per tenant; observe unknown outcomes, corruption/repair age, and GC backlog.

追问：把假设改一行，重算受影响的路径 Follow-ups: change one assumption and recompute its path

1 · 如果要求断一个 AZ 仍能写呢？ 1 · What if writes must survive one unavailable AZ?

原三副本与六块全确认策略会暂停新写；要继续就需要另一套足够完整的放置域，或明确承认降级冗余。三副本改为先两份确认，省了等待却让重建窗口只有两份；4+2 只剩四块就发布，则发布时没有额外丢块余量。可以预留第四个 AZ 或更大码并按每个 AZ 块数验算，也可以选择故障时拒写。答案必须同时更改确认条件、放置与耐久风险，不能只改红线颜色。

The baseline all-copy/all-fragment acknowledgement gates stop writes. Continuing requires alternative complete placement or explicit degraded redundancy. Two-copy receipts shrink protection; publishing only four 4+2 fragments leaves no loss margin. A fourth AZ or larger code needs placement arithmetic. Update the acknowledgement gate, placement, and risk together.

2 · 如果对象都是十 KB 呢？ 2 · What if every object is 10 KB?

百 PB÷十 KB=十万亿对象；按一 KB 行就是十 PB 元数据，一份元数据已经是 payload 的十分之一，三副本三十 PB。原六十四片每片会有约 156.25 TB 元数据，点查与恢复都不能照旧预算。要改 per-object 元数据大小、分片数量、批量索引与查询模型，同时 pack 能减少底层文件数，却不会消灭对象 API 必须记住的十万亿个名字。

100 PB/10 KB is ten trillion objects. At 1 KB each, metadata is 10 PB logical and 30 PB replicated. Sixty-four shards average about 156.25 TB each. Recompute row size, shard count, indexing, and query budgets. Packs reduce physical files, not the ten trillion names the API must retain.

3 · API 确认后，怎样观测设计是否真的守约？ 3 · How do we observe post-acknowledgement correctness?

用独占探针 key PUT 带 operation_id 的版本，再 GET 校验 version_id 与 checksum；DELETE 后无版本读不能看到旧 current，显式保留版本按策略读取。分开统计确认后不可读、checksum 错、未知完成状态、LIST 漏项与缺副本年龄。小对象读 99.9% 是本章 SLO，错误预算是请求分母乘 0.001；耐久丢对象的事件不能用“GET 有 99.9% 成功”替代。把元数据不可达的失败与 payload 数据丢失区分，恢复才有正确优先级。

Use a dedicated probe key for PUT with operation id, then verify version id/checksum on GET. After DELETE, unversioned reads must not see old current while retained version reads follow policy. Separate post-ack unreadability, corruption, unknown completion, LIST omissions, and replica-deficit age. The 99.9% small-read SLO allows 0.001 of requests; read availability does not measure object loss.
