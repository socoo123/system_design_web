任务调度系统Job scheduler

约 45 分钟 · 前置：Ch08、Ch18、Ch24、Ch41 · 6 组演进图，共 31 帧~45 min · after Ch08, Ch18, Ch24, Ch41 · 6 evolution decks / 31 frames

本章要点：任务到期后，仍要留下可恢复的执行记录Core: a due time needs recoverable work

设计调度系统时，先分清三种成功：返回 202 表示任务定义已持久保存；T1 提交表示某次计划触发已生成执行记录；run 进入 succeeded 才表示业务端给出了确定结果。本章把计划中的每个触发时刻称为“火点”，把为它保存的执行记录称为 run。同一个 run 可以有多次执行尝试（attempt）；worker 返回 accepted 只表示收到了请求，也不代表通知已经送达。接下来沿着“时间索引 → 唯一火点 → 租约代次 → 稳定业务键”逐步设计。

Separate three successes: 202 means a durable definition; T1 means a materialized occurrence; succeeded means a confirmed business result. One run may have several attempts, and worker acceptance does not establish notification delivery. Follow time index → unique occurrence → lease generation → stable business key.

本章设计单地域、多实例运行的 cron 周期任务与一次性延迟任务，用对账、巡检和延迟关单作例子。任务之间的依赖编排交给工作流处理。开始前先确认：任务允许迟到多久，能否放弃错过的业务窗口，不同火点的执行能否重叠，以及业务效果最终在哪个存储中提交。

Scope is one region with multiple instances, recurring cron and one-shot delays, illustrated by reconciliation, checks and order closure. Workflows own dependencies. Clarify allowed lateness, whether intervals may be dropped, overlap across occurrences and where effects commit.

范围、容量与时间假设Scope and assumed capacity

基线方案使用一个权威事务库。压力场景假设 1 万个任务定义全部每分钟触发一次；每次执行平均耗时 0.2 秒，按 60% 的计划使用率计算，整个执行池需要 56 个并发槽。执行租约为 30 秒，每 10 秒发送一次心跳，业务调用在 20 秒后超时，最多自动尝试 5 次。后面的停机恢复例子只涉及 10 个任务，采用另一组负载假设，不能把两组流量相加后仍沿用原来的预算。

Use one authoritative transactional database. In the stress case all 10,000 definitions fire each minute; 0.2 s mean service and a 60% utilization budget imply 56 pool slots. Leases last 30 s, heartbeats 10 s, business-call timeout 20 s, with at most five automatic attempts. A separate recovery example covers ten jobs; it does not share the stress case’s load assumptions.

领取执行权和记录完成结果都只访问权威主库。故障切换必须保留已确认的任务定义、run 和业务去重记录，不能仅凭副本数量推断数据不会丢失。无法确定哪个主库可以安全承担权威时，系统应暂停新的领取操作，并展示任务到期后的滞后时间（due lag），不能从副本数据猜测当前持有者。

Claims and completion use the authoritative primary. Failover must preserve acknowledged schedules, runs and business deduplication records; copy count alone is not durability. Without a safe authority, pause claims and expose due lag rather than infer ownership from replicas.

T1：把火点记录和下一触发时间一起提交T1: commit the occurrence and next cursor together

注册 API 把任务定义、版本和注册幂等回执放在同一个数据库事务中提交，成功后才返回 202；认证和同键冲突处理沿用 Ch09 的模式。下面的实现从已经验证的任务定义开始。第一组图要解决的是：推进 next_run_at 时，必须同时留下持久的 ready 行，提交后再向 worker 投递。若进程在提交后、发送前崩溃，恢复者可以重新扫描 ready；若发送后丢失确认，就重投同一个 run_id。需要队列时，可以在 T1 中加入待投递消息表（dispatch outbox），再由转发程序 relay 恢复投递。

The registration API returns 202 after definition, version and registration receipt commit together, using Ch09’s authentication and same-key conflict model. The code begins with validated definitions. Deck one’s key rule is to leave a durable ready row when advancing next_run_at, then dispatch. A crash before delivery re-scans ready; a lost delivery ACK resends run_id. A queue variant adds a dispatch outbox inside T1, relayed after commit.

在 run 中固定本次执行的身份与输入Freeze identity and input in the run

每次触发都由非空唯一键 (job_id, schedule_version, scheduled_at UTC) 标识，分别对应任务、计划版本和原定的 UTC 触发时刻，不能改用机器当前时间。修改任务定义只影响后续生成的 run；已有 run 沿用自己的处理参数和业务键 effect_key，领取执行权时也不会重新读取最新任务参数。业务键要按业务意图选择，例如用同一租户下的 close:o7 标识同一次关单。新增一个 schedule_version，并不自动意味着业务可以再生效一次。[3]

The non-null unique key is (job_id, schedule_version, scheduled_at UTC), rather than a machine’s current time. Edits affect future materialization; an existing run keeps its frozen input and effect_key, and claims do not reload new job parameters. Choose effect identity by business intent, such as tenant-scoped close:o7. A new schedule version does not automatically authorize another effect. [3]

-- PostgreSQL 18 teaching schema; one authoritative scheduler database.
CREATE TABLE job (
  id text PRIMARY KEY, version bigint NOT NULL CHECK (version > 0),
  shard smallint NOT NULL CHECK (shard BETWEEN 0 AND 15),
  enabled boolean NOT NULL, next_run_at timestamptz,
  policy text NOT NULL CHECK (policy IN ('skip','coalesce','catch_up')),
  lateness_ms bigint NOT NULL DEFAULT 60000 CHECK (lateness_ms >= 0),
  spec jsonb NOT NULL, recovery_cutoff timestamptz
);
CREATE INDEX job_due ON job(shard, next_run_at, id) WHERE enabled;
CREATE TABLE run (
  id uuid PRIMARY KEY, job_id text NOT NULL REFERENCES job(id),
  schedule_version bigint NOT NULL, scheduled_at timestamptz NOT NULL,
  payload jsonb NOT NULL, effect_key text NOT NULL,
  state text NOT NULL CHECK (state IN
    ('ready','running','retry_wait','succeeded','cancelled','review')),
  attempts integer NOT NULL DEFAULT 0 CHECK (attempts BETWEEN 0 AND 5),
  generation bigint NOT NULL DEFAULT 0 CHECK (generation >= 0),
  owner text, lease_until timestamptz, retry_at timestamptz,
  cancel_requested boolean NOT NULL DEFAULT false,
  effect_unknown boolean NOT NULL DEFAULT false, result jsonb,
  CONSTRAINT occurrence UNIQUE(job_id, schedule_version, scheduled_at),
  CHECK ((state = 'running' AND owner IS NOT NULL AND lease_until IS NOT NULL)
      OR (state <> 'running' AND owner IS NULL AND lease_until IS NULL))
);
CREATE INDEX run_ready ON run(state, retry_at, scheduled_at);
CREATE INDEX run_expired ON run(lease_until) WHERE state = 'running';
-- spec includes the pinned calendar/timezone rules and handler input.
-- A separate audit table stores skip/coalesce ranges in the same T1.

下面的伪代码对应第 2、4 帧中的火点生成与恢复。PostgreSQL 18 的 SKIP LOCKED 适合多个消费者并发处理队列表，但查询会跳过已锁定的行，因此读到的是不完整视图。行锁在事务结束时释放，只保护本次生成 run 的过程，不能代替后续执行所需的租约。[1][2]

This pseudocode implements frames 2/4. PostgreSQL 18 SKIP LOCKED suits consumers of a queue-like table but gives an incomplete view. Row locks end with the transaction; they protect materialization, not handler execution. [1][2]

materialize(shard):                         // PostgreSQL READ COMMITTED
  BEGIN
  jobs = SELECT * FROM job WHERE enabled AND shard = :shard
         AND next_run_at <= clock_timestamp()
         ORDER BY next_run_at, id LIMIT 100 FOR UPDATE SKIP LOCKED
  for j in jobs:
    t = SELECT clock_timestamp()            // after acquiring this row lock
    if calendar.is_recurring(j.spec) and (j.recovery_cutoff != null
       or j.next_run_at < t - j.lateness_ms * 1ms):
      continue                             // bounded misfire planner owns this case
    fire = j.next_run_at
    next = calendar.next_after(j.spec, fire) // null for a one-shot; else > fire
    require next == null or next > fire
    payload, key = freeze_input_and_business_key(j, fire)
    inserted = INSERT INTO run(id, job_id, schedule_version, scheduled_at,
                  payload, effect_key, state)
               VALUES(uuid(), j.id, j.version, fire, payload, key, 'ready')
               ON CONFLICT ON CONSTRAINT occurrence DO NOTHING RETURNING id
    if inserted is empty:
      old = SELECT * FROM run WHERE job_id=j.id AND schedule_version=j.version
                                  AND scheduled_at=fire
      require old.payload == payload and old.effect_key == key
    UPDATE job SET next_run_at=next WHERE id=j.id
  COMMIT                                  // do not dispatch before this succeeds
  // Any pre-commit error rolls back runs AND cursors.
  // Unknown COMMIT: discard connection, re-read authoritative cursor/runs.
  // Dispatch/recovery scans persisted ready rows; duplicates retain run.id.

日历适配器 calendar 必须根据固定的表达式、IANA 时区、时区规则版本和夏令时（DST）策略，枚举严格递增的原定 UTC 火点。对于一次性任务，适配器返回 null，表示没有下一火点。freeze_input_and_business_key 只根据既定输入做确定性的纯计算。

插入冲突时，只能将 occurrence 唯一约束冲突作为重复处理，随后还要比较已保存的参数与业务键；其他数据库错误都应回滚。若无法确认 COMMIT 是否成功，要丢弃连接，再从主库重读游标和 run，不能根据内存中尚未确认提交的结果发送 RPC。

The calendar adapter enumerates the original expression, IANA timezone, pinned timezone rules and DST policy as strictly increasing UTC instants; one-shot jobs have a null next occurrence. freeze_input_and_business_key is deterministic pure computation. Only the occurrence conflict is handled as replay, with frozen-input comparison; other database errors roll back. An unknown COMMIT requires discarding the connection and re-reading primary state, not dispatching from unconfirmed memory.

cron 按日历继续推进，不会等待上一次执行成功；固定延迟（fixed delay）才是从 finished_at 加上间隔，算出下一次时间。本例允许不同火点的执行重叠。如果业务要求同一任务串行执行，还需要任务级的活动指针或并发槽，并在领取执行权的同一事务中校验。暂停任务定义只会停止后续生成 run，已有的 ready 或 running 记录不会自动取消。

Cron advances calendar instants without waiting for the previous success; fixed delay derives the next time from finished_at. This example permits distinct occurrences to overlap. Serial execution needs a job-level active pointer or slot checked with the claim transaction. Pausing a definition stops future materialization; existing ready/running runs are not automatically cancelled.

容量：分别估算平均流量与整分钟突发Capacity: distinguish average rate from aligned bursts

平均每秒触发 166.7 次，不代表每秒最多只有这些任务：整分钟时，1 万个任务可能同时到期。每批处理 100 行，需要 100 批事务，但这个批量大小不能说明 worker 的执行吞吐。第二组图中的 16 个稳定逻辑分片只负责分摊扫描，共用的仍是一个数据库。迁移期间即使两个调度器扫描到相同范围，也要靠行锁和唯一火点身份避免重复生成记录。

166.7/s is an average; a minute boundary can make 10,000 rows due together. Batches of 100 need 100 transactions without establishing execution throughput. Deck two’s 16 stable logical shards divide scans, not databases; overlapping scans during reassignment still rely on row locks and unique identity.

展开并发槽、突发完成时间与存储的计算Slot, burst and storage arithmetic

平均触发速率为 10,000 ÷ 60 = 166.666… 次/秒。乘以平均执行时长 0.2 秒，得到平均占用 33.333… 个槽；再除以 0.6 并向上取整，就得到 56 个槽。

在每次执行固定为 0.2 秒、没有额外开销的模型中，56 个槽的吞吐为每秒 280 次。若把任务看作可连续分割的工作，总完成时间的下界为 35.714… 秒；实际需要 ceil(10,000÷56)=179 轮，因此要 35.8 秒。若要求 5 秒内完成，理想情况下至少需要 400 个槽；仍按 60% 使用率预留容量时，则约需 667 个槽。这些计算都还没有计入领取和排队开销。

10,000 / 60 = 166.666…/s; multiplying by 0.2 s gives 33.333… occupied slots, then dividing by 0.6 and rounding up gives 56. With fixed 0.2 s runs and no overhead, 56 slots supply 280/s. The fluid lower bound is 35.714… s, while ceil(10,000/56)=179 discrete rounds take 35.8 s. Five-second completion needs at least 400 ideal slots, or about 667 at the same 60% budget, before claims and queueing.

任务定义的原始数据为 10,000×1 KB=10 MB，保存三份共 30 MB。每分钟生成 1 万个 run，一天就是 10,000×1,440=1,440 万个；按每行 200 B、保留 7 天计算，1,440 万×200 B×7=20.16 GB，三份共 60.48 GB。

这些都是按十进制单位估算的原始行大小，没有计入索引、WAL、执行尝试审计、结果和备份。清理时只删除终态历史，ready、running、retry_wait、review 中的工作和仍需保护的业务键都要保留。

Definitions: 10,000×1 KB=10 MB, or 30 MB for three copies. Runs: 10,000×1,440=14.4M/day; 14.4M×200 B×7=20.16 GB, or 60.48 GB for three copies. These decimal raw-row estimates exclude indexes, WAL, attempt audits, results and backups. Clean terminal history only, preserving ready/running/retry_wait/review work and still-needed effect keys.

观测时应分别统计到期滞后、最老 ready 记录的等待时长、过期租约、领取被拒次数和下游错误。开始迟到的时间等于“实际开始时间 − scheduled_at”；要看业务何时完成，还需加上处理器的执行时间。每秒轮询一次，只能说明检测延迟的一部分。

扩容前先找出瓶颈。扫描慢时可以增加扫描器；如果不足的是执行能力或下游预算，增加扫描器只会更快地堆积待执行任务。

Track due lag, oldest ready age, expired leases, rejected claims and downstream errors separately. Start lateness is actual start minus scheduled_at; completion also includes handler time. One-second polling covers only part of detection latency. Add scanners for scanning limits; execution/downstream bottlenecks otherwise create backlog faster.

执行租约：用代次保护状态，用业务幂等保护效果Execution lease: generations protect state; receivers protect effects

第三组图沿着一个反例展开：Worker A 一直暂停到第 31 秒，Worker B 接管同一个 r7，把代次从 41 推进到 42；A 恢复后却仍可能发送旧请求。租约过期不会终止旧进程，调度库中的代次也不会自动约束远程系统。因此，被保护的存储必须自己检查并拒绝旧持有者的操作。[4]

Deck three retains the key counterexample: A pauses until second 31, B takes over r7 and advances generation 41→42, and A can still resume sending requests. Expiry does not kill a process or automatically fence remote systems. The protected resource must enforce stale-authority rejection. [4]

领取执行权：短事务提交后，再执行业务Claim briefly, execute outside the transaction

领取操作接收持久保存的 run_id 和本次持有者标识 owner；owner 由进程启动 UUID 与本次领取 UUID 组成。成功后返回已提交的代次、租约和固定的处理参数。只有未请求取消，且处于以下状态之一的运行才能领取：ready、已到重试时间的 retry_wait，或租约已过期的 running。每次合法领取都计为一次 attempt，包括崩溃后的接管，不能因为没有拿到调用结果就重置尝试次数。

Input is a durable run_id and unique owner (process boot UUID plus claim UUID); output is a committed generation, lease and frozen input. Only ready, due retry_wait or expired running is eligible. Every claim counts as an attempt, including crash takeover; missing results do not reset the budget.

claim(run_id, owner):                       // owner = boot UUID + claim UUID
  BEGIN
  r = SELECT * FROM run WHERE id=run_id FOR UPDATE
  t = SELECT clock_timestamp()             // not transaction-start now()
  if r is absent or r.cancel_requested: ROLLBACK; return NOT_CLAIMED
  eligible = (r.state == 'ready')
          or (r.state == 'retry_wait' and r.retry_at <= t)
          or (r.state == 'running' and r.lease_until <= t)
  if not eligible: ROLLBACK; return BUSY_OR_TERMINAL
  if r.attempts == 5:
    UPDATE run SET state='review', owner=null, lease_until=null,
                   effect_unknown=true WHERE id=run_id
    COMMIT; return REVIEW
  UPDATE run SET state='running', attempts=attempts+1, generation=generation+1,
                 owner=:owner, lease_until=t+30s, retry_at=null,
                 effect_unknown=true WHERE id=run_id
    RETURNING id, owner, generation, lease_until, payload, effect_key
  COMMIT
  return committed claim                   // handler runs outside the transaction
  // A lost commit ACK is not a failed claim. Read this owner from the primary
  // and obtain its current generation/valid lease before issuing any effect.
  // Do not create another occurrence or issue an RPC from an unconfirmed claim.

判断租约前，要先取得保护这行记录的行锁，再读取实际数据库时间。PostgreSQL 的 now()/CURRENT_TIMESTAMP 固定在事务开始时刻；如果先取时间、再等待行锁，拿到锁时租约可能已经过期，旧时间却仍会把它判为有效。本例在持锁后调用 clock_timestamp()，并且在取样、判断和更新期间不做 RPC。[12]

行锁使这些判定依次进行，但不保证租约在物理 COMMIT 落盘的瞬间仍然有效。如果数据库事务异常挂起，接管操作也必须等这个事务结束。

Sample actual database time after acquiring the protected row lock. PostgreSQL now()/CURRENT_TIMESTAMP uses transaction-start time: sampling before waiting can admit an already expired lease. This example calls clock_timestamp() after locking, with no RPC between sampling and update. [12] Decisions serialize while locked; this does not claim the lease is still valid at physical commit. A stuck database transaction also blocks takeover until it ends.

心跳、完成、超时与取消都由同一行状态决定One state gate for heartbeat, completion, timeout and cancellation

下面的伪代码把几种状态变化放在同一处处理。心跳与完成请求必须对应 running 状态，持有者和代次都要匹配，并且在持锁后读取的时间点上租约仍未到期。调用超时后，系统保留结果未知标记 effect_unknown，等待退避时间后仍使用同一个业务键重试。

退避等待要有上限并加入随机抖动，执行还需遵守共享的下游预算。过期清理器 reaper 和直接接管过期运行是两条可能竞争的恢复路径，两者都通过同一行锁依次判定和更新。

The following pseudocode keeps failure branches together. Heartbeat and completion require running, matching owner/generation and an unexpired lease at the locked sample time. Timeout retains effect_unknown and retries the same business key after bounded backoff with jitter, subject to shared downstream admission. A reaper and direct expired takeover are competing recovery paths serialized on the same row.

transition(id, action, owner=null, gen=null, result=null):
  BEGIN
  r = SELECT * FROM run WHERE id=:id FOR UPDATE
  t = SELECT clock_timestamp()             // read AFTER lock acquisition
  if r is absent: ROLLBACK; return NOT_FOUND
  if action == 'cancel':                    // authenticated management command
    r.cancel_requested = true
    if r.state == 'ready' and r.attempts == 0: r.state = 'cancelled'
    if r.state == 'retry_wait': r.state = 'review'
    // A running attempt can still report a confirmed effect; cancel is not undo.
  else if action == 'reap':
    if r.state != 'running' or r.lease_until > t: ROLLBACK; return NO_CHANGE
    r.effect_unknown = true                 // expiry does not prove no effect
    r.state = 'review' if r.cancel_requested or r.attempts == 5 else 'retry_wait'
    r.retry_at = t + bounded_backoff(r.attempts) if r.state == 'retry_wait' else null
  else:
    if r.state != 'running' or r.owner != owner or r.generation != gen
       or r.lease_until <= t: ROLLBACK; return STALE
    if action == 'heartbeat': r.lease_until = t + 30s
    else if action == 'complete':
      require result is a durable, authenticated result for r.effect_key/payload
      r.state = 'succeeded'; r.result = result; r.effect_unknown = false
    else if action == 'timeout':
      r.effect_unknown = true               // retain the SAME business key
      r.state = 'review' if r.cancel_requested or r.attempts == 5 else 'retry_wait'
      r.retry_at = t + bounded_backoff(r.attempts) if r.state == 'retry_wait' else null
    else: ROLLBACK; return BAD_ACTION
  if r.state != 'running': r.owner = null; r.lease_until = null
  UPDATE run SET state=r.state, owner=r.owner, lease_until=r.lease_until,
    retry_at=r.retry_at, cancel_requested=r.cancel_requested,
    effect_unknown=r.effect_unknown, result=r.result WHERE id=:id
  COMMIT
  // Errors roll back. Lost ACK: read the saved state, never overwrite success.

20 秒 RPC 超时只表示本地停止等待，不能证明订单没有关闭。第 5 次尝试在租约有效时仍可提交确定结果；如果该次尝试超时或租约过期，任务就因尝试次数耗尽转入持久的待核查状态 review，此时业务效果仍可能未知。只有业务适配器验证了同一租户、同一操作键和固定输入对应的确定结果，才能提交 complete；accepted、网络超时，或尚未提交的结果行暂时查不到，都不能作为完成证据。Worker 失去租约后应停止发起新动作，已经发出的在途动作仍由接收端幂等保护。

A 20 s RPC timeout ends local waiting without proving the order remained open. Five exhausted attempts enter durable review, possibly with unknown effects. complete requires the business adapter to verify a durable result for the same tenant, operation key and frozen input; acceptance, timeouts or absence of an uncommitted row are insufficient. Stop new actions after losing authority; receiver idempotency still protects in-flight actions.

取消时也要区分是否尝试过。尚未执行过的 ready 可以记为 cancelled；正在 running 的任务只记录取消请求，由执行方配合停止，若随后拿到确定的业务结果，仍允许记录完成。已有尝试的 retry_wait 则转入 review，不能把它说成“从未执行”。核查或人工处理都要沿用原业务键并留下审计记录；本例不实现完整的人工控制台。

还要区分单次运行与共享资源：单个 run 的代次只在这个 run 内递增，不能充当跨任务的资源隔离令牌（fence）。若多个任务需要操作同一资源，必须另用同一权威分配单调递增的令牌，并由该资源验证。

An unattempted ready run may become cancelled. Running cancellation records a cooperative request and still permits confirmed completion. A previously attempted retry_wait becomes review, not “never executed.” Review/query/manual actions retain the original key and audit evidence; a full review console is outside this example. Per-run generations are not resource fences across jobs: shared resources need tokens from a common monotonic authority enforced by that resource.

错过火点：先确定补哪些窗口，再限制恢复速度Misfire: retain original intervals and bound recovery

停机后补出尚未生成的火点，与重试已有 run，是两种不同的恢复。这里单独看迟到容忍为 0 的例子：[09:00,11:00) UTC 内，每个按分钟触发的任务有 120 个错过的火点，10 个任务共 1,200 次；11:00 的正常火点另算。每个任务只能在跳过 skip、合并 coalesce、逐点补齐 catch_up 中选择一种策略，图中的三行不是依次执行的三个步骤。

Recovering unmaterialized occurrences differs from retrying an existing run. With zero lateness tolerance, in [09:00,11:00) UTC each minute job has 120 missed slots, giving 1,200 for ten jobs; the live 11:00 occurrence is separate. skip, coalesce and catch_up are alternative per-job policies, not three sequential executions.

选择 skip 时，调度器记录放弃的范围，适用于只查看当前状态的巡检。选择 coalesce 时，用最后一个错过火点的稳定身份生成 run，并在输入中固定整个遗漏区间；处理器必须真正覆盖这段区间。选择 catch_up 时，则按原计划逐个生成火点，每页最多 100 个，页内的 run、审计记录和游标在同一事务中提交。

本轮恢复要固定第一个仍可正常处理的火点 cutoff，后续各页继续使用这个边界。不能因为处理到一半时看起来“已经不太迟了”，就退出尚未完成的恢复。

skip audits abandonment and suits current-state checks. coalesce uses the last missed occurrence identity with a frozen complete interval that the handler must actually cover. catch_up creates original occurrences in pages of at most 100; each page commits runs, audit and cursor together. Pin the first live occurrence cutoff throughout that recovery pass, continuing remaining pages even when they no longer appear very late.

recover_missed(job_id):                     // recurring calendars with future fires
  BEGIN
  j = SELECT * FROM job WHERE id=job_id FOR UPDATE
  t = SELECT clock_timestamp()
  if not j.enabled or j.next_run_at == null: ROLLBACK; return NONE
  missed_before = t - j.lateness_ms * 1ms
  if j.recovery_cutoff == null and j.next_run_at >= missed_before:
    ROLLBACK; return NONE
  cutoff = j.recovery_cutoff ?? calendar.first_at_or_after(j.spec, missed_before)
  // Equality at t-tolerance remains live; use the SAME predicate as materialize.
  // Pin this cutoff across catch-up pages. Missed fires are in [cursor, cutoff).
  from = j.next_run_at
  require cutoff > from
  if j.policy == 'catch_up':
    fires = calendar.first_at_most_100(j.spec, from, cutoff)
    for fire in fires:
      INSERT ready occurrence with frozen input and UNIQUE identity
      // Same INSERT + conflict comparison as materialize; all within this T1.
    next = calendar.next_after(j.spec, fires.last)
  else if j.policy == 'coalesce':
    last = calendar.last_before(j.spec, cutoff)
    INSERT one ready occurrence at last, with immutable range [from, cutoff)
    // The handler contract must cover the entire range; use the same T1 insert.
    next = cutoff
  else if j.policy == 'skip': next = cutoff
  else: ROLLBACK; return BAD_POLICY
  INSERT audit(job_id, version, from, next, policy)
  UPDATE job SET next_run_at=next,
                 recovery_cutoff=(cutoff if next < cutoff else null)
    WHERE id=job_id
  COMMIT
  // No RPC in T1. Failure rolls back the page and cursor; ACK loss re-reads both.
  // Live cutoff fires use the normal path, independently of missed intervals.

这段恢复过程只处理仍有后续火点的周期计划 calendar。每个任务定义都保存非负的迟到容忍 lateness_ms，默认为 60,000 毫秒。只有 next_run_at < t−lateness_ms 才算错过火点（misfire），恰好等于边界时仍走正常路径。cutoff 由 calendar.first_at_or_after(spec, t−lateness_ms) 返回，是不早于该阈值的第一个原计划火点，不能用从 epoch 起取模的方式代替。例如，原火点为第 30、90、150 秒，容忍为零，在第 180 秒恢复时，下一个火点是第 210 秒，合并运行的身份是第 150 秒。

一次性任务默认补做原 deadline 对应的执行；T1 保留原身份，并把 next_run_at 置为 null。如果产品允许放弃，必须明确记录 skipped，不能因为找不到下一次 cron 时间就漏掉这次工作。

This routine is for recurring calendars that still have future occurrences. Each definition stores nonnegative lateness_ms, defaulting to 60,000 milliseconds. Only next_run_at < t−lateness_ms is a misfire; equality remains on the normal path. cutoff is the first original occurrence returned by calendar.first_at_or_after(spec, t−lateness_ms), rather than epoch modulo. For fires at seconds 30, 90 and 150, recovery at 180 with zero tolerance gives next=210 and coalesced identity=150. A one-shot defaults to materializing its original deadline, retaining identity and setting next_run_at=null. Dropping it requires an explicit audited skip policy; absence of a next cron instant must not lose it.

正常生成 run 与恢复过程必须使用同一个迟到阈值。假设原火点为第 0、60、120 秒，当前是第 90 秒，容忍为 60 秒，那么只有第 0 秒的火点算错过，cutoff 应为第 60 秒。第 60 秒的火点只迟到 30 秒，即使选择 skip，也必须留给正常路径处理。若直接按当前第 90 秒找到 cutoff=120 秒，就会错误地跳过仍应执行的工作。已经固定 cutoff 的恢复过程要完成剩余各页，不能按新时间重新判断整轮是否属于 misfire。

Normal materialization and recovery must share the same threshold. For fires 0/60/120 s, now=90 s and tolerance=60 s, only fire 0 is missed and cutoff=60 s. Fire 60 is only 30 s late, so even skip must leave it for normal execution. Choosing cutoff=120 from now=90 would drop still-live work. A pinned recovery pass finishes its remaining pages without reclassifying the whole pass from a fresh time sample.

恢复速度取决于可用余量：100−80=20 次/秒，所以 1,200÷20=60 秒只是流量恒定、没有额外失败和开销时的理想下界。正常流量若已占每秒 100 次，就没有排空积压的余量。对账可以把 [watermark,cutoff) 合成一个处理区间，但必须有证据表明 cutoff 之前的数据已经完整；水位只能越过已持久完成的连续前缀。补建新火点和核查已有结果未知的 run，都要限速。

Spare capacity is 100−80=20/s, so 1,200/20=60 s is an ideal lower bound under constant load with no additional failure or overhead. At 100/s live load there is no drain capacity. Reconciliation can process [watermark,cutoff), but cutoff needs completeness evidence and the watermark advances only over a durably finished contiguous prefix. Rate-limit both new recovery occurrences and investigation of unknown runs.

Quartz 2.3.0 JobStoreTX 的 misfireThreshold 默认为 60000 ms；Airflow 3.0.0 的 catchup_by_default=False。这些值来自各自版本的公开配置，不能代替本章的迟到 SLO 或租约 TTL，也不能当成全行业默认。究竟跳过还是补齐，仍取决于业务是否要求覆盖遗漏的窗口。[5][6]

延迟任务：持久保存截止时间，时间轮负责提醒Delayed jobs: a wheel is a hint; the deadline is durable

要在创建订单 30 分钟后关单，先持久保存绝对 UTC 截止时间 deadline=创建时刻+1,800 秒。如果利用到期索引分页轮询已经足够，就无需再加时间轮。第五组图中的时间索引 Timer index 可以丢失后重建；它提供的候选必须带有 job_id、版本和 deadline。调度器回到权威记录，核对 enabled、当前版本和到期条件后，才能进入 T1。旧槽或重复提示都不能直接调用业务处理器。

Persist an absolute UTC deadline of creation time plus 1,800 s for a 30-minute close. Omit a timing wheel when indexed due polling is sufficient. Deck five’s Timer index is rebuildable; hints carry job_id, version and deadline, checked against authoritative enabled/version/due state before T1. Stale or duplicate hints cannot invoke the handler directly.

每槽 1 秒、共 60 槽的时间轮，一圈覆盖 60 秒。1,800 mod 60=0 表示 30 圈后回到同一槽，并不表示现在就到期。可以保存剩余轮数 rounds、使用分层时间轮，或只装载即将到期的窗口，最终都要比较绝对 deadline。Netty 4.1 将 HashedWheelTimer 用于近似的 I/O 超时调度，并没有承诺业务准点执行或持久恢复。[7]

重启时要分页重建未来的提示，并另外扫描停机期间到期的定义；只重建未来索引会漏掉一次性任务。

A 1 s×60-slot wheel spans 60 s. 1,800 mod 60=0 means the same slot thirty revolutions later, not immediate expiry. Use rounds, hierarchy or near-window loading, then check the absolute deadline. Netty 4.1 describes approximate I/O timeout scheduling, not punctual business execution or durability. [7] Rebuild future hints in pages and separately scan deadlines missed during downtime; future-only reconstruction loses one-shot jobs.

cron 定义要保存 IANA 时区和明确的夏令时（DST）策略，生成的火点则用 UTC 保存。每天某个本地时刻，并不总等于每隔 86,400 秒：时钟向前跳时，某些本地时刻不存在；向后拨时，同一时刻可能出现两次。如何处理这两种情况要写入定义，并按固定的时区规则版本枚举火点。[11] 到期和租约判断使用数据库时间，本地测量经过时长使用单调时钟。如果授时出现大幅异常，任务及时性仍会受影响，增加代次不能修复时钟问题。

Cron stores an IANA timezone and explicit DST policy; occurrences store UTC. A fixed local daily time is not always an 86,400 s interval. Define omitted and repeated local-time behavior and enumerate with pinned timezone rules. [11] Use database time for due/lease decisions and monotonic time for local elapsed time. Generations do not repair timeliness under large authority-clock errors.

业务 T2：把幂等记录、状态更新与 Outbox 一起提交Business T2: commit key, state predicate and outbox together

第六组图明确区分两个数据库：调度库 Schedule DB 不参与订单库 Order DB 的 T2。close:o7 在当前租户内标识同一个关单意图，不论第几次尝试、是否来自旧 worker，还是由人工恢复，都沿用这个键。接收端验证身份和参数后，持有订单行锁，检查当前状态和真正的业务截止时间；得到确定结果后，才保存可供后续重复请求读取的回执。[8]

Deck six keeps the database boundary explicit: Schedule DB does not join Order DB’s T2. Tenant-scoped close:o7 identifies one closure intent across attempts, stale workers and manual recovery. After identity/input verification, the receiver checks order state and the authoritative business deadline while holding the order row lock, saving a replayable receipt only for a confirmed result. [8]

close_order(authenticated_tenant, key, order_id, canonical_payload):
  require caller may close this tenant's order and key == 'close:' + order_id
  BEGIN                                    // T2 is ONLY in Order DB
  o = SELECT * FROM orders WHERE tenant=:tenant AND id=order_id FOR UPDATE
  if o is absent: ROLLBACK; return NOT_FOUND
  old = SELECT * FROM inbox WHERE tenant=:tenant AND operation_key=key
  if old exists:
    if old.payload != canonical_payload: ROLLBACK; return CONFLICT
    COMMIT; return old.result
  t = SELECT clock_timestamp()              // Order DB judges business deadline
  if o.state == 'UNPAID' and o.close_at > t:
    ROLLBACK; return RETRY_AT(o.close_at)     // do NOT cache an early no-op receipt
  if o.state == 'UNPAID':
    changed = UPDATE orders SET state='CLOSED'
              WHERE tenant=:tenant AND id=order_id AND state='UNPAID'
                    AND close_at <= t RETURNING id
    require changed has exactly one row
    result = CLOSED
    INSERT INTO outbox(tenant, event_id, payload) VALUES(:tenant, 'closed:'+o.id, ...)
  else: result = NOOP_TERMINAL              // paid/closed cannot reopen here
  INSERT INTO inbox(tenant, operation_key, payload, result) VALUES(...)
  COMMIT; return result
  // Any error rolls back order + receipt + event; unknown COMMIT => same-key retry.
  // Worker marks run succeeded only after CLOSED/NOOP_TERMINAL is confirmed.
  // Relay sends committed events, then records delivery; a lost ACK may resend.
  // Sink commits UNIQUE(tenant,event_id) inbox + its local effect before ACK.

本例中，已支付 PAID 和已关闭 CLOSED 都是不能重新打开的终态。规范化输入 canonical_payload 由已经验证的 order_id 和操作构造，不包含 attempt_id。同一租户、同一个 key 如果对应不同参数，要返回冲突。

如果提前唤醒，订单尚未到业务 deadline，接口返回 RETRY_AT，并且不能保存“无需关闭”的终态回执。否则真正到期后，重试仍会反复读到早先那次“不做处理”的 no-op 结果，订单再也无法关闭。Worker 收到 RETRY_AT 后重新安排原操作，此时不能标记 succeeded。

PAID/CLOSED are non-reopenable terminal states in this example. canonical_payload is constructed from validated order identity and operation, without attempt_id. Same-tenant/same-key changed input conflicts. An early wake-up returns RETRY_AT without saving a terminal no-op receipt; otherwise later legitimate closure would replay that early no-op forever. The worker reschedules the original operation on RETRY_AT rather than marking success.

如果 T2 已提交，但业务响应或 run 完成写入丢失，调度器应保留结果未知状态 unknown，用同一业务键取得原结果，再由当前代次完成 run。本章的 run succeeded 表示订单已关闭，或已经处于无需关闭的终态；通知进度则由 outbox 单独记录。

Relay 在发送后、记录 delivered 前崩溃，会再次投递。事件接收端必须用非空唯一键 (tenant,event_id) 记录 inbox，并把去重记录与本地效果放在同一个事务中提交，之后才返回 ACK。[9]

If T2 commits but the reply or run completion write is lost, retain uncertainty, retrieve the original same-key result, then complete using the current generation. Here succeeded means closed or an already terminal no-op; notification progress belongs to outbox. A relay crash after sending but before delivered bookkeeping resends the event. The sink commits a non-null unique (tenant,event_id) inbox and its local effect together before ACK. [9]

上述保证依赖接收端支持本地事务和幂等处理。如果普通邮件接口不支持发送幂等键，即使用了 Outbox，邮件仍可能重复发送；取消任务、调用超时和调度租约都不能撤回已经发生的效果。

业务去重记录的保留期限要覆盖所有可能的重放。关单键保留到订单归档，不能随着 7 天的 run 历史一起删除。Kubernetes CronJob 的文档同样说明，近似调度可能重复创建或漏建任务，因此任务需要幂等；其并发策略只约束同一个 CronJob。[10]

The proof applies only to receivers supporting the local transaction/idempotency contract. A plain email interface without send idempotency may still send twice through an outbox; cancellation, timeout and scheduler leases cannot undo it. Effect retention covers every permitted replay: keep close keys until order archival independently of seven-day run history. Kubernetes CronJob likewise documents approximate creation with duplicates or omissions, requiring idempotency; concurrency policies apply within a CronJob. [10]

复盘：说明持久状态与可运行验证的范围Review and executable checks

复述方案时，沿着四处持久状态讲：T1 保存唯一的 ready 行和下一游标；领取操作保存当前代次和租约；超时后保留原业务键与结果未知状态；业务 T2 保存效果、回执和事件。需要扩容时，先判断是扫描、执行还是下游预算不足；需要跨地域时，先确定唯一权威由谁承担。

Name four durable facts: T1’s unique ready row and cursor; the claim’s generation and lease; the original key and uncertainty after timeout; and business T2’s effect, receipt and event. Scale the exhausted scan, execution or downstream budget; establish authority before adding regions.
