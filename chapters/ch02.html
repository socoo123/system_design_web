先说演进，再落笔Say the evolution, then draw it

单机，拆层，然后 LBOne box, then a split, then an LB

中文

第 1 集：用户经 DNS 拿到公网 IP，HTTP 打到一台机器，上面同时跑 web 和数据库。DNS 用托管服务，先当成已知外部依赖。你要能补一句：权威 DNS 以后可以做 geo 路由，细节留到第 7 集。

新痛点说出口：web 和 DB 抢同一份 CPU、内存、NVMe；没有冗余，进程一挂全站挂；垂直加配有硬件天花板。

第 2 集：web 放业务，DB 单独一台。2026 默认先选关系库，PostgreSQL 这一类。有 schema、要事务、要 join，就别为了显得分布式改 NoSQL。纯 KV、纯时序、海量写入再换专用存储。

第 3 集：水平加 web，前面放托管 LB。LB 做两件事：健康检查摘掉坏节点，以及把流量摊开。机器同构，轮询就够；长连接再提最少连接。客户端只看见 LB 的公网入口，web 之间走内网。

停在这里要承认：DB 还是一台，读一涨先死在库上。session 如果还在某台 web 的内存里，LB 只能 sticky，水平扩展是假的。第 6 集再拆。现在先写上这块隐患。

English

Episode 1: DNS hands the user a public IP, HTTP lands on one machine, and that machine runs web and the database. Treat DNS as a managed external. You should be able to add: authoritative DNS can do geo routing later. Details wait for episode 7.

Say the new pain: web and DB fight for the same CPU, RAM, and NVMe. No redundancy, so one process death takes the site. Vertical scale hits a hardware ceiling.

Episode 2: web holds the logic, DB gets its own machine. In 2026 the default is a relational store first, PostgreSQL-class. Schema, transactions, and joins do not get a NoSQL box just to look distributed. Pure KV, pure time-series, or massive writes, then a specialized store.

Episode 3: add web boxes horizontally, put a managed LB in front. The LB drops unhealthy nodes and spreads traffic. Homogeneous machines: round-robin is enough. Long-lived connections, then least-conn. Clients only see the LB. Web boxes talk on the private network.

Stop and admit it: the DB is still one machine, and reads die there first. If session still lives in one web’s memory, the LB has to be sticky, and horizontal scale is fake. Episode 6 splits that. Write the landmine on the board now.

存储选型在 Ch37 · 存储。L4 / L7 和一致性哈希 LB 在 Ch39 · 负载均衡。HTTP 读路径在 Ch40 · 协议。Storage choice is Ch37 · storage. L4 / L7 and consistent-hash LB are Ch39 · load balancing. The HTTP read path is Ch40 · protocols.

主从、缓存，然后把 session 拿出去Replica, cache, then session leaves the web

中文

第 4 集：web 能加了，典型业务仍是读多写少，读把单库打满。术语用 primary / replica。一次说完三件事：读摊开、数据有副本、库挂了还能切。

复制默认先说异步：快，主挂可能丢掉还没复制出去的写入。要更小的丢失窗口，再提半同步，至少一个 replica 收到才 ACK。等所有 replica 会把跨 AZ 延迟写进关键路径。金融可以谈，社交 timeline 通常不值得。

新痛点先记在白板上：failover 不是改一条 DNS；replica 会落后。用户写完立刻读 replica，可能读到旧值。这两点是后面的 deep dive。

第 5 集：热点读走 cache-aside。miss 回源再回填；写库之后删缓存，不改缓存。头像、JS、视频走 CDN 和对象存储。TTL 必须有。cache 自己要多副本，不然只是把 SPOF 搬了个地方。

2026 可以补一句：多个派生数据不想让应用双写时，用 CDC 听 WAL 或 binlog 做失效或回填。会 aside 就能过，CDC 是加分。穿透、击穿、雪崩只点名：空值 TTL、热点互斥、TTL 加抖动。

第 6 集：web 无状态。session 放到共享存储，或用 JWT，web 只验签。任意一台都能接，LB 不必粘滞。JWT 的代价说出来：主动登出要黑名单，或短 access 加 refresh。无状态副本才能按指标加实例，编排细节另读。新痛点：共享 session 是新依赖；单 Region 挂了，前面这些救不了跨洲用户。

English

Episode 4: web can grow, and a typical product is still read-heavy, so reads fill the single database. Say primary / replica. Three wins in one breath: reads spread out, data has copies, a dead database can still fail over.

Default replication is async: fast, and a dead primary can lose writes that never reached a replica. A smaller loss window is semi-sync: ACK after at least one replica has it. Waiting for every replica puts cross-AZ latency on the critical path. Finance can talk about that. A social timeline usually should not.

Park the new pain on the board: failover is not “change a DNS record,” and replicas lag. A user who writes and immediately reads a replica can see a stale value. Those two are the deep dive.

Episode 5: hot reads go cache-aside. A miss reads origin and fills. After the DB write, delete the cache. Do not update it. Avatars, JS, and video go through a CDN and object storage. TTL is required. The cache needs its own replicas, or you only moved the SPOF.

One 2026 line: when several derived stores should not be dual-written by the app, use CDC on the WAL or binlog to invalidate or refill. Aside is enough to pass. CDC is extra credit. Penetration, breakdown, and stampede: name empty-value TTL, a mutex on the hot key, and TTL with jitter.

Episode 6: the web tier is stateless. Session lives in a shared store, or in a JWT the web only verifies. Any box can take the request, so the LB does not stick. Say the JWT cost: logout needs a denylist, or a short access token plus refresh. Only stateless replicas scale from a metric. Orchestration details live elsewhere. New pain: the shared session is a new dependency. A dead Region still does not save a user on another continent.

多 Region，然后才是 MQ 和分片Multi-Region, then MQ and sharding

中文

第 7 集的痛点：单 Region 故障域太大，跨洲用户每次 RTT 都是百毫秒级。同一 Region 里多 AZ 是 2026 的默认高可用，不是加分项。真要容灾和就近访问，入口用 geoDNS 或 Anycast，按位置和健康检查切流量。

Active-PassiveActive-Active
流量一个 Region 接写，另一个热备两个都接
failover分钟级切主本来就活着
数据单向复制，冲突少双向写，冲突是 hard part
成本备可以降配接近两份活资源

Active-Active 不是免费的全球低延迟。跨洲同步，要么为了一致加延迟，要么为了可用接受短暂分叉。按数据选，不要按整站选：账户可以偏一致，Feed 可以偏可用。常见逃法是用户固定写归属 Region，而不是一上来全球同步写。对象存储的跨 Region 复制好讲，疼的是数据库。

第 8 集上半：上传转码、通知、刷派生数据如果同步做，写路径被慢任务堵住，web 和 worker 也不能分开扩。写入先落到托管 Kafka 这一类日志，web 尽快返回，积压就加消费者。生产默认 at-least-once，所以消费方用业务唯一键做幂等。exactly-once 作为口号很响，工程上多半是至少一次加上幂等。MQ 解决不了单库写天花板。

第 8 集下半：主从只扩读。按分片键把数据拆开。键要高基数、分布均匀、常用点查落到一个 shard。user_id 通常可以；gender 或单调时间戳当唯一键容易热点。2026 第一句：能用原生分布式 SQL 就优先，让存储层切 range、再平衡、做多副本。面试仍会问手搓分片，因为 hard part 没变：分片键、reshard、热点、跨片 join。跨片 join 和跨片事务优先避开，同一聚合的数据放一起。到这里演进可以收住，转 Step 3。

English

Episode 7 pain: one Region is too big a failure domain, and every cross-continent RTT is hundreds of milliseconds. Several AZs inside one Region is default HA in 2026, not extra credit. Real disaster recovery and proximity mean geoDNS or Anycast at the edge, switching on location and health.

Active-PassiveActive-Active
TrafficOne Region writes, the other is hot standbyBoth take traffic
failoverMinute-class cutoverAlready live
DataOne-way replication, few conflictsBidirectional writes. Conflict is the hard part
CostStandby can be smallerClose to two live copies

Active-Active is not free global low latency. Cross-continent sync either adds latency for consistency, or accepts a brief fork for availability. Pick per data, not per whole site: accounts can lean consistent, a feed can lean available. The usual escape is a user always writes their home Region, not global sync-on-write from minute one. Object storage replication is the easy sentence. The database is the pain.

Episode 8, first half: if transcode, notifications, and derived data run on the request, slow jobs block the write path, and web and workers cannot scale apart. Land the event on managed Kafka, or a similar log. The web returns fast. Backlog means add consumers. Production default is at-least-once, so the consumer is idempotent on a business unique key. exactly-once is usually at-least-once plus idempotency. MQ does not lift the single-DB write ceiling.

Second half: primary/replica only scales reads. Split rows by a shard key. The key needs high cardinality, an even spread, and point lookups on one shard. user_id usually works. gender, or a monotonic timestamp as the only key, hotspots. First sentence in 2026: prefer native distributed SQL, and let the storage layer split ranges, rebalance, and keep replicas. Interviews still ask for hand-rolled sharding, because the hard part did not change: shard key, reshard, hot keys, cross-shard join. Avoid cross-shard joins and cross-shard transactions. Keep one aggregate together. Park the evolution here and switch to step 3.

失败路径：failover 和读到旧值Failure path: failover and a stale read

中文

Step 3 挑 1–2 个挖透。这题的 hard part 通常是下面两块，外加分片键。三个都浅，不如一块讲完。

failover 五步：探测（连续健康检查失败）→ 选本（复制位点最新的 replica）→ 对齐（追上旧 primary）→ 切路由 → 补副本。异步下，ACK 了但还没进 replica 的写入会丢。这就是 RPO。半同步缩小窗口，代价是写延迟。说你接受多大窗口，用什么复制模式买这个窗口。

写后立刻读是必追问。三种接法，说清 trade-off 即可。

做法效果代价
写后短时间读 primary该用户 read-your-writesprimary 读压力上去
带版本，replica 没追上就回 primary更准要暴露位点或版本
半同步stale 窗口变短写变慢

单调读：同一用户钉在同一个 replica，别让 LB 在落后程度不同的副本之间跳。刷新之后数据变少，就是这个 bug。

缓存写路径是先写 DB，再删缓存。删是幂等的。并发下「写库同时 SET 缓存」会把旧值盖回去。删完靠下次读回填，TTL 当兜底。仍可能发生：读拿到旧行，写删了空缓存，读再把旧行 SET 回去。短 TTL 把窗口限住。下游多（缓存、搜索、数仓）就提 CDC，不要在白板上现编一套双写协议。

English

In step 3, pick one or two and go to the bottom. The hard part here is usually the next two, plus the shard key. Skimming all three scores worse than finishing one.

Failover in five spoken steps: detect consecutive health-check failures, pick the replica with the newest position, catch it up, cut routing, rebuild replicas. Under async, a write can be ACK’d and still never reach a replica. That loss is RPO. Semi-sync shrinks the window and slows writes. Say how large a window you accept, and which mode buys it.

Read-your-writes is a must-follow-up. Three moves. Name the trade-off.

MoveEffectCost
After a write, read primary for a short windowThat user gets read-your-writesPrimary read pressure goes up
Client carries a version; lagging replica falls back to primaryMore preciseYou expose a position or version
Semi-syncShorter stale windowWrites get slower

Monotonic reads: pin the same user to the same replica. If the LB hops across replicas that lag by different amounts, a refresh makes the data shrink.

The cache write path is write the DB, then delete the cache. Delete is idempotent. SET in the same breath as the DB write can put the old value back under concurrency. The next read fills. TTL is the net. A race remains: a read holds the old row, a write deletes an empty cache, the read SETs the old row. A short TTL bounds that window. Several downstreams (cache, search, warehouse) means mention CDC. Do not invent a dual-write protocol on the board.

四个 trade-off，各选一边Four trade-offs, pick a side

中文

面试官要的是你选边，并说出代价。下面四笔按追问出现的顺序画。默认答案放左边或中间，你准备放弃的那一侧标出来。

复制：先异步。对方追丢数据，再把半同步摆上来。等所有副本，只在对方明确要更小 RPO、且能接受写变慢时才谈。

会话：sticky 是过渡或反例。正文默认共享 session 或 JWT。两种都要说出作废和依赖。

多 Region：默认同 Region 多 AZ，跨 Region 先 Active-Passive。Active-Active 的 hard part 是双向写冲突。

分片：hash % N 改 N 几乎全量搬家。能用分布式 SQL 就让它再平衡。手搓时提前说迁移窗口，不要假装取模能活到很大。

English

They want you to pick a side and name the cost. Draw these four in the order follow-ups show up. The default sits on the left or in the middle. Mark the side you are ready to drop.

Replication: async first. If they push on data loss, bring up semi-sync. Waiting for every replica only if they ask for a smaller RPO and will accept slower writes.

Session: sticky is a transition or a counter-example. The body default is a shared session or a JWT. Both need a sentence on revoke and on the new dependency.

Multi-Region: default is several AZs in one Region. Across Regions, start Active-Passive. The hard part of Active-Active is a bidirectional write conflict.

Sharding: change N on hash % N and you move almost every row. Distributed SQL rebalances for you when you can use it. If you hand-roll, say the migration window up front. Modulo does not quietly survive a much larger N.

中文

English

  1. Why not draw the final architecture? They score the evolution. Opening with the final picture is over-engineering.
  2. I wrote, refreshed, and don’t see it? You read a lagging replica. After a write, read primary for a short window, or fall back when the version has not caught up.
  3. If the primary dies, do we lose data? Async, yes. Talk RPO and the window you accept.
  4. Cache and DB disagree? Aside, delete, TTL. Many downstreams, mention CDC.
  5. Can’t sticky still scale? For a while. Box death drops the session, and scale-in has to migrate it. The answer you stand on is stateless.
  6. Multi-Region that is both fast and consistent? Pick per data. Accounts and a feed do not need the same answer.
  7. Traffic times 10? Find which layer dies first: LB, cache, primary writes, or a hot shard. Then replicas or sharding. Adding machines with no layer named is not a plan.
