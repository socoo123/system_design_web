本章要点：固定版本，分配资源，再逐步上线Core: versions, resources and rollout

平台要回答三个问题：这组设备加载了什么，能否承接当前请求，出错后怎样退回旧版本。本章沿着这条主线展开：先固定不可变的上线组合（bundle），再放置并预热完整副本，按多种资源约束决定是否接纳请求，最后灰度发布，并等旧请求的实际工作结束后回收资源。版本登记服务（Registry）和副本控制器（Fleet Controller）负责准备与协调，不参与每个 token 的传输。

  • 版本：把权重、分词器（tokenizer）、提示词（prompt）、引擎镜像和运行配置固定为同一组合。
  • 资源：先筛选符合设备与隔离条件的位置，再原子预占租户和副本两边的资源信用；平均占用、吞吐和故障余量分别估算。
  • 上线：先准备好新容量，再发布更高的路由修订号（revision）。在途请求沿用原来的上线组合；旧版本保留了多少热容量，决定能否快速回滚。

Prove what a device group loaded, whether it can accept this request, and how to recover.Pin an immutable bundle → place/warm complete replicas → admit resource demand → roll out and retire old streams. Registry and Fleet Controller do not carry each token.

  • Versions: pin weights, tokenizer, prompt, image and runtime configuration together.
  • Resources: filter device/isolation constraints, then atomically reserve tenant/replica credit. Size means, throughput and failure headroom separately.
  • Rollout: prepare capacity before publishing a higher revision. In-flight work keeps its bundle; retained warm capacity enables fast rollback.

设计范围与容量假设Scope and capacity assumptions

本章设计一个单地域、供内部多个租户使用的在线模型托管平台。Ch29 负责引擎内部的批调度与 KV 页，Ch32 负责 API 契约与 token 账本；本章负责部署、设备组和版本发布。训练会更新权重，还要单独预算梯度、优化器状态、激活和检查点（checkpoint）；这里仅接收训练产物，不能用在线推理的 KV 预算估算训练成本。离线批任务使用独立队列；如果借用在线 GPU，就必须能及时归还，回收和重新加载期间不计入在线热容量。

本章所有数字都是教学假设，没有进行 GPU 压测。每副本 C=4 req/s，表示在权重、精度、请求长度分布和服务目标（SLO）固定时，假设能够满足目标的最高接纳速率。验证时要把超时、取消和失败都算进去，同时检查延迟与错误率。有效吞吐（goodput）只统计达标完成的请求，不能代替总接纳速率。使用 Little 定律还要求系统稳定，并且到达率和驻留时间采用相同的“准入到物理释放”边界；算出平均在途数 160，并不能证明尾延迟达标。

Design a single-region internal multi-tenant online hosting platform. Ch29owns engine iterations/KV pages; Ch32owns APIs/token accounts. Here we own deployment, device groups and rollout. Training updates weights and budgets gradients, optimizer state, activations and checkpoints separately. We receive its artifacts; online KV sizing does not size training. Batch has a separate queue; borrowed online devices count as warm only after reclaim/load completes.

All numbers are teaching assumptions; no GPU load test was run.C=4 assumes a maximum admission rate meeting fixed workload/profile SLOs. Include timeout/cancel/failure outcomes and validate errors plus latency. Goodput counts compliant completions, not all admissions. Little’s law uses a stable, identical admission-to-physical-release boundary; 160 does not establish tail behavior.

总图：控制面准备 READY 端点，请求面从中选择Overview: request and control planes meet at READY endpoints

第 5 帧可以作为方案总览。一次请求依次经过 Client、Gateway、推理路由器（Inference Router）和模型执行端（Model Worker），生成的 token 再沿原路逐跳返回。路由器为请求固定一份完整的上线组合及路由修订号，并携带可信租户身份、请求摘要和期限。KV 状态留在模型执行端；控制面既不为每次请求重新下载权重，也不传输生成的 token。

Use frame 5 as the overview.Client → Gateway → Inference Router → Model Worker, with token replies reversing the hops. Router pins one coherent bundle/revision and carries trusted tenant, request digest and deadlines. KV remains on the worker; control does not download weights per request or move tokens.

副本控制器先持久记录部署信息（deployment）、稳定的副本标识 replica_id、上线组合、设备集合和部署代次（generation），形成期望状态，再协调加载。如果创建命令的回复丢失，就按原身份查询，不能另建一个副本。设备的唯一预占用于防止重复分配；按持有者（owner）条件写入，以及节点代理拒绝旧代次命令，则用于阻止过期控制者继续操作。副本只有在完整内容、镜像、设备组和当前部署代次都匹配，并通过代表性请求预热后，才能报告可接流量（READY）；端口能连接还不够。控制器核实这份完整的观测证明后，才把端点发布给路由器。Kubernetes 的控制回路可以帮助理解“期望状态与实际状态不断对齐”；具体代次与准入协议由本章约定。[10]

控制器不可用与权威库不可用，处理方式不同。如果 Fleet/Registry API 故障，但资源账本仍可用，已有热副本可以在有效路由下继续获得准入凭证。若账本不可达，就无法原子扣减资源信用，必须立即停止新准入；已经接纳的流仍按原契约完成退休。中央账本仍是本方案的可用性依赖，不能因为控制器不传 token，就把整个控制面都从依赖链中划掉。端点选择也可以与流量转发分开：Gateway API Inference Extension 的端点选择组件 EPP 为代理挑选端点，不负责代理全部 token。[5]

Fleet Controller persists deployment, stable replica IDs, bundle/device set and generation before reconciliation; uncertain create calls query that identity. Unique device reservations, conditional ownership and node-agent generation checks address different races. READY proves exact content/image/device group/current generation plus representative warmup, not an open port. Only complete observed proof publishes endpoints. Kubernetes documents desired/actual control loops; epochs/admission here are our protocol. [10]

Controller loss differs from authority-store loss.With Fleet/Registry APIs down but Ledger available, warm workers may receive permits under valid routes. An unavailable Ledger immediately stops new holds because credit cannot be serialized; accepted streams retire normally. A central authority remains an availability dependency. Selection and forwarding may be separate: the Gateway API Inference Extension EPP selects endpoints for a proxy rather than carrying all tokens. [5]

模型版本：先封存内容，再证明能够服务Model versions: seal content, then prove serving readiness

上线组合（bundle）把一次部署需要的内容完整、不可变地固定下来。它包含权重分片、分词器、提示词、引擎镜像摘要、量化与运行配置，以及模型适配器（adapter）和兼容的基础模型（base）。每个文件的摘要都写入清单（manifest）。下载时必须固定在同一个不可变提交版本，不能中途追随不断变化的 main 分支。Hugging Face 支持按提交版本（commit revision）下载；MLflow 的别名（alias）则可以重新指向不同版本。这两种机制本身都不提供本章要求的跨记录原子发布。[1][2]

A bundle is a complete immutable serving combination.Pin weight shards, tokenizer, prompt, engine image digest, quantization/runtime configuration, adapters and compatible base, with per-file hashes in a manifest. Download one immutable revision, never a moving main branch. HF supports commit revisions; MLflow aliases can be reassigned. Neither alone provides our multi-record atomic publication. [1][2]

顺序是先写完并校验对象，再登记上线组合，最后加载、预热到 READY。对象已写入但登记失败时，只留下孤立对象，后续按引用关系与留存规则清理；若先登记再异步补分片，读者就可能看见不完整的版本。摘要校验失败应记录失败，旧部署代次迟到的 READY 报告应忽略，不能原地修改已封存的清单，或让旧端点重新生效。日志应关联请求标识 request_id、上线组合摘要 bundle_hash、路由修订号 route_revision，以及副本和进程/设备代次（replica/epoch），只记录 model=prod 无法定位实际执行版本。

按 A6，单份冷加载为 40 GB÷2 GB/s+100 s=120 s；9 份冷下载合计 360 GB。如果 2 GB/s 是共享出口的总速率，仅下载就至少需要 180 s，不能给 9 个加载者各算一条独享链路。本地缓存也需要完整性校验，以及磁盘、CPU 和并发预算。提示词或 LoRA 适配器文件较小，仍会消耗 GPU 资源：更长的提示词或输出会增加输入预填充（prefill）、KV 和驻留成本；模型适配器还必须绑定兼容的基础模型。

Complete and verify objects, register the bundle, then load/warm to READY. Objects without a registry commit are orphan cleanup candidates; publishing before async upload exposes incomplete content. Hash failures and late old-generation READY reports cannot patch a sealed manifest or revive stale endpoints. Correlate request/bundle/revision/replica/epoch rather than only model=prod.

A6: 40 GB/2 GB/s+100 s=120 s; nine cold copies total 360 GB. With 2 GB/s aggregate egress, download work alone needs at least 180 s. Caches still require integrity, disk/CPU and concurrency budgets. Smaller prompts/adapters are not zero-cost: longer prompts/output increase prefill/KV/residence; adapters pin compatible bases.

设备与故障域：分别计算占用、吞吐和幸存容量Devices and failure domains: occupancy, throughput and survivors

先判断一个完整副本能放在哪里，再计算每种设备故障会带走多少完整副本。显存、设备互联、镜像和租户隔离都是必须满足的条件。先让副本跨机器分散（spread），再在合格位置内尽量填满资源（binpack）。Kubernetes 的 MostAllocated 用于资源评分；要把分散放置设成硬约束，还需要 DoNotSchedule 等相应配置。调度评分与分散放置都不能替代 GPU 隔离，也不能证明故障后的容量足够。[3][4]

First find eligible devices, then count complete replicas lost with each failure.Memory, interconnect, image and isolation are hard constraints. Spread across machines before packing eligible placements. Kubernetes MostAllocated is a scoring policy; hard spread needs the appropriate DoNotSchedule policy. Neither proves GPU isolation or surviving capacity. [3][4]

先算平均占用下界：20×8=160，ceil(160/32)=5；再算正常吞吐预算：ceil(20/(4×0.8))=7。如果把 7 个副本按 3/2/2 放置，失去副本最多的机器后只剩 4 个，原始容量为 16/s，80% 预算为 12.8/s。改用 9 个副本、按 3/3/3 放置后，正常有 288 个槽位和 36/s；单机故障后剩 192 个槽位、24/s 原始容量，峰值负载达到 83.3%。若仍按 80% 预算接纳，就只有 19.2/s，至少要拒绝 0.8/s，即峰值的 4%；要接住全部峰值，则须另外验证降级后的 SLO。原始容量覆盖到达率，并不能保证 p99 达标。

如果故障后仍要维持相同的 80% 预算，三台机器均衡放置至少需要 11 个副本。按 4/4/3 放置，最大故障损失为 4 个，仍有 7×3.2=22.4/s；10 个按 4/3/3 放置，最大损失后却仍只有 19.2/s。下面的 Java 17 代码按最大故障域计算，不能把单机故障的 N−1 理解为只少一张卡。本章继续采用允许故障降级的 9 副本方案，后续的 12 张卡与 20 张卡预算也都以此为基础。

Occupancy lower bound:20×8=160; ceil(160/32)=5. Normal rate budget:ceil(20/(4×0.8))=7. Seven spread 3/2/2 leave four after the largest loss: raw 16/s, planned 12.8/s. Nine spread 3/3/3 give 288 slots/36/s; six survivors give 192 slots/raw 24/s at 83.3% load. The same 80% budget is only 19.2/s: reject at least 0.8/s (4%) or validate a degraded SLO. Raw coverage does not prove p99.

Preserving the same 80% budget after failureneeds at least eleven across three balanced nodes (4/4/3): lose four, retain 7×3.2=22.4/s. Ten (4/3/3) still leave only 19.2/s. The Java17 calculation uses the largest domain loss, not one missing device. Nine remains our degradation-allowed choice; the twelve/twenty-GPU rollout figures retain it.

import java.util.Arrays;

// Java 17. All rates are teaching assumptions for one fixed workload/profile.
public final class Capacity {
    static double surviving(int[] perNode, double admittedPerReplica) {
        int total = Arrays.stream(perNode).sum();
        int largestLoss = Arrays.stream(perNode).max().orElseThrow();
        return (total - largestLoss) * admittedPerReplica;
    }

    static int sameBudgetReplicas(int domains, double peak, double planned) {
        for (int n = 1; ; n++) {
            int largestLoss = (n + domains - 1) / domains;
            if ((n - largestLoss) * planned >= peak) {
                return n;
            }
        }
    }

    public static void main(String[] args) {
        double peak = 20, residence = 8, cap = 4, headroom = 0.8;
        int slots = 32;

        System.out.printf("meanActive=%.0f slotLowerBound=%.0f normal=%.0f%n",
                peak * residence, Math.ceil(peak * residence / slots),
                Math.ceil(peak / (cap * headroom)));
        System.out.printf("nine: rawSurvivor=%.1f plannedSurvivor=%.1f%n",
                surviving(new int[]{3, 3, 3}, cap),
                surviving(new int[]{3, 3, 3}, cap * headroom));
        System.out.printf("same-budget N-1 across 3 nodes: %d%n",
                sameBudgetReplicas(3, peak, cap * headroom));

        if (sameBudgetReplicas(3, peak, 3.2) != 11) {
            throw new AssertionError();
        }
        if (surviving(new int[]{4, 4, 3}, 3.2) < peak) {
            throw new AssertionError();
        }
        if (surviving(new int[]{4, 3, 3}, 3.2) >= peak) {
            throw new AssertionError();
        }
    }
}

每张 GPU 都要单独核算显存，不能把空闲字节随意相加。对每张卡，都须满足：权重分片 + 引擎临时空间峰值 + KV 信用 + 安全余量 ≤ 可用显存。教学算例为 80 GiB−40 GiB 权重−8 GiB 临时峰值−8 GiB 余量=24 GiB KV 预算；这里使用 GiB，与前面 40 GB 的磁盘产物是两项独立假设。KV 占用随活跃上下文和模型结构变化，仅限制 32 条序列还无法限定显存。vLLM v0.15.1 分别讨论了序列数、每批 token 数、KV 不足和并行度，但没有提供本章的容量数字。[6]

异构 GPU 要按运行规格（profile）分别标定精度、上下文范围、容量和临时空间峰值，不能合并两张不兼容设备的空闲显存。张量并行（TP）副本必须一次唯一预留整个设备组，并在整组就绪后报告 READY；本章约定，只要一个并行进程（rank）不可用，整个副本组就不可服务。若副本组跨机器，故障损失应包括所有使用了故障机器的组，不能只数该机器上的 rank。空闲卡和仍在加载的副本，都不计入幸存热容量。

Device memory is not one freely pooled bucket.Each device must fit its weight shard + peak engine workspace + KV credit + safety reserve. A teaching 80 GiB−40 GiB weights−8 GiB workspace−8 GiB reserve leaves 24 GiB KV; this is independent of the 40-decimal-GB disk artifact. KV depends on live context/model geometry; 32 sequences alone do not bound it. vLLM v0.15.1 separately discusses sequence/batch-token limits, KV pressure and parallelism, not our capacity numbers. [6]

Benchmark heterogeneous profiles separately for precision/context/capacity/workspace; free bytes on incompatible devices cannot be added. Reserve TP devices as a whole and require whole-group READY; one unavailable rank makes that replica group unavailable in this contract. Node loss removes every group touching that node, not just local ranks. Empty devices/loaders are not surviving warm capacity.

多维准入：先预占资源，再派发，物理退休后才归还Admission: durable multidimensional holds, unique dispatch, physical retirement

监控指标帮助路由器选择候选，资源账本决定是否允许预占。平台同时约束序列数与 KV 信用。可信组件根据分词结果、输出上限、模型结构和运行规格计算 KV 需求，再向上取整到 MiB；这份信用是保守预留量，并非当前已分配的 KV 页。运行规格的可用容量已扣除权重和临时空间峰值；Ch29 仍需在引擎每轮调度时执行批内 token 数与计算预算。拿到准入凭证，也不能让引擎突破显存或调度限制。

Metrics choose candidates; authority decides credit.Bound both sequences and KV credit, rounded up to MiB from trusted tokenization/output bounds, geometry and device profile. Credit is conservative reservation, not allocated live pages. Profile capacity already subtracts weights/workspace; Ch29 still enforces per-iteration batch-token/compute limits. A platform permit cannot override engine memory/scheduling limits.

资源预占：两边账本与唯一请求在同一事务中提交Reserve both budgets with one request identity

下面摘自使用本地 SQLite 文件数据库的可运行 Python 实现。事务封装 write_tx 执行 BEGIN IMMEDIATE，再以 COMMIT 或 ROLLBACK 结束；不同连接、不同进程的写入由数据库串行化。租户和副本两边的序列、KV 条件更新，以及唯一请求身份 (tenant,rid)，在同一事务中提交。如果副本侧扣减失败，先前的租户扣减也会回滚。同一个请求键若改变正文、上线组合、运行规格或信用量，就报冲突；重放已到终态的请求也不会重新执行。[11]

This runnable Python/SQLite file-database excerpt uses BEGIN IMMEDIATE and COMMIT/ROLLBACK. SQLite serializes writers across connections/processes. Tenant/replica sequence and KV conditional updates plus unique (tenant,rid) share a transaction; second-step failure rolls back the first. Changed body/bundle/profile/credit conflicts, and a terminal replay never reopens work. [11]

def take(db, table, identity, kv):
    # table is an internal constant: tenant or replica, never client SQL.
    sql = f'''UPDATE {table} SET used_slots=used_slots+1, used_kv=used_kv+?
              WHERE id=? AND used_slots+1<=slots AND used_kv+?<=kv'''
    if db.execute(sql, (kv, identity, kv)).rowcount != 1:
        raise Refused(table + ' capacity')


def reserve(db, q, clock, fail_after_tenant=False):
    fp = encoded([q['body'], q['bundle'], q['profile'], q['kv']])
    with write_tx(db):
        now = clock()
        old = db.execute(
            'SELECT * FROM permit WHERE tenant=? AND rid=?',
            (q['tenant'], q['rid'])
        ).fetchone()
        if old:
            if old['fingerprint'] != fp:
                raise Refused('same key, different request')
            return dict(old) | {'created': False}

        r = one(db, 'SELECT * FROM replica WHERE id=?', (q['replica'],))
        t = one(db, 'SELECT * FROM tenant WHERE id=?', (q['tenant'],))
        s = one(db, 'SELECT * FROM snapshot WHERE rev=?', (q['rev'],))
        rev = one(db, 'SELECT rev FROM control WHERE id=1')['rev']
        endpoints = json.loads(s['payload'])['endpoints']
        exact = [r['id'], r['epoch'], r['bundle'], r['profile']]
        if (
            q['kv'] <= 0
            or q['rev'] != rev
            or now >= s['expires']
            or exact not in endpoints
            or not r['ready']
            or r['draining']
            or (r['bundle'], r['epoch'], r['profile'], r['tier']) != (
                q['bundle'], q['epoch'], q['profile'], t['tier']
            )
        ):
            raise Refused('ineligible or stale')

        deadline = min(q['deadline'], s['expires'])
        if now >= deadline:
            raise Refused('deadline')

        take(db, 'tenant', q['tenant'], q['kv'])
        if fail_after_tenant:
            raise RuntimeError('injected before replica charge')
        take(db, 'replica', q['replica'], q['kv'])

        values = (
            q['tenant'], q['rid'], fp, q['bundle'], q['replica'],
            q['epoch'], q['profile'], q['kv'], q['rev'], deadline
        )
        db.execute("INSERT INTO permit VALUES(?,?,?,?,?,?,?,?,?,?,'HELD')", values)
        return dict(permit(db, q['tenant'], q['rid'])) | {'created': True}

派发：查询到状态，不会重新获得执行权Dispatch: observing state does not regrant execution

def begin_dispatch(db, tenant, rid, clock):
    with write_tx(db):
        now = clock()
        p = permit(db, tenant, rid)
        if p['state'] != 'HELD':
            return False

        r = one(db, 'SELECT * FROM replica WHERE id=?', (p['replica'],))
        rev = one(db, 'SELECT rev FROM control WHERE id=1')['rev']
        if (
            now >= p['deadline']
            or p['rev'] != rev
            or not r['ready']
            or r['draining']
            or r['epoch'] != p['epoch']
        ):
            close_credit(db, p, 'EXPIRED')
            return False

        db.execute(
            "UPDATE permit SET state='DISPATCHING' WHERE tenant=? AND rid=?",
            (tenant, rid)
        )
        return True  # Only this successful caller may send once.


def consume(db, tenant, rid, worker, epoch, bundle, clock):
    with write_tx(db):
        now = clock()
        p = permit(db, tenant, rid)
        r = one(db, 'SELECT * FROM replica WHERE id=?', (worker,))
        if (
            p['state'] != 'DISPATCHING'
            or now >= p['deadline']
            or (worker, epoch, bundle) != (p['replica'], p['epoch'], p['bundle'])
            or r['epoch'] != epoch
            or r['bundle'] != bundle
            or not r['ready']
        ):
            return False

        db.execute(
            "UPDATE permit SET state='RUNNING' WHERE tenant=? AND rid=?",
            (tenant, rid)
        )
        return True  # Only this successful caller may enqueue GPU work once.

代码在取得写锁后才调用 clock()，读取权威时间，因此等待写锁期间跨过截止时间，也会被拒绝。只有首次得到 begin_dispatch=True 的原调用者可以发送一次，只有首次得到 consume=True 的原调用者可以把工作放入 GPU 队列一次。如果事务已提交但确认回复丢失，或提交后进程崩溃，后来查询到 DISPATCHING/RUNNING 的调用者也不能补发或补启动。本例选择保留信用，等待核查或隔离，代价是可能无法继续推进，并不保证恰好完成一次。重启时必须先隔离旧进程、旧设备，再启用新的进程/设备代次 epoch；仅靠进程内的 Set 无法恢复这些事实。

运行中的请求，或派发结果未知的请求取消后，都先进入 RETIRING。物理退休要求可信完成适配器确认全部相关 GPU 内核、复制操作和流依赖已结束，或旧进程、设备已被隔离或重置；此后才能把终态与租户、副本两边的信用归还放在同一事务中提交。重复通知或旧代次回执不会重复归还。CUDA event 只证明它所捕获的工作完成，任意一个 event 完成并不代表整张卡都可安全复用。[12]本例测试只是注入可信完成通知，没有运行 CUDA。只有未派发的 HELD 可以与派发原子竞争并过期；TTL 不能释放 DISPATCHING 或结果未知的占用。执行达到 60 s 时启动终止流程，也不能提前归还信用。

等待队列另有 40 条硬上限和 200 ms 准入期限；20×0.2=4 只是稳态平均排队数。公平排队要考虑预计工作量，每租户 16 条并发也不能覆盖任意长的上下文。账本拒绝或不可达时，不得发送请求。Ch32 的 token 预留在另一套账本中，拒绝后的释放与后续结算需通过持久、幂等的终态记录或 outbox 恢复，不能把两个数据库说成同一笔事务。

Sample the authority clock after acquiring the writer lock, so a lock wait crossing deadline rejects. Only the original begin_dispatch=True caller may send once; only the original consume=True caller may enqueue once. A lost commit ACK or post-commit crash cannot authorize a later observer to resend/relaunch. This model sacrifices progress, retaining credit for reconciliation/fencing; it does not promise exactly-once completion. Fence old processes/devices before a new epoch; an in-memory Set is insufficient recovery.

Canceling RUNNING/unknown dispatch enters RETIRING. A trusted adapter must prove all relevant kernels/copies/stream dependencies ended, or fence/reset the old device/process, before terminal state and both refunds commit together. Repeated/old-epoch notices cannot refund twice. CUDA events prove captured work, not all-device safety from an arbitrary event. [12]The tests inject completion notices and do not run CUDA. Only HELD may expire against dispatch atomically; TTL never refunds DISPATCHING/UNKNOWN. Sixty seconds starts termination, not early reuse.

The queue separately caps forty with 200-ms admission deadlines. 20×0.2=4 is mean queue occupancy, not a maximum. Fair scheduling estimates work; sixteen concurrent requests do not cover arbitrary contexts. Never send after refusal/unavailable Ledger. Releasing independent Ch32 token holds needs durable idempotent terminal/outbox recovery; two databases are not one transaction.

租户与 KV 亲和：先满足隔离条件，再考虑缓存命中Tenants and KV affinity: isolation before hits

路由器先按权限、上线组合、隔离等级、运行规格和期限筛选，再用缓存命中给合格候选加分。私有资源池满了，就拒绝请求，或选择同等级的私有备用池，不能悄悄转入共享池。若首选执行端因为热点而满载，可以换到同一上线组合的合格执行端，重新计算输入预填充；已经开始输出的流，则继续固定在原执行端与原调用尝试（attempt）上。

Filter authority, bundle, isolation tier, profile and deadline before scoring cache hits.A full private tier rejects or uses equivalent private backup. A full preferred worker can yield to an eligible same-bundle worker and recompute prefill; an active stream remains pinned to its worker/attempt.

执行端本地的 KV 缓存，按可信租户身份、精确计算内容和 token 前缀划分命名空间。权重、分词器、模型适配器或位置配置变化后，不能误用旧块；旧命名空间要随在途请求逐步排空，不能直接删除仍被引用的页。这也不同于 Ch32 缓存整份答案的做法。vLLM 安全说明把共享前缀造成的 TTFT 差异视为时序侧信道风险，并用 cache_salt 限定只有相同 salt 才可复用缓存。平台应注入不可猜测的秘密值，不能相信用户自报的 salt；共享同一进程本身也不构成租户隔离。[8]

NVIDIA GPU Operator 24.9.1 说明，按时间片共享 GPU 的“副本”之间没有显存或故障隔离；MIG 提供相应的硬件隔离，但无法隔离宿主机、网络等所有共享资源。[7]因此，本章为敏感租户使用独立进程和明确的设备边界。命名空间保护缓存复用边界，硬件边界约束资源与故障影响，公平队列处理等待，三者各有职责。16×4,000=64,000 与 16×32,000=512,000 只是总 token 工作量的示意，既不是 KV 字节数，也不保证运行时间恰好增加八倍。

Worker-local KV namespaces include trusted tenant and exact computational identity/token prefix. Weight/tokenizer/adapter/position changes cannot reuse incompatible blocks. Drain referenced old namespaces rather than deleting live pages. This differs from Ch32 answer caching. vLLM documents prefix TTFT timing risk and same-salt reuse; inject an unpredictable secret rather than trusting caller salt. A shared server process is not tenant isolation. [8]

NVIDIA GPU Operator 24.9.1 documents no memory/fault isolation between time-sliced GPU “replicas”; MIG provides corresponding hardware isolation but not all shared host/network isolation. [7]Sensitive tenants here use dedicated processes and explicit devices. Namespaces, hardware boundaries and fair queues protect different things. 64,000 versus 512,000 total tokens illustrates work, not KV bytes or a guaranteed eightfold runtime.

发布与回滚：调整新请求，保留旧契约和热容量Rollout and rollback: new traffic, pinned contracts and warm capacity

先准备好 READY 容量，再提高新版本的流量权重。峰值 20×10%=2 req/s，所以一个假设容量 C=4/s 的灰度副本只是起点。全量切到 v2 后，如果还保留完整的 v1 热回滚容量，加上两个小模型副本，就需要 9+9+2=20 张卡；起步灰度则是 9+1+2=12 张卡。v2 至少运行 5 分钟，并取得 600 个可比样本后，才考虑逐步放量（ramp）；数据不足就暂停放量。这只是示例观察门槛，不能证明统计置信度。10% 表示请求比例，若长度和输出分布变化，还要重新测量资源分布。

Prepare READY capacity before raising traffic weight.20×10%=2 req/s; one assumed C=4/s canary is only a start. Full v2 plus full warm v1 rollback and two small-model replicas need 9+9+2=20 GPUs, versus 9+1+2=12 initially. Consider ramp after ≥5 min and ≥600 comparable samples; missing evidence freezes it. 发布事务：快照、幂等结果与审计一起提交Commit snapshot, idempotency result and audit together

下面的代码检查端点的上线组合、进程/设备代次和运行规格是否完整匹配，是否 READY 且未排空，以及 API 与持久状态结构（schema）是否兼容。多个发布者竞争同一个预期修订号 expected_revision，只有一个能成功；回滚同样发布更高的修订号，只是内容选回旧组合。示例实现的是这些元数据边界，没有计算生产环境的 SLO 或容量门槛，也没有验证真实预热。实际发布时，还要把已审核的质量、容量证据绑定到相应部署代次，不能把测试夹具中的 ready=1 当作实测结果。

The code checks exact endpoint bundle/epoch/profile, READY/non-draining state and API/persisted-state schema compatibility. Only one publisher wins expected_revision; rollback selects old content with a higher revision. The model implements these metadata boundaries, not production SLO/capacity gates or real warmup. Actual publication must bind approved quality/capacity evidence to matching generations; fixture ready=1 is not a measurement.

def publish(
    db, key, expected_rev, weights, endpoints, expires, actor,
    fail_before_audit=False
):
    payload = encoded({'weights': weights, 'endpoints': endpoints})
    fp = encoded([expected_rev, payload, expires, actor])

    with write_tx(db):
        old = db.execute('SELECT * FROM publication WHERE key=?', (key,)).fetchone()
        if old:
            if old['fingerprint'] != fp:
                raise Refused('publication key conflict')
            return old['rev']

        c = one(db, 'SELECT * FROM control WHERE id=1')
        if (
            c['rev'] != expected_rev
            or not weights
            or any(type(w) is not int or w <= 0 for w in weights.values())
        ):
            raise Refused('revision or weights')

        seen = set()
        for identity, epoch, bundle, profile in endpoints:
            r = one(db, 'SELECT * FROM replica WHERE id=?', (identity,))
            m = json.loads(one(
                db, 'SELECT manifest FROM bundle WHERE hash=?', (bundle,)
            )['manifest'])
            if (
                not r['ready']
                or r['draining']
                or bundle not in weights
                or (r['epoch'], r['bundle'], r['profile']) != (epoch, bundle, profile)
                or (m['api'], m['state']) != (c['api'], c['state_schema'])
            ):
                raise Refused('unready or incompatible bundle')
            seen.add(bundle)
        if seen != set(weights):
            raise Refused('missing endpoint')

        rev = expected_rev + 1
        db.execute('INSERT INTO snapshot VALUES(?,?,?)', (rev, payload, expires))
        db.execute('UPDATE control SET rev=? WHERE id=1 AND rev=?', (rev, expected_rev))
        db.execute('INSERT INTO publication VALUES(?,?,?)', (key, fp, rev))
        if fail_before_audit:
            raise RuntimeError('injected before audit')
        db.execute('INSERT INTO audit VALUES(?,?)', (rev, actor))
        return rev

错误率、TTFT、输出速度、拒绝量和质量，都要按上线组合、租户、请求长度桶和执行代次分别观察。失败灰度的 5% 错误率乘上 10% 请求比例，全局只有 0.5%，会通过 1% 的聚合门槛；两组 p95 也不能简单加权。回滚前要验证旧版本仍然健康、客户端契约兼容，且峰值与故障预算足够。如果新旧版本所在机房一起故障，改别名并不能恢复服务。

兼容性还包括已经写下的状态。如果新版写入的会话或检查点结构无法被旧版读取，切回旧权重也会导致状态读取失败。应先扩展字段、让读取方兼容新旧格式，并在整个热回滚窗口保留旧格式或双读适配；等旧请求和旧写入方都排空，且不再需要快速回退旧版后，才收缩结构、删除旧格式。这就是先扩展再收缩（expand/contract）。破坏兼容性的迁移，需要独立的版本命名空间，以及明确的转换或失败策略；本例直接拒绝 schema 不匹配，没有实现通用的 KV 或检查点迁移。

路由回滚只影响新准入，不会迁移正在生成的状态。账本为新预占和新派发检查最新 revision，因此旧路由缓存不能继续获得准入。已经获准的 DISPATCHING 仍可在原期限内被消费，RUNNING 则沿用原上线组合直到退休；坏版本的流可以明确终止，不能改接 v1 的后半段。A9 的签名和时钟范围由真实适配器校验，凭证也不能续期到原快照期限之后。权威库不可用或签名状态无法确认时，都停止新准入。通知只提示重新读取完整快照，乱序通知不能降低 revision。

30 分钟热回滚窗口结束后，先撤下旧路由，再原子阻止新派发、清理未派发的预占；等 RUNNING 和派发结果未知的请求都经过核查、物理退休后，才卸载。旧请求达到 60 s 时启动终止流程；如果仍未证实旧执行已被隔离，资源信用就继续保留。KServe Next 的相对权重 9:1 代表 90/10，它也提醒把零权重后端转为正权重前要考虑预热风险；其 force-stop promotion 会释放旧 GPU。[9]本章为热回滚额外保留旧容量，因此不能先释放旧 GPU，再声称还能热回滚。产物保留 7 天支持冷恢复；旧卡卸载后，恢复时间至少还要包含重新加载。

Slice errors, TTFT, output speed, rejection and quality by bundle/tenant/length/epoch. A 5%-failing canary at 10% request share yields only 0.5% aggregate, below a 1% global gate. Never linearly mix p95 values. Before rollback verify old health, client compatibility and peak/failure budgets; an alias cannot repair a shared facility outage.

Compatibility extends beyond weights.If v2 writes session/checkpoint schemas an old reader cannot understand, returning weights to v1 may break reads. Routing rollback does not migrate active generation state.Ledger checks the latest revision for new holds/dispatches; stale caches cannot mint permission. Already granted DISPATCHING may be consumed within its original deadline; RUNNING retains its bundle through retirement. Explicitly terminate bad streams rather than splicing v1 output. Real adapters validate A9 signatures/clock bounds and cannot extend a permit past the original snapshot. Unknown authority/signature fails closed. Notifications prompt full reads; out-of-order hints never lower revisions.

After thirty warm minutes, withdraw routes, atomically stop dispatch/expire undispatched holds, reconcile RUNNING/unknown dispatch to physical retirement, then unload. Sixty seconds triggers termination, while missing fence evidence retains credit. 复盘：用四个反例检查整套方案Review: four counterexamples explain the system

  • 两个路由器争最后一份 KV 信用：即使监控都显示空闲，也只有一个事务能同时扣减租户和副本信用；任何一步失败都完整回滚。
  • 命令发出后回复丢失：按稳定身份查询原状态；查询结果不会重新授予发送或启动权，结果未知也不能靠 TTL 归还信用。
  • 回滚前新版已写入状态：同时检查上线组合、API 与检查点兼容性；破坏旧格式会让热回滚失效。
  • 一台机器故障：先移除受影响的完整副本组，再重算 19.2/s 规划容量；替补未完成加载前不计入容量。

  • Two Routers race final KV credit:both see free metrics, but only one tenant+replica transaction wins; failure rolls back fully.
  • Lost command reply:query the stable identity; observation never regrants send/launch, and TTL does not refund UNKNOWN.

  • Lose one machine:remove affected whole groups, recompute 19.2/s planning capacity, and exclude loading replacements.
