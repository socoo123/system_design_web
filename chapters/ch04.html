设计限流器Design a rate limiter

这一章结束你能做什么What you can do after this chapter

把一条请求画成 Client → Gateway → Service，并在 Gateway 旁边接共享 Redis：先判定，再转发；正常、超限和依赖故障三条回程都讲清。

用连续补充的令牌桶完成一次手算；给出滑动计数不等于严格滚动窗口的反例；用两个并发请求解释为什么读、判、写必须原子完成。

从容量推导故障放行的上限，解释热点、超时重试、时钟回拨和异步复制分别会破坏什么保证。读完能在白板上讲一份有边界的方案。

Draw Client → Gateway → Service with shared Redis beside Gateway: decide before forwarding, and explain the success, quota-denial, and dependency-failure return paths.

Work a continuously refilled token bucket by hand, give a counterexample to strict rolling guarantees from a sliding counter, and use two concurrent requests to justify atomic read-test-write.

Derive a bounded fallback from capacity and identify what hot keys, timeout retries, clock rollback, and asynchronous replication can break. Leave with a design you can defend at a whiteboard.

先定合同，再写假设Set the contract, then the assumptions

我先确认限谁、限什么，以及超过后拒绝还是排队。这里做单地域的 HTTP API，按已认证用户和路由模板共享配额，允许短突发，用令牌桶。网关问 Redis 原子扣减，允许才转发，超额返回 429。Redis 不可用时，普通读在独立容量上限内降级；短信等敏感接口停止服务。若要求任意滚动一分钟都不能超额，我会换精确滑动日志，并重新估内存。

限流同时可能服务两个目标：用户之间公平，整层服务不被压垮。一个用户每分钟只能发一百次，不代表一百万个用户合起来不会把系统打满。先问清本题主要保护哪一个，再把另一个写成独立约束。套餐配额是产品合同；下游能承受多少是容量预算。它们可能共用执行位置，但不能用同一个数字代替。

继续澄清成本单位。读一个小对象与导出一百万行都算一次，会让昂贵接口绕过保护。主例用每次 cost=1，复杂任务可以按预估工作量收费，但最终用量未知时还需要预留、结算和幂等。这里先不扩成计费系统。也不把同步拒绝偷偷改成队列：进入队列意味着承诺延后执行，必须另定最大排队长度、截止时间和取消语义。

算法的精确性只能对着合同说。令牌桶可以精确执行自己的突发包络，却不是严格的滚动窗口配额；两个窗口加权是估计，不会因为存在 Redis 就变成精确。单地域、多网关、正常状态不丢失是第一版边界。全球配额、机房分区和切主期间的误差，留到故障部分说明，不能藏在“分布式”三个字里。

I will clarify the identity, cost unit, and whether excess requests are rejected or queued. This design is a single-region HTTP API with a shared quota per authenticated user and route template. Short bursts are allowed, so I use a token bucket. Gateway asks Redis to debit atomically and forwards only an allow; excess gets 429. During Redis failure, ordinary reads have a separate bounded capacity fallback, while sensitive APIs such as SMS stop. A strict rolling-minute contract would require an exact sliding log and a new memory estimate.

Rate limiting may pursue fairness and aggregate safety. One hundred requests per user per minute does not prevent a million users from overwhelming the service together. Identify the primary objective and state the other as a separate constraint. A plan quota is a product contract; downstream throughput is a capacity budget. They can share enforcement placement without sharing a number.

Clarify the cost unit. Counting a small read and a million-row export equally allows expensive work to bypass protection. The main example uses cost=1. Variable work can use estimated cost, but unknown final usage introduces reservations, settlement, and idempotency. That billing system is outside this chapter. Queuing is also a different promise: it needs queue length, deadlines, and cancellation semantics.

Accuracy is relative to a contract. A token bucket can enforce its burst envelope exactly without enforcing a strict rolling quota. Two weighted counters remain approximate in Redis. The initial boundary is one region, multiple gateways, and intact state in healthy operation. Global quotas, partitions, and failover errors need explicit treatment later.

容量先算到能决定下一笔Estimate enough to make the next decision

十进制估算：1,000,000×200 B=200 MB，一份主状态加一份副本约 400 MB。这里的 200 B 是带键名和对象开销的暂定预算，不能拿两个数值字段的字节数冒充实际占用；Redis 编码、键长度、过期索引和内存碎片都要用代表性数据测量。备份、连接、复制缓冲和进程空间还没算。结论是这组假设还没有用内存逼出分片，绝不是“内存可以忽略”。

峰值 10,000/s 且每请求检查一个桶，判定量是 10,000 次脚本/秒。若再独立查用户、租户两个桶，最坏可到 20,000 次/秒；若合并到同槽脚本，则仍是 10,000 次调用，但每次工作更多。正常 p99 2 ms 和截止 5 ms 都是设计目标，不是 Redis 的速度保证。压测要带真实键分布、脚本和故障流量；很多不同键可以分片，一颗热点键不能靠增加无关分片变快。

A6 的 6,000/s 是本章独立的容量教学预算，沿用 Ch03“按下游可承受量反推”的方法，不是复制它的用户规模。入口到达 10,000/s 与计划处理 6,000/s 之间有缺口，必须有总量和并发保护。用户桶只规定谁能争取资源；Service 还要在自己的容量边界拒绝过载，不能让大量合法用户把总体保护绕开。

In decimal units, 1,000,000×200 B=200 MB; primary state plus one replica is about 400 MB. The 200 B is a provisional allowance including key and object overhead, not the byte size of two numeric fields. Measure actual encoding, key length, expiry metadata, and fragmentation with representative data. Backups, connections, replication buffers, and process space are extra. Memory has not yet forced sharding under these assumptions; it is not negligible.

At 10,000 arrivals/s and one bucket check each, the store receives 10,000 script executions/s. Two separately checked user and tenant buckets can require 20,000/s. A same-slot combined script keeps 10,000 calls but performs more work per call. The 2 ms p99 and 5 ms deadline are targets, not Redis performance claims. Test real key distributions, scripts, and failure traffic. Many keys can be sharded; one hot key cannot be accelerated by unrelated shards.

The 6,000/s in A6 is this chapter’s independent capacity assumption. It reuses Ch03’s method, not its user population. A 10,000/s arrival rate against a 6,000/s processing plan needs aggregate and concurrency protection. User buckets determine eligibility; Service still rejects overload at its own capacity boundary so many legitimate users cannot bypass aggregate protection.

第一笔：网关先判定，再放行业务First stroke: decide at Gateway, then forward

正常路径与可信的配额键Healthy path and a trusted quota key

沿第三帧走一次：Client 带凭证请求 GET /items，Gateway 验证身份，归一化路由，得到类似 rl:{tenant42:user9}:items 的键；脚本返回 allow 后，Gateway 才调用 Service。Service 返回 200 到 Gateway，再到 Client。deny 则只回 Gateway，由它结束请求并返回 429。Redis 存的是额度状态，不是业务代理，不能画成业务请求穿过 Redis 才到服务。

鉴权前还可以按可信来源 IP 做粗保护，免得攻击者先耗尽验签资源；鉴权后才知道真正的用户与套餐。不能直接相信任意 X-Forwarded-For，也不能用客户端传来的 user_id 建桶。IP 是网络出口，校园或公司可能很多人共用一个地址，所以它适合粗防护，通常不适合独自承担用户公平性。路由用模板而不是带随机参数的原始 URL，否则攻击者每换参数就换一个新桶。

选择 Gateway 是为了复用入口、鉴权和规则发布能力，并不是“业务里有限流就错”。针对昂贵查询的并发限制、按实际工作量扣费，可能需要服务内的公共库或独立判定服务。业务实例无状态指权威数据不只留在实例内存；调用共享配额库并不破坏这条性质。客户端降速能减少无用请求，但它可被绕过，不能当唯一防线。

Walk frame 3: Client sends authenticated GET /items. Gateway verifies identity, normalizes the route, and builds a key such as rl:{tenant42:user9}:items. Only an allow from the script triggers a Service call. A 200 returns Service → Gateway → Client. A deny returns to Gateway, which ends processing with 429. Redis stores quota state; it is not a proxy for business traffic.

A coarse guard on a trusted source IP can protect authentication resources before identity is available. User and plan quotas follow authentication. Do not trust arbitrary X-Forwarded-For or client-supplied user_id. An IP may represent a school or office, making it a coarse protection signal rather than a fair user identity. Normalize route templates; random URL parameters must not create fresh buckets.

Gateway placement reuses ingress, authentication, and policy rollout. It does not make service-side limiting inherently wrong. Expensive-query concurrency controls or actual-work accounting may belong in a shared library or decision service. Stateless business instances can still call shared quota storage. Client throttling reduces wasted requests but is bypassable and cannot be the only enforcement.

规则更新不是每次请求再读配置中心Do not fetch policy configuration for every request

最后一帧新增的 Policy 是控制面：它把带版本的规则送到 Gateway 的本地快照，判定时携带版本与参数。配置中心短暂不可用时沿用最后一份有效配置，并监控版本年龄；没有任何有效配置的实例按接口风险决定能否接流量。若每次请求都同步问配置中心，限流器就多了一条没必要的可用性依赖。

规则变更会影响旧状态。B 从大变小时，已有 token 要钳到新 B；r 变化时，不能把上一版本积累的整个时间差都用新速率重算。可让桶保存策略版本，定义切换时刻与迁移方式。仅给 key 加一个新版本后缀虽然容易，却会初始化一个新满桶，发布时就多送一次突发。灰度期间两套规则并存，也要知道哪些请求按哪一份合同执行。

同一个用户可到任意 Gateway，因此第一版用共享状态解决跨实例一致性。粘滞路由只是在理想时把请求集中到一台，重启、滚动发布和故障转移仍会丢本地额度。分片路由可以是有效设计，但它要解决所有权迁移和状态交接；仅打开负载均衡的 sticky 选项并没有完成这些工作。

Policy in the last frame is a control plane. It supplies versioned rules to a local Gateway snapshot; decisions carry the version and parameters. Keep the last valid snapshot during a configuration outage and monitor its age. A new instance with no valid policy follows the endpoint’s risk policy. Synchronous policy fetches on every request add an unnecessary availability dependency.

Policy changes affect existing state. Lowering B clamps current tokens; changing r must not apply the new rate retroactively to the entire previous interval. Store a policy version and define transition time and migration. Adding a version suffix to the key creates a fresh full bucket and grants another burst at rollout. Mixed versions during canaries need an explicit contract.

A user can reach any Gateway, so shared state is the initial cross-instance solution. Sticky routing only concentrates requests while conditions remain ideal; restarts, deploys, and failover still lose local quota. Ownership-based sharding can work, but requires migration and state handoff. Enabling a load-balancer sticky option does not implement them.

第二笔：把令牌桶按时间算完Second stroke: work the token bucket through time

先补齐，再判断，再扣减Refill, test, then debit

令牌桶保存剩余额度 tokens 和上次更新时间 last。收到 cost 后计算 available=min(B, tokens+r×dt)；只有 available≥cost 才扣减，拒绝不扣。补充按时间差惰性计算，不需要给每个桶开一个定时任务。RFC 3290 附录 A 给出按速率 R 和突发 B 限制流量的模型；这里把报文字节替换成请求成本，示例数值由本章自定。[1]

从 t=0 满桶开始，t=10 到达三次请求。虽然过去十秒能产生 2/3 个 token，桶已满，所以补后仍是 4，扣三次剩 1。t=20 又来两次：先补 10/15，得到 5/3；放行第一次剩 2/3，第二次因为不足 1 被拒绝。t=25 再补 5/15，恰好得到 1，重试获准后剩 0。小数只是手算表示；实现可以用定点单位保留余量，避免每次截断让低速用户永远攒不够额度。

第二十秒被拒绝时，等待时间是 (cost−available)/r。此时 available=2/3，得到 (1−2/3)/(1/15)=5 秒。这个时间只是在没有别人抢额度、规则不变的情况下最早可能成功的时间，不能保留未来名额。多个客户端都等五秒后同时回来，仍会有人被拒，所以还需要抖动和有限重试。

A token bucket stores tokens and the last update time. Compute available=min(B,tokens+r×dt), then debit only if available≥cost. Denials do not debit. Lazy elapsed-time refill needs no timer per bucket. RFC 3290 Appendix A defines a rate R and burst B traffic model; this chapter substitutes request cost for packet bytes and supplies its own example values. [1]

Start full at t=0. At t=10, refill is capped at 4, and three requests leave 1. At t=20, another 10/15 produces 5/3. Admit one, retain 2/3, and deny the second. At t=25, 5/15 brings the balance to 1 and a retry leaves 0. Fractions are a teaching notation. Fixed-point units can preserve fractional credit; truncating every small refill can starve low-rate users.

For a denial, the earliest wait is (cost−available)/r. At t=20 this is (1−2/3)/(1/15)=5 seconds. It assumes unchanged policy and no competing consumer. It is not a reservation. Several clients returning together can still be denied, so use jitter and bounded retries.

B 和 r 分别解决什么What B and r control

r 控制长期持续速率，B 控制积攒后能马上花掉的额度。状态完整、时钟满足假设且没有重复初始化时，任意长度 T 的区间里获准成本不超过 B+rT。代入本例，60 秒是 4+(1/15)×60=8。它允许先用存量再用新补额度，所以“每分钟补四个”不能写成“任意一分钟最多四次”。B=1 只意味着不能积攒多次突发，并不自动变成带队列、恒速出站的漏桶。

从峰值反推桶深也要扣掉同时补进来的额度。若希望以 p 的速率持续 d 秒，而补充率是 r，且 p>r，至少需要 B≥(p−r)×d。把 B 简单写成峰值持续秒数乘 r，混淆了输入和补充的差额。反过来，B 再大也不会提高长期 r，却会让瞬时更多工作进入 Service；后者若只能同时处理有限任务，还要独立限制并发。

过期策略会改变算法本身。本例从空到满需要 B/r=60 秒，选择最后访问后 120 秒过期，正常空闲期结束后重建满桶不会早于自然补满。TTL 若只有十秒，攻击者等键消失就能重新领四个，持续绕过 r。TTL 用来回收长期不用的状态；不能把频繁驱逐当作普通缓存命中损失。权威额度被逐出就是额度重置，要隔离内存、监控驱逐，并定义写入失败如何处理。

r sets sustained rate and B sets accumulated immediate credit. With intact state, valid clock assumptions, and no duplicate initialization, admitted cost over any interval T is bounded by B+rT. Here 60 seconds gives 4+(1/15)×60=8. Existing credit plus refill means “four refilled per minute” is not “at most four in every minute.” B=1 restricts accumulation; it does not create a queued constant-output shaper.

Sizing a burst subtracts refill during the burst. To sustain arrival rate p for d seconds with refill r and p>r, require B≥(p−r)×d. Multiplying burst duration by r alone confuses incoming and replenished work. Larger B does not raise long-term r, but admits more instant work, so Service needs a separate concurrency bound.

Expiry changes the algorithm. Empty-to-full takes B/r=60 seconds; our 120-second idle TTL cannot recreate a full bucket before normal refill would. A ten-second TTL would let an attacker repeatedly obtain four fresh tokens. TTL reclaims idle state. Eviction of authoritative quota is a reset, not a harmless cache miss: isolate memory, monitor eviction, and define write-failure behavior.

第三笔：并发、时间和故障不是同一种保证Third stroke: concurrency, time, and failure guarantees

原子性只解决哪段竞态Which race atomicity actually solves

两台 Gateway 都读到剩余 1，各自在内存判断允许，再各写回 0。最后 Redis 的值依然是 0，看上去没有负数，却已经放行两个请求。单条 INCR 原子并不意味着整段读、判、写原子。图中 A 的 Lua 先完成 1→0，再回 allow；B 的 Lua 后执行，见到 0 就回 deny。这里假设两次之间没有补充，合计允许一次才是正确结果。

Redis 官方文档说明脚本执行期间不会被其他命令插入，因此读状态、按时间补充、判断和写回可以做成一个临界区；pipeline 只合并网络往返，不能代替这个临界区。[2] 脚本必须短而有界，不能扫描所有用户。这里保护的是一次判定的隔离性，不能把它扩写成“整个系统永不超额”。

面试写伪步骤就够：验证 B、r、cost 的合法性；读 tokens、last 与策略版本；取时间并补充；判断后保存新状态和安全 TTL；最后返回 allowed、remaining、retry_after。cost>B 的请求永远无法攒够，不能让客户端永远重试。所有可预先发现的参数或类型错误应在写之前检查；脚本错误不应被当成正常 deny。

Two Gateways can each read 1, decide locally, and write back 0. Redis ends at zero with no negative value, yet two requests were admitted. Atomic INCR alone does not make read-test-write atomic. In the diagram, A completes 1→0 before allow; B then sees zero and returns deny. Assuming no refill between them, one admission is correct.

Redis documents that other commands cannot interleave with a running script, so refill, test, and write fit inside one critical section. Pipelining reduces network round trips without providing that isolation. [2] Keep the script short and bounded; never scan all users. This protects one decision, not an unconditional system-wide no-overshoot claim.

Whiteboard steps suffice: validate B, r, and cost; read tokens, last, and policy version; sample time and refill; test and save state with a safe TTL; return allowed, remaining, and retry_after. cost>B can never accumulate enough credit and must not lead to endless retries. Detect predictable input and type errors before writes. A script error is not a normal quota denial.

用 Redis 时间，仍然要处理回拨Server time still needs rollback handling

Redis TIME 返回服务器 Unix 秒和当前秒内的微秒，它提供同一权威实例的时间来源，不承诺单调。[3] 若各网关自己上传 now，机器间偏差会让同一个桶被提前补充；换成服务器时间可以去掉这类跨客户端偏差，但操作系统调时和主从切换仍可能让时钟改变。

教学处理是 effective_now=max(redis_now,last)，再用 effective_now−last 算 dt，并把 last 更新到 effective_now。只把 dt 钳成 0、却把 last 写回更早时间，会在时钟追上时重复补充。向前大跳时 min(B,…) 最多补满，但仍可能提前送出一个 B 的突发；若合同不能接受，需要检测跳时、暂停补充或引入更强的时间与状态协议。

TTL 同样依赖实际时间推进，前跳可能让键过期重建，所以不能用回拨公式包装成绝对保证。部署时要监控时间偏差和切主事件。主例的 B+rT 包络是在状态保留、计时可靠的健康区间内成立；超出这个区间要报告额度重置风险，不能继续宣传严格的真实时间上限。

Redis TIME returns server Unix seconds and microseconds within the current second. It provides a common authority’s clock, not a monotonic guarantee. [3] Server time removes client-to-client skew from gateways supplying now, but OS clock changes and failover still matter.

A teaching guard is effective_now=max(redis_now,last). Compute dt from that value and save effective_now as last. Clamping only dt while writing an older last can refill twice when time catches up. A forward jump is capped by B but may grant a burst early. Stricter contracts need jump detection, paused refill, or a stronger time and state protocol.

TTL also follows time advancement; a forward jump can expire and recreate a key. The rollback formula is not an absolute guarantee. Monitor clock offsets and failover events. The main B+rT envelope holds in healthy periods with retained state and reliable time. Outside them, report reset risks rather than promising a strict real-time bound.

超时、复制和多个桶Timeouts, replication, and multiple buckets

判定超时不代表脚本没执行。可能已经扣了一次，allow 回复却在网络里丢失；网关立即重试会扣第二次，导致误拒。主例在结果未知时不重试配额扣减，也不盲目转发敏感请求。若要求同一次请求重试得到同一判定，可以用短期 request_id 去重记录，但它增加状态、有效期和同槽约束；请求身份还必须可信。配额幂等与业务写入幂等是两件事。

主库上的原子扣减不等于切主后不会丢。Redis 默认异步复制，已经返回的修改可能尚未到达副本。[4] 假设切主丢了两次扣减，恢复后就可能再放两次；损失量随尚未复制的状态而变。同步等待副本可以缩小窗口，但不能把普通主从描述成强一致账本。短信成本上限或支付额度若要求不可超发，要明确更强的持久一致性方案和不可用时拒绝的代价。

用户桶、租户桶同时约束一个请求时，必须说明扣减顺序。先扣用户再发现租户不足，会浪费用户额度；补偿退款又可能遇到并发和重试。要求一起成功或一起不扣，就把有关状态放到同一个原子操作可覆盖的位置。Redis Cluster 的多键操作受槽位限制，可用 hash tag 把相关键放到同槽，但全局租户键也可能因此成为热点。[5] 分别判定、容忍保守多扣是另一份合同，不能伪称跨分片原子。

A timeout does not mean the script did not run. A debit may commit while allow is lost; retrying immediately debits twice and can cause false denial. This design does not retry an unknown debit or blindly forward sensitive work. A short-lived request_id decision record can make retries return the same result, at the cost of state, retention, and slot constraints. Request identity must be trusted. Quota idempotency and business-write idempotency are distinct.

Atomic debit on the primary does not guarantee survival of failover. Redis replication is asynchronous by default, so acknowledged changes may not yet be on a replica. [4] If two debits are lost, two extra admissions may become possible. The amount depends on unreplicated state. Waiting for replica acknowledgements reduces a window without turning ordinary replication into a strongly consistent ledger. Hard SMS-spend or payment limits need stronger durability and consistency, with explicit refusal during failure.

If user and tenant buckets both apply, specify debit ordering. Debiting user first can waste credit if tenant then rejects; refunds introduce more races and retries. All-or-nothing debit needs state within one atomic operation’s scope. Redis Cluster constrains multi-key operations by slots; hash tags can colocate related keys but a global tenant key may become hot. [5] Independent checks with conservative overcharging are a different contract, not cross-shard atomicity.

第四笔：滑窗计数省了什么，又丢了什么Fourth stroke: what a sliding counter saves and loses

固定窗口的问题，不能靠改名解决A new name does not repair a fixed window

固定窗口按整分钟清零，L=7 时可以在第 59.9 秒放七次、第 60.1 秒再放七次：仅 0.2 秒内十四次，每个固定窗却都合法。这不是实现竞态，而是合同允许的边界突发。按自然日的免费次数可能就需要固定窗口，明确日界线和时区即可；若下游不能接这股尖峰，再加瞬时保护。算法不是按“高级程度”排序，而是按产品想限制什么选择。

加权滑动计数保留前一窗 P 和当前窗 C。当前窗过去比例 f 后，用 estimate=C+P×(1−f) 估计最近一个窗口的用量。Cloudflare 2017 年工程文章明确说明它假设前一采样期请求分布均匀；原文演算 42×0.75+18=49.5，是近似值。[6] 本章不借用其线上效果来保证自己的准确率。

判定新请求必须算上它自己。取 A8：P=5、C=3、f=0.3，已有估计为 3+5×0.7=6.5。cost=1 的新请求使结果变成 7.5，超过 L=7，应该拒绝。只比较 6.5≤7 就放行，是漏掉候选成本。若规则真的采用“当前值低于阈值就允许再加一次”的宽松语义，必须显式承认超一笔；这里使用不超过阈值的判定。

A fixed window resets on a minute boundary. With L=7, seven requests at 59.9 s and seven at 60.1 s produce fourteen in 0.2 s, while both fixed windows remain legal. This is a contract boundary, not a race. A daily free-use quota may intentionally use a fixed window with a stated timezone. Add instantaneous protection if downstream cannot absorb the burst. Algorithms match contracts rather than an abstract sophistication ranking.

A weighted counter retains previous count P and current count C. After fraction f of the current window, estimate=C+P×(1−f) approximates recent usage. Cloudflare’s 2017 article explicitly assumes uniform arrivals in the previous sampling period; its example is 42×0.75+18=49.5. [6] Its observed production results are not accuracy guarantees for this design.

Include the candidate cost. Under A8, P=5, C=3, f=0.3 gives existing estimated usage 3+5×0.7=6.5. A cost=1 candidate makes 7.5, exceeding L=7, so deny it. Comparing only 6.5≤7 omits the new request. A looser “below threshold before increment” contract must explicitly allow that overshoot; this chapter tests the candidate-inclusive total.

图中的反例：算式没错，也可能违反严格合同The diagram: correct arithmetic can still violate a strict contract

图中七次都发生在 t=59，t=90 时当前窗还没有其他请求。加权算法把上一窗折半，只算 7×0.5=3.5；候选加进去为 4.5，会允许。但真正的最近一分钟是 (30,90]，七次全在里面，新一次使总数为八。它没有算错加减乘除，错的是把均匀分布假设当成事实。反过来，若上一窗七次都在 t=10，真实窗口里已经没有它们，加权值却仍然保留 3.5，也可能保守误拒。

严格滚动上限可以用只记录获准请求的滑动日志。在同一个原子操作里，删除窗口外的记录，数剩余条目；少于 L 才添加本次唯一成员并允许，否则拒绝且不添加。以 (now−W,now] 为口径，刚好落在左边界的记录要删除；成员不能只用毫秒时间戳，否则同毫秒的两个请求可能互相覆盖。需要唯一请求标识或其他不会冲突的成员值。

只记获准请求时，单桶最多保留 L 条有效记录，并不是每一个被拒请求都必须占内存。代价仍然高于两个计数器：按 A2 的一百万活跃桶和本节 L=7，最坏七百万条有效记录，另有键和索引开销；精确内存要测。若合同统计所有尝试而非获准数，拒绝也要计入，那是另一个更容易受攻击流量影响的容量模型。

All seven diagrammed requests occur at t=59. At t=90, current count is zero. Weighting halves the previous seven to 3.5; with the candidate, 4.5 is allowed. The true interval (30,90] still contains all seven, so the candidate makes eight. Arithmetic is correct; uniform distribution is false. Conversely, seven requests at t=10 would have expired from the true interval while the estimate retains 3.5 and can cause conservative denials.

A strict rolling limit can keep a log of accepted requests only. Atomically remove expired entries, count what remains, and add a unique member only if count

Accepted-only logs retain at most L valid entries per bucket; rejected requests need not consume entries. This still costs more than two counters. A2’s million active buckets and L=7 imply up to seven million valid entries plus keys and indexes; measure actual memory. Counting every attempt, including rejection, is another contract with a capacity model more exposed to attack traffic.

第五笔：热点先挡住，故障也要有上界Fifth stroke: bound hot traffic and failure behavior

本地预检能省调用，但不能偷换权威Local prechecks reduce calls without replacing authority

健康状态下，本地粗限通过之后仍必须得到 Redis 的 allow，业务请求才会放行。因此本地预检本身不会增加相对权威桶的超发，只会多拒一些请求；它也不能修复 Redis 丢状态造成的额度重置。Envoy 文档明确介绍先本地粗限、再全局细限的两阶段方式，用来吸收会压垮共享限流服务的大突发。[8] 这与先领一批额度再本地消费的方案不同，后者需要证明总租出额度不超过权威余额。

预检不是免费公平。用户流量碰巧集中到某一台 Gateway，那里本地桶已空，其他三台还闲着，用户依然可能被拒。降低本地阈值能保护 Redis，但会增大这种保守拒绝；提高阈值会把更多压力送到共享桶。应分开观察 local_denied 与 quota_denied，再看热点键和路由分布，不能只拿总 429 比例调参。

按用户哈希分片可以拆开很多独立桶，但同一个租户的热点桶仍只属于一个分片。把它随意拆成十个互不协调的键，每键仍给原额度，等于总限额放大十倍。可选方案是本地粗限、把固定总额分给子桶，或批量预分配额度；后二者都要处理额度闲置、转移和重复领取。保留不超过总额的守恒关系，比给图多画几台 Redis 更关键。

In healthy operation, passing the local precheck still requires Redis allow before forwarding. The precheck cannot itself exceed the authoritative bucket; it can only add denials. It also cannot repair resets caused by lost Redis state. Envoy documents coarse local limiting followed by fine global limiting to absorb bursts that would overwhelm the shared service. [8] Leasing batches of credit for local use is different and needs a conservation proof.

Local prechecks trade fairness for protection. A user concentrated on one exhausted Gateway can be denied while three other gateways remain idle. Lower thresholds protect Redis but increase conservative denials; higher thresholds expose more shared load. Track local_denied and quota_denied separately alongside hot keys and routing distribution, instead of tuning from total 429 ratio.

Hashing by user separates independent buckets, not one hot tenant bucket. Splitting it into ten independent keys with the original quota multiplies the total limit by ten. Alternatives include coarse local filtering, fixed subdivisions of a total budget, or leased credit batches. The latter two need idle-credit, transfer, and duplicate-allocation handling. Preserve the total-credit invariant before drawing more Redis nodes.

读降级必须同时写下台数、速率和突发Read fallback needs instance count, rate, and burst

Redis 全部超时，直接让 10,000/s 绕过配额，会撞上 Service 的 6,000/s 容量预算。“读请求可以 fail-open”不是充足的答案。本章只对允许放宽用户配额的普通读启用有界降级：最多四个网关，每个独立应急桶 r=500/s、B=50。它们合起来长期 2,000/s，任意 T 秒内最多 4×50+4×500T=200+2,000T。

在一秒窗口上最多 2,200 次，小于计划 6,000 次；但零时刻仍可同时冲进 200 次，所以还要在 Service 限制在途请求，并通过压测验证队列和延迟能否承受。这个算式仅覆盖这四个入口、没有额外旁路的假设。实例扩到八台会把包络翻倍；故障期新实例和反复重启不能各自领一份全新应急桶，必须冻结成员、继承额度或从保守空桶启动。

有界降级保的是服务容量，不是某个用户的严格配额。Redis 超时也可能发生在扣减已经成功之后，本地再允许一次只是在产品可接受的故障合同内继续读，不能声称这次还有精确的 remaining。敏感接口在无法确认额度时停止，返回依赖不可用；不要把一个未知结果写成“确认超额”。

If all Redis checks time out, forwarding 10,000/s unconditionally exceeds Service’s 6,000/s plan. “Reads fail open” is incomplete. Only ordinary reads whose product contract permits relaxed user quotas enter bounded fallback: at most four Gateways, each with emergency r=500/s and B=50. Together they allow a sustained 2,000/s and at most 4×50+4×500T=200+2,000T over T seconds.

A one-second interval permits at most 2,200, below the 6,000 plan, but 200 can still arrive instantly. Limit in-flight Service work and load-test queueing and latency. The calculation covers exactly these four ingress instances without bypass traffic. Eight double the envelope. New or repeatedly restarted instances must not obtain fresh emergency buckets: freeze membership, inherit credit, or start conservatively empty.

Bounded fallback protects capacity, not strict per-user quota. Redis may already have debited before a timeout. Allowing a read locally is an explicit relaxed failure contract and cannot report an exact remaining value. Sensitive endpoints stop when quota cannot be checked. An unknown decision is not a confirmed over-quota result.

恢复与多地域：额度要守恒Recovery and multiple regions must conserve credit

故障恢复时，不让所有 Gateway 同一刻用请求洪峰探活。控制少量探测，观察判定延迟和错误率，再逐步恢复权威检查；应急档使用量单独标记，评估是否需要补偿或调整下一段额度。一次已扣减但未执行业务的请求，损失的是利用率；若为了追回它就无条件退款，又可能给已执行的请求重复额度。先定义可接受的误拒与超发方向，再选择补偿协议。

多地域默认各放一份完整额度，会把总合同乘上地域数量。若总预算是每分钟 100，可静态给两个地域分 60 和 40，合计仍是 100；这会浪费空闲地域的份额，却避免跨洋同步判定。动态借额度需要唯一所有者、有效期和转移过程中的守恒；如果任何地点都必须随时用满全球额度又绝不能超，就必须承担协调延迟，网络分区时也不能让两边无限继续放行。

限流与熔断最后分清：限流按允许的工作量拒绝；熔断根据依赖失败情况停止无效尝试；并发限制按正在执行的数量保护资源。一个十分钟任务即使每秒只接一个，也可能堆出很多在途工作。这三个控制可以协作，但图里每一条拒绝路径要有明确原因，不能把全部异常都归到“限流触发”。

During recovery, avoid every Gateway probing with full traffic at once. Permit a few probes, observe decision latency and error rates, and gradually restore authority checks. Label fallback consumption separately and decide whether reconciliation is necessary. A debit without business execution loses utilization; unconditional refunds risk duplicating credit for work already executed. Choose the acceptable error direction before defining compensation.

Giving every region the full quota multiplies the global contract. A total 100/minute can instead be split 60/40 across two regions, conserving 100 but stranding unused credit. Dynamic borrowing needs ownership, validity, and conservation during transfer. If every location must use all global capacity immediately without overshoot, coordination latency and refusal during partitions are unavoidable.

Rate limiting rejects excess work volume; circuit breaking suppresses calls to a failing dependency; concurrency limiting protects the number of in-flight operations. Even one new ten-minute task per second can accumulate considerable work. These controls cooperate but need distinct refusal reasons rather than classifying every failure as rate limiting.

响应合同：429、503 与客户端重试Response contract: 429, 503, and client retries

确认用户超出配额时返回 429 Too Many Requests，说明触发的规则，并给有意义的重试提示。RFC 6585 第 4 节定义 429，并允许携带 Retry-After；它没有要求限流器必须使用哪一种算法。[9] 本章 t=20 的例子返回 Retry-After: 5，因为离一个可消费 token 还差五秒。不要暴露其他用户、其他租户的余额。

Retry-After 可用非负整数秒或 HTTP 日期，具体语法来自 RFC 9110 第 10.2.3 节。[10] 用秒数能减少客户端对服务器时钟的依赖；不足一秒时向上取整，不能返回小数秒并期待所有 SDK 都理解。响应体可带稳定的错误码和请求标识，让客户端区分配额耗尽、策略拒绝和临时依赖错误。

Redis 不可用而停止敏感请求时，本设计用 503 Service Unavailable 表达服务暂时无法完成，而不是无证据地说用户已经超额。503 同样可以给重试提示。[10] 这属于本章对依赖故障的接口选择，具体网关可有不同错误映射，但监控与客户端合同必须一致。知道本地安全桶已耗尽时，也要表明是局部保护规则，而不是伪造权威用户余额。

客户端收到 Retry-After 后至少等待该时长，再加随机抖动；没有提示时使用带上限的指数退避。限制尝试次数与总体截止时间，避免每台 SDK 自动重试把十倍流量重新打回系统。业务写入能不能重试还取决于幂等语义，不能因为收到一个限流头就认为重复提交订单一定安全。

A confirmed user-quota violation returns 429 Too Many Requests with the relevant rule and a useful retry hint. RFC 6585 §4 defines 429 and permits Retry-After without prescribing an algorithm. [9] The t=20 example returns Retry-After: 5 because one usable token is five seconds away. Do not expose another user’s or tenant’s balance.

RFC 9110 §10.2.3 defines Retry-After as a nonnegative integer number of seconds or an HTTP date. [10] Seconds reduce dependence on client/server clock alignment. Round fractional seconds upward rather than expecting every SDK to parse decimals. A stable error code and request ID distinguish quota exhaustion, policy denial, and dependency failure.

This design uses 503 Service Unavailable when sensitive work stops because quota cannot be checked. It does not claim the user exceeded a known quota. A 503 may also carry a retry hint. [10] Gateways can map dependency errors differently, but monitoring and client contracts must agree. A known local safety-bucket exhaustion should identify that local rule without inventing an authoritative user balance.

Clients wait at least Retry-After and add jitter. Without a hint, use capped exponential backoff. Bound attempts and the overall deadline so automatic SDK retries do not amplify traffic tenfold. Retrying business writes also depends on idempotency; a rate-limit header does not make duplicate order submissions safe.

配额头要写明版本和语义Version quota headers and define their semantics

扩展配额头不是越多越好。旧客户端可能依赖 X-RateLimit-*，其中 Reset 的时间口径需要在本接口文档里定义。IETF 的 RateLimit-Policy 与 RateLimit 字段在这里仅引用可复核的 draft-ietf-httpapi-ratelimit-headers-10：发布于 2025-09-27，标注到期 2026-03-31，是一个固定版本的草案。[11] 本章不据此断言阅读时最新标准的状态，也不要求所有服务同时发两套头。

该版本以 q、w 表示配额策略，以 r、t 表示剩余与时间信息，但字段含义必须匹配算法。令牌桶并没有每分钟统一归零的时刻；本例的五秒是获得一个 token 的等待时间，不是整个桶重置。余额只是判定瞬间的快照，其他并发请求马上就可能把它花掉；故障降级时未知的权威余额应省略。协议选定版本后，用契约测试验证客户端理解，再考虑迁移兼容。

More quota headers are not automatically better. Legacy clients may depend on X-RateLimit-*; define Reset’s time convention in this API’s contract. This chapter references the inspectable draft-ietf-httpapi-ratelimit-headers-10 for RateLimit-Policy and RateLimit: published 2025-09-27 with expiry 2026-03-31. [11] It is a fixed draft revision, not a claim about the latest standard at reading time or a mandate to emit two header families.

That revision uses q and w for policy information and r and t for remaining/time information, but interpretation must match the algorithm. A token bucket has no universal minute reset. This example’s five seconds is time to one token, not a complete reset. Remaining credit is a snapshot that concurrent requests can immediately consume. Omit an unknown authoritative balance during fallback. Select a protocol revision and verify client semantics before migrating compatibility.

上线前追问：看什么，怎么验证Before launch: what to observe and verify

先做影子判定：计算 would_deny，但在已有安全保护下暂不按新规则拒绝，观察哪些用户、路由和套餐会被影响。不能把影子模式当成防护已经生效。逐步启用时同时看业务成功量、Service 在途数和尾延迟；429 变多可能是在有效拦截，也可能是错误键归一化把所有用户合成一个桶。只看 Redis CPU 很低，无法知道规则有没有错杀。

监控至少分出 allow、权威 deny、本地 deny、脚本错误、判定超时和故障放行；再看判定 p99、活跃桶数、驱逐次数、复制滞后、配置版本年龄与热点分布。指标标签用路由模板和套餐层级，不能把每个 user_id 都做成时序标签。必要的请求采样可以用于追查，但样本不应泄露凭证，也不能把大量被拒请求的日志写入变成新的瓶颈。

验证用能推翻方案的小场景：只剩一个 token 时并发两个请求；连续小时间差补充；恰好到达窗口左边界；两个请求同毫秒；时钟回拨；扣减成功但回复丢失；切主丢失已确认状态；TTL 过早过期；配置降额；故障期增加网关实例。每个场景先写预期 allow 数和错误类型，再运行实现。平均吞吐达标不能替代这些合同测试。

Start with shadow decisions that compute would_deny without enforcing the new policy, under existing safety protection. Observe affected users, routes, and plans; shadow mode is not enforcement. During rollout, watch business completions, in-flight Service work, and tail latency. More 429s can mean effective protection or a broken key that combines all users. Low Redis CPU does not prove fairness.

Separate allow, authoritative deny, local deny, script errors, decision timeouts, and fallback admissions. Monitor decision p99, active buckets, eviction, replication lag, policy age, and hot-key distribution. Use bounded route-template and plan labels, not a timeseries per user_id. Request samples can assist investigation without exposing credentials or turning rejection logging into a bottleneck.

Use small falsifying scenarios: two concurrent requests for one token; repeated tiny refills; exact left-window boundary; same-millisecond arrivals; rollback; committed debit with a lost reply; lost acknowledged state on failover; premature TTL; quota reduction; and extra Gateways during fallback. State expected admissions and error types before running an implementation. Average throughput cannot replace contract tests.

收尾：用一分钟把完整图讲回去Close: explain the complete design in one minute

入口峰值一万次，先鉴权、归一化路由，再查共享额度。默认允许突发，选 B、r 令牌桶；每次补充、判断、扣减在 Redis 一次原子执行，允许才进业务，200 逐跳回网关和客户端，拒绝在网关返回 429。严格滚动配额改用保存获准时间的日志，不拿两个加权计数冒充精确。热点先本地粗限，正常仍问权威。Redis 故障时，普通读最多四台、每台 500/s 和 50 突发，敏感请求返回 503；时钟、驱逐、复制和超时都各有边界。

追问“如果用户公平与容量保护冲突”时，说清先保整体容量，再讨论套餐优先级与局部拒绝；不能保证所有用户随时拿满额度。追问“能否强制全球精确”时，说清协调与可用性的成本。追问“哪个数要压测”时，指出每桶内存、脚本吞吐、判定 p99 和 Service 的突发承受力，别把教学假设当成采购依据。

下一章 Ch05 会继续解决键到机器的映射。本章先记住：增加分片能分散不同桶，不能自动拆开一个权威热点桶。容量方法回看 Ch03；把限流放进完整业务请求，可对照 Ch09。延伸到 M6 时，Ch39 对应入口与无状态，Ch42 对应弹性、熔断和背压；这些章节待上线后再展开。

At ten thousand arrivals/s, authenticate, normalize the route, then check shared quota. Short bursts use a B,r token bucket. Redis atomically refills, tests, and debits; only allow reaches business work. A 200 returns through Gateway to Client, while Gateway sends 429 for a denial. A strict rolling quota needs accepted-arrival logs, not two weighted counters presented as exact. Local coarse limiting protects hot traffic while healthy requests still ask authority. On Redis failure, reads use at most four Gateways with 500/s and burst 50 each; sensitive APIs return 503. Clocks, eviction, replication, and timeouts each have explicit limits.

If fairness conflicts with capacity, protect aggregate capacity first, then discuss plan priority and local rejection; not every user can receive their full quota at all times. Global exactness costs coordination and availability. Measurements still needed are per-bucket memory, script throughput, decision p99, and Service burst tolerance. Teaching assumptions are not procurement data.

Ch05 will cover key-to-machine mapping. More shards distribute independent buckets; they do not automatically split one authoritative hot bucket. Revisit Ch03 for estimation and Ch09 for a complete business request. Future M6 follow-ups are Ch39 for ingress and statelessness, and Ch42 for elasticity, circuit breaking, and backpressure.
