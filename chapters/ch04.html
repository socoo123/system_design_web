设计限流器Design a rate limiter

约 30 分钟 · 前置：Ch01–Ch03 · 从配额合同到原子判定与故障边界~30 min · after Ch01–Ch03 · from quota policy to atomic decisions and failure limits

本章核心：规则、判定、失败三件事Core: policy, decision, and failure

限流器把请求分成允许、确认超额、无法判定。本例用 GET /items 串起三项决定：按谁共享额度？怎样原子补充与扣减？权威不可用后还承诺什么？

A limiter distinguishes allow, confirmed quota denial, and an unavailable decision. Follow GET /items through three choices: who shares credit, how refill and debit become atomic, and what remains guaranteed when authority fails.

主线是 Gateway 鉴权 → Redis 判定 → Service 执行。允许突发选令牌桶；严格滚动窗口换滑动日志。保留的五组动画分别展示请求路径、余额变化、并发顺序、窗口反例和故障预算。

The main path is Gateway authentication → Redis decision → Service execution. Use a token bucket for bursts or an accepted-request log for a strict rolling window. Five retained decks show the request path, balance changes, serialization, a window counterexample, and fallback budgets.

需求与边界：用户公平不等于全层容量Contract: per-user fairness is not aggregate capacity

设计单地域 HTTP API，按已认证用户 × 路由模板共享配额，主例每次成本 cost=1，超额立即拒绝。昂贵导出可以按工作量收费；队列、最终用量结算和业务幂等是额外合同，本章不把它们隐含在“限流”里。

Design a single-region HTTP API with shared credit per authenticated user × route template. The main example charges cost=1 and rejects excess immediately. Expensive exports may charge by work; queueing, final-usage settlement, and business idempotency require additional contracts.

教学入口峰值 10,000/s，Service 计划处理 6,000/s，部署四台 Gateway。一个用户守规矩不代表所有用户合起来不过载，因此同时保留 Service 的总量与在途并发保护。令牌桶手算使用 B=4、r=1/15 token/s；这些都是设计假设，未做压测。

Teaching assumptions: 10,000 arrivals/s, a 6,000/s Service plan, and four Gateways. Individually compliant users can still overload the service, so retain aggregate admission and in-flight concurrency controls. The worked bucket uses B=4 and r=1/15 token/s. These values are assumptions, not load-test results.

In decimal units, 1,000,000×200 B=200 MB, or about 400 MB with one replica. The per-bucket allowance is provisional; measure encoding, fragmentation, expiry metadata, process space, and replication buffers. The 2 ms p99 and 5 ms deadline are targets to validate. Memory has not yet forced sharding under these assumptions; hot keys and tail latency may constrain the design first. Test the actual key distribution and script.

配额键与规则快照Quota keys and policy snapshots

Gateway 验证身份并归一化路由，构造 rl:{tenant42:user9}:items；只有 allow 才进入 Service，200 沿 Service → Gateway → Client 返回。鉴权前可以用可信来源 IP 粗保护；鉴权后按用户公平。不能信任任意 X-Forwarded-For、客户端 user_id 或带随机参数的原始 URL。

Gateway authenticates and normalizes the route to build rl:{tenant42:user9}:items. Only allow reaches Service; 200 returns Service → Gateway → Client. Before authentication, a trusted source IP can provide coarse protection; afterward use user identity for fairness. Do not trust arbitrary X-Forwarded-For, client-supplied user IDs, or raw URLs with random parameters.

Policy 向 Gateway 推送带版本的本地快照；配置短暂不可用时沿用最后有效版本并监控年龄，不为每次请求再加一次同步依赖。本节选择网关复用入口能力；按真实工作量或并发数限流也可能位于服务内。客户端降速可被绕过，不能独自执法。

Policy supplies versioned local snapshots to Gateway. During a short configuration outage, retain the last valid version and monitor its age instead of adding a synchronous dependency to each request. Gateway reuses ingress infrastructure; work-based or concurrency limits may belong inside a service. Client throttling is bypassable and cannot enforce the contract alone.

规则更新与多桶扣减Policy changes and multi-bucket debit

下面代码固定规则 v1；版本不符返回错误，不能自动新建满桶。降 B 要钳余额，变 r 要明确切换时刻，不能用新速率重算全部旧时间。直接换版本 key 会额外送一桶突发。粘滞路由也不能解决重启或迁移丢额度。

The code below fixes policy v1 and rejects version mismatches instead of creating a new full bucket. Lower B clamps credit; changing r requires a transition time rather than applying the new rate retroactively. A versioned key alone grants another full burst. Sticky routing does not preserve credit through restarts or ownership migration.

用户桶和租户桶若要求一起扣或一起不扣，读判写必须在一个可覆盖两者的操作内。Redis Cluster 可用 hash tag 同槽，但可能集中热点；跨槽分别扣减会保守多扣，退款又需要并发与重试协议。[5]

All-or-nothing user and tenant debit must share one operation covering both states. Redis Cluster hash tags can colocate keys but may concentrate hot traffic. Separate cross-slot debits can conservatively overcharge; refunds need their own concurrency and retry protocol. [5]

机制一：先补充，再判断和扣减Mechanism 1: refill, test, and debit

r 限长期速率，B 限积攒突发。 健康计时、状态保留且没有重复初始化时，任意长度 T 的区间获准成本不超过 B+rT。本例一分钟上界是4+4=8，不是严格“任意一分钟四次”。[1]

r bounds sustained rate; B bounds accumulated burst credit. With reliable time, retained state, and no repeated initialization, admitted cost over interval T is bounded by B+rT. Here the one-minute bound is 4+4=8, not a strict four requests in every rolling minute. [1]

对应图2–4帧：available=min(B,tokens+r×dt)，足够才扣 cost。t=10 三次后剩1；t=20补到5/3，允许一次后剩2/3，第二次拒绝；t=25补到1再扣到0。下一节把这条状态转移放进 Redis 的一次执行，防止两个网关同时花同一个 token。

Frames 2–4 use available=min(B,tokens+r×dt) and debit cost only when sufficient. At t=10 three admissions leave 1. At t=20 refill yields 5/3; one admission leaves 2/3 and the next is denied. At t=25 refill reaches 1 and debit leaves 0. The next section places this transition inside one Redis execution so two gateways cannot spend the same token.

拒绝时最早等待 (cost−available)/r：此处为5秒。它不预留未来额度，其他请求可能先消费，所以客户端还需抖动和有限重试。补充按时间差惰性计算，不必为每个桶创建定时任务；小数余量不能每次截掉。

The earliest wait after denial is (cost−available)/r, here five seconds. It reserves no future credit; competitors may consume it first, so clients need jitter and bounded retries. Refill is lazy elapsed-time arithmetic, not a timer per bucket. Preserve fractional credit between decisions.

桶深、TTL与容量的关系Burst size, TTL, and capacity

要支持输入速率 p 持续 d 秒、且 p>r，至少需要 B≥(p−r)d；更大 B 不提高长期 r，却增加瞬时在途工作。本例从空到满需 B/r=60秒，正常时钟下最后访问后120秒过期可安全重建满桶；回拨时另加欠时（见下方代码），且不允许早驱逐。TTL=10秒会让用户等键消失反复领四个。权威额度被驱逐就是重置，必须隔离内存并处理写入失败。

Sustaining input rate p for d seconds with p>r requires B≥(p−r)d. Larger B increases immediate work, not sustained r. Empty-to-full takes B/r=60 seconds, so a 120-second idle TTL can safely recreate a full bucket under healthy clocks and no early eviction. A ten-second TTL grants repeated fresh bursts. Evicting authoritative credit is a reset: isolate memory and handle write errors.

关键实现：一次判定的原子边界Key implementation: one decision’s atomic boundary

同一桶的一次读、补、判、写必须串行。 图中A先把1扣到0，B随后只能拒绝；若A、B都先读1再写0，最终余额虽不负，业务却放行两次。单条INCR或pipeline都没有自动覆盖整段判断。[2]

Serialize the read, refill, test, and write for one bucket. A first debits 1 to 0, then B must deny. If both read 1 before either writes 0, the final balance is nonnegative but two requests pass. Neither a standalone INCR nor pipelining automatically covers the whole decision. [2]

把图里的 EVAL 展开Expand the EVAL in the diagram

下面是可执行的 Redis 7+ Lua 教学示例，固定规则 v1，不是完整生产限流服务。输入可信键与整数 cost（1–4），返回 [allowed, remaining_credit, wait_ms]。一个 token=15,000 份，每毫秒补 1 份；t=20 剩 10,000 份，精确保留 2/3 token。输出 token 数除以 15,000，HTTP 等待秒数取 ceil(wait_ms/1000)。实现以毫秒计时，包络按计量时钟解释；与连续真实时间比较，边界有不足 1 ms 补充量的量化误差。

This is an executable Redis 7+ Lua teaching example with fixed policy v1, not a complete production limiter. A trusted key and integer cost (1–4) produce [allowed, remaining_credit, wait_ms]. One token is 15,000 credits; each millisecond adds one. At t=20, 10,000 credits preserve 2/3 token exactly. Divide remaining credits by 15,000 and round wait_ms/1000 upward for HTTP seconds. The envelope uses the metered millisecond clock; compared with continuous real time, boundary quantization contributes less than 1 ms of refill.

-- Redis 7+ teaching example; KEYS[1]: trusted quota key, ARGV[1]: cost.
-- Policy v1: B=4; 15000 credits/token; refill=1 credit/ms.
local function integer(x, lo, hi)
  return type(x) == 'number' and x >= lo and x <= hi and x == math.floor(x)
end
local cost = tonumber(ARGV[1])
if #KEYS ~= 1 or not integer(cost, 1, 4) then
  return redis.error_reply('INVALID_COST_OR_KEY')
end
local time = redis.call('TIME')
local now = tonumber(time[1]) * 1000 + math.floor(tonumber(time[2]) / 1000)
local raw = redis.call('GET', KEYS[1])
local state = {v=1, credit=60000, last=now}
if raw then state = cjson.decode(raw) end
-- The timestamp bound also keeps JSON encoding exact for this example.
if not integer(now, 0, 9000000000000) or type(state) ~= 'table'
   or state.v ~= 1 or not integer(state.credit, 0, 60000)
   or not integer(state.last, 0, 9000000000000) then
  return redis.error_reply('INVALID_STATE_OR_CLOCK')
end
local effective = math.max(now, state.last)
local elapsed = math.min(60000, effective - state.last)
local available = math.min(60000, state.credit + elapsed)
local needed = cost * 15000
local allowed = available >= needed
local remaining = allowed and (available - needed) or available
local lag = effective - now
local wait_ms = allowed and 0 or (lag + needed - available)
local payload = cjson.encode({v=1, credit=remaining, last=effective})
-- The only write commits both state and expiry; errors return no allow.
redis.call('SET', KEYS[1], payload, 'PX', 120000 + lag)
return {allowed and 1 or 0, remaining, wait_ms}

源码：token-bucket.lua，页面与文件逐字比对；运行与验证方式。整数时间上限是这个示例的数值约束，不是 Redis 时间范围；异常 JSON、错误键类型或策略版本均报错，不能当成余额不足。

Source: token-bucket.lua, checked byte-for-byte against this block; see execution and validation. The timestamp bound is this example’s numeric constraint, not Redis’s time range. Malformed JSON, wrong key types, and policy mismatches are errors, not quota denials.

由 Redis 主节点执行整段 EVAL，不是 Gateway 先GET再把结果传给脚本；脚本期间其他命令不能插入。GET与唯一SET访问同一个 key，SET PX同时写状态与TTL（回拨时加上尚未追平的时差）；所有可预见校验、序列化先完成，SET报错则不给allow。脚本短而有界，不扫描其他用户。Redis脚本不是带自动回滚的数据库事务；多次写后再报错不能假定前面的写已撤销。

The owning Redis primary executes the entire EVAL; Gateway must not GET first and pass stale state into it. Other commands cannot interleave with the script. GET and the sole SET use one key; SET PX writes state and TTL together, adding the clock catch-up gap after rollback. Validate and serialize before writing; a failed SET produces no allow. Work stays bounded without scanning users. Redis scripts are not database transactions with automatic rollback; an error after earlier writes does not imply those writes were undone.

本地单机版可以用每桶互斥锁覆盖同一状态转移，并用单调时钟；它只约束一个进程。四台各初始化B=4会送出16个突发，不能称为共享B=4。分布式版必须让同一键的所有请求到同一权威并执行上述临界区。

A single-process version can protect the same transition with a per-bucket mutex and use a monotonic clock. It covers only that process. Four independently initialized B=4 buckets grant a burst of 16, not one shared burst of 4. Distributed enforcement routes the same key to one authority executing this critical section.

正常轨迹与反例Normal trace and counterexamples

图中并发：初态15,000份、无补充，A扣到0且allow，B见0且deny。回拨：last=20,000ms而now=19,000ms，effective仍是20,000，既不补也不倒退last；回到20,000仍不补。若last比now未来100秒，空桶需先追平100秒再补满60秒；TTL延到220秒，拒绝等待也加上100秒，不能固定120秒提前重建满桶。若只钳dt却把last写成19,000，就凭空多补1,000份。cost=5直接报参数错误，永远不返回“稍后重试”。

For the diagram’s race, start with 15,000 credits and no refill: A allows and leaves zero; B sees zero and denies. For rollback, last=20,000ms and now=19,000ms keeps effective at 20,000: neither refill nor timestamp moves backward. Returning to 20,000 adds nothing. If last is 100 seconds ahead, an empty bucket needs 100 seconds to catch up and 60 to fill: extend TTL to 220 seconds and denial wait by 100 seconds, avoiding premature full recreation at 120 seconds. Clamping dt but writing last=19,000 would invent 1,000 credits. cost=5 fails validation instead of asking for an impossible retry.

隔离、时钟、持久性分别承诺Isolation, time, and durability are separate promises

Redis TIME 是服务器墙钟，不承诺单调；max(now,last)仅处理回拨。向前跳会提前补满或让TTL到期，切主也可能换时钟，所以B+rT只在计时与状态前提成立时成立。更严格的真实时间合同要检测跳时、暂停补充或改用更强协议。TTL 也按墙钟到期。[3] [11]

Redis TIME is a server wall clock without a monotonic guarantee. max(now,last) handles rollback only. Forward jumps can refill early or expire the key, and failover can change clocks; B+rT depends on the stated time and state assumptions. A stricter real-time contract needs jump detection, paused refill, or a stronger protocol. Expiry also follows wall time. [3] [11]

超时可能发生在SET成功、回复丢失之后。本例不自动重试未知扣减，也不退款：重试可能扣两次，盲目退款可能复活已使用额度。需要判定幂等时，把可信request_id的结果记录与桶状态放在同一原子范围并规定保留期；它仍不代替业务幂等。

A timeout can follow a successful SET with a lost reply. This design does not automatically retry an unknown debit or refund it: retry can debit twice, while blind refund can recreate spent credit. Idempotent decisions require trusted request IDs and retained results in the same atomic scope as the bucket; this still does not provide business idempotency.

异步复制可能丢掉已确认扣减，切主后重新放出额度；假设丢两次扣减，就可能多放两次。WAIT可减小风险，但不能把普通Redis主从变成强一致账本。硬成本上限需要更强的持久一致性与故障拒绝。Ch01引用的严格回源gate是依赖合同，不能仅凭这段Redis示意宣称已实现其切主保证。[4]

Asynchronous replication can lose acknowledged debits and restore credit after failover; losing two debits can permit two extra admissions. WAIT reduces risk without making ordinary Redis replication a strongly consistent ledger. Hard cost ceilings require stronger durability, consistency, and refusal during failure. Ch01’s strict origin gate is a dependency contract; this Redis sketch alone does not implement its failover guarantee. [4]

机制二：严格滚动窗口需要保存时间分布Mechanism 2: strict rolling limits retain arrival times

两个加权计数是近似，不能保证任意一分钟最多L次。 图中L=7、W=60秒，七次都在t=59；t=90的新请求会暴露被压缩掉的时间分布。

Two weighted counters are approximate, not an at-most-L guarantee over every rolling minute. With L=7 and W=60 seconds, all seven requests occur at t=59. The t=90 candidate exposes the missing arrival distribution.

Use C+P×(1−f)+cost. The diagram estimates 0+7×0.5+1=4.5≤7 and allows, although the real interval (30,90] contains 7+1=8 and must deny. Separately, P=5, C=3, f=0.3 gives 6.5 before the candidate and 7.5>7 afterward: deny. Cloudflare explicitly assumes a constant previous-period rate; observed accuracy is not a guarantee. [6]

精确日志的最小状态转移Minimal exact-log transition

# Teaching pseudocode: one authoritative serialized operation
# Contract: accepted requests in (now - W, now], cost = 1
checkRolling(key, now, uniqueAttempt):
    remove entries with timestamp <= now - W
    if count(entries) >= L:
        return DENY                    # rejected attempts are not logged
    insert (timestamp=now, member=uniqueAttempt)
    return ALLOW                       # only after the insertion succeeds

这是算法伪代码；Redis实现可在同一个EVAL里用有序集合依次删除、计数、添加。整个序列串行才有意义，不能拆成客户端三次调用；脚本错误按依赖失败处理，不假定自动回滚。uniqueAttempt必须是本次尝试的唯一成员，同毫秒的不同请求不能用时间戳互相覆盖；请求重试去重需要另行设计。本例按获准数计，只保存获准请求，最多L条有效记录。百万桶、L=7时最多七百万条，另加索引和键开销。

This is algorithm pseudocode. A Redis implementation can remove, count, and insert sorted-set entries inside one EVAL. The whole sequence must serialize; three client calls do not suffice. Treat script errors as dependency failures without assuming automatic rollback. uniqueAttempt must uniquely identify this attempt, so simultaneous requests cannot overwrite a shared timestamp member. Retry deduplication is separate. Counting admissions retains at most L valid entries: a million buckets at L=7 need up to seven million entries plus key and index overhead.

窗口口径是 (now−W,now]，恰好在左边界的记录删除。其“精确”仍以前后一致的权威时间、状态不丢和原子判定为前提；时间跳变与切主问题不会因换成日志消失。

The interval is (now−W,now]; remove entries exactly at the left boundary. Exactness still assumes consistent authoritative time, retained state, and atomic decisions. Logs do not eliminate clock jumps or failover loss.

故障路径：超额与无法判定分开Failure path: separate denial from an unknown decision

正常时本地粗限之后仍查共享权威；故障时才切换明确的降级合同。 普通读可牺牲用户配额精度保护容量，短信等敏感操作停止服务。[8]

Healthy requests still check shared authority after a local coarse guard; only failures enter the explicit fallback contract. Ordinary reads may relax per-user accuracy while protecting capacity. Sensitive operations such as SMS stop. [8]

把三条返回路径写出来Write the three return paths

# Teaching pseudocode: every admitted request still faces Service capacity
handle(request):
    identity = authenticate(request)
    key = quotaKey(identity, normalizedRoute(request))
    if not localPrecheck.tryConsume():
        return 429(code="local_protection")
    result = quota.checkOnce(key, cost=1, deadline=5ms)
    if result is DENY:
        return 429(code="quota_exceeded", retryAfter=result.wait)
    if result is ALLOW:
        return Service.callOnceWithinCapacity(request)
    # Timeout, script error, or unavailable authority: never invent a denial.
    if request is not an eligible ordinary read:
        return 503(code="quota_unavailable")
    if not emergencyBucket.tryConsume():
        return 503(code="fallback_capacity_exhausted")
    return Service.callOnceWithinCapacity(request)

quota.checkOnce调用前文完整EVAL，明确禁止客户端/代理自动重试未知扣减。localPrecheck和emergencyBucket各在单进程用锁保护完整补判扣，前者只减少权威调用，后者只在eligible读的故障分支消费；不能共用或拿预检成功冒充共享allow。Service仍独立控制总量和并发，获准不保证最终200，也不因业务失败自动退额度。

quota.checkOnce invokes the complete EVAL above, with client/proxy retries of unknown debits disabled. localPrecheck and emergencyBucket each lock the full transition inside one process. The first reduces authority calls; the second is consumed only by eligible fallback reads. They are distinct buckets, and passing a precheck is not shared allow. Service independently bounds aggregate work and concurrency; admission guarantees neither 200 nor an automatic refund after failure.

429表示已确认触发某条限流规则，RFC 6585允许Retry-After；本例t=20返回5秒，按RFC 9110使用整数秒（不足一秒向上取整）或HTTP日期。无法检查敏感请求时本设计返回503。降级容量用尽也返回503并标记原因，不能伪造用户余额。[9] [10]

429 means a known rule denied admission; RFC 6585 permits Retry-After. At t=20 return five seconds, using RFC 9110 integer seconds rounded upward or an HTTP date. This design returns 503 when sensitive requests cannot be checked and when fallback capacity is exhausted, with distinct reasons and no invented user balance. [9] [10]

四台应急桶的预算怎么来Derive the four-bucket fallback budget

最多四台Gateway，每台应急桶r=500/s、B=50，所以任意T秒的降级获准量≤200+2,000T。一秒上界2,200，小于6,000/s教学预算；但瞬时仍有200，且部分正常流量可能同时继续，因此Service总量/并发保护始终生效。这个式子只约束应急流量，不能保证整个系统成功吞吐或p99。

At most four Gateways each have emergency r=500/s and B=50, so fallback admissions over T seconds ≤200+2,000T. The one-second bound is 2,200 against a 6,000/s teaching budget, but 200 may arrive instantly and some normal traffic may continue. Service aggregate and concurrency controls remain active. The formula bounds fallback traffic only, not system-wide successful throughput or p99.

故障期扩到八台会翻倍；反复重启满桶也会重复赠送突发。冻结成员或安全继承额度；替换实例从空桶启动仍须禁止新旧所有者同时消费。恢复用少量探测逐步回权威，不能每次短暂抖动都重新初始化满应急桶。客户端至少等Retry-After并加抖动，限制次数与总截止；写操作能否重试还取决于业务幂等。

Eight Gateways double the envelope; repeated restarts with full buckets duplicate bursts. Freeze membership or safely transfer credit. Empty replacement buckets still require preventing concurrent consumption by old and new owners. Recover through limited probes and retain emergency state across flapping. Clients wait at least Retry-After plus jitter and bound attempts and deadlines. Business-write retries require business idempotency.

热点与全球额度Hot keys and global quotas

正常本地预检只增加保守拒绝，不会额外放行；流量集中到一台时，其他网关闲着也可能拒绝。哈希分片拆开不同桶，不能拆开一个权威热点桶。把总额度固定分给子桶或预租批次可以分散压力，但必须证明领取、转移和过期过程中额度守恒。

Healthy local prechecks add conservative denials, never extra admissions. A busy Gateway can deny while others sit idle. Hash sharding spreads different buckets, not one authoritative hot bucket. Fixed subdivisions or leased batches spread work only if allocation, transfer, and expiry preserve total credit.

全球固定分钟额度100可按同一窗口拆60/40，代价是空闲份额浪费；若采用令牌桶，则B与r都必须分摊，不能只写“每分钟100”。动态借用需唯一所有者与转移协议；跨地域严格共享不能同时免协调延迟、免分区拒绝。

A fixed global minute quota of 100 can split 60/40 over the same window at the cost of stranded credit. For token buckets, partition both B and r, not an ambiguous “100 per minute.” Dynamic borrowing needs unique ownership and a transfer protocol; strict global sharing cannot avoid both coordination latency and refusal during partitions.

Use shadow decisions under existing protection before gradually enforcing. Separate allow, quota_denied, local_denied, timeout, script_error, fallback_allow, and fallback_exhausted. Track decision p99, in-flight work, eviction, replication lag, and policy age. Use bounded route/plan labels rather than one series per user ID. Neither low CPU nor many 429s proves correctness.

一分钟口述：按认证用户和路由建共享桶，B管突发、r管长期；一个EVAL串行补判扣，allow才进Service，超额429，未知按风险503或有界读降级。严格滚动合同改用获准日志；时钟、TTL、复制、重试和成员变化各有前提。限流管工作量，熔断管失败依赖，并发限制管在途数。

One-minute explanation: share a bucket per authenticated user and route. B governs bursts and r sustained rate. One EVAL serializes refill, test, and debit. Allow reaches Service, confirmed denial returns 429, and unknown decisions trigger risk-based 503 or bounded read fallback. Strict rolling limits use accepted-request logs. Clocks, TTL, replication, retries, and membership each have explicit assumptions. Rate limits bound work, circuit breakers suppress failing dependencies, and concurrency limits bound in-flight operations.
