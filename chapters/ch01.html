世界地图：先认依赖，再选积木World map: dependencies before components

先看这张地图的四帧：最小读写闭环、旁路缓存、异步投递、按需协调。它展示可选机制；后面的商品 GET 只用其中一条读路径。灰色是请求，绿色是回复，橙色虚线是异步，红色虚线是故障或拒绝。

The four frames add a minimal read/write loop, a look-aside cache, asynchronous delivery, and optional coordination. These are choices; the product GET below uses just the read path. Gray means request, green reply, dashed orange asynchronous delivery, and dashed red failure or rejection.

缓存减少重复读取，代价是旧值和新的故障依赖。业务行与 outbox 若由同一数据库事务提交，可留下可恢复的投递责任；Relay 重发仍可能产生重复，Worker 的副作用要另做幂等（Ch20、[6]）。租约用于约束并发所有权，不等于“恰好执行一次”；过期持有者与重复请求仍需处理（Ch08、[4]）。

Caching avoids repeated reads at the cost of staleness and a new dependency. Committing business rows and outbox in one database transaction preserves a recoverable delivery obligation; relay retries can duplicate delivery, so worker effects still need idempotency (Ch20, [6]). A lease controls concurrent ownership; it does not guarantee exactly-once execution. Expired holders and repeated requests need separate handling (Ch08, [4]).

第一步 · 定范围：先写成功与失败Step 1 · Scope: define success and failure

开场可以只说：“先设计非个性化商品详情读，返回标题、价格、可售标记和图片 URL；结账和搜索不在本轮。确认规模与旧价窗口后，我画一次 GET，再检查缓存失效。” 对方没有给数字时，明确写教学假设后推进。

Open with: “I will design non-personalized product-detail reads returning title, price, availability, and image URLs. Checkout and search are outside this round. After confirming scale and staleness, I will walk one GET and test cache failure.” If numbers are missing, state working assumptions and continue.

Minimal data: Product(id PK, title, price_cents, currency, availability, image_urls, version). Read one row by id. A cached version identifies content but does not prove it is current. Trust and scope differ: leaving checkout unwired excludes its design; it does not place checkout outside the security boundary.

100 是满载数学上限；80 是本例自设的规划预算，两者都不是压测结果。 10ms源自Dean 2007年的数量级例子 [1]。为了练习，我们再假设每次回源（含404和超时尝试）只发一次查询、耗一个单位；实际DB可能命中缓冲池、做多次I/O或有不同查询成本，必须换成测量。20/s余量并不证明80ms尾延迟或写峰值能达标。

100 is a fully busy mathematical ceiling; 80 is our chosen planning budget. Neither is a load-test result. The 10ms comes from Dean’s 2007 order-of-magnitude example [1]. For this exercise each origin attempt—including not-found and timeout attempts—issues one query costing one unit. Real queries may hit buffers or require multiple I/Os and different costs; replace this model with measurements. Reserving 20/s does not prove an 80ms tail or sufficient write-peak capacity.

回源负载 = 峰值QPS × (1 − 有效命中率)。所以 h ≥ 1 − 80/5000 = 98.4%；98%只是卡住100/s满载上限，90%则产生500回源/s。这里的“命中”必须还能在截止前发送；过期、缓存超时都算未命中。即使平均命中率足够，同步过期仍会制造尖峰，所有回源都需要gate。

Origin load = peak QPS × (1 − usable hit rate). Thus h ≥ 1 − 80/5000 = 98.4%. A 98% hit rate merely reaches the fully busy 100/s ceiling; 90% yields 500 origin reads/s. A hit counts only if it can still be sent before expiry. Expiry and cache timeouts count as misses. Even adequate average hits allow synchronized-expiry spikes, so every origin path needs admission.

缓存是候选方案，不是由QPS自动证明的唯一答案。要验证工作集、缓存容量与命中率；若Store实测已能满足5,000QPS和延迟，先不加缓存。若未命中代价高而命中率达不到要求，可增加存储读能力或改变访问路径；均匀访问也不必然“几乎零命中”，还取决于整个工作集能否装入缓存。更多估算见 Ch03。

A cache is a candidate, not the only answer implied by QPS. Validate working set, cache capacity, and hit rate. If measured store capacity already meets 5,000 QPS and latency, start without it. Otherwise increase read capacity or change access patterns when cache misses remain too costly. Uniform access does not necessarily mean near-zero hits; the whole working set might fit. See Ch03.

第三步 · 高层：一次 GET 连到实现Step 3 · High-level: connect one GET to code

沿图读一次：Client → Edge → Product Service；可用缓存命中返回200，否则经过回源gate查询Product Store。Store拥有商品行，服务实例可以替换，缓存可以丢。第4帧就是本例的总览：队列没有参与同步读，第二区域尚未设计。

Walk Client → Edge → Product Service. A usable cache hit returns 200; otherwise an admitted request queries Product Store. The store owns product rows, service instances are replaceable, and cache contents may be lost. Frame 4 is the overview: the queue is outside this synchronous read and a second region is not designed yet.

关键实现：先判缓存，再受控回源Key implementation: cache first, bounded origin next

下面是教学伪代码，输入商品id，输出200/400/404/503。它对应图中的lookup、origin read、fill与回复；5ms缓存等待是80ms请求目标中的教学子预算，不代表生产推荐值。客户端与代理不自动重试，缓存熔断只改变是否尝试lookup，不绕过gate。

This is teaching pseudocode: product id in, 200/400/404/503 out. It maps to lookup, origin read, fill, and reply in the diagram. The 5ms cache wait is an illustrative sub-budget within the 80ms request target, not a production recommendation. Clients and proxies do not retry automatically. An open cache circuit skips lookup but never skips the gate.

GET product(id):                          # teaching pseudocode, not Java
    require validId(id)                    # otherwise 400
    entry = cache.getWithin(id, 5ms)        # timeout/open circuit => MISS
    if usable(entry):
        return replyBefore(200, entry.row, entry.valid_until)

    if originGate.tryAdmitOne() != GRANTED:
        return 503                         # no DB call; no automatic retry
    observed_at = boundedClock.now()
    valid_until = observed_at + 30s - 300ms
    result = store.readOnceFresh(id, remainingRequestBudget())
    # one query, no hidden retry; NOT_FOUND and TIMEOUT also spend admission
    if result is ERROR or TIMEOUT:
        return 503                         # never convert failure into 404
    if result is NOT_FOUND:
        return 404                         # this example does not cache 404
    entry = Entry(result.row, valid_until)
    if not usable(entry):
        return 503                         # late result: no fill and no 200
    cache.tryFillAsync(id, entry)           # best effort; preserve deadline
    return replyBefore(200, entry.row, entry.valid_until)

原子边界只在准入决定处。 originGate.tryAdmitOne()由独立的共享准入组件串行化“检查余额并扣一个单位”，全体实例合计80/s、突发1；不是每台80，也不能存放在本次宕掉的Cache里。准入未知或组件不可用就拒绝，已扣额度不因404/超时退回；切主不能凭空重置满额度。读客户端只执行一次DB尝试，另有有界并发与请求deadline。详见 Ch04；这里声明依赖契约，不实现分布式限流器。

The atomic boundary is admission only. An independent shared component serializes checking and consuming one unit in originGate.tryAdmitOne(): 80/s across all instances, burst 1. It is neither 80 per instance nor stored in the failed Cache. Unknown or unavailable admission fails closed; 404s and timeouts do not refund credit, and failover cannot reset a full allowance. The read client makes one DB attempt with bounded concurrency and a deadline. See Ch04; this declares a dependency contract, not a distributed-limiter implementation.

Cache与Store没有跨系统事务。异步回填失败只损失命中率；迟到回填保留原截止，读取方仍校验。readOnceFresh要求当前权威在调用开始后建立读快照，不用任意滞后副本或旧事务快照。Store超时是依赖失败，不是商品不存在。

Cache and Store have no cross-system transaction. Failed asynchronous fills reduce hit rate; late fills preserve the original deadline and readers still validate it. readOnceFresh requires the current authority to establish its snapshot after the call starts, not an arbitrarily lagging replica or old transaction snapshot. Store timeout is a dependency failure, not proof that a product is absent.

30秒契约：截止不续期，最后发送也检查30-second contract: never renew the deadline; check final sending

usable(entry)要求条目存在、时钟界限已验证、当前时间早于 valid_until。假设观察端与发送端各有≤100ms绝对时钟误差，再预留100ms完成最后检查与发送，因此扣300ms。这是条件化教学契约：时钟界限失效时不服务旧值。

usable(entry) requires an entry, verified clock bounds, and current time before valid_until. Assume each observing/sending clock has at most 100ms absolute error, and reserve another 100ms for final check through send completion: subtract 300ms. This is a conditional teaching contract. When the clock bound cannot be verified, refuse old values.

replyBefore不是普通return：截止随响应传到最终发送方（本例Edge），发送方复查并在100ms预留内完成；否则中止响应，计为失败。缓存、本机副本和Edge都继承同一截止，不以回填时刻续30秒。此处不实现时钟监控、传输中止或完整熔断状态机；对应机制见 Ch38。

replyBefore is not a plain return: propagate the deadline to the final sender (Edge here), which rechecks and completes within the reserved 100ms or aborts the response and records failure. Shared cache, local copies, and Edge inherit one deadline; fill never starts a new 30 seconds. Clock monitoring, transport abort, and a complete circuit-breaker state machine are outside this snippet; see Ch38.

第四步 · 深挖：缓存失效，存储不能陪着倒Step 4 · Deep dive: contain cache failure

正常miss与缓存故障走同一个回源gate。 第2帧先暴露无上限fallback的危险，第3帧加准入，第4帧说明被拒绝者。按本例预算，持续峰值下最多约80次/s进入Store，其余至少约4,920次/s返回503；获准请求也可能404或因Store失败返回503，不能把80称作必然成功。

Normal misses and cache failure use the same origin gate. Frame 2 exposes uncapped fallback, frame 3 adds admission, and frame 4 shows rejection. At sustained peak, at most about 80 attempts/s reach Store and at least about 4,920/s are rejected with 503. Admitted requests may still return 404 or fail with 503; 80 is not guaranteed successful throughput.

503牺牲这次调用的可用性，以避免故障扩散；它不是CAP意义下“选择可用”。返回Retry-After只能提供等待提示，客户端仍需有界退避与抖动，不能齐刷刷重试。恢复时先探测、小步升流，同时看Store排队与错误；缓存恢复不代表立刻有足够命中。SRE过载章节支持快速拒绝与有条件降级 [2]。

A 503 gives up availability for this call to contain failure; it does not choose availability in the CAP sense. Retry-After is only a delay hint; clients still need bounded retries with backoff and jitter. Recover with probes and gradual traffic while watching store queues and errors: a recovered cache may still be cold. The SRE overload chapter supports rejection and conditional degradation [2].

可选降级只能使用已经存在且未过截止的本机副本。冷实例没有副本，超时也不能编造缓存命中。单进程合并同key请求可以减少重复工作，却不能替代全局准入。99.9%是目标：整层缓存故障时大量503会消耗错误预算，当前设计还需要故障频率/时长与恢复演练来证明可达。

Optional degradation can use only a local copy that already exists and is still before its deadline. Cold instances have no such copy; a timeout cannot manufacture a hit. Per-process coalescing helps duplicate work but does not replace global admission. The 99.9% is a target: cache-tier failures spend the error budget, and this design still needs evidence about outage frequency, duration, and recovery.

Budget cross-region calls using actual RTT and tail latency. The California–Netherlands 150ms in Dean’s slides is a historical order of magnitude, not a current measurement for arbitrary regions [1]. During a partition, state behavior by operation: browse continues only while the 30-second contract remains provable, then refuses; single-authority price writes refuse if safe commit is unavailable. Bounded staleness does not guarantee availability through an arbitrarily long partition. Avoid labeling the whole system “AP” [5].

卡住时说明缺的依据：“我需要知道Store的实测容量；先用80/s教学预算继续，之后替换。”别沉默堆组件，也别在方法章把每种机制都展开。队列是否出现取决于异步任务与交付语义，不由0.6写QPS单独决定；第二区域取决于故障恢复和地域需求，不是可用性百分比自动生成的盒子。

When stuck, name missing evidence: “I need measured store capacity; I will proceed with the teaching budget of 80/s and replace it later.” Avoid silently accumulating components or expanding every mechanism. A queue depends on asynchronous work and delivery semantics, not a 0.6 write-QPS number alone. Another region depends on recovery and geographic needs; an availability percentage does not automatically draw it.

观测用四个黄金信号 [3]：延迟分开200与503；流量区分有效命中、回源与拒绝；错误包括依赖失败及违反本例延迟/新鲜度目标的响应；饱和观察Store队列、在途数与准入量。最后一句：“这个方案依赖98.4%有效命中；缓存全失效时优先保护Store，接受大量503。下一步验证工作集、压测和故障恢复，而不是宣称SLO已经达标。”

Use the four golden signals [3]: separate 200 and 503 latency; distinguish usable hits, origin calls, and rejections; track dependency failures and violations of the stated latency/freshness targets; watch store queues, in-flight work, and admission for saturation. Close with: “This design depends on 98.4% usable hits. During a full cache failure it protects Store at the cost of many 503s. Next I would validate the working set, load, and recovery before claiming the SLO.”

  5. [5] Eric Brewer, 2012, CAP Twelve Years Later: How the “Rules” Have Changed. 作者原文：分区下按操作选择；取消操作损失可用性。Original author’s article: choices by operation during partitions; canceling loses availability.
  6. [6] AWS Prescriptive Guidance, Transactional outbox pattern. 业务行与outbox同事务，投递可能重复，消费者需幂等。Business rows and outbox share a transaction; delivery can duplicate, requiring consumer idempotency.
