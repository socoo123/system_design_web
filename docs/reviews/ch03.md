## 纠错与主要复算

| 原问题 | 修正与依据 |
|---|---|
| 10台正常60%，故障后9×1000仍称有余量，易被理解为保持预算 | 明确图为读流量白板初算；67%超过60%。白板仅读正常10、同预算N−1为11；精确读正常12、N−1为13。 |
| 写仅300/s所以“不改N” | 白板同池等成本总量6300/600需11；精确总量210M×3/86400=7291.6667，正常ceil(P/600)=13，N−1=14。 |
| 13台正常够用被当成故障也够用 | 13台失1台预算7200，低于7291.6667；14台失1台预算7800才够。原始12000能力不能替代7200预算。 |
| 一天用10⁵秒被误视作安全估算 | 结果是精确值0.864倍，低估13.6%；最终台数用86400秒。 |
| 二/十进制差异“不影响分片” | GiB≈1.074GB、TiB≈1.100TB；接近阈值会改变结论。KB在本章明确为十进制kB。 |
| CDN请求命中率直接乘字节 | 90%明确为字节命中率，或请求等大前提；精确API净荷1.111Gb/s，媒体回源2.778Gb/s。 |
| 10.95TB可被当成完整硬盘规划 | 仅三份行数据；加假设1.5放大/0.7填充率得23.4643TB，备份、WAL、重建、放置另计。 |
| 6/s错误回源远低于单盘100/s所以安全 | 已有约300/s miss；独立错误精确305.7/s，保守306/s，再计写/重试与剩余容量；100/s故障上限是聚合教学策略，不是实测能力。 |
| 三盘承担300/s视作可用配置 | 100/s是串行10ms寻道的100%忙理想上限；60%预算至少5盘，仍未计写/故障。 |
| 请求失败率与时间可用率互换 | 日请求99.9%给200000次/天；8.76h/年属于另一时间指标，非请求错误的实际停机换算。 |
| “失败互不重叠”却乘成功率 | 乘0.9995³需独立事件；互斥失败相加才是99.85%。 |
| Ch09未发布实例数，短链只写20台 | 对齐已验收Ch09：正常20、同预算N−1为21；若同池等成本加入写，复算后仍20/21。 |

## 代码保证和实际运行

`CapacityEstimate.java`为Java17+标准库可运行示例。核心方法使用BigInteger精确分子/分母和余数做向上取整；输入成本已归一化，整数峰值系数与整数利用率百分比；返回整数部署台数。

- 正常：210M日工作量、3倍、1000/台、60% → 正常13、N−1为14。
- 边界：恰好6000峰值需10台，日工作量增加1后需11；零需求返回0（无热池约束）；短链20/21。
- 错误：负流量、峰值0、单机0、利用率0/101、负故障数抛IllegalArgumentException；超int部署数抛ArithmeticException。
- 核心反例：13台失1后7200不够，14台失1后7800足够。
- `javac --release 17 -d /tmp/ch03-java examples/ch03/CapacityEstimate.java` 与 `java -cp /tmp/ch03-java CapacityEstimate`通过。本机JDK21.0.2，以Java17目标编译；未谎称在JDK17运行时测试。
- 输出：`PASS: 10 valid cases, 7 rejected inputs, N-1 counterexample`。
- 浏览器脚本逐字核对页面代码与源文件`BEGIN PAGE`/`END PAGE`片段一致。

这只是容量算术模型，不验证压测能力、负载均衡均匀性、故障切流速度、相关故障或生产SLO。零负载不分配热备；非整数成本可先归一化，需自行确认成本模型。
