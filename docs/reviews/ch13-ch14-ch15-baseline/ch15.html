这一章结束你能做什么What you can do after this chapter

从一条文件保存路径画起，把小元数据请求与大块字节拆开；用明确的教学假设算文件 QPS、块 PUT、上传带宽和版本占用。讲清内容哈希如何命名块、服务端如何确认续传状态，以及两个离线设备为什么不能靠“最后一次写入”默默合并。最后把提交、变更日志、通知、补拉和回收连起来，指出每一个会丢文件或复活旧版本的窗口。

Start from one save path and separate small metadata calls from large bytes. Use labeled assumptions to size file requests, block PUTs, bandwidth and versions. Explain content keys, authoritative resume state and why offline devices cannot silently merge with last-write-wins. Connect commit, change log, hints, catch-up and reclamation, identifying windows that lose files or revive old versions.

30 秒开场：先确认是文件网盘The 30-second open: agree on a file drive

我先按纯文件网盘来设计：上传、下载、多端同步和版本历史。文件有稳定 file_id，版本是有序块列表；元数据由关系库做权威，字节进不可变对象。客户端切块、问缺块、直传并校验，最后带父版本条件提交。冲突保留另一份文件；通知只是叫醒设备，漏通知靠游标补拉。先算带宽和块请求数，再画分层，最后讲续传、冲突和回收。

I will design a file drive: upload, download, device sync and version history. A stable file_id owns ordered block manifests. A relational database owns metadata; immutable objects hold bytes. The client chunks, discovers missing data, uploads directly and verifies, then conditionally commits the parent version. Conflicts keep a separate file. Notifications are hints, with cursor catch-up after missed hints. I size bandwidth and block operations before layering, then explain resume, conflicts and reclamation.

先问六件事：纯文件还是字符级实时协作、单文件上限、是否支持长期离线、多端冲突要不要保留两份、版本保留多久、分享是否限制在租户内。答案会改变机制：长期离线需要持久变更日志，保留历史会扩大回收根集合，分享要在每次读 manifest 和签下载地址时检查权限。没有答案的规模自己写为 assumption，再继续画；不能把“最新版本”含糊地解释成所有设备同时看到。

Ask six things: files or character-level collaboration, file limit, long offline periods, whether conflicts retain both copies, version retention, and tenant-scoped sharing. Long offline periods need a durable log; retained history expands GC roots; sharing needs permission checks on manifests and download grants. Label unanswered scale choices as assumptions and continue. “Latest” must not imply simultaneous visibility on every device.

本章的保存语义固定为：服务端确认版本提交以后，读取权威 head 能看到该版本；其他设备最终补拉到它。上传进度完成、对象 PUT 完成、版本提交完成、另一端本地替换完成，是四个不同的状态。弱网下界面允许显示“正在上传”或“等待解决冲突”，但不能在只收到单个块 ACK 时显示整个文件已同步。

Saved means that after a version commit is acknowledged, authoritative head reads see it; other devices catch up eventually. Upload progress, object PUT completion, version commit and local replacement on another device are four distinct states. The UI can show uploading or conflict resolution, but one block ACK must not mean the entire file is synced.

一天文件保存数是 10,000,000 × 2 = 20,000,000，平均 20,000,000 ÷ 86,400 ≈ 231.5 次/秒，峰值约 1,157.4 次/秒。这只是文件级操作。一天入站 10,000,000 × 100 MB = 1 PB，平均 11.57 GB/s，乘 8 是 92.59 Gb/s，再乘峰值 5，约 462.96 Gb/s。字节走直传的原因就在这笔带宽，不是元数据 API 已经有几十万 QPS。

10,000,000 × 2 = 20,000,000 file saves/day; ÷86,400 ≈231.5/s average, ≈1,157.4/s at peak. Those are file operations. Daily inbound is 10,000,000 ×100 MB =1 PB, averaging 11.57 GB/s or 92.59 Gb/s, with a 5× peak of ≈462.96 Gb/s. This bandwidth forces direct upload; it does not mean the metadata API has hundreds of thousands of QPS.

块请求必须另算。100 MB/人除以 4,194,304 B 得到约 23.84 个满块；每个文件向上取整。若每人两份都恰好是 50 MB，每文件 ceil(50,000,000 ÷ 4,194,304) = 12 块，一天 2,000 万 × 12 = 2.4 亿 PUT，平均约 2,778/s，峰值约 13,889/s。只知道总字节数时，每文件尾块最多再多一块：1 PB ÷ 4 MiB + 2,000 万 < 2.585 亿块/天，峰值约 14,955/s，先预算约 1.5 万。真实分布决定更精确的数。

Size block operations separately. 100 MB/user ÷4,194,304 B ≈23.84 full-block equivalents, but round up per file. If both files are exactly 50 MB, each needs ceil(50,000,000/4,194,304)=12 blocks: 240M PUTs/day, ≈2,778/s average, ≈13,889/s peak. With total bytes alone, each file adds less than one rounding block: 1 PB/4 MiB +20M <258.5M blocks/day, ≈14,955/s peak. Budget around 15K initially; the size distribution gives a closer estimate.

配额天花板是 50,000,000 × 10 GB = 500 PB，不能说成已经落盘的占用。按每日 1 PB 输入，连续 30 天全部是新内容且完全不共享，字节增量上界是 30 PB；教学模型乘三份是 90 PB，未含此前仍存的文件、manifest、日志和备份。若只保证版本保留 30 天，也不能把所有当前文件 30 天后删掉，所以这不是全站存储总量。去重率未知，容量先用 0% 节省；上线后再从唯一块增量测节省比例。

The quota ceiling is 50,000,000 ×10 GB =500 PB, not occupied storage. With 1 PB/day of entirely new unshared input, 30 days adds at most 30 PB of logical bytes; three teaching-model copies are 90 PB, excluding older live files, manifests, logs and backups. Thirty-day version retention does not delete every current file after thirty days, so this is not total site storage. Plan with 0% dedup savings until unique-block growth is measured.

下载按每次保存只同步到另一个设备估为同量级，不把上传和下载相加后说成一条方向的网卡速率。公开分享、重复下载和本地缓存命中需要分别加减。5 秒同步目标只覆盖在线设备与小增量：4 MiB × 8 ÷ 20 Mb/s ≈ 1.68 秒是纯传输下限，还要留出通知、鉴权和落盘时间；1 GiB 在同一链路上约 429 秒，不能承诺也在 5 秒内完成。

With one other syncing device per save, downloads have a similar magnitude; do not combine both directions into one-direction NIC capacity. Public sharing, retries and local cache hits need separate accounting. A five-second sync target applies to online devices and small deltas: 4 MiB ×8/20 Mb/s ≈1.68 s of transfer alone, plus notification, authorization and persistence. A 1 GiB transfer takes ≈429 s on that link and cannot share the five-second target.

15.1 · 分层：字节直传，版本由元数据发布15.1 · Layers: direct bytes, metadata publication

正常路径：先给权限，再让字节离开 APINormal path: authorize, then move bytes off the API

客户端先请求初始化，带 file_id、base_version、总长度和有序块摘要。Metadata 查文件 ACL、租户和配额，创建 upload_session；Block svc 查租户内已经验证的块，为缺块签短期上传地址。客户端用这些地址直接 PUT Object store，服务端核内容与声明一致，再返回耐久收据。最后一次 commit 请求回到 Metadata。图中 Primary → Metadata → Client 的绿色回程，表示版本事务真正完成，不是只拿到一个预签名地址。

The client initializes with file_id, base_version, length and ordered digests. Metadata checks ACL, tenant and quota and creates an upload session; Block svc finds verified tenant blocks and signs short-lived grants for missing ones. The client PUTs directly to Object store, with server-side content validation and durable receipts, then commits through Metadata. The green Primary → Metadata → Client reply means the version transaction completed, not merely that a URL was issued.

为什么这样选：小事务和大吞吐各有故障域Why: separate small transactions from large throughput

关系库保留 file_id、parent_id、name、head_version、ACL 和租户配额；版本行保留 parent_version、manifest_id、size、提交幂等键。路径只是目录属性，重命名不能变成重新上传字节；稳定 file_id 让移动、重命名和改内容各自有条件更新。一次提交还要保证同目录名称唯一、配额没有被并发上传越过。若只检查旧配额再分别加用量，两份文件会一起通过检查；预留额度或条件更新必须在同一事务里判定。

The relational database owns file_id, parent_id, name, head_version, ACL and quota. Versions hold parent_version, manifest_id, size and a commit idempotency key. Paths are directory attributes: stable file_id separates renames, moves and content edits. Commit also enforces name uniqueness and concurrent quota accounting. Reading quota and later incrementing it separately lets two uploads both pass; reservations or conditional updates must be transactional.

另一种方案是所有字节经 Block svc 代理。它能统一流式校验、加密和网络入口，客户端更简单；代价是峰值约 463 Gb/s 要穿过整层服务，扩容、故障和成本都随字节增长。直传把这笔吞吐放到存储接入层，但授权、校验、超时重试和可观测性都要做。这里选直传不是说代理永远错误，而是当前吞吐假设已经让无理由的中转太贵。

Proxying every byte through Block svc can centralize streaming validation, encryption and ingress and simplify clients. Its cost is ≈463 Gb/s across the service tier at peak, with scaling and failures following byte volume. Direct upload moves throughput to storage ingress but still needs grants, checksums, retries and observability. Under these assumptions, an otherwise unnecessary proxy is expensive.

故障窗口：字节成功而发布失败Failure window: bytes succeed, publication fails

Object store 与 Primary 不在一个本地事务中。我们选择“先存字节、后发版本”：对象成功、元数据失败会留下暂时无引用块，之后由会话重试或回收处理；反过来先写 head 再补块，会让用户下载到缺失对象。服务端核验后还要给块加活跃租约，避免核验与 commit 之间被 GC 删掉。commit 原子更新 head、完整 manifest 引用、change log 和 outbox；版本提交结果丢失时用同一个幂等键查询或重试，不重复创建版本。

Object store and Primary do not share a local transaction. Bytes first means metadata failure leaves temporary orphans for session recovery or GC. Publishing head first exposes missing objects. Verification must also pin blocks with active leases so GC cannot delete them before commit. Commit atomically updates head, complete manifest references, change log and outbox. A lost commit response is queried or retried with the same idempotency key rather than creating another version.

故障时保留行为要明确：Primary 不可用就停止目录和版本写入，客户端继续本地保存；已经授权的块上传可继续，但不能显示发布成功。Block svc 无法核验时不提交新版本，不能相信客户端 ACK。Object store 某个块取不到时，下载失败的仍是那份版本，不改成一个少块的“成功”文件。静态图用逻辑服务省了部署细节，正文必须把每个成功边界讲清楚。

If Primary is unavailable, stop directory and version writes while clients save locally. Existing upload grants can continue, but publication remains pending. If Block svc cannot verify, do not commit based on client ACKs. A missing object fails that version’s download; it cannot become a shorter successful file. The logical diagram omits deployment details but preserves each success boundary.

15.2 · 分块与 COW：复用的条件要说清15.2 · Chunking and COW: state the reuse conditions

正常路径：完整 manifest 引用不可变块Normal path: complete manifests reference immutable blocks

本章选 SHA-256 作内容摘要，key 是 tenant_id 加摘要，另记块长度和核验状态。客户端的 hash 只是声明，服务端必须通过可信存储校验或读回验证后才登记 durable；有条件创建使同租户并发传同一 hash 不覆盖已存在字节。Venti 论文说明内容摘要可以作为块标识，并把重复内容合并；它使用的历史算法不直接当成本章算法选型。[1] 内容寻址解决“字节是谁”，访问权限仍由文件和租户决定。

Use SHA-256 digests with tenant-scoped keys, lengths and verification state. Client hashes are claims; trusted storage validation or read-back precedes a durable record. Conditional creation avoids overwriting existing content on concurrent uploads. Venti demonstrates digest-addressed blocks and coalescing duplicate content; its historical hash choice is not this chapter’s algorithm choice. [1] Addressing identifies bytes; file and tenant permissions still authorize access.

Dropbox 公开 content_hash 算法按 4,194,304 字节切块，先逐块 SHA-256，再拼接二进制摘要做一次 SHA-256。[2] 这是验证整文件内容的 API 算法；它不是关于内部去重布局的保证。本章借这个公开量级，把块大小设为 4 MiB，并直接用每块摘要命名独立对象。两者设计各有用途，不把 Dropbox 最后一次聚合 hash 误写成每个对象的 key。

Dropbox’s public content_hash algorithm splits at 4,194,304 bytes, hashes each block with SHA-256, then hashes the concatenated binary digests. [2] It verifies whole-file content and does not promise an internal dedup layout. This chapter assumes the same 4 MiB scale but names independent objects by their individual digests; Dropbox’s final aggregate digest is not each object key.

图中的 v7 和 v8 都是完整有序 manifest：v7 为 [hA,hB,hC]，v8 为 [hA,hD,hC]。父版本记录编辑来自哪一版，不表示读 v8 要读取 v7 再应用补丁。每条块引用还含长度；最后一块可以不足 4 MiB，空文件用空列表与零长度表示。完整列表使单版恢复简单；大 manifest 可以分页或分层，但仍需版本内校验一致，不能一半读到旧列表、一半读到新列表。

Both v7 and v8 have complete ordered manifests: [hA,hB,hC] and [hA,hD,hC]. Parent versions record editing ancestry, not a patch-replay requirement. References include lengths, with short tails allowed; empty files have an empty list and zero length. Complete manifests simplify restore. Large manifests may be paged or hierarchical, but a version must not mix old and new list fragments.

取舍：块大小让请求数和修改放大互换Trade-off: block size exchanges requests for edit amplification

1 GiB ÷ 4 MiB = 256 条引用；只存 32 字节二进制摘要，列表至少 8,192 B = 8 KiB，还没算长度、索引和序列化。若缩到 64 KiB，共 16,384 块，摘要列表至少 512 KiB，请求数放大 64 倍。大块降低查缺和 PUT 数，却可能为一个小改动上传整块；小块省改动带宽，却让清单、索引和调度更忙。不能只说“1 GB 会炸表”，要指出炸的是哪类请求或数据。

1 GiB/4 MiB =256 references; 32-byte binary digests alone cost 8,192 B =8 KiB before lengths, indexes or encoding. At 64 KiB, there are 16,384 blocks and at least 512 KiB of digests, with 64× the operations. Large blocks reduce lookup and PUT counts but amplify small edits; small blocks reduce edit bytes while enlarging manifests and scheduling load. Name the cost rather than claiming a 1 GB file explodes metadata.

“改一行只上传一两块”只对边界保持、改动局部的例子成立。文件头插一个字节会把后面的定长边界全推移，许多摘要一起改变；压缩包或加密文件也可能让局部编辑传播到大量字节。content-defined chunking 用内容决定边界，在插入后通常能重新找到旧边界；restic 的设计文档给出这种增量复用机制。[3] 它仍有扫描、hash CPU 和块长变化的代价，不是任何编辑都能保证一块。

“An edit uploads one or two blocks” requires local changes with preserved boundaries. A prefix insertion shifts fixed-size boundaries; compressed or encrypted formats may propagate edits widely. Content-defined chunking usually resynchronizes boundaries after insertion, as documented by restic. [3] It adds scanning and hash CPU and variable sizes, and cannot guarantee one changed block for every edit.

故障与边界：hash 不是授权凭证Failure and boundary: a hash is not an access credential

查缺块接口只在已授权的租户域内工作；知道 hash 不能下载别人的文件，也不能直接把别人的块挂到自己的 manifest。跨租户去重会把命中与否变成“别人是否存过某内容”的信号，还会让逻辑配额与物理节省混在一起。默认租户内去重，用户配额按逻辑文件大小收；相同字节共享不改变权限。服务端还要拒绝同 key 下长度不一致、未校验或被删除中的块引用。

Missing-block lookup is scoped to an authorized tenant. Knowing a hash must not grant downloads or adoption of another tenant’s blocks. Cross-tenant reuse can disclose content existence and confuse logical quota with physical savings. Default to tenant-scoped dedup with logical file-size quota; byte sharing does not change permissions. Reject mismatched lengths, unverified objects and blocks being deleted.

旧块不被原地修改，新块核验失败就不加入新 manifest；客户端保留旧本地文件和未成功的编辑。两个并发上传同一内容可以先各自写 staging 对象，由服务端校验后晋升到内容 key，或使用具有摘要校验和条件创建的存储能力。具体选哪个取决于存储接口；不具备可信校验时，不能把“签了 URL”说成完成了内容寻址验证。

Never edit old blocks in place. Failed verification excludes a new block while the client keeps the old file and pending edit. Concurrent uploads can use staging objects followed by verified promotion, or trusted checksum validation with conditional creation. Choose according to storage capabilities; a signed URL alone does not establish content integrity.

15.3 · 断点续传：超时后向服务器对账15.3 · Resume: reconcile after a timeout

正常路径：以会话和收据为准Normal path: trust sessions and receipts

会话 u42 持久记录租户、文件、base_version、manifest、已验证块和过期时间。块状态先是 missing，上传中只能算 pending，核验通过并建立保护租约后才是 durable。客户端的位图用于减少本地重复工作，服务器状态才决定 commit 门槛。本组另用 1 GiB 新文件，省略普通成功 PUT。hR 的 ACK 丢了，status 确认含它共 192 块已耐久，只剩 64 块，hS 代表其中一块。

Session u42 persists tenant, file, base_version, manifest, verified blocks and expiry. Blocks move from missing to pending to durable only after verification and lease protection. Client bitmaps reduce local work; server state controls commit. This deck uses a separate 1 GiB new file, omitting ordinary successful PUTs. hR loses its ACK; status confirms 192 durable blocks including hR, with 64 remaining and hS representing one.

若 ACK 丢失后马上重复 PUT，同 hash、同长度的已验证内容应当可安全重复；但重试只能用会话允许的 key，不能在不同内容间复用序号。状态查询发现对象存在却缺核验记录时，Block svc 重新核验并补记，不能只凭对象名判成功。签名地址过期后刷新授权，保留同一会话和已耐久块；会话已经过期就重新初始化并查缺，旧会话不能复活到旧权限。

Repeating a verified same-hash, same-length PUT is safe, but retries stay within authorized session keys and must not reuse an ordinal for different content. An existing object without a verification record requires verification and record repair, not trust in its name. Expired grants can be refreshed within a live session. An expired session requires reinitialization and fresh authorization; old permissions must not be revived.

三种机制要区分：独立块、顺序偏移、multipartDistinguish independent blocks, offsets and multipart

图用独立块对象的应用层续传：256 个 hash 各有对象，上传到一半就查哪些 durable。另一种 tus 1.0.0 核心协议使用 HEAD 查 Upload-Offset，再用 PATCH 从该字节偏移续传；偏移不匹配返回 409，核心是顺序进度，不是随便并行乱序发块。[4] 单个大对象的 multipart 则先创建 upload id，上传带 part number 的分片，complete 按编号拼成一个对象。[5] 三者都能续传，但持久状态与完成条件不同。

This diagram resumes independent content objects by querying which of 256 hashes are durable. The tus 1.0.0 core uses HEAD to read Upload-Offset and PATCH from that byte position, rejecting mismatches with 409; it tracks sequential progress. [4] Multipart creates an upload ID, accepts numbered parts and completes them into one object in part order. [5] All resume uploads, but their persisted state and completion conditions differ.

4 MiB 逻辑块不能未经检查就当成某个厂商 multipart 的非末尾 part。S3 文档规定这类 part 至少 5 MiB，末尾 part 例外。[6] 本章 4 MiB 块作为独立对象做普通 PUT，未违反这个规则；若需要把一组逻辑块打包成一个大物理对象，应选择满足接口限制的传输 part，并另存逻辑块到对象偏移的索引。打包可减少小对象成本，但读取、核验和回收都更复杂，本轮不引入这个额外层。

Do not map a 4 MiB logical block blindly to a vendor’s nonfinal multipart part. S3 specifies a 5 MiB minimum with a final-part exception. [6] Independent ordinary PUTs of this chapter’s 4 MiB objects do not violate that rule. Packing logical blocks into a physical object requires compliant transport parts and an offset index, complicating reads, checksums and reclamation; this design does not add that layer.

代价与故障窗口：续传减少浪费，不保证瞬间完成Cost and failure window: resume reduces waste

假设 1 GiB 文件已确认 192/256 块，剩余 64 块共 256 MiB。20 Mb/s 链路上，剩余传输的理想下限是 268,435,456 B × 8 ÷ 20,000,000 ≈ 107.37 秒，整文件是 429.50 秒；少传约 75% 的字节。块失败不应触发整文件重来，但多个在途块可能一起丢，需要重发未核验的那部分。限制并发窗口、指数退避加抖动；无限并行会争夺同一弱网带宽并拖慢所有块。

With 192/256 verified blocks in a 1 GiB file, 64 blocks or 256 MiB remain. At 20 Mb/s, the ideal lower bound is 268,435,456 B ×8/20,000,000 ≈107.37 s versus 429.50 s for the full file, saving about 75% of bytes. Reissue unverified in-flight blocks rather than the whole file. Bound concurrency and use exponential backoff with jitter; unlimited parallelism competes for the same weak link.

complete 不能把对象存储返回的 ETag 一律当作内容 SHA-256，S3 也明确完整对象的 ETag 不一定是 MD5。[5] 使用明确的校验算法、长度和应用级块摘要；multipart 的 complete 要携带正确的 part 编号与收据，应用块会话的 complete 要确认全部有序引用已 durable 且受租约保护。若客户端只上传了“缺块集合”中的一部分，commit 必须拒绝，不用空块凑出目标长度。

An object ETag is not automatically content SHA-256; S3 also states that a completed object’s ETag need not be MD5. [5] Use explicit checksum algorithms, lengths and application digests. Multipart completion requires part numbers and receipts; application completion requires every ordered reference durable and leased. Reject incomplete missing-block sets rather than fill the target length with empty bytes.

未完成会话需要清理。假设 A11：每天 1 PB 中有 1% 上传被放弃，每天新增 10 TB 暂存字节；保留 48 小时就可能积到约 20 TB，还没乘存储冗余。24 小时的会话到期只是停止续传和释放保护，清理按回收规则执行；multipart 暂存 part 要显式 complete 或 abort 才停止占用和相应计费。[5] 监控会话年龄、未发布字节和核验失败率，比只盯上传开始 QPS 更能发现泄漏。

Under A11, if 1% of 1 PB/day is abandoned, staging grows by 10 TB/day; a 48-hour retention can accumulate ≈20 TB before redundancy. A 24-hour session expiry stops resume and releases protection; deletion follows GC rules. Multipart parts require completion or abort to release storage and associated charges. [5] Track session age, unpublished bytes and verification failures, not just upload-start QPS.

15.4 · 发布与冲突：比较父版本，保留失败编辑15.4 · Publication and conflicts: compare the parent

正常路径：同一文件只有一个条件提交胜出Normal path: one conditional writer advances the head

Metadata 提交必须在 Primary 上原子比较，而不是先 SELECT head，再无条件 UPDATE。可理解为 UPDATE files SET head=8 WHERE file_id=f1 AND head=7，只有影响一行才算成功；同一事务插入版本、挂接完整 manifest、消费已预留配额、写变更日志与 outbox，并把会话保护转成保留版本的引用。另一请求如果看到影响零行，不能忽略它继续返回成功；它必须得到冲突。

Compare atomically at Primary rather than SELECT head followed by an unconditional UPDATE. Conceptually update head to 8 only where file_id=f1 and head=7; one affected row means success. The same transaction inserts the version, complete manifest references, quota accounting, change log and outbox, and converts session pins into retained references. Zero affected rows must return a conflict, not success.

同一个请求的幂等键要与 file_id、父版本和 manifest 摘要绑定。提交成功而 ACK 丢失后，客户端重试应读到原结果，不再对 head=7 做第二次新提交然后被误报冲突。幂等键相同但内容不同要拒绝。内容寻址的 CAS 是 content-addressable storage；本节的 CAS 是 compare-and-swap。它们分别回答“字节存在哪里”和“谁能推进版本”，不能说加了 hash 去重就自动解决了并发覆盖。

Bind an idempotency key to file_id, parent and manifest digest. After a lost success ACK, retry returns the original result rather than rerunning a new parent=7 update and falsely reporting conflict. Reject the same key with different content. Content-addressable storage identifies bytes; compare-and-swap controls head advancement. Deduplication alone does not prevent lost updates.

为何保留两份：服务器不能替用户合并任意文件Why keep both: arbitrary files cannot be safely auto-merged

A 和 B 都离线编辑 v7。A 先成功得到 v8，B 的 parent=7 条件失败。若 HTTP 用强 ETag 的 If-Match 表达这个条件，RFC 9110 把它定义为防止 lost update 的前置条件；不匹配返回 412。[7] 业务 JSON 的版本条件也可返回明确定义的 409，但两种协议不能把状态码混为同一层。图统一用 If-Match 语义的 412，并沿 Primary → Metadata → Client B 返回失败。

A and B edit v7 offline. A creates v8 first; B’s parent=7 fails. Strong ETag If-Match conditions prevent lost updates in RFC 9110, with 412 on mismatch. [7] An application JSON version condition may define 409 instead, but do not conflate the layers. The diagram consistently uses If-Match-style 412 and returns it Primary → Metadata → Client B.

默认策略让 B 另存一个新 file_id=f99，名字显示冲突副本；原 f1 的 head 仍是 v8，f99 从自己的版本 1 开始。新文件在事务里申请目录名和配额，重试仍用幂等键，不能每次网络超时都多生成一份。保留两份让用户看见冲突，代价是目录更乱和额外逻辑配额。后写覆盖可以是明确的产品选择，但它会隐藏另一份编辑，不能宣传成安全合并，也不能按客户端墙上时钟决定顺序。

Default to a new file_id=f99 displayed as a conflict copy. f1 stays at v8 while f99 starts its own version 1. Allocate its name and quota transactionally and retry with idempotency so timeouts do not create endless copies. Keeping both exposes conflicts at the cost of clutter and quota. Last-write-wins is a possible explicit policy, but hides another edit and must not be called safe merging or ordered by client wall clocks.

故障窗口：删文件、改名和权限都参与比较Failure window: deletion, rename and ACL changes also race

离线设备回来时发现 head 已被删除，不能拿旧文件内容无条件重建原路径。删除是带版本的 tombstone，和修改一样写进变更日志；用户明确选择恢复才生成新的恢复操作。重命名和移动也要比较目录状态，目标名已占用则返回冲突。ACL 被撤销后，旧 upload_session 的存在不能代替当前提交权限；commit 重新鉴权，失败编辑留在客户端，不把它上传到已无权访问的目录。

An offline device must not recreate a deleted path unconditionally. Deletion is a versioned tombstone in the change log; restoration is an explicit new operation. Renames and moves compare directory state and handle occupied destinations. An old upload session cannot substitute for current commit permissions after ACL revocation. Reauthorize and retain rejected edits locally rather than publish to a revoked directory.

这里的“保留两份”只保证系统成功接收的两份内容分别有去处。还没上传的字节、设备硬盘损坏、超过历史保留期的版本，不会因为这个策略自动得到永久保护。客户端必须先本地持久化编辑再排上传；冲突提示让用户确认解决后才删候选副本。把“永不丢用户字节”改成有边界的保存语义，才有办法解释断电、过期和撤销权限时的行为。

Keeping both preserves edits that the system successfully accepts, not forever protection for unuploaded bytes, device disk loss or expired history. Clients persist locally before scheduling upload, and remove a candidate only after conflict resolution is confirmed. Bounded save semantics let the design explain power loss, expiry and revoked access.

15.5 · 多端同步：通知可丢，变更日志不能丢15.5 · Sync: lossy hints, durable change history

正常路径：提交、释放通知、按游标补拉Normal path: commit, release hints, pull from a cursor

每次成功事务写一条单调推进的账号或租户内 change_seq，内容包括 file_id、版本、动作和可见目录变化。Relay 只读 Primary 已提交的 outbox，把 event 102 发给 Notifications；后者给设备一个“有变化”的信号。outbox 与版本行同事务，解决数据库成功、进程在发通知前崩溃的双写窗口。[8] Relay 发成功但没来得及标记，也会再发一次；设备必须容忍重复，不能把图中的橙虚线说成恰好一次。

Each committed transaction records a monotonically advancing account- or tenant-scoped change_seq with file, version, action and directory effects. Relay reads committed Primary outbox entries and sends event 102 to Notifications, which emits a hint. The outbox shares the version transaction, closing the database-success/process-crash gap. [8] A relay can resend after failing to record delivery, so orange arrows are not exactly once.

Client B 持久保存 cursor=101，醒来后请求 changes(after=101)，Metadata 读 Primary，再逐跳返回变更和授权 manifest。Google Drive 的公开接口也采用保存 page token 再拉 changes 的方式。[9] 本章的 change_seq 是教学协议，不声称等于某厂商 opaque token 的内部结构。列表分页要固定读取边界或明确终止游标，避免边翻页边发生新变更时漏项；不用“扫描目录 mtime”替代有删除记录的日志。

Client B persists cursor=101 and pulls changes after it. Metadata reads Primary and returns authorized changes and manifests. Google Drive publicly uses stored page tokens to retrieve changes. [9] This chapter’s change_seq is a teaching protocol, not a claim about opaque token internals. Pagination needs a fixed boundary or explicit ending cursor to avoid missed concurrent updates; directory mtime scans cannot replace a log with deletions.

为什么拉缺块：在线通知与持久状态分工Why pull missing bytes: hints and durable state differ

拿到 v8 的 [hA,hD,hC] 后，本地如果已经验证 hA、hC，只下载 hD。块下载可以并行，但临时文件要按 manifest 的索引和长度重组，核验完成后原子替换目标文件。对同一个 file_id 的应用串行处理；已应用 v8 的设备遇到重复 v7 不回滚。压缩多次连续保存可以直接应用最新 head，但不能跳过删除、权限变更和会改变本地路径的目录动作。

With v8’s [hA,hD,hC] and verified local hA and hC, download only hD. Parallel block fetches still reconstruct by manifest order and length, then atomically replace after validation. Serialize application per file_id and never roll v8 back to duplicate v7. Coalescing saves may fetch the latest head, but must preserve deletion, permission and path-changing actions.

游标推进需要区分“已收到”和“已应用”。最简单的教学方案在本地文件替换和本地数据库记录持久化之后才推进 applied_cursor；并发下载时用持久待办队列记录已收到事件，只有所有较早事件都完成才推进连续水位。若先把 102 写成完成，再下载 hD，下载失败或设备断电后可能再也不拉这条事件。恢复时扫描临时文件与待办，允许同一版本重复应用并校验，不能只信内存进度。

Distinguish received from applied cursors. The simple design advances applied_cursor after file replacement and local database persistence. Concurrent downloads use durable pending work and advance a contiguous watermark only after earlier entries finish. Marking 102 complete before fetching hD can skip it after failure or power loss. Recovery reconciles temporary files and pending work and tolerates verified repeated application.

故障窗口：离线很久、权限撤销、对象取不到Failure window: long offline periods, ACL revocation, missing objects

通知可以用长轮询或 WebSocket，它没有权威状态。Google Drive 的 changes 通知用响应头表达变化，不带文件内容，仍要另读变更集合。[10] 本章允许通知丢失，不把它作为正确性的唯一依赖。 在线设备周期性补拉，重连先从持久游标走，不等下一条通知。日志过期时服务端明确返回需要重建快照；客户端保留本地未提交编辑，先拿一致目录快照及其结束游标，再补拉之后的变更，不能直接跳到“当前 cursor”而漏掉中间删除。

Use long polling or WebSocket for hints, not authority. Google Drive changes notifications carry state in headers without file contents; clients still retrieve changes separately. [10] This design tolerates lost hints instead of making correctness depend on delivery. Devices pull periodically and resume from durable cursors on reconnect. Expired logs require an explicit snapshot rebuild: retain unsent local edits, obtain a consistent directory snapshot plus its ending cursor, then replay later changes. Jumping to the current cursor can miss deletions.

下载授权必须在读 manifest 和签 URL 时重新检查。签名 URL 是短期 bearer capability，知道块 hash 不给权限；撤销 ACL 后不再续发，但已经签出的地址可能在过期前仍能使用。若产品要求立即撤销，需要在线下载授权层或等效的存储策略，代价是每次读取多一跳。TLS、静态加密仍是默认；端到端加密会改变摘要计算、服务端校验、搜索和共享密钥的边界，应作为单独需求重新设计。

Recheck permissions when reading manifests and signing URLs. Signed URLs are short-lived bearer capabilities; hashes grant no rights. Revocation stops new grants, but existing ones may work until expiry. Immediate revocation needs an online authorization layer or equivalent policy, adding a read hop. TLS and at-rest encryption are default; end-to-end encryption changes digests, validation, search and key sharing and deserves separate design.

15.6 · 回收：共享字节不能跟着单个文件直接删15.6 · Reclamation: shared bytes outlive individual files

正常路径：先删目录引用，再证明块无人使用Normal path: remove references, then prove blocks unreachable

删文件先提交 tombstone，让其他设备能补拉到“文件被删了”。当前版本与历史版本的保留规则独立：移到回收站仍可恢复，历史保留期内的 manifest 仍是回收根。GC 从 Primary 取 live heads、保留版本、冲突副本和活跃会话，把这些 manifest 的所有块标为保护。不可变块曾被 v7 引用，不意味着删了 v7 就可删；v8 的 hA、hC 还在图中共享。

Deletion first commits a tombstone so other devices learn it. Trash and history retention are separate policies, and retained manifests remain roots. GC marks blocks reachable from live heads, retained versions, conflict copies and active sessions in Primary. A v7 reference does not make a block exclusive to v7: v8 still shares hA and hC.

宽限期设为教学假设 48 小时，让失败提交和短暂离线重试有机会重新对账；但它不提供并发安全。GC 在某个时刻看到零引用后，新会话可能开始复用同一个旧 hash。如果直接异步 DELETE，就可能删掉刚刚成功发布的字节。保护租约必须参与提交和回收的判定，新上传能登记 pin，提交把 pin 转为版本引用；这些转换需要同一权威状态协调，而非三个服务各看一份缓存。

An assumed 48-hour grace allows recovery but is not concurrency safety. After GC observes zero references, a new upload can adopt the old hash; an uncoordinated DELETE may remove newly published bytes. Lease pins participate in commit and reclamation. Uploads acquire pins and commit converts them to version references under one coordinated authority, not independent cached views.

取舍：简单栅栏先保证安全，再优化暂停范围Trade-off: fence first, optimize pause scope later

图选容易解释的 epoch 栅栏：mark 阶段收集根，最终核验和 sweep 时短暂阻止受影响租户的新版本发布；等待已经进入提交的操作结束，再核候选块无人引用且无活跃租约，最后删除。正在上传的字节可继续进入 staging，但不能越过发布栅栏。如果扫描很久，不把整段 mark 都放进暂停窗口，先扫再在短窗口核候选；更复杂的分段栅栏和 epoch 屏障能减小暂停面，但不能省掉与并发提交的协调。

The diagram chooses a simple epoch fence: mark roots, briefly block publication for affected tenants during final validation and sweep, wait for in-flight commits, recheck candidates and leases, then delete. Uploads may continue into staging but cannot cross the fence. Keep long marking outside the pause; validate candidates in a short final window. Finer fences reduce scope but cannot remove coordination with commits.

故障窗口：回收失败花空间，回收误判丢内容Failure window: failed GC spends space, incorrect GC loses content

Object store 删除失败，候选保留删除状态并安全重试；同 key 的未来重建必须有明确代际或排他保护，避免延迟到达的旧 DELETE 删除新对象。GC 进程崩溃后按持久 epoch 状态恢复，发布栅栏只能在确认仍不会有在途删除伤到新提交时释放。保证不了这些边界时先保留候选，空间账单会增加，但系统不会把仍有效的 manifest 指向已删除字节。

Failed deletion is durably tracked and retried. Recreating the same key needs generations or exclusive protection against a delayed old DELETE. Recover GC from persisted epoch state and release publication fencing only after ensuring in-flight deletion cannot harm new commits. If these boundaries cannot be established, retain candidates and spend space instead of leaving valid manifests pointing at deleted bytes.

版本占用也要用唯一块重算。图中三块 12 MiB，加一次中间等长改动只多 4 MiB，总共 16 MiB；若随后每次把三块全部改掉，十个版本就是 10 × 12 = 120 MiB，不会因为 COW 自动变成接近一份。版本保留策略要同时约束时间与份数，配额按产品语义定义历史是否计费；不能把“30 天历史”说成存储成本有固定 30 倍或固定 1 倍。

Count unique blocks for versions. The diagram starts at 12 MiB and adds 4 MiB, totaling 16 MiB. If every later edit changes all three blocks, ten versions consume 10 ×12 =120 MiB despite COW. Bound retention by age and count and define history quota semantics; thirty-day history does not imply a fixed 30× or 1× cost.

追问与翻车点：把限制说成可验证的行为Follow-ups and failure-prone answers

“为什么不一开始做跨地域双活？”先问单地域故障时的恢复目标；元数据强一致 head 若跨洋同步，会增加写延迟，异步复制则故障切换可能丢最近提交。字节多地域复制不自动解决目录竞争，两个地域都接同一 file_id 写入需要额外仲裁或冲突语义。把恢复目标和允许丢多少时间内的提交写清，再讨论扩展；本章逻辑 Primary 没有承诺跨地域零丢失。

For multi-region active-active, establish recovery targets first. Synchronous metadata heads add intercontinental latency; asynchronous replication can lose recent commits on failover. Replicating bytes does not resolve directory races; concurrent regional writers need arbitration or conflict semantics. State the tolerated loss window before extending the design. This chapter’s logical Primary does not promise zero-loss regional failover.

“分享热门文件怎么办？”下载仍走授权的对象路径，可以按不可变块或文件导出物加缓存，但私有内容要把权限和短期地址的生命周期算进去。用户私有同步通常不是公开视频播放模型，不能无条件把所有对象放进共享 CDN。对象存储热点、单租户查缺风暴、巨型目录和同一文件的竞争分别扩展；别让 231 次文件保存这个平均数掩盖某一热文件的局部瓶颈。

For popular shared files, downloads stay on authorized object paths; cache immutable blocks or exports with permission and grant lifetime semantics. Private sync is not automatically public video distribution. Scale storage hot spots, tenant lookup storms, huge directories and contention on one file separately. The average of 231 file saves/s can hide a local hot-file bottleneck.

“空间紧了能不能马上缩历史？”先把保留策略改成一次元数据事务并产生可补拉变更，再让 GC 按新根集合回收；不能直接按对象年龄删。用户正在查看旧版时可以持有短期读取租约，租约保护边界要和下载授权一致。版本、配额、回收站、冲突副本各自对用户可见，后台省空间不应让已经显示可恢复的旧版突然成为损坏文件。

When shortening history, first transactionally change retention metadata and expose relevant changes, then reclaim from the new roots; do not delete by object age. A historical reader may hold a short read lease aligned with download authorization. History, quota, trash and conflict copies are user-visible contracts; background space savings must not silently corrupt versions advertised as recoverable.

先定纯文件范围，再把 2,000 万文件/天、约 1.5 万峰值块 PUT/s 和约 463 Gb/s 入站分开算。Metadata 负责权限、目录、head 和事务；Block svc 负责查缺、授权、核验；Client 直传不可变 Object store。v7 到 v8 共享 hA、hC，只有等长局部改动才保证只多 hD。ACK 丢失先问服务器状态，全部块 verified 且 pinned 才提交。两个 parent=7 只有一个推进 head，失败编辑另存冲突副本。

Scope to files, then separately size 20M files/day, ≈15K peak block PUTs/s and ≈463 Gb/s inbound. Metadata owns permissions, directory, head and transactions; Block svc owns lookup, grants and validation; Client uploads immutable bytes directly. v7 and v8 share hA and hC; only the stated same-length local edit adds just hD. After lost ACKs, query authoritative state; commit only verified pinned blocks. One parent=7 writer advances head, and the other saves a conflict copy.

发布事务写 change log 和 outbox，Relay 发可重复的通知，其他设备按游标取权威 manifest，只下载缺块，校验和本地替换后才推进已应用进度。删除先变成 tombstone，GC 保护当前版、历史、冲突副本和会话，栅栏核验后才删无引用块。六组完整图各用一分钟口述，尤其练“对象已经存好但版本未发布”与“版本已发布但另一端未应用”的差别。下一题 Ch16 评论系统换成讨论树、计数和热点；这章的事务与幂等边界仍能复用。

Commit writes the change log and outbox; Relay emits repeatable hints. Devices pull authoritative manifests by cursor, fetch missing blocks, verify and replace locally before advancing applied progress. Delete with tombstones; GC protects current versions, history, conflict copies and sessions before fenced deletion.
