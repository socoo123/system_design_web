30 秒开场：先确认点播与可播放的定义The 30-second open: VOD and the meaning of playable

我设计 UGC 点播：先确认长视频、设备兼容与私有播放要求。按五百万日活，每天五十万次上传、两千五百万次观看估算。API 分配视频和签发能力，源文件直传；转码异步生成对齐的阶梯，校验分片后发布版本指针。播放器经 CDN 拉清单和分片，用吞吐与缓冲选档。接着算源站 miss 的容量，以及热片加 AV1 是否回本。

I’ll design UGC VOD, first checking duration, devices and private-playback requirements. At 5M DAU I estimate 500K uploads and 25M views daily. API allocates videos and signs capabilities; source bytes upload directly. Async workers build aligned rungs and publish a version pointer after output validation. Players fetch CDN manifests and segments, choosing rungs by throughput and buffer. Then I size origin misses and test AV1 payback for hot titles.

澄清六件事就能继续：点播还是直播、平均时长与源大小、上传与观看频次、需要的分辨率与设备、允许多久才可播放、是否付费或私有。回答改变组件：点播能预计算全片；直播必须边产生边发布；私有内容需要 CDN 每次请求验权。本章选择单地域控制面与全球 CDN，源上传、转码、播放是主线，评论和搜索作为已有业务接口。

Six questions determine the design: VOD/live, duration and source size, upload/view frequency, resolutions/devices, acceptable processing delay, and paid/private access. VOD can precompute a title, live publishes while producing it, and private media requires authorization at CDN requests. This chapter uses a single-region control plane and a global CDN, with existing product APIs for comments and search.

一条视频有三个不同承诺。上传成功只表示源文件完整存在；低档已可播表示最小阶梯通过检查；全档完成表示当前配方要求的产物齐全。用户看到“处理中”不是上传失败。把 READY 定义为可获取清单、初始化信息和清单引用的所有必需分片，才有办法判断部分转码失败能否先开播。

An upload receipt means the complete source exists. Base-playable means the minimum ladder passed validation. Full-ready means every required output for the recipe is complete. Processing is distinct from upload failure. READY requires a reachable manifest, initialization data and every required referenced segment, so partial transcoding failure has an explicit publication contract.

先用约五分钟确认范围与数量级，十分钟走上传和可播放版本，再用十五分钟讲阶梯、ABR 和回源，最后检查故障与成本。本章阅读约四十分钟；面试时每组最后一帧能在一分钟内口述。直播扩展只说明滑动清单、部分分片和端到端延迟预算；CMAF 本身不保证固定几秒延迟。

Use about five minutes for scope and scale, ten for upload/publication, fifteen for ladder, ABR and origin, then review failures and cost. Reading takes about forty minutes; each final frame should be explainable in a minute. The live extension names sliding manifests, partial segments and an end-to-end latency budget; CMAF alone guarantees no fixed delay.

这个 GET 数还是下界模型。音视频分开下载时每个时间片可能不止一次请求；拖动、预取、重试与清单拉取继续加量。字节也要量实际发送，而不是只看视频标称码率。进度条来回拖动会下载重复区间，自动预加载会给未观看内容付钱，低平均码率不保证出口账单按同样比例下降。

This GET estimate is a simplified lower-bound model. Separate audio/video tracks, seeking, prefetch, retries and manifest fetches add requests. Bill actual delivered bytes rather than nominal video bitrate: repeated seeks download ranges again, and prefetch pays for unwatched content. A lower nominal rate does not ensure equal billing reductions.

14.1 · 直传上传：控制面如何确认字节真的到了14.1 · Direct upload: confirm that the bytes really arrived

正常路径从 POST /videos 开始。Video API 验证账户和配额，在 Metadata 建立 video_id、owner、上传 attempt、服务端分配的 source_key 和 UPLOADING，再签发只允许该 key 的 PUT/上传分块能力。本章明确选择启用并保持对象版本化，complete 时固定物理 versionId。客户端直传 Source object 后，用 POST /videos/{id}/complete 交回收据；API 按 (bucket,key,versionId) 验证对象归属、完整大小和校验结果，再 CAS 将该上传 attempt 的 source_version 绑定到这个物理版本并提交 UPLOADED，重复 complete 只能复用同一绑定。绿色响应逐跳回到调用方。[1][10]

The path starts at POST /videos. Video API checks ownership/quota and persists video_id, owner, upload attempt, a server-assigned source_key, and UPLOADING, then issues object-scoped PUT/part capabilities. This design explicitly keeps object versioning enabled and pins a physical versionId at complete. After direct upload, Client submits a receipt through POST /videos/{id}/complete. API verifies ownership, complete size, and checksum at (bucket,key,versionId), then CAS-binds that attempt’s logical source_version to the physical version and commits UPLOADED. Repeated complete must reuse that binding. Replies return hop by hop. [1][10]

为什么让字节绕开 API：500K ×300 MB =150 TB/天，平均150×1012÷86,400 ≈1.736 GB/s =13.89 Gb/s，峰值69.44 Gb/s。签发只有峰值约29次/s。把大文件经 API 转发，会让部署、内存缓冲和上传失败与业务小请求一起争资源。替代的代理上传适合必须同步审查字节的约束，但要单独规划流式代理容量，不能沿用签发 QPS 来估实例。

Direct upload follows from 150 TB/day: 150×1012/86,400 ≈1.736 GB/s =13.89 Gb/s average, or 69.44 Gb/s peak, versus about 29 issuance requests/s. Proxying large files couples buffering, deploys and upload failures to small business calls. A streaming proxy can meet synchronous inspection requirements, but needs its own byte capacity rather than issuance QPS sizing.

上传 multipart 与播放分片必须分开讲。存储分块是任意连续字节区间，完成时按 part number 拼回一个对象；不要求每块能独立解码。[2] 播放分片要能从适当随机访问点开始解码，转码器负责对齐。源文件上传中断只需重传缺块，不要因为块中间出现预测帧就重传前一组视频画面。具体续传协议留到 Ch15，这里只确认完整对象后才调度。

Multipart upload and playback segments solve different problems. Upload parts are contiguous byte ranges, concatenated by part number on completion; each part need not decode independently. [2] Transcoders align playback random-access points. An interrupted source upload retransmits missing parts, not earlier pictures because a part contains predicted frames. Ch15 covers the full resumable protocol; scheduling waits for the completed object.

故障窗口在“存储已经完整写入，客户端还没通知 API”。客户端通知、对象完成事件和 UPLOADING 扫描都只能触发对具体 versionId 的核实，事件不是权威。source_version 是逻辑业务版本，Metadata 的绑定记录还保存 bucket、key、物理 versionId、大小与校验值；调度消息引用这个绑定，转码 worker 的 HEAD/GET 始终指定 versionId，不能 GET 当前 key。[10] 预签名 PUT 可以在到期前重放，同 key 上传仍可能产生更晚的物理版本，[1] 但它不会改变已固定版本的字节；新源要新 attempt 与新逻辑版本，不能改掉正在执行的绑定。上传能力没有 DeleteObjectVersion、改 bucket 版本配置或任意 key 权限；服务也不在使用期间挂起版本化。非当前版本的生命周期清理必须排除受引用源，等相关任务、重试和保留策略解除引用后，清理器才按具体 versionId 删除。版本化不能防住有删版本权限的主体，权限与清理规则是这份不可变合同的一部分。

Client receipts, completion events, and UPLOADING reconciliation trigger verification of a specific versionId; events are hints. Logical source_version binds in Metadata to bucket, key, physical versionId, size, and checksum. Jobs reference that binding; every worker HEAD/GET specifies versionId rather than reading the current key. [10] A presigned PUT can be replayed before expiry and produce a newer physical version at the same key. [1] It cannot change the pinned version’s bytes. New sources require a new attempt and logical version. Upload capabilities cannot delete versions, change bucket versioning, or write arbitrary keys, and the service keeps versioning enabled. Noncurrent-version lifecycle deletion excludes referenced sources; cleanup deletes an exact versionId only after jobs, retries, and retention release their references. Versioning alone does not protect against authorized version deletion: permissions and cleanup are part of the immutability contract.

受限能力需要限定对象、方法和期限。A13 的十五分钟不是上传全部完成的承诺，大文件续传可以重新申请后续能力；过期、断线和完成确认分别处理。API 为“创建视频”接收客户端幂等键，重复请求返回原 video_id。半成品到期后要清理未完成 multipart，并释放配额，不能只删除 Metadata 行让孤儿块继续占钱。[1][2]

Restrict capability by object, method and expiry. A13’s fifteen minutes is not a promise to finish the whole upload; resumable clients can obtain further capabilities. Handle expiry, connection loss and completion separately. An idempotency key reuses video_id on repeated creation. Expired attempts clean up incomplete multipart data and release quota, rather than merely deleting Metadata and leaving billable orphan parts. [1][2]

14.2 · 可靠转码：任务完成和视频可播不是同一个提交14.2 · Reliable transcoding: task completion and publication are separate

UPLOADED 之后，对象完成事件把源版本交给 Jobs，Transcoder 读取源、执行配方并写 Origin。持久事件可以重复，不能假设一次到达就永远不会再来；S3 原文明确是至少一次投递，也不把通常几秒到达写成硬上限。[3] API 与转码解耦，上传连接不等待整片完成，播放器读取的是 Metadata 上已经发布的版本。

After UPLOADED, completion events enqueue source-version jobs. Transcoder reads the source, runs the recipe and writes Origin. Durable events can repeat: S3 explicitly describes at-least-once delivery and no hard seconds-level guarantee. [3] Upload requests do not wait for transcoding; players use the version already published in Metadata.

一次任务的幂等身份是 (video_id, source_version, recipe_version)；source_version 指向上文固定的物理 versionId，单次执行另有 attempt。产物写入确定的版本路径；并发重放必须复用等价产物或在独立临时前缀产出，再由一个发布者选中完整结果。只拿 video_id 去重会阻止新源重转，只拿消息 id 去重又挡不住同一视频被不同消息重复调度。

Job identity is (video_id, source_version, recipe_version); source_version resolves to the pinned physical versionId above, and each execution has its own attempt. Use deterministic versioned paths with equivalent-output reuse, or isolated temporary prefixes and one publication winner. Deduplicating only by video_id prevents re-encoding a new source; deduplicating only message ids misses separate messages for identical work.

发布顺序是不可倒的：分片写完并确认，校验时长、段数、解码与引用，最后生成完整清单；再 CAS 把 Metadata 的 ready_version 指到它；最后 ack Jobs。跨对象存储和数据库没有一个总事务。把清单与产物放在不可变版本里，让小指针成为可播放提交点，读者才能永远看到一套完整文件，而不是半套新分片加半套旧清单。

Publication order is segments and acknowledgements, duration/count/decode/reference validation, final manifest, CAS of Metadata’s ready_version, then Jobs ack. There is no transaction spanning storage and database. Immutable output versions make the small pointer the publication commit, so readers get a complete generation rather than mixed old and new files.

三个崩溃点逐个看。写了一半就死，指针未变，临时产物稍后清理；全部写完但 CAS 前死，重试校验同一版本再提交；CAS 后 ack 前死，重试发现相同 ready_version 就确认成功。旧配方迟到时 CAS 还要比较期望的源版本与配方，不能让更旧的 attempt 把新版本覆盖掉。租约和 attempt fencing 要相配，任务被重新领取之后，旧执行者失去发布权。

Three crash windows have explicit outcomes. Partial outputs leave the pointer unchanged and are cleaned later. Complete outputs before CAS can be revalidated and published. A crash after CAS but before ack rechecks the identical ready_version and succeeds. CAS also checks expected source/recipe versions; lease expiry and attempt fencing prevent a stale worker from publishing over newer work.

对象完成、业务行更新和入队之间仍会漏一条任务。可用“更新业务行并写 outbox”把调度意图留在同一事务里，由 relay 投给 Jobs；本图采用对象事件加补漏扫描，不把 API 直接双写队列当可靠保证。每分钟检查 UPLOADED 但无运行或完成任务的记录，重新投同一幂等 key；一分钟只是补漏周期，队列积压与执行时间还要另外加。

Scheduling can still be lost between object completion, database update and enqueue. An outbox transaction can persist intent for a relay; this diagram uses completion events plus reconciliation rather than treating direct API dual writes as reliable. Scan UPLOADED records without active/completed work every minute and resend the same key. That scan interval excludes backlog and execution latency.

暂时网络错误最多三次 attempt，并用退避与抖动；源损坏、格式不支持等确定失败提前终止，写可解释的错误。耗尽任务进 Dead letters，检查源或配方后重投。worker 不在 ack 后继续“顺便补分片”；一旦确认，系统就失去了可靠重试那部分工作的责任。低档先成功可以发布 BASE_READY，全阶梯后来升级为 READY，清单只列已验证可用档。

Retry transient faults within three attempts using backoff and jitter; deterministic corrupt/unsupported input terminates early with an actionable error. Exhausted jobs go to Dead letters and return after review. Workers must not acknowledge and then finish required segments afterward. Validated low rungs can publish BASE_READY, later upgraded to full READY; manifests list only validated available rungs.

容量不能由上传 QPS 直接换成少量 worker。A10 全阶梯合计十 worker-min/片，平均占用500K ×10÷1,440 ≈3,472个槽位；按70%使用率，3,472÷0.7向上约4,961个槽位。这是聚合计算量，平行出三档不会把它除以三。五倍峰值要么准备更多计算，要么承认队列会排队；先保障低档和新上传，补高档与 AV1 可以降优先级。

At ten aggregate worker-minutes per ladder, average occupied slots are 500K ×10/1,440 ≈3,472. At 70% planned utilization, round up to about 4,961 slots. Parallel rungs do not divide aggregate work by three. A 5× peak needs more compute or explicit queuing; prioritize base rungs and new uploads while deferring high-rung/AV1 work.

故障监控要看最老任务年龄、等待时长和源文件到首个可播版本的延迟，而不只看队列条数。相同的一千条任务，十秒短片和十分钟高复杂度源需要的计算差很大。按预计剩余 worker-seconds 分队列更接近负载；扩 worker 之前还要检查 Origin 写入和源读取是否限速，不能用更多消费者把存储同时打到过载。

Monitor oldest-job age, waiting time and source-to-first-playable latency, not only queue length. A thousand short clips differ greatly from a thousand complex ten-minute sources. Estimated remaining worker-seconds better describe load. Before scaling consumers, check source-read and Origin-write capacity so extra workers do not overload storage.

14.3 · 阶梯从源并行长出：对齐边界才可以换档14.3 · Parallel source-derived rungs: align boundaries for switching

图里三个 encode 都从 Transcoder 分发的同一源版本来，各自写 Origin；360p、720p、1080p 是选择，不是转码流水级。重新放大低分辨率产物不会恢复源细节，还可能再引入损失。实际可以共享解码或中间帧来减少重复计算，但隔离任务时每档重试要确定地引用同一源，不能“从上一档随手取个文件”。

All three encoders derive from the same source version and write Origin independently. Rungs are alternatives, not serial processing stages. Enlarging a low rung cannot restore source detail and can add loss. Shared decode/intermediate frames may save compute, but isolated retries still bind to the same source rather than arbitrary lower-rung files.

每档大小用“码率 ×时长 ÷8”算。十分钟低档0.8×600÷8 =60 MB，中档2×600÷8 =150 MB，高档4×600÷8 =300 MB，合计510 MB。三档总码率6.8 Mb/s并不是播放器同时接收的速率：播放器在每个时间段选择一档。输出写入按全部档相加，播放出口按实际所选档积分，这是两个不同的容量。

Rung bytes are bitrate ×duration /8: 60 MB, 150 MB and 300 MB for ten minutes, totaling 510 MB. The summed 6.8 Mb/s is not received simultaneously by the player, which selects one rung for each interval. Output storage sums rungs; playback egress integrates selected-rung bytes.

原始新增150 TB/天，全阶梯产物500K ×510 MB =255 TB/天，两者405 TB/天。恒定新增且都留365天：源54.75 PB，产物93.075 PB，合计147.825 PB逻辑量。没有把内部冗余、备份、字幕、缩略图和日志算进去。说“转三档就存储乘三”会把实际码率预算抹掉；说“缓存命中高所以源不用留”又把可淘汰副本当成权威存储。

Sources add 150 TB/day and ladders 255 TB/day, totaling 405 TB/day. With constant growth and 365-day retention, logical bytes are 54.75 PB of sources plus 93.075 PB of outputs =147.825 PB. Internal redundancy, backups, subtitles, thumbnails and logs are extra. Rung count alone cannot determine bytes, and evictable CDN copies do not replace authority.

四秒切段是本章策略，不是 HLS 强制值。编码时把各档可独立解码的随机访问点放到一致的时间边界，尽量使用闭合 GOP、避免依赖上一分片的画面。播放器从720p第n片切到360p第n+1片时，音视频时间戳要连续；RFC 的 INDEPENDENT-SEGMENTS 描述不依赖其他分片的数据，Apple 规范另外要求各视频档分片边界对齐。[4][5]

Four seconds is our policy, not an HLS requirement. Align independently decodable random-access points across rungs, using closed GOPs and avoiding prior-segment dependencies. Switching from 720p segment n to 360p n+1 requires a continuous audio/video timeline. RFC INDEPENDENT-SEGMENTS describes independence from other segments; Apple separately requires aligned video boundaries. [4][5]

HLS 的 multivariant playlist 给出可选流，media playlist 再列具体片；DASH 的 MPD 描述相应表示与段。编码格式、封装和交付协议是三个维度：AV1 不等于 DASH，H.264 不等于 HLS。满足共同编码、时间线、封装及加密约束时，CMAF 媒体可以被两套清单引用。[6] 有些 DRM 或设备要求不同，仍会留下不同产物，不能承诺任何 HLS/DASH 都只占一份。

HLS multivariant playlists identify alternatives and media playlists list segments; DASH MPDs describe representations and segments. Codec, container and delivery protocol are separate dimensions. Compatible codec, timeline, packaging and encryption constraints allow HLS and DASH to share CMAF media. [6] Device/DRM differences may still require distinct outputs; sharing is conditional.

固定阶梯适合先跑通流程，但分辨率不自动决定最佳码率。低运动片和复杂动作片用同一个配方，会分别浪费字节和牺牲画质。Netflix 的 per-title 原文按内容复杂度优化配方，[7] 本章沿用这个机制，未拿其某次实验当本系统节省常数。做复杂度采样、保留真正有收益的档，是用额外分析计算换输出和出口减少；低分辨率源也不应盲目上采样到1080p。

A fixed ladder is a starting point, not an optimal bitrate for every title. One recipe wastes bytes on simple content and loses quality on complex motion. Netflix per-title encoding adapts recipes to content complexity. [7] We borrow the mechanism, not a universal experimental saving. Analysis adds compute to reduce output/egress; low-resolution sources should not be blindly enlarged to 1080p.

长尾变体另算：80% 冷片只出60+150=210 MB，20% 热片出510 MB，平均0.8×210+0.2×510=270 MB/片；日产物135 TB，比全三档255 TB少120 TB。代价是冷片第一次需要高档时还没有它，所以先用可用档开播，后台补齐。这个比例是教学假设；不能把省掉的高档同时许诺成“任何新片都立即1080p可播”。

In the separate long-tail variant, 80% at 210 MB and 20% at 510 MB average 270 MB/title: 135 TB/day, saving 120 TB against 255 TB. A cold title’s first high-rung request cannot instantly get a missing encode; serve available media while producing it asynchronously. The mix is an assumption, incompatible with immediate 1080p for every upload.

14.4 · ABR：按下一片的下载时间保护缓冲14.4 · ABR: protect the buffer using the next download time

正常播放先通过 Video API 取得已发布 manifest_version 与播放能力，随后媒体字节只走 Client → CDN；miss 的回程是 Origin → CDN → Client。HLS 通常先取 multivariant、再取选中档的 media playlist，之后才按清单拉初始化与媒体片。[4] 视频 API 可以继续提供标题和播放进度，但不在每片字节路径上。图省略了这次小 JSON 控制请求，保留完整媒体闭环。

Playback first obtains published manifest_version and a capability from Video API; media then follows Client → CDN, with misses returning Origin → CDN → Client. HLS generally fetches multivariant and selected media playlists before initialization/media data. [4] Video API serves titles/progress outside the media path. This deck omits that small control call while keeping the complete media loop.

播放器需要两个观测：最近分片实际吞吐，以及缓冲里剩余可播秒数。仅把测速最大值当可用带宽，会被突发抖动骗到高档；只看缓冲很满，又会在持续弱网里迟迟不降级。本章用吞吐估计×0.8作为简单余量策略，配合缓冲下降提前降档。实际 ABR 还要平滑估计、升档滞后和设备解码能力，避免每片都在两档之间来回跳。

Observe recent segment throughput and remaining playable buffer. A peak speed sample overestimates sustained capacity; a full buffer alone can delay downgrades on lasting weak networks. Our example chooses 0.8× estimated throughput with buffer-aware downgrade. Production ABR smooths estimates, delays upgrades and checks decode capability to avoid rung oscillation.

在16 Mb/s 链路上，1080p一片有4×4=16 Mb，下载16÷16=1 s，四秒媒体只用一秒拿到，净加三秒缓冲。链路跌到1 Mb/s后，仍选高档要16 s，八秒缓冲就不够了。若下一片立刻改360p，大小0.8×4=3.2 Mb，下载3.2 s，缓冲8−3.2+4=8.8 s。假定这八秒是发出低档请求那一刻的缓冲，公式没有声称已经等待十六秒后还能恢复到八点八秒。

At 16 Mb/s, a 1080p segment has 16 Mb and downloads in one second, gaining three seconds of buffer. At 1 Mb/s it takes sixteen seconds, exhausting an eight-second buffer. An immediate next 360p request takes 3.2 seconds and yields 8−3.2+4=8.8 seconds. The eight seconds is measured when that low-rung request starts, not after already waiting sixteen seconds.

正在下载的高档若发现无法赶上播放截止，可以取消并从同一时间边界重取低档，但已经发送的字节不会退款。保守重选要算剩余时间和额外请求往返，不能把上面的“下一片”推导原封不动用在半片取消上。播放器通常小步预取，拖动时丢掉不再需要的缓冲请求；预取过多虽降低首帧等待，却会给立刻退出的用户制造大量浪费。

A high-rung transfer that will miss its deadline can be cancelled and retried at the same boundary, but already sent bytes remain billable. Rescheduling includes remaining time and another request round trip; the next-segment calculation is not a partial-transfer cancellation model. Modest prefetch and cancellation on seeks limit waste, while aggressive prefetch spends bytes on early exits.

把分片从4 s改成2 s，同样十分钟观看变成300次媒体GET，平均请求约86,806/s，峰值约434,028/s；同总码率下观看字节不因此减半。更短分片让换档机会更频繁，但增加 HTTP、清单与编码关键帧开销。更长分片降低请求数，却让一次下载错误和高档误选占用更长时间。选长度时把这些代价说出来，而不是把“越小越快”写成唯一准则。

Two-second segments make 300 media GETs per ten-minute view: about 86,806/s average and 434,028/s peak. Viewer bytes at the same bitrate do not halve. Shorter segments offer more switching opportunities but add request, manifest and keyframe overhead; longer segments reduce requests while extending the damage of download failures or poor rung choices.

旧稿把 progressive 下载说成必须整文件等完、缓存一定差，这不准确。放好初始化信息的 MP4 可以边下边播，HTTP Range 也能缓存；它的主要限制是同一个表示里不容易按段切不同码率。只有一种码率、短小素材和简单播放器时，progressive 可以是有效替代。需要多档、可控换档和跨设备播放时，再为 HLS/DASH 的清单与打包成本付钱。

Progressive MP4 need not download the whole file before playback or always cache poorly. Correct initialization placement enables progressive start and HTTP Range can be cached. The main limitation is switching bitrate representations per interval. Short single-rate assets with simple players can use progressive delivery; multi-rung controlled switching justifies HLS/DASH packaging and manifests.

故障行为看播放器截止时间：单片超时可以有限重试或降档，不能一直重试耗尽缓冲。403 往往是播放能力过期，按控制面续期；404 若来自已发布清单，是产物或发布一致性故障，不能当成普通弱网。首帧、重缓冲和解码失败要由客户端上报，CDN 全部200也可能没人顺利播放。A15 把播放尝试成功率、首帧和卡顿分开定义，不能拿控制 API 可用率替代体验。

Failures follow playback deadlines: retry or downgrade within bounds rather than draining the buffer indefinitely. An expired capability can cause 403 and needs control-plane renewal. A published manifest’s 404 is an output/publication fault, not ordinary weak networking. Clients report startup, rebuffer and decode failures; CDN 200s alone do not prove playback. A15 separates attempt success, startup and stalls.

14.5 · CDN：命中省回源，出口仍然要付钱14.5 · CDN: hits save origin work while viewer bytes remain

先算两张账。观看出口25M×0.3 GB=7.5M GB/天，按A6每GB一美分，7.5M×$0.01=$75,000/天。提高命中率仍然要把这些字节从边缘送给用户。Origin费用则取决于未命中字节、跨区域与供应商计价；它可能还有每次请求费用。上述七万五只是一项教学算术，不能用来宣称任何平台的真实账单，也不足以证明全系统成本一定只由 CDN 决定。

Viewer egress is 25M×0.3 GB =7.5M GB/day, or $75,000/day at the assumed cent/GB. Higher hits still send these bytes to users. Origin charges depend on missed bytes, regional transfers and pricing, potentially with request charges. The $75K is one illustrative line item, not a real platform bill or proof that CDN dominates every system.

回源按有效字节命中率算，不能偷换成请求命中率。若大量小清单命中、大的高码率片没命中，请求95%命中不等于字节95%。基础模型把 CDN 与 Shield 合并后的字节命中设95%，先忽略并发合并收益；于是平均回源7.5 PB×5%=375 TB/天，约34.72 Gb/s，峰值约173.61 Gb/s。这个上界已超过100 Gb/s，说明默认参数本身需要进一步措施。

Use effective byte hits, not request hits: cached small manifests and missed large segments can yield very different rates. At 95% combined CDN/Shield byte hits, ignoring concurrent-collapse savings, origin sees 375 TB/day, about 34.72 Gb/s average and 173.61 Gb/s peak. This upper bound already violates the 100 Gb/s assumption and requires another decision.

解法可以扩大源站，也可以把有效未命中比例压到100÷3,472.22≈2.88%，即字节命中至少97.12%。Shield 是共享回源缓存，把许多边缘 miss 汇在一层，厂商原文说明它可以让同一对象从源站取一次供各边缘使用。[8] 1,000个同 key并发请求合成一个回源，是同一 Shield、同一对象和重叠时间窗的算例；1,000个不同片不会神奇合并。

Either increase origin capacity or reduce effective misses to 100/3,472.22 ≈2.88%, requiring at least 97.12% byte hits. Shield shares origin-facing caching across edges. [8] Collapsing 1,000 concurrent same-key requests to one fetch assumes one Shield, one object and an overlapping window; different segments cannot collapse together.

先保住已命中的绿线。Origin 超过预算时限制回源并发与字节速率，对不能服务的 miss 给有界错误；失败依次 Origin → Shield → CDN → Client，播放器再决定是否降档或有限重试。新版本的片不能拿上一版本不同时间戳的片替换。允许复用的只是同一不可变对象的已缓存副本；Origin坏了不会让所有命中都必须失败，也不会让每个 miss 直接绕到公开源。

Keep serving cache hits. Cap origin-facing concurrency and byte rate, returning bounded errors for unserviceable misses. Failure returns Origin → Shield → CDN → Client, where the player can downgrade or retry within its deadline. Do not substitute differently timed segments from an older generation. Immutable cached copies survive origin loss, without public-origin bypass for every miss.

缓存 key至少包含video、manifest/source版本、codec、rung、segment序号；否则两个档或两次重转会碰在同一个地址上。版本化分片可长缓存，发布后的 VOD 清单也能按不可变版本缓存；“当前哪个版本可播”的小指针与私有鉴权另有短期限。尽量让许多用户共享同一媒体 key，个性化广告、不同音轨或真正不同的字节必须继续区分，不能为了提高命中混掉内容。

Cache identity includes video/generation, codec, rung and segment index so encodes do not collide. Versioned VOD segments and manifests can be cached as immutable objects; current-version pointers and authorization have separate lifetimes. Share keys for identical media, retaining distinctions for personalized ads, tracks and genuinely different bytes.

私有播放先验权再查共享缓存。短寿命 signed cookie可以授权某视频的一组片，[9] CDN 每次都验证签名、期限和资源范围，即使命中也不跳过。授权凭据不必成为媒体缓存身份，但缓存键必须仍隔开不同内容；不能简单删除 query string就声称安全。Origin只接受受控 CDN/worker访问，播放能力失效时返回403，而不是把私有原始桶地址给播放器。

Authorize private playback before shared-cache lookup. A short-lived signed cookie can cover a video’s segment set; CDN checks signature, expiry and resource scope even on hits. [9] Authorization need not fragment identical media cache identities, but distinct content must remain separated. Do not merely strip query strings and call it safe. Origin accepts controlled CDN/worker access; invalid capabilities fail rather than exposing a public bucket.

缓存热片是按需填充和保留，不是上传一完成就把全片主动推到全球。预热前几个高播放区域的首片能减少启动 miss，但长尾全量预热会复制永远没人看的字节。区域热度和各档访问分布要分别量，某地常用720p不代表那里需要全部1080p。冷片仍经 CDN 的 miss 路径回源，播放器保持同一域名、验权和故障预算；“冷片回源”不等于客户端直连 Origin。

Populate and retain hot media on demand rather than pushing every title worldwide after upload. Regional startup-segment prewarming can reduce cold starts, while full long-tail prewarming copies unwatched bytes. Measure heat by region and rung. Cold titles still use the same authenticated CDN miss path; origin retrieval does not mean client-to-Origin bypass.

14.6 · AV1：先算回本，再决定给哪条片加一套14.6 · AV1: compute payback before adding a codec ladder

H.264兼容阶梯作为基础，AV1给实测支持的设备和有足够未来观看的片。Netflix 在2021年的工程原文已经讨论 TV 能力验证、按需求排编码优先级与体验监控，[10] 所以这不是等到某个年份突然必须全量迁移的选择。编码端可以用 CPU软件实现或硬件加速，GPU不是 AV1 的定义；要同时测编码成本、吞吐、画质与播放端功耗。

Keep a H.264 compatibility ladder and add AV1 for tested devices and sufficient future demand. Netflix’s 2021 engineering report already covers TV capability validation, demand-prioritized encoding and experience monitoring. [10] Adoption is not a calendar-triggered full migration. CPU software and hardware acceleration are options; GPU is no definition of AV1. Measure encode cost, throughput, quality and playback power.

先控制比较条件：同一源、同画质目标、同样观看时长，记录实际送出的字节。不同内容、encoder preset、码率上限和设备，会改变节省；“AV1永远比HEVC省30%”不是可复用事实。本章25%是A12的测量结果假设，不冒充 Netflix 或某硬件的数字。低码率让用户更久停在高档时，平均交付字节可能与离线测试不同，最终要看线上ABR行为。

Compare the same source, quality target and watch duration, then measure delivered bytes. Content, preset, rate caps and devices change savings; a universal 30% advantage over HEVC is unjustified. Our 25% is an A12 measurement assumption, not a Netflix/hardware result. Better efficiency can keep players at higher quality, so online ABR may differ from offline bitrate comparisons.

A12 每次合格观看节省0.3 GB×25%=0.075 GB，按$0.01/GB是$0.00075。把额外编码、分析、存储和运营分摊到同一90天窗口，假设$6/片，阈值$6÷$0.00075=8,000次未来合格观看。若实际只观看一半且每次只省0.0375 GB，收益减半，阈值翻到16,000。公式是增量成本÷每次节省，不要用历史总播放次数抵未来编码成本。

Each eligible view saves 0.075 GB, or $0.00075 at the assumed price. At a $6 incremental encoding/analysis/storage/operations cost in the same 90-day window, break-even is 8,000 future eligible views. If half-length viewing saves only 0.0375 GB, the threshold doubles to 16,000. Use future incremental savings, not historical views.

“热门”还要扣能力分布。若一个片预计90天内20,000次观看、只有30%可走 AV1，合格观看6,000次，省6,000×$0.00075=$4.50，仍小于$6，应暂缓；30%只是这一追问的变体输入。Title demand 汇总区域与设备预测交给 Codec policy，后者排队生成额外档，发布成功之前播放继续用H.264。别把这一判定放到每个分片 GET 上。

Popularity also needs device eligibility. A variant forecast of 20,000 views at 30% AV1 eligibility yields 6,000 eligible views and $4.50 savings, below $6; defer the work. The 30% is a follow-up input. Title demand feeds Codec policy, which queues extra encodes; H.264 remains available until publication. This decision does not run on each segment GET.

若全系统仅一半观看具备 AV1 能力、其中都达到同画质25%实际字节节省，出口整体才降0.5×25%=12.5%。基础$75K/天最多按这个模型少$9,375/天，剩$65,625；额外转码与存储成本尚未扣。全库冷片转 AV1 可以花掉很多计算，却对观看最多的那一小部分之外没有收益。先按可获得的90天收益排序，再与保障首个低档的任务分开优先级。

If only half of all views are AV1-eligible and those save 25% delivered bytes, system egress falls 12.5%, saving $9,375/day from $75K and leaving $65,625 before extra compute/storage costs. Whole-library encoding can waste work on unwatched titles. Rank by obtainable 90-day benefit, below first-playable base-rung priority.

切换与回退也要有版本边界。API 或客户端在打开视频时根据可用编码、profile、level、色彩与设备能力选兼容清单；播放中降码率通常留在同一codec阶梯。跨codec切换可能需要新的初始化与解码器状态，不能把它当成同一档普通切片。AV1解码失败回到H.264会话，统计原因并逐步关闭出错设备上的选项，别用CDN成功率掩盖黑屏。

Select a compatible manifest using codec/profile/level/color and device capability at session start. Bitrate changes normally stay within a codec ladder. Cross-codec switching can need different initialization and decoder state, not merely another ordinary segment. AV1 decode failures reopen a compatible H.264 session and inform rollout controls; CDN success must not hide black screens.

旧产物什么时候删：发布新 ready_version 不表示旧清单无人再读。A13至少保留24小时，并在有效会话或清单缓存引用更久时继续延长，直到引用失效才回收。下架与撤权另处理：短令牌只能给最多五分钟的自然到期窗口；若要求立即撤销，就要增加在线拒绝列表或 CDN 可同步的阻断机制，不能只等待文件删除和缓存TTL。

Publishing a new ready_version does not retire old manifest readers. Keep old outputs at least 24 hours and extend while valid sessions or cached manifests reference them. Removal/revocation is separate: a five-minute token allows that expiry window. Immediate revocation needs an online denylist or synchronized CDN blocking rather than waiting for deletion and cache TTL.

追问与翻车点：沿着同一张图回答Follow-ups and failure points: answer on the same diagrams

要1080p立即可播怎么办？ 将全三档变成发布门槛，上传到首播延迟会受最慢必需任务约束。可以提高并行与算力，但仍保留异步状态；不能返回上传成功就承诺已可播。要实时直播怎么办？ 源从完整文件变成连续输入，清单滚动、片持续产生，编码器与发布点都在线；LL-HLS 的部分片减少等待，但端到端延迟还包括采集、编码、网络与播放器缓冲。

What if immediate 1080p is required? All three rungs become the publication gate, and first-play latency follows the slowest required work. More parallel compute helps but does not merge upload acknowledgement with playable status. What about live? Continuous input, rolling manifests and ongoing publication replace whole-file processing. LL-HLS partial segments reduce waiting but capture, encode, network and player buffering still contribute latency.

全球CDN都冷了怎么办？ 使用 Shield、并发合并、回源封顶与少量有收益的预热；多个不同片仍需要源容量。源站丢产物怎么办？ 命中暂时继续，缺片从保留源版本重转，严格校验后重新发布；备份和多故障域冗余负责持久性，不能把几份边缘副本当备份策略。成本减半能做到吗？ 先明确是边缘费、源费、编码费还是总成本，再改变交付字节和可计费输入。

What if all edges are cold? Use Shield, request collapse, origin caps and profitable prewarming; distinct segments still consume capacity. What if outputs are lost? Hits may continue while missing outputs are regenerated from retained source versions and validated. Durable redundancy/backups are distinct from edge caches. Can costs halve? Name edge, origin, encode or total cost first, then revise delivered bytes and billing inputs.
