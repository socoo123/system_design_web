这一章结束你能做什么What you can do after this chapter

中文

从进程内的业务读取画起，再补发布、权威存储、watch 与应用闭环。每加一个组件，都能指回连接数、字节率或故障窗口。

把提交、获取、应用三种成功分开；用发布代次解释灰度与合法回退，用最后一次权威确认解释安全开关何时拒绝。

走完提交后崩溃、漏通知、历史裁剪、冷启动和重连风暴，给出可测的新鲜度目标与容量账。

English

Start with in-process business reads, then complete publish, authority, watch, and application. Tie each component to connections, bytes, or a failure window.

Separate commit, fetch, and apply. Use publication generations for rollout and valid rollback, and recent authority confirmation for critical-key denial.

Walk a crash after commit, missed hints, compaction, cold starts, and reconnect storms with measurable freshness and capacity assumptions.

30 秒开场：先定义“生效”Opening: define what applied means

中文

我设计的是应用运行时配置：超时、限流阈值、feature flag 和少量安全开关。业务请求只读进程内完整快照。SDK 启动拉取，之后用一条复用的 long-poll 或 push 收提醒，再拉正文。发布用条件事务保存内容、选择规则、审计、幂等结果和持久变更记录。201 确认权威提交，客户端 applied_generation 确认实际应用。灰度按认证实例稳定分桶；回退推进代次，重新选择好的旧内容。中心失联时普通值沿用好快照，危险动作要求近期权威确认。

先问五件事：动态配置还是随二进制部署的文件；多少进程、各订阅多少 namespace；允许多久看旧值；哪些动作在不确定时必须停止；是否要灰度与撤回。服务发现更新健康地址，配置发布更新值和规则，心跳不能混成版本。密钥发放、完整服务治理和代码发布各有自己的生命周期，不塞进第一张图。

namespace 是应用、环境、集群下的配置包。相关键在一个包内原子发布，不同包不承诺同时切换。若跨包组合必须原子，先合成同一 bundle；分别读取两个“最新包”，可能得到从未审核过的参数组合。下面所有容量和时间都是 assumption，引用只支持外部机制。

English

This is runtime application config: timeouts, limits, flags, and a few critical switches. Business requests read a complete in-process snapshot. An SDK fetches at startup, then multiplexes long-poll or push hints and fetches bytes separately. A conditional transaction stores content, selection rules, audit, an idempotent result, and durable changes. A 201 confirms authority commit; applied_generation confirms actual client application. Authenticated identities drive stable cohorts. Rollback advances generation while selecting old good content. Ordinary values survive an outage locally; dangerous actions require recent authority confirmation.

Ask about runtime config versus deployed files, process and namespace counts, tolerated staleness, actions that must stop under uncertainty, and rollout plus withdrawal. Discovery changes healthy addresses; config changes values and rules. Heartbeats are not config versions. Secret distribution, full governance, and binary deployment have separate lifecycles.

A namespace is a bundle under application, environment, and cluster. Related keys publish atomically inside a bundle; different bundles do not switch together. Combine them if atomic cross-bundle selection is required. Reading two latest bundles independently can create an unreviewed combination. All capacity and timing figures below are assumptions; citations support external mechanisms.

中文

容量分三条账。业务读是 10,000 × 1,000 = 10,000,000/s。空闲 watch 续约是 10,000 / 60 ≈ 167/s，外加 1 万连接；64 KB 预算合计约 640 MB，还没算 TLS 与运行时开销。单节点计划承载 5,000 × 70% = 3,500 条，10,000 / 3,500 向上为 3 台，再加 1 台，共 4 台。退出一台仍有 10,500 条计划容量。挂起请求必须用异步连接表，不是 1 万条线程。

原始正文 2,000 × 4 KB × 30 = 240 MB，三副本为 720 MB。发布、普通对账、安全确认是不同请求；库负载还要加权威选择视图、冷 miss 和 relay 读。watch 续约命中服务已追上的代次索引时，不逐次查库。因此 50 + 167 + 33 不是 Config Store 总 QPS，720 MB 也不能推出“整库 1 GB 足够”。

English

Keep three accounts. Business reads are 10,000 × 1,000 = 10,000,000/s. Idle watch renewals are 10,000 / 60 ≈ 167/s plus 10,000 connections. A 64-KB budget totals about 640 MB before TLS and runtime overhead. Planned node capacity is 5,000 × 70% = 3,500. Round 10,000 / 3,500 up to 3 and add 1, for 4 nodes. One loss leaves 10,500 planned connections. Park watches in an asynchronous connection table rather than ten thousand threads.

Raw content is 2,000 × 4 KB × 30 = 240 MB, or 720 MB for three copies. Publish, reconcile, and confirmation are different workloads; authority views, cold misses, and relay reads add store load. Watch renewals can use a caught-up service generation index without a store read each time. Hence 50 + 167 + 33 is not the store total, and 720 MB does not justify a one-GB total database budget.

高层架构：先把业务读移出控制面Architecture: keep business reads outside the control plane

中文

正常业务走 Business Code → Local Snapshot → Business Code；后面的策略图再展开本地 Action Gate。SDK 后台向 Config Service 请求，服务查 Config Store，正文原路返回。SDK 核对身份、schema、摘要和可执行参数，构造新快照再交换引用。业务线程不等 watch，不读数据库，也不在断线时临时补一笔 RPC。

Console 管草稿审批，Config Service 管鉴权、校验和连接，Config Store 管持久发布状态。Notify Relay 从同库 ChangeLog 尾读提交过的变更，叫醒持有 watch 的服务节点。提醒只含 namespace 与 generation，正文另取。relay 是角色，可以部署在服务节点里；独立总线只帮广播，不能取代权威日志和客户端对账。

1 万连接推动服务扩容，50/s 发布没有逼出写分片。namespace 代次在存储事务推进，各服务实例不会各自生成一个 42。Apollo 文档给出 long-poll 提醒、客户端另拉正文、本地文件与周期拉取的组合。[7] 本章采用角色拆分，再明确自己的原子发布与关键证明契约。

小规模可让 Console、Service、Relay 同部署，Store 用事务存储，接口边界仍保留。Git 可以存草稿和审核；运行中 SDK 仍需取值、订阅与应用协议。每业务请求查权威可增强语义，却把 1,000 万次/秒带回控制面；99% 缓存命中仍留 100,000/s，是发布峰值的 2,000 倍。快照首先移走这条依赖。

English

Business Code → Local Snapshot → Business Code is the local loop; a later diagram expands Action Gate. The background SDK requests Config Service, which reads Config Store and returns bytes along the same path. The SDK verifies identity, schema, hash, and executable parameters before swapping a prepared snapshot. Business threads do not wait for watch, read the database, or make outage-time RPCs.

Console owns drafts and approval, Config Service owns authentication, validation, and connections, and Config Store owns durable publications. Notify Relay tails committed ChangeLog records and wakes watch-owning service nodes. Hints contain namespace and generation, while bytes are fetched separately. Relay is a role that can run within service nodes. A broker helps broadcasting without replacing authority or reconciliation.

Ten thousand connections expand the service tier; fifty publishes/s do not force write sharding. Store transactions advance namespace generation, so service instances cannot independently invent 42. Apollo documents long-poll hints, separate payload pulls, local files, and periodic refresh.[7] We use that separation and define our own atomic publish and critical-proof contracts.

At small scale the Console, Service, and Relay may share a deployment with transaction storage. Git may hold drafts and reviews, but SDKs still need selection, subscription, and application protocols. Reading authority on every business request moves ten million reads/s back into the control plane; even 99% hits leave 100,000/s, two thousand times peak publishes. Snapshots remove that dependency.

API 与数据模型：内容身份和发布顺序分开API and model: content identity versus publication order

Idempotency-Key: request-7

  rollout: { percent: 5, salt: "s1" } }
201 { generation: 42, stable_release: "R17", canary_release: "R18" }
409 stale generation or same key with different payload

GET /v1/snapshots/{namespace}
If-None-Match: "namespace:g42:cohort:rule-revision"
200 { generation, selected_release, bundle, checksum, policy }
304 selected view unchanged  // not an authority proof by itself

200 { changed: [{ namespace, generation }] }

{ namespace, applied_generation, selected_release }
200 { current_generation, selected_release, authoritative: true }

ContentRelease(id, namespace, bundle, checksum, schema_version)
Current(namespace, generation, stable_release, canary_release,
        rollout_rule, rule_revision)
Publication(namespace, generation, publisher, request_id, reason)
Dedupe(principal, namespace, request_key, payload_hash, result)
ChangeLog(namespace, generation, event_id)
LocalView(bundle, applied_generation, selected_release,
          content_loaded_at, confirmed_at_monotonic)

中文

ContentRelease 是不可变内容 R17、R18，generation 是发布顺序 41、42、43。Current 包含稳定、金丝雀指针与规则。新增正文、调整比例、全量与回退都推进 g，即使字节不变。客户端按 g 排序，release_id 与 checksum 核内容；g=43 选回 R17 完全合法。相关键一次替换，不做多个 key 的静默合并。

expected_generation 针对整个 Current。A 改比例、B 改超时，都基于 41，只有一个事务推进到 42；另一方 409 后重新审核差异。Dedupe 作用域含认证主体、namespace 和请求键，绑定完整语义请求的哈希。同键换正文冲突；相同重试先取已存结果，再检查新事务的代次条件。

ETag 标识该调用者选择的完整视图，含代次、规则与身份选择上下文。RFC 9110 的 If-None-Match 和 304 是条件 GET 的表示比较，不是“系统没有发布”。[6] 本章 watch 空闲用 204；关键确认用专用无缓存接口，一次线性化读拿到规则和内容选择，再核对已应用视图。

权限按应用、环境、集群、namespace 约束。发布者来自认证主体，实例标签由控制面签发，自己传 tag=canary 不能自选生产值。摘要检测损坏，不替代 TLS、身份和读权限。A8 的 256 KB/键、1 MB/包是设计上限，超界 413；大对象受控外置，指针对应内容也要验摘要和授权。

English

ContentRelease identifies immutable R17 or R18, whereas generation orders publications 41, 42, and 43. Current holds stable and canary pointers plus rules. Content edits, percentages, promotion, and rollback all advance g, even with unchanged bytes. Clients order by g and verify bytes by release_id and checksum. Generation 43 selecting R17 is valid. Replace related keys together rather than silently merging independent writes.

expected_generation guards all of Current. Editors changing rollout and timeout from 41 cannot both advance to 42; the loser reviews a 409 diff. Dedupe is scoped by principal, namespace, and request key, with a hash of the complete semantic request. Changed payloads conflict; identical retries recover the saved result before a new-transaction generation check.

An ETag represents this caller’s complete selected view, including generation, rule, and identity-selection context. RFC 9110 defines If-None-Match and 304 as conditional representation comparison, not absence of publications.[6] Our idle watch uses 204. Critical confirmation is a dedicated uncached linearizable read of rules and selection, checked against the applied view.

Permissions cover application, environment, cluster, and namespace. Publishers are authenticated and tags are control-plane issued, so callers cannot self-select production values with tag=canary. Digests detect corruption rather than replacing TLS, identity, and authorization. A8 caps keys at 256 KB and bundles at 1 MB, with 413 above those design limits. External object references need digest checks and authorized access.

发布：一次提交留下所有恢复依据Publish: one commit leaves recovery records

中文

控制台先提交完整草稿，服务检查权限、schema 和业务范围：超时为正、限流阈值不溢出、百分比合法。查幂等结果；不存在才进入条件事务，校验 expected_generation、保存 ContentRelease、更新 Current，同时追加 Publication、Dedupe 和 ChangeLog。任一项失败全部撤销。事务是全做或全不做；分五次插入不天然等于同一次原子提交。[3]

Config Store 抽象的是事务与多数派持久化，普通单主数据库不会自动满足。可以使用共识事务存储，或明确关系库的复制提交策略。三成员 Raft 的健康当前任期条目通常需 2 个成员持久后提交；旧任期条目不能仅数副本判定提交。领导者应用已提交操作才返回本章结果。[2] 少数派不接发布，业务继续按本地策略读。

201 沿 Store → Service → Console → Admin 回来，确认已提交 g=42 与可恢复结果。提交后、通知前崩溃，ChangeLog 仍在，relay 重启继续尾读。投递后、记进度前崩溃会重复提醒，SDK 比较 g 去重，不重复切资源。若独立总线挂了，发布成立但事件积压，新鲜度受损；积压年龄要告警。

201 丢失与事务失败分开。同键、同正文取回原 g=42，不“修复”成第二次发布。24 小时去重覆盖最多 15 分钟重试。审计保存谁、何时、为何、旧新指针，进程日志不等于持久审计。通知离开发布线程；金丝雀应用确认另查询，不把获取失败追溯成权威提交失败。

若要求“201 之后每次业务读都必须新”，push 加 30 秒过期拒绝仍不足。需要操作同步线性化读，或严格租约失效协议等旧授权到期，把网络或慢读者放进关键路径。默认异步方案接受新旧并存；证明过期只限制失联后旧允许的继续时间，不是全体瞬时切换。

English

Validate the complete draft: permissions, schema, positive timeouts, non-overflowing limits, and legal percentages. Recover an idempotent result first. Otherwise one conditional transaction checks expected_generation, saves ContentRelease, updates Current, and appends Publication, Dedupe, and ChangeLog. Failure aborts all records. Atomicity is all or nothing, not five separate inserts.[3]

Config Store abstracts transactions and majority durability; an ordinary primary database does not automatically provide it. Use consensus transaction storage or specify replicated commit policy. A healthy current-term Raft entry in three members normally needs two durable members. Old-term entries cannot commit merely by counting copies. Apply the committed operation before returning our result.[2] Minorities reject publications while business reads keep local policies.

The 201 returns Store → Service → Console → Admin, confirming committed g=42 and a recoverable result. A crash before notify leaves ChangeLog for a restarted relay. A crash after delivery but before recording progress repeats hints; SDK generation comparison avoids duplicate resource changes. Broker failure retains the publication but accumulates events and degrades freshness, requiring backlog-age alerts.

A lost 201 is different from an aborted transaction. An identical key and payload recover g=42 rather than publishing twice. Twenty-four-hour dedupe covers fifteen-minute retries. Audit persists who, when, why, and pointer changes; process logs alone do not. Notify is off the publish thread, and canary application is a separate query. Fetch failure does not undo authority commit.

If every read after a 201 must be fresh, push plus thirty-second expiry is insufficient. Use a synchronous linearizable authority read per operation or strict lease invalidation that waits for old authority to expire, paying network or slow-reader costs. The asynchronous design allows mixed versions; proof expiry bounds stale permission after isolation without instantaneous fleet cutover.

watch：关闭检查与挂起之间的丢唤醒窗口Watch: close the check-to-park race

中文

先取一致快照及 g，再用 g 订阅。服务登记等待者后，在同一同步规则下复查当前代次；更大的 g 已存在就立即返回。发布插在“检查”和“登记”之间也不会漏。节点启动先加载并追上持久代次，才开放 watch；索引是可重建派生状态，不能重启成空后把客户端 42 判为没变。

提醒只说明包变了。SDK 一笔权威选择读拿到 g、规则和指针，再按不可变 release_id 拉正文。42、43 的提醒可合并到最新视图，不要求每次中间修改都业务应用。ZooKeeper standard watch 是一次性，触发后重设，期间可能错过中间变化；3.6.0 起还有 persistent watch，所以“所有 watch 一次性”不成立。[1] 两种都需要重连与失效修复。

fetched_generation 与 applied_generation 分开。解析、跨键校验、预建连接池或规则对象、业务确认、原子换引用都成功，再推进 applied。失败保留旧值，记录错误并限速重试；不能游标先写 42，连接池失败后实际仍旧。需要快速重挂监听时可另存 received_cursor，但待应用的最新目标不能丢。

g=43 已应用，慢 GET 的 42 随后回来，直接丢弃。比较的是发布代次，不是内容新旧。权威读落后本地就重试可信路径，不从滞后副本续证明。etcd 区分默认线性化 KV 与可能旧的 serializable 读，watch 也不保证线性化或有界到达。[4] 不能只知道 commit index 就认定任意副本仍有当前权威。

断线从保存游标恢复，历史存在则重放；裁剪了就 RESET，取完整当前视图及 g，应用后 watch(g)。登记后复查继续兜住快照读与重订阅之间的新发布。etcd API 用 compact_revision 指示旧 start_revision 失效。[5] 本章 namespace 的 generation 要关联实际存储 revision，两个编号不能直接混用。

A5 的 99%/10 秒是正常传播 SLO，A6 的 300 秒是普通漏提醒兜底。60 秒 long-poll 通常在变更时立即解开，但持续漏提醒时，300 秒对账不保证 10 秒恢复。测 commit 到 applied 分布，漏提醒与解析失败也算未达标。紧急开关另用 A7；普通值也要求故障中 10 秒恢复，就重算对账周期与容量。

English

Fetch a consistent snapshot with g, then subscribe using g. Register the waiter and recheck current generation under the same synchronization rule; return immediately if newer data already exists. This closes the check-to-register race. On startup, load and catch up durable generation before accepting watches. A rebuildable empty index cannot treat client generation 42 as unchanged.

A hint only says a bundle changed. Read g, rules, and pointers as one authoritative selected view, then fetch immutable bytes. Hints for 42 and 43 may coalesce into one latest application. ZooKeeper standard watches fire once and must be reset, potentially missing intervening changes. Persistent watches also exist since 3.6.0, so not every watch is one-shot.[1] Both need reconnect recovery.

Separate fetched_generation from applied_generation. Parse, validate cross-key constraints, prepare resources, obtain business acceptance, and atomically swap before advancing applied. Failures retain old data and retry with limits. Reporting 42 before pool preparation fails leaves actual behavior old. A separate received_cursor may rearm listening quickly, provided the latest pending application target remains queued.

Discard a delayed 42 GET after applying 43. Order publication generations, not content age. Retry stale authority reads through a trusted path instead of renewing proof from a lagging replica. etcd distinguishes default linearizable KV from possibly stale serializable reads, and watch has neither linearizability nor bounded delivery.[4] A known commit index alone does not validate any replica’s current authority.

Resume the saved cursor while history exists. Otherwise RESET, fetch a complete current view with g, apply, and watch after g. Register-and-recheck covers intervening publications. etcd compact_revision indicates an expired start_revision.[5] Namespace generation must map to the underlying store revision; the numbers are not interchangeable.

A5’s 99% within ten seconds is a normal propagation SLO; A6’s 300 seconds is ordinary missed-hint fallback. Changes usually wake a sixty-second long-poll immediately, but five-minute reconciliation cannot guarantee ten-second recovery of a persistently broken hint path. Measure commit-to-applied latency including missed hints and parse failures. Critical switches use A7; stricter ordinary failure recovery needs a new reconciliation and capacity budget.

本地快照：应用完整视图，单独确认安全资格Local snapshot: apply a whole view, confirm authority separately

中文

业务操作先捕获完整快照引用，从同一份视图读相关键。SDK 后台建 staging，校验与准备成功后一次交换；旧请求可用完旧值，新请求拿新视图。回调驱动业务准备新资源；组件不支持热更新就 requires_restart，控制台显示待重启，不能把拉到 JSON 当生效。外部资源失败保留旧 applied，报告原因，不抹掉权威发布。

serve_last 使用最后一份校验且应用成功的快照。冷启动可读好磁盘；磁盘也没有时，只对明确有安全默认值的普通键降级。必需键没有安全默认就让功能不就绪，不能随手编超时。已经运行与新进程分别走一次路径；“旧进程有内存”解释不了冷启动。

磁盘写临时文件，校验并刷新文件，原子改名后按文件系统要求刷新目录。启动核对格式、身份、摘要和兼容 schema。只说 rename 原子不考虑断电，可能仍丢最新文件；可留上一份完整快照恢复。磁盘写失败保留好内存并报告持久化错误，让运维知道重启可能退到更旧值。

安全 key 不看 content_loaded_at。allow=true 一天没改，但每 10 秒权威确认，可以仍是当前；磁盘旧值刚载入，年龄零，却没有新鲜证明。A7 下记确认请求发出时的单调时间；2 秒内得到无缓存、线性化且与已应用视图一致的结果，才建立最多 30 秒证明。不一致先应用新视图再确认，不能为未应用的 43 给旧 42 续资格。

过期、无证明、认证失败或重启，Action Gate 只拒绝危险动作，普通值继续读。heartbeat 说明连接活着，缓存与一般 304 说明表示未变，都不能续确认。有效期从请求起点保守计时，不从收到延迟响应再送 30 秒。长暂停与休眠必须使资格失效，使用计入暂停的经过时间或恢复时清证明；磁盘不保存跨重启的单调时钟资格。

关键键 deny 默认、最长证明期与 policy 下限由应用契约固定，发布只在契约内修改。否则坏发布把 fail_closed 改成 serve_last 就绕过防线。1,000 / 10 = 100 权威读/秒；若所有 10,000 进程都要确认，是 1,000/s，重测 quorum 读预算。30 秒限制失联后的旧允许窗口；立即撤权需要更强操作协议。

English

A business operation captures one complete snapshot reference and reads related keys from it. The SDK builds staging and swaps once after validation and preparation. Old requests may finish on old data. Callbacks drive resource preparation. Components without hot reload use requires_restart and appear pending restart, rather than fetched JSON counting as applied. Resource failure retains old applied state without erasing the publication.

serve_last keeps the last validated and successfully applied view. Cold starts may use a valid disk copy. Without one, only ordinary keys with explicit safe defaults degrade; mandatory keys without safe defaults leave the function unready. Do not invent arbitrary timeout defaults. Existing and new processes require distinct paths.

Write a temporary file, validate and flush it, rename atomically, and flush the directory as the filesystem requires. Startup verifies format, identity, hash, and schema compatibility. Atomic rename alone may still lose the latest file on power failure; keep an earlier complete copy. Disk errors retain good memory while reporting persistence failure because restart may use older data.

Critical keys do not use content_loaded_at. An allow unchanged all day can still be current if authority checks succeed every ten seconds. Newly loaded old disk data has zero loading age and no recent proof. Record the monotonic request-start time. A successful uncached linearizable confirmation within two seconds, matching the applied view, establishes at most thirty seconds of proof. Apply a different view first; confirmation for unapplied 43 cannot renew applied 42.

Expiry, missing proof, authentication failure, or restart makes Action Gate deny only the dangerous action. Heartbeats prove connectivity; cache hits and ordinary 304s prove representation equality, not authority. Start validity at request initiation rather than granting thirty extra seconds to delayed responses. Pauses and sleep must invalidate proof using suspension-aware elapsed time or clearing proof on resume. Do not persist monotonic-clock qualification across restart.

The application fixes deny defaults, maximum proof lifetime, and a safety-policy minimum. Otherwise a bad publication could turn fail_closed into serve_last. One thousand subscribers checked every ten seconds require 100 authority reads/s; all ten thousand require 1,000/s and a new quorum-read budget. Thirty seconds bounds stale permission during isolation; immediate revocation needs a stronger operation protocol.

灰度与回退：代次前进，内容可以回到旧版Rollout and rollback: advance generation, reuse content

中文

g=42 的 Current 存 stable=R17、canary=R18 与 5% 规则。服务用认证实例计算 H(namespace, salt, instance_id) % 100，小于 5 选 R18，其余 R17，整包只选一份。标签与比例语义要明确，例如只在批准集群内分桶；模糊说“tag 或 5%”可能额外把全部内部实例选进来。

固定 salt 和稳定身份使选择可复现；5% 扩到 20% 保留 salt，旧桶仍包含。均匀哈希下 10,000 × 0.05 = 500 只是预期，精确人数需名单。实例重建换身份会重新分桶，需要跨重启稳定就用受控标识。5% 实例不等于 5% 流量，负载不均要另测；看组间业务健康，而非只看连接都活着。

调比例不改正文也发布新 g、追加审计与 ChangeLog。R18 有错，发布 43 清空 canary、选择 R17，或只撤回金丝雀。SDK 接受更大的 g，合法回退不会被“内容版本只能升”挡住。不必复制 R17 伪造成 R19；保留发布动作的新顺序和坏 R18 的历史即可。

“指针回旧内容一定被 304 吞掉”过强。只比较内容编号、不推进规则代次会漏变化；ETag 包含新 g 与规则就能正确选择。原本就在 R17 的客户端可以不重载正文，但仍更新 g=43 的视图。回退与发布用同一条件事务，写明 reason、历史目标和操作者，不删除坏发布。

Fowler 区分运维与发布开关，并用稳定 cohort 解释渐进启用。[9] 这里按实例暴露配置；用户实验可在业务用 user_id 求值。不同值若导致互不兼容的数据写入，缩百分比救不了，要先做兼容代码演进。短期 flag 应有 owner 和到期清理，不让 namespace 长年堆满没人敢撤的分支。

English

Current at g=42 stores stable=R17, canary=R18, and a five-percent rule. Authenticated instances use H(namespace, salt, instance_id) % 100: below five selects R18, otherwise R17. Select one whole bundle. Specify tag-plus-percentage semantics, such as bucketing only inside an approved cluster; ambiguous OR can include all internal instances unexpectedly.

Fixed salt and stable identity make selection repeatable. Retain salt when expanding from five to twenty percent so prior buckets remain. Uniform hashing gives an expected 10,000 × 0.05 = 500; exact counts need a list. New instance identities rebucket, so cross-restart stability needs controlled IDs. Five percent of instances need not mean five percent of traffic. Measure group business health rather than connectivity.

Rule-only changes publish a new g, audit, and ChangeLog. If R18 is bad, publish 43 selecting R17 and clearing canary, or withdraw only the canary. SDKs accept the higher generation even with older content. There is no need to fabricate R19 from R17; retain the new publication order and bad R18 history.

Returning an old content pointer does not inevitably lose rollback to a 304. Content-only comparison without rule generations can miss changes; ETags with the new g and rule select correctly. Clients already on R17 may skip byte reloading while updating the view to 43. Rollback uses the same conditional transaction, recording reason, historical target, and operator without deleting the bad publication.

Fowler distinguishes operational and release toggles and stable cohorts for gradual enablement.[9] Here instances determine config exposure; user experiments may evaluate user_id in business code. Incompatible data writes need compatible code evolution, not merely smaller percentages. Temporary flags need owners and cleanup dates.

故障与容量：提醒很小，恢复正文并不小Failure and capacity: small hints, large recovery bytes

中文

按 namespace 每 5 秒短轮询，10,000 × 10 / 5 = 20,000/s。复用 60 秒 long-poll 空闲约 167/s，差约 120 倍。变更提前解开挂起，续约率会上升，167 不是全天上限。push 仍约 1 万连接，少空闲续约却保留重连、慢消费者、心跳与背压；应用排队和权威读取也在传播关键路径，连接方式不保证亚秒。

全体重连批量取 10 包，每进程 400 KB，10,000 × 400 KB = 4 GB。未压缩且无复用时一秒拉完约 32 Gb/s；30 秒平均 333 包请求/s、133.3 MB/s = 1.07 Gb/s。旧稿 400 MB 只算一个包，少 10 倍。若分 namespace GET，就是约 3,333 正文请求/s，字节相同；低请求数不等于低出口。

客户端断线先随机延迟，再有上限指数退避与 Full Jitter，AWS 原文解释无抖动退避仍成簇重试。[8] 30 秒窗口只给平均值，还用 A10 聚合 500 包/s 准入与 Retry-After 封住尖峰。普通进程保留快照等候；关键证明照常到期，不能为了重连风暴暂停安全时钟。

Bundle Cache 按不可变 release_id 存正文。相同 namespace/release 在单节点 single-flight；多节点仍需共享缓存或统一 origin 预算，否则各自一个 miss 仍放大到节点数。权威 Current 与正文分开读：顺序要可信，旧正文可长期缓存。Cache 全挂要封顶回源，余请求等待或降级，不把所有重连倒进库；慢消费者队列也有限，溢出后断开并从游标恢复。

一个 40 KB namespace 全量到 1 万进程是 400 MB；10 秒目标仅正文就需平均 40 MB/s = 320 Mb/s。500 人一批共 20 批，每 0.25 秒准入，保守安排约 5 秒，剩余给 GET、校验和应用。TLS、重试、事件和其它包另计。50/s 发布峰值若都全量，是 50 × 400 MB = 20 GB/s = 160 Gb/s，必须合并待发代次、排队与限制大范围发布。

按 namespace、g、release 上报 fetched、applied、失败原因和确认年龄，聚合看新鲜度分布与组间健康。遥测失败不回滚本地快照；缺上报记 unknown，不默认成功。错误升高停止扩围，发布更大 g 选择好内容，仍限速修复。schema 合法的 1 ms 超时也能打坏业务，语义坏配置只能靠领域校验与金丝雀观察补齐。

English

Short polling each namespace every five seconds is 20,000/s. Multiplexed sixty-second long-poll renews about 167/s while idle, roughly 120 times less. Changes wake it early and increase renewal rate. Push still holds about ten thousand connections and requires reconnects, slow-consumer control, heartbeats, and backpressure. Transport alone does not guarantee sub-second application.

A reconnect batch needs ten bundles, or 400 KB/process. Ten thousand processes require 4 GB: about 32 Gb/s in one uncompressed second without reuse. Over thirty seconds this is 333 batch requests/s and 133.3 MB/s, or 1.07 Gb/s. The old 400-MB figure omitted nine bundles per process. Separate namespace GETs produce about 3,333 payload requests/s with the same bytes.

Use random reconnect delay followed by capped exponential backoff and Full Jitter; AWS explains why unjittered retries still cluster.[8] A thirty-second window is an average, while A10 aggregate admission at 500 bundles/s and Retry-After bound spikes. Ordinary clients wait with snapshots; critical proofs expire normally. Recovery cannot pause the safety clock.

Bundle Cache stores immutable release IDs. Single-flight coalesces per-node misses; multiple nodes need shared caching or a common origin budget. Separate authoritative Current from payload reads: ordering must be trusted while old immutable bytes remain cacheable. Cache-wide failure caps origin, queues or degrades excess work, and does not dump all reconnects on the store. Bound slow-consumer queues; disconnect overflow and resume from cursors.

One forty-KB namespace to ten thousand processes is 400 MB. Ten-second completion requires at least 40 MB/s or 320 Mb/s of average payload egress. Twenty batches of five hundred every quarter second reserve roughly five seconds for admission, leaving time for fetch and apply. Account separately for TLS, retries, hints, and other bundles. Fifty such full publishes/s would require 20 GB/s or 160 Gb/s, forcing coalescing, queueing, and limits on broad publications.

Report fetched, applied, failures, and proof age by namespace, g, and release. Missing telemetry is unknown rather than successful, and does not undo good local data. Rising errors stop expansion and trigger a newer generation selecting good content through the limited repair path. A valid one-ms timeout can still break business behavior; domain checks and canary observation must catch semantic bad config.

追问与翻车点Follow-ups and common mistakes

中文

要求“全球一秒关闭入口”时先改契约。30 秒证明不足，缩到一秒要提高确认预算，还需可说明的时钟与暂停行为。严格立即撤权则把权威检查变成操作同步依赖。多区域先做单写权威、区域缓存正文；失联普通键沿用、关键动作证明到期停止。异步区域副本不能续当前权威资格；多区域同时发布必须先定义冲突与顺序，不能两边都自造 g。

配置中心与服务发现可复用进程和认证，但数据与订阅负载要隔离：频繁健康地址与人为审计发布不是同一种变化。收尾三句：201 确认事务，applied 确认行为；规则改变也推进代次；控制面失联按 key 契约沿用或拒绝。

English

For globally closing an entry within one second, change the contract first. Thirty-second proof is insufficient; one-second proof needs a higher confirmation budget and defined clock and pause behavior. Strict immediate revocation makes authority synchronous per operation. Start multi-region with one write authority and regional byte caches. Ordinary values survive isolation; critical actions stop at proof expiry. Async replicas cannot renew current authority; concurrent regions need a conflict and ordering protocol.

Config and discovery may share processes and authentication while isolating data and subscriptions. Dense healthy-address updates differ from audited human publications. Close on three boundaries: 201 confirms the transaction, applied confirms behavior; rules advance generation; key contracts determine outage-time service or denial.

补齐三条故障边界Three more failure boundaries

中文

多台 Config Service 持有不同客户端连接，每台都必须追上相关 namespace 的变更。relay 按节点保留消费游标，或用广播订阅把提醒发给全部连接持有者。不能把服务节点放进同一个竞争消费组，让一次事件只由其中一台拿走，其它节点的 watch 会永远等不到这条提醒。节点重建先加载代次；保留历史不覆盖它的游标时，走 RESET，不假装事件已经送完。

审计和 ChangeLog 的保留不能简单套用正文“每键 30 份”。仍被稳定或金丝雀指针引用的内容不可清理；可供回退的历史按产品保留期保留。ChangeLog 裁剪边界与可恢复游标协议配套，落后客户端显式重新取完整快照。幂等结果至少覆盖重试窗口，过期旧意图不能靠换键无限自动重发，必须回控制台核对现状。

安全证明约束的是动作入口。如果危险工作持续数分钟，开始时资格有效不意味着运行到最后仍可继续；业务需在可取消的检查点重验，或使用服务端授权的操作令牌与撤销机制。关键 key 缺失、schema 不兼容、默认 deny 被删除都按不允许处理。更新快照时，要把该视图对应的证明一起失效或原子替换，避免新正文沿用另一代的旧证明。

English

Different Config Service nodes own different client connections, so each must catch up relevant namespace changes. Keep a relay cursor per node or broadcast hints to all connection owners. Putting nodes in one competing consumer group delivers each event to only one node and leaves other watches unwoken. Rebuild generation state before serving; an expired history cursor requires RESET.

Audit and ChangeLog retention cannot simply reuse thirty content versions per key. Retain content referenced by stable or canary pointers and rollback history according to its policy. Compaction must match cursor recovery, forcing lagging clients to fetch full snapshots. Dedupe must cover retries. Expired intentions return to console review rather than endlessly resubmitting with new keys.

Proof governs action admission. A multi-minute dangerous task cannot infer continuing authority from its initial check: recheck at cancellable checkpoints or use an operation authorization and revocation protocol. Missing critical keys, incompatible schema, or removed deny defaults deny the action. Updating the view must invalidate or atomically replace its associated proof, preventing a new view from reusing another generation’s qualification.
