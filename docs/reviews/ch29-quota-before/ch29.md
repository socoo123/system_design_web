## 技术收紧与数字

| 原章缺口或歧义 | 本轮处理 |
|---|---|
| 页信用、取消等概念正确，但没有可执行落点 | 补本地worker账本、页incarnation、immutable ticket快照、generation/boot隔离、引用与pin分离；暂停后续issue，全部相关访问退休后才归还信用。 |
| 公平仅写加权份额/年龄提升，缺少准入/退出操作 | 显式global100、tenant queue25、active32/5,120页；tenant/request游标和deficit跨轮保留；release用charged.remove仅结算一次。政策是教学选择，不称vLLM默认。 |
| 600ms只约束入ready前，实际首次prefill可能仍延后；输出cap缺操作 | ready未首次prefill也检查同一wait_deadline；另有验证后的service budget。输出count达cap先stop；进度仅在唯一ticket被complete接受后应用。 |
| Little定律的在途与KV边界不够明确 | λ为稳定准入/退出GPU尝试率，含取消；W从信用准入到引用/信用释放，排队不在W中。平均信用不是实际活页/缓存页。 |
| goodput12直接用于接纳容量和队列μ容易混淆 | C=12改为**未实测**的、≥99%请求联合达标约束下最高接纳率；70%规划=8.4。goodput只计达标完成率，不能直接充当总完成率。100/12明确是假定总完成率的名义工作量。 |
| 客户端SSE块间隔可能不等于token ITL，两个p99也非联合99%请求 | TTFT用客户端，ITL/TPOT用worker token-ready；客户端块间隔另报。A5明确每请求TTFT≤800ms且该请求最大worker ITL≤50ms，联合≥99%，并解释边际p99不证明联合。N=1的TPOT无定义。 |
| 单GPU fence可能被误解成随便一个stream完成就安全 | CUDA event仅覆盖captured work；实际适配必须覆盖全部kernel/copy/block-table的stream依赖。Java手工complete明确不是CUDA验证。 |
| worker死亡、同key与发送回包未知只有描述 | 补唯一行/条件绑定/条件终态伪代码，bind后投递前崩溃允许失败关闭；同key不重开、active不被TTL删、终态过期不承诺无限去重。明确未运行真实PG。 |

## 代码与实际执行

命令：`python3 examples/ch29/check.py`，`node examples/ch29/sync.mjs --check`。Java17实际编译，5类场景/**577项断言通过**，含100次真实CPU并发cancel/EOS竞争。[代码结果](ch29-code-results.json)保存Java版本与源码哈希；这不是577种独立分布式实验。

- 正常iteration引用状态、普通EOS、17-token向上取整及上下文溢出；128信用满但物理页空时第129拒绝。
- A在途kernel仍访问P7，cancel后保持refs/pins/完整信用，B不能提前获准；fence后才可复用；重复ticket和旧incarnation不能减B的引用。
- 完整共享前缀，A/B分别在途时A退出仍保留B引用/pin；两者退出后可驱逐cache；拒绝部分页/重复retain。
- 同attempt旧generation仍live时新代次拒绝，释放后旧cancel无效；workerDied隔离旧池、新boot拒绝旧消息，故意碰撞numeric ticket也不误删新ticket。

[伪代码正常/危险时序表](ch29-traces.md)分别推演有界queue、公平deficit/输出上限、attempt双bind竞争、bind后崩溃、流write回包歧义。它们明确是手工协议推演，未冒充PG/GPU或网络实测。
