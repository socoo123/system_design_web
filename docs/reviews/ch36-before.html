先把操作、窗口与 assumption 钉住 Fix operations, windows and assumptions

我先问这一次操作需要什么承诺。写已经成功之后，另一端必须读到它吗？断网时允许哪一边拒绝，哪些数据可以短暂旧？平时的复制等待占多少延迟，超时后是否能重试？最后再规定用户怎样算成功，按有效事件算 SLO 与预算。CAP 管分区下无法同时兑现的保证，PACELC 补上日常复制的延迟代价，SLO 把选择变成可测的用户结果。

这是 M6 的基础章，用寄存器、购物车与结账旅程串起取舍。不同组是独立场景，Replica A/B 始终叫副本；系统品牌不能代替读、写和恢复规则。

所有 A 编号都是教学 assumption，引用只支持外部定义与机制。读本章要同时回答约束、决策、代价与失败行为，先固定分母和窗口，再报几个 9。

Start with the operation contract: must a later remote read see a completed write, which side may refuse during a split, and which data may be stale? Then specify normal replication waits, timeout recovery and user success. CAP bounds partition guarantees, PACELC adds everyday replication latency, and SLO measures the result.

This M6 foundation uses a register, cart and checkout. Replica A/B retain their names across independent scenarios; product names cannot replace read/write/recovery rules.

A-numbers are teaching assumptions; sources establish external definitions/mechanisms. State constraints, decisions, costs and failures, with the denominator/window before nines.

CAP：从一笔写后的旧读看见矛盾 CAP: a stale read after a completed write

先固定历史，才有一致性的判断 Define the history before judging consistency

图先从两个相同的 x=0 开始，复制通道断开以后，A 对 write(x=1) 返回成功。我们再让另一位读者在 B 调 read。若没有其它写，线性一致要求把每个操作放在调用到返回之间的某一点，并按一个寄存器的顺序执行；现实中已经结束的写，必须排在后来才开始的读前面。B 的 x=0 无法满足这个顺序。读者与写者是否同一人都不影响这个要求。Gilbert 与 Lynch 的 atomic consistency 用的就是这个语义。[1]

B 的难处是没有足够信息。它看到的本地状态，既可能对应“A 没写”，也可能对应“A 写了但消息丢失”。只看 B 的内存、时间戳或 CPU 都无法判断。它若保证总能给出寄存器值，就存在给错值的执行；若等待远端证明，分区持续多久就可能等多久。

The history begins at x=0. During the split A acknowledges x=1, then a different reader calls B. Linearizability places each operation between invocation and response in one legal register order, preserving real-time precedence. With no other write, B’s x=0 cannot fit that order, irrespective of reader identity. Gilbert/Lynch call this atomic consistency. [1]

B cannot distinguish no remote write from a completed remote write whose messages never arrived. Local memory, timestamps and CPU do not reveal the missing fact. Returning a value can be wrong; waiting for proof can last as long as the split.

A 是完成操作，P 是允许发生的通信故障 A means operation completion; P describes possible communication failure

定理里的 A 要求非失败节点收到的每个请求最终完成，没有承诺一秒或一百毫秒期限。工程里的 503 能及时解开客户端等待，却不是成功完成读写寄存器操作；把所有请求迅速拒绝，不能证明实现了 CAP 可用性。反过来，一个理论上最终返回、却拖了十分钟的系统，也可能完全不满足产品 SLO。后面两组图会把数学中的活性和用户的期限分开。

P 描述模型允许副本之间丢失消息。系统可以选择单节点、不承诺跨节点共享状态，或者明确排除某种故障，但不能在保留共享副本并要求面对分区的同时，把“不要 P”当作第三种修复方法。无分区时可以正常同时实现一致与服务能力；“只在分区时选择”是工程提示，也不能读成协议能立即准确检测分区。Brewer 强调应按操作细分，并设计检测、分区期限制与恢复。[2]

CAP A requires eventual operation completion at a non-failed node, without a one-second latency bound. Fast 503 is operationally useful but does not complete the register operation. Conversely, an eventual ten-minute result can fail the product SLO. Separate theoretical liveness from user deadlines.

P allows lost inter-replica messages in the model. A single-node or deliberately restricted-failure design can state its narrower contract, but shared replicas that must handle partitions cannot repair them by simply “dropping P.” Healthy operation can offer both properties; the engineering prompt to decide during a split does not imply instant accurate partition detection. Brewer discusses per-operation choices and recovery. [2]

这个证明没有替你实现数据库 The proof does not implement your database

线性一致并不等于“最终副本一样”，也不是 ACID 四个字母里的 C。它约束读写历史；事务隔离约束一组操作如何相互影响，多个键的库存和账本仍需事务与业务不变量。只在钱包余额读上保证最新，也挡不住两笔扣款分别检查同一个余额再各自提交。面试时先指出定理讨论的对象，再交给 Ch18/Ch24 的状态机、唯一身份和事务边界。

一个常见跳步是把超时当失败，再在别处生成新请求。CAP 没告诉你远端是否已经提交，甚至选择保一致的协议也会丢回包。可靠的恢复把原业务键带回来查询；未经确认的操作记为 UNKNOWN。这样既不会冒称成功，也不因一次超时造出第二份副作用。

Linearizability is neither eventual agreement nor ACID’s C. It constrains histories, while isolation governs interacting transaction operations; multi-key inventory/ledger rules still need transactions and invariants. Fresh wallet reads alone cannot prevent two independent check-then-debit transactions. Identify the theorem’s object before applying Ch18/Ch24 mechanisms.

Timeout does not prove remote noncommit, even under a consistent protocol. Recovery queries the original business key and preserves UNKNOWN until resolved, avoiding both false success and a second effect.

保一致：多数派继续，少数派明确拒绝 Preserve consistency: serve the majority, refuse the minority

正常路径：多数派提交，确认逐跳回来 Normal path: majority commit and full acknowledgment return

三成员组的多数派为 floor(3/2)+1=2。图里 A 为当前任期 leader，它把日志发给 B，B 持久记录并返回 ACK；按共识提交规则完成并应用这笔当前任期记录以后，A 才经 API 回复 Client。这个顺序把“本地收到了”与“外部可以依赖成功”分开。C 的通信被隔离，A/B 仍有两票，正常的多数派操作可以继续。复制从 A 发出，B 不直接给客户端成功。

这不是通用的 W=2 写协议。Raft 的任期、日志匹配、选举限制和当前任期提交条件一起保护历史。[5] 如果省掉这些规则，两份互相不同的记录也可以分别拿到两个 ACK。图展开一次当前任期提交，完整日志与选举规则由共识实现保证。

A three-member majority is floor(3/2)+1=2. Current-term leader A sends a log entry to B, receives durable ACK, commits/applies under the protocol, then returns A → API → Client. Isolated C does not remove majority A/B service; B never directly acknowledges the client.

This is not a generic W=2 protocol. Raft terms, log matching, election restrictions and current-term commit rules jointly protect history. [5] Two arbitrary ACKs are insufficient. The picture relies on a consensus contract for the full election/log rules.

少数派拒绝的范围要说准确 Specify which minority operations are refused

C 一侧即使进程和磁盘都健康，也无法凑齐多数派，不能确认新写。强读同样需要验证当前领导权与可见提交点；单纯看本地行不是证明。etcd 3.6 默认提供线性一致的相关操作，而请求改为 serializable 可以减少共识读的代价，同时允许读到相对 quorum 的旧数据。[6] 讨论 etcd 时仍要指明 API 与一致性模式。

如果多数派也凑不齐，整个该组暂停进展。拒绝是保安全的工程选择，不是在承诺所有节点都有业务成功。读一个与共享写无关的常量可以不受影响，读另一份允许旧值的展示数据也能另立契约；不需要把账户、购物车和整站页面绑在一个开关上。故障域按 shard 或组变化时，只限制受影响的那一部分，并把被拒绝的用户旅程记入自己的 SLI。

A healthy isolated C cannot confirm new writes without majority. Strong reads also require leadership and commit visibility proof. etcd 3.6 distinguishes default linearized operations from explicitly serializable reads that may be stale relative to quorum. [6] State etcd’s actual API/mode.

Loss of every majority halts progress for that group. Refusal protects safety while sacrificing successful operations there. Constants, separate weak display data and other shards can retain separate contracts; count refused affected journeys in their SLI.

恢复时，提交历史和业务结果分别确认 Recovery checks both history and business results

网络恢复后，C 从合法 leader 追日志，旧任期的 A 即便从长暂停中醒来，也不能继续以过期身份推进共识状态。但客户端的 k7 可能已经提交，只是 OK 没到达。重试先查询 k7 的持久结果；若业务库与共识元数据是不同事务域，还要在业务库里把幂等键与效果原子写入，不能假设选主协议顺手提供了一次扣款。

“CP 恢复后不需要对账”因此过于绝对。共识防止已提交日志形成两个相互冲突的历史，却不证明通知、支付渠道和用户回包都完成。未提交日志、未知回执、外部服务的状态仍需核查。代价是分区期部分拒绝，收益是不用让业务处理任意两份已提交账本；不要为了隐藏拒绝，在少数派擅自本地确认。

On healing, C follows the valid leader and stale terms cannot advance consensus. But k7 may already have committed despite a lost OK. Query its durable result; if business state uses another transaction domain, atomically deduplicate key/effect there. Election does not provide exactly-once charging.

Consensus prevents conflicting committed histories, not incomplete notifications, channel actions or user responses. Recovery still reconciles unknown receipts and external effects. Accept minority refusal rather than locally acknowledging an unsafe ledger write.

保服务：分叉可接纳，合并必须有业务规则 Preserve service: admit divergence with a real merge rule

可用的承诺必须包含冲突处理 An available contract includes conflict handling

购物车例把语义放宽：每边可以持久保存本地版本并确认加入，通信恢复后应用再合并。A 加 apple、B 加 bread 都成功，恢复时只做本例的集合并集，写回双方为 {apple,bread}。这条链必须有结果写回，否则只是发现冲突、没有修复副本。Dynamo 论文把版本与应用协助的冲突处理作为高可用设计的一部分，并使用 hinted handoff 等机制处理临时不可达。[4]

合并的风险随操作改变。仅加入时 union 不丢商品；若另一边已经删除 apple，简单 union 会把它复活。数量加减需要辨认操作身份，删除需要因果信息或相应的集合规则。选 last-write-wins 则要承认某个并发版本可能被舍弃，物理时钟不能证明业务意图。最终一致只说满足前提后的收敛，没有默认的恢复期限；本章不把五秒写成来自论文的保证。

The cart weakens semantics: each side durably accepts a local version, then the application reconciles after healing. Add-only union yields {apple,bread} and writes back to both copies. Dynamo includes versioning, application-assisted reconciliation and temporary-failure handling. [4]

Union can resurrect a removed item; decrements/removes need operation identity and causal rules. Last-write-wins can discard concurrent intent, and physical timestamps do not prove that intent. Eventual convergence has assumptions and no automatic five-second deadline.

W+R>N 证明交点，不证明整套语义 W+R>N proves overlap, not the complete contract

另看固定三成员集合。W=2、R=2 时，任意写集合与读集合的交点至少是 W+R−N=2+2−3=1。若一笔写已在固定 W 中完成、成员没变、读拿到各副本版本且能正确挑出新值，这个交点能帮助看见那笔写。它没有规定并发写的总序、暂存写能否被读见、读修复是否必须在返回前完成，也没有覆盖迁移和选主。缺少这些条件，不能从一个不等式跳到线性一致。

“所有 quorum 系统都做不到线性一致”同样不成立。有协议把多数派读、写回与版本规则组合成原子寄存器。这里反对的是仅凭集合相交就宣称性质，而不是否定 quorum 这个工具。共识日志和普通版本 KV 都用投票集合，但完整语义取决于协议；面试时把版本排序、读屏障和失败行为写出来，比增加一个 C 标签有效。

For fixed N=3, W=2, R=2, minimum intersection is W+R−N=1. With a completed write, stable members and correct version selection, overlap helps see that write. It does not define concurrent order, tentative-write visibility, return-time repair or membership transitions.

Conversely, quorum protocols can implement linearizable registers when they include suitable version/read-writeback rules. The mistake is inferring the full property from overlap alone, not using quorums. State ordering, read barriers and failures.

一台坏了能工作，不等于每个活节点都能工作 Surviving one failure is not availability at every live node

三节点失去一台，另两台能凑 W=2，所以从幸存多数派访问仍成功。但 2+1 分区时，单节点一边无法达到 W=2 或 R=2，接到请求就要拒绝或等；定理中的 A 要求那一边的非失败节点也完成。说“少一台仍可用”是故障容忍能力，说“所有分区都可用”是更强且不同的保证。两句话必须分开。

Dynamo 的 sloppy quorum 在不可达时可能使用偏好列表外的临时节点；这时虽然各自收到两个 ACK，读、写集合却不一定在原来的三份里相交。[4] 调高 W/R 通常提高等待代价与可见性条件，不能保证任意分区仍可写。Cassandra 等产品还可按请求、地域和配置改变规则，本章不声称一个跨版本“默认 N/W/R”。AP/CP 与 PACELC 标签用于解释具体配置下的代价，不用作产品出生证。

With one member down, two survivors may meet W=2. In a 2+1 split the singleton cannot meet W=2 or R=2; CAP A also covers that live node. Failure tolerance from reachable survivors is a different claim.

Dynamo’s sloppy quorum can use temporary nodes outside the preferred set, so nominal ACK counts need not intersect in the original N. [4] Higher W/R increases waits and constraints but cannot make every partition writable. Product request/region/configuration choices vary; this chapter asserts no universal default N/W/R.

PACELC：没有分区时，复制确认仍在改延迟 PACELC: replication barriers cost latency even without a split

平时也在付钱：哪一个 ACK 卡住成功 Normal operation still pays: which ACK gates success

PACELC 的 P 分支问分区时的可用与一致，Else 分支问平时复制带来的延迟与一致性代价。Abadi 在 2012 年提出这套框架，强调正常运行时的取舍会持续影响系统。[3] 这里把它落成确认门槛，不背四格数据库名单。本地持久就回，用户可较快拿到成功；等必要远端副本持久再回，承诺更强，成功路径也被远端拖住。

A4 的简化模型里，接入/API 往返合计 2 ms，本地持久 1 ms，所以早确认约 3 ms。若本地和复制并行，远端需要一轮 RTT 加自身 1 ms 持久，同步模型为 2+max(1,RTT+1)。RTT=4 ms 时是 7 ms；RTT=80 ms 时是 83 ms。串行则改为 2+1+RTT+1，分别为 8 与 84 ms。我们选并行模型画图，因此图注与正文只用 7/83，不把不同调度方式混成同一个数字。

PACELC asks A/C during partitions and L/C during ordinary replication. Abadi’s 2012 framework foregrounds that recurring cost. [3] Make the acknowledgment barrier concrete: local durability allows early response; required remote durability extends the critical path.

A4 assumes 2 ms overhead and 1 ms local persistence, so early response is 3 ms. Parallel replication gives 2+max(1,RTT+1): 7 ms for RTT=4, 83 for RTT=80. Serial work gives 2+1+RTT+1, or 8/84. The diagram consistently uses the parallel model.

持久、可见和强读是三份不同的承诺 Durability, visibility and strong reads are distinct promises

等到 B 持久不能单独证明读新鲜。B 可能还没有应用日志，另一个 B 类副本可能更慢，客户端还可能被路由到一个旧 leader。因此同步复制要说清等待的是接收、落盘还是可查询；读要验证提交点和领导权。图中的 commit v 是会话令牌：后续读先要求所在副本应用到 v，达不到就等待或转权威端。这个办法针对读己之写；如果别的用户还有后续写，完整线性一致还需遵守那些历史。

早确认的另一笔成本是容灾。A 本地持久以后立即成功，B 尚未追平时 A 永久丢失，切到 B 会丢掉已经确认的尾部写。可以改本地域多数派确认以抗单机故障，却依然有整个地域丢失的风险。零跨地域 RPO 要重新设计持久屏障，RTO 则是恢复服务时间，两者也不是同一个数。缓存命中无法补出根本不存在于幸存副本里的写。

B durability alone does not prove searchable freshness or current leadership. Specify receive/persist/apply barriers and strong-read validation. Commit token v can wait/route until application reaches v for read-your-writes; other users’ histories still require a stronger protocol for full linearizability.

Early local ACK can lose acknowledged tail writes if A is permanently lost before B catches up. A local majority protects against machine loss but not necessarily regional loss. Cross-region zero RPO requires a new durability barrier; RTO is service recovery time, a separate measure.

数字只改放置与契约，不冒充 p99 Use the arithmetic to change placement and contracts

20 ms 的教学目标里，7 ms 尚有 13 ms 条件余量，83 ms 已超 63 ms，不能靠加 App 机器解决远端关键路径。可把写归属与所需多数派留在靠近写者的地域，远端展示走明确弱读；若业务必须全球实时线性一致，就接受协调延迟并修改目标。动态换地域也要安全交接领导权，不能两边都因为“就近”成为可写主。

这些毫秒是预算模型，不能相加两个依赖的 p99 就声称算出整条路径 p99；尾部会受相关抖动、排队、额外协议轮次影响。对无分区时的 Else 做说明，也不允许故障时偷偷把同步写降成异步成功。若要降级，事先把可丢数据范围、用户状态和恢复行为写进契约；账本通常选择拒绝而不是改变成功的含义。

Under the 20 ms target, 7 leaves conditional room of 13 ms, while 83 exceeds it by 63. More App instances cannot remove remote coordination. Place write authority/quorum near writers or permit weak remote displays; global real-time ordering may require a slower target and safe authority transfer.

These are budget calculations, not composed p99 measurements. Correlated jitter, queues and extra rounds matter. Failure must not silently turn synchronous success into asynchronous success; any weaker contract needs explicit loss scope and recovery semantics.

SLI / SLO / SLA：把成功钉在用户边界 SLI / SLO / SLA: define success at the user boundary

先测用户完成什么，再设目标 Measure the user outcome before setting its target

SLI 是测量定义，SLO 是这份定义上的目标，SLA 是带约定后果的对外服务协议；SLA 并不是某条运行链上的下一个技术组件。[7] 对内目标常留余量以避免对外违约，但“必须更紧一档”不是数学关系；两者可能在窗口、排除项、赔付规则上本就不同，必须读具体契约。

A6 选择一秒内得到正确且持久的结账终态决策，按 checkout_id 计一件有效旅程。eligible 的范围在知道成败之前确定，格式合法、已进入支持范围的请求都计入，过载拒绝不能事后被移除。good 是 eligible 的子集，还要满足结果和期限。正常拒付可算“决策接口可用”，却不能算“支付完成率”；如果产品要衡量支付成功，另设业务指标，不能要求服务把用户余额不足也改成成功。

SLI defines measurement, SLO its target, and SLA an external agreement with consequences. [7] Internal targets often leave margin, but no theorem requires one tighter “nine”; contracts can differ in windows, exclusions and remedies.

A6 counts one eligible checkout_id journey and requires a correct durable terminal decision within one second. Determine eligibility before knowing outcome, including supported overload refusals. Good is a subset meeting the result/deadline. Valid decline can satisfy decision availability but not payment completion; use a separate business conversion measure.

UNKNOWN、重试和丢测量都要有归属 Assign UNKNOWN, retries and missing telemetry

Client → Edge → API → Ledger 正常逐跳，Ledger 确认后才给成功。若已入账但返回包丢了，正确性记录可以是已入账，用户侧旅程却超过期限或 UNKNOWN；两种账不能互相擦掉。本例以相同 checkout_id 合并重试，在最终判定时留下原始开始时间，不能每次重试重置一秒时钟。请求级成功率也可以另记，但总请求数包含重试，不能和旅程级 good 混除。[8]

API 若直接回复 202，只证明请求被接纳，不证明已完成结账。业务可以改成异步完成旅程，持久记录接单，再量另一个完成期限；这是显式换 SLI。没有流量时分母为零，仪表盘应显示无数据；测量丢失时还要告警数据质量，不能把缺失样本补成成功。Edge 看不到客户端断线后的最终感受，所以重要旅程可加客户端观测，并明确覆盖率，不能把服务端代理当全知视角。

Normal replies follow Ledger → API → Edge → Client. A committed ledger entry with a lost reply can be correct business state but a bad user journey. Deduplicate checkout_id retries while retaining the original deadline start. Request-level success may be measured separately with its own retry-inclusive denominator. [8]

202 proves acceptance, not completed checkout; an async completion SLI needs a distinct durable admission and deadline. Zero traffic is no data, missing telemetry is a quality issue, and server-side Edge observations have client-visibility limits. Add client measurement with explicit coverage where needed.

降级保住哪条 SLO，也要写出删掉的能力 State which SLO degradation preserves and what it removes

A7 的 Feed 在权限已验证、内容年龄不超过 30 秒时允许旧值；用户仍能阅读，代价是新帖稍晚出现。超过年龄给失败，不能任意续旧证明。撤销权限没有同样的豁免，账本的未知扣款也没有；“系统可降级”必须落到某条数据与操作上。图里的红线把账本失败一跳一跳传回，意味着这一条完成旅程消耗预算，即使拒绝是正确的选择。

为了报高可用，把缓存余额当真实余额继续扣款，是用错误结果掩盖拒绝。正确性约束通常要用唯一键、余额不变量与核账单独守住，不把“可以允许一万次错误请求”解释成“可以容忍一万次重复扣款”。目标应按用户损失、使用模式与可承受成本选，支付不天然固定四个 9，内部工具也不天然三个 9；五个 9 是否值得，需要明确目标和工程证据。

A7 allows Feed display up to 30 seconds old under validated permissions, trading new-post visibility for reading. Over-age values fail; revoked permissions and unknown debits have no exemption. The red ledger return counts a bad completed journey even when refusal protects safety.

Using cached balance for unsafe debits cannot improve true availability. Unique keys, balance invariants and reconciliation separately protect correctness; an allowed bad-request budget is not permission for repeated charges. Choose targets from user loss/cost/evidence, without assigning fixed nines to product categories.

Error budget：事件余额、时间口径与依赖 Error budget: event balance, time denominator and dependencies

比例乘分母，才得到能花的预算 A ratio needs its denominator to become a budget

令 E 为窗口有效事件，B 为 bad，目标 S。SLI=(E−B)/E，允许 bad=E×(1−S)，剩余=E×(1−S)−B。A9 的 E=10,000,000、S=0.999，允许 10,000；已有 6,000，所以剩 4,000，为原允许量的 40%。当前达成率是 (10,000,000−6,000)/10,000,000=99.94%，仍高于 99.9%。报“预算剩 99.94%”混淆了达成率和余额比例。

滚动 30 天会同时移出旧 bad 和旧 eligible，并加入新流量。某个事故离窗，余额可能变好；一大段好流量离窗，也可能让余额变差。它不是必须等下个月一号重新发放的固定配额。发布门每次读当前窗口；多维 SLO 还要分别算可用、延迟或新鲜度，不能把每项的余额简单相加。[8]

Let E be eligible events, B bad, S target. SLI=(E−B)/E, allowance=E(1−S), remaining=E(1−S)−B. A9 allows 10,000 and retains 4,000, or 40%; achieved SLI is 99.94%, a different percentage.

Rolling windows remove both old bad and old eligible while adding new traffic. Balance can improve or worsen without a calendar reset. Production gates read the current window. Keep availability, latency and freshness budgets separate. [8]

43.2 分钟是时间口径，不是万能换算 43.2 minutes belongs to a time-based denominator

独立的时间 SLI 以 30×24×60=43,200 分钟为分母，99.9% 允许 43,200×0.001=43.2 分钟，99.99% 为 4.32 分钟，99.999% 为 0.432 分钟=25.92 秒。请求 SLI 的同三档在一千万事件中分别允许 10,000、1,000、100 次 bad。这些是两种口径的对照，不是看到 43 分钟就能随时停服 43 分钟的许可证。

A10 另设全窗口持续 1,000 次/秒，总 E=1,000×30×24×3,600=2,592,000,000，预算为 2,592,000。20 分钟、10% 失败产生 1,000×1,200×0.1=120,000，花 120,000÷2,592,000≈4.63%。若同样时段全失败，是 1,200,000，花约 46.30%。若只把事故时流量提高十倍而其余时间不变，分母也增加：E=2,602,800,000，允许 2,602,800；全失败 12,000,000，约花 461.04%，已经大幅超支。不能换了峰值仍沿用旧分母。

For a separate time SLI, 30×24×60=43,200 minutes. Allowances are 43.2 minutes at 99.9%, 4.32 at 99.99%, and 25.92 seconds at 99.999%. Ten million request events instead allow 10,000/1,000/100 bad. These compare denominators; they are not permission to stop at any arbitrary time.

A10 steady 1,000/s gives E=2,592,000,000 and allowance 2,592,000. At 10% bad for 1,200 s, 120,000 bad spends 4.63%; full failure spends 1,200,000 or 46.30%. Increasing only incident traffic tenfold also changes E to 2,602,800,000 and allowance to 2,602,800; 12,000,000 bad spends 461.04%. Recompute the denominator.

依赖不能靠乘法凭空变成很多个 9 Dependencies cannot gain nines by optimistic multiplication

A11 假设独立、且两个依赖都必须成功，串行路径为 0.999×0.999=0.998001，即 99.8001%；坏率为 0.1999%，对 99.9% 目标几乎是两倍预算。并联且任一能及时接管时，纸面成功率为 1−0.001×0.001=0.999999，即 99.9999%。这两笔改变图的理由不同：串行需要减少关键依赖或提高各依赖，冗余则要额外画健康检查、容量和安全切流。

并联结果依赖独立故障。同一 AZ 电源、配置错误、发布和入口网络可能同时影响两份，切流也可能超出用户期限。把这些共同原因遗漏再宣称六个 9，只是把最重要的失败从模型中删掉。更稳妥的替代是把非核心推荐、通知等移出完成路径，同时明确超时降级；付款渠道若是完成所需则仍在路径上，不能因为外包就从 SLO 账单里拿掉。

A11 independent mandatory series dependencies yield 0.999²=0.998001, or 99.8001%; bad rate 0.1999% nearly doubles a 99.9% allowance. Independent timely parallel failover yields 1−0.001²=99.9999%. Series improvements and redundancy require different design changes.

Shared power, config, releases, networks and slow failover invalidate optimistic independence. Model those causes/capacity and remove optional recommendations/notifications from critical completion where possible. A required outsourced payment channel still belongs in the user SLO.

从 burn 到发布门：把稳定性决策闭成环 From burn to release gate: close the reliability loop

Burn rate 说的是当前烧钱速度 Burn rate measures current spending speed

burn rate=观测 bad 比例÷允许 bad 比例。99.9% 的允许比例是 0.001，当前 1%=0.01，所以 burn=10。若有效流量稳定且从完整预算开始，30÷10=3 天烧完；只剩 40% 时，30×0.4÷10=1.2 天。真实流量和滚动窗口变动会影响预测，因此发布门还需看实际 bad 次数与余额。burn 为零只是当前窗口没测到 bad，不证明不存在潜伏的业务错误。

SRE Workbook 给出的起点包括：一小时和五分钟窗口都超过 14.4 倍，或六小时和三十分钟窗口都超过 6 倍时 page。[9] 30 天=720 小时，14.4×1÷720=2%，6×6÷720=5%。这是稳定事件速率下烧掉完整预算的比例，不是“消耗剩余余额的百分比”。本例 99.9% 对应坏率阈值为 1.44% 与 0.6%，与 SLO 本身的 0.1% 不是同一个数。

Burn=observed bad fraction/allowed fraction. At 99.9%, 1%/0.1%=10. Stable traffic spends a full budget in 30/10=3 days, or 1.2 days with 40% remaining. Window/traffic changes require actual counts and balance too.

Workbook starting points page when 1 h AND 5 min both exceed 14.4×, or 6 h AND 30 min both exceed 6×. [9] With 720 hours, 14.4×1/720=2% and 6×6/720=5% of the full budget under stable rate. Bad-rate thresholds here are 1.44% and 0.6%, not the allowed 0.1%.

双窗口避免旧事故拖住告警 Two windows avoid alerts held by a recovered incident

长窗口把一次尖刺平滑成持续消耗，短窗口要求近期仍在烧。只用长窗口，故障恢复后可能继续叫很久；只用短窗口，一次偶发失败会触发很多噪音。每对窗口用 AND，两档严重程度用 OR。它是建议起点，不能在很低流量的工具上无条件照搬。

低流量时，一个失败就可能跳过比率阈值，零请求则根本无比率。应结合事件量、合成探测、期限与值班策略，分别处理无数据和业务错误，调整窗口也要回算预算消耗。全月余额还健康，新版灰度却持续高 burn，立即暂停放量；全月余额已耗尽但当前恢复，也应按政策修复与复评，不能用短窗变绿抹掉旧损失。

Long windows capture meaningful spend; short windows confirm ongoing burn and reset sooner after recovery. Use AND within each pair and OR between severity pairs. These are starting points, not universal low-traffic thresholds.

Low event counts can make one failure dominate, and zero traffic has no ratio. Combine event volume, synthetic checks and on-call needs, then recompute spending for changed windows. Pause a burning canary despite healthy monthly balance; current recovery does not erase previously exhausted budget.

预算政策必须把修复与重新发布接回去 A budget policy closes the repair and release loop

公开的 Example Error Budget Policy 使用四周窗口，并列出预算耗尽后的发布限制与例外。[10] 本章 A12 改用滚动 30 天：冻结功能放量，继续经审查的安全和紧急可靠性修复。窗口与动作是团队约定，SLO 的算式本身不会自动推出“必须冻发版”。保留责任人、计算口径与分歧处理，才让 gate 真的能执行。图里的 Repair 回到门，意味着修复证据、当前窗口和灰度健康度都要重新审。

回退前先检查数据和外部效果。v8 可能写了 v7 不认识的新 schema，也可能已产生不可逆扣款；代码切回不撤销这些事实。能安全回退才回 v7，否则关闭受影响功能或做前向修复。已经计入的 bad 不因回退退款，后续窗口自然移动与真实成功才能改变余额。“SLO 一破就自动 rollback”漏掉安全前提，也把用户目标误写成了固定发布算法。

面试收尾按图回答：完成后读到什么，分区时谁拒绝，平时等哪些 ACK，失败后如何查结果。再按用户旅程算预算、监测 burn、控制放量；成功的含义不能在故障时偷偷改变。

The public example policy uses four weeks and documents restrictions/exceptions. [10] A12 instead uses rolling 30 days: freeze feature expansion while permitting reviewed urgent/safety reliability fixes. These are team policy choices, not consequences dictated by the formula; define owners, measurement and dispute handling, then review repairs/current balance/health before reopening.

Check rollback data/effect compatibility. v8 schemas or charges remain after a code switch. Roll back safely or disable/forward-fix; observed bad events are not refunded. “Automatically roll back whenever SLO fails” omits these conditions.

Close with later-read semantics, partition refusal, normal ACK barriers and recovery; then define journeys, budget, burn and rollout. Never silently redefine success during failure.
