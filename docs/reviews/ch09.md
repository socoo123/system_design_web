## 技术更正与保证

| 原问题 | 本轮结果与依据 |
|---|---|
| F01：19×1000被称为舒适容量 | 每台预算600，正常20台；20台故障后19×600=11400不足11600。N−1需21台，20×600=12000。Local合计2.1GB、leader最多21、错误分配预算16800/s同步；10倍增长正常194、N−1为195 |
| code冲突直接判alias争用 | 同alias同key并发可能先撞Link主键。先ROLLBACK，再用新主库语句查owner/key；有同摘要胜者回放201，不同摘要409，无胜者再区分alias或生成码碰撞 |
| 事务与幂等只有描述、无实现 | Link PK、Idempotency复合PK、响应快照、同库BEGIN/INSERT/COMMIT明确；失败先回滚，commit-unknown丢连接并同key重试，503不等于确定没写 |
| SQL别名/绑定与快照不清 | 明确`:owner`、`:key`绑定参数和VALUES绑定约定；READ COMMITTED新语句回读胜者，避免同一CTE默认可见并发winner；不在aborted事务内继续查询 |
| 新请求时间校验可能误拒绝旧幂等重试 | 语法规范化后先查已存回执，再检查新建expiry；原创建已过期/撤销也回放原回执，当前状态另读 |
| 模型允许pending，创建却一律active | 可信服务端风险准入决定initialStatus，客户端不能指定；pending同事务提交并保存在回执；读取pending给无Location的200待审页，blocked/revoked给410 |
| 业务到期与缓存新鲜度混写 | valid_until只表示快照最大年龄；新鲜active的到期返回410，陈旧快照且库错误给503。硬expiry判断用安全时间上界+1秒发出预算，允许提前拒绝；缓存不延长到期 |
| 8+1+1中时钟余量含混 | 1秒为生产者/消费者合计误差，不是每机各1秒；另1秒为最终检查至响应发出上限。超界时失败关闭；副本旧值不可重新标fresh |
| 缓存miss可能被英文描述成可负缓存 | 只有成功、空结果的主库读建立负缓存；Local/Redis miss本身不证明不存在，依赖错误不写404 |
| version floor过度抽象 | 单个Redis EVAL比较floor及现有value.version、原deadline后回填；失效先max抬floor再删低版本。Local使用同一临界区；仍以原deadline封顶丢事件窗口 |
| 管理If-Match冲突 | 明确已授权资源的前置版本不匹配为412；不存在可404；outbox INSERT失败与状态更新一起回滚 |
| no-store闪卡暗示每次点击必回源 | 只约束遵守标准的HTTP缓存；不能清此前缓存的永久跳转、收回URL、控制历史/已打开页面或保证统计不丢 |
| redirect一概依赖healthy Mapping Store | 仅cache miss需要库；新鲜缓存命中可在库故障时继续至原deadline |

主要数字由验证程序独立复算：62⁶=56,800,235,584，35.725 bit；生日碰撞50%点约280,610；占用365M时单候选碰撞0.642603%、期望1.006468次、5次连续约1.096×10⁻¹¹。182.5GB逻辑/547.5GB三份、5.8MB/s出口、95%命中580/s、90%命中1160/s、整层故障10800失败/s、10000日错误预算约0.926s，均按教学假设标注。
