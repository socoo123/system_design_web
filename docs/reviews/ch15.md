## 实施与代码边界

开场改为路径、成功与同步进度三个决定，主线为「可信对象 → pin → 条件版本提交 → 设备连续应用」。A1–A11 和三个延伸追问折叠；算式仍展开。删除旧八行弱答案表、重复图注释义与长收尾，将失败反例靠近实现。非 SVG 中文统计 8,989→7,220，仅作记录，未套字数下限。中英、所有图注/无障碍描述与 17 张 `cards-grid` 闪卡同步。

页面 5 段代码来自 [examples/ch15](../../examples/ch15/README.md)，由 `sync.mjs --check` 逐字检查：

| 源文件 | 保证与简化边界 |
|---|---|
| `schema.sql` | PG18 约束形状，给出 guard、generation 与 Receipt 主键/部分唯一索引，其余相关表键在注释及正文中固定。不是完整 DDL 或部署。 |
| `pin.pseudo` | init 冻结清单；上传必须实际验精确 staging 版本的摘要/长度，并确认最终不可变对象；未知结果不能入 READY。授权、session/attempt、复用证明与 pin 在同一 guard 事务协调。 |
| `complete.pseudo` | 同租户 guard 持锁至提交；先重放 owner/key/intent 最小回执，再校验会话终态、当前 ACL、源复用证明、完整有序 pins、父版与配额。版本/ref/head/逻辑计费/change/outbox/receipt/session 一起提交；任一失败回滚。 |
| `changes.pseudo` | 普通 change_head 随事务递增，不用 sequence；固定 H（包括合法 H=0），原日志扫描后授权过滤。token 绑定用户/租户/H/ACL epoch；保留 floor 或权限 epoch 失效时重建快照。 |
| `gc.pseudo` | guard 下复核完整根/pins/attempt，持久 DELETING 与精确 DeleteJob 后再事务外删对象。未知删除立即返回重试，不落 DELETED；终态不复活、物理 key 不复用，版本化存储绑定精确 version ID。 |

本章选择「所有仍保留版本的完整逻辑长度」计配额，包含历史/回收站；去重不减账，剪除保留版本时才同事务释放引用和计费。实现并非所有产品都应采用的政策，避免把 `used += size` 与当前 head 计费混用。会话终态和最小回执本例不 GC；即使后来撤权，也只允许 owner 查询自己最小保存状态，不返回 manifest/URL。内容、新写与新授权始终检查当前 ACL。

明确修正了四个遗漏：同租户 hash 命中不授予采用权；普通预签 PUT 可重用/覆盖，必须隔离可变 staging 与最终 generation；change_seq 不能从分号顺序推断提交顺序；旧 DELETE 不能仅靠 48 h grace 防止伤到同 key 重建。数据库 guard 是教学简化，会串行化一个租户；逻辑服务分离并不使跨库事务凭空成立。

## 实际执行验证

[代码结果](ch15-code-results.json) / [执行日志](ch15-tests.txt)：Python 3 标准库 SQLite 与 SHA-256，**65 项断言通过**。执行 unchanged `schema.sql` 的部分唯一约束，再运行元数据与对象两个独立 SQLite 文件的完整教学模型。模型用 `BEGIN IMMEDIATE` 代替 PG 行锁，粒度更粗，不能据此声称跑过真实 PG 并发或分布式复制。

- 正常完整提交；缺块/错长度/错摘要/换清单/空摘要拒绝；未知 PUT 不入 READY，同一最终 generation 恢复丢 ACK；后续 staging 修改不改变最终字节。
- 中途注入 abort，Version/ref/head/quota/change/outbox/receipt 全回滚；普通 change_head 回到 101，下一次成功为 102。
- 16 个线程同键完成只产一个 v8/102；两个不同会话真并发 parent=7 恰好一个成功、一个 412，失败者保留 pins；同会话换 key 仍同结果，同 key 换会话/意图拒绝。
- 目标撤权/删除/会话到期/配额超限拒绝新提交；最小 owner 回执在撤权/过期后仍可重放；同租户私有块不能采用，源读权在 pin 后撤销也阻止完成。
- pin 先胜 GC 拒删、GC 先胜采用旧 generation 受阻；新 generation 可发布；活上传 attempt、保留版本与 read pin 均保护对象。未知 DELETE 保留 DELETING，重试旧 key 后迟到重复 DELETE 不伤新对象。
- 故意不分代、重用 `unsafe-key` 的负例确实把新字节删掉；这是风险反例复现，而非宣称实际存储故障实验。
- 固定 H 分页、过滤空页仍推进原日志 cursor、ACL epoch/retention floor reset、H=0 在后续写入后仍保持 0。

## 独立复核返修 · 多租户写范围 P1
