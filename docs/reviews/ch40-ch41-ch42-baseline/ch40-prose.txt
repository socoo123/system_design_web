A1 把公开请求固定为每秒 2,000 次，命中率假设 80%，所以回源是 2,000×0.20=400 次/秒。这个减法保留了共享缓存；它没有证明源站最多只能扛 400。全冷时回源会回到 2,000，是否需要保护由源站预算另定。登录后的个人信息不进这个公开命中模型，不能把同一个 80% 套在私有订单上，也不能把“可缓存 GET”和 App 的 Cache-Aside 混为一种布置。 A1 assumes 2,000 public requests/s and 80% hits, so origin sees 2,000×0.20=400/s. This arithmetic motivates shared cache but does not establish a 400/s origin limit. All-cold load is 2,000/s; origin protection needs a separate budget. Private orders are outside this public hit model. HTTP response caching and App-owned Cache-Aside have different placements. 为什么选资源合同，而不是只列四个动词 REST 是 Fielding 在 2000 年论文第 5 章提出的架构约束集合：客户端与服务端分离、无状态交互、缓存、统一接口、分层，以及可选的按需代码。[1] 统一接口包括资源标识、通过表示操作、自描述消息和超媒体驱动状态。常见 HTTP JSON API 借用了这些规则，但用了 JSON 不等于完整满足 REST。面试先说资源、表示、状态与导航合同，再谈具体动词；不要拿一个序列化格式代替架构理由。 Fielding’s 2000 chapter 5 defines REST through client/server separation, stateless interaction, cache, uniform interface, layering and optional code-on-demand. [1] The interface includes resource identity, representations, self-description and hypermedia. HTTP JSON APIs often borrow these rules; JSON alone does not establish REST. Explain resource, representation, status and navigation before listing verbs. 无状态交互要求请求携带解释所需的上下文，不是要求服务没有数据库。商品库存当然可以持久保存。把会话放共享库能让任意副本接请求，却不自动满足严格的 REST 会话约束。代价也要承认：公开表示和认证信息会反复携带，中间层必须按合同理解字段；内部专用批处理可能更适合一个明确的 RPC 方法，省下不需要的通用表示。 Stateless interaction requires sufficient context in each request, not an absence of databases. Inventory remains durable. Shared sessions can make replicas interchangeable without automatically meeting strict REST session constraints. Public representations/authentication repeat context and intermediaries must interpret the contract; an internal batch operation may benefit from a specific RPC instead. 失败行为：安全、幂等和结果查询不是一回事 HTTP 语义把 safe 与 idempotent 分开：GET 不应被设计成扣款；PUT、DELETE 的幂等说的是重复相同请求的预期效果。[2] DELETE 第二次可以回不同状态，不能要求两次字节一致。创建或扣款 POST 若要安全重试，要由业务把 operation key、参数摘要和结果与动作原子保存；这是应用合同，不是 POST 自带属性。首请求已提交但回程断了，客户端只知道结果未知，应以原身份查回执，盲目换 key 会真的做第二次。 HTTP distinguishes safety from idempotency: GET should not implement charging; PUT/DELETE idempotency concerns repeated intended effects. [2] A second DELETE may have a different response. Retriable POST mutations need an application transaction binding operation key, argument digest, result and effect. If commit succeeded but the reply was lost, query using the original identity; a new key can execute again. 共享缓存还要正确处理 Cache-Control、Vary 和认证。这里只示例公开响应 public, max-age=30 ；私有数据采用明确的不共享策略，不能用 URL 相同推断表示相同。ETag 是验证器，条件请求得到 304 后按缓存规则更新已有表示的元数据。[2][3] 304 不携带一份全新业务正文，也不能靠本地猜测续新鲜度。机制与权威事实的详细边界回 Ch38；这里先确保请求、验证和回程都没有绕过授权。 Shared reuse must honor Cache-Control, Vary and authentication. This exercise uses public, max-age=30 ; private data has an explicit nonshared policy. Equal URLs alone do not prove equal representations. ETag validates; a 304 updates stored metadata under caching rules. [2][3] It is neither a fresh business body nor permission to invent renewed freshness. Ch38 covers the deeper authority boundary. 内部 gRPC：类型合同与截止时间一起传播 [existing animation] 一跳 RPC 的两层合同 Gateway 接公开 JSON 后，用生成的 stub 调 App 的业务查询；App 返回 protobuf 消息和最终 RPC status，Gateway 再变成 HTTP 状态与公开表示。gRPC 的 unary、server-stream、client-stream 和 bidi 是四种调用形状，流内顺序也不等于业务落盘。[4] 这张图只是一跳，不为了展示“内部系统”把每个业务字段拆成微服务。想换协议的证据应是共享 schema、跨语言客户端和内部流，而不是未经测量地说二进制一定更快。 Gateway maps JSON into a generated stub call to App, then maps the protobuf result and final RPC status back to public HTTP. Unary, server-stream, client-stream and bidi are four RPC shapes; ordered messages do not imply durable business acceptance. [4] Keep one hop rather than splitting every field into a service. Shared schema, language support and internal streaming justify the switch; “binary is always faster” does not. 原生 gRPC 的常见协议合同运行于 HTTP/2，一条连接有多条 RPC stream。外层 HTTP 200 不能代替最终 grpc-status；代理吞掉 trailers 会把业务失败伪装成正常 HTTP 返回。[14]gRPC-Web 给浏览器另外一套可用合同，官方示例使用 Envoy 转接。[6] 浏览器的 fetch 不能让 JavaScript 任意发送原生 HTTP/2 帧、完整控制 trailers；也不能把原生 gRPC 的四种流能力无条件承诺给任意 Web 客户端。 The common native gRPC contract uses HTTP/2 with multiple RPC streams on one connection. HTTP 200 is not final grpc-status; dropped trailers can hide an RPC failure. [14] gRPC-Web provides a separate browser contract and the official example uses Envoy. [6] JavaScript fetch does not expose arbitrary native HTTP/2 frames or full trailer control; do not promise every native streaming shape to every web client. 为什么字段号和剩余时间都不能重置 protobuf 字段号决定线上身份。删掉的号和名称要 reserve，不能复用给另一种含义；新增字段还要检查旧消费者忽略它以后是否仍然安全。[7] 例如新加一个“需要人工确认”字段，旧服务虽然能解析，却可能按原逻辑直接执行，这叫语义不兼容。滚动升级要容忍新旧版本共存，Gateway 的 DTO 映射也属于合同测试范围，不能只用“能反序列化”验收。 Protobuf tags identify wire fields. Reserve deleted numbers and names; additions also need semantic compatibility checks. [7] An old consumer may parse a new approval-required field yet ignore it and execute immediately. Rolling upgrades must support coexistence, and Gateway DTO mapping is part of contract validation. Successful deserialization is insufficient. A2 的总预算 300 ms，在发内部请求前已经花 40 ms，再为回程保留 20 ms，下游只剩 300−40−20=240 ms。继续扇出时再减实际已花时间，不能每一跳重新领 300。gRPC 文档强调显式设置 deadline，并在传播时扣除已用时间；派生的应用工作也要自己响应取消。[5] 图中红色返回逐跳回客户端，取消只解决不再需要的工作，不能把已提交数据恢复到过去。 A2 starts at 300 ms; after 40 ms elapsed and a 20 ms return reserve, downstream has 300−40−20=240 ms. Further calls deduct additional elapsed work. gRPC recommends explicit deadlines and propagation of remaining time; spawned application work must cooperate with cancellation. [5] Red failure returns hop by hop. Cancellation stops unwanted work but does not undo committed data. 替代与窗口：何时能重试，何时先查询 一次超时可能发生在排队、执行前、执行中或提交后的回程。业务写若无原子幂等和回执查询，换成 gRPC 只改变编码，不会消掉未知结果。A3 给最多两次总 attempt，而且共享原截止时间；第二次启动前先检查剩余预算、失败是否允许重试、是否带原 key。只剩很少时间时直接返回失败，比发出注定迟到的工作更容易解释。重试的次数与成功率不是一个指标，调用库和 Gateway 不能各自偷偷加两次。 A timeout can occur while queued, before execution, during execution or after commit on the return path. Without atomic idempotency and result lookup, gRPC changes encoding rather than uncertainty. A3 caps total attempts at two under the original deadline. Check remaining time, retry eligibility and identity before starting the second. Too little time means fail instead of spawning doomed work. Library and Gateway retries cannot each silently multiply attempts. 保持内部 HTTP JSON 也是合理替代：低调用密度、团队共享语言少、现成运维工具重要时，统一资源合同可能更便宜。gRPC 换来 stub 和明确方法，也带来 schema 发布、状态映射和代理配置成本。均衡器若只在连接上分配，一条繁忙 HTTP/2 连接还会粘在同一后端；可用 L7 RPC 选路或受控客户端的多后端发现。扩容不会自动分走已经开始的长流，这条边界与选协议一起口述即可。 Internal HTTP JSON remains valid for low call density or teams prioritizing existing tooling. gRPC gains stubs and explicit methods while adding schema release, status mapping and proxy costs. Connection-level balancing can pin a busy HTTP/2 connection; L7 RPC routing or controlled client discovery may help. Scaling does not redistribute an existing long stream. WebSocket：双向通道不是持久消息回执 [existing animation] 从握手到双向消息 聊天两端都持续发帧时，先经 Edge 做 HTTP/1.1 Upgrade，Gateway 校验身份、Origin、子协议，再回 101；此后是 WebSocket 帧。[8] 对浏览器，Origin 检查能约束站点来源，但不能替代用户认证，非浏览器调用者也可能伪造它。每条消息里的房间、对象和动作仍要业务授权，不能因为握手已通过，就把整条连接变成全库通行证。 For continuous chat uplink/downlink, HTTP/1.1 Upgrade passes through Edge to Gateway, which checks identity, Origin and subprotocol and returns 101 before WS frames. [8] Browser Origin checks constrain site origin, not user identity; nonbrowser callers can forge them. Room, object and action authorization remains per message. A valid handshake is not access to every resource. 101 是这一种承载的握手结果，不能写成所有 WebSocket 都必须有 101。HTTP/2 上 RFC 8441 使用 Extended CONNECT，成功回应采用相应的 2xx 状态。[9] 白板按题目环境选择一种，既不把 H1 的 Connection/Upgrade 头硬塞进 H2，也不把 TCP 连接复用等同于业务会话重建。图上的组件名保持职责不变，只在线和副标题中标协议；这样更换承载不会看起来多出一个叫“WS”的服务。 101 belongs to this HTTP/1.1 handshake. RFC 8441 uses Extended CONNECT over HTTP/2 with a corresponding successful 2xx response. [9] Choose the environment-specific handshake; do not transplant H1 Connection/Upgrade into H2 or confuse transport reuse with session reconstruction. Network receipt proves arrival at that layer; Pong is a control response, not persistence of m7. Recipient application requires a separate business acknowledgement. This drawing expands sender acceptance only; Ch12 covers fan-out. Socket writes do not establish exactly-once effects. 窗口在提交之后、receipt 被客户端看到之前。App 可能已经存了 m7，Edge 却断了。重连必须带原消息身份查结果，并用最后已应用的序号补缺和去重；用当前时间造新 id，会把同一动作当成新消息。撤销用户权限后，长连接也应在消息或订阅边界复查并关闭不再允许的对象。连接还活着不代表授权还活着，某次心跳成功更不能续一份已经撤销的权限。 Commit can precede client observation of the receipt, and Edge may disconnect in between. Reconnect with the original message identity, recover its result and replay after the last applied sequence with deduplication. A fresh timestamp ID can create a duplicate action. Revoked permissions require rechecking and closing disallowed objects at message/subscription boundaries; liveness does not renew authorization. 容量与替代：连接必须有退出条件 A4 中每个连接最多排队 64 KiB，20,000×65,536=1,310,720,000 B，除以 2³⁰ 约 1.22 GiB。它只是所有发送缓冲同时到上限的 payload 总额，不含 TLS、内核 socket、索引和应用对象。按“一个连接只发很少数据”把缓冲忽略，会在一批客户端变慢时暴露。可以丢旧光标位置、合并输入状态，但持久聊天消息不能静默丢；满了就断开，让客户端从业务日志恢复。 A4 caps queues at 64 KiB per connection: 20,000×65,536=1,310,720,000 B, about 1.22 GiB using 2³⁰. This is payload when all queues reach the cap, excluding TLS, sockets, indexes and objects. Slow readers expose ignored buffers. Coalesce disposable cursor/typing state, but never silently discard durable chat messages; close and recover from the business log. A5 假设最短空闲超时 60 s，每 20 s 检测能避免正常安静连接仅因无数据被关闭，但网络或事件循环抖动仍会误判。健康检查、业务进度和慢读指标分别记录，故障后一批客户端用退避和抖动重连，先限订阅与回放再扩连接。偶尔发命令、主要看通知的界面，也能选择 POST 上行加 SSE 下行；聊天偏向 WS 是交互便利，不是 SSE+POST 在逻辑上绝不可能双向。 A5 assumes a 60 s shortest idle timeout and 20 s liveness checks; quiet healthy connections can remain open, but jitter can still cause false detections. Separate health, business progress and slow-reader metrics. Jitter reconnects and bound subscriptions/replay. Occasional commands plus mostly notifications can use POST uplink with SSE downlink. WS is convenient for chat, not a proof that SSE+POST is logically impossible. SSE：自动重连之后，还要定义恢复契约 [existing animation] 事件格式与日志范围 原生 EventSource 建立 GET 订阅，响应类型是 text/event-stream 。 data: 承载文本， id: 更新事件标识，空行结束事件；事件流使用 UTF-8。连接丢失后可自动重连，已有 last event ID 会在适用的重连请求中带回；204 可以让客户端停止重连。[10] 这些是浏览器与字节流的规则，服务器没有因此获得持久队列、业务确认或无限历史。 Native EventSource subscribes with GET to text/event-stream . data: carries text, id: supplies identity, and a blank line ends the event; encoding is UTF-8. On reconnect a stored last event ID can be sent back, and 204 stops reconnect. [10] These are browser/framing rules, not a durable queue, business receipt or unlimited history. 本章应用把标识定义成 scope、epoch、连续 seq。Client 带 E:42，Gateway 验证用户对 scope 的权限，再从 Event Log 查询 E:42 之后的事件，即 seq &gt; 42 ，从 E:43 开始且包含 43，并持续尾读。客户端要去重、识别缺口和 epoch 变化。浏览器 last event ID 是传输状态，handler 出错、页面崩溃、状态没落下来都不能据它认定业务已应用；确实需要可靠处理时，应用另外维护已应用游标，再显式传回它，不直接冒充浏览器内部状态。 Our application defines scope, epoch and contiguous sequence. For E:42, Gateway verifies scope permission, reads events with seq &gt; 42 , starting at and including E:43, and tails Event Log. Client deduplicates and detects gaps/epoch changes. Browser last event ID is transport state; handler failure, page crash or unpersisted state can invalidate application progress. That is about five minutes of history, not guaranteed recovery for every five-minute outage: rate changes, backlog, pruning and authorization also matter. Multiply by scopes and add indexes, replicas and cursor metadata. If history is gone, reconnection works but replay does not; use RESET. 裁剪后为什么要同一快照的状态和游标 游标过旧或 epoch 改变，Gateway 在流内发送应用定义的 RESET，客户端丢弃这轮局部状态，普通 HTTP 读取 Snapshot。Snapshot 返回一致的业务状态及它对应的游标，再订阅游标之后的日志。状态与游标要来自同一截面；若先读状态，再另读最新高水位，中间的变更可能没进快照，却被游标跳过。Snapshot 的生成与所需日志区间之间也要保住保留关系，否则客户端又会立即 RESET；无法保住时返回明确失败，不能无限循环装作恢复成功。 For an old cursor/epoch, Gateway sends an application-defined RESET. Client discards partial state, reads Snapshot over ordinary HTTP and subscribes after its matching cursor. State and cursor must describe one cut: reading state and then an unrelated latest highwater can skip intervening changes. Preserve the needed log range while obtaining/subscribing from the snapshot, or fail explicitly rather than looping RESET forever. TCP chunk、HTTP frame、一次 ReadableStream read 和一个 SSE event 没有一一对应关系。一个事件能被切成多次 read，多条事件也可能一次到达。解析器要保留未完成的行与 UTF-8 解码状态，看到空行才发布完整事件；不能每次读一块就直接 JSON.parse。代理、压缩器和写入端可以有限聚合，但聚合等待必须有上限，既保效率也不能把整段生成攒完再交给用户。 TCP chunks, HTTP frames, stream reads and SSE events are not one-to-one. HTTP/2 与 HTTP/3：丢包后谁等待 [existing animation] 先把接收端的层次展开 HTTP/2 已经在一条 TCP 上复用多个 stream，并不是 HTTP/3 才发明并行。上排把接收端的 TCP 层展开成框，是为了看到传输交付点；它不是新的一台中间服务。A10 假设包 P1 携带 A 的前部字节并丢失，随后携带 B 的 P2 已到。TCP 保证一个字节流按序交付，缺口补齐前，后来到达的 B 字节也不能越过它交给 HTTP/2；这就是跨 stream 的 TCP head-of-line blocking。 HTTP/2 already multiplexes streams on one TCP connection; parallelism did not start with HTTP/3. The upper TCP receive box exposes an endpoint layer, not a new service. Under A10, P1 containing earlier A bytes is lost and later B packet P2 arrives. TCP’s ordered byte-stream delivery prevents later B bytes passing the gap to HTTP/2: cross-stream TCP HOL blocking. 下排改成 QUIC。RFC 9000 把可靠顺序放在各条 stream 内，包里哪些流的数据丢了，就等待那些流的重传。[11] 如果 B 字节和解码依赖都齐，B 可以继续；A 仍然等。这是图中正常交付线与上排淡化线的区别，不是“UDP 发出去就不管了”。QUIC 仍负责确认、重传、流量控制与加密，应用获得的是一个受约束的可靠传输。 QUIC provides reliable order per stream. RFC 9000 ties loss blocking to streams whose data was in the lost packet. [11] Ready B data with satisfied decoding dependencies can advance while A waits. That is the live lower delivery path versus the muted upper path, not fire-and-forget UDP. QUIC still handles acknowledgement, repair, flow control and encryption. 收益的前提与还剩下的等待 A10 故意让 A/B 在不同包；若 P1 同时装了两者，两条流都可能缺数据。丢包还会影响共享拥塞控制，网络容量下降时其他流也未必保持原速度。HTTP/3 的 QPACK 把头部表状态放在独立流，但请求头可能等待必要的表项；应用若规定 B 必须使用 A 的结果，传输的独立性也帮不了它。[12] 所以口述“减少 TCP 引入的跨流等待”，不能承诺“HTTP/3 所有请求互不影响”。 A10 deliberately separates packets: if P1 carried both streams, both can need repair. Loss also affects shared congestion, so other streams may slow down. HTTP/3 QPACK state uses independent streams but headers can need table entries; applications may also make B depend on A. [12] Say it reduces TCP-induced cross-stream waiting, not that all HTTP/3 requests are independent. 选型收益应在题目路径上验证：移动弱网、多资源页面、频繁切网时，这一差异可能改善可见等待；同地域一次短 unary RPC 未必有值得迁移的收益。保持 HTTP/2 的替代仍然成立，它有熟悉的代理与诊断工具，减少部署成本；HTTP/3 则要求客户端、入口和网络都支持。换传输不替代应用 deadline、缓存、准入和业务幂等，源站慢 SQL 也不会因 QUIC 自动消失。 Validate benefits on the actual path: mobile loss, many resources or network switches may improve visible waits, while one short same-region unary RPC may not justify migration. HTTP/2 offers familiar proxies/diagnostics and lower deployment effort; HTTP/3 needs client, edge and network support. Transport does not replace deadlines, caching, admission or idempotency, nor fix slow SQL. QUIC 边界：early data、迁移与回退 [existing animation] 0-RTT 的零是少等一轮，不是没有网络时间 客户端已有恢复信息时可以尝试在握手完成前带 early data。A11 假设 RTT 为 40 ms，服务器接受安全早期读取时，可能省一轮约 40 ms 的握手等待；冷连接、拒绝 early data 或原请求仍需业务排队时都不能套这个收益。零轮等待不代表服务器响应无需传播，也不代表请求一定被接受。不要把“0-RTT”直接写成首响应 0 ms，更不要从它推出所有弱网请求都会更快。 With resumption information, a client may try early data before handshake completion. A11’s 40 ms RTT can yield a roughly one-RTT handshake saving when safe early reads are accepted. Cold connections, rejected early data or business queues invalidate that shortcut. Zero handshake waits does not mean zero propagation, guaranteed acceptance or universally faster weak-network requests. early data 存在重放风险。HTTP 的规则限制早期发送不安全或未知安全性的方法，425 Too Early 是明确拒绝处理这种风险的回应。[13] 本例对扣款等请求采取保守策略：可信 Early Gate 在 dispatch 前拒绝，425 经 Gateway、Edge 回客户端，握手完成后才用原 operation key 重试。握手重放保护、跨节点去重范围和业务幂等是不同层，单机进程里的短期 key 集合不能消掉集群重放窗口。 Early data has replay risk. HTTP restricts unsafe or unknown-safety early methods and 425 Too Early explicitly refuses that risk. [13] This exercise conservatively rejects mutations at trusted Early Gate before dispatch, returning 425 through Gateway/Edge, then retries with the original key after handshake. Handshake replay defenses, cluster-wide deduplication and business idempotency have distinct scopes; a short-lived local key set cannot cover the cluster window. 代理要保住来源事实，迁移要验证路径 如果 Edge 终结 QUIC 后丢掉 early-data 来源，Gateway 可能把早期扣款当普通请求执行。A12 要求入口生成可信标志并转交检查点，清理客户端伪造的同名内部头；否则在 Edge 直接禁用相应早期请求。图里 Early Gate 是 Gateway 的逻辑检查职责，不必单独部署一台服务。拒绝与已执行必须分清：已经 dispatch 才回 425，就不再具备本例“尚未发生副作用”的证据，恢复还要查原动作回执。 If Edge drops early-data provenance after terminating QUIC, Gateway can treat an early mutation as ordinary. A12 requires trusted ingress provenance with forged internal headers removed, or rejection at Edge instead. Early Gate is a logical Gateway check, not a mandatory separate deployment. Returning 425 after dispatch loses this exercise’s evidence that no effect occurred; query the original operation instead. Wi-Fi 切蜂窝会改变地址，connection ID 让端点仍可能识别原连接，但 RFC 9000 的迁移需要新路径验证，并受端点能力与策略约束。[11] connection ID 不是授权令牌；不能凭它把任意新地址当作已可信。业务会话与原操作身份也要继续保留。切网期间仍可能丢包、排队或等待验证，所以说“有机会保住连接”，不要说“切网完全无感”，更不能把同一个 id 误当成重复业务的安全许可。 A Wi-Fi/mobile switch changes addresses; connection ID can preserve recognition of a connection, but RFC 9000 requires path validation subject to endpoint capability/policy. UDP 不通的失败方式要提前写进合同 HTTP/3 连接失败可能来自 UDP 不可达，标准建议尝试基于 TCP 的 HTTP。[12] A12 先确保客户端和 Edge 支持对应 TLS/TCP 路径，再切换承载，不改资源或操作 key；不能把失败的生成 POST 顺手重执行一遍。握手尚未发业务和业务可能已到服务是两种恢复条件：前者可建立新连接再发，后者按原操作查询。回退是可用性设计的一部分，需要限额、诊断与真实失败网络验证。 HTTP/3 can fail when UDP is unreachable; the standard recommends attempting TCP-based HTTP.
