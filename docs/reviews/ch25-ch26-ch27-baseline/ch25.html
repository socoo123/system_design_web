这一章结束你能做什么What you can do after this chapter

从任务定义画到认领、执行与恢复，分清注册、火点生成和业务成功。任务已保存不等于跑过，一行 run 不等于 handler 只调用一次，worker 成功不等于通知已送达。每组终图都能指出填住崩溃窗口的持久记录。

Trace definitions through claims, execution and recovery. Separate registration, occurrence creation and business completion: a saved schedule is not execution, one run does not mean one handler call, and worker success is not delivered notification. Name the durable record closing each crash window.

本章设计 cron 与一次性延迟任务，例子是对账、巡检、关单和重试，重点是认领、租约、补偿与幂等。多步依赖交给工作流引擎；Ch34 的模型循环可以被定时唤醒，选择下一步仍是它自己的职责。

We design cron and one-shot delayed reconciliation, checks, order closure and retries, focusing on claims, leases, recovery and idempotency. Workflow engines own multi-step dependencies; a timer may wake Ch34’s model loop while the loop retains responsibility for choosing steps.

30 秒开场与全部假设The 30-second open and assumptions

我先做单地域、多实例的后端任务调度。任务定义和运行记录以一个事务数据库为权威，按到期索引小批认领；同一事务生成唯一火点的 ready run，并推进 cron 游标。worker 用独立执行租约领取 run，重试沿用原 run_id，旧代次不能回写完成。misfire 按 job 选跳过、补一次或逐窗补齐，补偿共享下游预算。延迟任务先存绝对截止点，时间轮只加速叫醒。外部效果由业务端幂等键和本地事务收口，通知从业务 Outbox 恢复。

I start with a single-region, multi-instance backend scheduler. One transactional database is authoritative for definitions and runs. Small indexed claims atomically create a unique ready occurrence and advance its cron cursor. Workers use separate execution leases; retries keep run_id and stale generations cannot complete it. Per-job misfire policy chooses skip, coalesce or interval replay within a shared downstream budget. Persist absolute deadlines before adding a timing index. Business-side idempotency and local transactions protect effects; an outbox recovers notifications.

澄清六件事：周期还是延迟、是否有依赖、重复执行代价、允许迟到多久、错过窗口能否丢、副作用在哪个存储。漏一个对账日与漏一分钟巡检不同，关单与邮件也有不同幂等能力。已有 DB 就先用事务认领；Redis 可减抢占，不能成为唯一正确性来源。

Clarify periodic or delayed work, dependencies, repetition cost, lateness, whether intervals can be dropped, and effect storage. Missing a settlement day differs from missing a minute of inspection; orders and email have different idempotency. Start with transactional database claims; Redis may reduce contention without becoming the sole correctness authority.

先落任务与火点，再交给执行者Persist the schedule and occurrence before dispatch

正常路径：注册、物化、执行是三个提交边界Normal path: registration, materialization and execution

注册请求带调用方身份、job_id、cron 或 delay_until、时区、misfire_policy、concurrency_policy 和超时。Job API 校验表达式与参数，写入 Schedule DB 后返回 202 和版本。调用方丢了响应，可以用同一注册请求键读取结果。202 的承诺是“这份定义已经保存并可被恢复”，不能说已经完成任务，更不能等待邮件、对账或关单处理器跑完才把注册请求结束。

Registration carries caller identity, job_id, cron or delay_until, timezone, misfire and concurrency policies, and timeout. Job API validates and saves the versioned definition, then returns 202. A caller with a lost response can retrieve the result using the same registration key. Acceptance means the definition is durable and recoverable; it does not mean the work completed, and registration should not wait for email, reconciliation or order closure.

Scheduler A 查询所属逻辑片中 next_run_at 已到期且未暂停的行，锁住小批数据。一个短事务 T1 读取当前版本和原 scheduled_at，插入 ready run，再按 cron 规则计算下一个火点并更新游标。三件事一并提交，任何一步失败都回滚。run 身份用非空的 (job_id, schedule_version, scheduled_at_utc) 唯一键，不能用 scheduler_id 或实际开始时刻：两台机器现在的毫秒数不同，同一火点就会变成两个身份。[3]

Scheduler A selects due, enabled rows for its logical shards and locks a small batch. Short transaction T1 reads the current version and original scheduled_at, inserts a ready run and advances the cron cursor. All commit or roll back together. A non-null unique key on (job_id, schedule_version, scheduled_at_utc) identifies the occurrence; scheduler identity and actual start time would give competing instances different identities. [3]

为什么这样选：游标前进不能丢掉未投递的工作Decision: advancing a cursor must preserve undispatched work

图上把 ready 留在库里，是为了关闭最常见的双写窗口。若先改 next_run_at，再只往内存线程池放任务，进程在两步之间死掉，这次执行再也扫不到。相反，先发 worker 后记运行行，崩溃时会不知道是否已经发过。T1 留下持久 ready 后，发送只是可重试动作；恢复者扫 ready，再把相同 run_id 交给 worker。需要队列时，可在同一库的 T1 内加 dispatch outbox，由 relay 发送，不能在提交后凭一次 publish 就删除恢复证据。

Persisting ready closes the dispatch gap. Advancing next_run_at before enqueueing only in memory can permanently lose a run if the process dies between them. Sending first leaves uncertainty about whether dispatch happened. After T1 persists ready, delivery is retryable: recovery scans ready and resends the same run_id. If a queue is needed, T1 can include a dispatch outbox in the same database, with a relay publishing it; a post-commit publish alone is not durable recovery evidence.

周期游标按“已物化哪个火点”推进，不能一律等成功才算下次。cron 描述墙钟上的日历点，上一轮慢了并不会把下一轮自动推迟。若业务要求完成后再等十分钟，那是 fixed delay，需要 finished_at 加间隔生成下一次；两者要在定义中区分。某个 job 不允许重叠时，单独用 job 级并发槽、当前 run 指针或等价事务约束，不能靠“每个火点唯一”推导“两个不同火点不会同时跑”。

Advance a cron cursor by the occurrence that has been materialized, rather than waiting for its success. Cron defines calendar instants; a slow previous run does not automatically move the next one. Waiting ten minutes after completion is fixed delay and derives its next occurrence from finished_at. If overlap is forbidden, enforce a separate job-level slot or active-run pointer transactionally. Uniqueness of each occurrence does not prevent different occurrences from overlapping.

故障窗口：同一身份、不同尝试、独立结果Failure window: one identity, several attempts, separate outcomes

Worker A 的 accepted 是收到请求，不是业务效果已完成。它还要从 Schedule DB 领取执行租约，检查 ready 或可接管状态，记录 attempt、owner、generation 和 lease_until。网络重复发送 r7 时，只有符合条件的领取能变更当前所有者；其他调用读取当前结果或退出。若 worker 已执行但确认丢失，另一轮仍可能再次进入 handler，所以我们承诺的是可恢复的至少一次尝试，并在业务端证明效果只生效一次，不承诺处理器只被调用一次。

Worker accepted means receipt, not completed effects. The worker must claim an execution lease in Schedule DB and persist attempt, owner, generation and lease_until. Duplicate delivery of r7 only changes ownership if claim predicates allow it; other callers read the current result or exit. Lost acknowledgements can still cause another handler attempt. The contract is recoverable at-least-once attempts with business-side effect protection, not one handler invocation.

Schema 只保留能够恢复的事实：jobs 保存定义、版本、逻辑片、下次火点与策略；runs 保存火点身份、状态、attempt、当前所有者、租约、重试时刻和最终结果引用。ready 与运行中的记录不能被七天历史清理误删。控制台查执行历史可以走只读副本，认领和完成必须回权威主库；主库不可安全确认时，系统暂停新认领并报告滞后，而不是从副本猜一个所有者继续发副作用。

Keep recovery facts in the schema: jobs stores definition, version, logical shard, cursor and policies; runs stores occurrence identity, state, attempt, owner, lease, retry time and final-result reference. Seven-day terminal-history cleanup must never delete ready or active runs. History views may use a read replica, but claims and completion use the authoritative primary. When it cannot safely confirm ownership, stop new claims and report lateness instead of guessing from a replica.

平均触发率之外，还要画突发与认领Draw bursts and claims beyond the average fire rate

推导：速率决定并发，日总量决定历史Calculation: rate sizes execution; daily volume sizes history

压力场景把 10,000 个定义全设为每分钟运行，平均火点速率是 10,000 ÷ 60 = 166.666…/s。这不是上界：常见分钟表达式会让全部任务在同一个秒点到期，瞬时待处理数是 10,000。按平均处理 0.2 秒，稳态平均占用 166.666… × 0.2 = 33.333… 个并发槽。再除以计划使用率 0.6，向上取整得到 56 槽。槽数可以分布在几台 worker 上，机器数还需要 CPU、内存和下游调用的压测结果。

Set all 10,000 definitions to every minute in the stress case. Average occurrence rate is 10,000 / 60 = 166.666…/s, while an aligned boundary can make all 10,000 due at once. Mean service time gives 166.666… x 0.2 = 33.333… occupied slots; dividing by 0.6 planned utilization and rounding up gives 56 slots. Slots can span several workers; machine count also needs measured CPU, memory and downstream-call costs.

再做一个固定时长、没有调度与网络开销的理想模型：56 槽 ÷ 0.2 秒 = 280 次/秒，10,000 ÷ 280 = 35.714… 秒。这个商是完整执行突发的流体近似下界，离散批次还要向上取整到 179 轮，也就是 35.8 秒；真实慢任务与争抢只会更慢。如果面试官要求五秒内全部完成，理想并发至少 10,000 × 0.2 ÷ 5 = 400 槽，60% 计划使用率则约 667 槽，并且还没给认领与排队留时间。

Under a fixed-service-time model with no scheduling or network overhead, 56 / 0.2 = 280/s and 10,000 / 280 = 35.714… s is a fluid lower bound. Discrete rounds require 179 rounds, or 35.8 s, before tail latency and contention. Finishing all work in five seconds needs at least 10,000 x 0.2 / 5 = 400 ideal slots, or about 667 at 60% planned utilization, excluding acquisition and queueing time.

存储另算：定义只有 10,000 × 1 KB = 10 MB，三份 30 MB。每分钟压力场景一天生成 10,000 × 1,440 = 14.4M 条 run；200 B 一条、留七天，是 14.4M × 200 × 7 = 20.16 GB 原始行，三份 60.48 GB。这里用十进制单位，索引、WAL、备份、参数、结果和每次 attempt 的审计都未算。小时级或日级混合任务的历史明显更少，因此不能拿定义条数直接断言元数据有 GB，更不能把这项压力估算当成生产事实。

Storage is separate: 10,000 definitions x 1 KB = 10 MB, or 30 MB for three copies. Every-minute stress produces 10,000 x 1,440 = 14.4M runs/day. Raw rows total 14.4M x 200 B x 7 = 20.16 GB, or 60.48 GB for three copies. These decimal figures exclude indexes, WAL, backups, parameters, results and attempt audits. Mixed hourly/daily jobs have much less history; definition count alone does not justify a GB claim.

认领机制：分片减工作量，事务守住同一火点Claim mechanism: shards reduce work; transactions protect identity

先用 (shard, next_run_at, job_id) 或匹配过滤条件的等价索引找 due，每批最多 100 行。10,000 个同时到期需要 100 批，但每批多久仍由索引命中、锁等待和事务写放大决定。PostgreSQL 的 SKIP LOCKED 能绕过其他事务已锁住的行，适合多个消费者读取队列式表；它不提供一般查询的一致视图，也不自动记住“哪条已经执行”。本章在锁持有期间提交 ready 与游标，拿它做短期认领而非长期执行锁。[1][2]

Use an index such as (shard, next_run_at, job_id), matching the due predicate, and at most 100 rows per batch. An aligned 10,000-row burst needs 100 batches, but duration depends on index access, contention and write amplification. PostgreSQL SKIP LOCKED can bypass rows locked by other consumers of a queue-like table; it is not a general consistent view or execution ledger. Persist ready and cursor while the short claim transaction holds locks. [1][2]

图上两台 scheduler 共用 Schedule DB。逻辑片可用 hash(job_id) 的结果对稳定片数取模，实例只领取其中若干片；扩实例时迁移片归属，不直接拿当前实例数重新取模全部任务。故障恢复与归属迁移允许短暂重叠扫描，因为最终身份和状态在库里收口。16 是 A4 的教学值，不代表需要十六个数据库，更不代表分片算法本身可以避免 split-brain 或旧 owner 恢复。

Both schedulers share Schedule DB. Hash job_id into a stable logical-shard count and assign subsets to instances; scale by moving shard ownership instead of rehashing all jobs against instance count. Recovery and migration may overlap scans because identity and state are enforced in storage. A4’s 16 shards do not mean sixteen databases and do not by themselves prevent split-brain or a stale owner resuming.

替代与失败时行为：先限制并发，再讨论加速Alternatives and failure behavior: bound execution before acceleration

扫描和执行解耦：ready 可大量物化，发送却受 worker 与下游额度约束，积压留库里。允许抖动的巡检可以错峰，业务日期和订单 deadline 不能随意平移。DB 认领压测够用就先拿掉 Redis 锁与时间轮；加组件要解决测到的成本。

Separate materialization and execution: ready backlog remains durable while worker and downstream limits bound dispatch. Jitter may stagger inspections but cannot arbitrarily move business dates or order deadlines. Omit Redis locks and timer wheels when measured database claims suffice; add components to solve measured costs.

监控至少把 due lag、ready 最老年龄、运行租约过期数、重复领取拒绝数与下游错误分开。due lag 变大可能是调度扫描慢；ready 积压可能是执行或下游容量不足。提高 scanner 数量只解决前一类，甚至会给后一类制造更快的积压。迟到 SLO 用 scheduled_at 到实际开始的差，业务完成 SLO 再加 handler 时间；A3 的一秒轮询只贡献检测误差的一部分，不能推成“每个任务最多晚一秒”。

Monitor due lag, oldest ready age, expired execution leases, rejected duplicate claims and downstream errors separately. Due lag may indicate acquisition delay; ready backlog may indicate worker or downstream limits. More scanners help only the first and can worsen backlog growth. Start-lateness SLO measures actual start minus scheduled_at; completion adds handler duration. A3’s one-second poll bounds only part of detection delay, not total task lateness.

租约过期后，旧 worker 仍然可能写A stale worker can still write after lease expiry

正常路径：短事务领取，持久租约执行Normal path: short transaction, durable execution lease

执行租约属于一条 run，不是整个 scheduler 进程。Worker A 用一个短事务把 r7 从 ready 改为 running，设置 owner=A、generation=41、lease_until=DB_now+30s，递增 attempt，再提交。行锁在提交时释放，处理器在事务外工作，避免把数据库连接和行锁占上十分钟。每十秒心跳一次，更新条件仍包括 owner、generation 和尚未过期；不能把无条件续租理解成“只要我恢复就能把旧权利续回来”。

An execution lease belongs to one run. Worker A briefly changes r7 from ready to running, assigns owner A, generation 41 and lease_until = DB_now + 30 s, increments attempt and commits. It executes outside that transaction. Heartbeats every ten seconds condition on the same owner, generation and an unexpired lease; a resumed process cannot unconditionally renew authority that already expired.

r7 已运行 20 秒仍无确定结果，客户端调用超时只影响这一段等待，不代表远端动作没有发生。worker 可以停止继续发送新动作，把状态转为待重试或待查，保留原业务键。若业务动作耗时很长，应该续租和拆出可恢复检查点，而不是让数据库事务一直打开。更长 TTL 能减少误接管，却同时拉长真正崩溃后的恢复延迟，选值要根据观测到的暂停、网络和业务成本，不能靠平均 0.2 秒证明30 秒一定安全。

A 20 s call timeout ends local waiting without proving the remote action failed. Stop sending new actions and retain the original business key for retry or investigation. Long operations need lease renewal and recoverable checkpoints, not an open database transaction. A longer TTL reduces premature takeover but delays real crash recovery; observed pauses, networking and business costs determine it. Mean service time 0.2 s cannot prove a 30 s TTL safe.

故障窗口：接管只改变权利，不停止旧进程Failure window: takeover changes authority, not process liveness

图中 Worker A 长暂停，租约在第 30 秒过期。第 31 秒 Worker B 看见过期行，用 CAS 检查状态、原代次和到期时间，接管同一个 r7，把 generation 推成 42。这两个数字只演示单条 run 的代次，不是从 Redis 随机锁值自动得到的全局 fencing token。重试身份保持 r7，attempt 改变；如果接管者新建另一个 scheduled_at 或 run_id，就绕开了我们原本要保护的同一火点。

Worker A pauses past expiry at 30 s. At 31 s, Worker B checks the state, prior generation and expired lease using CAS, takes over r7 and advances its generation to 42. These numbers are per-run generations, not a global fencing token automatically supplied by a random Redis lock value. Retry preserves r7 while attempt changes; assigning a new occurrence identity would evade the protection.

Worker A 恢复后仍会发送 gen=41 的完成写，所以最后两帧把红线画到 Schedule DB，再把拒绝送回 A。状态更新要满足当前 owner 与 generation 相等、租约尚有效、状态仍是 running，才允许成功或心跳。判断发生在持久提交处，不是在 worker 发送前做一次本地判断。Kleppmann 的 fencing 讨论强调：保护资源的服务必须参与拒绝旧令牌，只有锁服务发号却让资源无条件写入，暂停窗口还在。[4]

Worker A can still send generation-41 completion after resuming. The red path reaches Schedule DB, which returns rejection. Successful completion and heartbeat require current owner and generation, an unexpired lease and running state, checked atomically at persistence. Kleppmann’s fencing discussion requires the protected resource to reject stale authority; issuing tokens without enforcement leaves the pause window intact. [4]

代价与边界：运行状态安全不等于外部副作用安全Cost and boundary: run-state safety is not effect safety

这个 CAS 护栏只证明旧 worker 不能把 r7 改成成功，不能撤销它已经发出的远程邮件或关单请求。若多个 job 都修改同一份共享资源，单条 run 的代次彼此不可比较；真正保护该资源的 fence 必须按资源或同一锁域生成，并在该资源侧验证。本章的订单例子不用假定远端支持调度租约：订单端以 close:o7 和状态条件去重关单，接管后的重试仍走同一键。两种护栏回答的是不同问题，不能把它们合成一句“有 fencing 就只跑一次”。

This CAS prevents stale r7 completion; it cannot retract an already sent email or order-close request. Per-run generations are not comparable across different jobs modifying one shared resource. Fencing that resource needs tokens from a shared authority domain and enforcement there. Our order example instead uses business key close:o7 and an order-state predicate, retaining the key across takeover. Run ownership and effect deduplication answer different questions.

不同火点另设并发策略：独立窗口可以重叠，共享游标用 job 级活动指针。取消已认领任务需要合作，interrupt 撤不回已发出的动作；只取消未开始工作，或由业务存储拒绝旧版本。保存取消请求、未开始、已生效与未知结果，取消不是回滚。

Different occurrences need a concurrency policy: independent windows may overlap; a shared cursor needs a job-level active pointer. Cancellation is cooperative and cannot retract a sent operation. Restrict it to unstarted work or enforce versions at business storage. Persist cancellation requested, not started, applied and unknown separately; cancellation is not rollback.

恢复不能只报 TTL。数据库健康、扫描无积压的理想条件下，30 秒租约加 1 秒轮询约 31 秒后才开始接管，之后还要排队、查询和重试。失去权威主库不能自认持锁继续写；监控可读旧 owner，认领必须读当前权威状态。

Recovery is more than TTL: with healthy storage and no scan backlog, a 30 s lease plus a 1 s poll permits takeover after roughly 31 s, followed by queueing, queries and retries. Authority loss cannot justify continued writes. Monitoring may show a stale owner; claims require current authoritative state.

错过补偿：先定义窗口，再用余量恢复Misfire: define missed intervals, then recover within spare capacity

正常路径：误差阈值与业务策略分开Normal path: lateness threshold and business policy are separate

misfire 是计划火点过了容忍阈值仍未被处理，不等于 handler 已开始后失败，也不等于 ready 还在正常排队。扫描游标保留原 scheduled_at，检测逻辑才能区分“晚一点执行”与“需要丢弃或重放旧窗口”。Quartz 2.3.0 的 JobStoreTX 文档把 misfireThreshold 默认写为 60000 毫秒，也就是 60 秒；这是产品判定常量，不是本章迟到 SLO，更不能机械地等于一个锁 TTL。[5]

Misfire means an occurrence passed a tolerance before scheduling; it differs from an already started handler failing or a ready run normally queueing. Keeping scheduled_at lets policy distinguish ordinary lateness from abandoned or replayed intervals. Quartz 2.3.0 JobStoreTX documents a default misfireThreshold of 60000 ms, or 60 s. That product tolerance is neither our lateness SLO nor automatically one lease TTL. [5]

图的恢复例子只看十个分钟 job，停机区间是 [09:00, 11:00) UTC，包含 09:00 到 10:59 的 120 个火点。十个任务合计 1,200 次；11:00 的正常火点另算，不能首尾都算进去变成 121。下一游标来自原计划序列，而不是恢复机器当前时间随意拼出的新身份。识别漏槽后，再按 job 的策略决定是否物化 run；决定本身也留审计范围和原因，便于事后说明哪个窗口被故意放弃。

For ten minute jobs, outage interval [09:00, 11:00) UTC includes 09:00 through 10:59, or 120 occurrences per job, totaling 1,200. The live 11:00 occurrence is separate; counting both endpoints would incorrectly give 121. Derive the cursor from the original schedule sequence, not a recovering machine’s arbitrary now. Decide materialization per job and audit the missed range and reason, including deliberately abandoned intervals.

三种策略：丢旧、合并、逐窗补齐Three policies: skip, coalesce and replay intervals

skip 只排下一个未来火点，旧窗口记为 skipped，适合每次查看当前状态的巡检与缓存刷新。fire-once-now 在本章定义为合并补一次：选最后一个错过火点作为稳定身份，处理器收到整个遗漏区间，十个 job 共生成十条 run。它要求业务允许一次覆盖遗漏工作；如果 handler 每次只处理单个分钟数据，改成补一次就会悄悄漏掉另外 119 个窗口。不能只因为系统启动压力小，就给计费任务全局套上 skip。

Skip schedules the next future occurrence and audits old intervals as skipped, suitable for current-state checks and cache refresh. Here fire-once-now coalesces a missed range under the latest missed occurrence identity, producing ten runs for ten jobs. The handler must actually cover the entire missed work; a single-minute handler would otherwise drop 119 intervals. Low restart pressure alone does not justify globally skipping billing work.

catch-up 逐个物化原计划槽，保留各自身份，再走同一认领、租约和幂等路径。对账常用业务 watermark 补窗口：处理 [last_success, cutoff)，全部效果持久提交后再推进水位，失败重试沿用旧起点。若分块成功，就按连续完成前缀推进，不能跳过中间失败块。cutoff 要由数据完整性决定，恢复时的 now 不保证渠道文件已齐；因此补窗口减少唤醒次数，却没有免除幂等、完整性与水位事务。

Catch-up materializes original slots with their identities and uses normal claims, leases and idempotency. Reconciliation may instead process [last_success, cutoff), advancing the watermark after durable effects. Chunked work advances only a contiguous completed prefix, never past a failed middle chunk. Cutoff depends on data completeness; recovery time now does not prove upstream reports complete. Window coalescing reduces wake-ups without removing idempotency or watermark correctness.

故障恢复：预算用减法，排空用除法Recovery: subtract live load before dividing backlog

A6 假设共享下游安全预算 100/s，正常负载 80/s，补偿最多拿 20/s。所以 1,200 ÷ (100 − 80) = 60 秒是理想排空下界；不是 1,200 ÷ 100 = 12 秒，后者把正常业务预算抢光了。补偿 token 受全局与每个业务键的限制，执行池有空槽也不能超下游额度。正常流量涨到 100/s，净排空能力变成零；这时应该延迟补偿或调整业务优先级，不能偷偷扩大 worker 并发把数据库一起拖垮。

A6 assumes 100/s of downstream-safe capacity and 80/s live load, leaving 20/s for recovery. Therefore 1,200 / (100 - 80) = 60 s is an ideal drain lower bound, not 1,200 / 100 = 12 s using the whole budget. Global and per-business limits constrain recovery even if worker slots are idle. If live load reaches 100/s, spare capacity is zero; defer recovery or revise priorities rather than increasing concurrency until storage fails.

Airflow 3.0.0 的 DAG Runs 文档明确默认 catchup_by_default=False，逐区间补齐需要开启 catchup；它说明一个公开实现的默认策略，不能推成“所有调度器都默认 skip”，也不能推成 catch-up 已经过时。[6] 正确选择来自业务是否依赖完整区间。对允许丢旧的任务，显式 skip 更容易恢复；对结算，宁可让补偿有可解释的滞后，也不能把系统变绿当成业务数据齐全。图上的三行是不同 job 的互斥策略，不是同一个火点依次运行三遍。

Airflow 3.0.0 documents catchup_by_default=False, with explicit catchup needed for interval replay. This establishes one implementation’s default, not universal skip behavior or obsolescence of catch-up. [6] Business interval requirements decide. Checks may skip old work; settlement may accept visible recovery lag instead of silently omitting data. The diagram’s three rows are alternative per-job policies, not three executions of one occurrence.

重试失败任务和补错过火点还要分开。前者是同一个 run 的新 attempt，保留原 scheduled_at；后者是过去没有物化过的不同火点。达到五次自动尝试就落入持久 failed/review，保留业务键、输入、最后错误和未知结果标记，人工可以查询后重试同一操作。拒绝无限立即重试；退避与抖动减少同步风暴，但不能替代补偿预算，也不能让 unknown 外部效果被当成“已经失败，换个键再做”。

Retrying a failed run creates another attempt of the same occurrence; recovering missed scheduling creates distinct previously unmaterialized occurrences. After five automatic attempts, persist failed/review with business key, input, last error and uncertainty. Manual recovery queries then retries the same operation. Backoff and jitter reduce synchronized retry storms but do not replace admission budgets or justify retrying an unknown external effect under a new key.

延迟任务：内存索引可以丢，截止点不能丢Delayed jobs: the index may disappear; the deadline must survive

正常路径：截止点先持久化，候选再验证Normal path: persist a deadline, then validate candidates

延迟关单在注册时保存 created_at + 30 分钟，也就是 +1,800 秒的 delay_until；一次性任务完成后不再生成下一 cron 槽。数据库有 (state, delay_until, job_id) 等匹配索引时，一秒轮询 due 可以是很小的范围查询，不等于每秒扫全部订单。订单状态查询属于业务处理器，调度库只存叫醒事实。先测量索引范围与批量认领，如果足够就停在这一层，避免把时间轮当成任务调度的必选组件。

Persist delay_until = created_at + 30 min, or +1,800 s, at registration. A one-shot job has no next cron slot after completion. With a matching index such as (state, delay_until, job_id), due polling can be a small range query instead of a full-order scan. The handler owns order-state checks; scheduling stores wake-up intent. Measure indexed claims before making a timing wheel mandatory.

时间轮把近未来候选按 tick 分桶，适合大量近期限、允许近似精度的叫醒。Netty HashedWheelTimer 文档把它定位为近似 I/O 超时调度，并明确 tick 会检查此前到期任务；它不承诺准时业务执行，更不提供本章的持久恢复。[7] 我们只借这个数据结构思想：Schedule DB 仍是权威，Timer index 可以重建。高精度、任意长延迟、跨机器协调与业务失败恢复，不能从“轮里找到一个槽”自动得到。

A timing wheel buckets near-term candidates by ticks. Netty describes HashedWheelTimer as approximate I/O timeout scheduling, checking earlier-due tasks at a tick; it does not provide precise business execution or our persistent recovery. [7] Borrow the structure while retaining Schedule DB as authority and treating Timer index as rebuildable. Finding a slot does not establish precision, long-range timing, distributed coordination or business recovery.

推导与替代：一圈只有一分钟，订单要等三十分钟Calculation and alternatives: one minute horizon, thirty minute delay

A7 的 1 秒一槽、60 槽只覆盖一分钟。1,800 秒取模 60 得到零，代表在 30 圈之后落到当前槽，不代表现在到期。单层轮需要 rounds 与绝对 deadline 再校验；也可以用分层轮，把远期任务逐步移入近窗，或只装载数据库里下一分钟候选。图上统一叫 Timer index，是因为这些方案都只负责加速找到候选，到期谓词仍由 Schedule DB 决定。持久 ZSET 也一样，要把认领与状态变更做原子，不能先 pop 再调用 worker 后才补运行行。

A7’s 1 s tick and sixty slots cover one minute. 1,800 modulo 60 equals 0, but means 30 revolutions later, not due now. A single wheel needs rounds and absolute-deadline validation; alternatives include hierarchical wheels or loading only the next minute from storage. All are Timer index accelerators; Schedule DB decides due eligibility. A persistent sorted set likewise needs atomic claims and state changes rather than pop, dispatch, then record the run.

候选消息带 job_id、版本和 deadline，Scheduler A 回权威行确认未取消、版本仍当前、deadline 确实不晚于 DB_now，再生成唯一 run。改时间或删除任务后，内存轮可能仍有旧槽；版本校验让它变成无效提示。取消已经被认领的任务则存在竞态，不能靠从轮里删掉候选停止已执行的动作。对订单，最终 still_unpaid 与 deadline 条件由 Order DB 同事务判断，付款已确认就返回 no-op，调度器无需在自己的缓存里猜订单是否还未付。

A candidate carries job_id, version and deadline. Scheduler A checks current version, cancellation and due time against the authoritative row before creating a unique run. Old index entries after edits become invalid hints. Deleting a hint cannot cancel already claimed effects. For orders, Order DB atomically checks unpaid state and business deadline, returning a no-op when payment won; the scheduler should not guess payment state from its own cache.

故障窗口：重建未来，还必须扫过期Failure window: reload future work and scan overdue rows

内存轮丢失不应让任务定义丢失。重启先读取数据库中的近未来定义重建索引，再从保存的游标与当前时间之间查 due，按各 job 的 misfire 策略处理遗漏。只装“重启时刻以后”会漏掉停机期间已经到期、又没有下一火点的一次性任务。重建流量也要分页和限速，正常认领不等待全量几十万行装完；同一候选被重建与扫描同时叫醒时，唯一火点和持久状态挡住重复物化。

Losing an in-memory wheel must not lose job definitions. Reload near-future definitions and separately scan due work between saved cursors and current time, applying each misfire policy. Reloading only future tasks loses one-shot deadlines that passed during downtime. Page and limit reconstruction rather than waiting for a complete reload before normal claims. Duplicate hints from rebuild and scanning still pass unique occurrence and durable-state protection.

墙钟日历与经过时间也要分清。cron 定义保存 IANA 时区，物化后的火点保存 UTC；一天固定本地时间与每隔 24 小时并非总是同一序列。夏令时前跳可能不存在某个本地时刻，后退可能出现两次，应在任务定义中明确跳过还是按不同 UTC 瞬间执行。Quartz 的 CronTrigger 教程提醒夏令时切换会跳过或重复某些时间，并支持显式时区；本章不把任何地区的所有调度都简化为每天加 86,400 秒。[11]

Cron stores an IANA timezone while materialized occurrences store UTC. A fixed local daily time is not always an every-24-hour sequence. DST can omit or repeat local instants, requiring an explicit job policy. Quartz’s CronTrigger tutorial warns of skipped or repeated times around DST and supports an explicit timezone. [11] Do not simplify every region’s daily schedule to adding 86,400 seconds.

租约以 DB 时间做条件，单进程超时测量用单调时钟；时钟校正后重新枚举火点，但不改变已经保存的身份。时间回拨不能导致同一版本、同一 UTC 火点重新生成一份 run，向前跳也不能绕过 misfire 策略。数据库时钟大幅漂移会影响接管时机和检测延迟，必须监控并暂停不可靠的动作；数据库中的代次与业务端幂等保护安全性，授时与检测策略保障及时性，两者不能互相替代。

Use database time for lease predicates and monotonic time for process-local elapsed time. Clock corrections may cause re-enumeration without changing saved occurrence identity: backward jumps must not duplicate a UTC occurrence, and forward jumps still require misfire policy. Large authority-clock errors affect takeover and lateness and require monitoring and suspension of unreliable actions. Generations and business deduplication protect safety; clock management protects timeliness.

业务端幂等与 Outbox：让重试不重复生效Business idempotency and outbox: retry without repeating effects

正常路径：业务事务在业务库里闭合Normal path: the business transaction closes in its own database

图中关单命令以 close:o7 作为稳定业务键，同一个订单的任意 attempt 都用它。Worker A 先调用 Order API，订单端在 T2 内原子插入 inbox 键、检查 unpaid 与关单截止条件、修改订单、保存确定结果、插入 outbox e7，提交后才把结果回给 worker。唯一键失败的重复请求读取已存结果，而不是再次应用业务变更。AWS 的幂等 API 讨论强调调用方请求标识与意图校验；同键不同参数要报告冲突，不能把碰巧相同的参数直接等同为相同意图。[8]

Use close:o7 across all attempts to close the same order. Order API transaction T2 inserts the inbox key, checks unpaid status and business deadline, applies closure, saves the result and adds outbox e7. Only then does it reply. Duplicates retrieve the saved result. AWS’s idempotent API discussion distinguishes caller request identity and intent; the same key with changed parameters must conflict, while equal parameters alone do not prove equal intent. [8]

Schedule DB 与 Order DB 是两个事务边界，不能写成“run 成功、订单关闭、Outbox 一起提交”，除非题目明确三者就在同一个事务库。本章 worker 只有在拿到 Order API 的确定结果后，才带当前租约与代次 CAS 完成 r7。如果 T2 成功、回程丢失或 worker 在标成功前死掉，下次还是 close:o7；订单端返回原结果，新的合法 attempt 再完成调度状态。这个恢复步骤解决两库之间的不确定性，没有假装一次本地事务覆盖远程 RPC。

Schedule DB and Order DB are separate transaction boundaries. They cannot atomically commit run success, order closure and outbox unless explicitly colocated. After a confirmed Order API result, the worker completes r7 using its current lease and generation. If T2 commits but reply or run completion is lost, a new attempt calls close:o7 again, retrieves the original result and completes the scheduler state. This repairs uncertainty between databases without claiming one local transaction includes a remote RPC.

通知路径：先提交事件，消费者也要去重Notification path: commit the event and deduplicate at the consumer

Relay 只读 Order DB 已提交的 outbox，再把 e7 交给 Event sink；业务 API 不在提交后直接发一条“尽力而为”的通知。Relay 在发送后、记录已送达前死掉会重投，所以 Event sink 在自己的事务内保存 inbox 事件键与业务效果，提交后才确认。AWS 的 Outbox 原文把同库更新与事件行放同一事务，并指出重复消息需要消费者幂等；本章使用它关闭双写缺口，不把它说成网络恰好交付一次。[9]

Relay reads committed outbox e7 from Order DB and sends it to Event sink, rather than relying on best-effort post-commit API publication. A crash after send but before delivery bookkeeping causes redelivery, so the sink atomically saves its inbox key and effect before acknowledging. AWS’s outbox description pairs same-database updates with an event row and notes consumer idempotency for duplicates. [9] This closes dual-write loss rather than promising one network delivery.

关单 handler 的成功定义是“订单端已经给出可重复查询的关闭或无需关闭结果”，通知完成另看 outbox 的投递进度。已经支付的订单返回 no-op，也可以是一次成功的业务判断；无法确定订单端是否提交则留 unknown/retry，不能把超时变成终态成功。若通知业务要求必须全部发送才算完成，应显式增加等待事件或工作流状态，不把一个 worker 的 accepted 偷换成整条链路完成。状态名必须对应证据，否则重试时不知道该查哪个存储。

Handler success means the order service has a durable, repeatable closure or no-op result; notification delivery has separate progress. An already paid order may produce a successful no-op decision. Unknown order commit after timeout stays unresolved, not succeeded. If all notifications must finish before the job is complete, add an explicit wait or workflow state rather than treating accepted as end-to-end completion. State names must identify evidence and its storage.

替代与边界：哪些效果仍然不能保证一次Alternatives and boundary: effects without an atomic receiver

并非所有外部系统都能把效果与去重键原子提交。邮件服务如果没有幂等发送键，你在本地先标“发过”再发可能丢邮件，先发再标又可能重复；普通 Outbox 只能让发送可恢复，不能证明收件人只收一封。需要供应商幂等接口、可查询的外部对象，或业务接受少量重复，再在文档中写清。不要把数据库关单的证明复制到短信、扣款和任意脚本上；每个接收端都要回答它把去重证据与实际效果放在哪里。

Not every external system atomically couples its effect with a deduplication key. Without an idempotent email-send interface, marking sent before sending risks loss; sending first risks duplication. An outbox makes attempts recoverable, not necessarily one received email. Use provider idempotency, queryable external objects or explicitly accepted duplication. The order-database proof does not automatically apply to SMS, charges or arbitrary scripts; each receiver must name where effect and deduplication evidence are committed.

幂等键的保留期限要覆盖可能的迟到与重试。A8 七天只是终态运行历史查询期，A10 的 close:o7 一直保留到订单归档，不能在删除 run 历史时顺手删掉仍可能重投的业务键。归档后若允许人工重放，先恢复去重证据或以订单终态拒绝修改。故障时“删键再来一次”会解除原本的保护，遇到 unknown 尤其危险。人工修复也沿用原操作键、输入和证据，并且有独立审计；不是绕过唯一约束的后台快捷入口。

Deduplication retention must cover late arrival and retries. A8’s seven days is terminal-run history; A10 retains close:o7 until order archival. Run cleanup must not erase protection for still-redeliverable effects. Manual replay after archival restores evidence or relies on authoritative terminal state to reject changes. Deleting a key to retry removes protection, especially for unknown outcomes. Manual repair retains operation identity and audit evidence instead of bypassing constraints.

Kubernetes CronJob 官方说明可能重复创建或漏建 Job，要求幂等；并发策略仅约束同一 CronJob。[10] 工作流负责多步等待与恢复，Ch34 另管模型选步；它们可以复用定时入口，仍需自己的恢复契约。本章停在独立 job。

Kubernetes CronJob documents duplicate or missing Jobs and requires idempotency; concurrency policy applies within one CronJob. [10] Workflows own multi-step waits and recovery, while Ch34 owns model-selected steps. They may reuse timers while retaining separate recovery contracts. This chapter ends at independent jobs.

口播顺序是：Job API 先把定义持久保存；Scheduler 认领时同事务写唯一火点与 ready 并推进游标；Worker 重试沿用 run_id、租约代次挡住旧完成；业务端用稳定操作键原子提交效果与去重，Outbox 和消费者 inbox 让通知可恢复。万级分钟任务平均 166.7/s，56 槽只说明稳态并发，整分钟突发至少几十秒；定义约 10 MB，七天 run 历史才到 20.16 GB 原始。错过十个 job 的两小时是 1,200 次，余量 20/s 理想排六十秒。

Speak the sequence: Job API durably saves the definition; scheduler claims atomically persist the unique occurrence and ready state while advancing the cursor; workers retain run_id and reject stale completion through generations; receivers atomically commit effects and deduplication under stable keys, with outbox and inbox for notification recovery. Every-minute stress averages 166.7/s; 56 slots describe steady demand while aligned bursts take tens of seconds. Definitions are about 10 MB, seven-day raw runs 20.16 GB. Recovery of 1,200 runs at 20/s takes at least sixty seconds.
