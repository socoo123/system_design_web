 需求与边界：先写操作与分母 Contract: operations and denominators first 
 同一系统可以让账本强读拒绝、购物车接纳分叉、Feed 展示有限旧值。决定落到 数据 × 操作 × 故障 ，不能用品牌代替。每组图是独立场景，A 编号都是教学假设；没有数据库压测或真实故障注入。
 One system may refuse an unsafe ledger read, admit divergent cart additions, and show bounded-stale Feed data. Decide per data × operation × failure , rather than by product name. Decks are separate scenarios; A-numbers are teaching assumptions, without benchmarks or real fault injection.

 CAP：完成写之后的旧读就是反例 CAP: a stale read after a completed write 
 两个活副本在分区两侧都返回本地结果，会产生违反实时先后的历史；等待或拒绝则让出 CAP A。 先看第 3 帧的写 OK，再看第 4 帧后来才调用的读；第 5 帧是替代选择。
 Two live replicas serving local results across a partition can violate real-time order; waiting or refusing sacrifices CAP A. Frame 3 acknowledges the write, frame 4 invokes the later read, and frame 5 shows the alternative.
 先画同一个寄存器的两份副本，初值 x=0。CAP 的前提是副本间的消息无法送达。 Start with two copies of one register, both x=0. CAP concerns unavailable inter-replica messages. 
 第二笔切断 A、B 的消息，两个进程都活着。慢网络与真正分区在有限等待内可能无法区分；超时只是本次操作的决策点，不是证明对端已死亡。 Cut communication while both processes stay alive. A finite timeout may not distinguish slowness from a partition; it is an operation decision, not proof of death. 
 第三笔让 A 完成写 x=1，再给 Writer 成功。这里故意测试“两边继续本地服务”的主张；时间顺序钉死为写已返回之后，另一端才开始读。 Let A complete x=1 and acknowledge Writer, testing the claim that both sides continue local service. The next read starts strictly after this completed write. 
 再画 B 的本地读与回程。没有中间写，完成写之后的读仍返回 x=0，就无法放进遵守实时先后的单一顺序；最终追平也修不掉这次历史。 Add B’s local read and reply. With no intervening write, x=0 after completed x=1 cannot fit a real-time-respecting single history; later convergence cannot repair it. 
 最后补上另一条决策：B 拒绝或等待。错误响应能让工程客户端及时结束等待，却不满足定理中“每个非失败节点上的操作都完成”的 A；正确性保住，可用性让出。 Add refusal/waiting as the alternative. A fast error helps a client stop waiting but does not satisfy CAP A, which requires completion at every non-failed node. 
 C 是历史的安全性，A 是操作的活性 C is history safety; A is operation liveness 
 共享读写寄存器初值 x=0；A 完成 x=1 后 B 才读，无中间写。线性一致要求操作看似发生在调用与返回之间，且遵守已经发生的先后，因此 x=0 不合法。B 无法区分“远端没写”与“远端写完但消息丢了”；最终追平修不掉这次历史。原始 CAP 证明使用 atomic / linearizable consistency。 [1] 
 这里使用异步网络模型，非失败进程仍获公平执行，消息可任意多次丢失，包括持续分区。要求是 所有允许执行 都同时满足两个保证；一个无法两全的执行就能反驳该主张。“不要 P”只能缩窄模型，不能修复仍需面对的跨副本分区。
 The shared register starts at x=0. A completes x=1 before B invokes its read, without an intervening write. Linearizability places each operation between invocation and response, respecting real-time precedence: x=0 is illegal. B cannot distinguish no remote write from a completed one with lost messages. Convergence cannot repair this history. The original CAP proof uses atomic / linearizable consistency. [1] 
 The asynchronous model gives non-failed processes fair execution while allowing arbitrary message loss, including a lasting split. Both guarantees must hold in every allowed execution ; one conflicting execution defeats the claim. Excluding P narrows the model without repairing partitions the design still has to handle.
 “最终完成”没有一秒期限 Eventual completion has no one-second bound 
 CAP A 要求非失败节点接到的操作最终完成，不给固定延迟上限。快速 503 没有完成寄存器读写；十分钟后正确返回也可能违反产品的一秒 SLO。有限超时不能证明对端已死。工程上按操作决定拒绝范围与恢复流程，不是“选 CP 就整站停”。 [1] [2] 
 线性一致不等于 ACID 的 C，也不自动给跨键事务。两次“强读余额，再分别扣款”仍可能越过余额不变量；扣款的原子条件与幂等身份见 Ch18 / Ch24。
 CAP A requires eventual completion at each non-failed node without a fixed latency limit. Fast 503 does not complete a register operation; a correct ten-minute reply may fail a one-second SLO. A finite timeout cannot prove remote death. Specify per-operation refusal and recovery rather than assuming every CP split stops the whole site. [1] [2] 
 Linearizability differs from ACID C and does not supply multi-key transactions. Two fresh balance reads followed by separate debits can still violate an invariant; Ch18 / Ch24 cover atomic debit and idempotent identity.
 保一致：提交与强读都需要证明 Preserve consistency: prove commit and strong reads 
 A/B 多数派可继续提交，隔离 C 拒绝新写和没有屏障的强读。 第 2–3 帧展开一笔当前任期记录：A 持久、B 持久 ACK、按协议提交并应用，最后 A → API → Client 返回。
 A/B can commit as a majority; isolated C refuses new writes and unproven strong reads. Frames 2–3 expand one current-term entry: A persists, B durably acknowledges, the protocol commits/applies, then replies A → API → Client.
 先画 Client → API → Replica A。写入 leader 本地日志还不是提交；客户端超时也不能直接推出失败，必须保留相同业务键查询结果。 Start Client → API → Replica A. A local leader log is not commit; a timeout requires checking the same business key rather than assuming failure. 
 加 B 的日志和持久 ACK：三票里的两票构成多数派。共识还要有任期、日志顺序与提交规则；这张图讲一笔当前任期写，不能只凭“两个 ACK”宣布实现了 Raft。 Add B’s durable ACK: two of three votes form a majority. Terms, log order and commit rules remain required; this depicts one current-term write, not all of Raft. 
 确认只从 A 经 API 逐跳回 Client。C 被隔离不妨碍 A、B 提交，保一致的系统仍可在多数派继续服务；CP 并不等于“一断网全站停机”。 The result returns A → API → Client. Isolated C does not stop majority A/B commit; preserving consistency need not stop the entire site. 
 补少数派入口和拒绝回程。C 不能发新写或无证明的强读；若允许 serializable 本地旧读，必须单独声明弱语义，不能算进线性一致的承诺。 Add minority refusal. C cannot serve new writes or an unproven strong read; optional stale local reads need an explicitly weaker contract. 
 完整图加恢复约束：旧 leader 被新任期挡住，未知写先查 k7。共识保提交历史，业务唯一键保一次扣款；网络恢复不会自动消掉已执行但丢回包的副作用。 Complete recovery with term rejection and k7 lookup. Consensus protects commit history; a business key protects one charge. Reconnection cannot erase a lost-result effect. 
 关键实现：成功、未知、不可用分开返回 Implementation: separate success, unknown, and unavailable 
 以下是 操作契约伪代码 ，覆盖第 3–5 帧并预告下一组购物车。 Consensus 是完整外部共识：任期、选举限制、日志匹配、当前任期提交规则由它执行，不是“两个 ACK”或本地锁。 proposeAndApplyOnce 在同一复制状态机内校验 id/payload，把业务效果与持久回执一起提交。真实账本若在另一数据库，必须使用那里的原子约束，不能借此接口跨事务域。 [5] 
 This operation-contract pseudocode covers frames 3–5 and previews the cart. Consensus implements full terms, elections, log matching, and current-term commit rules rather than two ACKs or a local lock. proposeAndApplyOnce checks id/payload and commits effect/receipt in one replicated state machine. A separate business database needs its own atomic effect/receipt constraint; this interface does not span transaction domains. [5] 
 # Teaching contract; Consensus is a real external protocol, not a local lock.
strongWrite(id, payload, deadline):
 # applyOnce checks id+payload and stores receipt+effect in one state machine.
 result = Consensus.proposeAndApplyOnce(id, payload, deadline)
 if result == COMMITTED:
 return OK(result.receipt)
 if result == ID_REUSED_WITH_OTHER_PAYLOAD:
 return CONFLICT
 # A timeout/no quorum does not prove that an earlier attempt did not commit.
 return UNKNOWN(id) # retry/query with the same id and payload
strongRead(key, deadline):
 # Barrier validates current leadership and obtains a safe commit index.
 index = Consensus.readBarrier(deadline)
 if index is unavailable or not waitApplied(index, deadline):
 return UNAVAILABLE
 return StateMachine.readAtLeast(key, index)
addOnlyCart(id, item):
 # One local durable transaction: unique id+payload, add, and retry receipt.
 # A failed/unknown local commit returns UNKNOWN, never a fabricated OK.
 return LocalStore.commitOnce(id, ADD(item))
healCart(left, right):
 merged = left.items UNION right.items # add-only contract; no removes
 persistAndRetryBoth(merged) # delivery may retry; union is idempotent 
 失败边界： 无多数派或超时可能掩盖已提交结果，因此写返回 UNKNOWN，保留原 id/payload 查询/重试。强读拿不到领导权与提交位点证明就 UNAVAILABLE；还必须等本地应用到该位点，不能只读本地最新行。恢复后旧任期被挡住，也不代表支付回包与外部效果已经对账。
 etcd 3.6 的 KV 操作通常默认线性一致；显式 serializable 读可接受相对 quorum 的旧数据。Watch 另有语义，不能泛称所有 API 都是强读。本章未运行 etcd 集群。 [6] 
 Failure boundary: no quorum or timeout can hide commit, so writes return UNKNOWN and retain the original id/payload for recovery. Strong reads without leadership/commit proof return UNAVAILABLE and await local application through that index. Reading the newest local row is insufficient. Term rejection does not reconcile external effects or lost payment replies.
 etcd 3.6 KV operations normally default to linearizability; explicit serializable reads accept data stale relative to quorum. Watch has separate semantics, without a blanket strong-read guarantee for every API. No etcd cluster was run here. [6] 
 保服务：允许分叉，就定义合并 Preserve service: define how divergence merges 
 两侧接纳 add-only 购物车加入，恢复时并集并写回双方。 成功是本地持久接纳，尚未承诺所有端点立即看到同一列表。
 Both sides admit add-only cart additions, then union and persist the merge to both copies on healing. Success means local durability without immediate agreement at every endpoint.
 先画允许本地成功的购物车契约。A 加 apple 即返回，副本间当前不通；它承诺保存本地版本，不承诺所有端点马上看到同一份列表。 Begin with a locally successful cart contract. A accepts apple despite blocked communication; it preserves a local version, not immediate agreement across endpoints. 
 再加 B 的 bread 与独立回程。两个成功并不等于产生一个总序；冲突处理要理解“同时加入不同商品”，不能按最后到达的字符串覆盖整份购物车。 Add B’s independent bread write/reply. Two successes do not create a total order; whole-cart last-arrival replacement could discard a valid item. 
 恢复后汇集两份版本。Merge 是应用合并步骤，图为本次并发加入选集合并集；如果操作含删除或数量减少，单纯 union 会复活商品，必须换规则。 On recovery, gather both versions. Merge is application reconciliation; union works for this add-only example, while remove/decrement needs a different rule. 
 补合并结果写回 A、B，闭合恢复流程。追平以通信恢复、重试和冲突规则为前提；“最终一致”没有自动给出五秒内追平，更不能把之前的分叉改称线性一致。 Return the merge to A/B. Convergence assumes restored communication, retries and a resolution rule; eventual consistency gives no automatic five-second bound or retroactive linearizability. 
 最后把 quorum 边界写在完整图旁：2+2−3=1 仅证明固定集合有交点；2+1 分区时，单节点一侧凑不齐 W=2/R=2，所以“掉一台还工作”不等于 CAP 的每个活节点都可用。 Add the quorum boundary: 2+2−3=1 proves fixed-set overlap only. In a 2+1 split the singleton cannot meet W=2/R=2, so surviving one failure does not imply CAP A. 
 第 3–4 帧闭合“收集版本 → 合并 → 写回”。 LocalStore.commitOnce 的本地事务绑定操作身份与加入效果；磁盘失败仍可能 UNKNOWN。union 仅适用于纯加入，删除会复活，数量减少还需其他规则。收敛依赖通信恢复、重试与合并规则，没有自动五秒保证。Dynamo 支持版本/应用协助合并，也说明 sloppy quorum 临时节点可能不在原偏好集合内。 [4] 
 Frames 3–4 close collection, merge, and persistence. LocalStore.commitOnce binds operation identity and addition in one local transaction; failed persistence can remain UNKNOWN. Union fits additions but can resurrect removes; decrements need further rules. Convergence requires restored communication, retries, and merge rules, without a five-second bound. Dynamo describes versioning, application-assisted reconciliation, and sloppy-quorum temporary nodes outside the preferred set. [4] 
 交点不等于线性一致：读先新后旧 Overlap is insufficient: a newer read followed by an older read 
 固定 N=3、W=2、R=2，交点至少 2+2−3=1。下面 可运行 Python 反例 允许读到未凑齐 W 的版本，读在返回前不 writeback：R1 读 A/B 得 x=1；R1 返回后，R2 读 B/C 得 x=0。把未完成写排在 R1 前会让 R2 错，排在 R1 后会让 R1 错。交点始终存在，历史仍不合法。
 Fixed N=3, W=2, R=2 ensures overlap ≥2+2−3=1. This runnable Python counterexample exposes a version before W completes and returns reads without writeback. R1 reads A/B and gets x=1; after R1 returns, R2 reads B/C and gets x=0. Placing the pending write before R1 makes R2 wrong, and placing it after R1 makes R1 wrong. Overlap persists but the history is illegal.
 def quorum_without_writeback():
 # N=3, W=2, R=2; one immutable version order, no failures of local memory.
 replicas = {"A": (0, "x=0"), "B": (0, "x=0"), "C": (0, "x=0")}
 replicas["A"] = (1, "x=1") # W has only one ACK: the write is pending
 r1_members = {"A", "B"}
 r2_members = {"B", "C"}
 assert len(r1_members & r2_members) == 1
 r1 = max(replicas[n] for n in r1_members)
 # R1 responds x=1; it does NOT write that version back before returning.
 r2 = max(replicas[n] for n in r2_members) # R2 starts after R1 responds
 assert (r1[1], r2[1]) == ("x=1", "x=0")
 # Place pending write before R1 and R2 is wrong; after R1 and R1 is wrong.
 # There is no second write that could restore x=0.
 return {"R1": r1[1], "R2_after_R1": r2[1], "linearizable": False} 
 边界： 这是确定性本地历史重放，不是分布式实现或不可能性证明。完整协议可组合版本规则、读屏障/返回前写回实现更强保证；这里只否定“一个交集公式就够了”。2+1 分区时单节点仍凑不齐 W=2 / R=2，从多数派可服务不等于每个活节点满足 CAP A。Ch06 固定/宽松 quorum 的边界与此一致。
 Boundary: this deterministic local history is neither a distributed implementation nor an impossibility proof. A complete protocol can add version rules, barriers, or writeback before returning to establish stronger guarantees; overlap alone is insufficient. A 2+1 singleton cannot meet W=2 / R=2. Majority service does not establish CAP A at every live node, consistent with Ch06’s fixed/sloppy quorum boundaries.
 PACELC：复制确认影响日常延迟 PACELC: replication barriers affect everyday latency 
 P 时讨论可用/一致；Else 时，复制系统仍在延迟/一致性之间选择。 这是设计框架，不是产品出生标签。Abadi 的 2012 论文明确 Else 的复制背景；下面只比较持久屏障，远端 ACK 本身不能证明线性一致。 [3] 
 P asks about availability/consistency; Else asks about latency/consistency in replicated systems. This framework is not a permanent product label. Abadi’s 2012 paper gives the replication context for Else. These durability barriers alone do not establish linearizability. [3] 
 先画本地持久成功的闭环。教学模型只计 API/接入合计 2 ms 与本地持久 1 ms，得到 3 ms；这是条件算术，不是某数据库 p99 的测量。 Start with local durability and the full return path. Assumed overhead 2 ms plus persistence 1 ms gives 3 ms, a conditional calculation rather than a measured p99. 
 加远端复制，早确认不等 B。代价是 B 可能尚无这笔写；若 A 在追平前永久丢失，故障切流还可能丢已确认写，单机持久并不代表跨地域零 RPO。 Add remote replication outside the acknowledgment barrier. B may lack the write; losing A before catch-up may lose acknowledged data during failover. 
 第三笔只改确认门槛：同步等 B。假设本地与远端并行，2+max(1,4+1)=7 ms；RTT 变 80 ms 后是 83 ms。若过程串行或协议多轮，就要重算，不能把这数说成通用上限。 Change the success barrier to B durability. Assuming parallel work, 2+max(1,4+1)=7 ms; RTT 80 gives 83 ms. Serial work or extra rounds requires a new calculation.

 SLI：先定义一个旅程怎样算 good SLI: define a good journey first 
 一秒内得到正确、持久的结账终态决策才 good；同 checkout_id 的重试共享原期限。 合法拒付可满足“决策可用”，不是支付转化成功。UNKNOWN、503、202 pending、错误结果或超时都不是 good。
 A good journey receives a correct, durable terminal decision within one second; retries share the original checkout_id deadline. A valid decline can satisfy decision availability without payment conversion. UNKNOWN, 503, pending 202, incorrect results, and late replies are not good.
 先画用户边界。一个实例健康不代表结账成功，Edge 拿到 200 也不代表正确入账；先规定一秒内给正确且持久的结果，再决定哪些事件算 good。 Start at the user boundary. Process health and HTTP 200 do not prove checkout success; define a correct durable outcome within one second before counting good events. 
 加入账本与逐跳回程。写已提交却回包丢失，业务仍可能成功，但本次用户旅程未知或超时；服务可用性与事后正确性要分开记录，重试保持同一 checkout_id。 Add Ledger and hop-by-hop replies. A lost post-commit response may leave the user journey bad while business settlement succeeded; preserve the checkout_id on retries. 
 加两个计数器：eligible 在看到结果前按契约确定，good 还需满足结果与期限。本例以 checkout_id 去重重试；若换成请求级 SLI，分母与告警都要一起换。 Add eligible/good counters. Eligibility is determined before outcome; good additionally satisfies result/deadline. This logical SLI deduplicates checkout_id retries. 
 补故障回程，账本错误经 API、Edge 到 Client。拒绝未知扣款保护正确性，但仍消耗可用性预算；既不能把 503 移出分母，也不能把 UNKNOWN 改名为成功来保报表。 Add the full failure return. Refusing an unconfirmed debit protects correctness but spends availability budget; neither exclude 503 nor relabel UNKNOWN as success.

 关键实现：原始时间、去重、完整 cohort Implementation: original time, deduplication, complete cohorts 
 Python 输入是可信入口的 Attempt ：原始 started_ms、固定 eligible、观测时间、终态与独立核实的 correct/durable 标志；不是凭 200 猜测。相同身份不同参数在业务入口拒绝。按 id 合并后，取 cutoff=now−1000 ms ，只数原起点在 (cutoff−W,cutoff] 的完整 cohort，报表落后一秒。重试改起点/eligibility 是数据质量错误。
 Trusted ingress Attempt records retain original started_ms, fixed eligibility, observation time, outcome, and independently verified correct/durable flags; HTTP 200 supplies neither. Business ingress rejects identity reuse with different parameters.  def counts(attempts, now_ms, window_ms):
 if window_ms <= 0:
 raise ValueError("window must be positive")
 cutoff = now_ms - DEADLINE_MS # complete cohorts; one-deadline lag
 groups = {}
 for a in attempts:
 groups.setdefault(a.checkout_id, []).append(a)
 eligible = bad = 0
 for rows in groups.values():
 first = rows[0]
 identity = (first.started_ms, first.eligible)
 if any((r.started_ms, r.eligible) != identity for r in rows):
 raise ValueError("retry changed original start or eligibility")
 if not first.eligible or not cutoff - window_ms < first.started_ms <= cutoff:
 continue

 关键实现：同口径计数与显式无数据 Implementation: consistent counts and explicit no-data 
 可运行 Python 消费上一函数的月窗与四个短窗 (eligible,bad) 。 BAD_PPM=1000 、 SCALE=1,000,000 表示 99.9%；整事件向下取整，burn 用有理数。它只门控功能放量；安全/紧急可靠性修复走另一个经审查的政策通道，不能把功能发布改名为修复绕过。

 def budget(eligible, bad):
 if not (0 <= bad <= eligible):
 raise ValueError("invalid counts")
 if eligible == 0:
 return None # no data, never 100% success
 allowed = eligible * BAD_PPM // SCALE # maximum whole bad events
 return {"remaining": allowed - bad, "allowed": allowed,
 "burn": Fraction(bad * SCALE, eligible * BAD_PPM)}
def feature_gate(month, windows, telemetry_complete, canary_healthy, reviewed):
 # All inputs use the same SLI, cohort cutoff, and service scope.
 monthly = budget(*month)
 rates = {name: budget(*windows[name])
 for name in ("1h", "5m", "6h", "30m")}
 if not telemetry_complete or monthly is None or any(v is None for v in rates.values()):
 return "HOLD_NO_DATA"
 if monthly["remaining"] <= 0:
 return "FREEZE_FEATURES"
 burn = {name: value["burn"] for name, value in rates.items()}
 page = ((burn["1h"] > Fraction(72, 5) and burn["5m"] > Fraction(72, 5))
 or (burn["6h"] > 6 and burn["30m"] > 6))
 if page:
 return "HOLD_BURN"
 if not (canary_healthy and reviewed):
 return "HOLD_REVIEW"
 return "ALLOW_NEXT_CANARY_STEP" # reviewed repair uses a separate policy path

 CAP 的 C 具体是什么？ What is CAP C? 遵守实时先后的原子读写历史；不是最终一样，也不是 ACID C。 An atomic read/write history respecting real time, not eventual agreement or ACID C. 
 快速 503 满足 CAP A 吗？ Does fast 503 satisfy CAP A? 不能完成寄存器操作；它只让客户端及时知道不能服务。 No; refusal does not complete the register operation, though it informs the client promptly. 
 CP 分区时全站都停吗？ Does a CP split halt the entire site? 三成员的 A/B 两票仍能提交；隔离 C 的新写与无证明强读拒绝。 Two of three A/B can commit; isolated C refuses new writes and unproven strong reads. 
 写超时能换一个业务键重试吗？ May a timeout retry use a new business key? 先查原键，可能已提交但丢回包；新键可能重复副作用。 Query the original key: a lost reply may hide commit, and a new key can repeat effects. 
 W=2、R=2、N=3 证明了什么？ What does W=2/R=2/N=3 prove? 固定集合交点至少 1；无返回前修复仍可先新后旧，不证明线性一致或少数派可用。 Fixed-set overlap ≥1; without return-time repair reads can regress. It proves neither linearizability nor minority availability. 
 购物车为什么不总用 union？ Why not always union carts? 只加入可合并；删除会复活，数量变化要另定因果规则。 Add-only merges work; removes may resurrect and quantity changes need causal rules. 
 并行同步复制的条件延迟？ Conditional parallel replication latency? 2+max(1,RTT+1)，RTT 4/80 ms 对应 7/83 ms；不是 p99 实测。 2+max(1,RTT+1): 4/80 ms RTT gives 7/83 ms, not measured p99. 
 202 待处理算完成结账吗？ Does 202 pending complete checkout? 不算；若改异步旅程，另立持久接单与完成期限的 SLI。 No; an async journey needs separate durable admission and completion-deadline SLI. 
 一千万事件、99.9%、6,000 bad 剩多少？ 10M events, 99.9%, 6,000 bad: balance? 允许 10,000，剩 4,000=40%；达成率另为 99.94%。 Allow 10,000, retain 4,000=40%; achieved SLI is separately 99.94%. 
 43.2 分钟适用于什么？ When does 43.2 minutes apply? 30 天时间 SLI；请求预算要按事件，峰值不能直接换分钟。 A 30-day time SLI; request budgets use events and cannot ignore traffic peaks. 
 99.9% 下 1% 错误的 burn？ Burn at 1% bad for 99.9% SLO? 10 倍；稳态完整预算三天，剩 40% 约 1.2 天。 10×; stable-rate full budget lasts three days, 40% about 1.2 days. 
 双窗口怎样组合，回退退预算吗？ How combine windows; does rollback refund budget? 每对 AND、两档 OR；坏事件仍在窗口，回退先验兼容，修复后复评。 AND within pairs, OR across pairs; bad remains, check rollback compatibility and review repairs.
