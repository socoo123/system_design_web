## 技术更正与实现边界

| 原问题/遗漏 | 更正与保证 |
|---|---|
| 用户平均粉丝F=200直接用来算发帖工作 | A3明确为“按发帖加权”的平均F。若热门作者更频繁发帖，用户均值不能代替该值；契约验证给出两者不等的反例 |
| 发布幂等/原子提交只有文字 | PostgreSQL `publish_key(author_id,idem_key)`主键裁决并发，同库Post/回执/Outbox一次提交。唯一冲突先ROLLBACK，再用主库新语句读胜者；COMMIT未知丢连接、503、同key重试，24h保留窗口明确 |
| Worker输出与检查点的故障窗口未实现 | task以event_id唯一，固定模式和可保留的粉丝快照。持久输出后才CAS检查点；各输出库的(user_id,post_id)/(author_id,post_id)唯一键吸收重放。没有跨片大事务，也不拿published_at当任务完成 |
| 粉丝分页在变化关注图上可能漏 | Graph分页要求同一个稳定且可恢复的快照；失效显式修复。异步反向索引需变更日志与对账，不能靠一个cursor宣称无漏 |
| 模式切换只补历史，缺最后写入屏障 | 模式行和发布读锁协调；排他锁下固定最后旧代际提交位点并切新代际，补追最终位点后才激活新读模式。旧模式事件继续完成；旧来源保留到读窗口退出 |
| “新关注从关注时刻开始”与pull历史读取矛盾 | 改成明确的保留窗口历史补建契约：先注册pending边供新事件纳入，再补历史并追到登记后的作者提交位点，完成才激活follow_version，构建中503。无跨库物理时钟精确排序承诺 |
| 重视图刚构建就被当作新鲜，cursor签名被当作快照 | 所有来源水位通过才声明新鲜度。视图不可变，cursor绑定user/version/snapshot；缺源503，版本变409，过期410/刷新，不偷偷换快照 |
| 固定快照被当作迟到扇出的完整解 | 固定快照只固定包含的集合；严格历史完整还要所有来源追到选定提交位点。当前页seek允许晚扇出在刷新后出现 |
| cursor的实际消费边界没有实现 | Java全序堆归并，最多5×limit来源行（含重复）；删除/权限过滤仍前移。第23个候选填满一页只推进至23，未消费预取不跳过；空页也校验权限版本 |
| “回源2s截止+TTL25s≤27s”缺远端晚SET/响应边界 | token的epoch、代际、安装截止由缓存端执行时原子校验；API超时不取消排队SET。只用主库新语句；固定TTL不续期，最坏缓存驻留27s，再计响应≤2s约29s。缓存重启/元数据淘汰不复用旧token |
| 缓存正文被误当权限凭证的风险 | post:{id}共享正文不能授予权限。返回前检查当前follow/block版本，权限服务不可用失败关闭；私密/立即撤回另查权威，不沿用普通删除宽限 |

代码是教学接口，不是完整后端工程。`schema.sql`的带参数seek语句需要服务层绑定；`FeedPage.java`只提供归并、过滤和预算内核，外围Source/View/Bodies适配器承担签名、用户/版本、保留窗口、完整来源、权威权限、不可变快照及超时契约。源码中未用本地锁冒充分布式事务。

## 容量独立复算

- 峰值占30k整层38.5802%，净余18,425.9259行/s；60k backlog理想排空下限3.2563s，未含偏斜/重试/副本故障。
- 纯pull平均462,962.9630次作者探测/s；hybrid K=8尾部峰值92,592.5926/s。两者都可以缓存，不能把batch算成免费存储工作。
- 指针工作集128GB（十进制）；复制每行1KB正文为2TB，约15.625倍。正文365天三份逻辑量1.095TB，索引/媒体/备份等另计。
- 正常正文点查2,314.8148+1,160=3,474.8148/s；低于假设4k。缓存失效希望回源231,481.4815/s，为预算57.8704倍。
- 20条完整页最多200/s，50条最多80/s，且取Timeline预算较小者；补页按实际点查扣费。200k日读错误预算在固定峰值缓存故障下约17.58385s用尽。限流不证明99.9%可用性。

## 一手引用与支持范围

2026-10-23实际浏览核对，网页/论文链接在对应正文附近：

1. [TAO原论文](https://www.usenix.org/system/files/conference/atc13/atc13-bronson.pdf) §3：对象、关联、有序关联列表，支持关注图的访问方向；不当作本章feed实现或吞吐证明。
2. [Redis ZADD](https://redis.io/docs/latest/commands/zadd/)：已有成员更新score、同score字节序、double精度限制。并不提供本文持久输出约束或缓存lease API。
3. [Kafka 4.1 Design](https://kafka.apache.org/41/design/design/) Message Delivery Semantics：Kafka内部事务可涵盖offset/topic输出，外部输出需要目标系统协作；本文选择持久幂等，不声称队列开关可包住所有inbox。
4. [Scaling Memcache at Facebook](https://www.usenix.org/system/files/conference/nsdi13/nsdi13-final170_update.pdf) §3.2.1：lease token随delete失效、防stale set；本文epoch/安装截止/固定TTL/29s是额外自设契约，没有借用论文旧性能数字。
5. [PostgreSQL 18 LIMIT/OFFSET](https://www.postgresql.org/docs/18/queries-limit.html)：LIMIT需要唯一确定顺序；OFFSET跳过行仍要计算。5×limit预算是本章决定。
6. [Transactional outbox原模式](https://microservices.io/patterns/data/transactional-outbox.html)：业务与消息同事务、独立relay、发送后未标记可重复发布；本章另设300ms与24h假设。
7. [PostgreSQL 18 Row Comparisons](https://www.postgresql.org/docs/18/functions-comparisons.html) §9.25.5：非空tuple按字段从左至右比较，支持(time,id)排他上界；不是快照完整性保证。
8. [PostgreSQL INSERT](https://www.postgresql.org/docs/18/sql-insert.html) / [Transaction Isolation](https://www.postgresql.org/docs/18/transaction-iso.html)：唯一索引并发冲突、ON CONFLICT及READ COMMITTED新语句快照。冲突后读胜者需新语句，不在失败事务继续查。
