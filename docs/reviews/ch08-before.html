30 秒开场：先问双跑会造成什么 The 30-second opening: what does double execution cost?

我先问同一任务双跑是多算一次，还是会写坏共享状态。前者可以用已有 Redis 的 SET NX PX 加随机 owner，解锁原子比对；后者先看数据库唯一约束、条件更新或事务能否完成。确实需要跨系统协调时，再用可靠协调器发递增世代，资源端原子验号。下面讲三处窗口：过期后的旧写、未复制就切主、看门狗随进程暂停。锁只协调谁能开始，最终写是否成立由资源端决定。

“写库就必须加分布式锁”也是误判。两次计算同一张缩略图，最后覆盖同样内容，可能只浪费 CPU；两次支付若共享幂等请求号，并由账本事务保证只记一笔，也不一定需要外部锁。反过来，只在内存里做计算，但重复计算会触发不可撤销的远端调用，就不能因为没有本地 SQL 把它归成效率锁。要追踪最终副作用。

效率锁的契约是“尽量减少重复”，协调层短暂失效时允许双跑，业务结果仍合法。正确性要求则是库存不为负、同一业务请求不重复记账、过期领导者不能覆盖新状态。这些是不变量，面试时要写成能由存储检查的条件，不能用“全局互斥”四个字替代证明。Kleppmann 用效率与正确性来区分锁的用途，本章按这个问题顺序组织。[9]

澄清先收成五个问题：资源粒度是什么，结果能否幂等，临界区通常多久、最长多久，已经有什么协调或存储服务，拿不到锁要立即失败还是等候。若对方要求公平、可重入、阻塞等待，再分别补契约。默认先做不可重入的 tryLock；多地域共识、Raft 日志和选主过程留作后续深入，主线只讲调用方与资源端的行为。

I first ask whether duplicate execution wastes computation or corrupts shared state. For the former, use an existing Redis with SET NX PX, a random owner, and atomic release. For the latter, first try database uniqueness, conditional updates, or a transaction. If coordination across systems is necessary, a reliable coordinator issues ordered epochs and the resource validates them atomically. Then cover old writes after expiry, failover before replication, and a watchdog paused with its process. Coordination admits work; the resource decides which mutations are valid.

A database write does not automatically require a distributed lock. Duplicate thumbnail computation may only waste CPU. A payment ledger can use a shared idempotency key and one transaction to record a single effect. Conversely, computation that triggers an irreversible remote call can require correctness even without local SQL. Follow the final side effect.

An efficiency lock reduces duplicate work while accepting occasional overlap with legal results. Correctness invariants include nonnegative inventory, one ledger effect per operation, and no stale leader overwriting new state. Write these as enforceable predicates rather than relying on the phrase “global exclusion.” Kleppmann distinguishes efficiency from correctness uses; this chapter follows that question order. [9]

Ask five questions: resource granularity, idempotency, typical and maximum duration, existing coordination/storage, and fail versus wait on contention. Add fairness, reentrancy, or blocking only when required. Start with a nonreentrant tryLock; keep consensus internals and multi-region election outside this core discussion.

一条命令拿锁，原子比对再释放 Acquire in one command; release with an atomic owner check

正常路径：owner 只标识这次持有 Walkthrough: the owner identifies this acquisition

同一个 SKU 的竞争都使用 lock:sku:7，每次尝试产生新的随机 owner。A 用一条 SET 写 owner a 与过期时间，NX 让存在的键不能被覆盖；Redis 1 返回 OK，A 才执行临界区。B 的 NX 返回未成功，就退出或按约定等待。资源粒度决定串行范围：锁住整张库存表会把不同 SKU 也排在一起，锁到每个 SKU 才只合并真正的竞争。[1]

图里的第三步绕过 Redis，直接从 Worker A 写 Primary，再收到提交结果。锁服务并不代理数据库写，也看不到 SQL 是否成功。完成后 A 比较当前 owner 与 a，一致才删除，得到释放结果；B 的后续尝试再成功为 b。编号表示先后事件，之前的 OK 与 busy 是完成过的历史，不表示两个人在正常路径里同时持有。

All contenders for one SKU use lock:sku:7 and each attempt has a fresh random owner. SET writes a and expiry together; NX prevents overwriting an existing key. A works only after OK, while B exits or waits as agreed. A table-wide key serializes unrelated SKUs; per-SKU keys isolate actual contention. [1]

Step 3 writes from Worker A directly to Primary and receives commit. Redis neither proxies SQL nor observes its result. A then atomically deletes only if the current owner is a. B’s later attempt becomes b. Event numbers show chronology; prior OK and busy replies are completed history, not simultaneous normal ownership.

SET lock:sku:7 <random-owner> NX PX 10000

为什么获取、解锁都要原子 Why acquisition and release must be atomic

SETNX 后再 EXPIRE 的错误不在“多一次网络”，而在两条命令之间可崩溃：存在的键没有过期，后来的 Worker 会一直失败，直到有人明确清理。原子 SET NX PX 消除这个特定窗口，代价是客户端必须解释三类结果：明确成功、明确 busy、结果未知。收到超时不能当成没写入；获取可能已执行而 OK 丢了，此时不开始业务，等待过期或用自己的 owner 安全清理。

裸 DEL 更危险。A 的租约过期，B 已把键设为 b；A 的 finally 到达后若直接删除，就会删除 B 的有效租约。先 GET 确认再 DEL 仍是两步：GET 看见 a，随后 a 过期且 b 成功，最后 DEL 删掉 b。下面的 Lua 把比较和删除放在 Redis 的同一个原子执行窗口，返回 0 表示当前不是自己；返回 0 不能推导成“业务也一定没发生”。[2]

SETNX followed by EXPIRE leaves a crash window with a key that never expires. Atomic SET NX PX removes that window. The caller must still distinguish success, busy, and unknown results. A timeout may mean acquisition executed but its reply was lost. Do not begin business work on an unknown result; wait for expiry or safely clean up your own owner.

A raw DEL can delete B’s valid lease after A expires. Separate GET and DEL also race: GET sees a, then a expires and b acquires before DEL. The Lua comparison and deletion share one atomic execution window. A zero return means the key is not yours; it says nothing about whether your business mutation happened. [2]

if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0

pipeline 只减少往返，不把多条命令自动变成同一个原子判断。Lua 能保证本 Redis 实例上这段执行不被其他命令插入，却不会把业务库和 Redis 合成一个事务。当前 Redis 文档还提供 8.4 起的 DELEX key IFEQ owner；旧版本保留 Lua。两者都解决“只删自己的 owner”，都没有赋予随机串一个可比较的新旧顺序。[11]

Pipelining reduces round trips but does not make the decision atomic. Lua serializes this script on one Redis instance; it does not create a transaction with the business database. Current documentation also provides DELEX key IFEQ owner since Redis 8.4, with Lua for older versions. Both check ownership equality, not epoch ordering. [11]

容量与替代：先算命令，再看热点 Capacity and alternatives: count commands, then inspect the hot key

A1 的 1,000 次首次尝试包含 800 成功与 200 busy。每个成功再解锁一次，所以固定 TTL 的命令量是 1,000+800=1,800 次/s，不是笼统的“一千次加解锁”。若 200 个失败者各多试三次，新增 200×3=600 次/s，总量变成 2,400。若还有 60 个长期持有者每 10 s 续一次，平均再加 60÷10=6 次/s；实际重启与批量调度会让续租同一刻扎堆，平均值不能代替峰值。

单个热键更早限制吞吐。临界区稳定占用 20 ms，即使获取与释放完全不耗时，无开销上限也只有 1÷0.020=50 次/s；每秒 100 次想成功，利用率至少 100×0.020=2，已超过 1。加五台 Worker 或五个锁节点，都不会让同一份库存同时安全写两次。要缩短临界区、合并操作或排队限流；能拆的是独立资源，不能把同一个余额随意拆成多把锁再假装仍互斥。

随机退避让失败者错开下一次尝试，并用总截止时间限制等待。它改善竞争时的负载，不保证公平，也不能把锁变成持久队列。要公平顺序或每个任务最终都被处理，就需要队列、状态机或协调器提供明确等待契约。可重入同样是另一个协议：owner 要包含进程与线程身份，计数的增减、过期和续租都得原子维护；随机 token 加一个本地整数不足以实现跨实例重入。

At A1/A2, 1,000 initial attempts include 800 successes and 200 busy. One release per success yields 1,000+800=1,800 commands/s. Three extra attempts for each failed contender add 200×3=600, giving 2,400. Sixty long-lived holders renewing every 10 s add 60÷10=6/s on average; synchronized scheduling can make the renewal peak much higher.

A stable 20 ms critical section has a zero-overhead ceiling of 1÷0.020=50/s. One hundred successful operations/s would require utilization 100×0.020=2. More workers or lock nodes do not let one inventory item mutate safely in parallel. Shorten work, batch, queue, or throttle. Split independent resources, not one balance into unrelated locks.

Random backoff spreads retries and a total deadline bounds waiting. It improves load but promises neither fairness nor durable delivery. Fair ordering or eventual processing needs an explicit queue/state-machine contract. Reentrancy is another protocol: process/thread identity, counters, expiry, and renewal must be coordinated atomically; a local counter alone is insufficient.

过期后的旧写：把 fencing 落到资源端 Old writes after expiry: enforce fencing at the resource

故障窗口：租约结束，进程和数据包还在 Failure window: expiry leaves the process and packets alive

A 拿到租约与 33 后暂停，服务端租约照常失效，B 获得 34。B 的写把业务状态和 max_fence=34 一起提交；A 恢复后仍可能使用旧内存，甚至在暂停前已经发出一包写请求。Primary 看见 33 小于已记录的 34，就拒绝并回给 A。33、34 的反例来自 Kleppmann 原文，本文增加了资源端原子写的边界；它们只是演示世代，不代表真实账户或业务版本。[9]

随机 owner 与 fencing token 各干一件事：a、b 是身份，可检查相等；33、34 是世代，可比较先后。把 UUID 的字典序或生成时间当作先后顺序，都没有获得协调器的持有顺序。增加 TTL 可以降低正常任务撞上过期的概率，却不能证明进程暂停、网络延迟或恢复后的重试一定短于这个 TTL。保护共享写的检查必须到达共享资源。

A acquires 33 and pauses; its lease expires and B gets 34. B commits business state with max_fence=34. A may resume with stale memory or have already sent a delayed packet. Primary rejects 33 after observing 34 and replies to A. The 33/34 example comes from Kleppmann; this page makes the atomic resource boundary explicit. These are illustrative epochs. [9]

Random owners provide identity and equality; fencing tokens provide ordered epochs. UUID lexical order or timestamps do not establish acquisition order. A longer TTL may reduce ordinary expiry but does not prove a bound on pause, packet delay, or recovery. The write guard must reach the shared resource.

资源端：检查与修改同成同败 Resource enforcement: check and mutation share one atomic decision

本章 A7 限制一次持有只做一次业务修改，所以条件可以用 last_fence < f。在同一个 UPDATE 里比较并写新世代，两个请求不能各自先 SELECT 后都放行。WHERE 没命中返回 0 行，调用方必须当拒绝或结果需核对，不能忽略影响行数仍说成功。示例 inventory 行事先存在，last_fence 初始化为 0 且不可为空，所有写入口都遵守同一条件；否则旁路 SQL 能绕开 fence。

A7 permits one mutation per acquisition, so a strict last_fence < f check works. Compare and install the epoch in the same UPDATE. Zero affected rows means rejection or a result that must be reconciled, never ignored success. The row already exists, last_fence starts at 0 and is NOT NULL, and all write paths must obey the guard; bypass SQL would evade it.

UPDATE inventory
SET qty = qty - :amount, last_fence = :f
WHERE sku = :sku
  AND last_fence < :f
  AND qty >= :amount;

fencing 不等于幂等。带着 34 的同一笔扣减因响应丢失再来一次，严格小于规则会挡第二次，但调用方还不知道第一次是否成功；需要用业务 operation_id 查回执。若一次持有允许多次不同写，通常允许同世代继续执行，并把操作序号或幂等键单独检查。不能一边用严格小于拒绝相同 token，一边承诺一个租约里随便做多次写；契约与条件必须对应。

另一个边界是“新号已发出”不等于“资源已经看到新号”。B 只获得 34 尚未接触 Primary 时，数据库仍可能接受 33 的第一笔写。fencing 保证资源持久化记录更高世代后拒绝旧世代，不保证在墙钟到期的瞬间拒绝所有旧包。若业务要求新任开始前就完全排除旧任，交接应先在资源上安装新世代并成功，再开始工作；更强的每写验当前持有则需要与权威持有状态原子关联。上述 UPDATE 若库存条件失败，也不会提升世代；若先安装新号完成交接，业务写应改验当前号相等，并单独检查操作幂等。

Fencing is not idempotency. A repeated debit with 34 is blocked by the strict predicate, but a lost reply leaves the caller unsure whether the first debit committed. Look up the operation receipt. Multiple mutations under one epoch need same-epoch acceptance plus separate sequencing/idempotency. A strict comparison cannot silently support unrestricted multiple writes.

Issuing a new epoch is not the same as the resource observing it. Before B reaches Primary, a first write with 33 may still pass. Fencing rejects older epochs after a newer one is installed, not every old packet at the exact wall-clock expiry instant. A handoff needing stronger exclusion must first install the new epoch at the resource, or validate ownership atomically with the write. A failed stock predicate in this UPDATE also leaves the epoch unchanged. For an install-first handoff, durably install the epoch, then require equality for business writes and enforce separate operation idempotency.

发号端：单调号必须绑定这次成功持有 Issuance: the ordered epoch must belong to this acquisition

原稿的“拿锁后单独 INCR”必须改。设 A 的 SET 成功，随后在 INCR 前暂停；租约过期后 B 成功并拿到 100，A 恢复才执行 INCR 得到 101。资源端反而把旧任当新任，这是操作顺序本身的反例，不需要切主就能成立。把 SET 与 INCR 放在同一原子脚本里，可以消掉此处插队；还要在成功设置 owner 的同一次决策里把 token 交给这次持有，失败者不能拿号后冒充成功。

但原子脚本仍只管一个 Redis 主节点。计数没复制就切主，下一任可能重用或倒退；不让计数键过期，也不能消除日志丢失。需要可靠保存持有顺序的协调服务、资源数据库自身的世代，或经过完整故障模型证明的发行机制。图上 Coordinator 因此与 Redis 1 分开命名：它是假设满足这些保证的接口，不是给单节点 INCR 换个名字。

etcd 的锁接口给出持有期间存在的 ownership key，并可在 etcd 事务中检查它；KV 更新的 revision 提供一致顺序。[6][7] 外部数据库不会自动读取这份状态：使用与成功持有绑定的 key 创建 revision 作为世代，还要把它传给资源并检查。不要拿一个无关 GET 响应的最新 header revision 发号。灾难恢复、重建集群后还要保持世代命名空间不回退，必要时引入资源认可的新 incarnation；revision 不是跨所有重建天然永增的魔法数字。

资源端也要可靠。max_fence 与库存必须同事务、同耐久等级，不能在本地内存里记最大号，重启就忘。若支付网关既不验世代也无幂等请求号，客户端多画一个 fencing 框仍不能阻止重复扣款；要改下游接口、改业务状态机或改变承诺。共识租约也不能远程终止一个暂停的 Worker，资源配合是不可省的成本。

Separate INCR after acquisition is wrong. A succeeds at SET, pauses before INCR, expires, and B acquires token 100. A then resumes and increments to 101, making the old owner appear newer. An atomic acquisition-and-counter decision removes this interleaving; the issued token must be bound to the successful owner, never treated as proof by a failed contender.

An atomic script only covers one Redis primary. Failover can lose the counter and reuse or regress epochs; a nonexpiring key does not prevent lost replication. Use durable ordering in a coordinator, resource-owned epochs, or an issuance protocol with a proved failure model. Coordinator is a distinct interface assumption, not Redis INCR renamed.

etcd’s lock API supplies an ownership key usable in etcd transactions, and KV revisions provide ordering. [6][7] An external database still needs a token derived from the successful ownership key and must validate it. An unrelated GET header revision is not an acquisition token. Restore or cluster recreation also needs a nonregressing epoch namespace, potentially a resource-recognized incarnation; revision is not globally eternal.

The resource must persist max_fence atomically with inventory at the same durability level. A local in-memory maximum disappears on restart. A payment provider with neither epoch checks nor idempotency cannot be protected by drawing a fencing box client-side. Change the downstream contract or business state machine. Consensus cannot remotely terminate a paused worker either.

主从切换与 Redlock：高可用不自动等于安全 Failover and Redlock: availability does not automatically prove safety

正常确认与故障确认是两条线 Successful acknowledgement and failure are separate paths

第一步 A 收到 Redis 1 的 OK，第二步锁值还没到 Redis 2，第三步主节点宕机。第四步控制面提升 Redis 2，空键允许 B 的 NX 成功；第五步 B 收到 OK。Redis 内部每一时刻在当前主节点都可能只存一个 owner，但两台 Worker 依照各自收到的确认继续工作，业务仍能双跑。官方分布式锁文档就给出了这个异步复制反例。[11]

图里从 Redis 1 返回 A 的红线代表后续交互发现服务失败，不会抹掉先前那条绿色 OK。A 应停止继续派发新写、核对业务结果，但已经发送的请求仍能到 Primary。故障“在哪一层吸收”因此必须分开说：锁客户端能挡新的调度，存储条件才能挡旧的变更；把锁服务断连画成 Worker 自动消失，会漏掉真正需要保护的包。

A gets OK from Redis 1 before replication reaches Redis 2. Redis 1 dies, the control plane promotes Redis 2, and B acquires the absent key. Each current primary may hold one owner, while two workers act on their separate acknowledgements. Redis’s official locking documentation describes this asynchronous-replication failure. [11]

The red reply is a later failed interaction, not cancellation of the earlier green OK. A should stop new writes and reconcile, but already sent requests can still reach Primary. The client blocks new dispatch; storage predicates block stale mutations. Disconnecting the lock service does not make the worker disappear.

WAIT 的代价与边界 WAIT: cost and limits

在同一个连接上成功写锁后，WAIT 可以等待指定数量的副本收到这个连接之前的写，并返回已经确认的副本数；客户端还必须检查实际返回数。超时只表示没等到目标数，不会回滚刚才的 SET。等待意味着获取路径增加复制延迟与失败分支，如果少副本时仍开始业务，就保留了原先的风险。[3]

更不能把 WAIT 写成“复制后绝不丢锁”。官方明确说明它不会让 Redis 成为强一致存储，切主时仍可能丢掉已经向多个副本同步的写。[3] 效率锁可以用它缩小数据丢失概率，同时接受重复计算；正确性锁则仍需可靠世代与资源验证，或者直接回数据库约束。这里的改正不是否定 WAIT 的价值，而是把它的承诺写到准确的位置。

WAIT can wait for a requested number of replicas to acknowledge previous writes on the same connection and returns the actual count. Check that count. Timeout does not undo SET. Waiting adds replication latency and a failure branch; starting work despite insufficient acknowledgements keeps the original risk. [3]

WAIT does not make Redis strongly consistent and failover can still lose writes acknowledged by multiple replicas, according to its documentation. [3] It can reduce loss risk for an efficiency lock accepting duplicate work. Correctness still needs durable epochs and resource validation, or database constraints. Use its actual guarantee.

替代：可靠协调器会换来什么 Alternative: what reliable coordination costs

已有 etcd 且需要领导者交接、租约与顺序时，让锁 key 附着 lease，按接口处理 KeepAlive、撤销与持有 key 的丢失。共识服务在失去法定多数时会拒绝需要提交的更新，付出可用性代价来维持顺序；不能把这一行为包装成“任何网络故障都还能拿锁”。外部写仍需要 fencing，内部 etcd 写则可在同一个事务中检查 ownership key。[6][7]

选择比较应写成约束与代价：已有 Redis、重复计算可接受，就用短租约降低重复率；所有状态都在 Primary，就用它的事务减少系统边界；必须跨系统选主且资源能验世代，再选可靠协调器。不要背一个通用延迟排行榜。协调器是共享依赖，要给获取和续租独立超时、监控持有丢失、演练隔离与恢复；三台或五台只是拓扑，不能代替故障契约。

With existing etcd and a need for leases/leadership order, attach ownership to a lease and handle KeepAlive, revocation, and key loss. Loss of quorum blocks commits, sacrificing availability to preserve ordering. External writes still need fencing; internal etcd mutations can check ownership within the same transaction. [6][7]

Choose from constraints: existing Redis and tolerable duplicate computation favor short leases; data co-located in Primary favor its transactions; cross-system leadership with enforceable epochs favors reliable coordination. Avoid a generic latency leaderboard. Give coordination separate timeouts, loss monitoring, and recovery drills; node count alone is not a contract.

Redlock 的完整说法与争议 Redlock: algorithm and disagreement

Redlock 向互不复制的 N 个 Redis 主节点申请相同 key 与随机 owner。官方例子 N=5，至少 3 个成功，而且获取总耗时必须小于 TTL；有效窗口还要扣除耗时与时钟余量。比如 TTL=10 s、耗时 0.1 s、教学余量 0.2 s，剩余 10−0.1−0.2=9.7 s。即使拿到三份，若耗时 10.1 s，窗口已为负，仍不能执行。这些是协议的条件，不是画五个圆柱就得到的安全性。[11]

它的多数派不等于 Raft 的已提交日志：没有共同复制的状态机历史，也不提供可比较的持有世代。Kleppmann 的分析强调暂停与时间模型、缺少 fencing；Antirez 的答辩强调有界相对计时和获取前后重新检查时间，并不同意其全部结论。[9][10] 两篇是有争议的技术论证，不是“2026 年全行业已经否定 Redlock”的投票。本章的选择是：当业务正确性依赖锁时，不把它当第一答案，先找可执行的不变量。

现行 Redis 文档本身也提醒使用 fencing、不要假设进程活着就仍持有锁，并讨论 TTL 的时钟限制。[11] 因此正文不沿用“官方只教多数派、没有谈旧写”的旧印象。随机值依然是安全解锁的身份，不是有序世代；应用自行引入可靠发号器后，还得证明发号与持有顺序如何对应，不能说“再 INCR 一下”就把这些问题略过。

Redlock acquires one owner on independent Redis masters. The documented five-node example requires at least three successes and acquisition within TTL, with elapsed time and clock margin deducted. An illustrative 10 s TTL, 0.1 s elapsed, and 0.2 s margin leave 9.7 s. Three successes taking 10.1 s still fail the validity test. These are protocol conditions, not consequences of node count. [11]

Its majority is not a committed Raft log or a shared state-machine history, and it does not issue ordered ownership epochs. Kleppmann critiques timing assumptions and missing fencing; Antirez emphasizes bounded relative timing and elapsed-time checks and disputes the conclusion. [9][10] This is a technical disagreement, not an industry vote. This chapter prefers enforceable invariants for correctness-sensitive work.

Current Redis documentation also discusses fencing, live processes losing locks, and TTL clock limitations. [11] Random values remain release identities rather than ordered epochs. Adding an issuance service requires proving how its epochs correspond to ownership; an extra INCR cannot replace that argument.

看门狗与业务超时：续租也有失败路径 Watchdogs and deadlines: renewal also fails

固定 TTL：从发请求时就开始扣预算 Fixed TTL: budget from before the request

A4 的业务 P99=2 s、TTL=10 s，比例 10÷2=5 只能说明常见尾部有余量；P99 不是最长耗时，仍有超过它的任务。A5 示例获取耗去 100 ms，再保留 200 ms 安全余量，剩余 10−0.1−0.2=9.7 s；8 s 的本地工作截止点留下 9.7−8=1.7 s。客户端从发送前的单调计时开始算保守截止点，不能收到 OK 后重新给自己完整十秒。

固定租约故障时等待到期，是用恢复速度换长任务空间；10 s 比 5 分钟更快交接，但更容易碰到慢任务。到期和网络抖动时刻不是精准秒表承诺。若进程连续健康、释放成功，下一任不用等 TTL；若释放结果未知，就只做原子 owner 清理，不能因“我超时了”删除当前键。获取超时、业务超时、释放超时要分别记录，合成一个 timeout 会丢掉恢复依据。

TTL/P99 = 10÷2=5 only describes headroom against a percentile, not a maximum. Subtract illustrative 100 ms acquisition and 200 ms margin to get 9.7 s; an 8 s local deadline leaves 1.7 s. Budget with monotonic elapsed time from before sending, rather than granting a fresh ten seconds after OK.

Fixed TTL trades takeover speed for room for long work. Ten seconds hands over faster than five minutes but expires sooner on slow tasks; expiry is not a precise availability stopwatch. Healthy release avoids waiting. On uncertain release, only perform an owner-checked cleanup. Distinguish acquisition, business, and release timeouts for recovery.

续租：刷新的是有效 owner，不是无限授权 Renewal refreshes a matching owner, not unlimited authority

图的 30 s 租约在 t=0 获取，t=10 成功续满到 t=40。Watchdog 是同进程的后台线程，比较 owner 仍是 a 才原子延长，不允许拿到旧对象就无条件 PEXPIRE 当前键。Redisson 官方指南给出默认 watchdogTimeout 30 s；当前 RenewalTask 源码按这个值除以 3 调度，所以这里用约 10 s。[4][5] 调度延迟、批量续租与网络时间都可能推迟实际完成，不能把“每十秒”当硬实时保证。

整个进程 t=11 停到 t=45，业务线程与续租线程一起停。距最后一次续租到期还剩 40−11=29 s，暂停持续 45−11=34 s；所以 t=40 已过期，B 在 t=41 成功。A 恢复后续租比较发现 owner b，返回失败。这条红回程要停在 Watchdog，由它通知任务停止新操作并核对结果；不能画成 Redis 直接把数据库里的旧写自动撤回。

本图的所有时间是理想化演示，前面的绿线表示过去成功过的事件，最后的红线才是本次晚到的续租。主线程如果忘了检查续租丢失，健康的后台线程也无法替它证明所有写合法。重入锁还要检查具体的持有线程与计数，不能把上面简单字符串锁的续租脚本直接当成 Redisson 内部实现。指定固定 leaseTime 与使用自动看门狗是两种调用策略，按实际客户端版本核对。[4]

The illustrative lease acquired at t=0 is renewed at t=10 until t=40. Watchdog runs in the same process and extends only a matching owner atomically, never unconditional PEXPIRE. Redisson documents a 30 s default and its current RenewalTask schedules at timeout/3, hence roughly 10 s here. [4][5] Scheduling and network delays prevent hard real-time guarantees.

Both threads pause from t=11 to t=45. Remaining lease is 40−11=29 s and pause is 45−11=34 s. Expiry occurs at t=40 and B acquires at t=41. A’s late renewal sees b and fails. Watchdog handles that failure by stopping new work and reconciling; Redis cannot recall business mutations.

These are idealized event times. Green arrows are completed successes; the final red route is the late renewal. The business thread must handle ownership loss, and a reentrant lock has thread/counter semantics beyond this string-owner example. Fixed leaseTime and automatic watchdog behavior are separate invocation choices; verify the client version. [4]

业务超时：停止等待不等于停止副作用 Business timeout: stopping the wait does not stop the effect

“业务超时小于 TTL 就安全”要改成有条件的预算规则。8 s 超时能让调用方不再派发新的 SQL，但 7.9 s 已发出的请求可能在网络里拖到 12 s；JVM 暂停时本地定时器也不按时执行。取消 Future、断开 HTTP、线程中断都不自动证明远端数据库已取消或回滚。超时后的结果是未知，先按 operation_id 查状态，再决定重试或补偿；写入口继续检查世代与业务条件。

真正需要三层配合：租约限制其他 Worker 何时能开始，本地截止点限制自己继续提交工作的意愿，资源端约束限制晚到写是否合法。看门狗只延长第一层，不能替换后两层。对于偶发长计算，可续租减少重复；对于写账本，即使用续租也要幂等请求号和事务保护。不要把更长租约当成解决错误的方法，五分钟只是把崩溃后的等待从十秒拉长三十倍。

上线观察不只看获取成功率。把 busy、获取结果未知、续租失败、剩余租期、临界区耗时、fence 拒绝、幂等回放分别计数；热点等待应按资源键聚合，避免被全局平均掩盖。演练整个进程暂停、网络单向隔离、写请求迟到和协调器恢复，核对的是不变量是否仍成立。给每个场景一个可解释结果，比宣称“有看门狗所以绝对互斥”更能回答面试官的故障追问。

An 8 s deadline limits new dispatch but cannot recall a SQL request sent at 7.9 s and delivered at 12 s. Local timers also pause. Cancelling a future, disconnecting HTTP, or interrupting a thread does not prove remote rollback. Treat the result as unknown, reconcile by operation ID, and keep storage guards on all writes.

Three layers cooperate: the lease admits contenders, local deadlines stop new work, and resource predicates validate delayed mutations. Watchdogs extend the first layer only. Renewal can reduce duplicate long computations; a ledger still needs idempotency and transactions. Five minutes merely makes the crash wait 300÷10=30 times longer than ten seconds.

Track busy, unknown acquisition, failed renewal, lease remainder, critical-section duration, fence rejection, and idempotent replay separately. Aggregate contention by resource key. Exercise whole-process pauses, one-way partitions, delayed writes, and coordinator recovery against invariants. Explain each outcome rather than asserting absolute exclusion from a watchdog.

能在数据库完成的互斥，先留在事务里 Keep exclusion in a transaction when the database can enforce it

正常路径：同一个请求只产生一份回执 Walkthrough: one receipt for one operation

A9 假设库存行、业务请求记录与回执都在 Primary，操作是短事务。A 先在事务里用唯一且非空的 operation_id 占住 op:7，再做带库存条件的扣减并保存结果，三项一起提交。任意一步失败都回滚，不会有“请求显示完成但没扣减”或“已扣减却没有幂等记录”的中间状态。请求号还需绑定 SKU、数量等参数，同一个号换一份载荷要拒绝，不能回放成另一笔业务。

B 同时或稍后用 op:7 重试。UNIQUE 保证同一请求只出现一次，并发插入可能等原事务结束；原事务提交后，B 查到已存结果才可以回放。若原事务回滚，B 可以重新尝试成为执行者。单纯捕获唯一键异常然后返回成功不成立，因为还没查到正确回执。PostgreSQL 约束文档定义的是唯一性，不替应用定义“失败等于成功”的业务语义。[8]

A9 co-locates inventory, operation records, and receipts in Primary within a short transaction. Claim op:7 under a UNIQUE NOT NULL ID, conditionally debit, store its result, and commit together. Failure rolls all back. Bind the operation ID to SKU/amount and reject reuse with a different payload rather than replaying a different operation.

B retries op:7. A unique constraint prevents duplicate records; a concurrent insertion may wait for the original transaction. Replay only after finding its committed receipt. If the original rolls back, B may retry execution. A uniqueness exception alone is not success. PostgreSQL defines uniqueness, not the application meaning of the outcome. [8]

不同请求仍需条件更新，锁不能替代不变量 Different operations still need guarded mutation

op:8 是另一笔合法请求，即使它有全新的唯一号，也可能与 op:7 争最后一份库存。图中它读到版本 12，更新时当前已经是 13，WHERE version=12 不匹配，因此影响 0 行。可以重读新状态，在业务允许且总等待预算未用完时重试；不能把 0 行当成已成功扣减。若只要不超卖，直接在 UPDATE 中检查 qty≥amount 也能表达核心不变量，版本号则保护读改写依赖的状态。

op:8 is distinct and may compete for the last unit despite a unique ID. It expects version 12 but current version 13 yields zero affected rows. Reread and retry only if allowed within a total deadline. For nonnegative inventory, qty≥amount in the UPDATE expresses the core invariant; a version guard additionally protects read-modify-write assumptions.

UPDATE inventory
SET qty = qty - :amount, version = version + 1
WHERE sku = :sku
  AND version = :expected_version
  AND qty >= :amount;

这里有三种不同检查：UNIQUE(op_id) 把同一请求合并，version 比较识别不同请求读到了旧状态，qty 条件保证扣减后库存不为负。fencing 的世代又是第四种，表示哪个协调持有者更新。它们可以组合，但不能互相冒充；把数据库行 version 直接拿来做协调器世代，仍需说清它如何随每次持有更新、如何与写关联以及恢复后是否保留。

事务内行锁是可选替代：先锁住这一行再读改写，数据库串行化竞争并释放事务锁。代价是连接、锁等待和死锁重试；外部调用、几十秒计算不要放在持行锁的事务里。乐观条件写适合冲突低且重试便宜，悲观行锁适合竞争较高且短操作，但两者遇到 20 ms 的单热点仍最多约 50 次/s。改变锁的位置，没有取消串行工作本身的上限。

These guards differ: UNIQUE(op_id) deduplicates one operation, version detects stale read-modify-write state, qty protects nonnegative stock, and fencing orders coordinator holders. They can combine but are not interchangeable. A row version used as a coordination epoch still needs explicit issuance, binding, and recovery rules.

A short transaction may pessimistically lock the row before reading and modifying. It costs connections, waiting, and deadlock retries; keep long computation and remote calls outside it. Optimistic guards suit cheap low-conflict retries; row locks suit short high-contention work. Either still has roughly a 50/s ceiling for a serial 20 ms hot item.

故障与边界：一个事务装不下外部世界 Failures and limits: an external effect does not fit inside the transaction

Primary 提交后回包丢失，A 不知道结果，但 op:7 的回执与扣减同样耐久，重新读回执即可确定。若 Primary 的故障模型允许丢掉已确认事务，那么业务和回执都可能丢；引入 Redis 锁不会补回数据耐久性。幂等记录有保留期限，删除后再来旧请求会再次执行，因此保留窗口至少覆盖业务约定的重试、补偿和对账时间，不能为了省空间随手设一分钟。

长任务可以先提交“待执行”，用带 owner 与世代的任务状态机领取，完成时条件更新当前持有；这已经是另一个租约协议，不能把一个永久 UNIQUE 占位说成崩溃后自动接管。远端支付、邮件或文件写出也不受本地 SQL 回滚支配。可以先把 outbox 与业务一起提交，再由投递者调用支持幂等的下游；对方不支持幂等时，必须承认重复窗口并改接口或业务流程。

选择顺序因此很实用：先写必须成立的业务条件，再看单库事务是否足够；只有协调跨机器或跨系统执行确实有价值时才加锁。拿不到锁的行为也属于产品语义：订单可以返回正在处理并给请求号查询，批处理可以跳过本轮，必须处理的任务可以排队。不要让所有失败者在一把热锁上无限自旋，锁竞争只会把请求预算吃完，并不会替你保存任务。

If commit succeeds but its reply is lost, op:7’s durable receipt reveals the outcome. If the database can lose acknowledged transactions, a Redis lock cannot repair that durability failure. Idempotency retention must cover the agreed retry, compensation, and reconciliation window; deleting the receipt permits old operations to execute again.

Long tasks may use a durable pending state and a separate owner/epoch claim protocol with conditional completion. A permanent unique claim does not automatically recover after a crash. Remote payments, mail, and file writes do not roll back with local SQL. An outbox can record intent atomically and deliver to an idempotent downstream; otherwise acknowledge and redesign the duplicate window.

Start with business invariants, test whether a local transaction suffices, and add a lock when coordinating execution across processes actually helps. Contention behavior belongs to the product contract: return processing with a queryable operation ID, skip a batch cycle, or queue guaranteed work. Endless hot-lock spinning neither preserves tasks nor creates capacity.

面试官问“你能保证绝对互斥吗”，先把对象说清：服务端当前 key 的唯一 owner、客户端认为自己持有、资源端允许的业务变更，是三个不同观察点。我们保证资源不变量的方式是原子条件、可靠世代和幂等，而不是保证所有远端进程在同一瞬间停止。若资源根本不提供这些接口，应坦诚说明仍有哪些副作用可能重复，再讨论改产品契约。

If asked for absolute exclusion, distinguish the server’s current key owner, client ownership belief, and permitted business mutations. Atomic predicates, durable epochs, and idempotency enforce resource invariants; they do not stop every remote process at the same instant. If the resource lacks these interfaces, explain the remaining duplicate effects and change the contract.
