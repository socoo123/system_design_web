即时配送Instant delivery

约 40 分钟 · 前置：Ch19、Ch20、Ch24、Ch25 · 6 组 / 31 帧演进图~40 min · after Ch19, Ch20, Ch24, Ch25 · 6 evolution decks / 31 frames

本章主线：先守住双方占位，再优化匹配Core: preserve bilateral occupancy before optimizing matching

  • 一个订单只有一个当前执行者。每个骑手槽位只绑一单；本章每人最多两个槽位，offered 也占位。
  • 派单事实放进一个事务。预占、accept、到期、取消都经过同一订单与容量权威；旧代次不能恢复执行权。
  • 位置是投影，履约是事实。新鲜点用于召回，掉线与 GPS 过期不能自动撤回已经取走的餐。
  • One current assignee per order. Each courier slot binds one order; this example allows two slots, including unanswered offers.
  • One transaction authority. Reservation, accept, expiry and cancellation use the same order/capacity authority. Old generations cannot regain execution rights.
  • Location is a projection; fulfillment is fact. Fresh points support recall. Disconnection or stale GPS cannot revoke physical custody.

30 秒开场与必要假设A 30-second opening and assumptions

我设计一城外卖履约：支付确认后，先持久保存 pending_match；召回附近候选，过滤新鲜度、资质和容量，再比较到店路耗与迟到风险。选人后原子预占订单和骑手槽位，提交 offer 与 Outbox，骑手 accept 成功才 assigned。服务端到期扫描释放未接 offer 并推进 generation；旧消息重试只能查询原结果。高峰按区域控制新承诺，保住存量履约。

先澄清配送类型、平台接受订单的时刻、多单上限、准时目标与取餐后交接权限。本章选外卖、准时优先、每个 offer 只发给一个骑手；同一骑手可占两个不同槽位。广播抢单也要经过相同的事务约束。

Design one-city food fulfillment. After confirmed payment, persist pending_match, recall nearby couriers, filter freshness/eligibility/capacity, then compare pickup travel and lateness. Atomically reserve order and courier slot with offer/outbox; assigned requires committed business acceptance. Server expiry releases unanswered offers and advances generation. Retried old messages query original results. Gate new zone commitments while protecting existing work.

Clarify delivery type, platform acceptance, multi-order limit, punctuality and post-pickup handoff authority. This example prioritizes punctuality and sends each offer to one courier; a courier may occupy two distinct slots. Broadcast grabbing still needs the same transactional constraints.

先分别估订单、位置与用户出口Size orders, location and viewer egress separately

订单平均 500,000÷86,400≈5.79/s，10 倍峰值约 57.87/s。首轮每单召回 20 人是约 1,157 人次/s，过滤后 8 人去一个取货点是约 463 个路耗元素/s；元素不是 HTTP 调用数，重试另算。

10,000 名在线骑手每 5 秒上报一次是 2,000 点/s；200 B/点给出 0.4 MB/s = 3.2 Mb/s 原始负载。若到每人 1 Hz，变成 10,000/s 和 2 MB/s，均为五倍；是否承受得住要压测写放大和连接开销，位置和业务控制分别留配额。

3,000 名观看者每 5 秒最多推一票是 600 推送/s、120 KB/s。骑手与观看连接合计 13,000 条，连接预算不能用消息速率代替。按订单订阅，避免全城 2,000×3,000 = 600 万次点投递/s。

Orders average 500,000/86,400≈5.79/s, about 57.87/s at 10× peak. Twenty recalled couriers give 1,157 candidate visits/s; eight retained origins to one pickup give about 463 route elements/s. Elements are not HTTP calls; retries add load.

10,000 couriers reporting every 5 s produce 2,000 points/s. At 200 B, payload is 0.4 MB/s = 3.2 Mb/s. One Hz produces 10,000/s and 2 MB/s, both 5×. Measure index amplification and connection costs; isolate location and control quotas.

3,000 viewers limited to one point per 5 s require 600 pushes/s and 120 KB/s. The 13,000 courier/viewer connections need a separate budget. Order-scoped subscriptions avoid 2,000×3,000 = six million citywide point deliveries/s.

最新点与历史留存：展开存储算式Latest points versus history: storage arithmetic

最新详情负载 10,000×500 B = 5 MB，不含索引、对象开销和复制。若在线数全天不变并全量留点，2,000×86,400×200 B = 34.56 GB/天；真实在线数应按时间积分。履约行 500,000×2 KB = 1 GB/天，30 天三份为 90 GB；attempt、Outbox、日志、备份另算。均用十进制 KB/GB。

Latest details are 10,000×500 B = 5 MB before indexes, object overhead and replication. Constant all-day online count with complete retention gives 34.56 GB/day; integrate real online counts over time. Fulfillment rows are 1 GB/day, or 90 GB for 30 days and three copies. Attempts, outbox, logs and backups are extra. Units are decimal.

履约入口：持久事实先于通知Fulfillment: durable facts precede delivery

用已认证上游的 (scope, upstream_order) 创建履约，绑定规范化订单摘要；同身份同内容回原单，改内容则冲突。支付确认来自服务端持久事实。一个事务写 pending_match、generation=7、匹配期限与待匹配 Outbox，提交后 202 只表示工作可恢复。提交响应丢失是未知，重试固定身份，不能新建第二笔。

Match 读新鲜位置只是旁支；Fulfillment DB 才保存当前 attempt 和槽位。Gateway 合并画出 Outbox relay 与设备通道，只发已提交 offer，重复投递仍需消费者去重。设备重连先拉当前快照；传输 ACK 不等于业务接单。[5]

Create with authenticated upstream (scope, upstream_order), bound to a canonical order digest. Identical retries return the original order; changed content conflicts. Payment confirmation comes from durable server facts. One transaction stores pending_match, generation 7, deadline and match outbox. A committed 202 means recoverable work. A lost commit reply is unknown: retry the fixed identity.

Fresh location is an advisory branch; Fulfillment DB owns current attempts and slots. Gateway combines the outbox relay/device channel, sends committed offers and tolerates duplicates with consumer deduplication. Reconnect fetches the current snapshot. Transport ACK is not acceptance. [5]

双边唯一落在哪个键上Where bilateral uniqueness lives

订单保留 state、generation、current_attempt、attempt_count 和 match_deadline；attempt 保留骑手、截止点、原回执与配置版本。active_slot 把槽位绑定到当前单：同一订单只能有一个活动占位，同一骑手的同一槽位只能有一单。骑手可有两个槽位，所以不能直接给 courier_id 加唯一约束。occupied 与槽位计数必须同事务维护；行内 CHECK 不能证明跨表一致。[2]

Orders retain state, generation, current attempt, attempt count and match deadline; attempts retain courier, deadline, original receipts and configuration version. active_slot uniquely binds both order and courier slot. A courier has two slots, so courier_id alone is not unique. Maintain occupied with slot rows in one transaction; a row CHECK cannot prove cross-table consistency. [2]

-- Executable SQLite subset of the teaching model; parent tables in schema.sql.
CREATE UNIQUE INDEX order_identity ON orders(scope, upstream_order);
CREATE UNIQUE INDEX attempt_generation ON attempts(order_id, generation);
CREATE TABLE active_slot (
  courier_id TEXT NOT NULL REFERENCES courier_capacity(courier_id),
  slot INTEGER NOT NULL CHECK(slot >= 0),
  order_id TEXT NOT NULL UNIQUE REFERENCES orders(order_id),
  attempt_id TEXT NOT NULL UNIQUE REFERENCES attempts(attempt_id),
  PRIMARY KEY(courier_id, slot)
);
CREATE UNIQUE INDEX event_identity ON outbox(event_key);
-- One live slot per order; one order per courier slot. A courier has two slots.
-- A transaction also checks slot < capacity and changes occupied with the slot.
-- CHECK(0 <= occupied AND occupied <= capacity) is only a row-local guard.
-- All reserve/release writers lock order, then the same courier_capacity row.

代码是教学约束；完整父表和可执行适配见 examples/ch27。生产需限制所有写者走相同路径，批量操作按固定顺序锁全部订单再锁骑手行，死锁/序列化中止整笔重试。位置详情是另一份可重建投影，不能替代这些键。

These teaching constraints have complete parent tables and an executable adapter in examples/ch27. All production writers must follow the same path. Batch operations lock orders then courier rows consistently and retry whole aborted transactions. Location details remain a separate rebuildable projection.

候选与打分：分数之后仍要预占Recall and scoring still end in a reservation

按取货点附近格子或 GEO 限量召回、去重、批读详情，排除旧会话、过期点、资质不符、暂停与满载者。Redis GEOSEARCH 提供半径/方框召回，没有配送运力语义；地理最近也可能在河对岸。[3] 朝向一般是软特征，过期位置则是硬门限。

先过滤到 8 人再计算 8×1 个路耗元素；Google Routes 支持整请求或单元素错误。gRPC 流式结果明确不保证顺序，REST 不支持该流式方式；按返回的起终点索引归位，缺失/失败元素不能当零。[6] 成本 J=到店分钟+4×迟到风险+2×负载：A 为 2+2+2=6，B 为 4+0.4+0=4.4，选 B；系数是分钟等价惩罚的教学取值。

评分不是锁。路耗返回时 B 的名额可能已被别的区占走。下面重新锁订单和同一骑手容量行，检查当前代次、预算与槽位，然后提交双方占位、offer 与事件。候选详情在预占前重读，其服务端新鲜度截止点带进事务，等锁后已过期就重选。位置是读时快照，断线仍可能发生在检查之后；它不与履约跨库原子提交。发生冲突重新选人；不要拿着数据库锁调用 Routing。[1]

Bound recall around pickup through cells/GEO, deduplicate and batch-load details. Reject wrong sessions, stale, ineligible, paused or full couriers. GEOSEARCH supplies radius/box recall without delivery capacity semantics; nearby can mean across a river. [3] Heading is usually soft; stale location is a hard gate.

Filter to eight before calculating eight route elements. Google Routes can fail a whole request or individual elements. gRPC streaming explicitly permits unordered results; REST does not support that streaming mode. Map origin/destination indexes and never treat missing/error elements as zero. [6] J=pickup minutes+4×late risk+2×load gives A=6 and B=4.4. The minute-equivalent weights are teaching choices.

Scoring is not locking. Another zone can occupy B while Routing runs. Lock order and the same capacity row, recheck generation/budget/slots and commit reservation, offer and event together. Re-read candidate details before reservation and carry server-derived validUntil into the transaction; reject if lock waits exhaust it. This is a read-time location snapshot: disconnection can still follow the check, without a cross-store atomic promise. Rematch on conflict; never hold DB locks across Routing calls. [1]

reserve(orderId, expectedGeneration, courierId, attemptId):
  point = readCurrentCandidateSnapshot(courierId)         // before DB locks; server-derived validity
  begin transaction
    o = SELECT order FOR UPDATE                         // lock order first
    old = SELECT attempt WHERE id = attemptId
    if old exists:
      require old binds (orderId, expectedGeneration, courierId) else CONFLICT
      commit; return old.offerReceipt, currentSnapshot(o) // no new occupation
    c = SELECT courier_capacity FOR UPDATE             // same authority in all zones
    now = SELECT clock_timestamp()                     // after both locks, not now()
    require o.state == pending_match and o.currentAttempt == null else CONFLICT
    require o.generation == expectedGeneration else CONFLICT
    require now < o.matchDeadline and o.attemptCount < 3 else EXHAUSTED
    require point exists and now <= point.validUntil else REMATCH
    require not c.paused and c.occupied < c.capacity else REMATCH
    require courierId not in this order's persisted cooldown set else REMATCH
    slot = smallest unused slot in [0, c.capacity)
    deadline = min(now + 20 seconds, o.matchDeadline)
    INSERT attempt(attemptId, orderId, o.generation, courierId, deadline, offered)
    INSERT active_slot(courierId, slot, orderId, attemptId) // UNIQUE both sides
    UPDATE courier_capacity SET occupied = occupied + 1 WHERE id = courierId
    UPDATE order SET state = offered, currentAttempt = attemptId,
                     attemptCount = attemptCount + 1
    INSERT outbox(eventKey = "offer:" + attemptId, immutableOfferPayload)
  commit; return offerReceipt, currentSnapshot(o)
  // Any statement/constraint failure rolls back every write; do not send yet.
  // Retry deadlock/serialization aborts with the same identity and fresh reads.

所有区域借来的 B 都回同一容量权威。offer 已占位，accept 不再加一；完成或合法释放才减一。固定 attempt 重投回原回执和当前快照，已经过期的 offer 不会复活。公平可在满足硬门限后按等待年龄打破同分；一秒批量窗口可改善贪心匹配，但等待也要计入 120 秒期限。

Borrowed B always uses the same capacity authority. Offer consumes a slot; accept does not add another. Completion or valid release decrements once. Same-attempt retries return the original receipt and current snapshot without reviving an expired offer. Fairness can tie-break by age; a one-second batch can improve greedy matching but consumes the 120 s budget.

accept 与到期：同一事务决定谁赢Acceptance and expiry serialize in one authority

图中的 v7 就是订单 generation。accept、拒绝和到期都先锁同一订单，再锁相同容量行；数据库提交才决定状态。先校验 attempt 绑定与骑手身份，再回放原成功。历史 accept 回执附带当前快照：后来取消、完成或改派时，它只证明曾接受，不能让旧设备继续取送。

锁后读取实际数据库时间。PostgreSQL 的 now()/CURRENT_TIMESTAMP 固定在事务开始，等锁后可能已过期；clock_timestamp() 才取调用时刻。[11] 普通 Read Committed SELECT 也不是互斥锁。[10] 权威墙钟需监控与误差约束，时间异常时暂停相关转换；generation 的单调性独立于墙钟。截止点约定 accept: now<deadline，expire: now≥deadline，没有双方都能成功的间隙。

Diagram v7 is the order generation. Accept, reject and expiry lock the same order then capacity row; DB commit decides state. Validate attempt bindings and courier identity before replaying success. A historical acceptance includes the current snapshot. After cancellation/completion/reassignment, it proves prior acceptance without renewing execution rights.

Read actual DB time after locking. PostgreSQL now()/CURRENT_TIMESTAMP retain transaction-start time, possibly before a lock wait crosses the deadline; clock_timestamp() observes call time. [11] A plain Read Committed SELECT is not mutual exclusion. [10] Monitor and bound authoritative wall-clock error; pause time-sensitive transitions when uncertain. Generation monotonicity is independent of wall time. Accept uses now<deadline and expiry now≥deadline.

decideOffer(op, orderId, attemptId, generation, authenticatedCourier):
  begin transaction
    o = SELECT order FOR UPDATE
    a = SELECT attempt WHERE id = attemptId
    require a binds (orderId, generation) else CONFLICT
    if op in {ACCEPT, REJECT}: require a.courier == authenticatedCourier else FORBIDDEN
    if op == ACCEPT and a.acceptReceipt exists:
      commit; return a.acceptReceipt, currentSnapshot(o) // historical, no reactivation
    require o.currentAttempt == a.id and o.generation == generation else STALE
    require o.state == offered and a.result == offered else STALE
    c = SELECT courier_capacity WHERE id = a.courier FOR UPDATE
    now = SELECT clock_timestamp()
    if op == ACCEPT:
      require now < a.deadline else CONFLICT
      receipt = fixedAcceptReceipt(a)
      UPDATE attempt SET result = assigned, acceptReceipt = receipt
      UPDATE order SET state = assigned
      INSERT outbox("assigned:" + a.id, currentAssignment)
    else:
      require op == REJECT or (op == EXPIRE and now >= a.deadline) else NOT_DUE
      DELETE active_slot WHERE attempt_id = a.id        // require one deleted row
      UPDATE courier_capacity SET occupied = occupied - 1 WHERE id = a.courier
      UPDATE attempt SET result = (op == REJECT ? rejected : expired)
      next = now >= o.matchDeadline or o.attemptCount >= 3 ? failed : pending_match
      UPDATE order SET state = next, currentAttempt = null, generation = generation + 1
      INSERT outbox(keyFor(orderId, generation + 1, next), nextWorkOrFailure)
      // Persist courier cooldown with the retry work; retries do not reset budgets.
      receipt = fixedDecisionReceipt(a, op)
  commit; return receipt, currentSnapshot(o)
  // Only this offered branch expires. Assigned/picked_up keep their slot.

accept 先赢：offered→assigned，占用仍为 1，后续到期扫描无效。到期先赢：a1=expired，订单 pending_match、v7→v8，释放一次并写重匹配事件；旧 a1/v7 接单返回冲突。每次新派用新 attempt；三次 20 秒仅是 60 秒等待，召回、路耗、队列还消耗剩余匹配预算。

Acceptance first changes offered→assigned, keeps one occupied slot and makes expiry a no-op. Expiry first marks a1 expired, releases once, advances 7→8 and persists rematching; old a1/v7 conflicts. New dispatch gets a new attempt. Three 20 s waits consume 60 s before recall, routing and queue time.

取消和改派必须先确认实物归属Cancellation and reassignment require custody control

未接 offered 可直接取消；pending_match 取消只需锁订单、写终态和事件。assigned 之后的取消不能只看数据库“还没报 pickup”：骑手可能已拿餐而回报延迟。先由有权限的运营流程核实撤销/交接、取得绑定本单/attempt/代次的可信凭据，再释放槽位。已取餐更要完成实物交接。GPS 断线和工作租约到期都不是这种凭据。

An unanswered offer can be cancelled; pending cancellation only locks the order and commits terminal state/event. After acceptance, absence of a pickup upload does not prove food remains at the restaurant. Authorized operations must verify cancellation/handoff with evidence bound to order/attempt/generation before releasing capacity. GPS loss and worker lease expiry are not custody evidence.

finishOrRelease(orderId, attemptId, generation, action, authenticatedActor, verifiedEvidence):
  require action in {PICKUP, DELIVER, CANCEL, REASSIGN} else INVALID
  begin transaction
    o = SELECT order FOR UPDATE
    a = SELECT attempt WHERE id = attemptId
    require a binds (orderId, generation) else CONFLICT
    require authorizedActorAndEvidence(action, authenticatedActor, o, a, verifiedEvidence) else FORBIDDEN
    if storedReceipt(action, a) exists:
      require same evidence binding else CONFLICT
      commit; return storedReceipt, currentSnapshot(o)
    require o.currentAttempt == a.id and o.generation == generation else STALE
    if action == PICKUP:
      require o.state == assigned else CONFLICT
      UPDATE order, attempt SET state/result = picked_up
    else:
      if action == DELIVER: require o.state == picked_up and deliveryProof else CONFLICT
      if action == CANCEL: require o.state == offered else CONTROLLED_HANDOFF_REQUIRED
      if action == REASSIGN:
        require o.state in {assigned, picked_up} and verifiedCustodyClear else REVIEW
      c = SELECT courier_capacity WHERE id = a.courier FOR UPDATE
      DELETE active_slot WHERE attempt_id = a.id         // require one deleted row
      UPDATE courier_capacity SET occupied = occupied - 1 WHERE id = a.courier
      UPDATE attempt SET result = terminalResult(action)
      next = action == REASSIGN ? pending_match : terminalResult(action)
      UPDATE order SET state = next, currentAttempt = null, generation = generation + 1
    INSERT operation_receipt(action, a.id, evidenceBinding, fixedReceipt)
    INSERT outbox(fixedEventKey(action, a.id), stateOrRematchIntent)
  commit; return fixedReceipt, currentSnapshot(o)
  // Verified custody evidence is a trusted operations dependency, never stale GPS.

本地事务把凭据去重、状态、槽位释放和持久事件绑在一起，不能替外部世界保证交接。例子的可信凭据由显式适配契约提供。attempt、原回执和 generation 不随短 TTL 清除；归档也须让未知旧身份只能查询/拒绝，防止备份恢复或晚到命令被当成新工作。

The transaction binds evidence deduplication, state, release and durable event; it cannot itself prove a physical handoff. Trusted evidence is an explicit adapter dependency. Do not expire attempt identities, original receipts or generations with short TTLs. Archived unknown old identities must query/reject rather than become new work after delayed commands or backup restoration.

位置：会话、排序与新鲜度分别验证Location: validate session, order and freshness separately

epoch 由服务端单调分配并保留在点 TTL 之外；每次重连都换新 epoch、清旧点并重新采样。断线事件必须带 epoch 做条件更新，旧连接的延迟断线不能关闭新会话。序号只在当前会话内比较；客户端不能自选更大 epoch。业务在线、连接存活与 GPS 新鲜是三个字段。

下列伪代码描述单个骑手会话记录的存储事务/CAS。重复或迟到 seq 返回当前序号，不改 captured_at、received_at 或 TTL；较高 seq 的旧采样也要先拒绝。节流在此之前按骑手和区域执行，控制动作有独立配额。静止心跳维持 liveness，不能把旧 GPS 洗成新点。

The server durably advances epoch beyond point TTL. Every reconnect gets a new epoch, clears the old point and requires a new sample. Disconnect updates match epoch, so an old delayed disconnect cannot close the new session. Sequence ordering applies within the current session; clients cannot select epochs. Business availability, connection liveness and GPS freshness are separate fields.

This pseudocode uses a per-courier storage transaction/CAS. Duplicate or older sequences return the current sequence without changing capture/receipt time or TTL. A higher sequence with stale capture also fails. Apply courier/zone throttling before this step and isolate control quotas. Stationary heartbeats maintain liveness without refreshing old GPS.

startSession(authenticatedCourier, trustedClockBound):
  begin location-store transaction
    INSERT empty session if absent; on an identified unique race restart transaction
    s = SELECT session FOR UPDATE
    UPDATE session SET epoch = s.epoch + 1, connected = true,
                       seq = -1, point = null, clockBounded = trustedClockBound
  commit; return serverIssuedEpoch                       // retained beyond point TTL

applyPoint(authenticatedCourier, inputEpoch, inputSeq, inputPoint):
  begin location-store transaction
    s = SELECT session FOR UPDATE
    now = authoritativeTimeAfterLock()
    require s.epoch == inputEpoch and s.connected else STALE_SESSION
    require inputSeq >= 0 and LocationGate.fresh(now, inputPoint, s.clockBounded) else INVALID

    UPDATE session SET seq = inputSeq, point = inputPoint, receivedAt = now, expiresAt = now + 60s
    // Index delivery may be lossy; periodic reconciliation repairs omissions.
  commit; return inputSeq

disconnect(inputCourier, inputEpoch):
  UPDATE session SET connected = false, point = null
    WHERE courier_id = inputCourier AND epoch = inputEpoch
  // An old disconnect cannot invalidate a newer session. Reconnect gets a new epoch.

把 ±5 秒误差写进代码Include the ±5 s clock uncertainty

A6 假设采集时钟相对服务端误差可证明不超过 ±5 秒。保守年龄上界为 now−captured+5s，要求 ≤30 秒；同时拒绝 captured>now+5s 的明显未来点，因此可接受区间是 −5s≤now−captured≤25s。误差界不可信就排除；这不是防伪造 GPS 的物理证明。

下面是完整可运行 Java 17 纯校验类，包含边界自检；不提供时钟同步或分布式 CAS。读候选时再次按当前时间计算，不能用 60 秒回收 TTL 当 30 秒业务新鲜度。

A6 assumes a defensible relative clock-error bound of ±5 s. Conservative age is now−captured+5 s≤30 s, while captured>now+5 s is rejected. Thus −5 s≤now−captured≤25 s. Exclude unbounded clocks; this is not physical proof against spoofed GPS.

This complete runnable Java 17 pure validator includes boundary checks, without clock synchronization or distributed CAS. Recompute freshness at candidate read time; the 60 s cleanup TTL does not replace the 30 s business age bound.

/** Java 17, dependency-free pure validation; no storage or clock synchronization. */
public final class LocationGate {
    public record Point(long capturedAtMs, double accuracyM, double lat, double lon) {}
    public static boolean fresh(long nowMs, Point p, boolean boundedClock) {
        if (!boundedClock || p == null || nowMs < 0 || p.capturedAtMs() < 0
                || !Double.isFinite(p.accuracyM()) || p.accuracyM() < 0 || p.accuracyM() > 50
                || !Double.isFinite(p.lat()) || Math.abs(p.lat()) > 90
                || !Double.isFinite(p.lon()) || Math.abs(p.lon()) > 180) return false;
        try {
            long delta = Math.subtractExact(nowMs, p.capturedAtMs());
            // Trusted relative clock error <= 5 s. True capture-age upper bound <= 30 s.
            return delta >= -5_000 && delta <= 25_000;
        } catch (ArithmeticException invalidTime) {
            return false;
        }
    }
    public static void main(String[] args) {
        if (!fresh(100_000, new Point(75_000, 50, 31, 121), true)
                || fresh(100_000, new Point(74_999, 50, 31, 121), true)
                || fresh(100_000, new Point(105_001, 5, 31, 121), true)
                || fresh(100_000, new Point(100_000, Double.NaN, 31, 121), true)
                || fresh(100_000, new Point(100_000, 5, 31, 121), false))
            throw new AssertionError("freshness boundary failed");
        System.out.println("LocationGate: normal/stale/future/NaN/unbounded checks passed");
    }
}

轨迹与 ETA：位置可丢，履约状态可恢复Tracking and ETA: lossy points, recoverable fulfillment

Authorize order ownership/current attempt before subscribing; revoke/rebind after completion or reassignment. Pushes carry generation, attempt, epoch and sequence. Reconnect fetches an authorized current snapshot, and the client rejects old generations. Strict privacy also checks authorization at the server send gate or bounds grants; a DB version change cannot retract bytes already in flight.

WebSocket can carry courier bidirectional traffic; SSE suits one-way viewers. EventSource supports reconnection/Last-Event-ID without automatic complete history. [8][7] A slow viewer keeps only the latest point. Delivered/cancelled/reassigned use durable control state/events, never the overwriteable location slot or inferred movement.

到店与出餐并行，降级不能制造新事实Parallel preparation and travel; honest degradation

未取餐：到店 4 分钟、出餐剩 6 分钟、到户 8 分钟，则 ETA=max(4,6)+8=14 分钟；相加为 18 重复算了并行等待。取餐后只算剩余送达路径，多单要包含已有停靠并保护先前承诺。

本地 Routing 等待预算耗尽不代表它回复失败。优先用仍有效且绑定当前 attempt、阶段、起终点和交通上下文的缓存，标低可信；单元素失败、缓存过期/错上下文则 ETA 暂不可用，不能把缺失路耗填零。直线距离÷假设速度只是粗参考。位置过期显示最后更新时间，并停止把它用于新派单。

Before pickup, 4 min travel, 6 min remaining preparation and 8 min delivery give ETA=max(4,6)+8=14 min. Adding 18 double-counts concurrent waiting. After pickup use remaining travel; multiple orders include existing stops and protect prior promises.

Exhausting the local Routing wait budget is not a failure reply. Prefer valid cached durations bound to current attempt, phase, endpoints and traffic context, labelled low-confidence. Missing elements or expired/wrong-context cache mean unavailable ETA, never zero duration. Distance/speed is only a rough fallback. Display stale point age and exclude stale points from new matching.

饭点运力：有界积压与持久恢复Peak supply: bounded backlog and durable recovery

在 A8 的恒定教学速率下，20/s 到达、12/s 可行派单，净增 8/s；初始 600 个队列空位约 75 秒耗尽。邻区从同一容量权威最多借 2/s 后，净增仍 6/s；若从相同初始空位重算，是 600÷6=100 秒，不是永久稳定。到达降到 ≤14/s 才不继续增长，清掉存量则需严格低于服务率。服务率指可行派单，不是 worker 消费速率。

队列只索引 DB 的 pending_match。按区域限制并发、优先老单/承诺期限；丢队列消息、worker 崩溃仍从权威行扫描，重复任务必须带 generation。下面将扫描候选与锁内重验分开，不能让旧扫描结果越过已接受/已取消状态。

At A8’s constant teaching rates, 20/s arrivals and 12/s feasible assignments grow backlog by 8/s, filling 600 initial free slots in about 75 s. Borrowing 2/s through the same capacity authority still grows 6/s; the same initial 600 slots then last 100 s, without stability. Arrival≤14/s stops growth; draining requires less. Service means feasible assignments, not worker dequeue speed.

The queue indexes durable pending rows. Bound per-zone concurrency and prioritize age/promise deadlines. Recover lost queue deliveries or workers by scanning authoritative rows; duplicate work carries generation. Scan candidates and revalidate under locks so stale scans cannot override acceptance/cancellation.

Quote short-lived supply before payment. Show supply failure when overloaded; actual request-rate limits may use 429 with optional Retry-After. [9] A quote is not a courier slot. Never discard committed work with 429; exhausted attempts/deadlines persist failure and notification/compensation intent.

After confirmed payment with unknown fulfillment creation, query/retry the fixed upstream identity. Before compensation, the fulfillment authority fences future creation/dispatch with a cancellation tombstone, including when no row exists, then emits a fixed compensation key. Temporary absence alone is insufficient. Accepted/picked custody requires controlled handling before funds race ahead.

Reduce optional point traffic, bound Routing concurrency and tighten new admission. Location authority failure pauses new candidates; fulfillment authority failure stops reservation/acceptance. Recover with jitter and zone quotas while current couriers retain custody.
