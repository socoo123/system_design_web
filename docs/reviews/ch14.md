## 机制与纠错结果

| 原问题 | 实施结果与保证边界 |
|---|---|
| 只有“CAS/幂等”文字，没有实际提交落点 | 上传具体versionId的核实在事务外，随后Video→Upload锁内绑定SourceBinding、保存源回执和唯一Job。先有耐久任务才由事件/扫描唤醒；数据库与队列没有跨系统总事务。 |
| 路径“版本化”可能被旧worker覆盖；重复编码未必字节相同 | J稳定，领取epoch递增且不重置，各epoch使用隔离前缀；create-only PUT与无删除worker权限保护key，每个对象另固定物理versionId。所有清单子URI各自带versionId，CDN保留/转发此内容身份。没有要求编码器输出确定性。 |
| 源checksum类型与算法未具体化 | 源multipart明确选CRC32/FULL_OBJECT，HEAD按algorithm/type/value核对，worker对精确GET字节同算法复算。产物SHA256来自完整字节，不拿multipart复合SHA256或ETag冒充整文件摘要。[13] |
| 任务完成/视频READY分离，旧任务可能覆盖新目标 | 发布一次检查目标J、RUNNING、epoch、有效DB租约和BUILDING；精确Build清单、ready_root和Job.DONE同事务。COMMIT未知新连接回读结果，DONE只确认，不能把ready拨回旧版本。 |
| UPLOADED扫描覆盖不全 | 唯一Job同源绑定提交；扫描到期QUEUED/RETRY_WAIT和过期RUNNING，即使早先唤醒已ACK也恢复。每领取消耗一次预算，临时失败持久next_at；终态人工重驱留操作记录并增加预算，不重置epoch。 |
| HEAD/清单校验之后GC可能先删 | GC按同样Video→Job→Build锁序先提交DELETING再删精确版本；当前ready/会话/留存/有效领取保护引用。发布时仍检查BUILDING及有效领取。源上传清理也与complete共享Video→Upload门，受引用源不删除。 |
| BASE_READY与全档门槛混在叙述 | 基本代码明确全三档发布；BASE→FULL作为独立变体，说明允许配方与单调质量级别，FULL失败保留BASE，不宣称已实现该变体。 |
| 引用[10]重复；Apple对齐要求泛化 | Netflix AV1保留[10]，S3版本化改[11]，补[12]条件写、[13]完整/复合checksum、[14]行锁、[15]READ COMMITTED。Apple一般§8.22的SHOULD与tvOS修订MUST分别说明。 |
