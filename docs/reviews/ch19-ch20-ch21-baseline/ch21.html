30 秒开场：先定义成功，再选择闸The 30-second opening: define success before choosing a gate

中文

我先问订房型还是指定房，住几晚、允许超售吗。默认一地域、同库库存与 hold：每夜条件扣减，整段入住一个事务。确认和释放抢同一 hold 的状态，回补按它拥有的房晚做。秒杀若入口超过 DB 预算，我加 Redis 闸，Lua 只给准入 token，真正成功仍是 DB 已提交的 HELD。提交未知先查同一请求键，关闭迟到创建后才修复闸。Outbox 负责 DB 状态和事件，重建还要暂停与 epoch 围栏。

本场只设计有限库存的占用、确认和归还。酒店搜索、动态定价、渠道聚合和支付账本留在接口边界；订单生命周期见 Ch18，消息投递见 Ch20。从支付侧收到“已收款”只是确认指令的输入，不能跳过库存权威的判定。

房型池不是唯一资源。某酒店标准房同一夜有二十间，就是二十个可替换名额；指定物理房间的一夜才是一个名额。秒杀 SKU 也可能有一万件，与房型池同为计数库存，区别主要在争用形状和入口预算。不会因为名字叫秒杀，就把正确性搬到 Redis 或断言必须用某一种锁。

成功分三层：入口令牌只表示可以排队，Lua token 只表示允许试库存，201 HELD 表示 DB 已提交占用；后续 CONFIRMED 才是最终确认。若改成异步创建，只能回 202 pending 并给可查询的稳定身份，承诺的持久受理要先写可靠记录。本章用同步 DB 终审，未知提交回可重试错误，避免把丢得掉的 token 包装成已订房。

English

I first ask whether the booking is a type or an assigned room, how many nights, and whether overbooking is allowed. Default to one region with inventory and holds in one DB: conditional allocation for every night in one stay transaction. Confirmation and release compete on one hold state, and restoration follows the nights it owns. If flash-sale ingress exceeds the DB budget, add Redis admission: Lua grants a token, while actual success is a DB-committed HELD. Resolve unknown commit through the same request key and close delayed creation before repairing the gate. Outbox binds DB state to events; rebuilding also needs pause and epoch fences.

The scope is occupying, confirming, and returning finite inventory. Search, dynamic pricing, channel aggregation, and payment ledgers stay at interface boundaries; order lifecycle is Ch18 and message delivery is Ch20. A payment-side “funds received” message supplies a confirmation command; it cannot bypass inventory adjudication.

A room-type pool is not a unique resource. Twenty interchangeable standard rooms for one night are twenty slots; an assigned physical room-night is one slot. A flash-sale SKU may have ten thousand units and is also counted inventory. Contention shape and ingress budget differ. Its name alone neither moves correctness into Redis nor mandates a lock type.

Success has three levels: an ingress token permits queuing, a Lua token permits trying inventory, and 201 HELD means the DB committed an allocation. CONFIRMED is a later final confirmation. Async creation may only return 202 pending with a stable queryable identity; promised durable acceptance first requires a reliable record. This chapter uses synchronous DB adjudication and a retryable error for unknown commit, rather than presenting a losable token as a booking.

中文

酒店均值要算完整：5,000×200=1,000,000 间，×70%=700,000 个已住房晚/日，再÷3 晚=233,333 次入住/日，÷86,400≈2.70 次/s。这是稳态简化，取消、试占和尖峰另计。库存行数是 5,000×10×365=18,250,000，不是“全国房间数×每天请求数”。一晚最后一间仍可能挤进数百个请求，日均不能代表热点行预算。

秒杀先看差额：2,000÷800=2.5，入口即使已限流，仍超 DB 库存事务预算。正向创建只放 500/s，剩下确认 200/s、释放 50/s，总计 750/s；恢复期间暂停销售，所以不假设恢复作业也免费塞进余下 50/s。500×0.020=10 个平均在途是 Little’s Law 的算术直觉，慢请求会占更久，连接池仍要有硬上限。没有这条预算证据时，DB 条件扣减加入口限流可能已经够，Redis 可以不加。

English

Compute the hotel mean fully: 5,000×200=1,000,000 rooms, ×70%=700,000 occupied room-nights/day, ÷3 nights=233,333 stays/day, ÷86,400≈2.70/s. This steady-state simplification excludes cancellations, attempted holds, and peaks. Night rows are 5,000×10×365=18,250,000, not national rooms times daily requests. Hundreds of requests may still contend for the last room; a global mean does not size a hot row.

For the sale, 2,000÷800=2.5: even rate-limited ingress exceeds the inventory-TX budget. Admit only 500 creates/s; 200 confirms/s and 50 releases/s bring the total to 750/s. Sales pause during recovery, so its work is not assumed to fit freely in the remaining 50/s. 500×0.020=10 mean in-flight is the arithmetic intuition of Little’s Law; slow requests hold connections longer, so a hard pool limit still applies. Without this budget evidence, DB conditional allocation plus ingress limiting may already suffice and Redis can be omitted.

1 · 先画库存权威，再加展示缓存1 · Draw inventory authority before the display cache

中文

资源键先写清楚：房型池是 (hotel_id, room_type_id, stay_date)，指定房晚是 (room_id, stay_date)，SKU 是 (campaign_id, sku_id)。酒店区间统一成当地营业日期的半开区间 [入住日,退房日)，住三晚只占三行，不把退房日也扣一间。时区只用于把用户输入变成营业日期，不靠客户端时钟判断 hold 是否过期。API 拒绝非正整数 q 和空日期范围，DB 的 hold_items.q 也设为正数约束。

计数池可存 free,reserved,confirmed,cap，创建在 DB 执行 UPDATE ... SET free=free-q,reserved=reserved+q WHERE key=? AND free>=q 并检查影响行数。在 PostgreSQL 18 的 Read Committed 下，竞争更新会等待，并重新检查最新行上的条件 [1]。这个具体单行模式可以不用应用先读 version；加 version=expected 是为了检测其他业务变化，不是“不加 version 就会超卖”。所有写必须走同一条件路径，不能留一个管理员无条件扣减后门。

CHECK 再兜住非负数与 free+reserved+confirmed=cap，这些列要 NOT NULL。它保护同一行，不能替你验证另一张表的 hold 所有权，普通 CHECK 也不保证跨行总量 [2]。指定房可用活跃 occupancy 表上的唯一键，每夜插一行，释放时同事务删除活跃占用；若和历史共表，改成覆盖 HELD/CONFIRMED 的部分唯一索引。对日期区间建排他约束是另一种模型，需明确区间和取消后的活跃谓词，不用把三种模型同时堆成默认答案。

正常 POST 是 API 鉴权、校验请求键与摘要、DB 条件占用并存 hold，知道提交后返回 201。重放返回同一 hold 身份和当前状态；第一次曾是 HELD，不代表一天后重试还能宣称它仍活跃。展示查询可以先读 Read Cache，缓存值只提示“可能有房”。实际售罄沿 DB → API → Client 拒绝，缓存脏值不会越过 DB 终审。

代价是热门一夜仍由同一行串行，缓存只减少详情读，不能加快这条竞争写。简单低流量酒店可以先直读主库，省下派生状态；需要缓存时，用短 TTL、事件失效和监测跟踪陈旧，不承诺展示剩余数精确到每一毫秒。渠道外部库存也不能只看本库 cap，必须把外部确认与可回滚协议作为新增边界。

English

Write resource keys first: a pool uses (hotel_id, room_type_id, stay_date), assigned rooms use (room_id, stay_date), and a SKU uses (campaign_id, sku_id). Normalize a hotel stay to local business dates [check-in,check-out); three nights occupy three rows, excluding departure day. Time zones convert input dates; client clocks do not decide hold expiry. API rejects nonpositive or noninteger q and empty date ranges; DB hold_items.q also has a positive-quantity constraint.

A counted pool may store free,reserved,confirmed,cap. Creation executes UPDATE ... SET free=free-q,reserved=reserved+q WHERE key=? AND free>=q and checks the affected count. PostgreSQL 18 Read Committed waits on competing updates and rechecks the condition on the updated row [1]. This specific single-row pattern need not first read an application version. Adding version=expected detects other business changes; its absence does not imply oversell. Every writer must use the guarded path, with no unconditional administrative allocation bypass.

CHECK backs up nonnegative counters and free+reserved+confirmed=cap, with NOT NULL columns. It protects one row, not ownership in another hold table or a cross-row aggregate [2]. Assigned rooms can use uniqueness on active occupancy, inserting one row per night and deleting active occupancy in the release transaction. If history shares the table, use a partial unique index for HELD/CONFIRMED. Range exclusion is another model requiring interval and active-state predicates, rather than stacking three defaults.

A normal POST authenticates, checks request identity and hash, allocates conditionally and persists the hold, then returns 201 after known commit. Replay returns the same hold identity with its current state; an original HELD does not promise the hold is still live a day later. Display reads may use Read Cache as a hint. Actual sold-out rejection returns DB → API → Client; stale display data cannot bypass DB authority.

The hot night still serializes on one row. Cache reduces detail reads, not contention writes. A small hotel can read Primary directly and avoid derived state. If caching is needed, short TTLs, invalidation events, and staleness monitoring apply without promising a millisecond-exact display. External channel inventory also cannot rely only on local cap; external confirmation and rollback protocols form an additional boundary.

2 · 三夜入住必须全拿或全不拿2 · A multi-night stay is all nights or none

中文

主例初始可用 [2,1,2]，一间房住三晚，目标是 [1,0,1]。一笔事务先建立请求身份，再按日期顺序对三行条件 UPDATE，逐条确认恰好一行受影响，最后插入 hold、三条 hold_items 和 outbox，提交后才返回。指定房模型则是一次事务插入三条活跃房晚占用，任何唯一冲突撤销整段。数据库事务提供全有或全无与中间状态隔离 [3]，但不会自动推测你的业务“少一晚就不算”。

独立失败例从原来的 [2,1,2] 开始订两间。第一夜暂时变 0，第二夜不足，必须 ROLLBACK；可用仍是 [2,1,2]，不是 [0,1,2]，更不是只把失败的第二夜“退回去”。UPDATE 影响 0 行本身是合法 SQL 结果，应用必须把它转成整段失败。确定失败也在返回前通过同一请求键串行保存 REJECTED 终态；若重复创建已经赢了，则返回既有 hold。失败响应只有在回滚结果已知时才说未占；连接断了就进入未知状态核查，不能在另一条连接凭印象重复扣。

固定按日期排序拿锁，减少 A 先拿 D1、B 先拿 D3 的反向等待。条件 UPDATE 本身也会取得行锁，“乐观锁”不等于数据库完全没有锁。SELECT FOR UPDATE 先锁全范围再检查也能正确，适合需要一起读取复杂定价或限制的短事务，代价是锁持有更长。序列化级别可保护更复杂的跨行谓词，但冲突会要求重试 [1]，不是免费扩大热房晚吞吐。

重试只有在事务已回滚、冲突可重试时才做，重新读全范围并重跑整笔事务；库存不足不做毫无意义的自动重试。A11 最多额外两次，100 个竞争请求最坏 100×(1+2)=300 次尝试。抖动退避和池上限能缓冲，但没有创造新的房间；如果同一夜一直抢最后一间，应该快速拒绝、排队或缩小可接入量。

释放也按范围原子。先锁 hold、CAS 到 RELEASED，再读它的 hold_items，把每夜 reserved 减 q、free 加 q，并在同一事务写 outbox。不能只看到汇总 reserved≥q 就扣，因为其中可能全是别的客人的占用。库存行和所有权失配应回滚并告警，不能为了清扫描任务而继续提交部分回补。

同酒店日期按 hotel_id 共置，是为了避免三夜跨片。它并不保证一笔团体多酒店订单天然原子；若题目要求跨酒店全成全败，要选真正跨片事务或明确的分阶段保留和补偿，成功语义也随之改变。单酒店多夜这一轮不为假想微服务切开事务，把原本一个提交点换成三个危险窗口。

English

The main example starts free [2,1,2]; one room over three nights should leave [1,0,1]. One transaction establishes request identity, conditionally updates each date in order, verifies exactly one row each, inserts hold, three hold_items, and outbox, then commits before replying. For assigned rooms, insert three active occupancy rows in one transaction and roll back the stay on any unique conflict. DB transactions provide all-or-nothing and isolate intermediate states [3]; they do not infer the business rule that a missing night invalidates the stay.

The separate q=2 failure starts at the original [2,1,2]. D1 temporarily becomes 0, D2 is insufficient, and ROLLBACK leaves [2,1,2], not [0,1,2] or a refund of only D2. Zero affected rows are a legal SQL outcome; the application must turn them into whole-stay failure. Before returning a definite rejection, serialize a durable REJECTED outcome on the same request key; if a duplicate create already won, return its existing hold. Claim no allocation only after a known rollback. A lost connection requires unknown-outcome resolution, not another decrement based on a guess.

Acquire dates in fixed order to reduce A taking D1 while B takes D3. Conditional UPDATE itself takes row locks; optimistic locking does not mean a lock-free DB. Locking the whole range with SELECT FOR UPDATE can be correct for complex short-transaction rules, but holds locks longer. Serializable isolation protects more complex cross-row predicates and requires conflict retries [1]; it does not freely increase hot-row throughput.

Retry only known-rolled-back, retryable conflicts by rereading the whole range and rerunning the transaction. Insufficient stock does not justify automatic retries. A11 permits two extra tries: 100 contenders can produce 100×(1+2)=300 attempts. Jitter and pool limits absorb pressure without creating rooms. Persistent contention on the last room calls for fast rejection, queuing, or reduced ingress.

Release is range-atomic too. Lock the hold, CAS to RELEASED, read its hold_items, restore each night’s counters, and write outbox in the same transaction. An aggregate reserved≥q does not establish ownership and may belong entirely to other guests. Counter/ownership mismatch rolls back and alerts rather than committing a partial restoration to clear a scan task.

Co-locating dates by hotel_id avoids cross-shard stays. It does not make a group order across hotels automatically atomic. That scope needs real cross-shard transactions or staged reservation and compensation, with changed success semantics. This single-hotel round keeps one commit point rather than splitting it into three windows for hypothetical services.

3 · 确认与过期争抢一次所有权3 · Confirmation and expiry compete for one ownership transition

中文

创建把 free 移到 reserved，确认把 reserved 移到 confirmed，释放把 reserved 移回 free。举一个 cap=10 的 SKU：先占 3 件是 (free,R,C)=(7,3,0)；确认后 (7,0,3)，可用没有增加；释放后 (10,0,0)。这两种终态互斥，同一 hold 不会先确认再作为“到期库存”释放。合法售后取消另有状态与政策，不混进未付款 hold 的回补函数。

确认与扫描都锁同一 hold 记录，条件更新只从 HELD 出发。确认要求在拿到锁后读取的 DB 权威当前时间早于 deadline；释放要求时间达到或超过 deadline。例如 PostgreSQL 的 now()/CURRENT_TIMESTAMP 是事务开始时刻，锁等待后要取 clock_timestamp() 等当前 DB 时钟 [9]。截止定义为拿到锁后的串行判定点，提交本身可能晚于 deadline，不承诺墙钟绝不晚提交。多夜创建也要服从短事务和锁等待预算。状态、逐夜计数和 transition_version 一起事务提交，只有受影响一行的胜者生成事件；败者读出当前终态返回。

如果确认先赢，过期扫描看到 CONFIRMED 就做零次恢复。如果释放先赢，付款后来的确认不能把 RELEASED 改回 CONFIRMED，因为房晚可能已给别人。它返回库存确认失败，由支付/订单侧记录已付款未获库存，进入对账、退款或人工处理。安全释放解决的是名额不会被重复还，不替代支付成功的商业补偿。

deadline 是状态转换资格，不是一个会自动执行事务的时钟。扫描每 5 秒是 A9 的目标；线程排队、主库故障会让实际释放更晚。在此期间到期 HELD 仍占 R。拿“15 分钟到了”从重建的 reserved 里减掉，却未完成释放事务，会把同一件库存再卖一次。少卖要监控并尽快修，但不能用放宽占用真相换吞吐。

每次释放保留确定的事件键，例如 (hold_id, transition_version)，重复扫描、重复调用和消息重投都读终态。DB 更新和 outbox 在一次提交里，不采用“状态已改 RELEASED，进程下一行再加库存”的做法；否则崩溃后状态已经阻止补做，库存反而永久少了一份。外部 Redis 效果另外去重，不拿 DB 的一次 CAS 代替跨网络幂等。

指定房晚与房型池的释放策略不同，所有权原则一样。前者删除本 hold 的活跃占用，历史保留；后者增加本 hold_items 每夜对应的 free。业务若允许房型超售，先明确总量、停售、安全余量和安置成本，设置整数 cap 并写到同一行。不能把某书的 10% 当行业默认；本章 cap=total，指定房和秒杀不允许隐含超卖。

English

Create moves free to reserved; confirm moves reserved to confirmed; release moves reserved back to free. For cap=10, holding 3 gives (free,R,C)=(7,3,0); confirming gives (7,0,3) without increasing free; releasing gives (10,0,0). The terminal outcomes are exclusive. A hold cannot confirm and then restock as expired. Legitimate post-sale cancellation has separate states and policy.

Confirmation and scanning lock the same hold row and conditionally transition only from HELD. Confirm checks authoritative current DB time after lock acquisition against deadline; release requires time at or beyond it. For example, PostgreSQL now()/CURRENT_TIMESTAMP use transaction-start time; after locking, use current DB clock such as clock_timestamp() [9]. The cutoff is the serialized decision after lock acquisition; commit itself may occur after deadline, so there is no wall-clock commit promise. Multi-night creates also obey short-transaction and lock-wait budgets. State, night counters, and transition_version commit together. Only a one-row winner emits the event; losers return the existing terminal state.

If confirmation wins, expiry observes CONFIRMED and restores nothing. If release wins, late payment cannot change RELEASED to CONFIRMED because another guest may own the nights. Reject inventory confirmation and let payments/orders record paid-without-inventory for reconciliation, refund, or manual handling. Safe stock release does not replace payment compensation.

Deadline is eligibility to transition, not a clock that runs a transaction. Scanning every 5 seconds is A9’s target; queuing and DB failures add delay. An expired HELD still occupies R. Removing it from rebuilt occupancy merely because 15 minutes passed, without a release transaction, can sell the same unit again. Monitor undersell without weakening authority.

Each release has a deterministic event key such as (hold_id, transition_version). Repeated scans, calls, and redelivery return the terminal result. DB stock restoration and outbox share one commit; do not set RELEASED then restore counters in the next application step, as a crash could leave a terminal state that prevents repair while stock remains missing. External Redis effects deduplicate separately; one DB CAS is not cross-network idempotency.

Assigned rooms delete this hold’s active occupancy while retaining history; pools restore free for the exact nights in hold_items. If the business allows pool overbooking, define capacity, stop-sale margins, and relocation cost, then write an integer cap to the same authority row. A book’s 10% is not a default. This chapter uses cap=total, with no implicit oversell for assigned rooms or sales.

4 · 规模逼出 Redis 闸，DB 仍然终审4 · Scale earns a Redis gate; the DB still adjudicates

中文

A6 与 A7 才把闸加出来：Edge 给 API 2,000/s，DB 只有 800 笔库存事务/s，还要留确认与释放。Redis Lua 可以先检查 stock 提示、epoch、同用户请求摘要、限购标记及正向创建预算，再一次写准入账本与扣提示值。新 token 上限 500/s，售罄或重复请求不落库存写。单用户限购在 DB 也要有权威约束，否则 Redis 丢标记后换键就能绕过政策。

Redis 文档保证 Lua 执行期间其他命令不能插入 [4]，这是单实例命令的原子执行。写到一半发生脚本错误不能假定所有修改像关系事务那样回滚，所以先校验类型、范围、键格式和预算再变更，脚本应短且有边界。集群多键脚本的 stock 与 token 共用 {sku} hash tag [7]；把一万用户按 user_id 随便分不同槽，会把一个 SKU 的总库存约束拆散。

Lua 返回 token 后，API 进入 DB 同一事务：创建或锁住请求身份，核对摘要和准入 epoch，条件扣减真实库存，写 hold、hold_items 与 outbox。DB 不够就拒绝，即便 Redis 认为有货也不能成功。整个提交已知才回 201；单纯 token 只在内存，客户端等待或得到明确的 pending/错误，不能凭 token 去发货。

首批 10,000 件以 500 新 token/s 至少 10,000÷500=20 秒入闸，假设每 token 一件、不重新开放释放库存；这是节流的设计取舍。真实活动中被释放的件可以再占，所以累计创建 hold 次数、核查读和失败事务都可能超过 10,000，不把“成功数不超过库存”误写成“DB 总工作量不超过库存”。最后确认的件数才受 cap 约束，取消再售是另一个业务周期。

500 创建、200 确认和50 释放合计 750/s，剩下 50/s 只是一份预算余量，不是无界重试入口。观察排队、行锁等待、创建/确认比例与 pending 数，超过预算就减少准入。平均 20 ms 对应十个在途，p99 一抖可能迅速占满连接；并发上限和每类事务速率要一起配置。把 DB 所有耗时藏进 Lua 平均耗时，是另一种虚假容量。

替代方案是直接用 DB 条件 UPDATE 配入口令牌和短队列，或按活动预先分配不可重复的配额给多个闸。前者状态少、可验证，流量已经被控制时完全成立；后者增加配额迁移和利用率不均，必须保证总配额不超过 cap。单热 SKU 不能靠增加 Redis 分片自动并行同一 Lua；Lua 是过滤器，DB 条件库存与所有权才是不超卖的最后保证。

English

A6 and A7 justify the gate: Edge gives API 2,000/s, while the DB has 800 inventory TX/s and also needs confirmations and releases. Redis Lua can check the stock hint, epoch, scoped identity/hash, purchase-limit markers, and positive-admission quota, then write an admission ledger and decrement its hint. Cap new tokens at 500/s; sold-out and duplicate attempts avoid stock writes. Purchase limits also need DB authority, or lost Redis markers and new keys bypass policy.

Redis guarantees no interleaving during Lua execution [4], an execution atomicity property of one instance. Do not assume a mid-script error rolls back all writes like a relational transaction. Validate types, quantities, key formats, and quota before mutation, and keep scripts short and bounded. Cluster multi-key stock and token keys share the {sku} hash tag [7]; spreading users across slots would fragment the SKU-wide constraint.

After Lua returns a token, API performs one DB transaction: create or lock request identity, verify hash and admission epoch, conditionally allocate real stock, and write hold, hold_items, and outbox. Insufficient DB stock rejects even a positive Redis hint. Only known commit returns 201. An in-memory token means waiting or an explicit pending/error result, never shipment permission.

The initial 10,000 units take at least 10,000÷500=20 seconds to admit, assuming one unit/token and no reopening released inventory. This is a throttling trade-off. Released units may be held again, so lifetime creates, reconciliation reads, and failed transactions may exceed 10,000. Successful confirmed units are capped, not total DB work; post-sale cancellation/re-sale is another business cycle.

500 creates, 200 confirms, and 50 releases total 750/s. The remaining 50/s is budget headroom, not an unbounded retry lane. Watch queuing, lock waits, transition ratios, and pending inventory and reduce admission as needed. At a 20 ms mean there are ten in-flight creates, but slow-tail requests can exhaust connections quickly; configure both concurrency and per-class rates. Hiding DB time behind a Lua mean gives false capacity.

Alternatives include DB conditional UPDATE with ingress tokens and a short queue, or preallocated nonoverlapping quotas across gates. The first is simple and valid when ingress is controlled. The second adds quota migration and uneven utilization and must keep total quotas within cap. Adding Redis shards does not parallelize one hot SKU’s Lua. Lua filters attempts; authoritative DB stock and ownership provide the final oversell guard.

5 · 提交未知与 Redis 孤儿必须关闭迟到写5 · Unknown commit and Redis orphans must close delayed writes

中文

最危险的窗口不是 DB 明确拒绝，而是它已经提交、API 没拿到回程。客户端超时重试时带同一请求键与摘要；请求身份域至少包含用户和操作，不能让另一用户猜到键后读出或取消你的 hold。不同数量或日期复用同键返回冲突；同键终态不重新创建。Redis 看见已有 token 也只能返回同一准入身份，再由 DB 查明实际状态。

先看孤儿：Lua 扣了提示数，进程死在写 DB 之前，没有 hold 行可扫描。准入账本记录 token、请求身份、epoch、数量、请求摘要和待核查时间，核销前不直接 TTL 删除它。过了 A10 的三十秒只说明要核查。Redis 的 keyspace 通知通过 Pub/Sub 投递，断线期间会丢，expired 事件也不保证在 TTL 到零瞬间出现 [5]；更基本的是，删除 token 本身从不会替另一个 stock 键 INCR。

Reconciler 用同一 DB 请求唯一键执行串行的“解结果或取消”协议。有记录就锁并读取；不存在则争取插入 CANCELLED tombstone 并提交。CREATE 必须先写这把唯一键，再扣库存，且见到终态就停止。若旧 CREATE 已在事务中插入键，取消的唯一冲突或锁等待必须等它提交/回滚；若取消先成功，迟到 CREATE 看到墓碑只能返回取消。不能只 SELECT 查空、发 INCR，再任由旧请求落库。

若查明是 HELD，按 deadline 决定等待还是走正常释放事务；CONFIRMED 不回配额；CANCELLED、REJECTED 或 RELEASED 才产生恢复这次 token 的终态收据。对 DB 结果仍不确定、无法取得锁或主库不可用，保持待核查并封顶新准入，不恢复库存。这里接受暂时少卖，避免“为了用户快一点”在提交未知时发出第二份名额。

DB 的一次释放只是第一段幂等。Reconciler 发 Redis 收据后可能丢了 ACK，必须重发同一 epoch+token_id+transition_version。Lua 校验 token 所有者、数量与 epoch，原子登记已应用收据再加一次提示数。旧状态没有拥有权，或已确认/已处理，就加零次；已取消而没有 token 的请求也不凭空创造配额。收据去重记录不能比最大重放窗先消失。

若恢复效果失败，DB 的 free 已经正确，Redis 提示可能偏少；Outbox 可可靠地安排再次同步，或按下节重建。若 Redis 状态整层丢失，孤儿账本也一起丢了，不能声称扫描一定找回每个 token。此时关闭闸、围栏旧 epoch，再从 DB 重建；未成功落库的 token 被新 epoch 淘汰，旧 API 事务也必须被 DB 拒绝。

15 分钟是占用期限，24 小时是本章合同重试窗，两者不是同一个 TTL。请求身份/tombstone 至少保留到重试窗结束且在途任务排空；活跃 hold 的所有权还要保存更久。若要删去老身份，服务端必须能验证旧键的有效期或签发域，过期只查询/拒绝，不能把任意旧包当新 CREATE。合法的新购买意图使用新键，不能以“缓存过期”为理由对同一意图再扣库存。

English

The most dangerous window is a DB commit whose reply never reached API. Retries carry the same key and hash. Scope identity by user and operation so another user cannot guess a key and read/cancel your hold. Reusing the key with changed quantity/dates conflicts, and terminal keys never create again. Redis can replay an admission identity, but the DB resolves actual status.

For an orphan, Lua decremented the hint and the process died before the DB write: there is no hold row to scan. Keep token, identity, epoch, quantity, hash, and investigation deadline in the admission ledger until resolution, without deleting it by TTL. A10’s thirty seconds only triggers investigation. Redis keyspace Pub/Sub loses events while disconnected, and expired events need not arrive exactly at TTL zero [5]. Deleting a token also never INCRs another stock key.

Reconciler serializes “resolve or cancel” on the same DB unique identity. Lock an existing row, or compete to insert and commit a CANCELLED tombstone. CREATE must claim this key before stock allocation and stop on a terminal state. If old CREATE already inserted the key in its transaction, cancellation waits for commit/rollback through uniqueness or locking. If cancellation wins first, late CREATE returns cancelled. A missing SELECT followed by INCR while delayed CREATE remains possible is unsafe.

A resolved HELD waits or undergoes normal expiry release depending on deadline. CONFIRMED gets no quota restoration. CANCELLED, REJECTED, or RELEASED can produce a terminal receipt for this token. Unknown outcomes, lock failures, or unavailable Primary remain pending with new admission capped, without restoring inventory. Accept temporary undersell rather than issuing another slot before knowing commit.

One DB release is only the first idempotency boundary. A lost Redis ACK requires replay of the same epoch+token_id+transition_version. Lua checks owner, quantity, and epoch and atomically records application with one hint restoration. No ownership, confirmation, or prior processing means zero restoration; a cancelled request without a token creates no quota. Keep receipt deduplication beyond the maximum replay window.

If the effect fails, DB free stock is already correct while Redis may understate it. Outbox can reliably schedule synchronization retries or recovery can rebuild. Whole Redis loss also loses orphan records; scanning cannot promise to recover every token. Close admission, fence the old epoch, and rebuild from the DB. Unpersisted old tokens are discarded and old API allocations must be rejected by the DB fence.

Fifteen minutes is the hold deadline; twenty-four hours is this chapter’s contractual retry window. Keep identity/tombstones until both retry-window end and in-flight drain, with live ownership retained longer. To delete old identities, the server must validate old key lifetime or issuance scope; expiry permits only query/rejection, never silently treating an old packet as new CREATE. A genuinely new purchase uses a new key; cache expiry cannot justify a second allocation for one intent.

6 · 暂停、围栏、快照、恢复；Outbox 不越界6 · Pause, fence, snapshot, resume; keep outbox inside its boundary

中文

Redis Lua 的执行原子性不等于重启持久性。AOF 和复制能缩小数据丢失风险，不能把每次已返回的准入 token 当成最终售出真相；Redis 的每秒 fsync 策略明确有丢最近写的窗口 [6]。因此 DB 每次创建保留条件库存终审。若只在 Redis 不超卖，重启恢复出更多 stock 就会把旧销售再卖一遍；本方案最多多发准入、DB 拒绝，并由监控触发关闭闸。

简单可验证的恢复协议先暂停同 SKU 的全部库存状态变化，包括创建、确认和释放，暂停指令写 DB active 标记并将 epoch 从 e7 增到 e8。相关事务都要锁/验证同一围栏记录，暂停提交会等已进入的事务结束，尚未执行的 e7 创建之后被拒绝。入口开关是减压，DB 围栏才是最后保护。已付款等待确认的请求要返回 pending 并可重试，不能在维护期间悄悄绕过 pause。

排空后取一致快照，用 free=cap−reserved−confirmed 重建，包含所有 HELD，不因已经到 deadline 而漏掉；同时装载仍活跃 hold 的所有权和必要的身份/终态去重信息。把新 e8 闸设置为未就绪，完整安装基线并得到确认后才打开 DB active 与入口。若中途失败继续关闸，不能半份数据就营业。

快照已经包含 e7 的 DB 变更，旧 e7 Redis 效果一律忽略，不能回放后把同一次释放再加一遍。恢复后，原来在 e7 创建但仍 HELD 的 hold 可以正常确认/释放；新事务按当前 e8 生成事件，释放依照重建进 e8 的所有权恢复配额。不能只沿用 hold 创建 epoch，结果把所有旧 hold 的未来释放永久丢掉。全量暂停较容易核验；若要求不中断重建，必须增加快照位点、变化日志追平与切换屏障，不是一句“从 DB 读一遍”就够。

Outbox 在库存/hold 同一 DB 事务里记录状态变更与版本，Reconciler 作为投递器读取并发给 Order API，收到对方持久确认才标送达。请求 API 不在提交后裸发消息。投递器崩在发出后、标记前，会再次发；AWS 的模式原文明确提醒重复消息与消费者幂等 [8]。消费者以 event_id 去重，并以 hold_id 的 transition_version 拒绝旧版本覆盖终态；去重记录与本地业务效果同事务，才不在崩溃后丢工作。

这张 Outbox 只闭合“DB 状态已变但事件没发”的窗口，不包含此前 Redis Lua。Redis 同步失败用终态收据和重建收尾；外部订单/支付各有自己的幂等域。本章接受派生闸暂时少卖、维护暂停与事件延后，保住的硬约束是 DB 已确认加未释放占用不超过 cap。是否用异步事件、是否买更小恢复停顿，是成本选择，不能写成所有路径已经恰好一次。

English

Atomic Lua execution is not restart durability. AOF and replication reduce data-loss risk but do not turn an acknowledged admission token into sales authority; Redis documents a recent-write loss window with once-per-second fsync [6]. Every DB create retains conditional stock adjudication. Redis-only correctness could resell old sales after restart restores excessive stock. Here excess tokens are rejected by DB and monitoring closes the gate.

The simple verifiable recovery pauses every inventory transition for the SKU: creates, confirms, and releases. Write DB active=false and advance epoch e7 to e8. All such transactions lock/check the same fence, so pause commit waits for entered transactions and later e7 creates are rejected. The ingress switch reduces load; the DB fence provides final protection. Paid requests waiting to confirm remain pending/retryable during maintenance rather than bypassing pause.

After draining, take one consistent snapshot and rebuild free=cap−reserved−confirmed, counting every HELD even past deadline. Install live hold ownership and required identity/terminal deduplication state. Keep the e8 gate unready until the baseline is fully installed and acknowledged, then enable DB active and ingress. A failed installation stays closed rather than serving half a snapshot.

The snapshot already includes e7 DB changes, so ignore e7 Redis effects instead of applying a release twice. A still-HELD hold created in e7 may confirm/release after recovery; the new transition generates a current-e8 event, and release restores quota against its imported e8 ownership. Reusing only the hold’s creation epoch would lose all future releases of old holds. A full pause is easier to verify. Online rebuilding instead needs a snapshot position, replay catch-up, and cutover barrier, beyond reading the DB once.

Outbox records state and version in the same DB inventory/hold transaction. Reconciler reads and delivers to Order API, marking delivery only after durable acknowledgement. Request API does not publish naked after commit. A crash after send but before marking redelivers; AWS’s source explicitly warns of duplicates and consumer idempotency [8]. Consumers deduplicate event_id and use per-hold transition_version to reject stale overwrites. Deduplication and local business effect share a transaction to avoid lost work after crash.

Outbox closes the DB-state/event-send window, not the earlier Redis Lua boundary. Terminal receipts and rebuilding repair Redis effects; orders/payments have their own identity domains. Accept temporary gate undersell, maintenance pause, and delayed events while keeping DB confirmed plus unreleased holds within cap. Async delivery and smaller recovery pauses are cost choices, not a claim of universal exactly-once.

“热房晚也上 Redis 吗？”先测条件事务、行锁等待和失败比，若 DB 预算能守住，入口限流就足够。加闸后不删 DB 终审，多个房晚还要同事务；跨夜 Lua 同槽与多资源可用性不能凭单 SKU 脚本直接迁移。

“维护不能停确认怎么办？”把 A14 改掉就要买更复杂的在线重建：快照位点、变化日志、按版本对齐与切换 fence。只有读出 free 数，无法知道读期间哪笔释放已经算进来。先给暂停版完整边界，再说明多花什么换掉停顿。

“剩余数必须精确吗？”如果产品要求每次读都线性一致，就查库存权威或用可证明的读协议，支付更多读预算；展示缓存只能承诺限定陈旧。准确剩余和公平先到先得也不是同一要求，公平排队、账号反作弊、外部渠道同时占房要分别澄清。

English

“Should a hot hotel night also use Redis?” First measure conditional-TX cost, lock waits, and rejection ratios. If the DB budget holds, ingress limiting suffices. Adding a gate does not remove DB authority or multi-night transactions; single-SKU Lua does not automatically solve multi-resource availability and slot placement.

“What if confirmation cannot pause during maintenance?” Changing A14 buys online rebuilding with snapshot position, change-log catch-up, version alignment, and a cutover fence. Reading free alone cannot reveal which concurrent release was included. Present the complete paused design first, then name the added machinery that removes the pause.

“Must remaining stock be exact?” Linearizable reads require the inventory authority or a proven read protocol and additional read budget. Display cache can only promise bounded staleness. Exact counts and fair first-come-first-served are also different requirements; clarify queuing fairness, anti-abuse, and simultaneous external-channel holds separately.

收尾：说清名额在哪里、什么时候能归还Close: say where ownership lives and when it may return

中文

酒店从 DB 全房晚事务开始，指定房唯一占用与房型池计数分开。秒杀从预算逼出 Redis 准入闸，DB 终审保不超 cap；Lua token、HELD 与 CONFIRMED 是三个不同结果。提交未知不猜，先锁同一请求身份解结果或取消；确认与过期抢一次状态，回补库存、事件同事务。Redis 效果另去重，重启先暂停和围栏再重建，Outbox 不跨出数据库边界。

合上页面，拿三夜 [2,1,2]、一个丢 COMMIT ACK 的 token 和一个 e7 迟到请求，分别走到安全终态。能说清“为什么此刻不允许归还名额”，比背“Lua+TTL+Outbox”更有用。下一章 Ch22 把资源换成 blob，继续追踪元数据提交与数据持久性的边界。

English

Begin hotels with one transaction for all nights and distinguish assigned occupancy from counted pools. Earn a Redis admission gate from flash-sale budgets while DB authority enforces cap. Lua token, HELD, and CONFIRMED are different outcomes. Resolve unknown commit by locking the same identity, not guessing. Confirmation and expiry win one state transition; stock and event commit together. Redis effects deduplicate separately, and restart rebuilds only after pause and fencing. Outbox stays inside its DB boundary.

Close the page and walk three nights [2,1,2], a token with a lost COMMIT ACK, and a delayed e7 request to safe outcomes. Explaining why a slot cannot yet be restored is more useful than reciting “Lua+TTL+Outbox.” Ch22 changes the resource to blobs and continues tracing metadata commit versus data durability.
