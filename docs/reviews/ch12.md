## 纠错与实现契约

| 开始时问题 / 未落地处 | 本轮处理 |
|---|---|
| 30 台按 60k 规划，失一台后把 29×100k 叫余量，60% 口径含混 | 正常至少30，同预算 N−1 取31：30×60k=1.8M；30→29 只有1.74M规划容量，62.07%虽低于原始上限，已超60%。正文、A3、D1F5、英文、闪卡一致。 |
| seq/去重/outbox 只有事务承诺，无实现 | 普通 conversation.head 行锁持到提交；message/receipt/outbox 与 head 同事务，真实主键限制；发送和成员/策略变更先锁同一会话。失败整体回滚，不使用独立 nextval。ACK到达顺序不等于提交顺序。 |
| 成员检查在正文中可能理解成锁外缓存检查 | 新发送在会话锁内检查当前 membership；同键已提交结果可返回发送者自己的最小回执，即使后来被移除，也不返回正文。 |
| SQL事务容易被误认为自动获得三副本保证 | PG18 DDL/行锁仅落地约束/本地原子边界；A5还要求共识持久日志、事务决定、无已确认尾部回退的提升与恢复。正文说明可选事务/复制数据库承载且未实现/实测该存储。 |
| 24h自动重试窗易被理解成任意迟到重复安全 | 本例不 GC send_receipt，正文明确回执可比一年正文更久；GC另需可验证关闭的发送epoch/绝对受理期限及有界在途排空。实际负例验证删receipt后同旧键再插入。 |
| ACK未知、Relay发布与标记边界不够具体 | commit-unknown丢连接同键查权威；Relay只发布已提交行，Queue耐久接受后再标记，发布后标记前崩溃可重复；envelope为纯编码，唯一事件键(conv,seq)。 |
| 连续前缀缺少过滤/保留期闭合规则 | 设备本地entry+cursor同耐久事务；TOMBSTONE/服务端认证OMITTED覆盖原seq，不把过滤空行当已齐；过保留floor显式RESET_REQUIRED，新授权baseline/view，旧页不得混用。 |
| D4F5 “max(108,107)”可能误指把Read和Delivered混成一列 | 各列独立max，Read≤本设备已报告的连续Delivered；D=108/R=108后晚D107均不回退。UI声明不能证明人眼或受攻击设备真实落盘。 |
| Receipt svc单独画成存储容易隐含跨库事务 | 明确Receipt Store为conversation/member同权威分区同库的逻辑表组；独立svc不是独立事务数据库。成员行锁与receipt初始化/max同事务，不假装跨库FOR SHARE。 |
| epoch路由仅口头要求比较 | 条件SQL展示登记持锁递增、到期/关闭只匹配epoch+connection；持久epoch不随缓存TTL消失，未知登记废弃后重登记。不是暂停旧网关的分布式锁。 |
| 仅检查成员版本可能被读为移除即收回所有字节 | 定义授权派发点检查，拒绝变更后新授权，旧view失效；已授权在途/已保存字节不可收回。更严格撤权响应后的发包截止需网关确认屏障，本例未实现。 |
| Presence“先快照再订阅”有空窗 | 先订阅缓冲再读快照，仍以当前租约/周期刷新修补丢提示；不把无可靠游标的Pub/Sub宣称无缝同步。 |
