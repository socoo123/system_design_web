## 发现、纠错与保证

| 发现 | 处理与证据 |
|---|---|
| 原 Delivery 只有 owner/until，未说明旧 worker 如何避免覆盖继任状态 | 增加单库 `lease_epoch`。领取短事务持行锁，结果事务只更新同代次且仍 leased 的任务。旧代次仍保存自身 Attempt 的迟到证据。代次只约束本地状态，不能取消旧外部调用或冒充供应商 fencing。 |
| 只有接口与数据表，事务、领取和重试没有可追踪实现 | 补4段同源实现/约束片段，涵盖唯一冲突先回滚再回读、COMMIT未知不发送、条件领取、started记录、结果/重试outbox同提交及补偿扫描。 |
| 停止重试容易被理解为确定未发送；迟到成功可能隐藏在 failed/expired 后 | `uncertain`保留未知可能性，查询返回调度状态与Attempt/Receipt观察两栏。迟到accepted仍展示新证据但不重开调度；accepted/delivered/display/read/业务verify分别定义。缺少回执或无法关联时保持未知，不猜配。 |
| APNs 429 被概括为单token过热 | 按reason区分TooManyRequests和TooManyProviderTokenUpdates，不能对所有429只退避设备。[3] |
| 原图和假设给FCM发送设置5秒，而新核对的scale-fcm建议至少10秒 | 正文、A8、D3 F2–F5标签/描述/图注与代码统一10秒；30秒DB租约另扣门、网络和结果预算。该推荐不是所有供应商的默认超时。[2] |
| 通用秒级SMS退避可能被误套给FCM/APNs | FCM429尊重Retry-After，无header等60秒，整体/topic初始至少1分钟；APNs5xx为15分钟。provider_not_before取max后不再受本地60秒上限截短，超过验证码not_after即过期。[2][3] |
| 失效token响应可能误伤新的登记或迟到重新登记 | 所有重新登记都递增version，即使token字符串相同。Device更新带尝试版本。APNs还核对失效timestamp与登记时间；仅在已知时钟误差下能证明适用时发INVALID_TOKEN，不能比较则REGISTRATION_RECHECK并不删登记。该保守策略是教学设计，不是Apple提供了时钟界。[3] |
| 只有未发布outbox不能恢复已经发布却丢失的唤醒 | 扫描到期queued/retry_wait及过期leased，并同事务写repair outbox和wake_no，不重置终态。last_woken_at在接受时初始化并声明NOT NULL默认值。首次未补偿过的queued及expired lease均有反例检查。 |
| 实施中发现repair/retry若只以(id,数字)命名会跨事件撞键 | ready/retry/repair/dlq分别带事件命名空间；同一语义重放仍使用稳定键。 |
| 24小时幂等保留可能被误读成24小时后必可重用 | 改为至少24小时、长于调用方重试窗口；本例随Notification保留30天，不承诺提前复用。回放先于新请求时间校验，原成功请求不会因后来过期被误拒。 |
| 外部载荷/受众引用若尚未耐久就回202，数据库事务无法补救 | 小OTP加密载荷同库保存；外部引用在接受前已耐久，数据库回滚的孤儿另行清理。活动不在接口内展开千万人。 |

本章原容量推导已经区分用户通知与设备端点，本轮保留并独立复算，没有把
旧章正确的数字记成新纠错：140M/86400=1,620.37037/s，5倍=8,101.85185/s；
14M/2000=7,000s≈1.94444h；共享余量379.62963/s下活动约36,878.05s≈10.24390h；
