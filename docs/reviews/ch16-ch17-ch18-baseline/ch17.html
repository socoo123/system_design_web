30 秒开场：先定入口的契约 The opening: define the ingress contract

中文

我先按单地域、业务 API 来设计：峰值一万次请求每秒，统一 L7 网关在门口做鉴权、粗权限、配额和路由，后面的订单服务保留库存和订单归属判断。网关不保存用户会话，四个实例共享限流状态，路由配置和验证密钥在本地缓存。正常响应原路返回，超限在门口返回 429，下游超时返回 504。客户端页面差异大时再加 BFF；服务间治理另有边界。

澄清先收成三个能改图的问题：客户端是否需要差异聚合，凭证由谁签发以及能否离线验证，哪些接口在限流存储故障时必须拒绝。移动端、网页端只需相同接口时，先保留统一网关；支付、登录和短信不能沿用公开列表的降级政策。入口是南北向业务数据面；控制面负责发布路由、密钥来源和策略版本，不能把这两个名字写反。

English

I design business APIs in one region at 10,000 peak requests/s. A shared L7 gateway owns authentication, coarse permission, quotas, and routing; Orders retains inventory and object-ownership decisions. The gateway holds no authoritative user session. Four instances share quota state and cache routing configuration and validation keys locally. Responses return along the original path; quota exhaustion returns 429 and upstream timeout returns 504. Add a BFF when client page requirements justify one, with a separate boundary for service-to-service governance.

Three clarifications change the picture: whether clients need different aggregation, who issues credentials and whether they can be validated offline, and which routes must reject requests when quota storage fails. If mobile and web use the same APIs, start with a shared gateway. Payments, login, and SMS cannot inherit public-list fallback policy. North-south business requests form the data plane; the control plane publishes routing, key-source, and policy versions.

入口与控制面：先让四台网关可替换 Ingress and control plane: make four instances interchangeable

正常路径与容量：返回也穿过入口 Walkthrough and capacity: the return crosses ingress too

中文

一次读取先经过 L4 LB 到 Gateway。Gateway 使用本地路由快照，剥离身份头，验证凭证，执行配额和粗权限，再把请求发给 Orders。Orders 返回数据，Gateway 组装协议响应，经 L4 LB 返回 Client。网关保存连接、缓存和在途请求是正常的；“无状态”指换一台也能用同一份外部权威记录作出决定，不是机器内存里什么都不能放。

A3 先给每台可用 4,000 QPS，峰值 10,000 ÷ 4,000 = 2.5，向上至少三台；再给失去一台留位置，于是启用四台。四台共有 16,000 可用 QPS，剩三台是 12,000，峰值利用这份已留余量预算的 83.3%。这里的可用能力已经包含舒适余量，不能又乘一次 60%。若丢失一个区域会一次少两台，剩下 8,000 就不够，需要重新算区域故障容量。

带宽要同时看两侧。按 A2，客户端请求入站 10,000 × 2 KB = 20 MB/s = 160 Mb/s，响应出站 10,000 × 4 KB = 40 MB/s = 320 Mb/s。转发请求给 Orders 另有 20 MB/s 出站，接收 Orders 响应另有 40 MB/s 入站，所以整个 Gateway 池每方向各有 60 MB/s = 480 Mb/s 的应用体字节。四台均匀分摊是每台每方向 120 Mb/s；少一台则 160 Mb/s。协议头、TLS、重试和日志另算，不能把外侧 320 Mb/s 当成全部网关网卡需求。

English

A read passes L4 LB to Gateway. Gateway uses a local routing snapshot, strips identity headers, validates credentials, checks quotas and coarse permission, then calls Orders. Orders returns data and Gateway produces the protocol response through L4 LB to Client. Connections, caches, and in-flight requests are normal local state. Stateless means another instance can make the decision from the same external authority, not that memory must be empty.

A3 gives each instance 4,000 usable QPS. 10,000 / 4,000 = 2.5 requires at least three, plus one for a loss, so run four. Four provide 16,000 usable QPS, and three provide 12,000; peak uses 83.3% of that already-reserved budget. Do not multiply usable capacity by another 60%. A failure domain that removes two instances leaves only 8,000 and requires a new zone-loss calculation.

Account for both sides. With A2, client ingress is 10,000×2 KB=20 MB/s=160 Mb/s and client egress is 10,000×4 KB=40 MB/s=320 Mb/s. Forwarding adds 20 MB/s outbound, while backend responses add 40 MB/s inbound. The gateway pool therefore handles 60 MB/s=480 Mb/s of body bytes in each direction. Four equal instances carry 120 Mb/s per direction each; after one loss, 160 Mb/s. Headers, TLS, retries, and logs are extra.

为什么配置不进每条请求 Why configuration stays outside each request

中文

路由、配额和密钥来源由控制面发布，数据面保留最后一份已验证快照。控制面故障时，已有请求继续按旧版本走，新规则暂时无法生效。替代方案是在每次转发前远程查配置，这会把控制面抖动加入所有请求的延迟和可用性账，还可能让一万 QPS 一起等待。同一快照内的策略可原子切换，跨实例、跨资源的更新却仍有传播窗口。

发布要先检查默认拒绝规则、重叠路由、目标集群和期限，再让少量实例采用，确认应用状态后推广。Envoy xDS 的 ACK 表示资源经过验证并有应用意图，并不证明已经全部成功应用；NACK 也不保证该响应里的每个资源都未采用。[7] 本章选择“本地快照全部校验通过才替换”是我们自己的额外契约，不冒充任何协议默认提供的全站事务。

新实例若没有可用快照和验证密钥，保持未就绪，不向 LB 报健康。进程活着与能安全接业务是两种健康；旧实例可继续，空白新实例不能默认放行。连接排空也要单列窗口：发布时先摘新连接，再等在途请求结束或到期限，不突然切断所有 HTTP/2 流。这样控制面中断影响更新速度，实例故障影响局部容量，两个问题不会被一句“无状态就能扩”混掉。

English

The control plane publishes routes, quotas, and key sources; the data plane keeps the last validated snapshot. During a control-plane outage, existing traffic uses the old version and new rules wait. A remote configuration lookup before every forward would add control-plane latency and availability to every request and could stall all 10,000 QPS. One local snapshot can activate atomically, but changes across instances or resource types still propagate.

Validate default-deny policy, overlapping routes, target clusters, and deadlines before a limited rollout, then inspect applied state before expanding. In xDS, ACK signals validation and intent, not successful application; NACK does not guarantee that no resource was accepted. [7] Our all-validated-before-local-snapshot-replacement rule is an additional contract, not an assumed protocol-wide transaction.

An instance without a usable snapshot and validation keys stays unready and must not advertise health to LB. Process liveness differs from readiness to serve safely. Old instances can continue while empty new ones cannot allow traffic by default. Deploys first drain new connections, then let in-flight work finish or expire rather than abruptly cutting all HTTP/2 streams. Configuration availability and instance capacity remain separate failure windows.

鉴权：凭证有效，身份头才有资格进入私网 Authentication: trusted identity starts after valid credentials

正常路径：先验证用途，再写身份 Walkthrough: validate purpose before writing identity

中文

客户端携带的是面向这个 API 的 access token。Gateway 先清理同名身份头，再按预先可信的 issuer 找验证配置，限制允许算法，验签，并检查受众、过期、必要的时间约束与 scope。只有验证完成，才把 tenant、subject 等字段写进内部身份上下文。路径匹配需要先知道 route_id 和所需权限，但用户身份不能来自未经验证的 token 声明。[1]

OIDC ID token 向客户端证明登录，不能因为它也是 JWT 就送进任意资源 API。采用 RFC 9068 的 JWT access token 契约时，资源侧验证 token 类型、issuer 和 audience，避免把别的用途、别的服务的令牌换来调用 Orders 的资格。[2] JWT 只是结构，不保证可撤销也不保证保密；Bearer 凭证通过 TLS 传输，access log 不能把 Authorization 原样留下。[3]

服务若信任身份头，必须同时限制调用方只能来自受信 Gateway 或中间服务，并验证这些对端身份；单纯“在内网”不是证明。这里用入口隔离加 mTLS 约束来源。更严格的系统可把用户上下文签名给下游，或让服务重新验 API access token；这会多花 CPU 和配置成本，却能覆盖信任模型变化。不能把“每服务验签永远错误”当通用结论。

English

The client presents an access token intended for this API. Gateway clears identity headers, selects validation settings from a pretrusted issuer, restricts algorithms, verifies the signature, and checks audience, expiry, required time constraints, and scope. Only then does it write tenant and subject into internal identity context. Route matching may precede authentication to determine requirements, but identity cannot come from unvalidated claims. [1]

An OIDC ID token proves login to a client and is not interchangeable with authorization for an arbitrary API. Under RFC 9068, validate access-token type, issuer, and audience to prevent substitution across purposes and services. [2] JWT is a format, not a guarantee of revocation or secrecy. Protect bearer credentials with TLS and exclude Authorization from access logs. [3]

A service that trusts identity headers must also restrict callers to trusted gateways or intermediaries and authenticate those peers. Being on a private network is insufficient. Here ingress isolation and mTLS constrain the source. A stricter system may sign user context or revalidate the API access token downstream, trading CPU and configuration cost for another trust model. Per-service validation is not universally wrong.

代价与失败窗口：缓存密钥不等于永远信任 Costs and failure windows: cached keys need a policy

中文

按 A5，一万次/秒 × 0.0002 秒 CPU = 2 核，是整个 Gateway 池验签的 CPU 需求；均匀四台每台约 0.5 核，三台约 0.67 核。这不是总 CPU，解析、TLS 与路由还没算。若改成每条 token 都去 IdP introspection，一万 QPS 就变成一万次远程身份查询，身份服务故障会进入所有 API。需要即时撤销时可以选择 introspection，但要明确缓存、超时与拒绝策略，不能只画一个 IdP 就宣称解决。

已知 key 用缓存验证；未知 kid 触发受控刷新，同一刷新合并，限制每台每秒最多一次，失败的未知 key 短时记住。四台最多 4 次/秒，而非攻击流量一万次/秒。不能跟随 token 内任意 jku 去下载密钥，RFC 8725 指出这会引入 SSRF 风险。[1] 缓存里没有可信 key 或旧 key 已过策略允许期限，就拒绝并标明验证依赖不可用，不能把签名检查跳过。

轮换时先发布新公钥，等数据面可验证后再用新私钥签发，并保留旧公钥覆盖旧令牌有效期和允许时钟偏差。A6 的 5 分钟令牌只是示例；泄漏后撤销密钥或主体的生效时间还取决于缓存刷新和吊销政策。无效、过期 token 回 401 和认证挑战，已验证身份缺 route scope 回 403；无法取得验证依赖通常按不可用处理，不能谎称用户凭证必然错误。对象归属仍由 Orders 查询领域记录决定。[3]

English

A5 gives 10,000/s×0.0002 CPU s=2 aggregate CPU cores for validation. Four equal instances use roughly 0.5 core each, or 0.67 with three. Parsing, TLS, and routing are extra. Per-token introspection instead creates 10,000 remote identity queries/s and puts identity-service availability on every API. It may be appropriate for immediate revocation, but requires explicit caching, timeout, and rejection policy.

Known keys validate locally. Coalesce unknown-kid refreshes, cap them at one per second per instance, and briefly remember failed unknown keys. Four instances then generate at most four refreshes/s rather than 10,000 attacker-driven requests/s. Do not follow arbitrary jku URLs; RFC 8725 identifies SSRF risk. [1] If no trusted usable key exists, reject with an authentication-dependency-unavailable classification rather than skipping verification.

Publish a new public key before issuing with its private counterpart, and retain the old public key through old-token validity plus allowed clock skew. A6’s five-minute token is illustrative; compromise response also depends on refresh and revocation policy. Invalid or expired tokens return 401 with a challenge, while a verified identity lacking scope returns 403. An unavailable validation dependency is distinct from proven bad credentials. Orders still checks object ownership. [3]

限流：共享桶成立，故障降级也必须有上界 Rate limiting: shared quotas and bounded fallback

正常路径与原子性：谁可以扣哪个桶 Walkthrough and atomicity: who debits which bucket

中文

鉴权成功后，key 用 tenant、subject 与规范化 route_id，组合能避免不同租户恰好有相同 sub 时相互挤占。method 也要进入路由定义：读订单与创建订单不共用同一政策。未登录路线可以按可信来源解析出的 IP 做粗限，但 NAT 会把许多用户压成一个来源，IP 不替代登录后的用户桶。浏览器缓存和客户端自限能减流量，却没有资格决定服务端配额。

A7 的桶容量 40、每秒补 20。刚满时可放行 40 个突发，之后持续速率趋向 20/s；不是任意一秒只能过 20 个。读取旧令牌、按时间补充、最多补到容量、扣除并更新过期要在一次原子判定里完成。Redis Lua 原文说明脚本执行是原子的，同时也会阻塞其他工作，所以这段操作必须短，不能循环扫描百万桶。[4] 多个键要同一判定时，还要满足实际分片的共址限制。

四台分别维护完整桶会让同一用户同时花四份：4 × 20 = 80/s，突发 4 × 40 = 160。sticky 只能把当前连接粘住，换连接、扩容和故障迁移都会破坏计数。共享 Redis 保留一份逻辑额度，网关实例仍可替换。代价是正常每请求一次判定，一万请求/秒就是一万次操作/秒；按 A8 的 2 ms 等待，约 10,000 × 0.002 = 20 个判定在途，热点单键、网络和脚本预算仍需要实测。

English

After authentication, key the bucket by tenant, subject, and normalized route_id so identical subject strings in separate tenants do not collide. Include method in route identity; reading and creating orders have distinct policy. Public routes can use a trusted source IP for coarse limits, but NAT combines many users, and IP does not replace an authenticated user bucket. Client-side controls cannot authorize server quota.

A7 has capacity 40 and refill 20/s: a full bucket admits a 40-request burst, then approaches 20/s sustained. Refill, clamp, debit, and expiry updates occur in one atomic decision. Redis scripts are atomic but block other activity while running, so keep the operation short rather than scanning a million buckets. [4] Multi-key decisions must also satisfy the actual cluster’s key-colocation constraints.

Four full local buckets would grant one user 4×20=80/s sustained and 4×40=160 burst. Sticky connections fail across new connections, scaling, and failover. Shared Redis preserves one logical quota and interchangeable gateway instances. The cost is 10,000 decisions/s; A8’s 2 ms wait implies roughly 20 in-flight decisions. Benchmark hot keys, network, and script budgets.

为什么还要总量保护和内存账 Why aggregate protection and memory sizing remain separate

中文

一百万活跃桶 × 100 B = 100 MB 单份；A4 的两份拷贝是 200 MB。这个数只含暂定键和值，不含对象、哈希表、分配器、复制缓冲和故障重建，不能据此采购刚好 200 MB。TTL 负责清理闲置身份，不是权限撤销。恶意制造身份或路径若能无限造 key，内存会先被打满，所以 route_id 必须规范化，主体只能来自已验证凭证，且总 key 数要有观测和准入约束。

用户桶保证公平，不保证 Orders 不过载。假设十万人每人都合法发 20/s，就是两百万请求/秒，仍会打穿业务池。入口因此还有服务总速率和在途预算，高风险服务内部还可按数据库容量保护。网关的用户配额与服务的容量保护解决两个问题，各自有明确所有者。串在一条请求上的两次限制要讲清扣费语义：入口已拒绝不再到业务；业务拒绝也不把它记成一次成功交易。

已知桶耗尽返回 429，本章约定附 Retry-After；RFC 6585 定义 429，并允许这个头，不强制固定的计数算法或身份维度。[5] 剩余额度头若存在只是本次观测，多实例并发会马上改变它，客户端不可把它当预留。公开的自定义 X-RateLimit 头也不是天然的通用标准。安全日志保留 route_id、policy_version、限流结果与等待时间，按原因区分配额拒绝和基础设施错误。

English

A million active buckets×100 B=100 MB per copy, or 200 MB for A4’s two copies. That tentative key-and-value estimate excludes objects, hash tables, allocation, replication buffers, and recovery headroom. TTL removes idle identity state, not permissions. Normalize routes, derive subjects only from valid credentials, and observe and bound key creation to avoid unbounded memory growth.

User quotas provide fairness, not backend capacity. A hundred thousand legitimate users at 20/s would generate two million requests/s. Keep an aggregate service-rate and in-flight budget, with backend protection tied to database capacity where needed. User quota and capacity protection have distinct owners. Define accounting explicitly: ingress rejection never reaches the service, and backend rejection is not a successful transaction.

Known quota exhaustion returns 429, with Retry-After by our contract. RFC 6585 allows that header without mandating an algorithm or identity dimension. [5] Remaining-quota metadata is a current observation, not a reservation under concurrent traffic. Custom X-RateLimit fields are not automatically a universal standard. Log route_id, policy version, admission result, and wait time, distinguishing quota rejection from infrastructure error.

故障窗口：未知额度不能无限放行 Failure window: unknown quota cannot mean unlimited access

中文

Redis 等待到 A8 的 5 ms 上限，Gateway 不能知道还有多少令牌。支付、短信与登录按本章契约拒绝，用 503 表示判定依赖不可用；不是 429。允许的公开只读可进入 A9 的本地紧急总桶，每台持续 100/s，固定四台持续最多 400/s，并最多带来总计 400 个额外突发。相对一万 QPS，持续只放 4%，其余失败或用明确降级结果，不能说成读接口一律 fail-open。

这个应急桶没有精确用户公平性，也没有全地域强计数。降级时冻结四台池、设置短期明确政策并报警；若自动扩成八台，8 × 100 = 800/s，上界会翻倍。更强的替代是预先划分配额租约，未过期的份额按保守规则使用，或直接所有请求拒绝。Redis 异步复制切换还可能丢失已扣令牌而重复放行，所以强扣费配额不能把可用性优先的计数器当作账本。

English

After A8’s 5 ms Redis wait cap, quota is unknown. Payments, SMS, and login reject with 503 for an unavailable admission dependency, not 429. Approved public reads may use A9’s emergency aggregate buckets: 100/s per instance, at most 400/s sustained with a fixed four-instance pool, plus at most 400 aggregate burst. This admits only 4% of the 10,000 QPS sustained, not universal fail-open.

The emergency buckets lose precise user fairness and strongly consistent regional counting. Freeze the pool at four during fallback and use an explicit short-lived policy with alerts: eight instances would double the cap to 800/s. Alternatives include conservative preallocated quota leases or rejecting all traffic. Async Redis failover can also lose token debits and admit extra work, so availability-oriented quota state cannot serve as a strict billing ledger.

BFF：少一轮客户端往返，换一层有界聚合 BFF: fewer client round trips for bounded aggregation

什么时候加，正常路径怎样走 When to add it, and how the request flows

中文

移动首页确实需要把订单、个人资料和评论裁成同一块页面数据时，BFF 才有具体工作。Gateway 先完成身份和粗限，Mobile BFF 接受可信上下文，并行向三个服务取所需字段，等必需数据后组装一份 JSON，再经原路径返回。网页端若使用相同数据形状，可复用它；只有不同的页面契约才值得第二份 BFF，不能按客户端名称机械复制一套入口政策。

按 A10，一次示例的分支用时为 80、40、120 ms，组装 20 ms。串行是 80 + 40 + 120 + 20 = 260 ms；独立并行是 max(80,40,120) + 20 = 140 ms，节省 120 ms。省掉的是串行等待，不是每台下游计算，也不是必然达到 140 ms 的页面 p99。各服务的 p99 不能直接取最大当整体 p99，因为尾部事件与相关性会改变联合分布。

BFF 也放大下游调用。假如一万 QPS 都访问这一页面、每次三条分支，调用总量是 10,000 × 3 = 30,000 RPC/s，每个服务各一万，网关流量没有凭聚合凭空变小。若每条分支再允许最多三次尝试，最坏总量会变成九万 RPC/s。聚合层必须限制分支数、每路并发和期限，并把共享剩余期限传下去，才能避免少一轮客户端往返换成后端风暴。

English

A BFF has concrete work when a mobile page needs one shaped response from orders, profile, and comments. Gateway authenticates and applies coarse admission; Mobile BFF accepts trusted context, reads the three services in parallel, assembles required fields, and returns along the original path. Web can reuse the same shape; only a distinct page contract justifies another BFF.

A10’s illustrative branch durations are 80, 40, and 120 ms with 20 ms assembly. Serial work is 260 ms; independent parallel work is max(80,40,120)+20=140 ms, saving 120 ms of waiting rather than backend computation. This is not a guaranteed page p99: individual p99s do not determine the joint tail distribution.

If all 10,000 QPS use this page, three branches produce 30,000 RPC/s, 10,000 per service. Aggregation does not erase work. Up to three attempts on each branch would create 90,000 RPC/s in the worst case. Bound fan-out, per-branch concurrency, and deadlines, and propagate remaining time so fewer client round trips do not become a backend storm.

取舍与故障：只降级产品允许缺的区块 Trade-offs and failure: degrade only optional blocks

中文

Comments 在 A10 中被明确标为可选，失败红线到 Mobile BFF 就停，页面返回订单和资料，并把评论区标成暂不可用。Orders 是必需：它失败时不能用空数组伪装“没有订单”，要按页面契约失败或返回明确部分状态。把全部下游错误都吞成 200 会让用户和监控误以为业务成功，也会把预算的失败定义偷换掉。

替代是客户端直接调用多个共享 API。它省掉 BFF 的部署、额外一跳和缓存，但弱网会多付往返，前端也要处理部分失败。只有一条业务读取时，BFF 通常没有聚合收益。另一个替代是在业务服务提供专用读模型，让页面不再跨三个服务临时拼装；代价是读模型同步和陈旧窗口。这些取舍由页面约束决定，不能靠“现代系统都上 BFF”来回答。

BFF 不负责复制库存、退款资格和支付补偿。若聚合变成“先改订单再扣余额，失败再撤销”，它已经跨过页面塑形边界，需要业务编排和持久状态。网关与 BFF 的部署权限也应分开：页面团队能改变字段，不应顺手改变全站认证规则。服务网格的东西向保护可继续存在，但不因为多一层 sidecar 就天然获得用户对象权限。

English

A10 explicitly makes Comments optional. Its failure stops at Mobile BFF, which returns orders and profile with comments marked unavailable. Orders is required: failure cannot masquerade as an empty order list. Fail the page or expose explicit partial status according to contract. Swallowing every error as 200 misleads users and monitoring.

Clients can instead call shared APIs directly, avoiding a BFF deployment, hop, and cache but paying more round trips and handling partial failures. A single backend read rarely gains aggregation value. A dedicated business read model can remove three-way fan-out, trading synchronization and staleness. Page requirements decide the choice.

Keep inventory, refund eligibility, and payment compensation out of the BFF. A flow that mutates orders and balance and compensates on failure requires durable business orchestration. Separate page-shaping deployment authority from global authentication-policy authority. East-west mesh protection can coexist, but adding a sidecar does not establish user-level object permission.

路由与灰度：版本选择是一份可观测政策 Routing and canary: version selection is observable policy

正常路径：匹配优先级与可信 cohort Walkthrough: match precedence and trusted cohorts

中文

Gateway 先做规范化，再按明确优先级匹配 host、method、path；较具体的路由覆盖默认路由，未匹配的入口默认拒绝或返回明确 404。不能让内部 host 从公网默认路由进入，也不能让编码后的不同路径逃离同一个权限和配额规则。HTTP 路由原文列出虚拟主机、路径及 header 等匹配能力，说明这是 L7 政策，不是按连接分配的 L4 功能。[9]

本章选稳定身份 cohort 灰度。用可信 tenant 与 subject 的哈希选择 10% 用户进入 Orders v2，剩下进入 v1，同一轮发布保持分组。按 A11 每人速率相同才有 10,000 × 0.10 = 1,000 QPS 的估算。随机逐请求加权更贴近瞬时流量比例，却会让同一用户在两版之间跳；cohort 更适合用户体验连续性，但单个热点用户就可能把 v2 打到远高于 10% 的流量。

测试定向规则必须来自已经授权的身份或内部可信标记，不能让任何公网用户写 x-canary: true 就进入内部试验。版本路由本身也不提供数据兼容性：两个版本若对同一订单记录作不同解释，即使用户粘在一版，后台任务和回调仍可能交叉处理。服务要采用兼容字段和状态迁移，网关只负责把确定的路由结果记下来。

English

Normalize before applying explicit host, method, and path precedence. Specific routes precede defaults, and unmatched ingress rejects or returns an explicit 404. An internal host cannot enter through a public default, and encoded path variants cannot escape one permission and quota rule. HTTP routing documents virtual hosts, path, and header matching as L7 behavior. [9]

We choose a stable identity cohort: hash verified tenant and subject so 10% of users use Orders v2 throughout a rollout. A11’s equal per-user rate assumption is needed for the 1,000 QPS estimate. Random per-request weighting better targets traffic share but switches one user between versions. Stable cohorts improve continuity while hot users can skew the actual traffic share.

Targeted testing requires authorized identities or trusted internal markers, not a public x-canary header that grants experiment access. Routing alone does not ensure data compatibility: background work and callbacks may process the same order across versions even when the user is pinned. Services own compatible fields and state migrations; Gateway records the route choice.

回滚窗口：新请求改路由，在途写不重放 Rollback window: reroute future requests, never blindly replay writes

中文

配置版本从 v42 到 v43 时，每台网关在本地切换，其他实例可能还在旧版。观察应包含 route_id、policy_version、upstream_version 和 cohort，错误率与延迟按版本拆开看；汇总后的全站曲线可能把 10% 新版的故障冲淡。回滚先把新请求导向 v1，再确认各实例已应用和 v2 在途请求排空。请求中固定一次快照，不能匹配用新版、配额又读旧版。

请求已发到 v2 后发生超时，不能因为 v1 健康就把同一创建订单再送一遍。v2 可能已经提交，只是响应丢失；这样换版本重放会造成重复订单。安全重试要由接口的幂等契约和业务持久去重共同决定，路由权重不具备补偿事务能力。GET 可按剩余期限换到其他健康实例，也须满足读语义；写入的不确定结果则由请求标识查询和后续对账处理。

控制面失联时保持最后好版本，意味着紧急拒绝政策也可能延迟到达。这个可用性选择必须显式接受：稳定的普通路由继续运行，但安全撤销类政策要有独立有效期限或紧急下线机制。另一种设计是过期就停止接流量，更保护政策新鲜度，却可能把配置系统故障变成全站不可用。面试里说清哪类政策允许旧、最长旧多久，比一句“配置热更新”更有价值。

English

During v42 to v43, each gateway activates locally while others may retain v42. Observe route_id, policy_version, upstream_version, and cohort, and split errors and latency by version so aggregate graphs do not hide a bad 10% canary. Rollback sends future requests to v1, then confirms applied versions and drains v2. Pin one snapshot per request rather than mixing new routing with old admission policy.

After an order creation reaches v2 and times out, v1 health does not justify replaying it: v2 may have committed before losing the response. Replay safety comes from the API’s idempotency contract and durable backend deduplication, not routing weights. GET may choose another healthy instance within deadline and read semantics; uncertain writes need request-status lookup and reconciliation.

Last-good configuration preserves service during control-plane loss but can delay emergency denial policy. Accept that explicitly: ordinary routing may remain, while security-revocation policy needs its own expiry or emergency shutdown mechanism. Expiry-to-reject better protects freshness but can turn configuration failure into a site outage. State which policies may be stale and for how long.

期限、重试与熔断：给慢请求的账封顶 Deadlines, retries, and breaking: bound slow work

正常与超时：一份期限向下递减 Success and timeout: one decreasing deadline

中文

按 A12，总预算 300 ms，政策阶段 20 ms 已包含 Redis 等待，下游最多 240 ms，最后 40 ms 供回程和余量。前面多用了时间，后面的允许时间就减少，不能每过一层又重新获得 300 ms。BFF 的每条分支也继承同一剩余期限。把连接建立、读取响应与排队各设一个独立超时，仍需确保它们的组合不突破总期限，否则三个都没到单项上限，用户却早已等超时。

下游等待到点由网关返回 504，沿 Gateway、L4 LB 到 Client；如果已经知道目标不可接收，新请求可提前返回 503。[6] 客户端取消时，网关尽量取消下游并释放资源，但这只是传播取消意图，不能保证数据库事务同步回滚。返回的错误语义必须让调用方知道“业务结果未知”与“从未转发”不同，否则自动再下单会把超时事故变成重复交易事故。

在途量是速率乘占用时间。最坏假设全部一万 QPS 都等待 240 ms，下游在途是 10,000 × 0.24 = 2,400，四台均分约 600。这里忽略政策和回程，是下游等待的账；按总 300 ms 看完整请求则约 3,000。在途请求还不等于 TCP 连接，因为 HTTP/2 可以复用多条流。限制池、待处理队列和单路并发，超出预算快速拒绝，而不是通过加长队列把已超期限的工作继续保存。

English

A12’s 300 ms total assigns 20 ms to policy including Redis, at most 240 ms upstream, and 40 ms to return and reserve. Time consumed upstream reduces later allowance; no layer resets the deadline to 300 ms. BFF branches inherit remaining time too. Separate connect, queue, and response timeouts still need to fit the end-to-end deadline.

An upstream deadline returns 504 through Gateway and L4 LB; known inability to admit new work can return 503 immediately. [6] Propagate cancellation and release resources, but cancellation intent does not guarantee transaction rollback. Distinguish an unknown business outcome from never-forwarded work so automatic resubmission does not turn timeout into duplicate transactions.

In-flight work is rate times residence time. If all 10,000 QPS wait 240 ms, upstream in-flight work is 2,400, roughly 600 per instance across four. This excludes policy and return; at the full 300 ms, complete requests are about 3,000. Requests are not TCP connections because HTTP/2 multiplexes streams. Cap pools, pending work, and route concurrency, rejecting excess rather than retaining expired work.

重试预算：幂等只是第一道门 Retry budgets: idempotency is the first gate

中文

A13 最多额外尝试一次。示例两次各 80 ms，加 20 ms 等待和 20 ms 政策是 2 × 80 + 20 + 20 = 200 ms，低于 300 ms；但如果第一次已经用完 240 ms，下次就没有原预算，不能再完整等一轮。每次重试还要判断剩余时间、目标健康、全局重试额度和请求体是否可重放。退避加随机抖动只是错开节奏，不能替代次数与总期限上限。

假如一万原始 QPS 全部多试一次，业务尝试会到两万/秒，正好在下游最弱时翻倍。只允许最多 5% 的原始请求额度用于额外尝试，才有 10,000 × 0.05 = 500 次/秒，合计最多约 10,500 次尝试/秒。这个全局预算要跨实例成立，或者保守分配固定份额，不能每台按全站五百份再给一遍。Gateway、BFF、服务内客户端若每层各两次尝试，三层最坏是 2 × 2 × 2 = 8 次，必须约定一个重试所有者。

HTTP 幂等描述的是重复请求的预期业务效果，不是每次响应必须相同。RFC 9110 明确限制代理自动重试非幂等请求。[6] POST 即使带上 idempotency key，只有服务把键、参数绑定、结果和去重窗口持久化，并处理“执行中但还没结果”时，接口才具备明确重放契约。网关透传这个键很有用，却不能靠一行 header 保证只扣一次库存；订单章会继续讲这份业务状态。

English

A13 permits at most one extra attempt. Two 80 ms attempts plus 20 ms wait and 20 ms policy total 200 ms, below 300 ms. If the first attempt already consumed 240 ms, a fresh full attempt does not fit. Check remaining time, backend health, retry budget, and replayable bodies on every retry. Jitter changes timing but does not replace count and deadline limits.

Retrying every original request once doubles 10,000 QPS to 20,000 attempts/s just when upstream is weakest. A 5% extra-attempt budget grants 500 retries/s and at most about 10,500 attempts/s. Enforce it across instances or conservatively partition it. Three layers each allowing two attempts can produce 2×2×2=8 attempts; define one retry owner.

HTTP idempotency concerns intended business effects, not identical responses. RFC 9110 restricts proxy retry of non-idempotent requests. [6] An idempotency-key header is insufficient unless the service durably binds it to parameters, outcome, and a deduplication window and handles an in-progress result. Gateway can forward the key but cannot guarantee one inventory debit by adding a header.

熔断与观测：健康状态和资源保护分别说 Breaking and observability: separate health from resource caps

中文

图下方的 Closed、Open、Half-open 是可选健康策略。按 A14，十秒窗至少一百次调用后，失败率达 50% 开路，等待五秒每实例只放一条探针，探针成功逐步恢复，失败重新等待。这些都是本章假设，低流量接口要避免样本不足触发错误决定。三态不是所有代理的默认行为：Envoy 的 circuit breaking 文档主要描述连接、待处理请求、并发请求和重试等资源上限，资源满即可拒绝，不需要先观察 50% 失败。[8]

开路的新请求在 Gateway 就返回 503，不再碰 Orders；已有在途请求按照原期限结束。本章采用每实例一条探针，四台总计最多四条；探针也消耗真实容量。若要求服务级全局一条，则需额外协调，不能四台各发一条却宣称全局一条。健康检查、离群实例摘除与资源保护也不互相替代：一台慢主机可以单独被摘掉，整个服务的连接预算仍然需要守住。

观测至少区分 401、403、429、503 和 504，并记录是否已转发、上游版本、尝试次数、剩余期限与限流等待。指标标签用 route_id，不能用完整 URL 或 user_id 形成无限基数。按 A15，每条访问日志 300 B，一万 QPS 是 3 MB/s，一小时 10.8 GB；不要把峰值直接乘一天当日量。日志异步缓冲且有上限，满了按审计要求决定丢弃或拒绝，不能把磁盘写满偷偷接到所有请求的同步关键路径。

English

The diagram’s Closed, Open, and Half-open are an optional health policy. A14 opens after at least 100 calls in a 10 s window with 50% failures, then waits 5 s and admits one probe per instance; success permits gradual recovery and failure reopens it. These are assumptions, requiring care at low volume. Envoy circuit breaking primarily documents resource caps, which reject on saturation without first needing a 50% failure observation. [8]

New work while Open returns 503 at Gateway and does not reach Orders; existing work retains its original deadline. Here we allow one probe per instance, at most four total. Probes consume real capacity; a stricter global one-probe contract would require coordination. Health checks, outlier removal, and resource caps solve distinct problems and do not replace one another.

Distinguish 401, 403, 429, 503, and 504, recording forwarding status, upstream version, attempt count, remaining deadline, and admission wait. Use bounded route_id labels rather than user ids or full URLs. A15’s 300 B entry at 10,000 QPS is 3 MB/s or 10.8 GB/hour, not an all-day peak volume. Use bounded asynchronous logging and an explicit overflow policy.

追问与八个翻车点 Follow-ups and eight failure-prone answers

中文

“全世界一个精确用户桶呢？”先问配额是否是强扣费约束。若每个地域都能花完整 20/s，两个地域已经是 40/s；跨地域同步又会增加每个请求的延迟和分区时的拒绝。可按地域分配保守份额，或把强扣费记账交给权威服务。单地域共享桶不能自动升级成全球强额度。

“服务能直接被别人调用吗？”如果能，Gateway 剥头不能保护绕过它的调用，必须先补调用方认证和入口访问约束；若信任模型要求端到端用户凭证，下游也验证。网络拓扑和服务授权要一起说，不能只靠一张框写着 private 就消除伪造。

“网关自身会不会成为瓶颈？”CPU 按 A5 验签需要两核，QPS 按 A3 要四台，网卡 body 按 A2 每方向聚合 480 Mb/s，这三笔不能互相替代。连接数、HTTP/2 流、Redis 延迟和插件开销还要测量。峰值再乘十时先重算，而不是把所有可用性问题交给一句加机器。

“要不要把所有领域服务都拆开？”本章图上的 Orders、Profile 与 Comments 只为说明路由和聚合。服务拆分要由独立业务边界与团队约束决定，网关不会要求数据库跟着碎成几十份。下一章把入口之后的一笔订单走成状态机、库存预扣和支付回调，恰好能验证这里的细权限与幂等重放究竟由谁承担。

English

“What about one exact global user bucket?” Clarify whether it is a strict billing constraint. Two regions each granting 20/s create 40/s; synchronous coordination adds latency and partition-time rejection. Conservatively allocate regional shares or use an authoritative billing service. A regional bucket is not automatically globally exact.

“Can another caller reach the service directly?” If yes, stripping headers at Gateway does not protect bypass traffic. Add caller authentication and ingress restrictions, and revalidate end-to-end user credentials if required by the trust model. A private box label does not eliminate forgery.

“Can Gateway become the bottleneck?” A5 needs two aggregate validation cores, A3 needs four instances, and A2 gives 480 Mb/s of body traffic in each direction. These are different budgets. Measure connections, HTTP/2 streams, Redis latency, and policy overhead, then recompute when peak changes.

“Must every domain become a separate service?” Orders, Profile, and Comments illustrate routing and aggregation. Independent domain and team boundaries determine service decomposition; the gateway does not demand dozens of databases. The next chapter follows order state, inventory reservation, and payment callbacks, showing who actually owns fine permission and replay safety.

中文

最后一分钟从一条请求收口：Client 经 L4 LB 到 Gateway，受信密钥验证 API 凭证，共享桶决定准入，Orders 判断领域权限并返回。Gateway 四实例承受峰值与一台故障，控制面快照不在请求里，BFF 只为页面形状。超限 429，依赖不可用或开路 503，上游超时 504；回滚只改未来路由，写入未知结果交给业务幂等和对账。每句话都能在图上指出一条真实路径和一个明确边界。

English

Close on one request: Client passes L4 LB to Gateway, trusted keys validate API credentials, a shared bucket admits work, and Orders enforces domain permission and replies. Four gateway instances cover peak and one loss. Local snapshots keep the control plane outside requests; a BFF serves page shape. Use 429 for quota exhaustion, 503 for unavailable admission or an open breaker, and 504 for upstream timeout. Rollback changes future routing; business idempotency resolves uncertain writes.
