设计评论系统 Design a comment system

主线约 40 分钟 · 前置：Ch03、Ch10 · 6 组、30 帧演进图 ~40 min core · after Ch03 and Ch10 · 6 decks, 30 evolution frames

这一章结束你能做什么 What you can do after this chapter

中文

从一条帖子的读写路径画起，讲清父子关系如何保存、首屏如何限制工作量、下一页如何找到起点。再把点赞、审核和热点故障接回同一套可见性约定。每加一个组件，都回答它解决哪条约束、失败时谁还能返回。

合上页面后，你应能解释：为什么 20 楼各取 3 条不等于全局 LIMIT 60；为什么点赞去重和计数要原子执行；为什么写库后直接发消息会漏审核；为什么 cursor 不能冻结审核状态。图中的箭头是论证的一部分，不能只报 Redis、关系库和队列这几个名词。

English

Start with one post’s read and write path. Explain stored parentage, bounded initial work and the next-page anchor, then connect likes, moderation and hot-post failures to one visibility contract. Each component must answer which constraint it solves and who can respond when it fails.

After closing the page, explain per-root limits versus global LIMIT 60, atomic like deduplication and counting, lost moderation jobs after dual writes, and why a cursor cannot freeze visibility. Arrows are part of the argument; naming Redis, SQL and a queue is insufficient.

30 秒开场：先定产品，再估负载 The 30-second opening: scope before load

中文

我设计帖子下面的评论区：数据保留真实 parent_id，界面展示一级楼和摊平回复。先按千万日活、每天每人 2 条评论、10 次点赞、15 次列表请求、峰值五倍估算。首屏 20 楼，每楼最多 3 条回复；一级与楼内分别用 cursor。正文先写 pending，与 outbox 同事务，提交后回 202，审核通过再公开。点赞走可容忍丢失窗口的内存计数路径，去重和加数原子执行。热点读旁路缓存，故障回源有配额，删除内容不无限提供旧值。

先确认四件事：是帖子评论还是社交图；展示深度能否收成两级；默认按时间还是热度排序；审核未完成的内容谁能看。本章选择按时间倒序、先审后发，pending 仅作者可见。举报、编辑、删除会改变可见性，不能藏在“之后做风控”这句话里。关注关系、推荐排序和全局跨地域合并不进入本轮设计。

这里的默认方案来自这组约束，不是某个平台的内部架构，也不靠“今年大家都这么做”证明正确。若面试官要求点赞绝不丢，必须改成耐久明细或事件再投影；若要求热度排序，必须给排序结果一个版本。两种变化都会改路径，不能只替换一个组件名字。

English

I design comments under a post, storing real parent_id while showing roots and flattened replies. Assume ten million daily actives, two comments, ten likes and fifteen list requests each per day, with a 5× peak. Return twenty roots and at most three replies each, with separate root and thread cursors. Commit pending plus outbox before 202, then publish after moderation. Likes use a loss-tolerant memory path with atomic membership and count changes. Hot reads use look-aside cache, bounded origin access and no indefinite stale withdrawn bodies.

Confirm four choices: comments versus a social graph, two-level display, chronological versus ranked order, and who sees unmoderated content. This chapter chooses newest first and pre-publish moderation, with pending private to its author. Reports, edits and deletions affect visibility and must be addressed. Follow graphs, ranking and global merging stay outside this design.

These defaults follow the stated constraints, not a platform’s private architecture or a claim about the current year. Lossless likes require durable facts or events before projection. Ranked pages require a versioned ranking result. Both changes alter the path, not merely a component name.

把三个峰值和存储分别算完 Compute three peaks and storage separately

中文

评论每天 10,000,000 × 2 = 20,000,000 条，平均 20,000,000 ÷ 86,400 = 231.48/s，峰值约 1,157/s。点赞每天一亿次，平均 1,157.41/s，峰值约 5,787/s。列表每天一亿五千万次，平均 1,736.11/s，峰值约 8,681/s。后两条不能从“发评论才一千多”里面省掉，服务要承担鉴权、组装、读取和计数的不同成本。

按 A6，热帖收到约 8,681 × 40% = 3,472 次列表/s。缓存 95% 命中时，全站约 434 次页面/s 回源，热帖约 174 次/s；这是目标，不是保证。A7 的 600 配额给查询抖动留下约 166 次/s 余量。一次页面查询还可能做 20 次短索引探测，所以压测输入应是完整页面请求，不能拿“数据库每秒能查几万行”直接换算。

每天正文 20,000,000 × 0.5–1 KB = 10–20 GB，365 天为 3.65–7.30 TB 逻辑行数据，三份是 10.95–21.90 TB。峰值五倍只描述一天内的分布，不能再把日增乘五。图里的 Primary 是逻辑权威存储，不是承诺单机装下这份数据；物理分片数量还要加索引、明细和重建余量再定。点赞成员数与保留期另估，不能把“计数只有一个整数”当作整个点赞系统的空间。

English

Comments total 20,000,000/day: 231.48/s average and about 1,157/s peak. Likes total 100,000,000/day: 1,157.41/s average and about 5,787/s peak. Lists total 150,000,000/day: 1,736.11/s average and about 8,681/s peak. The smaller comment rate does not erase the distinct costs of authorization, assembly, reads and counters.

A6’s hot post receives about 8,681 × 40% = 3,472 list requests/s. At a targeted 95% hit rate, total origin is about 434 pages/s and that post about 174/s. A7’s 600 quota leaves roughly 166 pages/s of headroom. A page may include twenty short index probes, so benchmark full page requests rather than substituting a rows-per-second figure.

Bodies grow 10–20 GB/day, 3.65–7.30 TB over 365 days, and 10.95–21.90 TB with three copies. The peak factor describes distribution within a day and does not multiply daily bytes. Primary denotes logical authoritative storage, not a single-machine capacity promise. Physical shard count needs indexes, membership and rebuild headroom; a count integer does not account for like membership storage.

第一笔：读写主线与旁路缓存 Stroke one: the main path and look-aside cache

正常路径：正文与可见性先落权威库 Normal path: authoritative bodies and visibility

中文

Client 经 Edge 到 Comment API。Edge 校验令牌并执行按用户、IP 和帖子组合的入口配额，API 再校验帖子权限、内容长度及回复目标。每一层都给自己设超时，不能让下面的缓存或模型无限占着连接。拒绝发生在哪一层，响应就从那一层逐跳返回；429 是入口配额不足，503 是服务此刻无法安全完成，两者要分清。

POST 写入 pending 后只有事务提交成功才确认。公众 GET 只查 visible，作者查审核进度是另一条带身份约束的请求，不能让 pending 混入共享列表键。Primary 超时而提交结果未知，API 不应凭空说“失败且没写”；客户端带原请求键重试，查出同一个评论。第五组把持久投递意图接进同一事务，避免正文成功但永久没有审核任务。

列表采用 look-aside：API 先查 List cache，命中把结果经 API、Edge 返回；miss 时 API 自己查询 Primary，再回填。Cache 不在 API 与数据库之间串联，也不会替 API 自动查 SQL。缓存对象是一页有界切片，键包括 post_id、一级或楼内范围、排序模式、cursor 与版本；作者身份相关信息单独返回，否则同一缓存可能把某人的待审内容泄露给别人。

English

Client reaches Comment API through Edge. Edge validates tokens and user, IP and post quotas; API checks post access, body length and reply target. Each layer bounds waits. Responses return hop by hop from the refusing layer. Distinguish 429 for entry quota from 503 for current inability to complete safely.

A POST acknowledges pending only after commit. Public GET selects visible; author status checks are identity-bound and never mix pending into shared list keys. An unknown commit outcome is not proof of no write. Retry the original request key to recover the same comment. Deck five adds durable delivery intent to the transaction.

The API looks up List cache; hits return through API and Edge. On misses the API queries Primary and fills cache itself. Cache is not an inline SQL proxy. A key identifies post, root scope, order, cursor and version. Author-specific fields are separate, preventing shared caching of private pending content.

选择、代价与替代方案 Choice, costs and alternatives

中文

缓存 95% 命中把约 8,681 收到 434 页/s，留下它的理由是这次除法。代价是失效、版本与新鲜度管理，不能把这些全缩成“TTL 五秒”。列表正文、点赞计数、是否已赞各有不同更新节奏，不宜塞进一个每次点赞就失效的大 JSON。首屏切片只缓存正文及稳定标识，计数批量补齐；某用户是否已赞从该用户的成员状态查。

小规模可以先不缓存，用同一套有界查询压测证明预算够。这个替代避免失效复杂度，但按 A7，8,681 ÷ 600 ≈ 14.47，当前假设下全量回源已超配额，因此不能靠“关系库很快”略过缓存。深翻页常常命中低，要计入那 5% 的未命中；如果真实深翻比例把目标击穿，就扩大查询能力或限制展开频率，不把 95% 当成自然常数。

写后读自己不承诺“共享首页马上出现”。作者使用返回的 comment_id 查权威状态，列表仍遵守公开可见规则。审核通过后由事件失效相关首屏键，使新内容进入列表；删除和编辑也产生失效事件。故障时这些事件可以重复，旧快照回填却必须被挡住。第六组讨论这种竞态，而不是把删一个 key 当成完成了可见性设计。

English

A 95% target takes origin from about 8,681 to 434 pages/s; that arithmetic justifies cache. Its cost is invalidation, versioning and freshness, not merely “TTL five seconds.” Bodies, counts and caller membership change at different rates. Cache bounded bodies and stable ids, batch-hydrate counts, and fetch caller membership separately.

A smaller service can initially omit cache after benchmarking the same bounded queries. Under A7, however, 8,681 ÷ 600 ≈ 14.47, so full origin exceeds the quota. Deep pages tend to have lower reuse and must fit the miss fraction. If measured expansion traffic defeats 95%, improve origin capacity or restrict expansion, rather than treating hit rate as a constant.

Read-your-writes means the author can query authoritative status by returned comment_id, not immediate appearance in a shared public page. Approval, deletion and edits invalidate affected slices through events. Events may repeat, but stale snapshot fills must be fenced; deck six addresses that race.

第二笔：保存真关系，限制读出的树 Stroke two: preserve relations, bound the returned tree

Schema：parent_id 与 root_id 各管一件事 Schema: distinct roles for parent_id and root_id

中文

每条评论有 id, post_id, parent_id, root_id, author_id, body, status, version, created_at。一级 parent_id 为空，root_id 可规范为自己的 id；回复的 root_id 从被回复节点继承。服务端解析目标并核验 post_id 相同，不能相信客户端随手传来的 root_id。否则用户能把不同帖子的内容挂到一楼，权限过滤与分片定位都会出错。自引用关系能保存树结构；还要靠业务校验保持所属帖子与不可变父节点约定。[7]

图中 103 回复 101，但它和 101、102 一起显示在 Root 100 下面，文案保留“回复 @101”。这是把显示深度收成两层，不是丢掉实际关系。产品选择换来了可控制的布局和首屏工作量；若需要任意节点的完整子树，可以额外提供限额查询，不能因此让普通列表默认展开所有子孙。

邻接表插入一行，不需要重写其他评论的区间号；这不等于包含 B-tree、唯一约束和事务的插入都是 O(1)。物化路径会增长路径长度，移动子树需要更新后代；nested set 插入可能移动一段区间，写频繁的评论不适合把它当起点。真正频繁读任意子树时再评估闭包表，接受祖先关系数量随深度增长的写放大。选择由查询决定，不靠“树就用树算法”。

English

A comment stores id, post_id, parent_id, root_id, author_id, body, status, version and created_at. A root has null parent_id and may use its own id as root_id; replies inherit their target’s root_id. Resolve and validate targets server-side, including matching post_id, rather than trusting supplied root_id. Self-reference supports the tree, while business checks enforce post ownership and immutable parentage. [7]

Reply 103 targets 101 but displays with 101 and 102 beneath Root 100, preserving “reply to @101.” Display depth is bounded without discarding stored relationships. An optional limited subtree endpoint can support deeper inspection; it should not make every ordinary page traverse all descendants.

Adjacency insertion adds one row without rewriting interval labels; indexes, uniqueness and transactions still have cost. Materialized paths grow with depth and require descendant changes when moving subtrees. Nested-set insertion may shift an interval. Closure tables can serve frequent arbitrary-subtree reads, at the cost of depth-dependent ancestor writes. Choose from queries, not the word “tree.”

先限制每楼，再限制整个响应 Bound each thread before bounding the response

中文

先取 20 条一级，再为每个 root 按索引取最多 3 条 visible 回复。可以让一条 SQL 用 LATERAL 做每楼的短探测，索引为 (post_id, root_id, created_at, id) 并结合 visible 条件。它减少的是客户端和数据库之间的网络往返，不是把 20 次探测神奇变成一次。[3] 用 root_id IN (…) LIMIT 60 只会限制总数，热楼可能独占 60 条；若用窗口函数排名后截断，也要检查是否扫描了全部楼内候选。

A4 的上界是 20 + 20 × 3 = 80 条正文，按 1 KB 约 80 KB，尚不含包装和用户资料。若一楼有 A6 的十万回复，整树方案仅这一楼就约 50–100 MB；返回计数与少量预览则不会跟着长。reply_count 是可滞后的可见回复投影，不等于所有 pending 的数量。用户点展开才用这个 root 的 cursor，响应仍限 20 条，隐藏或删除的正文都先过滤。

需要分片时按 hash(post_id) 定位，让同一帖子的一页与回复目标检查落在同一分片。按 comment_id 随机分会把一页拆成多片请求，增加合并与尾延迟；代价是单帖仍可能很热。缓存先挡读，极端热帖的写再考虑楼级拆分及路由目录，明确会增加一级合并和迁移成本。不能把“按帖子分片”说成同时解决了热点写。

English

Fetch twenty roots, then up to three visible replies per root. One SQL can use LATERAL with indexed probes on (post_id, root_id, created_at, id) and visibility. This reduces network round trips, not the twenty probes themselves. [3] A global IN (…) LIMIT 60 may give all sixty to one hot thread. Window ranking also needs a plan check for full candidate scans.

A4 bounds the screen at eighty bodies, about 80 KB at 1 KB each before wrappers and profiles. A6’s 100,000-reply thread alone would cost about 50–100 MB under whole-tree loading. A count and preview remain bounded. reply_count projects visible replies and may lag; pending does not inflate it. Expansion uses a root cursor with another twenty-row bound.

When sharding becomes necessary, route by hash(post_id), keeping page reads and target checks together. Random comment-id sharding scatters pages and increases merge and tail costs. Post routing preserves a hot-post problem: cache protects reads, while extreme write hotspots may require thread routing and a directory, adding root merge and migration costs.

第三笔：cursor 锚住位置，不冻结世界 Stroke three: a cursor anchors position, not the world

查询与索引必须说同一种顺序 The query and index must agree on order

中文

一级页使用 post_id=? AND parent_id IS NULL AND status='visible'，下一页再加 (created_at,id) < (:t,:id)，按两列倒序取 20。时间相同的多行靠 id 打破并列，created_at 和 id 在分页期间不改。索引对齐这些谓词与顺序，可考虑一级且 visible 的部分索引；不能只建一个时间索引就宣布所有过滤都免费。唯一排序和大 OFFSET 仍计算跳过行的机制见 [1]，匹配 B-tree 与 LIMIT 的关系见 [2]。

图把页大小缩成 3：第一页 105、104、103；在顶部插入 106 后，OFFSET 3 会从新列表第四个位置重新数，103 可能再出现。cursor 记住 (t,103)，继续查更小的元组，得到 102、101、100。它省掉的是按位置数过历史前缀的工作，不保证每次查询只访问 20 个物理行；不可见行、索引形状、MVCC 和过滤都会影响执行计划。

cursor 编码 post_id、楼范围、排序类型、最后元组和格式版本并签名。换了帖子或排序不能接着使用旧 cursor，服务端返回明确错误；客户端丢失 cursor 只能刷新或重新从首页走。签名防篡改，不能代替帖子的访问权限。请求重复时相同 cursor 在实时列表中可能返回不同内容，因此请求幂等与结果快照要分开讨论。

English

Root pages filter post_id, null parent_id and visible status, then use (created_at,id) < (:t,:id), descending on both columns with LIMIT 20. id breaks timestamp ties; ordering fields stay immutable. Align indexes with predicates and order, possibly using a visible-root partial index. [1] explains unique ordering and skipped OFFSET rows; [2] explains matching B-tree with LIMIT.

The diagram uses three rows: 105,104,103. Insert 106 at the top and OFFSET 3 recounts positions, potentially repeating 103. A cursor remembers (t,103) and continues to 102,101,100. It avoids walking a positional prefix but does not promise exactly twenty physical row visits; visibility, indexes, MVCC and filters still matter.

Sign a cursor containing post, thread scope, order, last tuple and format version. A cursor cannot transfer to another post or order; reject mismatches explicitly. Missing cursors require refresh or restarting. Signing prevents tampering, not unauthorized access. Repeating the same cursor on a live list may return changed content; request idempotence and snapshot results are separate.

审核与删除如何改变翻页结果 How moderation and deletion affect pagination

中文

普通列表是实时视图：两次读取之间，pending 可能通过，visible 可能撤回。如果一条时间更晚的待审评论通过时已经位于游标上方，继续下翻不会自动补它。客户端显示“有新评论”并刷新，或按产品需要选择 published_at 作为不可变排序键。仅携带首页的最大时间也不能冻结未来发生的状态变化；Read Committed 下两次 SELECT 可看到不同提交。[9] 这里不把 cursor 宣称成快照。

需要一次会话内稳定遍历时，可以冻结 ID 列表或维护带版本的结果集合，另估保存时长、内存和失效代价。即使冻结了排序，已删除正文仍要过滤，不能为了“完整快照”重新曝光。热度排序也不能把每次变化的 like_count 直接放进 keyset 并许诺不重不漏；使用 ranking_version 定义一份排序结果，再在那份结果内翻页。

没有匹配索引时，cursor 也可能先扫描再排序；存在大量稀疏可见行时，返回 20 条不表示只读 20 条。应检查查询计划、实际扫描量和深翻的尾延迟。offset 对小集合或必须跳固定页码的管理界面可以成立；本章无限滚动的公众评论区选择 cursor，是因为插入与深翻约束，并不是 SQL 里出现 OFFSET 就算错误。

English

A live page can change between reads: pending may publish and visible may withdraw. An approval above the current anchor will not appear while paging downward; signal new comments and refresh, or choose an immutable published_at ordering key. A first-page time ceiling alone does not freeze later visibility changes. Read Committed permits successive SELECTs to see different commits. [9] A cursor is not a snapshot.

Stable traversal can use frozen ids or a versioned result set, with explicit retention, memory and invalidation costs. Withdrawn bodies must still be filtered even in a frozen order. For ranked pages, a changing like_count cannot guarantee no skips or duplicates in keyset paging; define ranking_version and page within that ordered result.

Without matching indexes, cursors can still scan and sort; sparse visibility means twenty returned rows may require more reads. Check query plans, scanned rows and deep-page tails. Offset can suit small collections or fixed-page administration. This public scrolling list chooses cursors because of insertion and depth constraints, not because OFFSET is universally invalid.

第四笔：点赞去重、计数、刷库是一套协议 Stroke four: membership, counts and flush form a protocol

正常路径：把“是否已赞”与计数一起改变 Normal path: change membership and count together

中文

点赞接口表达目标状态，例如 PUT liked=true；同一用户重复设置不应改变计数。Like cache 保存成员集合、live total 和 dirty delta；新增成员才把后两者各加一，取消已有成员才各减一。回复数则由可见性转换产生增减事件，不能见到发评 POST 就无条件加一。将每次点赞变成同一行的 UPDATE，即使没写 SELECT FOR UPDATE，仍有并发更新串行争用。问题是热行，不是某条 SQL 拼写。

把 SADD（或成员状态判断）、计数更新和脏增量合成短 Lua 操作，才避免去重成功后崩溃漏加数。Redis 的原子执行保证脚本不被其他命令穿插，不表示脚本失败会撤销已执行命令，所以先校验参数、键类型和范围，写阶段避免会出错的分支。[4] Cluster 多键操作要求同槽，成员、total、delta 使用 {comment:100} 标签；这同时把一条热评的写集中在一个槽，不能声称自动分散。[5]

整条点赞请求得到的 accepted 只承诺内存协议接收了这次状态。A8 允许未刷批次丢失，并明确成员明细和计数都是这条弱耐久路径的一部分；若希望“用户已赞状态永不丢、数字可以迟”，先把唯一的 (user_id,comment_id) 明细耐久提交，再异步投影。新增事实成功后才发事件，不能靠一份会过期的去重键证明永久唯一。

English

Use desired state, such as PUT liked=true. Like cache stores membership, live total and dirty delta; only new membership increments both counters, and only existing membership removal decrements them. Reply counts follow visibility transitions, not every comment POST. Any per-like UPDATE of the same SQL counter row can contend even without an explicit SELECT FOR UPDATE.

A short Lua operation combines membership checks, count changes and dirty delta. Atomic execution prevents interleaving; it does not roll back earlier commands after a script error, so validate arguments, key types and bounds before writes. [4] Cluster keys share a slot via {comment:100}. [5] This also concentrates a hot comment’s writes in that slot; it does not distribute them.

Accepted means the memory protocol received the desired state. A8 allows unflushed loss in both membership and count. If membership must survive while numbers may lag, durably commit unique (user_id,comment_id) facts first, then project asynchronously. A transient dedup key cannot establish permanent uniqueness.

为什么批次必须冻结，又为什么批号必须落库 Why batches freeze and their ids commit

中文

不能 GET delta、刷库、再把 delta 清零：读取后新到的点赞会被清零一起抹掉。原子地把当前 delta 交换成一个不可变批次 b17，新操作写进下一轮累积器。Counter flush 只读冻结批次，发送同一个 batch_id 和 delta，收到提交确认后才清除它。只有一个键持有一份批次还不够；重启、超时、并发 flush 都可能让同一批再次到达数据库。

Primary 在一笔事务里先写唯一 (comment_id,batch_id) 应用账本，首次写入才把持久计数加 delta；冲突说明这批已应用，返回成功而不重复加。[7] 图中提交后丢 ack，重试 b17 的结果仍是一次。账本保留必须长于最大重放窗口，批号也不能在恢复后复用；否则老批号被忘掉又会再次增数。“队列至少一次”本身不会使加数幂等。

A8 设 1,000 个脏键每 10 秒各刷一次，1,000 ÷ 10 = 100 笔计数事务/s；不是把每天一亿条点赞凭空变成一千条事件。不同评论的增量还在，不同用户的成员明细也仍占内存。这个路径降低关系库热计数写频率，代价是最多到下一次成功刷库前的数据都可能丢；刷库积压时窗口会变大，不能固定声称永远只丢十秒。

Like cache 丢失后先展示最后的持久计数并标记可能滞后，暂停或明确降级点赞写，按所选承诺恢复成员状态；无法恢复的未刷点赞不能假装已重建。若加入耐久明细，就按明细重算计数，并用检查点或版本切换防止旧重建结果覆盖新增量。单键继续超载时可以条带化计数，但成员与总数跨槽后不再有同一个原子脚本，必须重新设计去重与聚合。

English

GET delta, flush, then zeroing can erase likes that arrive after the read. Atomically rotate the current delta into immutable batch b17 while new operations use the next accumulator. Counter flush retries the same batch id and delta, clearing it only after committed acknowledgement. Restarts, timeouts and concurrent flushes can all replay a batch.

In one transaction, Primary inserts a unique (comment_id,batch_id) ledger record and increments the persistent count only on first insertion. A conflict means already applied and returns success without another increment. [7] After commit and lost acknowledgement, replaying b17 still applies once. Retain the ledger beyond replay windows and never reuse batch ids after recovery. At-least-once delivery alone is not idempotent arithmetic.

A8’s 1,000 dirty keys flushed each ten seconds yield 100 counter transactions/s. It does not erase one hundred million daily like operations or membership storage. It reduces SQL counter updates while exposing loss up to the last successful flush; backlog lengthens that window, so ten seconds is not a permanent maximum.

After Like cache loss, show the last persistent count as potentially stale and pause or explicitly degrade writes according to the contract. Lost unflushed membership cannot be claimed rebuilt. Durable facts allow recounting with checkpoints or version switches to protect new deltas. Counter striping changes slot boundaries and requires a new deduplication and aggregation protocol.

第五笔：审核投递先解决双写，再解决旧结果 Stroke five: close dual writes, then fence stale decisions

先审后发：202 与 visible 是两个承诺 Pre-publish: 202 and visible are distinct promises

中文

API 一笔事务写 pending 评论、请求幂等记录和审核 outbox。请求键绑定作者与正文摘要：同键同内容返回原 comment_id，同键不同内容拒绝。正文和 outbox 一起提交或回滚；relay 轮询已提交的 outbox 才送 Audit queue。[6] 如果写库后 API 直接发消息，进程在两步之间崩溃会留下永远待审的评论；先发消息再写库，则可能审核一条不存在的记录。

图里的绿回程是 Primary → API → Edge → Client，状态为 202 pending。它不经过 Worker，用户看到“已提交，审核中”，不是“已发布”。公众查询保持 status=visible；作者查询只允许本人看到 pending 与拒绝原因。队列有积压时已经接收的评论仍可查状态，API 不用持有连接等模型，但要对等待时间有产品说明与告警。

relay 发完消息后没收到确认可能再发，Worker 处理完后没 ack 也可能再消费。event_id 用于事件去重，comment_id 定位对象，content_version 定位被审的那份内容。状态更新要条件匹配版本与当前状态，写成功后另有可见性事件失效缓存、调整可见回复计数。这些下游事件也应该与状态提交同事务保存，不能修了第一次 outbox 又留下第二次双写。

English

The API atomically writes pending, request-idempotence record and moderation outbox. Bind the request key to author and body digest: same key and body return the same id, while mismatched content is rejected. Relay polls committed outbox. [6] Direct enqueue after SQL can strand a pending row after a crash; enqueue before SQL can create a job for a nonexistent row.

The green response returns Primary → API → Edge → Client as 202 pending, bypassing Worker. Public queries require visible; only the author can inspect private pending status and rejection reasons. Backlog does not require holding the API connection open, but the product needs status, expected waiting behavior and alerts.

Relay can resend after a lost acknowledgement, and Worker can reconsume after a lost ack. event_id deduplicates events, comment_id identifies the object, and content_version identifies reviewed content. Conditional state updates emit cache invalidation and visible-reply-count events; persist these with the state transaction too, avoiding another dual-write gap.

积压、失败队列与替代策略 Backlog, failed jobs and alternative policies

中文

A9 有 10 个 Worker，各 100/s，合计 1,000/s；评论峰值按未舍入算是 1,157.407/s。积压速度为 157.407/s，十分钟约 157.407 × 600 = 94,444 条。峰值期间这组 Worker 永远追不上输入，不能承诺几秒审核完成。换 20 个 Worker 则处理 2,000/s，峰值占约 57.9%；这个余量仍依赖每个 Worker 实测 100/s、任务复杂度和下游状态库预算。

监控最老待审年龄、重试次数和 pending 的超龄扫描，而不只看队列长度。不可恢复的格式错误进失败队列，作者看到可重试或人工处理的状态，不能静默丢弃后一直显示审核中。扩容还赶不上时，入口按用户与帖子收紧新提交，已提交的 outbox 保留重试；不要让反垃圾模型缓慢把整个评论 API 的连接拖死。

替代是先发后审：初始就是 visible，审核拒绝后转 rejected 或 deleted。好处是讨论立即开始，代价是违规会先曝光，撤回传播必须符合 A10。按作者或内容风险选择混合策略也成立，但消息要带实际初始状态，公众查询与计数投影遵循它，不能画 pending 的图却在正文声称所有用户已经上墙。模型特征只点名，当前题的重点仍是投递与状态。

English

A9’s ten workers provide 1,000/s against an unrounded peak of 1,157.407/s. Backlog grows at 157.407/s, about 94,444 jobs over ten minutes. That configuration cannot promise seconds to moderation. Twenty workers provide 2,000/s at about 57.9% peak utilization, conditional on measured per-worker capacity, task complexity and downstream budgets.

Monitor oldest pending age, retry count and overdue pending scans, not merely queue depth. Unrecoverable malformed jobs go to a failure queue with actionable author status. When scaling cannot keep up, tighten new submission quotas while preserving retries for accepted outbox events. Slow moderation must not consume all API connections.

Post-publish moderation starts visible and withdraws rejected content later. Discussion starts immediately, at the cost of exposure and A10-compliant withdrawal propagation. A risk-based mix is possible if messages carry actual initial state and reads and projections follow it. Do not draw pending while claiming public visibility. The focus here is delivery and state, not model features.

第六笔：缓存故障和撤回不能各说各话 Stroke six: cache failure must respect withdrawal

先把零星错误与整层宕机分开算 Separate isolated misses from whole-cache failure

中文

命中率正常时约 434 页/s 回源，小于 A7 的 600；整层 Cache 超时时，约 8,681 页/s 都会想查库，超过预算 14.47 倍。全局页面准入最多 600/s，最坏情况下其余约 8,081/s 返回 503 与 Retry-After。这里假设所有列表请求同时失去缓存且仍到达 API，没有本地副本帮忙，是保护回源的最坏情况。深翻和冷请求同样消耗配额，不能把 600 全分给首页再忽略其他读。

同键单飞让等待者共享一次回源，跨实例使用带有效期的租约，只有持有者查询并回填。等候有期限，Owner 消失后允许换代获取；旧 Owner 后来醒来要被 fencing token 拒绝。单飞只能合并相同键，许多不同 cursor 同时 miss 仍会打库，所以它与全局配额是两条规则。图上的绿色路径属于被准入的请求，红色逐跳回程属于超额请求，不是同一条请求又 200 又 503。

Nishtala 等人的 Memcache 论文解释了租约同时处理旧回填与惊群：删除会使旧 token 的回填失效。[8] 本章借用这个机制，不把论文的生产效果当自己的容量。若实现用 Redis 普通锁，必须自己补 token 校验和代际协议；SET NX 加 TTL 仅说明谁暂时拿到锁，并不能阻止超时 Owner 把陈旧结果写回来。

English

Normal misses are about 434 pages/s, below 600. A whole-cache timeout directs about 8,681/s to origin, 14.47× its budget. Global admission permits up to 600/s and worst-case excess about 8,081/s gets 503 with Retry-After. This assumes all list requests lose cache with no local-copy relief. Cold and deep pages share that quota.

Coalesce one key’s requests under an expiring cross-instance lease. Only the owner rebuilds; bounded waiters may obtain a newer generation after owner loss, fencing late owners. Different cursors remain different misses, so coalescing complements global admission. Green is admitted traffic; the red hop-by-hop response is excess traffic, not two responses to one request.

The Memcache paper explains leases against stale fills and herds, with deletion invalidating a token. [8] This chapter borrows the mechanism, not its production capacity results. A plain Redis lock requires an explicit generation and token check; SET NX with expiry alone does not stop a timed-out owner from writing stale data.

撤回窗口：失效、旧回填和有效期一起约束 Withdrawal: constrain invalidation, refill and expiry together

中文

先列时间线：读者在 v8 取到 visible 快照；管理员把 Primary 改为 deleted(v9)；失效事件删缓存；慢读者最后才把 v8 写回。只有删 key 会让旧内容复活。失效处理要提升该缓存键的 generation 并撤销旧租约，回填必须比较 token；内容版本则让审核和编辑结果不能跨版本更新。键 generation 与 comment version 是不同对象，不能拿某一条评论的版本直接充当整页版本。

失效事件也可能延迟或丢确认，因此 A10 的五秒上界还靠绝对有效期兜底。每份正文切片从权威查询开始时计算 valid_until，不从迟到的回填时重置五秒；服务端返回前检查它，并扣除时钟偏差及输出耗时的安全余量。超过有效期的慢 SQL 结果不入缓存，也不发送。这样即使失效传播失败，删除前的旧快照也不能一直续命；这是有时间边界的设计约定，必须监控真实撤回延迟。

这个五秒描述服务端最后一次允许发送旧正文的窗口；已发到客户端的内容还需要推送撤回或重新校验，离线截图不受服务器控制。若要求服务器提交删除的瞬间就不再返回旧正文，必须在出站路径同步验证可见性或使用更强协议，这会增加依赖与延迟。当前选择允许有界传播，不借“最终一致”掩盖无限曝光。可见性未知又回源无配额时，返回失败；点赞数字可以旧，被撤回的正文不能过期继续旧。

删除一级楼时本章保留无正文墓碑，并允许原本可见的回复在这个容器下继续展示；删除某条子评也不级联删除后代，避免把整楼改写塞进请求。若产品要求整楼隐藏，则在查询中检查 root 的可见状态并推进楼级 generation，这会改变索引与缓存键。不可展示的作者字段也要清理，不能只把 body 清空后留下已撤回的引用摘要。编辑后的 v9 重审，通过前旧正文按本章策略隐藏。

English

A reader loads visible v8; deletion commits v9; invalidation deletes cache; the slow reader then fills v8. Deleting a key alone permits revival. Invalidation advances that key’s generation and revokes old leases; fills compare tokens. Content versions separately fence moderation and editing. A comment version is not automatically a whole-page generation.

Invalidation can be delayed, so A10’s five-second bound also requires absolute expiry. Derive valid_until from the authoritative query’s start, not a delayed fill, and check before response with clock and output margins. Expired slow-query results are neither cached nor sent. Old pre-deletion snapshots cannot renew forever even when invalidation lags; monitor actual withdrawal delay.

Five seconds bounds the server’s last permitted send of stale bodies. Already delivered content needs client invalidation or revalidation; offline copies are outside server control. Immediate post-commit withdrawal requires synchronous visibility validation or a stronger protocol, adding latency and dependencies. This design allows bounded propagation, fails when freshness cannot be verified, and treats stale counts differently from expired bodies.

Deleting a root retains a bodyless tombstone and permits previously visible replies beneath it. Child deletion does not synchronously cascade to all descendants. Hiding an entire thread instead requires root-state checks and a thread generation, changing queries and keys. Remove private author fields and withdrawn quote summaries too. An edited v9 remains hidden under this chapter’s policy until approved.
