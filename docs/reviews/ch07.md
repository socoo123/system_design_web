## Technical corrections and contracts

| Finding | Change / evidence |
|---|---|
| An occasional last snapshot and an unspecified 30 s lease leave restart/pause/reuse conditions implicit | Specified irrevocable committed timestamp windows `[L,H)`, persisted generation/high watermark, row-lock claims and extensions. Each new boot burns the old grant; ambiguous replies are burned. H is explicitly exclusive. |
| Registry expiry or a local clock check cannot physically stop a paused old process | Old and new generations have disjoint numeric timestamp domains. Delayed old IDs may still arrive, but cannot collide with the new window. No downstream fencing or global response order is claimed. |
| Replaying an idempotently recovered old grant into reset sequence state can duplicate IDs | No restart replay is permitted. One grant has one live consumer; cloning state/grants is excluded. Java deliberately demonstrates unsafe replay colliding before exercising fresh-window recovery. |
| Zero sign bit does not imply a positive value | All-zero tuple is 0. The executable reserves timestamp 0 and accepts only `1≤L<H≤2^41`; maximum legal tuple is verified as `Long.MAX_VALUE`. |
| Local synchronization is not distributed worker ownership | Java protects only one generator object. Window/Registry persistence is an explicit prerequisite, specified separately in pseudocode. The example implements a fixed grant, not the renewal protocol or DB. |
| A 5 ms wait policy can be mistaken for an end-to-end response bound | Budget starts inside the local lock; scheduler pauses and lock queues are outside that latency guarantee. Timeout/large rollback/out-of-window permanently halt this object; recovery obtains a fresh grant. |
| Segment RETURNING and commit confirmation can be conflated | PostgreSQL transaction returns post-update bounds but the allocator installs them only after confirmed COMMIT. Unknown outcomes burn the result, never decrement the watermark. Stale replica promotion is explicitly unsafe. |
| Outage sizing used normal per-instance traffic only | Retained 1100/5000=0.22 s, added survivor load 1100/10000=0.11 s. In-flight next range gives 0.02/0.01 s. A 60 s target needs 300k/600k committed IDs plus burst headroom. |
| Unique primary keys are insufficient for business idempotency | Explained UNIQUE(caller,key), request digest checks and original-ID lookup; order and idempotency records commit together. |

The time-window protocol is an explicitly labelled teaching design. It requires durable single-authority allocation, no rollback of confirmed state during failover, trusted validated worker identities, single-consumer grants and no process-state cloning. Timestamp windows sacrifice availability after repeated boots or clock jumps. They are not real-time leases. SQL/high-watermark persistence is not implemented by the Java example.

## Primary-source verification

Actually opened the sources in the browsing tool on 2026-10-22 and checked the indicated source sections. All numerical load/threshold examples are chapter assumptions, not quoted production claims.

1. [Twitter historical IdWorker at b3f6a3c](https://github.com/twitter-archive/snowflake/blob/b3f6a3c6ca8e1b6847baa6ff42bf72201e2c2231/src/main/scala/com/twitter/service/snowflake/IdWorker.scala): fields 5+5+12, shifts22/17/12, synchronized nextId, immediate rollback exception, tilNextMillis strictly greater; constructor validates worker range but does not register ownership.
2. [Meituan Leaf 2017](https://tech.meituan.com/2017/04/21/mt-leaf.html): segment reservation and two-buffer mechanism; persistent sequential worker allocation. Did not inherit the old article’s overbroad UUID/database recommendation.
3. [Meituan Leaf 2019](https://tech.meituan.com/2019/03/07/open-source-project-leaf.html): SQL update/select/commit; two-buffer section explicitly bounds outage tolerance by a buffer’s consumption period; dynamic-step section `Q*T=L` and traffic-growth limitation.
4. [RFC9562 §§5.4,5.7](https://www.rfc-editor.org/rfc/rfc9562.html): 128-bit UUID, 122 random v4 bits, high48 Unix-millisecond v7 bits with remaining random/optional monotonic fields; no strict cross-process global ordering claim.
5. [MySQL8.4 clustered/secondary indexes](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html): secondary records carry primary-key columns; 3.2 GB is independently calculated raw payload only.
6. [RFC8259 §6](https://www.rfc-editor.org/rfc/rfc8259.html#section-6): interoperable integer range ±(2^53−1); supports decimal-string API representation.
7. [Flickr Ticket servers](https://code.flickr.net/2010/02/08/ticket-servers-distributed-unique-primary-keys-on-the-cheap/): SPOFs section specifies two servers, odd/even allocation, increment2/offset1,2.
8. [PostgreSQL17 UPDATE](https://www.postgresql.org/docs/17/sql-update.html) and [row-level locks](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS): RETURNING uses updated values, UPDATE writers conflict, FOR UPDATE blocks modification until transaction end. This supports the stated atomic boundary, not untested failover configuration.
